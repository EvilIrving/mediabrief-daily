Cat Wu：我觉得最难的是把握"恰到好处的 AGI 信念"。为一个超强的 AGI 模型做产品很容易，难的是针对当下的模型，想清楚怎么把它的能力最大限度地激发出来。

Lenny：你觉得 PM 需要培养哪些新兴技能？

Cat Wu：归根结底还是产品品味。写代码变得越来越便宜，更有价值的就变成了决定写什么。

Lenny：今天的嘉宾是 Cat Wu，Anthropic 的 Claude Code 和 Cowork 产品负责人。Cat 身处 AI、产品和开发领域一切变革的中心，她和她的团队正在打造的产品，正是最深刻地改变我们所有人做产品方式的那个。她满是洞见、智慧和经验，这一期千万不能错过。好，下面有请 Cat Wu。Cat，欢迎来到播客。

Lenny：我有一大堆问题，特别高兴你能来。我想先从了解你的角色开始。你和 Boris 一起工作——大家都知道 Boris，他那期是我播客里最受欢迎的一期，没压力哈。他创造了 Claude Code，带领工程团队，每天用手机提交无数个 PR，我都不知道现在数字是多少了。我觉得大家没有充分认识到你在 Claude Code、Cowork 以及你们做的所有东西的成功里所起的作用。帮我们理解一下你在团队里的角色：你和 Boris 怎么合作，怎么分工，Claude Code 团队里的 PM 是什么样子？

Cat Wu：我觉得能和 Boris 共事非常幸运，他是很棒的思考伙伴。他是技术负责人，也很大程度上是产品的愿景者。他非常擅长定下"三个月、六个月后产品应该是什么样"，也就是这个产品最具 AGI 感的版本是什么。而我的很多工作是想清楚：从我们今天所在的位置，到三到六个月后的那个愿景，路径是什么。我更多的时间花在跨职能协作上，确保市场、销售、财务、算力容量等等团队都认同这个计划，大家朝同一个方向划船；并确保功能一旦就绪，发布时没有任何阻碍。我觉得这在很多方面运作得很好，因为我们俩想法很合拍，但界线其实相当模糊。大概 80% 的事情我们想法一致，然后有 20% 的事情我比他更在意，我就来推动；另有 20% 是他比我更在意的，他就去推动。

Lenny：你在我们开始录之前提到，你一直在面试成百上千的 PM。说真的，要是每次有人找我介绍去 Anthropic 当 PM 我都能拿到一枚五分硬币，我现在的年化收入得有 300 亿了。那里简直是大家最想去工作的地方。所以我能想象你面试了多少 PM。你跟我说，你看到很多人的做法是错的——他们对"成为一个成功的 AI PM 需要什么"的理解是错的。聊聊你看到了什么，以及大家需要明白如今要成功需要什么。

Cat Wu：我觉得在 AI 之前，技术变迁要慢得多，所以你可以按 6 到 12 个月的时间跨度做规划。而且因为功能发布的节奏比较慢，所以会更强调和所有合作团队协调，确保他们发布的功能能为你的功能扫清障碍，因为那时写代码非常昂贵。而现在有了 AI，工程大大加速，模型能力也提升得很快，我们很多产品功能的周期已经从六个月缩短到一个月，有时缩短到一周甚至一天。在这种情况下，我们必须确保产品发布得非常快。这意味着作为 PM，应该少花力气去和合作团队对齐那种跨好几个季度的路线图，而多花力气去想：怎样用最快的方式把东西推出去？怎样在我们的产品矩阵里开辟一个"概念角落"，让工程师或 PM 一有想法，到周末就能送到用户手里？我认为在 AI 原生产品上做得最好的 PM，是那些能想办法缩短从想法到产品真正交到用户手里这段时间的人，同时帮团队定义：我的产品有哪些最重要的任务必须开箱即用。

Lenny：我很喜欢你说的这一点：大家还没意识到自己需要多快，而现在这份工作有多大比例就是推动、帮助团队快速前进。除了能用到最先进的模型之外，你和你的 PM 团队是怎么帮团队跑这么快的？

Cat Wu：我觉得第一件事是设定清晰的目标。因为大模型非常通用，这反而带来了很多模糊性：我们为谁而做、要解决什么问题、最主要的使用场景是什么。所以我认为一个优秀的 PM 能够说：好，我们的核心用户是专业开发者；这个功能要解决的主要问题，可能是权限确认弹窗太多、大家产生了疲劳；使用场景是我们希望企业里的专业开发者能安全地做到零权限弹窗。这其实是一个相当清晰的目标，因为它排除了很多减少权限弹窗的潜在做法，从而让人们用一条提示词就能完成多得多的工作。

第二件很重要的事，是找到一套可重复的功能发布流程。对 Claude Code 来说，我们几乎所有功能都以"研究预览"的形式发布。我们发布时会清楚地打上这个标签，让用户知道：这是一个早期产品，只是一个想法，我们想收集反馈并持续迭代，它不一定会被永久支持。这样做降低了我们发布一个东西的承诺成本，我们一两周就能推出一样东西。

第三件 PM 应该做的事，是帮团队建立一个框架，让大家知道什么时候该拉上跨职能伙伴，以及这些伙伴的预期是什么。比如我们在工程、市场和文档之间有一套非常紧密的流程。当工程师有一个他们认为已经就绪、并且我们内部已经自己用过（dogfood）的功能，他们就把它发到我们常设的发布频道里，然后负责文档的 Sarah、负责产品营销的 Alex，还有 Tak、Lydia 等人就会马上跟进，第二天就能把市场公告做出来。正因为我们有这样一套紧密的流程，任何工程师发布东西的阻力都降低了。PM 就是应该搭建这套机制的角色。

Lenny：PRD 在这里面处于什么位置？你说目标非常重要，要明确成功是什么样、为谁而做。你们现在还写 PRD 吗？还是就几个要点？在 PM 的世界里这件事是怎么演变的？

Cat Wu：我们做两件事。一是我们有非常严格的指标，并且每周和整个团队一起过指标。目的是确保每个人都深入理解我们业务的方方面面：关键目标是什么，趋势如何，是什么在驱动它们。第二件事是我们有一份团队原则清单，其中包括我们的核心用户是谁、为什么他们是核心用户。我们把这些都写清楚，是为了让团队里每个人都觉得自己理解业务是怎么运转的，理解什么对我们重要、我们愿意在哪些方面做取舍。这样大家就能自己做决定，而不会觉得被 PM 或其他相关方卡住。

Lenny：我很喜欢这里面很多内容都在说明：未来我们仍然需要 PM。现在到处都在说为什么还需要 PM，工程师直接构建发布就行了。

Cat Wu：我们其实有时也写 PRD。对于特别模糊的功能，写一页纸说明目标是什么、令人惊喜的使用场景是什么、当前有哪些需要修复的失败模式，确实有帮助。偶尔也有一些项目，尤其是需要大量基础设施、确实要花好几个月的项目，这种情况我们仍然会写 PRD。

Lenny：我想再深挖一下你们为什么能跑这么快。我从没见过像 Anthropic 这样的发布速度。有人做了一个 Anthropic 全公司的发布日历，几乎每天都有一个重大功能或产品。网上有人问：你们刚刚——不是发布，是做出了——一个不可思议的模型 Mythos，因为太强大还处于预览阶段，大家有点害怕它能做什么。你们一直在用它吗？这是你们能跑这么快的原因之一吗？

Cat Wu：我们已经连续好几个季度跑得很快了，所以我觉得不完全是。Mythos 是一个极其强大的模型，我们内部确实在用这些模型，我觉得这让我们的发布速度提高了一点，但我不认为它能解释大部分的提速。我觉得很大程度上是流程和团队预期。我们的流程非常少，我们想清除发布路上的每一道障碍，想确保团队里每一个人都觉得自己有能力在一周之内、有时甚至一天之内，把一个想法变成真正推向世界的东西。

Lenny：哇，既拥有最好的模型，又在这个规模上做产品，这是多大的优势。

Cat Wu：我们非常幸运能用前沿模型工作。

Lenny：天哪，太棒的优势了，造个东西，然后用它，然后加速得更快。有几个支线问题我想顺便聊聊，Anthropic 身上发生的事情太多了，我很好奇你的看法。一个是大约一周前，Claude Code 的全部源代码泄露了，被人放了出去。我想是有人犯了个错。你能说说吗？发生了什么，哪里出了问题？

Cat Wu：我们一看到就立刻调查了，发现这是人为失误造成的。是一个人在和 Claude 一起写 PR，这只是对我们发布软件包方式的一次更新，而且它实际上经过了两层人工审核。所以这是人为失误的结果，我们已经加固了流程，确保以后不再发生。

Cat Wu：我们看到对 Claude 的需求非常大，一直在努力扩展基础设施，同时让我们的 harness 更省 token，让你能用得更多。订阅并不是为第三方产品设计的，它们的使用模式和我们的第一方产品不同。我们花了很多时间想怎样提供最平滑的过渡，所以我很高兴能宣布：每个人在订阅之外都能获得一些额度。但确实，我们不得不做出艰难的决定，优先保障我们的第一方产品和 API，这个决定就是由此而来的。

Cat Wu：我们有几个 PM 团队，我想现在大概有 30 到 40 个 PM。有 Diane 领导的研究 PM 团队，负责理解客户对我们模型的所有反馈，再把这些反馈交给最合适的研究团队去处理，他们也负责统筹模型发布。有 Claude 开发者平台团队，维护 Claude Code 所依赖的 API，他们也发布像 Managed Agents 这样的东西——你可以构建自己的 agent，由我们代为托管。然后是 Claude Code 团队，负责 Claude Code 和 Cowork 两个核心产品。还有企业团队，帮助所有企业客户更容易地采用 Claude Code 和 Cowork，涵盖从成本控制、基于角色的权限控制（RBAC）到安全控制等各方面，确保企业用我们的工具时非常有信心、很放心。另外还有增长团队，负责我们整个产品矩阵的增长。我们和他们在 Claude Code 和 Cowork 的增长上合作非常紧密，我知道他们也和其他团队一起做 CDP 增长，也就是 Claude API 用户的增长。

Lenny：说到增长，你们的增长负责人 Amol 刚上过这个播客，他分享了一个很有意思、很少有人提的观点。大家总觉得未来需要的 PM 会更少——为什么还需要 PM，工程师直接发布就行。他的看法是：正因为工程师跑得太快，PM 和设计师被挤压了，没时间跟上正在发生的一切，每天都有功能上线。所以他认为需要更多的 PM。你怎么看？你觉得 PM 的招聘会增加吗？长期来看 PM 这个职业会怎样？

Cat Wu：我觉得所有角色都在融合。PM 在做一些工程工作，工程师在做 PM 的工作，设计师也在做 PM 并且提交代码。你要么招很多具备出色产品品味的工程师，要么工程师招聘保持不变、多招很多 PM 来帮助引导他们的部分工作。在我们团队，我们相当专注于招聘有出色产品品味的工程师，这样可以减少发布任何产品的额外开销。我们团队里有很多工程师完全能够端到端地做事：从在 Twitter 上看到用户反馈，到周末发布一个产品，几乎不需要产品经理参与。我认为这其实是发布东西最高效的方式。所以我觉得工程师和 PM 有点在重叠，多招哪一种都会带来很大的好处。我觉得产品品味仍然是非常稀缺的技能，只要我们觉得一个人有力地证明了这一点，我们基本上都会招。

Lenny：你的背景是工程，对吧？

Cat Wu：对，我做了很多年工程师，加入 Anthropic 之前很短暂地做过 VC。其实我们团队几乎所有的 PM 要么做过工程师，要么在 Claude Code 上提交过代码。我觉得这是帮助我们和团队建立信任、也让我们跑得快得多的原因之一。而且我们的设计师以前也做过前端工程师。

Lenny：哇。这正是大问题所在，维恩图正在合并。我觉得很多人的大问题是：如果你来自工程、产品或设计，哪种核心技能会最有价值？我能看出在 Anthropic、在 Claude Code，工程非常有价值。我好奇在其他公司，有设计背景转 PM 会不会更有价值，或者纯 PM 出身？

Cat Wu：我还是认为归根结底是产品品味。写代码变得越来越便宜，更有价值的就变成了决定写什么：这个功能正确的用户体验是什么，用户体验它最令人愉悦的方式是什么。我们收到成千上万的 GitHub issue，要求各种各样你能想到的东西，要想清楚哪些值得做、正确的做法是什么，需要很多用心和品味。我觉得这套技能可以来自任何背景，但这是最重要的。至于为什么工程背景特别有用——至少在接下来几个月里——是因为有工程背景的话，你对一件事该有多难有更好的判断，而这往往是你选择做什么的一个因素。如果某样东西很容易做，那与其争论，不如花一个小时直接做出来；但如果某样东西更难做，而你事先就知道，那你就明白，这会让团队花多得多的成本才能把它推出去。这对排优先级有一些帮助。

Lenny：你说"接下来几个月"，是因为模型在接下来几个月可能变得非常好，你可能不再那么需要知道这些？

Cat Wu：我觉得有价值的技能组合变化得相当频繁，所以很难预测几个月以后的事。这与其说是对会发生什么变化的判断，不如说是我认为会发生很大的变化。

Lenny：所以你不是在说等 Mythos 出来一切都会改变，我们完全不需要懂工程了？

Cat Wu：不是，我只是说每隔几个月，编码能力似乎就会有一次大幅提升，进而改变其他哪些角色有价值。我觉得最重要的是具备第一性原理思维：能够弄清技术格局在如何变化、团队真正需要你做什么，然后跳进去把那个缺口补上。因为工作正变得越来越没有固定形态，这意味着一个优秀的 PM 能够看清所有的缺口在哪里。

Cat Wu：找出其中优先级最高的，然后想清楚：我要怎么学会这套技能，或者我已有的哪些技能可以用来应对这个挑战。所以我觉得当下的环境看重的是能身兼数职、能随时切换角色，并且对自己做什么工作毫无身段、只求帮团队跑得更快的人。

Lenny：我很喜欢这个回答。我一直在问处于你这种位置的人——站在 AI 能力最前沿、用最新工具做产品的人——一个问题：在我们到达超级智能之前，人类大脑在哪些地方还会持续有用、不可或缺？我从你这里听到的，基本上是挑选要做的事、知道市场往哪走、想清楚优先级，然后判断你做出来的东西是否好、是否正确，并至少以某个早期版本把它推出去。这样理解对吗？还有没有别的、至少在接下来几个月里人脑仍然有用的地方？

Cat Wu：我觉得人类仍然提供一种模型所不具备的常识。任何一次产品发布都有上千个变动的环节，有些很小，但总有很多事情可能出错。我觉得模型并不总能很好地把握：所有的相关方都有谁，他们之间是什么关系，各自有什么偏好，用什么渠道和他们沟通才能让他们一直站在你这边。我觉得很多这种更隐性的常识、类似情商的知识仍然非常有价值。当然我们希望模型在这方面变得更好，我也相信它们会，但目前我觉得仍有差距。

Lenny：作为一个人，身处如此持续的变化之中，你是怎么应对的？就像身处龙卷风内部——也许风眼里很平静——你是怎么跟上正在发生的一切，又是怎么在我们经历的这一切疯狂中保持理智的？

Cat Wu：我觉得我们团队的人都是愿意拥抱混乱的人。我们尽量笑着面对每一个挑战，因为总有太多事情在发生，总有太多风险和棘手的局面，如果你对任何事都压力太大，你就会倦怠。所以我们非常看重这样的人：他们看着一个挑战会说，哦，这会很难，但我很兴奋去解决它，我会尽我所能做到最好；我知道我不会完美，但我晚上能安心入睡，因为我知道我已经尽力了。

Lenny：这对"未来哪些技能重要"是个很有意思的回答。我忘了是谁说的了，可能是 Ben Mann：现在是这个世界最"正常"的时候了，以后只会越来越不正常。

Cat Wu：是的，肯定会越来越难。我感觉很多周都是这样：周日晚上出了个 P0，到周一出了个 P00，到周一下午又出了个 P000，然后你会想，哇，我们周日怎么会那么担心那个 P0？但我觉得你必须承认，你能做的就那么多，你需要睡好觉，第二天才能做出好的决定，然后要无情地排定时间的优先级：最需要做对的是什么，并且接受放手一些事情。我们发布的一些产品没有我希望的那么精致，但我们的首要目标是赋能专业开发者。如果一个产品不够成功，只要它没有阻碍核心使用场景，那就没关系，因为我们会听到反馈，在下一个版本里修复。发布一个有 bug 的功能，以前是会让我夜不能寐的事，但现在我已经能坦然接受了，因为我知道我们会很快拿到反馈，并在下个版本里修复。

Cat Wu：没错，就是非常技术化的市场推广人员。

Lenny：明白，太好了。所以你是说，这可能是 token 用得第二多的组织。

Cat Wu：是的，而且我们也看到他们在挑战 Cowork 能力的边界。比如，这些人很多都同时负责多个客户，忙的时候一天可能有五到十场客户会面。所以他们经常用 Cowork 做的是：前一天晚上让它总结——明天有哪些客户会议？这个客户都找我要过什么？他们最关心什么？之前会议的待办事项有哪些？然后 Cowork 会整理出一份档案、一份简报，列出他们去下一场会议前应该了解的内容。Cowork 还能调研答案，比如客户问"功能 X 什么时候上线？"，Cowork 可以帮应用 AI 的同事在 Slack 里查到最新的预计时间，加到笔记里，这样在和客户通话时，应用 AI 的同事掌握的就是最新信息。这些都是大家为自己搭建、并分享给团队其他人的工作流。

Lenny：太酷了。最近有一个话题经常出现：token 花费超过了人的薪水，也就是有人用 AI 花的钱比自己挣的还多。Anthropic 内部有没有流传一些数字，比如工程师或 PM 每月、每天花多少 token？

Cat Wu：我们很清楚的是，随着模型变好，大家会把更多任务委托给它，在 Claude Code 和 Cowork 这类工具里花的时间也多得多。所以每当模型有一次跃升，或者产品有一次实质性改进，我们确实看到每位工程师、或者说每位知识工作者的 token 成本都在上升。我觉得它仍然远低于工程师的平均薪水，但我们看到这个比例在随时间上升。

Lenny：这太有意思了。我们聊到你们能用到最前沿的模型，在 Anthropic 工作的另一个优势，我相信是你们基本上有无限的 token，想用多少用多少，对吗？

Cat Wu：我们能用很多 token，但有些人确实会碰到上限。

Lenny：好吧，有上限，好吧，那就到此为止。感觉拥有最先进的模型带来的优势真是太多了，这是一个开始转动起来的、非常有意思的飞轮。

Cat Wu：我觉得我们也非常相信要赋能内部团队尽可能快地构建，同时我们也相信每个人都明白服务这些模型真正要花多少算力容量，我们相信团队会负责任地使用 token。浪费 token 是很被看不起的，但我们确实信任每个人自己去做这个判断。

Lenny：太好了。回到 PM 的角色，我们稍微聊过一些，但我觉得大家会很想听：你认为 PM 需要培养的新兴技能是什么？或者说，如今 AI 公司招 PM 时最看重什么？

Cat Wu：我觉得最难的技能，是能够定义一个月后产品应该是什么样子。在这个时间范围内，模型能做到什么、用户行为会如何变化，都有很大的不确定性。但我觉得有一些规律是最优秀的 PM 能看出来的，基于用户如何在挑战现有产品的极限。最优秀的 PM 能察觉到这些，能定下方向并稳步执行，而且如果模型能力比他们原先预期的好得多或差得多，也能调整路线。我觉得最难的是把握"恰到好处的 AGI 信念"，因为每个人都能看到那样一个未来：模型极其聪明，几乎什么都能做。在那种情况下，你其实不需要那么复杂的产品，你只需要再次回到一个文本框，告诉模型你想要什么，它聪明到能自己加上完成任务所需的任何工具或集成，它知道自己什么时候不确定，能提出澄清问题。为超强 AGI 模型做产品是相当容易的。我觉得难的是针对当下的模型，想清楚怎么最大限度地激发它的能力，怎么帮用户走上那条"黄金路径"，怎么引导用户利用模型的长处、弥补它的短处。这项技能相当稀缺。

Lenny：那怎么培养这项技能？基本上就是理解每个模型的极限吗？你说到品味——对模型能做什么、擅长和不擅长什么、哪里发生了变化，具备一种品味？

Cat Wu：我觉得就是花大量时间和模型对话、使用模型。我很喜欢做的一件事，是让模型反思它自己的行为。有时我注意到模型做了出乎意料的事，比如有些情况下模型改了前端，跑了测试，却没有真正去操作 UI。这时让模型反思自己为什么这么做，其实相当有用。有时它会说：嘿，系统提示词里有些地方让人困惑；或者，我没意识到前端验证是这个任务的一部分；或者，嘿，我把验证委托给了这个子 agent，子 agent 没做测试，而我没有检查它的工作。很多时候，只要对模型为什么做出那些决定保持好奇，就能看出是什么误导了它，然后你就可以修改 harness 来弥补差距。

另一件有帮助的事，是弄清楚哪些用户是你最信任的、能对模型给出准确反馈的人。通常有那么一小撮人，比别人更擅长说清楚是什么让某个模型、或某个模型加 harness 的组合变好。会给你反馈的人很多，但不是每个人的反馈都同样有分量。所以找到那样一个你信任的五人左右的小组，对快速拿到反馈非常重要。

我觉得第三件有用、但不是每个人都喜欢做的事，是构建评测（eval）。你不需要建几百个评测才有用，只建 10 个优秀的评测，就对帮助团队量化目标是什么、进展到哪了、还缺什么非常重要。所以我觉得评测是一件被低估的事，应该有更多 PM、更多工程师去做。

Lenny：我们聊过很多次评测，有一种趋势说未来的产品管理就是写评测，因为本质上就是"成功是什么样？好，我来把它具体定义出来，然后我们就知道了"。你会说你有多少时间花在写评测上？

Cat Wu：我觉得评测的重要性有点取决于你在做的功能，或者你要解决的问题。我们团队有很多人确实花大量时间做评测，我们有一个小组和研究团队紧密合作，更精确地理解 Claude Code 的行为、最大的改进空间在哪里，并尝试相当具体地衡量这些。我个人会在某个功能需要更多产品定义时跳进去做评测，产出通常是：这是我做的五个评测，这是运行方法，这些成功了、这些没成功，这是我用来提高成功率的提示词。不过这差别很大，取决于具体功能，不是每个功能都需要，但我觉得像记忆这样的功能能从中受益很多。

Lenny：你说有些人非常擅长评估模型，这点太有意思了，几乎就像是一种"人工评测"：他们知道模型在哪里突出、在哪里可能欠缺。有没有哪位你特别想点名表扬、非常擅长这件事的？

Cat Wu：我觉得有两类人在这方面非常厉害。一位是 Amanda，她负责塑造 Claude 的性格。这是一个非常难的角色，因为这个任务太模糊了。连编码都更容易，因为你能验证是否成功；而塑造性格需要对 Claude 应该是谁有非常强的信念。我觉得她有一种不可思议的能力，不仅能塑造这个性格，还能清楚地阐述目标是什么、性格是什么、什么是成功的、什么不是。

另一群我非常信任的人就是 Claude Code 团队。我们经常一起吃团队午餐，每当我们在测试一个新模型，获得反馈最快的方式之一，就是在团队午餐上挨个问每个人：嘿，你对这个模型什么感觉？我们经常会得到这样的反馈：这个模型没有充分解释它的思路，太生硬了；或者，嘿，这个模型特别爱写一大堆记忆，但我们不确定这些记忆质量高不高；或者有人会注意到，这个模型很爱自我测试，这很好；或者这个模型自我测试得不够。这些反馈决定了我们去看哪些数据来验证：这是否是一个更大范围的规律。我们有海量数据，但很难从中提取洞见，所以这群人的反馈帮助我们确定要检验哪些假设，然后我们就能提取数据去检验。

Lenny：你说到 Claude 的性格这一点。我请过联合创始人 Ben Mann 上播客，他谈到 Claude 的性格、Claude 的"宪法"是 Claude 非常重要的一部分。我事后才意识到，比如 OpenClaw 这件事，大家难过的原因之一其实就是性格——因为 Claude 的性格非常好、有趣、有意思，不像其他模型。他的说法是：性格正是让 Claude 在这么多事情上都很出色的原因。它感觉像是个微不足道的小事——好吧，它会很幽默很有趣、说话很好玩——但它其实是 Claude 成功的核心。关于大家可能不理解的、为什么你说的性格如此关键，你有什么可以分享的吗？

Cat Wu：当你回想所有共事过的人，总有一些人让你觉得：我真的很喜欢他们的能量，很喜欢他们的气场。而当人们谈到 Claude 和 Claude Code，大家最常提到的就是这一点：他们真的很喜欢 Claude 轻松有趣，同时在你的任务上又极其能干。大家真的很喜欢 Claude 不端架子。如果你告诉它"嘿，你这件事做错了"，它是真心地抱歉，会说"哦糟糕，谢谢你告诉我，我来修，我们一起来"。它也非常积极，如果你觉得"哦，这是个无法逾越的任务，我不知道从哪开始"，Claude 会说"没事没事，我觉得我们应该按这几步来，要我帮你开始吗？"我觉得一个好同事的部分特质就在于这种积极性、这种行动导向，以及能给你诚实的反馈，而不是对你说的每件事都附和。所以我们努力把这些注入到 Claude 里，因为我们认为这会让和它一起工作愉快得多。

Lenny：有件事我想回过头来聊。你说新模型出来时，你们经常得回头重新审视已经做好的东西。这太有意思了，也可能很让人沮丧："该死，又得重做这个东西，我得重新想。"聊聊你们需要多频繁地回头看——新模型一来，就得说"好，我们得重新审视几个月前发布的这个产品"。

Cat Wu：新模型带来的很多改动，其实是移除不再需要的功能。很多时候我们给产品加功能，是作为模型的"拐杖"，因为它自己不会自然地去做。经典的例子是待办清单（to-do list）。我们刚发布 Claude Code 的时候，大家会让它做大型重构，Claude Code 会说："好的，我需要修改这 20 个调用点。"然后它去改了 5 个就停了。于是我们想：怎样逼它记得把这 20 个全改完？我们团队的 Sid 说：好，我们想想人会怎么做。人会把需要改的所有东西列个清单，就像在 VS Code 里你会查出所有调用点，它们列在左侧，然后你一个一个过、全部替换。我们怎样给它一个这样的工具来调用？于是他加了待办清单。我们发现有了它，Claude 确实能把这 20 个调用点全改完。但到了 Opus 4 及之后的模型，我们意识到不需要再强迫它用待办清单了，它会自然地自己去用。对早期模型，我们得提醒它："嘿，待办清单上的事都做完了吗？没做完清单上的所有事之前不能结束。"而对后来的模型，不用提示，它就会自然地把清单上的事都做完。现在待办清单作为用户来说还是挺有用的，因为你能更清楚地看到 Claude 在做什么；但说实话，它现在已经是产品里被大大淡化的一部分，模型可能用它，也可能不用，它对模型完成全面的修改已经真的没必要了。

Lenny：我忘了是谁在播客上说过，模型会把你的 harness 当早餐吃掉。我听到的基本上就是：随着时间推移，你们会移除那些当初因为模型不按你想要的方式运作而不得不加在它之上的东西；随着模型变得更聪明，让它做你想做的事就变得越来越简单。

Cat Wu：是的，每次模型变聪明，我们都能移除很多提示词层面的干预。我们其实每次发布模型时都这么做：把整个系统提示词通读一遍，针对每一部分反思——模型还真的需要这个提醒吗？如果不需要，我们就把它删掉。

Cat Wu：不过新模型解锁的最激动人心的东西，是全新的功能。有很多功能我们在之前的模型上测试过，但准确率不够高，我们不想发布。一个例子是代码审查。我们尝试做过好几次代码审查产品，过去也发布过简单版本，也就是 /code-review 命令。直到最新的这些模型，我们才觉得：好，这个代码审查已经好到我们的工程团队在合并 PR 之前都依赖它通过。我们一直梦想 Claude 能成为一个可靠的代码审查者，让我们有信心它能抓住大部分 bug。直到 Opus 4.5、4.6 以及 Sonnet 4.6，我们才觉得：好，我们现在能同时运行多个代码审查 agent，遍历整个代码库，综合出一组真实的问题，工程师需要在合并前解决。这是最新模型解锁的一项新能力。

Lenny：这是这个播客上非常常见的另一个趋势：去做一个在未来六个月内可能变得可行的东西，处在"勉强能用"的边缘，然后模型会追上来，它会变成一个了不起的产品，而你会领先所有人。

Cat Wu：是的，正是如此。做一些还不一定能用的产品相当重要，这样你就知道这个产品要能用还缺什么，然后有了最新模型，你就可以直接把它换进你已经做好的原型里，看看这个新模型能不能补上那个差距。

Lenny：关于 Claude Code 和 Cowork 的走向、它们的愿景，你能谈多少？我想你不想透露太多目标，但感觉上面加了这么多很棒的功能——从手机上调度控制、各种移动端应用等等。怎样理解所有这些东西的长期愿景？

Cat Wu：我们是用"积木"的方式来思考这件事的。对 Claude Code 和 Cowork 来说，最核心的积木是让单个任务成功。你想产出某样东西，给它一个清晰的提示描述，它能不能稳定地产出可接受的结果，让你可以合并，或者分享给同事、外部受众？所以任务是核心积木。随着模型变聪明，任务成功率高了很多，然后我们看到大家开始同时做多个任务。多开 Claude 在 2025 年底是一件大事，之后只增不减。所以我们这样看：很好，一个任务能行了，现在你可以同时做六个任务。随着模型变得更聪明，我们的推演是：接下来，也许你会同时跑 50 个、甚至几百个 Claude。那我们需要构建什么样的基础设施来支持这一点？到那时你大概不会再把所有东西都在本地机器上跑了，内存根本不够。所以我们在思考：怎样让你更容易管理所有这些——它们大概会在远端运行；怎样构建界面，让你作为人知道哪些任务需要你去看；怎样确保 agent 充分验证了自己的工作，这样当你看一个任务、它说完成了，你能很快核实并完全相信它确实按你的要求完成了；以及怎样确保这个过程能自我改进，这样当你看到一个没做到你满意的任务，你可以给它反馈，模型在未来每一次运行中都会纳入这个反馈，从此不再犯这个错。这就是我们正带着用户一起走的演进路径。

Lenny：有很多人在听，很多产品经理、很多创始人、很多其他跨职能的人。大家对自己的角色、职业的未来有很多担忧。你有什么建议，让大家不只是在这场向高度 AI 驱动世界的转变中生存下来，而是真正成功、在这个未来里茁壮成长？大家需要听到什么、需要做什么？

Cat Wu：我觉得 AI 给了每个人比以往多得多的杠杆。所以我会推动你：每当你意识到自己在多次重复做某个手工任务时，就想想怎么用 Claude Code、Cowork 或其他 AI 工具把它自动化。大多数人的工作里都有自己特别喜欢的创造性部分，也有特别讨厌的繁琐部分。我觉得 AI 的美妙之处在于它能替你做那些繁琐的部分，它能从你每一次手工做那个任务中学习、泛化，然后自动执行，让你能专注于创造性的部分，这意味着你能做到比以前多得多的事。所以我对大家最直接的建议是：找出那些可以交给 Claude 的重复性部分，不断迭代这些自动化，直到成功率非常高；然后专注于：你还能为你的团队、你的产品、你的公司多做些什么，那些大家到目前为止都没精力去接的事；或者那个你一直觉得公司应该做、但你从来没精力去做的心头项目。如果 AI 能帮你处理那些繁杂的工作，你就多出了以前可能没有的 20% 时间。所以我的建议是：拥抱这些工具，把你不感兴趣的工作交出去，想清楚它怎样能让你加速，这样你就能做多得多的事。

Lenny：你刚才分享的内容里有一点很核心，我完全同意，那就是找到可以用 AI 解决的问题。这些工具有这么大的潜力，而对很多人来说难点就在于：我到底该做什么？你这里说的是：留意你一直在做、可以自动化的事情；留意那些一直在脑子里转、但你没时间去做的想法。基本上，核心建议就是为自己解决一个问题。

Cat Wu：没错。我还想推动听众专注于把你的自动化从"这是个很酷的概念"推进到"嘿，这真的 100% 都能用"。有时我看到用户尝试自动化某件事，做到 90%、95% 的准确率就放弃了。如果一个自动化不能 100% 都能用，它就不算真正的自动化。而最后那 5% 到 10% 确实更花时间，而且构建自动化本身往往比你自己动手做慢得多。我鼓励听众投入时间，圈定一个你真的想做到 100% 的自动化，下苦功教会 Claude 你的偏好，给它反馈，让它提升技能，直到达到 100%，然后你才能真正依赖它。一个 95% 的自动化没有多大价值。

Lenny：我在这方面太有罪了，这对我是非常好的建议。

Cat Wu：我也有这个毛病。我一直在教 Cowork 帮我把 Gmail 清到零未读，非常耗时间，而且你大概也意识到了，它肯定还没到位。

Lenny：是啊，好笑的是我脑子里想的正是这个。我设了一个工作流：我收到的每封邮件，它都会找出像垃圾邮件的那些——就是那种"嘿，我能上你的播客吗""这个怎么样"之类，我没时间处理的东西——然后把它们归到一个叫"spammy"的文件夹里。它 95% 都很好，但然后就会出现"哦，我错过了一封邮件"，因为我去那里翻了才发现。所以这对我是很好的督促，我要去改进它，把它做到完美。

Cat Wu：我们也在努力让定制这些命令的流程变得容易得多。因为现在我觉得你需要知道太多概念：你得知道要定义一个 skill，得知道要用这个 skill 并给它反馈，然后得知道要让 Cowork 根据你给的所有反馈更新这个 skill，然后你还得知道去哪里读这个 skill，确认反馈是按你想要的方式被纳入的。让这个流程真正顺畅、不再痛苦，也是我们的工作。

Lenny：太棒了。Cat，在进入非常刺激的快问快答环节之前，还有什么你想分享、想留给听众、或者想再强调的我们还没聊到的东西吗？

Cat Wu："直接去做"（just do things）。我觉得第一性原理思维很有价值。如果你知道自己在优化什么，并且有很强的第一性原理，你通常就能推导出正确的行动方向，并能清楚地向所有相关方阐述，然后你就应该直接去做。我觉得"职位"是虚构的。如果你理解了约束条件，你就能想清楚你能做什么，然后尽快去尝试，从错误中学习，如果做错了就道歉或者修正。你就是可以直接去做事——不管是谁说的这句话。我觉得这样告诉别人其实是一种解放。在很多公司里，角色定义得非常严格：这是 PM 做的，这是设计师做的，这是工程师做的；甚至团队范围也定义得很死板：这一块代码库我们碰，那一块我们不许碰。我觉得"直接去做"让人们觉得有权做这些决定，有权跨越团队边界，只为把事情做成。
