## 第一幕

### 配方与蓝图

标签和函数调用有什么区别？

这是一个标签：

`<p>Hello</p>`
这是一个函数调用：

`alert('Hello');`
一个区别是，`<` 和 `>` 又硬又尖，而 `(` 和 `)` 又软又圆。但我说的不是这个。这些只是视觉上的区别。我想问的是：它们的工作方式、它们的含义、我们对它们的期待，有什么不同？

当然，如果不说明用的是哪种语言，*标签*或*函数调用*本身并没有特定的含义。比如，JavaScript 的函数调用和 Haskell 的函数调用行为可能不同；HTML 标签和 ColdFusion 标签的行为也可能不同。尽管如此，正*因为*我们熟悉它们在流行语言中的工作方式，我们对标签或函数调用还是会有一些*预期*。尖尖的 `<` 和 `>` 携带着一组联想和直觉，柔软的 `(` 和 `)` 也是如此。我想深入挖掘这些直觉。

我们先看看 `alert('Hello')` 和 `<p>Hello</p>` 有什么共同点：

1.   **我们通过名字来引用一个函数或一个标签。** 按照惯例，函数调用通常以动词开头（`createElement`、`printMoney`、`querySelectorAll`），而标签通常用名词命名（比如 `p` 代表 *paragraph*，段落）。这不是硬性规定（`alert` 既是名词也是动词；`b` 代表 *bold*，粗体），但多数情况下确实如此。（为什么会这样？）
2.   **我们可以向函数或标签传递信息。** 前面，我们向标签和函数传递了一段文本（`'Hello'`）。但我们并不局限于传递单个字符串。在 JavaScript 函数调用中，我们可以传递多个参数，包括字符串、数字、布尔值、对象等等。在 HTML 标签中，我们可以传递多个属性，但它们的值不能是对象或其他富数据结构——这相当受限。好在 JSX 中的标签（以及许多基于 HTML 的模板语言）允许我们传递对象和其他任何富值。
3.   **函数调用和标签都可以深度嵌套。** 例如，我们可以写 `alert('Hello, ' + prompt('Who are you?'))` 来表达这两个不同函数调用之间的关系：内层 `prompt` 调用的结果与一个字符串拼接，然后传给外层的 `alert` 调用。（如果你不确定它做什么，可以在控制台里试一试。）虽然嵌套在函数调用中相当常见，但对标签来说，嵌套才*真正*是核心玩法。你几乎看不到一个标签完全孤零零地存在、不被其他标签包围。（为什么会这样？）

显然，函数调用和标签非常相似。它们让我们向一个有名字的东西传递一些信息，并且在需要时，让我们通过进一步嵌套来细化（向某个有名字的东西传递更多信息（想嵌套多深就嵌套多深（耶！）））

我们也开始隐约看到它们之间的根本区别。首先，函数调用倾向于是动词，而标签倾向于是名词。其次，你遇到深度嵌套标签的频率要高于深度嵌套的函数调用。

这是怎么回事？

先说后者。为什么标签总喜欢粘在一起？标签是不是天生就倾向于被其他标签吸引，直到它们——*咔哒！*——扣在一起？也许这些尖尖的家伙真的渴望连接？也许吧，但想想这一点：也许我们*喜欢*用标签来表达深度嵌套的结构，是因为我们能看到每个标签的 `</end>`，而不必去猜哪个 `)` 在闭合什么。

不是标签导致了深度嵌套——而是我们*选择*用标签*来做*深度嵌套。（回想一下，尽管 JSX 在头一两年几乎遭到一致的批评，JavaScript 社区最终还是广泛采用了它。嵌套标签是很难放弃的！）

好，假设我们*更喜欢*用标签来嵌套。但为什么标签倾向于是名词而不是动词？这是巧合，还是也有更深层的原因？

这更像是一种猜想，但我认为这是因为名词比动词更容易分解。名词描述的是*事物*，而事物往往可以纯粹地被描述为其他事物的组合。例如，一栋楼由楼层组成，楼层由房间组成，房间由人组成，而人由水组成。注意，这种描述是*永恒的（timeless）*——不是说它是经典，而是说它描述的是时间中的一个快照，就像电影中的一帧，或者像一张蓝图。你可以把时间从等式中去掉，它仍然是一个相当有用的描述。

而动词往往描述的是*随着*时间发生的*过程*——它们是*有时间性的*！想想一份烹饪配方：“把煎锅加热，放上黄油，等黄油融化，现在把鸡蛋倒进去。”虽然这里仍然有组合的机会（*怎么*打一个鸡蛋？），但顺序在这里至关重要！你需要时刻清楚哪一步先发生、哪一步接着发生，以及在步骤之间你要做出什么样的决定。与蓝图不同，配方有它的顺序，也有某种紧迫感。

那么，这和标签与函数调用有什么关系呢？

配方规定了一系列要按顺序执行的步骤。它由动词组成，但很少有大量嵌套。（事实上，嵌套可能只会让顺序变得模糊。）每一步都可能改变某些东西，或依赖于之前的步骤，因此必须严格按照写下的顺序、从上到下执行配方。这些配方，也就是所谓的*命令式*程序，是用函数调用来写的：

```
const eggs = crackEggs();
heat(fryingPan);
put(fryingPan, butter);
await delay(30000);
put(fryingPan, eggs);
```

而蓝图描述的是一个事物由哪些名词组成。它不规定特定的操作顺序——它只描述整体是如何拆分成部分的。这就是为什么这些蓝图，也就是所谓的*声明式*程序，自然会变得深度嵌套，因此用标签来写更方便：

```
<Building>
  <Roof />
  <Floor>
    <Room />
    <Room>
      <Person name="Alice" />
      <Person name="Bob" />
    </Room>
  </Floor>
  <Basement />
</Building>
```

许多现实中的程序结合了这两种技巧。例如，一个典型的 React 组件结合了一些命令式的配方（比如事件处理函数中的一系列函数调用）和一些声明式的蓝图（比如返回的 JSX 标签）。

然而，归根结底，我们的程序必须*做*点什么。配方是可以直接执行的——它们对下一步该做什么毫无歧义。做这一步，再做这一步，再做这一步，然后完成。而蓝图就只是蓝图——一个建造某物的详细计划。在某个配方真正决定去建造蓝图所描述的东西之前，它不会变成现实。（例如，React 会构建你的 JSX 蓝图所描述的 DOM。）

某种意义上，蓝图几乎就是一份配方，但它更被动、更惰性，对未来的解释保持开放。它是一份*把时间本身*从等式中剥离出去的配方。当你去掉时间，剩下的就只有结构——事物、名词、标签。

蓝图是一份*潜在的*配方。它是一个计划——它可能发生，也可能不会发生，取决于最终是否有某个配方去执行这个计划。

既然蓝图由标签组成，配方由函数调用组成，如果我们说蓝图是*潜在的*配方，那就可以推出……标签是*潜在的*函数调用。

等等，什么？

### Await 与 RPC

假设你想调用一个函数。这很简单：

`alert('Hello');`
你可以相当确定，一旦这个函数执行完毕，下一行就会立即运行。特别是，你可以拿到一个函数调用的*结果*，然后立即把它用于下一个函数调用，这一点非常棒：

```
const name = prompt('Who are you?');
alert('Hello, ' + name);
console.log('Done.');
```

然而，假设你想调用的函数在另一台计算机上。那就扫兴了，对吧？但这种事确实会发生。

处理这种情况的标准方法是发起某种网络调用。在这方面我们已经有很多现成的思路，比如 HTTP，甚至更底层的东西。我们大多数人整个职业生涯都没学过字节是怎么在海底电缆中传输的。真是了不起。

当然，问题在于，在网络调用结束之前，我们的程序无法继续。如果不和另一台计算机通信就无法知道这个人的 `name`，我们就需要在 `alert` 调用之前“暂停”代码的执行。

假设你是第一个遇到这个问题的人。

你可能会想到的一个办法是发明一个接收函数的 `callNetwork` API：

```
callNetwork('https://another-computer/?fn=prompt&args=Who+are+you?', (response) => {
  const name = response;
  alert('Hello, ' + name);
  console.log('Done.');
});
```

一旦响应到达，你的 `callNetwork` API 会用 `response` 调用传入的函数，此时剩下的代码会照常运行。

作为第一个想法，这实在不算坏。但也算不上好：

1.   **网络调用把我们的代码搅乱了。** 以前，代码按从上到下的顺序执行，但现在有了一个转折。从概念上讲，`alert('Hello' + name)` 是我们要表达的配方中“接下来发生的事”。然而，我们不得不把它放到 `callNetwork` 调用*里面*，这样计算机才知道要“等待”它。
2.   **我们切断了两段代码之间的联系。** 通常，当你想调用一个函数时，你直接*调用*它就行。前提是它在同一个文件里。如果它在另一个文件里，你就在那边 `export` 它，然后在这边 `import` 它。但在这种情况下，我们面对的不再是函数调用——而是 HTTP 调用。在和 REST API 打了几十年交道之后，这可能很难看出来，但在这种转换中我们其实丢掉了某种本质的东西。首先，它不会被类型检查！那个端点可能根本不存在。你不能 Command+点击进入那个调用，看看函数在哪里定义、做了什么。原本在被调用的函数和调用它的地方之间存在一种直接而真切的联系，但现在没有了——不是因为你*想要*引入某种漂亮的概念分离，而是因为你没有任何其他*手段*来保持这种联系。

如果我们设想 `alert` 函数*也*在另一台计算机上（也许是另一台不同的计算机），问题就更容易看清了。现在代码变成了：

```
callNetwork('https://another-computer/?fn=prompt&args=Who+are+you?', (response) => {
  const name = response;
  callNetwork('https://yet-another-computer/?fn=alert&args=Hello,+' + name, () => {
    console.log('Done.');
  });
});
```

那么，你如何解决这两个问题呢？

你想出了两个点子。

为了解决第一个问题（代码的“纠缠”），你引入了一个叫 `async` 函数的新概念。`async` 函数不保证在一步之内执行完——相反，它被预期可能会“暂停”执行（比如由于网络调用）。既然它可能暂停，*调用方*代码就需要“`await`”这个 async 函数调用，以表明它不会对这种暂停感到意外。这意味着*调用方*在某个时刻也会暂停，因此它*也*需要把自己标记为 `async`。于是 `async` 和 `await` 会沿着调用链向上传播，这样就没有人会对自己的代码“暂停”感到意外。至少这是你的想法。

这一点也不坏——事实上，它的某种变体几乎已经是新编程语言的标配。你不再需要[说服别人](https://tirania.org/blog/archive/2013/Aug-15.html)它是好东西了。

代码就变成了：

```
const name = await callNetwork('https://another-computer/fn=prompt&args=Who+are+you?');
await callNetwork('https://yet-another-computer/fn=alert&args=Hello,+' + name);
console.log('Done.');
```

现在你把目光投向第二个问题。你想做的是在一台计算机上调用一个叫 `prompt` 的函数，在另一台计算机上调用一个叫 `alert` 的函数。假设这些函数确实定义在你的代码库里。

如果你能真的从另一台计算机上 *import* 它们呢？

```
import { prompt } from 'another-computer';
import { alert } from 'yet-another-computer';
 
const name = await prompt('Who are you?');
await alert('Hello, ' + name);
console.log('Done.');
```

等等，但这并不能真正解决上面说的问题。比如，TypeScript 不会知道 `'another-computer'` 是什么。那么，假设你可以从这些函数在代码库中实际所在的位置导入它们：

```
import { prompt, alert } from './stuff';
 
const name = await prompt('Who are you?');
await alert('Hello, ' + name);
console.log('Done.');
```

可是等等，这只是一个普通的导入。它会把它们带进*这台*计算机上的程序，而你想要的是把它们部署到*另一台*计算机上。你希望它们在幕后通过 HTTP 跨越网络边界被远程调用，这一事实需要在代码中的某个地方表达出来。

我们来发明一种特殊语法来表达这一点。我们以后可能会修改这个语法，但现在先叫它 `import rpc`，因为我们这里描述的东西几十年来一直被称为 [RPC](https://en.wikipedia.org/wiki/Remote_procedure_call)，即“远程过程调用”：

```
import rpc { prompt, alert } from './stuff';
 
const name = await prompt('Who are you?');
await alert('Hello, ' + name);
console.log('Done.');
```

想象一下，TypeScript 现在不仅能让你点击进入这些函数，而且还*知道*它们位于一个远程边界之后，因此会强制要求它们被声明为 `async`，并确保它们输入和输出的类型保持可序列化（这样才能真正在网络上传输）。

好了，`async` / `await` 加上 `import rpc`，一天的发明够多了。

除非呢？……

### Call Me Maybe（也许会调用我）

一位同事带着一个问题来找你。“那个 `async` / `await` 和 `import rpc` 很棒，真的很棒。但它只在另一台计算机真的*回应*时才有效。想象一台*不回应*的计算机。你要怎么调用那里的函数？”

这个问题乍一听毫无意义，但你琢磨了一会儿。

如果另一台计算机不回应……那么自然，你无法知道它*什么时候*完成，所以用 `await` 暂停执行是行不通的。所以你不能这样做：

`await alert('Hello, ' + name);`
更糟糕的是，如果函数所在的计算机不回应，你就拿不到任何函数调用的*结果*，所以这样也不可能：

`const name = await prompt('Who are you?');`
你很想宣布这种情况没救了，但你试着批判性地思考。没错，你无法把信息*传回来*……但你仍然可以把信息*往前传*。

例如，这行代码只把信息往前传：

`alert('Hello');`
即使另一台计算机不回应，这里你也只是请求它用 `'Hello'` 字符串调用 `alert` 函数。你并没有要求任何返回。

所以这个调用应该是可以发出的！只不过……它不会完全像普通的函数调用那样工作，因此使用和普通函数调用相同的语法似乎不太对。通常，人们会期望下面的代码在函数调用*完成*之后执行，但这里你无法保证这一点。事实上，你甚至无法确定这个调用一定会成功——如果它因为网络在中途失败，你将无从得知。和 RPC 不同，你不会收到网络错误的通知。

这不是一个函数调用。它是一个……*潜在的*函数调用。它是一个将来可能发生、也可能不发生的调用。你可以说它是函数调用的蓝图。

我们为这些“潜在调用”编一个语法：

`alert⧼'Hello'⧽;`
我们以后可能会改掉这个语法。但现在让我们来想清楚这个语法的*语义*，也就是我们真正希望它做什么。在设计过程中，明智的做法是从限制条件出发（“另一台计算机无法回应”），看看它们是否对这些“潜在调用”的语义施加了某些不可避免的约束。

显然，这些“潜在调用”不会中断执行，也不会影响其余代码。它们不会“等待”任何东西，因为没有东西可等：

```
alert⧼'Hello'⧽;      // 无法知道它是否/何时成功或失败
console.log('Done.') // 立即运行
```

这就引出了一个问题：这些“潜在调用”应该返回什么？

```
const name = prompt⧼'Who are you?'⧽;
console.log(name); // ???
```

显然，`prompt⧼'Who are you?'⧽` 不可能返回 `prompt` 调用最终的实际返回值，因为另一台计算机无法回应。我们可以规定这个语法总是返回 `undefined`，但那感觉相当受限。我们将无法协调 `prompt` 这个“潜在调用”和 `alert` 这个“潜在调用”！

我们想实现的是类似这样的东西：

```
const name = prompt⧼'Who are you?'⧽;
alert⧼'Hello, ' + name⧽;
```

问题是，上面的代码说不通，因为我们无法从 `prompt` 这个“潜在调用”中拿到任何东西。所以我们既不能给 `name` 变量赋值，也不能在这台计算机上用 `+` 操作它的返回值。不过，这里有个点子。我们*可以*做的，是把上面两行*完全*用“潜在调用”来重写：

```
alert⧼
  concat⧼
    'Hello, ',
    prompt⧼'Who are you?'⧽
  ⧽
⧽;
```

（这里以及后文，假设 `concat` 是一个全局函数，值为 `(a, b) => a + b`。）

以这种方式重新组织代码有两个好处。首先，它避免了声明一个毫无意义的 `name` 变量的问题——这个变量不可能有任何有意义的值（因为我们还不在另一台计算机上）。其次，它让我们可以把这些嵌套的“潜在调用”看作一个单一的表达式，很容易编码成 JSON：

```
{
  fn: 'alert',
  args: [{
    fn: 'concat',
    args: ['Hello, ', {
      fn: 'prompt',
      args: ['Who are you?']
    }]
  }]
}
```

然后我们可以把这个 JSON 发送到另一台计算机（它无法回应我们！），它会用类似这样的函数来解释我们的指令：

```
function interpret(json) {
  if (json && json.fn) {
    // 按名字查找全局函数
    let fn = window[json.fn];
    // 解释参数中嵌套的潜在调用
    let args = json.args.map(arg => interpret(arg));
    // 现在真正执行调用
    let result = fn(...args);
    // 如果它返回了更多潜在调用，接下来执行它们
    return interpret(result);
  } else {
    return json;
  }
}
```

你可以在控制台中验证：把上面的 JSON 对象传给 `interpret()`，效果等同于原来的代码。（别忘了定义一个全局的 `concat`！）

换句话说，这个方法行得通！

我们再看一眼这个语法：

```
alert⧼
  concat⧼
    'Hello, ',
    prompt⧼'Who are you?'⧽
  ⧽
⧽;
```

我们已经看到，“潜在调用”之间的任何依赖关系，比如 `prompt` 和 `alert` 之间的依赖，都应该通过把这些“潜在调用”相互嵌套来表达。我们无法真的在它们之间插入*代码*，除非那段代码*也*位于另一台计算机上。在*这台*计算机上，它们更像是……标记（markup）。

既然我们没有其他组合调用的方式，可以预料嵌套层级会很深。所以让语法稍微更容易浏览一些也许是个好主意：

```
<alert>
  <concat>
    Hello,
    <prompt>Who are you?</prompt>
  </concat>
</alert>
```

注意一个奇特之处。

对于普通的函数调用，返回值由你调用的函数决定：

```
const result = prompt('Who are you?');
console.log(result); // 'Dan'
```

但对于“潜在”函数调用，返回值是*以数据形式存在的调用本身*：

```
const inner = <prompt>Who are you?</prompt>;
// { fn: 'prompt', args: ['Who are you?'] }
 
const outer = <concat>Hello, {inner}</concat>;
// {
//   fn: 'concat',
//   args: ['Hello', { fn: 'prompt', args: ['Who are you?'] }]
// }
 
const outest = <alert>{outer}</alert>;
// {
//   fn: 'alert',
//   args: [{
//     fn: 'concat',
//     args: ['Hello', { fn: 'prompt', args: ['Who are you?'] }]
//   }]
// }
```

这些调用还没有被执行——我们只是在构建这些调用的*蓝图*：

```
<alert>
  <concat>
    Hello,
    <prompt>Who are you?</prompt>
  </concat>
</alert>
```

这份“潜在调用”的蓝图看起来像代码，但行为却像数据。它在结构上与函数调用相似，但更被动、更惰性、对解释保持开放。我们还没有把这份蓝图*发送*给那台将真正解释它的计算机。

总之，一遍又一遍地写“潜在函数调用”让我有点烦了。

我们就叫它们标签吧。

* * *

### 拆分一个函数

这是一个函数：

```
function greeting() {
  const name = prompt('Who are you?');
  alert('Hello, ' + name);
}
```

如果你运行它，它会一次性执行完。函数通常都是这样。

假设你想把它的执行拆成两部分。第一部分立即运行。第二部分在调用方决定时运行。

这里有一个简单的做法：

```
function greeting() {
  const name = prompt('Who are you?');
  return function resume() {
    alert('Hello, ' + name);
  };
}
```

现在你可以分两部分运行这个函数：

```
const resume = greeting(); // 运行第一部分
resume();                  // 运行第二部分
```

现在假设你想在*另一台计算机*上运行第二部分。你仍然把它看作一个单一的计算。只是它恰好在物理上是分布式的。

“简单！”你说：

```
function greeting() {
  const name = prompt('Who are you?');
  return `function resume() {
    alert('Hello, ' + name);
  }`;
}
```

等等，什么？

好吧，这很聪明，你从函数中返回*剩下的代码*，这样它就可以被传送到另一台计算机上完成计算。但等等！这样行不通——从另一台计算机的角度看，`name` 没有定义：

```
function resume() {
  alert('Hello, ' + name); // 🔴 ReferenceError: name is not defined
}
```

“没问题，”你说：

```
function greeting() {
  const name = prompt('Who are you?');
  return `function resume() {
    alert('Hello, ' + ${JSON.stringify(name)});
  }`;
}
```

啊，我明白你做了什么。你把在第一台计算机上得到的 `name` 值*直接嵌入*到发送给另一台计算机的代码中。从它的角度看，`name` 会显得是*预先计算好的*，就好像它一直都在那里：

```
function resume() {
  alert('Hello, ' + "Dan");
}
```

事实上，那个函数完全不知道自己是一个更大图景的一部分。从它的角度看，世界是从第二台计算机*开始*的。随着这个函数变得越来越复杂，它可能会开始以为自己就是全部。这也没关系。

但你*看到了*全貌：

```
function greeting() {
  const name = prompt('Who are you?');
  return `function resume() {
    alert('Hello, ' + ${JSON.stringify(name)});
  }`;
}
```

这是一种有趣的形态——一个程序以一种可以通过网络传输的形式返回它自身剩余的部分，以便在另一台机器上继续执行。你可以称之为*跨网络的闭包*。注意它工作方式的几个特点：

*   **数据严格地单向流动——从第一台计算机流向第二台。** 第二部分可以看到第一部分的值（只要它们能转成文本）。但第一部分对第二部分一无所知。第一部分在写剧本；第二部分将在舞台上表演。
*   **第一部分和第二部分是完全隔离的。** 虽然它们是同一个概念上的*程序*的一部分，但它们是独立的*运行时环境*。它们无法在运行时彼此协调，因为它们被时间和空间隔开了。它们的模块系统彼此完全隔离，各自有自己的全局变量，甚至可能运行在不同的 JavaScript 引擎上。
*   **两部分之间的边界既坚固又流动。** 说它坚固，是因为这两个环境*确实*是分开的——除了被闭包捕获的东西之外，它们之间不共享任何东西。但说它流动，是因为*你*可以在两个世界之间移动东西。你可以选择哪些行在哪一边运行，什么时候宁愿在第二台计算机上运行更多代码，什么时候宁愿把已经预先计算好的数据传给它。

最后一点值得展开讲讲。假设你在写一个 [FizzBuzz](https://en.wikipedia.org/wiki/Fizz_buzz)，想对从 `1` 到 `n` 的数字弹出提示：如果数字能被 3 整除就提示 `'Fizz'`，能被 5 整除就提示 `'Buzz'`，能同时被两者整除就提示 `'FizzBuzz'`：

```
function fizzBuzz() {
  const n = Number(prompt('How many?'));
  for (let i = 1; i <= n; i++) {
    if (i % 3 === 0 && i % 5 === 0) {
      alert('FizzBuzz');
    } else if (i % 3 === 0) {
      alert('Fizz');
    } else if (i % 5 === 0) {
      alert('Buzz');
    } else {
      alert(i);
    }
  }
}
```

现在想象这是一个给*两台*计算机的程序。你可以用不同的方式拆分它。例如，你可以选择把所有工作都放在第二台计算机上做：

```
function fizzBuzz() {
  return `function resume() {
    const n = Number(prompt('How many?'));
    for (let i = 1; i <= n; i++) {
      if (i % 3 === 0 && i % 5 === 0) {
        alert('FizzBuzz');
      } else if (i % 3 === 0) {
        alert('Fizz');
      } else if (i % 5 === 0) {
        alert('Buzz');
      } else {
        alert(i);
      }
    }
  }`;
}
```

但也许你想在第一台计算机上运行 `prompt`。你可以把 `prompt` 调用移到前一部分，然后把 `n` 作为*数据*传给第二部分：

```
function fizzBuzz() {
  const n = Number(prompt('How many?'));
  return `function resume() {
    const n = ${JSON.stringify(n)};
    for (let i = 1; i <= n; i++) {
      if (i % 3 === 0 && i % 5 === 0) {
        alert('FizzBuzz');
      } else if (i % 3 === 0) {
        alert('Fizz');
      } else if (i % 5 === 0) {
        alert('Buzz');
      } else {
        alert(i);
      }
    }
  }`;
}
```

从第二台计算机的角度看，`n` 会显得是硬编码的。

事实上，你可以在第一台计算机上预先计算出每一条消息：

```
function fizzBuzz() {
  const n = Number(prompt('How many?'));
  const messages = [];
  for (let i = 1; i <= n; i++) {
    if (i % 3 === 0 && i % 5 === 0) {
      messages.push('FizzBuzz');
    } else if (i % 3 === 0) {
      messages.push('Fizz');
    } else if (i % 5 === 0) {
      messages.push('Buzz');
    } else {
      messages.push(i);
    }
  }
  return `function resume() {
    const messages = ${JSON.stringify(messages)};
    messages.forEach(alert);
  }`;
}
```

这样，从第二台计算机的角度看，除了遍历这些消息之外就没有剩下任何计算了。例如，如果我选 `16` 作为 `n`，从第二台计算机的角度看，整个程序是这样的：

```
function resume() {
  const messages = [1,2,"Fizz",4,"Buzz","Fizz",7,8,"Fizz","Buzz",11,"Fizz",13,14,"FizzBuzz",16];
  messages.forEach(alert);
}
```

预先计算 `messages` 的缺点是，要发送的数据量会随着 `n` 增长而增长。由于 FizzBuzz 算法很简单，更明智的做法是传送 `n` 本身，让第二台计算机自己去运行 FizzBuzz。重要的是，你可以在传递数据和运行代码之间*选择*取舍。

现在回到最初的例子。

我们已经阐明了一个概念：把程序拆分到两台计算机上，我们就获得了移动计算的灵活性。然而在实践中，你大概不想把一半代码写在字符串里：

```
function greeting() {
  const name = prompt('Who are you?');
  return `function resume() {
    alert('Hello, ' + ${JSON.stringify(name)});
  }`;
}
```

相反，如果能把 `resume` 写在另一个文件里，然后直接 *import* 它，那就好了：

```
import { resume } from './stuff';
 
function greeting() {
  const name = prompt('Who are you?');
  return resume(name);
}
```

只不过等等，`resume` 不能是普通的导入——*你希望把这个函数的代码发送到另一台计算机上！* 所以你其实并不想现在在这台计算机上*导入*函数本身或运行它的任何代码；相反，你想*引用*那个函数。这可能会让你想起 RPC，你曾为它发明了 `import rpc`。我们再发明一个类似的注解，用来标记一个要被发送到另一台计算机的函数：

```
import tag { resume } from './stuff';
 
function greeting() {
  const name = prompt('Who are you?');
  return resume(name);
}
```

为什么是 `import tag`？这个函数位于一台“不回应”的计算机上，所以你无法调用它。你最多只能做一次“潜在调用”——换句话说，一个标签！

```
import tag { resume } from './stuff';
 
function greeting() {
  const name = prompt('Who are you?');
  return <resume name={name} />;
}
```

（我们稍后会重新审视 `import rpc` 和 `import tag` 语法并加以修改。）

以这种方式拆分的程序通常被称为客户端-服务器应用。

```
import tag { Client } from './stuff';
 
function Server() {
  const data = precomputeData();
  return <Client data={data} />;
}
```

人们很容易把客户端和服务器看成两个相互通信的独立程序。但现在你知道了，它其实是一个单一的函数，通过把它自身剩余的部分在时间和空间上向前发送，形成了一个跨网络的闭包。

祝你从此*无法*忘掉这个视角。

* * *

### 两边的标签

几节之前，你发明了标签：

```
function greeting() {
  return (
    <alert>
      <concat>
        Hello,
        <prompt>Who are you?</prompt>
      </concat>
    </alert>
  );
}
```

提醒一下，标签和函数调用非常相似，但它们并不真正*调用*任何东西——它们只是反映了一次调用的结构。正因如此，它们是表示一种你*希望*发生的计算的完美方式——但也许不是现在，甚至不是在这里。标签代表一个计划，一份计算的*蓝图*：

```
function greeting() {
  return {
    fn: 'alert',
    args: [{
      fn: 'concat',
      args: ['Hello, ', {
        fn: 'prompt',
        args: ['Who are you?']
      }]
    }]
  };
}
```

标签本身什么也不做。需要有代码去真正*解释*它们在说什么。下面是我们见过的一种对上面例子有效的方法：

```
function interpret(json) {
  if (json && json.fn) {
    let fn = window[json.fn];
    let args = json.args.map(arg => interpret(arg));
    let result = fn(...args);
    return interpret(result);
  } else {
    return json;
  }
}
```

[运行代码](https://codesandbox.io/p/devbox/r2c-part1-forked-h73wkn?file=%2Fsrc%2Findex.mjs)，可以看到 `interpret(greeting())` 产生了预期的结果。

然而，解释这件事的特点在于它是主观的。对某样东西的解释不止一种。说实话，这就是解释的全部意义所在。它们允许这种灵活性。

在前面的例子中，`interpret` 函数直接在全局 `window` 作用域中寻找*实现*每个标签的函数。所以它能在那里找到 `window.alert`、`window.prompt` 等等。现在我们要做一个稍有不同的 `interpret` 版本。这个版本会接收一个显式的 `knownTags` 字典，里面包含这些函数。未知的标签将被跳过。

请看：

```
function interpret(json, knownTags) {
  if (json && json.fn) {
    if (knownTags[json.fn]) {
      let fn = knownTags[json.fn];
      let args = json.args.map(arg => interpret(arg, knownTags));
      let result = fn(...args);
      return interpret(result, knownTags);
    } else {
      let args = json.args.map(arg => interpret(arg, knownTags));
      return { fn: json.fn, args };
    }
  } else {
    return json;
  }
}
```

现在，如果你给 `interpret` 传入空的 `knownTags`，你会得到原始的调用树：

```
interpret(greeting(), {});
 
// {
//   fn: 'alert',
//   args: [{
//     fn: 'concat',
//     args: ['Hello, ', {
//       fn: 'prompt',
//       args: ['Who are you?']
//     }]
//   }]
// };
```

*然而*，[注意看](https://codesandbox.io/p/devbox/r2c-part1-forked-2cx44l?file=%2Fsrc%2Findex.mjs)如果你传入 `{ prompt: window.prompt }` 会发生什么：

```
interpret(greeting(), {
  prompt: window.prompt
});
```

现在它会先询问你的名字（`prompt` *确实*运行了），然后产生这棵树：

```
// {
//   fn: 'alert',
//   args: [{
//     fn: 'concat',
//     args: ['Hello, ', 'Dan' /* （或者你输入的任何内容） */]
//   }]
// };
```

你仍然得到一棵调用树，但这一次 `prompt` 已经从中“溶解”掉了！

做个实验，我们把 `prompt` *和* `concat` 都“溶解”掉（但不包括 `alert`）：

```
interpret(greeting(), {
  prompt: window.prompt,
  concat: (a, b) => a + b,
});
```

这一次，`prompt` 会像之前一样运行，但为 `alert` 调用准备的消息已经拼接好了——看不到 `concat` 了：

```
// {
//   fn: 'alert',
//   args: ['Hello, Dan']
// };
```

换句话说，除了 `alert` 调用本身，我们已经*预先计算*好了一切。

我们也试试像之前那样，把 `alert`、`prompt` 和 `concat` 一起“溶解”掉：

```
interpret(greeting(), {
  alert: window.alert,
  prompt: window.prompt,
  concat: (a, b) => a + b,
});
 
// undefined
```

这一次，所有步骤都会运行，所以不会剩下任何事情可做。

由于标签的蓝图是*永恒的*——它不规定操作的特定顺序，只规定它们的结构——我们获得了操纵这种顺序的自由。例如，我们现在可以把一个单一的计算*拆分*成几步：

```
const step1 = greeting();
// {
//   fn: 'alert',
//   args: [{
//     fn: 'concat',
//     args: ['Hello, ', {
//       fn: 'prompt',
//       args: ['Who are you?']
//     }]
//   }]
// };
 
const step2 = interpret(step1, {
  prompt: window.prompt,
  concat: (a, b) => a + b,
});
// {
//   fn: 'alert',
//   args: ['Hello, Dan']
// };
 
interpret(step2, {
  alert: window.alert,
});
// undefined
```

[运行代码。](https://codesandbox.io/p/devbox/r2c-part1-forked-wfvxhp?file=%2Fsrc%2Findex.mjs)

这可能会给你一个启发。

如果你在不同的计算机上运行 `step1` 和 `step2` 呢？换句话说，如果你先在第一台计算机上解释，或者说“溶解”掉*一部分*标签，然后把剩下的发送出去，稍后在第二台计算机上解释，或者说“溶解”掉呢？如果某些标签*天生更适合*在两边中的某一边被解释——例如，如果这两台机器能力不同——这可能会很有用。

想想水的状态转变：首先，冰在山顶融化成水。然后河水向下流淌。最后，水蒸发掉。标签也可以如此。一些标签可以在第一台计算机上早早融化。剩下的标签可以通过网络流向另一台计算机——并在那里迎接它们的命运。

* * *

### 两台计算机

你的理论难以捉摸，有时你觉得它是胡说八道，但它的大致轮廓正在浮现。如果要你总结一下目前为止的内容，你会这样说：

有些程序是跨多台机器的分布式计算。特别是，有些程序可以表示为跨越*两台*机器的函数（尽管原则上可以有更多台）。其中一些函数会有一种特定的形态——第一台机器完成一部分计算，然后通过把剩余的代码发送给第二台机器，把剩下的计算“移交”给它。这些就是你的理论所关注的函数。

我们给这两台机器的环境起个名字。你的程序始于 *Early（早期）*世界——第一台机器。一部分工作会在那里发生。然后剩下的工作被移交给 *Late（晚期）*世界——第二台机器。

Early 世界和 Late 世界是两个被时间和空间隔开的完全隔离的运行时环境，因此它们不共享任何状态或全局变量。Early 世界可以*给 Late 世界留下一些残余信息*——具体来说，就是剩下要运行的代码以及运行它所需的数据——但仅此而已。

Early 世界和 Late 世界不会直接 `import` 对方的代码，因为那只会把那段代码带*进*导入它的世界。然而，它们*会*做的，是*引用*对方的代码。`import tag` 和 `import rpc` 都是*引用*另一台计算机上的代码（而且是类型安全的！）并用它做些有用的事、却不把它真正加载进导入方世界的例子。

由于它们之间界限分明，Early 世界中的函数无法*调用* Late 世界中的函数。毕竟，函数调用的意义在于把信息*传回*给调用方，但如果调用方早已撒手人寰，这就不可能了。

然而，把信息从 Early 世界*向前*传给 Late 世界仍然是有意义的。为了支持这一点，你发明了一个比函数调用更弱的概念——*标签*。标签就像函数调用，但它被动、惰性、对解释保持开放。它是一个等待被实现的*潜在*函数调用。标签是*作为*数据的函数调用，可以现在执行，*也*可以在更合适的时间点执行，或者根本不执行。标签是一种原型调用（proto-call）。

你得意地站着，第一次看到你理论中那些零散的线索开始汇聚到一起。突然，Boss 战的音乐响起。

*有人提到时间了吗？*

* * *

### 时间反击战

你的第一个 Boss 就是时间本身。要打败时间，你必须证明你所谓的*永恒*蓝图确实是永恒的——改变它们的计算顺序不会意外地毁掉你的程序。你最好是对的！

这是你之前的 `greeting` 函数：

```
function greeting() {
  return (
    <alert>
      <concat>
        Hello,
        <prompt>Who are you?</prompt>
      </concat>
    </alert>
  );
}
```

我会把它稍微加强一点，让这场 Boss 战更有趣（也更可怕）。

我猜你会非常频繁地把 `alert` 和 `concat` 组合在一起，所以我把它们提取成一个单独的函数。我把它叫做 `p`，代表“paragraph（段落）”。

```
function p(...children) {
  return (
    <alert>
      <concat>
        {children}
      </concat>
    </alert>
  );
}
```

function interpret(json, knownTags) {

      let args = json.args.map(arg => interpret(arg, knownTags));

    }
  } else if (Array.isArray(json)) {
    return json.map(item => interpret(item, knownTags));
  } else {

  }
}
```

### 致命缺陷

刚才发生了什么？

原来你的理论有一个缺陷。即使你用标签而不是函数调用来描述程序，时间其实也很重要！至少对某些函数来说是这样。

看这个例子：

```
<concat>
  Hello,
  <prompt>Who are you?</prompt>
</concat>
```

当两个标签嵌套时，应该按什么顺序解释它们？应该先解释 `<prompt>`，再把它的结果传给 `concat` 函数吗？还是应该让 `concat` 函数接收*作为标签本身*的 `<prompt>`？

我们可以先考虑普通函数调用的行为：

```
concat(
  'Hello, ',
  prompt('Who are you?') // 这会先运行
)
```

如果你不确定的话：在 JavaScript 中调用函数时，它的参数会*先*被计算——在这些值确定之后，函数才会被调用：

```
function concat(a, b) {
  // a 是 'Hello, '
  // b 是 'Dan'
  return a + b;
}
```

我们处理标签的 `interpret` 函数也按同样的顺序应用它们。当它遇到像 `<concat>` 这样的标签时，它会*先*对其参数运行 `interpret`，以防里面有像 `<prompt>` 这样的嵌套调用。只有*之后*它才会调用 `concat()`：

```
function interpret(json, knownTags) {
  if (json && json.fn) {
    if (knownTags[json.fn]) {
      let fn = knownTags[json.fn];
      let args = json.args.map(arg => interpret(arg, knownTags));
      let result = fn(...args);
      return interpret(result, knownTags);
    } else {
      // ...
    }
  } else {
    // ...
  }
}
```

因此，这段代码：

```
<concat>
  Hello,
  <prompt>Who are you?</prompt>
</concat>
```

目前等价于这段：

```
concat(
  'Hello, ',
  prompt('Who are you?') // 这会先运行
)
```

然而，这里有些不对劲。

我们的标签不是应该是*永恒的蓝图*，摆脱 JavaScript 那种“参数必须先求值”的烦人求值顺序约束吗？如果这些“标签”最终的行为和函数调用一模一样，那它们还有什么用？

好吧，但这*还能*怎么运作呢？

那么，如果这段：

```
<concat>
  Hello,
  <prompt>Who are you?</prompt>
</concat>
```

改为等价于这段呢：

```
concat( // 这会先运行
  'Hello, ',
  <prompt>Who are you?</prompt>
)
```

想象一下，标签是*由外向内*而不是*由内向外*求值的。那么，当你有一个里面包含 `<prompt />` 的 `<concat>` 时，你不会先看到 `prompt` 调用。相反，你会在 `<prompt />` 仍然是*一个标签*的情况下进入 `concat`：

```
function concat(a, b) {
  // a 是 'Hello, '
  // b 是 { fn: 'prompt', args: ['Who are you?'] }
  return a + b;
}
```

当然，那会彻底搞坏 `concat`，因为它只能拼接*字符串*，而不能拼接像 `<prompt />` 这样尚未运行的任意计算。

这个问题并非 `concat` 独有。例如，`alert` 函数也期望接收一个*字符串*。它不知道如何处理一个表示标签的对象：

`alert({ fn: 'concat', args: [/* ... */] });`
或者更确切地说，它会*处理*它——把它强制转换成像 `"[object Object]"` 这样的字符串。

这就解释了 Boss 战中发生的事！

虽然我们的 `interpret` 函数通常会先处理参数，但我们特意*推迟*了对 `<concat>` 标签的解释，以证明顺序无关紧要。然而，顺序*确实*重要——`concat` 和 `alert` 函数都*需要*它们的参数是普通字符串而不是标签。

看来你的永恒蓝图终究没那么永恒。函数*需要*先计算出它们的参数。时间就藏在那里。

你的理论有一个致命缺陷。

你的理论有一个致命缺陷。对此你可以做三件事。

你可以假装它不存在。但那修不好你的理论。

你可以放弃你的理论。但你确实*发现了*一些东西，不是吗？

如果我们改为直接传递原始参数（即使其中包含标签）呢？

```
function interpret(json, knownTags) {
  if (json && json.fn) {
    if (knownTags[json.fn]) {
      let fn = knownTags[json.fn];
      let args = json.args;
      let result = fn(...args);
      return interpret(result, knownTags);
    } else {

```

当然，这会彻底破坏我们之前的每一个例子。记住，`alert()` 无法处理像 `<concat>` 这样的对象参数——而 `concat()` 本身也[无法处理](https://codesandbox.io/p/devbox/r2c-part1-forked-rnvdg2?file=%2Fsrc%2Findex.mjs)像 `<prompt>` 这样的对象参数。它想要两个字符串，而不是标签：

例如，把 `<concat>` 换成 `<p>` [就不再导致](https://codesandbox.io/p/devbox/r2c-part1-forked-kw9cxj?file=%2Fsrc%2Findex.mjs)输出出错：

      </concat>

}
 
// ...

  <p>

  p: p,

// { fn: 'alert', args: [{ fn: 'concat', args: ['Hello, ', 'Dan'] }] }
```

这看起来可能无足轻重（我们以后仍然需要运行 `concat`）。但实际上这非常重要！`concat` 和 `p` 这两个函数之间有某种根本性的不同。*由外向内*的调用顺序会搞坏 `concat`，但不会搞坏 `p`。

### 嵌入与内省

看这两个函数：

```
function concat(a, b) {
  return a + b;
}
 
function pair(a, b) {
  return [a, b];
}
```

它们有什么不同？

显然，它们的用途不同。一个拼接字符串。另一个用提供的两个元素创建一个数组。但在它们如何对待自己的参数这一点上，还有一个更微妙的区别。

为了解释它，我会用一个类比。

假设你的工作是把绳子的各段系在一起。这并不太难。你拿起两段绳子，把它们系在一起，工作完成。现在假设有一天，有人递给你一段绳子和……一个南瓜。突然之间，你没法工作了。你需要抓住两段绳子的末端，但南瓜没有末端。

现在，你可能会由此得出结论：随意把东西换成南瓜会导致灾难，有时确实如此。但并非总是这样。

假设你有了一份新工作，在玩具店包装礼物。你整天包装各种礼物，不管是玩偶、小汽车，还是一整栋玩具房子。然后有一天，有人递给你一个南瓜。虽然你可能出于原则拒绝这个请求，但*从技术上讲*，你完全可以把南瓜包好。当你包装东西时，你并不依赖它们的属性（比如绳子之所以为绳子的特性）。你只是把它们放进盒子里。你是在*嵌入*，而不是在*内省*。

上面 `concat` 和 `pair` 的区别在于，`concat` *在乎*传给它的是什么。它在*内省*。如果你传给它一个南瓜，它就无法工作。但 `pair` 会欣然接受绳子、玩具或南瓜。它在*嵌入*，所以它不在乎。

我们来看看这和执行顺序有什么关系。

由于 `concat` 会*内省*参数 `a` 和 `b`（具体来说，`+` 会把它们转成字符串），如果你把一个未解释的标签作为参数传进去，`concat` 就会出错：

```
concat('Hello ', <prompt>Who are you?</prompt>);
// 'Hello, [object Object]'
```

而 `pair` 则是*嵌入*它的参数 `a` 和 `b`。它产生一个新的 `[a, b]` 数组——无论你传入什么作为 `a` 或 `b`，这都能正确工作。所以它乐于接受一个标签作为参数之一。它只是把那个标签嵌入到自己的输出中：

```
const todo = pair('Hello ', <prompt>Who are you?</prompt>);
// ['Hello, ', { fn: 'prompt', args: ['Who are you?'] }]
```

这让你可以在 `pair` 调用*之后*的某个时候再去解释那个标签：

```
const result = interpret(todo, { prompt: window.prompt });
// ['Hello, ', 'Dan']
```

我们来总结一下。

一般来说，函数希望在调用之前计算好它们的参数。然而，如果一个函数只是把参数*嵌入*到输出中而不*内省*它，你就可以推迟计算这个参数。你可以在这个参数仍未计算（是一个标签）的情况下调用那个函数，并在必要或方便的时候再计算那个标签。

也许你终究找到了打败时间的方法。

### 思考与执行

你的程序还是一样：

```
function app() {
  return [
    <greeting />,
    <p>The time is: <clock /></p>
  ];
}
 
function clock() {
  return new Date().toString();
}
 
function greeting() {
  return (
    <p>
      Hello,
      <prompt>Who are you?</prompt>
    </p>
  );
}
 
function p(...children) {
  return (
    <alert>
      <concat>
        {children}
      </concat>
    </alert>
  );
}
 
function alert(message) {
  window.alert(message);
}
 
function prompt(message) {
  return window.prompt(message);
}
 
function concat(a, b) {
  return a + b;
}
```

但你的 `interpret` 函数更简单了——它*由外向内*地解释标签。它不会试图在调用前解释参数；相反，它*把标签传给其他标签*。

```
function interpret(json, knownTags) {
  if (json && json.fn) {
    if (knownTags[json.fn]) {
      let fn = knownTags[json.fn];
      let args = json.args;
      let result = fn(...args);
      return interpret(result, knownTags);
    } else {
      let args = json.args.map(arg => interpret(arg, knownTags));
      return { fn: json.fn, args };
    }
  } else if (Array.isArray(json)) {
    return json.map(item => interpret(item, knownTags));
  } else {
    return json;
  }
}
```

时间冲你冷笑。

*“这行不通的，对吧？函数需要知道它们的参数。”*

“*有些*函数需要。”

你检查程序中的所有函数，看它们是*内省*你嵌套在其标签内的东西，还是只是*嵌入*它而不做内省：

*   显然，`alert` 和 `concat` 会内省你放进它们标签里的东西。
*   有些函数（`app`、`clock` 和 `greeting`）根本不接受任何参数。
*   虽然你*确实*向 `p` 传入了东西，但它只是嵌入你在其中嵌套的任何东西。
*   `prompt` 的情况比较模糊。从技术上讲，它确实内省了 `message` 参数（因为它把 `message` 传给了内置的 `window.prompt`）。然而，到目前为止，我们还没有想在 `<prompt>` 里嵌套其他标签的冲动。所以只要我们承诺不这样做（例如通过某种方式限制类型），这就无关紧要。

为了理清思路，你将引入一个新的约定。

那些在接收标签作为参数时不会出错的函数，也就是那些*嵌入*而不是*内省*参数的函数，从现在起名字以大写字母开头：

```
function App() {
  return [
    <Greeting />,
    <P>The time is: <Clock /></P>
  ];
}
 
function Clock() {
  return new Date().toString();
}
 
function Greeting() {
  return (
    <P>
      Hello,
      <prompt>Who are you?</prompt>
    </P>
  );
}
 
function P(...children) {
  return (
    <alert>
      <concat>
        {children}
      </concat>
    </alert>
  );
}
 
function alert(message) {
  window.alert(message);
}
 
function prompt(message) {
  return window.prompt(message);
}
 
function concat(a, b) {
  return a + b;
}
```

我们给这些首字母大写的函数起一个特别的名字：组件（Components）。组件是我们程序的“大脑”——它们负责想清楚需要做什么。因为它们不内省你嵌套在里面的东西，所以它们可以以任意顺序、分任意多步、一起或分开运行。换句话说，组件*是*真正永恒的。它们摆脱了未来的束缚，因为它们*返回*标签；它们也摆脱了过去的束缚，因为它们*接收*标签作为参数。

那剩下的函数呢，比如 `alert`、`prompt` 和 `concat`？我们称它们为原语（Primitives）。原语也可以作为标签使用，但它们不只是嵌入东西——它们会内省它。它们*必须*知道自己的所有参数。原语是我们程序的“肌肉”——在组件已经完成了大部分思考之后，它们才真正去*做事*。原语最后运行：*“先思而后行”*。

这一区分让你可以很自然地把程序切成两个阶段。

首先，你需要*思考*——也就是运行组件。你现有的 `interpret` 函数可以处理这件事：

```
const primitives = interpret(<App />, {
  App,
  Greeting,
  Clock,
  P
});
 
// [
//   { fn: 'alert', args: [{ fn: 'concat', args: ['Hello', { fn: 'prompt', args: ['Who are you?'] }] }] },
//   { fn: 'alert', args: [{ fn: 'concat', args: ['The time is: ', 'Wed Apr 09 2025 15:13:04 GMT+0900 (Japan Standard Time)'] }] }
// ]
```

*思考*之后，你需要*执行*。“思考”阶段的结果只包含原语。我们来创建一个新的 `perform` 函数，它看起来和 `interpret` 很像，但它处理的是原语而不是组件。由于原语会内省东西、需要*知道*它们的参数，`perform` 确保它们由内向外运行：

```
function perform(json, knownTags) {
  if (json && json.fn) {
    let fn = knownTags[json.fn];
    let args = perform(json.args, knownTags);
    let result = fn(...args);
    return perform(result, knownTags);
  } else if (Array.isArray(json)) {
    return json.map(item => perform(item, knownTags));
  } else {
    return json;
  }
}
```

注意，`perform` 不包含任何跳过未知标签的代码——它假设 `knownTags` 包含它可能遇到的*所有*原语。这是因为 `perform` 的定位就是*最终*一步，不允许你再进一步拆分计算。

现在你可以用 `perform` 来完成计算：

```
perform(primitives, {
  alert,
  concat,
  prompt
});
 
// undefined
```

这会显示 prompt 和两个预期的提示框。

[运行代码。](https://codesandbox.io/p/devbox/r2c-forked-6f6jz7?file=%2Fsrc%2Findex.mjs)

那么，你打败时间了吗？

算是吧。

以前，`interpret` 很脆弱，因为跳过*某些*标签（比如 `concat`）会破坏另一些标签（比如 `alert`）隐含假设的顺序。但现在这种情况不会再发生了。现在 `interpret` *只*处理组件，而组件不介意以任意顺序运行（因为它们*嵌入*而不是*内省*）。

另一方面，原语现在由 `perform` 处理，而它总是一步完成工作。所以那里也不会出现这个问题。

如果你将来把程序扩展到跨越两台计算机，被拆分到两台计算机上的会是组件（而不是原语）。这是因为组件不介意以不同顺序运行。而原语则必须在最后一起运行——这就把它们牢牢地放在了 Late 世界中。

如果你对运行 Late 世界的计算机有一定控制权，你可以做一个有趣的优化。你可以把你预期所有程序都会共享的原语和 JavaScript 运行时一起*预装*好。当然，这样一组原语必须经过精心挑选，以服务尽可能广泛的使用场景。但你已经能看到一些不错的候选者了！例如，你的 `P` 函数作为原语也许更合理：

```
function p(...children) {
  return (
    <alert>
      <concat>
        {children}
      </concat>
    </alert>
  );
}
```

可以说，“段落”是许多程序都可能想显示的东西！

如果你想得更大一些，你可能会想出一整套这样的原语——有些是图形性的（比如让某些东西变成 `<b>粗体</b>` 或 `<i>斜体</i>`），有些是行为性的（比如展开 `<details></details>` 或 `<a />` 链接）。

现在，如果很多程序都使用相同的原语，而且每个人都在用它们构建复杂的程序，那么把它们的内部实现从 JavaScript 移到某种更底层的语言（比如 Rust 或 C++）里可能就很合理了。然后它们可以通过某些更高层的 API 暴露给 JavaScript。接着可以重写 `perform`，用这些 API 来编排计算：

```
function perform(json) {
  if (json && json.fn) {
    let tagName = json.fn;
    let children = perform(json.args);
    let node = document.createElement(tagName);
    for (let child of [children].flat().filter(Boolean))) {
      node.appendChild(child);
    }
    return node;
  } else if (typeof json === 'string') {
    return document.createTextNode(json);
  } else if (Array.isArray(json)) {
    return json.map(perform);
  } else {
    return json;
  }
}
 
const tree = perform(json);
document.body.appendChild(tree);
```

你甚至可以设计一门*专门*用来描述这种原语树的声明式语言。它可以被设计得比我们现在的方案更宽容，因为在某些使用场景下，手写它会比较方便。

关于原语说得够多了。接下来，我们将假设存在[相当多的原语](https://developer.mozilla.org/en-US/docs/Web/HTML/Element)，它们被写成小写的标签（比如 `<p>`），并且存在一个知道如何处理它们的 `perform` 函数。

时间退到一旁。

你已经学会了驾驭时间的力量——*并且*学会了尊重它的法则。现在，如果你想继续你的学业，是时候学习空间的课程了。

### 代码与数据

在这篇文章的前半部分，我们学会了如何在时间上拆分计算。

结果发现，计算中的某些部分——那些主动*做*事情的原语——不喜欢被拆开，希望一起执行。计算的另一些部分——那些*思考*事情的组件——可以在不同的时间、以不同的顺序，甚至可能在不同的*地点*执行。

我们暂时把组件和原语放到一边。

我们来研究一下*在时间上*拆分函数和*在空间上*拆分函数的区别。我们前面看到，要在时间上拆分一个函数，只需增加嵌套就够了：

```
function greeting() {
  const name = prompt('Who are you?');
  return function resume() {
    alert('Hello, ' + name);
  };
}
```

这让你可以分步运行它，而不是一次运行完。

```
const resume = greeting(); // 运行第一步
resume();                  // 运行第二步
```

`greeting` 的返回值是一个函数——但这不是全貌。关键在于，这个函数嵌套在 `greeting` *内部*，否则它就无法读取 `name` 变量。换句话说，`greeting` 既返回了一段代码（`alert` 调用），*也*返回了这段代码所需要的一段数据（`name` 变量）。

如果你把 `resume` 提取为一个顶层函数，这一点就更明显了。现在它必须把 `name` 作为显式参数接收：

```
function resume(name) {
  alert('Hello, ' + name);
}
```

我们该怎么调整 `greeting` 来适应这一点呢？我们可以让它返回一个嵌套函数，由这个函数把 `name` 提供给 `resume`：

```
function greeting() {
  const name = prompt('Who are you?');
  return () => resume(name);
}
 
function resume(name) {
  alert('Hello, ' + name);
}
 
const resume = greeting(); // 运行第一步
resume();                  // 运行第二步
```

但我们还可以更进一步。从概念上讲，`() => resume(name)` 组合了两条信息：*代码*（`resume`）和*数据*（`name`）。我们可以通过返回 `[resume, name]`——代码与数据*配对*——来让这种关系变得明确：

```
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
 
function resume(name) {
  alert('Hello, ' + name);
}
 
const [code, data] = greeting(); // 运行第一步
code(data);                      // 运行第二步
```

事实上，这看起来和我们目前用于*标签*的对象表示法非常相似，只不过 `fn` 函数是一个*真正的函数*而不是字符串：

```
function greeting() {
  const name = prompt('Who are you?');
  return { fn: resume, args: [name] };
}
 
function resume(name) {
  alert('Hello, ' + name);
}
 
const { fn, args } = greeting(); // 运行第一步
fn(...args);                     // 运行第二步
```

这几乎就像 `greeting` 返回的是一个*标签*，而不是一个函数调用。它表达了*它接下来想要运行的代码*，但它还没有真正*去做*。

这给了我们一个看待标签究竟是什么的新视角。是的，标签是一个潜在的函数调用。但另一种看法是：*标签是代码与数据的配对。*

* * *

### 时间与空间

现在我们来回忆一下如何在空间上拆分计算。我们之前发现了一种可行的模式——把一段代码作为字符串返回：

```
function greeting() {
  const name = prompt('Who are you?');
  return `function resume() {
    alert('Hello, ' + ${JSON.stringify(name)});
  }`;
}
 
const code = greeting();
```

然后你可以调用 `greeting()`，保存它返回的 `code`，再在另一台计算机上把它*作为代码*运行。第二台计算机会以为*这*就是整个程序：

```
function resume() {
  alert('Hello, ' + "Dan");
}
```

但*你*知道，真正的程序包含这两部分。

目前，`greeting` 返回的是一个代码字符串。然而，把它看作同时返回了代码*和*数据也是完全合理的。我们只是恰好把数据（`name` 变量）直接插值到了那个代码字符串中。

如果我们把 `resume` 的代码移到 `greeting` 外面，这一点就更明显了：

```
const RESUME_CODE = `
  function resume(name) {
    alert('Hello, ' + name);
  }
`;
 
function greeting() {
  const name = prompt('Who are you?');
  return [RESUME_CODE, name];
}
 
const [code, data] = greeting();
const jsonString = JSON.stringify([code, data]);
```

既然 `resume` 接收 `name` 作为参数，`greeting` 就需要*同时*返回 `resume` 函数的代码*和*它所需要的数据（`name`）。然后我们可以拿着 `[code, data]`，用 `JSON.stringify` 把它转成 JSON，再在另一台计算机上 `JSON.parse` 它，最后调用 `code(data)` 来完成程序。

当然，写程序时，我们并不真的想把 `resume` 的代码当作一个*字符串*来考虑。我们想把它当作一段普通的代码：写在顶层，有语法高亮，可以做类型检查，等等：

```
function resume(name) {
  alert('Hello, ' + name);
}
```

但我们要怎么把这段代码和 `greeting` 函数*连接*起来呢？

```
function greeting() {
  const name = prompt('Who are you?');
  return [RESUME_CODE, name];
}
```

这些函数就像存在于两个不同的*世界*中——一个存在于即将被发送的代码字符串的“外面”，另一个存在于它的“里面”。就好像 `greeting` 在写一个故事，而 `resume` 是那个故事*里面*的某个人。

它们之间有清晰的逻辑连续性，但隔开它们的鸿沟远比“位于不同文件”宽得多。当 `greeting` 函数运行时，`resume` 只是一个字符串——与其说是一个真正的函数，不如说更像一个计划或一个想法。另一方面，当 `resume` 最终运行时，它完全不知道 `greeting` 曾经存在过——它收到的只有传给它的 `name`。

```
function greeting() {
  const name = prompt('Who are you?');
  return [RESUME_CODE, name];
}
```

```
function resume(name) {
  alert('Hello, ' + name);
}
```

如果你眯起眼睛看，仍然可以辨认出程序“真正”的形态：

```
function greeting() {
  const name = prompt('Who are you?');
  return `function resume() {
    alert('Hello, ' + ${JSON.stringify(name)});
  }`;
}
```

但这种“拆分”的看法对两个世界都更公平。它不偏重任何一方。它们两个*都是*我们的程序，只是被时间和空间拆开了：

```
function greeting() {
  const name = prompt('Who are you?');
  return [RESUME_CODE, name];
}
```

```
function resume(name) {
  alert('Hello, ' + name);
}
```

问题是，我们如何把它们连在一起？

* * *

### 两个世界

把两个世界连在一起最简单的方法，是给 Late 世界中的每个函数一个唯一的名字，让我们可以从 Early 世界中引用它。

例如，我们可以假设我们永远只需要一个叫 `resume` 的函数：

```
function greeting() {
  const name = prompt('Who are you?');
  return ['resume', name];
}
```

```
window['resume'] = function resume(name) {
  alert('Hello, ' + name);
}
```

虽然这有点笨拙，但它*确实*建立了一种显式的（尽管脆弱的）联系。如果我们哪天要在 Late 世界中重命名 `resume`，我们也许会记得在代码库中搜索其他可能引用它的代码，然后可能会找到 Early 世界中的 `greeting`。我们甚至可以给 `window['resume']` 加上类型。

这个方案并没有*那么*糟糕。事实上，它和*你*引用任何浏览器内置原语时幕后发生的事情很相似。你并没有从任何地方直接导入它们；你只是使用像 `p` 这样的全局名称：

```
function Greeting() {
  const name = prompt('Who are you?');
  return <p>Hello, {name}</p>;
}
```

```
document.createElement = function(tagName) {
  switch (tagName) {
    case 'p':
    // ...
  }
}
```

从这个意义上说，浏览器内部本身就是一种“Late”世界。它们的很大一部分是用不同于 JavaScript 的语言编写的，并且没有直接暴露给你的程序。与 `p` 这样的原语相关的大量逻辑——包括应用样式、文本排版、绘制、合成、渲染等等——会在你调用 `document.createElement('p')` *之后*的某个时刻运行。从这个意义上说，`<p>` 确实是一个*标签*——一个仍需将来某种“执行”的调用。

但我们别跑题了。浏览器原语可以使用全局名称，是因为它们的数量有限，你需要能查到它们，而且它们在各个项目之间总是相同的。而如果你自己定义函数，你大概会希望它们之间有更显式的联系。

让我们回到你想要连接的那两部分：

```
function greeting() {
  const name = prompt('Who are you?');
  return [RESUME_CODE, name];
}
```

```
function resume(name) {
  alert('Hello, ' + name);
}
```

显而易见的第一步，是把 `resume` 函数标记为 `export`。你希望其他文件中的代码能够引用它。它不是一个可以随意删除的实现细节。你不希望它看起来像死代码！

```
function greeting() {
  const name = prompt('Who are you?');
  return [RESUME_CODE, name];
}
```

```
export function resume(name) {
  alert('Hello, ' + name);
}
```

既然你已经 `export` 了它，下一步自然就是在这里 `import` 它：

```
import { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [RESUME_CODE, name];
}
```

```
export function resume(name) {
  alert('Hello, ' + name);
}
```

只不过等等。

这帮不了你！

你想得到的是 `RESUME_CODE`，也就是前面的这个东西：

```
const RESUME_CODE = `
  function resume(name) {
    alert('Hello, ' + name);
  }
`;
```

但你通过导入 `resume` *得到*的是另一个东西：

```
function resume(name) {
  alert('Hello, ' + name);
}
```

*你把反引号弄丢了！*

* * *

### 小心鸿沟

让我们彻底说服自己：使用 `import` 是行不通的。

归根结底，我们想做的是把这个模式*模块化*：

```
function greeting() {
  const name = prompt('Who are you?');
  return `function resume() {
    alert('Hello, ' + ${JSON.stringify(name)});
  }`;
}
```

为此，我们把 `greeting` 和 `resume` 函数拆到了两个不同的世界中——但结果是，我们失去了它们之间的语法联系。

假设我们试图用一个 `import` 来跨越两个世界之间的“鸿沟”：

```
import { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
```

```
export function resume(name) {
  alert('Hello, ' + name);
}
```

不幸的是，除非我们改变 `import` 的工作方式，否则这本质上只会把 `resume` 函数*本身*“带进” `greeting` 的世界：

```
function resume(name) {
  alert('Hello ', + name);
}
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
```

```
export function resume(name) {
  alert('Hello, ' + name);
}
```

换句话说，程序的整体形态看起来大致是这样的：

```
function greeting() {
  const name = prompt('Who are you?');
  return function resume() {
    alert('Hello, ' + name);
  };
}
```

但我们*需要*的整体形态看起来大致是这样的：

```
function greeting() {
  const name = prompt('Who are you?');
  return `function resume() {
    alert('Hello, ' + ${JSON.stringify(name)});
  }`;
}
```

关键全在反引号！

当我们 `import` 某样东西时，我们就把那段代码带进了导入方的世界。但我们这里*想要*的只是*引用*那段代码，而不执行它的任何部分。我们想让 `greeting` 返回一个关于南瓜的*故事*——而不是一个真正的南瓜。

如果你设想 `resume` *本身*也导入了某个第三方库——比如用来显示一个 toast 提示——`import` 的问题就更明显了：

```
import { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
```

```
import { showToast } from 'toast-library';
 
export function resume(name) {
  showToast('Hello, ' + name);
}
```

使用普通的 `import`，我们整个程序的形态相当于这样：

```
// 来自 toast-library
function initializeToastLibrary() { /* ... */ }
function showToast(message) { /* ... */ }
initializeToastLibrary();
 
function greeting() {
  const name = prompt('Who are you?');
  return function resume() {
    showToast('Hello, ' + name);
  };
}
```

然而，我们*想要*的形态更接近这样：

```
function greeting() {
  const name = prompt('Who are you?');
  return `
    // 来自 toast-library
    function initializeToastLibrary() { /* ... */ }
    function showToast(message) { /* ... */ }
    initializeToastLibrary();
 
    function resume() {
      showToast('Hello, ' + name);
    }
  `;
}
```

两个世界之间的边界是坚固的，而且*理应*如此。我们希望每个世界内部的行为都是一致的——至少对任何已有的代码来说如此。

为了确保这一点，来自 Early 世界的导入*应该*成为 Early 世界的一部分。来自 Late 世界的导入*应该*成为 Late 世界的一部分。就其自身而言，每个世界都应该表现得像一个独立的隔离程序——不搞任何花样。

我们不想破坏这种一致性。

我们需要的只是一扇*门*。

* * *

### 一扇门

我们需要一种方式来表达：“我想引用另一个文件里的这个东西，但我实际上并不想执行、甚至不想加载它的任何代码。只要给我一个能让我以后以编程方式找到那个东西的代码的东西就行。”幸运的是，这一切完全是虚构的，所以我们可以随便编一个语法来表达它。

*噔噔！*

```
import tag { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
```

```
import { showToast } from 'toast-library';
 
export function resume(name) {
  showToast('Hello, ' + name);
}
```

什么，*就这样*？

当然，为什么不呢。

好吧，但这个语法*做*什么？

嗯，首先，我们假设它只是返回函数的源代码。这会让我们能够像最初打算的那样，把那段代码发送到另一台计算机：

```
import tag { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
 
const [code, data] = greeting();
// [
//   'function resume(name) { showToast("Hello, " + name); }',
//   'Dan'
// ]
```

然而，这其实没什么大用——注意，`showToast` 不见踪影。我们真正想要的不是*单单 `resume` 函数*的源代码，而是*另一台计算机加载并运行 `resume` 所需的一切*。

这是第二个想法。

我们为什么不让它返回某种专门为定位代码而设计的标识符呢？例如，它可以把文件名和导出名组合起来：

```
import tag { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
 
const [code, data] = greeting();
// [
//   '/src/stuff/resume.js#resume',
//   'Dan'
// ]
```

当然，这意味着这个格式必须在某种程度上知道另一台计算机*如何*加载和执行代码。例如，如果另一台计算机运行的是 Node.js 进程，它可以从文件系统中 `import()` 那个文件——前提是该文件会被部署到那台计算机上。如果另一台计算机运行的是 Web 浏览器，它可以通过 HTTP 从一台必须提供该文件的服务器上 `import()` 它。

对于 Web 浏览器来说，逐个导入远程文件、依靠浏览器的模块系统去下载它们的每个依赖，可能效率不高。相反，使用一个自动化的*打包器（bundler）*（它会把这些代码合并成若干代码块）并使用打包器专用的标识符可能更合理：

```
import tag { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
 
const [code, data] = greeting();
// [
//   'chunk123#module456#resume',
//   'Dan'
// ]
```

在最简单的情况下，如果所有要发往 Late 世界的代码最终都被组装成一个巨大的单一文件，通过网络发送给另一台计算机，那么这个标识符可以就是被引用函数的全局名称：

```
import tag { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
 
const [code, data] = greeting();
// [
//   'window.resume',
//   'Dan'
// ]
```

重要的是，我们现在有了一种语法，可以让 Early 世界中的某段代码*引用* Late 世界中的某段代码。它是两个环境之间的一扇*门*。

它让我们可以实现这样的效果：

```
function greeting() {
  const name = prompt('Who are you?');
  return `
    import { showToast } from 'toast-library';
 
    function resume() {
      showToast('Hello, ' + name);
    }
  `;
}
```

只需要这样写：

```
import tag { resume } from './resume';
 
function greeting() {
  const name = prompt('Who are you?');
  return [resume, name];
}
```

```
import { showToast } from 'toast-library';
 
export function resume(name) {
  showToast('Hello, ' + name);
}
```

它让我们可以写一个横跨两个编程环境的单一程序。

### 春季大扫除

我们已经在两个世界——Early 世界和 Late 世界——之间找到了一扇*门*。这扇门，`import tag`，将让我们可以在时间*和*空间上拆分计算。

不过在使用这扇门之前，我们需要先打扫一下屋子。我们要对标签语法做一些调整，让它更适合编写组件。（如果你熟悉 React，你会发现这些调整让我们更接近 JSX。）

看这个例子：

```
function App() {
  return (
    <div>
      <Greeting />
      <p>The time is: <Clock /></p>
    </div>
  );
}
```

到目前为止，我们一直假设这个语法会产生这样一棵对象树：

```
function App() {
  return {
    fn: 'div',
    args: [
      { fn: 'Greeting', args: [] },
      {
        fn: 'p',
        args: ['The time is: ', { fn: 'Clock', args: [] }]
      }
    ]
  };
}
```

这一切都很好，但它没有给我们留下传递像 `<p className="text-purple-500">` 这样具名属性的方法。我们要调整一下约定：组件和原语都不再接收按位置排列的 `args`，而是接收一个包含*具名*参数的单一对象。我们把这个对象叫做 `props`，意思是“properties（属性）”。嵌套的标签会移到该对象中一个叫 `children` 的 prop 里。

```
function App() {
  return {
    type: 'div',
    props: {
      children: [
        { type: 'Greeting', props: {} },
        {
          type: 'p',
          props: {
            className: 'text-purple-500',
            children: ['The time is: ', { type: 'Clock', props: {} }]
          }
        }
      ]
    }
  };
}
```

我擅自把 `fn` 改名为 `type`。既然像 `<p>` 这样的原语现在是在幕后由 `document.createElement('p')`（不管它是什么）处理，而不是由我们自己的 `p()` 函数处理，再把 `p` 称作“函数”就有误导性了。

我们需要调整 `interpret` 以适应这些变化。如果你不记得它长什么样了，别担心——已经过去一阵子了。这是重要的部分：

```
function interpret(json, knownTags) {
  if (json && json.type) {
    if (knownTags[json.type]) {
      let Component = knownTags[json.type];
      let props = json.props;
      let result = Component(props);
      return interpret(result, knownTags);
    } else {
      let children = json.props.children?.map(arg => interpret(arg, knownTags));
      let props = { ...json.props, children };
      return { type: json.type, props };
    }
  } else if (Array.isArray(json)) {
    return json.map(item => interpret(item, knownTags));
  } else {
    return json;
  }
}
```

我们也会调整 `perform`，加入一些应用 `className` 之类 props 的新逻辑：

```
function perform(json) {
  if (json && json.type) {
    let tagName = json.type;
    let node = document.createElement(tagName);
    for (let [propKey, propValue] of Object.entries(json.props)) {
      if (propKey === 'children') {
        let children = perform(propValue);
        for (let child of [children].flat().filter(Boolean)) {
          node.appendChild(child);
        }
      } else {
        node[propKey] = propValue;
      }
    }
    return node;
  } else if (typeof json === 'string') {
    return document.createTextNode(json);
  } else if (Array.isArray(json)) {
    return json.map(perform);
  } else {
    return json;
  }
}
```

现在 `<p className="text-purple-500">` 就能工作了！

### 更多春季大扫除

现在正好可以再做一个提升体验的改动。

回想一下，现在要把一棵组件树转换成一棵原语树，你必须把所有已知组件作为一个字典传给 `interpret` 函数：

```
function App() {
  return (
    <div>
      <Greeting />
      <p>The time is: <Clock /></p>
    </div>
  );
}
 
function Greeting() {
  return (
    <p>
      Hello, <input placeholder="Who are you?" />
    </p>
  );
}
 
function Clock() {
  return new Date().toString();
}
 
const primitives = interpret(<App />, {
  App,
  Greeting,
  Clock
});
```

[运行代码。](https://codesandbox.io/p/devbox/r2c-forked-sg7dnt?file=%2Fsrc%2Findex.mjs)

然而，这感觉相当傻。当我们写 `<Greeting />` 时，`Greeting` 函数已经在作用域里了。即使它不在，我们也会*想要*把它导入作用域，让这种联系变得明确。那么，既然 `Greeting` 函数已经在作用域中，为什么 `<Greeting />` 语法不能“记住”它指的是哪个 `Greeting` 呢？

我们可以通过采用一个新约定来解决这个问题。如果标签是小写的，比如 `<div>`，我们就让它在标签的对象表示中的 `type` 保持为像 `'div'` 这样的字符串。但如果标签以大写字母开头，比如 `<Greeting />`，我们就把它的 `type` 改为*`Greeting` 函数本身*，而不是 `'Greeting'` 字符串：

```
function App() {
  return {
    type: 'div', // 原始值（字符串）
    props: {
      children: [
        { type: Greeting, props: {} }, // 组件（函数）
        {
          type: 'p', // 原始值（字符串）
          props: {
            children: [
              'The time is: ',
              { type: Clock, props: {} } // 组件（函数）
            ],
          }
        }
      ]
    }
  };
}
```

方便的是，我们早就一直用大写字母作为组件名的开头来区分它们和原语，所以不需要重命名任何东西。

这让我们可以简化 `interpret` 函数。它不再需要随身携带一个 `knownTags` 字典，而只需检查 `typeof json.type`。如果 `json.type` 是一个函数，那么*这个函数本身*就是组件。否则，它一定是原语：

```
function interpret(json) {
  if (json && json.type) {
    if (typeof json.type === 'function') {
      let Component = json.type;
      let props = json.props;
      let result = Component(props);
      return interpret(result);
    } else {
      let children = json.props.children?.map(interpret);
      let props = { ...json.props, children };
      return { type: json.type, props };
    }
  } else if (Array.isArray(json)) {
    return json.map(interpret);
  } else {
    return json;
  }
}
```

现在我们可以直接调用 `interpret`，不必传给它任何额外信息：

```
const primitives = interpret(<App />);
// {
//   type: 'div',
//   props: {
//     children: [{
//       type: 'p',
//       props: {
//         children: [
//           'Hello, ',
//           { type: 'input', props: { placeholder: 'Who are you?' } }
//         ]
//       }
//     }, {
//       type: 'p',
//       props: {
//         children: ['The time is ', 'Wed Apr 09 2025 15:13:04 GMT+0900 (Japan Standard Time)']
//       }
//     }]
//   }
// }
```

`interpret` 函数会由外向内“溶解”我们所有的组件，只留下原语。然后 `perform` 函数会由内向外“溶解”所有原语，生成最终结果——一棵浏览器 DOM 树：

```
const tree = perform(primitives);
// [HTMLDivElement]
document.body.appendChild(tree);
```

### Early 组件与 Late 组件

这是你完整的组件树：

```
export function App() {
  return (
    <div>
      <Greeting />
      <p>The time is: <Clock /></p>
    </div>
  );
}
 
function Greeting() {
  return (
    <p>
      Hello, <input placeholder="Who are you?" />
    </p>
  );
}
 
function Clock() {
  return new Date().toString();
}
```

[运行代码。](https://codesandbox.io/p/devbox/r2c-forked-n5gvxs?file=%2Fsrc%2Findex.mjs)

要打败空间，你必须把这个计算拆分到两台不同的计算机上。

具体来说，`App` 和 `Greeting` 应该在第一台机器上运行，而 `Clock` 组件应该在第二台机器上运行。这两部分计算应该被无缝地组合起来，并在第二台计算机上变成一棵浏览器 DOM 树。你不应该修改组件函数中的任何代码。

我们一步一步来。

你要做的第一件事是把 `Clock` 移到另一个文件中并 `export` 它：

```
export function Clock() {
  return new Date().toString();
}
```

现在你可以从主文件中导入它：

```
import { Clock } from './Clock';
 
export function App() {
  return (
    <div>
      <Greeting />
      <p>The time is: <Clock /></p>
    </div>
  );
}
 
function Greeting() {
  return (
    <p>
      Hello, <input placeholder="Who are you?" />
    </p>
  );
}
```

只不过等等，这并没有把代码拆分到两台计算机上。为此，你需要通过把 `import` 改成 `import tag` 来*打开一扇门*。你从 Early 世界打开这扇门，立即*让 Late 世界显现出来*：

```
import tag { Clock } from './Clock';
 
export function App() {
  return (
    <div>
      <Greeting />
      <p>The time is: <Clock /></p>
    </div>
  );
}
 
function Greeting() {
  return (
    <p>
      Hello, <input placeholder="Who are you?" />
    </p>
  );
}
```

```
export function Clock() {
  return new Date().toString();
}
```

如果你检查 `App` 组件返回的标签，你会注意到 `<Clock />` 标签变成了某种奇特的东西：

```
{
  type: 'div', // 原始值（一个字符串）
  props: {
    children: [{
      type: Greeting, // 组件（一个函数）
      props: {}
    }, {
      type: 'p',
      props: {
        children: [
          'The time is ',
          {
            type: '/src/Clock.js#Clock', // 这是什么？
            props: {}
          }
        ]
      }
    }]
  }
}
```

按照我们最新的约定，以大写字母开头的标签会使用作用域中对应的值作为 `type`——例如，`<Greeting />` 会变成 `{ type: Greeting, props: {} }`，其中 `Greeting` 是一个函数。

`<Clock />` 也是如此。`Clock` 以大写字母开头，所以我们得到 `{ type: Clock, props: {} }`。然而，`Clock` 不是普通的 `import`，而是 `import tag`——我们之前把它定义为与普通 `import` 不同的东西。它给我们的不是 `Clock` *函数*，而是一种*引用*——一个以后能让我们从另一台计算机加载 `Clock` 源代码的标识符。这就是那个 `'/src/Clock.js#Clock'` 字符串。

现在是引入一些术语的好时机：

*   **Early 组件**是在 Early 世界中执行的组件。在这个例子中，`App` 和 `Greeting` 是 Early 组件。
*   **Late 组件**是被发送到 Late 世界去完成工作的组件。在这个例子中，`Clock` 将是唯一的 Late 组件。

你会想先溶解 Early 组件。这会给你 Late 世界的代码以及这段代码所需的数据。你将*用*这段代码构建 Late 世界，并在那里溶解 Late 组件。*那*会给你原语。

听起来是个计划。

我们在 Early 世界中运行 `interpret(<App />)` 并检查结果。注意所有 Early 组件（`App` 和 `Greeting`）是如何从输出中溶解掉的：

```
{
  type: 'div',
  props: {
    children: [{
      type: 'p',
      props: {
        children: [
          'Hello, ',
          { type: 'input', props: { placeholder: 'Who are you?' } }
        ]
      }
    }, {
      type: 'p',
      props: {
        children: [
          'The time is ',
          {
            type: '/src/Clock.js#Clock',
            props: {}
          }
        ]
      }
    }]
  }
}
```

剩下的只有原语（`'div'`、`'p'`、`'input'`）和……Late 组件（这里只有 `'/src/Clock.js#Clock'`）。我们不需要为 Late 组件做任何特殊处理——因为它们不是函数，`interpret` 不会尝试执行它们，而是把它们留在原处，就像它对待原语一样：

```
function interpret(json) {
  if (json && json.type) {
    if (typeof json.type === 'function') {
      let Component = json.type;
      let props = json.props;
      let result = Component(props);
      return interpret(result);
    } else {
      let children = json.props.children?.map(interpret);
      let props = { ...json.props, children };
      return { type: json.type, props };
    }
  } else if (Array.isArray(json)) {
    return json.map(interpret);
  } else {
    return json;
  }
}
```

由于 `interpret` 的结果不包含任何函数，它可以很容易地转换成字符串，然后通过网络发送：

```
const lateComponents = intepret(<App />);
const jsonString = JSON.stringify(lateComponents);
```

之后，在另一台计算机上，你可以把这个字符串再转回对象。你可能会忍不住立即把它传给 `perform` 来创建 DOM 树：

```
const lateComponents = JSON.parse(jsonString);
const tree = perform(lateComponents);
```

然而，这会[给你一个错误](https://codesandbox.io/p/devbox/r2c-forked-t2v9js?file=%2Fsrc%2Findex.mjs)：

```
function perform(json) {
  if (json && json.type) {
    let tagName = json.type;
    // 🔴 Failed to execute 'createElement' on 'Document':
    // 提供的标签名（'/src/Clock.js#Clock'）不是有效名称。
    let node = document.createElement(tagName);
    // ...
    return node;
  } else {
    // ...
  }
}
```

对了——`perform` 只处理原语，但 `Clock` 是一个 Late 组件。你已经在 Early 世界中溶解了 Early 组件（`App`、`Greeting`）。现在你在 Late 世界中，所以是时候溶解 Late 组件（`Clock`）了。

你试着调用 `interpret` 来溶解剩下的组件：

```
const lateComponents = JSON.parse(jsonString);
const primitives = interpret(lateComponents);
```

但什么也没发生。`'/src/Clock.js#Clock'` 标签还在那里。

*空间冷笑。*

啊对，`interpret` 只会尝试执行*函数*：

```
function interpret(json) {
  if (json && json.type) {
    if (typeof json.type === 'function') {
      let Component = json.type;
      let props = json.props;
      let result = Component(props);
      return interpret(result);
    } else {
      let children = json.props.children?.map(interpret);
      let props = { ...json.props, children };
      return { type: json.type, props };
    }
  } else if (Array.isArray(json)) {
    return json.map(interpret);
  } else {
    return json;
  }
}
```

但你手上的只是一个*引用*，一个告诉你去哪里*获取* `Clock` 函数的地址。你仍然需要在这台计算机上真正加载它。

*空间递给你这个：*

```
async function loadReference(lateReference) {
  // 假装它是通过网络或从打包器缓存加载的。
  await new Promise(resolve => setTimeout(resolve, 3000));
  if (lateReference === '/src/Clock.js#Clock') {
    return Clock;
  } else {
    throw Error('Module not found.');
  }
}
```

好吧，假设有人给了你一个能替你做这件事的函数。也许它由环境提供，或者由那些开发打包器的好心人提供。你可以把 `'/src/Clock.js#Clock'` 交给它，它会异步地加载 `Clock`：

```
await loadReference('/src/Clock.js#Clock');
// function Clock(){}
```

这是拼图的最后一块。

每当你的 `JSON.parse` 函数遇到看起来像引用的东西时，就把它传给 `loadReference()`，并保存好每一个这样的 Promise：

```
const pendingPromises = [];
const lateComponents = JSON.parse(jsonString, (key, value) => {
  if (typeof value?.type === 'string' && value.type.includes('#')) {
    // `value.type` 是一个引用，但我们想要一个函数。
    // 开始加载那个函数。
    const promise = loadReference(value.type).then(fn => {
      // 函数加载后，直接在解析后的 JSON 中替换它。
      value.type = fn;
    });
    // 记录它何时完成。
    pendingPromises.push(promise);
  }
  return value;
});
 
// 等待所有引用加载完毕。
await Promise.all(pendingPromises);
```

经过这番处理后，`lateComponents` 对象会是这样：

```
{
  type: 'div',
  props: {
    children: [{
      type: 'p',
      props: {
        children: [
          'Hello, ',
          { type: 'input', props: { placeholder: 'Who are you?' } }
        ]
      }
    }, {
      type: 'p',
      props: {
        children: [
          'The time is ',
          {
            type: Clock, // 加载好的函数！
            props: {}
          }
        ]
      }
    }]
  }
}
```

里面只有 Late 组件和原语——所有引用都已加载。

现在你终于可以把它传给 `interpret`，执行 `Clock` 了。这会给你一棵原语树，你可以用 `perform` 把它变成 DOM：

```
const primitives = interpret(lateComponents);
const tree = perform(primitives);
document.body.appendChild(tree);
```

这样，你就完成了！

在 Early 世界中，你用 `interpret` 溶解所有 Early 组件。这会给你一个字符串，它表示如何在 Late 世界中完成计算：

### 组合

## 尾声

还有一些我们没讲到的内容，但恐怕我的纸快用完了。如果有心的读者沿着这条思路继续下去，可能会发现以下几点：

*   **毒丸（Poison Pills）：** 随着代码库的增长，你会越来越发现自己不想时刻去想自己处在哪个世界——你只想声明自己所依赖的能力。例如，如果你在从数据库读取数据，而整个数据库都存在于 Early 世界中，你会希望有某种方式给数据库模块下“毒丸”，使得从 Late 世界导入它会立即导致构建错误（而不是，比如说，试图把数据库代码打包进去）。在 Node.js 中，[自定义用户条件（custom user conditions）](https://nodejs.org/api/packages.html#resolving-user-conditions)提供了一种方便的方式来强制执行这一点。
*   **指令（Directives）：** 事实证明，`import tag` 和 `import rpc` 虽然在理论上很优雅，但在实践中用起来并不顺手。两个世界之间的技术隔离必须保持坚固；然而，在心理上，你会逐渐转向这样写代码：仿佛处在哪个世界并不重要。有了毒丸来确保东西不会在*错误*的世界中执行，你基本上可以“自动驾驶”般地移动边界——四处挪动代码，并根据构建错误开凿新的“门”。当你*想要*开凿一扇“门”时，你会发现把它标记在 *`export` 旁边*比标记在 `import` 的地方更自然。这能让你快速地让边界“出现”或“消失”——被导入的模块处在哪个世界成了一个实现细节。给导出加注解的一种方式是（滥）用[指令语法](https://stackoverflow.com/a/37535869)。如果你再把 Early 和 Late 改名为更有描述性的名字（例如，“Early”可以变成“Server（服务器）”，“Late”可以变成“Client（客户端）”），那么 `import tag` 就可以被放在 `export` 旁边的 [`'use client'`](https://react.dev/reference/rsc/use-client) 取代，而 `import rpc` 可以变成 [`'use server'`](https://react.dev/reference/rsc/use-server)。
*   **数据获取：** Early 世界（或者你愿意的话，叫 Server 世界）是获取数据的完美场所，因为你有机会把代码部署到低延迟的环境中。调整代码让“思考”阶段可以是异步的并不难；你可以把它当作练习，看看能否做到。
*   **流式执行：** 在我们的例子中，计算的每个阶段都是顺序发生的：前一个阶段完全结束之前，下一个阶段不会开始。然而在实践中，由于组件可以由外向内执行，你可以把*所有*阶段混合起来，以非阻塞的方式执行它们。具体来说，与其等待一整棵 Late 组件（或者我们该叫它们 Client 组件？）的 JSON 树，你可以开发一种专门的传输格式，在未完成的计算处留下“空洞”，之后再用更多 JSON 填补这些空洞。
*   **有状态的 Late 世界：** 如果你引入状态（State）的概念，Late 组件会变得有用得多。这再次强调了标签是一个*潜在的*函数调用——它可能发生，可能不发生，也可能*发生很多次*。每当你改变某个 Late 组件的状态时，你都可以重新执行它，而不影响任何 Early 组件。这确保了状态变化能保持可预期的即时性。
*   **重新利用 Early 和 Late 世界：** 记住，Early 和 Late 世界不必与现有的“服务器”和“客户端”概念一一对应。例如，如果你的 Late 组件是有状态的，而你有一台服务器，你可能会发现在那台服务器上*同时*运行 Early *和* Late 世界很有用。在服务器上，你会用*初始*状态调用 Late 世界——以生成一棵初始的原语树，然后把它转换成像 HTML 这样的格式。这让你可以很早就开始向用户展示内容——在任何 Late 组件在用户的机器上加载之前。
*   **缓存：** Early 世界不必按需运行。事实上，你可以提前运行它，并存储其计算的中间结果（这通常被称为静态站点生成）。如果你雄心勃勃，你甚至可以再添加一个世界——[缓存世界](https://nextjs.org/docs/app/api-reference/directives/use-cache)——来跨请求复用部分计算。
