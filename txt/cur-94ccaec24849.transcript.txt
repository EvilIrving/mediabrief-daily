就近放置（Colocation）

我们都希望代码库易于维护，所以一开始都怀着最好的意愿，想让代码库（或我们负责的那一角）可维护、易理解。随着时间推移、代码库不断增长，管理依赖（JS、CSS、图片等）会变得越来越难。项目越大，代码库中就有越来越多的部分变成“部落知识”（只有你或少数几个人知道的知识），而这类知识会助长“技术债”（不管这个说法准不准确）。

我希望代码库不仅对我（写代码的人）来说易于管理，对我的队友、未来的维护者，以及六个月后的我自己也是如此。我想我们都同意，这是一个值得在代码库中努力追求的理想。我们手头有很多不同的工具和技巧可以实现它。

我们来谈谈代码注释

我不想讨论该不该给代码写注释（应该写），也不想讨论注释该写什么（你应该在注释里解释为什么要做一件出人意料的事，好让后来的人理解导致这段出人意料或古怪的代码的那些决定）。（好吧，也许我确实想稍微谈谈这个。）我想关注的是这些注释放在哪里。我们通常会把注释和它所解释的代码“就近放置”，尽可能紧挨着相关代码。

设想一下，如果我们换种做法呢？如果我们把这些注释放进一个完全独立的文件里，比如一个巨大的 DOCUMENTATION.md 文件，甚至是一个和 src/ 目录一一对应的 docs/ 目录。听起来好玩吗？是啊，我也不觉得。不把注释和它所解释的代码放在一起，会遇到一些严重的问题：

- 可维护性：它们会更快地不同步或过时（比现在还快）。我们会移动或删除某个 src/ 文件，却不去更新对应的 docs/ 文件。
- 适用性：看 src/ 里代码的人可能会漏掉 docs/ 里某条重要的注释，或者不给自己的代码写注释，因为他们没意识到自己正在编辑的 src/ 文件已经有一个对应的 docs/ 文件。
- 易用性：在这种结构下，从一个位置切换到另一个位置的上下文切换也会很麻烦。要和分散在多个位置的文件打交道，可能很难确保你拿到了维护一个组件所需的全部东西。

我们当然可以为这种注释风格制定一套约定，但我们为什么要这么做呢？把注释和它所解释的代码放在一起，不是更简单吗？

那又怎样？

现在你大概在想：“对啊，废话，这就是为什么没人搞 docs/ 这一套，大家都把注释和代码放在一起。这很明显。你到底想说什么？”我想说的是，就近放置的好处无处不在。

HTML/视图

以 HTML 为例。把注释就近放置的所有好处，同样适用于我们的模板。在 React 这样的现代框架出现之前，视图逻辑和视图模板会放在完全不同的目录里，这就会陷入上面描述的同样问题。如今，像 React 和 Vue 那样把它们放在同一个文件里要常见得多。用 Angular 时，即使不在同一个文件里，模板文件至少也紧挨着与之关联的 JS 文件。

CSS

这个概念同样很适用于 CSS。我不打算和你争论 CSS-in-JS 的优劣（它棒极了），但它的好处简直好得出奇。在这里了解更多。

测试

文件就近放置的概念也非常适用于单元测试。你有多常见到这样的项目：有一个 src/ 目录，还有一个塞满单元测试、试图镜像 src/ 目录的 test/ 目录？上面描述的所有陷阱在这里同样适用。我大概不会走到把单元测试和代码放在同一个文件里的地步，但我也不完全排除这是个有意思的想法（具体实现留给读者作为练习）。

为了让代码库更易维护，我们应该把测试文件和它所测试的文件或文件组放在一起。这能确保新人（或六个月后的我）来看代码时，立刻就能看到这个模块有测试，并把这些测试当作了解该模块的参考。当他们做出修改时，也会提醒他们更新（增加、删除、修改）测试，以反映他们的改动。

状态

应用和组件的状态也能获得同样的好处。状态与使用它的界面之间越是脱节、越是间接，就越难维护。让状态局部化不仅有利于可维护性，还能提升应用的性能：组件树一角的状态变化，比树顶端的状态变化重新渲染的组件要少得多。让你的状态局部化。

“可复用”的工具文件

这同样适用于“工具”文件和函数。设想你正在写一个组件，看到一段不错的代码可以抽成一个独立的函数。你把它抽了出来，心想：“嗯……我敢打赌很多人都用得上这个。”于是你把它拿出来，放进应用的 utils/ 目录，然后继续过你的日子。

后来，你的组件被删除了，但你写的那个工具函数眼不见心不烦，它（连同它的测试）保留了下来，因为删除组件的人以为它被更广泛地使用着。多年来，工程师们辛辛苦苦地确保这个函数和它的测试继续正常运行，却根本没意识到它已经完全不需要了。白费力气，徒增认知负担。

如果你当初就把这个函数直接留在使用它的文件里，故事就会完全不同。我不是说不用费心给复杂的工具函数写单元测试（请务必写），而是说把它们放得离需要它们的地方更近，能帮你避免问题。

原则

就近放置的概念可以归结为这样一条基本原则：

把代码放在尽可能靠近它相关之处。

你也可以说：“一起变化的东西，应该在合理范围内尽量放在一起。”（Dan Abramov 曾经对我说过类似的话。）

让开源变得（更）容易

除了避免前面讨论的问题，用这种方式组织项目还有其他好处。把一个组件变成开源项目，往往只需要把文件夹复制粘贴到另一个项目里，再发布到 npm。然后你只要在自己的项目里安装它、更新 require/import 语句，就大功告成了。

例外

当然，对于覆盖整个系统或部分系统、说明各部分如何集成的文档，确实有充分的理由单独存在。那么跨越多个组件的集成测试或端到端测试该放在哪里呢？你可能认为这些是例外，但它们其实也可以很好地遵循上面提到的原则。

如果我的应用里有一部分与用户认证相关，而我想记录这个流程，我可以在存放所有用户认证相关模块的文件夹里放一个 README.md 文件。如果我需要为这个流程编写集成测试，也可以把这些测试的文件放在同一个文件夹里。

至于端到端测试，通常放在项目根目录更合理。它们的范围超出了项目本身，延伸到系统的其他部分，所以在我看来把它们放在一个单独的目录里是合理的。它们其实并不和 src/ 里的文件一一对应。事实上，端到端测试根本不关心 src/ 是如何组织的。在 src/ 目录里重构、移动文件，完全不应该需要修改端到端测试。

结论

我们的目标是构建尽可能易于维护的软件。我们从注释的就近放置中获得的可维护性、适用性和易用性，同样可以从其他东西的就近放置中获得。如果你从没试过，我建议你试一试。

附言：如果你担心违反“关注点分离”，我建议你看看 Pete Hunt 的这场演讲，重新评估一下它的含义 😀。

再附言：我还应该指出，这一点也非常适用于图片以及其他任何资源。而当你使用 webpack 这样的工具时，就近放置这些资源也简单得不得了。说实话，在我看来这正是 webpack 的核心价值主张之一。
