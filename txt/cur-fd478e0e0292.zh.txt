从 AI 智能体到远程代码执行：搭建一套漏洞研究工作流

优势不在 AI 模型本身，而在于你如何围绕它组装系统。我们构建了一套定制的智能体框架（harness），把漏洞研究拆成若干独立阶段，从代码库探索、分析，到验证和利用。把这套工作流用于 FreeRDP 后，它发现了几个可以串联成远程代码执行的漏洞，整个过程中由人类研究员验证发现并引导方向。

## 引言

安全研究员一天的大部分时间都在读代码。有时要读几千行，只为找到真正要紧的那几行。大部分阅读并不是有意义的工作发生的地方。真正的工作是"起疑的那一刻"：这个长度字段在这里校验了、在那里却没有；这个状态可以进入两次；这个循环信任了一个它不该信任的值。那一刻只需几秒，抵达那一刻却可能要好几天。

智能体能在几分钟内遍历一个代码库，把散落在各个文件中的函数联系起来，追踪那些研究员手工拼凑要花长得多时间的关系。不太清楚的是，这么大的产出量最终得到的是什么：是真实的漏洞，还是一堆需要逐一筛查的误报。

我们想把这种原始算力变成一种方法。我们为漏洞研究构建了一个智能体框架：也就是管理 AI 智能体完成任务所需的工具、上下文、结构和规则的外围系统。在我们这里，它包括一张覆盖目标的可查询图谱、一个确定性分析核心、一组解读其输出的"透镜"，以及一条供智能体逐级推进的分阶段流水线。框架负责提出攻击向量、探索相关代码路径并编写概念验证（PoC），每个关键步骤都有研究员把关。

我们的目标不是一键式漏洞查找器，而是"一套可以运行、检查和复现的方法论"：智能体负责打基础、关联发现、提出线索，研究员负责验证线索、指挥调查，并决定哪些值得投入更多时间。我们真正追求的，是让研究员一整天都在"怀疑"，而不是在"翻代码"。

本文跟随这套工作流，从对代码库的第一遍扫描一直走到可用的漏洞利用，并展示沿途每个阶段的输出。我们在 FreeRDP（一个开源 RDP 客户端）这个大型目标上做了测试，它发现了两个可以串联成"客户端远程代码执行"的漏洞。

## 问题所在，以及我们的应对

2025 年 12 月下旬，一个人把矛头对准了墨西哥的九个政府机构。不是一个团伙，也不是国家级项目。在随后七周里，此人输入了 1,088 条指令，产生了 5,317 条命令，分布在 34 个独立会话中执行。Claude Code 承担了约 75% 的实时攻击操作，涉及 305 台内部服务器；另一条基于 GPT-4.1 搭建的流水线负责阅读窃取到的数据并规划下一步行动。近 2 亿条记录被窃取：税务申报、民事登记、患者数据、车辆记录、选民名册。这些取证结果来自攻击者自己被缴获的服务器。

这里有用的数字是比例：每输入一条指令，大约执行了五条命令。三个月前，一场与中国有关联的行动中也出现了类似模式：据报道，模型承担了针对约三十个组织的战术工作的 80% 到 90%。

对防御方而言，重要的变化在于一个操作者能持续完成的工作量。墨西哥那次行动只由一个人实施，而自动化覆盖了以前需要多种技能组合才能完成的任务。防御方常常假设攻击者的技能水平给他们能做的事设了上限；智能体工具削弱了这一假设。

那场行动并没有依赖新颖的利用技术，它的意义在于一个操作者能完成的工作规模。这就引出了本项目背后的防御问题：如果自动化能降低大规模利用已知弱点的成本，它能否同样降低发现和理解新弱点的成本？我们构建这套工作流就是为了检验这个问题，并把它对准了 FreeRDP。

同样的规模化产出能力，也给防御方带来了另一个问题：产出更多不一定意味着有用的发现更多。curl 就很好地说明了这一点。它收到的报告中，确认属实的漏洞比例从 15% 以上跌到 5% 以下，2025 年大约每五份报告就有一份是机器生成的噪音，而每份都要耗费志愿者团队几个小时。这个漏洞赏金计划最终关闭了。这些报告之所以代价高昂，是因为很多看起来似是而非：它们引用真实的函数和代码路径，描述的攻击场景必须经过调查才能排除。

因此，稀缺资源是"研究员的注意力"，而不是系统能产出多少发现。我们把工作流设计成先大范围搜索，再花机器时间过滤和验证候选，然后才请研究员去检查。

## 已有的方案，以及我们为何仍要自己做

已有几个系统用不同方法解决了这个问题的相邻部分：Google 用于 AI 辅助漏洞研究的 Big Sleep，OpenAI 用于对代码仓库做持续安全分析的 Aardvark，以及为 DARPA 的 AI 网络挑战赛（AIxCC）开发的自主系统。

它们的成果表明，智能体辅助的漏洞研究是可行的。Big Sleep 在 SQLite 中发现了一个威胁行为者已经知晓的内存破坏漏洞，并在 FFmpeg、ImageMagick 等项目中报告了另外二十个漏洞。Aardvark（现已更名为 Codex Security）根据代码仓库构建威胁模型，对照它测试每一次提交，并在沙箱中验证发现。DARPA 的 AI 网络挑战赛则采取了另一种思路，系统被设计成自主发现并修补漏洞。

但它们各自都是为与我们"相邻"的任务而建，而不是为我们的任务。Aardvark 在你提交代码时监视仓库，如果代码是你自己的，这个思路很对；但如果你在审计一个从未接触过的东西，它就毫无帮助。Big Sleep 是 Google 内部工具。AIxCC 的系统预设已有模糊测试框架，并以无人值守运行作为评分标准；而我们关心的 FreeRDP 攻击面并没有现成的模糊测试框架，我们也无意无人值守地运行。

更深层的原因更简单："一个自己决定一切的工具，交给你的只有结论，别无其他。"然后你得重做一遍工作来确认它是否属实，成本大致相当于自己去发现它。curl 的维护者在 2025 年就一直在对陌生人的报告做这件事。我们可不想对自家工具的报告也这么做。

## 工作流全景

这套架构把两种我们想区别使用的特性分开：语言模型擅长生成和探索假设，但它们的输出不可复现（因为其非确定性的本质）。

因此系统分为两层。"确定性核心"把代码索引成可查询的图谱，从攻击者可控的数据源到危险的汇点运行静态污点分析，再把结果送入一组更窄的透镜：已知的 CVE 和 CWE 模式，以及少量针对目标的专门检查。其上的"智能体层"负责形成假设、阅读核心发掘出的内容、判断哪些是真的，并把它推进到 PoC。

核心的调校偏向"召回率而非精确率"。它有意过量产出，因为一条从未生成的线索就再也找不回来了；而智能体层的存在，就是为了让这种过量产出变得负担得起。它的作用不是找 bug，而是"吸收大范围搜索必然产生的噪音"，让研究员只看到幸存下来的东西。

核心是可复现的。智能体层不可复现，也不需要可复现，它需要的是"可审计"。

具体来说，流水线分八个阶段运行：

```
graph → recon → slicing → analysis → triage → poc → chain → exploit
```

| 阶段 | 作用 |
| --- | --- |
| `graph`（图谱） | 索引代码库。 |
| `recon`（侦察） | 把结构转化为攻击面。 |
| `slicing`（切片） | 把范围收窄到单个假设——没有哪个智能体能在整个仓库上推理得好。 |
| `analysis`（分析） | 在该切片上运行污点分析、模式匹配和其他透镜。 |
| `triage`（分诊） | 把输出分为"真实""不明"和"噪音"。 |
| `poc`（概念验证） | 尝试让幸存者真正触发。 |
| `chain`（串链） | 判断两个弱原语能否组合成一个强原语。 |
| `exploit`（利用） | 把经过验证的原语或链变成可用的漏洞利用。 |

（图：八阶段工作流）

研究员在阶段"之间"工作，从不在阶段内部插手。这也意味着他们可以从任一阶段介入：端到端跑完全程；在 recon 之后停下，把假设拿到别处使用；或者把自己的一个发现交给流水线，让它做 triage 和 poc。没有哪个阶段假定前一阶段一定是由我们的系统而不是由人来完成的。

本文余下部分把这些阶段应用到 FreeRDP 上，并展示每一步产出的成果。

## 以 FreeRDP 为例深入工作流

我们把工作流对准 FreeRDP 在提交 `993499447` 时的代码树，别的什么都没给它。没有 FreeRDP 过往 CVE 列表，没有模糊测试语料，也没有提示哪些子系统历来比较薄弱。`git clone`，然后开跑。

FreeRDP 是大多数 Linux RDP 客户端所基于的库：Remmina、GNOME Connections、KRDC，以及 Apache Guacamole 的 guacd 中的 RDP 支持。同一代码树也实现了服务端，GNOME Remote Desktop 和 KRDP 用的就是它，所以两种角色共享的解析代码会从两个方向暴露出来。我们审计的是客户端，在客户端从网络上解析的每个字节，最终都来自用户选择信任的某台服务器。

### 第 1 步：图谱、侦察与切片

```
graph (*) → recon (*) → slicing (*) → analysis → triage → poc → chain → exploit
(*) 下文讲解的步骤
```

Graph 把目标索引成智能体可以查询的表示：本次运行共有 13,506 个函数、3,105 个类型和 31,705 条调用边，其中包括为已解析的函数指针添加的合成边。

这张图谱并不是用来整体浏览的，它的价值在于收窄视野。例如，`libfreerdp/core/nego.c` 负责 RDP 连接开始时的协商交换。解析这个文件，就能给智能体提供它的定义、参数以及与代码库其余部分的关系。

（图：nego.c 在图谱中的解析结果）

在此基础上，可达性查询把一个暴露的入口点变成一个工作集：

```
$ sift graph reachable nego_recv --files
libfreerdp/core/nego.c
libfreerdp/core/tpdu.c
libfreerdp/core/tpkt.c
… 6 more
```

从 `nego_recv` 出发，工作集一共是九个文件。其他入口点范围更大：`rdpgfx_recv_pdu` 可达 67 个文件，`rdp_recv_pdu` 可达 65 个。切片利用这些关系，让每次调查都足够小，使智能体无需把整个仓库装进上下文就能推理。

Recon 补充了暴露面信息。它把代码分组为组件，估计攻击者可控的数据到达每个组件的直接程度，并生成威胁模型、屏障图和一份排好序的切片列表。

（图：按暴露程度划分的组件）

本次运行产生了 304 个切片。下面讨论的两个发现分别来自第 166 号切片 `libfreerdp/core/nego` 和第 109 号切片 `channels/urbdrc/client/data_transfer`。纯机械的排序不会把其中任何一个排在前面。研究员把排序当作地图，而不是判决。

### 第 2 步：分析

```
graph → recon → slicing → analysis (*) → triage → poc → chain → exploit
```

每个切片独立分析。确定性核心构建更深的图谱，运行静态污点分析，并应用配置好的透镜。污点分析运行两次：第一次使用引擎已知的源和汇，第二次在智能体识别出目标特有的"词汇"之后再跑，比如 FreeRDP 的流操作、读取宏和内存分配封装函数。

在第 166 号切片中，引擎产生了 14 个发现。其中两个放在一起变得很有意思：

```
f-007  attacker-controlled length stored in nego->RoutingTokenLength
                         ↕ ?
f-005  same field later used as a Stream_Write size
```

（即：f-007 攻击者可控的长度被存入 nego->RoutingTokenLength；f-005 同一字段后来被用作 Stream_Write 的写入大小。）

引擎能确定两个端点，但无法确定它们在 `nego` 对象生命周期中的关系。它把两者分开报告，而不是凭空捏造一条数据流边。这正是下一阶段要解决的那种模糊性。

（图：f-005 与 f-007 合并）

第 109 号切片产生了 116 个发现。其中两个指向一条 USB 重定向完成路径：出错时，攻击者提供的 `OutputBufferSize` 被保留下来，尽管实际上没有写入任何数据。客户端随后在发送响应时使用这个大小，从而泄露了残留在堆分配中的字节。

此时，两个切片共产生了 130 个发现，但它们仍只是候选，不是已确认的漏洞。这一阶段出现误报是意料之中的，每个发现都还需要调查和验证。

### 第 3 步：分诊与 PoC

```
graph → recon → slicing → analysis → triage (*) → poc (*) → chain → exploit
```

Triage 在分类之前先把相关发现归组。本次运行中，130 个发现归为 36 个簇：20 个真实且可达，3 个潜在，3 个混合，10 个误报。

这些分类随后经过动态检验。对每个候选，流水线针对 FreeRDP 构建一个小型测试框架，并在 AddressSanitizer（ASan）下运行。正是在这里，一个看似合理的静态发现要么变得可测量，要么被丢弃。

对第 166 号切片，triage 把 `f-007` 和 `f-005` 重新合到一起。`f-007` 终止于 `nego_set_routing_token`，在那里由网络数据得出的长度被存入 `nego->RoutingTokenLength`。`f-005` 在后面接上同一个字段：它在 `nego_send_negotiation_request` 中被作为长度参数传给 `Stream_Write`。

把两个发现连起来，就确立了一条候选路径，但还不是漏洞。`nego->RoutingTokenLength` 有两种被赋值的途径。第一种最后证明是安全的：协议中的一个长度字段把路由令牌限制在不会溢出目标缓冲区的大小。PoC 证实了这个边界，于是这条路径被丢弃。

第二种途径来自"服务器重定向 PDU"（Server Redirection PDU）。恶意服务器可以提供 `LoadBalanceInfo`，FreeRDP 在建立重定向后的连接时会把它重新用作路由令牌。这条路径没有同样的长度限制。

我们用一台恶意服务器和一个带 ASan 插桩的 FreeRDP 客户端复现了它。服务器发送了 600 字节的 `LoadBalanceInfo` 载荷，加上 cookie 头之后变成 615 字节的路由令牌。在 `Stream_Write` 处，FreeRDP 试图把这 615 字节复制到 `nego_send_negotiation_request` 创建的 512 字节分配空间中：

```
==4514==ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 615

#2  Stream_Write
#4  nego_send_negotiation_request  libfreerdp/core/nego.c:1098
#9  rdp_client_redirect            libfreerdp/core/connection.c:715

0x75e976227180 is located 0 bytes after 512-byte region
[0x75e976226f80,0x75e976227180) allocated by thread T2 here:

#1  Stream_New
#2  nego_send_negotiation_request  libfreerdp/core/nego.c:1083
```

`rdp_client_redirect` 这一栈帧证实，溢出是经由服务器驱动的重定向路径触发的，而不是测试框架直接调用了有漏洞的函数。

测试使用的是 `WITH_VERBOSE_WINPR_ASSERT=OFF`，也就是 Debian 和 Ubuntu 构建所用的配置。如果启用详细断言，边界检查会在越界写入到达 `memcpy` 之前让客户端中止。

USB 重定向的发现也经过了同样的验证流程。在那个案例中，候选原语是未初始化堆内存泄露。我们把 ASan 配置为用 `0xcd` 填充新的堆分配；同样的字节模式原封不动地出现在 FreeRDP 发出的 PDU 中：

```
[poc] heap pattern bytes (0xcd) in region [36..100): 64 / 64
```

只有通过这种动态验证的发现，才会被送到串链阶段。

### 第 4 步：串链

```
graph → recon → slicing → analysis → triage → poc → chain (*) → exploit
```

串链阶段只处理经过验证的簇。在这里，协商阶段的 bug 提供了一个攻击者可控但"盲"的堆写入，而 USB 重定向的 bug 提供了对堆内容的可见性。泄露发生在会话建立之后，随后一次服务器重定向可以强制客户端重新连接并触发写入。这两个原语结合起来，使远程代码执行变得可信，但尚未得到证明。

### 第 5 步：利用

```
graph → recon → slicing → analysis → triage → poc → chain → exploit (*)
```

到了利用阶段，智能体与研究员之间的分工平衡发生了变化。前面各阶段产出的成果检查起来成本很低：一条路径、一个源码位置、一份 ASan 跟踪或一个测量值。利用阶段就没那么宽容了。比如，一个失败的堆布局假设，往往说明不了它为什么失败。

所以我们给利用阶段配了专门的框架，而不是让通用智能体自由迭代。它提供利用相关的专门知识，并把过程拆成一组关卡，每一关都必须验证通过，智能体才能继续往下走。

这让智能体在有边界的任务上保持有用：解读泄露的字节、枚举写入可触及的对象、测试堆布局假设、为单个实验生成测试框架。这也让它的进展可以检查。成功的一步意味着某个预期属性已被实际测量到，而不仅仅是模型认为这个方法说得通。

局限依然存在。在这次运行中，智能体并没有独立收敛到完整的利用。当我们所用的模型不再取得有用进展时，我们介入了两次：第一次是在从泄露中推导 libc 基址时，第二次是在把各原语组合成可用载荷时。

利用过程依次经历了以下阶段：

```
✔  Lab set up: client VM, hostile server
✔  Cluster 2 write primitive measured
✔  Control-flow hijack demonstrated
✘  libc base from the cluster 28 leak
── researcher intervention 1 ──
✔  libc base recovered
✔  ASLR defeated
✘  Working payload
── researcher intervention 2 ──
✔  Leak and write composed into one session
→  /tmp/pwned
```

（即：搭好实验环境——客户端虚拟机与恶意服务器；测得第 2 簇的写原语；演示控制流劫持；未能从第 28 簇的泄露得到 libc 基址——研究员第一次介入；恢复 libc 基址；绕过 ASLR；未能做出可用载荷——研究员第二次介入；在同一会话中组合泄露与写入；最终生成 /tmp/pwned。）

（动图：客户端远程代码执行尝试）

## 结论

在 FreeRDP 上，这套工作流在本文讨论的两个切片中共产生了 130 个发现。分诊把它们归为 36 个簇，其中 20 个被复现为真实且可达。有两个发现提供了实现客户端远程代码执行所用的原语。

这套工作流并没有消除噪音，也不是为此设计的。确定性核心之所以能大范围搜索，是因为并不指望研究员检查它产出的每一个发现。切片让单次调查保持有界，聚簇把相关证据汇集起来，PoC 则提供了一种手段，在投入更多时间之前否定或证实由此产生的假设。

切片排序也说明了我们为什么要让研究员留在环路中。两个相关切片在 304 个中分别排第 166 和第 109 位。排序能考虑解析量、暴露程度等属性，但无法涵盖一个组件可能引起安全研究员兴趣的所有理由。它提供的是一个有序的搜索空间，而不是决定该调查什么。

从 `git clone` 到向维护者提交报告，用了四天，对象是一个约五十万行、多年来一直被审计和模糊测试的 C 代码库。模型只是这个过程的一部分。围绕它的，是让其输出可用于漏洞研究的那些部件：可查询的代码表示、确定性分析、有界切片、附在发现上的证据、动态验证、利用框架，以及研究员检查点。

两个漏洞都已报告给 FreeRDP 维护者。FreeRDP 只是我们的测试案例，真正的目标是工作流本身：它能否让大型代码库变得切实可查，又不让研究员的时间成为瓶颈。
