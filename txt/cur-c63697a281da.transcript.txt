主持人 A：大家好，欢迎收听硬地骇客。过去很长一段时间，我们都在聊 agent，但大多数讨论都集中在模型上，比如 Claude 和 ChatGPT 谁更强，国产模型里谁跟 Claude Opus 4.7 更接近。但今天我们想换个角度。同一个模型，放在普通的聊天框里，它可能只是给你一段建议；但你如果把它放在 Claude Code 里，它就能读文件、改代码、给你跑测试、给你看有什么报错，甚至完成整个功能。还有一点，同一个模型，放在 Claude Code 里和放在 OpenCode 里，表现可能也千差万别。这中间发生的变化，其实不只是模型，还有模型周围的那套工作环境。我们今天要聊的核心就是这套环境，叫 agent harness。我就先不扯这么多了，你们能不能先给大家介绍一下，到底什么是 agent harness？

主持人 C：好。harness 这个概念相对还是比较新的，可能也就是今年才开始讲。我感觉大家对这个概念的理解也还在变化当中。有一种说法是：agent 就是大模型加上 harness。这种理解是说，除了大模型之外，所有帮助大模型去工作的外围东西都是 harness。也有一种理解认为，大模型、agent、harness 是三层东西：大模型在最底下，agent 包着大模型，赋予它角色、工作能力、习惯之类的——agent 是给大模型赋予人格的；harness 则是给整个 agent 赋予工具、赋予环境的。我之前还看到 Twitter 上有人说，他以为的 harness 就是那种完全自主的 AI，不需要人去跟它聊天，它自己就能把活全干完。我觉得这个理解肯定是不对的。你可以做一套不需要人去聊天的 harness 体系，但那只是因为你把 harness 做成了这个样子，而不是说 harness 就一定是这个样子。

我自己对 harness 的理解是这样的。我觉得 harness 这个词挺巧妙的，它就是挽具嘛，用来控制牛马的东西。如果不是因为 agent harness 这个词，我都不知道以前就有一个东西叫 test harness，也就是说这个概念不是在 agent 领域才新出现的。从这个名字里我们也能感觉到，harness 是帮助人去控制和驾驭 agent，或者说驾驭大模型的。人骑马起码需要一副马鞍，用 agent 也需要一副“agent 鞍”。所以它其实是一个围绕 agent、去控制它、增强它的体系。当然也不完全是控制和驾驭，它也是让 agent 和真实工作环境连接起来的一种实现。它纯粹是一个工程层面的东西，不像大模型那样是自主性很强的东西，而是框得比较死的工程实现。

但说到这里，仔细想想会觉得有点耳熟。以前 agent 其实就是在大模型上面做这件事的，对吧？在 harness 出现之前，我们聊 agent 的时候会聊 agent 里应该包含什么，比如提供能力：集成一些 MCP，或者给一些外部工具调用能力，function call 之类的，这些以前是在 agent 层面的。但今天这一层的职责似乎被划分到了 harness 这一层。很多概念原本在以前的 agent 概念里，只是今天新增的这一层，把能力执行、权限控制、操作日志记录，甚至包括对大模型或 agent 的评分——怎么评价它执行得好不好——都放到了 harness 这一层。这些是比较客观、比较“实权”的部分，也就是 harness 掌控了实际的权力。agent 可以放飞自我，但 harness 手握缰绳。如果让我来说的话，没有套上 harness 的 agent 是自由的，可以随意发挥。我们今天看很多新闻，比如之前那个把数据库全删了的事情，这种东西其实就应该由 harness 去控制。套上了 harness，agent 才能更稳定、更可靠地工作。我理解它是这样一个东西。

主持人 A：harness 这个词也挺有意思的，刚才你也讲它是马具相关的东西。之前不是火了一个叫“小龙虾”的东西，也就是 OpenClaw 嘛，OpenClaw 之后现在又有一个新的东西叫 Hermes Agent。Hermes 就是爱马仕，爱马仕最早出名的其实就是马具，后来才变成做包的。这个名字起得也蛮有意思。好，我们回过头来，不扯别的了。我们以前用 LLM，主要是在 LLM 里用它的 tool call、MCP、skills 等等。现在变成了：以前是在 LLM 里控制这些工具，现在变成要用一个外部的东西来控制大模型，相当于控制反转了，对吧？那为什么到今天这个阶段，我们需要用 harness 来控制 LLM 呢？这个逻辑是怎么产生的？

主持人 B：从我的角度理解，像 tool、MCP，当然 skills 是更高层级的封装，这些东西不能简单理解成单纯是从 LLM 内部向外做控制。确实有这种成分，比如大模型要调用外部的一个 API 去做某个操作，这好像确实是向外控制。但实际上还有很大一部分工具调用，目的是让大模型从外部世界获取大量数据和状态，因为它需要这些数据来判断环境、感知上下文和背景。所以它调用工具的目的，本身也是让自己工作得更好，是用来约束大模型的。从这个角度看，它也不单纯是我们说的从内部控制外部。比如我们去调用编译工具，检查大模型自己写的代码是否正确、能否编译通过，这本身也是在约束自己、判断自己的工作成果是否正确。还有很多 skills，比如做设计、做 PPT 的，你去看那些 skill，很多时候都是在定义规范，比如设计风格，以及整个工作流应该怎么运作，这些明显都是用来约束 LLM 的。所以你写 skill 也好，开发一个 tool 或 MCP 也好，大多数时候都是在给 LLM 提供一种约束能力，让它在这条路上跑得更自然，达到你预期的结果。

所以本质上，大模型能调用工具、能决策用什么工具，目的也是让自己工作得更好。我认为这里不需要纠结它是不是存在反转，它可能并不是一种反转，而是一种进化路线，整个大模型发展的路径就是这样。我始终认为它是“训练模型的智能”加“外部控制”两条腿在走路。早期大模型很弱的时候，大家更多把注意力放在训练模型的智能上；当智能达到一定程度、已经足够之后，大家就开始把注意力分配到外部的工程环境上。我们也可以看到，早期 LLM 最弱的时候，大家的注意力在 prompt 上，那时候强调 prompt engineering，很多时候就是在 prompt 上控制 LLM。那个时期大家研究 prompt 有各种奇技淫巧，这些技巧用来干嘛？都是用来控制大模型，让它工作得更好。后来模型能力越来越强，比如支持了工具调用。支持工具之后有一个很大的好处：你可以通过写代码、通过工程的方式去控制 LLM。一直到今天，所有的 MCP、skills，包括现在的 context engineering，以及 harness engineering，很多都要借助工具调用。所以本质上是因为工具调用能力在 LLM 上增强了，大家发现有更多可以研究的方式去控制 LLM。所以我一直认为，外部控制这件事是伴随整个大模型的发展路径逐渐增强的。

主持人 C：听你说“控制反转”，我觉得“控制”这个词，我会更倾向于理解成增强和约束大模型的行为。因为在 agent harness 这个体系里，真正拥有自主性的还是 agent 或者说大模型，它会自己决定要干什么。只不过这件事能不能干，或者干的时候需要的额外外部信息，是由 harness 提供给它的。以前没有 harness 这一层的时候，等于整个 agent 一体，自己同时是决策者、执行者，同时又是权限管理员、审查人员，所有角色都它一个做了。这样实现起来很方便，但 agent 的权力就太大了。今天 agent 的能力越来越强，自主性也越来越强。我们看过的那些例子都是这样：它的自主性强调的是想尽一切办法去实现目的，各种高危操作它都做得出来。如果你不能很好地控制它，捅的娄子可能就会越来越大。随着大家的摸索和实践，自然就开始划分权责和层次，这时就出现了独立于 agent 之外、专门做约束和限制的 harness 层。harness 层是受控的，它大部分规则和能力是硬编码进去的，或者有一些策略去做这件事。总之它跟大模型不一样，不是完全自主的。你可能在边缘用模型做一些辅助，但核心职责是确定性的。比如不能直接访问 workspace 之外的路径，不能访问用户目录下的高敏感文件之类的，这些都是 harness 硬编码掉的，一定不能让模型去判断。它就在这些方面做约束。

主持人 A：harness 去约束模型的行为，能不能具体一点？比如一个 harness 系统，实际上要约束哪些东西？

主持人 B：这又涉及对 harness 的理解了。我自己对 harness 的理解是：除了大模型之外的所有工程实现。归归可能更倾向于认为 harness 是在 agent 之上的一层，但我一直觉得 agent 和 harness 之间有一个非常融合的部分，没有那么清晰的界线，说 agent 之上、用户自己构建的那层才叫 harness，这个分界线其实没那么明显。我的理解是，只要是能让 LLM 工作得更好、把它约束得更好、控制得更好、引导得更好的东西，都是环境赋予 LLM 的一种反馈，这些可能都属于 harness。当然，除了我们自己，大家在理解上也会有分歧，这很正常，网上大家对 harness 的理解也各不相同。

为什么我觉得是“除了 LLM 之外”呢？你会发现 Claude Code 也就是 Anthropic 团队，在不断写博客讲 harness design 的时候，比如讲针对长时间运行的任务怎么设计，里面就提到了一些 agent 层面的控制细节和策略。比如因为模型能力不足、上下文长度不够，在以前 4.5 的模型上可能会出现“上下文焦虑”：上下文快填满时，整个 agent 就工作得不好了。但随着模型提升，这种上下文焦虑可能就消失了。有很多这样的细节，他们都认为属于 harness design 的范畴。而随着模型进步，他们认为的 harness 里的很多东西也在逐渐消失，不需要做得那么复杂了，比如上下文管理就变得更简单了。所以我现在讲 harness 系统需要管哪些东西，一定是基于我的理解，也就是“大模型之外的所有工程实现”。

第一部分，我觉得是 agent 本身的工程。今天我们有了大模型的 API，要自己开发一个 agent 的整个 runtime，这一部分我认为也属于 harness 的范畴，只是对大多数普通用户来说不太需要接触。这里面首先是 prompt，这是我们最早用来约束、控制大模型的东西，在单次对话里引导大模型工作得更好。接下来是 context 管理，包括上下文压缩，以及刚才提到的上下文焦虑。上下文焦虑是说，比如有 10K 的上下文，当它用到 8K 快满的时候，模型自己都开始焦虑了，好像“我剩余的额度不多了，马上就要挂了”，于是开始停止工作或者工作得不好，虽然上下文还没用完。甚至很多人认为超过 50% 之后模型就开始焦虑了。所以这涉及很多上下文管理，包括压缩、重置等等。工具这部分就不多说了，我们以前有很多期节目专门讲过工具怎么调、模型的工具调用，这些都属于 agent 工程的范畴。记忆我们也讲过。

权限控制这件事我觉得真的挺有意思。刚才归归也举了例子，agent 在工作时把数据库删了，这在 X 上传得很火。除了删数据库，我们也会发现，今天 agent 对你本地文件的权限，像 Claude Code 已经帮你定义得很好了。我只是认为他们还没有把权限这件事抽象得更好，还没把整个数字世界都抽象完整。比如对本地文件的修改，他们本身就定义了好几种权限：是否可以修改、是否需要用户同意、是否可以直接运行。Claude Code 里本身就有这样一套权限模型，而这套模型显然是可以扩展的，扩展下去就涉及数据库的访问权限应该是只读还是读写，或者是管理员权限等等。最后你会发现，这些权限规则一扩展，都被纳入 agent 的范畴里了。当然对今天的用户来说，agent 还提供了各种机制，我觉得这是从用户体验角度出发的，比如各种 AGENTS.md、CLAUDE.md、Cursor 里的 rules 文件等等，这些都是用户接口，让用户可以用自然语言去控制 agent、控制大模型。从这个角度看，这块肯定是今天做得最多的，这也是为什么大家觉得做一个 agent 有挺多工程工作要做，还挺复杂的。

除了 agent 本身之外，当我们把 agent 用到一个特定的项目环境中时，也会有很多特定的约束。比如刚才提到的各种 md 文件，我们需要通过这些文件设定项目背景、项目介绍、编码规范等等，还有项目怎么做单元测试、集成测试，整个流程怎么跑起来。这些定义好了，agent 就可以直接调用去检验成果。还有一类是，当你把 coding agent 集成到一些非编程场景时，你肯定需要打造这个场景里特定的规范和工具，去构建一个专属的 agent。我觉得这一层是比较有意思的。今天也有很多人在说一种未来新的生意形态：大家不要再去研究各种 agent 怎么搞，而是直接基于 Claude Code 封装一层，做成能够直接帮某个企业私有化的一套工作流。某个企业有自己的生意，它的生意肯定不是写代码，可能是其他某种数字化业务。你能不能基于 Claude Code 再包一层壳？这层壳形成的东西，可能就是一个新的工作流场景，去解决特定的生意问题。所以这一层我认为就是 harness。照这样发展下去，你会发现 harness 可能真的不只是给程序员、工程师用的一套规则规范，它可能真的可以用到专有领域，定义一个专有领域的产品。

主持人 A：它就变成了一个 coding agent 的套壳产品。

主持人 B：对，就是这样。

主持人 C：其实刚才讲的这个概念认知，现在确实挺模糊的，因为很多以前 agent 的东西，现在都在往 harness 那一层的概念里拿。在我的理解里，今天 agent 更多是在承担一个角色或者说人格，真正的能力都被放到 harness 里去了。比如记忆，我会理解为 harness 提供记忆机制，但由 agent 决定要调取哪些记忆、哪些东西值得长期记忆。harness 提供这个机制，包括做一些记忆的权限控制，比如这份记忆能不能在多个不同的 session 或多个不同的 agent 之间共享。基本上我会觉得，随着大模型能力越来越强，不管是 agent 还是 harness，可能都会越来越薄，最终留下的是控制、环境和能力的提供。

我理解最重要的几个部分是：一是提供可控的环境。比如我作为一个 harness，可以给你提供一个 sandbox，让你在沙箱里工作；我可以提供 worktree，让你并行做很多需求。二是提供可调用的工具，并配套权限管理。三是增强获取上下文的能力，比如记忆机制，比如按任务类型组装上下文：harness 可以判断这是一个 coding 任务，那应该读哪些上下文给你；如果是一个 SRE 的任务，又该找哪些上下文给你。包括你今天跑了一个测试，测试失败了，那应该组装什么样的上下文：失败的原因是什么、在哪一行失败、之前某个更早的 commit 是成功的、中间代码发生了什么 diff 之类的，这些都可以由 harness 组装好交给大模型。除此之外，还有一个很关键的，是提供可观察性和可验证性，也就是整个执行结果、日志，包括像 Codex 提供的浏览器插件、在 Mac 上做 computer use 的插件，能让大模型打开 Chrome 或者打开一个应用，看实际执行结果怎么样。这些东西给了 agent 一个能工作的环境，也给了它验证工作结果的方式，能让整个 agent 以目的、以结果为导向运作起来。我觉得这是很关键的。

主持人 A：你们刚才讲的概念不统一的问题，确实每个人现在的理解都不太一致。之前我听张小珺的播客，她采访了罗福莉，就是小米 MiMo 的负责人。罗福莉讲，之前大家都知道 Claude Code 效果好，但不知道是怎么回事，因为 Claude Code 是黑盒；当 OpenClaw 出来的时候，大家才发现这个框架好强大。她说在 OpenClaw 3 点几的版本时接入别的模型，不只是 Claude，比如接入小米自己的模型，效果也很好。所以 agent harness 这件事，让我很惊奇的是，训练大模型的团队竟然跟我们的认知基本是同步的，这一点我还是有点震惊。这是不是从侧面说明，大模型和 harness 本质上是两件事？

主持人 B：我觉得本质就是两件事，本来就是两条路：一条是训练智能，一条是做外部工程。做模型的团队本身主要是以训练智能为主。harness 则是外部工程的积累，需要大量传统软件工程的方法论和辅助工具来积累，这是需要时间的。你得干过很多年传统软件工程，才知道原来有这么多方式可以做这些奇奇怪怪的事情。比如你是一个计算机专业刚毕业的学生，没干几年程序员、没写过几年代码，很多东西你是不知道的，你也不知道原来有那样一个工具存在，Linux 上可能有些奇奇怪怪的工具你也就知道几个。它就是这个道理，需要积累。你看在 AI 之前，当然还没有所谓的大模型研究人员，但互联网公司里肯定都有团队在研究算法，推荐算法、搜索、用户画像这些。那些人每天都在研究算法，但当时我们做工程的人觉得他们就是“调参”的，觉得他们根本不会写代码，可能 Python 都只会写几行。就是这样两帮人：一帮人做算法，在我们眼里是调参；另一帮人像我们，写代码、做工程、做各种乱七八糟的工具。两帮人在那个年代真的没什么交集。

你们还记得我们有一期节目讲字节模型泄露的事吗？最后我们从技术上推导出来，就是因为 Python 的一个底层机制用得不对、理解不对，导致了那样的问题。当时网上很多人讨论，说做模型的人不懂这个非常正常，他们根本不会理解到那个点上，所以会出那样的问题。这就是因为是两帮人，算法和工程在很长一段时间里没什么交集，各干各的。所以哪怕回来看今天做大模型、做算法的研究人员，他们对 harness 这件事也没有什么超前的认知，这非常合理。人都是一样的，没见过、没做过，就没有认知。

主持人 C：说到这个，我又想说 harness 这个词真的很好，因为你可以很自然地拿它来做比喻。我们可以说，做大模型的人其实是在育种，他们想的是怎么培育出最好的马，关心的是马跑得快不快、力量强不强。但这些人真要去骑自己培育的马时，也一样要去驯服它，给它套上鞍具、套上缰绳才能骑，不然一样会被甩下来。所以他们也会发现 harness 是必要的。而我们作为普通的 AI 用户，我们不驯马，直接花一两百块一个月把马买来，要用它的时候，也一定需要套上 harness，这匹马才好用。所以这确实是两个层面的东西，对训练大模型的人来说也一样，他要用大模型也得套上 harness。而且实际上，真正的终端用户可能也不太关心这件事。他看到的不管是 Codex 还是 Claude Code，背后是不是一个大模型套一个 harness，他都无所谓，他看到的就是一个整体的 AI 产品。你给我一匹训好的、已经套好东西的马，我花钱直接骑，也不管上面装的是什么。

主持人 A：没错。你刚才讲写算法的人和做工程的人是两拨人，互相不知道对方在干嘛。前段时间 Claude Code 的前端代码，它的 source map 因为被放在了公开的 CDN 上，大家拿到 source map 之后，直接把 Claude Code 的所有代码都还原出来了。这是不是也从侧面证明了这两拨人的差别？从前端工程层面，到底该不该把 source map 放出来，可能他们心里都没底。而这件事之后，我觉得业界的 harness 水平好像都提升了，因为代码都被弄出来了。

主持人 C：可能是吧，因为 harness 本身就是工程层面的东西，很好复刻，不像大模型。你把开源大模型给普通人，普通人也复刻不了；但工程层面的东西确实很好复刻。

主持人 B：对，现在更好复刻了，照着写一遍就完了，非常夸张。

主持人 A：harness 这个思路，我理解理论上很早就能做。那为什么到现在大家才把这个概念整体提出来，而且很多人都开始疯狂在做？现在才爆发，是因为模型能力到了临界点，还是有别的原因？

主持人 B：这种事情，我个人觉得很难找准究竟是什么原因驱动的，可能也没那么多道理可讲，事情的发展就是这么神奇和动态。但回过头看，还是有一些值得看的东西。我们聊了这么多，至少有一个主题：harness 本质上是一种控制论，是一个工程话题。放到控制论和工程这个主题里，我发现 AI coding，也就是编程这件事，真的给大模型提供了一个非常核心的练兵场。关于 AI coding，我们往期也聊过好几期，这个观点我到今天也没变：AI coding 是大模型在现实世界、在业务落地上最好的场景，是非常核心的练兵场。当大家都沉迷于在编程上使用大模型之后，就开始探索各种奇技淫巧，这恰好是程序员、工程师最喜欢干的事，我们发现有各种工具可以探索。产品团队肯定也一样。

这种探索里，我觉得比较有代表性的产品有两个：一个是 Cursor，一个是 Claude Code。Cursor 我们也聊过好几期了，它从早期一直在专注设计一个好用的 IDE，给人做一个好用的工具，让人加入到编程环境中去控制 LLM。Cursor 做的事情其实也是控制 LLM，只是我觉得它走了一条弯路，一条传统的路：提供好的 UI 工具，让人更好地控制 LLM。你会发现 Cursor 做的事情就是让人去扮演 harness 的角色。当然，人本身就是一种更智能的 harness，人就是最智能的那个 harness，只是人的精力和体力有限，没法长时间自动化地应付大量工作。而 Claude Code 从一开始就在探索用自动化的系统而不是人去控制 LLM。所以我说 Cursor 只是走了一条弯路，但本质上大家都一样，都是为了更好地控制大模型。Claude Code 走的自动化系统这条路，研究起来是一个很大的话题，想象空间肯定更大，价值也更高，可探索的东西非常多。而恰好编程这个领域有非常多可用的工具，能辅助你实现自动化。所以说 AI coding 就是大模型最佳的练兵场，这里经过很多年的软件工程积累，已经拥有非常多好的资产。所以这次爆发，我认为不单纯是大模型能力到达了临界点，而是 harness 这种自动化控制系统积累到了一定程度。积累到那个程度后，我们突然发现它开始生效了，给我们一种惊喜的感觉：好像它真的可以替代我们程序员了。大家有了这种感觉，所以就开始爆发。harness 本身是一个纯工程系统，工程的积累确实需要时间，也依赖这个领域里是否已经存在很多资产和工具。所以它的很多效果来自细节的打磨，就是要反复迭代工程效果。传统工程里那句名言一直非常有用：魔鬼在细节里。它就是不断打磨细节，然后突然生效，我们就觉得这事成了，程序员好像真的可以被替代了，然后就火了。

主持人 A：那我再提一个问题。对于 agent 系统来说，如果我有一套非常好的 harness，背后用什么大模型差距是不是就不大了？比如背后是 Sonnet 还是 GLM，差距可能不会被拉得很大。你们怎么看？

主持人 B：这个我们自己肯定没有做过专业的测评。但今天很多人的观点是，harness 或者说控制系统比大模型更重要。当然不是说你的模型太拉垮也行，一个很强、一个很弱那肯定不行，模型怎么也得是顶级的。在这个前提下，大家普遍认为 harness 更重要一点。从我自己的体验来说，大家都知道今天买编程工具的订阅，有些模型的配额、credits 用完之后，可能会降级到稍微差一点的模型。确实有影响，但这时如果你把任务稍微拆分、精细化一下，或者人参与控制得多一点，就发现好像也行，没有那么明显的问题，它也能工作得很好。这就是人投入精力多少的问题：你多投入一点，相当于人扮演 harness 的角色多一点。最后发现模型降一个版本，说实话影响不是很大，当然人会累一点。

我更关注的是：一个设计良好的 harness 系统，不只是能稳定、高质量地完成任务，而且在模型升级之后，它不能成为累赘，不能有很多冗余，要能在模型进化后卸掉不必要的约束。我的意思是，虽然今天用 coding agent 时模型降一个版本好像没什么关系，但模型其实还是重要的。它的重要性在于，模型往前推进时，你的 harness 系统会变得越来越简单。不是有传言说，像 Manus 团队半年内重写了 5 次整个系统，也就是重写了整个 harness 吗？每一次重写都在变得更简单。我们自己做 Podwise 的过程中也一直是这样，虽然我们没有那么复杂、完备的 agent harness 环境，但每次重写都在让事情变得越来越简单。所以模型还是重要的，模型越强，你构建的 harness 可能就越自然，而不是越复杂。今天我们看到的所有 agent 和 harness 系统，未来某一天也可能会变得更简单。简单了之后，我相信质量会更高。不是越复杂质量越高，而是做得越简单、越自然、越顺理成章，效果可能越好。所以我一直觉得模型和 harness 是相辅相成的关系，不能说今天把 harness 做得很牛，模型就变得没那么重要了，我认为不是这个逻辑。

至于模型和 harness 谁更重要，我觉得这可能不是我们应该特别关注的问题。我认为未来在一些特定领域、特定业务场景，或者一个特定的企业，自己去构建自己的 harness 系统，也就是我们刚才说的定制自己私有的那部分东西，这在未来可能是挺有价值的。大家可以去关注、去思考一下，自己平时的工作流里，或者自己的企业、自己的业务里，是不是可以打造一套自己的 harness 系统。

主持人 A：还是回到马。就像刚才归归说的，大家都在养马，那我们需要做的就是找一匹最烈的野马，套上你的马鞍，可能就能工作得很好。这里的马就不是我之前理解的 LLM 了，说的就是 coding agent 这个场景：找一个很牛的 coding agent，然后打造一套属于我们自己的工作流、自己的 harness，最后可能就能解决企业的一些 agent 自动化的问题。我觉得这件事可能真的更有价值。

主持人 B：这里我再补充一个观点。有很多团队，很多创业团队都在做 agent，都说自己要做通用 agent。我一直认为，成为通用 agent 的门槛其实是 coding agent。大家能理解吗？反过来说，一个不擅长写代码的 agent，不可能成为真正的通用 agent。我觉得这是很显然的道理，因为在数字世界里，绝大多数问题和场景都可以通过写代码解决。特别是现在有了大模型这种智能的加持，在过去传统的写代码里，有一部分任务完成不了，比如需要理解人的意图、理解自然语言的任务，传统代码做不到。但今天有了智能加持，再叠加传统代码，你会发现数字世界的所有问题感觉都可以完成了。所以想做通用 agent，先做一个很强的 coding agent，再基于编程能力去打造能解决真实数字业务流程的场景，我觉得这是非常顺理成章的事。

主持人 C：我也比较认可这个观点。虽然 harness 不能直接提升大模型的智能，但今天大模型的产出质量本来就很大程度上是靠流程和工具保障的，也就是 harness 在保障。它提供的上下文、工具、流程控制，包括验证结果的能力，都是工程层面的东西，让大模型能够真正稳定、高质量地干活。从原理上讲，我自己推测，对于结果可验证的任务，harness 可以在很大程度上补足大模型的智力差距，因为结果可验证嘛，差一点的模型大不了多跑两轮。但对于偏创造、偏发散、没有客观可验证结果的任务，对上下文的要求也没那么精细，harness 的能力可能就没那么关键，还是得靠大模型本身的智力。从原理上我感觉是这样。你也可以反过来想：一个非常强的大模型配上一个很烂的 harness，或者压根不给 harness，它能得到好结果吗？我觉得大概率不行，因为最基础的，它可能连足够的上下文都拿不到。上下文不精确，活肯定干不好。

主持人 A：你讲的这个确实是。我最近特别喜欢用 Grok，为什么呢？因为 Grok 有 X 相关的所有资源，而且 Grok 搜索的时候特别激进。可能它模型能力不是特别强，但它搜索特别激进，会把 Reddit、X、各个地方都搜一遍。首先 Grok 自己就有 X 的资源，再加上搜索激进，所以它拿到的结果，我觉得很多时候都比别的好。而且我相信它有 X 上的很多数据，所以让 Grok 去写一些能在 X 上火的内容，效果好像更好一些。

主持人 B：拿 Grok 去搜一些比较实时的东西，效果也会比较好。

主持人 A：对，是的，它会帮你搜到 X 上的东西，因为它有 X 搜索的 API。所以我现在还经常用 Grok 去搜东西。

主持人 C：对，你讲的确实是这样。一个很好的大模型，如果没有好的上下文，比如没有 Grok 的这种 X 搜索，你想让它拿到很新的消息是比较难的，它可能只有训练时的数据，比如半年前的，那就不太行了。

主持人 A：那我们再回过头来。假如把 agent harness 比作大模型之上的操作系统，相当于大模型是内核（kernel），harness 变成了外壳（shell）。那未来是会像 iOS、安卓那样只剩几套，还是说未来仍然有大量机会？你们怎么看？

主持人 B：这又回到一个现象：我们录播客录了很多内容了，每次准备新节目时，总会想到这个东西我们好像以前也接触过，发现在大模型这条路上，我们其实思考过方方面面的东西，节目里也有过很多相关的讨论和观点。结果发现这些东西也在动态发展，我觉得挺有意思的。在很早的一期节目里，我们自己表达过一个观点：大模型不可能成为操作系统。那时候我们认为 AI 这条路不可能发展成今天操作系统这种形态，至少大模型不可能，因为那时候还没有 agent，大家也不知道后面会怎样，没想到今天变成这个样子，发展挺快的。所以今天如果再问这个问题，从操作系统的角度看，我会认为 agent 是有可能成为操作系统的，已经有点这个意思了。当然它还没有像操作系统那么复杂，没有扮演操作系统那么底层、那么多的能力，也还没有像操作系统那样构建起完备、丰富的生态。但从 agent 的形态上看，感觉有点那个意思。这也只是一种感觉，并不是说它最终一定会成为一个新型操作系统，但成为新时代的操作系统是有可能的。

我还是认为 agent 和 iOS、安卓的生态逻辑应该差不多，而不是说只存在几个 agent，然后就没事可干、没有机会了。我觉得不会是这样的逻辑。所有新技术、新平台的出现，一定会促成大量新的机会。就像 iOS 和安卓带来了大量 app 时代的机会，很多人靠开发 app 活着，现在很多互联网公司也是靠 app 活着。所以如果 agent 有成为平台级操作系统的意思和机会，它肯定不会封死大家的路。在所有技术的发展里，应该都会有大量机会。我一直认为的是：基于 agent 去构建我们自己专属的 agent。未来可能会有几个通用的 agent 平台，不管是不是 Claude Code、Codex 这些，我们能不能基于这样的平台去构建自己专属的 agent？这个专属 agent 就是我们前面讲的，可能是某个企业专属的 agent，也可能是某个人特定工作流专属的 agent，可能会产生大量这样的 agent 形态。所以我不认为会有一个所谓的通用 agent 吃掉整个数字世界的所有业务。哪怕是所谓的 AGI，一个 agent 可以干所有的事：能写代码，能帮我画图，能帮我做音乐，还能帮企业做客户管理、销售管理，可能吗？我觉得不太可能，一个 agent 很难扮演这么多能力。所以我认为这里“通用”的意思，更多是一个通用的操作系统、一个通用的框架层面的通用。我们基于这样一个通用平台去打造专属业务，我觉得是合理的。从这个角度看，应该会出现大量新机会，大家不用再去开发很多以前老的 SaaS、app，而是转去开发新的 harness 层、agent 层的东西，可能是这样吧。

主持人 C：在我的理解里，harness 里有很多能力是通用的，比如可观察性、权限控制、收集上下文这些。但它也需要领域化，不同领域需要的能力不一样。比如 coding harness 肯定要有 Git 相关的能力；如果是专注于自动化的 harness，比如专注于 Web automation 的 harness，需要的能力可能就跟 coding harness 不一样。我不知道后面会不会有 CRM 的 harness、ERP 的 harness，但这种业务型的 harness 需要的能力肯定也不一样。或者今天那些做 CRM、ERP 的厂商，会不会像我们今天都在出 skills 一样，出一个 harness 能力包？我不知道会不会有这种东西，但它可以是装到现在通用 harness 上的一个能力包，让它可以去做 CRM 相关的事情。如果用操作系统来比喻，通用的 harness 底座就是操作系统，这些领域能力就是安装上去的能力包。你要解决的是能力发现的问题，因为能力太多了，它可能会有能力发现的问题。但如果我做一件事时，可以限定就在这个能力包的范围内做，好像也可以。我感觉可能会是这样一种形态。

主持人 A：对，我们聊到 skills，现在大家有 skills marketplace，那在 skill 之上，比如 harness，我感觉 harness 本身也需要一个市场，不管它现在卖不卖。如果大家不以 harness 为盈利目标，它也可以做成像 skill marketplace 一样的东西；如果大家要以 harness 本身来盈利，就像今天有 OpenCode、Claude Code、Codex，后来你也可以做各种各样别的东西拿去盈利，或者做不同领域的，比如做一个 CRM 的 harness，包装成软件拿去卖，这也是一种方式。但我觉得 harness 这件事还在发展过程中，从 harness 这个概念出现到现在也就不到半年；从罗福莉讲她看到 OpenClaw 到现在，可能也就两三个月。所以这事还在发展中，我们也会持续跟进，看后续行业怎么发展，后面也可以经常跟大家聊聊这边的进展。好，那我们本期节目就先到这里，希望听完本期节目的朋友都有所收获，也欢迎大家在下方留言，参与我们节目的互动。我们下期再见，拜拜。
