Episode 417: Alex Petrov on Database Storage Engines ｜ Software Engineering Radio ｜ 56分钟 ｜ https://se-radio.net/2020/07/episode-417-alex-petrov-on-database-storage-engines/

本期由 Adam Gordon Bell 主持，嘉宾是 Cassandra 核心贡献者、O'Reilly《数据库内核》（Database Internals）一书的作者 Alex Petrov。两人避开查询优化和事务，专门聊数据库最底层的存储引擎：数据怎样写进磁盘、又怎样读回来。

Petrov 把存储引擎定义为离用户最远的一层，它和预写日志、事务处理器耦合很紧。正因如此，像 MySQL 那样可替换存储引擎的数据库并不多见。MongoDB 从 MMAP 换到 WiredTiger 是个例子；试图给 Cassandra 换上 RocksDB 的 Rocksandra 项目则说明，可插拔远不是实现一个读写接口那么简单。内存数据库也各不相同，有的完全不碰磁盘，有的用磁盘做恢复日志或冷数据存储。他认为只要最终要访问磁盘，存储引擎就是位于各层缓存之下的那部分。至于把 Cassandra 配上大内存能否像 Redis 一样快，他的回答是很难，两者各有所长。

他解释了为什么磁盘结构本质上比内存结构难。哈希表擅长按键随机访问，却答不了"姓氏以 P 开头的所有人"这样的范围查询。在磁盘上，文件系统只提供定位、读字节、写字节，页内指针、跨页指针和整个布局都得自己设计。用数据库而不是平面文件，理由是存储、访问和更新三方面的效率，而很多早期数据库正是有人厌倦了每个项目都重复同一套代码才写出来的。

接着他从二叉树、二叉搜索树一路推到 B 树。二叉搜索树放到磁盘上，扇出太低、局部性差，频繁的再平衡还意味着反复重写磁盘。B 树每个节点有 n 个键、n+1 个子指针，一次读一个页，在页内二分查找，寻道次数大致等于树的层数。页满就分裂，容量随层数指数增长。谈到索引，他指出表本身就是按主键组织的索引。二级索引有三种做法：存主键，不复制数据但要查两次树；存磁盘偏移，省一次查找但和主表耦合很紧；存整条记录，读最快但要复制数据。他还提到 Uber 那篇比较 MySQL 和 Postgres 的博客。这种读写取舍可以用 RUM 猜想概括：读、更新、内存三种放大不可能同时优化。

LSM 树是在 B 树上逐步加约束推出来的：先让页不可变，得到写时复制 B 树，例如 OpenLDAP 用的 LMDB，可以免去预写日志；再加上内存缓冲和预写日志，就是 O'Neil 论文里的双组件 LSM 树，最后用多组件加压实回收被覆盖的键。传统说法是 B 树利于读、LSM 利于写，因为 B 树写之前要先查找位置，LSM 只需追加日志和内存表。Petrov 认为 LSM 读性能差是背了黑锅，实现得当、用足优化后读也可以很快，代价是持续的压实，也就是 RUM 里的内存和写放大。主持人用文件柜作比：B 树是归档到位，LSM 是先塞进去、读时再翻找。实例方面，PostgreSQL 和 MySQL 用 B+ 树（PostgreSQL 用 B-link 变体），Cassandra 和 RocksDB 用 LSM，Bw-Tree 则是建在日志结构存储上的混合方案。

SSD 改变了这道算术题：机械盘可以原地覆写，SSD 却必须按块擦除，并在后台做垃圾回收。小而频繁的原地更新会悄悄带来大量额外工作，所以写满页、避免原地更新的日志结构和写时复制设计更契合 SSD。最后谈到未来，他总结 2019 年的论文，看到两个趋势：一是专门化存储取代通用数据库；二是能根据负载自动调整页大小、访问路径乃至存储格式的"自动驾驶"数据库。在云时代，数据库要越来越了解用户，而不是要求用户了解数据库。
