驾驭工程：在智能体优先的世界里用好 Codex

过去五个月，我们团队一直在做一个实验：构建并交付一款软件产品的内部测试版，其中手写代码为零行。

这款产品有每天使用的内部用户，也有外部的 alpha 测试者。它会发布、部署、出故障、被修复。不同之处在于，每一行代码——应用逻辑、测试、CI 配置、文档、可观测性和内部工具——都是由 Codex 编写的。我们估计，构建它所用的时间大约是手写代码所需时间的十分之一。

人类掌舵，智能体执行。

我们有意选择了这个约束，以便去构建那些能让工程速度提升几个数量级所必需的东西。我们只有几周时间来交付最终达到一百万行代码的成果。为此，我们需要理解：当一个软件工程团队的主要工作不再是写代码，而是设计环境、明确意图、构建让 Codex 智能体能可靠工作的反馈回路时，会发生哪些变化。

这篇文章讲的是我们用一支智能体团队构建一款全新产品所学到的东西——什么出了问题，什么产生了复利效应，以及如何最大化我们唯一真正稀缺的资源：人的时间和注意力。

## 我们从一个空的 git 仓库开始

空仓库的第一次提交落在 2025 年 8 月下旬。

最初的脚手架——仓库结构、CI 配置、格式化规则、包管理器设置和应用框架——是由 Codex CLI 使用 GPT-5、在一小组现有模板的引导下生成的。就连指导智能体如何在仓库中工作的初始 AGENTS.md 文件，本身也是 Codex 写的。

没有任何预先存在的人工编写代码来锚定这个系统。从一开始，仓库就是由智能体塑造的。

五个月后，仓库中包含了约一百万行代码，涵盖应用逻辑、基础设施、工具、文档和内部开发者实用程序。在此期间，仅由三名工程师驱动 Codex 的小团队开启并合并了大约 1500 个拉取请求（PR）。这相当于平均每名工程师每天 3.5 个 PR，而且令人惊讶的是，随着团队扩大到现在的七名工程师，吞吐量反而提高了。重要的是，这不是为了产出而产出：这款产品已被内部数百名用户使用，其中包括每天使用的内部重度用户。

在整个开发过程中，人类从未直接贡献过任何代码。这成了团队的一条核心理念：不手写代码。

## 重新定义工程师的角色

人类不再亲手写代码，这带来了另一种工程工作，聚焦于系统、脚手架和杠杆。

早期进展比我们预期的慢，不是因为 Codex 能力不足，而是因为环境定义不充分。智能体缺乏朝高层目标推进所需的工具、抽象和内部结构。我们工程团队的主要工作变成了让智能体能够做有用的工作。

在实践中，这意味着深度优先地工作：把较大的目标拆解成更小的构建块（设计、编码、评审、测试等），提示智能体构建这些块，再用它们解锁更复杂的任务。当某件事失败时，解决办法几乎从来不是"再努力一点"。因为推进的唯一途径是让 Codex 去做，人类工程师总会介入任务并追问："缺少的是什么能力？我们怎样才能让它对智能体既清晰可读、又可强制执行？"

人类几乎完全通过提示与系统交互：工程师描述一个任务，运行智能体，让它开一个 PR。为了推动 PR 完成，我们指示 Codex 在本地评审自己的改动，在本地和云端请求额外的特定智能体评审，回应任何来自人类或智能体的反馈，并循环迭代，直到所有智能体评审者都满意（这实际上就是 Geoffrey Huntley 提出的"Ralph Wiggum 循环"）。Codex 直接使用我们的标准开发工具（gh、本地脚本和仓库内嵌的技能）来收集上下文，无需人类往 CLI 里复制粘贴。

人类可以评审 PR，但不是必须的。随着时间推移，我们已经把几乎所有的评审工作都推向了智能体之间的互相评审。

## 提高应用的可读性

随着代码吞吐量增加，我们的瓶颈变成了人工 QA 的能力。由于固定的约束一直是人的时间和注意力，我们努力为智能体增加更多能力，让应用 UI、日志和应用指标这些东西本身对 Codex 直接可读。

例如，我们让应用可以按 git worktree 启动，这样 Codex 就能为每个改动启动并驱动一个实例。我们还把 Chrome DevTools 协议接入了智能体运行时，并创建了处理 DOM 快照、截图和页面导航的技能。这让 Codex 能够直接复现 bug、验证修复、推理 UI 行为。

我们对可观测性工具也做了同样的事。日志、指标和链路追踪通过一个本地可观测性栈暴露给 Codex，这个栈对每个 worktree 都是临时的。Codex 在一个完全隔离的应用版本上工作——包括它的日志和指标，任务完成后就会被销毁。智能体可以用 LogQL 查询日志，用 PromQL 查询指标。有了这些上下文，像"确保服务启动在 800 毫秒内完成"或"这四条关键用户路径中没有任何 span 超过两秒"这样的提示就变得可以处理了。

我们经常看到单次 Codex 运行在一个任务上持续工作六小时以上（往往是在人类睡觉的时候）。

## 我们把仓库知识作为记录系统

上下文管理是让智能体有效完成大型复杂任务的最大挑战之一。我们最早学到的教训之一很简单：给 Codex 一张地图，而不是一本 1000 页的说明书。

我们尝试过"一个大 AGENTS.md"的做法。它以可预见的方式失败了：

- 上下文是稀缺资源。一个巨大的指令文件会挤占任务、代码和相关文档的空间——于是智能体要么漏掉关键约束，要么开始针对错误的约束做优化。
- 指导过多就等于没有指导。当一切都"重要"时，就没有什么是重要的。智能体最终只会在局部做模式匹配，而不是有意识地导航。
- 它会立刻腐烂。一本大一统的手册会变成过时规则的坟场。智能体分不清哪些仍然成立，人类也不再维护它，这个文件悄悄变成了一个诱人的隐患。
- 它很难验证。单独一大块内容不适合做机械化检查（覆盖率、新鲜度、归属、交叉链接），所以偏离是不可避免的。

所以，我们不把 AGENTS.md 当作百科全书，而是当作目录。

仓库的知识库存放在一个结构化的 `docs/` 目录中，被当作记录系统。一个简短的 AGENTS.md（大约 100 行）被注入上下文，主要充当地图，指向其他地方更深层的事实来源。

（图：仓库内知识库的目录布局。）

设计文档被编目和索引，包括验证状态，以及一组定义智能体优先运作原则的核心信念。架构文档提供了领域和包分层的顶层地图。一份质量文档为每个产品领域和架构层打分，并持续追踪差距。

计划被视为一等产物。小改动使用临时的轻量计划，而复杂工作则记录在执行计划中，附带进度和决策日志，并提交到仓库里。进行中的计划、已完成的计划和已知的技术债务都被版本化并放在一起，使智能体无需依赖外部上下文就能运作。

这实现了渐进式披露：智能体从一个小而稳定的入口开始，被告知下一步去哪里看，而不是一开始就被信息淹没。

我们以机械化方式强制执行这一点。专门的 linter 和 CI 任务会验证知识库是最新的、有交叉链接的、结构正确的。一个定期运行的"文档园丁"智能体会扫描那些过时、已不反映真实代码行为的文档，并开 PR 进行修正。

## 目标是让智能体可读

随着代码库的演进，Codex 做设计决策的框架也需要演进。

由于仓库完全由智能体生成，它首先是针对 Codex 的可读性进行优化的。就像团队致力于让新入职的工程师更容易理解代码一样，我们人类工程师的目标是让智能体能够直接从仓库本身推理出完整的业务领域。

从智能体的角度看，任何它在运行时无法在上下文中访问到的东西，实际上都不存在。存放在 Google Docs、聊天记录或人们脑子里的知识，系统都无法访问。仓库本地的、版本化的产物（例如代码、markdown、schema、可执行计划）就是它能看到的全部。

我们认识到，随着时间推移，需要把越来越多的上下文推进仓库。那次让团队在某个架构模式上达成一致的 Slack 讨论呢？如果智能体发现不了它，它就是不可读的，就像三个月后入职的新员工也无从知晓一样。

给 Codex 更多上下文，意味着组织并暴露正确的信息，让智能体能在其上推理，而不是用临时指令把它淹没。就像你会向新队友介绍产品原则、工程规范和团队文化（包括表情符号偏好）一样，把这些信息提供给智能体，会带来更一致的产出。

这种框架厘清了许多权衡。我们偏好那些能在仓库内被完全内化和推理的依赖和抽象。那些常被称为"无聊"的技术，由于可组合性、API 稳定性以及在训练集中的代表性，往往更容易被智能体建模。在某些情况下，让智能体重新实现部分功能，比绕过公共库中不透明的上游行为更便宜。例如，我们没有引入一个通用的 `p-limit` 式的包，而是实现了自己的带并发控制的 map 辅助函数：它与我们的 OpenTelemetry 埋点紧密集成，测试覆盖率 100%，行为完全符合我们运行时的预期。

把系统更多部分转化为智能体能直接检查、验证和修改的形式，会提高杠杆效应——不仅对 Codex，对同样在这个代码库上工作的其他智能体（例如 OpenAI 的安全研究智能体 Aardvark）也是如此。

## 强制执行架构与品味

单靠文档并不能让一个完全由智能体生成的代码库保持一致。通过强制执行不变量而不是对实现进行微观管理，我们让智能体能快速交付，又不破坏基础。例如，我们要求 Codex 在边界处解析数据结构（"解析，而非校验"），但并不规定怎么做（模型似乎喜欢 Zod，但我们并没有指定这个库）。

智能体在边界严格、结构可预测的环境中最为高效，所以我们围绕一个严格的架构模型构建了应用。每个业务领域都被划分为一组固定的层，依赖方向经过严格校验，允许的依赖边也有限。这些约束通过自定义 linter（当然是 Codex 生成的！）和结构测试以机械化方式强制执行。

下图展示了这条规则：在每个业务领域（例如应用设置）内，代码只能沿着一组固定的层"向前"依赖（Types → Config → Repo → Service → Runtime → UI）。横切关注点（认证、连接器、遥测、功能开关）通过一个单一的显式接口进入：Providers。其他一切都被禁止，并以机械化方式强制执行。

这种架构通常要等到你有数百名工程师时才会去做。有了编码智能体，它成了早期的先决条件：正是这些约束让速度得以实现，而不会带来腐化或架构漂移。

在实践中，我们用自定义 linter 和结构测试来强制执行这些规则，外加一小组"品味不变量"。例如，我们通过自定义 lint 静态强制执行结构化日志、schema 和类型的命名规范、文件大小限制，以及特定平台的可靠性要求。由于 lint 是自定义的，我们会编写错误信息，把修复说明注入智能体的上下文。

在以人为先的工作流中，这些规则可能显得吹毛求疵或束手束脚。而对智能体来说，它们成了乘数：一旦编码下来，就会同时作用于所有地方。

与此同时，我们明确区分哪里需要约束、哪里不需要。这就像领导一个大型工程平台组织：在中心强制执行边界，在局部允许自主。你非常关心边界、正确性和可复现性。在这些边界之内，你允许团队——或智能体——在如何表达解决方案上拥有很大的自由。

由此产生的代码并不总是符合人类的风格偏好，这没关系。只要产出是正确的、可维护的、对未来的智能体运行可读的，它就达标了。

人类的品味被持续地反馈回系统。评审意见、重构 PR 和面向用户的 bug 会被记录为文档更新，或直接编码进工具。当文档不够用时，我们就把规则升级为代码。

## 吞吐量改变了合并哲学

随着 Codex 吞吐量的增加，许多传统的工程规范变得适得其反。

仓库以最少的阻塞式合并关卡运作。PR 的生命周期很短。测试的偶发失败通常通过后续重跑来处理，而不是无限期地阻塞进度。在一个智能体吞吐量远超人类注意力的系统中，纠正是廉价的，等待是昂贵的。

在低吞吐量环境中，这样做是不负责任的。而在这里，这往往是正确的权衡。

## "由智能体生成"到底意味着什么

当我们说代码库是由 Codex 智能体生成的，我们指的是代码库中的一切。

智能体产出：

- 产品代码和测试
- CI 配置和发布工具
- 内部开发者工具
- 文档和设计历史
- 评估框架
- 评审意见和回复
- 管理仓库本身的脚本
- 生产环境仪表盘定义文件

人类始终在循环之中，但工作在一个与过去不同的抽象层次上。我们给工作排定优先级，把用户反馈转化为验收标准，并验证结果。当智能体遇到困难时，我们把它当作一个信号：找出缺少的是什么——工具、护栏、文档——然后反馈回仓库，而且总是让 Codex 自己来写修复。

智能体直接使用我们的标准开发工具。它们拉取评审反馈、在行内回复、推送更新，并且经常自己压缩合并（squash and merge）自己的 PR。

## 不断提高的自主程度

随着越来越多的开发循环——测试、验证、评审、反馈处理和恢复——被直接编码进系统，仓库最近跨过了一个有意义的门槛：Codex 可以端到端地推动一个新功能。

只需一个提示，智能体现在就可以：

- 验证代码库的当前状态
- 复现一个报告的 bug
- 录制一段演示故障的视频
- 实现修复
- 通过驱动应用来验证修复
- 录制第二段演示问题已解决的视频
- 开一个 PR
- 回应智能体和人类的反馈
- 检测并修复构建失败
- 仅在需要判断时才上报给人类
- 合并改动

这种行为高度依赖于这个仓库特定的结构和工具，在没有类似投入的情况下不应假定它能推广——至少目前还不能。

## 熵与垃圾回收

完全的智能体自主也带来了新问题。Codex 会复制仓库中已有的模式——即便是参差不齐或次优的模式。随着时间推移，这不可避免地导致偏离。

起初，人类手动处理这个问题。我们团队过去每周五（一周的 20%）都在清理"AI 垃圾"（AI slop）。不出所料，这无法规模化。

于是，我们开始把所谓的"黄金原则"直接编码进仓库，并建立了一个定期的清理流程。这些原则是有主见的、机械化的规则，让代码库对未来的智能体运行保持可读和一致。例如：(1) 我们更偏好共享的工具包，而不是手搓的辅助函数，以便把不变量集中管理；(2) 我们不"YOLO 式"地试探数据——我们校验边界或依赖类型化的 SDK，这样智能体就不会意外地在猜测的数据结构上构建。我们有一组后台 Codex 任务按固定节奏运行，扫描偏差、更新质量评分，并开出有针对性的重构 PR。其中大多数能在一分钟内评审完并自动合并。

这就像垃圾回收。技术债务就像高息贷款：持续地小额偿还，几乎总是比任其复利累积、再痛苦地集中处理要好。人类的品味只需捕获一次，然后在每一行代码上持续强制执行。这也让我们能每天发现并解决不良模式，而不是任由它们在代码库中扩散几天或几周。

## 我们仍在学习的东西

到目前为止，这一策略在 OpenAI 内部发布和推广阶段都运作良好。为真实用户构建真实产品，帮助我们把投入锚定在现实中，并引导我们走向长期可维护性。

我们还不知道的是，在一个完全由智能体生成的系统中，架构一致性在数年时间里会如何演变。我们仍在学习人类判断在哪里能发挥最大杠杆作用，以及如何把这种判断编码下来，使其产生复利。我们也不知道，随着模型能力持续提升，这个系统会如何演变。

已经清楚的是：构建软件仍然需要纪律，但这种纪律更多地体现在脚手架上，而不是代码上。让代码库保持一致的工具、抽象和反馈回路正变得越来越重要。

我们现在最困难的挑战集中在设计环境、反馈回路和控制系统上，以帮助智能体实现我们的目标：大规模地构建和维护复杂、可靠的软件。

随着 Codex 这样的智能体承担软件生命周期中越来越大的部分，这些问题会变得更加重要。我们希望分享这些早期经验，能帮助你思考该把精力投向哪里，这样你就可以放手去构建。
