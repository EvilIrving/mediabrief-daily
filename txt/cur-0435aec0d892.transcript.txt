Philip Winston：欢迎收听 Software Engineering Radio。我是 Philip Winston。今天请来的嘉宾是 Maxim Fateev。Maxim 是 Temporal 的联合创始人兼 CEO，曾在 Amazon、Microsoft、Google 和 Uber 担任领导角色。他在 Amazon 主导过 AWS Simple Workflow Service 的开发，在 Uber 主导过开源的 Cadence workflow。Maxim 拥有计算机科学和物理学学位。今天我们要聊用分布式系统自动化业务流程，不过先从一个不是人人都熟的术语说起——durable execution（持久执行）。Maxim，什么是持久执行？为什么它是有用的抽象？

Maxim Fateev：持久执行是一种我们提出的新抽象，目前还不太广为人知，但我觉得每个工程师都应该把它放进工具箱。想法很直接：想象一个运行时，始终把你的代码执行的完整状态持久化保存。这意味着如果进程崩溃，或发生网络故障、断电等任何基础设施中断，问题解决后你的代码会继续跑；如果进程崩了，执行会被迁移到另一个进程；如果整片区域宕机，恢复后代码也会接着执行。我说的不只是进程，而是完整状态。比如有个函数要依次调三个 API：A、B、C，卡在 B 上时进程崩了，这次执行会迁到另一台机器，仍然卡在 B 上；B 的结果两天后才回来，它也能继续。所有局部变量和整个状态——包括阻塞中的调用——一直被完整保留。

Philip：太好了，后面会细讲原理。在那之前先讲点历史、我们怎么走到今天。不过先描述一下今天的 Temporal。

Maxim：Temporal 是开源项目，MIT 许可，你可以自己跑，包括 SDK 库和保存状态的后端服务器。这个项目我们在 Uber 启动，最初叫 Cadence；大约四年前我们成立公司，fork 了项目，改名 Temporal。它已经在生产环境高规模跑了七年，被全球数千家公司用于关键任务。

Philip：再往前一点。Cadence 之前你在 Amazon 做 Simple Workflow Service。那个项目怎么开始的？目标是什么？

Maxim：我想再往前说。我 2002 年第一次加入 Amazon，那时 Amazon 正积极从单体迁到微服务架构——当时还不叫微服务，就叫 services，后来叫 SOA，基本想法一样：单体不可持续，光重新链接那个二进制在高端桌面上就要四十五分钟，没法做开发。Amazon 必须拆。实践上我们用当时的标准做法：用队列把多个服务连起来，执行后端业务流程。我是弹出广告（pop-ups）组的 tech lead，负责 Amazon 所有后端弹出广告相关的东西；我还做过队列用的分布式复制存储，我觉得它现在还在给 Simple Queue Service 当后端。

我处在大量设计选择讨论的中间。当你用队列和事件驱动架构建大规模系统时，很快会发现那不是正确的抽象——事件和队列不是建这类系统的正确抽象。很重要的一点是：它们是很棒的运行时抽象。事件驱动和队列给你出色的运行时特性：比如你的服务慢了，别的服务不会被拖慢，因为东西可以缓存在队列里；你的服务甚至可以宕机，别的服务都未必察觉，只是觉得消息没来或在缓冲。所以运行时特性很好，但作为设计选择，它们会造出很残酷的系统：一切和一切相连，没有清晰 API，很难在每个服务里做状态机、支撑所有业务逻辑。

我们团队意识到了这一点，开始想编排器。Amazon 内部有一个基于 Petri 网想法、建在 Oracle 之上的编排器，用来编排订单。我们开始想更可扩展的方案。内部做了三个迭代、三个版本，只有第三个公开，就是 AWS Simple Workflow Service。试了很多次才大致做对，但即便 SWF 我也不觉得真正做对了——它仍然不是很受欢迎的服务——不过我们学到很多。后来我们各自去了别的公司。Temporal 的联合创始人 Samar Abbas 曾和我一起做 Simple Workflow，他去了 Microsoft，在那里写了 Durable Task Framework，后来被 Azure Functions 采用，现在微软有 Azure Durable Functions。然后我们在 Uber 重逢，把这些想法收进来，做了下一代技术——也就是现在的 Temporal。你可以把它看成十多年迭代的延续。

Philip：你们决定 fork Cadence 做成 Temporal，而不是推倒重来，是怎么定的？

Maxim：你会重来，通常是因为觉得现有方案不够好。但 Cadence 是扎实的：我们在生产跑了三年多，大规模跑了两年，有一百多个用例用在关键应用上。我们也知道有很多想修的地方——三年学了很多——但我们承诺了完全向后兼容和在线升级，不能破坏任何东西。要从 A 点不破坏地走到 B 点会极其难。fork 之后，我们实际上有了一次性机会去修很多小问题：比如从 thrift 迁到 protobuf，从 Uber 专用协议迁到 gRPC——这些从安全等角度看好处很大。还有很多别的小事。从 fork 到宣布生产可用，我们花了一年，就改这个 fork，因为改动太多了。

Philip：你提到 MIT 许可。Temporal 哪些部分在许可范围内？客户端 SDK、服务器、Web 界面？

Maxim：Temporal 有一个后端集群，里面有多个角色。你当然可以在单个二进制里跑所有角色——本地开发用的单二进制版本就这样，还带 UI——也可以把大约五个角色拆成多组 worker、多组进程来跑。后端还需要数据库。开源版官方支持 MySQL、Postgres、Cassandra，也正式支持 SQLite。集群连数据库，通过前端角色暴露 gRPC 接口；整个集群是 MIT 许可，可以自己跑。写应用时，业务逻辑在集群外，应用通过 gRPC 连后端；应用不需要开端口，只做出站连接到集群。这些组件都是 MIT。Java SDK 因为历史原因是 Apache 2——最初 fork 自我在 Simple Workflow 时做的 Amazon 框架实现。

Philip：接下来会进入 Temporal 核心概念：workflow、activity、timer 等。先提几期相关旧节目：第 502 期 Omer Katz 讲用 Celery 做分布式任务队列；第 351 期 Bernd Rücker 讲用工作流管理编排微服务；第 198 期 Wil van der Aalst 讲工作流管理系统。最后那期十年前了，但很多概念今天仍在讨论。进入核心概念：你不一定把 Temporal 叫工作流系统，但 workflow 是核心概念之一。在 Temporal 语境下，workflow 是什么？

Maxim：很重要：我说 Temporal 里的 workflow，永远指我刚才描述的持久执行。你用顶级编程语言写代码——Java、Go、TypeScript、PHP、.NET——这段代码是持久的。我们始终保存完整状态，包括阻塞中的调用和所有变量。凡是需要持久性、需要完成保证、需要 saga 或跑补偿的场景，Temporal 都很合适。问题是：人们一听“工作流引擎”，往往想到你提到的那些 YAML/XML/JSON、画流程图的方案。那些方案从没真正火起来，因为工程师在多数用例里根本不会考虑它们——它们从来不是开发者优先。总有人承诺非技术人员能画图写工作流，现实是从来行不通；工程师还是得写 XML/JSON 或画图，而这不是工程师想要的。他们想要代码。所以我说 workflow 永远指持久执行，这和别人卖的“工作流”（总是某个 JSON/XML 文件）非常不一样。

Philip：我用过 AWS Step Functions 和 Google Cloud Workflows，工作流用 JSON 或 YAML 描述。JSON/YAML 也许很适合配置，但在那些系统里你实际上是在受限语言里写命令式代码，那会很不舒服。实现 Temporal、支持任意（至少好几种）编程语言，有哪些技术挑战？每种语言有不同 SDK，但一定有共同技术在支撑。

Maxim：要始终保存代码状态，基本上只有两种路。一条是每次代码推进后对内存做快照存起来，换机器时加载内存继续跑。某些运行时也许行，比如 WebAssembly；但你没法轻易把 Java 执行的完整状态——尤其卡在某些调用上时——序列化出来。对 Go、TypeScript 也一样：技术上也许能，但要很深地黑运行时。

另一条路是我们说的 replay（重放）：从头跑代码，每次执行外部动作就拦截；若该动作已完成，就把结果喂回去。比如代码卡在函数 B，进程崩了，你会有一份我们叫 event history（事件历史）的记录：动作 A 已请求且完成，动作 B 已请求但未完成。恢复时重跑这个函数，调 A，验证历史里有对 A 的调用，把 A 的结果给代码，代码从 A 走到 B；再验证 B 的调用在历史里，于是知道现在卡在 B，等 B 的结果送达。

细节很多。比如怎么保证 B 的结果路由到当前正在等它的那个进程——因为前一个已经崩了——所以有一整层路由。一个大前提是：函数代码必须是确定性的。意思是再跑一遍会走到同一点。如果代码写 `if random > 50` 走分支 A 调 API A，否则调 B，这就不确定——每次从头跑可能走不同分支。要用随机数，就得用确定性随机：第一次调用时真正随机，重放时返回同一值。Temporal 为随机、时间、建线程等提供了专门 API，因为线程默认也不确定，除非用我们自己的运行时。

Philip：举个简单例子。我有邮件或消息应用，有个函数可以按指定时长延迟发消息。工作流在某个端点之后启动，用户告诉延迟多久。工作流代码看起来是线性的：开始、sleep（timer）、再真正发消息。第一次跑到 timer 时发生了什么？是退出吗？怎样才能稍后继续？

Maxim：工作流代码跑在应用空间，不在 Temporal 集群里。通常你会建我们叫 workflow worker 的进程来承载工作流代码。可以把 worker 想成队列消费者，类似一直跑着消费 Kafka 的进程。Temporal worker 一直跑，一直监听 Temporal 内部叫 task queue 的特定队列；比如注册说我在听这个任务队列上的某类工作流。你启动工作流时，Temporal 内部会事务性地创建任务状态并放进该队列，没有竞态。

然后 worker 取到任务，里面有工作流参数等信息，开始执行。碰到 sleep，无法继续推进，sleep 会变成 create timer 命令发回 Temporal 服务器；Temporal 在基础设施里创建持久 timer，存进数据库。如果 sleep 两周，两周后 timer 触发，创建新任务，某个（可能不同的）worker 进程取到任务，恢复工作流状态，解除 timer 阻塞，继续往下跑。

Philip：所以 worker 不一定退出，但 sleep 开始时那个任务可以算结束了？

Maxim：正是。还有一个优化：我们会在 worker 里把工作流状态缓存一段时间。如果 sleep 很短，或只是等 activity 完成，很可能很快又需要这个工作流，不想每次都恢复。跑得快的工作流会一直被缓存，只投递新事件，不必做恢复——这纯粹是优化。

Philip：说到时长：在你或 Temporal 看来，什么算短工作流、什么算长？我常发现讨论工作流时，自己想的范围或时长和对方差很远。Temporal 用户的时长范围大概怎样？

Maxim：首先，持久执行不在乎时长。可以极短，也可以极长，关键是持久性和完成保证，尤其是补偿。比如即时支付：时间预算很紧，但某个 API 失败时你要跑补偿——从 A 账户扣了钱，往 B 打失败了，要很快给用户返回错误，同时保证钱退回原账户。今天跨服务没有事务，Temporal 是分布式架构里替代事务的最佳方式之一。这是很常见的用例，即使时长很短、有人在等，也适用。

同时我们也有始终在跑的工作流，我们叫 entity workflow（实体工作流）。比如一个代表用户的工作流，处理所有与该用户相关的通信。实际例子：航空公司积分计划。可以为每个客户跑一个一直在的工作流，监听航班完成等事件；每次航班完成就按航程加积分。积分可以直接存在工作流变量里，因为它们始终持久。到一定积分可以跑 activity 通知别的服务：你现在是金卡会员。也可以在工作流里放 timer，每月发邮件告知积分和新促销。这个工作流一直跑，直到客户离开系统——这类场景里几乎从不发生。

Philip：我见过“工作流即实体”的想法，后面会再谈。先回到核心概念。讲完 workflow，下一个是 activity。我延迟发信的例子用了 sleep/timer，但 activity 更一般。Temporal 里什么叫 activity？它应具备什么属性？

Maxim：如前所述，Temporal 靠重放恢复工作流状态，主要求是代码确定性。任何外部 IO 天生不确定：这次成功、下次失败、返回值也可能不同。所以 Temporal 拦截那些外部调用，定下规则：所有外部通信走 activity。每种语言里 activity 就是一个函数，像任务一样——队列消费者处理队列任务，Temporal 里你写一个通常就是函数的 activity，从工作流里调用时就会执行。我们对函数里能写什么几乎不设限。

和队列任务比，Temporal activity 的好处是：首先可以跑任意久，必要的话一年也行。长跑 activity 你要心跳，不想设一年超时干等到超时；可以每分钟心跳，进程一崩大约一分钟后重试。心跳里还能带进度信息：扫巨大数据集时每条记录心跳一次进度，失败重启后读上次心跳数据接着干。activity 也可取消：在心跳的前提下可以优雅处理取消。还可以把 activity 路由到特定主机——比如 A 在某台机器下了文件，后续 activity 就路由到那台。失败时按指数退避重试，重试多久都行：一周、一个月都支持。这和队列很不同——队列里任务时长和重试次数通常很受限。

Philip：activity 当然可以在远程系统上，某种 RPC 或 Web 接口。但即便在同一进程里，有时也该当成 activity 吗？

Maxim：这其实是 Temporal 的设计选择：每个外部 IO 都应活在 activity 里。我们有 local activity 概念，和 workflow 同进程跑，在某些场景做优化，支持非常低延迟。但如果是发邮件，就应该是 activity，由工作流去调“发邮件”activity。

Philip：确定性我们谈过了。分布式系统里另一个常出现的概念是幂等。activity 都需要幂等吗？还是只会被调一次？

Maxim：好问题。Temporal 不会盲目重试 activity。失败或超时会看关联的重试策略；若策略里 max attempts 设为 1，就不会再试。那时工作流会收到错误，需要自己处理——就是普通语言抽象，比如 Java 里 try/catch 抓住 activity 失败，再跑补偿等。比“盲目重试”更细致。但现实中最常见做法是让 activity 幂等，然后默认盲目重试——我们默认会重试。重要的是 Temporal 是完全一致的系统：只有你要求时才重试。若 max attempts=1，存在 activity 从未真正执行的可能——比如任务送达、timer 启动后进程崩了。这种情况下 Temporal 保证超时后异常会交给工作流，不会丢掉这次 activity，但可能落到“从未执行”的局面，你得自己处理错误。若做了幂等，就不用想这些，可以说一直重试直到成功。

Philip：你刚才提到 saga 模式。Temporal 帮你实现它吗？先说 saga 是什么——好像和“多个 activity，有的成功有的失败，想撤销已成功的那些”有关？

Maxim：我不确定教科书怎么精确表述，按我的理解：你执行多个 API 调用，它们会改存储、改状态，但跨调用没有事务。最典型：从账户 A 扣钱、往账户 B 打钱；A 扣成功了，B 因账户 ID 错误失败。没有事务时，技术上只能跑补偿——把钱退回 A。这种场景到处都是，你 practically 必须跑补偿。saga 就是说：你跑了比如十个 activity，八个成功、第九个失败，怎么给前面八个跑补偿？

相对任何别的框架——尤其那些 JSON/YAML 的——Temporal 因为代码很动态，让实现 saga 变得非常琐碎简单。saga 的补偿保证是什么？Temporal 保证你的函数即使进程崩、出故障也会继续跑。所以 Temporal 很容易保证：出了事这个过程还会继续；你的代码有 try/catch，catch 里跑补偿，对 Temporal 来说是很容易的保证。还可以写辅助类，比如 Java 里 Temporal 有 saga 类，本质上就是一堆回调的集合；你说 compensate，就去执行这些回调，回调里可以带补偿逻辑。

关键是动态性。想象有五十种可能的 activity，复杂分支逻辑下每次事务只执行其中五个，且每次是哪五个都不同。用 Temporal，你把 saga 传下去，每个分支记下执行过哪些，补偿时就补偿那五个。换成任何静态图或 YAML/XML 生成的图试试——没有动态补偿，你 practically 得给每条路径和补偿路径分别建模，分支稍多就不可管理。我们发现这是 saga 该怎么实现上很常见的误解：在 Temporal 里琐碎，在基于配置的语言里几乎做不到。

Philip：听起来每种语言的 SDK 在 saga 上提供了挺精巧的一块；而基于配置语言的工作流系统除非系统本身提供，否则没有那一层。

Maxim：有趣的是 saga 本身并不精巧。SDK 精巧的部分是保证你的代码继续跑、完整状态被保留。saga 本身就像我说的，一个你可以二十分钟写完的类：补偿列表，然后 compensate 时遍历跑回调。我写那个 saga 类大概不到一小时。任何人都能写自己的库和框架。Temporal 提供的是运行时保证：代码完成、状态可变（durability）。有一种叫法是 fault oblivious（对故障无感）：你的代码甚至不需要知道出过故障，因为恢复是无缝的。

Philip：这让人想到关注点分离。我看工作流代码时，焦点在事情顺利的那条 happy path，不必操心重试——大概就是这个目标。

Maxim：失败有两类。一类是基础设施失败：进程崩、网络断、断电——与业务逻辑无关的。Temporal 无缝处理它们，你甚至不用想，它们不是你代码的一部分，也不必为了扛住恢复去自己持久化状态，因为状态始终持久，每个局部变量都是 durable 的。另一类是业务级失败：比如往账户存款时账户 ID 错了，基础设施层帮不上忙，这是你的业务逻辑，你可以抛异常再处理。在 activity 里可以区分哪些异常可重试、哪些不可重试。

你可以说“错误账户 ID”是不可重试异常，它会传到工作流，工作流跑 saga 补偿退钱；若是超时、数据库抖动或空指针之类，就会重试。还有意思的一点：间歇问题可以变成两小时修好的问题。比如空指针，你看代码发现问题路径，activity 还在重试，你部署修 bug 的新代码，两小时后下一次重试就过了——什么都不用额外做，工作流继续跑，像没发生过，任何部署都不会打断它们。这是很强的范式：生产出了问题可以边跑边修而不丢状态。

很多人刚接触 Temporal 的第一反应是：间歇错误就让工作流失败吧。不，你不需要那样。你可以按需重试任意久。不必引入人工流程、死信队列、各种脚本——那些都可以去掉。内化这点需要时间，人们不习惯“连想都不用想这类问题”，但上了 Temporal 之后会觉得非常有力。

Philip：你在说开发者和运维一起定位问题，多半会用到 Temporal 的 Web 界面。它提供什么信息？有什么用？

Maxim：好消息是：我们记录工作流里每一个事件，实际上用事件溯源恢复状态，意味着什么都记了。每次 activity 调用你看得到参数，每次完成看得到结果；activity 失败、工作流卡住时，能看到为何失败、重试了多少次、下次何时重试；能看到迄今执行的所有步骤、参数、所有 timer 等，很容易理解发生了什么，能见度很深。最坏情况：你拿到空指针却不懂为什么，因为路径很复杂——可以按一个按钮下载工作流历史（JSON 一类格式），插进本地调试器，想重放多少次就多少次，在本地复现问题。这是非常强的排障手段。

UI 还提供单个工作流的历史和不同视图。你可能有几亿、几十亿工作流在跑，所以我们有索引和自定义属性，可以按条件列出、过滤、计数：给我这个客户昨天失败的所有工作流，列出来再深挖。Temporal 也和常见指标、上下文传播、日志集成；每个 activity、每个工作流、每次重试都会自动打点，不必先加一堆自定义指标才能看懂应用。

Philip：核心概念差不多齐了：workflow、activity、timer、事件历史与重放、错误重试、调试用 Web 界面。回到你说的“工作流即实体”——那些除非实体消失否则从不结束的工作流。你提到了 signal 和 query。能说说吗？它们一开始不太像我熟悉的工作流概念。

Maxim：我们现在有 signal、query 和 update（update 是后来加的）。signal 是打进工作流的单向调用，实质上是把事件投递给某个工作流实例：你说 signal workflow，给出 workflow ID。顺便说，workflow ID 由应用开发者提供，我们按 ID 保证唯一性——系统里不会有两个相同 ID 的工作流同时跑——于是 practically 得到工作流的 exactly-once 执行保证。signal 就是事件，怎么处理取决于语言；Java 里就是回调：这类 signal、这些参数，每次事件进来就调回调，工作流可以异步地反应。

query 是同步地从工作流取出信息。你发起 query，会进到工作流里的回调；这个回调不能改工作流状态，只能返回数据——返回什么由你的代码决定：图片、状态、任意拼接。调用方同步阻塞；要在 UI 上展示这个工作流的信息，就 query，阻塞等到数据回来再画。update 则像两者合在一起：你发请求进工作流，进回调，工作流可以按需阻塞这个回调，某时返回结果，调用方才解除阻塞。update 有两种调用方式：短请求（如即时支付）可以同步；也可能更久，后台做优化过的长轮询取结果。概念上：signal 是单向事件，query 只往外取信息，update 则是“我想领这个促销”——update 工作流改状态、可能跑 activity，再解除 update 调用并告诉你成功或拒绝。

Philip：再举一个 update 的例子，我还不太清楚。

Maxim：换个例子。想象实现向导式的分页流程，比如结账管道——我在 Amazon 做过订购服务，有点感觉。先展示购物车页，选几项点下一步，下一页因选择而不同；填支付信息再下一步，下一页又不同。你可以有一个 checkout pipeline 工作流，阻塞等待某一页返回数据；数据一到就解除阻塞，执行业务逻辑（包括 activity），然后说：现在展示另一页，返回新页面信息，再次阻塞。于是整个向导可以建模成这个阻塞式工作流：展示页一、业务逻辑、展示页二、业务逻辑……想多复杂都行，因为是代码；有状态的会话就是一个工作流。这是很好的实现方式。

Philip：interceptor 呢？好像 strictly 在客户端？我不确定。

Maxim：目前只有客户端 interceptor，我们也在考虑服务端，有些场景需要。想法是：有时想为特定业务用例横切功能。比如每次 activity 完成都往 Kafka 发事件进数仓——你可以写 interceptor，我们在工作流前方拦截所有 API 调用，你可以说在每次 activity 完成后跑一个往 Kafka 发布的 activity；把 interceptor 注册到 worker，每个工作流自动获得这能力。用例很多。以前没有 interceptor 时，人们只能去包一层 Temporal API；现在可以写 interceptor，正常工作流仍用标准 API，就能开箱获得这些能力。

Philip：也就是你想注入到每个工作流里的横切关注点。

Maxim：对，也可以是 activity。

Philip：这就接到各语言客户端 SDK。核心概念和一些扩展概念讲完了。你们有 Go、Java、PHP、Python、TypeScript 的 SDK，.NET 也快来了。我读到至少部分客户端库建在 Rust 核心上，却没有 Rust SDK。客户端 SDK 的结构是怎样的？

Maxim：我们的客户端相当“厚”，因为要实现很复杂的状态机，保证代码执行正确；服务器 API 只给你历史——一堆事件——你得经过大量状态机把它变成实际代码执行。我们也希望每个 SDK 尽可能像该语言的母语：TypeScript 要感觉正常；.NET 要用正常的 async；Python 用 asyncio；Java 我们做阻塞式同步调用，因为 Java 当时还没有像那样的 async。Go 则要用 channel 和 select。

所以每一层都先有“尽量语言原生”的逻辑，底下是非常复杂的状态机。我们发现共同状态机大概占代码和复杂度的 80%。于是我们决定写一个库封装这些复杂度，选了 Rust：和很多语言集成得好，有不错的原生绑定（Python 等），也能走 C API。开发团队也喜欢 Rust。这个核心写了一年，非常复杂，但我们几乎没见过崩溃或实现层面的毛病——逻辑 bug 有，但和实现相关的崩溃几乎没有，对这么复杂的组件来说很惊人。Rust 核心就是库；Python、.NET、TypeScript 都坐在上面，实现简单得多。Java 和 Go 在核心之前就写了，仍各自独立实现状态机。有好处：比如我知道 Go/Java 开发者不太喜欢链进共享库，Python 开发者还好。我们不确定会不会把核心放进那些 SDK，也在想别的办法；理想是每个 SDK 都用核心，走着瞧。总有一天会有基于这个核心的 Rust SDK，只是还没排上优先级。

Philip：所有语言里大概都需要的一个工作流特性是并行执行：五个任务同时跑，不知道哪个最久。你喜欢用哪种语言举例说明怎么做并行？

Maxim：非常依赖语言。Java 里异步调用，拿回 Promise（类似 Future，但为了确定性做了简化），然后循环 `promise.get` 阻塞，或等列表里第一个就绪。用 .NET 就用各种 async 函数，await 那些调用返回的 task，就是正常语言构造，没什么魔法。Go 里可以用 goroutine 开五个并行；也可以调 activity 拿 Future，用 future.get 做异步风格。你有完整的 Go 语言能力，包括 goroutine，来做并行。

Philip：呼应重放机制，绑到并行：假设并行启动五个长任务，代码要等全部完成。某一个完成时会发生什么？工作流会不会每完成一个就被重跑一遍？还是系统知道要等全部？

Maxim：目前没有服务端“等全部再通知”。工作流会收到每一个完成通知，然后继续阻塞。若不太久，工作流会缓存在 worker 上，开销不大；若非常长跑，工作流可能被恢复多次，但既然那么长，这通常不是问题。我们考虑过“全部就绪再唤醒工作流”一类特性，目前只是优化点，还不是大家真正的痛点。

Philip：客户端 SDK 先告一段落，接下来谈 Temporal 集群和 Temporal Cloud。先从集群说起：作为开发者，搭起来要做什么？单二进制怎么用？生产怎么走？

Maxim：本地开发，Mac 上可以 `brew install temporal`，拿到 Temporal 二进制——CLI 加功能完整的服务器都在一个二进制里——然后 `temporal start-dev`。默认可以用内存里的 SQLite 起服务器，很适合开发：每次重启就清掉状态。还有 UI，本机直接打开 Web UI。单二进制就有完整开发环境。忘了提：我们还有不依赖服务器的单元测试框架。比如 Java 里单测工作流，用我们的支持类即可；即使工作流要 sleep 两周，框架会发现并快进两周，毫秒级测完跑几周的工作流。

真要开发可以继续用单二进制；也可以部署到自己的基础设施。有人用 docker compose 做多角色安装，Temporal 各角色分成容器；若要看指标长什么样，用 compose，因为单二进制不含 Prometheus。生产上 Temporal 后端是 Go 编译的二进制，想怎么部署都行：裸机 SCP 到五十台机器配好、保证互通（需要节点间直连），前面给前端加负载均衡。现在多数人用 Kubernetes 或类似技术，用 Helm Chart 部署，或自己写 Chart，或用 ECS 等。Temporal 对怎么跑这些二进制没有强意见；有些要求围绕前端负载均衡、节点通信，以及要供给数据库、建好 schema，把连接交给集群。

Philip：说到数据库，单二进制里是内存……刚才说 MySQL？

Maxim：是 SQLite。

Philip：抱歉，SQLite。你说重启反而好，因为重置状态。数据库里到底有什么？严格是正在执行的工作流加一点调试用历史，还是还有别的？

Maxim：里面有工作流状态、工作流历史、以及用来跨工作流列表的索引。还有技术组件，比如持久 timer——因为只有工作流状态不够：sleep 三十天需要持久 timer，还有很多活动部件。从你的视角看，概念上就是工作流状态、历史、任务和索引。生产部署、尤其大规模时，我们建议和 Elasticsearch 集成，索引放在 ES 里。

Philip：回到实体工作流：有些工作流可能永远跑。状态放多少在工作流里、多少仍放自己的数据库，这是要做的决策吗？人们通常怎么做？

Maxim：好问题。航空积分那个用例，我知道有很大规模的生产用例根本不用外部库，状态就放在那儿——也没多少状态，就是积分，也许再加一点近期事件去重用的 ID。有些基本限制：我们不直接存工作流的“内存快照”，只通过记录事件来存——工作流输入参数和 activity 结果构成状态。历史大小限制大约 50MB；单个 activity 结果不能超过 2MB。所以即便 25 个 activity 各返回 2MB 也会超。我们不建议那么干。要传大 blob，Temporal 不是合适技术，建议存别处、传指针。我们不是大数据系统。

实体工作流“永远跑”的一个 caveat：想象事件循环一直处理事件，历史会无界增长。我们有特殊机制叫 continue-as-new：有点像尾递归消除——从头再调这个工作流，显式传入状态，历史重置为零。这类工作流预期周期性做这个切分，重置历史大小，从而 practically 无限时长跑下去。它也让代码升级更容易：工作流已启动后再升级代码并不平凡，周期性 continue-as-new 能带来升级上的保证。

Philip：你在暗示工作流版本管理。长时间跑的工作流上代码可能变，怎么知道某次执行和新代码是否兼容？

Maxim：这总体是个难题——飞行中更新代码。长跑类系统里版本管理大致两条路。一条是启动时钉死版本：这个工作流以版本一启动，你部署版本二，新工作流钉在版本二；你没法轻易给版本一修 bug，因为新工作流才受益。对相对短的工作流（一小时到一天）这很常见，我们也推荐，生活更简单。但若工作流跑一个月、又不做 continue-as-new、只是一串要一个月的步骤，为每个版本维护一池 worker 会变成噩梦，甚至不现实。

所以 Temporal 提供我们叫 patching 的能力：给已经在跑的工作流打补丁。做法是在代码里同时保留新旧两版——可以在库里、在某个函数、在多处——写 `if` 旧版本走旧代码、新版本走新代码。用我们的 API 可以验证是否所有旧版本工作流都已完成，然后删掉旧分支。这让你能给已在跑的工作流修 bug，并保证兼容；版本条件有专门支持，也有单测和重放支持，避免误破兼容。

Philip：版本管理听起来会复杂，但若你根本没有工作流的显式表示，版本问题只会更大——如果你根本没用这类系统的话。

Maxim：更糟，几乎不可能。你可以做向后兼容的小改，但一旦要做不兼容变更——逻辑散落在多个服务、编排到处都是、不在一处——practically 做不到。有客户说他们卡住了，不敢改，不知道会弄坏什么。事件驱动、尤其编排式（choreography）系统，可以想成一大团全局变量：有人说“我发消息，某个服务会消费，我甚至不用知道是谁”是好事——其实不是，就像全局变量，你一改，不知道代码别处哪里会坏。这类系统极难维护，也难保证变更不破坏。

Philip：集群这边接下来的话题会通向 Temporal Cloud：扩容时发生什么、怎么管。有个多集群复制的概念——为性能、为可靠性，还是两者？

Maxim：纯粹为可靠性。先谈性能和可扩展性，再谈多集群。Temporal 的设计几乎可以无限扩展，practically 能打满任何数据库——到目前我们还没找到打不满的库。应用和集群配置正确时，瓶颈永远是数据库，而且是 CP 数据库。MySQL 和 Postgres 没有内建分片，通常只能垂直扩展；有人用 Vitess 一类方案横向扩，我们不直接支持。多数情况拿到最大实例，扩到某点就撞墙。用 Cassandra 可以加更多主机横向扩，我们见过上百节点的 Cassandra 跑某些负载，Temporal 集群本身跟得上数据库。低速率用例用 MySQL/Postgres 就好；高速率自建版多半要上 Cassandra。

回到多集群：Temporal 用很独特的方式跨区域、跨可用区保证可靠性。单个集群可以部署在多个可用区——Cassandra 三可用区、Temporal 集群也分散——扛住单可用区故障没问题。但整片区域宕机或数据库损坏呢？Temporal 允许在不同区域跑更多集群，彼此完全独立，有各自的存储，甚至不同类型：一个 MySQL、一个 Cassandra 都行。它们用 Temporal 专用的高层应用协议通信，实际上是运送我们放进事件历史的那些事件。这意味着集群如此独立，没有 blast radius 问题——你发不出一条命令同时弄坏两个集群。这比你看到的多数多区域数据库可用得多：那些库常常一条 schema 变更或一条坏命令就能打垮整系统。我们知道多数故障是操作失误、升级失误、版本失误。多区域下集群甚至可以跑不同版本。

按设计，这种多区域与故障转移可用性非常高。因为是异步复制——为了性能，不想等远端区域往返——我们实际上有冲突解决代码。数据库往往只看最后时间戳丢掉其余；Temporal 会检测冲突并解决，即使故障转移前不是每个事件都传到了，也不丢数据、不丢事件。多区域支持很强；当年在 Uber 写的时候，这是跑重要负载的主需求——扛不住整数据中心或整区域故障，就不能跑一级负载。这不创造性能，纯粹为可用性：每个集群独立、有自己的规模上限，假设远端集群跟得上同样规模，通常一样大。每个 namespace 可以单独故障转移。Temporal 有 namespace 概念，是多租户系统，不必整集群切换，必要时切单个 namespace。这不会让集群更快，只是更可靠。

Philip：这是 Temporal Cloud 的好引子。你提到 namespace，你们把 Cloud 定位成 namespace-as-a-service，而不只是托管集群。这两个概念有何不同？namespace-as-a-service 的优势是什么？

Maxim：开源就有 namespace：你部署一个集群，可以在里面建多个 namespace，但你仍然有一个集群。在 Temporal Cloud，我们只给你 namespace，集群概念都不暴露。幕后当然还有集群，但那是我们的问题，不是 Cloud 用户的问题——就像你用 S3 建 bucket，完全不感知 S3 后端有没有集群。Temporal Cloud 一样：走 API 建 namespace，拿到端点，立刻可用。我们要保证这个 namespace 的可扩展性和可靠性，单个 namespace practically 可以无限扩。我们测过每秒三十万 actions，还能更高，只是不想付更高的账单。高吞吐用例扛得住。

能做到是因为我们 practically 写了自己的存储。存储是可插拔的，可以接不同库；我们为自己写了库——只为一个 API、非常窄的访问与更新模式——所以能为这个用例做到极高效、极快、极可扩展。当然不是通用数据库，但让 Cloud 的规模远超 Cassandra 一类，可用性也高于现有那些库。

Philip：你提到 S3，情况类似：要容纳极大的客户规模动态范围。很多客户刚起步，只用你们侧一个集群的一小片；也有客户多团队采用、背后相当于多个集群的算力。

Maxim：我们是多租户的，如前所述不直接提供集群。每个集群可以跑多个客户的多个 namespace，我们会做分配逻辑让负载均匀，留足余量，也有伸缩能力扛尖峰。高吞吐、低吞吐客户都有。多个团队用 Temporal 时，每队多半有自己的 namespace，甚至不必在同一集群。同时，若某个 namespace 需要极高速率，我们也绝对支持。例子：每一条 Snapchat story 更新都是一个走我们 Cloud 的 Temporal 工作流。我们可以到非常高的速率——想象新年夜或超级碗时 Snapchat story 的量。SNAP 用我们服务的原因之一，就是不必为这些事件自己操心扩容，Temporal 服务本身扛着。

Philip：Temporal Cloud 上的保留期和 analytics 呢？我大概不想用同一套库既跑实时工作流又跑去年任务的分析。有什么组合？

Maxim：目前 Cloud 里可以把工作流在 namespace 内留到大约三个月，以后可能加长。在那之前或之后，任何时候都可以配 export：按合适格式把工作流历史放到你自己的 S3 bucket。工作流完成后交给你，合规永久保存也好、跑批处理也好，都常见。

Philip：这和总体可观测性有关。既然跑在 Cloud，若我想自己做调试或核算，有哪些钩子？

Maxim：首先当然有 UI。忘了提：UI 做的一切都走定义良好的 gRPC 接口，你完全可以自己做一版 UI。其次有 CLI：UI 能做的、甚至更多，都可以用 CLI，同一套接口——列工作流、发 signal、发命令、query 等，Cloud 上 CLI 很强。指标方面可以暴露特定 Prometheus 端点，用你自己的证书访问自己的指标。多数指标其实由 SDK 打出；只有 SDK 看不见的服务端指标（多半性能相关、用来优化负载）经 Cloud 那个端点暴露，你也能访问。

Philip：若我需要加密输入输出、不能在 UI 里直接看到明文，有 codec server 一类的东西让我看到实际数据？

Maxim：先给大图。很多人一听“用 Temporal Cloud 还是开源”，第一反应是：我们绝不会用你们的 SaaS。解释完 Cloud 怎么工作之后，多数人会说：哦，这完全可行，能过安全评审——我们过了全球最大银行那种极严的评审。为什么？几件事。第一，加密。Temporal 不是数据库，后端集群不必看懂数据内容。代码跑在你这边：Temporal 只跑后端集群，就像 Confluent 跑你的 Kafka 集群、你在自己环境跑发布/消费应用一样。你链上 SDK，按你喜欢的方式部署应用，Temporal 不知道你怎么部署；它只需要你连到 Temporal 集群。从你的 VPC 或数据中心只需出站连接到 Temporal，Temporal 从不回连——永远是你的代码到 Temporal，经 gRPC，只开一个端口。

然后你可以在发送前加密一切，因为 Temporal 从不查看 payload。activity 输入或工作流输入用你的 codec server、你的算法、你的密钥加密，Temporal 永远看不到明文。UI 有插件：浏览器里跑的 JavaScript 可以指向你 VPC 内本地的 codec，浏览器直连那个 codec 解密——若你有权限。未加密数据从不离开你的内网或 VPC。三件事很重要：Temporal 不跑你的代码；它从不看明文；除了连 Temporal 端点没有别的连接。这三点足以过最严组织的安全评审。

Philip：这又回到节目开头的关注点分离：Temporal 不必知道我代码的内部细节，那不是它的职责域。

Maxim：对。Temporal 不懂你的工作流逻辑，看不到任何代码。它看到的 practically 只是事件：跑这个 activity、完成这个 activity、建这个 timer、触发这个 timer。很低层；业务逻辑活在你的代码里，Temporal 永远看不见。

Philip：很说得通。定价呢？Temporal Cloud 怎么计费？

Maxim：百分之百按用量。你只为用到的付费。用量单位叫 action：每次 activity 执行是一个 action，每次 signal 是一个 action。

Philip：Cloud 差不多就这些，该收尾了。你说单二进制是上手 Temporal 的好方式。对新手还有别的建议吗？看网站、视频？推荐什么？

Maxim：强烈建议上我们的课程。网站资源区有 How to learn Temporal 的链接，有入门指南和课程。主要语言都有 101、102 一类课程。想学懂 Temporal，绝对建议上课——我描述起来像魔法，上课之后你明白魔法怎么运作，就变得显而易见，然后可以专心写应用，少踩边界情况。也请加入我们的 Slack 社区；我们有论坛，Slack 大概九千人，社区很健康，大家经常互相帮忙。你也能在那儿找到我：Maxim Fateev，有问题可以直接问。

Philip：进阶用户想参与实现、既然开源，Slack 有专门频道吗？还是邮件列表？

Maxim：Slack 有频道，主要在 GitHub 提 issue 和请求。有不少大贡献，尤其 SDK：比如 Ruby SDK 由 Coinbase 贡献，现在 Stripe 和 Coinbase 一起维护；还有 Scala SDK 等。也有公司用 Temporal 当引擎做开源项目，这也很常见。

Philip：当引擎是什么意思？

Maxim：比如 Netflix：内部版 Spinnaker 需要 CI/CD 和部署管道，他们用 Temporal 作为底层实现重写了。想象你做创业公司、做机器学习平台并开源——完全可以以 Temporal 为核心，外面砌业务逻辑，省大量时间，practically 只写业务逻辑。我们还有 startup 计划：很多创业公司喜欢我们，价值主张很清楚——代码写得更快、更少、更好排障，公司做大了也能无限扩展。有创业公司流量几个月涨一千倍、一万倍，一行代码都不用改，Cloud 扛住了全部负载。

Philip：课程和其他资源的链接我会放进节目注释。Temporal 和 Temporal Cloud 接下来做什么？看向 2024 年一季度或 2024 年。

Maxim：几件大事。一是把我提到的多区域支持产品化；Cloud 里之前还没跑起来，明年年初会有，我们叫 global namespace——跨多区域分布的 namespace，给负载很高的可用性。二是 Cloud 目前还不能只填信用卡就自助注册，还要填表等邮件，比必要的复杂；明年年初会做完全自助的注册流水线。三是重要项目 Nexus：换一种想 Temporal 的方式——不只是工作流，而是长时操作的服务网格。你调 activity 时，技术上是在用该语言的阻塞或 async 方式调远程机器上的函数，也就是可以跑五天的 RPC。这范式让开发比用一堆事件建模简单得多。我们想让它成为一等公民：定义 API，每个 API 都能跑任意久，于是可用 Temporal 当服务网格把企业里各服务连起来，不必依赖队列或事件，practically 做长时 RPC。项目叫 Nexus，第一版预计明年年初。
