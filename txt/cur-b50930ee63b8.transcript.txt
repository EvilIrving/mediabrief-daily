# React 状态管理比较考察

2021年7月24日 发布

大家好。在 React 相关的话题中，状态管理占了相当大的比重，进一步说，就是各种各样的状态管理库。虽然有点晚了，我还是把 React 中状态管理的方法以及几个状态管理库做了比较考察，整理成了这篇文章。

## `useState` + 逐层传递（prop drilling）

React 中最基本的状态管理是 `useState`。如果状态只在一个组件内部使用，`useState` 非常合适，几乎可以说没有其他选择。

问题在于想在应用的大范围内使用某个状态的时候。如下图所示，考虑这样一种情况：在分叉的组件树末端，有多个组件（使用者）想要引用同一个状态。

与 `useState` 搭配时，最原始的方法是通过 props 逐层传递（日文称为"水桶接力"）。props 是从父组件向子组件传递信息的手段，也是 React 中最基本的组件间通信手段。下图展示了这一过程。

在原生 React 中，组件间的信息传递原则上是"从父到子"。因此，被多个组件共享的状态必然要保存在它们的共同祖先组件中。在上图中，位于组件树顶端的组件持有该状态。这个状态通过逐层传递一直传到末端的使用者（图中的粗箭头）。

另外，如果使用者需要更新状态，同样需要把更新状态的函数通过 props 一路传到使用者那里。

### `useState` + 逐层传递的特点：从职责的角度

这种方法的特点是，**传递状态的职责会落到状态的直接使用者以外的组件身上**。在图中，那些从上面接收状态再原样传给下面的组件就属于这种情况。

一般来说，组件会把它接收的 props 明示为接口。接口代表了组件的职责，所以组件就负有接收这些 props 并恰当使用它们的职责。

这些组件实际上做的只是"把 props 传给子组件"，但对 React 组件而言，"如何使用接收到的 props"本身属于组件内部实现的范畴，并不是职责；职责其实是"根据传入的 props 渲染出恰当的 UI"。也就是说，即便某个组件实际上只是在逐层转交通过 props 传进来的状态，**在接口（职责）上它也是这个状态名副其实的使用者**。

换句话说，在 `useState` + 逐层传递的方法中，只是把状态传给子组件的组件和真正使用状态的组件，在接口上是无法区分的。如下图所示，**接口上的状态使用者比实际使用者更多**。这就是 `useState` + 逐层传递这一方法的特点。

因此，是否采用 `useState` + 逐层传递，可以根据上述情况是否与实际情况相背离来决定。也就是说，如果实际上（包括逐层传递途中的组件在内）组件树上有很多组件都在使用这个状态，那么 `useState` + 逐层传递是合适的。反之，如果有很多组件实际上并不使用该状态、却把它包含在 props 中，就会造成接口与实际相背离的局面，此时 `useState` + 逐层传递就不合适。

### 更实际的视角

上面是从接口、职责这种较为抽象的角度做的分析，下面在此基础上换一个更实际的视角来看。

首先，`useState` + 逐层传递在性能上可能处于劣势。包括通往使用者途中的组件在内，许多组件实际上都以 props 的形式接收状态，这意味着（即使用 `React.memo` 等抑制了重新渲染）状态变化时这些组件都会被重新渲染。结果就是渲染的组件比实际需要的更多。

此外，在重构过程中，状态的类型或名称（即 props 的类型或名称）也可能发生变化。这时，接口中包含该状态类型或名称的组件越多，需要修改的组件也就越多。这说明所谓的内聚度变低了。

基于以上原因，如果重视性能和代码的可维护性，不推荐使用 `useState` + 逐层传递。

## 使用 `useContext`

如果想避免 `useState` + 逐层传递的问题，在原生 React 中可行的选择是使用 `useContext`。`useContext` 使组件之间能够通过 props 以外的方式传递信息。不过，"从父到子"的原则依然保持不变。

下图展示了使用 `useContext` 时状态的传递方式。

由于"从父到子"的原则，实际的状态位于组件树顶端这一点和逐层传递时并无不同。使用 context 时的特点是，在使用者们的上层存在一个叫 Provider 的组件。Provider 下面的子组件可以通过 `useContext` 获取状态的内容。图中的虚线表示的就是这一点，说明可以不经过中间的组件、直接从 Provider 获取状态。

另外，正如图中绿色粗箭头所示，从拥有 `useState` 的组件到 Provider 的传递仍然要使用 props。

### 从接口的角度考察

从接口（组件接收的 props）的角度来看，这个状态已经不再出现在组件的 props 中。中间的组件自不必说，就连作为使用者的组件也不是通过 props，而是通过 `useContext` 接收状态。由此可见，使用状态不再是组件的职责，而被视为组件内部处理的一部分。

换个说法，来自 context 的状态被视为一种外部数据源。平时，各种组件会跳出 React 的世界，直接与 DOM 或网络打交道，这些就相当于外部数据源。由于 context 是通过 `useContext` 而不是 props 获取的，它虽然是 React 机制的一部分，却具有接近这类外部数据源的性质。

也就是说，从 context 获取所需状态的组件，在接口上的表现类似于从外部服务器 fetch 信息的组件。问题在于，像这样把获取外部数据源作为组件内部实现的一环，可测试性会稍差一些。

如果不喜欢这一点，可以引入所谓"container 组件与 presentational 组件"之类的概念，在一定程度上解决。这时，container 组件就成为只负责不知从何处（实际上是从 context）拿来状态的轻薄组件，而 presentational 组件则负责渲染由 container 组件通过 props 传入的状态。通过这样拆分职责，测试会稍微容易一些。

### 更实际的考察

从性能角度看，`useContext` 比 `useState` + 逐层传递更有优势。因为使用 `useContext` 后，状态变化时只有真正使用该状态的组件才会被重新渲染。位于组件树顶端与使用者之间的中间组件，只要不使用 `useContext`，就不会被重新渲染<sup>1</sup>。

但是，当组件间共享的状态变得复杂时，就会产生不满。如果有多种全局使用的状态，它们各自的使用者也不同。这种情况下，就必须按状态的种类分别准备不同的 Provider。用图来表示就是下面这样。

像这样，有 3 种状态且各自的使用者不同时，就需要准备 3 个 context（以及 3 个 Provider）。当某个 context 的状态内容更新时，只有使用它的组件会被重新渲染，其他 context 的使用者不受影响。

把状态共享拆分到多个 context 中的目的，是让状态更新引起的重新渲染最小化。通过 `useContext` 从同一个 context 获取数据的组件们，会在数据更新时一齐重新渲染。如果为了性能想细致地减少无用的重新渲染，就需要相应地准备更多 context。嫌麻烦的话，也可以把各种状态都塞进一个组件里，但这样一来，随着状态越来越庞大，使用 context 带来的性能优势也会逐渐减弱。

总结一下，用 `useState` + `useContext` 做全局状态管理时，必须在**管理大量 context** 和**性能下降**之间二选一。反过来说，如果能接受这一点，`useState` + `useContext` 是有效的，而且还有不需要下文介绍的其他库这一优点。特别是组件树规模不太大的话，性能下降在某些情况下也可能处于可接受范围内。

## react-redux

下面来看使用状态管理库的情况。首先是在面向 React 的状态管理库中知名度首屈一指（需要引证）的 react-redux。其架构如下图所示。

值得注意的是，状态的实体位于组件树外部的 Store 中。如图中虚线所示，使用状态的组件直接 subscribe（订阅）Store（当 Store 有更新时重新渲染）。许多面向 React 的状态管理库有一个共同特点：不依赖 React 内置的手段来获取状态更新并重新渲染。甚至可以毫不夸张地说，这正是使用状态管理库的理由<sup>2</sup>。

react-redux 的一个特点是，每个状态使用者身上都附带着一个 **selector**。从 API 上说，selector 就是传给 `useSelector` hook 的函数，它从状态（Store 中管理的全部状态）中只挑出要用的部分并返回。连接到 Store 的使用者们，即使 Store 的状态更新了，只要该组件用到的部分（selector 返回的值）没有变化，就不会重新渲染。

因此，只要使用 `useSelector`，重新渲染就会被自动优化。像这样用函数来控制重新渲染，是 `useContext` 或内置了它的自定义 hook 无法重现的行为（除非大量制造 context），而能够借助外部 Store 的订阅（subscription）机制做到这一点，正是 react-redux 提供的主要价值。

Redux 的另一个特点是状态集中在一个大的 Store 中。Store 中包含一份大数据，囊括了所有使用者所需的状态，而 selector 的设计就是从这份数据中只取出所需的部分。

另外，图中依然出现了 Provider，但它的作用是把"应该连接哪个 Store"这一信息传递给下层组件，并不传递状态本身。如前所述，Store 基本上只有一个，因此无需考虑这个 Provider 引起的重新渲染。

### 从接口与架构的角度

使用 react-redux 时，组件通过 `useSelector` hook 获取状态。因此，关于组件接口，与 `useContext` 时相同的考察依然适用。也就是说，从 Store 获取状态仍然是组件内部处理的一环，在可测试性等方面也没有特别的差别。

这次值得关注的是新登场的 Store 这一要素。Store 是（redux 而非 react-redux 的）一个要素，是内含状态的可变（mutable）对象。它拥有标准的读取 API（`getState`、`subscribe`）和更新 API（`dispatch`）。

Store 本身是可变的，但 react-redux 以符合 React 架构的方式把它接入了进来。这种"接入"并不是 redux 特有的，编写一个读取提供 `getState` 和 `subscribe` 的外部数据源、并恰当地重新渲染的组件，属于 React 练习题级别的课题。不过，由于可以向 `useSelector` 传入 selector、可以在 selector 中使用 props 等，会带来一些细节问题，而尽可能替你处理好这些问题，正是 react-redux 作为一个库的意义所在。

说到 Redux，大家熟知的是 reducer、action 等要素，但它们是构成 Store 的材料，从状态管理的角度看只是配角，所以没有出现在上图中。尤其是 action，笔者认为如果把它看作更新状态的手段，就显得有些冗余。action 的真正价值，应该在于它结合 redux middleware 提供了一种消息传递（message passing）架构。笔者认为，Redux 中就这样同时存在着状态管理和消息传递这两种不同的职责。本文只关注状态管理这一面。

不过值得一提的是，作为获取更新函数（`dispatch`）的方法，提供了独立于 `useSelector` 的 `useDispatch`。不使用 `useSelector`、只使用 `useDispatch` 的组件（专门负责更新状态的组件），在 Store 内的状态更新时不会重新渲染。要用 `useContext` 实现同样的效果，必须把传递状态的 context 和传递状态更新函数的 context 分开；而 react-redux 则像这样内置了最佳的手段。

重新总结一下作为状态管理的 react-redux 的特点：第一个特点是，它把状态保存在组件树外部，通过自身的订阅机制控制状态更新时的重新渲染，从而**以低成本提供经过优化的重新渲染**。不过，优化的重新渲染可以说是状态管理库的基本要求，并不能算 react-redux 所特有。

react-redux 特有之处在于，**用一个 Store 管理（全局共享的）所有状态，再通过 selector 从中只取出所需部分的这种接口**。特别是 selector 的类型是 `(state: 全てのステート) => 必要なステート`（即"(state: 全部状态) => 所需状态"）这样的形式，状态的使用者总是不得不意识到整体的状态（通过适当准备自定义 hook，这一点可以得到一定程度的缓解）。

## Recoil

这里我们选取 Recoil 作为与 react-redux 相对照的状态管理库。Recoil 在性能方面与 react-redux 特性相似，但提供的是截然不同的接口。

上面所示的 Recoil 概念图表明，在 Recoil 中，负责保存状态的是被称为 Atom 的东西。组件可以订阅 Atom（图中的虚线）。

此外，Recoil 还有 Selector 这一概念，它订阅 Atom（或其他 Selector）并计算出自己的值。组件不仅可以订阅 Atom，也可以订阅 Selector。借助 Selector，还可以把多个 Atom 的数据组合起来，计算出所需的数据。Atom 和 Selector 统称为 RecoilState。

理所当然，订阅 Atom 或 Selector 时的重新渲染是经过优化的。也就是说，订阅 Atom 时，只有 Atom 的数据发生变化时组件才会重新渲染。另外，在 Atom→Selector→组件 这样的订阅链中，Atom 的内容变化时 Selector 的内容会被重新计算，但如果结果与之前相同，组件就不会重新渲染。因此，如果想比 Atom 的数据更新更细致地控制组件的重新渲染，可以像这样在中间插入 Selector。

### 架构上的特点

如上图所示，把 Recoil 与 react-redux 相比，其特点在于并非所有状态都集中在一处。在 Recoil 中，作为数据源的 Atom 存在多个是很常见的情况。这使得在 redux 中无法实现的"状态的 code splitting（代码分割）"成为可能。Recoil 的官方网站上也以"The state definition is incremental and distributed, making code-splitting possible."（状态的定义是增量式、分布式的，使代码分割成为可能）来宣传这一点。

在前面的图中 Atom 集中在右上方，而如下图所示，Recoil 也很适合那种只在组件树末端少量使用（但被多个组件共享）的用例。

如果像 Redux 那样把所有共享状态都保存在一个大 Store 中，就会让人犹豫是否要为末端这种小小的共享状态去添加状态。而在 Recoil 中，即使是这种情况，也能自然、轻松地创建共享状态。把状态的来源分散开，就有这样的架构优势。而且，如果进行了恰当的 code splitting，在引用 Atom 的组件被加载之前，Atom 本身也不会被加载。也就是说还有性能上的优势。

Recoil 在架构上的有趣之处在于，上述 Atom、Selector 的概念是以底层且灵活的形式提供的。也就是说，把 Recoil 作为零件来用，就能搭建出随心所欲的架构。而且，它还提供了主要与异步处理相关的、从一个 selector 生成另一个 selector 的辅助函数，进一步突显了"零件"这一面。

例如，也可以把状态塞进一个大 Atom，有意以类似 Redux 的架构来使用 Recoil（下图）。在这张图中只有一个 Atom，并为每个使用者准备了对应的 Selector。这与前面 react-redux 的情况非常相似。

像这样，使用 Recoil 提供的零件，就能构建出随心所欲的架构。在项目结构上，Atom 和 Selector 放在哪里、是集中放在专门的目录里，还是把 Selector 放在作为使用者的组件旁边，正因为它是底层的，所以有选择的余地，这一点有待今后进一步研究。

Recoil 本身是一个比较新的状态管理库，其 API 也是充分利用 Hooks 的现代化设计。再加上它对异步处理有出色的支持，可以期待它与计划在 React 18 中引入的 Suspense 和 Concurrent Rendering（并发渲染）有良好的亲和性。

此外，它还通过 `atomFamily`、`selectorFamily` 这样的 API 支持动态生成 Atom 和 Selector，包含动态状态管理的逻辑也可以用 Recoil 实现。

总结一下，Recoil 的特点是**以 Atom、Selector 这种简单的概念为基础，在不强制特定架构的前提下提供全局状态管理的零件**。可以把订阅管理等麻烦的部分交给 Recoil，同时用随心所欲的架构来进行状态管理。

顺便说一句，上图中看起来状态是保存在 Atom 里的，但实际的保存位置是 RecoilRoot<sup>3</sup>。更准确地说，应该把 Atom 和 Selector 理解为定义了数据流的 DAG（Directed Acyclic Graph，有向无环图）中的节点。从这个角度看，也可以说 Recoil 的特点是能够以热插拔的方式添加新的状态定义。

## mobx-react-lite

作为另一个状态管理库的例子，我们来看看 mobx-react-lite。顾名思义，它是 MobX 的 React 绑定。lite 指的是由于采用基于 Hooks 的 API，只支持函数组件。

在 MobX 中，状态是可变对象，通过对该对象进行破坏性修改来表示状态的更新。前面介绍的各种方式与此形成对照：存在 `useState`、Store、Atom 这样的"状态容器"，实际的状态只是普通的不可变对象，状态更新是通过准备另一个对象来完成的。MobX 不需要这类"状态容器"或"状态更新函数"之类的概念，卖点是可以直接读写状态。官方文档把这一点形容为"Straightforward"（直截了当）。

从本文的视角来看，与之前的状态管理库相比，MobX 的一大区别是**对状态的订阅是隐式进行的**。在 MobX 中，表示状态的对象会被加工成 **observable**（可观察对象）。而组件则被声明为引用它的 observer（观察者）。当 observer 对 observable 对象进行 `obj.foo` 这样的普通引用时，就会检测到对 `foo` 的隐式依赖。之后，当该属性的值发生变化时，相应的 observer 会自动重新渲染。正是这一机制实现了经过优化的重新渲染。

也就是说，在 MobX 中，组件表达对状态的依赖的手段是 `obj.foo` 这样的普通属性引用<sup>4</sup>，声明依赖时不使用 props、`useContext`、`useSelector` 等显式 API。

像前面一样用图来表示 MobX 的状态管理架构，就是下面这样。不过，对 MobX 而言，这张图只是一个例子。

因为组件如何引用状态（observable）并没有固定下来，可以考虑多种方式。上图假定的是最简单的模式，即**把 observable 放在全局变量中**。也就是说，把做成 observable 的对象放在全局位置，使用状态的组件只要声明为 observer，之后像平常一样读取该对象，就能获得经过优化的重新渲染。

其他方式还有通过 props 或 context 传递 observable 等。在这些情况下，就构成了以本文开头介绍的 `useState` + 逐层传递或 `useContext` 方式为基础，再用 MobX 的优化重新渲染来弥补性能缺陷的结构。

由此也可以认为，**MobX 提供的不是整个状态管理，而是专门用于优化重新渲染的零件**。

不过，我个人认为 MobX + React 在易用性方面稍逊一筹。首先，要享受 MobX 带来的优化重新渲染，就必须把组件全都显式标记为 observer。这是让 MobX 能追踪依赖关系所必需的，但非常费事。另外，如前所述，对状态更新的订阅是隐式进行的，所以 `obj.foo` 这样的普通引用就带有了副作用。这与 React 的思路不太契合。再者，如果真想优化重新渲染，就必须在组件树中细致地控制这个副作用在哪里发生，可维护性会大大降低（MobX 官方文档中以"Optimizing React component rendering"为题给出了实例，相当痛苦，不妨看看）。

## 总结

本文对 React 中的状态管理方法（包括几个状态管理库）进行了比较和分析。简要总结如下。

- `useState` + 逐层传递的特点是，包括只负责中转状态的组件在内，状态的使用者都会在接口（props 定义）上被明示。
- `useContext` 与逐层传递的区别在于，对状态的依赖被内化到组件中，这一特点也被几乎所有状态管理库继承。单靠 `useContext` 在性能上并非最佳，不满意的话就要借助状态管理库。
- react-redux 的特点是状态被外置到 Store 中、所有状态集中在一个 Store 里的架构。包括 react-redux 在内的许多状态管理库，从重新渲染性能的角度来看都是最优的。
- Recoil 可以把状态分散到多个 Atom 中。它通过原始（primitive）的 API 提供不强制架构的状态管理零件，从而有助于构建最合适的架构。
- mobx-react-lite 的特点在于对状态的依赖是隐式的、并且是一种副作用。它只专注于优化重新渲染，在与 Recoil 不同的意义上作为状态管理的零件发挥作用。

### Q & A

- （在这里填入你喜欢的库）怎么样？
  - 请联系笔者。说不定会被加进这篇文章。
- jotai 怎么样？
  - 在架构上与 Recoil 相同。它的文档一开头就是与 Recoil 的比较，列举的区别主要是 API 上的差异而非架构层面的差异，由此可见。
- 用 SWR 或 React Query 这类数据获取库来管理状态怎么样？
  - 关于这一点，React Query 的文档中有一页题为"Does React Query replace Redux, MobX or other global state managers?"（React Query 能取代 Redux、MobX 或其他全局状态管理器吗？），可供参考。
  - 实际上，这些库确实提供了某种状态，当然就是装着获取到的数据的状态。而且由于缓存在组件之间共享，这是一种全局状态。它们提供的 API 主要目的是省去与管理这种缓存相关的样板代码。
  - 如果全局状态的主要用途就是保存获取到的数据，那么也有可能不再需要其他状态管理库。
  - 这些库拥有用来识别缓存数据的"键"（key）这一概念，数据可以由末端组件随意添加，因此作为状态管理架构，它们与 Recoil 相近。另一方面，这些库侧重于以易用性为第一位的高层 API，与以底层 API 为中心的 Recoil 形成对照。
  - 这些库的状态管理是自成一体的<sup>5</sup>，如果还有很多与数据获取无关的状态，要在两种状态管理融合的状态下获得最佳性能恐怕很难。如果这里需要最佳性能，也可以考虑不用 React Query 或 useSWR 等，而是向 Recoil 之类靠拢。
