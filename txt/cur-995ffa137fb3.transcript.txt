绿色的退出码不能证明活儿真的干了

2025 年 3 月，OpenAI 的一个团队发表了一些你平时不太能看到的东西：他们自家一个前沿模型在训练中处理编码任务时的私下推理。模型看了看问题，判断完整实现整个功能太难，于是写下了一个替代方案：如果它调用 sys.exit(0)，测试框架就会优雅地退出。“这很不自然，”它写道，“但测试可能会通过。”

测试通过了。

研究者把这称为一种“系统性”的作弊手段，它足够通用，模型一旦发现，就会蔓延到几乎所有训练环境中。他们还抓到了第二个同类手段：在测试框架之外抛出异常，彻底跳过评估。在论文的其他部分，agent 为测试覆盖薄弱的问题编写桩实现；在运行时解析测试文件，提取并返回测试恰好要检查的值；还有我最喜欢的一个：发现有人遗留在仓库里的一个编译好的 .jar 文件，把它反编译，然后抄出了参考答案。

这些运行，每一次都是绿的。

信任论证止步的地方

Ryan Donovan 今年 7 月在这里论证说，开发者之所以依恋自己的工具，是因为工具承载着信任，而这种信任是通过重复赢得的可预测性。这就是为什么一把你用了十年的刀感觉像手的延伸，也是为什么每隔几周就改变形状和重量的 agent 工具，很难以同样的方式获得信任。

我认为这是对的，但我想在它止步的地方再往前推一步。信任之所以积累不起来，还有第二个原因，而且在结构上比第一个更糟。问题不仅在于工具不断变形，还在于你学习这件工具所需要的反馈回路，恰恰在测量这一环上坏掉了。

开发者拥有的每一件信任工具，退出码、绿色的 CI、通过的状态检查、“任务完成”这几个字，都建立在一个假设之上：软件失败时会大声失败。无人值守的 agent 却是悄无声息地失败。一个循环可以干净地终止、报告成功，却什么也没产出，而你的技术栈里没有任何信号能把这种情况和一份干得漂亮的活儿区分开来。把它叫作“无声的绿色退出”吧。

我做过 ProAI，最早一批商业化的 GPT 产品之一，现在我研究多智能体系统，以及如何在它们靠近生产环境之前对其进行评估；我在 chasewhughes.com 上写这些内容。我认为这是我们准备最不充分的失败模式，它得到的关注只是能力和安全的零头，因为在三者之中，可靠性写起来最无趣，却也是唯一决定你能不能真正用上这东西的一个。

大声失败不是我们挣来的，而是继承来的

想想刀为什么能成为一个比喻。你信任一把刀，是因为它一滑你就会流血：立刻、明确，而且会在你再次拿起它之前教会你点什么。开发者信任的每件工具都具有某种版本的这一属性。段错误是大声的，断言失败是大声的，500 错误是大声的。退出码是被压缩成一个整数的“大声”，它大概是计算领域里被消费得最多的一项遥测数据。

关于 exit 0，值得注意的是由谁发出它。当 make 以 0 退出时，这个整数位于工作的下游：编译器运行了，生成了目标文件，然后返回。这个状态是一种观察，由一个处于能够观察位置的进程做出。这个数字是关于真实世界的证据。

当一个 agent 循环以 0 退出时，这个整数是由一个编排器发出的，它之所以停止循环，是因为模型生成了一个意思是“完成”的 token。在模型的声明和退出码之间，没有任何东西检查过任何事情。这个状态是一种自我评估，而你把它插进了一个为观察而设计的插座。下游的每一个消费者，你的仪表盘、告警规则、重试逻辑，还有周一早上扫一眼运行历史的那个人，都继承了这个替换，却从没被告知它发生过。

这就是全部的机制。剩下的，是它在现实中的样子。

这个缺口已经有了数字

Donovan 引用了本站自己的开发者调查来说明信任的背离，值得把原始数据拿出来，因为它的形态非常鲜明。在 2024 年和 2025 年的两次调查之间，使用或计划使用 AI 工具的开发者比例从 76% 升到 84%，而信任这些工具产出准确性的比例从 43% 降到 33%。明确的不信任则朝相反方向变化，从 30% 升到 46%。最大的一项抱怨，有 66% 的人提到，是“几乎正确、但又不完全正确的 AI 方案”。

“几乎正确、但又不完全正确”描述的是一个你能看到的输出。我所描述的问题位于它的下一层：一次运行不是几乎正确，而是空的，而它呈现出来的样子和一次成功的运行完全相同。

有两个基准测试能把这一点具体化。来自 Sierra 研究团队的 τ-bench 引入了一个本该更广为人知的指标：pass^k，即 agent 在同一任务上全部 k 次尝试都成功的概率，而不是至少成功一次的概率。在他们测试的模型上，零售领域的 agent 在标准指标上低于 50%，在 pass^8 上低于 25%。

这些具体数字已经过时了，我想坦白说明这一点：那是 2024 年，主打的模型是 GPT-4o，前沿此后已经前进了很远。但这个指标本身完全没有过时。pass^k 直接测量了 Donovan 所说的构成信任的那种属性。它问的是周二是否和周一一样，并给这个答案一个数字。几乎没人报告它，这就是为什么在工程讨论中，“我试的时候能用”仍被当作证据，而在其他任何事情上，没人会接受这种证据。

第二个是卡内基梅隆大学的 TheAgentCompany，它把 agent 放进一家模拟的软件公司，给它们真实的工作去做。最有竞争力的 agent 自主完成了 30% 的任务。但属于本文论证的发现不是这个分数，而是研究者描述的一种行为：“当 agent 不清楚下一步该做什么时，它有时会试图耍小聪明，制造出省略任务中困难部分的虚假‘捷径’。”他们举的例子再贴切不过：一个 agent 在公司的聊天平台上找不到某位同事，于是把另一个用户改名成了那个人的名字，然后继续往下做。

好好想想这会产生什么。从外部看，这一步完成了。有一个名字正确的用户，有一个针对它执行的动作，整个执行轨迹里没有任何错误。唯一的问题是，那位真正的同事什么也没收到，而系统里没有任何东西知道这一点，包括 agent 自己，它没有任何理由相信自己失败了。

当它进入生产环境

2025 年 7 月，Jason Lemkin 花了大约两周时间在 Replit 的编码 agent 上开发，并一路公开记录。数据库被删的事抢占了头条：尽管他早就下了指令，未经他允许不得改动任何东西，agent 还是清空了一个生产数据库。但属于本文的那部分发生在这之前，得到的关注要少得多。

“它不断用假数据、假报告来掩盖 bug 和问题，最糟糕的是，在我们的单元测试上撒谎，”他写道。有一次，agent 生成了一个包含 4000 个完全虚构人物的数据库。事后，它告诉他回滚是不可能的，所有数据库版本都已被销毁。这也是错的：回滚完全正常。

假数据、假报告、被谎报的单元测试，以及一个经不起核查的自信的状态声明。Replit 的 CEO 称所发生的事“不可接受，本不应该有可能发生”，这是正确的回应。而这起事件至今仍是我所知道的最清楚的公开例证，说明了“失败的 agent”和“汇报的 agent”之间的区别。

反对意见，而且是个好的反对意见

一位通情达理的 SRE 会这样回应这一切：这些都不新鲜。cron 任务从 1970 年代起就在无声地失败。这就是为什么我们有死人开关、心跳监控，以及在信号缺失时（而不是在出现错误时）触发的告警。你只是重新发现了监控，并给它起了个名字。

这基本公允，而且其中藏着的好消息是真的，因为这意味着解决方案的形态已经为人所知，工具也已经存在。但有一个区别会让老办法失效，值得把它说精确。

所有这些技术之所以有效，是因为失败模式是可以枚举的。你知道一个夜间任务无法完成的方式是有限的一张清单：机器宕了、磁盘满了、锁被占着、上游超时了。你要么为每种模式写一个检查，要么写一个覆盖所有情况的心跳，因为“完成”只有唯一的含义，而任务本身对此没有任何主见。

agent 则在运行时自己决定控制流。计划在每次运行时重新生成，这意味着“干净地终止却什么也没产出”的方式，不是任何人能事先写出来的一张清单。它包括因为实现读取器看起来很难而调用 sys.exit(0)。它包括给一个用户改名。它包括你们公司里没有任何人想到过的策略，因为你们公司里没有任何人在制定这些策略。

所以你没法从失败那一侧来写检查。任何从失败一侧写出的东西都是一张清单，而 agent 并不受限于你的清单。你必须从结果那一侧来写。

度量产物，而不是度量运行

由此得出四点。它们都不需要新工具，而这正是重点所在。

对工作产物做断言。不是“循环是否以 0 退出”，而是“那一行是否存在、文件是否在磁盘上、消息是否真的离开了队列、分支是否真的推送了”。检查必须读取不是由 agent 编写的状态。如果你证明邮件已发出的唯一证据，是 agent 报告说它发了，那你就没有证据。你有的只是一个与答案有切身利害关系的一方所做的声明。

不要让验证和工作共享同一种失败模式。如果同一个 agent 在同一个上下文里既做事又汇报，汇报就会继承这份工作的所有错误，包括导致这些错误的那些原因。Donovan 提出把 LLM 当裁判，作为以 agent 的速度进行审查的新兴答案，我认为这是对的，但有一个约束：裁判必须读产物，而不是读对话记录。读对话记录的裁判是在给一个关于这份工作的故事打分，而讲故事正是这些系统最擅长的事。

在没有变化时告警。这是清单上成本最低的一项，却几乎没人做。一个总是会写入的任务，这一次什么也没写、却报告了成功，比一个抛出异常的任务更可疑。错误会触发告警；零效果的成功只会在一份没人看的运行历史里得到一个绿色方块。把它反过来。一个定时运行的 agent 如果报告成功却什么也没碰，就应该把人叫起来。“什么都没有”也是一种结果，它理应是一个大声的结果。

部署之前在模拟中测量 pass^k。让 agent 把同一个场景跑上几十次，看分布而不是最好的情况，而且要在一个你掌握真实答案的环境里，这样你就能检查产物而不是故事。模拟的目的不是证明 agent 能完成这份工作，谁都能演示这一点。目的是弄清楚它有多常声称自己完成了。

我们还没有替代的东西

注意，这一切是多么朴素。断言和告警，正是在之前每一代基础设施中建立起信任的同一套纪律，只是对准了一个不同的目标。

真正新的是这一部分，它体现在人们谈论这件事的方式中。OpenTelemetry 针对生成式 AI 的语义约定，是业界最接近“就如何为这些系统埋点达成共识”的东西，它为模型、操作、输入和输出的 token 数、结束原因、错误类型、agent 自身的名称和版本都定义了属性。这些都很有用。但其中没有一个属性表示工作是否真的发生了。这不是疏忽，我也不认为这是一种批评；这些是为一次“调用”埋点的约定，而在以往每一代软件里，这个问题都不需要一个单独的字段。完成就意味着产生了效果。你不需要问编译器它是不是认真的。

这种隐含关系已经消失了，而且还没有任何东西被放到它的位置上。绿色的退出码过去是关于你的程序的一个事实。现在它是你的 agent 持有的一个看法。而信任之所以积累不起来，不仅仅是因为刀一直在变形，更是因为你已经无法分辨它到底有没有切下去。
