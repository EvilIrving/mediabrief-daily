데이터 분석 에이전트를 만들며 배운 컨텍스트 설계 ｜ Kakao Tech ｜ 文章 ｜ https://tech.kakao.com/posts/838

Kakao Tech 工程师 logan.wvl 总结了开发一个数据分析智能体时的上下文设计经验。这个智能体接到业务问题后，会自己找数据、写 SQL、执行并解释结果。他把上下文拆成三块来讲：系统提示词、工具规格说明和消息数组，然后介绍两种上下文工程手法：渐进式发现和子智能体。

系统提示词只放贯穿全程的通用内容：角色定义、安全规则（比如不执行会暴露用户标识符的 SQL，改为提供汇总统计）、判断标准和默认值（没说口径时默认按 DAU）、多个工具共用的使用原则、回答原则，以及领域背景和按服务整理的表清单。GPT-4 时代模型自己判断能力弱，他们曾在系统提示词里写死"Workflow"步骤和各种情况的规则；模型变强后，改为把每个工具的使用条件写进各自的规格说明，交给模型自行决定顺序。这也符合 Anthropic"提供极其详细的描述"的建议：在 Claude Code 里，工具说明约 15k token，是系统提示词（3.7k）的 4 倍。

工具规格说明要写清作用、调用条件、参数含义与选择标准，以及结果怎么呈现。以图表生成工具为例：只在用户明确要求、且已有 SQL 结果时调用；用 enum 限定 chart_type，并给出"趋势用 line、类别比较用 bar"之类的选择标准；内部生成 Vega-Lite 的 LLM 看不到对话，所以要求主智能体在 instruction 里写明要展示什么、强调什么；图表直接显示在屏幕上，回答里只补一两句洞见。工具不宜越拆越多，可以借《A Philosophy of Software Design》的"深模块"思路合并：笔记工具用 note_key 是否为 null 来区分新建和修改；"写 SQL、执行、改错、重跑"这一串步骤，则整体封装成一个工具，也就是一个子智能体。消息数组按顺序记录对话、工具调用和结果。比如知道有 service 列但样本值里没有服务 A 的实际取值时，模型会先去查过滤值；"把时间范围延长到一个月"这类后续请求，也靠这份记录来定位要改的分析。

渐进式发现指像 Claude Code 找登录代码、或 Agent Skills 先看名称再读详情那样，边探索边决定下一步读什么。他们起初用独立的探索智能体找表，但主智能体不知道有哪些表可用，常常反复搜索后才发现根本没有需要的表。后来把各服务的表清单作为"索引"写进系统提示词，再按需查询详细结构，更早发现缺表，也减少了轮次。子智能体则用来隔离用完即弃的中间记录：原来失败的 SQL 和报错一直堆在主消息数组里，现在交给专门的 SQL 子智能体处理，主智能体只拿回最终 SQL、状态和结果，但必须在指令里写明已确认的条件，因为子智能体看不到对话。两种做法看似相反，判断标准是同一个：信息之后还用不用得到。用得到就留在主上下文，比如表清单和结构；用不到就放进子上下文，比如报错记录。
