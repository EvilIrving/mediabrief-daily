主播：大家好，这里是 AsyncTalk。今天想跟大家聊一聊前段时间发布的 TypeScript 7。大家在去年就已经收到这个比较爆炸性的新闻了：TypeScript 要用 Go 来重写。今年它终于把它落地了。

TypeScript 7 有非常巨大的性能提升，大概在 10 倍左右。首先，VS Code 的 tsc 类型检查从 78 秒降到了 7.5 秒，这是一个非常巨大的提升，尤其是对 VS Code 这样的超大项目来说。其实我们公司那边也有个项目，大概是 58 万行代码的量级。

这个量级的代码，用 tsc 检查大概要 64 秒左右。当我把它升到 TS 7 的时候，只要大概 3 秒钟左右，效果非常明显。虽然我们的代码仓库没有达到 10 倍的效果，但它已经让人非常惊艳了。

最主要的是，这个升级过程几乎是无痛的。如果你的产品是一个普通的、做外部开发的产品，那对你来说它完完全全是无痛的。基本上我们代码写完之后，会有一些 lint、一些类型检查，而类型检查我们基本上是去调 tsc 的命令行来做的。如果你也是这样一种普通项目，你今天就可以直接无痛替换了。因为对于这种 CLI 使用的场景来说，基本上没有任何变化。它只是内部代码的重写：用 Go 去重写，用了一些多线程的技术来加速整个检查过程。

其实对我来说，最重要的是编辑器的使用。我知道大家现在基本上可能已经在用 coding agent 来干活了，相当一部分人可能都已经不怎么看代码了。但对于我这种稍微有些传统的人来说，我还是会时不时用编辑器去做一些事情、检查一些代码，有自己手动微调代码的场景。在这种场景下，TS 7 带来的变化对我来说是最为重要的。

因为我工作中有一个项目，从前几年大概 200 万行代码的规模，扩展到最近大概 300 万行代码的级别了。当你在维护如此量级的代码库时，你会发现里面各种各样的问题都被放大了。就像我之前跟大家提到过的编译速度、粒度提升的问题一样，在这样一个巨大项目里，你的代码编辑器承担的任务是非常庞大的。

就像我那个项目，我一天打开编辑器，编辑器里的 TypeScript 语言服务（LSP）基本上一天要崩溃五六七八次。要么是内存占用太高，要么是 CPU 太高。当然我没有细查过问题，但情况就是这样，它会崩溃非常多次。我相信是因为我们的代码量级有些过于庞大了。当我们迁移到 TS 7 的时候，带来的效果不仅仅是项目不再崩溃了，而且在做 TS 类型提示的时候，它会响应得更快。

这个快是随着代码量级越大越明显的。当然，那个 300 万行的项目我并没有去做升级，因为它的升级有点可怕。但 58 万行的那个项目做了升级。升级之后，我自己的体感相当不错，应该是再没有崩溃过了，代码类型提示的速度体感上也有一些提升。

但我前面说的那些项目，都是非常标准的外部开发项目，用的都是 tsc 命令行工具。如果你的项目用到了 TypeScript 的 API，情况就会变得有点麻烦了。比如说，至少在 Next.js 某个版本之前，它的 lint 实际上是通过 TypeScript 里的 API 来做的，它需要去调用 typescript 这个包里的 API 来做一些事情。这种情况在 TS 7 上还没有原生支持。

据我所知，一些大的开源库目前已经支持了。比如较新版本的 Next.js，可以通过 next.config 里一个实验性的、使用 TypeScript 原生 CLI 的参数去开启。这样，如果你的项目只依赖 Next.js，它就可以升级到 7，然后正常使用。但如果你有一些其他的依赖，比如我之前推荐过的 Hey API，它会调用一些 TypeScript 里的 API。对于这样的项目，我可能就要去观察它们仓库的兼容情况了。据我了解到的消息，TypeScript 7.1 版本会去支持 API 这类东西。所以如果你的项目重度依赖 TypeScript 的 API，那你可能没法这么丝滑地升级，可能要再看一下其他方案，或者稍微再等一等。

接下来，我其实想聊一个跟 TypeScript 本身无关的东西。因为 TypeScript 这个版本在我看来没什么好讨论的：它就是很好、很快，功能也很正常。如果你只用 CLI，就直接无痛升级就好，这在我看来没有什么疑虑，因为社区以及一些公司都已经在用了。如果你的项目重度依赖 API，那就再等等呗，等到 7.1 版本再看看。

其实在之前 TS 7 preview 版本刚发的时候，在外网引起了相当大的舆论风波。目前在编程圈，重写的一种"政治正确"是拿 Rust 去重写一切。像我们都知道的，前段时间比较火的 Bun，我们上一期也聊了，Bun 是拿 Rust 去重写的，效果看起来也还不错。更早一些的 CLI 系统工具里，用 Rust 写的项目就更多了。比如我自己比较喜欢用的、用 bat 去替换 cat 这类 Rust 工具。那为什么 TypeScript 要拿 Go 来重写呢？

有很多采访，也有各种各样的说法。但这里我想自己尝试解读一下这件事。其实我自己用 Go，大概有个七八年的经验。如果有关注我的一些项目，你会发现除了前端项目，基本上都是用 Go 实现的。无论是 CLI、web server，还是一些桌面工具，我基本上都是拿 Go 来写的。

另一方面，我也试过 Rust。我用 Rust 写过一些简单的 HTTP 工具、一些 CLI 项目，代码量级不算高，估计大概几万行左右。我自己的观点是，我个人更偏好 Go，和 TypeScript 团队的想法是一样的。如果是我来重写 TypeScript，我相信我大概也会拿 Go 来重写。

我认为这是一种个人选择。对我来说，Go 语言的平衡性做得非常好。首先是它的性能，Go 的性能绝对不差。我要跟互联网上那些可能没写过代码的程序员拜托一下：Go 的性能绝对不算差，它实际上就是机器那种基本的性能。如果你只是拿 1+1、2+3 这种简单的例子来做对比，我并不能同意。你可以拿一些真实的项目、真实的场景来看看，Go 的性能绝对不算差。毕竟它是一种静态语言，静态语言的性能是不太可能差的。它编译成机器码，不需要 VM 这种东西。

另一方面是它的学习曲线。Go 语言的设计是非常克制的。指针我得说确实非常复杂，有各种操作上的小技巧，但 Go 语言克制了非常多。你看泛型这样一个几乎广为人知的概念，在 Go 里也是经过非常慎重的考虑之后才去做的。

在 Go 里，我印象非常深的是它对 error 的处理。像我们现在普通的语言，基本上都是用 try-catch 的方式来做。它有没有好处？有，它很方便，然后会一层一层往上抛。但它有没有别的问题？最大的问题就是"惊喜"：你并不知道哪里会抛错。上层抛出来一个错，可能是下面两百层的某个地方触发的。当然，如果你的同事写代码再"骚"一点，他甚至可以让你的系统崩溃，而你却不知道真实的崩溃原因是什么。这是一个非常痛苦的点。我相信只要你维护过稍微大一点的系统，你都会理解 try-catch 并不是一个很好的设计。

但 Go 对这件事的做法非常坚持：每一个函数都需要显式地返回 error。这样当你写代码的时候，你就知道这个地方可能会有 error，你得处理一下，或者非常明确地表示"我不处理"。

另一点，我认为 Go 在平衡上做得很好的，是几乎所有语言都有的三目运算符，Go 里面是没有的。你去学 Go 的语法，会发现它没有，非常简单，你只能用一个 if-else 来做这件事。我认为这是 Go 里面非常勇敢的设计之一。我相信你如果写过前端代码，就知道大家其实很喜欢写这种三目运算符。但三目运算符有个非常大的问题，就是可读性非常差。每多一层三目运算符，可读性就急速下降。我可以很确定地说，地球上没有人能够理解四层嵌套的三目运算符。

因为三目运算符就是一个 if-else，如果叠 4 层，可能性就已经变成 2 的 4 次方，对吧？就变成 16 种可能性了。在短短几行代码里有 16 种可能性，我不知道人脑的构造要到何等层次才能轻易理解这件事。在我看来，三目运算符就是一个很大的糟粕，而 Go 里面就明确说了不支持。

像泛型，我当然是蛮喜欢泛型这个设计的，因为泛型可以有相当高程度的抽象。但我相信大家如果写过泛型，也会同意一件事：泛型把很多问题变得很复杂。当然有好多人能拿泛型写出花来，短短几行代码写出一些非常高深的操作和技巧。但我要说，大多数人并不是那种神仙，大多数人是不会做 TS 那种类型体操的。同样，我也不认为我们应该学习这种类型体操，因为它不是正常人的思维。我也不认为它是 AI 应该去理解的东西。一段逻辑就应该简简单单，在可读性第一的前提下，我们才可以谈其他的东西。

那我们回到另一个问题：Rust 的性能好不好呢？非常好，它甚至能让你自己掌控内存回收。因为 GC 不可避免地会影响性能，而且它也有一定的不可预测性。Rust 没有 GC，让你自己控制内存，这样你就可以写一些极端高性能的场景，一些计算不会被 GC 打断。它的好处就是极致的性能；同样，它的坏处就是你需要自己手动去管理。

Rust 这个语言我用下来，给我的感觉就是每次都要重新学一遍，它的语言体系太复杂了。如果你很喜欢 Rust，我其实建议你去搜一下 Pin、Unpin、Box、Waker 这些概念，对我来说是比较复杂的。当然它最复杂的还是生命周期。就像我前面说的，你可以自己控制内存，但它也不像 C 或 C++ 那样让你自己去调 malloc 或 free，而是通过生命周期的方式来做这样一个设计。我只能说它有点太难了。

那如果到今天你还认为 Rust 是一门很好的语言，会更倾向于拿 Rust 来重写 TypeScript，有没有这种可能呢？我认为是有的。因为 TypeScript 其实和 Bun 比较像：它有非常充足的测试用例，也有非常大的使用量。所以我认为，拿 AI 用 Rust 去重写 TypeScript，应该是一个非常有可能的项目，而且很有可能在短短两周之内就做完。但我考虑的是可读性、可扩展性，以及将来的维护。

我认为 Go 可能是一门最适合人类维护的语言。Rust 是吗？当然也是，但我认为在这种平衡的把握上，它也许更偏向性能一点。如果到这里你还是十分不同意我的说法，当然欢迎你在评论区谈谈你的看法。

但我更建议的做法是：我们可以尝试拿 Rust 去写一个大概 1 万行量级的项目。我相信很多 Rust 的拥趸，真的拿 Rust 写过一万行以上的代码之后，应该就会冷静一些。写完之后也欢迎在评论区聊一聊你的看法：Rust 这门语言是不是该去重写万物，TypeScript 团队的决策是不是一个错误。OK，我们今天的节目就到这里，我们下期节目再见，拜拜。
