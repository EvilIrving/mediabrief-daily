旁白：随着大语言模型能力持续增强，AI 编程智能体正在迅速重塑软件的构建、审查与维护方式。软件开发的瓶颈正从代码生成转向规划、审查、部署与协调。这一转变催生了一类新的智能体系统：它们在受约束的环境中运行，能在很长的时间跨度上进行推理，并与 IDE、版本控制系统和问题跟踪器等工具打通。OpenAI 走在 AI 研究与产品开发的最前沿。2025 年，公司发布了 Codex，这是一个智能体编程系统，被设计为在沙箱环境中安全工作，同时与现代软件开发技术栈的各个环节协作。

Thibault Sottiaux 是 Codex 的工程负责人，Ed Bayes 是 Codex 的产品设计师。在本期节目中，他们与 Kevin Ball 一起探讨 Codex 是如何构建的、模型与 harness（运行框架）的协同演化、多智能体的未来、Codex 的开源 CLI、模型专门化、延迟与性能方面的考量，以及更多话题。

Kevin Ball，又称 KBall，是 Mento 的工程副总裁，也是面向工程师和工程管理者的独立教练。他曾联合创办两家公司并担任 CTO，创办了圣地亚哥 JavaScript 聚会，并通过 Latent Space 组织 AI in Action 讨论小组。可以查看节目说明，在 Twitter 或 LinkedIn 上关注 KBall，或访问他的网站 kball.llc。

Kevin Ball：是啊，我对这期很期待。你们在做一些非常有意思的事情，我很想深入聊聊。不过先从你们自己开始吧。能不能各自介绍一下背景，以及你们是怎么参与到 Codex 中的、在那里做什么？

Ed Bayes：好的。我是 Codex 的产品设计师，加入 OpenAI 差不多一年了。在那之前我做过机器人方面的工作，总体上一直处在设计与研究的交叉地带。我在编程团队大概六个月了。随着每一次模型发布、每一次产品发布，我越来越深入到编程这一块，很高兴来聊聊。Tibo，你呢？

Thibault Sottiaux：我是 Tibo，其实和你差不多同一时间加入。从我记事起，我就一直在折腾、思考智能系统。这是我小时候尝试写的最早的程序之一。随着时间推移，它变得越来越迷人。我感觉如今它真的变成现实了：我终于拥有了七岁时就想做出来的东西——我可以在终端里打字，得到一个智能的回应，就像电脑里住着一个小助手。想到这件事成真了，真的很疯狂。我大约一年半前加入 OpenAI，那时这些都还不可能，我们还没有能在很多很多小时、很长时间里可靠工作的智能体。自从我觉得模型真正具备了这种能力，我就一直在 OpenAI 折腾这件事。去年年底，我有点着迷于这样一个想法：模型能力会持续进化，真正关键的是围绕它搭建合适的基础设施和产品，这样我们才能持续受益，获得相比单纯和模型聊天而言实用性上的阶跃式提升。我当时觉得聊天这种形式已经有点饱和了，而我们能表达的东西其实多得多。它随着时间不断演化，今年早些时候做了大量原型，然后真正组建成了一个团队。现在我们这边已经有相当多的人在推动 Codex，我得说，现在比以往任何时候都更令人兴奋。

Kevin Ball：是的，过去几年我确实在各个方面都感受到了这种加速，在我们这个行业里亲身经历它真的很疯狂。我很想深入聊其中几个方面。你刚才提到的一个区分是：一边是模型、模型的能力及其进步，另一边是围绕它的基础设施、harness 和各种组件。我很好奇，从你们的角度看，你和团队怎么理解这两者之间的关系？它们如何连接、如何相互反馈？

Ed Bayes：好问题。研究和基础设施方面我听 Tibo 的。但我认为过去大约六个月里发生的一个非常有意思的进展，就是模型和 harness 的这种协同演化，而它真正在我们的产品中汇聚到了一起：如果你在我们的 harness 里使用我们的模型，体验和在别处使用是不一样的。作为一个做产品、做设计的人，我觉得这非常令人兴奋——不只是造一个可以通过 API 调用、出现在别处的模型，而是真正让这两者一起协同演化，以及由此可能带来的各种了不起的东西。

Thibault Sottiaux：没错，这种协同演化确实存在，而且发生在很多层面上：harness 和模型在协同演化，需要随之演化的产品也在协同演化，现在这一切都在以非常快的速度进行。我们显然还没有找到最终的形态——你该如何与一个越来越智能、替你做各种事情的系统交互。不过说到 harness，它其实就是你的身体，对吧？你有大脑，也有身体，身体决定了你最终如何作用于周围的世界。此外还有更多一层，那就是你如何行动——但要安全地行动。所以我们开箱即有的一点是：Codex 运行在沙箱里，网络访问受限，文件系统访问受限。这非常重要，因为它让模型可以试验、可以触碰它的环境，却不会造成潜在的负面后果。这是一个重要话题，我们非常多地从对齐和安全的视角来看待编程智能体。于是还有一个问题：harness 在哪里结束，世界又从哪里开始？但我们确实看到，把两者放在一起考虑时，效果会好得多，我认为这一点会一直成立。另外还有一个单独的方面：与这个智能体交互的正确界面是什么？这正是产品真正发挥作用、带来惊喜的地方。我认为随着智能体变得永不被打断、永远运行下去，这方面肯定还需要继续演化，到那时会是完全不同的局面。

Kevin Ball：沙箱这一点也许值得深入聊一会儿。我注意到的一件事是——我会用所有的智能体，至少出于研究目的；有些我每天都用，今天早些时候我还在用 Codex 帮我解决一个问题；有些我只是试一下，然后说"算了，你还没准备好"或者"我不打算用你"——Codex 最突出的一点就是它强沙箱的模式。一开始一切都在沙箱里，这既是好事，有时也让人沮丧，会造成一些别扭的用户体验。所以我很好奇你们如何权衡这一点，以及你们认为这种安全问题会在整个生态中如何演变？

Ed Bayes：这是个非常好的问题。从产品角度、从用户体验角度来看，正如你说的，一些张力正是在这里显现的：你总是被要求批准某些命令。说到底，这些智能体极其强大，所以我们有出色的沙箱和安全特性，这也是产品的核心部分，是你可能选择 Codex 而非其他产品的原因之一。在这些约束之内，我仍然认为可以在用户体验上做一些有意思的事情，让它稍微轻松一点，并把一些控制权交到用户手里。用户可以更改他们的沙箱权限，可以更改模式。如果你在 IDE 扩展里使用我们的产品，基本上可以在两种模式之间选择：一种是智能体模式，它会自行去你的工作目录里做修改；另一种是只读模式，限制更多一些，会在很多地方向你请求权限。我们最近发布的一个功能我觉得挺让人兴奋：随着你一路批准某些命令，我们会给你细粒度的控制，让你清楚自己到底在批准哪些命令，以及它们会如何保存到你的配置里。我们也在探索这在你和你的团队之间应该如何定位。所以说到底，就是把控制权交给用户，同时仍然保持非常高的安全门槛。

Thibault Sottiaux：是的，如果我们退一步看 Codex 的起点：它最初是网页版 Codex，有时也叫 Codex Cloud。我们从一开始的理念就是，这一切都应该在安全的环境中进行，所以它是一个完全隔离的虚拟机，有自己的沙箱，底层用的是 Kata Containers。然后在此基础上，我们决定通过 Codex CLI 和 Codex VS Code 扩展，把它真正带到你的机器上，同时坚守"默认安全"这一原则。在沙箱外运行有多方便都无所谓。说到底，如果你不用沙箱，你就是把控制权交给一个能力很强、非常智能的实体，让它用你自己的凭据对你的机器做任何它想做的事，并承担由此可能带来的一切后果。默认情况下，我们更倾向于安全。当然，确实存在你不想用沙箱的场景，我们会提醒你谨慎，但如果你清楚自己在做什么，我们也支持。

Kevin Ball：嗯，我得说，Codex 从来没有试图删掉我的数据库，而我试过的编程智能体可不都是这样。

Thibault Sottiaux：有时候，智能体可能无意中做了某件事，从而给作为用户的你带来负面后果；也可能是它被人诱导了，显然还有提示词注入等其他风险需要考虑。但说到底，如果你确实把一个相当敏感的东西交给智能体控制，而你既不希望它被删除，也不希望发生任何其他恶意操作，那这是你作为用户值得思考的事情。而我们也确实觉得自己在这方面负有责任，要确保不会出现意料之外的负面后果。

Kevin Ball：你提到运行 Codex 的不同方式，这让我想到另一个很想听你们聊的问题：你们内部是怎么用 Codex 的？你们是全部通过 Codex 网页版或者云端——不管现在叫什么——来运行，还是有人用 IDE？你们是像我一样的 CLI 极客吗？内部是什么情况？

Ed Bayes：这个问题很好。我们这儿有个梗，就是"一切皆 Codex"，对吧？我们有一堆 Codex 模型，有 Codex 网页版，还有 CLI 产品，我们把它们看作是同一个编程智能体出现在不同的地方。但在内部，看它如何随时间演变真的很酷。正如 Tibo 所说，我们今年早些时候首先发布了网页产品，内部对它非常兴奋。它真正酷的一点是：你连接上 GitHub 和团队设置，就可以进去指着一行代码提出需求，它能做到相当惊人的事情。这对比如 UX 文案团队，或者想修改某段定价文字的市场团队来说非常有赋能作用——他们可以自己动手，不必去麻烦某个前端工程师。这是我们最早看到的使用场景之一。然后 CLI 也非常受欢迎，公司里有一大批出色的开发者，开发者常常就生活在命令行里，所以它变得很流行。不过就我个人而言，我经常在 IDE 扩展里用它。我更喜欢图形界面，喜欢能到处点一点，这也就是我惯用的开发环境。最近我们还看到一些很酷的东西：我们上线了 Linear 集成，也上线了 Slack 集成。所以现在你经常会在讨论串里看到这样的情形：大家可能在来回讨论一条客户反馈，或者某个新功能，然后有人直接插进来 @Codex，这就会在后台启动一个任务，它会通过 Slack 或 Linear 流转，然后给你发一个可以点开的卡片，你可以在网页上打开它。看到它出现在讨论串里挺酷的。你也可以在 Linear 里给它分配 issue，这特别好玩。所以我会说，它有点像是那种无处不在的东西。不过我感觉规模化使用相当普遍，有很多不同的使用场景。

Thibault Sottiaux：在技术人员当中是这样，但我们也有很多"环境式智能"，它就在你周围。包括代码审查：OpenAI 写的每一个 PR 都会经过 Codex 审查，它在某种程度上成了一张安全网。考虑到它每天能抓出多少严重缺陷、节省多少时间，很难想象没有这张安全网的世界。它能比我们互相审查代码时投入的时间深入得多，尤其是现在生成代码已经这么便宜了。另一个很酷的地方是，这不只是技术人员的事，公司里越来越多的人在用这个工具做远远不止写代码的事情。

Ed Bayes：是的，过去几个月我在设计团队里看到一个很酷的趋势。我们有几个 Slack 群，就是那种"进行中的工作"群，大家会把作品贴出来。我看到过去几个月里，内容慢慢地——其实也不算慢——从 Figma 里的静态图片，变成了可交互的原型，有时甚至是可以点进去亲自使用的链接，这很酷。我私信过几个贴这些东西的人："我都不知道你会写代码。"他们说："我之前不会，直到我试了 Codex。"所以这里有一个范围：它既适用于对代码审查标准要求很高的专业软件开发者，也适用于设计师可以随便玩的一次性原型，这样你就能测试响应式布局，以及各种在静态原型里没法测的边界情况。它基本上把学科之间的边界打通了——在过去五十年左右，或者说近期的技术史上，由于这些学科的划分，甚至在组织内部也常常有一些多少有些人为的边界：这些员工可以接触这项技术，那些不行。我认为它是一个很好的均衡器。

Kevin Ball：那我们也许值得把这个过程梳理一遍。你提到了软件开发生命周期里的几个不同环节，Codex 正在那些地方发挥作用、加快进度、简化流程或者打通边界。你们有没有系统地思考过整个生命周期？放眼我们这个行业，大家都在试图弄清楚如何适应。我认为开发软件的过程在过去一年半里的变化，可能比我此前二十年职业生涯里的变化还要大，这真的很疯狂。那么你们在所有这些环节上，是如何借助 Codex 去适应的？

Thibault Sottiaux：这也许又回到了协同演化。你可以做大量第一性原理式的思考，试图弄清楚应该如何组织团队和工作，才能在这个过程中最大程度地受益；或者你也可以保持高度灵活，每天都在学习，让你作为团队、作为个人、作为组织的工作方式与编程智能体一起协同演化。我们确实看到了很多这样的情况，比如充满干劲和雄心的小团队能取得多得多的成果，效率极高，因为他们能更快地迭代和学习。我们在 Sora 上看到了这一点，最近在 Atlas 上也看到了：代码库的整块部分仅凭一个想法就被搭了起来，背后只是少数几个人在真正驾驭一整串 Codex 智能体。但同时也很明显，瓶颈在不断转移。代码生成现在几乎可以说已经解决了，瓶颈正在转向代码审查、转向部署，也转向规划，以及把大量想法和用户反馈结合起来。我们在 Codex 团队思考如何解决这些瓶颈，我们绝对不只专注于代码生成。这也是为什么我们很早就开始投入代码审查，因为我们判断出它会成为瓶颈。所以这个故事、这幅图景里有很多内容：有些瓶颈我们提前预见到了，有些则是"我们真没想到这个，现在它要撑不住了，因为其他一切都变得太高效了"。

Ed Bayes：是的，自从加入 OpenAI 以来，真正让我惊讶的是，构建这些触达数十亿人的产品的团队竟然这么小。我记得和一位设计师聊过，他当时在 Deep Research——我想是这个产品——团队规模是一个产品经理、一个设计师、几个工程师、几个研究员，默认就刻意保持精简。我认为我们内部之所以能做到这一点，是因为我们作为同事也在与模型协同演化：我们在构建这些模型，能立刻用上它们，并真正把它们融入大家的工作流。看着这一切很酷。另外，我们构建产品的方式是为专业软件开发者而构建，这意味着要考虑产品开发的整个生命周期。正如 Tibo 所说，这不只是写代码，还有规划过程，也就是开头的环节——所以要用 Linear 或 Slack 这类工具，在人们工作、交流和规划工作的地方与他们相遇，把智能体集成进去；在代码审查环节也是如此，Tibo 已经讲过了。所以我觉得未来一个值得关注的方向是：思考软件开发周期的完整生命周期是什么样的，以及在代码生成之外还能在哪些地方提供支持。

Thibault Sottiaux：其中有些部分更容易攻克。回到我们之前关于安全和沙箱的讨论：代码生成显然属于容易的那部分，它比较容易在沙箱里完成。但如果你考虑接下来围绕部署、以及为一个服务值班会发生什么，你就进入了一个全新的领域。如果我们希望由智能来驱动这些，如果我们希望由智能体来驱动这些，它们就得以一种本身就带有大量风险的方式行动。你该怎么做？怎么实现？我认为如何安全地做到这一点，仍然在很大程度上是一个开放问题。

Kevin Ball：这又引出了我的另一个问题。我们在谈把它应用到各种各样的事情上，而我在工作中和各种工具打交道时确实观察到，不同的模型似乎擅长不同的事情。GPT-5 出来的时候——我们大量使用 Go——它在 Go 上的表现非常出色，毫无疑问，完胜我们当时用的其他所有模型。但它有时在 HTML 和 CSS 上没那么好，所以那部分工作我们有时仍然会去用其他模型，甚至可能是非 OpenAI 的模型。你们怎么看这种多模型的问题？你们是在追求一个什么都能做的模型、让大家都来用它，还是在设想一个多模型的未来？你们认为这个生态会如何发展？

Thibault Sottiaux：我们当然是在追求一种圣杯：一个在所有方面都出奇地好的模型，这样你就不必再去纠结该选哪个模型。但实际上，我们认为它会演变成更像一个多智能体的世界：你不一定得亲自去决定"为了完成这项工作，底层的正确配置是什么——具体用哪个模型、哪种配置、哪些工具"，也许你在这方面也会得到帮助。我们也意识到，正如人类需要协作才能在世界上做成有用的事，智能体或许也一样，需要彼此协作，发挥各自的特定长处。这里面有一系列问题，比如：作为一个模型，你如何表明自己的长处？这是模型本身就知道的吗？是模型内在的、它所拥有的知识吗？还是需要由你这个人类、或者由其他模型去发现，才能理解"这其实是这种配置相比另一种配置的长处"——后者也许以更低的成本取得相近的结果，或者前者能取得更好的结果但延迟更高。所以存在各种权衡。我认为这会是一个智能体之间协作的美好世界，但希望对作为用户的你来说也会简单得多。
