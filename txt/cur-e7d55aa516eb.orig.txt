# 세 번 그리던 화면을 한 번에: CLAYDesign이 디자인시스템으로 화면을 생성하는 방법

김상국, 류현승

화면 하나가 서비스에 나가기까지는 기획자, 디자이너, 개발자가 같은 화면을 각자 한 번씩, 모두 세 번 그립니다.

![기획자, 디자이너, 개발자가 같은 화면을 차례로 세 번 그리는 흐름](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-three-roles.png)

개발 중에 기획이 바뀌면 와이어프레임, 시안, 코드를 모두 다시 수정해야 합니다. 단계마다 앞 단계의 결정 사항을 보고 담당자가 다시 그리므로, 완성된 화면이 처음 기획과 어긋나기도 합니다. 소통 중에 의도가 다르게 전달되거나, 개발 과정에서 구현이 달라지기 때문입니다.

디자인시스템팀은 범용 AI 디자인 도구(Claude Design, Figma Make 등)로 이 과정을 줄여 보려 했지만, 도구가 그린 화면은 그럴듯해 보여도 배달의민족(이하 배민)의 디자인시스템에 없는 컴포넌트를 쓰고 색과 간격을 지어냈습니다. 겉보기에는 배민 화면 같지만, 자세히 보면 배민의 디자인을 따르지 않았습니다. 그래서 어디가 디자인시스템에서 벗어났는지 하나하나 찾아야 했고, 결국 디자인시스템에 맞춰 화면을 한 번 더 그려야 했습니다.

---

## 디자인시스템이 있기에 직접 만들 수 있었습니다

배민의 디자인시스템인 클레이 민트에는 AI에게 알려 줄 구성 요소가 이미 갖춰져 있었습니다. 컴포넌트마다 쓸 수 있는 값이 정해져 있고, 색과 간격은 디자인 토큰으로 정의되어 있습니다. 컴포넌트와 디자인 토큰은 Figma와 웹, iOS, Android에서 같은 이름과 구조를 따르도록 협의해 두었고, 언제 무엇을 쓰는지 정한 가이드와 원칙도 있습니다.

하지만 이 정보를 범용 도구에 프롬프트로 넣어 주는 것만으로는 충분하지 않았습니다. 실제 배민 화면의 구성을 참고해 그리게 하고, 디자인시스템에 맞는지 검사해 틀린 값을 고치고, 그린 결과를 Figma 레이어와 플랫폼별 코드로 바로 내보내는 과정까지 하나로 이어져야 다시 그리는 일을 없앨 수 있기 때문입니다. 그래서 디자인시스템팀은 이 전 과정을 다루는 사내 도구로 CLAYDesign을 직접 만들었습니다.

CLAYDesign은 사용자에게 한 줄 프롬프트를 받아 배민 디자인시스템의 컴포넌트로 화면 시안을 그립니다. 그린 시안은 Figma와 React, SwiftUI, Compose 코드, 그리고 사내 테스트용 배민 앱인 베타앱으로 바로 확인할 수 있습니다. 전사에서 정식으로 운영을 시작한 첫 주에는 300명이 넘는 사용자가 화면 1,000개 이상을 만들었습니다.

![](https://techblog.woowahan.com/wp-content/uploads/2026/11/%EC%8A%A4%ED%81%AC%EB%A6%B0%EC%83%B7-2026-11-19-%EC%98%A4%ED%9B%84-4.40.51-750x418.png)

이 글은 사용자가 CLAYDesign에 프롬프트 한 줄을 넣었을 때 어떤 과정을 거쳐 화면을 만들고 내보내는지, 입력부터 출력까지 여섯 단계를 차례로 따라갑니다.

## 용어와 구성 요소 설명

CLAYDesign이 동작하는 방식을 이해하는 데 도움이 되는 용어를 먼저 정리합니다.

| 용어 | 뜻 |
| --- | --- |
| 화면 JSON 문서 | 화면 하나를 요소 목록으로 표현한 JSON 문서입니다. AI는 코드 대신 이 문서를 작성합니다. |
| 카탈로그 | AI가 쓸 수 있는 컴포넌트, 속성, 디자인 토큰, 아이콘의 목록입니다. 디자인시스템 코드 기반으로 자동으로 만듭니다. |
| 템플릿 | 디자이너가 Figma에 그린 배민 화면을 등록한 것입니다. 고르면 Figma 시안을 화면 JSON 문서로 바꿔 시작점으로 씁니다. |
| 디자인 레퍼런스 | 배민 화면 한 장을 영역별로 설명한 문서입니다. 템플릿에 없는 영역을 그릴 때 찾아 씁니다. |
| 유효성 검사 도구 | 저장하기 전에 화면 JSON 문서를 카탈로그와 대조하는 코드입니다. 틀리면 저장하지 않습니다. |

CLAYDesign은 사용자 PC의 데스크톱 앱과 AWS 위의 사내 서버, 사내 GitLab의 저장소 두 개로 이루어집니다. AI 호출은 모두 사내 서버가 맡아서, 사용자는 AI 도구나 모델 계정 없이 사내 계정으로 로그인만 하면 됩니다.

![CLAYDesign의 구성 요소](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-architecture-overview.png)

*CLAYDesign의 구성 요소와 기본 연결. 아래 단계마다 같은 그림에서 해당 단계에서 쓰이는 부분만 진하게 표시합니다.*

CLAYDesign은 여섯 단계로 화면을 만듭니다. 질문으로 프롬프트를 채우고, 템플릿을 고르고, AI에게 디자인시스템을 알려 줍니다. AI가 화면 JSON 문서를 쓰면 CLAYDesign이 결과를 검사하고 여러 환경으로 내보냅니다.

![한 줄 프롬프트가 화면이 되기까지 거치는 여섯 단계](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-flow-six-steps.png)

## 1단계: 짧은 프롬프트는 질문으로 채웁니다

프롬프트를 작성하는 방식은 사용자마다 달라서, 짧은 화면 생성 요청 프롬프트도 자주 들어옵니다. 빠진 내용을 그대로 AI에게 맡기면 AI가 매번 다르게 정의해서 결과가 들쑥날쑥해집니다. 그래서 사용자에게 프롬프트를 길게 다듬게 하는 대신, 화면을 그리기 전에 질문 폼으로 빠진 내용을 묻기로 했습니다.

![시연 프롬프트에 뜬 질문 폼](https://techblog.woowahan.com/wp-content/uploads/2026/11/96ee4e96-e766-410b-8a82-0138bafa5663-750x741.png)

*AI가 사용자의 프롬프트를 보고 선별한 질문과 선택지만 보입니다.*

![1단계에서 쓰는 구성 요소](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-architecture-stage1.png)

표준 질의서는 화면을 그리는 데 필요한 질문을 미리 정의해 둔 파일입니다. 질문마다 문구와 묻는 조건, 답하지 않았을 때 쓸 기본값이 있습니다. 질문은 생성 목적, 서비스, 대상 지면, 변경 범위, 화면 형태(풀 페이지, 바텀시트, 모달), 주요 행동, 필수 정보의 일곱 가지입니다. 서비스처럼 답이 정해진 항목에는 고정 선택지도 있습니다.

```
# 표준 질의서의 한 항목을 간단하게 바꾼 예시입니다
- id: service
  label: 서비스
  question: 어떤 서비스인가요?
  kind: choice
  when: 프롬프트에서 관련 사항이 안 보일 때
  options: [음식배달, 픽업, 한그릇, 브랜드관, 장보기쇼핑, 배민클럽, ...]
```

### 질문 판정

앱은 사용자 프롬프트 뒤에 표준 질의서의 항목을 한 줄씩 덧붙여 사내 서버로 보냅니다. 줄마다 항목 id와 질문, 묻는 조건이 있고 끝에 빈칸이 있습니다.

```
purpose (이번 화면으로 어떤 걸 해결하고 싶어요? - 묻는 조건: 프롬프트에서 관련 사항이 안 보일 때) :
service (어떤 서비스인가요? - 묻는 조건: 프롬프트에서 관련 사항이 안 보일 때 / 선택지 고정: 음식배달 · 픽업 · …) :
```

*앱이 프롬프트 뒤에 덧붙이는 질문 줄의 예입니다. 실제로는 일곱 항목이 모두 붙습니다.*

모델은 이 질문 줄마다 끝의 빈칸에 아래 세 판정 가운데 하나를 채워 돌려줍니다.

- `known`: 프롬프트나 서비스 도메인에서 이미 답을 알 수 있어서 묻지 않습니다.
- `ask - 후보1 / 후보2`: 사용자가 고르지 않으면 결과가 달라지므로 묻습니다. 사용자에게 보여 줄 선택지 후보를 함께 작성합니다.
- `skip`: 묻는 조건에 맞지 않아서 묻지 않습니다.

![앱이 질문 줄을 덧붙여 보낸 프롬프트에 모델이 판정을 채우고, 앱이 ask 항목만 질문 폼으로 띄우는 흐름](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-question-judgment.png)

질문 문구와 표시 순서는 앱이 표준 질의서에서 채웁니다. 고정 선택지가 있는 항목은 AI가 프롬프트에 맞지 않는 선택지를 걸러 내기만 하고, 고정 목록이 없는 항목만 AI가 후보를 만듭니다.

앱이 문구를 직접 채우는 까닭은 질문 폼은 사용자가 프롬프트를 보낸 바로 뒤에 떠야 하기 때문입니다. 늦게 뜨면 사용자가 질문을 놓칠 수 있기 때문입니다.

처음에는 모델이 질문 문장까지 새로 만들어서, 질문 폼이 뜨기까지 실측 6.8초가 더 걸렸습니다. 지금은 표준 질의서에 정의한 질문 문장을 앱이 그대로 쓰고, 모델은 질문 줄 끝의 빈칸에 판정만 채웁니다. 질문이 미리 정의되어 있고 빈칸만 채우면 되니, 답 형식을 따로 설명할 필요도 없어졌습니다. 그래서 같은 사용자 프롬프트에서 모델에게 보내는 질문 판정 프롬프트가 6,288자에서 1,556자로 줄었습니다. 프롬프트를 줄인 뒤에도 실측에서 나온 질문은 이전과 같았습니다.

사용자가 고른 답은 프롬프트 바로 뒤에 이미 확인된 요구사항 목록으로 붙습니다. 답하지 않은 항목에는 기본값으로 채우라는 표시와 표준 질의서의 기본값이 함께 붙습니다. 질의응답으로 프롬프트를 채우면, 누가 작성하든 같은 기준으로 화면이 그려집니다.

## 2단계: 빈 화면 대신 배민 화면에서 시작합니다

프롬프트를 채웠으니 이제 어떤 화면에서 그리기 시작할지 정할 차례입니다. 질문으로 프롬프트를 채워도, 빈 화면에서 그린 결과는 배민답지 않았습니다. AI가 컴포넌트와 디자인 토큰을 알아도, 그것을 어떻게 조합해야 배민다운 화면이 되는지는 모르기 때문에, 빈 화면에서 시작하면 AI는 간격과 스타일을 지어냈고, 결과는 그럴듯해도 배민 화면처럼 보이지 않았습니다.

그래서 CLAYDesign은 템플릿에서 시작합니다. 템플릿은 디자이너가 디자인시스템으로 Figma에 그려 둔 실제 배민 화면을 등록한 것입니다. 이런 화면에는 컴포넌트를 어떻게 조합하고 간격과 강조를 어떻게 두는지가 이미 배민의 기준대로 담겨 있습니다. AI는 템플릿의 조합을 그대로 두고 필요한 영역만 고치므로, 결과도 배민다운 화면이 됩니다.

![2단계에서 쓰는 구성 요소](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-architecture-stage2.png)

### 템플릿

템플릿마다 Figma 프레임의 위치(파일과 노드 id)와 id, 이름, 별칭, 설명, 지면 갈래(푸드, 커머스 등), 레이아웃 유형(카드를 쌓는 화면, 바텀시트 등), 목록에 보일 썸네일을 데이터베이스에 저장합니다. 화면 구성 자체는 저장하지 않는데, 화면의 원본을 Figma 한 곳에만 두어(단일 원본, SSOT), 디자이너가 Figma에서 고친 내용이 템플릿에 그대로 반영되게 하기 위해서입니다. 템플릿이 선택되면 그때 Figma에서 프레임을 받아 화면 JSON 문서로 바꿉니다.

템플릿 고르기는 1단계의 질문 판정과 동시에 실행합니다. 앱은 프롬프트와 등록된 템플릿 목록을 함께 보내 AI에게 하나를 고르게 합니다. 목록에는 각 템플릿에 든 정보인 id, 이름, 별칭, 설명, 지면 갈래를 싣습니다. 마카롱 공방 프롬프트라면 AI는 푸드 장바구니 템플릿을 고르고, 고른 템플릿과 판정을 짧은 JSON으로 돌려줍니다.

```
{ "id": "food-cart", "match": "same", "title": "마카롱 공방 장바구니" }
```

*설명을 위한 예시입니다. 실제 템플릿 id와는 다릅니다.*

판정은 `same`과 `similar` 타입 두 가지입니다. 첫 번째 `same`은 프롬프트가 말한 화면과 같은 화면이 목록에 있을 때입니다. 이때 AI는 상단바, 서비스 탭, 결제 금액 같은 화면 틀은 그대로 두고, 콘텐츠 영역만 템플릿의 예시를 따라 다시 그립니다. 두 번째 `similar`는 같은 화면이 없을 때입니다. 이때 AI는 영역 구성이 가장 가까운 화면을 골라 색과 여백, 컴포넌트를 고르는 방식을 따라 화면 전체를 고칩니다.

![same은 콘텐츠 영역만 다시 그리고, similar는 가까운 화면을 따라 화면 전체를 고치는 비교](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-template-same-similar.png)

### 디자인 레퍼런스

템플릿이 모든 영역을 갖추지는 못합니다. 예를 들어 마카롱 공방 프롬프트에 쿠폰 배너와 리뷰 요약도 넣어 달라고 하면, 장바구니 템플릿에는 없는 영역이 생깁니다. 이런 영역은 디자인 레퍼런스에서 가져와 그립니다. 디자인 레퍼런스는 배민 화면 한 장을 영역으로 나눠, 영역마다 무엇을 어떤 값으로 그렸는지 설명한 문서입니다.

![템플릿에 없는 영역마다 디자인 레퍼런스를 찾는 흐름](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-reference-per-area-1.png)

*쿠폰 배너는 장보기쇼핑 화면에서, 리뷰 요약은 음식배달 화면에서 레퍼런스를 찾아와 장바구니에 그립니다.*

AI가 영역마다 디자인 레퍼런스를 찾으려면, 레퍼런스가 영역 단위로 검색되어야 합니다. 그러면서도 원본 값을 잃지 않도록 레퍼런스 하나를 파일 세 개로 나눠 지식베이스에 저장합니다.

| 파일 | 담는 것 | 쓰이는 때 |
| --- | --- | --- |
| `.md.metadata.json` | 제목, 요약, 키워드, `design-reference` 태그 | 검색할 때 필터로 씁니다. |
| `.md` | 영역별 설명과 영역별 골격 | 검색되고, 그릴 때 프롬프트에 실립니다. |
| `.spec.json` | 화면 JSON 문서 원본 | 색인에서 빼 두고, 정확한 값이 필요할 때만 주소로 엽니다. |

> **메타데이터 파일**: 검색 색인(Amazon Bedrock Knowledge Bases)이 원문과 함께 읽는 속성 파일입니다. 원문 파일 이름 뒤에 `.metadata.json`을 붙여 같은 위치에 두면, 검색할 때 이 속성으로 문서를 거를 수 있습니다. [AWS 문서](https://docs.aws.amazon.com/bedrock/latest/userguide/s3-data-source-connector.html#ds-s3-metadata-fields)

`.md`의 앞부분은 영역마다 무엇을 담고 어떤 값으로 그렸는지 작성한 설명입니다. 뒷부분의 영역별 골격은 서버가 화면 JSON 문서를 정적으로 분석해, 영역마다 어떤 컴포넌트를 어떤 토큰으로 어떻게 쌓았는지 작성합니다. 메뉴 목록처럼 같은 모양이 반복되는 항목은 첫 항목만 작성하고, 몇 번 반복되는지 `×3`처럼 표시합니다. AI는 이 골격을 보고 레퍼런스 영역의 구조와 토큰 값을 그대로 따라 그립니다. 예전에는 값이 몇 번 쓰였는지만 문장으로 요약했는데, 요약만으로는 AI가 디자인 레퍼런스의 값의 사용 패턴과 디자인 규격을 참조하지 못했습니다. 쿠폰 배너가 든 스토어홈 레퍼런스의 골격 일부는 이렇습니다.

```
## 영역 top-area · 「{테마관} 전용 쿠폰 챙겨가세요!」
- 컴포넌트: ListHeader, Typography
- 토큰: gap 100×2/125×2; paddingTop 200×2; ...; borderRadius ref.radius.large; textStyle descriptionMediumEmphasized
Flex top-area flexDirection=column
  Flex gap=100 style={paddingTop=200 paddingRight=200 paddingBottom=200 paddingLeft=200 backgroundColor=sem.color.surfaceContainer}
    div img ×3
  Flex flexDirection=column gap=100 style={paddingTop=200 paddingBottom=200 backgroundColor=sem.color.surfaceContainer}
    ListHeader list-header color=onWhiteBG
    ...
```

이렇게 나눠 둔 디자인 레퍼런스는 화면을 그릴 때 영역마다 찾아 씁니다. AI가 화면을 그리기 전에 사내 서버가 프롬프트로 한 번 먼저 검색해 결과를 후속 프롬프트 덧붙여, 그리는 동안 AI가 영역마다 다시 검색하도록 했습니다. 처음 구현 시점에는 사용자 프롬프트 하나로 디자인 레퍼런스를 검색하게 했으나, 화면 전체를 가리키는 질의라서 배너나 목록처럼 영역 하나를 그리는 데 필요한 문서는 검색 결과에 잘 들어가지 않았습니다. 지금은 화면을 그리기 전에 화면을 이루는 영역부터 AI에게 작성하게 합니다. 그다음 영역마다 영역 이름으로 디자인 레퍼런스를 다시 찾게 하고, 여러 영역은 한 번에 함께 검색하게 합니다.

```
1. 프롬프트를 읽고 이 화면이 어떤 영역으로 이루어지는지 먼저 작성한다.
   상단바, 검색줄, 배너, 카테고리 줄, 목록, 하단바처럼 나눈다.
2. 영역마다 그 영역을 어떻게 그리는지 찾는다.
   질의는 그 영역의 이름으로 한다.
3. 여러 영역은 한 번에 함께 검색한다.
4. 규격은 찾았는데 간격, 색, 글자 값이 요약에서 잘려 보이면 원문을 연다.
5. 영역별 근거를 다 모은 뒤에 화면 JSON 문서를 생성한다.
```

*사내 서버의 화면 생성 시스템 프롬프트에서 차례 부분을 간단하게 바꾼 예시입니다.*

![디자인 레퍼런스를 찾는 도구 호출의 흐름](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-seq-reference.png)

*사내 서버가 먼저 한 번 검색하고, 모델이 그리는 동안 도구로 영역마다 다시 찾습니다.*

디자인 레퍼런스 검색에는 지식을 검색하는 도구와, 검색 결과가 알려 준 주소의 원문을 읽는 도구를 씁니다. AI는 화면을 그리는 동안 이 두 도구를 직접 호출하고, 이미 있는 화면을 고칠 때도 고칠 영역 하나를 가리키는 질의로 근거부터 찾습니다.

검색할 때는 앞에서 본 디자인 레퍼런스 파일 세 개가 각자 쓰입니다. 첫 검색은 문서 종류로만 거르고, 이어서 메타데이터 파일의 `design-reference` 태그로 거른 문서 안에서 한 번 더 찾습니다. 디자인 레퍼런스가 다른 문서보다 검색 결과 순위가 낮아져 누락되지 않게 하려는 것입니다. 두 결과를 합쳐 레퍼런스를 몇 건 고르고, 검색 조각 대신 `.md` 파일 전체를 프롬프트에 싣습니다. `.md` 아래에는 `.spec.json`의 원문 주소를 한 줄 추가해 두어, AI가 `.md`에 없는 정확한 값이 필요할 때 원본을 열게 합니다.

![두 번 검색한 결과를 합쳐 .md 전체와 .spec.json 주소를 메시지에 싣는 흐름](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-reference-search-1.png)

## 3단계: 디자인시스템을 시스템 프롬프트에 넣습니다

2단계의 템플릿과 디자인 레퍼런스가 화면의 구성을 알려 준다면, 구성을 이루는 컴포넌트와 값은 디자인시스템이 알려 줍니다. 모델을 추가로 학습시키는 방법도 있지만, 디자인시스템은 계속 업데이트되어서 바뀔 때마다 다시 학습시키기 어렵습니다. 그래서 화면을 생성할 때마다 디자인시스템 정보를 시스템 프롬프트에 함께 넣습니다.

![3단계에서 쓰는 구성 요소](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-architecture-stage3-1.png)

시스템 프롬프트에 함께 보내는 디자인시스템 정보는 다음과 같습니다.

- 카탈로그: 쓸 수 있는 컴포넌트와 속성, 디자인 토큰, 아이콘의 목록입니다.
- 컴포넌트 선택 가이드: 비슷한 컴포넌트 가운데 무엇을 고를지 정한 기준입니다.
- 디자인 원칙: 어떤 화면에나 적용되는 배치와 강조 규칙입니다.

### 카탈로그

세 가지 가운데 카탈로그는 사람이 직접 관리하지 않습니다. 생성 스크립트가 TypeScript 컴파일러 API로 디자인시스템 패키지의 타입 선언 파일(`.d.ts`)을 읽어 만듭니다. 읽는 대상은 컴포넌트와 디자인 토큰, 아이콘을 정의한 패키지입니다. 타입 선언에서 `'black' | 'mint'`처럼 값을 나열한 부분은 고를 수 있는 값 목록이 됩니다. JSDoc 주석의 첫 줄은 AI가 읽는 컴포넌트와 속성의 설명이 됩니다.

> **JSDoc**: 코드 바로 위에 `/** */` 형식으로 설명을 작성하는 JavaScript와 TypeScript의 주석 형식입니다.

```
// 디자인시스템 코드에 원래 있던 타입 선언입니다(설명을 위해 줄였습니다)
type FilledButtonProps = {
  /** 버튼 색상 */
  color: 'black' | 'mint' | 'gray' | 'white'
  /** 버튼 크기 */
  size: 'small' | 'large'
}
```

```
// 생성된 카탈로그의 FilledButton 항목입니다(color만 남겼습니다)
'FilledButton': {
  "props": {
    "color": { "description": "버튼 색상", "kind": "enum", "values": ["black", "gray", "mint", "white"], "required": true },
    ...
```

AI는 카탈로그에 있는 이름과 값으로만, 아래와 같이 화면 JSON 문서를 작성합니다.

```
"coupon-button": {
  "type": "FilledButton",
  "props": { "color": "mint", "label": "쿠폰 받기" }
}
```

카탈로그는 한 곳에서 만들고 여러 곳에서 함께 읽습니다. 시스템 프롬프트와 저장 전 유효성 검사 도구, 사용자가 속성을 직접 고치는 인스펙터가 모두 같은 생성 파일을 참조합니다. 덕분에 세 곳이 허용하는 값과 선택지가 서로 어긋나지 않습니다.

디자인시스템 버전을 올리면 생성 명령을 다시 실행해 카탈로그를 새로 만듭니다. 누가 생성 파일을 직접 고치면 다시 만든 결과와 달라져 테스트가 실패합니다. 사내 서버도 같은 카탈로그로 검사하는데, 앱 저장소의 CI가 main에 합칠 때마다 생성 파일을 서버 저장소로 복사합니다.

카탈로그에는 컴포넌트뿐 아니라 디자인 토큰도 들어 있어서, AI는 색과 간격도 컴포넌트처럼 디자인 토큰 이름으로 씁니다. 쿠폰 배너를 화면 JSON 문서로 작성하면 이렇습니다.

```
"coupon-banner": {
  "type": "Flex",
  "props": {
    "gap": "100",
    "style": {
      "padding": "200",
      "borderRadius": "ref.radius.xLarge",
      "backgroundColor": "sem.color.surfaceContainer"
    }
  }
},
"coupon-title": {
  "type": "Typography",
  "props": { "content": "디저트 3,000원 할인", "textStyle": "titleSmall", "color": "foregroundPrimary" }
}
```

카탈로그는 컴포넌트 속성을 토큰 이름의 열거형으로 정의하므로, 픽셀이나 색 코드를 쓰면 유효성 검사에서 걸립니다. 토큰으로 그리면 테마도 따라옵니다. 배경색을 `surfaceContainer`라는 이름으로 작성했으므로, 같은 문서가 라이트 테마와 다크 테마에서 각 테마의 색으로 그려집니다. Figma나 코드로 내보내도 같은 토큰 이름이 남으므로, 디자이너와 개발자가 값을 다시 맞추지 않아도 됩니다.

> 레이아웃 컴포넌트의 `style`은 예외입니다. 처음에는 `style`도 토큰만 받았는데, 그러자 회색 바탕 위에 흰 카드를 얹는 흔한 구성을 만들 방법이 없었습니다. 토큰에 없는 값이 필요해진 모델은 값을 지어내거나 가장 가까운 토큰을 잘못 골랐습니다. 지금 `style`은 토큰을 먼저 쓰게 하되, 토큰에 없는 값은 `16px` 같은 CSS 값으로도 작성할 수 있게 열어 두었습니다.

### 컴포넌트 선택 가이드와 디자인 원칙

카탈로그에 있는 컴포넌트와 값만 써도 어색한 화면이 나옵니다. 버튼 세 개를 모두 강조하면 무엇을 눌러야 할지 알 수 없습니다. 카탈로그는 무엇을 쓸 수 있는지만 알려 주기 때문입니다. 컴포넌트 선택 가이드는 고르는 기준을 알려 줍니다. 가장 중요한 행동 하나만 강조하고, 여러 개를 고르면 Checkbox, 하나만 고르면 Radio, 바로 켜고 끄면 Switch를 쓰는 식입니다. 가이드는 앱 저장소의 설정 파일에 컴포넌트별로 작성해 둡니다.

![버튼 세 개를 모두 강조한 화면과 가장 중요한 행동 하나만 강조한 화면](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-button-emphasis.png)

카드 박스 안에 카드 박스를 또 넣지 않는 것처럼 화면 전체에 적용되는 규칙은 디자인 원칙으로 알려 줍니다. 디자인 원칙은 지식베이스의 문서 하나에 모여 있습니다. 화면의 뼈대를 세우는 순서, 배경과 콘텐츠를 구성하는 방식, 선과 글자와 색의 세부 규칙, 강조하는 방법, 쓰지 말아야 할 것을 담고 있습니다. 이러한 원칙은 디자이너가 직접 고치며 관리합니다. 사내 서버는 원칙 문서를 검색에 맡기지 않고 지식베이스에서 직접 읽어, 모든 생성 호출에 함께 싣습니다. 원칙은 어떤 화면에나 걸리는 규칙이라서, 검색에 맡기면 사용자의 프롬프트에 따라 빠지기 때문입니다.

### 프롬프트 캐시

카탈로그와 컴포넌트 선택 가이드, 디자인 원칙을 생성할 때마다 넣으니 시스템 프롬프트가 길어집니다. 프롬프트가 길면 호출할 때마다 같은 내용을 다시 처리하느라 응답이 늦어지고 비용도 늘어납니다. 매번 같은 앞부분은 프롬프트 캐시에 담아 다시 쓰면 이 부담을 줄일 수 있습니다. 사내 서버는 이 시스템 프롬프트를 아래 순서로 조립합니다.

![사내 서버에서 새 화면을 만들 때 모델이 받는 것](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-prompt-structure.png)

*시스템 프롬프트에는 디자인시스템 정보가, 사용자 메시지에는 프롬프트와 답, 참조 문서, 첫 검색 결과가 실립니다.*

카탈로그와 컴포넌트 선택 가이드는 디자인시스템 버전이 바뀔 때만 달라지고, 그중 카탈로그가 가장 큽니다. 베타 기간의 로그를 분석해 보니 화면 생성 호출의 42%가 직전 호출 뒤 5분 안에 왔습니다. 5분은 Bedrock 프롬프트 캐시가 유지되는 시간입니다. 그래서 바뀌지 않는 앞부분을 한 블록으로 묶고, 블록 끝에 캐시 기준점을 둡니다.

캐시가 유지되는 동안 다음 호출은 약 3만 8천 토큰을 다시 처리하지 않고 캐시에서 읽습니다. 베타 기간 중 하루(24시간)를 기준으로 측정해 보니, 사내 서버가 AI에게 보낸 입력 토큰의 21%를 캐시에서 읽어 약 380만 토큰을 절약했습니다. 사용자가 많을수록 5분 안에 이어지는 호출도 많아지므로, 사용자가 늘어난 정식 운영에서는 절약하는 양이 더 커집니다.

## 4단계: AI는 코드 대신 화면 JSON 문서를 씁니다

프롬프트와 템플릿, 디자인시스템 맥락이 모였으니 이제 AI가 화면을 그릴 차례입니다. AI는 화면을 그리는 동안 템플릿에 없는 영역의 디자인 레퍼런스를 찾고, 찾은 내용을 바탕으로 화면을 코드 대신 JSON 문서로 작성합니다.

![4단계에서 쓰는 구성 요소](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-architecture-stage4.png)

화면을 그린다고 하면 먼저 React 같은 특정 플랫폼의 코드를 떠올리기 쉽지만, AI가 React 코드를 쓰면 바로 그려지는 곳은 웹뿐입니다. 같은 화면을 iOS와 Android, Figma로 옮기려면 플랫폼마다 코드를 다시 만들어야 합니다. 또, 네이티브 코드는 화면을 보려면 매번 빌드해야 합니다. 그래서 CLAYDesign의 AI는 코드 대신 화면을 JSON 문서로 씁니다. 화면 JSON 문서는 어디서든 읽을 수 있는 데이터입니다. 문서 하나로 여러 플랫폼의 화면을 만들 수 있고, 저장하기 전에 정해진 규칙으로 검사할 수도 있습니다.

### 화면 JSON 문서의 형식

화면 JSON 문서의 형식은 Vercel이 공개한 [json-render](https://json-render.dev)의 `Spec`을 가져왔습니다. 요소 안에 요소를 겹겹이 넣지 않고, `elements`에 요소를 하나씩 나란히 작성한 뒤 부모와 자식을 키 이름으로 잇습니다.

```
{
  "root": "screen",
  "elements": {
    "screen": { "type": "Flex", "children": ["banner"] },
    "banner": { "type": "Flex", "children": ["text", "button"] },
    "text":   { "type": "Flex", "children": ["title", "desc"] },
    "title":  { "type": "Typography", "props": { … } },
    "desc":   { "type": "Typography", "props": { … } },
    "button": { "type": "FilledButton", "props": { … } }
  }
}
```

이 형식을 선택한 이유는 다음과 같습니다.

- AI가 쓰기 쉽습니다. 괄호를 깊이 맞출 필요가 없어서 화면이 길어져도 실수가 적습니다.
- 생성하는 동안에도 그릴 수 있습니다. 요소가 하나씩 완성되므로, 문서가 다 오기 전에도 이미 도착한 요소만으로 화면을 그릴 수 있습니다.
- 경로 한 줄로 요소를 가리킬 수 있습니다. `/spec/elements/button/props/color`처럼 작성하면 어느 요소든 바로 찾아가므로, 바뀐 부분만 골라 고치기 쉽습니다.

저장할 때는 이 `spec`을 감싸 문서 형식 버전과 화면 제목, 디자인시스템 버전을 함께 작성합니다. 모델은 제목과 `spec`만 쓰고 나머지는 앱이 채웁니다. 화면은 여러 장을 한 묶음으로 저장하고, 화면 사이의 흐름도 묶음에 함께 둡니다.

json-render에서 가져온 것은 문서 형식과 타입까지입니다. CLAYDesign은 정적인 시안을 만들기 때문에, 상호작용을 위한 필드는 쓰지 않습니다. 유효성 검사 도구와 렌더러는 직접 만들었습니다. 라이브러리가 제공하는 두 기능을 아래와 같은 이유로 그대로 쓰기 어려웠기 때문입니다.

- 유효성 검사: json-render의 유효성 검사는 카탈로그에 컴포넌트가 하나만 등록되어 있을 때만 속성 값까지 확인했습니다. 컴포넌트가 둘 이상 등록되면 이 검사가 속성 확인을 건너뛰었습니다. 그래서 컴포넌트를 수백 종 등록한 카탈로그에서는 잘못된 속성 값도 그대로 통과했습니다.
- 렌더러: json-render의 렌더러는 자식 요소를 상자 하나로 한 번 더 감싸서 그렸습니다. 그런데 디자인시스템 컴포넌트는 정해진 자리(슬롯)에 바로 들어온 요소만 알아봅니다. 그래서 ListItem의 아이콘처럼 슬롯에 넣은 요소를 컴포넌트가 알아보지 못해 화면에서 사라졌습니다.

직접 만든 렌더러에서는 `FilledButton.Leading`처럼 부모와 슬롯 이름을 이은 카탈로그 항목으로 슬롯을 펼쳐 두었습니다.

### 화면 그리기

이렇게 디자인 레퍼런스까지 활용해 화면을 그리면 완성까지 시간이 걸립니다. 그래서 사용자가 빈 화면을 보며 기다리지 않도록, 완성된 요소부터 보여 주는 부분 로딩을 씁니다. 앞서 설명한 것처럼 화면 JSON 문서는 요소가 하나씩 완성되는 형식이라, 사내 서버는 모델의 답을 받는 대로 읽어 괄호가 닫힌 요소만 골라 냅니다. 고른 요소는 짧은 간격으로 SSE(server-sent events, 서버가 연결 하나로 이벤트를 이어 보내는 방식) `draft` 이벤트에 실어 앱으로 보냅니다. 앱은 받은 조각을 합쳐 `root`에서 닿는 요소만 그리고, 아직 완성되지 않은 자식 요소는 스켈레톤으로 표시합니다.

이렇게 앱에 도착한 요소는 앱의 렌더러가 화면 JSON 문서의 `type` 이름으로 디자인시스템 패키지에서 실제 컴포넌트를 찾아 불러옵니다. 프리뷰에 보이는 버튼은 비슷하게 흉내 낸 요소가 아니라 배민 디자인시스템의 버튼입니다. 속성 값의 뜻은 바꾸지 않고, 컴포넌트가 받을 수 있는 표현으로만 바꿔 넘깁니다.

### 부분 수정과 버전

AI에게 화면 전체를 다시 쓰게 하면, 요청하지 않은 곳까지 조금씩 달라지기 쉽습니다. 그래서 화면을 고칠 때는 바뀐 부분만 담은 패치를 받습니다. 쿠폰 받기 버튼을 검정으로 바꿔 달라고 하면, AI는 버튼의 색을 경로 한 줄로 가리키는 연산 하나만 돌려줍니다. 템플릿으로 시작하는 첫 생성도 같은 방식으로, 템플릿 문서를 고치는 패치를 받습니다.

```
[{ "op": "replace", "path": "/spec/elements/coupon-button/props/color", "value": "black" }]
```

![쿠폰 받기 버튼의 색만 바꾸는 패치를 적용하기 전과 후](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-patch-example.png)

앱은 받은 패치를 적용하고, 유효성 검사를 거쳐 새 버전으로 저장합니다. 새 버전은 패치를 적용한 뒤의 화면 묶음 전체를 담은 스냅샷이고, 한 번 저장하면 바꾸지 않습니다. 고칠 때마다 v2, v3처럼 버전이 쌓이므로 언제든 이전 버전으로 돌아갈 수 있습니다.

단계별 주문 흐름처럼 화면 구조 자체를 크게 바꿔야 하는 프롬프트라면, 모델이 패치로는 담기 어렵다며 화면 전체를 다시 만들겠다고 답할 때도 있습니다. 그러면 패치로만 답하라고 한 번 되돌려 보내고, 그래도 안 되면 이전 문서를 참조로 실어 화면 전체를 새로 만듭니다.

## 5단계: 저장 전에는 검사하고, 저장 뒤에는 제안합니다

AI가 쓴 화면 JSON 문서는 바로 저장하지 않습니다. 3단계에서 카탈로그를 시스템 프롬프트에 넣어도, AI가 목록 밖의 이름을 지어낼 수 있기 때문입니다. 예를 들자면 배민 아이콘에는 커피 아이콘이 없는데, AI가 `HomeFillIcon` 같은 이름 규칙을 보고 `CoffeeFillIcon`이라는 이름을 지어낸 일이 실제로 있었습니다. 그럴듯한 이름이라 사람이 보고 넘기기도 쉽습니다.

![5단계에서 쓰는 구성 요소](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-architecture-stage5-1.png)

### 유효성 검사

유효성 검사의 기준은 3단계에서 시스템 프롬프트에 넣은 것과 같은 카탈로그입니다. 유효성 검사는 정해진 규칙대로 동작하는 코드가 맡으므로, 같은 문서에서는 언제나 같은 결과가 나옵니다. 유효성 검사는 두 단계로 진행합니다.

1. 문서가 정해진 형식(필드 이름과 값의 종류)을 지켰는지 스키마로 확인합니다.
2. 카탈로그와 대조합니다. 카탈로그에 없는 타입, 모르는 속성, 허용되지 않은 값, 끊긴 자식 참조, 잘못된 위치에 놓인 슬롯 같은 위반을 찾습니다.

화면 JSON 문서는 AI가 그릴 때만 바뀌지 않습니다. 사용자가 인스펙터로 값을 고치고, 빈 화면을 더하거나 화면을 복사하고, Figma 시안을 가져오기도 합니다. 어떤 경로로 바뀌든 같은 유효성 검사 함수를 거쳐야 저장됩니다. 그래서 저장된 화면 JSON 문서에는 신뢰할 수 있는 디자인시스템의 컴포넌트와 값만 남습니다.

유효성 검사에 걸린 문서는 저장하지 않습니다. 어느 요소의 어떤 값이 왜 틀렸는지 문장으로 작성해 AI에게 돌려보내고, 고친 문서를 다시 받습니다. 사내 서버가 새 화면을 만들 때 보내는 교정 프롬프트는 이런 형식입니다.

```
카탈로그에 맞지 않는 곳:
- cafe-icon: Icon.name 값이 규격에 맞지 않습니다: 허용 값 381종에 없습니다: CoffeeFillIcon.
- home-icon: Icon.name 값이 규격에 맞지 않습니다: 허용 값 381종에 없습니다: HomeFilIcon. 이름이 비슷한 값: HomeFillIcon

고칠 화면 문서:
{ … }
```

*서버의 교정 프롬프트 형식에 위의 두 위반을 넣어 다시 쓴 예입니다.*

아이콘처럼 고를 수 있는 값이 많으면, 틀린 값마다 이름이 비슷한 후보만 함께 알려 줍니다. 값을 모두 나열하면 메시지가 길어져 어느 값이 틀렸는지 알아보기 어렵기 때문입니다.

`HomeFilIcon`처럼 글자 하나가 빠진 오타는 AI가 후보를 보고 바로 고칩니다. 교정은 최대 두 번까지만 하고, 교정본의 위반이 줄지 않으면 거기서 멈춥니다. 끝까지 남은 위반 요소는 빼고, 무엇을 왜 뺐는지 응답에 함께 실어 사용자에게 알립니다.

![유효성 검사와 교정의 흐름](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-seq-repair.png)

*사내 서버가 위반을 문장으로 돌려보내 고치게 하고, 앱이 저장하기 전에 한 번 더 유효성을 검사합니다.*

### 디자인 린트

유효성 검사를 통과했다고 배민다운 화면이 되지는 않습니다. 카탈로그에 있는 것만 써도 카드 안에 카드를 또 넣거나, 배경에 묻히는 글자색을 쓰거나, 영역마다 그림자를 줄 수 있습니다. 디자인 린트는 저장한 화면 JSON 문서에서 이런 곳을 찾아 고칠 방법을 제안하는 규칙입니다.

![디자인 린트 규칙 세 가지의 예](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-design-lint-rules.png)

*디자인 린트의 일부 규칙을 발췌하였습니다.*

3단계에서 시스템 프롬프트에 함께 넣은 디자인 원칙 가운데, 코드가 늘 같은 판단을 내릴 수 있는 것만 골라 린트 규칙으로 옮겼습니다. `nested-card`(카드 안의 카드), `no-shadow`(그림자), `foreground-contrast`(글자색 대비)가 대표적인 예시입니다. 간격과 모서리에 토큰과 정확히 같은 픽셀 값을 쓰면 토큰 이름으로 바꾸는 규칙도 있습니다. 디자인 린트는 렌더링 결과의 픽셀을 측정하지 않고, 화면 JSON 문서와 카탈로그, 토큰 사전만 보고 판정합니다.

글자색 대비는 [WCAG 대비 공식](https://www.w3.org/TR/WCAG22/#dfn-contrast-ratio)으로 라이트와 다크 두 테마에서 모두 측정합니다. 다만 기준값은 접근성 기준인 4.5가 아니라 읽을 수 없는 수준인 2.0으로 잡고, 반투명한 위계 색은 같은 계열의 불투명한 기준색으로 측정합니다. 디자인시스템의 `Foreground/Quaternary` 글자색은 흰 바탕 위 대비가 1.46인데, 디자인시스템이 일부러 그렇게 연하게 만든 값입니다. 접근성 기준을 그대로 쓰면 Foreground 계열이 통째로 걸려 글자 위계가 사라집니다.

유효성 검사는 틀린 문서를 막고, 디자인 린트는 저장한 뒤에 어색한 곳마다 고칠 방법을 제안합니다. 적용할지는 사용자가 정합니다. 규칙은 기준일 뿐이고, 마지막 결정은 화면을 만드는 사람이 내려야 하기 때문입니다. 사용자가 제안을 적용하면 최신 문서에 해당 규칙만 다시 실행하고, 유효성 검사를 거쳐 새 버전으로 저장합니다. 어드민에서 강제로 지정한 규칙에 걸린 곳은 사용자 선택 없이 저장 전에 자동으로 고칩니다.

---

## 6단계: 화면 JSON 문서 하나를 여러 곳으로 내보냅니다

4단계에서 AI가 코드 대신 화면 JSON 문서를 썼으므로, 유효성 검사를 통과해 저장된 문서는 마지막 단계에서 다시 그리지 않고 여러 환경으로 내보낼 수 있습니다. 디자이너는 Figma로, 개발자는 코드로 이어받고, 기획자는 베타앱이나 웹 페이지에서 바로 확인합니다. 글 앞에서 같은 화면을 세 번 그리던 기획자, 디자이너, 개발자가 이제 같은 문서 하나에서 출발합니다.

![6단계에서 쓰는 구성 요소](https://techblog.woowahan.com/wp-content/uploads/2026/11/diagram-architecture-stage6.png)

웹은 React, iOS는 SwiftUI, Android는 Compose 코드로 내보냅니다. 코드 제너레이터는 AI를 다시 호출하지 않고 화면 JSON 문서를 곧바로 코드로 바꿉니다. 같은 문서에서는 언제나 같은 코드가 나오고, 버튼을 누르면 기다리지 않고 코드를 받을 수 있습니다. 생성된 코드는 디자인시스템 컴포넌트를 불러 쓰고, 색과 간격도 3단계에서 본 토큰 이름 그대로 작성합니다. 개발자는 이 코드를 실제 서비스로 가져가 데이터와 동작을 붙입니다.

세 코드 제너레이터는 디자인시스템 공통 가이드와 각 플랫폼의 코드 구조를 따르고, 테스트로 모두 같은 규칙을 지키는지 확인합니다. 프리뷰와 내보낸 코드가 같게 그려지는지도 테스트로 확인합니다. 그래서 개발자는 어느 플랫폼의 코드를 받든 프리뷰에서 본 화면과 같다고 믿고 쓸 수 있습니다.

Figma로 내보낼 때는 앱과 Figma 플러그인이 로컬 WebSocket으로 연결됩니다. 앱이 화면 내용을 보내면, 플러그인이 디자인시스템 라이브러리에서 컴포넌트를 불러와 배치하고 변수와 글자 스타일을 연결합니다. 화면 JSON 문서에 토큰 이름으로 쓴 색과 간격이 Figma에서도 디자인시스템의 변수로 이어집니다. 디자이너는 디자인시스템과 이어진 레이어를 받아 그대로 이어서 작업할 수 있습니다.

생성된 결과를 사내 서버에 올리면 화면을 볼 수 있는 주소가 생깁니다. 이 주소로 휴대폰의 배민 베타앱이나 웹 페이지에서 화면을 열 수 있습니다. 기획자와 디자이너는 실제 기기에서 화면의 크기와 흐름을 확인하고, 주소를 동료에게 보내 함께 검토합니다.

## 골든셋으로 확인합니다

여섯 단계의 결과는 AI에게 기본으로 전달되는 내용에 따라 달라집니다. 1단계의 표준 질의서, 2단계의 템플릿 목록, 3단계의 시스템 프롬프트가 여기에 해당합니다. 이 내용을 고치다 보면 한 프롬프트의 결과는 좋아졌는데 다른 프롬프트의 결과는 나빠지는 일이 생깁니다. 몇 개만 눈으로 보고 반영하면 이런 일을 놓치기 쉽습니다. 그래서 프롬프트마다 기대 결과를 정해 둔 시험 문항을 만들고, 이 묶음을 골든셋이라고 부릅니다. 골든셋은 동작마다 따로 채점합니다.

| 동작 | 확인하는 것 | 채점 | 실행 |
| --- | --- | --- | --- |
| 템플릿 고르기(2단계) | 프롬프트에 맞는 템플릿을 고르는가 | 기대한 템플릿이면 1점, 아니면 0점입니다. 문항별 가중치로 평균을 냅니다. | 관련 프롬프트가 바뀐 MR과 매일 밤 일정에서 CI가 실제 모델로 실행하고, 기준 점수에 못 미치면 실패합니다. |
| 고치는 중 질문(1단계) | 수정 프롬프트를 받고 바로 고칠지, 먼저 물을지 판단하는가 | 물어야 할 항목 조합이 기대와 같으면 1점입니다. | 프롬프트를 고칠 때 사람이 돌립니다. |
| 그리기(4단계) | 빈 화면에서도 프롬프트대로 그리는가 | 컴포넌트와 글자, 순서는 코드가 채점하고, 프롬프트의 의도는 다른 모델이 기준표로 따로 채점합니다. | 사람이 돌립니다. |

그리기 문항은 사내 서버의 실제 생성 경로를 그대로 지나므로 지식 검색까지 함께 시험합니다. 프롬프트의 의도처럼 코드로 판정할 수 없는 기준은 다른 모델이 채점하고, 채점 결과는 구조 점수와 섞지 않고 따로 봅니다.

### 사용자 반응

베타 테스트에 참여한 디자이너들은 디자인시스템이 그대로 반영된 결과물이 나온다는 점을 가장 큰 가치로 꼽았습니다.

> 디자인 시스템이 반영된 결과물이 출력되는 게 가장 좋은 포인트였어요. 결과물이 실제 배민앱 내에서 활용 가능한 스타일로 나와 참고하기 유용했습니다.

> 디자인 시스템 2.0으로 드래프트를 만들어 줘서 작업 시간이 줄어든다는 점이 좋았어요.

디자이너가 부족할 때, 기획자가 새로운 아이디어를 발산할 때 CLAYDesign을 찾는 일도 늘고 있습니다. 디자이너가 부족한 팀은 기획 단계에서 바로 디자인시스템을 따르는 시안을 만듭니다. 기획자는 떠오른 아이디어를 곧바로 화면으로 만들어 동료와 함께 견줘 봅니다.

## 비슷한 고민을 하는 팀에게

1. **코드가 아는 값은 모델에게 쓰게 하지 마세요.** 모델에게는 고르는 일만 맡기세요. 질문 문구는 앱이 채우고 모델은 판정만 내리며, 템플릿도 모델은 고르기만 합니다. (1단계, 2단계)
2. **빈 화면보다 템플릿에서 시작하고, 검색은 영역마다 하세요.** (2단계, 4단계)
3. **디자인시스템을 사람이 따로 옮겨 적지 말고 코드에서 뽑으세요.** (3단계)
4. **가이드로 정할 수 없는 화면 원칙은 디자이너가 직접 쓰게 하세요.** (3단계)
5. **화면은 코드 대신 JSON 문서로 쓰게 하세요.** 데이터라서 검사하기 쉽고, 바뀐 부분만 패치로 고칠 수 있습니다. (4단계, 5단계)
6. **채점 기준을 먼저 정하고, AI에게 주는 내용을 고칠 때마다 다시 채점하세요.** 디자인 가이드 하나를 추가한 작은 변경이 템플릿 고르기 정확도를 어긋나게 한 적도 있습니다.

## 마치며

클레이디자인을 통해 화면의 기준을 새로 만들지 않고, 이미 있던 디자인시스템을 단계마다 AI가 읽게 했습니다. 카탈로그는 디자인시스템의 타입 선언에서 나오고, 템플릿과 디자인 레퍼런스는 디자이너가 그린 배민 화면에서 나옵니다. 컴포넌트 선택 가이드와 디자인 원칙도 디자인시스템이 정해 둔 기준입니다. AI는 디자인시스템의 구성 요소로 화면 JSON 문서를 쓰고, 유효성 검사와 디자인 린트, 코드 변환은 정해진 규칙대로 동작하는 코드가 맡습니다. 디자인시스템이 있었기에 AI가 배민답게 그릴 수 있었습니다.

이 구조는 다른 디자인시스템으로도 넓힐 수 있습니다. 사내에는 지금 쓰는 클레이 민트 말고도, 사장님 서비스에 쓰는 클레이 블루 같은 디자인시스템이 있습니다. CLAYDesign은 디자인시스템 정보를 생성할 때마다 시스템 프롬프트에 넣으므로, 정보만 바꾸면 다른 디자인시스템으로도 그릴 수 있습니다.

디자인시스템을 운영하는 팀이라면, 이미 정해 둔 컴포넌트와 토큰, 가이드를 AI가 읽을 수 있는 형태로 정리하는 일부터 시작해 보세요. 이 글이 비슷한 도구를 고민하는 팀에게 출발점이 되면 좋겠습니다.
