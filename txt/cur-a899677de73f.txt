Making Sense of React Server Components ｜ Josh W. Comeau ｜ 文章 ｜ https://www.joshwcomeau.com/react/server-components/

Josh W. Comeau 这篇文章（2023 年 9 月，2025 年更新）想澄清围绕 React 服务器组件（RSC）的大量困惑。作者坦言，亲手试过之后，他对这项技术的兴奋程度远超预期。

文章先从服务器端渲染讲起。早期 React 应用多为客户端渲染：用户收到一个只有空 div 和脚本标签的 HTML，要等 JS 包下载、解析、执行之后才能看到界面，而且包会随功能增加越来越大。SSR 改由服务器生成完整 HTML，浏览器端的 React 再“水合”这份现成的 DOM，绑定事件、补上交互。作者引用 Dan Abramov 的比喻：水合就是用交互的“水”浇灌“干燥”的 HTML。

接着作者用时间线图对比几种数据获取流程，并引入三个性能指标：首次绘制（FCP）、页面可交互（TTI）和内容绘制（LCP）。客户端渲染要先下载 JS、渲染外壳，再向 API 请求数据，最后才渲染内容。SSR 只是更快画出带加载状态的外壳，用户真正想看的内容仍要等第二次往返。既然请求本来就从服务器开始，更合理的做法是在首次请求时就查好数据库，直接返回填满内容的页面。Next.js 的 getServerSideProps 等元框架方案早已能做到这一点，但有三个缺点：只能用在路由顶层组件，各框架做法不统一，而且所有组件依旧都要在客户端水合。

React 官方给出的答案就是服务器组件：组件可以只在服务器上运行，甚至可以是 async 函数，直接在组件里查询数据库。关键在于，服务器组件只运行一次、永不重新渲染，输出被视为不可变。因此 state、effect 等 API 都不能用，但也不必再担心副作用重复执行。原来的普通组件被改称“客户端组件”。作者不喜欢这个名字，因为客户端组件其实在服务器和客户端都会渲染。当时只有 Next.js 13.4+ 的 App Router 支持 RSC，因为它需要和打包器、服务器、路由深度集成。组件默认是服务器组件，要在文件顶部写上 'use client' 指令才会成为客户端组件；'use server' 则属于另一个功能，即 Server Actions。

最绕的是“边界”。如果某个持有 state 的组件变成客户端组件，它重新渲染时，它渲染的子组件也必须能重新渲染。所以规则是：客户端组件只能导入客户端组件。'use client' 实际上划出了一条客户端边界，边界内的组件被隐式转换为客户端组件。不过可以通过改变“拥有者”来绕开限制。作者以深色模式切换为例：把带 state 的部分抽成 ColorProvider 客户端组件，通过 children 接收内容，再由服务器组件 Homepage 导入并渲染 Header 和 MainContent。决定 props 的是导入并渲染它们的 Homepage，而不是树上的父组件，所以这两个组件仍然可以是服务器组件。'use client' 是在模块层面、沿着导入关系生效的。

从底层看，服务器组件的代码不会进入 JS 包。服务器把它的渲染结果（虚拟 DOM 描述）内联在 HTML 的 script 标签里，客户端水合时直接复用。所以 JS 包变小了，HTML 变大了，总体传输量通常还是更少，HTML 也是分块流式传输的。想看真实的序列化格式，可以用 Alvar Lagerlöf 的 RSC Devtools。

谈到优势，作者认为性能提升反倒最不令人兴奋：多数 Next.js 应用已经够快，语义化 HTML 在水合前也基本可用。真正吸引他的，是不必再在功能和包体积之间取舍。比如完整的语法高亮库有好几 MB，放进服务器组件就不占任何包体积，Bright 正是按这个思路设计的。此外，服务器组件不涉及依赖数组、过期闭包、记忆化这些由“状态变化”带来的复杂问题，写起来轻松。最后他指出，RSC 只是“现代 React”的一块拼图，与 Suspense 和流式 SSR 结合，可以先发外壳、再把内容流式推送并分段水合。文末是他的课程《The Joy of React》的推介。
