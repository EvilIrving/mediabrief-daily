JS Party 第 315 期由 Amal Hussein 和 Nick Nisi 主持，嘉宾是 Google Chrome 团队的 Annie Sullivan（Core Web Vitals 技术负责人，在 Google 工作 19 年）和 Rick Viscomi（Web 性能开发者关系负责人）。节目录制于 2024 年 2 月 28 日，此时 INP 再过几周就要正式取代 FID，成为 Core Web Vitals 之一。

开场先把几个基础概念讲清楚。主线程是 JavaScript 运行和 DOM 更新的地方，执行期间会阻塞界面，所以性能建议总说"别阻塞主线程"。事件循环是浏览器调度主线程工作的机制，可以把它想成一个不停转动的轮子，Rick 推荐看 Jake Archibald 的演讲《In the Loop》（"双重 requestAnimationFrame"为什么有效，用它就能解释）。网页和游戏一样有帧率，长动画帧就是耗时超出用户预期的那一帧。对交互来说，响应应在 100 毫秒以内。"响应性"在这里指从用户操作到下一帧画面出现的时间，跟响应式设计无关。"交互"只算点击、轻触、按键这类离散操作，而且按下和抬起分开处理，不会因为用户抬手慢而扣网页的分。滚动不算在内，因为 GPU 加速滚动基本不归页面控制。

Core Web Vitals 是 Web 的"健康指标"，共三项：LCP 衡量加载，INP（之前是 FID）衡量交互响应，CLS 衡量布局稳定。Annie 回顾了来历：onload、DOMContentLoaded、Speed Index、FP、FCP 这些指标，要么跟用户实际感受对不上，要么没法在真实用户环境里测，加起来大概有"七百万种测法"，开发者反而无所适从。所以 Google 回到用户体验本身，挑出几个关键时刻，并坚持用真实用户数据来衡量。Rick 强调了真实用户数据和实验室数据的区别。Lighthouse 分数是 Speed Index、TBT 等指标的加权汇总，变绿只能说明测试配置下查得到的问题都解决了。没测交互就看不出 INP 问题，没往下滚动就看不到布局偏移。真实数据看第 75 百分位，这也意味着还有 25% 的用户比这个数更慢。指标很少改动，改也是基于反馈做小修正。例如服务端渲染加水合时，同一个 LCP 元素会渲染两次，现在改为按第一次计，受影响的网站不到 1%。三项指标互相牵制，很难只刷其中一项。要是指标显示很快、用户却觉得慢，那就是 bug。分数只看自己网站的用户分布，拖慢别人的网站也不会让自己显得更快。

谈到 SEO，Rick 说 Chrome 和搜索之间有一道墙，他只能引用搜索文档：建议网站做好 Core Web Vitals，以便在搜索中取得成功、提供良好体验。他更愿意谈性能的内在价值：给转化漏斗上润滑油，让用户少些摩擦、少些愤怒狂点，对整个生态也是好事。Annie 提到 Core Web Vitals 技术报告，可以对比各个平台和框架的表现。Core Web Vitals 主要面向内容型网站，长时间运行的应用需要补充其他指标，比如帧率。不过数据显示，用户在应用里停留的时间远比开发者以为的短。需要更细数据时，可以直接用底层的性能 API，它会报告每一次交互和每一次绘制。

INP 是这期的重点。它取整个页面生命周期里大约最慢的一次交互：200 毫秒以内为良好，超过 500 毫秒为差。每 50 次交互剔除最慢的一次，实际相当于第 98 百分位，不过大多数页面加载的交互少于 10 次。阈值定在 200 而不是 100 毫秒，一是照顾低端设备，二是取的是接近最差的那一次。INP 只衡量到"下一帧"，也就是用户能否立刻看到反馈，不管整个操作要多久完成。上传文件这类耗时操作，只要马上显示加载状态、让主线程保持空闲就行。如果把两秒的 JavaScript 一口气跑完，用户会再点一次，第二次交互同样被卡住。FID 被替换，是因为它只测首次交互的输入延迟。框架改成了可中断的水合，Chrome 也去掉了不必要的双击缩放延迟，FID 问题很快就基本消失了。但每 100 个页面里仍有 1 个会在点击后冻结超过一秒，而且用户 90% 的时间花在页面加载完成之后。Nick 问一直播放的下雪动画会不会影响 INP。Annie 的回答是：如果用 JavaScript 逐帧改 DOM，动画的耗时会算进交互响应；改用 CSS 动画或合成器动画就没有影响。Chrome 会判断交互是否真的引起了需要重新绘制的变化，再把交互和对应的那次绘制关联起来。

INP 的常见问题分两类：事件处理函数本身太慢，或者主线程正忙别的事，导致输入延迟。Rick 打了个比方，一个是路上有坑，一个是车太破。具体原因包括 DOM 过大（HTML 规范页面是极端例子）、JavaScript 太多（下载、解析、编译都有成本），以及该推迟的工作（比如统计分析）没有推迟。对策是用 DevTools 性能面板做追踪，用客观数据代替感觉。代码里可以设置让出点，比如 0 毫秒的 setTimeout，或者用 Scheduler API 的 postTask 声明优先级。GoogleChromeLabs 提供了 scheduler-polyfill，yield 当时在 Chrome 源试用中，预计 2024 年晚些时候进入稳定版。React Suspense 这类框架机制也能帮忙排定优先级。

LCP 是"最大的内容绘制"。它必须是用户能看到的内容，背景色变化不算，算的是 h1、图片、段落这类东西，并以最后一个候选元素为准。用户一旦开始交互，就不再更新候选。Rick 提醒，"首屏以下一律懒加载"有例外：如果很多用户通过深层链接直接落到页面中部，那里的配图就可能是 LCP，应该根据数据排除在懒加载之外。web-vitals.js 的归因功能，就是把团队成员调试这类问题的经验固化下来的结果。CLS 按偏移面积占视口的比例计分。考虑到长时间打开的页面，计算方式从"整个生命周期累加"改成了"会话窗口"：把短时间内连续发生的偏移归成一组，每组最长 5 秒，取最差的一组。和内容对齐的骨架屏不算刷分，它确实能改善体验，在低网速地区尤其明显。

落地方面，Rick 建议从 web.dev 文档入手。先用 CrUX 和 PageSpeed Insights（免费，覆盖超过一千万个网站，可看页面级或源级数据）或 Search Console 确认自己到底有没有性能问题。平时在本地用节流、A/B 测试、性能追踪和 Web Vitals 扩展程序，在问题上线之前把它找出来。需要登录的网站在 CrUX 里只有源级汇总，想要页面级的诊断就得部署第一方 RUM。性能工作没有银弹，就像每天刷牙，需要网站、框架、CMS、浏览器一起出力。在其他浏览器方面，各项指标都基于 W3C Web 性能工作组的开放标准，Firefox 已经实现了 LCP 和大部分 Event Timing。WebKit 投入较少，Annie 鼓励开发者直接向 WebKit 提需求。对于"Google 想当 Web 老大"的批评，Annie 表示欢迎，正因为 Google 影响力大，外界的监督才更重要。最后 Rick 总结说，性能本身就是一种可访问性，太慢的网站用户根本用不了。WPO Stats 上有大量案例可以说服还在观望的人。他鼓励大家公开分享自己的优化案例，让更多人重视性能。
