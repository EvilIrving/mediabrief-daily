JavaScript 模块体系中原生 JSON 模块导入（JSON Module Imports）与运行时 fetch 动态拉取，在底层生命周期、错误隔离与内存垃圾回收（GC）机制上存在本质差异。尽管各主流浏览器引擎已通过基线标准全面支持 import data from './data.json' with { type: 'json' } 规范，但在生产级 Web 运行时环境中，将其作为通用数据请求手段直接替代 fetch 会引入不可忽视的架构缺陷与内存驻留泄漏隐患。

从模块图加载与异常容错的角度审视，两者的执行生命周期截然不同：
1. 静态导入的故障级联：静态 import 语句与宿主 JavaScript 模块图强绑定。如果目标 JSON 文件发生网络请求超时、404 状态码或内容语法解析错误，整个模块依赖图的加载会被立即阻断，导致包含它的脚本整体执行失败，且在当前执行环境中完全无法挂载兜底回退逻辑。
2. 动态 import() 与 fetch() 的容错差异：尽管动态 import() 支持通过 try/catch 捕获异常，但 fetch 提供了更丰富的底层内省能力。通过 fetch 可以直接检查 response.status 状态码，并在 JSON 解析崩溃前调用 response.text() 获取原始畸变报文，便于实施针对性的业务降级与异常日志上报。

更深层的工程陷阱存在于模块映射表（Module Map）的生命周期与内存驻留机制：
- 模块缓存的永久驻留：在规范中，浏览器通过 import 载入的任何模块（无论是 JS、WASM、CSS 还是 JSON）都会被永久缓存在当前执行上下文（页面或 Worker）的模块映射表中，即便请求失败亦会被缓存标记。如果开发者尝试对带查询参数的动态接口使用 JSON 导入（例如 import('/api/search?q=' + query)），每一个独立 URL 都会在模块图中创建一条永不释放的模块记录，直接引发不可回收的内存泄漏。
- 垃圾回收阻断与内存固化：通过 fetch 获取的 JSON 数据对象在脱离作用域且无外部强引用时，能被垃圾回收器即时回收；而通过 import 导入的 JSON 数据，其根对象会作为模块记录的默认导出被模块图永久强引用。即便业务代码尝试将其局部引用置为 null，整个庞大的数据对象依然常驻内存，无法释放。

在打包构建与工程落地层面，JSON 模块导入的最佳场景仅限于构建阶段已知、且需要全量消费的本地静态元数据或配置文件。常规打包工具无法对嵌套的 JSON 对象键名实施摇树优化（Tree-shaking）；即便部分打包器通过非标准语法支持顶层属性解构引入，依然无法消除深层冗余数据。若仅为读取单一版本号等字段而导入庞大的 package.json，应当在构建工具插件中前置完成提纯与剔除，而非在运行时依赖模块导入。
