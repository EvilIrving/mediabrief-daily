旁白：现代 Web 开发需要越来越多的工具：格式化器、linter、打包器、插件。每样工具通常各有配置、依赖和性能开销。随着应用越来越复杂，维护这条工具链本身就成了真正的负担。

Biome 是面向 Web 项目的开源工具链，把格式化和 lint 合进一个快速、有主张的工具。它用 Rust 写成，目标是 Prettier 和 ESLint 的即插即用替代品：合理的默认值、极少配置，以及 CLI 与编辑器环境一致的行为。Biome 还引入了模块图，支持跨文件分析，以及不依赖 TypeScript 编译器的类型感知 lint 规则。

Emanuele Stoppa，大家叫他 Ema，是 Cloudflare 的高级系统工程师、Astro 的负责人之一，也是 Biome 的创建者和首席维护者。这期节目里，Ema 和 Josh Goldberg 聊 Biome 的历史、linter 与格式化器的底层原理、Biome 的架构与它要替代的那些工具有何根本不同，以及项目和社区接下来会怎样。

本期主持人是 Josh Goldberg，独立全职开源开发者。他主要做 TypeScript 生态的项目，尤其是 typescript-eslint——让 ESLint 和 Prettier 能跑在 TypeScript 代码上的那套工具。他也是 O'Reilly《Learning TypeScript》一书的作者、微软开发者技术 MVP，以及 SquiggleConf（优秀 Web 开发者工具大会）的联合创始人。可在 Bluesky、Fosstodon 和个人网站上找到 Joshua K. Goldberg。

Josh：今天请来的是 Emanuele Stoppa，Cloudflare 的开源维护者、Biome 的创建者，也是 Astro 的负责人之一。Ema，欢迎来到 Software Engineering Daily。

Ema：谢谢邀请，Josh。最近怎么样？

Josh：挺好的。很高兴能跟你聊。你最近在技术圈做了不少有意思的事：在 Astro，加入了 Cloudflare，还是 Biome 的创建者和首席维护者。进入这些之前，你是怎么开始写代码的？

Ema：跟外面大多数开发者大概一样——"我想做电子游戏"。这基本上就是我入行的原因。事情并没有按我想的发展。我去了大学，本来该学游戏设计，可到了我该上那门课的那年，没有教授。于是我只好选了别的课。最终我完全没做电子游戏相关的事。我就去做了 PHP、Postgres，以及当时 Web 开发那一套，就这样入门了。然后是 PHP 开发者、jQuery，一路走到 React 和我们现在这些酷家伙。

Josh：想到开发前端全栈应用、PHP、jQuery，你会有什么情绪吗？

Ema：会，因为我看到很多当年用过的模式又回来了，比如 SSR——以前对 React 开发者来说这还不是回事，到处都是 SPA，人人都在做单页应用。然后 SSR 又回来了，因为那本来就是你在 PHP 里做事的方式。我是说，这儿没什么新东西。我们只是在用不同的工具做同样的事，用 JavaScript 而不是 PHP、C# 或 Java。当时我们有的就是那些。

有点奇怪，因为我们并没有发明什么，也没有重新发明轮子。没什么令人兴奋的——只是同样的模式换了不同的工具和库。我喜欢的是，现在的工具简化了流程。当年我想做 SPA 或岛屿架构之类的时候，一团糟。现在我们知道怎么做这些事了，库也允许我们这么做。我会想：啊，谢天谢地，现在可以很快做完了。

Josh：很好，我们学会了用更干净的语法做同样正确的技术。这也带到你的一次转折：你一开始是做应用的普通开发者——PHP、jQuery 等等——但某个时候转向了开发者工具。在那个领域，你最早关联、也引起不少关注的项目之一是 Rome。能讲讲它是怎么来的、是什么吗？

Ema：对。Rome，Rome Tools，本来想做成面向所有 Web 项目的一体化工具：格式化、lint、打包、测试，全都放进一个应用或二进制里。我非常喜欢它背后的使命。过去我一直很难维护那么多开发依赖——格式化器、linter、打包器、插件。Rome 像一股新鲜空气。当时我正想找一个开源项目贡献，心想：行，干吧。我就这样加入了。

当时 Rome 是 TypeScript 写的。后来 Rome 拿到了一些融资，开了公司，我也以员工身份加入了那个工具。基本上就是这么过去的。不过我对开源的热情更早，也不止 Rome。在那之前我参与过 Webpack，是 CLI 团队的一员。为什么？因为我在工作过的每家公司都跟 Webpack 较过劲，差不多成了专家。我也在 Stack Overflow 上回答问题之类的。我想加深对 Webpack 的了解，做法就是走进开源，向真正的创造者学习。

Josh：你是怎么从学 Webpack，跨到回馈项目、帮助别人的？对很多人来说，那道难度的悬崖好像挺吓人的。

Ema：是的，确实吓人。但最终你就是得去做。像一次信仰的跳跃。然后你会明白，你不可能什么都知道。你得跟这件事和解，说："这个我不会，那个我不会，但我在这件事上有经验。"也许那就是你的解法，也许那是另一种解法。一旦你明白不可能什么都懂，并接受别人可能有答案，事情就容易了。最终你只是做自己想做的事，试着学自己想学的东西。

Josh：而对你来说，那就是把你提到的那些复杂技术栈，简化成更容易驾驭的东西。

Ema：对，完全正确。做工具之前我在前端，那是完全不同的世界。工具需要很多与前端不同的知识，但也有相似之处。有些教训可以从前端带过来：无障碍、错误处理，跟浏览器较劲，跟很多上下文里不工作的东西较劲。你把这些带进工具。比如错误处理是一样的：用户犯了错，你得处理；后端做了古怪的事，你得处理。工具也一样。用户总是通过 CLI 之类输入东西，你本质上得给出体面的反馈。上下文不同，但最终它是一个产品。你有用户，你得提供他们喜欢的好东西。没那么可怕。

我是说，在编程里，你遇到的问题大体总是一样的。不同上下文。但最终就是关于数据。你拿到一些数据，得解析它们，然后拿它们做点什么。如果不行，你就给出好的反馈；如果行，你就给出用户想要的反馈。

Josh：函数式程序员听了大概会高兴——一切最终都变成返回两种类型之一的函数。

Ema：正是。

Josh：那我们聊聊"拿它们做点什么"。你已经在好几个处理代码、构建代码的项目上干过了。最基础地说，在进入细节之前：什么是 bundler，或者说打包器是什么？

Ema：哦。打包器是什么？就像你说的，打包器是一种链接器。就是把不同的文件拿来，做成全部链接在一起的东西。在现代编程、在 Web 生态里，打包器得把散落在应用和依赖里的大量 JavaScript 文件拿过来，最终做出对你作为开发者、尤其对最终用户来说，浏览器里好用的东西。

你得发出不会坏掉的东西，得发出不会下载很久的东西。你不能把所有文件、所有依赖都发出去，否则就是成兆成兆的 JavaScript 让用户去下。它还得处理很多不同的东西：HTML、CSS、Sass、Less、TypeScript、CoffeeScript，现在还有 WASM，等等。在我看来，打包器如今其实是你能创造或贡献的最困难、也最有成就感的软件之一，因为要操心的事很多。我觉得任何人想做这块都能学到很多——还包括 source map。

Josh：是的，里头事情很多。假设我有一个最简陋的应用，用 import 和 export。有一个 HTML 页面，一个从几个 node modules 导入的 JavaScript 文件，也许还有另一个导入它并调用的 JavaScript 文件。我想把它变成某个 .com 网站，并用一个工具来做。首先，我需要用工具吗？有没有什么情况下可以不用？

Ema：你可以用工具，也可以不用。取决于你的口味。当年用 PHP 这类东西时，你不需要。你就有一个 PHP 文件，里面是你的 JavaScript 和一切。开箱即用。后来事情变得更复杂了。用户需要更多。浏览器能力更多了。我们现在在浏览器里录制这次访谈，这是十年或十五年前做不到的。能力增加了，我们手里的工具更多了。连应用本身，也基于我们想交付的东西而变复杂了。

最终你会想用一个工具。它大大简化了样板：搭页面、DOM，甚至 JavaScript 交互之类。你可以自己做，但如今事情太多了，你不想做那个。你想专注于应用，不想专注于样板。所以是的，如今你应该用一个简化所有基础的工具，好专注于在浏览器上创造你想要的任何东西。甚至 Electron，做原生应用。看，能力增加了，可能性是无穷的。

Josh：好，你说服我了——为我的 HTML 和几个 JavaScript 文件的页面用打包器。那它实际怎么工作？我们怎么从分散在不同 JavaScript 文件里的源码，变成用户运行的、带有你刚才说的那些优化的东西？

Ema：这是个很有意思的问题。我没有一个清晰的标准答案。但作为做这类事的一些工具的开发者——比如 Astro——它怎么工作？你有页面的概念，本质上就是用户落地的入口点。从那里开始，你本质上开始构建依赖树：样式、CSS 文件、组件、JavaScript 文件，页面需要的任何东西。打包器就是这么工作的。

你有入口点，用户需要交互的地方。叫它们页面。在多数情况下，入口点和页面是同义词。在那里，打包器创建一份资产的依赖树。它需要发出什么，才能渲染并让页面可用？当然，理解 CSS 文件有很多挑战。如今更复杂了，因为有些应用里样式是跟组件一起发出去的，像原子一样。

以 Vue、Svelte 和 Astro 为例。它们有单文件组件的概念。每个文件组件可以包含一段 JavaScript、一段 HTML、一段样式。当树里有多个组件时，你还得理解这些样式该按什么顺序打包在一起，才不会把最终结果搞乱。

你可能有一个按钮被导入在树的中间或末尾，然后你得决定：好，现在顺序是什么？这就是打包器做的事。它负责替你解决这类问题，这样你就不必去较劲。当然也可能有 bug，但那就是打包器替你做的。

JavaScript 也一样。你的树里有很多脚本导入。你得确保它们按顺序导入和执行。最终你的按钮会对表单提交做出反应，或对表单里的错误做出反应，而不弄坏其他脚本。我觉得打包器就是这样工作的。

Josh：有意思的是你描述资产的方式——你的解释里几乎没有什么是 JavaScript 文件特有的。假设我们有一种新资产。假设我想导入某个 .webp 图片，然后在文件里当源字符串用。在这个体系里，是不是意味着我可以对不同种类的资产有某种任意可扩展的插件？

Ema：对，技术上是的——如果打包器允许你这么做。但本质上，打包器需要以非常抽象的方式工作，然后又得有专门的部分，去理解它实际在处理什么。CSS 文件、有不同扩展名和编码的图片等等。我们有 WASM，也需要自己的实例化和其他东西。

比如字体，那是另一种需要以特定方式对待的资产。是的，如今我们在做的打包器必须设计得通用且可扩展，好让用户按自己的需要扩展。因为不是每个人都要处理 Web 图片、AVIF 或视频——也有这类资产。自从 Webpack 或 Rollup 时代以来，我们在做通用的打包器，用户可以扩展它。我们定下了一套插件系统，用户基本上可以对打包器做任何事。

Josh：用户想做什么就做什么，给了用户很大权力。但很多资深 Web 开发者会记得，权力是有代价的。我们聊聊其中两个代价：性能，以及可配置性或易用性。外面有几千行、又慢的 Webpack 配置的恐怖故事。你会怎么回应？

Ema：我对插件的信念或看法最近变了很多，尤其是我现在在做用原生语言写的 Biome，以及完全不同的、使用插件的 Astro。正如你所说，有代价。我觉得人们不该付那个代价。你有很多扩展性。但那很好——你周末做项目，可以写插件，有一种权力感。你在做大事，因为你在创造东西。

但硬币的另一面是：你在工作，你要对雇主的产品负责。那就是你付的代价。你有很多插件、很多扩展、很多集成要对付，它们对你的应用有成本。当然，打包器多少得对此负责，降低性能开销、让它更快。

但到某个点，我觉得这不再是打包器或工具、插件系统的责任了。那是插件维护者的责任。最终谁付代价？用户。我逐渐意识到，我们只需要在某些事情上有插件系统。别的东西不该扩展太多，而应该烘焙进工具里。工具可以正确地做，可以监控性能。但如果我们把所有这些集成和插件都交给用户，最终工具性能会下降。你就会落到 Webpack 打包一个应用要三十分钟那种地步。

我不知道。我们一直在试图解决这个问题。我们有 Rollup。现在又有 Rolldown，想用不同的语言、也许不同的架构来修。但我觉得它解决不了一切，因为应用会更强大、更吃资源、更大——技术就是这样。也许三四年、五年后，我们又会看到同样的问题，又会用同样的方式去解决。

我现在意识到，也许我们得做点不同的事。这就是为什么配置应该是静态的，不该是动态的。它们应该可预测。事实上，我知道 ESLint 付过这个代价，所以 V9 把配置改成了 flat config。它容易调试。以前他们搞不清是哪个插件在捣乱，因为全是递归，很难调试。于是他们意识到得做点什么。

他们打破了生态。但我觉得那是必须做的事。作为开源维护者，我理解他们从哪儿来、为什么这么做。当然很多用户不高兴。他们犯了错，得修。有些用户不高兴。但长期来看，我觉得会值回来。

Josh：你怎么知道、或者说你怎么判断，强大的用户和全面的内置之间，那条界线该画在哪儿？

Ema：说实话我没有答案。那条线很难画。我觉得也是试错的事。它可以非常可扩展。说实话，我真的不知道。插件系统让你什么都能做。但如果你给得太多，你最终会弄坏东西。你会发现，如果插件系统更紧、功能更少，本可以做很多优化，现在却做不了。

举个例子，ESLint 有很棒的插件系统，插件到处都是。但代价是他们现在没法创新了。ESLint 的力量来自插件系统，但现在他们没法尝试新东西，因为否则所有这些插件可能在不知情的情况下坏掉或退化。那大概就是那条线。你应该给足够的权力取悦开发者和用户，但不要多到让你自己没法创新。

你是程序员。作为程序员，你也想寻找新东西、尝试新东西，我觉得那是我们的热情之一。如果你没法尝试新东西，那还有什么意义？最终就只是做维护。我不知道。会变得无聊。也许这就是你最终去创建新项目、尝试新东西的原因。

Josh：是的，有一种自然循环：项目一旦成功，就会被拖住。我想聊聊很多项目——包括 Rome、Biome 和 Astro——的一个重大新方向：原生速度的代码。你主导了 Rome 从 TypeScript 到 Rust 的转换。首先，为什么是 Rust？对那些还没听过这番热闹的人来说：为什么这么多项目专门转向 Rust，或者至少转向原生？

Ema：为什么是 Rust？我觉得有两个主要原因，也许三个。我们列出来再数。第一，它是一门非常严格的语言。当你有依赖时，弄坏它的风险更小。系统紧到即使有 major 版本，破坏性变更也更少；或者有的话，你在编译期立刻就能抓住。它给了你带很多依赖的安全感，但至少它们不会像在 TypeScript 或 JavaScript 里那样频繁坏掉。你的工具维护负担更小。

第二本质上是速度。Rome 用 TypeScript 时其实很棒，但内存消耗很大。那时 Rome 能打包自己。作为一个二进制，它能打包自己。而在做这件事时，它吃掉大量内存。8GB 内存。不可持续。感觉像碰到了 Node.js 的极限。于是我们决定：好，也许得去别处。你可以试很多优化，但如果你没法真正驾驭内存——是的，JavaScript 有一些垃圾回收工具，但非常非常有限。Rust 作为原生语言，让你管理内存的方式远超 JavaScript。

第三点是跟 WASM 集成有多容易。Rust 有用 wasm-bindgen crate 的原生绑定。把你的 Rust 代码移植到 WASM 非常容易，然后可以发到浏览器，或其他能解释并执行 WASM 的语言。对 playground 这类东西真的很棒。

我觉得这些就是原因。当然，语言类型很强。但 TypeScript 也以另一种方式有类型。那不是问题。Rust 最近因内存安全获得了很多关注。你不必像 C、C++ 或类似语言那样直接打交道，因为 Rust 用借用检查器替你做。适应需要一段时间。但那是语言替你做的事。你不必操心那部分，可以专注于应用。

Josh：听起来很棒。我们时间往前跳一点。Rome 大概是 2021–2022 年那一阵。我们怎么从 Rome 走到 Biome？这两个项目有什么不同？

Ema：对。大概一年半，我们在 Rome 处得很好，做得不错。但最终背后的公司撑不住了，融不到更多钱，只好关掉。事情是，我喜欢这个项目。我是在被雇之前就加入开源项目的。他们也想继续。

即使我离开公司、加入另一家公司之后，我仍在给 Rome 做贡献。其他人加入了。不再只有我一个。最终我们有了一个志愿者团队，我们继续发版。我其实很想换项目的面貌，但那总需要很多工作：logo、名字、网站域名。你不想做那些，真的很烦。但最终我们不得不做，因为 NPM token 过期了。我们没法再在 NPM 上发布新版本了。我们实际上是被迫搬家的。

为什么叫 Biome？当时 Rome 的 CTO James 有个想法：万一我们要改 Rome，就叫它第二罗马——Second Rome，Biome，就是这个点子。我问他：我能用吗？你觉得行吗？他说：当然，去吧。最终 Rome 在十二月倒下，第二年八月我们宣布 Biome 是新的 Rome。

我会说使命稍有变化，因为我们不再聚焦打包器之类。因为我们资源更少，没有专人投入项目。我们现在聚焦格式化器和 linter，因为那是我们已有的。我们不是横向铺开，而是纵向做深。往 linter 和格式化器里塞更多功能。更多语言。仍然是更多 lint 规则、更多格式化能力。但目前我们不聚焦打包器或测试套件之类。我觉得我们对这个状态挺满意。我们仍在做很棒的事。

Josh：好，我们聊聊那些很棒的事。我聊过的大多数用户对格式化和 lint 作为议题并不特别熟悉。他们知道这些东西会整理代码库。也许知道 lint 做更多逻辑，格式化更多是——格式化空白。Biome 在格式化和 linter 方面为用户做什么？

Ema：首先，它想提供与现有工具不同的开发者体验。更好的消息，真正可操作的东西。你有一个错误，Biome 告诉你：好，你应该这样，或者你不该这样。

有些用户确实把 linter 当成"有也不错"。我们还试图教人们怎么做事。我们发过一条针对 JavaScript `.reduce` 的 lint 规则，说：返回累加器时不要用展开运算符。规则告诉你别这么做，因为那是性能问题。

我见过有人以前不知道这个。一旦知道了这条规则，他们就学到了东西。那是使命之一：你有一个会教你东西的 linter。因为正如我前面说的，不是每个人什么都知道。如果我们有机会教你点什么，我觉得我们就做对了。我们在传播知识。所以我们的 lint 规则必须有很高的标准。它们必须告诉你为什么这是一个错误。因为如果你说不出一个错误为何存在，那它就不是错误，是无意义的点。

至于格式化，它想提供比当时已有工具更快的体验。我知道过去用户对 Prettier 的性能有些不满——那时候它是 JavaScript 世界和 Web 世界里唯一广泛使用的格式化器。用 Biome，我们提供非常相似的格式化，但至少更快，尤其在 CI 之类场景。

但我们也想提供一种与其他工具绑定的体验。比如 Biome 知道你的 git ignore 文件，于是直接挂上去，不会格式化你在 git 里忽略的文件。你也可以跟编辑器配置集成。你有编辑器配置，就不必维护一份 biome 配置，直接用你已有的。不只是 lint 和格式化，我们也拥抱其他工具，让 Biome 了解你在用什么，并从中学习。

我们对 Svelte、Vue、Astro、CSS Modules、Tailwind 也在做同样的事。看，Web 开发相当广阔。我们不想把自己限制在一种工具上。我们认为应该真正拥抱很多工具，去了解它们，学到你可能不知道的东西。

Josh：你点到了用 Biome 真正可爱的一点：正如你所说，全在里头。一条命令就能跑格式化和 linter。以你的经验，配置 Biome 比比如五年前配置那些东西简单多少？

Ema：我觉得其实非常好、非常快，因为你不会丢很多时间。我还记得多年前搭 ESLint 和 Prettier 的时候。后来容易了一点。但事实是你得装三四个包，然后还得配置 ESLint 去用 Prettier 的配置或插件——我不记得了。简直是噩梦。当然，花十分钟。但为什么非得这样？你不该在这些工具上花那么多时间。这就是 Biome 存在的原因。一份配置、合理的默认值，意味着你装上依赖就完了。不用再做别的，直接用。如果你不喜欢默认值，好，你可以跑 `biome init` 改默认值，就这样。

而且，你也不必再去格式化被 linter 修好的代码，因为全在里头。Biome 替你做了。它在编辑器里开箱即用。你在 CLI 里得到的，在编辑器里也一样。你什么都不用做。当然可以装扩展，但除此之外，你不必像 Prettier 或 ESLint 那样装两个扩展，不必改任何配置。全在里头。大多数时候开箱即用。看，用户在搭工具上花的时间更少，就可以去做他们想做的编程。因为那才是我们喜欢做的。我们不喜欢搭工具。

Josh：完全同意。再往工具里挖一点。格式化这几年没有显著变化，除了默认值或配置可能不同，架构相当稳定。Lint 这边就不一样了——Biome 做 lint 的方式跟之前的 ESLint 差得相当多。Biome 的 lint 规则跟前辈 ESLint 规则有什么不同？

Ema：好。我们最近在 Biome 里发了一样东西：类型感知规则和项目级规则。我们知道有 typescript-eslint。谢谢你，Josh，为我们带来了这些。借助 TypeScript 的 ESLint 提供了很有用的规则，比如 no-floating-promises 或 no-misused-promises。但我知道这类插件得做一些 ESLint 本身提供不了的事，比如扫描整个项目或整个依赖树。因为这类规则需要理解的不只是你在编辑器里打开的那个文件，还得解析类型、依赖。它们得做大量工作才能运转。那是 ESLint 开箱不提供的，但 Biome 提供。

Biome 在这种情况下，能在真正开始 lint 之前扫描你的整个项目。它能收集一堆信息，好提供强大的洞察，比如 no-import-cycles。它能飞过你项目的整个导入树，理解你是否真的在形成环。它能扫描你的依赖，理解你是否在用 package.json 里没装的依赖。

比如我最近合并的一条 lint 规则，能理解你是否在用一个哪里都没定义的 CSS class。Biome 能扫描整个项目——CSS 文件、JavaScript 文件、Vue 文件，所有文件。它收集所有信息，然后跑那条 lint 规则，检查你的组件、div 或随便什么元素。它读你用的 class，检查它们是否真的在项目某处定义过。

如果没有，它说：哎呀，你在用一个哪里都没定义的 CSS class。它还能展示实际被分析的组件树。这正是 Biome 模块图提供的能力——在某种意义上是语言无关的。它能同时收集多种语言、文件或资产，比如 HTML、CSS、JavaScript 等等。

我为他们做成的事感到非常自豪，因为据我所知，今天我们有的那些工具做不到这个。那就是 Biome 能提供、而现有工具可能缺乏或开箱不提供的东西。

Josh：你已经提到两大特性了：开箱的类型化 lint 规则，以及 Biome 模块图。先聊聊类型化 lint 规则。Biome 里的类型信息是怎么工作的？

Ema：对。在 Biome 里我们试着做得不一样，因为那本质上就是我们做事的方式——提供与你已有的不同的东西，你可以试试。Biome 做的是所谓的类型推断。它实际上尝试收集并推断——如其名——你的代码、JavaScript/TypeScript 文件的类型。

这个项目和努力是由另一位核心贡献者主导的。Vercel 实际上雇佣了那位贡献者来真正交付这个特性。那是一次很棒的社区努力，需要大量资源和时间。但现在我们能发出不需要真正 TypeScript 编译器的 lint 规则。你不必靠 TypeScript 来理解你是否错误地使用了 promise，或者有一个你没 await 的悬空 promise。

它怎么工作？本质上，引擎重度依赖模块图，去收集和读取项目用到的所有文件，以及依赖。不只是项目本身，还有应用涉及的所有库。然后有大量工作去扁平化表达式、函数等等。我不知道所有细节，因为那是另一位核心成员主导的。但我确实修过那儿的几个 bug。因为引擎需要很多工具——不只是模块图，还有语义模型。

就在前几天，我修了一个 bug：Biome 无法推断某个依赖的类型。比如从 Lodash 导入一个函数，它搞不清那是不是 promise。我通过把语义模型接入推断系统修好了。或者说我得以发出另一条叫 noUnnecessaryConditions 的规则，它告诉你：哦，你不需要做这种检查，因为它总是为真。你有一个变量总是为真。它试图推断它何时改变值之类的。最终到了 if 或随便什么地方，它告诉你：哦，没必要做任何检查，因为这个变量从不改变，总是为真。希望这回答了你的问题。

Josh：非常有帮助。你现在又提到另一种图——语义图。语义图和模块图有什么区别？

Ema：它不叫语义图，叫语义模型。模块图本质上只是一种数据结构，检查：好，这个模块、这个文件被另一个文件导入，等等。它非常通用。它告诉你什么导入、什么导出。就这样，没有别的。

语义模型实际上更专门。它不知道其他文件，只知道一个文件。而且它非常针对那种文件。在 JavaScript 里，它专门理解文件内部的各种作用域。你有 GlobalScope，函数里的作用域，然后箭头函数没有自己的作用域，类有不同的作用域。这就是语义模型做的事。比如它还检查一个绑定是否被导出。它做非常专门的事。

对 CSS 来说，比如它专注于计算你 class 的优先级。如你所见，它跟你所渲染语言的隐含语义绑得很紧。肯定还会有，比如 GraphQL 的语义模型。我不懂那门语言。其他维护者比我更有专长，但我知道他们会用它、会创建它，好提供专门的规则。模块图只是你所有文件的一大堆数据。基本上是一棵树，有枝有叶。你有边——它们怎么彼此连接。大多像一张蛛网。你得在里面导航，才能收集你需要的信息。

Josh：在原生速度的代码里写 lint 规则的一个困难是：许多最终用户并不是原生速度的开发者。Biome 在做什么来解决这种开发者互操作的困难？

Ema：嗯，正如我们提到的，Biome 有一套插件系统来试图弥合差距——基于一种叫 GritQL 的 DSL 的插件系统。经过很多讨论之后，一段时间前选它当了赢家。我们知道我们做不完所有事。有些需求是项目特有的，属于你的架构、你的雇主、你的代码库。那就是我们认为插件真正有用的地方。因为还有你的敏感数据之类。

你有这种强大的 DSL，Biome 能解释它，它有自己的运行时。用这些插件，用户能检查代码。顺便说一下：直到现在，这些插件还不能提供代码修复。到现在为止，规则就是：这是诊断，这是错误，就这样。我们现在有一个 PR，能真正提供代码修复。大概在下一个 minor 里，用户就能创建能自动修复代码库里可能问题的 lint 规则了。

这其实打了我自己"插件不好"的那个点。但我觉得这种情况下它们其实是合理的。因为工具不可能什么都知道，也不应该知道。我不该知道你代码库的那些怪癖，因为那是敏感数据。那就是插件说得通的地方。你借力工具——Biome、ESLint、Oxc，随便什么——然后针对你代码库、针对你的需求去应用，因为它们属于你的项目。

Josh：听起来你可以把 lint 规则的代码修复当成一种 codemod 工具来用。

Ema：对，完全正确。

Josh：很高兴听到这个。真的很酷。已经有 Biome search 命令了。光看 biomejs.dev 上 GritQL 的参考页，好像用不多的语法就能做很强大的匹配。你看到很多开发者上手并用它了吗？

Josh：太好了。你提到的一个有意思的点是编辑器支持。能告诉我们的听众，LSP 是什么、在这个上下文里意味着什么吗？

Ema：当然。LSP 是 Language Server Protocol，语言服务器协议。如缩写所说，它是一种协议，用来创建能在所有编辑器客户端里工作的编辑器服务器。如今绝大多数编辑器客户端都支持这个协议。所以 VS Code、Zed、WebStorm，以及所有 JetBrains IDE、Vim、Helix——它们现在都支持 LSP。这其实相当强大，因为我们只需要在一个地方开发服务器，DX 在本质上所有编辑器里都一样。

Biome 的使命之一也是聚焦 LSP。提供一体化体验，意味着我们在一个地方实现业务逻辑，然后你在 CLI、LSP、playground、任何客户端里得到同样的观感。因为 Biome 本质上是一个服务器，你有多个客户端。我们对诊断就是这么做的。你在 CLI 里看到的，跟编辑器里看到的是一样的。Biome 潜在能做、而其他工具做不到的一件事，是借力模块图实现 go-to 之类的东西。你有一个函数，想知道它在哪儿定义。你 Cmd+点击，它带你去定义处。那是 Biome 潜在能做的事。

Biome 有无穷的可能性，因为一切都是中心化的。我们拥有整条栈，我们拥有信息。但仍然需要时间。我在搭整套基础设施。我有很多想法，只是需要时间去实现。现在有了这些 AI agent，我能更快做事，因为它们写代码，我审。希望这回答了你的问题。
