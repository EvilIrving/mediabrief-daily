https://overreacted.io/npm-audit-broken-by-design/

安全很重要。没有人愿意站出来主张"少一点安全"。所以没有人愿意把话说出口。但总得有人说。

那就我来说吧。

**`npm audit` 的工作方式是坏的。把它作为每次 `npm install` 之后的默认行为推出，这个决定仓促、欠考虑，而且对前端工具链来说完全不合适。**

你听过"狼来了"（[the boy who cried wolf](https://en.wikipedia.org/wiki/The_Boy_Who_Cried_Wolf)）的故事吗？剧透一下：狼把羊吃了。如果我们不想让自己的羊被吃掉，就需要更好的工具。

时至今日，`npm audit` 已经成了整个 npm 生态的污点。修复它的最佳时机，是把它设为默认之前。次佳时机，就是现在。

在这篇文章里，我会简要说明它是怎么工作的、为什么是坏的，以及我希望看到哪些改变。

## [npm audit 是怎么工作的？](https://overreacted.io/npm-audit-broken-by-design/#how-does-npm-audit-work)

_如果你已经知道它的原理，可以[直接跳过](https://overreacted.io/npm-audit-broken-by-design/#why-is-npm-audit-broken)。_

你的 Node.js 应用有一棵依赖树。它可能长这样：

```
your-app
  - view-library@1.0.0
  - design-system@1.0.0
  - model-layer@1.0.0
    - database-layer@1.0.0
      - network-utility@1.0.0
```

很可能，它比这深得多。

现在假设在 `network-utility@1.0.0` 中发现了一个漏洞：

```
your-app
  - view-library@1.0.0
  - design-system@1.0.0
  - model-layer@1.0.0
    - database-layer@1.0.0
      - network-utility@1.0.0 (Vulnerable!)
```

这个漏洞会被发布到一个专门的注册表里，下次你运行 `npm audit` 时 `npm` 就会去访问它。从 npm v6 开始，每次 `npm install` 之后你都会得知这件事：

```
1 vulnerabilities (0 moderate, 1 high)
 
To address issues that do not require attention, run:
  npm audit fix
 
To address all issues (including breaking changes), run:
  npm audit fix --force
```

你运行 `npm audit fix`，npm 会尝试安装包含修复的最新版 `network-utility@1.0.1`。只要 `database-layer` 声明的依赖不是_精确地_锁定在 `network-utility@1.0.0`，而是某个包含 `1.0.1` 的允许范围，这个修复就能"直接生效"，你会得到一个正常运行的应用：

```
your-app
  - view-library@1.0.0
  - design-system@1.0.0
  - model-layer@1.0.0
    - database-layer@1.0.0
      - network-utility@1.0.1 (Fixed!)
```

又或者，`database-layer@1.0.0` 严格依赖 `network-utility@1.0.0`。这种情况下，`database-layer` 的维护者也需要发布一个新版本，允许改用 `network-utility@1.0.1`：

```
your-app
  - view-library@1.0.0
  - design-system@1.0.0
  - model-layer@1.0.0
    - database-layer@1.0.1 (Updated to allow the fix.)
      - network-utility@1.0.1 (Fixed!)
```

最后，如果没有办法平滑地升级这棵树，你可以试试 `npm audit fix --force`。它本来是用在这种情况下的：`database-layer` 不接受新版本的 `network-utility`，_而且_也不发布更新来接受它。于是你相当于自己动手解决问题，可能要冒引入破坏性变更的风险。有这么个选项看起来挺合理。

**这就是 `npm audit` 在理论上应该有的工作方式。**

正如某位智者所说，理论上，理论和实践没有区别。但实践中有。好戏就从这里开始。

## [为什么 npm audit 是坏的？](https://overreacted.io/npm-audit-broken-by-design/#why-is-npm-audit-broken)

我们来看看它在实践中表现如何。我会用 Create React App 来测试。

如果你不熟悉它：它是一个集成外观层，把多个其他工具组合在一起，包括 Babel、webpack、TypeScript、ESLint、PostCSS、Terser 等等。Create React App 接收你的 JavaScript 源代码，把它转换成一个包含静态 HTML+JS+CSS 的文件夹。**值得注意的是，它产出的_不是_一个 Node.js 应用。**

我们来新建一个项目！

`npx create-react-app myapp`
项目刚一创建，我就看到了这个：

```
found 5 vulnerabilities (3 moderate, 2 high)
  run `npm audit fix` to fix them, or `npm audit` for details
```

哦不，看起来很糟！我刚创建的应用就已经有漏洞了！

至少 npm 是这么告诉我的。

我们运行 `npm audit` 看看是怎么回事。

### [第一个"漏洞"](https://overreacted.io/npm-audit-broken-by-design/#first-vulnerability)

这是 `npm audit` 报告的第一个问题：

```
┌───────────────┬──────────────────────────────────────────────────────────────┐
│ Moderate      │ Regular Expression Denial of Service                         │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Package       │ browserslist                                                 │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Patched in    │ >=4.16.5                                                     │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Dependency of │ react-scripts                                                │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Path          │ react-scripts > react-dev-utils > browserslist               │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ More info     │ https://npmjs.com/advisories/1747                            │
└───────────────┴──────────────────────────────────────────────────────────────┘
```

显然，`browserslist` 有漏洞。它是什么、又是怎么被用到的？Create React App 会针对你的目标浏览器生成优化过的 CSS 文件。比如，你可以在 `package.json` 里声明只面向现代浏览器：

```
"browserslist": {
    "production": [
      ">0.2%",
      "not dead",
      "not op_mini all"
    ],
    "development": [
      "last 1 chrome version",
      "last 1 firefox version",
      "last 1 safari version"
    ]
  }
```

这样输出里就不会包含过时的 flexbox hack。由于多个工具都依赖同一种描述目标浏览器的配置格式，Create React App 使用共享的 `browserslist` 包来解析这个配置文件。

那这里的漏洞是什么？["正则表达式拒绝服务"（Regular Expression Denial of Service）](https://owasp.org/www-community/attacks/Regular_expression_Denial_of_Service_-_ReDoS)的意思是，`browserslist` 里有一个正则表达式，在遇到恶意输入时可能变得非常慢。所以攻击者可以精心构造一个特殊的配置字符串，传给 `browserslist` 后让它的速度呈指数级下降。听起来很糟……

等等，什么？！我们回想一下你的应用是怎么工作的。你有一个配置文件，_在你自己的机器上_。你_构建_你的项目。你得到一个装着静态 HTML+CSS+JS 的文件夹。你把它放到静态托管上。你的应用用户**根本不可能**影响你的 `package.json` 配置。**这完全说不通。**如果攻击者已经能访问你的机器、能修改你的配置文件，那你面临的问题可比慢吞吞的正则表达式大多了！

好吧，看来这个"中危""漏洞"在这个项目的语境下既不是中危，也不是漏洞。我们继续。

**结论：在这个语境下，这个"漏洞"是荒谬的。**

### [第二个"漏洞"](https://overreacted.io/npm-audit-broken-by-design/#second-vulnerability)

下面是 `npm audit` 贴心报告的下一个问题：

```
┌───────────────┬──────────────────────────────────────────────────────────────┐
│ Moderate      │ Regular expression denial of service                         │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Package       │ glob-parent                                                  │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Patched in    │ >=5.1.2                                                      │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Dependency of │ react-scripts                                                │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Path          │ react-scripts > webpack-dev-server > chokidar > glob-parent  │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ More info     │ https://npmjs.com/advisories/1751                            │
└───────────────┴──────────────────────────────────────────────────────────────┘
```

我们来看看 `webpack-dev-server > chokidar > glob-parent` 这条依赖链。这里的 `webpack-dev-server` 是一个**仅用于开发**的服务器，用来在**本地**快速提供你的应用。它用 `chokidar` 监视文件系统的变化（比如你在编辑器里保存文件时）。而它又用 [`glob-parent`](https://www.npmjs.com/package/glob-parent) 从文件系统监视模式中提取文件路径的一部分。

不幸的是，`glob-parent` 有漏洞！如果攻击者提供一个精心构造的文件路径，就可能让这个函数的速度呈指数级下降，这会……

等等，什么？！开发服务器在你的电脑上。文件在你的电脑上。文件监视器用的是_你自己_指定的配置。这些逻辑没有一处离开你的电脑。如果攻击者高明到能在你本地开发时登录_你的机器_，他们最不想干的事就是构造特别长的文件路径来拖慢你的开发。他们会去偷你的密钥。**所以这整个威胁是荒谬的。**

看来这个"中危""漏洞"在这个项目的语境下既不是中危，也不是漏洞。

**结论：在这个语境下，这个"漏洞"是荒谬的。**

### [第三个"漏洞"](https://overreacted.io/npm-audit-broken-by-design/#third-vulnerability)

我们来看看这一个：

```
┌───────────────┬──────────────────────────────────────────────────────────────┐
│ Moderate      │ Regular expression denial of service                         │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Package       │ glob-parent                                                  │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Patched in    │ >=5.1.2                                                      │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Dependency of │ react-scripts                                                │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Path          │ react-scripts > webpack > watchpack > watchpack-chokidar2 >  │
│               │ chokidar > glob-parent                                       │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ More info     │ https://npmjs.com/advisories/1751                            │

```

等等，这和上面那个是同一回事，只是依赖路径不同。

**结论：在这个语境下，这个"漏洞"是荒谬的。**

### [第四个"漏洞"](https://overreacted.io/npm-audit-broken-by-design/#fourth-vulnerability)

哎哟，这个看起来真的很严重！**`npm audit` 居然好意思用红色把它显示出来：**

```
┌───────────────┬──────────────────────────────────────────────────────────────┐
│ High          │ Denial of Service                                            │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Package       │ css-what                                                     │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Patched in    │ >=5.0.1                                                      │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Dependency of │ react-scripts                                                │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ Path          │ react-scripts > @svgr/webpack > @svgr/plugin-svgo > svgo >   │
│               │ css-select > css-what                                        │
├───────────────┼──────────────────────────────────────────────────────────────┤
│ More info     │ https://npmjs.com/advisories/1754                            │
└───────────────┴──────────────────────────────────────────────────────────────┘
```

这个"高危"问题是什么？"拒绝服务"。我可不想服务被拒绝！那就太糟了……除非……

我们来看看这个[问题](https://www.npmjs.com/advisories/1754)。显然 [`css-what`](https://www.npmjs.com/package/css-what) 是一个 CSS 选择器解析器，在遇到精心构造的输入时可能变慢。这个解析器被一个从 SVG 文件生成 React 组件的插件使用。

也就是说，如果攻击者控制了我的开发机或者我的源代码，他们会放进去一个特殊的 SVG 文件，里面带有一个精心构造的 CSS 选择器，让我的构建变慢。说得通……

等等，什么？！如果攻击者能修改我应用的源代码，他们多半会直接往里放一个比特币挖矿程序。除非用 SVG 能挖比特币，否则他们为什么要往我的应用里加 SVG 文件？再说一遍，这_完全_说不通。

**结论：在这个语境下，这个"漏洞"是荒谬的。**

"高危"也就这么回事。

### [还要继续吗？](https://overreacted.io/npm-audit-broken-by-design/#shall-we-keep-going)

到目前为止，这个孩子已经喊了五次"狼来了"。其中两次是重复的。其余的，结合这些依赖的实际用法来看，都是荒谬的伪问题。

五次误报倒也不算太糟。

**不幸的是，这样的误报有好几百条。**

这里有[几个](https://github.com/facebook/create-react-app/issues/11053)[典型](https://github.com/facebook/create-react-app/issues/11092)的讨论串，但还有更多[链接在这里](https://github.com/facebook/create-react-app/issues/11174)：

![图 1：许多 GitHub 讨论串的截图](https://imgur.com/ABDK4Ky.png)

**我花了好几个小时，把过去几个月里报给我们的每一个 `npm audit` 问题都看了一遍。对 Create React App 这样的构建工具依赖来说，它们看起来全都是误报。**

当然，这些问题都是可以修的。我们可以放宽一些顶层依赖，不再锁定精确版本（这会让补丁版本里的 bug 更频繁地混进来）。我们可以多发几个版本，只为了走在这场安全表演的前面。

但这是不够的。想象一下，如果你的测试 99% 的时候都因为莫须有的原因失败！这会浪费以"人·十年"计的精力，让所有人都痛苦不堪：

*   **它让初学者痛苦**，因为这是他们在 Node.js 生态中的第一次编程体验。安装 Node.js/npm 本身就已经够让人困惑了（如果你因为某个教程让你这么做而在哪里加了 `sudo`，那就祝你好运吧），而当他们尝试网上的示例、甚至只是创建一个项目时，迎接他们的就是这个。初学者不知道正则表达式_是什么_。他们当然也没有能力判断：当他们用构建工具生成一个静态 HTML+CSS+JS 网站时，正则 DDoS 或原型污染到底值不值得担心。
*   **它让有经验的应用开发者痛苦**，因为他们要么浪费时间去做显然没必要的工作，要么和公司的安全部门斗争，试图解释 `npm audit` 是一个_从设计上就_不适合做真正安全审计的坏工具。是的，它就是在这种状态下被设成了默认。
*   **它让维护者痛苦**，因为他们不能专心修 bug、做改进，而是不得不引入那些根本不可能影响自己项目的假漏洞修复，否则用户就会沮丧、害怕，或者两者兼有。
*   **总有一天，它会让我们的用户痛苦**，因为我们已经训练出了整整一代开发者：他们要么因为警告太多而看不懂，要么干脆_无视_警告，因为警告总是出现，而有经验的开发者每次都（正确地）告诉他们并没有真正的问题。

雪上加霜的是，`npm audit fix`（这个工具建议你使用的命令）还有 bug。我今天运行了 `npm audit fix --force`，它把主依赖**降级**到了一个三年前的版本，而那个版本有着真正的、_实打实的_漏洞。谢谢你啊 npm，干得漂亮。

## [接下来怎么办？](https://overreacted.io/npm-audit-broken-by-design/#what-next)

我不知道怎么解决这个问题。不过这套系统本来也不是我加的，所以我大概也不是解决它的最佳人选。我只知道它坏得一塌糊涂。

我见过几种可能的解决方案。

*   **如果某个依赖不在生产环境运行，就把它移到 `devDependencies`。**这提供了一种方式，声明某个依赖不会出现在生产代码路径中，因此没有相关风险。然而，这个方案有缺陷：
    *   `npm audit` 默认仍然会对开发依赖发出警告。你得_知道_要运行 `npm audit --production` 才能看不到来自开发依赖的警告。知道这么做的人，大概本来就已经不信任它了。这对初学者也没有帮助，对那些安全部门要求审计一切的公司员工也没有帮助。
    *   `npm install` 仍然使用普通 `npm audit` 的信息，所以实际上你每次安装东西时仍然会看到所有误报。
    *   任何安全专家都会告诉你，开发依赖实际上_确实是_攻击途径，而且可能是最危险的途径之一，因为它极难被发现，代码又是在高度信任的假设下运行的。**这正是现状特别糟糕的原因：任何真实的问题，都会被埋在几十个伪问题底下，而 `npm audit` 正在训练人们和维护者去忽略这些问题。**这种事发生只是时间问题。

*   **发布时把所有依赖内联进去。**我越来越多地看到和 Create React App 类似的包这么做。比如 [Vite](https://unpkg.com/browse/vite@2.4.1/dist/node/) 和 [Next.js](https://unpkg.com/browse/next@11.0.1/dist/) 都直接把依赖打包进自己的包里，而不是依赖 npm 的 `node_modules` 机制。从维护者的角度看，[好处显而易见](https://github.com/vitejs/vite/blob/main/CONTRIBUTING.md#notes-on-dependencies)：启动更快、下载更小，还有一个不错的额外好处——用户不会再报来那些假漏洞。这是钻系统空子的巧妙办法，但我担心 npm 正在给整个生态制造怎样的激励。内联依赖在某种程度上违背了 npm 存在的全部意义。
*   **提供某种方式来反驳漏洞报告。**当然，Node.js 和 npm 并非完全不知道这个问题。不同的人提出过不同的修复建议。比如，有一个[提案](https://github.com/npm/rfcs/pull/18)，提供一种手动处理 audit 警告的方式，让它们不再显示。然而，这仍然把负担压在应用的使用者身上，而他们不一定了解依赖树深处的哪些漏洞是真的、哪些是假的。我也有一个[提案](https://twitter.com/dan_abramov/status/1412380714012594178)：我需要一种方式，向我的用户标明某个漏洞不可能影响到他们。如果你不信任我的判断，为什么还要在你的电脑上运行我的代码？我也很乐意讨论其他方案。

问题的根源在于，npm 加入了一个默认行为，它在很多情况下会导致 99% 以上的误报率，制造出极其令人困惑的第一次编程体验，让人们和安全部门斗争，让维护者再也不想和 Node.js 生态打交道，并且总有一天会让真正严重的漏洞在无人察觉的情况下溜进来。

必须做点什么了。

与此同时，我打算从今往后，把我看到的所有来自 `npm audit`、但并不对应可能影响项目的_真实_漏洞的 GitHub issue 都关掉。我也邀请其他维护者采取同样的策略。这会让我们的用户感到沮丧，但问题的核心在 npm。这场安全表演我受够了。Node.js/npm 完全有能力解决这个问题。我正在和他们联系，希望看到这个问题被优先处理。

今天，`npm audit` 从设计上就是坏的。

初学者、有经验的开发者、维护者、安全部门，以及最重要的——我们的用户——都值得更好的。
