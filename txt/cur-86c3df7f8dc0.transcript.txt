Chris：好的。我的论点是：大型的客户端 UI 库已经真正占据了统治地位。过去几年我们开始看到一些反弹，因为——我是会嘲讽 React，但它确实把自己要做的事情做得特别好。只是我认为它可能带来了很多我们并不总是认真评估的权衡，比如加载所有那些客户端 JavaScript 带来的性能影响，以及由此引入的脆弱性。

所以在过去一年左右，我们看到人们尝试用几种不同的方式来解决这些短板。一类是做同样事情的更小版本。比如 SolidJS，采用和 React 类似的模式，但体积小得多。Preact 可能是这一类里最流行的，它几乎一字不差地照搬了 React 的 API，但体积只有十分之一。而且正因为如此，加上底层抽象更少，它渲染 UI 实际上也快得多……所以在很多方面，它是比 React 更好的 React。这股潮流火到什么程度呢：Vue 的作者尤雨溪（Evan You）受到了 Alpine.js 的启发——Alpine.js 的定位就像是 Vue 世界里的 Preact——于是他自己做了一个迷你版 Vue，叫 petite-vue，只有 6KB 左右，是一个面向更窄使用场景的衍生项目。

这是一方面。另一方面，有些人一直试图把服务端渲染硬塞进这些 UI 库里。比如 Next.js，或者 Vue 对应的 Nuxt。它们挺有意思，但它们做的是一种混合方案：先渲染出初始视图，然后照样把整个库都发给浏览器，再在浏览器里做某种"交接"。所以你消除了一个问题，但并没有真正解决核心问题——JS 太多了。我作为一个以教 JS 为生的人说这话：我们用的 JS 实在太多了。所以我们一直在这个想法周围打转。然后我想说，在过去一年里，我们看到思路发生了转变：从"如果让 JavaScript 实时运行、做所有事情会怎样"，转向"如果我们构建一些编译器，让你按自己喜欢的方式写代码，但把那些代码全部剔除，最终输出更像老式 DOM 操作的东西，会怎样？"——后者出于很多原因有很多好处。

我所知道的这一类里最早的是 Svelte。你可以用基于状态的 UI 方式来编写代码，然后把它编译成 HTML 文件，里面会混入一些辅助函数，但输出的 JavaScript 通常比你写的还少，而且更接近你手写老式 DOM 操作时会写出的代码。所以如果你的 UI 只有一个元素发生变化，它不会为了渲染那一处变化而去对比整个 UI，而是有针对性地更新那个元素的文本，或者切换某个 div 的 class，或者做其他需要做的事。这样你仍然保留了很多人似乎喜欢的那种编写体验，但对使用你产品的用户来说，开销和性能损耗都小了。

同一类里比较新的还有 Astro，它的工作方式和 Svelte 很像，但走得更远，也更"疯"：它的思路是"如果你可以把所有喜欢的库都带过来，混在一起，然后只输出你需要的代码，会怎样？"在一个 Astro 项目里，你可以引入一个你喜欢的 React 组件，再加几个你喜欢的 Vue 组件，再拿几个 Svelte 文件，统统混在一起，它会输出以静态 HTML 为主、按需点缀一些 JavaScript 的结果，这真的非常疯狂。

Netlify 开发者关系团队的 Jason Lengstorf 做过一个实验：他把一个 Next 项目移植到 Astro，几乎用的是完全相同的代码，只需要做几处小调整让它适配。结果 Astro 编译出的代码——我记得是少用了 90% 的 JavaScript，加载和运行速度快了三倍，而他那边几乎没改什么。

所以我现在的处境是：我不知道这些工具本身就是下一个大东西，还是通往真正下一个大东西的过渡。给点背景——KBall，你在这行也挺久了……你还记得——你没我老，你还有头发，挺好的……

KBall：那我想深入聊聊这个转变：JavaScript 作为——你说的是服务端语言；我几乎更愿意把它理解为"我们用它来描述应用，然后它以某种方式被编译掉"。
