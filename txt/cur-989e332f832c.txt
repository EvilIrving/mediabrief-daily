驾驭工程：在智能体优先的世界里用好 Codex Harness engineering: leveraging Codex in an agent-first world ｜ OpenAI News ｜ 文章 ｜ https://openai.com/index/harness-engineering

这是 OpenAI 一个内部团队在 2026 年 2 月发布的实验报告：五个月里，他们做出一款有内部日活用户和外部 alpha 测试者的产品，手写代码为零。应用逻辑、测试、CI、文档、可观测性和内部工具全部由 Codex 编写，用时约为手写的十分之一。仓库 2025 年 8 月下旬从空仓库起步，脚手架和最初的 AGENTS.md 都由 Codex CLI 配合 GPT-5 生成。五个月后代码量约一百万行，合并了约 1500 个 PR。起初三名工程师平均每人每天 3.5 个 PR，团队扩到七人后吞吐量还在上升。口号是"人类掌舵，智能体执行"，文章要讲的是工程师的工作因此变成了什么。

早期进展慢，原因不是模型不行，而是环境没有定义清楚。于是工程师的工作变成"赋能智能体"：把目标拆成小构建块，遇到失败不叫它"再努力"，而是追问缺了什么能力、怎样让这种能力对智能体可读、可强制执行。PR 由 Codex 自审，再请其他智能体评审，然后循环迭代到所有评审者满意，类似 Geoffrey Huntley 提出的"Ralph Wiggum 循环"；人类评审变成可选。瓶颈随后转到人工 QA，他们就让应用对智能体"可见"：每个 git worktree 都能独立启动一个实例，接入 Chrome DevTools 协议，用于 DOM 快照、截图和页面导航；再为每个 worktree 配一套临时的可观测性栈，智能体用 LogQL、PromQL 查日志和指标，"启动低于 800 毫秒"这类要求因此可以直接交给它。单次运行常常持续六小时以上。

上下文管理方面，教训是"给地图，不给千页手册"。一个巨大的 AGENTS.md 会挤占上下文、让重点失焦、迅速过时，而且无法校验。所以 AGENTS.md 缩到约 100 行，只当目录用；真正的知识放在结构化的 docs/ 里，作为记录系统，包括设计文档、架构地图、各领域质量评分，执行计划和技术债务也提交进仓库。linter 和 CI 负责校验文档的新鲜度和链接，还有一个"文档园丁"智能体定期开 PR 修正过时内容。核心观点是：智能体看不到的东西就等于不存在，Slack 讨论、Google Docs 和人脑里的知识都要搬进仓库。这也影响了技术选型：偏好"无聊"、稳定、训练数据里常见的技术，有时宁可让智能体自己写一个带并发控制的 map 辅助函数，也不引入 p-limit 这样不透明的依赖。

架构上，他们强制规定不变量，但不微观管理实现方式。例如要求在边界处解析数据，但不指定用什么库（模型自己偏爱 Zod）。每个业务领域按 Types → Config → Repo → Service → Runtime → UI 单向分层，横切关注点只能经由 Providers 接口进入，全部用 Codex 写的自定义 linter 和结构测试来强制执行，lint 报错信息里直接写好修复说明。这种通常要到几百名工程师规模才会做的架构，在这里成了起步前提，因为规则一旦编码，就会同时作用于所有地方。代码风格不必合人类口味，只要正确、可维护、后续智能体读得懂就行。高吞吐也改变了合并哲学：阻塞关卡尽量少，偶发失败的测试靠重跑解决，因为纠错便宜、等待昂贵；作者承认在低吞吐环境里这样做并不负责任。

如今只需一个提示，Codex 就能复现 bug、录下故障视频、修复、驱动应用验证、再录一段修复后的视频、开 PR、回应反馈、修好构建，然后合并，只有需要判断时才找人。但作者提醒，这依赖这个仓库的特定投入，不能想当然地推广。新问题是熵增：智能体会复制仓库里已有的坏模式。团队一度每周五花 20% 的时间清理"AI 垃圾"，后来改为把"黄金原则"写进仓库，例如优先使用共享工具包、不 YOLO 式地猜测数据结构，再由后台 Codex 任务定期扫描偏差、开小型重构 PR 自动合并，像垃圾回收一样持续偿还技术债。

结论偏审慎乐观：纪律依然需要，只是从写代码转移到了搭脚手架、设计反馈回路和控制系统上。至于架构一致性能否撑过数年，以及模型变强后这套体系如何演变，作者坦言还不知道。
