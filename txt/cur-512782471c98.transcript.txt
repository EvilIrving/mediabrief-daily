npm audit：设计上就是坏的

2021 年 7 月 7 日

安全很重要。没人想当那个主张"少一点安全"的人，所以没人愿意说出来。但总得有人说。

那就我来说吧。

npm audit 的工作方式是坏的。把它作为每次 npm install 之后的默认行为推出，是仓促的、欠考虑的，对前端工具链来说也是不合格的。

你听过"狼来了"的故事吗？剧透一下：最后狼把羊吃了。如果不想让羊被吃掉，我们就需要更好的工具。

时至今日，npm audit 是整个 npm 生态的一个污点。修复它的最佳时机是把它设为默认之前，其次就是现在。

在这篇文章里，我会简要说明它是怎么工作的、为什么是坏的，以及我希望看到哪些改变。

注：这篇文章的语气带着批评，也有些尖刻。我理解维护 Node.js、npm 这样的大型项目极其困难，错误也可能要过一段时间才会显现。我只是对这种局面感到沮丧，而不是对相关的人。我保留了尖刻的语气，是因为这些年来我的沮丧与日俱增，我不想假装情况没有它实际上那么糟。我最沮丧的是看到那么多人把这当作自己的第一次编程体验，还有那么多人因为无关的警告而无法部署自己的改动。我很高兴这个问题正在被考虑，我也会尽力为提出的解决方案提供意见！💜

npm audit 是怎么工作的？

如果你已经知道，可以跳过这一节。

你的 Node.js 应用有一棵依赖树，可能长这样（原文此处为示意图）。多半还要深得多。

现在假设在 network-utility@1.0.0 中发现了一个漏洞。

它会被发布到一个专门的登记库里，下次你运行 npm audit 时 npm 就会读取它。从 npm v6 起，每次 npm install 之后你都会看到这个提示。

你运行 npm audit fix，npm 会尝试安装包含修复的最新版 network-utility@1.0.1。只要 database-layer 声明的依赖不是精确的 network-utility@1.0.0，而是某个包含 1.0.1 的允许范围，修复就"直接生效"，你得到一个能正常运行的应用。

另一种情况是，database-layer@1.0.0 严格依赖 network-utility@1.0.0。这时 database-layer 的维护者也需要发布一个新版本，允许使用 network-utility@1.0.1。

最后，如果没法平稳地升级依赖树，你可以试试 npm audit fix --force。它的用途是：database-layer 既不接受新版 network-utility，也不发布更新来接受它，于是你自己动手解决，冒着引入破坏性变更的风险。这看起来是个合理的选项。

理论上，npm audit 就是这样工作的。

正如某位智者所说，理论上理论和实践没有区别，但实践中有。好戏就从这里开始。

为什么说 npm audit 是坏的？

我们来看看它在实践中怎么运作。我用 Create React App 来测试。

如果你不熟悉它：它是一个集成外壳，组合了多个工具，包括 Babel、webpack、TypeScript、ESLint、PostCSS、Terser 等。Create React App 接收你的 JavaScript 源码，把它转换成一个静态的 HTML+JS+CSS 文件夹。值得注意的是，它产出的并不是一个 Node.js 应用。

我们来新建一个项目！

项目刚一创建，我就看到了这个提示。

糟糕，看起来很严重！我刚建的应用就已经有漏洞了！

至少 npm 是这么告诉我的。

我们运行 npm audit 看看怎么回事。

第一个"漏洞"

npm audit 报告的第一个问题是：browserslist 有漏洞。这是什么，它是怎么被用的？Create React App 会针对你所支持的浏览器生成优化过的 CSS 文件。比如，你可以在 package.json 里声明只支持现代浏览器，这样输出里就不会包含过时的 flexbox 兼容写法。由于多个工具都依赖同一种描述目标浏览器的配置格式，Create React App 用共享的 browserslist 包来解析这个配置文件。

那这里的漏洞是什么？"正则表达式拒绝服务"（ReDoS），意思是 browserslist 里有一个正则表达式，遇到恶意输入时可能变得非常慢。于是攻击者可以构造一个特殊的配置字符串，传给 browserslist 后让它呈指数级变慢。听起来很糟……

等等，什么？！我们回想一下你的应用是怎么工作的。你的机器上有一个配置文件。你构建项目，在一个文件夹里得到静态的 HTML+CSS+JS，然后把它放到静态托管上。你的应用用户根本不可能影响你的 package.json 配置。这完全说不通。如果攻击者已经能访问你的机器、修改你的配置文件，你面临的问题可比慢吞吞的正则表达式大多了！

好吧，看来这个"中危""漏洞"在项目的语境下既不是中危，也不是漏洞。我们继续。

结论：在这个语境下，这个"漏洞"很荒谬。

第二个"漏洞"

npm audit 很贴心地报告的下一个问题，是 webpack-dev-server > chokidar > glob-parent 这条依赖链。webpack-dev-server 是一个只在开发时使用的服务器，用来在本地快速提供你的应用。它用 chokidar 监视文件系统的变化（比如你在编辑器里保存文件时），又用 glob-parent 从文件监视模式中提取文件系统路径的一部分。

不幸的是，glob-parent 有漏洞！如果攻击者提供一个特制的文件路径，这个函数可能会呈指数级变慢，这会……

等等，什么？！开发服务器在你的电脑上，文件在你的电脑上，文件监视器用的是你自己指定的配置。这些逻辑没有一样离开过你的电脑。如果攻击者高明到能在你本地开发时登录你的机器，他最不想做的事就是构造特别长的文件路径来拖慢你的开发。他会去偷你的密钥。所以这整个威胁都是荒谬的。

看来这个"中危""漏洞"在项目语境下既不是中危，也不是漏洞。

结论：在这个语境下，这个"漏洞"很荒谬。

第四个"漏洞"

哎哟，这个看起来真的很严重！npm audit 居然用红色显示它。

这个"高危"问题是什么？"拒绝服务"。我可不想服务被拒绝！那就太糟了……除非……

我们看看这个问题。显然，CSS 选择器解析器 css-what 遇到特制的输入时可能会很慢。这个解析器被一个从 SVG 文件生成 React 组件的插件使用。

所以这意味着：如果攻击者控制了我的开发机或者我的源代码，他们放进一个特殊的 SVG 文件，里面有一个特制的 CSS 选择器，让我的构建变慢。说得通……

等等，什么？！如果攻击者能修改我应用的源代码，他们多半会直接往里面塞一个比特币挖矿程序。他们为什么要往我的应用里加 SVG 文件，除非 SVG 能挖比特币？同样，这完全说不通。

结论：在这个语境下，这个"漏洞"很荒谬。

还要继续吗？

到目前为止，"狼来了"已经喊了五次。其中两次是重复的，其余的在这些依赖的实际用法下都是荒谬的非问题。

五次误报也不算太糟。

不幸的是，这样的误报有几百个。

这里列了几个典型的讨论帖，从这里还能链接到更多。

我花了几个小时，查看过去几个月里报告给我们的每一个 npm audit 问题，在 Create React App 这种构建工具依赖的语境下，它们全都像是误报。

当然，这些都是可以修的。我们可以放宽一些顶层依赖，不再锁定精确版本（这会让补丁版本里的 bug 更常溜进来）。我们可以为了跟上这场安全表演而发布更多版本。

但这远远不够。想象一下，如果你的测试 99% 的时候都因为莫须有的原因失败！这会浪费人类几十年的工作量，让所有人都很痛苦：

- 它让初学者痛苦，因为这是他们在 Node.js 生态里的第一次编程体验。好像安装 Node.js 和 npm 还不够让人困惑似的（如果你照着教程在某处加了 sudo，那就祝你好运了），他们在网上试例子、甚至只是创建一个项目时，迎接他们的就是这个。初学者不知道什么是正则表达式，当然也不具备判断能力：用一个构建工具生成静态 HTML+CSS+JS 网站时，正则拒绝服务或原型污染到底值不值得担心。
- 它让有经验的应用开发者痛苦，因为他们要么得浪费时间做明显不必要的工作，要么得和公司的安全部门争论，解释 npm audit 从设计上就是一个不适合做真正安全审计的坏工具。是的，不知怎么的，它就以这种状态被设成了默认。
- 它让维护者痛苦，因为他们不能专心修 bug、做改进，而是不得不引入那些根本不可能影响自己项目的虚假漏洞修复，否则用户就会感到沮丧、害怕，或两者兼有。
- 总有一天，它会让我们的用户痛苦，因为我们训练了整整一代开发者：要么被铺天盖地的警告淹没而看不懂它们，要么干脆无视它们，因为警告总是在那儿，而有经验的开发者（正确地）告诉他们每一次都没有真正的问题。

雪上加霜的是，这个工具建议使用的 npm audit fix 还有 bug。我今天运行了 npm audit fix --force，它把主依赖降级到了一个三年前的版本，而那个版本有真正的漏洞。谢谢你，npm，干得真好。

接下来怎么办？

我不知道该怎么解决这个问题。不过这套系统本来就不是我加的，所以我大概也不是解决它的最佳人选。我只知道它坏得一塌糊涂。

我见过几种可能的解决方案。

- 如果某个依赖不在生产环境运行，就把它移到 devDependencies。这提供了一种方式来声明某个依赖不在生产代码路径中使用，因此没有相关风险。但这个方案有缺陷：
  - npm audit 默认仍会对开发依赖发出警告。你得知道要运行 npm audit --production 才能不看到开发依赖的警告。知道这么做的人，大概早就不信任它了。这对初学者也没有帮助，对那些安全部门要求审计一切的公司员工也没有帮助。
  - npm install 仍然使用普通 npm audit 的信息，所以每次安装东西时，你实际上还是会看到所有误报。
  - 任何安全专业人士都会告诉你，开发依赖其实是一个攻击途径，而且可能是最危险的之一，因为它很难被发现，代码又是在高度信任的假设下运行的。这正是情况格外糟糕的原因：任何真正的问题都会被埋在几十个非问题之下，而 npm audit 正在训练大家和维护者无视它们。这种事迟早会发生。
- 发布时把所有依赖内联进来。我越来越多地看到和 Create React App 类似的包这么做。比如 Vite 和 Next.js 都直接把依赖打包进自己的包里，而不是依赖 npm 的 node_modules 机制。从维护者的角度看，好处显而易见：启动更快，下载更小，还有一个不错的附带好处：用户不会再报来虚假的漏洞。这是钻系统空子的巧妙办法，但我担心 npm 正在给整个生态制造怎样的激励。内联依赖有点违背 npm 存在的全部意义。
- 提供某种对漏洞报告提出反驳的方式。Node.js 和 npm 当然并非对这个问题一无所知，不同的人针对它提出过不同的建议。比如，有一个提案是允许手动处理 audit 警告，让它们不再显示。但这仍然把负担压在应用使用者身上，而他们未必了解依赖树深处哪些漏洞是真的、哪些是假的。我也有一个提议：我需要一种方式，向我的用户标明某个漏洞不可能影响到他们。如果你不信任我的判断，那你为什么要在自己电脑上运行我的代码？我也很乐意讨论其他方案。

问题的根源在于，npm 加入了一个默认行为，而它在许多情况下会导致 99% 以上的误报率，造成极其令人困惑的第一次编程体验，让人们和安全部门争执，让维护者再也不想碰 Node.js 生态，并且在某个时候会让真正严重的漏洞悄无声息地溜进来。

必须做点什么了。

在此期间，我打算关闭今后看到的所有来自 npm audit、且不对应能影响项目的真实漏洞的 GitHub issue。我邀请其他维护者也采取同样的做法。这会让我们的用户感到沮丧，但问题的核心在 npm。我受够了这场安全表演。Node.js 和 npm 完全有能力解决这个问题。我正在和他们沟通，希望看到这个问题被优先处理。

今天，npm audit 从设计上就是坏的。

初学者、有经验的开发者、维护者、安全部门，以及最重要的，我们的用户，都值得更好的东西。
