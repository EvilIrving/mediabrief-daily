## Flexbox 简介

CSS 由许多不同的布局算法组成，官方称为“布局模式”。每种布局模式都是 CSS 里一门独立的小型子语言。默认布局模式是 *Flow 布局*，但我们可以通过修改父容器的 `display` 属性来选择 Flexbox：

（交互演示：切换 display 值，查看“Hello to the world”四个元素的排列与主轴）

当我们把 `display` 改为 `flex`，就创建了一个“flex 格式化上下文”。这意味着默认情况下，所有子元素都会按照 Flexbox 布局算法来定位。

**每种布局算法都是为解决特定问题而设计的。**默认的“Flow”布局用于创建数字文档；它本质上就是 *Microsoft Word* 的布局算法。（配图：Word 里那个乐于助人的回形针助手 Clippy。）标题和段落作为块纵向堆叠，而文字、链接和图片之类的东西则不显眼地待在这些块里面。

**那么，Flexbox 解决什么问题？**Flexbox 的核心是把一组元素排成一行或一列，并让我们对这些元素的分布和对齐拥有*多到离谱*的控制力。顾名思义，Flexbox 的核心是*灵活性*。我们可以控制元素是放大还是缩小、多余空间如何分配，等等。

## Flex 方向

如前所述，Flexbox 的核心是控制元素在一行或一列中的分布。默认情况下，元素会在一行中并排排列，但我们可以用 `flex-direction` 属性切换成一列：

（交互演示：切换 flex-direction，显示主轴）

使用 `flex-direction: row` 时，*主轴*水平延伸，从左到右。切换到 `flex-direction: column` 时，主轴垂直延伸，从上到下。

**在 Flexbox 中，一切都以主轴为基础。**算法并不关心垂直还是水平，甚至不关心行还是列。所有规则都围绕这条主轴，以及与之垂直的*交叉轴*来构建。

**这非常酷。**学会了 Flexbox 的规则，我们就能在水平布局和垂直布局之间无缝切换。所有规则都会自动适应。这是 Flexbox 布局模式独有的特性。

默认情况下，子元素会按照以下 2 条规则定位：

1. **主轴：**子元素会挤在容器的*起点*。
2. **交叉轴：**子元素会拉伸以填满整个容器。

下面是这些规则的简单图示：

（图示：row 与 column 两种方向下的默认排列）

在 Flexbox 中，由我们决定主轴是水平还是垂直延伸。这是所有 Flexbox 计算所依附的根基。

## 对齐

我们可以用 `justify-content` 属性改变子元素沿主轴的分布方式：

（交互演示：调整 flex-direction 与 justify-content）

说到主轴，我们一般不会考虑对齐单个子元素，而是关注*整组的分布*。

我们可以把所有元素挤在某个特定位置（用 `flex-start`、`center` 和 `flex-end`），也可以把它们分散开（用 `space-between`、`space-around` 和 `space-evenly`）。

**对于交叉轴，情况有点不同。**我们使用 `align-items` 属性：

很有意思……`align-items` 拥有和 `justify-content` *一部分*相同的选项，但两者并不完全重合。

它们为什么不共享相同的选项？我们很快就会解开这个谜，但首先我还要介绍另一个对齐属性：**`align-self`**。

与 `justify-content` 和 `align-items` 不同，`align-self` 应用在*子元素*上，而不是容器上。它让我们可以改变某个特定子元素在交叉轴上的对齐方式：

（交互演示：调整单个子元素的 align-self）

`align-self` 拥有和 `align-items` 完全相同的取值。事实上，**它们改变的是完全相同的东西。**`align-items` 是*语法糖*，一种方便的简写，自动为所有子元素一次性设置对齐方式。

没有 `justify-self`。（至少在 Flexbox 中没有。这个属性在 Grid 布局模式中有实现。）要理解为什么没有，我们需要更深入地挖掘 Flexbox 算法。

### content 与 items

根据目前所学，Flexbox 可能显得相当随意。为什么是 `justify-content` 和 `align-items`，而不是 `justify-items` 或 `align-content`？

再说了，为什么有 `align-self`，却没有 `justify-self`？？

**这些问题触及了 Flexbox 最重要、也最常被误解的一点。**为了帮助解释，我想用一个比喻。

在 Flexbox 中，元素沿主轴分布。默认情况下，它们整齐地并排排列。我可以画一条水平直线，把*所有*子元素串起来，就像一串烤肉（也就是烤串、希腊烤肉 souvlaki、土耳其烤肉 shish kebab）：

（插图：一根木签上水平串着 3 块肉，木签标注“主轴”）

但交叉轴就不同了。一条垂直直线永远只会穿过*一个*子元素。

它不太像烤肉串，更像一组一口大小的热狗/维也纳小香肠：

（插图：3 根独立的鸡尾酒小香肠，每根都被自己的牙签垂直穿过，牙签标注“交叉轴”）

这里有个显著的区别。对于鸡尾酒小香肠，每个元素都可以沿着自己的牙签移动，*而不会干扰*其他元素：

（交互演示：拖动单根小香肠上下移动）

相比之下，由于主轴把每个兄弟元素都串在了一起，单个元素*无法*沿着签子移动而不撞到兄弟元素！**试着左右拖动中间那块：**

**这就是主轴与交叉轴的根本区别。**当我们谈论*交叉*轴上的对齐时，每个元素都可以随心所欲。而在*主*轴上，我们只能考虑如何分配*整组*元素。

**这就是为什么没有 `justify-self`。**中间那块设置 `justify-self: flex-start` 意味着什么？那里已经有另一块了！

有了这些背景，我们来给讨论过的 4 个术语下个准确的定义：

* `justify`——沿*主轴*定位某物。
* `align`——沿*交叉轴*定位某物。
* `content`——一组可以被分配的“东西”。
* `items`——可以单独定位的单个元素。

**所以：**我们用 `justify-content` 控制整组沿主轴的分布，用 `align-items` 沿交叉轴单独定位每个元素。这是我们用 Flexbox 管理布局的两个主要属性。

没有 `justify-items` 的原因和没有 `justify-self` 一样：在主轴上，*我们必须把元素看作一个整体*，看作可以被分配的内容。

那 `align-content` 呢？其实，Flexbox 中*确实*有它！我们稍后讨论 `flex-wrap` 属性时会讲到。

## 假设尺寸

我们来谈谈我对 Flexbox 最让人大开眼界的领悟之一。

假设我有如下 CSS：

```
.item {
  width: 2000px;
}
```

一个理智的人看到这段代码可能会说：“好吧，那我们会得到一个 2000 像素宽的元素。”*但这总是成立吗？*

我们来测试一下：

（代码演示）

```
<style>
  .flex-wrapper {
    display: flex;
  }
  .item {
    width: 2000px;
  }
</style>

<div class="item"></div>

<div class="flex-wrapper">
  <div class="item"></div>
</div>
```

很有意思，对吧？

**两个元素应用了完全相同的 CSS。**它们都是 `width: 2000px`。然而，第一个元素比第二个宽得多！

区别在于*布局模式*。第一个元素用 Flow 布局渲染，而在 Flow 布局中，`width` 是一个*硬约束*。当我们设置 `width: 2000px`，就会得到一个 2000 像素宽的元素，即使它不得不像那个以破墙而出闻名的北美卡通形象（Kool-Aid Man）一样冲破视口的边缘。

然而在 Flexbox 行中，`width` 属性的实现方式不同。它更像是一个建议，而不是硬约束。

规范对此有个名称：*假设尺寸*（hypothetical size）。它是元素在一个完美的乌托邦世界里、没有任何阻碍时*本应*具有的尺寸。

唉，事情很少这么简单。在这个例子里，限制因素是父元素*没有空间*容纳一个 2000px 宽的子元素。于是子元素的尺寸被缩小，以便放得下。

这是 Flexbox 哲学的核心部分。事物是流动的、灵活的，可以根据世界的约束进行调整。

## 放大与缩小

我们已经看到，Flexbox 算法通过*假设尺寸*内建了一些灵活性。但要*真正*看清 Flexbox 能有多流动，我们需要讨论 3 个属性：`flex-grow`、`flex-shrink` 和 `flex-basis`。

我们逐一来看。

### flex-basis

我承认：很长一段时间里，我都没真正搞懂 `flex-basis` 到底*是怎么回事*。😅

**简单来说：**在 Flexbox 行中，`flex-basis` 的作用和 `width` 一样。在 Flexbox 列中，`flex-basis` 的作用和 `height` 一样。

正如我们所学，Flexbox 中的一切都*依附于主轴/交叉轴*。例如，`justify-content` 会沿主轴分布子元素，而且无论主轴是水平还是垂直，它的工作方式都完全相同。

但 `width` 和 `height` 并不遵循这个规则！`width` 永远影响水平尺寸。当我们把 `flex-direction` 从 `row` 切换到 `column` 时，它不会突然变成 `height`。

**所以，Flexbox 的作者们创造了一个通用的“尺寸”属性，叫 `flex-basis`。**它就像 `width` 或 `height`，但和其他一切一样依附于*主轴*。它让我们可以设置元素在主轴方向上的*假设尺寸*，不管主轴是水平还是垂直。

在这里试试看。每个子元素都设置了 `flex-basis: 50px`，你可以调整第一个子元素：

（交互演示：切换方向并调整第一个子元素的 flex-basis）

和我们在 `width` 上看到的一样，`flex-basis` 更像是一个建议，而不是硬约束。到了某个程度，空间就不够让所有元素都保持指定尺寸了，于是它们必须妥协，以避免溢出。

### flex-grow

默认情况下，Flexbox 上下文中的元素会沿主轴缩到它们最小的舒适尺寸。这常常会产生多余的空间。

我们可以用 `flex-grow` 属性指定如何消耗这些空间：

（交互演示：flex-grow 取 0（默认）或 1）

`flex-grow` 的默认值是 0，这意味着放大需要主动选择。如果我们希望某个子元素吞掉容器中所有多余的空间，就需要明确告诉它。

**如果*多个*子元素都设置了 `flex-grow` 呢？**这种情况下，多余的空间会根据各子元素的 `flex-grow` 值按比例分配。

我觉得用可视化来解释会更容易。试着增减每个子元素的值：

（交互演示：分别调整两个子元素的 flex-grow）

第一个子元素想要 1 份多余空间，第二个子元素也想要 1 份。这意味着总份数是 **2**（1 + 1）。每个子元素按比例分得一份多余空间。

### flex-shrink

到目前为止的大多数例子里，我们都有多余的空间可用。但如果子元素对容器来说*太大*了呢？

**我们来测试一下。**试着缩小容器，看看会发生什么：

（交互演示：两个子元素 flex-basis 分别为 300px 和 150px，显示实际尺寸与缩减比例）

有意思吧？两个元素都会缩小，**但它们是按比例缩小的。**第一个子元素始终是第二个的 2 倍宽。（你可能会看到一些舍入问题，显示差了一两个像素。这很可能是我这个过度设计的演示的缺陷！）

友情提醒，`flex-basis` 和 `width` 的作用相同。我们用 `flex-basis` 是因为这是惯例，但如果用 `width`，我们会得到**完全相同的结果**！

`flex-basis` 和 `width` 设置的是元素的*假设尺寸*。Flexbox 算法可能会把元素缩到这个期望尺寸以下，但默认情况下，它们总是一起缩放，保持两者之间的比例。

那么，如果我们*不*想让元素按比例缩小呢？**这就是 `flex-shrink` 属性登场的地方。**

花几分钟摆弄一下这个演示。**看看你能不能弄明白这里发生了什么。**我们下面再来探讨。

（交互演示：两个子元素 flex-basis 均为 250px，可调整 flex-shrink 和容器宽度）

好，我们有两个子元素，每个的假设尺寸都是 250px。容器至少需要 500px 宽，才能以假设尺寸容纳这些子元素。

假设我们把容器缩小到 **400px**。嗯，我们没法把 500px 的内容塞进一个 400px 的袋子里！*我们有 100px 的赤字。*元素们总共需要让出 100px 才能放得下。

**`flex-shrink` 属性让我们决定这笔差额如何偿还。**

和 `flex-grow` 一样，它是一个比例。默认情况下，两个子元素都是 `flex-shrink: 1`，所以每个子元素承担一半的差额。它们各自让出 50px，实际尺寸从 250px 缩到 200px。

现在，假设我们把第一个子元素调到 `flex-shrink: 3`：

（截图：上面的演示锁定在 400px 宽，第一个子元素的 flex-shrink 为 3）

总赤字是 *100px*。通常每个子元素承担一半，但因为我们调整了 `flex-shrink`，第一个元素最终承担了 ¾（75px），第二个元素承担 ¼（25px）。

注意，绝对值并不重要，**关键在于比例。**如果两个子元素都是 `flex-shrink: 1`，每个子元素承担总赤字的一半。如果两个子元素都调到 `flex-shrink: 1000`，每个子元素承担总赤字的 1000/2000。无论哪种，结果都一样。

不久前我对 `flex-shrink` 有了一个顿悟：我们可以把它看作 `flex-grow` 的“逆运算”。它们是同一枚硬币的两面：

* `flex-grow` 控制元素小于容器时*多余空间如何分配*。
* `flex-shrink` 控制元素大于容器时*空间如何削减*。

这意味着**同一时刻只有*一个*属性会生效。**如果有多余空间，`flex-shrink` 就没有作用，因为元素不需要缩小。如果子元素对容器来说太大，`flex-grow` 就没有作用，因为没有多余空间可分。

我喜欢把它想成两个独立的世界。你要么在地球上，要么在《怪奇物语》里那个邪恶的平行维度“颠倒世界”里。每个世界都有自己的规则。

（代码演示：Flex Shrink 小球演示）

```

  }
</style>

<div class="wrapper">
  <div class="item ball"></div>
  <div class="item stretch"></div>
  <div class="item ball"></div>
</div>
```

```
.item.ball {
  min-width: 32px;
}
```

## 最小尺寸陷阱

这里还有*一件事*要讲，而且它非常重要。它可能是全文最有用的一点！

假设我们在为一家电商网站构建一个流式搜索表单：

（交互演示：可调整宽度的搜索表单）

当容器缩小到某个程度以下时，**内容溢出了！**

*可为什么？？*`flex-shrink` 的默认值是 `1`，我们也没去掉它，所以搜索输入框*应该*能够按需缩小！它为什么拒绝缩小？

**原因是这样的：**除了*假设*尺寸，Flexbox 算法还关心另一个重要尺寸：*最小尺寸*。

Flexbox 算法拒绝把子元素缩到其最小尺寸以下。内容宁可溢出也不会进一步缩小，*无论我们把 `flex-shrink` 调得多高！*

文本输入框的默认最小尺寸是 170px 到 200px（因浏览器而异）。这就是我们在上面碰到的限制。

在其他情况下，限制因素可能是元素的内容。例如，试着调整这个容器的大小：

（交互演示：一个元素写着“这一项里最长的单词是 ‘sesquipedalian’（冗长的）”，另一个写着“这一项没有长单词”）

对于包含文字的元素，最小宽度是*最长的不可断开字符串*的长度。

**好消息是：**我们可以用 `min-width` 属性重新定义最小尺寸。

（交互演示：min-width 取 auto（默认）或 0px）

通过直接在 Flexbox 子元素上设置 `min-width: 0px`，我们告诉 Flexbox 算法覆盖“内置”的最小宽度。因为我们把它设成了 0px，元素就可以按需任意缩小。

同样的技巧也可以用 `min-height` 属性用在 Flexbox 列中（不过这个问题似乎不太常出现）。

### 自动外边距

还有一个与间距相关的技巧我想分享。它从 Flexbox 早期就存在了，但相对鲜为人知，我第一次发现它时简直*大开眼界*。

`margin` 属性用于在特定元素周围添加空间。在某些布局模式中，比如 Flow 和定位布局，它甚至可以通过 `margin: auto` 来居中一个元素。

在 Flexbox 中，自动外边距要有趣得多：

（交互演示：margin-left / margin-right 取 0（默认）或 auto）

前面我们看到 `flex-grow` 属性可以吞掉所有多余空间，把它分给某个子元素。

**自动外边距会吞掉多余空间，并把它用作元素的外边距。**这让我们可以精确控制多余空间分配到哪里。

一种常见的页头布局是一侧放 logo，另一侧放几个导航链接。下面是用自动外边距构建这种布局的方法：

（代码演示）

```
<style>
  ul {
    display: flex;
    gap: 12px;
  }
  li.logo {
    margin-right: auto;
  }
</style>

<nav>
  <ul>
    <li class="logo">
      <a href="/">
        Corpatech
      </a>
    </li>
    <li>
      <a href="">
        Mission
      </a>
    </li>
    <li>
      <a href="">
        Contact
      </a>
    </li>
  </ul>
</nav>
```

**Corpatech** 这个 logo 是列表中的第一项。通过给它设置 `margin-right: auto`，我们把所有多余空间收集起来，强行塞到第 1 项和第 2 项之间。

我们可以用浏览器开发者工具看看这里发生了什么：

（截图：上面的演示中，第一项与其他项之间有一个橙色矩形，代表外边距）

这个问题还有很多其他解法：我们可以把导航链接放进它们自己的 Flexbox 容器里，或者用 `flex-grow` 让第一个列表项放大。但我个人很喜欢自动外边距这个方案。我们把多余空间*当作一种资源*，并精确决定它该去哪里。

## 换行

呼！到目前为止我们讲了*很多*内容。最后我还想分享一个重要的要点。

到目前为止，我们所有的元素都在单行/单列中并排排列。`flex-wrap` 属性让我们可以改变这一点。

看看这个：

（交互演示：flex-wrap 取 nowrap（默认）或 wrap，三个元素 flex-basis 均为 180px）

大多数时候，当我们在二维空间里工作时，会想用 CSS Grid，但 Flexbox + `flex-wrap` 绝对有它的用武之地！这个例子展示的是[“解构煎饼”](https://web.dev/patterns/layout/deconstructed-pancake/)布局：在中等尺寸的屏幕上，3 个元素堆叠成一个倒金字塔。

当我们设置 `flex-wrap: wrap` 时，**元素不会缩到其假设尺寸以下**。至少，在可以换到下一行/列的情况下不会！

**等等！**那我们的烤肉串/鸡尾酒小香肠比喻怎么办？？

使用 `flex-wrap: wrap` 后，我们不再有一条能串起每个元素的单一主轴线。实际上，**每一行都相当于一个独立的迷你 flex 容器。**不再是 1 根大签子，而是每行都有自己的签子：

（插图：两串烤肉，每串有两块鸡肉）

我们目前学到的所有规则，在这个缩小的范围内继续适用。比如 `justify-content` 会分配每根签子上的两块肉。

但是嗯……现在有多行了，`align-items` 怎么工作呢？交叉轴现在*可能*会穿过多个元素了！

**花点时间想想。**你*认为*改变这个属性会发生什么？有了答案（或者至少有个想法）之后，看看对不对：

（交互演示：调整 align-items）

每一行都是它自己的迷你 Flexbox 环境。`align-items` 会让每个元素在包裹每一行的那个看不见的盒子里上下移动。

但如果我们想*对齐这些行本身*呢？可以用 `align-content` 属性做到：

（交互演示：调整 align-items 与 align-content）

总结一下这里发生的事：

* `flex-wrap: wrap` 给了我们两行东西。
* 在每一行内，`align-items` 让我们可以把每个子元素单独上下滑动。
* 然而拉远来看，我们在一个 Flexbox 上下文中有这两行！交叉轴现在会穿过*两*行，而不是一行。所以我们不能单独移动各行，需要*整体*分配它们。
* 按照上面的定义，我们处理的是 *content*，而不是 *items*。但我们谈论的仍然是交叉轴！所以我们要用的属性是 `align-content`。

## 你坚持到了最后！

我想承认一件事：**这是一篇很密集的教程。**我们在兔子洞里钻得*非常*深，除非你已经是 Flexbox 高手，否则我估计你现在有点头晕了。😅
