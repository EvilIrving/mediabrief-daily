我如何把 GTA 在线模式的加载时间缩短了 70%

《GTA 在线模式》（GTA Online）以加载缓慢而臭名昭著。我最近重新拿起这款游戏，想打完一些新出的抢劫任务，结果"震惊"地（反讽）发现，它的加载速度和七年前刚发布时一样慢。

是时候了。是时候查个水落石出了。

侦察

首先，我想看看是否已经有人解决了这个问题。我找到的大多数结果都是些道听途说：有人说游戏太复杂，所以需要加载这么久；有人说它的 P2P 网络架构很烂（我没说它不烂）；还有一些繁琐的方法，比如先进入故事模式、再进入单人战局；以及几个可以跳过启动时 R* 标志视频的模组。再读了一些资料后我得知，把这些方法结合起来，能省下足足 10 到 30 秒！

与此同时，在我的电脑上……

基准测试

故事模式加载时间：约 1 分 10 秒
在线模式加载时间：约 6 分钟整
已禁用启动菜单，计时从 R* 标志出现到进入游戏（不计 Social Club 登录时间）。
老旧但还算可以的 CPU：AMD FX-8350
廉价 SSD：KINGSTON SA400S37120G
内存总得有：2 条 Kingston 8192 MB（DDR3-1337）99U5471
还算不错的显卡：NVIDIA GeForce GTX 1070

我知道我的配置有些过时了，但到底是什么东西能让进入在线模式多花六倍的时间？用"先进故事模式再进在线"的方法，我测不出任何差别，之前也有人得出了同样的结论。即便它真的有效，效果也会淹没在噪声里。

我（并不）孤单

如果这项投票可信的话，这个问题普遍到足以让超过 80% 的玩家感到些许恼火。已经七年了，R*！

我四处看了看，想找出那幸运的约 20%、加载时间不到 3 分钟的玩家是谁，结果发现了几个用高端游戏电脑做的基准测试，在线模式的加载时间大约是 2 分钟。为了 2 分钟的加载时间，我愿意去杀（划掉）去破解！这似乎确实和硬件有关，但有些地方说不通……

为什么他们的故事模式仍然要花将近一分钟来加载？（顺便说一句，那个用 M.2 硬盘的测试没算启动标志的时间。）而且他们从故事模式进入在线模式只多花一分钟，而我要多花大约五分钟。我知道他们的硬件配置好得多，但肯定没好到五倍。

高度精确的测量

我拿起"任务管理器"这样强大的工具，开始调查哪种资源可能是瓶颈。

花了一分钟加载故事模式和在线模式共用的资源（这部分和高端电脑差不多）之后，GTA 决定把我机器上的一个核心跑满整整四分钟，别的什么也不干。

磁盘占用？没有！网络占用？有一点，但几秒后基本降到零（除了加载那些轮播的信息横幅）。GPU 占用？零。内存占用？完全平稳……

怎么，它在挖矿还是什么？我闻到了代码的味道。非常糟糕的代码。

单线程瓶颈

我这颗老 AMD CPU 虽然有 8 个核心，性能也还行，但它是老古董了，那时 AMD 的单线程性能远远落后于英特尔。这也许不能解释全部的加载时间差异，但应该能解释大部分。

奇怪的是，它只占用 CPU。我原本以为会看到大量读取磁盘来加载资源，或者大量网络请求来在 P2P 网络中协商战局。但这个？这很可能是个 bug。

性能分析

性能分析器是找出 CPU 瓶颈的好工具。只有一个问题：大多数分析器依赖对源代码插桩，才能完美地掌握进程中发生的事情。而我没有源代码。我也不需要精确到微秒的读数，我面对的是长达四分钟的瓶颈。

于是轮到栈采样登场：对于闭源程序，这是唯一的选择。每隔一段时间转储一次运行中进程的调用栈和当前指令指针的位置，构建出调用树，再把它们加总起来，统计到底发生了什么。据我所知（可能是我孤陋寡闻），在 Windows 上能做到这一点的分析器只有一个，而且它已经十多年没更新了。它就是 Luke Stackwalker！谁来给这个项目一点关爱吧 :)

通常 Luke 会把相同的函数归为一组，但由于我没有调试符号，只能靠肉眼比对相近的地址来猜测是不是同一个地方。结果我们看到了什么？不是一个瓶颈，而是两个！

深入兔子洞

我借来"我朋友"那份完全合法的"业界标准反汇编器"（不，我真的买不起那玩意儿……总有一天我要学会用 Ghidra），开始拆解 GTA。

看起来完全不对劲。大多数知名游戏都内置了防逆向工程的保护措施，以挡住盗版者、作弊者和模组作者。虽然这从来没能真正挡住他们。

这里似乎用了某种混淆或加密，把大部分指令都替换成了乱码。不必担心，我们只需要在游戏执行我们想看的那部分代码时转储它的内存。指令无论如何都必须在运行前解除混淆。我手头正好有 Process Dump，就用了它，不过能做这类事的工具还有很多。

问题一：竟然是……strlen？！

反汇编这份已经去掉部分混淆的转储后，发现其中一个地址居然带着一个不知从哪儿来的标签！是 strlen？沿着调用栈往下，下一个的标签是 vscan_fn，再往后就没有标签了，不过我相当肯定那是 sscanf。

它在解析某样东西。解析什么呢？理清反汇编代码要花很久，所以我决定用 x64dbg 从运行中的进程里转储一些样本。经过一番单步调试后发现，那是……JSON！他们在解析 JSON。足足 10 MB 的 JSON，包含约 6.3 万个条目。

```
...,
{
 "key": "WP_WCT_TINT_21_t2_v9_n2",
 "price": 45000,
 "statName": "CHAR_KIT_FM_PURCHASE20",
 "storageType": "BITFIELD",
 "bitShift": 7,
 "bitSize": 1,
 "category": ["CATEGORY_WEAPON_MOD"]
},
...
```

这是什么？根据一些引用来看，它似乎是"网络商店目录"的数据。我猜它包含了 GTA 在线模式里所有可以购买的物品和升级。

可是 10 MB？那算不了什么！用 sscanf 也许不是最优选择，但肯定不至于那么糟吧？嗯……

是啊，那得花上好一阵子了……说句公道话，我之前也不知道大多数 sscanf 实现都会调用 strlen，所以我不能责怪写这段代码的开发者。我原本以为它只是逐字节扫描，遇到 NULL 就停下。

问题二：我们用个哈希……数组？

原来第二个罪魁祸首就在第一个的旁边被调用。它们甚至是在同一个 if 语句里被调用的，就像这段难看的反编译代码所显示的那样。

所有标签都是我起的，我不知道这些函数和参数实际叫什么。

第二个问题是什么？解析完一个物品后，它会被存进一个数组（或者是内联的 C++ list？我不确定）。每个条目大概是这样：

```
struct {
 uint64_t *hash;
 item_t *item;
} entry;
```

但在存进去之前呢？它会把整个数组逐个检查一遍，比较物品的哈希值，看它是否已经在列表里。有约 6.3 万个条目，如果我没算错的话，那就是 (n^2+n)/2 = (63000^2+63000)/2 = 1984531500 次检查，其中大部分都是无用功。你们有唯一的哈希值，为什么不用哈希表呢？

我在逆向时把它命名为 hashmap，但它显然是 not_a_hashmap（不是哈希表）。而且更妙的是：在加载 JSON 之前，这个哈希-数组-列表之类的东西是空的。而 JSON 里的所有物品都是唯一的！他们根本不需要检查它是否已在列表中！他们甚至有一个直接插入物品的函数！用那个就好了！说真的，这是什么鬼！？

概念验证

这些都很好，但除非我真的测试一下，否则没人会把我当回事，我也没法给这篇文章起个标题党的标题。

计划是什么？写一个 .dll，注入 GTA，钩住一些函数，？？？，然后大功告成。

JSON 的问题很棘手，我实际上不可能替换掉他们的解析器。换一个不依赖 strlen 的 sscanf 会更现实。但还有一个更简单的办法：

- 钩住 strlen
- 等待一个很长的字符串出现
- "缓存"它的起始位置和长度
- 如果之后再次在该字符串范围内调用，就返回缓存的值

大致如下：

```
size_t strlen_cacher(char* str)
{
 static char* start;
 static char* end;
 size_t len;
 const size_t cap = 20000;
 if (start && str >= start && str <= end) {
 len = end - str;
 if (len < cap / 2)
 MH_DisableHook((LPVOID)strlen_addr);
 return len;
 }
 len = builtin_strlen(str);
 if (len > cap) {
 start = str;
 end = str + len;
 }
 return len;
}
```

至于哈希数组的问题，就更直接了：既然我们知道这些值是唯一的，那就完全跳过重复检查，直接插入物品。

```
char __fastcall netcat_insert_dedupe_hooked(uint64_t catalog, uint64_t* key, uint64_t* item)
{
 uint64_t not_a_hashmap = catalog + 88;
 if (!(*(uint8_t(__fastcall**)(uint64_t*))(*item + 48))(item))
 return 0;
 netcat_insert_direct(not_a_hashmap, key, &item);
 if (*key == 0x7FFFD6BE) {
 MH_DisableHook((LPVOID)netcat_insert_dedupe_addr);
 unload();
 }
 return 1;
}
```

概念验证的完整源代码在这里。

结果

那么，它奏效了吗？

原始在线模式加载时间：约 6 分钟整
只修复重复检查：4 分 30 秒
只修复 JSON 解析：2 分 50 秒
两个问题都修复：1 分 50 秒
(6×60 − (1×60+50)) / (6×60) = 加载时间缩短 69.4%（不错！）

当然奏效了！:))

这很可能解决不了所有人的加载时间问题，不同系统上可能还有别的瓶颈，但这是一个如此巨大的漏洞，我真不知道 R* 这些年怎么会一直没发现。

太长不看

- 启动 GTA 在线模式时存在单线程 CPU 瓶颈
- 原来是 GTA 解析一个 10 MB 的 JSON 文件很吃力
- JSON 解析器本身写得很差、很幼稚
- 解析之后还有一个缓慢的物品去重过程
