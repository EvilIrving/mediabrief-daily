“慢”是什么意思？我以前说过，现在再说一遍：如果你没有测量过，它就不慢；即便测量了，脱离上下文的数字也毫无意义。

话虽如此，有些人因为担心 `postMessage()` 的性能，甚至根本不考虑采用 Web Worker，这说明这个问题值得研究。我上一篇关于 worker 的博文也收到了类似的反馈。让我们用实际数字来衡量 `postMessage()` 的性能，看看到什么程度你会面临超出预算的风险。如果原生的 `postMessage()` 对你的用例来说太慢了，又能怎么办？

## postMessage 的工作原理

开始测量之前，我们需要先理解 `postMessage()` *是*什么，以及我们想测量它的哪一部分。否则我们最终只会收集到无意义的数据，得出无意义的结论。

`postMessage()` 是 HTML 规范的一部分（不是 ECMA-262！）。正如我在关于深拷贝的文章中提到的，`postMessage()` 依靠结构化克隆把消息从一个 JavaScript realm 复制到另一个。仔细看一下 `postMessage()` 的规范，会发现结构化克隆是一个两步过程：

### 结构化克隆算法

1. 对消息执行 `StructuredSerialize()`
2. 在接收方 realm 中排入一个任务，该任务执行以下步骤：
  1. 对序列化后的消息执行 `StructuredDeserialize()`
  2. 创建一个 `MessageEvent`，并在接收端口上派发一个携带反序列化后消息的 `MessageEvent`

这是算法的简化版本，以便我们专注于与本文相关的部分。它在*技术上*并不准确，但可以说抓住了精髓。例如，`StructuredSerialize()` 和 `StructuredDeserialize()` 并不是真正的函数，因为它们（目前还）没有通过 JavaScript 暴露出来。这两个函数实际上做什么？目前，**你可以把 `StructuredSerialize()` 和 `StructuredDeserialize()` 分别看作 `JSON.stringify()` 和 `JSON.parse()` 的更聪明版本**。说它们更聪明，是因为它们能处理循环数据结构，以及 `Map`、`Set`、`ArrayBuffer` 等内置数据类型。但这些聪明之处是否有代价？我们稍后再谈。

上面的算法没有明确说出的一点是：**序列化会阻塞发送方 realm，而反序列化会阻塞接收方 realm。** 还不止于此：原来 Chrome 和 Safari 都会推迟执行 `StructuredDeserialize()`，直到你真正访问 `MessageEvent` 上的 `.data` 属性。而 Firefox 则在派发事件之前就进行反序列化。

**注：** 这两种行为*都*符合规范，完全合法。我给 Mozilla 提了一个 bug，询问他们是否愿意统一实现，因为（延迟反序列化）能让开发者自己控制何时承受反序列化大负载的“性能开销”。

考虑到这一点，我们必须选择基准测试*什么*：我们可以测量端到端，也就是测量从 worker 向主线程发送一条消息需要多长时间。然而这个数字反映的是序列化与反序列化之和，而两者发生在不同的 realm 中。请记住：**折腾 worker 这一整套的动机，就是想让主线程保持空闲、响应迅速。** 另一种选择是把基准测试限定在 Chrome 和 Safari 上，测量访问 `.data` 属性所需的时间，从而单独测量 `StructuredDeserialize()`，但这会把 Firefox 排除在外。我也没找到除运行 trace 之外单独测量 `StructuredSerialize()` 的方法。这两种选择都不理想，但本着构建健壮 Web 应用的精神，**我决定运行端到端基准测试，为 `postMessage()` 的开销提供一个*上限*。**

对 `postMessage()` 有了概念上的理解，又下定了测量的决心，我将使用微基准测试。请注意这些数字与现实之间的差距。

## 基准测试 1：发送一条消息需要多长时间？

该基准测试会生成具有特定“广度”和“深度”的对象，广度和深度的取值都在 1 到 6 之间。**对每一种广度与深度的组合，从 worker 向主线程 `postMessage()` 1000 个不同的对象。** 这些对象的属性名是字符串形式的随机 16 位十六进制数，值则是随机布尔值、随机浮点数，或者同样是 16 位十六进制数形式的随机字符串。**基准测试测量传输时间并计算第 95 百分位数。**

## 基准测试 2：是什么让 postMessage 变慢？

为了验证这一点，我修改了基准测试：生成广度和深度在 1 到 6 之间的所有排列组合，但此外所有叶子属性都是长度在 16 字节到 2KiB 之间的字符串值。

### 结果

我认为相关性已经强到足以给出一条经验法则：**对象经字符串化后的 JSON 表示，大致与其传输时间成正比。** 然而更重要的一点是，**这种相关性只有对大对象才有意义**，这里的大是指超过 100KiB 的任何东西。虽然在数学上相关性成立，但在较小的负载上偏离要明显得多。

## 评估：关键在于发送消息

我们有了数据，但如果不放到具体情境中，它就毫无意义。要得出*有意义*的结论，我们需要定义“慢”。预算在这里是个有用的工具，我将再次借助 RAIL 准则来确立我们的预算。

根据我的经验，Web Worker 的核心职责至少是管理应用的状态对象。状态通常只在用户与应用交互时才会改变。按照 RAIL，我们有 100ms 来响应用户交互，这意味着**即使在最慢的设备上，你也可以 `postMessage()` 最大 100KiB 的对象，并保持在预算之内。**

如果你有 JS 驱动的动画在运行，情况就不同了。RAIL 对动画的预算是 16ms，因为每一帧都需要更新画面。如果我们从 worker 发送的消息会阻塞主线程超过这个时间，就麻烦了。看看基准测试中的数字，10KiB 以内的任何东西都不会对你的动画预算构成风险。话虽如此，**这是优先使用 CSS 动画和过渡、而非主线程 JS 驱动动画的有力理由。** CSS 动画和过渡运行在一个单独的线程——合成器线程（compositor thread）——上，不受主线程阻塞的影响。

## 必须。发送。更多。数据。

根据我的经验，对大多数采用主线程外（off-main-thread）架构的应用来说，`postMessage()` 并不是瓶颈。不过我承认，可能存在某些情形：你的消息要么非常大，要么需要以很高的频率发送大量消息。如果原生的 `postMessage()` 对你来说太慢，你能做什么？

### 打补丁

就状态对象而言，对象本身可能相当大，但发生变化的往往只是少数几个深层嵌套的属性。我们在 PROXX——我们那个 PWA 版扫雷克隆——中就遇到了这个问题：游戏状态包含一个表示游戏网格的二维数组。每个格子存储它是否是地雷、是否已被翻开、是否已被插旗：

```
interface Cell {
  hasMine: boolean;
  flagged: boolean;
  revealed: boolean;
  touchingMines: number;
  touchingFlags: number;
}
```
这意味着最大的 40×40 网格加起来大约有 134KiB 的 JSON。每次发送整个状态对象是不可能的。**我们没有在每次发生变化时发送整个新状态对象，而是选择记录变化、发送一个补丁集（patchset）。** 虽然我们没有使用 ImmerJS（一个用于处理不可变对象的库），但它确实提供了一种快速生成和应用这类补丁集的方式：

```
// worker.js
immer.produce(stateObject, draftState => {
  // Manipulate `draftState` here
}, patches => {
  postMessage(patches);
});
// main.js
worker.addEventListener("message", ({data}) => {
  state = immer.applyPatches(state, data);
  // React to new state
}
```
ImmerJS 生成的补丁长这样：

```
[
  {
    "op": "remove",
    "path": [ "socials", "gplus" ]
  },
  {
    "op": "add",
    "path": [ "socials", "twitter" ],
    "value": "@DasSurma"
  },
  {
    "op": "replace",
    "path": [ "name" ],
    "value": "Surma"
  }
]
```
这意味着需要传输的数据量与你的改动大小成正比，而不是与对象大小成正比。

### 分块

正如我所说，对状态对象而言，改变的*往往*只是少数几个属性。但并非总是如此。事实上，PROXX 中就有一种补丁集可能相当大的场景：第一次翻开可能影响多达 80% 的游戏区域，补丁集加起来大约有 70KiB。面向功能机（feature phone）时，这就太多了，尤其是我们可能还有 JS 驱动的 WebGL 动画在运行。

我们问了自己一个架构问题：我们的应用能支持部分更新吗？补丁集是补丁的集合。**与其一次性发送补丁集中的所有补丁，不如把补丁集“分块”成较小的分区，依次应用。** 第一条消息发送补丁 1-10，下一条发送 11-20，以此类推。如果把这一点推向极致，你实际上就是在*流式传输*补丁，从而可以使用你在响应式编程中熟悉和喜爱的所有模式。

当然，如果不小心，这可能导致画面不完整甚至错乱。不过分块方式由你掌控，你可以重新排列补丁的顺序来避免任何不良效果。例如，你可以确保第一块包含所有影响屏幕上可见元素的补丁，再把其余补丁放进几个补丁集中，给主线程留出喘息空间。

我们在 PROXX 中就做了分块。当用户点击一个格子时，worker 会遍历整个网格，找出哪些格子需要更新，并把它们收集到一个列表中。如果列表增长超过某个阈值，我们就把目前已有的内容发送给主线程，清空列表，然后继续遍历游戏区域。这些补丁集足够小，即使在功能机上 `postMessage()` 的开销也可以忽略不计，我们仍有足够的主线程预算来更新游戏界面。遍历算法从第一个格子向外进行，这意味着我们的补丁也按同样的顺序排列。如果主线程在一帧的预算内只能处理一条消息（比如在 Nokia 8110 上），这些部分更新看起来就像一段翻开动画。如果在性能强劲的机器上，仅凭 JavaScript 事件循环的特性，主线程就会持续处理消息事件，直到预算耗尽。

### 也许用 JSON？

`JSON.parse()` 和 `JSON.stringify()` 快得惊人。JSON 是 JavaScript 的一个小子集，因此解析器要处理的情况更少。由于使用频繁，它们也经过了大量优化。Mathias 最近指出，有时可以通过把大对象包裹在 `JSON.parse()` 中来减少 JavaScript 的解析时间。**也许我们也能用 JSON 来加速 `postMessage()`？遗憾的是，答案似乎是否定的：**

虽然没有明显的赢家，但原生 `postMessage()` 在最好情况下似乎表现更好，在最坏情况下则同样糟糕。

### 二进制格式

应对结构化克隆性能影响的另一种方法是干脆不用它。除了对对象进行结构化克隆，`postMessage()` 还可以*转移*（transfer）某些类型。`ArrayBuffer` 就是这类可转移类型之一。顾名思义，转移 `ArrayBuffer` 不涉及复制。发送方 realm 实际上会失去对该缓冲区的访问权，缓冲区从此归接收方 realm 所有。**转移 `ArrayBuffer` 极其快速，且与 `ArrayBuffer` 的大小无关。** 缺点是 `ArrayBuffer` 只是一块连续的内存。我们不再操作对象和属性了。要让 `ArrayBuffer` 派上用场，我们必须自己决定数据如何编组（marshal）。这本身就有代价，但由于在构建时就知道数据的形状或结构，我们有可能利用许多通用克隆算法无法使用的优化。

FlatBuffers 就是能让你利用这些优化的格式之一。FlatBuffers 有面向 JavaScript（以及其他语言）的编译器，可以把 schema 描述转换成代码。这些代码包含序列化和反序列化数据的函数。更有意思的是：FlatBuffers 不需要解析（或“解包”）整个 `ArrayBuffer` 就能返回其中包含的某个值。

### WebAssembly

那么大家最爱的 WebAssembly 呢？一种做法是借助 WebAssembly 使用其他语言生态中的序列化库。CBOR 是一种受 JSON 启发的二进制对象格式，已在许多语言中实现。ProtoBuffers 和前面提到的 FlatBuffers 也有广泛的语言支持。

不过，我们在这里可以更取巧一点：我们可以直接把语言的内存布局当作序列化格式。我用 Rust 写了一个小例子：它定义了一个 `State` 结构体（象征你的应用状态长什么样），带有一些 getter 和 setter 方法，以便我从 JavaScript 中查看和操作状态。要“序列化”状态对象，我只需复制该结构体所占的那块内存。要反序列化，我分配一个新的 `State` 对象，然后用传给反序列化函数的数据覆盖它。由于两边使用的是同一个 WebAssembly 模块，内存布局是完全相同的。

这只是一个概念验证。如果你的结构体包含指针（`Vec` 和 `String` 就包含），很容易陷入未定义行为。其中还有一些不必要的复制。请负责任地写代码！

```
pub struct State {
    counters: [u8; NUM_COUNTERS]
}
#[wasm_bindgen]
impl State {
    // Constructors, getters and setter...
    pub fn serialize(&self) -> Vec<u8> {
        let size = size_of::<State>();
        let mut r = Vec::with_capacity(size);
        r.resize(size, 0);
        unsafe {
            std::ptr::copy_nonoverlapping(
                self as *const State as *const u8,
                r.as_mut_ptr(),
                size
            );
        };
        r
    }
}
#[wasm_bindgen]
pub fn deserialize(vec: Vec<u8>) -> Option<State> {
    let size = size_of::<State>();
    if vec.len() != size {
        return None;
    }
    let mut s = State::new();
    unsafe {
        std::ptr::copy_nonoverlapping(
            vec.as_ptr(),
            &mut s as *mut State as *mut u8,
            size
        );
    }
    Some(s)
}
```
**注：** Ingvar 向我推荐了 Abomonation，一个相当可疑的序列化库，它甚至*连指针*都能处理。他的建议是：“[不要]尝试这个！”

这个 WebAssembly 模块 gzip 后约 3KiB，其中大部分来自内存管理和一些核心库函数。每当有变化时都会发送整个状态对象，但由于 `ArrayBuffer` 的可转移性，这样做极其廉价。换句话说：**无论状态多大，这种技术的传输时间都应该近乎恒定。** 不过，访问状态数据的成本会更高。凡事总有取舍！

这种技术还要求状态结构体不使用任何像指针这样的间接引用，因为这些值在复制到新的 WebAssembly 模块实例时会失效。因此，你在高级语言中可能很难使用这种方法。我推荐 C、Rust 和 AssemblyScript，因为你能完全掌控并充分了解内存布局。

### SAB 与 WebAssembly

**提醒：** 本节使用 `SharedArrayBuffer`，除桌面版 Chrome 外，所有浏览器都已禁用它。相关工作正在进行中，但无法给出预计时间。

我听到过多次请求——尤其来自游戏开发者——希望赋予 JavaScript 在多个线程之间共享对象的能力。我认为这不太可能被加入 JavaScript 本身，因为它打破了 JavaScript 引擎的一项基本假设。不过有一个例外，叫 `SharedArrayBuffer`（“SAB”）。SAB 的行为与 `ArrayBuffer` 完全一样，但转移时不是由一方 realm 失去访问权，而是可以被克隆，*两个* realm 都能访问同一块底层内存。**SAB 允许 JavaScript realm 采用共享内存模型。** 为了在 realm 之间同步，有 `Atomics` 提供互斥锁和原子操作。

使用 SAB，你只需在应用启动时转移一次内存块。然而，除了二进制表示的问题之外，你还得使用 `Atomics` 来防止一个 realm 在另一个 realm 仍在写入时读取状态对象，反之亦然。这可能带来相当大的性能影响。

作为使用 SAB 并手动序列化/反序列化数据的替代方案，你可以拥抱*多线程* WebAssembly。WebAssembly 已经标准化了对线程的支持，但前提是 SAB 可用。**借助多线程 WebAssembly，你可以用与多线程编程语言中完全相同的模式编写代码。** 当然，这样做的代价是开发复杂度、协调成本，以及可能需要交付更大、更单体化的模块。

## 结论

我的结论是：即使在最慢的设备上，你也可以 `postMessage()` 最大 100KiB 的对象，并保持在 100ms 的响应预算之内。如果你有 JS 驱动的动画，10KiB 以内的负载是没有风险的。这对大多数应用来说应该足够了。`postMessage()` 确实有开销，但还没到让主线程外架构变得不可行的程度。

如果你的负载比这更大，可以尝试发送补丁或改用二进制格式。**从一开始就把状态布局、可转移性和可打补丁性作为架构决策来考虑，可以帮助你的应用在更广泛的设备上运行。** 如果你觉得共享内存模型是最佳选择，WebAssembly 将在不久的将来为你铺平道路。

正如我在一篇关于 Actor 模型的旧文中已经暗示过的，我坚信我们*今天*就能在 Web 上实现高性能的主线程外架构，但这要求我们走出多线程语言的舒适区，也走出 Web 默认一切都在主线程上运行的舒适区。我们需要探索那些*拥抱* Web 和 JavaScript 约束的替代架构和模型。这样做的好处是值得的。
