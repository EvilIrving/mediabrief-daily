## 1. 模型架构概览

在更详细地讨论架构之前，先来概览一下这两个模型 gpt-oss-20b 和 gpt-oss-120b，见下方图 1。

如果你之前看过近来的 LLM 架构图，或读过我上一篇《大型架构比较》（The Big LLM Architecture Comparison）文章，可能会发现乍看之下并没有什么新颖或不寻常之处。

这并不奇怪，因为领先的 LLM 开发者往往使用同一套基础架构，再做一些较小的调整。以下纯属我的猜测，但我认为原因在于：

- 这些实验室之间人员流动频繁。
- 我们仍未找到比 Transformer 架构更好的东西。尽管存在状态空间模型和文本扩散模型，但据我所知，还没有人证明它们在这种规模上能和 Transformer 表现得一样好。（我找到的大多数比较只关注基准分数，这些模型在真实世界的多轮写作和编程任务上表现如何仍不清楚。截至撰写本文时，LM Arena 上排名最高的非纯 Transformer 模型是 Jamba，一种 Transformer 与状态空间模型的混合体，排在第 96 位。补充：有读者好心指出还有一个排名更高的混合模型：Hunyuan-TurboS（混元 TurboS），排在第 22 位。）

## 2. 从 GPT-2 说起

在比较 gpt-oss 和更新的架构之前，让我们先坐上时光机，与 GPT-2 并排对比一下（图 2），看看这一路走了多远。

gpt-oss 和 GPT-2 都是仅解码器（decoder-only）的 LLM，建立在《Attention Is All You Need》（2017）论文提出的 Transformer 架构之上。多年来，许多细节发生了演变。

不过，这些变化并非 gpt-oss 独有。后面我们会看到，它们也出现在许多其他 LLM 中。由于我在上一篇《大型架构比较》中讨论过其中很多方面，这里每个小节都会尽量简短、聚焦。

### 2.1 去掉 Dropout

Dropout（2012）是一种防止过拟合的传统技术，做法是在训练中随机"丢弃"（即置零）一部分层激活或注意力分数（图 3）。然而，现代 LLM 很少使用 dropout，GPT-2 之后的大多数模型都把它"丢掉"了（双关并非有意）。

我推测 GPT-2 最初使用 dropout 是从原始 Transformer 架构继承而来的。研究者们很可能注意到它并不能真正提升 LLM 的性能（我在小规模复现 GPT-2 时也观察到同样的现象）。这很可能是因为 LLM 通常只在海量数据集上训练一个 epoch，而 dropout 最初是为几百个 epoch 的训练方案设计的。既然 LLM 在训练中每个 token 只见一次，过拟合的风险就很小。

有意思的是，尽管多年来 Dropout 在 LLM 架构设计中几乎被忽视，我还是找到了一篇 2025 年的研究论文，它用小规模 LLM（Pythia 1.4B）做实验，证实在这种单 epoch 训练方案下，Dropout 会导致下游性能变差。

### 2.2 RoPE 取代绝对位置嵌入

在基于 Transformer 的 LLM 中，由于注意力机制的缘故，位置编码是必需的。默认情况下，注意力把输入 token 当作没有顺序。在原始 GPT 架构中，绝对位置嵌入通过为序列中每个位置学习一个嵌入向量（图 4）来解决这个问题，再把它加到 token 嵌入上。

RoPE（旋转位置嵌入，Rotary Position Embedding）引入了另一种思路：它不是把位置信息作为单独的嵌入相加，而是以依赖每个 token 位置的方式旋转查询（query）和键（key）向量来编码位置。（RoPE 是个优雅的想法，但也有点难讲清楚。我打算哪天单独详细介绍。）

RoPE 虽然在 2021 年首次提出，但随着 2023 年初代 Llama 模型的发布才被广泛采用，此后成为现代 LLM 的标配。

### 2.3 Swish/SwiGLU 取代 GELU

早期的 GPT 架构使用 GELU。为什么现在用 Swish 而不是 GELU？Swish（也称 sigmoid 线性单元，即 SiLU）被认为计算上略便宜一些，在我看来原因也就仅此而已。看不同的论文，你会发现两者在建模性能上互有小幅胜负。我认为这些微小差异大概在标准误差之内，实际效果会因超参数敏感性而有所不同。

激活函数曾是热门争论话题，直到十多年前深度学习社区基本统一采用 ReLU。此后研究者提出并尝试了许多曲线更平滑的类 ReLU 变体，最终留下来的是 GELU 和 Swish（图 5）。

早期 GPT 架构使用 GELU，其定义为 `0.5x * [1 + erf(x / sqrt(2))]`。这里的 `erf`（误差函数 error function 的缩写）是高斯函数的积分，通过对高斯积分的多项式近似来计算，因此比 Swish 中使用的 sigmoid 等更简单的函数计算开销更大；Swish 就是简单的 `x * sigmoid(x)`。

实践中，Swish 的计算量比 GELU 略小，这大概就是它在大多数新模型中取代 GELU 的主要原因。看不同的论文，其中一个在建模性能上可能稍好一些，但我认为这些提升往往在标准误差之内，胜者在很大程度上取决于超参数调优。

如今大多数架构都使用 Swish。不过 GELU 并没有被完全遗忘，例如谷歌的 Gemma 模型仍在使用 GELU。

不过更值得注意的是，前馈模块（一个小型多层感知机）被替换成了带门控的"GLU"版本，GLU 即门控线性单元（gated linear unit），在一篇 2020 年的论文中提出。具体来说，原来的 2 个全连接层被替换为 3 个全连接层，用法如下方图 6 所示。

乍一看，GEGLU/SwiGLU 变体似乎比常规前馈层更好，只是因为多了一层、参数更多。但这是一种错觉，因为实践中 SwiGLU/GEGLU 里的 `W` 和 `V` 权重层通常各自取传统前馈层中 `W_1` 层的一半大小。

为了更好地说明这一点，来看常规版本和 GLU 版本的具体代码实现：

假设嵌入维度为 1024。在常规前馈的情形下，参数为：

- fc1: 1024 × 4096 = 4,194,304
- fc2: 1024 × 4096 = 4,194,304

即 fc1 + fc2 = 8,388,608 个参数。

对于 GLU 变体，则有：

- fc1: 1024 × 1024 = 1,048,576
- fc2: 1024 × 1024 = 1,048,576
- fc3: 1024 × 1024 = 1,048,576

即 3 × 1,048,576 = 3,145,728 个权重参数。

所以总体而言，使用 GLU 变体参数更少，而且性能也更好。性能更好的原因在于这些 GLU 变体提供了额外的乘性交互，从而提升了表达能力（这与"深而窄的神经网络比浅而宽的网络表现更好"是同一个道理，前提是训练得当）。

### 2.4 混合专家取代单一前馈模块

除了像上一节讨论的那样把前馈模块升级为 SwiGLU 之外，gpt-oss 还用多个前馈模块替换了单一前馈模块，并在每个 token 生成步骤中只使用其中一个子集。这种做法称为混合专家（Mixture-of-Experts，MoE），如下方图 8 所示。

于是，把*单个*前馈模块替换为*多个*前馈模块（MoE 的做法）会大幅增加模型的总参数量。但关键技巧在于，我们并不会对每个 token 使用（"激活"）所有专家，而是由一个路由器（router）为每个 token 只挑选一小部分专家。

由于每次只有少数专家处于激活状态，MoE 模块常被称为*稀疏*模块，与始终使用全部参数的*稠密*模块相对。不过，MoE 带来的大量总参数提升了 LLM 的容量，意味着它在训练中可以吸收更多知识；而稀疏性又让推理保持高效，因为我们不会同时使用所有参数。

（趣闻：在大多数 MoE 模型中，专家权重占模型总参数的 90% 以上。）

### 2.5 分组查询注意力取代多头注意力

正如我在之前文章中提到的，分组查询注意力（Grouped Query Attention，GQA）近年来已成为多头注意力（Multi-Head Attention，MHA）的一种在计算和参数上更高效的替代方案。

在 MHA 中，每个头都有自己的一组键和值。GQA 则把多个头分组，让它们共享相同的键和值投影，从而减少内存占用。

例如，如图 9 所示，如果有 2 个键值组和 4 个注意力头，那么头 1 和头 2 可能共享一组键和值，头 3 和头 4 共享另一组。这种分组减少了键和值的总计算量，从而降低内存占用、提高效率；根据消融研究，这不会明显影响建模性能。

所以 GQA 的核心思想是：让多个查询头共享键头和值头，以减少键头和值头的数量。这样（1）降低了模型的参数量，（2）减少了推理时键、值张量占用的内存带宽，因为需要在 KV 缓存中存储和读取的键和值更少了。

（如果你好奇 GQA 的代码长什么样，可以看我的"GPT-2 到 Llama 3 转换指南"，其中有不带 KV 缓存的版本，另有带 KV 缓存的变体。）

虽然 GQA 主要是针对 MHA 的一种计算效率上的变通方案，但消融研究（比如原始 GQA 论文和 Llama 2 论文中的研究）表明，它在 LLM 建模性能上与标准 MHA 相当。

### 2.6 滑动窗口注意力

滑动窗口注意力（见下方图 10）最早在 Longformer 论文（2020）中提出，后来因 Mistral 而流行。有意思的是，gpt-oss 每隔一层就使用一次滑动窗口注意力。你可以把它看作多头注意力（这里是分组查询注意力 GQA）的一种变体，其注意力上下文被限制在更小的窗口内，从而同时降低内存占用和计算成本。

具体而言，gpt-oss 在关注完整上下文的 GQA 层与滑动窗口限制为 128 个 token 的 GQA 层之间交替。

正如我在上一篇文章中讨论的，Gemma 2（2024）使用了类似的 1:1 比例。今年早些时候的 Gemma 3 走得更远，改为 5:1 的比例，即每五个滑动窗口（局部）注意力层才配一个全注意力层。

根据 Gemma 的消融研究，滑动窗口注意力对建模性能的影响极小，如下图所示。注意 Gemma 2 的窗口大小是 4096 个 token，Gemma 3 将其缩小到 1024。而在 gpt-oss 中，窗口只有 128 个 token，小得惊人。

再说个趣闻：官方发布文章指出，滑动窗口注意力显然早在 GPT-3 中就已使用：

> 这些模型使用交替的稠密与局部带状稀疏注意力模式，类似于 GPT-3。

谁能想到呢！？我回头翻了原始的 GPT-3 论文，里面确实提到过：

> 我们使用与 GPT-2 [RWC+19] 相同的模型和架构，包括其中描述的修改后的初始化、预归一化和可逆分词，不同之处在于我们在 Transformer 的各层中使用交替的稠密与局部带状稀疏注意力模式，类似于 Sparse Transformer [CGRS19]。

### 2.7 RMSNorm 取代 LayerNorm

最后一个源自 GPT-2 以来的小调整，是用 RMSNorm（2019）取代 LayerNorm（2016），这是近年来的普遍趋势。

与用 Swish 和 SwiGLU 替换 GELU 类似，RMSNorm 也是那种规模虽小却合理的效率改进之一。RMSNorm 与 LayerNorm 的目的相似，都是对层激活进行归一化，如下方图 11 所示。

你也许还记得，不久之前 BatchNorm 还是这项任务的首选。此后它逐渐失宠，主要是因为它更难高效并行化（由于需要计算批次的均值和方差统计量），而且在小批量时表现不佳。

从上方图 11 可以看到，LayerNorm 和 RMSNorm 都会把层输出缩放到合理的范围内。

LayerNorm 减去均值再除以标准差，使层输出具有零均值和单位方差（方差为 1、标准差为 1）。

RMSNorm 则把输入除以均方根（root-mean-square）。这会把激活缩放到可比较的量级，但不强制零均值或单位方差。在图 11 所示的这个例子中，均值为 0.77，方差为 0.41。

LayerNorm 和 RMSNorm 都能稳定激活尺度、改善优化，但大规模 LLM 往往更偏好 RMSNorm，因为它计算更便宜。与 LayerNorm 不同，RMSNorm 没有偏置（平移）项，并把昂贵的均值和方差计算简化为一次均方根运算。这把跨特征的归约操作从两次减少到一次，降低了 GPU 上的通信开销，提高了训练效率。

### 2.8 GPT-2 的遗产

我仍然认为，GPT-2 是学习 LLM 时绝佳的入门架构。它足够简单，不会让你迷失在层层优化技巧中，但又足够复杂，能让你扎实掌握现代 Transformer 模型的工作原理。

从 GPT-2 入手，你可以专注于基础知识（注意力机制、位置嵌入、归一化以及整体训练流程），而不会被新架构中的额外特性和调整弄得不知所措。

事实上，我认为值得花时间先学习、甚至亲手实现 GPT-2，再在其上叠加更新的改动。这样你不仅更容易理解这些改动，而且很可能更懂得欣赏它们，因为你会更清楚它们试图解决的局限或问题。

例如，我最近就是从我的 GPT-2 代码出发，从零实现了 Qwen3 架构；它与 gpt-oss 极其相似，这就引出了下一个话题：把 gpt-oss 与一个更新的架构进行比较。

## 3. 将 gpt-oss 与近期架构（Qwen3）比较

既然已经走完了从 GPT-2 到 gpt-oss 的演变，我们可以更进一步，把 gpt-oss 与一个更新的架构 Qwen3 进行比较，后者早三个月于 2025 年 5 月发布。

之所以选 Qwen3，是因为截至撰写本文时，它是顶尖的开放权重模型之一。此外，Qwen3 的一款 MoE 模型在可训练参数的总体规模上与 gpt-oss 相当接近，基本可以直接比较。

下方图 13 将 gpt-oss-20b 与规模相当的 Qwen3 模型进行了比较。

可以看到，gpt-oss 20B 与 Qwen3 30B-A3B 的架构组件非常相似。除维度外，两者的主要区别在于 gpt-oss 使用了前文 1.6 节（原文如此，实为 2.6 节）讨论的滑动窗口注意力（图中未画出），而 Qwen3 没有。

下面各小节将逐一介绍值得注意的细节。

### 3.1 宽度与深度

仔细看这两个模型会发现，Qwen3 的架构要深得多，有 48 个 Transformer 块，而不是 24 个（图 14）。

另一方面，gpt-oss 的架构要宽得多：

- 嵌入维度为 2880，而非 2048
- 专家（前馈）中间投影维度同样为 2880，而非 768

还值得一提的是，gpt-oss 使用的注意力头数量是 Qwen3 的两倍，但这并不直接增加模型的宽度，宽度由嵌入维度决定。

在参数总量固定的情况下，两种做法孰优孰劣？经验法则是：更深的模型灵活性更强，但由于梯度爆炸和梯度消失导致的不稳定问题（RMSNorm 和捷径连接正是为缓解这些问题而设），训练可能更难。

更宽的架构则因为并行化更好，在推理时更快（每秒 token 吞吐量更高），代价是更高的内存开销。

至于建模性能，遗憾的是，除了 Gemma 2 论文中的一项消融研究（表 9）之外，我不知道有什么好的同条件比较（保持参数规模和数据集不变）。该研究发现，对于一个 9B 参数的架构，较宽的配置略优于较深的配置：在 4 项基准上，较宽模型平均得分 52.0，较深模型平均得分 50.8。

### 3.2 少量大专家与大量小专家

如上方图 14 所示，同样值得注意的是，gpt-oss 的专家数量出奇地少（32 个而非 128 个），每个 token 也只激活 4 个而非 8 个专家。不过，它的每个专家都比 Qwen3 的专家大得多。

这很有意思，因为近来的趋势和进展都表明，更多、更小的专家更有益。在总参数量不变的前提下，这一变化在下方取自 DeepSeekMoE 论文的图 15 中得到了很好的展示。

值得注意的是，与 DeepSeek 的模型不同，gpt-oss 和 Qwen3 都没有使用共享专家。

公平地说，gpt-oss 专家数量少可能是 20B 规模的副作用。看下面的 120B 模型，他们确实增加了专家数量（以及 Transformer 块数），而其他一切保持不变，如下方图 16 所示。

20B 和 120B 模型如此相似，一个平淡无奇的解释大概是 120B 模型才是主要关注对象。而做出一个更小模型的最简单方法，就是让它稍短一些（更少的 Transformer 块），并减少专家数量，因为大部分参数都在专家那里。不过也可以猜测：他们是否先开始训练 120B 模型，然后砍掉一部分 Transformer 块和专家，再继续预训练（而不是从随机权重开始）。

无论如何，只缩放这两项（Transformer 块数和专家数）是相当不寻常的。例如，看看多个尺寸的 Qwen3 MoE 模型（下方图 17），它们在更多方面上是彼此更成比例地缩放的。

### 3.3 注意力偏置与注意力汇点

gpt-oss 和 Qwen3 都使用分组查询注意力。主要区别在于，如前所述，gpt-oss 每隔一层通过滑动窗口注意力限制上下文大小。

不过，有一个有趣的细节引起了我的注意：gpt-oss 似乎在注意力权重中使用了偏置单元，如下图所示。

自 GPT-2 时代以来我就没见过有人用这些偏置单元，它们通常被认为是多余的。确实，我找到了一篇近期论文，从数学上证明了至少对键变换（k_proj）而言是这样。此外，实证结果也显示，有无偏置单元差别很小（见下方图 19）。

你可能还注意到了图 18 代码截图中 `sinks` 的定义。在一般模型中，注意力汇点（attention sink）是放在序列开头的特殊"始终被关注"的 token，用来稳定注意力，这在长上下文场景中尤其有用。也就是说，即便上下文变得非常长，开头这个特殊 token 仍会被关注，它可以学会存储一些关于整个序列的通用有用信息。（我认为它最早是在《Efficient Streaming Language Models with Attention Sinks》这篇论文中提出的。）

在 gpt-oss 的实现中，*注意力汇点*并不是输入序列中的真实 token，而是按注意力头学习的偏置 logit，附加到注意力分数上（图 20）。目标与上面说的注意力汇点相同，但无需修改分词后的输入。

### 3.4 许可证

最后，与 Qwen3 一样，gpt-oss 模型采用 Apache 2.0 开源许可证，这很棒（这也是我自己的开源项目偏爱的许可证）。这意味着这些模型可以被蒸馏进其他模型，或在商业产品中不受限制地使用。

**开放权重与开源 LLM。** 这一区分已经争论多年，但为避免对这次发布及其产物产生误解，值得澄清一下。有些模型开发者只发布模型权重和推理代码（例如 Llama、Gemma、gpt-oss），而另一些（例如 OLMo）则发布包括训练代码、数据集和权重在内的全部内容，算是真正的开源。

按照这个更严格的定义，gpt-oss 是一个*开放权重*模型（和 Qwen3 一样），因为它包含权重和推理代码，但不包含训练代码或数据集。不过，业界对这些术语的使用并不一致。

我猜"gpt-oss"中的"oss"代表*开源软件*（open source software）；不过令我惊喜的是，OpenAI 自己在官方发布文章中明确把 gpt-oss 描述为开放权重模型。

## 4. 其他有趣的细节

前面几节描述了自 GPT-2 以来架构的演变，并讨论了它与 Qwen3（以及大多数其他近期模型）的相似之处，但还有几个值得注意的细节我尚未提及。这些内容不太适合放在前面的章节里，但仍值得一说。

### 4.1 训练概况

遗憾的是，关于训练集规模和训练算法的公开信息不多。我从模型卡报告（1）和发布文章（2）中摘录了最有意思的几块拼图：

> gpt-oss 模型使用了我们最先进的预训练和后训练技术训练而成 [...]（1）
>
> [...] 需要 210 万 H100 小时才能完成，gpt-oss-20b 所需的时间则少了近 10 倍。（1）
>
> [...] 包括一个监督微调阶段和一个高算力的强化学习阶段 [...]（2）
>
> 我们在一个以英语为主、纯文本的数据集上训练这些模型，重点是 STEM、编程和通用知识。（2）

由此可知，gpt-oss 模型是推理模型。210 万 H100 GPU 小时的训练算力，与大约是其 5.6 倍大的 DeepSeek V3 模型所用的 278.8 万 H800 GPU 小时大致相当。遗憾的是，目前还没有 Qwen3 训练时长的信息。

有意思的是，gpt-oss 的训练小时估算同时包含了用于指令遵循的监督学习和用于推理的强化学习，而 DeepSeek V3 只是一个预训练基座模型，DeepSeek R1 是在其之上单独训练的。

### 4.2 推理强度

如上一节所述，gpt-oss 模型是推理模型。但特别有趣的是，它们经过训练，让用户可以通过推理时扩展（inference time scaling）轻松控制推理程度。

具体来说，gpt-oss 模型可以在系统提示中接收"Reasoning effort: low/medium/high"（推理强度：低/中/高）指令，这会直接影响回答长度和准确率，如图 21 所示。

这种可调节性很有用，因为它让我们能够在成本、算力和准确率之间取得平衡。例如，如果任务很简单，比如回答一个直白的知识问题或修正一个小错字，我们就可以跳过冗长的推理。这样既节省时间和资源，又避免了不必要的长回答和啰嗦的推理过程。

有些遗憾的是，与 Qwen3 或 OLMo 不同，OpenAI 没有发布进行基于强化学习的推理训练之前的基座模型。基座模型对研究推理方法的研究者来说是特别有价值的起点（这也是我目前喜欢用 Qwen3 Base 的原因之一）。我猜 OpenAI 的这个决定更多是出于行业和生产用例的考虑，而非研究方面的考虑。

注意，最初的 Qwen3 模型也有一个开启/关闭思考（推理）模式的开关（通过分词器中的 `enable_thinking=True/False` 设置，它只是添加 <think></think> 标签来关闭推理行为）。不过，Qwen3 团队在过去几周更新了模型，放弃了混合模型，转向专门的 Instruct/Thinking/Coder 变体。

原因是混合模式的性能不如各自独立的模型：

> 在与社区讨论并反思之后，我们决定放弃混合思考模式。我们今后将分别训练 Instruct 和 Thinking 模型，以达到最佳质量。（来源）

### 4.3 MXFP4 优化：一个小而重要的细节

一个有趣的惊喜是，OpenAI 发布 gpt-oss 模型时，对 MoE 专家采用了 MXFP4 量化方案。

量化格式曾经是个小众话题，主要和移动端或嵌入式 AI 相关，但随着模型越做越大，情况已经改变。在这里，MXFP4 优化让模型能在单个 GPU 设备上运行。

实际情况如下：

- 大模型（指 120B）可以装进单张 80GB 的 H100 或更新的 GPU。这不算消费级硬件，但嘿，租一台单 H100 的机器比租多 H100 机器便宜多了。而且我们不必操心把模型分布到多张 GPU 上以及由此增加的通信开销。AMD MI300X 显卡从第一天起就获得支持，这也非常好！
- 较小的 20B 模型甚至能装进 16 GB 显存；前提是必须是 RTX 50 系列或更新的 GPU 才能支持 MXFP4。（补充：最近通过一个补丁增加了对 RTX 4090 等旧显卡的支持。）

注意，这些模型在旧硬件上也能运行，只是不支持 MXFP4，因此会占用更多内存。没有 MXFP4 优化时，bfloat16 格式的模型大约要占用 48 GB（gpt-oss-20b）和 240 GB（gpt-oss-120b）。

顺便说一句，我用 ollama 在我的 Mac Mini 上就能流畅运行 gpt-oss-20b 模型。它大约占用 13.5 GB 内存，相当合理。

### 4.4 基准测试

这些模型还太新，尚无独立基准测试。我查看了 LM Arena 排行榜，发现 gpt-oss 还没有上榜。因此，根据 LM Arena 用户的评价，Qwen3-Instruct 目前仍是最强的开放权重模型（图 22）。

看 gpt-oss 发布文章中提供的推理基准，可以看到 gpt-oss 模型与 OpenAI 的专有模型以及 Qwen3 不相上下（图 23）。

不过需要补充的是，gpt-oss-120b 的规模几乎只有 Qwen3 235B-A22B-Thinking-2507 模型的一半，而且能在单张 GPU 上运行。

然而，基准性能并不总能反映真实世界的可用性。在过去几天有限的使用中，我发现 gpt-oss 相当能干。话虽如此，正如其他人观察到的，它似乎有相对较高的幻觉倾向（其模型卡中也提到了这一点）。

这可能源于它在训练上大量侧重数学、谜题和代码等推理任务，从而导致了某种"通用知识遗忘"。尽管如此，由于 gpt-oss 在设计时就考虑了工具使用，这一局限可能会随着时间推移变得不那么重要。开源 LLM 的工具集成仍处于早期阶段，但随着其逐渐成熟，我预计我们会越来越多地让模型在回答事实性或知识性问题时查询外部来源（比如搜索引擎）。

如果真是这样，那么优先考虑推理能力而非记忆可能是明智的。这很像人类在学校（或者说在生活中）的学习：解决问题的能力往往比死记硬背事实更重要。

## 5. gpt-oss 与 GPT-5

OpenAI 度过了忙碌的一周，在 gpt-oss 之后不久就发布了期待已久的 GPT-5 模型。GPT-5 的发布很有意思。如果说这里有什么必须说的，那就是：就基准性能而言，他们的开源模型与其最好的产品相比竟然如此出色，这让我非常惊讶（图 24）。

总而言之，尽管有人说这次发布被过度炒作，但我很高兴我们有了一批真正强大的新开放权重模型，与最好的专有模型差距不算太大。当然，基准测试往往不能准确反映实际使用，而且基于有限的使用还为时尚早。但我认为，对于喜欢使用开放权重和本地（或私有托管）模型的人来说，现在是个好时代。
