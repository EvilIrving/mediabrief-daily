主播：大家好，这里是 AsyncTalk，我是主播。今天想跟大家聊一个其实之前已经说过很多遍的话题，就是 Bun。Bun 在 8 月 21 号发布了 1.4 版本。据作者 Jarred 自己说，这是 Bun 自发布以来变化最小的一个版本。但我相信如果你有关注 Bun 以及作者本人的推特账号之类的，你会发现他说的"改动最小"，意思是对用户来说改动最小。但整个 Bun 所有的代码框架其实已经完全变了。它之前是用 Zig 写的一整套运行时系统，来做 JavaScript 的 runtime。如果你去看它的代码仓库，现在已经不是这个样子了，它是用 Rust 重写的。

大概就在上个月，用 Rust 重写 Bun 这件事引起了很大很大的争论。到现在为止，基本上已经尘埃落定了，因为就像你知道的，用 Rust 重写的 1.4 版本已经发布出来了。

所以我觉得 AsyncTalk 可以先简单聊一聊用 Rust 重写 Bun 这件事。其实 Jarred 写了一篇文章，介绍他是怎么用 Rust 重写 Bun 的整个过程。这篇文章我看过，写得非常好，里面提供了非常多的经验。大家可以搜一下，自己读一遍，我比较推荐大家去读这篇文章。我觉得里面有很多点非常有趣，所以我单独挑出来和大家聊一聊。

我觉得最有意思的第一点就是：他只花了 11 天，就把整个 Bun 运行时从 Zig 的系统重写成了一整套 Rust 系统。我可以说，11 天在之前是不可能发生的事情。你非常难以想象一个互联网基础设施、一个 JavaScript 运行时，可以在 11 天内重写完。这在 AI 之前是不可想象的。但放到有 AI 之后，Bun 做到了。

那我们就来聊一聊这个重写是怎么做的。Jarred 分享说，他是开了 64 个 Claude 的并行实例去做的重写，按 API 计费花了 16 万美金。

首先我们看一下 Jarred 介绍的动机。我们可以看这张图：Bun 其实和 Node.js 一样，都是在一个 JavaScript 引擎之上做的扩展。它扩展出去对接各种系统能力、网络能力，来让你的 JavaScript 代码能够运行，能和文件系统交互，能做很多事情。但在下面一层，是一个核心的 JavaScript 引擎。这个引擎不做网络、文件系统、连接之类的其他事情，它只负责一件非常具体的事：执行 JavaScript。

对于 Bun 来说，它用的不是我们熟知的 V8。像 Chrome、Node.js 底层用的是 V8，但 Bun 为了更高的效率，选择的是 Safari 底层的 JavaScriptCore。你去研究一下就会发现，JavaScriptCore 是一个带 GC 的运行时。GC 就是垃圾回收（garbage collection），你不用主动关心要删除某个对象、释放某块内存。但 Zig 是手动管理内存的，它不是那种智能、现代、带 GC 的语言。所以 GC 和手动内存管理混在一起，对 Bun 来说是一个比较棘手的问题，因此引发了非常多内存相关的 bug。Bun 处理这些问题也很困难，不如干脆转到 Rust 来做这件事。当然 Jarred 也说过，这不怪 Zig，这是他们在这种情况下特有的问题。

然后我们来讨论一下成本。像 Bun 这样一个系统，如果不修 bug、不修安全问题、各种安全修复也不做，单纯重写大概要多久？我觉得比较合理的情况是，三到五个非常懂这套系统的资深工程师或首席工程师，也需要一年的时间来重写，你可以想象这个成本。所以在 AI 之前，软件一般是不重写的，要么新开一个项目，然后去做迁移。但有了 AI 之后，这变得有可能了。

现在进入主题：整个过程是什么样子的。说起来其实比较简单。先跟现有的代码库去聊，做出一个方案——移植方案，还有一些关于生命周期（lifetime）的文档——生成之后，再用两份文档做对抗性 review。所谓对抗性 review，就是以互相挑出对方毛病为目的进行的 review。review 之后的那份文件，很多时候质量相对还不错。这时先拿三个文件试一下，接下来再进行大规模的迁移。

运行的时候，对抗性 review 是由两个 reviewer 来评的，它们的 context window 是完全隔离的。因为自己做开发、自己给自己测试，是一个很明显的错误，所以我们需要 QA。在重写 Bun 的过程中，就是新开 reviewer 去校验之前的实现到底对不对。

重写完成之后，肯定要进行编译。大家都知道 Rust 的编译是非常可怕、非常严厉的，你自己试过的话大概会 get 到这一点。编译错误对我们人来说当然非常痛苦，因为要一个个处理。但对 AI 来说其实是一件好事，因为它告诉 AI 这个地方错了，接下来 AI 就可以针对这个错误去理解项目、理解代码，再进行修复。

当然，迁移过程中有没有问题呢？问题肯定非常多。首先第一点是提交。你想想，有 64 个实例在写代码，你可以理解成不是 64 个 Claude 实例，而是 64 个开发者在同一个 repo 里做事情，那你就可以想象肯定会有非常多的代码冲突。解决办法基本上就是用 git stash，以及加一些规则（rules）明确告诉它：不要提交不属于自己范围内的代码。

还有一点，如果你们公司有稍微严格一点的代码测试要求，你就会发现有些人为了让测试通过，会去改断言。具体什么意思呢？大概就是右边这段代码：你怎么让"一加一等于三"成立呢？一个办法就是去修改断言，把 1+1 的 expect().toBe() 改成等于 3，它永远返回通过。这样它就"完成"了，对不对？另一个办法：我怎么让自己的代码不犯错呢？答案是不写代码。只要我不写代码，我的代码就不会有 bug，对吧？对 AI 来说也是这样，它会写出大量注释来解释"这个地方我不写了，这里只是一个 stub 放在这儿"。这样的代码肯定不是我们想要的，对不对？

所以当这种情况出现时，我们要在 rules 里写明：如果一段代码需要加大量注释来解释，就可以认为这段代码是错的，让它再去想想、再去改。

还有其他各种各样的问题。比如磁盘：写代码一定会大量操作文件，文件写得实在太多，把磁盘写满了。

其实我前面说了那么多问题，最核心的一点在于：重写过程中会发生各种各样的问题。还是那个出发点，我们把 AI 当成人来看。人是可能犯错的，AI 当然也可能犯错。问题在于，当人或者 AI 犯错的时候，我们应该怎么做？我们只能从自己身上找原因。所以当具体问题出现时，我们不是说"你把这个代码实现了"就完事，而是要去改自己的规则，具体地告诉 AI 不可以弄虚作假，不可以用 stub 糊弄、不实现代码，而是应该怎样去做。

用现在非常流行的话来说，就是"context, not control"：你给 AI 充足的上下文，告诉它应该以什么原则去改代码，至于具体怎么改，它可以自己看着办。也就是说，你让 AI 去写一段代码，让它去获取一份文件，那它是通过文件系统获取、通过网络获取，还是从别人发的聊天记录里获取，其实并不重要。我们只要告诉它我们想要什么，让 AI 自由发挥。当 AI 犯错的时候，我们不仅要告诉 AI 它做得不对，同样也要修改我们自己的流程、自己的规则，尽量减少接下来继续犯错。

最后一点：为什么 Bun 可以做这个重写？在我看来，Bun 是一个比较特殊的项目。它不像我们大多数人做的业务项目，它是一个非常底层的运行时项目。所以这样的项目天生就有巨大量级的测试用例。而且这些测试用例不仅是 Bun 团队或 Jarred 自己写的，社区其他项目的测试用例也可以拿来用。举个例子，用 JavaScript 执行一段代码时，1+1 等于 2，不仅 Bun 自己的代码里有这个测试，在 Node 或者像 Underscore 这种库里也同样要能通过。这就带来了海量的测试用例，可以让 AI 去跑测试，纠正它自己实现上的问题，让它理解自己哪里写得不对。

接下来一个问题，我相信大家看完这篇文章都会有的疑问：我自己的项目能不能拿 Rust 来重写？我首先给出建议：你不要这么做。因为你和 Bun 这个项目很不一样。Bun 有非常大量的测试用例在支撑，所以当你一段代码写错的时候，可能有三五十个测试用例覆盖着你这么一行看起来无足轻重的代码，一旦有问题就能很明显地看出错误。

我们大多数观众写的都是上层业务代码。首先，我认为你的测试用例可能并不多，有个 50% 的覆盖率，我相信都已经是凤毛麟角了。另一方面，很多时候业务逻辑是写不了测试的。有时候你甚至去问产品经理，他都不知道这段逻辑应该是什么样子。我相信这是大家平常工作的常态。

所以像 Bun 这种有明确预期的东西，是有可能用 AI 重写的；而我们现实中绝大部分产品其实不太能这么做，这是非常危险的。因为你不知道 AI 写出来的是什么，也没办法去验证，你要花非常大的精力靠人工验证，甚至你都不一定知道验证的对不对。所以现实中，我并不建议大家真的自己去做这件事。

另一方面是成本。你要知道，操作 AI 的这个人需要相当高的技术能力：他知道怎么组织 AI agent，知道具体的业务逻辑是什么样的、应该怎么运行。找到这样一个人还是相当困难的。同样，API 的价格也是非常夸张地高。

OK，如果想到这里你还是觉得自己非常有信心，有充足的财力，也对自己的能力有信心，真的要开始重写，那我建议你可以采用 Jarred 这样的方法去做迁移：先跟现有的代码库聊出方案，然后通过对抗性 review 互相找出问题，做成一份完整的迁移计划；再通过编译错误、执行测试用例、中间各种各样的对抗性 review，最终把它迁移出来。你可以参考这个方案。

当然最重要的一点是：当 AI 犯错的时候，你要把它当成一个人来看。不仅要说"这个 agent 的实现有问题"，同样也要反思自己的 rules 里是不是哪里有问题，需要改自己的规则、改自己的流程。因为在做这样一个重写项目的时候，我们不仅自己是实现者，同时也是一个管理者。
