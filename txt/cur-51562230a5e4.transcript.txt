DSL 让大语言模型用得更可靠

大语言模型生成代码的速度惊人，但要确保它们生成的恰好是意图中的东西，它们需要清晰的边界。抽象和领域特定语言（DSL）提供了一条从一开始就引导大语言模型的牢固安全带。Tickloom——一个用于说明分布式系统行为的领域模型和 DSL——的例子表明，我们可以把大语言模型既当作迭代构建 DSL 的伙伴，又当作使用它的自然语言接口。在大语言模型的世界里，这样的 DSL 可以成为软件系统的关键真相来源。

2026 年 7 月 14 日

现代大语言模型拥有惊人的能力。它们可以从一段高层次的自然语言描述生成大量代码，有时甚至是整套系统。这里有一个重要前提：需要构建什么的"意图"要被清晰表达出来，用大语言模型能够映射到编码构建块的精确用语。不过有两点值得注意：事先规格的局限，以及设计是如何通过实现被发现的。

事先规格的局限

构建大型系统涉及许许多多细小的设计决策，这些决策不可能事先全部知道，也不可能完全由一份高层次规格驱动。规格充其量是一个起始假设：真正的约束、权衡和边界情况，是在我们推进实现时迭代地发现的。我们在更早的一篇文章里详细讨论过这一点，并称之为"事先规格不可能"（Upfront Specification Impossibility）。重点不是规格毫无价值，而是第一份规格是有待修订的假设，从来不是完成的蓝图。

自然的应对是迭代：细化规格，生成代码，审阅返回的结果，把学到的东西喂进下一轮。当每一轮产生的是小而可审阅的改动时，这个循环效果很好。

设计是通过实现被发现的

在我们仍在发现设计时审阅代码，和写代码不是一回事。审阅生成的代码时，我们是一块块地核对它是否映射到意图，并寻找可能的陷阱。但审阅很少逼我们真正和设计决策较劲。写代码则相反，它逼我们思考具体的决策——比如职责该落在哪里，或者为了让设计能继续扩展该暴露哪些边界。正是在做这些决策时，设计才最充分地显现出来。

我们用来编码的语言和范式，会塑造我们得到的设计洞见。函数式设计路线或面向对象设计路线会揭示设计的不同侧面，以及该范式自然带有的惯用法与模式。

那么大语言模型该放在哪里？我认为它们扮演两个角色。在我们塑造设计及其词汇时，它们是很好的帮手，充当头脑风暴的伙伴，帮我们探索设计空间、发现正确的抽象。一旦词汇确立，大语言模型就成了通向它的出色自然语言接口。

领域抽象与 DSL

一个有用的框架是领域驱动设计。它的核心洞见是在代码中构建领域的共享概念模型，然后用这个模型——DDD 称之为通用语言（Ubiquitous Language）——既演化代码库，又给团队一套思考和沟通的词汇。在这个模型之上构建一门领域特定语言往往非常有效：一种表达领域概念与操作的受约束语法。如此看来，大多数开发就是构建领域模型并用它演化系统的过程。大语言模型扮演两个截然不同的角色，取决于领域模型是否已经存在。本文将聚焦领域特定语言（DSL）如何与大语言模型协作。

为什么 DSL 与大语言模型如此合拍

DSL 和大语言模型合拍，是一种常见体验。PlantUML、Mermaid 和 Graphviz 是用于可视化建模的领域特定语言；SQL 是查询数据库的 DSL；Kubernetes YAML 是描述云基础设施的 DSL。它们不是通用编程语言——它们被故意收窄，用来在一个领域里表达一小套概念。大语言模型擅长从一段普通英文描述生成 Mermaid 图、SQL 查询或 Kubernetes 清单，也就不足为奇。

我的观察是：DSL 让大语言模型更可靠，是因为它们对少量上下文示例反应极好。像 Java 这样的通用语言，表达同一意图有很多合法方式。DSL 把这种变化削掉了。给模型几个例子，就足以可靠地生成正确语法。值得注意的是，一线模型在训练时已经大量接触过 PlantUML 或 Java 的流式接口，所以它们并非从零开始。有意思的是，更小、更受约束的模型在面对一门真正新颖的 DSL 时表现会如何。

对 agent——在自主的"生成并检查"循环中运行的大语言模型，而不是一次性生成——还有一个好处。DSL 几乎总自带确定性的校验器：解析器、JSON Schema、类型检查器或编译器。agent 可以生成一个候选，拿去过校验器，再根据错误修复，全程不必有人介入。关键的是，错误是用领域层面的话表述的——"选客户端之前不能选操作"——而不是深埋在生成代码里的堆栈跟踪。DSL 的工具链本身就是出色的安全带。我们会在下面的 Tickloom 例子里具体看到：DSL 的语法由宿主语言的编译器强制执行，运行结果也会被自动检查。

需要指出，这不是放之四海而皆准的方案。优势只在 DSL 足够小、足够受约束、几条上下文示例就能传达用法时成立。设计和维护这门语言及其语义模型也有真实的前置成本。因此回报集中在结构良好、真正受约束、并有校验器支撑的 DSL 上。

例子：用大语言模型生成富含图表的 PowerPoint 演示文稿

大语言模型让定制工具变得很容易。我教分布式系统时经常需要做演示文稿，里面大多是解释集群中分布式操作的图。UML 序列图对此很合适，但在讲解消息如何流过集群时，一次性展示完整序列图并不太有用。我需要一个工具，能在 PowerPoint 里一步步展示序列图。在大语言模型帮助下，我做了一个工具：它处理一份描述演示结构、并引用 PlantUML 图的 YAML，然后生成 PowerPoint。PlantUML 图用步骤标记，工具为每一步生成一张单独的幻灯片。这样创建富含图表的演示就很容易了。

提示词会生成带步骤标记的 PlantUML；另有一小段 YAML 描述幻灯结构（例如标题与所用图的引用）。即便提示说的是"创建幻灯 YAML"，也不是任意 YAML：因为生成 PowerPoint 的工具及其理解的规格被放进了提示上下文，模型才能直接产出可被工具使用的正确规格。

注意：在这一个例子里，大语言模型扮演了两个不同角色。首先它是共同设计者——帮忙塑造带步骤标记的 PlantUML 扩展，以及叠在现有 PlantUML 工具之上的幻灯 YAML。然后，一旦这个小 DSL 存在，它就变成把英文请求变成合法规格的自然语言接口。文章结尾我们还会回到这种分工。

构建语义模型

上一节的例子很直接。YAML 被用作载体语法，我直接处理解析后的语法树，实际上把语法树本身当作语义模型（尽管这会把语法和执行语义耦合在一起）。但在更复杂的领域，比如分布式系统，我们需要更复杂的语义模型，来表示领域中的概念以及我们在代码库中做出的设计决策。下面看一个基于我构建的小型框架的例子，用来快速构建和测试分布式系统。

例子：Tickloom——分布式系统的语义模型

实现法定人数键值存储或 Raft、Paxos 这类共识协议是艰巨的任务。即便实现由提示词、规格或精心构造的 .md skill 文件增量引导，异步运行时仍会暴露大得吓人的实现决策空间。线程模型、网络模式、存储协调、重试行为和时间语义全都缠在生成的代码里。问题不只是代码生成的复杂度，更是验证的复杂度。线程调度、网络延迟、进程暂停和时钟偏移所有可能交错所形成的状态空间太大，系统性地审阅和验证所有交互行为的正确性几乎不可能。这正是即便在最久经考验的分布式系统里，Jepsen 测试仍能找到 bug 的原因。

这正是语义模型有益之处。Tickloom 是我构建的一个小框架，用来构造和测试分布式算法。它的抽象不是通用运行时；它们是关于分布式进程如何行为的一套设计决策。每个节点运行在单线程的 tick 循环中：每次调用 tick() 将逻辑时钟推进一格，并按固定、确定的顺序处理待办工作（网络，然后消息总线，然后进程，然后存储）。时间以 tick 计量，而不是毫秒。消息是普通的 Java record。跨副本的协调通过一个已经了解同伴、广播和法定人数的 Replica 基类来表达。

线程、计时、网络投递不再是每条提示词里要重新决定的开放问题。留给算法作者的是真正的协议逻辑。例如，一个法定人数副本不过是用框架词汇表达的一组消息处理程序。

因为框架提供了词汇——Replica、quorumRequest、countResponseIf、MessageType、Handler——提示词可以停留在协议层面，而不是底层管道。语义模型本身充当上下文。提示词点名的概念在代码库里都有具体类型，所以大语言模型不是在发明线程模型或网络层——它是在固定、被充分理解的基底上填写协议逻辑。

即便没有 DSL，好的抽象也有帮助

DSL 是光谱的一端，而且并不容易构建。在动手做自己的语言之前，值得注意：一套干净的抽象已经是同一思路的轻量版——正如框架为上面的法定人数存储提供了词汇，库的具名类型和方法本身就是模型可以锚定的词汇。Tickloom 的语义模型其实就是四条接缝——负责计算与消息处理的 Process/Replica、负责通信的 Network、负责持久化的 Storage，以及负责时间的逻辑 Clock——这种分解在不引入任何新语法的情况下就做了大部分工作。

这就是为什么抽象，而不仅仅是 DSL，与大语言模型合拍。一条"把 Raft 实现为 Tickloom Replica"的提示词，可探索的状态空间有限。现有的 QuorumReplica 还可以作为上下文中的范例。

例子：为测试分布式系统场景构建 DSL

实现算法是一回事；演练它是另一回事。分布式系统中的微妙 bug 藏在特定的次序里：一次写入在读者的法定人数转移之前复制到某一个节点，一次在错误时刻愈合的分区，两个时钟已经漂移的协调者。直接针对测试套件写这样的场景，要摆弄 future，还要手写 tick() 循环。意图——"Bob 经 Byzantium 写入，Alice 经 Athens 写入，读者看到 Bob 的值因为 Byzantium 的时钟更快"——被埋在机械细节下。这样的代码也很难验证：有几十个附带决策（何时 tick、如何编码字节、调用哪个工厂重载）可能被大语言模型弄错，审阅者必须逐个检查。

于是我在语义模型之上构建了一门内部 DSL，其词汇就是场景本身的词汇——服务器、客户端、谁连到谁、每个客户端做什么、做的时候生效的是哪些故障。同一个场景变成声明式的 Scenario：给定服务器与客户端拓扑、给定各服务器时间，再写出 Bob 写入、Alice 写入、READER 读到 "B" 等步骤。故障读起来也像英语：partition(BYZANTIUM).from(CYRENE)、reconnect(BYZANTIUM)、delay(...).byTicks(100)。语法通过渐进式接口由类型系统强制执行——不能在拓扑之前声明步骤，也不能在选定客户端之前声明操作——整类畸形场景根本编译不过。因为这是建在 Java 里的内部 DSL，宿主编译器免费校验语法，畸形生成会以恰好钉在非法步骤上的编译错误返回，而不是运行时惊喜。

DSL 一旦存在，对故障场景的自然语言描述几乎直接映射到它上。像"复现不可线性化的法定人数读"这样的提示，会得到完全落在 DSL 受约束词汇内的场景。因为表面如此之小——它能生成的合法代码空间远小于合法 Java 程序的空间——大语言模型几乎没有幻觉空间，审阅者可以把结果当作实验描述来读，而不是逐行审计的代码。即便模型产生幻觉，内部 DSL 也会编译失败，从而让模型有机会修正错误。

与大语言模型协作的两个阶段

从上面的例子里浮现出一个模式：在每一个例子中，大语言模型都以两种相当不同的方式有用。

第一阶段是设计抽象或 DSL 本身。这里最好把大语言模型当作头脑风暴伙伴，而不是代码生成器。正如本文开头所主张的，构成语义模型的设计决策不可能全部事先规定——我们是在实现它们时发现约束、权衡和边界情况的。所以这个阶段天生是迭代的、由反馈驱动的：你提出一个结构，拿真实案例去试，看看哪里别扭，再把学到的东西喂回下一轮。大语言模型加快这个循环——它草拟替代方案、批评设计、把一个想法从一种语言移植到另一种——但你牢牢坐在驾驶座上，因为这些正是你需要理解和拥有的决策。让 DSL 好用的结构，比如让非法场景编译失败的渐进式接口，或与生成它的构建器分开保存的语义模型，是靠迭代收敛出来的，不是靠写规格再生成代码得来的。

第二阶段在抽象或 DSL 就位之后开始。大语言模型做的事变了：它成为你所构建之物的自然语言接口。本文中的提示词都是例子——"把法定人数存储实现为 Tickloom Replica"、"写一个复现 DDIA §10.6 那次读的场景"、"为这张图创建幻灯 YAML"。在每一种情况下，英文描述几乎直接映射到你定义的词汇，大语言模型之所以是可靠的生成器，正是因为抽象既提供了锚定提示词的上下文，也提供了检查结果的安全带。

作为真相来源的 DSL

有一种日益增长的趋势，是把提示词当作主要的真相来源。设计良好的 DSL 从根本上改变了这种动态。我观察到的与 DSL 协作的关键优势之一是：生成的程序本身往往成为人类维护的工件。因为 DSL 密集、富有表现力，且基本没有附带样板，它以一种在生成很久之后仍然可读的形式捕捉解决方案的本质意图。如果大语言模型根据自然语言请求生成了一个 Tickloom 故障场景，所得场景已经用领域词汇表达。如果下个月场景需要改动，不必找回原来的提示词再整段重生成。DSL 有足够的上下文让大语言模型知道意图并在此基础上工作。持久的资产不是提示词，而是 DSL 和语义模型。
