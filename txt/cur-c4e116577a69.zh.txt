# 实用循环工程

## 2026 年 8 月 14 日

我通常的工作方式是，同时让五到十个 agent 并行工作。有些任务，只要我对停止条件以及围绕它的约束有非常清晰的认识，我就很乐意完全委托给 agent。还有一些任务，我会想盯得更紧一些，对 agent 正在做的事情进行代码审查。

在此基础上，你可能听说过**循环工程**（loop engineering）。几个月前我写过一篇长博文专门谈它。

> 循环是一种自主、自我纠正的反馈周期：AI agent 反复行动、测试结果、调整做法，直到达成某个特定目标。

现在基本上有两个核心原语可以考虑。在 Claude Code 中，有一个 **goal 原语**，它可以推动单个有边界的任务一直往前走，直到达成某个特定目标，比如一条可度量的终点线被越过。然后是 **loop**，它按定时器或固定间隔重复运行，所以你可以用它来安排定期执行的改动。

## 在原语成为原语之前

我记得在 Claude Code 和 Codex 内置这些原语之前，循环工程很大程度上就是自己搭一个 bash 循环，纯手工打造。我当时就是这么做的。你可能还记得今年早些时候，我们不少人都在把玩 Geoff Huntley 的 Ralph 循环。我们做实验，分享各自的工作流，分享哪些有效、哪些无效，但基本都是在个人项目上，即使撞了墙，对我们来说也没什么大代价，因为那只是个人项目。

随着我们逐渐看清循环工程的哪些模式、哪些方面已经比较成熟，我认为我们对如何“看护”它有了更清楚的认识。现在我基本可以依赖 Claude Code 和 Codex 中这些原语的输出了。我们已经走了一段路。但与此同时，你需要非常勤勉，因为如果你把循环晾在一边，又没有认真想过最终目标或约束是否定义清楚，就可能陷入麻烦的境地。这就是为什么在决定是否使用它时需要区分情况：一个没有用户、也没有多少历史复杂性的常青（evergreen）代码库，和比如说一个银行的棕地（brownfield）代码库，是不一样的。

## Claude Code 团队如何看待循环

Claude Code 团队发表了他们对四种循环的看法，这与我使用这些原语的方式不谋而合（见他们的文章）。在进入正题之前，先摘录一段要点：

*在 Claude Code 团队，我们把循环定义为 agent 不断重复工作周期，直到满足某个停止条件。我们根据以下几点对几种不同类型的循环进行分类：它们如何被触发、如何停止、使用哪个 Claude Code 原语、每种最适合什么类型的任务。并非所有任务都需要复杂的循环；从最简单的方案开始，有选择地使用这些模式。*

*你发出的每一条提示都会启动一个手动循环，由你主导每一轮。Claude 收集上下文、采取行动、检查自己的工作，必要时重复，然后回复。我们称之为 agent 循环（agentic loop）。例如，让 Claude 创建一个点赞按钮。它会读取你的代码、进行编辑、运行测试，然后交回一个它认为可以工作的东西。接着你手动检查工作，再写下一条提示。*

他们的文章逐级讲解了每一层。

**关于基于目标的循环：**

*有时候，单轮是不够的，尤其是对更复杂的任务。agent 能够迭代时表现更好。你可以用 /goal 定义“完成”是什么样子，从而延长 Claude 持续迭代的时间。当你定义了成功标准，Claude 就不必自己判断什么算“足够好”而提前结束循环。每当 Claude 试图停止时，一个评估模型会检查你的条件，并把它打回去继续工作，直到目标达成或达到你设定的轮数。这就是为什么确定性的标准——比如通过的测试数量或超过某个分数阈值——如此有效。例如：/goal 把首页的 Lighthouse 分数提高到 90 或以上，尝试 5 次后停止。*

**关于基于时间的循环：**

*有些 agent 工作是周期性的：任务保持不变，只有输入在变。例如每天早上总结 Slack 消息。另一些工作依赖外部系统，与之对接的一种简单方式是按间隔检查它，并对变化作出反应。例如一个可能收到代码审查意见或 CI 失败的 PR。对于这些情况，你可以用 /loop 来触发 Claude 运行，它会按间隔重新运行一条提示。例如：/loop 5m 检查我的 PR，处理审查意见，修复失败的 CI。/loop 在你的电脑上运行，所以如果你关机，它就会停止。你可以用 /schedule 创建一个例程（routine），把循环搬到云端。*

**以及最高一层，主动循环：**

*触发方式：事件或计划任务，没有人实时参与。停止标准：每个任务在达成目标时退出，例程本身则一直运行到你关掉它为止。最适合：持续不断、定义明确的工作流，如 bug 报告、issue 分诊、迁移、依赖升级。用量管理：把例程分配给更小、更快的模型，把最强的模型留给需要判断的决策。*

他们关于验证的建议值得整段搬过来，因为它把手动检查变成了 Claude 自己执行的东西：

```
---
name: verify-frontend-change
description: Verify any UI change end-to-end before declaring it done.
---
# Verifying frontend changes
Never report a UI change as complete based on a successful edit alone.
Verify it the way a human reviewer would:
1. Start the dev server and open the edited page in the browser.
2. Interact with the change directly. For a new control (button, input,
   toggle): click it, confirm the expected state change, and screenshot
   before/after.
3. Check the browser console: zero new errors or warnings.
4. Use the Chrome Devtools MCP, run a performance trace and audit
   Core Web Vitals.
If any step fails, fix the issue and rerun from step 1 - do not hand
back partially verified work.
```
## Goal

我使用 goal 的方式是：用它来构建任何具体的工作，直到可以证明它已完成。比如，你可以用 goal 说：确保这个体验在五秒内加载完成，一直做下去直到完成。它会持续使用一个独立的评估检查，反复确认完成标准是否已经满足。更好的做法是，把使用什么工具也说得更具体。

至于我实际跑到某个数字的目标，我做过几件事。我用 goal 处理过 GitHub issue：审查并关闭最近 10 个 issue，或者审查并推进最近 10 个 issue，诸如此类。这有点半开放，对吧？又或者：让这个页面加载速度快 50%。有时效果很好，有时不行，但关键在于实验。

## Loop

loop 更像一个调度器，它盯着某样东西，或者按某种节奏重复执行一个模式。所以可以把它想成有点像 cron。它最适合做轮询日志或监控外部状态之类的事。你也可以用它来定期检查进展。如果你发现自己按某种节奏重复做某些任务，loop 就很适合。

## 我委托什么，盯着什么

就我而言，我每天大概会用五到十个 agent。很典型的情况是，同时并发的最多大约五个。其中有些任务可能相对安全一些。比如：嘿，我实现了这个功能，去给它写文档。或者，去再检查一遍我们的测试覆盖率是否足够。诸如此类。如果我在处理一个更复杂的问题，或者某件事我知道即使给了它一份好的规格说明——或者我自以为好的规格说明——也尽量给了一些停止条件，它仍有相当的可能做不全对，我就会盯得更紧一些。如果任务涉及任何哪怕只是有点敏感的东西，无论是我给了它某个系统的访问权限，还是这个功能恰好涉及身份认证，或者与安全、金融相关，我肯定会密切关注。

总的来说，我确实认为我们会走到这样一个地步：人们对委托越来越放心，前提是他们有清晰的方法来验证目标或停止条件已经满足。但你仍然需要看一看代码、看一看生成出来的东西，确保它达到你的标准。

这里另一个重要的习惯是：不要让干活的 agent 自己判定活干得好不好。一个子 agent 起草改动，另一个独立的子 agent 来验证。

有时一个 agent 会对某件事很有把握，而一个负责验证的 agent 能发现它们未必预料到的问题。比如，它认为自己生成的体验的基线性能其实没问题，但它只在桌面端评估性能，而你实际关心的是移动端的体验。这可能意味着 agent 在问题的某一个维度上非常自信，却忽略了另一个维度。

这一点我是吃过亏才学到的。我当时很好奇：有没有什么我们遗漏了、而用户既没在 issue 跟踪器里、也没在任何评论里直接反馈过的东西？于是我让它去看看我们的一些竞争对手，整理一份清单，再做一些 PR——没有推送，只是本地的 PR——展示解决其中一些差距可能是什么样子。我差点就把其中一些改动推上去了。但我其实没有足够仔细地看它们。我通读了它的调研，却没有足够仔细地看实现。所以我委托了任务，却也差点把判断一并委托了出去。等我真正仔细看了那些改动，才意识到它们会给用户带来大量额外的复杂性，而我个人认为收益并不大。所以我觉得有时你需要提醒自己：不要把品味和判断委托给你的 agent。你委托的是任务，然后要真正回头检查它是否达到你的标准。

顺便说一句，goal 背后的评估器并不是那个检查者。它不会以任何方式审视内容的好坏。它所做的只是检查对话记录，看你规定的硬性规则是否已被满足。

```
/goal Refactor the data-fetching layer in Dashboard.tsx until Lighthouse performance score is >= 92 and LCP is under 1.8s as shown by the Lighthouse CLI output. Do not change the public API of any hooks. Each turn must improve at least one reported metric; abort if two consecutive turns show no improvement. Stop after 10 turns.
```
## 我每天运行的工作流

我每天都运行的一个工作流是这样的：我有一个很受欢迎的开源仓库叫 Agent Skills。它有超过 80,000 颗星，直到最近，我们每天要审查的 pull request 多达 80 到 90 个。所以我每天都会花些时间去处理这些。现在有了 loop，你可以说：每 24 小时或每 12 小时，检查一下 GitHub 仓库中有没有新的未关闭 issue，提供一份紧急程度摘要，或者做一轮初步审查，诸如此类。

```
/loop every 1h "Check the GitHub repository for any new open issues. Provide a bulleted summary of their urgency."
```
## 组合 loop 与 goal

你还可以把 loop 和 goal 组合起来用：用 loop 安排检查，再用 goal 解决问题。比如你可以说：每 24 小时循环一次，检查 GitHub 上标记为 bug 的 issue。如果有，就用 goal 实现修复，直到所有本地测试通过，然后推送分支。

```
/loop every 24h "Check GitHub for issues labeled 'bug'. If one exists, use /goal to implement a fix until all local tests pass and push the branch."
```
不过也要记住，goal 在能往里塞多少内容方面有一些局限。

他们的文章里还有一个组合示例，展示了这一切的发展方向：

*上面这些原语，加上 Claude Code 的其他功能，比如自动模式和动态工作流（研究预览版），可以组合成一个用于长时间运行工作的循环。例如，要处理收到的反馈，你可以使用：/schedule（研究预览版）运行一个检查新报告的例程，/goal 定义“完成”是什么样子，skills 记录如何验证。动态工作流负责编排 agent，对每份报告进行分诊、修复，并审查修复。自动模式让例程运行时不必停下来请求权限。合在一起，提示可能是这样的：/schedule 每小时：检查 project-feedback 频道中的 bug 报告。/goal：在本轮发现的每份报告都完成分诊、处理并回复之前不要停止。修复 bug 时，使用一个工作流在并行的 worktree 中探索三种解决方案，并让一个评审者以对抗的方式审查它们。*

## 分诊系统实际做了什么

在 PR 分诊中，当 loop 和 goal 协同为我工作时，我最终得到的是这样一个系统：它让我能够真正持续地接收 PR 和 issue，每天都能掌握摆到我面前的事情，尤其是能够交叉对照。这对我来说意义重大。如果我想推进某个特定目标，比如：嘿，我们要重做系统的这一部分，我需要确保凡是涉及这部分的 issue 都会因这次重做而被关闭，或者确保我们不会踩到别人的脚，我就可以把这些定义清楚。

计划任务非常适合定期审查新的 PR，关闭那些明显不合适的。举个好的停止条件的例子：我们有一套贡献指南，其中包括诸如“我们目前不接受翻译”这样的条款。

这并不是说我们不在乎，而是翻译对我们来说很难维护，因为提交进来的语言我们往往并不都会。所以如果我们告诉它，关闭任何触及贡献指南这一方面的 issue 或 PR，按计划运行时它在这件事上能做得非常好。这样就减少了我们需要审查的总量。

## 循环给不了你什么

经常有人问我，循环工程不太适合什么。一般来说，如果你对“完成”的最终状态、什么算完成、什么算好没有清晰的概念，它可能就不是适合你工作的模式。例如，一个模糊的目标会是“一直做下去，直到这个 UI 设计变好”。这是什么意思？对谁来说好？如何评估？需要人类品味、主观设计或开放式创意探索的任务都不太合适。当你对目标有相当清晰的认识时，我认为循环是值得考虑的选项。

## 细则

循环在原地空转的一个典型迹象是：同一条命令被一遍又一遍地尝试，结果却没有任何变化。同一条命令第三次执行，结果和第二次相比毫无变化，那大概就该停了。

还有一条值得知道的细则：周期性循环在创建七天后过期。我之前一直告诉别人是三天，其实是七天。而且循环是会话级的，所以当你开始一个新对话时它们就会停止——不过用 `--resume` 或 `--continue` 恢复该会话，会把仍在七天有效期内的周期性任务带回来。如果你需要比会话活得更久的东西，可以用 /schedule 在云端运行。

如果有某项检查你已经每天早上手动做，那就是你的第一个循环。我的第一个是那堆 pull request。
