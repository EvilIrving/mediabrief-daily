便利的代价（The cost of convenience） ｜ Surma ｜ 文章 ｜ https://surma.dev/things/cost-of-convenience/

Surma 想弄清楚什么才算好的开发者体验。他的方法是每次试用一个库或框架时留意自己"这感觉不对"的瞬间，再提炼原因。

他先描述 Web 平台：几十年由无数人扩展而成，从文档平台长成了强大的应用平台，因此在三个维度上都"坑坑洼洼"：抽象层级（从底层的 WebAssembly 到声明式的 CSS）、API 设计风格（老 API 生在 async/await 之前），以及各浏览器的支持与行为。"可扩展 Web 宣言"让平台优先提供底层原语，高层抽象交给生态。尽管如此，Web 开发者大多已经学会并接受了它，HTML、CSS、JS 乃至 pushState 的怪癖都熟了。

他的核心观察是：自己手里明明有解决问题的平台知识，抽象却不让用，这最让人恼火（Evan You 也说过类似的话）。平台的不平整看似是摩擦之源，但开发者往往早已掌握它；逼他们改用抽象，未必是净收益。他借 Martin Fowler 的说法区分库和框架：库是你调用它，框架是"别打给我们，我们打给你"的控制反转。框架把自己放在宇宙中心，一旦遇到它没预料的用例就麻烦了。

于是有几条原则。其一，逃生舱必不可少，比如 React 的 ref；但逃生舱往往让人一路掉回平台底层，得自己把框架替你做的事重做一遍，框架离平台越远，代价越大。相比之下，库和代码的接触面小，换起来爆炸半径也小。其二，复用平台已有的模式和惯用法。比如子组件给远处祖先传数据，平台上派发一个自定义事件就行，React 却要你层层传回调或学 context，除了"更地道"没什么实际好处。入门教程尤其应该让新手尽量用已有技能，一次只引入一个新概念。他把挫败感归结为：开发者没法用已有技能，或者因为按自己的方式做而受到不成比例的惩罚。所以抽象要可选，选择加入或选择退出都行，但"可选"是必须的；靠近平台模式还意味着卡住时能去 StackOverflow 自救。

其三，也是他最主要的建议：分层架构。不要做一个包住全部平台的单层抽象，让开发者只能二选一；而是像立体停车场一样一层叠一层，每层多一点便利，也多一点主张和约束，开发者按需下降一层两层。底层不该抽象掉平台，而应拥抱平台原语；每层只用下一层实现，这也逼着作者真正吃自己的狗粮。他以设计系统为例：现在要么是纯 CSS 类库，要么是 React 组件集，React 组件不合用时只能打猴子补丁、复制源码，或者退回 HTML+CSS 重写全部行为，用别的框架的人更是只能重写。若做成纯 CSS、Web Components、薄薄一层 React 封装三层，React 用户可以逐个组件降到 Web Components，Svelte、Solid 用户只需写一层薄封装。这一思路同样适用于 CLI、GraphQL API 等。

结论是：想清楚目标开发者已经带着什么技能，复用它们来降低认知摩擦，在入门流程中错开引入新概念；每个抽象都应可选、有逃生舱，并尽量暴露顶层之下的各层，让开发者能掌控、能自救。
