把 React 当作 UI 运行时（React as a UI Runtime） ｜ Overreacted, Dan Abramov ｜ 文章 ｜ https://overreacted.io/react-as-a-ui-runtime/

Dan Abramov 的一篇长文，不讲怎么用 React，而是把 React 当成一种"UI 运行时"，系统地解释它的编程模型背后的概念。他说读完你可能会更理解 React，也可能觉得它太复杂、再也不想碰，无论哪种他都欢迎反馈。

他从"宿主树"讲起：React 程序输出的是一棵随时间变化的树，比如浏览器的 DOM 或 iOS 的视图层级，React 的价值在于它对宿主树的变化是可预测且一致的。宿主实例就是这棵树里的节点，React 通过渲染器（如 ReactDOM、React Native）去操作它们。React 元素是描述宿主实例应该是什么样的普通对象，轻量且不可变，每次渲染都会生成新的元素树。入口是把元素渲染进容器；之后再次渲染时，React 通过"协调"来决定是更新现有实例还是新建：同一位置、同一类型就复用并更新属性，类型变了就销毁重建。条件渲染时用 null 占位保持位置不变；列表则需要 key，让 React 在重新排序时也能对上号。

接着是组件：返回元素的函数，它的输入是 props，应当是纯的，对 props 只读，但内部可以有局部变化。React 自己调用组件而不是你直接调用，这样它才能做惰性求值、管理状态、在合适的时机渲染。他依次讲了：状态是与树中某个位置绑定的局部可变数据，由 Hooks 提供；一致性：React 会把整个更新做完再修改宿主树，避免中间状态；记忆化可以跳过不必要的渲染；原始数据模型让 React 不追踪细粒度变化，而是重新渲染组件；批处理让同一事件中的多次 setState 只渲染一次；调用树就是每个组件实例所在的位置；context 把值传给子树而不必层层传 props；副作用在渲染之后执行，并通过依赖数组决定何时重跑；自定义 Hook 用来复用有状态的逻辑，而 Hooks 必须在顶层无条件调用，因为 React 靠调用顺序来对应状态。

他的落点是：React 的许多设计，看似奇怪的规则，其实都源于它作为一个负责管理宿主树、状态和副作用的运行时的需要。
