Gavin Henry：欢迎收听《软件工程电台》（Software Engineering Radio），我是主持人 Gavin Henry。今天的嘉宾是 Daniel Stenberg。Daniel 是瑞典的互联网协议专家和开发者，参与开源软件已有 30 年，最为人所知的身份是 curl 项目的创始人和首席开发者——curl 是全世界使用最广泛的软件组件之一。他还参与 IETF 的协议制定工作，写过关于 curl、开源、HTTP/2 和 HTTP/3 等主题的书，也是一位知名的公开演讲者。Daniel 目前受雇于 wolfSSL。

Daniel，欢迎再次来到《软件工程电台》。我的介绍有没有漏掉什么你想补充的？

Daniel Stenberg：我觉得没有，基本涵盖了我做的事。

Gavin Henry：今天这期的题目是"Daniel Stenberg 谈从 curl 中移除 Rust"。我希望听众能从中了解：你为什么想把 Rust 引入这个项目；你是怎样把 Rust 引入 curl 的；你为什么——我就用"放弃"这个词吧——决定不再继续；以及未来会怎样。然后希望能帮大家理解从中得到的经验教训，不管是别人想做类似的尝试，还是你们将来再回头做这件事时，都能更明智地推进。

我们先打个基础，提醒一下听众 curl 是什么。我想你大概是回答这个问题的最佳人选吧，Daniel。

Daniel Stenberg：我不确定我是最佳人选。说实话，我有时候都很难解释清楚它，我想这取决于你对这些东西了解多少。curl 是一个命令行工具和一个库，用来做网络传输，准确说是使用 URL 的互联网传输。它最广为人知的用途是做 HTTP 和 HTTPS，但它支持 28 种不同的 URL 协议，包括邮件协议 IMAP、SMTP、POP3，还有 FTP、SFTP、SCP，所以它支持很多传输协议，我还可以一直列下去。

我说到 curl 的时候，开发者想到的通常是命令行工具。但当然，libcurl 才是使用最广泛的组件——它是一个库，被嵌入到数以百万、数以十亿计的设备里，这些设备都用 libcurl 做互联网传输。所以 curl 一个非常重要的关键因素是稳定性、安全性，尤其是我们提供的 ABI 和 API 稳定性：一种可靠、稳定、基本上可以永远用下去的方式，让全世界所有用户都能直接升级到最新的 curl，而不必痛苦地去适配 ABI 或 API 的变化。

Gavin Henry：这需要大量的精力、大量的测试和大量的工作。

Daniel Stenberg：确实如此。

Gavin Henry：你说它被用在数十亿台设备上。你有没有一个按数量排的前五名清单，帮听众了解一下它都用在哪里？

Daniel Stenberg：按数量来说，我觉得什么都比不上手机和平板。它是 iOS 和 Android 里的嵌入式组件，所以基本上现存的每一部智能手机和每一台平板上都有它。那大概有 70 亿台设备之类的。

Gavin Henry：我本来想问它大概有多少用户，这就回答了。

Daniel Stenberg：是的。我一般会避免用"用户"这个词，因为有点怪。它是个库，是被别人拿去用的，不算真正的用户，而是嵌入在各种工具和应用里。它被用在所有这些手机上，有个好玩的地方：libcurl 是一个库，嵌在这些手机操作系统里，但系统并不把这个 API 开放给应用，所以很多应用会自带一份 libcurl 打包发布。所以如今一部典型的手机上其实装了好几份 curl，因为很多用户量巨大的应用也自带并打包了它——它们想用，但没法从系统层面调用。所以一部装了很多应用的典型手机上，可能有五份或十份 curl。

Gavin Henry：哇。我还想说，我刚买了 Nintendo Switch 2，有人发现它的鸣谢名单里也列了 curl，所以任天堂也在用。

Daniel Stenberg：是的，游戏机里也嵌入了它。

Gavin Henry：那你有没有从这些公司那里得到任何形式的支持？Android、苹果、谷歌、任天堂？还是说你不方便讲？

Daniel Stenberg：标准答案是没有。我有几个客户，确实只有几个，比我希望的少太多了。像这些大公司，大多数都只是免费用开源版本，看起来也挺满意。我尽量争取让更多的人真正付费购买支持，帮他们正确地使用 curl，这样他们就能资助我的维护和持续开发工作——当然不只是我，还有团队的其他人。但有时候这很难推销。

Gavin Henry：团队里有多少人是全职的，多少是志愿者？

Daniel Stenberg：我是唯一的全职。

Gavin Henry：所以是个很小的团队。每次有人讲起这种关键软件、关键的互联网软件，结果背后只有一个人或者几个人，我都觉得不可思议。除非你身在开源圈，否则没人真正理解这一点。

Daniel Stenberg：确实。而且它也有点受困于经典的经济学规律：如果不是非付钱不可，他们就宁愿不付。所有这些公司都不是非付不可，所以大多数就不付，尽管从道义上或者别的角度说，他们也许应该付、也可以付。

Gavin Henry：是的，我想他们都以为有别人在付。

Daniel Stenberg：而且也没人真的问过这个问题。我也不知道。

Gavin Henry：好。我联系你，是因为读到你去年 12 月——也就是六个月前——写的一篇博客，题目叫《放弃 Hyper》（Dropping Hyper）。因为我身在 Rust 圈，做过好几期关于 Rust 的节目，我知道 Hyper 是什么。在进入下一部分之前，你能先讲讲 Hyper 是什么吗？

Daniel Stenberg：Hyper 嘛，可以说是 Rust 世界里最接近 libcurl 的替代品。它是一个用于 Rust 的 HTTP 和 HTTPS 库。我想这基本就概括了。它是一个以各种方式做 HTTP 的 API。

Gavin Henry：那我先按我的理解总结一下背景，你当然可以纠正我。从历史上看，curl 一直存在或曾经存在内存相关的问题和漏洞，而推动这件事的动力，是想把一个用内存安全语言写的 HTTP 库版本引入 curl。对吗？

Daniel Stenberg：对，完全正确。curl 是用 C 写的，它诞生于 90 年代，是那种老派、经典风格的开源项目。所以它用 C 写成，C 是不安全的，这些年来我们当然也有过不少内存相关的安全问题。curl 还有一套后端系统，意思是你在构建 curl 时，基本上可以决定要用哪些后端，而这些后端都由不同的第三方库提供支持。比如你想要 TLS 支持，TLS 就由别人写的外部库提供，我们通过接口去调用；通常你可以在不同的库之间选择想要支持哪个 TLS 库，等等。我们在 SSH、内容编码、IDN、域名解析等不同部分也都有不同的后端。

所以 curl 本来就天然地在构建时提供一系列可选的后端。于是想法就是：curl 是用 C 写的，也许我们应该尝试让最终的构建使用更多内存安全的代码。所谓内存安全，就是使用比如用 Rust 写的库——说到这种替换，Rust 大概是最合适的选择。这件事其实是 ISRG 在他们的 Prossimo 项目里资助的。ISRG 就是 Let's Encrypt 背后的团队，他们有一个持续进行的项目，把内存不安全的项目替换成安全的项目，基本上就是把东西从不安全的语言重写成安全语言。他们资助了这件事，想法是我们为 curl 引入一个新的 HTTP 后端，由 Hyper 这个 Rust 库提供支持。这样，用这个 HTTP 后端构建 curl，就能得到一个比原来使用更多内存安全代码的版本。但它是一个可选的构建方式，你可以用原生的 C 版本，也可以用 Hyper 驱动的版本。

Gavin Henry：总结一下：curl 项目可以提供 28 种不同的协议，取决于你编译时怎么配置，或者操作系统、构建环境里有什么。这些协议都有一个后端，比如说到 HTTP，我们可以选择用 curl 原有的 C 实现，或者如果有别的实现，就用别的；TLS 也一样，你可以用不同的库来提供这种协议能力。

Daniel Stenberg：正是这样。

Gavin Henry：因为传统上你们有很多内存安全问题，而 Rust 是如今引入进来最合理的选择。而用 Rust 把整个东西彻底重写——或者重写任何东西——都是疯了。

Daniel Stenberg：所以像这样一点一点地做，基本上就是引入更多内存安全性的唯一可行之路：使用越来越多的替代后端，使用用内存安全语言写的后端。我们当时的想法就是这么做——而且我们也真的做了，所以它不只是一个想法，也真的变成了现实。

Gavin Henry：那你们是怎么决定的？Hyper 是 Rust 里的头号选择吗，还是你们有一些评判标准？能举例讲讲当时的思考过程吗？

Daniel Stenberg：其实没有多少思考过程。因为我对 Rust 生态和 Rust 世界并不太熟，所以我基本上就采纳了 ISRG 那边的建议，Josh 他们那些人。我也和 Hyper 的首席维护者 Sean McArthur 谈过，所以过程其实挺快的：我们判断它看起来是个合适的库，而且在技术栈中处于合适的抽象层级。所以我们认为它适合拿来构建。

Gavin Henry：好，所以你们有人指导。ISRG 是什么的缩写？Internet 什么来着？

Daniel Stenberg：Internet Security Research Group，互联网安全研究组。我觉得这个名字多少有点没什么意义。

Gavin Henry：他们就是 Let's Encrypt，那是他们做出来的。

Daniel Stenberg：我想他们是个基金会之类的，非营利组织。

Gavin Henry：很酷。所以他们在这方面给了指导。

Daniel Stenberg：没错，而且他们资助了这项工作。我们来来回回讨论了一下他们的想法和我的想法，以及怎么把它变成现实。然后我也和 Sean 谈了很多。

Gavin Henry：就是 Hyper 的维护者。

Daniel Stenberg：对，正是。因为我开始做这件事的时候——curl 是用 C 写的，Hyper 是用 Rust 写的，这是好几年前的事了——需要有一种方式从 C 去调用 Hyper，需要一个胶水层来确保我们能从 C 正确地使用 Hyper。而 Hyper 当时还没有这个东西。所以我和 Sean 在这方面来回沟通了很多，一边在 curl 里做这项工作，一边去创建那个胶水层。实际上我们得在好几个不同的地方同时干活。

Gavin Henry：所以并不是说有一个现成的 Rust 库，已经准备好了供 C 使用的外部函数接口，你直接拿来就用。里面要做的事多得多。

Daniel Stenberg：没错，这件事做得相当早，有很多活动的部件，要做很多事情才能让它跑起来。

Gavin Henry：是的，过去五年里 FFI 的整体状况改善了很多，对吧？我自己在另一个项目里也在用。

Daniel Stenberg：是的，确实有了明显的改进。因为我提到了所有这些不同的后端，你现在仍然可以用其他 Rust 后端来构建 curl。比如我们支持 rustls，也就是 Rust 写的 TLS 库；我们也支持 quiche，那是一个 HTTP/3 和 QUIC 库，同样是用 Rust 写的。所以仍然有办法用 Rust 驱动的后端来构建 curl，我也仍然在接触那个世界。

Gavin Henry：所以你们移除的只是提供 HTTP 的 Hyper。

Daniel Stenberg：对，我们并没有移除所有使用 Rust 的方式，只移除了 Hyper。而 Hyper 实际上是唯一的 HTTP 后端；我刚才提到的其他几个，是 TLS 后端和 HTTP/3 后端，它们在技术栈中接入的位置不同。Hyper 是 HTTP/1 和 HTTP/2 的。

Gavin Henry：因为这是 ISRG 资助的，他们也给了你们指导，所以你们不用在选什么上做很多决定，也不必用 Rust 从零开始写协议部分。

Daniel Stenberg：没错，因为那从来都不是个好主意——那工作量非常大，而且我自己也不算是 Rust 程序员，本来也不是用 Rust 写它的合适人选。而使用一个已经存在、经过验证、能用的东西，我认为是相当合适的选择。

Gavin Henry：是的。按我的理解，说到引入 Rust、用 Rust 重写或者移植到 Rust，选项要么就是你们做的这样，引入一个成熟的东西；要么就是移植 C 代码——一个屏幕上看着 C 代码，另一个屏幕上把那段 C 用 Rust 重写。这确实能行，但某种程度上也不行，因为还有符合 Rust 惯用法的写法。顺便说一句，我做过一期这方面的节目。我今年大部分时间都花在 Rust 相关的内容上，给听众列几期：最近一期是第 672 期，和 Luca 聊生产环境中的 Rust；第 670 期和 Matthias 聊用 Rust 做原型，那期聊得特别愉快；还有第 659 期讲符合惯用法的 Rust。大家可以去听听。总之，从零开始写，或者把 C 代码移植成对等的 Rust 代码，都是疯狂的。

在进入你们具体怎么做之前，最后收个尾：你看到的内存相关问题大多出在哪里？是在你们对 HTTP 规范的实现里，还是分散在不同后端、不同部分？最痛的地方在哪儿？

Daniel Stenberg：这个问题问得很好。我其实不认为我们的内存问题主要集中在 HTTP 相关的解析代码里。所以这件事并没有真正针对我认为问题最多的地方。但要找出这种规律真的很难：我们在哪里犯错最多，又该怎么修？通常我们遇到安全问题时，当然会试着找规律，看看能从中学到什么，以后怎么避免，等等。这些问题往往以各种方式分散在各处。另外，在过去，我想大概有十年了吧，我们在 curl 内部做了好几种不同的事情，让过去曾经犯过的那些错误更难再犯。所以我也认为，有很多方法其实就是写出更好的 C 代码，来避免其中一些错误。很多事情是同时进行的：在尝试引入更多 Rust 代码的同时，我们也确保写出更好的 C 代码，避开那些显然太容易让我们出错、引入错误的做法。所以现在我们引入了更多内部辅助函数，以及关于怎么做事的规则，就是为了更多地规避出错的风险。

Gavin Henry：对，把一些有风险的操作集中到一处来做。

Daniel Stenberg：没错，比如就是这样。

Gavin Henry：是的，我关注你的博客，还有你在 LinkedIn 上发的东西。我记得有一个漏洞大概存在了二十年之类的，因为某种冷门用法而突然冒了出来。所以总有东西潜伏在那里。

Daniel Stenberg：是的，是的，安全真的很难。

Gavin Henry：你还发过帖子——我会把它放进节目说明——讲那些新的 AI 工具涌进来报告安全和内存问题，结果全是编造出来的，提交的东西跟代码根本对不上。不过反过来说，也许那里面有什么东西可以做些分析，试着找出某种关联。但我觉得目前我们对这些东西已经有点失去信任了，所以那方面还有工作要做。

Daniel Stenberg：哦，是的。当然，理想状态是这些工具应该能找到问题，因为理论上它们应该可以，但我认为在它们能可靠地做到之前，我们还有更多工作要做。

Gavin Henry：是啊，我总想象它们会把你的代码走一遍，跑一些任务，生成模糊测试任务，做我们每天都听说的那些事，然后给你一份漂亮的小结报告："对了，我们刚做了件奇怪的事，发现了这个。"你会说"哦，谢谢"。但我不知道，我们离那一步还有点远。

Daniel Stenberg：是的。

Gavin Henry：那我们继续。先收个尾：Hyper 是最流行、最成熟的——不是唯一的，但是别人建议你们用的那一个；你们没有从零开始，因为那太疯狂了；而这次引入 Rust 并不是为了解决最多见、最常见的那类内存问题，只是因为这是正确的起步方式。

Daniel Stenberg：正是这样。想法就是，既然我们已经有不同后端这个概念，这就是又一种方式：再引入一个后端，替换掉原生代码。理论上我们将来还可以引入更多后端，通过创建用 Rust 写的新后端来替换 curl 的更多部分。所以理论上，随着时间推移，这多少就成了我不会去做的那种"用 Rust 重写"，只不过是另一种做法：在很长一段时间里一个组件一个组件地替换。

Gavin Henry：所以这是唯一一处……我们有实现各种协议的后端，既然这一个被拿掉了，现在是只剩 curl 自己的实现，还是还有别的？

Daniel Stenberg：对，基本上是这样。HTTP 后端这个概念是我创造的，在此之前并不存在。我为了能用 Hyper 才创造了它——用 Hyper 或者用原生实现。后来我移除了 Hyper 这条路，就没有其他后端了，所以我基本上把那扇门也关上了。现在我们不再有任何 HTTP 后端，只有原生代码。

Gavin Henry：是的，我想我在你们 GitHub 仓库里读到了移除的历史，你把所有选项都关掉了。

Daniel Stenberg：我也认为，整个 Hyper 之旅、这场冒险的部分教训，就是下次我们再尝试时应该怎样做这样一个 HTTP 后端。我觉得这次做得有点别扭，这也是我把它彻底移除、而不是为将来的可能性留着它的原因之一——它的做法并不是最好的。此后我们重塑了内部结构，确实改进了很多东西，重构了 curl 和 libcurl 的内部。所以我认为下次我们再尝试做 HTTP 后端时，处境会好得多，我们掌握的知识更多，会用稍微不同、更好的方式来做，以一种更面向未来、不那么取巧的方式接入 curl。

Gavin Henry：是的，我想它不是那种你为某个协议做的标准后端，从 libcurl 核心去调用后端钩子——不管你们是怎么做的——那一整条路径会完全不同，是全新的。

Daniel Stenberg：正是，因为我们从这件事中学到了很多，现在知道得更多了。

Gavin Henry：所以这不是失败，只是一个学习过程。

Daniel Stenberg：是的，绝对是。

Gavin Henry：好，这正好引到实际加入 Rust 这件事上。我自己做过，有点概念，但我想先描绘一下你们做这件事之前是什么样子。通常配置的时候——这是个基于 Autotools 的项目，所以就是 configure、make、test，对吗？

Daniel Stenberg：对，基本上是这样。还有 CMake 选项。

Gavin Henry：你们也有 CMake？

Daniel Stenberg：是的，是的，两者基本上功能相当，你可以随便选用哪个。

Gavin Henry：好，所以你在做配置这一步，运行配置脚本——我们就拿 Autotools 说吧——你可能会加 --help 看看怎么构建、有哪些选项。而在 2020 年那个时候，configure.ac 脚本里还没有任何东西能让你检测有什么、构建了什么，也没有东西能说"构建这个或那个"，对吧？

Daniel Stenberg：对，正是这样。

Gavin Henry：很好。所以当时也没有设置任何变量，让你据此说"好，用这段代码而不是那段代码"、"编译这段代码或者那个后端"，或者检查 Rust 是否安装、Rust 生态是否可用。

Daniel Stenberg：对，完全正确。

Gavin Henry：真正的零起点。那你是怎么开始这个过程的？能举例讲讲那段时间你最先处理的是哪些部分吗——如果你还记得的话。

Daniel Stenberg：当我想开始支持这样一个新东西时，通常第一步是确保我们能用 configure 检测到它。所以我先加 configure 规则，让你可以加上 --with-hyper 并提供安装路径，基本上就跟别的一样。因为我们支持用不同后端构建，你在 configure 命令行上选其他后端的方式，就是选这个后端的方式：你指定"我想用 Hyper，Hyper 装在这里"，然后我提供相应的 configure 魔法，让它检测 Hyper 确实存在、版本正确，然后确保能用它构建。那是简单的部分，只是确保库在那里、能用。

Gavin Henry：那你在 Rust 这边会怎么做？是不是要写个小 Rust 程序，再加上 Hyper 模块？

Daniel Stenberg：基本不用，因为我们需要的是 FFI 版本——其实甚至不是自动生成的 FFI，而是 Sean 先写的一个胶水库。所以我其实并不直接调用 Hyper 库，我调用的是那个小胶水库，或者说包装库，叫别的名字。我检测的就是那个库，因为那是带有 C 接口的库。所以我基本上就是确保能找到那个库、能链接它、能在里面找到某个符号并成功链接，就认为它合适、可用。

Gavin Henry：对，我在自己的项目里也是这么做的。我解释一下我的理解，我想你们也是这么做的：当你构建一个 Rust 项目时，你告诉 Cargo、告诉 Rust 生态把它构建成静态库或者共享库，而不是可执行文件，然后把它装到某个地方。你要检测的就是这个，对吧？然后"这个函数应该能通过这个库调用到"，能调到就说明装好了，然后设置一个宏定义，在构建时就可以用 #ifdef：如果有这个，就用这段代码；如果没有，就用另一段代码。

Daniel Stenberg：对。

Gavin Henry：很好，我理解了，希望听众也明白了。也就是说，Rust 可以构建成库，为 C 代码提供外部函数接口，也就是 FFI，你们做的就是这个。

Daniel Stenberg：是的。然后剩下的就是把代码以合适的方式拆分：Hyper 能提供什么，确保我以某种方式把它抽象出来，要么用原生代码，要么用 Hyper 库来做事——建立请求、添加头部、解析头部，所有做 HTTP 要干的事，这其实相当多。

Gavin Henry：那对 curl 核心来说，它只是在用一个 C 库，你不必考虑 Rust 是怎么做某件事的。

Daniel Stenberg：没错，这正是它的妙处。我完全不必把它当 Rust 来考虑。我只有一个 API，我拿来用就行，它背后是怎么实现的、用什么语言写的都无所谓。我只有一个 API 可以调用。

Gavin Henry：它可以是任何语言，只不过因为……选了 Rust。

Daniel Stenberg：正是。它是用什么语言写的，对我来说都无所谓，不重要。我有一个 API，有文档说明的行为、预期的结果和输入等等，我就用它。当然，我们——我和 Hyper 那边的 Sean——面临的挑战之一是：那时 FFI 这些东西还处于早期，我是在一个 C 程序里用 Hyper，所以大部分东西其实还不存在，也没有真正的文档。所以我们得大量沟通，我才能明白怎么用它。而且一般来说，从 C 使用 Rust、所有这些 FFI 的东西，有一个挑战：尽管 Rust 提供了一种相当方便的方式来生成代码供 C 使用，但这些 Rust 库的大部分文档都是写给 Rust 使用者的——这很自然，是给 Rust 用户的。但当你不用 Rust API、而是从 C 使用这个 FFI API 时，事情就复杂了，因为你落到了一个奇怪的中间地带：你得读 Rust 的文档，但那并不是它暴露给我的方式，因为我用的是 C API。

Gavin Henry：是的，通常的标准做法是，你创建一个 Rust crate，带 -sys 后缀，也就是 S-Y-S。那部分负责链接到 C 库，然后你再做一个符合 Rust 惯用法的漂亮 crate，链接到那些 C 的东西，把所有 C 的东西都藏起来。

Daniel Stenberg：没错，还有文档。

Gavin Henry：对。而你们的做法是要生成那个库，然后所有 rustdoc 文档记录的都是符号、函数调用和返回类型，因为在 Rust 那边是强类型的。我不认为有什么终极方案，也许可以通过 bindgen 和 libc 之类反向提供这些东西。你说 Sean……Hyper 本来就只是 Rust 的，对吧？它原来只是一个库，并没有内置任何东西来生成 C 的部分。

Daniel Stenberg：没有，但这已经在他们的计划里了。所以我并没有推动任何他们本来不打算做的事，只是他们还没做而已。所以我基本上是它的第一个用户。

Gavin Henry：那你们是不是得一起合作，设计出通过 Hyper 的库版本——也就是你要调用的那个 C 库版本——可以调用的函数名？

Daniel Stenberg：是的，因为它当时并不存在，所以他们基本上得一个一个地过，确保我能从 C 访问到，并且为 C 这一侧提供文档。这是个有意思的挑战。我认为一般来说，做这件事更大的挑战之一就在于这个中间地带：必须有一个 C 库或 C 接口供 C 代码访问，再由它深入到 Rust 代码里，这意味着你得有一个人在这个中间地带，真正对两种语言都感兴趣、都懂行，能理解它，有足够的兴趣去做，去写文档，去提供让这一切真正运转起来所需的功能。

Gavin Henry：是的，因为这相当于双倍工作量，对吧？你得先设计 Rust 函数，然后还得在那个 Rust 函数上——我猜一下 curl 里的标准做法——返回一个成功或失败的退出码，或者一个指向错误码的指针，或者两者都有，说清楚如果返回非零值是什么意思。等你真正写好之后，要考虑的事情多了去了：它是怎么被调用的，我们怎么提供 curl 需要的东西。而且你会失去 Rust 的很多主要特性，比如丰富的错误类型之类，因为你把它压缩成了 1 或 0，或者一个指针。

Daniel Stenberg：是的，正是。所以它得以某种方式翻译成 C 的方式。

Gavin Henry：我们已经说过这是可选启用的。你还记得在 Sean 做这个接口层的时候，你立刻发现了哪些问题吗？

Daniel Stenberg：我想我们最先遇到的主要问题之一，是 Hyper 与生俱来的异步特性——至少 Hyper 是用这种方式写的——这让它的 API 跟 C 接口通常的工作方式相比相当非正统，因为它们在内部如何运作、如何对外暴露上，采取的是完全不同的路子。所以对我来说，光是弄明白怎么用这个 API，学习曲线就很陡。但那更多只是去熟悉东西实际上是怎么运作的，我想当你要使用一个功能相当丰富的库并把它集成进来时，这是免不了的。

对我来说，做这件事时最大的挑战之一，是我们 curl 有一套相当庞大的测试套件，随着时间推移，测试越来越多。我们在测试套件里做的一件事是，比如验证 HTTP/1 的时候，当我们用 curl 发出一个请求，我们会验证发出去的请求和预期完全一致——请求里的每个字节都有它应该有的确定值。一个发出去的请求，如果是 120 字节，我们就会拿这 120 字节逐一比对，它们必须完全符合预期。同样，当我们从服务器拿到响应时，服务器发回一个响应，可能是多少字节我不知道，但我们下载下来的所有字节都必须和服务器发送的、或者 curl 保存下来的完全一致。

这其实引出了相当多有意思的挑战，因为 Hyper 暴露 HTTP 细节的方式不同，所以突然之间，我们几十年来写测试用例的那套方式就没那么容易用了，因为 Hyper 暴露得不一样。所以一开始就有一个挑战：我们怎么验证用原生代码完成的传输和用 Hyper 完成的传输是一模一样的？

Gavin Henry：是的，所以你没有了可以依赖的安全网——以前测试一失败，你就知道哪里没做对；现在你得去改变两者之间的约定。

Daniel Stenberg：是的。所以确保这件事能行的头几步中，有一步是我们得请 Sean 对 Hyper 做好几处不同的修改，让它以更接近 curl 的方式提供数据，这样我们才能在测试套件里使用它，确保请求——不是完全相同，但几乎相同，相同到足以让我们稍微调整一下测试套件，就能跑测试，确保它们的行为确实完全一致。

Gavin Henry：那要让 C 对接异步的 Hyper——我不确定它用不用 Tokio，我想是用的——是不是得写一大堆回调，然后等待返回？

Daniel Stenberg：不，我想他们把回调藏起来了。他们自己做回调，意思是你做了很多事，但得不到答复——你启动了一个操作，但不会立刻得到这个操作的结果，它只是返回"好的"，但其实还没执行，所以你得稍后再调用一次，才能知道它成功没有。就某种程度而言，当你引入——比如在我这个情况里——一种做 HTTP 的替代方式时，我有原生的方式和 Rust 的方式，如果其中一个后端思考问题的方式跟另一个完全不同，就会带来一些有趣的挑战。所以要在两条岔路之间做选择，同时确保 curl 的其他部分都看不到、不会因此受影响、不会因为两者采用的不同模式而行为异常，就变得有点复杂。这确实是个挑战。

Gavin Henry：是的。想象一下，你们有一套 API，或者说 ABI，用来给 curl 添加新后端。如果我过来做了一个全新的协议，想让 curl 支持它，我知道会有文档告诉我怎么把它接进你们的配置和构建流程。但对于这个 Rust 版本和 Hyper，这些都还不存在，因为你们以前没做过。

Daniel Stenberg：是的，正是。

Gavin Henry：你们有两个活动部件要对齐，要在一个全新的前沿上工作，还要把一些以前从没拆出来过的东西从 libcurl 里拆出来。好，那关于这个构建流程，你会或者能给其他人什么建议？其实按你的解释，它就只是另一个 C 库。

Daniel Stenberg：是的，我认为这是个相当巧妙的做法，我觉得很直接。从 C 的角度、从我们项目的角度看，它真的很方便，运作得很好。所以从技术上讲没有问题，我觉得在这方面真的没有什么应该或者需要改变的。我认为最大的问题——我要回到这一点，因为前面已经提过，而且我在其他 Rust 提供的后端上其实也看到了同样的问题——还是那个：你落到一个奇怪的境地，这些 Rust 库的文档往往相当好，但因为我不调用 Rust API，我就落到了一个奇怪的境地：我实际使用的那个 API 接口其实并没有文档。所以我不得不大量猜测，或者读代码，或者两者都做，去猜它实际上是怎么运作的，因为从 Rust 到 C 的翻译并不总是直截了当的。有时候我甚至连猜都没法猜，因为这很关键，它基本上取决于你具体是怎么做 FFI 翻译的。所以这算是一个常见的模式，我看到的。

Gavin Henry：你能举个例子吗？比如有一个函数，做某件事，返回某个东西，这个函数接口是有文档的，那问题在哪？

Daniel Stenberg：通常只有它的 Rust 版本有文档，当然，对它在 Rust 里使用时怎么运作，有相当详尽的说明。但我不在 Rust 里用它，我甚至看不懂文档里关于类型及其运作方式的那些说明，甚至返回码也看不懂，因为那并不完全是我……我不传那些参数，也拿不到同样的返回码。我拿到的通常是那个 API 经过调整或者扭曲的版本，但我需要的恰恰是那个特定版本的细节，因为我用的是 C API，不是 Rust API。

Gavin Henry：对，我明白了。我写某些函数时，只是因为 C 程序要调用它们才写的，所以我改了函数的签名和返回值。但我猜如果你有一个……

Daniel Stenberg：我觉得有时候更多是因为，在这种情况下，C 用户才是那个……我是怪胎，我是小众情况。所以当然，人们在牺牲业余时间，贡献自己的时间和精力，他们当然首先专注于让东西对 Rust 用户能用，所以 Rust 文档才是优先的。我对此没有异议，因为这合情合理。但有时候这就让从 C 使用它变得更难，因为文档往往是……

Gavin Henry：是的，Rust 这边的类型和结构体，当它们告诉 Rust 把它表示成 C 时，你只能看看出来的是什么样，对吧？

Daniel Stenberg：是的。然后又回到这一点：要把这件事做得真正好，你大概得同时相当懂 Rust 和 C，而这是一个很特殊的人群交集。

Gavin Henry：好，我要把话题转到我们所说的"复盘"上——找不到更好的词了。哪里出了问题，也就是这里的分析。第一个问题：curl 的这一部分适合用 Rust 吗？

Daniel Stenberg：是的，我认为它本可以是使用 Rust 的合适部分。我不认为问题出在 curl 的哪一部分上，因为就像我之前说的，我觉得只要我们花时间和精力、把它做对，基本上可以像这样为 curl 里的几乎任何东西引入后端。所以我不认为问题出在 curl 的这一部分。我认为最终让我们把它拿掉的首要原因，是我们并没有真正找到想要它的用户。

我有点喜欢那种"适者生存"的做法：为不同的方案提供不同的后端，让用户挑他们想要的去用。比如我们提供了一堆不同的 TLS 库方案，用户可以随便挑一个去构建 curl、去用。随着时间推移，我们可以发现："等等，这几个从来没人用，我们不用再支持了，可以移除。"基本上就是让用户来决定我们该有什么、什么在被使用、什么最好、他们想要什么。而相当明显的是，从很早开始，在整个项目过程中，我们都很难让任何人哪怕只是试用一下 Hyper 后端。基本上没人用它。而没有用户，我们的贡献者也就非常少，很少有人帮忙改进这个后端，真正参与进来帮我们的人非常少。

Gavin Henry：那你们怎么判断一个后端有没有人用、受不受欢迎？

Daniel Stenberg：基本上就是问人。我们每年做用户调查，通常也会在邮件列表上问，问那些常用的人"你们在用这个吗"。有时候你也能察觉到：比如某个严重的 bug 存在了一段时间，我们修好了，却从来没人跟我们报告过它，这就是个相当大的线索，说明其实没人在用。我们还把它标记成了实验性功能，这当然也阻碍了人们在生产环境中使用它。因为我们始终没能让它和原生实现做到百分之百一致，所以我记得启用 Hyper 时，一直有大概 3% 到 4% 的测试用例是被禁用的，因为我们始终没能让那些测试用例表现得完全一致。

Gavin Henry：是的，我想你可以这么说：如果它被标记为稳定，然后成了默认选项，你就会收到 bug 报告，人们会主动启用、会来帮忙。但如果你没走到那一步，那就是没走到。

Daniel Stenberg：没错，是的，当然，那是一个障碍，而且肯定是个主要障碍。

Gavin Henry：那其他 Rust 选项，TLS 那些，是在你开始这个项目之前就有了、你们有了一些经验，还是之后才做的？

Daniel Stenberg：quiche，就是 HTTP/3 那个，是在这之前就开始了。rustls 那个，我想基本上是在我做这件事的同时开始的。rustls 就是 rustls 嘛——我们对 curl 里的 TLS 理解得要深得多，curl 里也有好得多的基础设施和配套来支持 TLS 后端。所以我认为那条路走得更顺，和 curl 也更契合。而且我也认为 TLS 是一个更好的抽象层，也许比 HTTP 更好——我是说加引号的——因为内部 API 应该是什么样、怎么把 HTTP 抽象出去，这绝对远远谈不上清晰明了。

我们多次面对的挑战之一——我前面已经稍微暗示过了——是 Hyper 和 curl 处理 HTTP 的方式有点不同。比如从 Hyper 获取头部时，拿到的顺序多少是随机的，而 curl 总是按它们在线路上发送的顺序返回。如果顺序不一样，我当然就没法像现在的测试套件那样正确比对，这是一个例子。还有其他方面，比如 Hyper 在 HTTP 层确实有一些和 curl 不同的限制、约束和要求，这也带来了一些好笑的摩擦和差异：你用这种方式构建和用那种方式构建，行为会不一样，仅仅因为策略、信仰或者口味不同。

Gavin Henry：你们现在在用的那些 Rust 组件，同样也只是 C 库，被放进一个已经很成熟的环境里，因为你们早就有其他后端了。

Daniel Stenberg：是的。

Gavin Henry：而这一个让事情变得复杂了。一定有过某个时刻，你们想："等等，为了让它能用，我们得对 Hyper 做这么多改动。"你们有没有讨论过"干脆从零开始做吧"，因为你们已经试过了？还是根本没这回事？

Daniel Stenberg：我想没有，也是因为我自己不够格，我的 Rust 水平不足以去做这件事，所以我不会做；也正因为如此，我也绝不会想着去要求别人做。所以基本上就是要么用 Hyper，要么干脆不做——至少就当时而言是这样，因为我们已经有了这个 Hyper 方案，这就是我们费力想让它跑起来的东西。而且我认为我们也推进得相当远了，我们达到了大概 97% 的测试用例覆盖率，所以我觉得我们已经离成功很近了。但之后就停滞了，有一段时间没人做，它就一直停在那个状态，我们似乎也没有谁真正有兴趣推动它往前走。当它基本停在那个状态时，我们决定："等等，如果我们就停在这里，没人推动它，也没人真正需要它，还有这么多注意事项，我们还需要在内部用各种……也许谈不上丑陋，但有时候有点让人不舒服、有点怪异的方案，而我们仍然只走到了这一步，那也许这就该算是这场冒险的终点了。"然后承认我们并没能以一种恰当的方式把它做成。

Gavin Henry：这正好引到下一个问题：你们从这次尝试中得到了哪些好处？在我听来好像挺多的，学到了很多东西。

Daniel Stenberg：我认为我们学到了很多。我认为 Hyper 其实也学到了很多，他们和我们一样都有所改进。所以即使后来我们分道扬镳、不再使用 Hyper，我认为我们也在好几个方面改进了 curl。我们让 HTTP 处理变得更严谨、更严格，真正和 Hyper 看齐；为了能做后端分离，我们在内部做了大量清理，这帮助我们在内部以更干净的方式处理 HTTP。然后还有我们学到的这个教训：下次基本上应该怎样做这件事。整个 Hyper 之旅也恰好和我们在 curl 里做的其他重构同时进行，我认为 Hyper 的教训也帮助我们做决策、从中学习，并在重构 curl 内部时加以运用。所以我们心里有了这样一个想法：当我们——或者说如果我们——再做一次时，现在我们有了这些不同的工具和架构，能帮我们下次做得更好。

Gavin Henry：你们为引入 Hyper 所做的那些改动，有保留下来的吗？还是在移除 Hyper 时全都拆掉了？

Daniel Stenberg：很多改进是针对 HTTP 整体的，以及把 HTTP 和其他部分分离开。有些情况是——我不知道怎么解释——我们让其他代码部分"感染"了 HTTP 特有的知识，我们得确保这些东西不在通用部分里，而在 HTTP 部分里。我们做了很多这样的清理，这些肯定都保留下来了，而且随着时间推移还得到了加强和改进。所以我会说，相当多 HTTP 相关、协议相关的部分都保留下来了。我们基本上拆掉的，是那一整套试图实现灵活后端、可以二选一的做法，因为我们已经不再有那个东西了，所以也不需要提供它。我们拆掉的就是那部分。

Gavin Henry：这说得通。你在博客里说——我引用一下——"95% 的工作是容易的部分"。你能解释一下另一句话吗？"然而最后那几个百分点会变成足够大的摩擦，最终让我们承认失败、放弃，转而把它全部拔掉。"最后那一点是什么？

Daniel Stenberg：我想基本上是因为——我们总共大约有 2000 个测试用例，我想其中大约 800 个，或者一千个左右，是关于 HTTP 的。而我们降到了大概只有 15 个在用 Hyper 时失败。让最后这 15 个测试用例通过——正是它们最终压垮了我们，因为它们需要有一个人真正理解 Hyper，大概还要理解 C 胶水层、curl 以及涉及的协议，有时候还涉及更多协议，因为在这些情况下，很多时候它们还涉及 HTTP 认证机制，比如 NTLM、Digest 或者 Negotiate 这些可怕的东西。所以你真的需要某种特定的人，对所有这些都有深入了解——不是全部的知识，但你还需要有足够的兴趣和精力去真正钻进去、去做这件事。而我们基本上没找到这样有时间和精力的人。所以它们就一直留在那里，我看不到任何简单的出路，也看不到有谁可能会出现来做这项工作。

Gavin Henry：那这 15 个测试，你还记得其中一两个是什么、为什么失败吗？

Daniel Stenberg：为什么失败——这正是原因的一部分：如果我们确切知道它们为什么失败，事情就容易多了，但那本来就是需要去做的研究的一部分。问题出在 Hyper 方案做事的方式和原生方案做事的方式之间的交互或者差异上。我还可以补充一点：Hyper 并不能做 curl 能做的所有事，curl 能做的 HTTP 比 Hyper 多得多。所以 Hyper 提供的 HTTP 后端并不是 HTTP 的全部。HTTP 里仍然有一部分是 curl 用原生方式做的，比如所有那些认证机制。所以存在这样一种交互或者说中间状态：curl 会神奇地把怎么做 HTTP 的东西设置好，然后去使用 Hyper、和 Hyper 交互来执行 HTTP 请求。这不太好解释，我现在也记不清细节了，但它们大多是这样的情况：最终结果会有些许不同，取决于你用哪个方案，请求或响应会有细微差别。整个挑战就在于弄清楚为什么，以及该怎么修。

Gavin Henry：我能想象，因为我在自己的项目里做过类似的事，把 Rust 引进来，这也是我对这个话题感兴趣的另一个原因。所以我想象，那些 curl 仍然在做、而 Hyper 没做或者永远不会做的部分，由你来设置好，交出你的数据——你传过去的东西在内存里已经创建好了，对齐什么的都在 FFI 边界的 curl C 这一侧做好了，你把它推过边界交给 Rust，Rust 必须正确地解读和理解所有这些内容，做它那部分，做些改动，然后再把东西从 Rust 传回到 C 这边，跨过 FFI 边界，还得祈祷那部分不会被搞乱。然后你还得严格约定谁管理内存、谁做什么、谁来释放、谁来创建。这很快就会变得很复杂。

Daniel Stenberg：是的，就是那种交互，因为 Hyper 并不是 curl 所做的一切的百分之百替代品。

Gavin Henry：正是。

Daniel Stenberg：再加上它做事的方式不一样，所以也是这种性质的问题。它就是一个相当复杂的编程挑战——当然不是不可能，只是挑战大到足以成为一个障碍，没人真正去做。而当没人做的时间足够长之后，我就把它理解为：这大概也不是人们想做的事，也没有谁表现出兴趣要做。当然确实有人做过，帮了我们，我们能走到这一步，当然不只靠我或者 Sean，还要感谢一大批其他贡献者帮忙，所以周围是有人的。

Gavin Henry：我是说，你的标准显然非常非常高，甚至因为这是你的孩子。但你可以说这是个成功，你们走了那么远，只剩 15 个测试要解决，这其实是个相当大的胜利，对吧？

Daniel Stenberg：我是说，我认为我们证明了它确实可以行得通，证明了这个想法是站得住的，实现虽然不完美，但能用。所以从这个角度说，我认为这是个胜利。但最终我们没有走完全程。另外，事实上我们并没有谁真正需要它、使用它或者推动它，使用方也没有需求，这也是个相当大的因素，因为所有这些折腾到最后也没有什么大的收获。

Gavin Henry：是的，它是个功能构建，如果没人要，那它就只是个……

Daniel Stenberg：对。所以最后感觉就是：是的，这里有最后的摩擦，如果我们真的下大力气，也许能越过去、闯过去，但没人要求我们这么做，而最后那座大奖杯也不存在。

Gavin Henry：这个功能的资助方——我忘了缩写了——有没有给你们定时间表？他们说给你们一年还是五年，具体是怎么安排的？

Daniel Stenberg：没有，不是那样的。ISRG 灵活得多，他们在这件事上真的很棒，完全支持。这些年来我一直和他们保持着充分沟通。即使到了得出这个结论的时候——一开始其实也不算结论，更像是一个想法："也许我们就该认输、放弃，再把它拔掉"——我也一直在和他们沟通，他们对此非常好，完全理解。他们自己也费了很大劲去找人接手、把这项工作继续下去。最终我想我们都得出了结论：就目前而言，这是正确的决定。我是说，我们并没有为将来把这个想法、这项努力、这个概念的大门关死。谁知道呢？也许将来我们会回到这个想法，重新启动它。

Gavin Henry：是的，也许会出现某个契机，到时候重新拿起来就是顺理成章的事。这就是版本控制的美妙之处，所有历史都在那儿。我想我们已经谈过或者触及了这一点：其他人能从中学到什么？

Daniel Stenberg：一般性的教训基本上是：在一个较大的项目里替换 C/C++ 代码，这是一个合理的做法。从我参与 Firefox 那时起，我就一直挺喜欢 Rust 的这种做法：这是一种方便、得体的方式，一个组件一个组件地替换，而不是一口气把所有东西都重写成 Rust——你可以一个组件一个组件地来。我仍然认为这是个好办法，而且我认为我们证明了这样做是行得通的。至于其他方面，我觉得就更难说了，因为那就涉及到 API 具体怎么运作、怎么在一个软件里真正替换一个组件这些细节，而这比什么都更取决于具体是哪个软件。

Gavin Henry：我想我们已经谈到了我最后一个问题，就是为什么其他人没有站出来帮忙。你解释过，这里的知识领域涉及大概四样东西：Rust 的做法、C 接口、curl 里你要替换的那个具体部分，然后还有涉及的协议或规范，不管是认证，还是将来出来的 HTTP 第四版之类的。

Daniel Stenberg：是的。而且我认为，总体上就是大家看不到使用它有什么好处。我不认为大多数人觉得 curl 的原生方案不好、不安全或者怎样，所以人们本来也不会想着切换到这个新方案。于是我们就困在这样一个境地：用 curl 的人，对现有方案相当满意；用 Hyper 的人，大多是 Rust 用户，他们在 Rust 的世界里，已经在用 Hyper 了，反正也不用 curl。所以我们最后落在一个没有需求的中间地带。

Gavin Henry：是的。我想，如果这里并不是内存相关安全问题的重灾区，那你要么决定在 C 里处理它们、修复它们——就像你们一直在做的那样，通过重构来改进——要么引入 Rust 来做。但如果没有原始数据来说明"付出 X 的努力，能得到 Y 的回报"，就很难真正量化。

Daniel Stenberg：是的。我们还可以回到这一点：我本来就不打算移除原生的 C 方案，因为我认为 curl 的可移植性，以及 curl 在所有地方、所有东西上的普及，部分原因在于它的极强可移植性，而它之所以这么可移植，是因为它是用 C 写的。所以即使我们保留了 Hyper 后端，也会同时保留原生后端。所以即使我们提供了 Rust 版本，也仍然需要继续维护原生版本。

Gavin Henry：你知道有哪些 C 项目——你看过的，或者听众可以去看看的——在做你们已经在做的事，比如部分使用 Rust 之类的？

Daniel Stenberg：一个比较明显的兄弟项目是 Apache Web 服务器里的——我想叫 mod_tls——TLS 那个东西。我知道 Stefan Eissing 为 Apache 写了一个替代原来那个使用 OpenSSL 的模块，在你运行 Apache Web 服务器时改用 rustls。这基本上是同样的思路——角度略有不同，但精神是一样的：把一个 C 库替换成 Rust 库，以获得更多的内存安全。

Gavin Henry：好，我会把它放进节目说明，回头找你要链接。我想我们开始录音之前简单聊过 rustls，以及它底层的 TLS 实现也可以使用 C 库。我想总会在某个地方有一些 C 的 TLS 代码，取决于……

Daniel Stenberg：是的。这有时候有点讽刺，对吧？说是用 Rust 来实现内存安全，结果最后在里面某个地方还是用了 C 的版本。

Gavin Henry：正是。好，我想我们该收尾了。我真的很高兴我们做了这期节目，希望它能帮助其他人理解怎样把 Rust 加进他们的 C 项目、怎样取得成功。而且正如我们讨论的，这不是失败，只是一个需求和收益都不够、到最后又变得非常非常复杂的功能。有没有我们漏掉、你想提一下的？比如某个特别的亮点、你解决过的某个挑战，或者别的什么。

Daniel Stenberg：没有，我想我们已经涵盖了我想说的大部分内容。也许只是再强调一下：Sean 和 Hyper 项目真的很棒，帮了很多忙。这完全不是他们那边的错，绝对不是因为他们缺乏精力或者投入不够，基本上就是我们刚才谈到的那些原因。

Gavin Henry：那如果人们想问你一些具体的问题，或者也许想研究一下那些测试，该怎么联系你？还是说现在它都没了，要等到你们有能力或者有兴趣再做一次？

Daniel Stenberg：这些现在都从 Git 里删掉了。所以如果你想把它找回来，就得找回一个旧版本，从源码构建，然后试试看。我是说，如果你真的对做这种事时会碰到哪些怪问题感兴趣，可以这么做，但除此之外我觉得没多大意义。我们现在是在往前走，当然是在研究从各个可能的方面改进 curl，继续前进。如果有人觉得再做一次是个好主意，我们当然会考虑把它重新拿回到绘图板上，下次做得更好。所有关于 curl 的东西当然都在 curl.se 上，联系我们就行。

Gavin Henry：还有你的博客。

Daniel Stenberg：是的，当然。

Gavin Henry：我在想，会不会出现像 Hyper 第二版这样的东西，带有某种特定的能力……不过我想，有 Hyper 的作者，加上你这样的专家，如果办法存在，你们早就解决了。好的。Daniel，谢谢你来参加节目，这真是一次愉快的交流。我是 Gavin Henry，这里是《软件工程电台》，感谢收听。
