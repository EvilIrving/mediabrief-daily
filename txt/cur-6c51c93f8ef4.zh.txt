标题：为我们团队打造 vLLM 插件（第 2 篇）——从模型转换到部署的 AI-native 自动化
来源：NAVER D2
日期：2026-08-10

[第 1 篇](https://d2.naver.com/helloworld/0525182)介绍了把搜索与推荐模型迁到 vLLM 自定义插件、从而提升服务性能的过程。模型能在 vLLM 上跑起来之后，还有另一类问题：每个模型都要重复的转换流程很复杂，而且还得持续跟上 vLLM 的快速演进。

把一个 Hugging Face 模型挂到 vLLM 上，并不是按一下按钮就能完成的。但自动化可以按我们自己的问题不断“打磨”。我们把转换流程做成 Claude Code Skill，并在实际转换模型时经历了两次大的试错，技能本身也一直在改进。本文记录的是：如何用 AI-native 方式自动化 vLLM 模型转换到部署，以及我们如何不断打磨这套自动化。

结果是：用同一套流程转换了 7 个不同类型的模型并投入运营；把转换中发现的 45 条注意事项沉淀成可复用知识；把原先每次调用都塞进全部知识的方式，改成只拉取所需知识，使传递知识所需的单次调用 token 从 6900 降到 170，减少 97%。最后，我们把这种协作方式扩展到仓库边界之外：用户只需开一个 GitHub Issue，就能串起从转换到部署的端到端流水线。

本文涉及的模型转换与部署自动化整体结构如下。

（图 1：模型转换与部署自动化整体结构——负责转换与部署流程的技能在需要时调用领域知识技能）

## 模型转换为什么难

模型转换不是简单的代码迁移。要保留用 Hugging Face 训练出的权重，却必须按 vLLM 的执行方式重写模型实现。这同时需要模型侧与服务基础设施侧的知识。

（图 2：模型转换所需的两个领域知识——了解模型结构的模型开发者与了解 vLLM 基础设施的 MLOps 工程师之间存在知识缺口）

模型开发者熟悉内部结构与权重量映射，却不懂 vLLM 的池化接口或 IO Processor 等特殊知识；MLOps 工程师熟悉基于 vLLM 的基础设施，却不清楚权重结构，以及 Transformers 实现与 vLLM 实现之间的细微差别。

也就是说，模型开发者或 MLOps 工程师单独都很难完成。框架变化快更是雪上加霜：vLLM 大约三年从 v0.1 演进到 v0.20，约每两周发一版，接口也在变。让人每次都跟进适配并不轻松。

正因为两个领域交叉、框架又快速变化，我们从引入 AI 之初就决定用 AI-native 方式解决模型转换本身。

## 从模型路径到 PR 的转换技能

转换流程实现为名为 `convert-vllm` 的 Claude Code Skill。Claude Code Skill 是 Anthropic 编码代理 CLI（Claude Code）的功能：把重复工作的步骤写在 `SKILL.md` 里，代理需要时读取并执行。这样不必每次写长提示，就能复用已验证的顺序与判断标准。

用户输入 Hugging Face 模型路径后，五个可独立运行的子技能按序执行，直到创建 PR。

（图 3：vLLM 模型转换的五个阶段。无需输入输出前后处理的模型会跳过第三步。）

1. `setup-environment`：从 MLflow 与 S3 下载模型产物并配置开发环境。
2. `convert-model`：核心步骤。分析 `config.json`，判断生成、池化、分类等模型类型；接着编写 vLLM 用的配置类、模型类、权重加载代码与模型注册代码。
3. `develop-io-processor`：实现所需的输入输出前处理与后处理。仅部分模型（如池化模型）需要，是否执行由模型类型自动决定。
4. `test-and-benchmark`：编写单元与集成测试，并做最关键的等价性（parity）验证——确认 Hugging Face 原版与 vLLM 转换模型输出一致；同时测性能并写优化指南。
5. `finalize-and-publish`：把转换后的模型上传到 MLflow，写部署指南并创建 PR。

### 不为完全自动化而设计的两套协作机制

这五步并非全自动。我们设计了两套协作机制：由人审批转换方向与各步结果，并由独立代理验证实现。

（图 4：人与 AI、AI 与 AI 之间的验证结构——`plan.md` 审批门与使用独立上下文的验证）

第一是 `plan.md` 审批门。若把复杂转换从头到尾交给代理，错误判断可能很晚才被发现。因此执行前必须先把转换计划写成 `plan.md`；人审阅批准后才开始实现，每步结束后再确认结果，从而锁定整体方向与阶段性产出。

第二是把实现与验证的上下文分开。我们观察到：执行转换的代理在自检时，往往会预设自己的实现正确，从而漏掉错误。实现与验证的角色分离在 AI 代理之间同样必要，因此测试编写与结果验证由在独立上下文中运行的子代理负责。

### 转换越多，规则越多

用这套技能转换了分类、命名实体识别（NER）、嵌入、基于属性的情感分析（ABSA）、图像打分等 7 种不同类型模型并投入运营。过程中发现的陷阱（gotcha）整理成规则，供后续转换复用。

（图 5：随转换次数增加的规则数——从第一个模型的 5 条增至第七个模型后的 45 条）

把积累的规则用于下一次转换，避免重复踩坑，流程也逐渐变快。技能本身越来越“聪明”。如何把这些知识交给代理，后文再谈。

### 起点——200K 上下文催生的检查点结构

这套技能并非一开始就是现在这样。`convert-vllm` 的第一版在每一步都有保存进度的检查点。当时 Claude Code 的上下文上限是 200K token，跑完一步就容易塞满，很难在一个会话里做完五步；中途断开还得从该步重来。

于是做了 4 个检查点和 9 个状态字段，并支持 `--from=step` 从指定步骤重启。在当时的约束下这是最优解。

（图 6：200K 上下文下的检查点结构——在步骤之间保存状态以接续工作）

这些检查点成了第一次试错的主角。

## 试错一——AI 工具一变，技能也得变

检查点在当时的约束下必要，但 Claude Code 支持 1M 上下文后，前提变了。再次跑同一转换时，无需上下文压缩就能在单会话内跑完五步。

（图 7：上下文大小变化前后的执行结构对比）

删掉已无存在理由的检查点代码后，`SKILL.md` 从 492 行减到 332 行，少了 33%。原先每个会话发生五次以上的上下文压缩不再出现，九个状态字段也全部去掉。

（图 8：移除检查点前后对比——技能文档长度与上下文管理成本的变化）

`SKILL.md` 的三分之一并不是模型转换知识，而是绕过当时上下文上限的临时结构。工具约束消失后它仍留着，只会徒增复杂度。

这类事不会只发生一次。最近 Claude 模型从 Opus 4.6 换到 4.7 时，就有在 4.6 上能跑的技能部分失效。AI 工具更新频繁，影响面也难预判。技能不是做完就放着，而要和工具一起持续维护。**技术债不只产生在源代码里。**

## 试错二——必须设计给 AI 提供什么、何时、多少

第二次试错来自更根本的问题：如何把团队的领域知识交给代理。我们希望代理能自行参考各模型类型的实现方式与转换注意事项。

先说结论：最初选用的钩子（hook）方式会强制塞入全部知识，单次调用额外增加约 6900 token，反而损害质量。后来改成只选读所需知识的技能方式，单次调用降到 170 token，目标完成得更好。下面分享转换过程中的收获。

### 第一次尝试——用钩子强制注入全部知识

起初我们找的是“怎样让 AI 上下文无论如何都看到我们的知识”，答案是 Claude Code 的钩子：每次调用工具前后自动执行或往上下文插入指定内容。于是在每次工具调用前把整份知识库塞进上下文。

结果是：每调用一次工具约增加 6900 token；重复 22 次后，同一知识库重复占用约 15.2 万 token。

（图 9：钩子方式下上下文中不断增长的 token 数）

更大的问题不是量，而是相关性。任务只需要知识库的一部分，却每次都把无关知识整包灌入。转换池化模型时，生成、嵌入、重排序（reranking）规则也会进来，代理会引用错误规则。信息多并不等于 AI 更强：即便上下文上限到了 1M，信息越多，对重要内容的注意力仍会分散（attention dilution）。

### 技能加载知识的方式

为找钩子的替代，我们重新梳理了 Claude Code 选择与读取技能的三步：

1. 会话开始时，只有已注册技能 frontmatter 里的 `description` 进入上下文，尚未读 `SKILL.md` 正文。
2. 代理用用户请求与 `description` 比对，选择要用的技能。
3. 选定之后才读 `SKILL.md` 正文，并按需读取正文指向的 `references/` 文件。

技能的 `description` 是索引，说明何时该用它；真正的流程与知识只在被选中后进入上下文。好比面试前先看简历（description），录用后再翻作品集（正文与参考文档）。技能用 `description` 宣告用途，由模型自行挑选调用。

### 殊途同归的外部案例——Supabase `agent-skills`

我们找了公开案例，参考开源 BaaS、Firebase 替代方案 Supabase 的 [`agent-skills`](https://github.com/supabase/agent-skills)。Supabase 把 Postgres 的性能、安全与权限做法做成技能，让编码代理在工作中按需选读。[Supabase 博客](https://supabase.com/blog/postgres-best-practices-for-ai-agents)写道：MCP 给代理访问数据库的能力，agent-skills 则告诉它如何正确使用。

这正好点中钩子方式的问题：代理即使有能力，也不该靠强制塞入全部知识来决定此刻该看哪条规则；需要的是在恰当时机只读相关参考文档。

（图 11：Supabase agent-skills 的文件组织——以 `SKILL.md` 为入口，主题规则分在 `references/`）

Supabase 每条规则由 Problem、Wrong、Correct、References 四部分组成；30 条规则用含 `query-`、`conn-`、`security-`、`schema-` 等的 8 个前缀分类。不同领域的团队用同一设计工具落到几乎相同的结构，说明这适合管理领域陷阱。

### 模式借用与重组——`vllm_version` 与 `Source` 字段

我们沿用该结构，并按 vLLM 领域做了三处调整。

第一，规则用 `pool-`、`cls-`、`gen-`、`embed-`、`rerank-`、`general-` 前缀分类，每条仍由 Problem、Wrong、Correct、References 四部分构成。

第二，把转换流程与领域知识拆成两个技能。

（图 12：转换流程技能与领域知识技能的协作——流程技能只选读匹配模型类型的领域规则）

`convert-model` 管理转换步骤与顺序；`vllm-best-practices` 管理各模型类型的陷阱，充当领域知识的单一事实来源（SSOT）。前者像“课程表”，后者像“参考书”。`category-index.md` 是二者之间的显式指针：`convert-model` 处理某类模型时在此查规则位置，再调用 `vllm-best-practices` 只读那些规则。

第三，考虑到 vLLM 变化快，增加两项元数据（Supabase 原型没有）：

* `vllm_version: "0.14.1"`（frontmatter）：验证该规则时的 vLLM 版本，便于在如 0.15 发布后找出需复查的规则。
* `Source: <文件路径>:<行号>`（正文末尾）：实际验证该规则的代码位置，相关代码变更时可立刻核对有效性。

我们没有止于照搬公开好模式，而是按 vLLM 转换问题重塑了规则分类、技能协作，以及版本与源码追踪方式。

### 结果——单次调用 token 降 97%，决策主体转换

45 条规则整理为：池化 8、分类 7、生成 9、嵌入 6、重排序 8、通用 7。

（图 13：钩子与技能方式的 token 对比——6900 → 170，降 97%）

传递领域知识所需的单次调用 token 从 6900 降到 170。新会话中 `vllm-best-practices` 会自动被调用并只选读相关参考文档，也已验证。

比数字更重要的是：选择知识的主体变了。钩子由系统预先决定塞入什么；技能则由模型比对任务与描述后选择工具。决定、调用并阅读知识的主体从系统转到了模型。**钩子绕过这套选择机制，技能则利用它。**

## 从 GitHub Issue 启动的部署自动化

至此讲的是同一仓库内两个技能的协作。最后把方式扩展到仓库边界之外，让部署也按同一原理衔接。

### 一张 Issue 表单启动部署

在以仓库变更为准管理部署状态的 GitOps 仓库里，我们做了「KServe vLLM 新建部署」Issue 模板。Issue 一创建，GitHub Actions 就自动跑部署技能 `kserve-vllm-deploy`。

用户只需填 Issue 表单：模型名与版本、模型仓库路径、部署环境、GPU 类型。代理分析 Issue 后留言建议方向，包括命名规则校验、模型类型推断、按模型大小推荐 GPU、选择 vLLM 运行时版本、决定执行参数、将生成的文件列表与部署检查清单。人审阅后批准或要求修改。

下面是将 480M 图像打分模型 `clip-score` 部署到预发环境 H100 GPU 的真实案例。

（图 16–17：Issue 输入、代理分析评论，以及自动生成并合并的部署 PR——含 KServe values、app-of-apps 注册、API 端点配置，共 3 个文件 69 行变更）

人批准方向后自动生成 PR 并实际合并。用户只做了填 Issue 和点合并。之后由把 Git 状态同步到集群的 GitOps 工具 ArgoCD 完成部署。

### 为何不把 vLLM 知识放进 GitOps 仓库

写部署技能时发现两类知识会混进同一个 `SKILL.md`，于是按真实所有者拆分责任。

文件路径、app-of-apps 配置、GPU 区域映射属于 GitOps 仓库管理的基础设施知识；各模型类型的 vLLM 执行参数与运行时版本、按模型大小的 GPU 建议、IO Processor 用法，则应由 vLLM 插件仓库管理。

（图 18：按实际所属团队与仓库区分部署基础设施与 vLLM 模型服务知识）

若都塞进一个 `SKILL.md`，vLLM 0.15 发布时就要由 GitOps 仓库的负责人去改插件领域的执行参数。为避免知识落在非所有者处，两个领域被拆开。

### 用 Git 仓库分发技能

仓库间共享技能采用技能市场（marketplace）模式。这里的市场不是独立服务器，而是提供技能的 Git 仓库 URL。在 GitHub Actions 配置中指定仓库 URL 与插件名：

```
plugin_marketplaces: |  
  https://<git-host>/<org>/agent-plugins.git
plugins: |  
  pai-vllm-serve-guide
```

（图 19：经技能市场实现的跨仓库知识共享——vLLM 插件仓库提供服务知识，GitOps 仓库按需拉取）

vLLM 插件仓库以 `pai-vllm-serve-guide` 插件提供运营知识；GitOps 的部署技能在决定运行时、GPU、执行参数时调用它。参考文档沿用 `vllm_version` 与 `Source`，无论仓库内还是跨仓库都用同一套元数据管理规则。

领域知识管理因此从中心化变成由各领域所有者在自己仓库直接提供的分布式结构，类似普通代码引用软件包。

### 跨越仓库边界的协作模式

这是把仓库内两技能协作扩展到仓库之外。

（图 20：仓库内与跨仓库技能协作对比——流程技能在需要时选择领域知识技能的共通结构）

转换仓库里，`convert-model` 看 `category-index.md` 再选 `vllm-best-practices`；部署仓库里，`kserve-vllm-deploy` 经市场选 `pai-vllm-serve-guide`。边界不同，原则相同：领域知识由所有者提供，执行者在需要时拉取。

对用户而言，一个 Issue 就能完成从转换到部署；对内，两技能的协作经一行 Git URL 跨过仓库边界。

## 结语

在打造并运营 vLLM 模型转换与部署自动化的过程中，我们看到这些变化：

| 变更前 | 变更后 |
| --- | --- |
| 步骤间 4 个检查点 | 上下文压缩 0 次的单会话 |
| 单次调用 6900 token | 单次调用 170 token（降 97%） |
| 手动部署 | 端到端自动化（一个 Issue → 部署） |
| 知识落在非所有者仓库 | 所有者提供、消费者调用 |

四点教训：

第一，**AI 工具更新时，技能也要一起更新。** 200K 下最优的检查点在 1M 下只剩复杂度。绕过工具约束的结构，在约束消失后必须复查。技术债不只在源代码里。

第二，**必须亲自设计给 AI 提供什么、何时、多少。** 整包塞入不如让模型在需要时自选阅读。模型转得越多，经验证的陷阱越多，技能也持续改进。

第三，**AI-native 模式的真正价值不在照搬，而在按自己的问题重组。** 借用了 Supabase 的规则格式，但加上 `vllm_version` 与 `Source`，以便在快速变化的 vLLM 环境中追踪规则有效性。

第四，**好的协作结构能跨过仓库边界。** 流程技能在需要时选择领域知识技能——靠一行 Git URL 就扩展到了部署自动化。领域知识由所有者提供，消费者按需调用。

以上，就是我们把 vLLM 转换与部署做成 AI-native 自动化，并按自身问题不断打磨的过程。
