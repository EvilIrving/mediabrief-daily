构建数据分析 agent 过程中学到的上下文设计（데이터 분석 에이전트를 만들며 배운 컨텍스트 설계） ｜ Kakao Tech ｜ 文章 ｜ https://tech.kakao.com/posts/838

韩国 Kakao 技术博客的一篇经验分享。作者团队做了一个数据分析 agent：根据用户的业务问题找到合适的数据，写 SQL、执行、解释结果。文章围绕"上下文工程"展开，也就是在每一步给 agent 挑选并组织哪些输入信息，把上下文拆成系统提示、工具说明和消息数组三部分来讲。

系统提示放全局通用的东西：角色定义、安全规则（比如不执行会直接暴露用户标识的 SQL，改为建议做聚合统计）、信息不足时的默认值和需要确认的情况（没指定口径的用户数默认用日活，和既定指标定义冲突时先问用户）、多个工具共用的使用原则、回答规范（调用工具前用一两句话说明在做什么，不编造未经查询的数字），以及领域知识和按服务整理的表清单。作者回顾，GPT-4 时代模型自己判断流程的能力弱，他们把详细的工作流程都写在系统提示里；模型变强后，改为把每个工具的使用条件写进工具说明，让模型自己决定用什么、按什么顺序。他们引用 Anthropic"提供极其详细的描述"的建议，并指出 Claude Code 的工具说明约 1.5 万 token，是系统提示的四倍。以图表工具为例，说明里写清楚它做什么（基于执行结果生成 Vega-Lite 规格）、什么时候调用（只有用户明确要图、且已有 SQL 结果时）、结果怎么呈现（图已显示在界面上，不要把数据再用文字复述，只补一两句洞察），参数用枚举限定图表类型并给出选择标准；由于图表生成器内部调用另一个看不到对话的模型，主 agent 还要在 instruction 参数里写明这张图想展示什么、突出什么。工具太多会让说明膨胀、选择变难，他们借用《软件设计的哲学》里"深模块"的概念，把相关功能合并，比如笔记的新建和修改合成一个 upsert 工具，把写 SQL、执行、出错重试这一整套交给一个子 agent。

消息数组按顺序记录对话、工具调用和结果，agent 据此判断下一步，也用来理解"把时间改成一个月"这类追问。作者强调，agent 在不同阶段需要的信息不同，于是用了两种手段。一是渐进式发现：像 Claude Code 先搜文件名、再搜代码、再顺着定义和调用处追踪那样，让 agent 根据已发现的线索决定下一步看什么，skill 也是先看名字和描述再读细节。他们早期用一个独立的探索 agent 去搜表，结果主 agent 不知道自己能访问哪些表，要反复搜完才发现根本没这张表；后来把可访问的表清单按服务写进系统提示当作索引，主 agent 先从清单挑候选，再查具体结构，更早发现缺表，所需轮数也少了。二是子 agent：起初主 agent 自己写 SQL、出错再改，失败的 SQL 和报错一直堆在消息里，问题解决后仍被带进后续分析；改为由 SQL 子 agent 在独立上下文里处理，只把最终 SQL、状态和结果交回。至于为什么表探索收回主 agent、SQL 却交给子 agent，判断标准是这些信息之后还用不用得上：表清单和结构解读结果时一直需要，失败记录解决后就很少再看。
