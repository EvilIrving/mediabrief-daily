在 Anthropic，写代码已经不再是构建系统或做研究的瓶颈。Claude 能够自主迭代研究循环、对复杂程序做微观优化、从零搭建新服务，其速度和规模前所未见。如今的瓶颈，是所有按人类规模搭建的开发者基础设施：源代码控制、构建和 CI。

2026 年 5 月，Anthropic 平均每天合并约 2,500 个代码变更；到 9 月，我们每天合并超过 30,000 个。我们预计这种增长速度短期内不会放缓：合并代码的潜在需求几乎是无限的，我们每消除一个瓶颈，产出的代码量就会立刻再上一个台阶。

为了支撑这种增长，我们自研了版本控制系统 Scion，并在五个月内把整个 monorepo（单一代码仓库）从 git 完全迁移过来。同一时期，我们还打造并上线了代码审查界面（名为 Antique）、代码搜索、功能丰富的源码控制权限（IAM）系统、管理和落地大量已审代码的新方法，等等。本文专门讲我们如何构建 Scion。这是一个有意思的案例：正是 Claude 写代码的能力把我们逼到了这个处境，也正是这种能力让我们得以迅速构建出一个高质量、可扩展的系统来应对它。

在介绍我们构建了什么之前，得先承认我们的工作负载有多么特殊。不出所料，Anthropic 用 Claude 写软件的程度远超几乎所有其他公司，所以我们往往最先看到为人类规模打造的工具在哪里开始吃不消。源码控制只是其中一个例子。我们并不认为很多组织在近期就会遇到这些问题，但我们猜想，用 AI 编程工具的其他团队用不了多久也会碰到同样的压力点，所以我们想分享我们做了什么、学到了什么。

git 是一个去中心化系统：每个克隆都是完整、自足的仓库，可以在完全离线的情况下计算 diff、查看历史和 blame、检出任意版本。对绝大多数仓库来说，这是正确的设计，也是 git 成为标准的重要原因。

随着我们的 monorepo 不断膨胀，它越来越不适合这种设计。仅主分支的历史就接近 100 GB，压缩后的工作副本超过 25 GB。我们每天光为 CI 就执行约 2,500 万次代码检出，这还不算开发环境、智能体沙箱和研究任务。如果简单粗暴地拉取，每天的 git 流量将超过 600 PB。

git 提供了处理仓库局部的工具，比如浅克隆、稀疏检出和 promisor remote（按需拉取对象的远端）。除此之外，大型 monorepo 还有一些标准的变通办法，比如内部 git 镜像，以及存放在 blob 存储里的仓库快照（seed）。这些我们都用过——高峰时，我们运营着数百个内部 git 镜像来扛负载。这为我们争取了时间，但随着合并速率上升，它们越来越难运维。两次刷新之间，seed 离 main 分支最新提交越来越远；要让 diff、blame 这类依赖历史的操作在部分克隆上正常工作，需要越来越多的小心维护。

退一步看，我们发现和大多数公司一样，我们其实是把 git 当作有唯一权威副本的中心化系统在用，而我们几乎所有的客户端都是智能体和任务，它们天然是在线的。那些让 git 在分布式离线工作中表现出色的特性，正随着仓库变大而实实在在地妨碍我们扩展。于是我们问自己：如果从一开始就以“智能体永远在线”为前提来设计源码控制，它会是什么样子？

在智能体编程时代，许多关于软件如何开发的常见假设都在变化。构建 Scion 时我们拥抱了这些变化，从而在几条核心原则上采取了与 git 截然不同的路线。超大型 monorepo 的源码控制已有前例，尤其是 Google 的 Piper 和 Meta 的 Sapling，因此我们在构建 Scion 时可以借鉴它们来之不易的经验。我们的原则是：

客户端永远在线。git 假设客户端离线工作，需要仓库的完整副本。由于我们几乎所有客户端都是智能体和任务，我们围绕一个永远可达的服务器来设计 Scion 的客户端和协议，让客户端在需要时才拉取数据。

客户端与服务器不对称。在 git 中，每个客户端都能充当完整的服务器。在 Scion 中，由服务器回答文件历史和 blame 的问题、创建提交、执行合并和变基等。客户端维护一个有容量上限的本地对象缓存，把工作副本文件铺到磁盘上，监视文件系统变化，并为用户提供与服务器交互的顺手方式。它自己能算的东西很少，但换来的是本地所需数据大大减少。

全面的源码控制服务可以支撑许多新应用。用 git 时，一个 CI 任务或工具如果需要询问仓库的情况，比如某一行最后是谁改的、两个提交之间是什么关系，就得维护一份本地仓库副本，或者指望厂商特定的 API 能给出答案。用 Scion 时，客户端用到的所有源码控制查询也都通过 API 开放，所以很多情况下任务根本不需要本地仓库。许多内部工具，比如我们的自动二分定位（bisect）和自动回滚流水线，如果没有这种廉价、可编程的源码控制访问，就无法大规模落地。

一切都必须可水平扩展。高峰时我们运行着数百个 git 镜像，严重挤占容量，而且一旦仓库超出镜像的磁盘或内存上限就再也扩展不了。在 Scion 中，仓库数据是分布式的，每个组件都可以独立扩展；任何地方都不存在完整物化的仓库副本，连服务器上也没有。也没有 packfile（git 把对象压缩打包的文件）的对应物，所以不需要做仓库维护。

提交必须廉价、增量且无锁。在 git 里，你先在本地提交，再 push 出去分享。在 Scion 里，每一次提交、变基或合并都在服务器上发生，所以没有什么需要 push，但每个操作都必须快。创建提交并更新其下游数据结构的成本，必须随变更大小而不是整个仓库大小增长，否则服务器跟不上。Scion 的开发流程不鼓励使用 ref（指向提交的指针，比如分支和标签），main ref 和发布分支除外，因为每台服务器都必须达成一致的全局状态是一个迫在眉睫的扩展难题。

工作副本是可选的，并且天生是稀疏的。由于我们的 monorepo 太大，CI 每天又要检出代码数千万次，我们希望尽可能避免检出。有了 Scion，比如一个需要某提交与其合并基点之间 diff 的 CI 任务，可以直接向服务器要。写入也一样：很多写入负载同样可以跳过检出，完全通过 API 完成。Scion 的协议以稀疏检出（只包含客户端请求的目录）和虚拟化检出（按需物化文件）为中心，所以当任务确实需要磁盘上的文件时，客户端只为它真正读取的部分付出代价。

了解这些原则在构建 Scion 时如何落地会很有帮助。这些洞见也适用于其他源码控制系统，更广泛地说，适用于软件开发生命周期的其他环节。

在 Scion 中，工作单元是“变更集”（changeset），即预写日志（write-ahead log）里的一个条目。变更集存储了你对 git 提交所期待的大部分内容。但 git 提交存的是指向树（tree）的指针，而变更集存的是相对于其第一个父提交发生变化的文件列表，以及指向 blob 存储中压缩文件内容的内容寻址指针。变更集在服务器端创建，并立即在所有地方可用。

这种结构让我们能以极高的吞吐量接收变更集，因为不需要接收 packfile，没有加锁或跨服务器协调，也没有 ref 需要移动。从技术上说 Scion 也支持 ref，但由于创建和拉取提交都不涉及 ref，移动一个 ref 只是对单行 Spanner 记录做一次比较并交换（compare-and-swap），与创建变更集是分开进行的。

变更集只记录变化了什么，所以单靠它无法快速回答“某一行最后是谁改的”“哪些提交影响了某个文件”这类问题。为此，Scion 会基于变更集构建额外的数据结构，包括专门用于文件 blame 和路径历史的结构，以及提交图的跳表。凡是不直接属于变更集的东西，我们统称为“派生数据”，并通过一套通用机制来计算。每种派生数据都是递归定义的，它在某个变更集上的值，由它在该变更集各父提交上的值计算得出。

这套机制有三个好处。第一，当某种新数据结构能让某个操作更快时，我们可以轻松新增一种派生数据。第二，对每种派生数据，我们都可以选择是立即计算还是推迟计算，避免物化用不到的数据。第三，由于客户端从不接触这些数据结构的内部，我们可以在不改动客户端的情况下优化它们。随着系统发展，我们已经多次新增派生数据类型，比如用于拷贝检测或基于路径的文件搜索的新索引。

一小组 Scion 服务器为客户端需要的任何操作提供源码控制 API，比如获取变更集、计算 diff、查找合并基点和拉取 blob。所有源码控制数据都是内容寻址的，一份数据一旦存下就永不改变，任何服务器都可以缓存它而无需与其他服务器核对。因此这些服务器可以水平扩展，几乎不需要协调。它们本质上是大型缓存，还能即时计算派生数据并把结果写回 Spanner。

Scion 的众多使用方不再需要维护自己的本地仓库。对于需要询问源码控制问题（尤其是提交祖先关系和 blame）的 CI 任务或工具来说，拉取和维护仓库过去是一项不小的维护负担。迁移初期，在我们还没有自己的客户端、仓库格式和协议时，Scion 只回答这些“元数据”查询。拉取文件内容和物化工作副本是数据密集得多的操作，需要专门设计。

Scion 的 scn 客户端在几个重要方面偏离了 git 的拉取协议，因此适合一种高度可扩展的架构，所需 CPU 远少于 git 服务器。Scion 的协商过程不告诉服务器客户端已经有什么，而是只围绕客户端想要的树和 blob 进行。客户端从根树开始，检查本地存储里缺少哪些树并递归请求，然后对 blob 重复这一过程。每个请求针对的都是一个永不改变的具体对象，所以任何缓存都能应答，整个架构与传统的分层缓存非常相似。这个过程也高效且可续传，因为没有动辄几 GB 的单个 packfile 响应。稀疏检出乃至虚拟化检出都不需要特殊支持，因为客户端只是不去请求它不需要的树而已。

在机群中，客户端通过 socket 与守护进程 scion-daemon 通信，后者为整个节点存储对象。我们的大部分节点都需要访问 monorepo，而同一节点上的任务会复用大部分相同的对象。每个守护进程从一份定期刷新的快照启动，之后只与所在区域的树和 blob 缓存服务器 scion-cache 通信。这些缓存服务器直接从内存流式输出对象，格式就是守护进程要用的磁盘格式，因此无需花时间计算客户端缺少哪些对象，也无需做增量压缩。当缓存缺少某个对象时，它会去问权威的 scion-server，后者按需从 Spanner 或云存储读取。

scion-daemon、scion-cache 和 scion-server 对这套协议响应完全相同的 RPC，所以客户端不需要知道缓存拓扑。理论上任何一层都可以和任何其他层通信，但我们严格执行分层，以隔离故障域。我们要避免这样的情况：某个区域的 scion-cache 出故障，把上游 scion-server 压垮，进而拖垮整个系统。

这个系统的每一层都保持着 99% 以上的缓存命中率，而且不需要长期状态，所以需要时很容易扩容。按 CPU 和内存需求计算，我们的 Scion 基础设施规模如今比原先的 git 镜像基础设施小 200 倍。CI 和研究任务检出代码的速度快了两个数量级（几秒而不是几分钟），在整个机群释放出相当可观的容量；仅 CI 一项就省下了 25% 的 CPU 容量。客户端和缓存都不需要做仓库维护，这简化了任务的生命周期管理。

我们开始构建 Scion 时，恰逢 Claude Mythos Preview 和 Claude Tag 在内部上线。这两次发布既放大了对 Scion 的需求，也显著加快了我们构建它的速度。

举一个特别惊人的例子。今年早些时候，我们基本靠手写完成了第一版 git 到 Scion 的导入流水线原型。我们本以为它不错——直到拿到 Claude Mythos Preview 的一个早期内部快照。我们让它把整个流水线重写一遍，没有给任何额外指示，它写出的版本内存占用减少到二十分之一，速度快了 4 倍，同时保留了关于导入顺序和数据结构的所有隐含不变量。

我们在构建和运营 Scion 过程中学到的东西，对于智能体规模的软件该如何构建，提供了一些有意思的启示。

小团队快速开发将越来越常见。一个七人团队构建了 Scion 和 Antique（我们的代码审查工具，单独再写一篇博客也绰绰有余），外加五六个相关系统，并在五个月内完成了全面迁移。与此同时，每天合并的代码量增长了 10 倍。过去，开发和部署这样的源码控制系统，一家公司要投入多得多的工程师，花好几年做迭代式迁移。我们认为这种快速、灵活的迁移今后会更常见。

工程师的价值没有降低，但他们的工作在变。参与这个系统的每一位工程师现在都认为 Claude 写代码比自己强。但工程师们依然提供了不可或缺的东西：对高层系统间组件和设计层面权衡的理解，并围绕我们想解决的问题和必须达到的规模做出明智选择。我们常常发现，工程师的角色就是对 Claude 说“不”。智能体有时会为了迎合一种本就不该被允许的模式而违反系统的核心约束。这在迁移中尤其常见。例如，有好几个系统试图通过线性读取提交日志来暴力查找某个变更何时合入 main，而不是去问我们的代码审查工具。Anthropic 还大量使用对抗式审查，它在很多方面效果极好，但也可能目光短浅，所以需要有经验的工程师引导 Claude，别为了假想中的顾虑把系统的某些部分过度设计。例如，有一次审查对是否信任另一个内部服务过于戒备，导致 Claude 加入了过多的校验和复杂度。我们的团队成员仍会审查这个系统的每一个变更请求，但现在他们审视的是变更的意图，而不是逐行阅读代码。

我们得以大幅提升优化水平和质量。凭借 Claude 远快于我们的海量代码产出能力，Scion 成了我们参与过的测试最充分、防御最严密的代码库之一。即便时间紧迫，我们仍为遇到过的每一种非平凡的基础设施与源码控制交互构建了密闭（hermetic）仿真，还做了模糊测试和复杂的限流。Claude 还随手发现了重大优化——比如针对祖先查询的一项算法优化，原先的查询没有用上我们的一个索引——这种优化原本需要专家花几天甚至几周去分析调优……而第二天它又照样再来一遍。

我们为 monorepo 安全的新形态打下了基础。在庞大的 monorepo 里管理安全、保密和合规，和管理体量与规模同样重要。我们从一开始构建 Scion 时就考虑了这些。它支持对仓库的精细访问控制，也能对单个目录设置权限，在不丧失 monorepo 好处的前提下保护最敏感的代码。此外，我们打造的代码审查工具能对审批表达复杂的语义约束，从而区分只改注释这类简单变更和敏感的逻辑变更，让人工审查者专注于影响最大的变更。

运维可以达到新的卓越水平。我们团队大量使用 Claude Tag，它帮我们监控系统的每个组件。例如，我们建了一些 Slack 频道，让 Claude 在里面执着地只盯一个组件的健康状况。我们管这些 Claude 叫“超级粉丝”。我们有 scion-daemon 超级粉丝、scion-cache 超级粉丝、Antique 合并队列超级粉丝，等等。它们能访问我们的遥测和日志，表现得像一位经验丰富、闲来无事只顾刷新图表找异常的工程师。我们的所有系统也都有传统告警，但超级粉丝能发现细微而新颖的问题，相比之下那些告警显得很单一。

我们正在彻底重新审视自己的成见。这个项目促使我们认真审视其他为人类规模设计的工作流。比如，一个正规的合并队列在智能体规模下就没什么意义。当测试还在跑的时候就可能有成百上千个变更合入，CI 到底还意味着什么？我们没能有效复制业界标准的合并队列全局仓库锁，于是转而投入合并后、部署前的自动化测试。这意味着并发变更可能冲突，但 Claude 修复这些冲突的速度，通常比人类发现冲突还快。

我们把 Scion 视为应对能力日益增强的 AI 智能体所带来的扩展问题的答案之一。我们分享这些细节，是为了给面临类似挑战的团队提供一个例子，但我们并不认为我们的方案或考量适合所有情况。

Scion 绝不是通用场景下 git 的合适替代品。我们在这里描述的理念，只对真正巨型的 monorepo 才有意义——要么有数万名工程师，要么有成群的智能体在大量写代码。而且 Anthropic 情况特殊，我们能为内部使用花费的 token 远远超过任何其他企业实际愿意花的。我们这么做，既是为了满足自身的软件开发需求，也是为了测试 Claude 的能力。

现实地说，很难以对其他组织普遍有用的形式提供 Scion。它和 git 差异很大，公司需要迁移开发生命周期的每一个环节，而且它需要配套自己的代码审查、代码搜索和 CI。我们内部的这些组件高度定制，其他组织很难采用；我们也担心，试图做一个讨好所有人的公开版本，实际上并不会很有用。

不过，我们预计这类问题会在未来 6 到 12 个月内变得普遍，而让每家用 git 的公司各自孤军应对类似挑战，是对工程资源的低效使用。有鉴于此，我们认为最有影响力的做法是分享我们的思路，让其他开发者能把 Scion 最成功的部分应用到 git 上，而无需脱离 git 的整体模型。git 服务器不必和 git 客户端以同样方式工作；已有新颖的服务器架构能带来显著的扩展改进。git 平台可以像 Scion 那样提供全面的服务端 RPC，甚至可以在各代码托管平台之间以标准化方式提供，让 git 客户端学会与之对话。协商协议也不必非得是今天这个样子，git 中各种稀疏和浅层特性也可以做到良好组合。

最后，我们想致谢 git 社区近二十年来为数百万开发者扩展这个平台所付出的努力。我们的贡献要窄得多：分享我们对智能体软件开发如何与这些系统相互作用的早期观察，以便与 GitHub、GitLab 和开源社区合作，满足开发者不断变化的需求。随着软件开发生命周期与 AI 的指数级增长交汇，我们同舟共济。
