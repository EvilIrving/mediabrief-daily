主持人：OK，公司的工作我们可能放到后面一点聊，先聊一聊你在 CPython 方面的工作。众所周知，Python 的性能一直是大家诟病很多的问题。Python 团队，也就是所有的 Python 贡献者，在这方面其实也花了非常多的心思，包括最近大家可能听说过的 Faster CPython，以及各种大大小小的改进。今天我想请 Penguin 聊一下他在 CPython 里做的两个优化。

第一个是 Python 3.12，也就是即将发布的版本里新加的一个 opcode。如果大家不太熟悉什么是 opcode，说白了就是 Python 的字节码。Python 是一门解释型语言，和编译型语言不一样，Python 运行的其实是字节码：你的代码会先被编译成字节码，然后由 CPython 的虚拟机来执行。Penguin 你可以先简单介绍一下这个工作做了什么，以及你是怎么发现这个地方可以优化的？

Penguin：好。这个其实也是偶然，并没有刻意想着要去做这个优化。当时是在 profile 我们自己的解释器，想找优化点。看 profile 的时候我发现，Python 3.11 不是增加了自己的 opcode 统计嘛，就是那个 stats，你打开 stats=on 之后，它会往 /tmp 目录下输出这次执行期间所有的统计，包括 specialize 的情况和整体的执行次数。其中有一项记录的是每条指令的后一条指令是什么，并选出 top 5。当时我就发现，RETURN_VALUE 这条指令的前一条指令有很大概率是 LOAD_CONST，也就是加载一个常量。对应到代码上，就是 return None 或者 return 123 这种返回常量的写法。我们知道，Python 函数如果不写返回值，默认会 return 一个 None 出去。

这么看的话，LOAD_CONST 加 RETURN_VALUE 的场景应该是非常非常多的，适用面非常广。这时候就有一个很自然的想法：干脆把它们两个合成一条指令试一下。写完之后，我其实没觉得这条指令能有很大作用，感觉可能会快一点，但 benchmark 跑出来大概也就快零点几个百分点，应该不到 1%。提交到社区之后，社区那边用他们的机器跑，可能因为机器差异，也可能因为配置差异，跑出来比我自己测的还要好一点，超过了 1%。当时就觉得：哇，这么简单，一个 patch 就到手了？大概就是这个样子。

主持人：这里能不能请你再给不太了解这块的听众解释一下：你优化的实际上是 Python 函数里直接 return 的情况。原先一个 return 语句在 CPython 内部对应两个 opcode，或者说两条字节码，对吧？首先是一个 LOAD_CONST，相当于把一个常量值，这里实际上就是 None，因为 Python 内部 return 的是一个 None，加载到 Python 虚拟机的栈上，然后再把它 return 回去。

Penguin：对。如果大家对栈式的执行结构没有特别的印象：栈式执行结构是说，每次都把一条数据压到执行栈上，再对栈顶执行对应的操作。对 return 来讲，code object 里有一个 co_consts 这样的 tuple，里面存的是当前函数用到的所有常量。LOAD_CONST 就是从这个 tuple 里取出对应 index 的常量对象，压到栈上；之后 RETURN_VALUE 这个操作就是退出当前函数，并把栈顶的数据作为返回值。我的优化是说：既然我已经知道要 return 的常量是谁了，就没有必要先把它压到栈上再返回，完全可以把返回值直接设成对应的常量对象。这样就省掉了一条 LOAD_CONST 的执行时间。

主持人：相当于把一次入栈出栈的操作完全省掉了。

Penguin：对，是的。

主持人：之前你提到他们 profile 出来性能提升了 1%，这个 1% 具体是怎么算的？是在直接 return 的情况下提升 1%，还是说综合来讲，比如在一个真实的程序里提升了 1%？

Penguin：官方其实有一个项目叫 pyperformance，里面现在大概收集了 50 多个 case。它们是一些真实代码或者手写算法的片段，比如八皇后，比如 SQL 查询；有调用通用库的，比如 json 或者 zlib；还有专门测 Python 虚拟机启动时间的，比如直接写一条空语句反复调用。这个项目会驱动这 50 多个 case，每个 case 大概跑八遍，取算术平均值，然后拿两个版本之间每一项执行时间的平均值做比较，最后再对结果做一次算术平均，这个结果就是性能优化的点数。比如说我优化了 1%，意思是这 50 多项对比下来平均是 1%。其实这 50 多项里，可能有的 case 快了高达 10%，有的 case 慢了五六七个百分点。

有些 case 非常非常小，比如 Python 启动这个 case，小了之后受 profile 误差影响很大，就会导致这类很小的 case 怎么跑都不稳定，有时候很高，有时候很低，这可能是监控本身的误差。还有一些项目可以想象成执行时间本来很短，但我们做了一些额外的优化，导致它的编译时间变长了，这一来一去，在这个 case 上可能就起不到什么作用。

这个项目比较好的一点是，现在 Faster CPython 那边会定期把对应的数据推送到 Faster CPython 的仓库里。具体周期我不太清楚，应该是每个小版本都会做一次统计，包括里面的 profile 信息也都会推上去。大家如果感兴趣，或者想做优化方面的事情，可以关注一下，当作是了解他们的进展。看到里面有一些非常慢、或者说非常不和谐的数据，其实就可以去找对应的优化机会。

主持人：理解。那关于这个优化，能不能给大家简单讲一下：比如我想把两个 opcode 合成一个，那肯定要添加一条新的 opcode、一条新指令。这个工作量具体有多大？比如一个刚想在这方面做点工作的人，有没有能力完成这样的工作？

Penguin：我觉得里面困难最大的是搞清楚 Python 整个编译的流程，因为它很多东西都是自动生成的。Python 里有一个 opcode.py。如果大家用过 dis，也就是反汇编这个标准库，会发现 dis 里其实就是 import 了 opcode 这个 Python 文件。这里面写好了 opcode 的定义：它通过一个 def_op 函数，定义每个 opcode 的字符串是什么、有没有参数、是不是一条带地址的 jump，或者别的什么属性。如果我们要新增一个 opcode，就修改这个文件，可以照着已有的 opcode 去添加你想要的属性。如果想对它做 specialize，也就是特化，就在这个文件后面继续追加，写明要把它映射成哪一条或者哪几条指令。

这个文件会帮你自动生成 opcode 的定义，也就是 opcode.h，以及 opcode_targets，也就是跳转表。有了这些之后，一是要在 compile.c 里合适的位置加上编译这个语句或表达式的逻辑；二是要写它的执行逻辑，也就是它是怎么执行的。在 3.12 里，整个执行部分也改成了自动生成，应该是在 bytecodes.c 这个文件里，具体文件名我不太记得了。里面用的是一种类似 C 语言的 DSL 语法，写法更 high level、更贴近人一些，比如入栈出栈是用具体的变量名来表示的。你在里面写好执行这条 opcode 的逻辑，它也会自动生成，生成之后再全部编译到一起，整个解释器就能重新跑起来了。

麻烦的地方在于，由于自动生成的东西很多，调试的时候你会发现可能出现调试信息映射不上，或者你不知道该怎么改。比如我想在调试时对它生成出来的中间文件做一点修改看看效果，这时候你可能不知道这个文件在哪、是怎么生成的。所以第一步，我建议大家先去看一下它的 Makefile，或者把整个编译过程打印出来。等你知道每个步骤是哪个可执行文件在执行、输入输出分别是什么，再去改 opcode，可能就会轻松一点。

主持人：听起来还挺复杂，有一些 hidden knowledge，一些经验方面的东西。

Penguin：是的。我觉得他们现在这套流程是改得越来越复杂了。以前 3.11 开发的时候还好，虽然复杂，但没有这么复杂，现在是越来越复杂了。

主持人：我记得以前至少实际执行字节码那块是在 ceval.c 里，不是自动生成的。

Penguin：对，它现在是自动生成一个 .h，再 include 到 ceval.c 里。调试的时候你会发现 GDB 在乱跳，因为它不光是自动生成，生成的时候还生成了映射的行号，就是通过 #line 指令去指定 GDB 此时应该跳到什么位置。所以实际上是一个自动生成的文件和一个你手写的、用来生成文件的源文件，两边互相跳转。经常出现的情况是：你用 GDB 调试，本来想 step into，结果按 F8 直接跳过去了，你压根没注意到这里其实是个函数调用，应该按 F7，结果按成了 F8，然后就跑飞了，断点也断不住。

而且断点也很不好打。因为 GDB 在调试到那个宏之前，应该是不知道那个输入文件存在的，所以断点打上去可能会显示无效断点之类的。

主持人：I see，因为文件是生成的。感觉这方面如果你能写一些文章，会很有帮助。我其实也很好奇，社区他们自己写出这套东西之后，调试是怎么调的，总不会完全靠肉眼吧。

主持人：我觉得 in general 来说，你想优化一个系统，肯定是优化做得越多，系统越复杂，程序员越难理解这个系统。Python 做成现在这么复杂的东西，可能也是在经历这个过程。因为我知道它一开始其实非常简单，各种各样的 specialization、各种优化都是没有的。

Penguin：对，我觉得这一定程度上也跟解释器本身的基础设施有关系。我们可以看到，3.11、3.12 有一段时间他们都是在补课，比如怎么做 profiler、怎么输出 opcode 执行的 summary。这其实说明他们之前因为没有优化的需求，对运行状态的监控、runtime 信息的收集可能不是很重视，从 3.11 开始终于做这件事了。但每一项功能都需要打磨，而从 3.11 到现在开发中的 3.13，时间也不算太长。所以可能需要越来越多的开发者参与到优化这件事里，提出各种意见，他们才会意识到：原来我的这个工具应该这样用。这还是需要更多的社区反馈。我其实提了好几个 PR，都是在修它的 specialize。

specialize 的时候，比如我 specialize 失败了，那它其实应该说出……我先跟听众解释一下：3.11 里增加了一项叫 specialization 的优化。这是什么意思呢？比如 LOAD_ATTR 这条指令，我写一个 A.B，也就是取 A 这个对象的 B 字段，它会编译成一条 LOAD_ATTR 指令，语义就是在 A 里找到 B 这个字符串对应的对象。可以想象成 Python 的每个 object 都是一个 map 或者 dict，它的字段都作为 dict 的一个 entry 保存，key 是名称，value 是对应的指针。原来的 LOAD_ATTR 执行起来非常复杂，因为要考虑 descriptor，如果你重载过相关方法可能还要去执行它；对 immutable 和 mutable 的对象也要分开处理，对 mutable 的对象，它会用一个 dict 存后来加上去的字段。这就导致我做一次 A.B 这样的查询，背后可能是十几层 C 函数调用，非常非常复杂，可能牵扯到 hash map，可能要反复遍历某个数组。

但我们又知道，通常读操作总是比写操作多：读取 A.B 一般比给 A.B 赋值多得多。换句话说，读操作不会影响对象的布局，那我就可以用一些 cache 去缓存上一次读过的位置。specialize 做的就是类似的事情：执行时它会记录这条 LOAD_ATTR 读取的位置在哪里，比如 A 这个对象的指针往后偏移多少就是属性 B。把这个偏移记录下来，下次访问时如果发现还是 A 这个对象，或者跟 A 同类型的对象，就可以直接用指针加偏移访问到 B 所在的位置，取出里面的内容，起到加速作用。这就是 specialize 一个典型的工作流程。当然 specialize 不只针对 LOAD_ATTR，还有 LOAD_GLOBAL，或者一些二元操作。核心思想都是：把能帮我快速复现上一次操作的信息保存下来，再次执行到这条指令并发现类型一致时，就利用这些信息加速查询。

但也可以想象，由于 Python 非常动态，我再次执行 A.B 时，A 可能已经不是上一次的类型了。也就是说，要再次访问 B，就得重新走一遍查询流程。这时就会出现所谓的 specialize fail，也就是特化失败。特化失败时，我们会希望它给出失败原因，这样统计之后，可以把其中出现频率特别高的原因再做针对性的优化，或者看看有没有优化的机会。我当然希望这个原因非常细致、更精确一点：比如你是因为类型不一致失败的，还是因为再次读之前这个变量被写过、没办法回到原来的位置读取等等。

但其实在 3.11、3.12，甚至可能现在的 3.13，specialize 的失败信息只能叫"八仙过海，各显神通"：你要做这个优化，自己想办法吧。所以我提的几个 patch 都是修这类问题。比如可能出现两个不同的 specialize 用了同一个错误码宏，导致输出的信息都是错的：我 LOAD_ATTR 失败的原因其实是类型不一致，但它和 list 的某个操作，比如针对 list 的 FOR_ITER 优化，用了同样的信息，结果打印出来告诉我 index 不对之类的，看起来就非常离谱。你觉得这不应该是它特化失败的原因，但它就是这么显示的，等你去 debug 的时候才发现是函数调用的问题。

主持人：对，是这些基础设施的问题。因为指令特化也非常新，肯定需要时间去追赶。我觉得像你之前提到的 opcode 统计，比如统计某个 opcode 的下一个是什么、出现频率是多少，已经是非常大的进步了，应该能帮助检测到很多性能问题，再去做优化。我觉得这方面应该能逐渐赶上。

Penguin：对。大家如果觉得自己的某个文件跑得特别慢，其实也可以尝试去看一下，这样能帮我们发现一些问题。比如你发现执行的脚本里出现了过多的 LOAD_GLOBAL，那可能是你用了太多全局变量，导致它每次都不得不去全局符号表里查询。这时一个常见的优化手段，就是先把它赋给一个局部变量，比如 local 的 a 等于 global 的 b，之后每次都用这个局部的 a，就能起到比较好的加速效果。

主持人：是的。好，我们聊完了 3.12 里的这个……其实你之前好像没说新加的 opcode 叫什么，是叫 RETURN_CONST，对吧？

Penguin：对。

主持人：就是把 LOAD_CONST 和 RETURN_VALUE 合成了一条 RETURN_CONST 指令。聊完这个，接下来再聊一个 Penguin 在 3.11 里做过的优化，就是给 GA object 添加 vectorcall。这个我今天才知道，完全不懂，所以请 Penguin 简单介绍一下。

Penguin：这个其实也是一个巧合。当时我在写一个如何用 Python 做一些泛型操作的项目，算是练习式或者教学式的项目。我现在做了一段时间优化之后，写完一个 Python 脚本，会下意识地想象一下它现在的 opcode 是什么状态。当时我看到，比如可以写 a = list[int] 这么一个表达式，就是把 list[int] 作为一个值存到 a 里。我就在想，如果对这个 a 做一次调用，比如 a()，它会被编译成什么样子？然后我就去翻了它的编译代码和执行代码。我也是那次才知道原来还有 GenericAlias object 这个东西，也就是 GA object。

它是什么呢？它其实是保存了类型信息的一个东西。我们写 list[int]，这个 GA object 里会有两个元素：一个可以叫它主 type 或者 host type，也就是 list；另外它会用一个数组保存中括号里的内容。如果你写的是 dict[str, int]，这个数组就是 str 和 int 两个元素。当我对它进行调用的时候，比如把 list[int] 存到 a 里再调用一次，它其实会用它保存的 list 这个 type 直接做一次 type call。可以想象成这时候 a 已经等价于 list 了，它保存的 int 或者别的元素在调用过程中并没有起什么作用，这时就等价于直接调用 list 这个内置类型。

但它调用的时候走的是原来非常非常慢的一套逻辑，就是直接调用 GA object 的 tp_call。Python 里所有东西都是对象，任意对象都可以被调用，只不过调用可能会失败。调用本身其实是去调这个对象的 type 里保存的一个 tp_call 函数指针，这个指针对应的就是这个对象的调用逻辑。我发现这时候它走的就是 tp_call。tp_call 应该是大家最常见的 Python 调用逻辑了，它可以兼容任意的调用约定，比如传不定长参数、传 kwargs 等等。但它的坏处就是非常慢：每次调用都要分析传进来的参数里有没有变长参数，有的话要包装成 tuple；有没有带名字的参数，有的话要包装成一个 dict，然后再丢给真正执行的函数。所以这个过程里有很多封装和解封装的逻辑。

3.8 还是 3.10 的时候，已经加入了 vectorcall。vectorcall 的意思是：如果我发现参数的排布没有不定长参数之类别的调用约定，就是一个正常的、按 1、2、3、4 依次排好的函数调用，那就尝试走 vectorcall 的逻辑。直接把参数放在一个对应的数组上，其实就是放在它的栈上，只把栈上第一个参数的位置传给这个函数，它就可以直接用这个指针加偏移访问每个参数了。这样就省去了大量调用相关的代码，比如参数分析、box/unbox 等等。

而 list 正好是调用逻辑相对确定的，你要么传入另一个可迭代对象，要么传别的一些东西。所以我们可以尝试让 GA object 的 tp_call 直接去调用 list 的 vectorcall；或者更进一步，直接把 GA object 的调用逻辑改成：如果 host type 有 vectorcall，就去调用它。这样就相当于实现了最快的那套函数调用逻辑。这听起来可能非常不直观，需要大家对 Python 的函数调用以及 vectorcall、tp_call 这些逻辑有个简单的认识。总之我的修改就是：原来是一套非常慢的函数调用逻辑，现在如果存在对应的 vectorcall，就直接调用它，从而起到加速的作用。

主持人：我有两个问题。第一个是，如果这个 vectorcall 失败了，你是会走原来正常的调用逻辑吗？

Penguin：是这样，vectorcall 不会失败，它只可能不存在。比如你自己写一个 type，给它定义了 __call__，这样你就可以直接调用它的对象。这时候它一定只有 tp_call 而没有 vectorcall，就是 vectorcall 这个指针可能不存在，但它不会调用失败。

主持人：相当于你是检测它存不存在？

Penguin：对，我检测它存不存在，如果存在，就去调用它的 vectorcall。

主持人：OK，换句话说，GA object，也就是 list[int] 这种泛型对象，它一定存在 vectorcall 这个指针，你一定可以调用 vectorcall，不会失败。

主持人：理解。那我还有一个问题：为什么你会去调用一个泛型类型？感觉毫无意义。

这时候就会发现，你会遇到非常多需要 call type 的操作。比如 3.10 的时候，还没办法直接写一个泛型 T，必须把它变成一个 TypeVar，包装起来，写成 T = TypeVar("T")，然后才能使用这个 T。我当时就在想：既然泛型都可以直接赋值给某个变量，这时候 T 肯定就是一个变量、一个具体的 object，那它必然有初始化函数、有调用函数，或者可以对它做加法。比如我重载它的 __add__，那这个 type 就一定可以直接做加法。有了这些乱七八糟的想法，我就挨个去试，试到 call 的时候，我发现这个地方好像写得不是那么快。

我一直有一个观点：代码是生长出来的，项目是生长出来的，不是写出来、定义出来，或者像工程师那样一砖一瓦堆起来的。中间因为业务问题、挣不挣钱的问题、运维的问题等等各种原因，都会导致代码发生腐化，整个工程会逐渐向更差的状态滑落。这时需要有一个人帮你卡住它，告诉你现在有什么问题，我已经帮你挡住了这个下滑的趋势，但线上还是需要业务程序员去做这样那样的工作，去重构、去优化、去更新，这样才能保证项目继续运行下去。所以一定程度上来讲，做优化的这帮人本质上是在帮这个项目延长生命周期，让它不至于那么快死掉，不至于因为代码本身的问题而挂掉。

Penguin：这个问题问得好。我只能说，如果我们做出来，必然是有利于国产化的。以上仅代表个人想法，不代表我们组的官方态度。

第三位参与者：明白明白。我现在看到很多这类工作，就会下意识地去想，在国产化里这些东西能不能用上。

主持人：这个国产化指的是哪部分，CPU 吗？

第三位参与者：CPU、GPU 都有。从网卡、加速卡，到上层的 CPU、GPU，都是一套全新的东西。比如 AI 方向有华为的昇腾，还有上海的某家厂商，我忘了名字；CPU 有龙芯、华为的，还有几家我也忘了。反正要求的是国产化占比，政企那边对这方面的要求会比较多一些。

主持人：至少说明 job security 很有保障，未来很长一段时间都有活干。

第三位参与者：对，是的。

主持人：好，聊到这里，今天想聊的也差不多聊完了。Penguin 你有没有什么想对听众说的话，或者想聊但还没聊到的地方？

Penguin：其实差不多了，也没有什么觉得还没聊够的。

主持人：那我代表听众再问一个问题：如果有新毕业的同学，也想在大公司里做编译器方面的工作，你有没有什么建议？

Penguin：想做编译器工作的应届生，那可太稀有了。

主持人：你们现在招不到人，是这个意思吗？

Penguin：是这样，从整个生态来讲，编译器口应该是分到毕业生最少的方向了，可能比 OS 还要少。因为很多学生其实并不知道不同业务方向之间的分野，有的大有的小，也不知道具体差异在哪里，也不太清楚未来工作到底能做哪些业务、有哪些方向可以选。大家一说起互联网、IT、计算机，就是前端、后端、客户端，可能不知道其实还有人做 OS、有人做编译器等等。他本身不了解：我们学的是计算机，而不是互联网；作为程序员，你是一个计算机工程师，而不是互联网工程师。这个概念在国内被大众或者传媒混淆得很厉害。几年前我还能听到"嵌入式程序员不算程序员"这种说法。大家可能不知道有各种各样的方向可以选，然后就卷在了前端、卷在了后端。

现在每次有人在论坛或者别的地方问：哎呀，现在好卷啊，毕业生该怎么办？我都说：转编译器啊，去写编译器啊。这不是说我们组有多缺人，而是整个方向、整个大环境里，编译器总有缺人的地方，总有在招人的地方。因为整个环境是缺人的状态，哪怕今天腾讯不行、阿里不行，你还可以去别的公司，总有缺人的地方。而且随着业务规模扩大，比如 AI 时代到来，很多传统的编译器程序员都去做 AI compiler 了，需求一定是在往上涨的。但现在明显的一点是，进来的新鲜血液并不算多，能拿到的人才不算充裕。所以很多时候不是我们不想招人，而是真的招不到人。可能聊了半天觉得这个小伙子不错，结果被微信给抓走写后台去了，就有这样的情况。

主持人：所以你说的是在集团内招人的优先级不够，headcount 不够？

Penguin：不是集团的问题。我觉得是整个编译器方向，大家了解到、或者意识到这个方向缺人的程度不够，所以整个方向没有比较充足的人力，间接导致我们也招不到人。

主持人：换句话说，如果在校的同学想往这方面投入，其实是一个很不卷的赛道，对吧？

Penguin：对，相对很不卷了。我觉得一个毕业生也许能同时拿到两家的 offer，是有这个可能的。在现在的就业形势下，这已经是一个不错的状态了。

第三位参与者：我觉得这是一个很好的建议。我也跟着打个广告：如果你实在对编译器看不上眼，可以考虑一下我们 SRE，我们也非常缺人。我们 SRE 我觉得还是挺受重视的，非常缺人，可能招半年、招一年都招不到一两个合适的。我现在是自由职业给客户做事，我们有个岗位招了一年半才招到。

主持人：那可能是你们要求太高，跟编译器有点类似，都是要求比较高吧。

第三位参与者：其实也没有。主要是大家觉得这个东西跟我没什么关系，觉得太陌生，跟编译器有点像，导致新人来得少，最后市面上的供给也少。

主持人：没事，只要跟 AI 扯上关系，大张旗鼓地宣传这是 AI 时代的什么必备岗位，就能招到人了。

第三位参与者：OK。就像 Penguin 说的，这两年各种岗位的概念混淆得特别多。像做前端的，很多人会问：网络跟我有什么关系，我只是个前端。做后端的也会说：某某东西跟我有什么关系，我只是个 CRUD boy。大家其实是把互联网的某某工程师和计算机工程师等同起来了，而且很多时候他们并不认为自己是计算机工程师。

主持人：是的，编程不只是 CRUD。好，那我们今天差不多就到这里结束，大家跟听众们打个招呼吧。各位听众，我们下期再见，拜拜。

Penguin：好，拜拜。
