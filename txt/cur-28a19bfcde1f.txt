现代 Web 规范中通过 Fetch API 提供的流式处理能力，其核心设计目标在于实现边下载边解析或边处理边上传的数据流水线，而在测量精确的上传与下载传输进度方面存在根本性的机制错位。将请求流（Request Streams）或响应流（Response Streams）直接用于驱动用户界面的进度条，不仅会得出严重偏离物理事实的虚假进度，还可能在未来限制浏览器网络协议栈对缓冲区尺寸的深度优化。

在下载场景下，利用响应流（Response Body Streams）计算进度的失效根源在于内容编码解压缩的时序错位：
1. 压缩尺寸与解码载荷的冲突：通过 response.body.getReader() 或异步迭代器消费 Chunk 时，应用层读取到的是浏览器解压缩之后（Decompressed）的明文数据；然而，响应头中的 Content-Length 字段在启用 gzip 或 brotli 压缩传输时，记录的严格是网络传输中已编码压缩包（Encoded Size）的物理字节数。
2. 进度计算越界崩溃：当开发者使用累计读取的明文 Chunk 字节数除以 Content-Length 时，由于文本或 JSON 经压缩后的体积通常只有原始数据的 20% 到 50%，下载百分比会迅速突破 100% 乃至达到数百，导致前端进度计算完全失真。在流式 API 规范原生暴露未解压原始流（Raw Body）之前，响应流无法作为可信的下载进度度量工具。

在上传场景下，利用请求流（Fetch Upload Streams）度量进度的逻辑缺陷更为严峻：
- 投递行为与送达事实的错位：请求流允许将视频转码流或客户端生成的数据直接作为 POST 正文发送（需声明 duplex: 'half' 并基于 HTTP/2+ 多路复用传输），其核心优势在于计算与上传的并行重叠。然而，当应用向流管道推送 Chunk 时，从流中读取字节仅仅代表数据被浏览器的内部网络模块取走，绝不代表数据已通过网卡发送并在服务端确认接收（ACK）。
- 缓冲区与水位线干扰：流式规范依赖高水位线（High Water Mark）进行背压调控。网络引擎会在本地建立多级 Socket 缓冲区与重传队列。如果开发者将本地 Chunk 的出队时机作为上传进度，进度条会在数据刚写入本地内存缓冲区时瞬间假死或显示 100%，而真实的物理网络上传仍在后台缓慢进行。
- 阻碍浏览器底层演进：若前端生态大规模依赖请求流消耗来伪造上传进度，浏览器团队后续若为了提升吞吐量而增大内部缓冲区尺寸，就会直接导致上层应用的进度计算更加失真，从而迫使浏览器在性能演进与向下兼容间妥协。

在现阶段的浏览器标准中，若需实现具备物理准确性的传输进度监听，XMLHttpRequest 依然是唯一标准途径，其 xhr.upload.onprogress 与 xhr.onprogress 能够直接基于协议栈底层的物理分段确认事件触发回调。对于 Fetch API，目前由标准化组织推进的 Observer 提案（通过 fetch 配置 observer 监听请求与响应事件）正在制定中，在规范正式落地前，不应使用 Fetch 流来测量传输进度。
