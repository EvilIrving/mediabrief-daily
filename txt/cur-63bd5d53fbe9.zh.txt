用侧信道读取特权内存（Reading privileged memory with a side-channel）

发布者：Jann Horn，Project Zero

我们发现，CPU 数据缓存的时序可以被滥用，从错误推测执行（mis-speculated execution）中高效地泄漏信息，在最坏情况下，会在多种场景中造成跨越本地安全边界的任意虚拟内存读取漏洞。

已知这一问题的多个变体会影响许多现代处理器，包括 Intel、AMD 和 ARM 的部分处理器。对于少数几款 Intel 和 AMD CPU 型号，我们已经有能针对真实软件奏效的漏洞利用。我们于 2017-06-01 向 Intel、AMD 和 ARM 报告了这个问题 [1]。

到目前为止，这一问题已知有三个变体：

- 变体 1：边界检查绕过（bounds check bypass，CVE-2017-5753）

- 变体 2：分支目标注入（branch target injection，CVE-2017-5715）

- 变体 3：恶意数据缓存加载（rogue data cache load，CVE-2017-5754）

在本文所述问题公开披露之前，Daniel Gruss、Moritz Lipp、Yuval Yarom、Paul Kocher、Daniel Genkin、Michael Schwarz、Mike Hamburg、Stefan Mangard、Thomas Prescher 和 Werner Haas 也报告了这些问题；他们的［文章 / 博客 / 论文草稿］见：

- Spectre <https://spectreattack.com/spectre.pdf>（变体 1 和 2）

- Meltdown <https://meltdownattack.com/meltdown.pdf>（变体 3）

在研究过程中，我们开发了以下概念验证（PoC）：

1. 一个在用户空间演示变体 1 基本原理的 PoC，在测试用的 Intel Haswell Xeon CPU、AMD FX CPU、AMD PRO CPU 和一颗 ARM Cortex A57 上运行 [2]。这个 PoC 只测试能否在同一进程内、在错误推测执行中读取数据，不跨越任何权限边界。

2. 一个变体 1 的 PoC：在采用发行版标准配置的现代 Linux 内核下，以普通用户权限运行时，可以在 Intel Haswell Xeon CPU 上对内核虚拟内存中一段 4GiB 的范围 [3] 进行任意读取。如果启用了内核的 BPF JIT（非默认配置），它在 AMD PRO CPU 上也能奏效。在 Intel Haswell Xeon CPU 上，经过大约 4 秒的启动时间后，可以以每秒约 2000 字节的速度读取内核虚拟内存。[4]

3. 一个变体 2 的 PoC：在 Intel Haswell Xeon CPU 上、用 virt-manager 创建的 KVM 客户机内以 root 权限运行，宿主机运行特定（现已过时）版本的 Debian 发行版内核 [5] 时，可以以每秒约 1500 字节的速度读取宿主机内核内存，且仍有优化空间。在实施攻击之前，需要先进行一些初始化，对一台 64GiB 内存的机器来说大约需要 10 到 30 分钟；所需时间应大致与宿主机内存大小成线性关系。（如果客户机可以使用 2MB 大页，初始化应该会快得多，但这一点还没有测试过。）

4. 一个变体 3 的 PoC：以普通用户权限运行时，可以在满足某个前提条件的情况下，在 Intel Haswell Xeon CPU 上读取内核内存。我们认为这个前提条件是目标内核内存位于 L1D 缓存中。

关于这一主题的有用资料，请看下方"文献"一节。

关于本文中对处理器内部机制的解释，需要提醒一句：本文包含大量基于观察到的行为、对硬件内部机制所做的推测，这些推测未必与处理器实际的工作方式相符。

我们对可能的缓解措施有一些想法，并已将其中一部分提供给处理器厂商；不过，我们认为处理器厂商比我们更有条件设计和评估缓解措施，我们也期望由他们来提供权威指导。

我们发给 CPU 厂商的 PoC 代码和说明文档可以在这里获取：https://bugs.chromium.org/p/project-zero/issues/detail?id=1272。

# 术语表

提交（retire）：当一条指令的结果（例如寄存器写入和内存写入）被提交并对系统其余部分可见时，就称该指令提交（retire）了。指令可以乱序执行，但必须始终按顺序提交。

逻辑处理器核心（logical processor core）：逻辑处理器核心就是操作系统眼中的处理器核心。启用超线程时，逻辑核心数是物理核心数的整数倍。

已缓存 / 未缓存数据（cached/uncached data）：在本文中，"未缓存"数据指只存在于主内存中、不在 CPU 任何一级缓存中的数据。加载未缓存数据通常需要超过 100 个 CPU 时钟周期。

推测执行（speculative execution）：处理器可以在不知道一个分支是否会被采用、也不知道其目标在哪里的情况下越过该分支继续执行，因而会在尚不知道某些指令是否应当执行时就执行它们。如果这种推测事后被证明是错误的，CPU 可以丢弃由此产生的状态，不产生架构层面的影响，并在正确的执行路径上继续执行。在确知指令位于正确执行路径上之前，指令不会提交。

错误推测窗口（mis-speculation window）：CPU 推测执行了错误的代码、但尚未发现已发生错误推测的那段时间窗口。

# 变体 1：边界检查绕过

本节解释三个变体共同的理论基础，以及我们变体 1 PoC 背后的理论。该 PoC 在 Debian 发行版内核下于用户空间运行时，至少在以下配置中可以对内核内存中一段 4GiB 的区域进行任意读取：

- Intel Haswell Xeon CPU，eBPF JIT 关闭（默认状态）

- Intel Haswell Xeon CPU，eBPF JIT 开启（非默认状态）

- AMD PRO CPU，eBPF JIT 开启（非默认状态）

eBPF JIT 的状态可以通过 net.core.bpf_jit_enable 这个 sysctl 来切换。

## 理论解释

《Intel 优化参考手册》（Intel Optimization Reference Manual）<https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-optimization-manual.pdf> 在第 2.3.2.3 节（"分支预测"）中谈到 Sandy Bridge（及之后的微架构修订版本）时这样写道：

> 分支预测会预测分支目标，使处理器能在分支的真实执行路径确定之前很久，就开始执行指令。（Branch prediction predicts the branch target and enables the processor to begin executing instructions long before the branch true execution path is known.）

在第 2.3.5.2 节（"L1 数据缓存"）中写道：

> 加载操作可以：
>
> [...]
>
> - 在前面的分支得到解析之前，以推测方式执行。
> - 乱序地、重叠地处理缓存未命中。

《Intel 软件开发者手册》（Software Developer's Manual）[7] 第 3A 卷第 11.7 节（"隐式缓存（Pentium 4、Intel Xeon 和 P6 系列处理器）"）写道：

> 当一个内存单元被置为可能可缓存时，就会发生隐式缓存，即使该单元在正常的冯·诺依曼顺序中可能从未被访问过。由于激进的预取、分支预测和 TLB 未命中处理，P6 及更新的处理器系列上会发生隐式缓存。隐式缓存是现有 Intel386、Intel486 和 Pentium 处理器系统行为的延伸，因为在这些处理器系列上运行的软件同样无法确定性地预测指令预取的行为。

看下面的代码示例。如果 arr1->length 未被缓存，处理器可以推测性地从 arr1->data[untrusted_offset_from_caller] 加载数据。这是一次越界读取。这本应无关紧要，因为当分支执行完毕后，处理器实际上会回滚执行状态；推测执行的指令都不会提交（例如不会导致寄存器等受到影响）。

```
struct array {
  unsigned long length;
  unsigned char data[];
};
struct array *arr1 = ...;
unsigned long untrusted_offset_from_caller = ...;
if (untrusted_offset_from_caller < arr1->length) {
  unsigned char value = arr1->data[untrusted_offset_from_caller];
  ...
}
```

然而，在下面这个代码示例中就有问题了。如果 arr1->length、arr2->data[0x200] 和 arr2->data[0x300] 未被缓存，而其他所有被访问的数据都已缓存，并且分支条件被预测为真，那么在 arr1->length 加载完成、执行被重新引导之前，处理器可以推测性地完成以下操作：

- 加载 value = arr1->data[untrusted_offset_from_caller]

- 从 arr2->data 中一个依赖于数据的偏移处开始加载，把对应的缓存行载入 L1 缓存

```
struct array {
  unsigned long length;
  unsigned char data[];
};
struct array *arr1 = ...; /* small array */
struct array *arr2 = ...; /* array of size 0x400 */
/* >0x400 (OUT OF BOUNDS!) */
unsigned long untrusted_offset_from_caller = ...;
if (untrusted_offset_from_caller < arr1->length) {
  unsigned char value = arr1->data[untrusted_offset_from_caller];
  unsigned long index2 = ((value&1)*0x100)+0x200;
  if (index2 < arr2->length) {
    unsigned char value2 = arr2->data[index2];
  }
}
```

（代码注释：small array = 小数组；array of size 0x400 = 大小为 0x400 的数组；>0x400 (OUT OF BOUNDS!) = 大于 0x400（越界！））

处理器发现 untrusted_offset_from_caller 大于 arr1->length 后，执行会返回到非推测路径，但包含 arr2->data[index2] 的缓存行仍留在 L1 缓存中。通过测量加载 arr2->data[0x200] 和 arr2->data[0x300] 所需的时间，攻击者就能判断推测执行期间 index2 的值是 0x200 还是 0x300，从而得知 arr1->data[untrusted_offset_from_caller]&1 是 0 还是 1。

要真正把这种行为用于攻击，攻击者需要能够在目标上下文中，带着越界索引触发这种有漏洞的代码模式的执行。为此，这种有漏洞的代码模式要么已经存在于现有代码中，要么必须存在一个可以用来生成这种代码模式的解释器或 JIT 引擎。到目前为止，我们还没有真正找到这种有漏洞代码模式的任何现成的、可利用的实例；利用变体 1 泄漏内核内存的 PoC 使用的是 eBPF 解释器或 eBPF JIT 引擎，二者都内置于内核中，普通用户即可访问。

一个小变种是改为对函数指针进行越界读取，以便在错误推测路径中取得执行控制权。我们没有进一步研究这个变种。

## 攻击内核

本节更详细地说明如何利用变体 1、借助 eBPF 字节码解释器和 JIT 引擎泄漏 Linux 内核内存。虽然变体 1 攻击有许多有意思的潜在目标，但我们选择攻击 Linux 内核中的 eBPF JIT/解释器，因为与大多数其他 JIT 相比，它给攻击者提供了更多控制。

Linux 内核从 3.18 版开始支持 eBPF。无特权的用户空间代码可以向内核提供字节码，字节码经内核验证后：

- 要么由内核中的字节码解释器解释执行

- 要么由 JIT 引擎翻译成同样在内核上下文中运行的本地机器码（JIT 引擎逐条翻译字节码指令，不做任何进一步优化）

字节码的执行可以这样触发：把 eBPF 字节码作为过滤器挂到一个套接字上，然后从套接字的另一端发送数据。

JIT 引擎是否启用取决于一个运行时配置项，但至少在测试用的 Intel 处理器上，无论这个设置如何，攻击都能奏效。

与经典 BPF 不同，eBPF 拥有数据数组和函数指针数组之类的数据类型，eBPF 字节码可以对其进行索引。因此，可以用 eBPF 字节码在内核中构造出上面描述的代码模式。

eBPF 的数据数组效率不如函数指针数组，因此攻击会尽可能使用后者。

做测试的两台机器都没有 SMAP，PoC 依赖这一点（不过原则上这不应当是前提条件）。

此外，至少在做测试的那台 Intel 机器上，在核心之间来回传递（bouncing）被修改的缓存行很慢，原因显然是缓存一致性使用了 MESI 协议 [8]。在一个物理 CPU 核心上修改 eBPF 数组的引用计数，会使包含该引用计数的缓存行被转移到这个 CPU 核心上，从而让所有其他 CPU 核心读取该引用计数变慢，直到修改后的引用计数被写回内存为止。由于 eBPF 数组的长度和引用计数存放在同一个缓存行中，这也意味着在一个物理 CPU 核心上修改引用计数，会让其他物理 CPU 核心读取该 eBPF 数组的长度变慢（有意制造的伪共享）。

攻击使用两个 eBPF 程序。第一个程序以可配置的索引，通过一个按页对齐的 eBPF 函数指针数组 prog_map 进行尾调用。简单来说，这个程序用来确定 prog_map 的地址：猜测从 prog_map 到某个用户空间地址的偏移，并在猜测的偏移处通过 prog_map 进行尾调用。为了让分支预测认为该偏移小于 prog_map 的长度，中间会穿插对界内索引的尾调用。为了扩大错误推测窗口，包含 prog_map 长度的缓存行会被转移到另一个核心上。要检验某次偏移猜测是否成功，可以检测那个用户空间地址是否已被载入缓存。

由于这样直接暴力猜测地址会很慢，因此采用了如下优化：在用户空间地址 user_mapping_area 处创建 2^15 个相邻的用户空间内存映射 [9]，每个映射由 2^4 个页组成，总共覆盖 2^31 字节的区域。每个映射都映射到同一组物理页，并且所有映射都存在于页表中。

这样攻击就可以以 2^31 字节为步长进行。每一步中，在通过 prog_map 引发一次越界访问之后，只需检测 user_mapping_area 前 2^4 个页中每页的一个缓存行是否已被缓存。由于 L3 缓存是按物理地址索引的，对映射某个物理页的任一虚拟地址的访问，都会使映射同一物理页的所有其他虚拟地址也变为已缓存。

当这种攻击找到一次命中，也就是一个已缓存的内存位置时，内核地址的高 33 位就知道了（因为可以从命中时的地址猜测值推出），地址的低 16 位也知道了（从命中所在的 user_mapping_area 内偏移得出）。user_mapping_area 地址中剩下未知的是中间部分。

中间剩余的位可以通过对剩余地址空间做二分来确定：把两个物理页映射到相邻的两段虚拟地址范围，每段虚拟地址范围的大小为剩余搜索空间的一半，然后逐位确定剩余的地址。

此时，就可以用第二个 eBPF 程序来真正泄漏数据了。用伪代码表示，这个程序如下：

```
uint64_t bitmask = <runtime-configurable>;
uint64_t bitshift_selector = <runtime-configurable>;
uint64_t prog_array_base_offset = <runtime-configurable>;
uint64_t secret_data_offset = <runtime-configurable>;
// index will be bounds-checked by the runtime,
// but the bounds check will be bypassed speculatively
uint64_t secret_data = bpf_map_read(array=victim_array, index=secret_data_offset);
// select a single bit, move it to a specific position, and add the base offset
uint64_t progmap_index = (((secret_data & bitmask) >> bitshift_selector) << 7) + prog_array_base_offset;
bpf_tail_call(prog_map, progmap_index);
```

（代码注释：index will be bounds-checked by the runtime, but the bounds check will be bypassed speculatively = 运行时会对索引做边界检查，但这个边界检查会被推测性地绕过；select a single bit, move it to a specific position, and add the base offset = 选出单个比特，把它移到特定位置，再加上基准偏移。）

这个程序以运行时可配置的偏移，从 eBPF 数据数组"victim_map"中读取 8 字节对齐的 64 位值，并对该值做位掩码和移位，使一个比特被映射为两个相距 2^7 字节的值之一（用作数组索引时，这个距离足以保证不会落在同一个或相邻的缓存行中）。最后它加上一个 64 位偏移，再把得到的值用作 prog_map 的偏移进行尾调用。

接下来就可以用这个程序泄漏内存：反复调用该 eBPF 程序，传入一个指定要泄漏数据的、指向 victim_map 的越界偏移，以及一个使 prog_map + 偏移指向某个用户空间内存区域的、指向 prog_map 的越界偏移。误导分支预测和转移缓存行的方式与第一个 eBPF 程序相同，只是现在保存 victim_map 长度的缓存行也必须被转移到另一个核心上。

# 变体 2：分支目标注入

本节介绍我们变体 2 PoC 背后的理论。该 PoC 在 Intel Haswell Xeon CPU 上、用 virt-manager 创建的 KVM 客户机内以 root 权限运行，宿主机运行特定版本的 Debian 发行版内核时，可以以每秒约 1500 字节的速度读取宿主机内核内存。

## 基础

先前的研究（见文末"文献"一节）已经表明，处于不同安全上下文中的代码可以相互影响对方的分支预测。到目前为止，这只被用来推断代码所在位置的信息（换句话说，制造从受害者到攻击者方向的干扰）；而这一攻击变体的基本假设是，它也可以被用来重定向受害者上下文中代码的执行（换句话说，制造从攻击者到受害者方向的干扰，即反过来）。

这一攻击的基本思路是：瞄准包含间接分支的受害者代码，该间接分支的目标地址从内存中加载；把包含目标地址的缓存行刷出到主内存。这样，当 CPU 执行到这个间接分支时，它不知道跳转的真实目的地，而且在把该缓存行重新载入 CPU 之前都无法算出真实目的地，这需要几百个周期。因此，会有一个通常超过 100 个周期的时间窗口，CPU 在其中依据分支预测推测执行指令。

## Haswell 分支预测的内部机制

Intel 处理器所实现的分支预测，有一部分内部机制已经被公开；但要让这种攻击正常奏效，还需要大量进一步实验来确定更多细节。

本节重点介绍通过实验从 Intel Haswell Xeon CPU 上推导出的分支预测内部机制。

Haswell 似乎有多种工作方式差别很大的分支预测机制：

- 一个通用分支预测器，每个源地址只能存储一个目标；用于各种跳转，比如绝对跳转、相对跳转等等。

- 一个专门的间接调用预测器，每个源地址可以存储多个目标；用于间接调用。

- （根据 Intel 的优化手册，还有一个专门的返回预测器，但我们还没有详细分析它。如果能用这个预测器可靠地倾倒出虚拟机进入时所经过的部分调用栈，那会非常有意思。）

### 通用预测器

正如先前研究所记录的，通用分支预测器在预测时只使用源指令最后一个字节地址的低 31 位。例如，如果存在一条从 0x4141.0004.1000 跳转到 0x4141.0004.5123 的分支目标缓冲区（BTB）表项，通用预测器也会用它来预测从 0x4242.0004.1000 发出的跳转。当源地址的高位像这样不同时，预测出的目的地址的高位也会随之一起变化，在这个例子里，预测的目的地址将是 0x4242.0004.5123，所以这个预测器显然并不存储完整的绝对目的地址。

在用源地址的低 31 位查找 BTB 表项之前，会先用 XOR 把它们折叠在一起。具体来说，以下各位会被折叠在一起：

| A 位 | B 位 |
|---|---|
| 0x40.0000 | 0x2000 |
| 0x80.0000 | 0x4000 |
| 0x100.0000 | 0x8000 |
| 0x200.0000 | 0x1.0000 |
| 0x400.0000 | 0x2.0000 |
| 0x800.0000 | 0x4.0000 |
| 0x2000.0000 | 0x10.0000 |
| 0x4000.0000 | 0x20.0000 |

换句话说，如果把一个源地址同时与这张表中同一行的两个数做 XOR，分支预测器在查找时将无法区分得到的地址和原来的源地址。例如，分支预测器能够区分源地址 0x100.0000 和 0x180.0000，也能区分源地址 0x100.0000 和 0x180.8000，但不能区分源地址 0x100.0000 和 0x140.2000，也不能区分源地址 0x100.0000 和 0x180.4000。下文中把这种情况称为别名源地址（aliased source addresses）。

使用别名源地址时，分支预测器仍会预测出与非别名源地址相同的目标。这表明分支预测器存储的是截断后的绝对目的地址，但这一点尚未得到验证。

根据针对不同源地址观察到的最大向前和向后跳转距离推断，目标地址的低 32 位一半可能是以一个 32 位绝对值存储的，外加一个额外的位，用来表示从源到目标的跳转是否跨越了 2^32 的边界；如果跳转跨越了这样的边界，则由源地址的第 31 位决定指令指针的高半部分应当递增还是递减。

### 间接调用预测器

这一机制在查找 BTB 时的输入似乎是：

- 源指令地址的低 12 位（我们不确定是第一个字节还是最后一个字节的地址），或其中的一部分。

- 分支历史缓冲区的状态。

如果间接调用预测器无法解析某个分支，就改由通用预测器来解析。Intel 的优化手册暗示了这种行为："间接调用和跳转。它们可能被预测为具有单一不变的目标，也可能被预测为具有随近期程序行为而变化的目标。"（Indirect Calls and Jumps. These may either be predicted as having a monotonic target or as having targets that vary in accordance with recent program behavior.）

分支历史缓冲区（BHB）存储最近 29 个已采用分支的信息，基本上相当于近期控制流的指纹，用来更好地预测可能有多个目标的间接调用。

BHB 的更新函数的工作方式如下（用伪代码表示；src 是源指令最后一个字节的地址，dst 是目的地址）：

```
void bhb_update(uint58_t *bhb_state, unsigned long src, unsigned long dst) {
  *bhb_state <<= 2;
  *bhb_state ^= (dst & 0x3f);
  *bhb_state ^= (src & 0xc0) >> 6;
  *bhb_state ^= (src & 0xc00) >> (10 - 2);
  *bhb_state ^= (src & 0xc000) >> (14 - 4);
  *bhb_state ^= (src & 0x30) << (6 - 4);
  *bhb_state ^= (src & 0x300) << (8 - 8);
  *bhb_state ^= (src & 0x3000) >> (12 - 10);
  *bhb_state ^= (src & 0x30000) >> (16 - 12);
  *bhb_state ^= (src & 0xc0000) >> (18 - 14);
}
```

在用于 BTB 访问时，BHB 状态中的部分位似乎还会进一步用 XOR 折叠在一起，但具体的折叠函数尚未弄清楚。

BHB 之所以有意思，有两个原因。第一，要想准确地在间接调用预测器中制造冲突，就需要了解它的大致行为。第二，它还允许在攻击者能够执行代码的任何可重复的程序状态下倾倒出 BHB 状态，例如在攻击虚拟机管理程序（hypervisor）时，就在一次超级调用（hypercall）之后立即进行。倾倒出的 BHB 状态随后可以用来给虚拟机管理程序做指纹识别；如果攻击者能拿到虚拟机管理程序的二进制文件，还可以用来确定虚拟机管理程序加载地址的低 20 位（对 KVM 来说，就是 kvm-intel.ko 加载地址的低 20 位）。

### 逆向分析分支预测器的内部机制

本小节介绍我们如何逆向分析 Haswell 分支预测器的内部机制。其中一部分是凭记忆写下的，因为我们当时没有详细记录自己做了什么。

我们最初尝试利用通用预测器向内核进行 BTB 注入，用的是先前研究中的知识：通用预测器只看源地址的低半部分，并且只存储部分目标地址。这算是有点效果，但注入成功率非常低，不到 1%。（这就是我们在初步 PoC 中针对运行在 Haswell 上的、经过修改的虚拟机管理程序使用方法 2 时所用的方法。）

我们决定编写一个用户空间测试用例，以便更方便地测试分支预测器在不同情况下的行为。

基于分支预测器状态在超线程之间共享的假设 [10]，我们编写了一个程序，让它的两个实例分别绑定到某个物理核心上运行的两个逻辑处理器之一，其中一个实例尝试进行分支注入，另一个测量分支注入成功的频率。两个实例都在禁用 ASLR 的情况下运行，在相同的地址上有相同的代码。注入进程对一个访问（每进程独立的）测试变量的函数进行间接调用；测量进程对另一个函数进行间接调用，该函数根据时序检测每进程独立的测试变量是否已被缓存，然后用 CLFLUSH 将其驱逐。两个间接调用都通过同一个调用点（callsite）发出。每次间接调用之前，都用 CLFLUSH 把存储在内存中的函数指针刷出到主内存，以扩大推测时间窗口。此外，由于 Intel 的优化手册中提到了"近期程序行为"，我们在间接调用之前插入了一串总是会被采用的条件分支。

在这个测试中，注入成功率超过 99%，为我们之后的实验打下了基础环境。

然后，我们试图弄清预测方案的细节。我们假设该预测方案使用了某种全局分支历史缓冲区。

为了确定分支信息在历史缓冲区中停留多久，我们在那一串总是会被采用的条件跳转之前，插入了一个只在两个程序实例之一中会被采用的条件分支，然后改变总是被采用的条件跳转的数量（N）。结果是，当 N=25 时，处理器能够区分这些分支（错误预测率低于 1%），但当 N=26 时就无法区分了（错误预测率超过 99%）。

因此，分支历史缓冲区必须能够存储至少最近 26 个分支的信息。

接着，我们把两个程序实例之一的代码在内存中移来移去。这揭示出只有源地址和目标地址的低 20 位会对分支历史缓冲区产生影响。

在两个程序实例中用不同类型的分支做测试后发现：静态跳转、被采用的条件跳转、调用和返回对分支历史缓冲区的影响方式相同；未被采用的条件跳转不影响它；起作用的是源指令最后一个字节的地址；IRETQ 不影响历史缓冲区状态（这对测试很有用，因为它可以制造出对历史缓冲区不可见的程序流）。

把间接调用之前的最后一个条件分支在内存中多次移动位置后发现，分支历史缓冲区的内容可以用来区分这最后一条条件分支指令的许多不同位置。这表明历史缓冲区存储的不是一串小的历史值；相反，它似乎是一个较大的缓冲区，历史数据在其中混合在一起。

然而，一个历史缓冲区要对分支预测有用，就需要在采用了一定数量的新分支之后"忘掉"过去的分支。因此，当新数据混入历史缓冲区时，不能导致历史缓冲区中已有各位的信息向下传播；既然如此，向上组合信息大概也不会很有用。考虑到分支预测还必须非常快，我们得出结论：历史缓冲区的更新函数很可能是把旧的历史缓冲区左移，然后把新状态 XOR 进去（见示意图）。

如果这个假设正确，那么历史缓冲区包含大量关于最近几个分支的信息，但对于它所含数据涉及的最早那个分支，只包含与每次历史缓冲区更新时移位数相等的那么多位信息。因此，我们测试了这样一种情况：在一次跳转之后接 32 次源和目标都固定的、总是被采用的跳转，翻转这次跳转的源地址和目标地址中的不同位，看能否让分支预测区分一个间接调用。[11]

中间隔着 32 次静态跳转时，翻转任何位似乎都没有影响，于是我们减少静态跳转的数量，直到能观察到差异为止。中间隔着 28 次总是被采用的跳转时的结果是：目标地址的 0x1 位和 0x2 位、源地址的 0x40 位和 0x80 位会产生这样的影响；但同时翻转目标的 0x1 位和源的 0x40 位，或者同时翻转目标的 0x2 位和源的 0x80 位，则无法区分。这说明历史缓冲区每次插入时的移位量是 2 位，也说明了历史缓冲区最低有效位中存储的是哪些数据。随后，我们在被翻转位的那次跳转之后减少固定跳转的数量，重复这一过程，以确定其余各位中存储的是什么信息。

## 从 KVM 客户机读取宿主机内存

### 定位宿主机内核

我们的 PoC 分几步定位宿主机内核。需要确定、并且在后续攻击步骤中必需的信息包括：

- kvm-intel.ko 地址的低 20 位

- kvm.ko 的完整地址

- vmlinux 的完整地址

回头看，这样做复杂得没有必要，但它很好地展示了攻击者可以使用的各种技术。更简单的方法是先确定 vmlinux 的地址，再用二分法确定 kvm.ko 和 kvm-intel.ko 的地址。

第一步，泄漏 kvm-intel.ko 的地址。为此，先倾倒出进入客户机之后的分支历史缓冲区状态。然后，针对 kvm-intel.ko 加载地址第 12 到 19 位的每一种可能取值，根据加载地址猜测值和进入客户机之前最后 8 个分支的已知偏移，计算历史缓冲区最低 16 位的预期值，再把结果与泄漏出的历史缓冲区状态的最低 16 位进行比较。

分支历史缓冲区状态是通过测量一个有两个目标的间接调用的错误预测率，以每次 2 位的步长泄漏出来的。到达这个间接调用的一种途径是：从一条 vmcall 指令出发，后面跟着一串 N 个分支，这些分支的源地址和目标地址的相关位全部为零。到达这个间接调用的第二种途径是：从用户空间中一串受控的分支出发，这些分支可以用来向分支历史缓冲区写入任意值。

错误预测率的测量方式与"逆向分析分支预测器的内部机制"一节相同，使用一个加载某缓存行的调用目标，和另一个检查该缓存行是否已被加载的调用目标。

当 N=29 时，如果受控的分支历史缓冲区值为零，就会高频率地发生错误预测，因为来自超级调用的所有历史缓冲区状态都已被抹掉。当 N=28 时，如果受控的分支历史缓冲区值是 0<<(28*2)、1<<(28*2)、2<<(28*2)、3<<(28*2) 之一，就会发生错误预测；通过测试全部四种可能，就能检测出哪一种是对的。然后，对于递减的 N 值，四种可能是 {0|1|2|3}<<(28*2) | (history_buffer_for(N+1) >> 2)。对递减的 N 值重复这一过程，就能确定 N=0 时的分支历史缓冲区值。

此时，kvm-intel.ko 的低 20 位已经知道了；下一步是大致定位 kvm.ko。

为此要使用通用分支预测器，利用每次超级调用时从 kvm.ko 到 kvm-intel.ko 的一次间接调用插入 BTB 的数据；这意味着必须从 BTB 中泄漏出这次间接调用的源地址。

kvm.ko 很可能位于 0xffffffffc0000000 到 0xffffffffc4000000 范围内的某处，按页对齐（0x1000）。这意味着"通用预测器"一节表格中的前四项适用；对于正确的地址，会有 2^4-1=15 个别名地址。但这也是一个优势：它把搜索空间从 0x4000 缩小到 0x4000/2^4=1024。

为了找到源的正确地址或它的某个别名地址，在所有可能的调用目标处（泄漏出的 kvm-intel.ko 低 20 位，加上调用目标在模块内的偏移，再加上 2^20 的某个倍数）放置通过某个特定寄存器加载数据的代码，并在所有可能的调用源处放置间接调用。然后，交替地执行超级调用，以及通过不同的、互不为别名的可能调用源执行间接调用，同时使用随机化的历史缓冲区状态，使专门预测机制无法起作用。这一步之后，kvm.ko 的加载地址还剩 2^16 种可能。

接下来，可以用类似的方式，利用一次从 vmlinux 到 kvm.ko 的间接调用来确定 vmlinux 的加载地址。幸运的是，vmlinux 加载地址中被随机化的位都没有被折叠在一起，所以与定位 kvm.ko 时不同，结果会直接是唯一的。vmlinux 按 2MiB 对齐，随机化范围为 1GiB，所以可能的地址仍然只有 512 个。

由于（据我们所知）简单的超级调用实际上并不会引发从 vmlinux 到 kvm.ko 的间接调用，我们改为使用对一个模拟串口状态寄存器的端口 I/O，用 virt-manager 创建的虚拟机在默认配置下就有这个串口。

唯一剩下的信息是，kvm.ko 的 16 个别名加载地址中哪一个才是正确的。由于指向 kvm.ko 的一次间接调用的源地址已经知道，这可以用二分法解决：在各个可能的目标处放置代码，根据推测执行的是哪一份代码，加载两个缓存行之一，然后测量被加载的是哪一个缓存行。

### 识别缓存组

PoC 假设虚拟机无法使用大页。为了找出相对于 4KiB 页边界具有特定对齐方式的所有 L3 缓存组的驱逐集合（eviction set），PoC 先分配 25600 个内存页。然后在一个循环中，从所有剩余的未分类页中随机选出子集，使子集中包含某个缓存组驱逐集合的缓存组数量的期望值为 1；通过反复访问子集中的缓存行并检测这些缓存行是否始终处于已缓存状态（如果是，它们很可能不属于某个驱逐集合），把每个子集缩减为一个驱逐集合；再尝试用新的驱逐集合去驱逐所有剩余的未分类缓存行，以判断它们是否属于同一个缓存组 [12]。

### 定位客户机页的宿主机虚拟地址

由于这种攻击使用 FLUSH+RELOAD 的方法泄漏数据，它需要知道某一个客户机页在宿主机内核中的虚拟地址。PRIME+PROBE 等替代方法应该不需要这个条件也能奏效。

这一攻击步骤的基本思路是：对虚拟机管理程序发动分支目标注入攻击，让它加载一个攻击者控制的地址，然后检测这是否导致客户机拥有的页被加载。为此，可以使用一个简单地从 R8 所指定内存位置加载数据的 gadget；在这个内核版本上，执行到客户机退出后的第一个间接调用时，R8 到 R11 中仍然是客户机控制的值。

我们原本预计，攻击者在这一步要么需要知道必须使用哪个驱逐集合，要么需要同时暴力尝试；然而实验表明，使用随机的驱逐集合也行。我们的推测是，观察到的行为实际上是 L1D 和 L2 驱逐的结果，这可能足以支撑几条指令的推测执行。

宿主机内核在 physmap 区域中映射了（几乎？）全部物理内存，包括分配给 KVM 客户机的内存。不过，physmap 的位置是随机化的（按 1GiB 对齐），位于一个大小为 128PiB 的区域中。因此，直接暴力搜索一个客户机页的宿主机虚拟地址会花很长时间。这并非一定不可能；粗略估计，假设每秒成功注入 12000 次，并行测试 30 个客户机页，应该在一天左右、也许更短的时间内就能完成；但这远不如在几分钟内做到那样令人印象深刻。

为了优化这一点，可以把问题拆开：先用一个能从物理地址加载的 gadget 暴力搜索物理地址，然后再暴力搜索 physmap 区域的基地址。由于通常可以假设物理地址远低于 128PiB，它可以被更高效地暴力搜索；之后再暴力搜索 physmap 区域的基地址也更容易，因为这时可以使用按 1GiB 对齐的地址猜测。

要暴力搜索物理地址，可以使用以下 gadget：

```
ffffffff810a9def:       4c 89 c0                mov    rax,r8
ffffffff810a9df2:       4d 63 f9                movsxd r15,r9d
ffffffff810a9df5:       4e 8b 04 fd c0 b3 a6    mov    r8,QWORD PTR [r15*8-0x7e594c40]
ffffffff810a9dfc:       81
ffffffff810a9dfd:       4a 8d 3c 00             lea    rdi,[rax+r8*1]
ffffffff810a9e01:       4d 8b a4 00 f8 00 00    mov    r12,QWORD PTR [r8+rax*1+0xf8]
ffffffff810a9e08:       00
```

通过适当设置 R9，这个 gadget 可以从内核代码段附近的区域加载一个 8 字节对齐的值，尤其是可以加载 physmap 的起始地址 page_offset_base。然后，R8 中原有的值（物理地址猜测值减去 0xf8）被加到前一次加载的结果上，再加上 0xfa，然后对结果进行解引用。

### 缓存组选择

为了选出正确的 L3 驱逐集合，基本上就是用不同的驱逐集合执行下一节中的攻击，直到奏效为止。

### 泄漏数据

到了这一步，通常需要在宿主机内核代码中找到一些 gadget，用来真正泄漏数据：从攻击者控制的位置读取，对结果做适当的移位和掩码，然后把结果用作对攻击者控制地址进行加载的偏移。但把 gadget 拼凑起来、弄清楚哪些在推测上下文中能用，似乎很麻烦。所以我们决定改用内置于宿主机内核中的 eBPF 解释器：虽然没有合法途径能从虚拟机内部调用它，但只要这段代码存在于宿主机内核的代码段中，就足以让它可以被用于攻击，和普通的 ROP gadget 一样。

eBPF 解释器入口点的函数签名如下：

```
static unsigned int __bpf_prog_run(void *ctx, const struct bpf_insn *insn)
```

第二个参数是一个指针，指向一个待执行的、经过静态预验证的 eBPF 指令数组，这意味着 __bpf_prog_run() 不会进行任何类型检查或边界检查。第一个参数只是作为初始模拟寄存器状态的一部分被存储，所以它的值无关紧要。

eBPF 解释器提供的功能包括：

- 多个模拟的 64 位寄存器

- 对模拟寄存器的 64 位立即数写入

- 从模拟寄存器中存储的地址读取内存

- 位运算（包括移位）和算术运算

要调用解释器入口点，需要一个 gadget：在控制了 R8 到 R11、并且已知内存位置上有受控数据的条件下，能够取得对 RSI 和 RIP 的控制。下面这个 gadget 提供了这一功能：

```
ffffffff81514edd:       4c 89 ce                mov    rsi,r9
ffffffff81514ee0:       41 ff 90 b0 00 00 00    call   QWORD PTR [r8+0xb0]
```

现在，把 R8 和 R9 指向 physmap 中某个客户机拥有页的映射，就可以在宿主机内核中推测执行任意未经验证的 eBPF 字节码。然后，就可以用相对简单的字节码把数据泄漏到缓存中。

# 变体 3：恶意数据缓存加载

基本上，请阅读 Anders Fogh 的博文：https://cyber.wtf/2017/07/28/negative-result-reading-kernel-memory-from-user-mode/

概括来说，使用这一变体的攻击试图在不误导内核代码控制流的情况下，从用户空间读取内核内存。其做法是使用前面几个变体所用的代码模式，只不过是在用户空间中。其背后的想法是：访问某个地址时的权限检查，可能不在把数据从内存读入寄存器的关键路径上，因为放在关键路径上的权限检查可能会对性能产生重大影响。相反，内存读取可能会立即把读取结果提供给后续指令，而只是异步地执行权限检查，并在重排序缓冲区（reorder buffer）中设置一个标志，如果权限检查失败，该标志会导致引发异常。

对于 Anders Fogh 的博文，我们有几点补充：

"设想在用户模式下执行下面这条指令

```
mov rax,[somekernelmodeaddress]
```

它在提交时会引发一个中断，[...]"

也可以把这条指令放在一个高延迟的、被错误预测的分支后面执行，以避免引发缺页异常。这还可能通过增大从内核地址读取到投递相应异常之间的延迟，来扩大推测窗口。

"首先，我调用一个会访问这块内存的系统调用。其次，我使用 prefetcht0 指令，提高这个地址被加载到 L1 中的几率。"

当我们在执行系统调用之后使用预取指令时，攻击对我们就不再奏效了，我们完全不知道原因。也许 CPU 以某种方式记录了上一次访问是否被拒绝，如果被拒绝，就阻止攻击奏效？

"幸运的是，我并没有得到一次慢速读取，这说明当访问不被允许时，Intel 会把结果置零。"

这种情况（从内核地址读取返回全零）似乎发生在没有被充分缓存、但页表项存在的内存上，至少在反复尝试读取之后是这样。对于未映射的内存，从内核地址读取根本不会返回结果。

# 进一步研究的思路

我们认为，我们的研究留下了许多尚未探究的研究课题，我们鼓励其他公开研究者去研究这些课题。

本节包含的推测比本文其余部分还要多，其中是一些未经测试、很可能毫无用处的想法。

## 不借助数据缓存时序的泄漏

值得探究的是，除了测量数据缓存时序之外，是否还有其他微架构攻击可以用来把数据从推测执行中带出来。

## 其他微架构

到目前为止，我们的研究相对集中在 Haswell 上。如果能看到其他细节会很有意思，例如其他现代处理器的分支预测是如何工作的，以及它们有多容易受到攻击。

## 其他 JIT 引擎

我们针对 Linux 内核内置的 JIT 引擎成功开发出了变体 1 攻击。值得看看的是，针对更先进、但对系统控制更少的 JIT 引擎发动攻击是否也切实可行，尤其是 JavaScript 引擎。

## 更高效地扫描宿主机虚拟地址和缓存组

在变体 2 中，扫描某个客户机拥有页的宿主机虚拟地址时，也许先尝试确定它所在的 L3 缓存组会比较合理。做法可以是通过 physmap 用某种驱逐模式进行 L3 驱逐，然后检测该驱逐是否影响到了客户机拥有的页。

同样的方法也许对缓存组也有效：用一个 L1D+L2 驱逐集合，在宿主机内核上下文中驱逐函数指针；用内核中的一个 gadget，通过物理地址驱逐一个 L3 缓存组；然后借此识别客户机的缓存行属于哪些缓存组，直到构造出一个由客户机拥有的驱逐集合为止。

## 倾倒完整的 BTB 状态

鉴于通用 BTB 似乎只能区分 2^(31-8) 个或更少的源地址，在大约几个小时量级的时间内倾倒出由例如一次超级调用所产生的完整 BTB 状态，似乎是可行的。（先扫描跳转源，然后对每个找到的跳转源，用二分法确定跳转目标。）即使宿主机内核是自行编译的，这也有可能被用来识别宿主机内核中函数的位置。

源地址别名会在一定程度上降低其用处，但由于目标地址不受别名影响，也许可以把来自 KASLR 偏移不同的多台机器的（源，目标）对关联起来，并利用 KASLR 是加法性的、而别名是按位的这一点，减少候选地址的数量。

这样一来，攻击者就有可能根据跳转偏移或函数之间的距离，推测宿主机内核的版本或编译它所用的编译器。

## 变体 2：用更高效的 gadget 进行泄漏

如果变体 2 使用了足够高效的 gadget，也许根本没有必要把宿主机内核的函数指针从 L3 缓存中驱逐出去；只把它们从 L1D 和 L2 中驱逐出去也许就够了。

## 各种提速

尤其是变体 2 的 PoC 仍然有点慢。部分原因可能是：

- 它一次只泄漏一个比特；一次泄漏更多比特应该是可以做到的。

- 它大量使用 IRETQ 来向处理器隐藏控制流。

值得看看用变体 2 能达到多高的数据泄漏速率。

## 通过返回预测器进行泄漏或注入

如果返回预测器在权限级别变化时也不会丢失其状态，它可能有两种用处：一是从虚拟机内部定位宿主机内核（这种情况下可以用二分法非常快地找出宿主机内核的完整地址），二是注入返回目标（尤其是当返回地址存放在一个可以被攻击者刷出、并且在返回指令执行之前不会被重新加载的缓存行中时）。

不过，到目前为止，我们用返回预测器做过的实验都还没有得出确定的结果。

## 从间接调用预测器中泄漏数据

我们尝试过从间接调用预测器中泄漏目标信息，但没能成功。

- https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-optimization-manual.pdf：Intel 的优化手册中有许多有意思的优化建议，暗示了相关的微架构行为；例如：

  - "把数据紧跟在间接分支之后放置可能会导致性能问题。如果这些数据全是零，它看起来就像一长串以内存为目的操作数的 ADD 指令，这可能导致资源冲突并拖慢分支恢复。此外，紧跟在间接分支之后的数据，在分支预测［原文如此，branch predication］硬件看来可能像是分支，从而可能分支出去执行其他数据页。这可能导致随后的自修改代码问题。"

  - "加载操作可以：[...] 在前面的分支得到解析之前，以推测方式执行。"

  - "软件应避免写入正在执行的同一个 1KB 子页中的代码页，也应避免在正被写入的同一个 2KB 子页中取指。此外，把包含直接执行或推测执行代码的页作为数据页与另一个处理器共享，可能会触发 SMC 条件，导致机器的整个流水线和踪迹缓存（trace cache）被清空。这是由自修改代码条件造成的。"

  - "如果被映射为 WB 或 WT，处理器的推测读取有可能把数据带入缓存"

  - "如果不把该区域映射为 WC，可能会让该缓存行被推测性地读入处理器缓存（经由一个被错误预测分支的错误路径）。"
