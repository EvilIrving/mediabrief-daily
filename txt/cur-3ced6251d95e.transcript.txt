Wes：欢迎收听 Syntax。今天我们来聊浏览器新推出的 Speculation Rules API（推测规则 API），说说它的好处、缺点等等。先简单交代一下我为什么想聊这个。

几周前，McMaster-Carr 的网站在网上火了。大家都在说：McMaster-Carr 的网站怎么这么快？一家上百年历史的老公司怎么能做出这么快的网站？于是我研究了一下他们用了哪些技巧来让网站感觉尽可能快。其中一项——我敢说是性价比最高的一项——就是当你把鼠标悬停在链接上时，他们会预加载那个页面的 HTML，也就是预加载（preload）和预连接（preconnect）。这种做法已经存在很久了，而且其实已经内置在很多框架里，比如 Next.js。但现在我们迎来了 Speculation Rules API，它将直接内置在浏览器中，而且能做的事情比这还要多，非常有意思。我还看到 Harry Roberts 在他的网站 CSS Wizardry 上用了它，挺巧妙的。好，我们开始吧。

先快速聊一下 Sentry，而且是结合推测规则来聊。在为这期节目做准备时，我给 Sentry 性能团队的几个人发了消息。因为推测规则的核心思路是：你预取一些页面，因为你猜用户会去访问它们；等用户真正访问时，页面就已经加载好了。那就会引出一个问题：用户到底有没有去访问？你预下载的页面里有多少比例真正被用到了？我问了他们，结果他们内部已经在讨论，是不是该在仪表盘里展示这类数据。目前还没有这个功能，因为显然这个规范还没在所有浏览器里落地，但已经有人在讨论这或许是个值得在仪表盘里展示的好指标。去 sentry.io/syntax 看看吧，你可以全面了解应用的错误和性能，当你的应用有慢的地方时它会告诉你。

好，我们来聊聊预加载（preload）、预取（prefetch）和预连接（preconnect）。浏览器里很早就有一种 link 标签，你可以放在文档的 head 里，写 link rel="preload" 或 rel="preconnect"。比如预连接，它的作用是告诉浏览器：在请求的生命周期里，你得先弄清楚，比如这个字体是从 cdn.coolguy.net 加载的，那就要先查出 cdn.coolguy.net 的 IP 地址，还要完成整个 SSL 握手、确认没问题。那就提前把这些都做好，这样当我需要你从这个 URL 下载东西时，所有这些开销都已经完成了，直接开始下载就行。

Scott：对。不知道这个比喻恰不恰当：预加载就像是"穿好鞋、上车，我们出发了"；而预连接则像是"我们可能要去个地方，先把导航打开、查好路线"，这样等真要出发时，我们就知道该怎么走，知道有多远、要去哪里。

Wes：对，完全正确。预加载和预连接都非常好用的一点在于 HTML 的解析方式：你可以把 preload 或 preconnect 放在文档的 head 里，告诉它网页字体、样式表之类的资源，浏览器在真正遇到它们之前就会开始下载。比如说网页字体：你得先加载 HTML，然后解析 HTML，HTML 发现有一个 CSS 文件，再去加载并解析 CSS，解析 CSS 的过程中才发现："哦，有个网页字体，我去下载一下。"这样你的请求就形成了瀑布流。所以如果你能在浏览器连 body 开始标签都还没碰到的时候就告诉它……

Scott：你在 Web 开发中肯定遇到过这个。Google Fonts 就是个很好的例子，因为用 Google Fonts 时你访问的是另一个域名，浏览器并不一定知道那个域名的 IP 地址。所以当你从 Google Fonts 复制那段代码片段时，它会给你预连接的 URL，让你粘贴到文档的 head 里。

Wes：对，我记得。我还记得第一次用 Gatsby 的时候——那是 Gatsby 非常早期的版本——你加载什么都觉得：我的天，怎么这么快？然后打开网络面板，就看到它在疯狂预加载。

Scott：是啊，挺好的。

Wes：甚至比如你有分页：如果用户在第二页，你可以预加载第三页，因为用户很可能会点它。这样做的结果是，浏览器会去下载那个 HTML，让它热乎乎地准备好。而且在 link 标签的情况下，它还会遍历整个页面寻找其中的资源，如果页面上有图片标签和 CSS，也会一并下载。这个我们已经有了一段时间，但它必须逐个资源地去做。

现在有了这个新的 API，叫 Speculation Rules API。它允许你在页面里放一个 script 标签，type 是 speculationrules。在里面，你既可以指定预渲染（prerender），也可以指定预取（prefetch）。预取会直接把那个文档的 HTML 下载下来，热乎乎地放着备用。预渲染则更进一步，真的把它渲染出来——有点像在一个新标签页里那样——它会下载 HTML、解析、在 DOM 里完成布局、下载所需的所有资源，比如图片、字体等等。而且你还可以写规则，用 CSS 选择器来指定：当链接匹配这个规则时就下载，不匹配时就不下载。实际的预渲染也一样。

Scott：那在要求客户端下载的东西方面，这岂不是很快就会失控？

Wes：对，完全会。每次谈到预取和预渲染，大家都会说："好吧……"因为 Next.js 这个功能已经有很久了，如果你预取和预渲染得太激进，你的账单就会往上涨。所以你得认真想想，在这里预取、预渲染这些东西值不值得。不过在说那个之前，我先快速讲一下 Speculation Rules API 的另一个部分：你希望它有多积极，这叫做 eagerness（积极程度）。

Scott：好名字。

Wes：取值有 immediate、eager、moderate 和 conservative。即使你告诉它"这些是我可能想预加载的链接"，基于这些积极程度设置，设备也得自己做决定。像用户的网络状况、手机的速度等等，这些都会影响浏览器是否决定去做，甚至还有电量。如果你的用户只剩 4% 的电，那大概就不适合浪费在这上面了。因为在某个时刻，浏览器需要根据它所知道的信息做出这些决定。

不过像 Next.js 早就有这个了，很多框架都早就有了：当链接进入视口时就预加载，或者当有人悬停在链接上但还没点击时预加载。但这可能会有点贵，取决于成本是多少。想象一下加载 Syntax 首页：一个 100K 左右、相当大的 HTML 页面，加载一次要花我们多少钱？如果你是从 CDN 加载的，而它已经是静态的——比如很多博客文章就是纯静态页面——那在那里加载几乎不花钱。但首先，如果你的主机是按带宽收费的，那费用可能很快就会变高，因为你付费的带宽可能变成十倍。另外，这对服务器有没有成本？

Scott：那预渲染呢？你觉得他们做得怎么样？感觉那应该也是其中一部分。像有些框架点击链接时只是替换页面上的 HTML，不是整个页面，只是网站中变化的那一部分。

Wes：还有 stale-while-revalidate 这种做法。如果你的服务器前面有 CDN，你可以在响应上加一些缓存头，这样服务器就不需要每次都重新生成页面。你可以说：好，缓存三分钟。有些页面可以这样做，因为它对所有人都一样；而有些页面不行，因为里面是用户数据。比如你的个人资料页，你不能把用户的个人资料缓存在全局 CDN 上。

Scott：这正好是把状态放进查询参数的一个好理由，对吧？

Wes：对。

Scott：你把状态放进 URL，那你能预渲染这些 URL 吗？至少可以缓存它们。

Wes：如果你事先知道这些 URL，就可以预渲染。但举个例子，在 Syntax 网站上我们有节目列表，你翻到第二页，或者筛选 Hasty Treat，这些都会体现在 URL 里。理论上我们可以算出有 100 页、80 种不同组合，但到某个程度你会发现，每页显示多少条、你想看哪类节目……这些组合可能有好几千种，不知不觉就失控了，为几个页面生成上千个 HTML 页面。不过你可以做的是，在渲染之后把它们缓存起来。这样第一个访问的人拿到的是新鲜生成的版本，然后你把它放进缓存。这并不是说它慢——Syntax 网站在没有缓存的情况下也不慢——而是每次都要用服务器时间重新生成那个页面，这很贵。所以你要做的就是把"Hasty Treat 第 32 页"的结果存进缓存，保存这个版本，下次直接提供。

Scott：是的。我觉得还需要考虑的一点是：用户加载这些东西的成本是多少。现在不限流量已经很普及了，这已经不算大问题。说起来，我们节目上请过谁来着，他聊到非洲的网络连接？

Wes：对对对。

Scott：然后所有评论都在说："兄弟，我就是非洲人，我们的网速更快。"

Wes：是啊，我信。

Scott：所以你得考虑：用户是不是在用有限流量的套餐？是不是在较慢的网络连接上？我觉得这就是设备本身会在推测规则中发挥作用的地方——决定该不该做。因为再说一次，如果你在某些网站上想着"有何不可，干脆全都加载了"，那 2G 流量很快就会被烧光。

Wes：有意思。说到 McMaster-Carr 网站这件事，Vercel 的人做了一个叫 Next Faster 的东西，用 Next.js 重写了 McMaster-Carr 的网站，非常酷。它显然不是一模一样的网站，有些不同之处。我给他们发消息说：把 Vercel 的账单贴出来吧。因为所有人都在说："是啊，但预加载所有这些东西得花一大笔钱。"然后他们真的贴出来了。他们有 4.5 万独立访客，大约 100 万次页面浏览，也就是每位访客 20 个页面。我不相信大家真的点了 20 个东西，我敢打赌这意味着每个页面上预加载了 20 个页面。4.5 万独立访客、100 万次页面浏览，他们的总账单是 513 美元。这算多吗？

Scott：这真的取决于你的产品。我会说这挺多的。4.5 万访客，我会说这挺多的。

Wes：如果看明细，超过一半是 Edge 请求：Vercel 的 Edge 请求费用是 220 美元。另外 160 美元是图片压缩，也就是图片优化，而这只需要做一次，因为他们实打实有 10 万张图片需要调整尺寸，所以那 160 美元其实只会发生一次。剩下的大概是增量静态再生（ISR）的读写费用。没有什么别的特别突出的。不过这是在 Vercel 上，Vercel 在这类事情上出了名的贵，但对很多人——包括我们自己——来说是值得的，因为自己托管可能有点麻烦。所以我打赌，如果你专门追求节省成本，可以做得便宜很多。

Scott：对，他们并不是冲着省钱去的。

Wes：他们是冲着"我们来做一个感觉一模一样的 Next.js 网站"去的。事实上它连加载转圈都没有，加载得甚至更快。

Scott：哥们，我这是第一次了解这个。我们讨论过它目前的普及程度吗？

Wes：它现在在 Chrome 里已经可用了，其他浏览器还没有，我们在等 Firefox 和 Safari。不过这类东西很容易做 polyfill，尤其是预取，因为你只要拿这些正则（规则）去匹配就行。我猜肯定有推测规则的 polyfill……等一下，确实有一个 polyfill。所以你可以这么做。至于 Next.js，我觉得他们甚至没用这个，因为 Next.js 有更细的控制：它们并不会获取整个页面，而是可以只获取需要变化的那个组件，在组件层面进行，这挺巧妙的。所以这种预渲染网站的整体思路，对于让网站感觉很快是非常好的一件事。

还有一点是，McMaster-Carr 的 PageSpeed Insights 分数糟透了。所有做性能的人都说："不，这太糟糕了。"而看看真实的普通用户反应就很好笑。我收到了很多非 Web 开发者的消息，说："我喜欢这个网站，因为它太快了。"他们才不管 PageSpeed 分数高不高，他们只知道点一下按钮，页面就以最快速度出现。

Scott：是的，我们之前在节目里也说过，页面速度分数并不是全部。但如果你在慢速或者中等偏慢的网络下使用这个网站，你能感觉到、能看到它实际用起来很快，那你就不需要完美的 Lighthouse 分数了。重要的只是用户体验，因为说到底这才是唯一重要的，而不是分数。

Wes：前几天有人在推特上截图羞辱我，说我的 wesbos.com 在移动端只有 76 分左右，桌面端 90、94 分。我就想说：给我看一个真实的网站，不是那种在一个 div 里放一串链接的个人博客，给我看一个有大量图片、PageSpeed Insights 分数还很高的网站。就像你说的，我们这个行业里谁的性能最顶尖？就拿 Vercel 来说吧，vercel.com，看看它得几分。
