主播：大家好，这里是 AsyncTalk，我是主播。AsyncTalk 是一档由前端开发工程师随便聊聊业界最近发展的节目。今天我想讲一条升职加薪的好路子，这是我到目前为止看到的一个比较明确、而且比较通用的方向，也想分享给大家，那就是前端性能优化。

我们都知道，前端性能优化是一道非常标准的面试题，有很多很多种方式。比如升级到 HTTP/2，因为它有多路复用；或者以前非常传统的雪碧图，在 HTTP/2 之前雪碧图是非常有用的；还有把 JS minify 掉，等等，方法非常非常多。包括最近比较多的，你需要做 prefetch、preload 这样的一些手段。这些手段都在尽力降低网络延迟，但整个 round trip 是没办法做到巨大优化的。

最近我觉得这条路已经非常清晰了：你需要把 client side 的应用挪到服务端。用户请求一个页面，你在服务器上执行非常重的逻辑以及网络操作，然后把结果拼装起来返回给用户。用户看到页面的时候，其实没有执行任何 JavaScript，也没有发起网络请求——除了图片——所以会非常非常快。前面讲的那些传统性能优化方法，在服务端渲染这条路面前就显得效果没那么好了。所以今天我主要想聊的是，你可以怎样改造自己的网站，做一些性能更好的方案，以此辅助你的升职加薪，对吧？

我之所以说这是一条比较确定的路子，是因为 React 19 已经完全接纳了 Server Component 这个理念，这是非常确定的事情，所以我认为这个方向已经比较稳定了。React Server Component 这个概念出来之后，Node 的重要性陡然提升。当然之前 SSR 出来之后 Node 也很重要了，但我认为有了 Server Component 之后，整个前端业务就和 Node 分不开了。

这里我有必要解释一下服务端渲染和 Server Component 的区别。我知道很多人会把它们放在一起，但它们其实是两个完完全全不一样的东西。

我们回到很久以前，比如 20 年前。那时候没有前端应用，都是后端渲染：服务器接到一个请求，拼好 HTML 页面，返回给客户端，是这样一个路径。最初的后端渲染又发展了很多年，也许十多年，一直在优化模板这件事，我认为优化得最好的是 Ruby on Rails，它让你在做后端应用时渲染前端页面方便了很多。但再怎么方便，之后还是从后端渲染拆分成了前端渲染。前端渲染就是你可以用 JavaScript 做路由、做非常重的交互，后端慢慢变成纯 API 式的服务，给前端提供各种 API 和数据。

再之后，因为性能问题，又切回了服务端渲染。但需要注意，这时由 Node 做这一层服务端渲染，和以前靠 PHP、Ruby、Java 做的后端渲染很像，却不是一个东西。靠 Ruby 或 Java 做的后端渲染，你没办法撑起比较大规模的应用，因为页面和交互非常受限于整个后端模板，没办法做很重的交互，规模大不起来。当然你也可以靠堆人力把它做大，但相应的 bug 率也会上涨。而有了前端渲染之后，后端就不太关心样式这一层了，前端拆出一个团队来专门负责，规模就有机会变得很大。

再之后，又到了 Node 层来做服务端渲染，这时其实有点不一样：之前的后端渲染是以后端为主导的，而 Node 这一层、像 React 或 Vue 的服务端渲染，是以前端为主导的，前端需要什么，就一层一层拼接什么。而最近出现的 React Server Component，又是另外一个完全不同的概念。

Node 层的 SSR，虽然是在服务端执行的，但你写这块 SSR 代码的时候，还是要用前端思维来写逻辑。你需要注意，组件内部的数据要从上层传进来，而不能在组件里面直接读，因为它其实没办法读，对吧？但 Server Component 这个概念出来之后，你可以以更前端的方式写组件，不需要关心"数据只能从上层读"，而是可以在组件里直接读。发起的请求会在 Server Component 里处理，要么先放一个骨架屏在那里，要么去拉数据。Server Component 让你可以用更前端的形式和思维方式来做这种优化。

我说了三个阶段，三个阶段差别其实都挺大的。我们再收回到客户端渲染和服务端渲染。大家都知道，客户端渲染至少要有两次 round trip：首先用户请求一个 HTML 文件，服务端返回 HTML；客户端拿到 HTML 后解析，再请求 JavaScript；JavaScript 返回后执行，执行之后再去拉远端的 API 请求；API 返回之后，再做渲染。是这样一个流程。

而服务端渲染只有一次：请求打过去，服务端根据内部配置去请求网络，把数据塞到一个类似 Redux 那样的全局状态管理里，再执行服务端的模板，生成 HTML 返回给用户。等于说重活都在服务端做，用户只是发了一个请求，等一会儿就能看到整个 HTML 吐出来，是这样一个流程。

Server Component 也只有一次请求，而且可以做得比 SSR 更快。因为 SSR 需要先解析你的 JS 组件，拿到对应的 API 请求去请求，然后拼接模板，再返回给用户。但 Server Component 可以不这样做：它可以在最开始就先返回 HTML 的第一部分，然后通过 streaming 的形式继续返回给客户端。这样你就是一点一点地看到页面，甚至等 HTML 返回完了也没关系，它还可以继续往里推送内容，再做一些更新。怎么说呢，这有点像很早以前 Facebook 做的 BigPipe。但当年要做 BigPipe 是一件非常困难的事情，放到现在就变得非常简单，你只要把 React 升一下级、稍微改一改，就能做到。

前面讲了这么多好处，那具体怎么做呢？方案应该有两种，还是要看自己的场景。我的感觉是，React Server Component 的难度是比较高的，如果你要自己实现，应该是一件不太容易的事情。所以对于小项目，我比较建议直接迁移到 Next.js。但有一点要注意 Next.js 的 bug，就我个人体感，它的 bug 数量真的非常非常多，有可能会影响你。不过对小项目来说，我觉得是可以迁的。

大项目的话，上不上 Server Component 就要非常看你自己的水平。这里我要说一点：放弃其实并不丢人。Server Component 实现起来确实有点麻烦，如果你是大项目，整个项目的依赖、对性能和机器的要求又会变得非常复杂。这时你可以考虑自己实现一个 SSR。Server render 相对来说就比较简单，因为它本质上只是从组件里拿各种预定义的 API 接口，进行组合，塞到全局变量里，然后再拼模板，本质上就是这样一个逻辑。所以大项目可以考虑接入 SSR，哪怕是自己做的比较粗糙版的 SSR。

既然已经到了 Node 这一层，就有必要再说一下 API server。API server 有两种思路。一种是比较传统的、像 Spring 那种大而全的东西：你要实现一个接口，需要先定义入口，配置各种 router，还要分 model、controller，就是标准的 MVC 结构，当然 MVC 中间还衍生出 MVVM 等各种其他模式，总之就是把层级做得比较细、拆得比较开，DB 那层可能还有各种层级。我个人把这种非常大的 MVC 类型统一叫作 Spring-like 模式。

以下纯属我个人看法，如果有不对的，听众可以在评论区或者给我发邮件说。我认为这种 Spring-like 的模式概念过于复杂，测试也很复杂，比如你要测一个接口，需要先 set up 各种它需要的依赖，对吧？另外，它前期的学习成本比较高，在写出一个 hello world 接口之前，你需要了解一整套概念，其中一个没理解，你都没办法很好地写代码。再有就是维护成本高，像我刚刚讲的，这种项目很容易写出非常非常多的代码，而代码量一大，bug 率就会高，这应该算是共识了。

另一种就是 Node.js 这种，我把它叫作 Node 方式。你要定义一个接口，其实只需要写一个回调函数，处理 HTTP incoming message，对数据进行处理，然后就结束了。我认为这种方式入门成本很低，你可以写得非常简单，代码就能完成一些操作。但像我刚刚讲的，你如果需要引入 DB、缓存、rate limit 等各种东西，它对程序员素质的要求就比较高，你需要自己懂这些东西。Spring 那种是帮你都做好了，而 Node 这种需要你自己来做。但我个人更偏向 Node 这种，因为它的功能限制少，我想做一件事的时候它没怎么限制我，这是我个人比较看重的。

这算是一个小插曲，介绍了两种不同的 HTTP server 设计思路。总而言之，不管怎样，各位在考虑对前端项目做优化的时候，都不可避免要考虑到 Node 这一层，因为 Node 对性能优化的影响力非常大。所以我比较推荐各位听众多学习 Node，这是我个人的建议。在我能看到的未来，Node 这一块应该是躲不掉的。如果你对 Node 还不是特别了解，我觉得是时候自己做一些小项目参与一下了。

对于我们这些写前端比较多的听众来说，我觉得有几个点可以作为突破口去了解。第一个是 HTTP 模型。我觉得你可以不用管什么 OSI 七层模型、TCP 握手这些，其实没什么太大必要，因为在工作生活中，除了面试你应该都不会碰到这样的问题。大家需要理解的就是 HTTP 模型：一个请求进来，处理，然后一个响应出去，到这里就可以了。但有一些比较老的语言，比如 PHP 或 Python，其实并不是这种模型：它是一段脚本，你写的整段代码就是一个 handler，前面再起一层 CGI，有点像各个语言版的 Nginx 那一层来处理请求。所以这种模型不是事件驱动的形式，这和我们写 Web 的人的思路差异非常大，不是所有东西都以事件为模型来做的，后端有些设计还是比较古老的。HTTP 模型了解到这里就可以，基于此会衍生出非常非常多的东西，大家后面可以自己去了解。

另一点是 streaming 的概念。对前端来说，我们处理问题的方式很多时候是发起一个事件，等这个事件结束，然后做一个什么改变，中间只有一个 loading 状态，对吧？但对后端来说，它不能等，因为它要做很多很多事情。所以对后端来说，一个比较重要的概念就是 streaming：比如 1 加 1 等于 2，可以拆成 10 个步骤来做，每个步骤我都可以一点一点地把结果推出来。我觉得这个例子不是特别恰当。我想到一个例子：你跟 AI 聊天的时候，它实际上是一个字一个字蹦出来的，你就可以边看边读，这就是非常标准的 streaming 概念。我觉得这个概念在后端，尤其是做性能优化或者看未来趋势，应该是跑不掉的。

还有一点，我个人觉得纯前端是有天花板的，你的职业发展、你的知识都比较局限。所以我们需要一些新概念来冲击我们旧有的知识体系，我觉得我们还是需要不断进步、不断学习，这是我认为非常重要的东西。而后端就是一个很好的途径，因为它和前端的区别非常大。
