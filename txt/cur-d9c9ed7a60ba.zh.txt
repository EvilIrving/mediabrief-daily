CJ：它们已经存在很久了，所以会出现一个新的 HTTP 方法，这件事本身就很有意思。它目前是一个提议标准（RFC 10008），而 Node.js 已经在服务端的 HTTP 模块里实现了它，所以如果你在实现服务器，就可以监听它。它叫 QUERY。所以在一长串方法里，你有 GET、PUT、POST、PATCH、DELETE，现在 QUERY 是新的一个。它的思路是：有时候你会把数据硬塞进查询字符串，因为你想让它是个 GET 请求。在介绍里的例子中，常见的查询模式就像一个搜索地址，后面跟着查询字符串和一堆查询参数，比如 q=…、limit=10、sort=-published。这基本上就是你构造一个带数据请求的方式：数据在 URL 里，服务器根据这些数据来处理。

这种请求，我想正确的术语是"幂等的"（idempotent），基本上就是不会在服务端修改任何东西的请求，只是请求数据，服务器返回点什么。我们经常这么做，原因是 GET 方法官方并不支持在请求体里放数据。所以通常如果你有更复杂的数据要发送，但请求仍然是幂等的，你就会用 POST 请求。我们在 GraphQL 里就能看到这种情况：它总是一个 POST 请求，带着一大坨你要请求或读取的所有内容。它们之所以用 POST，就是因为需要的不只是 URL 状态，还需要在请求体里放真正的数据。

所以 HTTP QUERY 就是来解决这个问题的。本质上它就是一个可以带请求体的 GET。你可以把查询参数以表单 URL 编码的形式放进请求体，也可以在请求体里放 JSON，Content-Type 想设成什么都行。但关键是它仍然被归类为幂等请求，不会修改服务器上的任何东西，只是在请求数据。我还有另一篇博客文章，里面有一些更具体的例子。在实践中，GraphQL 就是可以采用它的东西之一：不再是 POST 到 /api/graphql，而是发一个 QUERY，请求体里带着 GraphQL 查询。类似地，他们还展示了一个例子，不用表单 URL 编码的请求体，而是用 JSON 请求体：你向某个端点发一个 QUERY 请求，带上 JSON 版的查询字符串，这样更易读，因为里面可以有数组类型，而用查询字符串时，通常要把同一个参数重复写好几次。

这很令人兴奋。正如我说的，目前只有 Node.js 的 HTTP 模块支持它。但 RFC 的意思就是"征求意见"，浏览器的实现者和其他所有人都可以发表意见，决定这个东西是否应该存在、规范是否需要调整。最终它会遍及整个 Web，这需要时间。但最终，如果大家都接受了，你就可以用 QUERY 代替 POST 或 GET。
