怎样修好任何 bug

我最近在 vibecoding 一个小应用，几天前撞上了一个 bug。

bug 大致是这样。想象 web 应用里有一条路由，展示一串步骤——本质上是卡片。每张卡片有一个按钮，点击后滚到下一张。一切正常。可一旦我试着在那个按钮里也调用服务端，滚动就不工作了：会抖动、会坏掉。

所以，加上一次远程调用，不知怎么就弄坏了滚动。

我不确定原因。显然，新加的远程服务端调用（我通过 React Router 的 actions 做的）不知怎地干扰了我的 scrollIntoView 调用。但我说不清怎么干扰的。起初以为是 React Router 重新渲染了页面（action 会导致数据重新获取），但原则上没有理由说重新获取会干扰正在进行的滚动。服务器返回的是相同条目，不该改变任何东西。

在 React 里，重渲染应当始终是安全的。另有什么不对——要么在我的代码里，要么在 React Router、React，甚至浏览器本身。

我怎么修这个 bug？

能让 Claude 来修吗？

第 0 步：直接修它

我让 Claude 修这个问题。

Claude 试了几手。它改写了包含 scrollIntoView 的 useEffect 里的条件，并说 bug 修好了。但没有用。然后它试着把平滑滚动改成瞬间滚动，还有别的一些改动。

每一次，Claude 都得意地宣布问题解决了。

但并没有！

bug 还在。

这听起来像是在抱怨 Claude，但写这篇文章的真正动机是：我看到人类工程师（包括我自己）也犯同样的错。所以我想记录下我通常用来修 bug 的流程。

为什么 Claude 一错再错？

因为**它没有 repro**。

第 1 步：找到 repro

repro，或称复现用例，是一组说明：照着做，你就能可靠地判断 bug 是否还在。它就是"测试"。repro 说明做什么、期望发生什么、实际发生了什么。

在我看来，我已经有一个不错的 repro：1）点按钮；2）期望滚下去，实际却是滚动抖动。更好的是，bug 每次都发生。

若 repro 不可靠（比如只有 30% 的尝试会出现），我就得逐步去掉不确定性来源（例如录制网络并在后续尝试中 mock），或者忍受每次潜在修复都要测更多遍的效率损失。幸运的是，我的 repro 很可靠。

然而对 Claude 来说，我的 repro 基本上不存在。

问题在于，repro 里的"滚动抖动"对 Claude 毫无意义。Claude 没有眼睛或其他直接感知抖动的方式。所以它本质上是在没有 repro 的情况下操作——它试图修 bug，却没有做任何具体验证。即便是最优秀的我们也常常如此。

这种情况下 Claude 没法严格照我的 repro 做，因为它不能"看"屏幕（截几张图也抓不住抖动）。所以若想让 Claude 来修，我的第一个 repro 就不合适。这看似 Claude 的问题，但和别人协作时并不罕见——有时 bug 只在一台机器、一个用户或特定设置下出现。

幸运的是有个技巧：只要你能说服自己新 repro 仍有助于推进原问题，你就可以用一个 repro 换另一个。

下面是如何改 repro，以及要注意的事。

第 2 步：收窄 repro

改你正在用的 repro 总有风险：新 repro 可能和原 bug 无关，解决它是在浪费时间。但有时改 repro……（原文继续说明把"看抖动"换成程序可测的信号。）

他让 Claude 在点击前后测量滚动位置：若位置不变，就证明滚动没发生。Claude 终于能验证 bug 存在了。

常见陷阱是：你以为找到了好 repro，其实新 repro 抓到的是表现相似的无关问题。**这是代价非常昂贵的错误**，可能浪费数小时去修另一个问题。

例如，Claude 可能读滚动位置读得太早，即便 bug 已修好，它仍会"看见"位置不变——连正确修复也会被测成仍坏。人类工程师也会这样。

**因此，每当你收窄 repro，还应确认用新 repro 仍可能得到正向结果（"一切正常"）。**

他让 Claude 注释掉最初暴露 bug 的网络调用。若新 repro（测滚动、点按钮、再测滚动）真正捕获了原 bug，则他已验证能修好原 bug 的改动（注释掉 action）也应修好新 repro 中的行为。确实如此。值得来回改几次，确认每次编辑都能预测新 repro 的结果。

这仍不意味着新 repro 代表同一问题，始终有风险。但"网络调用与滚动位置有关"至少和原问题一样可疑，本身就值得解决——足够继续用新 repro。

第 3 步：删光其他一切

他建了新分支，让 Claude 按如下工作流：1）跑 repro 确认 bug 在；2）从相关代码里删掉一点（组件、事件处理、条件、样式、导入等）；3）再跑 repro；4）若 bug 还在，提交；5）若 bug 没了，写下可能"修好它"的理论，然后 **reset 到上次提交**，试着删更小一块。

他出门前让 Claude 一直做，直到收窄到无法再减：一个不依赖额外库（甚至不要 React Router）、逻辑最少的 React 组件。

回来时 Claude 交了几个复现案例，但令人沮丧的是没有一个表现出 bug。它写了一大段：测过纯 React 状态更新、Router 重新验证、组件重挂载等等，真实页面仍失败，最小化案例却都正常；setTimeout 推迟网络调用的变通有效，但说不清为什么。

这是否意味着收窄并不总管用？不。意味着 Claude 没按指示做。但它失败的方式很有意思，因为人（包括我）也常犯。

简化代码时它开始形成理论，并去测这些理论、做孤立的复现——看到它们不表现出 bug。创建并测试理论很好！但指示的要点是：**任何时刻都要有一个 bug 仍在发生的检查点，每一步都在缩小该 bug 的表面积。**

Claude 太沉溺于自测理论，最后得到一堆并不表现 bug 的测试用例。理论失败时，正确做法是回到仍表现 bug 的原案例，继续删东西直到找到原因。

这让他想起良基递归（well-founded recursion）。错误的 fib 实现写成 fib(n) + fib(n-1) 会永远递归；Lean 等理解良基递归的语言会报错，因为 n 没有"变小"。收窄 repro 也一样：你要始终、**始终**在做增量进展，repro 不断变小。必须有纪律地一块块删，只有 bug 仍在时才提交。最终要么暴露你代码里的错，要么暴露你无法再减的底层（如 React）里的错。

重复，直到找到它。

第 4 步：找到根因

Claude 最终没独立解决，但把它推到了很近。

在他要求真正只删东西之后，删到问题落在单个文件。他把该文件移出路由，同样代码突然正常；移回路由又坏；做成顶层路由又好。

是嵌在根布局里时坏掉的。根布局里有 React Router 的 ScrollRestoration。原来有一个（六月已修好的）bug：ScrollRestoration 会在每次 revalidation 时激活，而不只是路由变更时。他的网络调用（经 action）会重新验证路由，于是在 scrollIntoView 期间触发 ScrollRestoration，造成抖动。

**这种一边确保 bug 仍在、一边逐项删除的工作流，多次救过他。**（他曾花一周删掉半棵 Facebook 的 React 树追一个 bug，最终 repro 约 50 行。）理论用尽之后，他不知道还有什么方法如此有效。

若项目是他自己搭的，会用最新 React Router，遇不到这个 bug。但项目是 Claude 搭的，不知为何决定用旧版核心依赖。

啊好吧！

vibecoding 的乐趣。
