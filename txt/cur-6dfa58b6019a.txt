Ep 48. 专访高天：为了当好 B站 up主，我成为了 Python 核心开发者 ｜ 捕蛇者说 ｜ 97分钟 ｜ https://pythonhunter.org/episodes/ep48

这期捕蛇者说由 Adam 主持，laike9m 和中途加入的信涛一起，专访第二次上节目的高天。他是 VizTracer 的作者、B 站技术 up 主，也是新晋 CPython 核心开发者，本职在微软做 Windows 操作系统安全。节目从他这四年的变化聊起，依次谈到如何成为核心开发者、Python 近来的大变化、性能优化观、技术内容创作，以及工作与兴趣的关系。

高天说，这四年的起点是自己的时间变多了：疫情期间少出门，后来搬到南湾转为纯远程工作。知乎只能回答别人的问题，他想自己决定聊什么，于是去 B 站做视频，主要讲进阶 Python。对于“哪来这么多时间”，他的回答是：本职工作不能太忙；游戏少打了；写 CPython、做视频本来就是他放松、换脑子的方式，每周几个小时，坚持久了总会有成果。

他的 CPython 之路始于粉丝群里有人报的一个 pdb bug：修改局部变量后执行 ll，值又变回原样。他确认这是 CPython 自身的问题并提了 PR，干等了好几周、四处 @ 人才被合并。第二次是追查 VizTracer 在 CI 上偶发的失败，花了一周找到 CPython 的一个竞态 bug，只改一行，Mark Shannon 很快就合了。这两次让他觉得给这种级别的项目做贡献并不难。之后他走两条路：一是刷新提的 issue，抢先复现、修复；二是盯住多年没人维护的纯 Python 模块 pdb，在 3.12 周期里集中清理了一批十年以上的老 bug。Irit Katriel 和 Brandt Bucher 经常帮他 review，他认为对新人来说，最难的就是找到人 review。大约 20 个 PR 之后，同在微软 Faster CPython 团队的 Brandt Bucher 邀请他当 triager，又过了一年左右，他成了核心开发者。

讲到动力，他强调这是纯志愿工作，没有回报，也没有 deadline，必须享受过程，不能只盯着结果。他的动力来自三方面：给大项目做贡献的成就感，本身就爱写代码，以及“Python 核心开发者”能让他在 up 主里独一份。和职业发展则几乎毫无关系。laike9m 打趣说这是一部轻小说《关于我为了在 B 站脱颖而出而成为 Python 核心开发者这件事》。他坦言，这个头衔在 B 站引起的波澜没有想象中大，但有长尾效应。真正的收获是参加 PyCon US 和 Language Summit 带来的社区归属感、对 Python 理解的提升，以及写的代码切实帮到了人。他还提到联系方式：短问题可以周六中午到他的 B 站直播间问，长问题去知识星球问。他也认为，提第一个 PR 只需要时间、精力和热情，用不着他指点；等到想进入社区、往 triager 或核心开发者方向走的时候，过来人的建议才更有价值。

给想入门的人，他建议从 issue 列表开始：帮人答疑、复现、修 bug，都会被常驻的少数志愿者看见。新人要做好 PR 不被合并的准备，优先修“绝对正确”的明确 bug，比如行为与文档不符、漏减引用计数；不要一上来就做性能优化、重构或大功能，因为这些往往有人提过，不做是有原因的。不熟 C 的话就避开 C 模块和编译器，改动要局部、隔离。他还澄清，就项目而言只有三种角色：只多一项合并权限的核心开发者、做分类和 review 的 triager，以及其他所有人。近年来几乎每位核心开发者都先当过 triager，triager 只是通往核心开发者路上的路标，不是弯路；核心开发者这个头衔则是社区对你已经在做的工作的“最后一枚勋章”。项目之外还有 Steering Council 和 PSF。laike9m 附和说，把成为核心开发者当目标本身既不现实也不讨好。

谈到 Python 的发展，高天先感谢微软出钱养了一支团队，再感谢“天降猛男”Sam Gross 的 PEP 703，让很多大改动同时推进。他解释，SC 对去掉 GIL 的态度是“先试”：free-threading 必须能一键撤回；如果对单线程性能和 C 扩展的影响可以接受，就转向无 GIL，否则退回。3.13 已经有实验性的 3.13t。JIT 迟迟没做，主要是志愿者团队有可维护性顾虑，现在采用 Brandt Bucher 的 copy-and-patch 方案，也在 3.13 开放了实验。另外还有子解释器，以及替代 settrace、setprofile 的 sys.monitoring。他列举了 Eric Snow、Mark Shannon 等微软员工的贡献。laike9m 则批评 Google 裁掉了整个 Python 团队，包括 Gregory P. Smith 和 pytype 的成员。对于微软的动机，高天算了一笔账：十来个人的成本对微软微不足道，技术上的直接收益未必大，名声上的收益却很明显。名声对社区来说没有成本，做得好就该夸，就像 VS Code 和 TypeScript 开源改变了开源社区对微软的看法。

他最想分享的实践建议是：大多数工程师大多数时候不该操心性能。“这样写更快”太容易成立，关键要问快多少：局部快多少，对整个项目又快多少。一个只占路径 0.2% 的函数，快一倍也毫无意义，代价却可能是可读性、稳定性或最坏情况下的性能变差。信涛补充了两个例子：编译器提示类的关键字应在定位瓶颈后再加；同事把报表程序优化到 10 分钟后难以扩展，最后改回原样，把启动时间提前两小时就解决了问题。laike9m 引用了 Joe Armstrong 的“先让它能跑，再让它漂亮，真有必要才让它快”。Adam 指出工程中的 N 是确定的，大 O 只能作参考；信涛举了 Redis 在小数据量时用列表代替哈希的例子。laike9m 又补充说，像生成器、N+1 查询这类已知的反模式应该避免，而把全局变量绑定到局部变量这类微观技巧完全不必在意。

在内容创作上，高天先决定做视频，再选内容，最终专攻市面稀缺的进阶 Python，比如 code object、frame、描述符、装饰器的原理，一度日更。后来他发现，纯技术内容涨粉有限，涨粉最多的是由他自己带起、又与技术挂钩的热点；而中阶知识讲得差不多了，就转向 code review 和周更。他认为选题应该与观众兴趣取交集，但观点和价值观不能迎合观众，可以挑观众爱看的苹果来吃，但不能把甜的说成酸的。他暂不做英文内容，因为对英文观众没有执念，母语表达更自如。他还提到，中文进阶技术视频存在真空，很多作者不剪辑、信噪比低。他录技术视频时想好一句说一句，只需要剪空白，借助剪映的自动去空白功能，一期大约两小时就能做完。他开知识星球，一是用门槛筛选提问，二是用付费读者的期待督促自己写比视频更快的文章，内容以他给 CPython 写代码的心得为主。他认为订阅者一半为学习、一半为支持。他不做播客，因为视频多一个画面维度；直播则是作为一个真实的人和粉丝闲聊互动，而不是输出内容。视频里的小错就留着，在下一期更正。

他介绍了自己在微软的工作，是 Win32 App Isolation：给 Win32 应用打包后附上一个低权限 token，让它跑在类似轻量容器的隔离环境里，被攻破时也不至于危及系统。这份工作和 Python 毫无关系。在工作与兴趣上，他主张不要让兴趣变成工作，因为工作里总有逃不开的恶心事，会把兴趣磨掉；而兴趣可以随时停，不理语气差的 issue，累了就歇两三周，所以能维持得长久。他拒绝过微软 VS Code Python 调试器团队的邀请，也拒绝过 Mark Shannon 提的 Faster CPython 转岗机会，理由除了这一点，还有职业上的稳定性考量：那个团队“四年五倍”的目标恐怕实现不了。laike9m 表示，换作他一定会去体验。关于时间管理，高天说自己从不设时间表，不追求 GitHub 每天都绿，累了就停更几个月，因为把事情当作可以放弃的，反而不容易放弃。Adam 说捕蛇者说唯一的原则就是不断更；信涛谈到给自己定系列文章周更后反而有了压力；laike9m 说不规律但一直在做也是一种 consistency。关于很多硅谷程序员下班从不写代码，大家都认为这也是正当的选择。为了求职去做开源性价比极低，真正的开源贡献也很难伪造。

推荐环节，高天推荐了 profiler 工具 py-spy 和 Scalene，以及基于 sys.monitoring、开销远低于 coverage.py 的覆盖率工具 SlipCover；顺带聊到 Astral 用 Rust 写工具，招揽了 Carl Meyer 等核心开发者。信涛推荐 B 站 up 主“历史调研室”，Adam 推荐了标准库 contextvars（PEP 567），用来在可观测性、i18n 等场景下像 Go 的 context 一样隐式传递上下文。
