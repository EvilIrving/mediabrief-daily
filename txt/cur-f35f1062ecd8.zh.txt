# 构建数据分析智能体时学到的上下文设计

作者：logan.wvl（Kakao Tech，2026 年 10 月 2 日）

LLM 智能体接到目标后，会寻找所需信息、选择合适的工具执行，观察结果后再决定下一步行动。Anthropic 公开了多个利用智能体的实验，介绍了用 Claude Sonnet 4.5 复现 Claude.ai 的实验，以及基于 Claude Opus 4.6 的智能体用 Rust 开发出能够构建 Linux 6.9 内核的 C 编译器的案例。随着模型性能提升，智能体能够自主完成的工作范围也在扩大。要完成这类工作，智能体必须能够掌握当前目标、进展情况以及之前工作的结果。

那么，应该在什么时候向智能体传递什么信息呢？筛选并组织 LLM 执行任务所需输入信息的过程，被称为上下文工程（Context Engineering）。本文讨论的数据分析智能体会针对用户的业务问题寻找合适的数据，编写并执行 SQL，然后解释结果。下面基于开发数据分析智能体的经验，看看我们是如何设计上下文，让智能体在每个阶段获得所需信息并决定下一步行动的。

# 上下文

上下文（context）通常被译作"文脉"或"语境"，但在 LLM 智能体中，它指的是模型在决定下一步行动或生成回答时接收的输入信息。其中包括智能体的角色和行为准则、可用工具的说明、与用户的对话以及工具执行结果等。本文围绕系统提示词、工具规格说明和消息数组这三个要素来考察上下文。

[图：上下文的三个组成要素]

## 系统提示词

系统提示词中写的是智能体在整个工作中应遵循的通用规则和基本背景知识。主要包含以下几项：

* **角色定义**：写明智能体承担什么角色、执行什么业务、应提供什么结果。
* **安全规则**：说明智能体使用工具和撰写回答时应遵守的限制及应对方式。
* **判断标准与默认值**：说明当仅凭用户请求无法获得足够信息时适用的默认值，以及需要额外确认的条件。
* **工具使用指南**：写明多个工具共同适用的使用原则、工具之间的优先级，以及必须遵守的流程。单个工具的作用、调用条件和输入值的含义写在工具规格说明中。
* **回答指南**：说明智能体向用户传达工作进展和结果时应遵守的共同原则。进度说明简短交代在做什么、为什么做；最终回答则只写到理解结果所需的程度。各个工具的结果以什么形式、在什么范围内说明，写在工具规格说明中。
* **预备知识**：提供理解用户请求、开始工作所需的领域背景。如果同时提供各服务的表清单，智能体就可以把它作为判断要探索哪些数据的出发点。

下面是体现上述各项的系统提示词示例。

```
<role>
- 당신은 데이터 분석가입니다. 사용자의 비즈니스 질문을 이해하고, 필요한 데이터를 탐색, 조회, 분석한 뒤 결과를 사용자가 이해하기 쉽게 설명하세요.
</role>

<defaults_and_decision_rules>
- 사용자가 사용자 수를 요청하면서 집계 기준을 지정하지 않으면 일별 활성 사용자 수(DAU)를 기본으로 사용하세요.
- 사용자 요청이 기존에 합의된 지표 정의나 집계 규칙과 충돌하면 어떤 기준을 따를지 사용자에게 확인하세요.
</defaults_and_decision_rules>

<tool_usage>
- 이미 확보한 정보만으로 답할 수 있으면 추가 도구 호출 없이 답하세요.
- 새로운 계산이나 추가 근거가 필요하면 적합한 도구를 호출하세요. 확인하지 않은 수치를 추정해 답하지 마세요.
</tool_usage>

<response_guidelines>
- 도구 호출 시 무엇을 왜 하는지 1~2문장으로 안내하세요.
- 최종 답변은 결과 전달에 필요한 만큼 작성하고, 이전 답변이나 동일한 정보를 반복하지 마세요.
- 도구 실행 후 답변의 형식과 범위는 해당 도구 명세서의 '결과 표시' 항목을 따르세요.
- 도구 결과를 설명한 뒤 추가 작업이 필요하면 같은 응답에서 다음 도구를 호출하세요. 명세서에서 답변 생략을 명시한 경우에는 설명을 생략하세요.
</response_guidelines>

<safety_rules>
- 사용자 식별자가 결과에 그대로 노출되는 SQL은 실행하지 마세요.
- 이러한 요청에는 사용자 수나 분포 같은 집계, 통계 분석을 대안으로 제시하세요.
</safety_rules>

<domain_knowledge>
- 서비스 이름: {서비스 이름}
- 서비스 설명: {서비스의 주요 기능과 목적}
- 용어와 약칭: {같은 데이터를 가리키는 용어와 약칭}
- 서비스별 테이블 목록: {서비스별 테이블 이름과 설명}
</domain_knowledge>
```

（中文对照：
<role>
- 你是一名数据分析师。理解用户的业务问题，探索、查询、分析所需数据，然后用用户容易理解的方式解释结果。
</role>

<defaults_and_decision_rules>
- 如果用户要求用户数但未指定统计口径，默认使用日活跃用户数（DAU）。
- 如果用户请求与既有约定的指标定义或统计规则冲突，向用户确认应遵循哪个标准。
</defaults_and_decision_rules>

<tool_usage>
- 如果仅凭已掌握的信息就能回答，则无需额外调用工具直接回答。
- 如果需要新的计算或额外依据，调用合适的工具。不要估测未经核实的数值来作答。
</tool_usage>

- 最终回答只写到传达结果所需的程度，不要重复之前的回答或相同的信息。
- 工具执行后回答的形式和范围，遵循该工具规格说明中的"结果显示"一项。
- 解释完工具结果后如果还需要进一步操作，在同一个回复中调用下一个工具。规格说明中明确要求省略回答的，则省略解释。
</response_guidelines>

<safety_rules>
- 不要执行会让用户标识符原样暴露在结果中的 SQL。
- 对于此类请求，提出用户数或分布之类的汇总统计分析作为替代方案。
</safety_rules>

<domain_knowledge>
- 服务名称：{服务名称}
- 服务说明：{服务的主要功能和目的}
- 术语与简称：{指代同一数据的术语和简称}
- 各服务表清单：{各服务的表名和说明}
</domain_knowledge>）

在我们最初开发智能体的 GPT-4 时期，模型自行判断适合当前情况的工具和工作顺序的能力比现在弱。当时，工具规格说明里只简单写每个工具做什么，详细的使用条件和流程都集中放在系统提示词里。我们设立了"Workflow"一项，在其中明确写出查找与请求相关的表、生成并执行 SQL 的顺序，并加入了"如果是已知的数据就跳过搜索"、"只需部分修改既有 SQL 的请求使用修改工具"之类针对具体情况的指令。后来随着模型性能提升，我们改变了结构，让模型根据用户请求和当前情况自行判断所需的工具和工作顺序。

为此，我们把每个工具的使用条件写进了该工具的规格说明。Anthropic 也在其工具定义指南中强调"提供极其详细的描述（Provide extremely detailed descriptions）"，建议具体说明工具做什么、应当或不应当在什么情况下使用、每个参数的含义和约束。在这个智能体中，我们也把各工具的使用条件、输入值的含义和结果传达方式写进工具规格说明，而在系统提示词中只保留角色、安全规则以及多个工具共同适用的使用原则。

## 工具规格说明

工具规格说明是描述智能体可用工具的作用和使用条件的文档。智能体根据这份说明判断现在需要哪个工具、应输入什么值、能从执行结果中期待什么。在下面的 Claude Code 案例中，工具规格说明的篇幅约为 15k token，约为系统提示词（3.7k token）的 4 倍。这表明要让智能体良好运作，必须写好充分的工具说明。

[图：Claude Code 中系统提示词与工具规格说明的 token 占比]

编写工具规格说明时，应具体说明工具的作用、调用条件、输入值的含义与选择标准，以及结果的传达方式。以图表生成工具为例。该工具基于既有分析工作的执行结果生成图表，智能体把图表类型和想通过图表确认的内容作为输入值传入。

* 工具作用：说明工具针对什么对象做什么事。图表生成工具的规格说明中写的是"基于执行结果生成 Vega-Lite Spec"。
* 调用条件：说明什么时候应该使用该工具。这个工具的规格说明中有"仅在用户明确要求生成图表时调用"和"必须有之前执行的 SQL 的结果"这两个条件。
* 结果显示：写明工具执行后要向用户说明什么。在这个智能体中，生成的图表会显示在屏幕上，因此我们让回答中不要把图表数据转写成文字，而是用一两句话补充从分析中得到的洞见。

输入值的含义和选择标准写在 `parameters` 中。例如 `chart_type` 指定要生成的图表类型，并用 `enum` 限制可选值。说明中同时提供符合分析目的的选择标准，比如"时间序列趋势用 `line`，类别比较用 `bar`"。

工具无法直接看到的上下文也必须作为输入值传入。这个智能体的图表生成工具会在内部调用另一个 LLM 来生成 Vega-Lite Spec。这个 LLM 看不到与用户的对话，因此我们让主智能体在 `instruction` 中写明想通过图表确认的内容和需要强调的部分。例如传入"展示 9 月每日 DAU 趋势和周末下滑"，生成器就会参考它来确定坐标轴标题和排序方式等，并让图表突出问题和重点。

下面是图表生成工具的规格说明示例。

```
{
  "name": "generate_chart",
  "description": "실행 결과를 기반으로 Vega-Lite Spec을 생성한다.\n\n## 호출 조건\n- 사용자가 명시적으로 차트 생성을 요청한 경우에만 호출한다.\n- 앞서 실행한 SQL의 결과가 있어야 한다.\n\n## 입력 원칙\n- 차트 생성기는 대화를 보지 못하므로, 차트로 확인하려는 내용과 강조할 부분을 instruction으로 전달한다.\n\n## 결과 표시\n- 차트는 화면에 표시된다. 차트 데이터를 글로 옮기지 않고 분석에서 얻은 인사이트를 한두 문장으로 덧붙인다.",
  "parameters": {
    "type": "object",
    "properties": {
      "chart_type": {
        "type": "string",
        "enum": [
          "bar",
          "line",
          "area",
          "point",
          "pie",
          "donut",
          "heatmap"
        ],
        "description": "차트 타입. 시계열 추세는 line, 시간에 따른 누적량이나 구성 변화는 area, 카테고리 비교는 bar, 구성비는 pie/donut, 두 변수 관계는 point, 2차원 분포는 heatmap을 사용한다."
      },
      "instruction": {
        "type": "string",
        "description": "이 차트로 확인하려는 내용과 강조할 부분을 한두 문장으로 설명합니다 (예: '9월 일별 DAU 추세와 주말 하락을 보여줘'). 생성기는 이 설명을 참고해 축 제목과 정렬 방식 등을 정하고, 질문과 강조점이 드러나도록 차트를 구성합니다."
      }
    },
    "required": [
      "chart_type",
      "instruction"
    ]
  }
}
```

（其中中文含义：description 为"基于执行结果生成 Vega-Lite Spec。## 调用条件 - 仅在用户明确要求生成图表时调用。- 必须有之前执行的 SQL 的结果。## 输入原则 - 图表生成器看不到对话，因此把想通过图表确认的内容和需要强调的部分通过 instruction 传入。## 结果显示 - 图表显示在屏幕上。不要把图表数据转写成文字，用一两句话补充从分析中得到的洞见。"；chart_type 的说明为"图表类型。时间序列趋势用 line，随时间的累计量或构成变化用 area，类别比较用 bar，构成比用 pie/donut，两个变量的关系用 point，二维分布用 heatmap。"；instruction 的说明为"用一两句话说明想通过这张图表确认的内容和需要强调的部分（例：'展示 9 月每日 DAU 趋势和周末下滑'）。生成器参考这段说明来确定坐标轴标题和排序方式等，并让图表突出问题和重点。"）

像上面的图表生成工具那样，每个功能都单独添加一个工具，工具数量就会越来越多。即使处理的是同一个对象，如果把创建、修改、查询功能各做成一个工具，再把工作的细分步骤也拆开提供，智能体要读的规格说明就会增多，选择工具时需要考虑的候选也会增多。相关工具共用的说明和输入规则也会重复出现。这种情况下，可以考虑能否把相关功能合并成一个工具。《A Philosophy of Software Design》（软件设计的哲学）中讲到了用简单接口提供丰富功能的"深模块"：调用方只需少量信息就能使用模块，复杂的内部处理由模块负责。智能体工具同样可以把相关功能合为一体，在内部处理细分工作。这样能减少工具说明的重复，也不必分别选择和调用多个步骤的工具。

例如，这个智能体有一个便利功能，可以把常用的 SQL 保存为笔记以便复用。笔记保存工具同时处理创建和修改：如果指定了目标笔记，就修改其现有内容；如果没有指定，就新建保存。

```
{
  "name": "upsert_note",
  "description": "SQL을 포함한 노트를 새로 저장하거나 기존 노트를 수정한다. 사용자가 저장 또는 수정을 명시적으로 요청했을 때 사용한다.",
  "parameters": {
    "type": "object",
    "properties": {
      "note_key": {
        "type": ["string", "null"],
        "description": "수정할 기존 노트의 key. 새 노트를 생성할 때는 null을 전달한다."
      },
      "body": {
        "type": "string",
        "description": "저장할 노트 본문. 기존 노트를 수정할 때는 수정이 반영된 전체 본문을 전달한다."
      }
    },
    "required": ["note_key", "body"]
  }
}
```

（其中中文含义：description 为"新建保存包含 SQL 的笔记，或修改已有笔记。在用户明确要求保存或修改时使用。"；note_key 为"要修改的已有笔记的 key。新建笔记时传入 null。"；body 为"要保存的笔记正文。修改已有笔记时，传入反映修改后的完整正文。"）

智能体调用同一个工具，通过 `note_key` 的值区分创建和修改。

由多个步骤构成的工作，也可以由一个工具来承担。在数据分析中，需要编写并执行 SQL，出错时再修改、重新执行。可以把这个过程合并成一个工具，而这个工具就成了专门负责 SQL 生成和执行的子智能体。主智能体传入分析目的和所需信息后，子智能体负责从编写 SQL 到执行和修正错误的全部处理。更多说明将在"子智能体"一节中讨论。

## 消息数组

消息数组是一个按顺序存放用户与 LLM 之间的对话、工具调用及其执行结果的列表。智能体以这份记录为输入，掌握用户的请求和迄今为止确认过的内容，并决定下一步行动。

以处理一个分析请求的过程为例。用户请求"统计过去一周服务 A 的每日用户数"，此时已经确认了要使用的表的结构（schema），但还没有确认实际的值。下面是一个简化示例：以包含结构查询结果在内的消息数组为输入，LLM 输出下一个工具调用。

[图：消息数组输入与 LLM 输出下一个工具调用的示例]

输入中按顺序包含了用户的请求、随之进行的结构查询调用及其执行结果。LLM 能从查询结果中确认存在 **service** 列，但由于样本值只包含部分取值，它还不知道服务 A 对应的实际值。因此，它输出的下一步行动是一个确认服务过滤值的工具调用。这个工具的执行结果也会被追加到消息数组中，作为下一次 LLM 调用的输入。即使是在处理单个用户请求期间，这个过程也会重复多次。这份记录还会在处理用户的后续请求时派上用场。一次分析结束后，如果收到"把时间范围延长到一个月"的请求，智能体会参考对话和执行记录，判断应该修改哪一项分析的时间范围。

# 上下文工程

智能体执行任务期间，所需的信息在不断变化。寻找符合请求的表时，需要服务说明和表清单；编写 SQL 时，需要所选表的详细结构和分析规则。SQL 执行过程中出现的错误和修改记录可用于解决问题，但在之后的分析中并非全都需要。本节介绍两种方法：用渐进式发现分阶段获取所需信息，以及用子智能体在独立的上下文中管理中间记录。

## 渐进式发现

Anthropic 在《Effective context engineering for AI agents》（面向 AI 智能体的有效上下文工程）中，把智能体自行探索数据、逐步发现相关上下文的方式称为"渐进式发现（progressive disclosure）"。智能体根据探索中获得的信息决定下一步要查看的对象。通过反复这一过程，把工作所需的信息加入上下文。

以 Claude Code 在项目中查找登录相关代码的过程为例。

1. 文件名搜索：搜索文件名或路径中是否包含 `login, auth, session` 之类的词，找到 `src/auth.ts, src/session.ts` 这样的候选。
2. 代码内容搜索：搜索与登录相关的关键词或函数名。在这个过程中，可能会在仅凭文件名难以判断相关性的 `src/routes.ts` 中，发现调用 `signIn` 函数的地方。
3. 阅读相关代码：阅读发现的调用位置以及函数的实现代码。例如，确认用 `authenticate` 进行认证、用 `createSession` 创建会话的流程。
4. 追踪定义与使用处：搜索上一步发现的 `createSession` 的定义和使用处。阅读 `src/session.ts` 中的实现和 `src/auth.ts` 中的调用部分，弄清其行为。

不是一开始就把要读的文件和要搜的函数全部定好，而是根据探索中发现的路径和函数名，决定接下来要读的文件或要搜的函数。

技能（Skills）也利用了同样的原理。智能体先查看技能的名称和说明，挑出当前工作需要的技能，再阅读所选技能的详细指令。如果指令中链接了额外的参考资料，就再按工作需要阅读这些资料。

在数据分析智能体中，我们把这一原理应用到了寻找分析所用的表和列的过程中。起初，由一个单独的探索智能体搜索相关服务和表，并获取详细结构。但由于主智能体不知道自己能访问哪些表，有时即便需要的表根本不存在，它也要反复探索之后才判断出无法分析。为了改进这一点，我们把服务说明和智能体可访问的全部表清单按服务整理好，写进了系统提示词。主智能体从这份清单中挑选候选表，再用结构查询工具获取所选表的列名、类型、样本值和分析规则。

[图：基于表清单与结构查询的表探索流程]

这样改动之后，我们能更早发现所需的表不在清单中的情况，寻找表所需的轮次也减少了。各服务的表清单就像技能的名称和说明一样，起到索引的作用，告诉智能体有哪些信息、在哪里可以进一步查找。智能体先用表名和简短说明缩小候选范围，再查询所需表的详细结构。也就是说，不是把所有信息都写进系统提示词，而是写一份索引，让智能体能够动态查找所需的信息。

## 子智能体

子智能体是从主智能体接收任务、在独立上下文中执行的智能体。Claude Code 有用于代码探索的 `Explore`、用于为制定计划做代码调查的 `Plan`，以及执行探索、修改代码等多步骤工作的通用子智能体 `general-purpose`。像这样，可以针对任务单独配置指令和工具。而且，子智能体工作产生的中间记录留在独立的上下文中，因此只需把必要的结果传给主智能体。

起初，由主智能体编写并执行 SQL，出错时还要负责修改和重新执行。在这个过程中，失败的 SQL 和错误信息不断堆积在消息数组里，即便问题解决之后，这些记录也会被包含进下一次分析的输入。为了改进这一点，我们设置了一个专门负责编写、执行 SQL 和修正错误的子智能体，让中间记录在独立的上下文中管理。

[图：主智能体与 SQL 子智能体的分工]

主智能体把负责 SQL 工作的子智能体当作工具来调用，同时传入分析目的、要使用的表、查询时间范围、过滤条件和统计口径。此时，所选表的结构和分析规则也会一并提供到子智能体的上下文中。由于主智能体的对话记录不会被原样传过去，之前确认过的条件也必须在工作指令中写明。子智能体处理完 SQL 的编写、执行和错误修正后，把最终 SQL、执行状态、结果或失败原因返回给主智能体。

前面在表探索中，我们不再设置单独的探索智能体，而是改为由主智能体直接查询结构。两种情况的区别在于：工作中获得的信息之后是否还会用到。表清单和结构在指示 SQL 工作和解读结果时始终需要，所以放在主智能体的上下文中。而失败的 SQL 和错误信息在问题解决后几乎不会再被参考，所以放在子智能体的上下文中处理，只把最终结果传给主智能体。

# 结语

本文介绍了我们在开发数据分析智能体时组织上下文的方法。系统提示词中写角色和通用规则，各工具的使用条件和输入值说明写在工具规格说明中。

在表探索中，我们预先提供各服务的表清单，再让智能体查询所需表的详细结构。改动之后，能更早发现所需表不存在的情况，探索所需的轮次也减少了。SQL 的编写和执行则拆分给子智能体，避免失败的 SQL 和错误信息不断堆积在主智能体的消息数组中。

开发智能体时，希望大家检查一下：每项工作需要什么信息，以及工作中获得的信息之后是否还会用到。
