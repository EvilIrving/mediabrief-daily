论合规与可读性：用 CSS 生成文字颜色 On compliance vs readability: Generating text colors with CSS ｜ Lea Verou ｜ 文章 ｜ https://lea.verou.me/blog/2024/contrast-color/

Lea Verou 是 CSS 工作组成员、相对颜色语法（RCS）的设计者。这篇 2024 年 5 月的技术文章要回答一个问题：在 `contrast-color()` 真正落地之前，能不能用已经发布的 CSS 特性自动给任意背景配出可读的黑或白文字，以及"可读"和"合规"之间该怎么取舍。

她先介绍 RCS：允许在任意颜色空间里对颜色分量做数学运算来派生新颜色。写作时除 Firefox 外都已支持（5 天后 Firefox 128 也上线），覆盖约 83% 用户，她认为配合 `@supports` 回退已经可以用于生产。需求来自颜色不归作者控制的场景：用户自选颜色（如 GitHub 标签，它自动选的文字色常常很差）、Web 组件的使用者传入的变量、Open Props / Material Design / Tailwind 这类外部设计系统。`contrast-color()`（原名 `color-contrast()`）正是为此设计，她推动把它缩减成可以较快发布的 MVP 并写入规范，但从规范到全浏览器支持乐观也要两年左右（级联层从 2019 年 10 月提案到 2022 年 3 月全面发布是最快的先例），所以需要过渡方案。

核心技巧是在 OKLCh 空间里设一个亮度阈值：用 `clamp(0, (l / 阈值 - 1) * -infinity, 1)` 把亮度变成 0 或 1，低于阈值得到白字、高于阈值得到黑字；思路是用比值减 1 的正负号，再乘以负无穷放大后截断。不支持 RCS 的浏览器则回退到半透明底色、`-webkit-text-stroke` 或多重 `text-shadow`。

文章分量最重的部分是验证这个阈值是否存在、该取多少。她指出 WCAG 2.1 对比度算法虽被许多国家写进法律，却早已被认为结果很差，中间亮度的颜色上几乎和随机猜测一样；更新的 APCA 准确得多，但还不是标准。因此她建议两步：用 APCA 保证真实可读，同时确保不违反 WCAG 作为合规兜底。她用 Color.js 遍历 OKLCh 范围，统计各亮度区间里黑白文字在两种算法下的表现，并强调只能反向推理：所有白字不达标的情况 L 都在 62.4% 以上，所以 L 低于这个值时白字一定合规。结论是 WCAG 在白字上大量误判，阈值偏低。若必须合规，阈值最高取 62.3%；只看可读性则取 68.7%–71.6% 之间，如 70%。颜色范围更窄时还能放宽，例如只考虑 sRGB 可显示的颜色时为 65%，P3 为 64.5%，中性色和粉紫色为 67%。最后给出一个带回退、并在支持时直接改用 `contrast-color()` 的完整工具类。

她提到的后续方向包括：在亮度 Y（XYZ 空间）上计算，这是 APCA 作者 Andrew Somers 建议的；以及如何生成接近背景色的深色调，而不只是纯黑。附录补充了三点。第一，用 Y > 0.36 作为阈值的方法，经 Lloyd Kupchanko 的演示对比，与 APCA 的吻合度比 L 阈值更高，所以只需黑白切换时推荐 Y 方法，需要自定义深色时用 L 方法。第二，她发现 `from` 里放 `color-mix()` 颜色会导致 RCS 失效的浏览器 bug（Chrome 125、Safari TP 194 已修复），最好的规避办法是用 `@property` 注册颜色变量，几乎不影响兼容性。第三，列出了社区分享的相关资源。整篇的态度很务实：现在就能用，同时直白地指出现行无障碍标准本身有缺陷。
