Scott：欢迎收听 Syntax，这里是周一的 Hasty Treat（短节目）。今天我们要聊为打造快速网站而生的新 Speculation Rules API（推测规则 API）。Wes，我对这个了解不多，不过照你这段小介绍，它是关于预加载、预取和预渲染的，所以我洗耳恭听，很期待学点东西。我是 Scott Tolinski，一名开发者，目前住在丹佛。和往常一样，和我一起的是 Wes Bos。最近怎么样，Wes？

Wes：嘿，没什么特别的，很高兴来聊预取、预渲染，它们的好处、缺点，所有这些好东西。我先简单讲一下我是怎么想到这个话题的。几周前，一条关于 McMaster-Carr 网站的推文很火，大意是说：McMaster-Carr 的网站怎么这么快？一家上百年历史的老公司，怎么能做出这么快的网站？于是我就想，好吧，我是 Web 开发者，那我来搞清楚。我很快研究了一下，最后做了一个小视频，讲他们用了哪些技巧让网站感觉尽可能快。其中一项——我敢说是性价比最高的一项——就是当你把鼠标悬停在链接上时，他们会预加载那些页面的 HTML。预加载、预连接，这种做法已经存在很久了，而且其实已经内置在很多框架里，比如 Next.js。但现在我们迎来了 Speculation Rules API，它将直接内置在浏览器中，而且能做的事情比这还要多，非常有意思。

Scott：对，我还看到 CSS Wizardry 的 Harry Roberts 已经在他的网站 csswizardry.com 上用上了它。

Wes：挺巧妙的，挺巧妙的。好，我们开始吧。

Wes：好，我们来聊预加载（preload）、预取（prefetch）和预连接（preconnect）。浏览器里很早就有一种 link 标签，你可以放在文档的 head 里，写 link rel="preload" 或 rel="preconnect"。它的作用是告诉浏览器：嘿，这是一个资源，不管是 HTML 页面、字体还是图片，我在文档的某个时候会需要它，所以你可以 a）直接开始下载它，这就是 preload；或者 b）preconnect，你可以告诉它先别下载任何东西，但先搞清楚它在哪。因为请求周期的一部分是：你得先弄清楚，比如这个字体是从 cdn.coolguy.net 加载的，那就要先查出 cdn.coolguy.net 的 IP 地址，还要完成整个 SSL 握手、确认一切正常。那就提前把这些都做好，这样当我真的要你从这个 URL 下载东西时，所有这些开销都已经完成了，直接开始下载就行。

Scott：对。不知道这个比喻恰不恰当：预加载就像是"穿好鞋、上车，我们出发了"；而预连接则像是"我们可能要去个地方，先把导航打开、查好路线"，这样等真要出发时，我们就知道该怎么走，知道有多远、要去哪里。

Wes：对，完全正确。预加载和预连接都非常好用的一点在于 HTML 的解析方式：你可以把 preload 或 preconnect 放在文档的 head 里，告诉它网页字体、样式表之类的资源，浏览器在真正遇到它们之前就会开始下载。比如说网页字体：你得先加载 HTML，然后解析 HTML，HTML 发现有一个 CSS 文件，再去解析 CSS，解析 CSS 的过程中才发现："哦，这有个网页字体，我去下载一下。"这样你的请求就形成了瀑布流。所以如果你能在浏览器连 body 开始标签都还没碰到的时候就告诉它"我会需要这个字体"或者"我会需要页头这张图"，它就会远远提前开始下载，用户感知到的网站速度就会更快。

Scott：你第一次在 Web 开发中碰到这个是什么时候？

Wes：Google Fonts 就是个很好的例子。用 Google Fonts 时你访问的是另一个域名，浏览器并不一定知道那个域名的 IP 地址。所以当你从 Google Fonts 复制那段代码片段时，它会给你预连接的 URL，让你粘贴到文档的 head 里。

Scott：对，我记得。我还记得第一次用 Gatsby 的时候——那是 Gatsby 很早很早期的版本——你加载什么都觉得：我的天，怎么这么快？然后打开网络面板，就看到它在做各种预加载。

Wes：是啊，挺好的。甚至比如你有分页：如果用户在第二页，你可以预加载第三页，因为用户很可能会点它。这样做的结果是，浏览器会去下载那个 HTML，让它热乎乎地准备好。而且在 link 标签的情况下，它还会遍历整个页面寻找其中的资源，如果页面上有图片标签和 CSS，也会一并下载。这个我们已经有了一段时间，但它必须逐个资源地去做。

现在有了这个新的 API，叫 Speculation Rules API。它允许你在页面里放一个 script 标签，type 是 speculationrules。在里面，你既可以指定预渲染（prerender），也可以指定预取（prefetch）。预取会直接把那个文档的 HTML 下载下来，热乎乎地放着备用。预渲染则更进一步，真的把它渲染出来——有点像在一个新标签页里那样——它会下载 HTML、解析、在 DOM 里完成布局、下载所需的所有资源，比如图片、字体等等，全都准备好，这样当你真点击那个链接时，页面会瞬间切换过来。推测规则里你可以这样写：当链接匹配某个正则时预渲染，或者当有某个选择器匹配 X、Y、Z 时预渲染。基本上你就是写一堆类似 jQuery 或 CSS 的选择器，规定链接匹配这个就下载、不匹配就不下载，实际的预渲染也一样。

Scott：有意思。那在要求客户端下载的东西方面，这岂不是很快就会失控？

Wes：对，完全会。每次谈到预取和预渲染，大家都会说："好吧……"因为 Next.js 这个功能已经有很久了，如果你预取和预渲染得太激进，你的账单就会往上涨。所以你得认真想想，在这里预取、预渲染这些东西值不值得。不过在说那个之前，我先快速讲一下 Speculation Rules API 的另一个部分：你希望它有多积极，这叫做 eagerness（积极程度）。

Scott：好名字。

Wes：取值有 immediate、eager、moderate 和 conservative。即使你告诉它"这些是我可能想预加载的链接"，基于这些积极程度设置，设备也得自己做决定。像用户的网络状况、手机的速度等等，这些都会影响浏览器是否决定去做，甚至还有电量。如果你的用户只剩 4% 的电，那大概就不适合浪费他们的电量去提前下载一堆页面了，对吧？

Scott：很酷，这个能内置进去挺好的。

Wes：是啊，因为在某个时刻，浏览器需要根据它所知道的信息做出这些决定。不过像 Next.js 早就有这个了，很多框架都早就有了：当链接进入视口时就预加载，或者当有人悬停在链接上但还没点击时预加载。但这可能会有点贵，取决于成本是多少。想象一下加载 Syntax 首页，如果我们开始预加载最近 10 期节目，那就意味着我们网站的工作量会变成 10 倍，那是不是你的账单也会变成 10 倍？所以这里有一些问题你应该想一想。一个普通的、只是被预取而不是预渲染的 HTML 页面大约是 30K 到 100K。你想想，好，100K 算是相当大的 HTML 页面了，加载一次要花我们多少钱？如果你是从 CDN 加载的，而它已经是静态的——比如我的网站，如果只是一个静态页面，很多博客文章就是纯静态页面——那在那里加载几乎不花我什么钱。但首先，如果你的主机是按带宽收费的，那费用可能很快就会变高，因为你付费的带宽会变成十倍。再者，服务器实际渲染这个页面有没有成本？如果有人落到某个页面时你就预加载 10 个额外页面，那你就要用掉 10 倍的服务器资源、10 倍的数据库时间。对用户来说这点增量的速度提升，对你值得吗？就 McMaster-Carr 网站而言，我想他们做了大量激进的缓存，所以非常值得。

Scott：你觉得他们也做了预渲染吗？感觉那应该是很重要的一部分。

Wes：他们没做预渲染，因为我认为预渲染是浏览器层面的东西。当然，如果你在 React 的世界里，大概也可以把整个东西在屏幕外预渲染好再换进来，但他们做的只是预先下载 HTML，然后当你点击链接时，他们只替换页面上的 HTML——不是整个页面，只是网站中变化的那一部分。

Scott：嗯，我刚才想的预渲染，几乎是那种静态站点的预渲染，你懂的，在构建时预渲染。

Wes：你是说像服务端渲染那样？

Scott：对，因为在 SvelteKit 里，任何路由你只要写 prerender = true，它就会把那个路由渲染成静态路由。

Wes：对，你可以那样做，也可以用 stale-while-revalidate。如果你的网站前面有 CDN，你可以在响应上加一些缓存头，这样服务器就不需要每次都重新生成页面。你可以说：好，缓存三分钟。有些页面可以这样做，因为它对所有人都一样；而有些页面不行，因为里面是用户数据。比如你的个人资料页，你不能把用户的个人资料缓存在全局 CDN 上。

Scott：不过这正好是把状态放进查询参数的一个好理由，对吧？

Wes：对。

Scott：你把状态放进 URL，那你能预渲染这些 URL 吗？至少你可以缓存它们。

Wes：如果你事先知道这些 URL，就可以预渲染。但举个例子，在 Syntax 网站上我们有节目列表，你翻到第二页，或者筛选 Hasty Treat，这些都会体现在 URL 里。理论上我们可以算出有 100 页、80 种不同组合，但到某个程度你会发现，每页显示多少条、你想看哪类节目……这些组合可能有好几千种，不知不觉就失控了，要生成一万个 HTML 页面。

Scott：对，但你可以做的是，在渲染之后把它们缓存起来。

Wes：这样第一个访问的人拿到的是新鲜生成的版本，然后你把它放进缓存。这并不是说它慢——Syntax 网站在没有缓存的情况下也不慢——而是每次都要用服务器时间重新生成那个页面，这很贵。所以你要做的就是把"Hasty Treat 第 32 页"的结果存进缓存，或者在上面加个缓存头，然后 CDN 就会保存这个版本，下次直接提供。

Scott：是的。还有一点需要考虑的是：用户加载这些东西的成本是多少。现在不限流量已经很普及了，这已经不算大问题。说起来，我们节目上请过谁来着，他聊到非洲的网络连接？

Wes：对对对，是 Tory（音），哦对。

Scott：他说"你们不了解非洲的网络状况"，结果所有评论都在说："兄弟，我就是非洲人，我们的网速比美国还快。"

Wes：我信。

Scott：所以你得考虑：用户是不是在用有限流量的套餐？是不是在较慢的网络连接上？我觉得这就是设备本身会在推测规则中发挥作用的地方——决定该不该做。因为再说一次，如果你在某些网站上想着"有何不可，干脆全都加载了"，那每天 2G 的流量套餐很快就会被烧光。

Wes：有意思。说到 McMaster-Carr 网站这件事，有几个人做了一个叫 Next Master 的东西，用 Next.js 重新实现了 McMaster-Carr 的网站，非常酷。它显然不是一模一样的网站，有些不同之处。我给他们发消息说：把 Vercel 的账单贴出来吧。因为所有人都在说："是啊，但预加载所有这些东西得花一大笔钱。"然后他们真的贴出来了。他们有 4.5 万独立访客，大约 100 万次页面浏览，也就是每位访客 20 个页面。我不相信大家真的点了 20 个东西，我敢打赌这意味着每个页面上预加载了 20 个页面。4.5 万独立访客、100 万次页面浏览，他们的总账单是 513 美元。这算多吗？

Scott：这真的取决于你的产品。我会说这挺多的。4.5 万访客，我会说这挺多的。

Wes：如果看明细，超过一半是 Edge 请求：Vercel 的 Edge 请求费用是 220 美元。另外 160 美元是图片压缩，也就是图片优化，而这只需要做一次，因为他们实打实有 10 万张图片需要调整尺寸，所以那 160 美元其实只会发生一次。剩下的大概是增量静态再生（ISR）的读写费用。没有什么别的特别突出的。不过这是在 Vercel 上，Vercel 在这类事情上出了名的贵，但对很多人——包括我们自己——来说是值得的，因为自己托管这些东西可能有点麻烦。所以我打赌，如果你专门追求省钱，可以做得便宜很多。

Scott：对，他们并不是冲着省钱去的。

Wes：他们是冲着"我们怎么做出一个感觉一样快的 Next.js 网站"去的。事实上它连加载转圈都没有，加载得甚至更快。

Scott：太酷了，哥们，我这是第一次了解这个。那我们讨论过它目前的普及程度吗？

Wes：它现在在 Chrome 里已经可用了，其他浏览器还没有，我们在等 Firefox 和 Safari。不过这类东西很容易做 polyfill，尤其是预取，因为你只要拿这些正则去匹配就行。我确定肯定有推测规则的 polyfill……等一下——

Scott：哦对，这太说得通了，你自己去预渲染或者预加载就行。

Wes：对，确实有一个 polyfill，所以你可以这么做。至于 Next.js，我觉得他们甚至没用这个，因为 Next.js 有更细的控制：它们并不会获取整个页面，而是可以只获取需要变化的那个组件，在组件层面进行，这挺巧妙的。所以这种预渲染网站的整体思路，对于让网站感觉很快是非常好的一件事。

还有一点是，McMaster-Carr 的 PageSpeed Insights 分数糟透了。所有做性能的人都说："不，这太糟糕了。"而看看真实的普通用户反应就很好笑。我收到了很多非 Web 开发者的消息，说："我喜欢这个网站，因为它太快了，这是我全世界最喜欢的网站。"能看到这些真的很好，因为这些是真实用户，他们才不管 PageSpeed 分数高不高，他们只知道点一下按钮，页面就以最快速度出现。

Scott：是的，我们之前在节目里也说过，PageSpeed 分数并不是全部，它只是一个工具。但如果你在较慢或者中等偏慢的网络下使用这个网站，你能感觉到、能看到它实际用起来很快，那你就不需要完美的 Lighthouse 分数了。重要的只是用户体验，因为说到底这才是唯一重要的，而不是分数。

Wes：前几天有人在推特上截图羞辱我，说我的 wesbos.com 在移动端只有 76 分左右，桌面端倒是 94 分，移动端大概 78 分之类的。我就想说：给我看一个真实的网站，不是那种在一个 div 里放一串链接的个人博客，给我看一个有大量图片、PageSpeed Insights 分数还很高的网站。就像你说的，我们这个行业里谁的性能最顶尖？就拿 Vercel 来说吧，vercel.com，看看它得几分。

Scott：那得有很多图片才行。

Wes：我们看看。Vercel 有很多图片吧？我想应该有，CSS 也肯定不少。哦，他们有很多图片，挺多的。

Wes：出来了，Vercel 的性能得分是 44。可你去他们网站看看，快得要命。这就是让人特别恼火的地方：这竟然被当成了黄金分数。给我看一个有真实客户的真实网站能拿到高分。如果你切到桌面端，通常会好一些，但它就像是在说："哦，如果你在一部降速的老式功能机上、用很差的 3G 访问……"那当然会慢，整个网站都会慢。这并不能成为做烂网站的借口，但我不认为 Lighthouse 分数是我们应该追求的目标。我不知道，你怎么看？

Scott：嗯，我觉得我的狗现在快疯了，我不知道她在干嘛，我想她听到了什么动静，以为外面有东西，所以有点呼哧呼哧的。

Wes：哦，好吧。为什么？
