React as a UI Runtime ｜ Overreacted, Dan Abramov ｜ 文章 ｜ https://overreacted.io/react-as-a-ui-runtime/

Dan Abramov 2019 年的这篇长文不讲怎么用 React，而是把它当作一种"编程运行时"，从第一性原理解释它的编程模型。他说明这不是入门文章，面向有经验的程序员和其他 UI 库的作者，不懂这些也能把 React 用好。

React 程序输出一棵随时间变化的"宿主树"，可以是 DOM、原生视图甚至 JSON，由渲染器负责与具体环境对话。React 押注两条原则：大多数更新不会彻底改变结构，UI 可以拆成规律的模式，所以它适合写 Twitter 客户端，却不适合 3D 屏保。最小单元是 React 元素，一个轻量、不可变的普通对象，像电影的一帧。再次渲染时 React 不推倒重建，而是"协调"：同一位置元素类型一致就复用宿主实例、只改属性，否则销毁重建。条件渲染因空位占住位置而不丢状态；动态列表重新排序则会错位，所以需要用"顺序变了仍是同一项"的值作 key。

组件是返回元素的函数，React 假设它对 props 是纯的，但更看重幂等而非严格纯粹。写成 <Form /> 而非直接调用，是一种控制反转：React 能给组件附上与树中位置绑定的状态，类型参与协调，能推迟工作让出主线程，还带来惰性求值的好处：把评论组件作为 children 传给页面，若页面因用户未登录提前返回，评论组件根本不会被调用，既省了白做的工作，也让代码更不脆弱。局部状态通过 Hooks 提供；工作分为可中断的渲染阶段和同步的提交阶段，避免用户看到更新到一半的界面。React 不默认做记忆化，因为很多组件每次拿到的 props 都不同；所以父组件更新默认协调整棵子树，太大时可用 React.memo 或 useMemo 跳过。

他解释了 React 为何不采用细粒度响应式订阅：建立监听会拖慢首次交互，多数交互又很小或是整页切换，React 的开销与视图大小而非数据模型大小相关；行情类处处变化的场景可能不是它的强项。同一事件内的多次 setState 会批处理，因此连加三次只加 1，需要用更新函数或 useReducer。

他用"调用树"作比喻：普通函数返回后栈帧消失，React 组件的帧（Fiber）则持续保存状态；Context 像组件的动态作用域；Effect 在绘制后执行副作用，依赖数组常是过早优化，写成空数组会让闭包里的计数永远停在 0，依赖必须包含所有会变的东西，或者干脆接受重新订阅。自定义 Hook 共享的是逻辑而非状态。Hooks 必须在顶层无条件调用，因为它们按调用顺序挂在 Fiber 上，和协调按位置对上元素是同一思路。他坦言并发模式、Suspense 等尚无定论，而大多数人无需想这些也能走得很远，恰恰说明 React 的默认设计是成功的。
