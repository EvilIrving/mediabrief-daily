我不能代表 Guillermo 发言，但我之所以如此强烈地认同他的话，是因为我作为 UI 工程师的经历，以及我个人在这个语境下对“集成”一词的理解。

尤其是在我职业生涯的那个阶段，我写的几乎所有代码要么直接在浏览器里运行，要么是为帮助我在浏览器里运行代码的工具而写的。所以很自然地，我会透过这段经历的视角来看待“单元”“集成”和“端到端”这些术语。事实上，我之所以在奖杯里加上“静态”，是因为在 JavaScript 的世界里，静态检查并不像测试金字塔提出时那些主流语言中那样理所当然。

我解释这些背景，是为了帮你理解测试奖杯本来应该如何解读。我从没考虑过它是否适用于微服务，甚至是否适用于后端服务。我是孤立地看待自己的代码库，试图在我自己负责的代码范围内，对我能写的各类测试进行分类。我一向把端到端测试看作这样一个地方：在不使用任何 mock（或者更实际地说，“尽可能少地使用 mock”）的情况下，验证一切都能正常工作。

于是剩下的就是把针对我自己代码的测试分成“单元”测试或“集成”测试。我把“单元”看作包含逻辑的单个函数、类或对象。下面是我（大致）的分类方式：

- 单元测试：测试那些没有依赖（协作者），或者依赖在测试中被 mock 掉的单元。
- 集成测试：测试多个单元之间的相互集成。

后来，我创建了 Testing Library，来推广那些对我最有效的测试实践：

按照我自己的定义，Testing Library 可以用来测试单个 React 组件（单元测试），用 MSW 模拟 HTTP 请求来测试整个页面（集成测试），用极少的 mock 测试整个应用（端到端测试），必要时甚至可以测试单个 React hook（更底层的单元测试）。如今 Testing Library 已是 React 应用最流行、事实上的标准……呃……测试库，而且在任何能找到 DOM 的地方，情况也越来越如此。2020 年 5 月，Testing Library 在 ThoughtWorks 技术雷达上获评“采纳”（Adopt）。

我预料有些人会这样回复这篇博文：“你当初为什么非要自己编定义？用现成的就行了。”所以我先在你问之前回答：“那二十几种不同的定义里，你希望我选哪一种作为我自己的定义？”😂 😭 Martin Fowler 在他关于测试形状的文章中，大致引述了一位“测试专家”的话。这位专家在 1990 年代被问到如何定义“单元测试”时说：

“在我培训课程的第一天上午，我就要讲 24 种不同的单元测试定义。”

这是一种令人遗憾的状况，而且可惜的是，从 90 年代起就一直如此。事已至此。我必须选一个对我来说说得通的定义，而作为一名教育者，我也必须选一个对我所教的人来说最说得通的定义。从采纳了我建议的人的反馈来看，我的决定是个好决定。

在讨论能否证明测试有效时，Tim Bray（在他的文章《二十年代的测试》中）说得很对：

“别自欺欺人，以为我们的软件测试信条构成了科学知识。”

我想说，这适用于测试的方方面面，而不仅仅是测试是否有效（它可以有效）。任何想给所有这些术语找到统一定义的尝试，都是徒劳的。我记得在 Assert(JS) 大会上演讲时（我在那里做了《写测试。别太多。主要写集成测试。》的演讲），我注意到每场演讲在测试建议上都大相径庭。但现在想来，我认为很多差异可以归因于我们对测试术语的定义不同，而不太在于我们追求信心的方式不同。

结论

总之，希望这能帮忙把事情说清楚一些。总结一下：当你尝试把测试奖杯应用到自己的情况时，要在单个代码库的范围内思考它。它在后端肯定也适用，但我只针对单体应用考虑过它，没有考虑过微服务，甚至 serverless 函数（而且我同意 Tim 的观点，我们大多数人如果可以的话，大概都应该写单体应用）。

测试奖杯（在被正确理解时）让我（以及无数其他人）清楚了该把测试精力放在哪里。在被正确解读时，它帮助我牢记这条关键原则：
