渐进式 JSON（Progressive JSON） ｜ Overreacted, Dan Abramov ｜ 文章 ｜ https://overreacted.io/progressive-json/

Dan Abramov 借"渐进式 JPEG"的思路问：传输 JSON 能不能也先模糊、再逐渐清晰？他以此为线索，讲清 React Server Components（RSC）的一项核心创新。

他先指出现状的毛病：JSON 要等最后一个字节到了才是合法的对象树，客户端只能干等、再 JSON.parse。如果服务器上某一部分很慢，比如加载评论要查一趟慢数据库，那么服务器没做完所有工作，客户端就开始不了任何工作。他调侃说 99.9999% 的应用都这么干（"这数字是我编的"）。

第一种改进是流式 JSON 解析器，能从不完整的输入里拼出对象树。但这样得到的对象是"畸形"的：顶层少了还没到的 footer，评论数组也看不出后面还有没有。类型对不上、分不清什么已完成，应用逻辑很难利用，所以流式 JSON 只在小众场景流行。这相当于 JPEG 默认的自上而下加载：清晰但只看到顶部 10%。HTML 默认的流式传输也是按文档顺序来的，截断点随意，还会打乱布局；更糟的是，按顺序流式传输时，一个慢的部分会拖住后面的一切，哪怕页脚早就在服务器上准备好了。

他提出的"渐进式 JSON"是改为广度优先发送：顶层对象里先用 "$1""$2""$3" 这样的占位符代替还没发的部分，之后在流里以任意顺序补发这些行；客户端把尚未到达的部分表示为 Promise，到了就 resolve，逐层填满整棵树。只要客户端能处理部分内容"未就绪"，这就是进步。在此基础上还可以优化：不慢的部分没必要单独成行，可以"内联"，比如只有文章和评论两处慢操作，就总共发三块，服务器可以自由选择分块策略，只要客户端能容忍乱序到达；反过来也可以"外联"，同一个对象（如多处引用的 userInfo）只发一次、其余引用同一行来去重，甚至能序列化普通 JSON 做不到的循环对象。

接着他点明，这基本就是 RSC 的工作方式：服务器组件里 await 加载文章和评论，React 把页面输出成渐进式 JSON 流，客户端重建为逐步加载的 React 树。关键转折在于，你并不想让页面随数据到达而乱跳，比如可能永远不想显示没有正文的页面。所以 React 不会为待定的 Promise 显示"空洞"，而是显示最近的、用 <Suspense> 声明的加载状态。没有 Suspense 边界时，数据照样流式到达，但 React 会等整个页面就绪再显示；给评论包一层 Suspense，用户就会看到两个阶段：文章连同页眉、页脚和评论占位一起出现，之后评论单独出现。也就是说，界面揭示的阶段与数据到达的方式解耦：数据一可用就流过来，揭示则按刻意设计的加载状态来。他打比方说，树里的 Promise 像 throw，Suspense 像 catch。他还强调这和 SSR、HTML 无关，是一种流式传输以 JSON 表示的 UI 树的通用机制，可以转成渐进揭示的 HTML，也适用于单页应用式的导航。

结论是：RSC 不是把数据作为一大块发送，而是由外向内发送组件树的 props，只要有刻意设计的加载状态可显示，React 就能在其余数据流入时先显示出来。他呼吁更多工具采用渐进式数据流：凡是"服务器停下来客户端才能开始"，或"一个慢东西拖慢其后一切"，都是信号。但光有流式传输不够，还需要一个能利用流、优雅处理不完整信息的编程模型，React 用 Suspense 来解决，他也想听听别的系统怎么做。
