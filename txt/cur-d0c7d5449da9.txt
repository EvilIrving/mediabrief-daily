编程 agent 的组成部分（Components of A Coding Agent） ｜ Sebastian Raschka ｜ 文章 ｜ https://magazine.sebastianraschka.com/p/components-of-a-coding-agent

Sebastian Raschka 写的一篇参考文章，讲编程 agent 和 agent harness 是什么、怎么运作。他的核心判断是：实用大模型系统近来的进步很大程度上来自"怎么用模型"，工具、上下文管理、记忆这些外围系统和模型本身同样重要，所以同一个模型在 Claude Code、Codex 里比在聊天框里强得多。

他先厘清概念：大模型是预测下一个 token 的核心；推理模型仍是大模型，只是在推理阶段多花算力做中间推理和自我验证；agent 是围绕模型的控制循环，决定下一步看什么、调用哪个工具、何时停止；harness 是管理上下文、工具、提示词、状态和控制流的软件脚手架，coding harness 则是专为软件工程定制的一种。他认为如今 GPT-5.4、Opus 4.6、GLM-5 这些原版模型能力已很接近，harness 往往才是拉开差距的因素，甚至推测把 GLM-5 放进类似 harness 也可能与 Codex 里的 GPT-5.4 相当，不过针对 harness 的后训练仍有帮助。

随后他结合自己用纯 Python 写的 Mini Coding Agent，讲六个组件。一是实时仓库上下文：动手前先收集 git 分支与状态、AGENTS.md、README、目录结构等"稳定事实"，做成工作区摘要。二是提示词结构与缓存复用：规则、工具描述和工作区摘要组成稳定前缀并尽量复用，每轮只更新短期记忆、近期记录和新请求。三是工具使用：模型只能从预定义的工具中选择并给出结构化参数，harness 先检查工具是否已知、参数是否合法、是否需要批准、路径是否在工作区内，通过后才执行，自由少了，可靠性和可用性反而更高。四是控制上下文膨胀：截短长输出，对历史做精简总结，近期事件保留细节、较早事件压得更狠，并对重复读取的文件去重；他说很多表面上的"模型质量"其实是上下文质量。五是结构化会话记忆：完整对话记录作为可恢复的持久状态存盘，另有一份小而不断改写的工作记忆，记下当前任务、重要文件和笔记，前者服务于重建提示词，后者服务于任务连续性。六是有边界的子 agent：把查定义、看配置、查测试失败原因之类的旁支问题委派出去，子 agent 继承足够上下文，但受只读、递归深度等限制；Codex 的子 agent 一般继承主 agent 的沙箱和审批设置，边界更多靠任务范围和深度。

最后他对比 OpenClaw：它同样有 AGENTS.md 等指令文件、JSONL 会话与压缩、子 agent，但定位是在多个聊天、频道和工作区中长期运行的通用本地 agent 平台，编程只是其中一类工作；编程 agent 则专为一个人在仓库里高效读改代码优化。文末附有新书《从零构建推理模型》的介绍。
