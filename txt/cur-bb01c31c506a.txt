论合规与可读性：用 CSS 生成文字颜色 On compliance vs readability: Generating text colors with CSS ｜ Lea Verou ｜ 文章 ｜ https://lea.verou.me/blog/2024/contrast-color/

Lea Verou 是 CSS 工作组成员、相对颜色语法（RCS）的设计者。这篇 2024 年 5 月的文章想解决一个老问题：颜色不由作者掌控时（用户自选的 GitHub 标签色、Web 组件的使用者传入的变量、外部设计系统），怎样自动配出可读的黑或白文字。专门的 `contrast-color()` 已经被她推动缩减成 MVP 写进规范，但乐观估计也要两年左右才能在各浏览器落地，级联层从提案到全面发布也花了两年多，所以她用已覆盖约 83% 用户的 RCS 做了一个过渡方案。

技巧是在 OKLCh 里设亮度阈值，用 `clamp(0, (l / 阈值 - 1) * -infinity, 1)` 把亮度压成 0 或 1，低于阈值出白字、高于阈值出黑字；不支持的浏览器用 `@supports` 回退到半透明底、文字描边或多重阴影。

文章重心在验证阈值。她指出被许多国家写进法律的 WCAG 2.1 对比度算法在中间亮度几乎等于乱猜，更准的 APCA 还不是标准，所以建议用 APCA 保证可读、以 WCAG 兜底合规。她用 Color.js 遍历颜色空间并反向推理：所有白字不达标的情况 L 都在 62.4% 以上，因此低于它白字必然合规；数据也显示 WCAG 在白字上大量误判、把阈值压得比 APCA 低得多。结论是必须合规时阈值最高 62.3%，只看可读性可取约 70%；颜色范围更窄时还能放宽，如 sRGB 内 65%、中性色 67%。附录补充：以 XYZ 的 Y > 0.36 为阈值与 APCA 更吻合，只需黑白时推荐它；还提到 `color-mix()` 放进 `from` 的浏览器 bug 可用 `@property` 规避。整体态度务实：方案现在就能用，同时直言现行无障碍标准本身有缺陷。
