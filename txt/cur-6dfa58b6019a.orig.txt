Adam：我是本期的主持人 Adam。要不先请高天简单讲讲这四年的变化？其实我们在群里交流得挺多，彼此的情况也比较了解。上次请你来的时候，主题主要是 VizTracer；四年过去，你既在 B 站做技术分享，又成为了 Python 核心开发者。这四年中间都经历了什么？

高天：四年前正好赶上世界上的一些状况，那时候出门比较少，多了很多闲暇时间去做些零七八碎的事。后来又搬了家，慢慢变成纯远程工作，一直到现在，所以自己的时间就多了一些。从那时候开始，我更多地接触了所谓的 community，也就是 Python 社区。最开始我只是自己用 Python 写程序，后来开始做一些开源项目，了解怎么宣传自己的工具或产品。再后来慢慢有机会接触到 CPython 的社区，应该也是那一年去参加了 PyCon China，做了一个跟 Viz 有关的 talk。之后跟整个社区就逐渐熟悉起来了。

B 站是我搬家之后开始做的。刚搬到南湾那边的时候比较无聊，没什么事。之前我在知乎写一些文章、答案，但知乎逐渐有些没落了，对吧？我就想做一些完全由自己决定的事。知乎有个问题：有人提什么问题，你才能答什么，你并不能完全掌控自己的创作，不是说今天有个想聊的东西就可以聊。所以我就想去 B 站试试，开始发一些视频，最开始基本都跟 Python 有关，积累了一定的粉丝量。到现在做的东西稍微杂一些，但基本还是围绕技术。总的来说，这四年我确实接触到了世界上不少不同的面相，但最初的根源，还是自己的时间相对多了一点，有功夫去让生活体验到不同的面相。

laike9m：这个话题也许后面可以展开聊，但我觉得很多人都很好奇：你有一份全职工作，还要做开源，还要当 B 站 up 主，我记得你以前视频里还说要打游戏，你是怎么有这么多时间的？

高天：我觉得最重要的一点是，你的本职工作不能太忙。如果白天的工作一天就占了你 10 个小时，那留给自己的时间确实会非常少。第二点，我这几年游戏打得少了，不少游戏时间都贡献给了这些零七八碎的事。还有一点，恰好我用来休闲放松的一些方式，被拿出来以后大家觉得还蛮酷的。不管是当 up 主，还是给 CPython 写代码，这些事有时候是我拿来休闲放松或者转换头脑的，比如工作干累了，就写点别的东西，或者做个视频。而别人的休闲方式，比如打游戏，除非你打得特别特别厉害、排名很高，否则大家会觉得你的时间就是纯休息了。我只是用来休息的时间做了一点稍微有趣的事，其实并不是时间多，大家的时间都差不多。而且说实话，这两件事也没有想象的那么费时间。每周拿出几个小时去做一件事，坚持得足够久，多多少少会有一点成果。

Adam：刚才高天提到，时间多了之后恰好有机会接触到 Python 社区，进而不断做贡献，成为了核心开发者。我挺好奇这个机会当时是怎么来的，以及之后是怎么一步步持续贡献的。我们之前在听众群里发过一份调查问卷，也有听众表示很好奇，怎样才能和社区建立这种联系，最后一步步成为核心开发者。

高天：这个故事最开始是这样的。我是先做的 B 站，做到有一定粉丝数之后，开了一两个群，群里有些朋友一起聊天。有一次群里有人说 pdb 有个 bug。我到现在都记得非常清楚，是 ll 的 bug：在 pdb 里，理论上你是可以修改局部变量（local variable）的值的，比如 x 本来是 1，你写 x = 2，x 就应该变成 2。但如果你在 x = 2 之后运行一下 ll，也就是 longlist，打印源代码，你会发现这个值又变回 1 了，你对局部变量写入的值就没了。我最开始觉得肯定是你哪里出了问题，后来仔细研究了一下，发现确实是 CPython 自己的 bug，而且恰好是一个我有能力改的 bug。这就成了我给 CPython 提的第一个 PR、改的第一个 bug。

说实话，这个过程并不是非常顺利。找到 bug 当天我很激动，提 PR 的时候也很激动，但这个 PR 被搁置了很久。CPython 现在全是志愿者（volunteer），review PR 的时间没那么多，很多时候你的 PR 可能就随风而逝了。我等了好几个礼拜，看没有反应，又尝试 @ 了其他人，才慢慢有人来 review，最后合并（merge）了进去。合进去那天我非常激动，还因为这事在 B 站发了个视频，播放量还不错。因为说实话，B 站上大部分人可能没什么机会给 Python 这种级别的项目提 PR、做贡献。有很多大项目可能藏在底层，但 CPython 知道的人相对多一点，所以我更高兴。

第二次是 VizTracer 的问题。大概有好几年的时间，每隔几天它在 GitHub 上的 validation 就会挂一次，我始终没能在本地复现。那阵子我觉得一定要把它搞出来，花了大概一周时间，发现是 CPython 那边一个类似竞态条件（race condition）的 bug。修那个 bug 其实就一行，找问题比较费劲，但修只修了一行。那次我也发了个视频，而且这次合并得很快，提完 PR，Mark 很快就看了，然后就合进去了。

这两次之后，我感觉给 Python 这种级别的项目做贡献也没有那么难，你就过去找到一个问题，把它修好就行了。于是我就想，那我看看 Python 还有什么问题吧。当时主要有两个途径。第一个，我白天没什么事的时候会刷一刷 Python 的 issues。issue 有新提的，你就跟别人在同一条起跑线上：刷到一个新 bug，看能不能复现；能复现，就可以很快判断它是不是真的 Python 的 bug；如果是，就可以着手修，修得比别人快就可以先提 PR。所以有一阵我非常喜欢刷 Python 的 issues，看能不能 repro。最开始我修了挺多零七八碎的 Python 问题，有的是 bug，有的是小 feature。

第二个途径，是我在给 pdb 改 ll 那段代码的时候，看了一下 pdb 的代码，整体做得挺粗糙的。改 ll 的过程中也发现了不少有问题的地方，我说这块怎么做得比我想象中粗糙这么多。后来才知道，那个模块已经很久没人维护（maintain）了，基本处于放在那里没人管的状态。所以有一阵我想，要不要尝试去做 pdb。我就去 issues 里搜 pdb 相关的 issue，发现大概有几十个，甚至奔 100 个。有一些比较杂、没什么意义，但有一些是五年前甚至十年前的 issue，到现在依然存在，问题很明确，也没那么难修。因为 pdb 是一个纯 Python 的模块，很多时候只在 Python 层面工作就可以。于是我就开始一个一个地给 pdb 修 bug，在 3.12 时期，我基本就是在不断给 pdb 修十年以上的老 bug。

正好遇到了几位比较好的核心开发者。一位是 Irit（Irit Katriel），她是 CPython 现在的一位女性核心开发者，也在微软工作；另一位是 Brandt Bucher，做 JIT 的那位核心开发者。他们俩比较频繁地帮我 review 代码。作为一个外来者，或者说所谓的新贡献者（new contributor），最难的其实是找到人帮你 review 代码、把它合进去。我可能运气比较好，一直有人帮我 review；他们不 review 的话，我就去 ping 他们：你来 review 一下呀。后来我也参与了一些 issue 的判断，有人提 issue、有问题的时候，你可以回答，告诉他这是怎么回事。因为有时候那其实就是 Python 本身的功能，Python 就是这么设计的；有时候则是真有问题，你就帮忙 fix。

大概在一二十个、20 个左右的 PR 之后，Brandt Bucher 联系了我。恰好我在微软工作，微软有一个 Faster CPython 团队，Brandt Bucher 就是那个团队的。他通过微软内部的联系方式找到我，说：我看你最近在 CPython 挺活跃的，要不要当一个 triager？我说可以啊。这大概是我正式开始比较勤奋地在 CPython 上找活干之后三四个月的事，三四个月后我就成了 CPython 的 triager。那时候我开始觉得，进入这个社区其实没有想象中那么困难，而且这个社区还挺缺人的，只要自己找活干，有很多活可以干。当然 Brandt Bucher 人也很好，我可能运气也比较好，他正好在微软工作，能找得到我，所以我挺快就成了 triager。那时候我就觉得，自己未来有可能某一天成为核心开发者，就按这个路线一直走下去吧。

后面从 triager 开始，又贡献了差不多一年。后面的事相对来说就更普通一些。我给 CPython 做贡献的视频一共做了大概 4 个：第一个 PR 做了一个，第二个 PR 做了一个，3.12 发布的时候做了一套“我在 3.12 贡献了什么代码”，最近的就是成为核心开发者。因为新鲜劲过去之后，至少我会意识到这件事没有那么困难，可以正常做，就跟平时在公司工作差不多：找到问题、解决问题、提 PR、合进去就行了。一旦步入正轨，我觉得这事对我来说好像没那么难。在一年前或者几个月前的我看来，核心开发者应该是未来某个时间点能够达成的成就，具体什么时候不知道，但我觉得自己应该是有机会的。

laike9m：听你的分享我觉得挺有意思的，也能让听众学到很多。一开始从 pdb 切入，确实是一个挺好的起步方法。像你说的，pdb 是纯 Python，又很多年没人维护。我当年看 dis 那个模块，就是分析字节码的那个模块，也发现有些地方写得非常粗糙。但我没有像你一样花时间去真正帮他们修一些东西，或者决定要长久地做这件事。在我看来，这个决定还是很重要的。你能不能分享一下当时的想法？是单纯对这件事有兴趣，还是希望给比较重要的项目做贡献，或者对职业生涯有帮助，希望将来靠这个更进一步？

高天：动力是非常非常重要的。因为 Python 这个项目是纯志愿者的，短期内你看不到任何实质性回报。第一个 PR 的时候成就感非常足，你可以说：我给 Python 做贡献了。但第二个、第三个、第四个的时候，就没有第一个那么足了。你做这事不赚钱，还会遇到很多阻力：你不是核心开发者，需要找人 review 代码，很多时候人家不 review，或者告诉你这个代码我不打算合，我认为这个 feature 没必要。所以我觉得动力是必须的。我成为核心开发者不算慢，应该是一年多一点，但哪怕是这一年里，很多时候也需要自驱力。因为没有公司逼你、没有老板逼你，你随时可以撂挑子不干，这是开源项目，我不干了就是不干了，你没有任何 deadline 的压力。所以我觉得，如果你真想成为某个项目的核心开发者，就不能仅仅想着要那个结果，一定要相对享受中间的过程。

你刚才说的那几点其实都存在。第一，给一个相对大型的项目做贡献的成就感。你出去可以跟人说：你知道吗，我给 Python 写代码。这种成就感是我比较需要的，或者说比较能让我开心的。第二，在自己的时间里，我也挺喜欢写程序的。我知道很多程序员下了班就不太写程序了，我还行，我还蛮喜欢写的。在给 CPython 写代码之前，我自己也做开源项目，做得挺高兴，所以这点我并不讨厌。第三，作为 B 站 up 主，这件事和 CPython 稍微有一点相辅相成的作用。作为 up 主，你有时候是不是会琢磨，怎么才能在众多 up 主里脱颖而出，成为一个稍微厉害一点的 up 主，让你的粉丝跟别人吹他喜欢的 up 主时有东西可说？你就会想，什么头衔可能酷一点？然后就觉得，Python 核心开发者这个头衔是不是还挺酷的？在 B 站你很可能是 up 主里独一份。所以当时多多少少也有一点这方面的动力。这几个方面其实都有，但职业发展这件事确实几乎完全没有。从我职业生涯开始到现在，我的工作都跟 Python 没有关系，所以唯独这个方向，当时基本不存在动力。

laike9m：我想到了一个轻小说标题：《关于我为了在 B 站脱颖而出而成为 Python 核心开发者这件事》。

高天：多多少少有这方面的动力吧，肯定不完全是，但想的时候确实想过。在觉得自己差不多要成为核心开发者的那阵子，我确实想过要怎么在 B 站上宣布这件事。

laike9m：那你现在回头看，无论是在这个过程中获得的，还是通过成为核心开发者想获得的，这些目标都达到了吗？

高天：说实话，成为核心开发者那一下，并没有引起我想象中那么大的波澜。也还可以，但我感觉大家对这个领域还是相对陌生。很多用 Python 的人，如果对这一块不熟，你跟他说这人是 Python 核心开发者，他可能完全没有概念：什么叫 core dev？世界上有多少个？起什么作用？所以 B 站上这个所谓的成就，其实没有想象中那么大。但也还可以，还是有很多人因此认识了我。而且我觉得这件事多少有一点长尾效应：不是说今天你成了核心开发者，这事就过去了；你成了之后就一直是。短期来看，甚至相当长一段时间内，我在 B 站很可能都是唯一一个 Python 核心开发者 up 主。所以不急，就算当时没有想象中那么好，慢慢地也会有一些吸引力。B 站这边差不多就是这样：还行，多少有点能拿得出手的东西，没有想象中那么好，但也可以理解。

其他方面，第一，在整个过程中我认识了 Python 社区里的不少人。这个社区挺好的，因为大家都是志愿者，整个环境非常友善。对我来说很重要的一点是，我参加了今年的 PyCon US，参加了 Language Summit，还做了 talk，因此认识了很多核心开发者，也认识了一些其他人，这种感觉很好。在一个社区里有一些归属感，有一些能跟人聊得很开心的地方，我觉得挺舒适的，这是社交方面。技术上，至少对 Python 的了解有比较明确的提升。现在回头看 VizTracer 的一些代码，当时是那种囫囵吞枣、能跑就行的代码，现在基本知道是怎么回事了，或者知道还有没有进一步优化的空间。当然还有一点非常非常重要：在真实世界里做的贡献、写的代码，确实让更多人的生活变得容易了一些。不仅仅是虚头巴脑地、在理论上或名誉上给一个重要项目做过贡献，而是在代码本身、项目本身上确实做出了一些有用的东西。所以总体来说，收获颇丰。

Adam：OK。从高天刚才分享的经历来看，假如我想为 Python 做贡献，不论最终目标是不是成为核心开发者，其实都可以先从关注 issue 列表开始。如果你没有恰好碰到自己真实遇到的 bug，那可以先去看看 Python 的 issue 列表，关注它，这也许是一个开始接触的机会？或者还有其他路径吗？

高天：我觉得这是一个特别特别好的切入点，就是去刷 issue 列表。issue 列表里经常是最新提出的问题，哪怕你没有因此成功提 PR，经常在里面回答问题，也会被大家看见。说实话，现在 Python 比较常驻的志愿者其实不多，所以你在 issue 列表里不停地帮人回答问题、解决问题，偶尔提几个 PR，很可能就会有人注意到你。triager 的门槛其实挺低的，core dev 相对高一点，但 triager 没那么高，你就是帮着 review 一下、回答一下 issue，这样就可以。比如我想给 CPython 做贡献，觉得自己技术实力够，但不知道去哪儿做，那么大一片代码也不知道从哪开始看——那就从 issue 开始，从那些可以复现的 bug 开始，然后去修复，这是一个非常非常好的途径和切入点。

当然，我觉得要做好自己的 PR 不被合并的准备。在进入这种大型开源项目之前，一定要有这个心理准备：不要觉得自己的第一个 PR 一定会被合并，或者把 bug 改掉了就一定会被合并。因为 Python 内部有很多考量（consideration）。我个人推荐，如果有能力、能找到的话，去修那些特别明显的错误，就是你改完之后它明显到绝对是对的。因为修复和改变有时候不一样。比如你想做一个性能优化（performance optimization），但这个优化可能之前有人提过，不做是刻意的，比如为了代码的可读性（readability）；或者你想重构某个部分，那它没被重构可能也是有原因的。所以在最开始、对代码库还不太熟的时候，如果想尝试，最好改那些特别明确的 bug。什么叫特别明确？就是它的行为跟文档（documentation）明显不一样。或者比如前两天我看了一个我自己独立合并的第一个 PR：有个引用计数忘了减，拿到一个新引用（new reference）之后没释放，他给释放了。你要是能遇到这种事，改出来自己信心特别足，肯定会被合并。最开始尽量不要提太大的 PR，比如加一整个 feature，或者把一大堆代码全重构了，那很可能会被拒掉。这是给想尝试的人的一些小建议。

laike9m：我之前也和另一位给 Python 做过贡献的同学聊过，就是 penguin。他做的是性能优化方面的，他的第一个、或者说第一个比较大的贡献，是去 profile 了一些字节码，发现 Python 有两个字节码总是一起用，如果把它们合成一个，能让 Python 快一些。这可能就是你说的性能优化那部分。我觉得这可能不太适合大部分人一开始就入手。门槛比较高，涉及引用计数（refcount）是吧？

高天：对，refcount。我不建议大家一上来就做那个，那是一个非常非常大的修改。

laike9m：是的，那个非常大。我看了一下那个 PR，需要很多背景知识，尤其是修改 C 的部分。

高天：对，这个也可以提一下。如果你发现某个部分、某个模块是纯 Python 的，修改起来可能会容易一些；涉及 C 的部分一般都会比较复杂，主要看你对 C 熟不熟。像我自己 C 本身特别熟，所以 C 和 Python 的部分对我来说差不多。但如果你相对对 Python 更熟、对 C 没那么熟，就尽量不要碰 C 模块，因为 C 的部分还是有些不一样。而 refcount 那个东西，主要可能要碰到编译器（compiler）了，那个地方就费劲了，贼复杂，我靠。

laike9m：对，尽量做那种隔离（isolated）的修改，就是你的修改是局部的，只看一点上下文就能知道它是对的，而不是要好几个文件来回查。

信涛：我想补充一下。这让我想起之前在看 C 语言的一个关键字，加和不加可以给编译器一些提示，编译出来的代码可能更快。我就想，写代码的时候到底怎么判断什么时候加、什么时候不加？后来看到腾讯一位比较资深的游戏工程师的解释，他说写代码的时候一般不考虑这些问题。需要这个关键字的时候，一般是你去看代码到底慢在哪里，发现编译器每次走到这里都会去内存重复读一个它已经知道的东西，因为它不确定这个值是否还没变，所以你才需要加上关键字，让编译器跳过这一步。所以就像高天老师刚才说的，写代码的时候不去考虑这些细节，到做性能优化的时候再来考虑怎么把耗时最长的地方优化掉，也就是先找到最需要优化的地方，再去优化。

另一个例子是我们前段时间一位同事分享的。大概是这样：有个程序每天凌晨 1 点之前要出报告，它每天 10 点开始跑，要跑 3 个小时。他觉得有点慢，数据越来越大，可能到 1 点都跑不完了。于是他把代码重写了一下：原来逻辑比较简单但耗时长，现在逻辑复杂一点，但可能 10 分钟就跑完了。但他遇到一个问题：后面再加需求的时候就不好加了，因为为了性能优化，代码现在耦合得比较紧。最后没办法，因为还有更多需求要进来，他又把代码 revert 回原来的方式，再往上加需求。而解决方法其实非常简单：原来 10 点跑，现在让它 8 点开始跑。因为不管 10 点还是 8 点，数据都已经准备好了。这样原来 3 个小时，后来数据多了跑 4 个、5 个小时都没问题，只要 1 点之前把结果准备好就行。所以这个例子里性能优化的意义不大，因为可以用一个更简单的方法解决问题。

laike9m：我觉得这个话题要聊的话可以聊非常多，因为性能以及性能优化本身就是写代码里非常值得探讨的话题。但我还是想简短引用一下 Joe Armstrong 那句名言。Joe Armstrong 是 Erlang 语言的发明人，他有一句关于性能、一直被引用的著名的话，我先用英文读一下，再用中文解释：“Make it work, then make it beautiful, then if you really, really have to, make it fast. 90% of the time, if you make it beautiful, it will already be fast. So really, just make it beautiful.”这句话用更浅显的方式翻译就是：写代码最需要注重的是可读性。如果你的代码已经非常可读，写得非常工整，用他的说法就是 beautiful、漂亮，那么绝大部分情况下，90% 的时候，它就已经足够快了。剩下那 10% 的情况，就像刚才信涛和高天提到的，你可能需要先 profile 找到性能瓶颈，再去优化那一部分。所以我觉得可读性才是真正重要的。

Adam：对，刚才高天提的是一个很务实、偏实践的经验，大家在做的时候或多或少都会遇到类似的情况：不要过早优化，甚至不要做一些无意义的优化。我之前遇到一个小例子，有同学和我探讨说，我这么写时间复杂度更低。我们经常刷 LeetCode 的话，都知道大 O 记号。但其实在实际工程中，这个 N 的规模是确定的，这时候时间复杂度可能只是一个相对的参考。我们有更确切的方式，像高天说的，能确切知道优化了多少，百分比是多少，真正优化下来的时间或性能是多少。所以可能需要多维度地去评价。

信涛：我想到 Redis 的哈希。O(N) 听起来可能比较慢，但 Redis 作为一个性能很高的缓存，它的哈希在元素数量比较少的时候，用的其实是列表（list）：比如你存了三个，每次查一个，它可能把三个都循环一遍。等 N 比较大的时候，它才会变成用 key 做哈希的真正哈希表。所以在 N 比较小的时候，O(N) 的性能其实比较高，可能比先计算哈希再去找 key 的 O(1) 还快。

laike9m：我还想补充一点。虽然我们说不要过早考虑性能优化，性能大部分时候不重要，但有一点我觉得很重要：要避免一些性能上的反模式（anti-pattern）。什么意思呢？就是有些人们已经总结出来、这样写会导致很大性能问题的写法，你是可以避免的，或者说已经有一些最佳实践（best practice），你只要遵循就好了。比如在 Python 里一个很著名的例子：如果你不需要真的存下一个列表，只是要对它循环，可以直接用生成器，就不需要真正创建一个列表，这样可以省内存。Python 已经给你提供了这些基础设施，也有了最佳实践，你只要去了解、去遵循就好。但比如一些很微观的东西，像访问全局变量比较慢，要把它绑定到一个局部变量上会更快，我觉得这种就完全没有必要了，语言层面也没有这种特别明确的最佳实践，所以大部分时候你基本都可以无视它。而另一些反模式，比如数据库查询的 N+1 问题，也是大家总结出来、明确知道有这么个问题，也有明确的规避方式。所以你只要了解一下这些反模式，避开它们，写出可读的代码，我觉得大部分时候你的代码性能就不会有问题。如果真的需要，再去 profile 并优化。
