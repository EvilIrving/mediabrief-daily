Armin Ronacher 的思考与文章

写于 2026 年 10 月 6 日

一年多以前，我在这里写过几篇文章，建议大家不要把自定义工具（或 MCP 服务器）加载进上下文，而是多用脚本。最重要的是，我写过《Code Is All You Need》（代码就是你所需要的一切），也写过 MCP 需要代码。在 Pi 1.0 中，我们通过 Codemode 加入了 MCP 支持。从某些方面看，这件事早该做了，但对有些人来说也许又有点意外。所以我想在这个博客上分享一些关于这一切意味着什么的新想法。

当像 Pi 这样的 harness 为 LLM 提供可调用的工具时，它会提供一些工具定义，这些定义随后在服务端被转换成某种 token 结构。模型是否倾向于调用某个工具，是强化学习过程的结果。如果你想了解更多，我以前写过这方面的内容。

我们强烈倾向于 CLI 和 bash 的原因之一，是它便于组合调用，而且模型在训练时也学会了文件系统如何运作。所以当它调用像 `echo foo > /tmp/test.txt` 这样的工具时，模型也知道，在这次工具调用之后，`/tmp` 里就有了一个叫 `test.txt` 的文件。

然而 bash 有一个根本性的限制：它只能组合可运行的程序。而有些东西不是程序，而是 LLM 的原生工具，而且某种程度上也必须是。

最明显的例子是 `read` 或 `view_image`。如果一个多模态模型需要读取图像，它不能用 `cat`，因为 harness 需要把真正的图像数据注入到 LLM 的协议中。

另一个相当鲜明的例子是子 agent。要生成和编排子 agent，很难避开由 harness 提供的工具。虽然理论上 agent 可以提供一个 CLI 工具，通过环境变量和 Unix 套接字与外层 harness 通信，但这是一个相当粗糙的过程。而且它还有另一个问题，那就是代码在哪里运行。

为了更好地理解这一点，需要多想一想各个部分都在哪里运行。通常确实涉及两个不同的系统。第一个是大脑，也就是 harness：它运行在一台机器上，是受信任的。第二个*往往*是同一台机器，但它其实是工具执行的地方：手。在 Pi 里我们现在把它叫作执行环境，但你可以把它看作所有操作的目标。

对我们而言至关重要的是，harness 这个大脑与运行 bash、执行工具的目标环境之间，有一条分界线。

一分为二会带来一些非常重要的后果。首先，这意味着它们运行在不同的文件系统上，并且具有不同的信任级别。比如，如果你用 Gondolin 这样的沙箱方案，你的 bash 相关操作会被很好地沙箱化，但 harness 本身不会。

这就引出了 Codemode 真正做的事：它是一种让 LLM 在 harness 一侧（而不是执行环境一侧）表达和编排复杂操作的方式。Codemode 运行在 harness 中，有它自己的沙箱。在 Pi 里，它运行在一个 WASM 运行时中的 QuickJS 里，并有刻意的限制：没有网络，没有文件系统，没有定时器，内存有限。唯一能做的就是调用更多工具。你也可以想象 Codemode 运行 Scheme 或其他某种语言。

如果你不熟悉 Codemode，它基本上就是一种在某种语言（我们这里是 JavaScript）内部发起工具调用的方式。这让你可以组合这些调用，而不必经过 LLM 的上下文。这个名字要归功于我们在 Cloudflare 的朋友，是他们起的。

例如，如果你把 bash 调用作为 LLM 中的普通工具调用发出，我们只会把最后 2000 行放进上下文，如果 agent 想看更多，就需要自己去查看溢出文件。但如果 agent 通过 Codemode 发起这次调用，Codemode 一侧就能以结构化方式拿到更大的输出。

最重要的是，因为 Codemode 是 JavaScript，agent 可以表达并发操作和基本的工作流。现在常见的 agent 用法是：先探查某个工具响应里的 5 到 10 项，看看它长什么样，然后写一个 Codemode 脚本来处理接下来的 n 项。

Codemode 还允许你把状态存进对话记录（transcript）！这意味着一次 Codemode 调用可以把数据存起来，会话中的下一次调用可以再把它加载回来。记住：这是在 harness 主机上，而不是在沙箱里。

在 Pi 里，Codemode 还允许你发起一些在 Pi 传统界面中自然没有意义的调用。比如，你想用图像模型生成图片，或者想用一次性（one shot）分类器模型对某段文本分类，Pi 的这些 API 通过 Codemode 暴露出来，而不是通过普通工具——那样只会浪费上下文。

既然已经讲了这么多，也许值得更具体地说明一下。我们来看看我最近几次 Pi 会话中的一些 Codemode 调用。注意，这些代码没有一行是人写的。它们来自 Pi 的真实会话，只是为了方便你阅读重新缩进了一下。agent 会自动开始使用 Codemode，要么是因为这类任务模型本来就会自然地选用这个工具，要么是因为用户让它这么做。

注意，Codemode 在 Pi 中默认只在启用 MCP 时才开启，但你可以在设置中用 `"defaultTools": ["+codemode"]` 打开它。直接让 Pi 帮你开启就行。

我们先从简单的图像生成开始。图像生成是 Pi 在 AI SDK 核心中支持的功能，但它不是 agent 能使用的工具。过去，使用图像模型的唯一方法是写一个定制扩展，或者让 agent 自己运行 node 并调用内部图像 API。但因为我们在 Codemode 中暴露了相当多的内部模型 API，这意味着 agent 可以使用它：

```
const [painter] = await models.getAvailableOfType("image");
const result = await models.generateImages(painter, {
  input: [{ type: "text", text: "A cute little puppy sitting on a grassy " +
    "lawn, soft natural light, photorealistic" }],
});
if (result.stopReason !== "stop") return result.errorMessage;
for (const block of result.output) {
  if (block.type === "image") image(block);
  else text(block.text);
}
```
注意，调用 `image()` 会把图像作为图像内容发回给 LLM。在 harness 一侧，它会把图像直接送进 agent，同时也作为临时产物写到磁盘上，以防 agent 想把这张图传回给 bash。

类似的情况也适用于 Jev 这样的分类器模型。通过典型的工具，它们也不太适合 agent 的工作流。但 Codemode 并没有为此提供一个定制工具，而是直接让 agent 深入 AI SDK 去调用它们。在这里你可以看到 Jev 如何被用来批量处理 GitHub issue，做一个快速的情感分析：

```
const jev = await models.getModelOfType("classifier", "typesafe", "jev-latest");
const r = await tools.bash({
  command: "gh issue list --state open --limit 100 " +
    "--json number,title,body,comments",
});
const issues = JSON.parse(r.output);
const results = await Promise.all(issues.map(async (issue) => {
  const res = await models.classify(jev, {
    state: {
      title: issue.title,
      body: (issue.body || "").slice(0, 4000),
      comments: issue.comments.slice(-5).map(c => c.body.slice(0, 800)),
    },
    questions: {
      sentiment: {
        type: "choice",
        instructions: "What is the overall sentiment of the author towards pi?",
        criteria: {
          positive: "Appreciative, happy, constructive praise",
          neutral: "Matter-of-fact report or request without emotion",
          negative: "Frustrated, annoyed, upset, or angry",
        },
      },
      frustration: {
        type: "score",
        instructions: "How frustrated is the reporter?",
        criteria: ["not at all", "mildly", "clearly frustrated", "very angry"],
      },
      kind: {
        type: "choice",
        instructions: "What kind of issue is this?",
        criteria: {
          bug: "Bug report or regression",
          feature: "Feature request or enhancement",
          question: "Question or support request",
          other: "Docs, discussion, meta, spam",
        },
      },
    },
  });
  if (res.stopReason !== "stop") {
    return { n: issue.number, title: issue.title, error: res.errorMessage };
  }
  return { n: issue.number, title: issue.title, ...res.answers };
}));
store("sentiment_results", results);
return results
  .filter(r => !r.error)
  .sort((a, b) => b.frustration.score - a.frustration.score)
  .slice(0, 12)
  .map(r => `#${r.n} ${r.frustration.score.toFixed(2)} [${r.kind.choice}] ${r.title}`);
```
注意，在上面这个例子里我们还调用了 `store()`，它把这次执行的结果写入会话记录。因此，之后的 Codemode 调用如果需要，就可以读回这个结果。

这里用 `Promise.all` 没问题，因为 Pi 自己把并发工具执行的总数限制为四个，其余的放在队列里。

一个更大胆的例子，是用 Jev 来驱动游戏引擎，以便调试：

在这里，它知道我的 `tankctl` 命令，并很快为它搭了一个最小的 harness，用来驱动游戏循环，协助用户调试一个问题。注意它构建了一个 30 步的循环，每一步都先回到游戏引擎获取当前状况的文本快照，再交给 Jev 决定下一步做什么：

```
const jev = await models.getModelOfType("classifier", "typesafe", "jev-latest");
const tank = async (cmd) =>
  (await tools.bash({ command: `tools/tankctl "${cmd}"` })).output;
await tank("start --map assets/maps/night_arena.map");
const questions = {
  action: {
    type: "choice",
    instructions: "You control the tank '@' in a top-down tank game. " +
      "Choose the best next action.",
    criteria: {
      attack: "an enemy has line of sight to you and you can fire at it",
      approach: "no enemy has line of sight; drive toward the nearest enemy",
      dodge: "an enemy shot is heading at you and will hit soon",
      powerup: "a powerup is close and no enemy threatens you",
    },
  },
};
function commandFor(choice, st) {
  const p = st.player;
  const enemy = st.enemies.filter(e => !e.dead)
    .sort((a, b) => (b.los - a.los) || (a.dist - b.dist))[0];
  if (choice === "attack" && enemy) {
    return `fire_at tank ${enemy.id}; frames 30 until clear,damage,kill`;
  }
  if (choice === "dodge") {
    // 朝垂直于最近来袭炮弹的方向移动
    const s = st.projectiles.filter(s => !s.yours)
      .sort((a, b) => a.eta - b.eta)[0];
    const dir = s && Math.abs(s.vel[0]) > Math.abs(s.vel[1])
      ? (p.pos[1] > s.pos[1] ? "+down" : "+up")
      : (p.pos[0] > (s ? s.pos[0] : 0) ? "+right" : "+left");
    return `input ${dir}; frames 20 until damage; input stop`;
  }
  const powerup = st.powerups.filter(u => u.available)
    .sort((a, b) => a.dist - b.dist)[0];
  if (choice === "powerup" && powerup) {
    return `goto ${powerup.pos[0]} ${powerup.pos[1]} 180`;
  }
  return enemy ? `goto ${enemy.pos[0]} ${enemy.pos[1]} 90` : null;
}
const log = [];
for (let step = 0; step < 30; step++) {
  const st = JSON.parse(await tank("state"));
  if (st.state !== "playing") break;
  const threats = st.projectiles
    .filter(s => !s.yours && s.miss_dist < 1.5 && s.eta < 1.5)
    .map(s => `incoming shot dist ${s.dist} eta ${s.eta}s`)
    .join("\n") || "no incoming shots";
  const r = await models.classify(jev, {
    state: { map: await tank("view 8"), threats, hp: st.player.hp },
    questions,
  });
  if (r.stopReason !== "stop") {
    log.push(`#${step} classifier error: ${r.errorMessage}`);
    break;
  }
  const choice = r.answers.action.choice;
  const cmd = commandFor(choice, st);
  if (!cmd) break;
  log.push(`#${step} hp=${st.player.hp} ${choice} -> ${await tank(cmd)}`);
}
return log.join("\n");
```
最后，Codemode 显然非常适合调用 MCP 服务器。而且因为我们实际上并不把任何 MCP 工具暴露给 LLM，agent 会先使用提供的 API 在 Codemode 中发起工具搜索，以发现它能用已连接的服务器做些什么。这种渐进式发现，使整个 MCP 这一套在今天的很多使用场景下都能运转得足够好。

比如在这里，你可以看到 agent 甚至没有去发现工具，就直接用上了 Sentry MCP，这大概是因为它在 RL 过程中已经学过 Sentry MCP 长什么样。但它是从我们注入系统提示词的内容中得知 Sentry 服务器本来就可用的。它并不是完全在瞎猜。

```
const orgs = await tools.mcp__sentry__find_organizations({});
const { organizations } = orgs.structuredContent;
const results = await Promise.allSettled(organizations.map(org =>
  tools.mcp__sentry__find_projects({
    organizationSlug: org.slug,
    regionUrl: org.regionUrl,
  })
));
return organizations.map((org, i) => {
  const r = results[i];
  if (r.status !== "fulfilled") return { org: org.slug, error: String(r.reason) };
  if (r.value.isError) return { org: org.slug, error: r.value.content };
  return {
    org: org.slug,
    projects: r.value.structuredContent.projects.map(p => p.slug),
  };
});
```
我真的不想在这里过多谈论 MCP，但 MCP 其实是一个能从 Codemode 中大大受益的协议。问题部分在于，MCP 在实践中往往面向那些（还？）不使用 Codemode 的 harness。但潮流正在转变。与此同时，一个临时的拐杖是像 Cloudflare 那样，在 MCP 服务器内部做 Codemode。可这样我们就有了 Codemode 套 Codemode，这相当糟糕。它意味着双重 JSON 转义，小一点的模型很容易被搞糊涂，而且内层代码无法调用外层工具。所以，比如你在 Pi 中使用 Cloudflare 的 MCP 服务器，agent 就需要写 JavaScript，再把它塞进更多的 JavaScript 里传过去。这真的不是最优的，但发生这种情况也可以理解：

```
const accRes = await tools.mcp__cloudflare__execute({
  code: `async () => {
    const r = await cloudflare.request({ method: "GET", path: "/accounts" });
    return r.result.map(a => ({ id: a.id, name: a.name }));
  }`,
});
const accounts = JSON.parse(accRes.content.map(c => c.text).join(""));
const out = [];
for (const account of accounts) {
  const r = await tools.mcp__cloudflare__execute({
    account_id: account.id,
    code: `async () => {
      const r = await cloudflare.request({
        method: "GET",
        path: \`/accounts/\${accountId}/workers/scripts\`,
      });
      return r.result.map(s => ({ id: s.id, modified: s.modified_on }));
    }`,
  });
  out.push({ account: account.name, workers: r.content.map(c => c.text).join("") });
}
return out;
```
那么最后：今天 Codemode 与 MCP 配合得怎么样？嗯……不算特别好。这是因为 MCP 服务器还没有真正面向使用 Codemode 的 harness（尽管我认为到现在大多数 harness 都已支持它）。

要让它运转良好，有以下一些建议：

- **结构化内容：**Codemode 希望调用返回格式良好的 JSON。所以这需要由服务器返回，而很多服务器还没有这么做。MCP 中的 `outputSchema` 机制非常适合这件事。
- **一致的结果：**一个有趣的失败情形是 MCP 服务器返回的数据不一致。比如因为它会根据结果集中的条目数量来尝试优化 token。这可能导致用 5 项做的初步探查成功了，但当服务器返回最大批量时却失败了。
- **大型二进制数据：**目前 MCP 还不支持大型二进制数据，所以相当多真正有意思的使用场景还完全没法很好地工作。最后你会用上各种奇怪的变通办法，比如用预签名 URL，让文件上传通过非 MCP 渠道进行。
- **可组合的工具搜索：**MCP 服务器可能比 MCP 客户端更清楚哪个工具适合某项任务。但目前没有好的机制让 harness 把工具搜索分发到多个 MCP 服务器上。这一切都是涌现出来的行为，在有多个活跃服务器时扩展性不好。

那么，这让我们处于什么位置？这是否推翻了我一年前鼓励使用 CLI 的观点？我不这么认为。事实上，在我看来，MCP 生态恰恰接受了我们一年前指出的行之有效的东西：代码。但 Codemode 超越了 MCP，因为它可以作为 harness 内部一个强大的机制，给 agent 更多的自由。

不过，也还有一些事情需要我们去弄清楚。其一，Codemode 的持久性（durability）更棘手。我们可能得从持久化工作流引擎那里借鉴一些思路，给调用做快照。又或者，考虑到 Starlark 的确定性，它也许是比 JavaScript 更好的组合语言。

图像、二进制数据，以及这种模式无法用于较小模型的问题，也都需要进一步完善。所以它肯定还不是一个完美的解决方案，但它是一个相当有用的模式，我预计我们会更多地利用它。
