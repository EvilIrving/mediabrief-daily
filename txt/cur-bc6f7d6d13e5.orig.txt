Uday: Before AI, we were measuring the standard stuff, like code throughput; those are the easy ones. Every few months we also do developer experience surveys and look at NPS, sentiment across all kinds of dimensions. We look at our code quality dimensions: what's our incidents per day, what's our code coverage, all of these metrics. Because you can create 100 diffs, but if they're not all feature diffs, maybe it's not necessarily increasing the value we provide to users. For example, one of the things we did is tag all of our PRs into categories: complexity level, and whether it's a feature PR, a bug fix, maintenance, testing, documentation. Then we can go into where the bottleneck is: is it in the PRD phase, the launch phase, the rollout phase? Gergely: And how is your mental model of software engineering changing compared to pre-AI and pre-these-tools? Is it still the same job?

Uday: Things have changed. At least in my total tenure in engineering, there's never been this much change in how I work. For example, we say all engineers at Uber are hands-on; even Distinguished Engineers at Uber are hands-on, they create PRs. But the job of engineering is, in some sense: how do you build the right context for the agents to produce reliable output? You need to get really good at context engineering. Before, I was operating with some context to do some tasks; now I'm always thinking: if I want to offload some of this work to an agent, what context would it need, and how do I set up the environment with that context so it can produce the work? Then you have to become really good at giving the right specs and the right constraints to the agents, apart from building the right context. Then multitasking has become a real thing. Before, it used to take so much time to create a PR, and you were laser-focused on that, but now you're constantly switching between so many things. So you need to become really good at multitasking across all the sessions: how do you scope the work, how do you track the work, how do you verify the work really quickly? Because if you're not able to verify the work and pick up any code smells from the agent, then you're shipping regressions into production. So context engineering, the ability to multitask, the ability to review and verify the outputs: these have become much more important now, because you're able to parallelize a lot more than before.

Gergely: One thing I'm picking up is maybe a new primitive. We used to build software thinking: how do I build this software and how do I verify it? Uday: Yeah. I'll give you an interesting example. I was working with some of the engineers on our customer support team. In the last few months we were able to take all of these steps and ask: how do I take all of the context and all of the principles I want to use for policy conversion and teach agents to do that, so I get a really good v0 policy that an agent can create? That used to take weeks; now it's on the order of days for any policy. Then, instead of doing manual evals, how can you use all the past context to create synthetic evals, so you can accelerate, deploy and verify quickly? Essentially what you are describing: instead of doing that work yourself, how can you build the right tools and harnesses so you can automate the workflow? Obviously you need the right guardrails and human verification steps in between, but you are designing a system that can do these things, instead of relying on so much manual work across all these steps.
