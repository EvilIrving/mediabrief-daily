理解布局算法
Josh W. Comeau ｜ 2022-03-28（最后更新于 2025 年 11 月 18 日）

几年前，我在 CSS 上有过一次“尤里卡！”时刻。

在那之前，我学 CSS 一直专注于我们写下的属性和值，比如 `z-index: 10` 或 `justify-content: center`。我以为只要大致了解每个属性的作用，就能深入理解整门语言。

我的关键领悟是：CSS *远远不只是*一堆属性的集合。它是一组相互关联的布局算法组成的星群。每种算法都是一个复杂系统，有自己的规则和隐秘机制。

光知道具体属性做什么是不够的。我们需要了解布局算法如何运作，以及它们如何*使用*我们提供的属性。

你有没有过这种令人不安的经历：写了一段熟悉的 CSS，以前用过*很多次*，结果却得到一个不同的、意料之外的结果？这非常令人沮丧，让这门语言显得不一致、不可靠。完全相同的 CSS 输入，怎么会产生不同的输出？？

这是因为属性作用在一个复杂系统上，而一些微妙的上下文会改变属性的行为。我们的心智模型不完整，于是就会遇到意外！

当我开始深挖布局算法后，一切都开始说得通了。困扰我多年的谜团一一解开。我意识到 CSS 其实是一门相当稳健的语言，并开始真正享受写 CSS！

在这篇博文中，我们会看看这个新视角如何帮助我们理解 CSS 中发生的事情，并用这个视角来破解一个出奇常见的谜团。🕵️

## 布局算法

那么，什么是“布局算法”？你可能已经熟悉其中一些了，包括：

* Flexbox
* 定位布局（例如 `position: absolute`）
* Grid
* Table
* Flow（流式布局）

（严格来说，它们叫布局*模式*，而不是布局算法。但我觉得“布局算法”这个说法更有帮助。）

浏览器渲染 HTML 时，每个元素的布局都会用一种主要的布局算法来计算。我们可以通过特定的 CSS 声明选择使用不同的布局算法。例如，应用 `position: absolute` 会让元素改用定位布局。

来看一个例子。假设我有如下 CSS：

```
.box {
  z-index: 10;
}
```

首要任务是弄清楚渲染 `.box` 元素会用哪种布局算法。根据提供的 CSS，它会用 *Flow 布局*渲染。

Flow 是 Web 的“元老级”布局算法。它诞生的年代，Web 主要被看作一个巨大的超链接文档集合，就像世界上最大的档案馆。它类似于 Microsoft Word 等文字处理软件所用的布局算法。

Flow 是非表格类 HTML 元素的默认布局算法。除非我们明确选择另一种布局算法，否则就会使用 Flow。

`z-index` 属性用于控制层叠顺序，决定元素重叠时哪个显示在“上面”。但问题是：**Flow 布局并没有实现它。** Flow 的全部意义在于创建文档式布局，而我还没见过允许元素重叠的文字处理软件。（大眼夹 Clippy 绝不会允许的！）

如果几年前你问我这个问题，我大概会这样说：

> 不把 `position` 设成“relative”或“absolute”之类的值，就没法使用 `z-index`，因为 `z-index` 属性依赖于 `position` 属性。

**这并不算*错*，但它是一个微妙的误解。** 更准确的说法是：Flow 布局算法*没有实现* `z-index` 属性，所以如果想让这个属性生效，就需要选择另一种布局算法。

这看起来像是我在咬文嚼字，但这个小误解可能导致大困惑。比如看这个例子：

（代码演示）

```
<style>
  .row {
    display: flex;
    gap: 16px;
  }
  .raised.item {
    z-index: 2;
    background: hotpink;
  }
</style>

<ul class="row">
  <li class="item"></li>
  <li class="raised item"></li>
  <li class="item"></li>
</ul>
```

在这个演示中，我们有 3 个兄弟元素，用 Flexbox 布局算法排列。

中间那个设置了 `z-index`，**而且它生效了。** 试着把它删掉，你会发现它落到了旁边元素的后面。

*这怎么可能？* 我们哪里都没设置 `position: relative`！

之所以有效，是因为 Flexbox 算法实现了 `z-index` 属性。语言作者在设计 Flexbox 算法时，决定把 `z-index` 属性接上，用来控制层叠顺序，就像它在定位布局中的作用一样。

**这就是关键的心智模型转变。** CSS 属性本身是没有意义的。是由布局算法来*定义*它们做什么、在计算中如何使用。

需要说明的是，有些 CSS 属性在所有布局算法中效果都一样。`color: red` 无论如何都会产生红色文字。但每种布局算法都可以覆盖任何属性的默认行为。而且很多属性根本没有默认行为。

**下面这个例子让我大开眼界：** 你知道 `width` 属性的实现方式会因布局算法而异吗？

证据如下：

（代码演示）

```
<style>
  .flex-wrapper {
    display: flex;
  }
  .item {
    width: 2000px;
  }
</style>

<div class="item"></div>

<div class="flex-wrapper">
  <div class="item"></div>
</div>
```

我们的 `.item` 元素只有一个 CSS 属性：`width: 2000px`。

第一个 `.item` 用 Flow 布局渲染，它真的会占据 2000px 的宽度。在 Flow 布局中，宽度是硬性规定。它会占用 2000px 的空间，不管后果如何。

而*第二个* `.item` 渲染在一个 Flex 容器内，也就是说它用的是 Flexbox 布局。在 Flexbox 算法中，宽度更像是一个建议。

Flexbox 规范把它称为*假设尺寸*（hypothetical size）。这是元素在理想世界里、没有任何约束或外力作用时*本应*具有的尺寸。在完美世界里，这个元素会是 2000px 宽，但它被放进了一个更窄的容器，所以会收缩以适应容器。

再强调一次，这里的思考框架非常重要。并不是 `width` 在 Flexbox 中有什么特殊注意事项，而是 Flexbox 算法以不同于 Flow 算法的方式实现了 `width` 属性。（我其实不确定这些东西在底层是怎么实现的，但根据我的经验，这种框架要有用得多。）

**我们写下的属性是输入，**就像传给函数的参数。由布局算法来选择如何*处理*这些输入。如果想理解 CSS，就需要理解布局算法如何运作。只知道属性是不够的。

## 识别布局算法

CSS 没有 `layout-mode` 属性。有好几个属性可以调整所用的布局算法，这其实可能相当棘手！

在某些情况下，应用于元素的 CSS 属性会让它选择某种特定的布局模式。例如：

```
.help-widget {
  /* 使用定位布局，因为有这条声明： */
  position: fixed;
  right: 0;
  bottom: 0;
}

.floated {
  /* 使用浮动布局，因为有这条声明： */
  float: left;
  margin-right: 32px;
}
```

在另一些情况下，我们需要看*父元素*应用了什么 CSS。例如：

```
<style>
  .row {
    display: flex;
  }
</style>

<ul class="row">
  <li class="item"></li>
  <li class="item"></li>
  <li class="item"></li>
</ul>
```

当我们应用 `display: flex` 时，其实并不是让 `.row` 元素使用 Flexbox 布局算法；而是在说*它的子元素*应该用 Flexbox 布局来定位。

用术语来说，`display: flex` 创建了一个 *flex 格式化上下文*。所有直接子元素都会参与这个上下文，这意味着它们会使用 Flexbox 布局，而不是默认的 Flow 布局。

（`display: flex` 也会把 `<span>` 这样的行内元素变成块级元素，所以它对父元素的布局确实有*一些*影响。但它不会改变所用的布局算法。）

### 布局算法的变体

有些布局算法分为多个*变体*。

例如，我们说定位布局时，它指的是几种不同的“定位方案”：

* Relative（相对定位）
* Absolute（绝对定位）
* Fixed（固定定位）
* Sticky（粘性定位）

每种变体有点像一个独立的小布局算法，不过它们确实有共同之处（例如都可以使用 `z-index` 属性）。

同样，在 Flow 布局中，元素可以是块级或行内的。稍后我们会详细讨论 Flow 布局。

### 冲突

如果一个元素同时应用了多种布局算法，会发生什么？

例如：

```
<style>
  .row {
    display: flex;
  }

  .primary.item {
    position: absolute;
  }
</style>

<ul class="row">
  <li class="item"></li>
  <li class="primary item"></li>
  <li class="item"></li>
</ul>
```

三个列表项都是 Flex 容器内的子元素，所以它们本应按 Flexbox 定位。但中间那个子元素通过设置 `position: absolute` 选择了定位布局。

据我理解，一个元素会用一种主要布局模式来渲染。这有点像选择器优先级：某些布局模式的优先级高于其他模式。

我不知道确切的层级关系，但定位布局往往压倒一切。所以在这个例子中，中间的子元素会使用定位布局，而不是 Flexbox。

结果是，Flexbox 的计算会表现得好像只有*两个*子元素，而不是三个。对 Flexbox 算法而言，中间那个子元素并不存在。（实际情况比这更复杂一些；Flex 父元素的绝对定位子元素有时仍然可以使用 Flexbox 属性。但在实践中，这种冲突很少见。）

一般来说，冲突通常是相当明显的、有意为之的。但如果你发现某个元素的表现不符合预期，不妨试着识别它在用哪种布局算法。答案可能会让你吃惊！

## 行内魔法空白

好了，来看一个经典的“令人困惑的 CSS”问题，看看关注布局算法如何帮我们解决它。

这里有一篮子猫：

（代码演示）

```
<div class="photo-wrapper">
  <img
    class="cat-photo"
    alt="一篮子猫"
    src="/images/cats.jpg"
  />
</div>
```

嗯……为什么图片下方多了一点空间？

如果用开发者工具检查，你会发现有几个像素的差异：

图片高 250px，但容器高 258.5px！

如果你熟悉盒模型，就知道元素之间可以用 padding、border 和 margin 来留出间距。你可能会以为图片上有 margin，或者容器上有 padding？

在这个例子里，**这些属性都不是罪魁祸首。** 正因为如此，多年来我私下一直把它叫作“行内魔法空白”。它不是由那些常见嫌疑人造成的。

要理解这里发生了什么，我们需要更深入地挖掘 Flow 布局。

### Flow 布局

如前所述，Flow 布局是为文档设计的，类似于文字处理软件。

文档具有以下结构：

* 单个字符组合成单词和句子。这些元素*行内*排列，一个挨一个，水平空间不够时换行。
* 段落被视为*块*，标题或图片也一样。块会从上到下、一个叠一个地纵向堆叠。

Flow 布局就基于这种结构。单个元素可以作为行内元素排列（并排，就像段落中的单词），也可以作为块级元素排列（从上到下堆叠的大砖块）。

大多数 HTML 元素都有合理的默认值。`<p>` 和 `<h1>` 被视为块级元素，而 `<span>` 和 `<strong>` 被视为行内元素。

行内元素本意是用在段落中间，而不是作为布局的一部分。比如，我们可能想在句子中间加一个小图标。

为了确保行内元素不会对周围文字的可读性产生负面影响，算法会加上一点*额外的垂直空间*。

回到我们的谜团：为什么图片会多出几个像素的空间？**因为图片默认是行内元素！**

Flow 布局算法把这张图片当作段落中的一个字符，在下方加了一点空间，以确保它不会和（理论上的）下一行文字的字符挨得太近，令人不适。

默认情况下，行内元素按“基线”对齐。这意味着图片的底部会与文字所在的那条看不见的水平线对齐。这就是图片下方有一些空间的原因——那是留给下伸部分的空间，比如字母 `j` 和 `p` 的下半截。

所以它不是 margin，不是 padding，也不是 border……而是 Flow 布局给行内元素加的那一点固有空间。

### 解决问题

解决这个问题有好几种方法。也许最简单的是在 Flow 布局中把这张图片当作块：

（代码演示）

```
<style>
  .cat-photo {
    display: block;
  }
</style>

<div class="photo-wrapper">
  <img
    class="cat-photo"
    alt="一篮子猫"
    src="/images/cats.jpg"
  />
</div>
```

在我的职业生涯中，行内魔法空白坑过我很多次，所以我把这个修复方法写进了我的[自定义 CSS Reset](https://www.joshwcomeau.com/css/custom-css-reset/)。

另外，由于这种行为是 Flow 布局独有的，我们也可以切换到另一种布局算法：

（代码演示）

```
<style>
  /*
    我们把它的*父元素*改为 Flex，
    这样子元素就会使用
    Flexbox 而不是 Flow：
  */
  .photo-wrapper {
    display: flex;
  }
</style>

<div class="photo-wrapper">
  <img
    class="cat-photo"
    alt="一篮子猫"
    src="/images/cats.jpg"
  />
</div>
```

最后，我们还可以用 `line-height` 把额外空间缩小到 0 来解决：

（代码演示）

```
<style>
  .photo-wrapper {
    line-height: 0;
  }
</style>

<div class="photo-wrapper">
  <img
    class="cat-photo"
    alt="一篮子猫"
    src="/images/cats.jpg"
  />
</div>
```

这个方案通过设为 0 去掉了所有额外的行间距。这会让多行文字完全无法阅读，但由于这个容器里没有文字，所以不成问题。

我建议使用前两种方案之一。介绍这一种纯粹是因为它很有意思（也因为它证明了问题出在行间距上！）。

## 建立直觉

**所以，要点是：**如果你只专注于研究具体 CSS 属性做什么，你永远不会明白这块神秘的空间从何而来。`display` 或 `line-height` 的 MDN 页面里都没有解释它。

正如我们在本文中学到的，“行内魔法空白”其实根本不是魔法。它是由 Flow 布局算法中的一条规则造成的：行内元素应受 `line-height` 影响。但多年来它在我看来*显得*很神奇，因为我的心智模型中有一个大窟窿。

CSS 中有*很多*布局算法，它们都有各自的怪癖和隐藏机制。当我们只关注 CSS 属性时，看到的只是冰山一角。我们永远学不到层叠上下文（stacking context）、包含块（containing block）或层叠来源（cascade origin）这些真正重要的概念！

遗憾的是，网上很多 CSS 教学同样浅薄。博文或推文经常分享一段好用的 CSS 片段，却不解释它*为什么*有效，或者布局算法如何使用它。（我得承认，我自己也犯过这个错！在社交媒体上分享 CSS 技巧时，篇幅根本不够提供所需的全部背景。）

CSS 是一门很难调试的语言：我们没有错误信息，没有 `debugger`，也没有 `console.log`。直觉是我们手里最好的工具。而当我们开始使用自己并未*真正*理解的 CSS 片段时，布局算法中某个隐藏的方面迟早会给我们的齿轮里卡进一把扳手，让我们寸步难行。

几年前，我决定开始培养自己对 CSS 的直觉。每当被某个意外行为打乱节奏，我就像泡进温水澡一样沉浸到问题里。我会深挖 MDN 文档和 CSSWG 规范，反复摆弄代码，直到觉得真正弄明白了发生了什么。

这绝对是一笔值得的投资，但天哪，它花了*太久*了。😅
