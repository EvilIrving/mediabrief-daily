实用循环工程（Practical Loop Engineering） ｜ Addy Osmani ｜ 文章 ｜ https://addyosmani.com/blog/practical-loop-engineering/

Google 工程师 Addy Osmani 分享他日常怎样用"循环"驱动编程 agent。他通常同时开五到十个 agent：有明确停止条件和约束的任务就完全放手，复杂或敏感的任务（碰到认证、安全、财务）就盯紧并审代码。

他先回顾背景：所谓循环，是 agent 反复行动、检查结果、调整做法，直到达成目标的自我纠错过程。早期大家靠手写 bash 循环，比如 Geoff Huntley 的 Ralph loop，主要在个人项目上试；现在 Claude Code 和 Codex 已经把它做成了原生功能，可以比较放心地依赖，但目标和约束没想清楚就放任它跑，照样会把代码库带进糟糕的状态，没有历史包袱的新项目和银行那样的老代码库要区别对待。他引用 Claude Code 团队对循环的分类：每次发提示本身就是人主导的循环；/goal 是目标驱动的循环，定义好"完成"的标准后，每当 agent 想停，就由一个评估模型检查条件是否满足，不满足就打回去继续，所以通过的测试数、分数门槛这类确定性的标准最有效；/loop 是按时间触发的循环，像 cron 一样定期重跑同一个提示，适合轮询日志、盯 PR 和 CI，搬到云端则用 /schedule；最高一级是主动循环，由事件或日程触发、无人实时参与，适合 bug 报告、问题分拣、依赖升级这类源源不断的明确工作，例行任务交给小模型，需要判断的再用最强的模型。他还照搬了团队的一份前端验证 skill：改完界面必须真的启动服务、点一遍、看控制台、跑性能检查，任何一步失败就从头再来。

他用 goal 把一件事做到"可证明完成"，比如把页面加载压到五秒内、处理完最近十个 issue，效果时好时坏，关键在实验。他强调两条习惯：一是做事的 agent 不能自己判定做得好，要由另一个子 agent 验证，因为前者可能只在桌面端测了性能，而你真正关心的是手机；二是只委托任务，不委托判断。他讲了自己差点栽跟头的经历：让 agent 调研竞品、在本地写出补齐差距的 PR，他读了调研却没细看实现，差点推上去，后来才发现这些改动会给用户带来大量复杂度，收益却很小。他还提醒，goal 背后的评估器并不判断内容好坏，只看对话记录里有没有满足你写下的硬性规则。

他每天跑的流程是给自己 8 万星的开源仓库 Agent Skills 做分拣：以前一天要看八九十个 PR，现在用 loop 每隔几小时汇总新 issue 的紧急程度、做第一轮审查，还可以把两者组合起来：loop 每天检查有没有标了 bug 的 issue，有就用 goal 修到本地测试全过再推分支。这套系统最大的价值是交叉对照，比如准备重做某块系统时，能把相关 issue 一并关掉。他的建议是：如果你每天早上都在手动做某项检查，那就是你的第一个循环。
