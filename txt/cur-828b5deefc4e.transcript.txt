小而专注的模块

做小而专注的模块，是为了可复用，也为了能够构建更大、更高级、同时更易于理解的东西。

这原本是我在 AMA（有问必答）里对"为什么你写这么小的 Node.js 模块"这个问题的回答。我的回答适用于 Node.js，在你的平台上可能不适用。这种做法在 Node.js 上效果之所以这么好，是因为它可以有嵌套依赖，所以依赖之间永远不会冲突。

人们太容易纠结于代码行数（LOC）了。代码行数基本无关紧要。一个模块是一行还是几百行并不重要，关键在于把复杂性封装起来。把 Node 模块想象成乐高积木。你不一定关心它是怎么做出来的，只需要知道怎么用这些积木搭出你的乐高城堡。通过编写小而专注的模块，你可以轻松构建庞大复杂的系统，而不必了解所有东西运作的每一个细节。我们的短期记忆是有限的。此外，把这些模块做成可复用的包，别人也能复用它们；当一个模块被改进或修复了 bug，所有使用者都会受益。

想象一下，如果每家电脑厂商都自己造 CPU，大多数都会造得很差，电脑会更贵，创新也会更慢。相反，大多数厂商用的是 Intel、ARM 等的芯片。

如果不是 npm 的运作方式，这一切都不可能实现。能使用嵌套依赖的美妙之处在于，我不必关心我用的某个依赖自己又有哪些依赖。这非常强大。

几年前，在 Node.js 和 npm 出现之前，我有一个很大的代码片段库，需要时就把片段复制粘贴进项目里。那些是偶尔派得上用场的小工具。现在 npm 就是我的代码片段库。既然可以导入，而且还能让意图更清晰，为什么要复制粘贴呢？修复一个片段里的 bug，只需要更新一个模块，而不用手动修复所有用到这个片段的地方。

举个例子，chalk 是 npm 上最受欢迎的模块之一。你可能没意识到，它其实是一组模块的集合。它依赖一个模块来检测终端是否支持颜色，依赖另一个模块来获取 ANSI 转义码，等等。这些本来都可以直接嵌在主模块里，很多情况下大概也确实是这样做的。但那样的话，任何想做另一个终端字符串样式模块的人，都得把所有轮子重新造一遍。有了这些支撑模块，别人就能轻松地从我们在 chalk 上的工作中受益，甚至可能通过改进其中某个依赖来间接帮助改进 chalk。

再举一个例子。我有个模块叫 user-home，用来获取用户的主目录。你可能觉得直接写 process.platform === 'win32' ? process.env.USERPROFILE : process.env.HOME 更简单，大多数人也确实是这么写的。但首先，为什么要求每个人都知道怎么获取主目录？为什么不用一块"乐高积木"呢？你可能还没意识到的是，这个判断是不完整的。在 Windows 上，你还应该检查 process.env.HOMEDRIVE + process.env.HOMEPATH，而且可能还想做一些额外的检查。乐高积木。（Node.js 现在其实已经为此提供了 API，正是出于上述原因。）

你会自己做鞋吗？不会，你在商店里买鞋。大多数人并不关心鞋是怎么做的，只关心它合不合脚。

我希望编程变得更容易，让构建耐用的系统变得更容易。在我看来，前进的道路绝对不是每个人都把一切重新发明一遍，一次又一次地犯同样的愚蠢错误。
