多发一点 CSS 来提升网站性能

作者：Josh Black。Josh Black 是一名常驻得克萨斯州奥斯汀的软件工程师，喜欢做设计系统、打造无障碍体验，也喜欢吃墨西哥玉米片（chilaquiles）。

我们是如何把 github.com 彻底迁离 CSS-in-JS 的。（阅读时间约 8 分钟）

Primer 设计系统支撑着你今天在 GitHub 上看到的许多体验。从按钮、横幅到面包屑导航，这些基础组件必须在各种各样的场景下做到无障碍、灵活且高性能。

早在 2023 年，某些页面上的组件数量开始激增。这让我们当时的 CSS-in-JS 方案遇到了几个性能上的难题：

- 由于样式要在客户端初始化，首次页面加载耗时更长
- 随着样式收集从客户端转移到服务端，服务端渲染性能下降
- 页面上的组件越多，样式更新就越失控

很明显，Primer 团队需要从根源上解决这个问题。我们需要找到一种替代方案，彻底避免当时方案在客户端和服务端带来的开销。最重要的是，无论选哪种替代方案，都必须保证迁移过程中不会把 GitHub 弄坏。

Primer 团队找到了一个满足所有条件的方案：CSS Modules。这种格式让我们能做最喜欢的一件事：编写和使用原生 CSS 特性，同时仍保留一定程度上我们已经习惯了的、CSS-in-JS 带来的就近放置和封装。

使用 CSS Modules，样式写在组件 JavaScript 源码旁边的 CSS 文件里。它还让所有类名默认都是局部的，避免了全局选择器带来的一些冲突和麻烦。这种格式也完全不需要任何客户端或服务端的运行时行为，样式会汇总成 CSS 样式表，作为页面 HTML 的一部分发送出去。

然而，这个方案和我们当时的 CSS-in-JS 方案截然不同。这一改变需要更新每一个 Primer 组件，以及 GitHub 中每一个用这种方式编写的组件。好在设计系统正是大规模交付这类改变的理想载体。

迁移到 CSS Modules 的局面很清楚：Primer 团队需要逐个更新组件，把它们从 CSS-in-JS 改成 CSS Modules。同时，我们对这些组件的改动不能破坏 GitHub 中的任何用法。最后，我们原来用于 CSS-in-JS 的底层技术，还必须对 GitHub 中仍在使用它的组件继续有效。

在这些约束下，我们决定采用渐进式迁移策略，这样就能安全地发布组件更新，而不会"把整个世界弄坏"。对每个组件，我们的计划是：

- 新增一个文件，把现有样式转写为 CSS Modules
- 把该组件加入一个功能开关，在新旧样式之间切换
- 用现有的视觉回归测试，验证 CSS-in-JS 方案和 CSS Modules 的快照完全一致
- 逐步放开功能开关，先给我们团队，再给 GitHub 员工，最后给所有 GitHub 用户，以便在过程中发现问题

随着 Primer 持续向 GitHub 交付这些改动，这个流程形成了一个很强的反馈循环，问题在早期就会被发现。功能开关让我们能安全地完成迁移，同时清楚地看到 CSS Modules 带来的性能收益。

到 2024 年 12 月，Primer 的所有组件都按这个流程迁移到了 CSS Modules。我们看到了全方位的性能提升，特别是：

- 页面服务端渲染时间减少 55%
- 页面上组件初始化时间减少 25%

既然在 Primer 做这项工作带来了明显的性能收益，我们开始思考：在 GitHub 的其他部分做同样的转换，能否看到类似的收益？同样，还要多久，我们才能最终在全公司放弃对 CSS-in-JS 的支持？

从 Primer 中移除 CSS-in-JS 方案，最棘手的部分之一是 sx 属性的使用。这个属性是给 Primer 组件设置样式和做定制的方式，各团队可以传入一个内联对象，定制组件的方方面面。它代表了 CSS-in-JS 最好和最坏的两面：

- 出色的 TypeScript 支持，并与我们的设计令牌（Design Tokens）集成
- 和组件放在一起，所有东西都在一个地方
- 由于 sx 使用的内联对象是动态的，运行时开销很高
- 页面上使用 sx 的组件越多，就越难扩展

因此，我们摆脱 CSS-in-JS 之旅的第一步，是减少整个 GitHub 中 sx 的使用。这能立刻带来类似迁移 Primer 组件时的性能提升，也为彻底从产品中移除 CSS-in-JS 做好了准备。

需要指出的是，虽然设计系统本身已经正式摆脱了 styled-components，但 GitHub 代码库的很大一部分并没有。多年来 sx 属性一直是 GitHub 事实上的样式标准，在我们能考虑让 GitHub 用上不依赖 styled-components 的崭新 @primer/react 版本之前，有成千上万个 sx 属性需要迁移。

那么……我们是怎样在提高信心、降低风险的同时完成如此庞大的工作量的？答案是：不一次性做完。

最初的 CSS 迁移其实比我们前面说的要复杂一点：除了把组件迁移到 CSS Modules、用功能开关在生产环境中测试并慢慢放量，我们还在一个过渡性的库 @primer/styled-react 中创建了"包装"组件。这个包唯一的目的，就是让新迁移的组件仍然能使用 sx。这样，GitHub 界面代码库中使用这个属性的地方，可以通过 @primer/styled-react 导入同一个组件继续使用；而不需要 sx 的地方则直接从 @primer/react 导入，享受性能收益。

迁移的下一阶段如下：

- 按包逐个进行：
  - 把所有 sx 用法转写成等价的 CSS Modules 文件，包括交叉对照（参见"迁移到 CSS 变量"）
  - 把 @primer/styled-react 的导入替换为 @primer/react 的导入
  - 在预生产环境中测试
  - 部署

有意思的是，正当我们准备开展这项浩大的工作时，styled-components 宣布进入维护模式，进一步证明我们走在正确的方向上。

这项工作于 2025 年 4 月启动，待迁移的 sx 属性最多时约有 7760 个；直到 2026 年 5 月才全部完成。起初，我们一位很棒的内部开发者 Ian Sanders 做了一个 VS Code 插件，辅助逐个属性迁移。内部还开发了一个类似的 codemod，用来迁移 GitHub 代码库中的整个文件。这项工作虽然需要一些人工把关和仔细验证，但大部分是自动化的。8 名工程师轮班，在 6 个月里迁移了 6419 个属性，部分页面的服务端渲染时间提升了 1% 到 22%。

在 GitHub 的另一边，Copilot 的能力正呈指数级增长。AI 变得更聪明、更能干；在这项工作仍在进行时，我们发布了 Copilot 编程 agent 和 Copilot 代码审查。

等我们在 2026 年 4 月重新捡起这项工作时，局面已经不同了：一个两名工程师的小组，凭着坚持不懈的决心和一大批 Copilot 编程 agent，在三周内把 sx 属性从 895 个降到了 0 个。

那是个重要的日子：我们终于完成了横在我们和彻底移除 styled-components 之间、酝酿多年的 sx 迁移……现在终于可以清理掉这些依赖，去做别的更激动人心的工作了，对吧？错！

GitHub 支持七种不同的主题，每一种都有高对比度模式的变体。而这一切，你猜对了，都是通过 styled-components 实现的。在考虑移除这些依赖之前，我们得先把主题功能解耦出来。

其实这并不像听起来那么严重。我们的主题变量一直是在 CSS 中、通过 @primer/css 包定义的，而且我们在 2025 年底迁移 @primer/react 时已经为不依赖 styled 的主题做好了规划。需要移除的是 styled-components 支撑的那些 JavaScript 用法和工具函数。于是，我们又一次开工了。

流程你已经熟悉了：执行迁移，慢慢放量，所有东西都加功能开关。两个月、几次小波折之后，我们一切就绪，可以移除依赖了；连这一步我们也加了功能开关。小心驶得万年船。

自 2026 年 6 月起，GitHub 已经 100% 运行在 CSS Modules 上。我们设置的种种保障措施，让我们能安全地推出重大的架构变更，在生产环境中做压力测试、发现错误、高效地调整和修复，最终实现目标，并一路收获可观的性能提升。

起初看起来只是一次 CSS 迁移，结果却变成了对 GitHub 如何大规模编写样式、实现主题和交付界面的一次渐进式平台重建。最终，我们不仅从 github.com 移除了 sx、styled-components 和 styled-system，而且整个过程中没有把 GitHub 弄坏。提升产品的性能、用户体验和愉悦感，始终是我们 GitHub 所有人最关心的事。
