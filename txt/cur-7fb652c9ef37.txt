扩展 Slack 与 GitHub：瓶颈不只在代码里 ｜ The Pragmatic Engineer Podcast ｜ 78分32秒 ｜ https://newsletter.pragmaticengineer.com/p/scaling-slack-and-github-with-maude

Maude Lemaire 在 Slack 工作近八年，后来进入 GitHub 解决数据库扩展问题，又在 Cursor 优化首个可见 token 的响应时间。她和主持人 Gergely Orosz 谈的不是一种通用的扩容配方，而是如何把产品的真实使用方式、数据库访问、消息分发和客户端体验连起来，找到整个系统真正需要改变的地方。

她父亲教过十七年计算机科学，家里留着她还是婴儿时坐在电脑前、拿着 ASCII 表的照片，但她起初认为计算机很无聊，打算研究遗传学。进入麦吉尔大学后，她选了微生物学、分子生物学和有机化学，还凭 AP 学分提前推进学业。几周后，她发现自己混淆了“擅长记忆”和“喜欢记忆”。为了转向化学工程，她先选了一门编程入门课，甚至叮嘱母亲别告诉父亲，免得自己不喜欢这门课，让深爱计算机的父亲失望。结果，她很快喜欢上了只用一台电脑、输入指令就能让事情发生的感觉。

她实习后回到 Rent the Runway，是因为那里把编程和时尚这两种兴趣结合起来，也因为她想向当时的技术负责人 Camille Fournier 学习。团队里有很多女性，Camille 的存在感和自信让她非常敬佩。Camille 在她正式回去后不久离开了公司，但一年后又帮助她进入 Slack。

2016 年的 Slack 虽然已经很受欢迎，架构却还难以支撑特别大的组织。Gergely 回忆，Uber 在 HipChat 泄露事件后评估过 Slack，但当时 Slack 无法支持四五万人聚集在同一空间，Uber 最终基于 Mattermost 做了 UChat。Maude 入职时，先跟着资深同事修复性能问题：初创公司为了获得下一个客户、推出下一个功能，会做明知以后需要重访的权衡。随着企业产品上线、IBM 开始大规模增加用户，这些历史上的捷径集中显露出来，公司专门建立了企业性能团队，她成了其中最初级的成员。她很喜欢这种位置，因为它迫使自己不断向更有经验的人学习。

早期 Slack 把公司或工作区作为数据库分片单位。一家公司的数据集中在一个分片，客户变大，就换更大的数据库，直到达到云厂商能提供的最大规格。WebSocket 消息服务器也按公司关联，整个公司的聊天活动会集中到同一服务器。企业版试图把大公司拆成多个小工作区，让营销、工程等部门各自成为一个“团队”，再用企业层实体把它们串起来。问题是，跨团队私信和全公司频道仍然需要共享上层空间，IBM 所有人会同时访问企业分片，原本以为拆小就能解决的负载又聚集了回来。

频道成员关系的数据结构也体现了产品成长的历史。公开频道、私信和私有频道各有一张表，后来出现的群组私信又塞进私有频道表。填充左侧栏和计算提及数量，需要跨表联合查询；这些操作对延迟十分敏感，局部调优已经走到了尽头，最终必须把成员关系迁到统一的表中。

迁移困难不仅在数据库，还在调用方式。Slack 当时的 PHP 代码非常过程化，SQL 直接写在大量 API 实现中，没有 ORM，也没有统一的数据访问层。团队担心抽象会隐藏昂贵查询，因此 Maude 没有一开始就引入复杂框架，而是找到四百多个调用位置，把原有 SQL 原封不动搬进命名明确的函数，先建立最薄的一层边界，再在边界内改变实现。整个过程配合大量功能开关、双写、历史数据回填和影子读取：仍返回旧表结果，同时读取新表，比较差异，确认一致后再切换。

即使这样，她也犯过错误。一次准备让 Slack 内部工作区读新表时，她看到数据差异，沿用测试期间“清掉新表数据再回填”的习惯，却忘了读开关还开着。内部同事的侧栏因此一片空白，回填大约需要二十五分钟。幸好旧表仍在，她可以先切回旧数据，再完成回填、重新切换。这里出问题的是内部工作区，不是所有外部客户的数据丢失。

接下来，Slack 要迎接一个预计五十万用户的大客户，原有十八个月的准备安排又因疫情被提前。Maude 认为，负载测试的第一步不是随意增加请求，而是明确产品会以什么方式失控。Slack 面临的两类典型问题是惊群和事件洪泛。

惊群是大量用户同时做同一件事。例如 CEO 在十万人频道宣布“周五放假”，通知让所有人几乎同时打开频道、读取历史，再加上自定义表情。一条消息先向十万人分发，每个表情反应也要再向所有在线用户分发；即便只有十个反应，消息量也会迅速膨胀。Slack 因此给 WebSocket 消息分优先级，负载很高时保住文字消息、丢弃表情事件。这个取舍本质上也是产品决策：工程师可以指出必须舍弃某些东西，但什么最重要，需要从用户体验出发判断。

她提到，每条消息可以有二十三种不同的自定义表情反应，但每种反应的追加人数没有同样的总量限制。她质疑第一万零一个赞究竟提供了多少价值，认为可以考虑直接截断计数或数量。困难还在组织上：自定义表情已融入整个 Slack 体验，却未必有明确的人负责决定合理上限。

事件洪泛则着眼于单个客户端被事件淹没，不必所有用户同时行动。一个人可能恰好加入很多繁忙频道。IBM 的 Jeff Robke 是管理员，加入了大量工作区；在旧架构里，每个工作区各自建立 WebSocket 连接。同一条企业级私信或共享频道消息，可能沿三十多个连接重复送达，没有去重，最终使客户端卡死或崩溃。最常用、最积极推动 Slack 的重度用户，反而承受了最糟糕的体验。

只压测 API 吞吐量和数据库，无法覆盖这样的完整链路。测试必须让五十万个客户端真的保持 WebSocket 连接，才能看到消息抵达之后引发的读取、回应和下游事件。团队曾在 Kubernetes 里启动大量无头 Chrome，让真实 Slack 页面执行脚本。这种办法保真度高，但内存、运维和费用都很难承受：按访谈里的估计，每个实例五小时约花 0.37 美元，一轮大规模测试约十五万美元；而且五小时中很大一部分时间还在恢复崩溃的 pod，并没有真正跑完想测的功能。

替代方案 Koi Pond 放弃完整浏览器，改用轻量 Go 进程模拟客户端。每个客户端建立真实 WebSocket 连接，收发事件，并按真实流程访问普通 API 和边缘缓存。这样不再测试浏览器全部细节，却保住了导致规模问题的关键路径。Maude 强调，这不是一味追求最高保真度，而是结合领域知识，在可控制、可重复、可负担的条件下模拟最重要的失败模式；以后发现新的失败方式，也能比较容易地修改行为。

为了不遗漏一个产品操作背后的调用，她又做了录制工具：用 Slack 命令开始记录，再完成一次实际流程，工具捕获所有普通 API、边缘缓存请求，以及双向 WebSocket 消息，再把需要的部分转成模拟客户端脚本。她希望把工具交给产品经理，让最了解文件、Canvas 等具体功能的人亲自录下使用流程，交给平台团队，以指定频率持续压测。性能和可靠性不是产品发布以后才处理的附加项，而是功能本身的一部分。

2024 年加入 GitHub 时，她面对的是另一种扩展压力：一部分流量仍跑在自有数据中心，团队既要迁往 Azure，也要减少不必要的计算，为有限的机器争取空间。她从 Slack 带来的经验包括使用 Vitess 对 MySQL 做更灵活的分片，把原先按团队放置的数据改按频道 ID 分布。团队可能大到一个分片装不下，频道通常是更小、更适合水平扩展的单位。

然而，当时 GitHub 全站的 pull request 和 issue 数据只有十六个分片。不能直接增加分片，是因为存在大量 scatter query：查询中没有足以定位分片的键，就得向所有分片查询，再汇总结果。她用“查出我创建的所有 pull request”举一个假设例子，并特别说明这未必就是系统中的真实散射查询。分片越多，这种查询的扇出越大；但不增加分片，每个分片又承受越来越重的负担。

她原以为可以沿用老办法，逐个消灭 scatter query，却发现 Rails 单体和 Active Record 把底层访问藏得很深。团队试着将某些业务域迁出单体，例如把 stars 相关逻辑抽到 Go 子系统。她和熟悉 Rails 的同事追到一个只有五行的函数，仍很难看出 SQL 到底在哪里生成。与能直观看到查询结构的手写 SQL、甚至 Prisma 相比，这种抽象让开发者很容易在不知道代价的情况下增加一行代码，也让后来修复访问路径变得困难。

GitHub 内部有工具显示一个页面运行了哪些 SQL、命中了哪些集群。她离开前看到，仓库首页一次加载能触发一百多条 MySQL 查询，跨至少三个集群。Active Record 的查询缓存又要求查询完全相同，已有用户查询结果，不代表加上另一项条件的查询就会复用。页面上许多计数仍实时计算。她再次提出产品问题：小仓库有三个待处理 PR，精确数字也许重要；但超过九十九以后，是否只显示“99+”就够了，而不必每次精确计数？

谈到 AI，她并不否认它能加快已确定方案的实现，却认为它对性能调查帮助有限。Cursor 的首个可见 token 延迟并不只是模型推理速度，还包括提示词提交后的上下文组装、缓存、推理代理，以及客户端与后端的流式通信。能缓存什么，受产品、隐私、负载和成本约束，不可能把所有请求都在 Redis 存二十四小时。HTTP/2 下的 gRPC 连接又承载多个并发流，直观体验与真实的同步、异步关系并不一致。

AI 能做基础埋点，却未必知道异步系统应该怎样观测。Cursor 既有包含数百万个 span、几乎无法分析的 trace，也有为省成本在多个位置分别采样而造成的问题。Maude 亲自读代码、重新梳理流程，要求采样在统一位置进行。她也让模型生成完整时序图，再去 Staples 打成大幅蓝图，一边读代码一边标注哪些关系正确、哪些工作必须先完成、哪些地方可以优化。

模型提出的常见建议是并行化互不依赖的任务，但并行未必解决产品的真实问题。一次模型兴奋地提出把四项任务并行，实际最长的那项仍远慢于其他三项，而只有约 1% 的用户需要另外三项；无条件做完所有工作，只会浪费资源、增加负载。真正有用的改动，反而可能是合理延长部分 Redis 数据的 TTL。对测试也类似：模型经常只写出确认自己实现正确的测试，她用变异测试故意改变代码，迫使模型发现没覆盖到的边界情况。

她仍然整天和 LLM 交流，用它做初步探索、处理日常小问题，但重要结论要手工验证。产品平台的目标是建立能承载未来开发的基础；只打好八成地基，剩下两成会拖累整栋房子，后续还会继续向外加建。AI 很擅长照着附近的例子追加实现，却不一定追问二十层之外的根本假设。她的工作恰恰是不断问：为什么要这样做？这个功能是否应该建在地基以外？

对于想进入平台领域的工程师，她最鼓励产品与平台团队之间的双向流动。很多优秀的平台工程师，最初是在产品开发中重复实现同一类问题两三次，受不了重复劳动，于是想把它一次性解决、做成供大家使用的能力。但留在平台太久，又容易脱离产品开发的真实压力。因此可以保留维护核心系统的固定成员，同时让产品工程师轮岗进入平台，也让平台工程师回产品团队实现功能，理解他们为什么快速发布、正在用哪些新工具。

在 AI 让代码更容易生成的环境里，平台护栏需要比过去更强：允许产品团队快速尝试，同时及时阻止或警告危险操作。她把过去的意大利面条式代码比作还能由人努力留在盘子里的面条，而现在面条像有了自己的生命，主动想往外跑。平台团队需要更主动地检验自己的系统，才能在开发速度提高时，仍交付可靠、有质量的体验。
