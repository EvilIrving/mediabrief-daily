TypeScript 编译器正经历由 JavaScript/Node.js 实现向 Go 原生重写的重大架构演进：TypeScript 7 核心团队通过逐行移植与共享内存并行将代码库性能提升近 10 倍，并围绕语言无关的进程间通信（IPC）重构了类型检查 API 边界。微软 TypeScript 首席产品经理 Daniel Rosenwasser 在访谈中详述了从 TypeScript 1.0 至今的演进历程、Go 原生版 7.0 与 7.1 API 设计，以及大模型时代类型系统设计的核心权衡。

Daniel 少年时在游戏论坛上发现一群青少年自己运营网站，由此从 HTML、QBasic、PHP 和 LAMP 栈一路学到编译器和程序语言理论课，认定自己要做开发者工具。他实习时被分到 Azure，后进入 TypeScript 团队。他认为做开发者工具的核心心态是共情：自己踩过的坑最清楚，例如曾专门为旧版 Visual Studio 补做一层语法着色，以消除开发者的挫败感；早年社区对微软开源缺乏信任，团队依靠长期坚持透明原则与技术自洽赢得认可。

谈到 TypeScript 与 JavaScript 的关系，Daniel 解释 TypeScript 本质上是“带类型语法和强大工具的 JavaScript”，其演进难点在于底层宿主语言具有独立的标准化轨道。早期 TypeScript 在 class 和模块规范正式标准化之前先行实现，导致用户在后续规范落地时经历多次迁移阵痛。装饰器是典型案例：2014 年前后 Flow 推出、Angular 团队提出 AtScript，TypeScript 团队与谷歌合作将装饰器推入 TC39，但提案后续在语义和 API 上均遭彻底重构。这段教训促成了团队延续至今的原则：JavaScript 特性必须推进至 Stage 3 阶段才会在 TypeScript 中正式实现，自家专属新增语法严格受限于“可擦除语法”，即剥除类型注解后必须直接还原为等价可读的现代 JavaScript；对于超出类型范畴的语言诉求，团队则转为在 TC39 内部担任推动者，可选链与空值合并即为该策略的标杆成果。

TypeScript 7 采用 Go 语言进行逐行移植，配合共享内存并行架构，在大型代码库上将编译速度提升了近 10 倍，并消除了单线程架构在超大型项目中频繁触发的内存溢出（OOM）与编辑器数分钟加载延迟。重构的真正难点在于 API 治理：旧版 API 经历十余年自发生长，而 Go 运行时对内存所有权与并发模型具有严格约束。团队最终确立了与宿主语言无关的进程间通信（IPC）协议边界，允许多个客户端共享同一后台项目会话（Session），该 API 将于 7.1 版本正式开放，为 Vue、Angular 等深度依赖嵌入式模板解析的生态工具提供低成本接入，同时也为 Oxlint 等基于 Rust 的新型工具链提供标准化的类型检查消费接口。

在底层设计考量上，选择 Go 语言让团队能够实现与现有算法逻辑近乎一对一的精准迁移，同时享受原生执行速度，且无需将 Go 运行时的内部内存布局泄漏给消费方；宿主工具通过 IPC 按需查询类型数据，避免在跨进程间进行冗余的全量地址空间镜像。关于否定类型（Negation Types）等高级特性的长期争论，Daniel 指出其核心瓶颈并非编译性能而是形式化复杂度：在构造主义逻辑下，unknown 涵盖一切取值，字符串与数字虽然互斥，但将 unknown 赋值给“非数字”在引入对象类型与结构子类型后，会导致数学推导与直觉理解产生剧烈冲突。此外，随着性能重构阶段性收尾，此前为性能让位的字符串字面量拆分等用户体验改进特性将重新进入研发视野。

展望 8.0，Daniel 认为大语言模型正在重塑类型系统的价值权衡：当模型使得编写团队专属的定制化 Lint 规则变得极为廉价时，底层编译器 API 的开放性与稳定性变得更加重要。对于更严格的 this 类型推断与否定类型，每个特性依然遵循“从负分起步”的克制设计原则。当前不依赖遗留编辑器插件的项目已可直接试用 TypeScript 7，并通过早期 IPC 协议与 Webpack 等构建工具集成运行。
