Thoughtworks 杰出工程师、《分布式系统模式》作者 Unmesh Joshi 2026 年 7 月发在 martinfowler.com 上的长文。论点很集中：大语言模型写代码极快，但要把意图写准，需要清晰边界；领域抽象和领域特定语言（DSL）就是从一开始引导模型的安全带。他以自己做的分布式系统框架 Tickloom 为例，说明可以先和模型一起迭代设计 DSL，再用自然语言当接口去使用它；这样的 DSL 甚至能成为 LLM 时代系统的真正"真相来源"。文末感谢 Martin Fowler 和 Rebecca Parsons 的反馈。

他先摆清两个前提。大系统有大量细小设计决策，无法全部写进事先规格——规格最多是待修订的假设（他称为"事先规格不可能"）。设计是在实现里被发现的：审代码很少逼你真正较劲设计决策，写代码才会。语言和范式会塑造你看见什么。因此 LLM 有两个角色：设计词汇时当头脑风暴搭档；词汇稳定后当自然语言接口。

为什么 DSL 特别合拍？PlantUML、Mermaid、Graphviz、SQL、Kubernetes YAML 都是故意收窄的语言，模型用几条上下文示例就能稳定产出正确语法，因为合法写法比 Java 少得多。对自主的 generate-and-check agent 还有一层：DSL 几乎总自带确定性校验器（解析器、JSON Schema、类型检查、编译器），报错还是领域语言（"选客户端之前不能选操作"），而不是深埋在生成代码里的堆栈。代价是设计维护 DSL 本身不便宜，收益集中在真正小而有校验器的 DSL 上。

例子一：他用 LLM 做了一个教学工具——带步骤标记的 PlantUML 加一小段描述幻灯结构的 YAML，自动拆成逐步讲解的 PowerPoint。模型先帮他共同设计这套小 DSL，再当把英文请求变成合法规格的接口。例子二：Tickloom。分布式算法的难点不只是生成代码，更是验证：线程、网络、存储、重试、时钟缠在一起，交错空间大到连 Jepsen 都能在久经考验的系统里挖出 bug。Tickloom 把决策钉死：每个节点跑单线程 tick 循环，按固定顺序处理网络、消息总线、进程、存储，时间用逻辑 tick 而不是毫秒，消息是普通 Java record，副本协调走知道同伴、广播和法定人数的 Replica 基类。于是提示词只需写协议逻辑。一套干净的抽象（Process/Replica、Network、Storage、Clock）本身就已经是轻量版的同一思路，不必非要新语法。

例子三：在语义模型之上再做内部 DSL，描述故障场景。原先用测试套件手写时钟漂移场景，意图淹没在 tick 循环和字节编码里；DSL 写成"服务器、客户端、谁连谁、每步读写、期间有哪些分区/延迟"，非法组合在编译期就失败。自然语言描述（比如复现《数据密集型应用系统设计》里某次不可线性化的法定人数读）几乎直接映射到这套词汇，模型幻觉空间极小，即便写错也会因编译失败而可修。

他总结出两阶段分工：先迭代地设计抽象/DSL（人坐驾驶座）；成型后 LLM 变成自然语言接口。趋势上有人把提示词当主要真相来源，而好的 DSL 会翻转这一点：生成出来的场景本身足够密、可读、少样板，下个月要改就改 DSL 程序，不必考古出原提示词再整段重生成。持久资产不是提示词，而是 DSL 和语义模型。
