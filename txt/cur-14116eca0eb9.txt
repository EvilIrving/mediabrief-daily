"use client" 是做什么的？ What Does "use client" Do? ｜ Overreacted, Dan Abramov ｜ 文章 ｜ https://overreacted.io/what-does-use-client-do/

Dan Abramov 的一篇文章，想把 React 服务端组件里的两条指令讲透：'use client' 和 'use server'。他提出一个大胆的论断：这两条指令的发明，应该和结构化编程的 if/while、一等函数、async/await 归为一类，会比 React 活得更久，最终成为常识。他强调它们其实和 React 无关，关乎的是模块系统。

他的出发点是：服务器要把代码送到客户端，靠的是发一个 <script>；客户端要回头找服务器，靠的是发一次 fetch。这两条指令就是对这两件事的抽象，提供一等的、有类型的、可静态分析的方式，把控制权交给另一台计算机上的代码。他的概括是："'use client' 是有类型的 <script>，'use server' 是有类型的 fetch()。"有了它们，客户端/服务器边界能在模块系统里表达，整个应用可以被当成横跨两台机器的单一程序，同时不忽视网络和序列化的鸿沟。

先讲 'use server'。他用一个点赞功能举例：后端定义 likePost、unlikePost 两个函数并挂到 /api/like、/api/unlike 路由上，前端再用 fetch 去调这些路由。这段代码没毛病，但是"字符串类型"的：我们想做的只是调用另一台电脑上的函数，却只能借 fetch 表达。如果把前后端看作一个程序，最直接的写法就是在前端 import { likePost } from './backend'，这在字面上当然不成立，后端代码不能在前端执行。但只要在后端文件顶部标注 'use server'，把它的导出声明为"可从前端调用"，框架就能在幕后自动建好 HTTP 端点，前端导入得到的就是一个发起 HTTP 调用的异步函数。他承认这不是新想法，RPC 存在了几十年，这只是面向客户端-服务器应用的一种 RPC。他也列出可能的异议：不支持代码库外的多个 API 使用方，要考虑版本和部署，比写 fetch 更隐式。但一旦接受"一个程序跨两台电脑"的视角，就回不去了：两个模块之间有了直接联系，可以加类型收紧契约、用"查找所有引用"看服务器函数在哪被用、用死代码分析清理没用的端点；更重要的是能写出同时封装前后端的自包含抽象，不用担心 API 路由爆炸，也不需要全局命名方案。联系从约定变成了语法，这扇门通向服务器。

再讲 'use client'。反过来，后端要把信息交给前端时，传统做法是渲染一段带 <script> 的 HTML，脚本再给按钮挂上交互逻辑。这样前端逻辑是全局的，没法渲染多个各自带数据和状态的按钮，HTML 模板和事件处理的显示逻辑也是两套。组件库解决了这些问题，于是改成一个声明式的 LikeButton 组件；先退回纯客户端渲染，服务器只负责在页面里用 JSON.stringify 塞进初始 props，这其实正是客户端路由出现前 React 接入服务端渲染应用的方式。可他指出这里又出现了字符串类型的传递：我们真正想说的是"让浏览器加载 frontend.js，找到 LikeButton，把这些数据传给它"。那就直接这么写：后端 import { LikeButton } from './frontend'，在 JSX 里渲染它，而前端文件标注 'use client'，声明它的导出"可从后端渲染"。后端导入得到的不是函数本身，而是一个客户端引用，比如 "/src/frontend.js#LikeButton"。JSX 序列化成 JSON 时，这个引用连同 props 一起写进去，框架据此生成从正确文件加载代码、调用正确函数的 <script> 标签；同样的信息还足以在服务器上先跑一遍组件、预生成初始 HTML，补回纯客户端渲染失去的东西，这一步是可选的，但用的是同一套原语。于是发送 <script> 的那部分程序和住在 <script> 里的那部分程序之间也有了直接联系，能做类型检查、能查引用，所有工具都看得见。

他的结论是"两个世界，两扇门"。这两条指令不该被理解为把代码"标记"成在客户端或在服务器上运行，它们的作用是在两个环境之间开门：'use client' 把客户端函数导出给服务器，服务器把它们当引用、渲染成 JSX 标签，最终变成 <script>；'use server' 把服务器函数导出给客户端，客户端把它们当成走 HTTP 的异步函数。两个环境不共享执行上下文，所以两种 import 都不执行任何代码，只让一端能引用另一端的代码并传信息过去。借此你可以用来自两端的逻辑编织、组合出可复用的抽象。他认为这个模式的意义超出 React 乃至 JavaScript：本质上就是模块系统层面的 RPC，外加一个向客户端发送更多代码的镜像孪生。服务器和客户端是同一个程序被时间和空间隔开的两端，指令为它们打开了门，而 import 是表达这种联系最直接的方式。
