也许我们不该审查所有这些代码 Maybe We Shouldn't Be Reviewing All This Code ｜ Martin Fowler ｜ 文章 ｜ https://martinfowler.com/rachels-ramblings/code-review.html

Thoughtworks CTO Rachel Laycock 在 Martin Fowler 网站专栏里的一篇回应文章。她最近在 Moderne 主办的 Code Remix 大会上和 DX 的 Brian Houck 同台，两人观点相左，Brian 随后写了《代码审查到底是为了什么？》，她写这篇来回应。她的副标题点明立场：问题也许不是 AI 搞坏了代码审查，而是我们一直在用代码审查解决错误的问题。

分歧的背景是 AI 产出的代码已经多到人审不过来：据报道 Meta 每个人工合入的 diff 里的有效代码行数一年增长了 106%，DX 的数据显示 PR 规模中位数增长了 64%。Brian 担心简单地把审查自动化掉，会丢掉审查承担的其他功能：团队分享知识、带新人、建立集体所有权、传播架构理解。她也认同这些都重要，但反问：为什么要等到代码审查时才做这些事？她一向不喜欢把 PR 当成开发流程的中心，因为那意味着先做完、打包、扔给别人，然后才讨论有没有用对的方式做对的事，更别提合并冲突浪费的时间。

她的主张是"把判断左移"，这是她在 Thoughtworks 早年学到的缩短反馈回路：有价值的反馈不要删掉，而是挪到它所服务的决策旁边。想比较不同方案，就在实现前比较；想传递知识，就结对编程，旁观别人推理比事后读成品学得多；想让新人学到资深工程师怎么思考，就让他们在思考的当下一起工作，或者在写代码（或让 agent 写）之前全队围着白板做设计；想要集体所有权，就让大家一起构建和运维，用结对、群体编程；想要架构一致，就一起设计，再把重要约束写成适应度函数；格式、lint、已知安全问题和能确定性测试的东西则全部自动化，"2026 年了不该还在争空格"。结对编程、主干开发、自动化测试、静态分析、适应度函数和安全扫描都把反馈提前，agent 也能参与这些回路，但真正的思考来自有经验的人。

这不是说永远不审代码，而是"例外审查"：根本性的架构变更、跨越敏感安全边界、影响面巨大、关键系统里不熟悉的部分，或者团队自己说"我对这个没把握"时，才需要另一位资深的人来看。这和"每个改动都要有人检查"的仪式完全不同。如果 agent 能产出十倍代码，但每一行最后都排队等资深工程师看，你得到的不是十倍效率的组织，而是一大堆积压和新瓶颈；让 AI 假扮人类审查者、以更快速度维持同一套流程，也只是在自动化仪式，而不是追问仪式为何存在。

她认同 Brian 担心的"认知债"和"意图债"：软件越长越大，负责它的人却越来越不懂它为何这样运作。但她认为强制 PR 并不是有力的防线，agent 写的实现越多，越需要刻意通过协作设计、结对、良好的边界、可执行的架构、共担运维职责，以及一些还没发明出来的实践来维持人的理解，"工程师需要理解系统，而不是 diff"。她的结论是 AI 暴露了一个问题：我们多年来把质量关卡、安全检查、架构评审、带教机制、知识共享、所有权模型统统压在了小小的代码审查上，在人写代码速度有限时还勉强行得通；这个约束正在消失，所以该问的也许不是怎么审得更快，而是为什么要等到代码审查才进行那些重要的对话。
