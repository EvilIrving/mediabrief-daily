Woowa Brothers 的 AI 治理，装进平台

Woowa Brothers 一直运营 AI Gateway，让多家供应商的 LLM 能以相同方式调用。起初，主要是需要替代模型、对接 Langfuse（记录并查看 LLM 调用追踪的工具）和汇总成本的课题，或者为概念验证（PoC）而使用公共凭证的课题在使用它。但随着使用 AI 的课题增多，Agent 开始反复调用 LLM 和工具，仅支持模型调用已经不够了。还需要一并管理谁为了什么目的使用 AI、用了多少、允许用到什么程度。

本文分享把 AI Gateway 扩展为全公司共同调用路径，并把申请、审核、批准流程做进自研 AI Studio 的经验。也会谈到如何通过 AI Gateway 和 AI Studio 管理成本与安全、如何把这一结构应用到 Agent，以及如何保护平台本身。

引言

使用增长，成本和安全隐患也会一起增长

从最初引入 LLM 开始，公司内的 AI 使用量就持续增长；随着 Agent 增多，课题和调用数量增长得更快。使用增长时，有些东西也会一起增长。

一是成本。虽然能看到总成本，但很难说明每个课题用了多少、为什么增加。另一个是安全风险。敏感信息可能流向外部供应商，同一个密钥被多处共用的情形也出现了。当更多团队创建 Agent 并连接公司内部工具和数据后，等问题发生后再去找哪个 Agent 由谁负责，就已经晚了。

但也不能禁止使用 AI。禁止使用虽然能降低成本和安全隐患，但 AI 带来的成果也会一起消失。因此选择的方向是：继续扩大使用，同时把成本和安全控制在规定范围内。

左图是禁止使用时的情形。成本和安全风险维持在较低水平，但使用也不会增长。右图是扩大使用并同步管理的情形。使用持续增长，但成本和安全保持在规定范围内。淡色线表示不加管理时成本和安全风险会扩大到什么程度。

AI 治理不是阻止使用

本文所说的 AI 治理，是指组织在什么范围内使用 AI、由谁判断和负责、如何确认并改进实际使用结果的体系。它不仅包括制定政策，也包括把政策落实到系统、在运营中再调整的过程。

通常提到治理，人们会想到因为安全和成本而增加审批与流程、限制使用。AI 平台则反过来做：由平台降低遵守安全和成本政策的负担，让成员专注于用 AI 做出成果。各团队在规定政策和资源范围内，不必每次等待审批就能实验，能查看课题成本和调用记录并改进，只有需要扩大使用范围时才接受审核。

平台要减轻这些负担，先有一件事要做。LLM 和 Agent 调用原本分散在多个服务中。平台把这些调用汇集到 AI Gateway 这一共同调用路径。汇到一条路径后，就能确认谁、用什么模型、用了多少，也能在一个地方执行允许模型、预算、调用限额等共同政策。以后 Agent 继续增加，Agent 的 LLM 和工具调用也会进入同一条路径。

先汇集路径也有原因。敏感信息泄露这类事故难以挽回，使用大幅增长后，再整理路径也很困难。所以决定在使用进一步增长之前，先把路径汇起来。

把整体结构分为申请、调用、记录

AI 平台负责的范围很广。本文讨论其中 AI Studio 和 AI Gateway，也就是管理 LLM 与 Agent 的使用、运营和记录的部分。Feature Store、ML Serving、Pipeline 等 MLOps 领域不在讨论范围内。

整体流程分为三部分。上方是 Control Plane（控制面）。申请人在 AI Studio 中填写目的、模型和预算并提出申请，根据政策只对必要项目接受审核。审核结束后，获批的配置会反映到 AI Gateway。

下方是 Data Plane（数据面）。AI 服务和 Agent 用 Virtual Key 调用 AI Gateway，AI Gateway 确认允许模型、预算和调用限额后，把请求转发给 LLM 供应商或 MCP 服务器。LLM 供应商包括 Bedrock、Azure、GCP，以及在公司数据中心 GPU 上直接提供推理服务的 AI 平台。

最后，所有调用都会作为记录留在 Observability 中。通过按课题划分的 Langfuse 追踪、Grafana 指标和 Slack 告警，重新审视并改进实际使用。概括来说，申请在 AI Studio，调用在 AI Gateway，确认靠记录。

1. AI Gateway，成为治理的基础

1.1 调用增多后，成本和责任都看不见了

使用 LLM 以来，凭证发放和使用方式也积累了许多做法。每当出现新课题，有时会新发凭证，也有多个课题共用一个凭证的情况。每家供应商的发放方式都不同，方式变更后旧密钥还留在那里。

在这种结构下，虽然能确认总成本，却很难按课题解释成本为什么增加。Bedrock 可以通过 AIP（Application Inference Profile，应用推理配置文件）拆分成本，但此前创建的资源没有 AIP 或标签。其他供应商的成本要在各自控制台中查看并另行汇总。连负责人也很难马上知道自己负责的课题用了多少。

随着 Agent 增多，问题更大了。Agent 即使处理一个请求，也会反复多次调用 LLM 和工具。调用变得更长、更多，如果不知道哪个课题推高了成本，就无法判断这项使用是否必要、能否减少。

最终，必须能用同一套标准回答以下问题：公司里使用 LLM 的课题和 Agent 有哪些，谁创建、谁负责，用了多少、使用量是否突然上升，是否在允许范围内使用。要回答这些问题，首先需要一个能在一个地方管理调用的基础。

1.2 用 LiteLLM 建立共同调用路径

因此引入了开源项目 LiteLLM 作为 AI Gateway。起点是 LLM Gateway，也就是能以相同方式调用多家供应商的共同调用接口。它不仅提供外部供应商的模型，也通过同一路径提供公司内部 AI 平台的模型；自建推理模型中除了 LLM，还有嵌入、OCR 等模型。

选择 LiteLLM 不只是因为能用相同方式调用多家供应商。它在访问权限、预算、使用记录管理，以及把范围扩展到 MCP（Model Context Protocol，LLM 连接外部工具和数据的标准协议）工具与 Agent 调用方面的方向，与 AI 平台想走的方向一致。调用、访问控制、预算管理、可观测性对接使用 LiteLLM 的功能；贴合组织政策和业务流程的课题登记、政策评估、公司审批系统连接，则在后面介绍的 AI Studio 中实现。

管理单位是项目。项目是把一个使用 AI 的课题注册到平台后的单位，负责人、预算、凭证和政策都挂在它上面。在 AI Gateway 中虽然以 Team 管理，本文统一称为项目。

1.3 汇集调用后，观测和控制成为可能

AI Gateway 把一个调用分四个阶段处理。第一阶段是密钥确认，用 Virtual Key 确认调用属于哪个项目。第二阶段是许可确认，确认该项目是否可以使用这个模型和工具。第三阶段是限额确认，确认是否超过预算、RPM（requests per minute，每分钟请求数）和 TPM（tokens per minute，每分钟 token 数）。第四阶段是转发。通过前三个阶段后，请求被转发给 LLM 供应商或 MCP 服务器；失败时重试或切换到替代模型。所有阶段都会记录按项目划分的成本和追踪。

调用限额是保护共享资源的手段。公司内部 GPU 和供应商配额由多个项目共同使用。为了防止某个项目使用量骤增或反复调用影响其他服务，可以按项目在需要时施加这一限额。

这些功能单看都是网关的运营功能。但以项目为单位把它们串起来，就成为规定谁能在多大程度上使用什么，并确认实际使用的治理基础。AI Gateway 是执行阶段，把获批配置应用到所有调用。

把既有课题迁移到 AI Gateway，并不只是改调用路径。既有课题需要以凭证名称、公司 Wiki 和请求记录为线索，找出对应的使用课题和负责人。能使用某个模型，和能立刻应用到既有服务，也不是一回事。由于各模型支持范围和版本差异，像嵌入这样难以直接迁移的情况也存在，服务级质量验证也需要时间。而且，发放密钥、交付密钥、把审核结果与课题手工对应的工作，不可能一直由人来承担。

剩下两个问题：按项目的模型、预算和限额由谁在哪里决定；以及如何让新课题从一开始就带着服务、负责人和政策进入。这两个问题的答案就是 AI Studio。

2. 用 AI Studio 连接申请与审核

2.1 能配置，并不意味着已被管理

通过 AI Gateway 已经可以设置预算、调用限额和允许模型，但每个项目该填什么值，Gateway 并不会决定。要定预算，需要审核课题和成本；要定允许模型，需要确认数据和安全标准。运营中变更值时，也要留下谁批准了什么。

判断所需的政策和审核已经存在。公司已有个人信息保护指南、生成式 AI 安全审核指南、MCP 安全性检查指南等政策，各组织也在进行成本和安全审核。

问题在于申请入口分成了三个。Bedrock 在申请窗口直接领取 AWS 密钥，外部供应商经过单独审核后发放密钥，AI Gateway 则只单独对接有需要的项目。入口有三个，课题清单也分成三份，没有任何一份能展示全貌。

于是把三个入口合并成 AI Studio 一个。课题登记、审核、批准都在 AI Studio 一处完成，并增加了获批后继续完成项目配置和密钥发放的功能。也就是说，把课题登记和政策评估附着到用户使用 AI 时必须经过的密钥发放流程上。

AI Studio 按三条原则设计。第一，默认范围直接发放，只审核范围之外的项目。第二，原始数据留在各系统，AI Studio 只按需读取。第三，把申请和调用通过项目连接起来，使发放之后仍能重新审核。

2.2 政策越多地落到平台，人工审核越少

第一条原则来自审核方式的演变。起初是查看 Wiki 文档，由人确认并审核所有项目。后来整理标准、划分项目再审核。标准被整理成具体项目后，其中一部分可以由平台而不是人来确认。现在把这些标准作为政策文件放进平台。默认范围由平台确认并直接发放，人只审核例外项目。

把政策作为文件管理后，相同的申请值总会按相同标准评估，审批记录中也能留下是按哪个政策版本判断的。

2.3 默认范围直接发放，只审核例外

在 AI Studio 注册课题后，系统会用政策评估申请值。如果在默认允许范围内，例如使用公司内部 AI 平台模型，就只需通过平台政策，无需等待另行批准，直接发放密钥。范围之外的项目则连接公司审批系统，接受成本审核和安全审核，再按获批配置发放项目密钥。禁止外传的信息、禁止使用的模型等不可允许项，会在发放前拦截。

审核只在必要时附加。选择成本较高的模型会增加成本审核，超过一定预算会增加预算审核，数据和安全项目则按相应标准审核。相互独立的审核并行进行；即使部分模型还在审核中，已经允许的模型也可以不等待，先行使用。

评估结果会直接显示在申请页面。页面会按项目说明是否通过、是否需要审核及原因，并提示如果把预算调整到默认允许范围，就可以不进入审批流程。用户据此可以把申请调整到允许范围内，也可以保留所需范围并请求审核。所需审批会自动提交到公司审批系统，申请人无需另写文档，也不用寻找该向哪个组织提出请求。

2.4 原始数据留在各系统，按需读取

如果 AI Studio 直接保存所有信息，各系统之间的值很容易不一致。因此把原始数据留在负责该信息的系统中。项目信息，也就是服务、负责人和用途，以服务目录为原始来源。AI Studio 只读取这些信息。用户选择目标服务后，还能看到目录中登记的规划与设计文档，因此不必重复提交相同内容，而是把原本就在管理的服务信息用作审核背景。

成本审核和安全审核的状态以公司审批系统为原始来源。AI Studio 发起审核请求并取回审批结果。成本审核由成本负责组织承担，安全审核由安全负责组织承担。预算、使用模型、RPM 和 TPM 以 AI Gateway 为原始来源。AI Studio 把获批配置登记到 Gateway 的项目设置中，密钥按该配置发放。

确认所需审批已经完成，并确认预算、允许模型等必要配置齐备后，才发放密钥。Virtual Key 不放入单独配置，允许模型和预算继承所属项目的设置。项目政策变更后，该项目的所有密钥都遵循同一标准，供应商原始密钥不会交给申请人。由于不把配置值复制到密钥上，系统之间的值不会不一致。

2.5 把申请与调用连接到同一个项目，发放后仍可重新审核

发放时，按照 AI Studio 项目一并创建 Gateway 项目、Virtual Key 和 Langfuse 项目，三个系统使用相同的项目名称。人不必对照各系统中不同的名称，审核历史、成本和调用记录都会连接到同一个项目。

在申请和审核侧，可以在项目中确认服务目录里的负责人和服务、规划与设计文档、审核结果、获批模型和预算。发放后的运营侧，可以在同一个项目中确认 Virtual Key 使用情况、Langfuse 调用日志与追踪、Grafana 和 Slack 的成本与运营告警。因为能连续看到当初想做什么样的申请，以及实际如何使用，所以发放后仍能重新审核是否按申请内容使用。

用户也直接管理课题。需要扩大范围时，在同一个项目里申请变更模型或预算，密钥也在 AI Studio 中直接创建和废弃。

通过申请和审核确定的配置会反映到 AI Gateway，经 Virtual Key 进入的调用都会留下按项目划分的记录。这些记录成为发放后管理成本和安全的依据。

3. 管理使用情况、成本与安全

调用按项目记录后，成本和安全管理也能以同一单位进行。成本分为确认、降低和调整预算；安全分为隔离敏感信息、施加护栏和追踪事故。

3.1 同一份记录，按查看者不同而不同呈现

记录积累在 AI Gateway 和 Langfuse。AI Gateway 保存成本、token 和预算使用量，Langfuse 保存调用追踪、提示和响应。同一份记录，不同的人需要的内容不同，因此拆分了界面。

项目负责人在用户仪表盘查看所负责项目的成本与预算、按模型和密钥划分的使用量、提示缓存情况。AI 平台在平台仪表盘查看 Gateway 和供应商的状态、延迟、错误。故障、预算耗尽、成本骤增等需要立即确认的信号，会通过 Slack 告警发送给成本审核负责人、运营负责人和项目负责人。

在 AI Gateway 查看成本有原因。LLM 成本在每次调用时产生。但原先使用的 Bedrock 账单数据要使用两天后才体现，在此之前无法知道成本。AI Gateway 在调用时按 token 数和单价立即计算成本。因此不必等成本增加后再找原因，而能先通知预算耗尽或使用量较平时骤增的项目。

不过两个数字的用途不同。Gateway 的成本用于骤增检测和预算管理等快速运营判断，准确账单金额与结算则用供应商的成本数据确认。

3.2 用提示缓存降低成本

使用情况按项目连接后，除了拦截和告警，还能做改进。平台找出成本上升的地方并展示给各团队，具体采用什么方法由服务团队确认质量后选择。下图是为说明这一过程而制作的示例，项目名称、成本和比例都不是实际值。

先看本月总成本、缓存比例（输入 token 中从缓存读取的比例）和预算使用率，再按项目拆分查看。在这个示例中，项目 A 使用了总成本的 45%，预算使用率也达到 92%，却完全没有使用缓存。其他项目则从缓存读取了约 60% 到 80% 的输入 token。

于是从提示缓存优化开始。按项目确认重复的系统提示、工具说明和参考文档是否被缓存，向缓存比例低的项目说明应用方法，然后在同一仪表盘再次确认缓存和成本变化。

以下开始是实际测量值，只更改了项目名称。把每次请求都会变化的内容从 system 提示移到 user 消息，并在 system 提示上加上 cache_control。对项目 A 应用提示缓存并比较前后，缓存比例从 5% 提升到 97%，单次请求成本降低 84%。代价是平均响应时间从 0.79 秒增加到 1.33 秒。这是因为网关（LiteLLM）在每次请求时多做了一次 Gemini 缓存查询。

模型和提示变化后，缓存状态也会变化，因此正在其他项目重复“在仪表盘发现、应用、再确认”的过程。

也可以通过平台的模型供应政策降低成本。例如 Amazon Bedrock 的 Global 跨区域推理，输入和输出 token 单价比 Geographic 跨区域推理低约 10%。如果课题满足数据处理区域要求，可以只在 Gateway 注册 Global 推理路径的模型，并把允许模型限制在该范围内。

3.3 预算在超支前告知

预算按项目设定。在 AI Studio 申请预算和限额，使用率上升时通过 Slack 向负责人发送告警，预算用完后由 AI Gateway 限制调用。需要更多预算时，在 AI Studio 申请变更，调整后的预算会再次反映到 AI Gateway。

这一流程之所以可行，是因为 AI Gateway 会按调用计算成本。不必等待账单数据反映，就能在超出预算前发出通知。

3.4 敏感信息先从处理环境上隔离

安全从决定敏感信息在哪里处理开始。包含敏感信息的请求经 AI Gateway 送往公司自建推理的 AI Platform，不流向外部，因此审核范围也缩小。一般业务信息可以送往 Bedrock、Azure、GCP 等外部供应商。

各供应商的安全标准不同，因此按处理环境划分哪些信息可以送往哪里。AI Studio 在申请阶段连接符合数据特性的使用范围，AI Gateway 执行获批的模型和调用路径。

3.5 护栏通过实验建立标准

并非所有政策都能直接用一个配置值应用。像敏感信息护栏这样，需要一边实验探测范围、准确率和延迟，一边确定标准的领域也存在。可以在 AI Gateway 中添加这类护栏模块。例如，把探测并掩码 PII（personally identifiable information，姓名或电话号码等可识别个人身份的信息）的模块加入 Gateway 配置，服务代码无需改动，所有调用都会按同一标准接受检查。

护栏可以应用到经过 AI Gateway 的调用的三个阶段。发往 LLM 之前的 pre_call 阶段，探测并掩码或拦截敏感信息。调用过程中的 during_call 阶段，在调用 LLM 的同时检查输入。收到响应后的 post_call 阶段，检查响应并还原被掩码的值。

这里平台和专业组织分工。AI 平台调研可应用的模块并做首次实验，共享探测结果和延迟等信息，也为安全负责组织提供亲自做同样实验的环境。要探测什么、在什么条件下拦截，由安全负责组织决定。把实验结果整理成政策负责人可以判断的形式并交付，被视为平台的职责范围。

pre_call 护栏针对每种信息项决定 MASK 或 BLOCK。MASK 是指，当服务发送包含电话号码的请求时，LLM 收到的是电话号码位置被遮住的请求，而服务收到的响应会还原原来的值。LLM 不看到实际值也能生成答案。

BLOCK 是指，像卡号这样不应发送的信息一旦出现，就不调用 LLM，直接返回错误。敏感信息从一开始就不会有机会流向外部。

3.6 用记录重新确认审核结果

所有调用都以项目名称留下，因此可以用记录确认是否遵守了审核时定下的要求。例如，约定不发送个人信息，却在追踪中发现了个人信息，就能立刻找到。约定只用于获批目的，却出现同一密钥从未获批的其他服务发起调用，也能通过记录确认。

改进对象也包括政策本身。如果针对某个条目反复出现例外申请，或默认允许范围与实际使用不符，就以审核记录为依据，与负责组织重新讨论标准。初期开展较全面的审核，再根据记录只保留真正需要判断的项目。

结果，成本侧通过成本确认、成本优化和预算调整来开展 FinOps（成本运营），安全侧通过敏感信息隔离、护栏应用和事故追踪来开展 SecOps（安全运营）。经过 AI Gateway 的 LLM 调用，现在可以按 FinOps 和 SecOps 运营。FinOps 与成本负责组织、SecOps 与安全负责组织共同运营。

4. 从 LLM 调用扩展到 Agent

4.1 Agent 还需要确认三件事

先整理 LLM 调用和按项目的治理，是因为 Agent 调用也会原样经过 AI Gateway 和项目配置。Agent 同样调用 LLM，因此预算、允许模型、追踪、护栏等 LLM 治理会原样适用。每个 Agent 不必重新实现模型访问、预算和按项目的记录。

不过 Agent 不只生成答案，还会执行工具。因此还要确认三件事。

第一，谁在调用。因为有多人调用 Agent，所以必须只能由允许的渠道和用户调用。第二，使用什么工具。Agent 会调用 MCP 工具，因此必须只能使用允许的工具。第三，以谁的权限查询。Agent 查询公司内部数据时，必须一并传递请求者信息。

把这三件事应用到调用路径的每个阶段，每个阶段就会有允许列表和默认值。Slack 用户发起请求时，首先只有 Agent 允许的渠道和用户能通过。新 Agent 从没有允许渠道和用户的状态开始。Agent 调用工具时，只有 AI Gateway 的 MCP Servers 中允许的工具能通过，新工具在获准前无法使用。最后，请求者信息会传达到完成安全审核的公司内部 MCP 服务器，查询权限由各系统判断。

4.2 谁能调用

在 AI Studio 的 Agent 设置中确定允许渠道和允许用户。列表中的渠道和用户调用时，Agent 接收请求；列表之外的渠道或用户调用时，Agent 不响应。新 Agent 只允许加入列表的对象。原则是从一开始就不创建任何人都能调用的 Agent。对已在运营的 Agent，也在逐步扩大应用这一限制。下图是示例界面。

4.3 可以使用哪些工具

MCP 服务器在接入前要经过安全审核。平台只把完成安全审核的 MCP 服务器列入清单，创建 Agent 的人只能从这份清单中选择要连接的服务器。审核前或不在清单中的外部 MCP 服务器无法选择。审核过的服务器以清单管理，因此其他 Agent 使用同一服务器时，不必重复相同审核。下图是示例界面。

连接 MCP 服务器并不意味着结束。AI Gateway 会按工具决定是否允许。示例中的 Text-to-SQL MCP 有四个工具：查询表、执行查询、创建表、删除表。这个 Agent 只开启两个读取工具，关闭写入和删除工具。只有开启的工具会显示在列表中并可调用。MCP 服务器新增工具时，工具会以关闭状态进入，因此即使服务器侧发生变化，在获准前 Agent 的行为范围也不会扩大。下图是示例界面。

4.4 以谁的权限查询

如果单独给 Agent 很大权限，经过 Agent 时就可能查到请求者原本看不到的数据。因此不单独给 Agent 权限，而是以提问者的权限执行。Text-to-SQL Agent 是典型例子。

请求者在 Slack 提问后，Agent 转发这个问题，Text-to-SQL MCP 生成 SQL。查询不以 Agent 账户执行，而以请求者账户执行。请求者的公司账户从始至终一并传递，因此即使问同一个问题，不同人的结果也不同。有权限的用户会收到包含其可见数据的结果，无权限的用户则查不到这些数据。

4.5 政策由平台负责，创建者专注 Agent

前面三件事——谁能调用、可以使用哪些工具、以谁的权限查询——如果由创建 Agent 的团队各自实现，每个 Agent 都会漏掉其中一项。有的 Agent 不传递请求者信息，有的 Agent 不限制工具权限。这些遗漏在检查时要逐个 Agent 确认，Agent 越多越难找。相反，在 AI Studio 创建 Agent 时，这三件事会作为默认设置加入，因此从创建时起就应用了全部共同政策。

Agent 在 AI Studio 中选择渠道、用户和工具来创建，并通过公共 Helm Chart 部署。公共 Chart 中包含开发者无法覆盖的共同设置。它固定模型和 MCP 的调用路径，并限制终端、文件、代码执行、浏览器等危险工具集合。如果缺少必要设置或无法解密 Secret，Agent 就不会运行。公共 Chart 已完成 Agent 漏洞审核。

这样部署的 Agent 在 Slack 中与用户对话。Agent 的模型调用经过 AI Gateway，工具调用经过 MCP Servers，追踪留在 Langfuse，用户反馈评分在 Slack 中收集。目标是无论使用哪种 Agent 框架，都保持相同的追踪和安全标准。

结果，平台与 Agent 创建者的角色分开了。平台负责 AI 治理。对 LLM 调用应用预算、允许模型、追踪、护栏和服务目录连接；对 Agent 调用应用渠道与用户许可、完成安全审核的 MCP、请求者信息传递和用户反馈收集。创建 Agent 的人则专注于选择渠道、用户、模型和工具，开发技能与提示，并查看记录进行改进。

5. 承担治理的平台也需要被保护

把调用和政策汇到一处，权限和数据也会汇到一处。承担治理的平台一旦被攻破，影响会扩散到多个课题。本章工作与安全负责组织、基础设施负责组织共同推进。威胁场景检查以及账户、网络隔离设计由安全负责组织承担，AI 平台负责把设计落到平台上。

5.1 密钥和调用汇集之处必须隔离

AI 平台汇集了供应商调用权限和凭证，提示、响应和工具调用结果也会经过这条路径。因此把它和其他服务放在同一网络中很危险。

第一个风险是普通服务的一个漏洞。如果处在同一网络策略内，普通服务的一个漏洞就可能顺着网络直接到达平台。

第二个风险是直接针对平台的攻击。包括让平台以正常权限执行非预期行为的提示注入、夺取管理权限的认证绕过、在服务器上执行任意命令的远程代码执行，以及让人使用植入恶意代码发行包的供应链攻击。

无论哪一种，AI 平台一旦被攻破，供应商调用权限和凭证、提示与响应都会暴露，影响还会扩散到已连接的系统。

因此用五项标准判断隔离对象：是否发放或中转凭证；是否在一处集中多个系统的权限；是否与外部 AI 通信；是否是执行多个服务政策的节点；是否面向两个以上环境。只要符合一项就视为隔离对象，AI Gateway（含 MCP 服务器）和 AI Studio 属于此类。只调用 AI 的服务不隔离，仍在原账户中运营。

5.2 迁移到独立账户和 VPC

于是把 AI 平台迁移到独立 AWS 账户和分离的 VPC（virtual private cloud，云中隔离出来的私有网络）。入口只有 AI Gateway 一个。服务账户中的 AI 调用服务只能通过 AI Gateway 进入，并沿用原有 Gateway 地址。AI Studio 和 Agent 也在这个账户内，原始凭证由 AI Gateway 管理。迁移账户时划分了 beta 和 prod 环境，也重新整理了按服务划分的 IAM Role 和通信路径。

出口也做了规定。Bedrock 通过 IRSA（IAM Roles for Service Accounts，为 Kubernetes Pod 授予 AWS 权限的方式）认证，GCP 仅允许平台的固定 IP。因此，服务绕过 AI Gateway 直接调用供应商的路径，已按全公司标准被阻断。

Gateway 对外暴露的范围也缩小了。指标和 API 文档路径必须经过认证才能打开，管理界面只有属于管理员 SSO 组的用户才能登录。

5.3 所有调用经过的路径不能停

和拦截同样重要的是不能停止。因为 AI Gateway 是所有调用都会经过的路径。

第一，部署时不让请求中断。新 Pod 准备好后才替换，终止的 Pod 先从负载均衡器摘除，再等待 30 秒，让进行中的请求和流式响应完成。这个时间是根据摘除目标后仍有请求进入的时间以及请求处理时间实测确定的。

第二，即使发生检查或故障，也只让一部分实例退出。Pod 按可用区分散部署，限制同时中断的数量，并自动扩缩容。

第三，供应商出错时，AI Gateway 会重试或改用替代模型响应。服务侧无需做任何改动。

结语

并不是一开始就设计了整个治理平台。先有通过 AI Gateway 连接并运营调用的基础，随着 AI 使用增加，才产生了在 AI Gateway 管理成本和使用范围的需要。

所有 LLM 和 MCP 调用都经过 AI Gateway 一处，政策在 AI Studio 中通过申请与审核确定。成本和安全靠记录确认，Agent 也在同一政策内运行。再通过独立账户、路径控制和零中断运营，保护承担治理的平台。

这件事不是 AI 平台独自完成的。成本负责组织、安全负责组织共同参与。

对照引言中的图，使用正以更多项目和 Agent 持续增长。成本通过按项目的成本和预算告警管理，安全通过政策、护栏和独立账户管理。管理节省出的空间，可以用来进一步扩大使用。

与过去相比，各团队使用 AI 的过程也变了。以前平台工程师手工发放凭证并通过 Wiki 传递，按项目的成本要在各供应商控制台分别确认。

现在在 AI Studio 中申请与发放相连，满足默认条件就直接发放，按项目的成本由 Gateway 立即汇总。用一个 Gateway 凭证，就能通过共同 API 实验多家供应商的允许模型；供应商故障由 Gateway 的重试和替代模型承担。供应商通知模型停止支持时，平台会确认并向使用该模型的项目说明。审核、成本和日志都留在同一个项目中。

到目前为止，已应用 LLM 调用管理、Agent 按工具许可、请求者信息传递。Agent 增多后，仅靠项目或密钥单位就不够了。因为同一项目内，各 Agent 做的事情和风险程度不同，一个请求还会引发多次工具调用。因此今后要把治理细化到 Agent 单位。

未来有五项工作。

- Agent Registry：登记并管理公司内有哪些 Agent、谁负责。

- 会话成本：当反复调用没有结束时，限制一个请求的成本和执行次数。

- Agent 认证与授权：处理 Agent 自身的认证和授权。

- 扩大护栏：扩大护栏的应用范围。

- 扩大自动批准：扩大自动批准范围，减少需要人工审核的项目。

质量评估也是剩余课题。仅靠使用量和成本，无法判断课题是否真正有帮助。目前正在把 Agent 的 Slack 反馈收集为 Langfuse 评分，并从评价较低的对话中开始收集评估对象。目标是即使降低成本或更换模型，也能用同一标准比较质量。

本文所说的 AI 治理，不是阻止 AI 使用的装置，而是让 AI 安全、快速扩展的工程实践。平台承担共性工作，各团队确认允许范围和课题状态，开展实验和改进。出现新的使用方式时，会在 AI Gateway 和 AI Studio 中加入必要的管理与控制。🎈
