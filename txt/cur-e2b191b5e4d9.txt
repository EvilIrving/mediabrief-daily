Were SPAs a big mistake? ｜ JS Party ｜ 55分钟 ｜ https://changelog.com/jsparty/224

《JS Party》第 224 期（2022 年 5 月）是一期 Yep/Nope 辩论节目，辩题取自 Chris Ferdinandi 当年 2 月的博文《SPAs were a mistake》，主持人 Jerod Santo 还特意加了个"大"字："单页应用（SPA）是一个大错误吗？"正方是 Divya Sasidharan 和 Nick Nisi；反方本该是 Kevin Ball（Kball）和 Amal Hussein，Amal 因家中施工缺席，Kball 只好单挑，扬言要召唤历届嘉宾的"幽灵"助阵。Jerod 照例当主持兼裁判，用 Christopher Hiller 的一声"Wut?"代替计时铃。

开场陈述中，Divya 先界定概念：SPA 把整个应用一次性加载到用户设备上，之后无需刷新页面；多页应用则每次导航都回服务器取页面。她攻击的是首屏成本：用户未必用到整个应用，却要为它全部下载买单。Kball 的立论是：正是 SPA 把浏览器从文档阅读器变成了能与原生应用比肩的应用平台。渲染之后，导航不必回服务器，只需一次 API 调用，交互也更灵敏；在 React、Vue 这类框架里掌控整个体验，比在服务端渲染页面上拼凑交互容易一个数量级。他提醒，辩题不是"某些场景下该不该用 SPA"，"博客不必做成 SPA"之类的说法都是稻草人。Nick 一边玩"二即是一，一即是无"之类的文字游戏，一边给出实质论点：SPA 默认破坏后退按钮和 URL，可访问性和 Lighthouse 分数都得靠每个团队自己补救，起点就处于劣势。Kball 的第二次陈述引用 Laurie Voss 的观点：浏览器进步得慢，用户态的库先探索，成功的做法再上升为平台能力，jQuery 之后就是 React 及其催生的 SPA。随后他效仿 Feross 当年的名场面"诉诸权威"，念了一串谷歌搜来的"SPA 好处"引语，被众人嘲为 Horse JS 式的断章取义。

快问快答环节火药味最浓。Kball 揭短：Nick 给 JS Party 游戏节目写的应用就是 SPA，还重写过一遍。Divya 提出全场最有分量的论点：Web 和原生是不同的平台，应当"为平台而构建"。后退、链接、历史记录是用户对 Web 的基本预期，SPA 却去模仿原生，逼着每个应用重造浏览器已有的功能，导致体验四分五裂。Kball 反驳说，这是"我的 SPA 坏了所以 SPA 坏了"，多页应用照样能做坏；他还举出 Figma、谷歌搜索、Facebook 都是 SPA，Divya 则回敬说 Figma 的桌面版体验更好。随后的交锋围绕平台演进展开。Kball 打了个比方：要让超负荷的设计师出新设计，最快的办法是先上线一个丑版本；SPA 就是那个丑版本，正是因为人们在浏览器之上造了大量东西，浏览器厂商才被迫补齐 API，否则安于现状的厂商根本没有动力投入。Divya 以汽车和公共交通作比：靠制造拥堵来逼城市修地铁行不通，不投资基础设施就别指望它变好；而且浏览器为了迁就 SPA 带来的预期打乱了自己的计划，否则"我们现在本可以有更好的表单"。Nick 补刀说，SPA 让 JavaScript 泛滥，连 flat 这样的方法命名都得为兼容性让路（他拿 Smoosh 事件打趣）。Kball 最后的立场是：标准流程太官僚，我的用户现在就有问题要解决，今天能用的工具往往就是 SPA。Jerod 宣布自己"不参与即胜利"，第二名给了 Divya 的"表单改革"论点。

第三部分是真心话。Kball 承认大多是辩论需要：SPA 适合 Slack、Figma 这类应用，真正的问题是它成了砸向每颗钉子的锤子；他看好 Remix 这类方案，既保留交互开发的便利，又找回服务端渲染的优点。天天写 SPA 的 Nick 说自己确实认为它是错误，因为它让系统过度复杂、维护负担沉重，但也承认它有用武之地，比如他们录节目用的 riverside.fm 网页应用就运行得近乎完美，嘉宾无需安装任何东西。Jerod 补充说，riverside 其实是个混合应用：演播室是单页，其他部分是多页。Divya 的结论是 SPA 被滥用了，"每人发一把电锤，结果拿来敲瓷砖"；Figma、VS Code 网页版、用 CRDT 的 Google Docs 这类重交互、问题域庞大的应用值得用 SPA，博客之类则大可不必。大家也聊了 SPA 架构的附带好处：同一应用可以打包进 Electron 或 Tauri 实现跨平台，降低开发成本，但并非每个应用都需要跨平台。Jerod 转述 Tom Preston-Werner 的观点：SPA 迫使团队把 API 和客户端分开，日后要做命令行工具、iOS 应用或公开 API 时更从容，长期看反而更经济。Kball 和 Divya 都注意到，Remix 这类框架会在分离前端的同时做服务端渲染，而边缘计算和多区域部署（Divya 在 Fly.io 工作，Fly 甚至会把数据分发到边缘）大幅缩短了往返时间，SPA 当初要规避的代价正在消失。

对 Jerod 提出的"整个行业向 SPA 的钟摆摆动是否白费"这个问题，Divya 认为有一部分确实是在重复发明轮子，并顺带吐槽在 Rails 里写 GraphQL 很痛苦，宁愿写 TypeScript，惹得 Ruby 爱好者 Jerod 和 Kball 抗议。Kball 给出了全场最认真的总结：平台和内核必须保持向后兼容，只能慢慢走，真正的创新发生在用户态；SPA 时期有不少弯路，但如果没有它，Houdini、Canvas、WASM 这些让浏览器能承载 Figma 这类复杂应用的能力不会走到今天。Jerod 的收尾是：选择太多恰恰让人想要标准答案，而辩论最后总会落到"看情况"，真正有意思的是中间地带。节目最后还预告了 2022 年 5 月 24 日至 25 日在盐湖城举办的 Remix Conf，并以韩式汗蒸房的玩笑收场。
