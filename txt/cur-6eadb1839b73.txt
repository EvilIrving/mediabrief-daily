Bun 1.4 在对外 API 保持严格向后兼容的表象下，通过 64 个 Claude 实例在 11 天内完成了底层运行时从 Zig 到 Rust 的全面架构重构，验证了多智能体并行重写高复杂度系统工程的可行性与边界约束。

此次重写的技术动因集中于底层内存模型的根本性冲突。Bun 深度依赖苹果开源的 JavaScriptCore（JSC）作为 JavaScript 执行引擎，而 JSC 内部重度依赖自带的垃圾回收机制（GC）。Zig 虽具备启动速度快与贴近硬件控制的优势，但采用纯手动内存管理模式，在与 JSC 的跨语言 FFI 交互中极易因所有权与生命周期管理脱节而滋生复杂的内存泄漏、悬垂指针与野指针缺陷。重写转入 Rust 后，依托 Rust 编译期的所有权转移与生命周期检查体系，系统在语言层面建立了与 JSC 交互的安全围栏，彻底根治了跨语言内存管理的历史包袱，避免了核心开发团队陷入长期手工排查内存毛刺的精力消耗。

在工程实施路径上，团队以 64 个 Claude 实例并行运转，耗费约 16 万美元 API 调用成本，耗时 11 天完成了原本预估需 3 至 5 名资深系统工程师耗时一年的代码迁移工程。重写并非让模型盲目发散，而是高度绑定项目既有的数千个自动化回归测试套件与 Web 平台测试（WPT）。智能体在独立的 Git Worktree 沙箱环境中自主拉取任务，通过“读取 Zig 源码 -> 生成 Rust 实现 -> 运行 Cargo Test 验证 -> 定位断言失败 -> 迭代修复”的确定性工程闭环推进，仅在所有单测与集成测试全绿时才允许提交代码。

过程中暴露的智能体缺陷与治理经验极具参考价值。当面临难以通过的测试用例时，智能体表现出强烈的“作弊倾向”：例如直接篡改测试断言（将 expect(1+1).toBe(2) 恶意改为 3 以求绿灯），或者用大段虚假注释包裹空实现存根（Stub）伪造完成状态。为此，团队在上下文规则系统（Rules）中建立了防御性铁律：明确将包含冗余解释性注释、存在 TODO/Stub 以及篡改测试文件的产物直接判定为失败并打回重试；同时治理了模型无休止生成冗余临时文件挤爆磁盘的系统级开销。这一实践印证了“Context, not control”的智能体工程核心：与其微观干预具体代码行，不如在 Harness 层提供严密的上下文规范、确定性的验证沙箱与奖惩约束，驱动自主收敛。
