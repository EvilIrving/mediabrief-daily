Matt Pocock 对谈 Lauren Tan：从信任阶梯到"米其林厨房"（直播访谈） ｜ imperia（X） ｜ 1:03:47 ｜ https://x.com/impreiaxbt/status/2108218392188518533

TypeScript 教育者、技能库作者 Matt Pocock 主持的一场直播问答，嘉宾是 SpaceX AI（原 Cursor）工程师 Lauren Tan。起因是 Lauren 那场"上个月发了 2500 个 PR"的演讲在 X 上爆火，Matt 想把它拆开来问清楚。两人都做流行的技能库，惺惺相惜，聊得像两位手艺人在交换心得。

Lauren 讲了自己的来路。她离开 Meta 的 React 团队后休息了一个月，"倦怠了就去做副业"。做副业时她发现自己整天在微观管理一个 agent，于是开始写技能，想把"像我一样写代码"教给 agent，这批技能后来成了 PStack 的雏形。三月加入 Cursor 后，她先被派去救 agent 窗口的性能，又一次发现自己成了 agent 和 Chrome DevTools 之间的"人肉代理"。她由此认定最重要的技能是验证：给 agent 一双手和眼睛，让它像用户一样运行应用、抓 trace，只有这样才谈得上闭环和"爬山"式迭代。如今 SpaceX AI 的每个应用都有一个自动维护的验证技能，已经成了团队的基础设施。她还把验证里确定性的部分写成 CLI 脚本，因为她发现每个 agent 都在"重新造一遍世界"，各造各的；她的原则是"确定性交给代码，判断留给 agent"，做迁移时也一样，用 codemod 这类脚本。

两人都认为领域专长比以往更重要，因为瓶颈已经从 agent 本身转移到"能不能把意图清楚地传达给它"。Matt 是戏剧专业出身，痴迷于措辞，说一个恰当的词会被 agent 抓住、在思考里反复强化，比如 TDD；Lauren 举了"同义反复测试"这个词，一个词就压缩了大量意图。

Lauren 不喜欢"软件工厂"这个说法，因为它听起来没有工艺感，她更愿意说"米其林厨房"。家常厨师什么都自己做，加一个人进厨房就乱了；主厨不亲手做每一道菜，却要像技术负责人那样组织整个厨房。所以工程师的新工作是打磨环境，也就是磨好刀。她类比 TypeScript 的类型收窄：用严格的约束把可能性压到只剩一条路。她的内部框架 Dune 就是这样，每个功能单独一个目录，配上严苛的 lint，让人很难写出坏代码。GrokBot 早期由八个万行以上的"上帝文件"组成，正是看到 agent 往这些文件里不断追加代码，她才想出了功能目录的做法。

2500 个 PR 从哪来？她说前提是环境，然后把外循环和内循环连起来。GrokBot 的 bot 订阅 Slack、X、邮件、Linear，例行地收集 bug 报告，再交给 Cursor 的"项目"（cloud 上的协调 agent，相当于行政主厨），由它判断一批相关报告是否该合并处理，再分派子 agent，免得各自为战、重复劳动。很多 PR 其实是"园艺"式的清理：比如一个 agent 专门扫描 React 的坏模式，但不直接修，而是先记到文档里当缓冲队列，她隔几天看一次，往往能发现"这些其实是同一个问题"。她同时开着十多个各管一块的"幕僚长"，其中一个只是出于好玩在探索用原生语言重写。

至于怎么审这么多 PR，她的回答是抽样而不是逐一把关：每天严格检查一部分代码，如果多个 agent 犯同一个错，就去改环境，而不是去纠正某一个 agent。PStack 的"全自动驾驶"模式会派出多个验证 agent 去 fuzz、点击应用、找回归问题，修到可以合并为止，很耗 token，但可以调。她现在第二天早上看提交历史，有问题就回滚并补规则。她承认第一次放手的那晚很害怕，"需要不少勇气"，现在反而"睡得更好"。她也强调，这和 Karpathy 说的忘掉代码的氛围编程不同：代码和环境依然至关重要，垃圾进、垃圾出。Matt 问到医疗、金融这类"单向门"变更怎么办，她坦言没有答案，关键在于这个领域能否被验证；她看好把证明和编程结合起来的新语言。

最后谈到怎么组合不同的技能库，她说技能就是写成文字的流程。每个厨师都带着自己的刀，所以要磨自己的技能：去翻自己过去的对话记录，找出反复纠正 agent 的地方，把它们变成技能或 lint 规则。她的 recall 技能就是这样来的。她预计随着模型变强，技能会越来越短，从实现细节变成纯粹的工作流。

附：Lenny's Newsletter 文章《How to turn your AI into a world-class designer》（作者 Anshu Chimala，2026 年 9 月 1 日，付费文章，免费预览只到第 6 条技巧）

Anshu Chimala 在苹果带过 12 年软件工程和设计团队，做未来 AI 产品的研究和原型。他的核心判断是：LLM 是"下一个 token 预测器"，又经过人类偏好的反复调教，每做一个设计决策都会挑最讨好所有人的那个选项，等于最极端的"委员会设计"，所以默认产出平庸。好设计恰恰相反，从感受出发、敢于打破常规。他借鉴双钻石模型，把流程改造成给 AI 团队用的三段：发现、定义、交付。

发现阶段的目标是跳出默认样式。第一招是种子字符串：只说"要独特、要随机"没用，模型只会预测"听起来随机"的 token。做法是借鉴 Sakana AI 的 String Seed of Thought，让 agent 先用 shell 生成一长串随机字符，再从中找子模式、特殊数字作为配色、版式、字体的灵感，并且不在设计里露出这串字符，这样每次的结果才真正不同。第二招是把提示写得更大胆，例如"每一屏都像游戏截图的像素风落地页""等距视角的 3D 城市，每个功能是一个街区""极端不对称、颜色字体故意冲突、留白让人不适，但依然好看"。找点子的方法：先让 AI 列一大堆不带细节的方向；挑几个，说出你的直觉反应（比如工业控制面板风"要触感和按键音，但别搞成卡通拟物"），让它按你的口味打磨；最后让它写出构建提示。他鼓励尝试听起来行不通的点子，失败的提示也留着，等新模型出来再试。

定义阶段要让设计有个性。第三招是用子 agent 做设计评论员，形成正反馈循环。写代码的 agent 看不清自己的作品，所以每一轮都截图，在全新的上下文里只把截图（不给代码和历史）交给一个更强的模型（文中用 Fable 5）评审：判断设计想要什么风格、顶级工作室会怎么做、最大差距在哪，惩罚明显的 AI 套路，给出具体意见和 10 分制评分；评到 9 分以上才停，但"9 分即停"这条标准不告诉评论员，以保持评分客观。结果评论员只占不到 10% 的输出 token，比直接让大模型重做便宜一半。要点包括：评价标准越客观越好，最好是把 4 张专业作品和 1 张自家截图放在一起让它排名；给参考图当情绪板而不是模仿对象；先跑一两轮看是否收敛，免得烧钱；评论员用大模型，执行者可以用较小的模型，但不能太小。第四招是用图像生成：agent 爱用渐变和几何图形，这是最明显的 AI 痕迹，要明确让它生成图片，结合着色器和 3D 效果，并逐帧在浏览器里验证。Codex、Antigravity、Grok Build 自带图像生成，提一句就会用；Claude Code 可以调用 Codex CLI 走 ChatGPT 订阅；否则就给一个限额的专用 API key，存在 gitignore 的 .env.agents 里，并在 AGENTS.md 里注明只供开发时使用。第五招是用视频生成做高级动效，通过 fal.ai 这类聚合平台让 agent 自己挑模型。一种用法是生成纯色背景的循环动画，再抠掉背景叠进 UI，例如让水晶碎裂旋转：先把页面背景色烘焙进折射效果，再用视频抠像模型去背景，效果远超代码能做到的。另一种是用关键帧插值做状态过渡，比如行李箱从悬空到落地打开再到物品落入，随滚动逐帧播放，只用了一条提示。

交付阶段的重点是删减。第六招是砍掉不增值的元素：AI 只会加不会减，过度解释和无用元素是 AI 设计的重要标志，克制才显得高级。他以自己的卡路里 App 为例：明明要求"极简"，AI 还是加了粉色光晕、随机高亮、多余标签和不如系统原生的自定义控件；改成以图片为中心的网格、去掉渐变和多余容器、使用 iOS 原生组件后，才"像苹果的设计"。他说模型自己不会冒险删代码，需要你推一把。第 7、8 条技巧（去除 AI 痕迹、手动重写文案）在付费墙之后，预览中看不到。
