读代码之前我先跑的几条 Git 命令

五条 git log 命令，在打开任何一个文件之前诊断一个新代码库：代码改动热点、巴士因子、bug 聚集区和危机模式。

Ally Piechowski · 阅读约 4 分钟

接手一个新代码库时，我做的第一件事通常不是打开代码，而是打开终端，跑几条 git 命令。在看任何一个文件之前，提交历史就能给我一幅项目的诊断图：谁建的它，问题集中在哪里，团队是在自信地交付，还是在雷区里踮着脚走路。

什么改得最多

```
git log --format=format: --name-only --since="1 year ago" | sort | uniq -c | sort -nr | head -20
```

我会在 app/ 或 src/ 目录下运行，而不是仓库根目录，否则锁文件、更新日志和生成的代码会占满整个列表。

这是过去一年里改动最多的 20 个文件。排在最上面的，几乎总是别人提醒过我的那个文件："哦对，那个文件。大家都不敢碰。"

文件改动频繁并不意味着它不好，有时只是因为开发活跃。但一个改动频繁却没人愿意负责的文件，是我所知道的最明确的危险信号。在那个文件里，每次修改都是补丁上打补丁，一个小改动的影响范围难以预测，团队估时总会多留余量，因为他们知道它会"反抗"。

微软研究院 2005 年的一项研究发现，相对改动量（按组件大小归一化后的改动）能很好地预测缺陷密度，而绝对改动次数本身的预测能力很差。上面那条命令统计的是绝对次数，所以我会取前 5 个文件，和下面的 bug 热点命令交叉比对。既改动频繁、bug 又多的文件，就是你最大的单一风险。Adam Tornhill 的《你的代码犯罪现场》（Your Code as a Crime Scene）围绕基于改动量的分析建立了一整套方法论，还包括这些原始命令覆盖不到的复杂度叠加分析。

谁建的它

```
git shortlog -sn --no-merges
```

按提交次数给所有贡献者排名。如果一个人占了 60% 或更多，那就是你的巴士因子。如果他六个月前已经离开，那就是一场危机。如果总排名中的头号贡献者没有出现在最近六个月的窗口里（git shortlog -sn --no-merges --since="6 months ago"），我会立即向客户指出这一点。

我也会看尾部。三十个贡献者，但过去一年只有三个还活跃，说明建这个系统的人和维护它的人不是同一批。

需要注意一点：压缩合并（squash-merge）的工作流会压缩作者信息。如果团队把每个 PR 都压缩成一个提交，这个输出反映的是谁合并了代码，而不是谁写了代码。在下结论之前，值得先问问他们的合并策略。

bug 聚集在哪里

```
git log -i -E --grep="fix|bug|broken" --name-only --format='' | sort | uniq -c | sort -nr | head -20
```

和改动量命令形式相同，只是筛选了提交信息中带有 bug 相关关键词的提交。把这个列表和改动热点对照一下，同时出现在两个列表里的文件就是风险最高的代码：它们不断出错、不断被打补丁，却从未被真正修好。

这取决于提交信息的规范程度。如果团队每次提交都写"update stuff"，你什么也得不到。但即使是一张粗略的 bug 密度地图，也比没有地图强。

这个项目是在加速还是在衰亡

```
git log --format='%ad' --date=format:'%Y-%m' | sort | uniq -c
```

按月统计整个仓库历史的提交次数。我会扫视输出，寻找其中的形状。稳定的节奏是健康的。但如果某个月的提交数骤降一半呢？通常是有人离开了。六到十二个月持续下降的曲线说明团队正在失去动力。周期性的高峰之后跟着几个安静的月份，说明团队是把工作攒成版本发布，而不是持续交付。

我曾经给一位 CTO 看他们的提交速度图，他说："那正是我们失去第二位资深工程师的时候。"他们之前从未把这条时间线联系起来。这是团队数据，不是代码数据。

团队多久救一次火

```
git log --oneline --since="1 year ago" | grep -iE 'revert|hotfix|emergency|rollback'
```

回滚和热修复的频率。一年几次是正常的。每隔几周就回滚一次，说明团队不信任自己的部署流程。这是更深层问题的证据：测试不可靠、缺少预发环境，或者部署流水线让回滚变得比应有的更难。结果为零也是一个信号：要么团队很稳定，要么没人写描述性的提交信息。

危机模式很容易解读。要么有，要么没有。

这五条命令只需几分钟就能跑完。它们不会告诉你一切，但你会知道该先读哪些代码，以及读的时候该注意什么。这就是第一天有条不紊地阅读代码库和四处漫无目的地闲逛之间的区别。

这是我做完整代码库审计时第一个小时的工作内容。

如果这些文件一直在拖你团队的后腿，请找我来，帮你理清该先修什么。
