# 重构的经济收益

作者：Giles Edwards-Alexander（Thoughtworks 欧洲、中东和印度区 CTO，在从移动到 AI 的各类技术，以及零售、金融科技和医疗等行业拥有超过 25 年的工程与技术领导经验。）

本文属于系列文章：Exploring Gen AI（探索生成式 AI）。

2026 年 7 月 30 日

为了熟悉智能体工程（agentic engineering）这个新世界，我构建了一个支持自己工作的应用。这是一个相当复杂的应用：高质量的 Web UI，带动态刷新和查找、模态框和自动保存，集成外部系统，有机器学习和文本分析、后台任务，还有一套完整的环境配置和全自动部署。它大约有 15 万行代码，主要是 Rust（约 12 万行），其余是 TypeScript 和 Terraform。

这些代码完全由智能体编写。主要是 Claude Code，也用了一些 Cursor。除了偶尔出于好奇看一眼，我没有阅读或审查过任何代码。

在构建应用的过程中，我能看到有些东西在走偏。有一次看着终端里滚过对某个文件第 4,000 行的编辑，我仔细看了看。数据访问层已经膨胀到 6,000 多行。随着更多功能落地，它还在继续增长。每一个查询，无论读还是写，都重复着同样的 HTTP 请求设置、同样的 JSON 编码和解码。最终它达到了 17,155 行。在单个 Rust 文件里。

## 一次重构实验

这个 17,155 行的文件就是整个数据访问层。一个单一的、自成一体的模块。审查代码后发现：没有去重，没有内部语言，函数提取很有限，类的提取几乎没有。但它确实有一个清晰的边界，有一个需要保持不变的接口。这是绝佳的重构对象。

对智能体代码库进行重构的目标，是现在把 token 花在重构上，让未来工作的 token 消耗更低。一个实验应当能够表明：随着这个文件被重构，在这个代码库中实现单独功能的 token 成本会下降。

正因为智能体从不学习，这件事现在才可以作为实验来做。我可以在每个重构阶段之后，提示一个全新的智能体去做完全相同的改动。与人类工程师不同，这个实验不会被从前面步骤中学到的东西污染。

1. 制定一个整体重构计划，遵循严格的重构纪律。
2. 设计一个有代表性的改动，用单个提示词描述。
3. 确立改动的基线成本：在一个子智能体中执行该提示词，并要求子智能体报告 token 消耗。
4. 丢弃这个改动。
5. 循环：
   1. 应用整体重构中的一个步骤。
   2. 在一个子智能体中执行*完全*相同的改动，获取该改动的 token 成本。
   3. 丢弃这个改动。
6. 记录重构每一步之后（包括基线）的全部 token 成本、执行改动所用时间以及代码行数。

代表性改动所用的提示词和所应用的重构步骤见下文附录。

一个注意事项：尽管 Claude 会显示 token 数、报告每个会话消耗的 token，并且按 token **计费**，它却没有提供可靠的实时计数 token 的方法。我假设这是个临时问题，会随时间改善。作为替代，子智能体报告收到和发出的字符数，并用 tiktoken 来近似 token 数，方法是把字符数除以四。

## 重构降低了 token 消耗

结果很清楚。在最大文件开始缩小之前，输入 token 基本持平，然后开始下降，接着用 Claude 的话说，"断崖式下跌"。

从基线到最后一次重构，同一任务的输入 token 从 **159,564** 降到 **27,360**。节省了 **132,204** 个 token，即 **83%**。而且这种节省不是一次性的。从此以后，每一次涉及数据访问层的改动成本都显著降低。

节省了多少钱？按撰写本文时 Sonnet 5 每百万 token 3 美元的价格计算，是 39.7 美分。不多。它会成倍放大吗？在调试中会怎样？更复杂的功能呢？这只是重构了代码库的一部分，能否对整个代码库进行激进的重构，处处找到节省？这些重构本身又要*花多少钱？*

这种节省是因为智能体需要读的代码更少了。但并不是因为需要读的代码总量变少了。数据访问层整体的代码量一直相当稳定。因此，要兑现这种节省，智能体必须能成功识别出需要阅读的最小文件子集。从结果看，情况似乎正是如此。在应用改动时阅读 Claude Code 的思考输出和文件读取摘要，也表明子智能体每次都成功地读取了越来越小的代码片段。

换句话说，随意把文件切成更小的文件不太可能有同样的帮助：即便每个文件更小，智能体也会被迫翻遍许多文件去寻找相关代码。虽然效果最大的一步发生在最后，但之前的步骤都是为这一节省做铺垫的重构。这并非事先计划好的。它只是重构通常的推进方式所带来的结果：先在文件内部做局部修改以提取重复代码，等一个重复的核心浮现出来后，再拆分成更小的文件。

重构并没有让代表性改动本身变小。写代码时产生的 token 数基本不受影响：输出 token 变化不大。这些 token 的价格是输入 token 的五倍。但它们的数量要少得多。有没有能够减少输出 token 产生的重构？我需要一个更复杂的样例改动来探索这些问题。非确定性的代码生成过程所带来的噪声，掩盖了代码分解方式变化所造成的任何差异。

## 关于过程的说明

Claude 不擅长重构。如果你阅读下面的提示词和重构步骤，就会清楚地看到，产生的重构是直接对提示词的回应。Claude 无法看着代码、看着一般意义上的重构手法，自己判断哪些适合应用：需要人类主动引导它。这与这个应用中更广泛的经验吻合。开发框架（harness）中包含一个明确的重构步骤。那个重构步骤并没有促使 Claude 去改进这个文件。更具轶事性的一点是，Claude.ai 比 Claude Code 更好。我用这两个界面分别制定了重构计划。Claude Code 发现第一步是提炼函数（Extract Function）。Claude.ai 走得更远，看出了可以提炼出一整个客户端类。

它在应用重构时也很糟糕。重构的机械操作是通过编写使用 grep 和 sed 的 Python 脚本来完成的。这些脚本经常被缩进搞糊涂。哦，多么讽刺。此外，价值最大的那一项重构在第一轮被漏掉了，不得不作为后续步骤重新应用。这就是为什么图中的步骤数与附录中的重构步骤对不上。

完成整个实验大约花了八小时。大部分时间无人值守。唯一的一次干预是在六小时四十分钟后，它看起来已经完成了，但其实跳过了那一步，需要重新引导。这个实验是在缓慢的酒店 WiFi 上运行的。我怀疑这是否影响了耗时。但对代码库做更深入的分析后发现，cargo 的临时构建缓存已经变得非常大。测试执行受到了严重影响。

## 后续工作与更广泛的意义

遗憾的是，直到实验已经完成，我才想到应该统计制定和执行重构计划所需的 token。我查看了做这项工作（包括设计和运行实验）期间的总消耗。我说不清执行重构需要多少 token。不过上限是五百万。这包括两次制定重构计划、设计实验（包括代表性改动）的工作，以及其他各种任务。后续工作应当更准确地统计重构所消耗的 token。

这只是一次实验，对象是一个规模不小、仍处于全新开发阶段（greenfield）、由单个开发者构建和维护的应用。但我认为这可能是一个有意思的第一步。这项工作展示了重构在时间和金钱上的价值，同时也衡量了重构有多昂贵。接下来值得研究的有：更复杂的改动、更大范围的重构、持续重构，甚至不同重构方法的相对价值。

这只是开始。

>   "response_chars": 7890
> }
> ```
>
> 不要提交改动。写完代码后停止。

重构步骤

这是用来制定重构计划的提示词。

> 遵循"重构是一系列可证明保持正确性的代码编辑"这一严格定义，并以 Martin Fowler 的《重构》第二版为依据，检查 @src/firestore.rs。这是一个 1.7 万行的 Rust 文件。任何文件都不应该那么长。它几乎肯定没有使用内部语言来构建和管理查询。给出并描述（但不要执行）一系列重构，在完全不改变接口的前提下大幅减少该文件的行数。

以下是所应用重构的描述，摘自 Claude 制定并遵循的计划。实际计划中包含预测的代码修改。对每项重构，都列出了要遵循的具体步骤。每个步骤都可以单独测试，也都单独测试过。这比大多数人类工程师所遵循的重构要严格。

这里列出的步骤与上面测量的改动并不直接对应，因为 Claude 在第一轮跳过了价值最大的单项重构（把 store 拆分成子文件），不得不在之后以两个额外步骤来完成。

#### 第 1 步——提炼类：`FirestoreClient`（Fowler §7.5）+ 提炼函数 × 4（Fowler §6.1）

**Fowler 参考：***提炼类*（Extract Class，7.5）；对每个原语使用*提炼函数*（Extract Function，6.1）

`FirestoreStore` 目前混杂了两种职责：

* **领域查询编排**——运行哪个查询、写入哪些文档、如何把结果解析为领域类型
* **Firestore HTTP 传输**——认证头、URL 构造、Firestore 线上类型的 JSON 编码/解码、遇到 PRECONDITION\_FAILED 时重试

Fowler §7.5 主张：当你能识别出一个类的数据和行为中一个内聚的子集时，就提炼出一个新类。传输职责拥有：`client: reqwest::Client`、`project_id: String`、`MetadataAuth`，以及 `documents_url()` / `auth_header()`。把这些提炼到一个新的 `FirestoreClient` 结构体中。

**预计节省：`FirestoreStore` 实现中约 1,200 行；`FirestoreClient` 净增约 120 行。**

#### 第 2 步——提炼函数：`extract_doc_id` 和 `new_link`（Fowler §6.1）

**Fowler 参考：***提炼函数*（6.1）

* **`extract_doc_id`**——表达式 `doc.name.rsplit('/').next()?.to_string()` 原样出现在全部 20 个 `parse_*_document` 函数的开头。把它提炼出来。
* **`new_link`**——构建一个带有 `metadata: HashMap::new()`、`provenance: None` 和新 UUID 的 `Link` 结构体，这样的代码出现了 62 次。提炼出一个工厂函数。

**预计节省：约 500 行**（62 个约 10 行的结构体 → 62 个约 2 行的调用；20 个解析函数各少 1 行样板代码）。

#### 第 3 步——提炼函数：link 查询管道辅助函数（Fowler §6.1）

**Fowler 参考：***提炼函数*（6.1）

在 `FirestoreStore` 的 trait 实现中，运行 link 查询之后反复出现两种子模式：

* **模式 A——从查询结果行中收集所有 link 文档（约 15 处）。**
* **模式 B——查询 link 并恰好返回一个目标 ID，缺失则报错（约 8 处）：**

**预计节省：约 200 行。**

#### 第 4 步——提炼函数：`FakeStoreInner` 上的 FakeStore link 谓词（Fowler §6.1）

**Fowler 参考：***提炼函数*（6.1）

在 FakeStore 的实现中，约 15 个方法重复着 `inner.links.iter()...` 的各种变体。

在 `FakeStoreInner` 上提炼出两个方法。这 15 个调用点随之变成单行。还需要按第二个谓词过滤的方法（例如同时检查 `to_kind`），在辅助方法的结果上链式调用 `.into_iter().filter(…)`。

**预计节省：约 120 行。**

#### 第 5 步——以函数调用取代内联代码 × 4：Firestore 值构造器

**Fowler 参考：***以函数调用取代内联代码*（Replace Inline Code with Function Call，8.5）

在编解码块之前添加四个私有的自由函数（文件级，不是方法）。把全部 128 个以上的 `json!({"stringValue": …})` / `json!({"timestampValue": …})` 等内联表达式替换为对这些函数的调用。每个多词的 json 宏调用变成一个简短的调用。

**预计节省：约 80 行（主要来自多行 json 宏折叠成单行）。**

#### 第 6 步——提炼类：`FieldsBuilder`（Fowler §7.3）

**Fowler 参考：***提炼类*（7.3）

约 20 个编码器函数都是这个形态：

```
let mut fields = serde_json::Map::new();
fields.insert("foo".to_string(), str_val(&x.foo));
fields.insert("bar".to_string(), ts_val(x.bar));
json!({"name": path, "fields": fields})
```

提炼一个小型构建器。用这个构建器重写每个编码器函数。一个约 40 行的编码器缩减到约 12 行。

**预计节省：20 个编码器函数共约 500–600 行。**

#### 第 7 步——搬移函数：提取 `src/firestore/queries.rs`

**Fowler 参考：***搬移函数*（Move Function，8.1）

把 `src/firestore.rs` 转换为模块目录：重命名为 `src/firestore/mod.rs`。然后创建 `src/firestore/queries.rs`，把全部 32 个 `LinkQuery` 常量以及 `LinkQuery`/`EqFilter`/`EqValue`/`Ordering`/`Direction` 类型定义移入其中。在 `mod.rs` 中添加 `pub(super) use queries::*;`。

没有行为变化；所有调用点引用的名字原本在扁平文件中就处于作用域内。

**使 `mod.rs` 减少约 800 行。**

#### 第 8 步——搬移函数：提取 `src/firestore/traits.rs`

**Fowler 参考：***搬移函数*（8.1）

把全部 17 个 `pub trait` 定义（及其关联的错误类型）移到 `src/firestore/traits.rs`。在 `mod.rs` 中用 `pub use traits::*;` 重新导出。

**使 `mod.rs` 减少约 1,900 行。产生一个约 1,900 行、需要进一步分解的 `traits.rs`。**

#### 第 9 步——搬移函数：把 `traits.rs` 拆分为 `traits/` 模块目录

**Fowler 参考：***搬移函数*（8.1）

把 17 个 trait 按领域分成四个文件，将 `src/firestore/traits.rs` 转换为模块目录：

| 文件 | Trait | 约行数 |
| --- | --- | --- |
| `traits/planning.rs` | `ConcentrationStore`, `GoalStore`, `ItemStore`, `NoteStore`, `PursuitStore`, `FocusPassStore` | ~650 |
| `traits/content.rs` | `CaptureStore`, `TagStore`, `UrlReferenceStore`, `DocumentStore`, `PaperStore` | ~550 |
| `traits/people.rs` | `ThoughtworkerStore`, `ExternalContactStore`, `CompanyStore` | ~300 |
| `traits/system.rs` | `SessionState`, `LinkStore`, `SuggestionStore`, `SuggestionVetoStore`, `OAuthTokenStore`, `MigrationLedger`, `EmbeddingStore`, `RuntimeConfigStore`, `SalesforceSyncStateStore` | ~400 |

`traits/mod.rs` 变成一个纯粹的重新导出文件（约 20 行）。关联的错误类型（`FocusPassError`、`SuggestionDecisionError` 等）随产生它们的 trait 一起移动。

**不改变任何 trait 定义，不改变任何调用点——只是搬迁位置。每个结果文件 300–650 行。**
