（说明：本期三位主持人在开场分别自我介绍，其中一位为一啸；下文“主持人甲”为主要提问、串场者，“主持人乙”为曾做过低代码平台的主持人，说话人依据上下文推断。开头赞助口播已删去。）

主持人甲：大家好，欢迎收听硬地骇客。最近 Podwise 发布了 CLI 和 Skills，这可能也是很多用户特别期待的一件事。当然，这并不是第一天就规划好的，我们只是不断地被用户的场景推着走。大家开始把播客内容接进“小龙虾”（OpenClaw），接进各种各样的 workflow 和自动化流程里，所以 Podwise 的用户也就需要从“人”进化到“agent”。今天正好趁这个机会，跟大家分享一下我们在这方面的一些思考。

主持人甲：首先，我想很多朋友会有一个疑问：为什么我们选择开发 CLI，而不是 API 或者 SDK，或者别的什么东西？听起来有点反潮流。

一啸：我觉得这不是反当下的潮流，更多是在反传统 SaaS 服务对外提供能力的方式。传统 SaaS 肯定都是以 API 或者包装一个 SDK 为主，对吧？但恰恰今天的潮流是提供 CLI，这是一件很反传统的事。在我看来，SDK、API 本质上还是给程序员编程用的，是写代码时用的。这些 SDK 和 API 往往设计得比较复杂，甚至很臃肿：一个 API 上可能有很多很多参数，这些参数以不同组合实现不同的功能效果，你得结合它丰富的文档，才能搞清楚这个 API 具体怎么用；你还需要定义很多 schema，整个结构是怎样的。所以 SDK 和 API 本质上是一件灵活编程的事，它不是给人直接友好使用的接口。

一啸：今天面向 agent，我们还是希望给到 agent 的是一个很干净的东西，就像人去使用一样，清晰易用，没有什么歧义，也不需要复杂的认知负担就能轻松使用的工具。CLI 本身就扮演了这样一个角色。我们都知道，早年 Linux、Unix 诞生的时候，只有 CLI 这样一种用户界面，它本质上是人和电脑、和机器交流的通道，是那个年代唯一的通道，后来才有了 GUI，有了大家点一点的方式。所以 CLI 本质上是一种可组合的文本接口。它不是代码接口，而是人可以直接使用的、可组合的文本接口。你看 CLI 天生就有很好的 stdin、stdout 这种很自然的输入输出流。对 agent 来说，它要的就是很自然的输入、很自然的输出，然后 CLI 又提供了 pipe 的组合——组合这一点就很重要了。在 Linux 这样的电脑上有很多很多工具，我们能通过 pipe 去组合，就能发挥出很强大的功能。比如我要搜索一段文本，可以 cat 一个文件，然后 grep 想要的内容，都是通过这种组合达到了很好的灵活性。

一啸：我觉得更重要的是，一个命令就能跑，认知负担超级超级低。这件事在今天的 Unix-like 系统上是很天然的。它不需要说我写一个 API 调用，还得先把它集成到代码里才能跑——那是多了一个步骤，而且工作量、认知成本都不低。agent 是会写代码的，今天还能写很复杂的代码，但实际上 agent 更会写、也更容易写一条命令，对吧？通过写一条 CLI 命令，就能很轻松地完成一个很复杂的工具调用，这件事的门槛相对 API 要低很多很多。这也是我觉得为什么今天大家在 agent 生态里做工具调用时，突然发现 CLI 运行得很稳定、很好用的一个重要原因。

主持人乙：我现在确实感觉大家都一股脑儿在做 CLI。比如我一直在用的 Obsidian，2 月底也 release 了一个 CLI。它做了有 6 年了吧，2020 年 release 的第一个版本。如果不是今天的 agent 生态，我估计再过 6 年它也不会想着要做个 CLI，对吧？它作为一个笔记编辑软件，不可能去做 CLI。包括我们自己也是，如果不是 agent 生态，肯定也不会想着去做 CLI。

主持人甲：没错。但今天 CLI 加上 Skills，应该是把软件接入 agent 综合成本最低的方式了。就像一啸讲的，如果你去做 SDK、做 API——当然 CLI 背后也有 API，只是我们不把这个 API 直接给到用户——用户就得写代码。虽然 AI 也会写代码，但 CLI 肯定更方便。所以一个是 AI 调用方便，一个是用户自己安装调试方便，包括我们自己开发也方便，可以快速复用软件已有的业务能力。

主持人甲：打个不太恰当的比喻：我们之前的软件就像做堂食的餐饮，终端用户到店吃饭，那门店得装修，服务也得周到，要考虑顾客的到店体验。CLI 就像堂食店加了个外卖，门店的能力是复用的，只要接上外卖平台，在门口安排个外卖取餐区就行了，这一块不用装修，也不用服务。甚至还可以做成外卖专门店，就像今天有些纯面向 AI 的软件一样。这也是因为有了外卖这个生态；CLI 也一样，有了 AI agent 这个生态之后，才成为一个新的生态板块，我就可以在现有软件的基础上把它加上去。

主持人乙：你这个比喻特别有意思，堂食加外卖。甚至可能人家把饭都摆在那儿了，你进来之后自己打：每个菜一个盘，你拿个盘子自己打，打完该付钱付钱，该干嘛干嘛。我觉得这个比喻挺有意思，它面向的客群不一样。

主持人甲：那我们既然做了 CLI，要不要先给大家介绍一下 Podwise 的 CLI 现在有什么能力？

一啸：我之前也看到大家在 X、在推特上讨论：今天作为 SaaS 提供方要去提供 CLI，有很多团队可能会做错。错在哪？很多 SaaS，特别是比较老的 SaaS，功能已经非常非常多了。如果公司觉得要紧跟潮流，或者要转向这样的战略，可能会觉得 CLI 的能力需要和 Web 版 SaaS 对齐，于是一股脑地把 Web 版的功能全部迁移到 CLI 上，最后得到一个非常臃肿、非常不好用的 CLI，甚至对 agent 一点都不友好。我觉得这个观点很正确。今天很多团队做 CLI 都会面临这样的决策：CLI 需要做成什么样子，要对应已有 SaaS 服务的哪一部分——这可能是最值得思考的问题。这里面肯定有取舍，你不可能把 SaaS 功能原封不动、一比一地搬到 CLI 上，那样真的会得到一个很难用的 CLI。

一啸：回到我们这次做 Podwise CLI，我们最终得出的功能其实只有四大类原子能力。我说的是原子能力，它不像 Web 界面那样，你打开一个页面，就给你呈现很多帮你计算好的结果或者工作流的结果，一眼就能看清楚。我们的 CLI 更多是在提供原子能力，你可以自己组合：写个脚本去组合，写个 skill 去组合，或者用自动化 workflow 去组合，最终达到你想要的结果。这是我们在功能设计上的目标。现有功能分成四大类：第一类是发现，也就是内容发现，因为我们平台上有很多很多内容；第二类是处理，处理一段音频、视频或者本地文件之类的；处理完之后，第三类是获取结果，可以拿到我们的逐字稿、各种总结结果；第四类是导出，把这些内容导出到外部平台，比如 Readwise、Notion、Logseq 等等。主要就是这四大类。

一啸：在发现里，我们做了非常完善的搜索能力，因为我觉得发现非常重要。你真要用一个 CLI，特别是用到 agent 这种场景去自动化驱动的时候，会发现人已经不在这个回路（loop）里了，那就需要 AI 自己去发现。所以我们做 CLI 时必须提供非常完善的发现能力，让 agent 能精准地找到想要的内容。我觉得这是所有做面向 agent 的 CLI 的人都需要思考的：怎么让它完成第一步“发现”。我想过这个问题，它其实是普适性的，并不是 Podwise 自己的问题。所以我们提供了 ask AI、search，包括能 list 你自己订阅的更新、你的 history 等等，让你所有的内容都能被完善地发现。总的来说，核心就是围绕这四大类原子流程展开的。

主持人甲：那在设计上我们有没有什么特别的考虑？因为 agent 现在也成了新的用户。我们以往是人类用户，那 CLI 还需要满足人类用户的调用吗？是要满足两类用户，还是 CLI 就专门面向 agent 用户去实现？这里面有没有什么取舍？

一啸：我觉得今天大家发现 CLI 比 MCP 好用，一个很关键的原因就是 CLI 人能直接用。这是非常关键的一点。我们在开发 CLI 的时候，我根本没想过写一个 MCP server 给 AI 用。因为我之前写过、最后去封装 MCP server 的时候，发现调试起来很麻烦——它不像 CLI，我在本地就能很轻松地调试。MCP 你必须接到那样一个编程生态里，也就是写代码，然后才能做调试，相对来说麻烦很多。所以我觉得 CLI 面向人类的设计是需要考虑的。

一啸：但面向人类的设计这件事，里面有一些技巧。大家都知道 CLI 是黑屏幕、白文字，对人来说视觉效果肯定赶不上 Web，表达没那么清晰。我们刚开始做的时候，自己也会想能不能加点颜色、加点动画，让它更好看、体验更好、更清晰——这对人来说确实非常重要。我们最终也选择加上去了，但加的方式值得大家参考：我们提供了一个单独的 pretty 选项，专门给人用。打开这个选项后，结果会被渲染，有颜色，该有动画的地方有动画，比如进度、处理中的 spinner 之类的。但这里有个小技巧：既然你提供了面向人的开关，就要防止 agent 误用。因为这个开关打开后，输出里会有大量非文本的东西，很多颜色编码、颜色控制字符，这些肯定会影响 agent 的正常运行，token 量也会非常非常大。所以一定要做个小处理：面向人的模式只能在终端的 TTY 环境下运行。大家都知道人用的环境是带 TTY 的，但 agent 把它当工具调用时肯定没有 TTY，通过管道重定向时也没有 TTY。所以要做这样的判断：识别出当前是人用的环境，就走面向人的 pretty 方式；如果发现不是人用的环境、没有 TTY 设备，就用最原始的纯文本方式输出。这只是兼顾人和 agent 的一个非常小的技巧。

一啸：回到 CLI 的设计原则，我们要特别考虑什么？除了前面提到的，我觉得非常重要的还是回到管道。管道是第一重要的。以前给人用的 CLI 经常不考虑管道：输入就是人提供的参数，输出比如要写文件，就设计一个 -o 或者 --output-file 选项，直接写进文件。很多很多 CLI 在这方面都是不合格的，几乎都这样做输入输出，根本没考虑用管道。其实我们做 CLI 不需要自己去写到某个文件，最好把这件事留给管道去做重定向。因为 agent 在编排的时候，除了用你的工具，还会调用系统里很多其他命令行工具，你的管道支持得好，最终的组合效果就会好很多。

一啸：第二是幂等，这也是非常重要的。人可能误操作，有时候还有保障，但 agent 操作起来可能很疯狂，毕竟它是自动化的，可能会有非常多的重复调用，所以幂等肯定非常关键。第三是不要交互式，这大家都能理解，agent 没办法进行交互式操作，你给它一个交互式界面，要输个 yes、输个 no 才能进行下一步，肯定不友好，我们要的是纯粹的非交互式命令。为什么不能交互？说白了 agent 主要理解的还是纯文本。我一直在想，为什么 agent 不能像人这样工作——看到这儿需要输入，就输入点什么。这更多还是因为今天的 agent 基于文本在工作。大家有没有听最近那期很火的播客，谢赛宁讲的一件事？谢赛宁更倾向于认为，在未来 AI 的世界里，视觉是非常非常重要的——可能因为他自己就是做视觉的——他觉得今天的 AI 没有真正的视觉能力。它不像人，我们是看到屏幕上有什么，再去输入、去点击；AI 不是这个逻辑，它更多是分析文本内容是什么，再去做相应的操作。这和人确实有很大不同。人现在的智能里，视觉扮演了挺重要的角色，这也是为什么我们看文字时会觉得有颜色很重要。

一啸：前面讲了三点：管道、幂等、不要交互。第四点是 help 信息，这不用多说，肯定要写得非常清晰，最好有直接复制就能用的例子，这非常重要。第五点是很多时候会被忽略的错误信息。CLI 访问后端 API，不管访问什么，肯定会出错。我们过去写错误信息更偏向程序员的方式，打印一个 error 怎样怎样。但现在最好的错误信息是能指导 agent 进行下一步行动的。比如 agent 去访问某个东西时没有认证、没有登录，你最好能告诉它如何去认证，能指导它下一步行动是最好的。最后一点比较重要的是输出结构，这没什么好说的，输出肯定要结构化，现在常用的做法一定会支持一个 JSON 选项，让它做 JSON 结构化输出。但不管是 JSON 还是 Markdown，内容表达的语义一定要清晰，每个字段是什么内容，一定要告诉 agent。这样整体下来，我觉得就算是一个比较好的、至少对 agent 挺友好的 CLI 了。

主持人甲：这几个点特别好。我印象特别深的一点是要有清晰的 help 示例。现在 agent 本身就会去执行 CLI 的 help，它已经内化了这个能力：找到一个 CLI 时，会先看一下 help 里到底有什么能力，再根据 help 里的参数提示做下一步清晰的调用。比如你想干嘛，它可以根据 help 里的示例帮你调用。如果没有清晰的示例，它就得去猜，失误率就很高。所以把每个命令具体做什么都标注清楚，对 LLM 来说是很重要的帮助。这可能也是大家现在设计 CLI 时需要关注的一件事。

主持人甲：当然，我们除了 CLI，在 CLI 之上还有很多 Skills。CLI 里那些原始操作，在 Skills 里都可以直接使用。比如你可以问：能不能帮我获取某一期节目的逐字稿，比如讲 2026 年 AI 发展趋势的那期？这些都可以直接调用 CLI 的原始能力。还有一个是工作流能力，我觉得这是 Skills 里比较关键的一层。怎么解释这个 workflow 呢？就是你可以把 Podwise 的搜索、处理、获取逐字稿、导出等等，通过 pipe、通过管道或者多次调用，串成一个完整的流程。举个简单例子：帮我找到一期播客，拿到它的总结，再把逐字稿拿出来，导出到 Notion 里。要完成找播客、拿总结、拿逐字稿、再导出这一串步骤，在 CLI 里可能要调用很多条命令；但如果做成 Skills，在 LLM 的环境里，整个流程就可以变成一句简单的自然语言：“请帮我找到最近讲 AI agent 的播客，把重点导出来，同步到 Notion 里。”你这么一说，LLM 就会自动把它拆成一连串步骤：先调用 CLI 里的 search 找内容；如果这期还没被处理，就调用 process 做一次 AI 处理；然后用 get 去拿 transcription 也好、summary 也好，拿到结构化内容；最后 export 到 Notion。也就是说，这个 workflow 不是你手写的，而是完整生成出来的。再进一步，这些 workflow 还可以固定下来，变成固定的 skill，还可以参数化、做嵌套。

主持人甲：这里面有一些很有意思的体验：以前你是在调用工具，现在更像是在描述任务，相当于把过程式编程变成了声明式编程，它可以帮你动态拼出这条工具链。在此基础上，我们还内置了一些挺有意思的 skills。比如你可以让 Podwise 帮你总结本周的播客周报：你自己看过、听过的播客，想 recap 一下、回顾一下本周到底看过什么、听过什么、学过什么，就可以让 Podwise 帮你整一份播客周报。它还可以帮你学外语：让 Podwise 记下你当前的英语水平，下次听新播客时，帮你把里面的生词、地道表达抽出来。还可以让 Podwise 跟你深度探讨一些内容，比如刚才一啸提到的谢赛宁那期播客，你可能有问题：世界模型和大语言模型到底有什么区别？为什么说世界模型更重要？当然这是他现在的观点。我们就可以跟它深度探讨，到底哪里有问题。我们内置了苏格拉底式问答，一个问题从头追到尾，跟你一起探讨到底有什么区别。这些是比较核心的 workflow，还有一些我们也内置了。大家想探索的话，可以在装了 Podwise Skills 之后，在 LLM 里问一下 Podwise：你有什么能力？大家可以深度探索一下，挺好玩的。

主持人甲：我觉得这部分比较神奇的是，LLM 内置的智能作用在 CLI 之上时，产生了很多化学反应。不光是 workflow 的执行，还有很多自然语言被 LLM 自动拆解成了多个 CLI 命令调用。如果你用的是 API 或者 SDK，是没法获得这种体验的。也就是说，有了原子能力，就可以做很多事。可能效率有点低，但对很多场景来讲无伤大雅。比如我们 Podwise 的播客场景，这样一步一步来，对性能要求不高，只是对串起这个流程的要求比较高，所以这对 Podwise 是非常有用的场景。这是一个非常神奇的体验，不知道你们怎么看 LLM 和 CLI 结合的化学反应？

一啸：其实就像你说的，用 API、用 SDK 可能就没办法获得这种神奇的体验。因为直接用 API、SDK，还是根据自己的需求去开发代码，写一个固定的 workflow，达不到 LLM 这种智能加持的自动化体验。我认为这里面最核心的化学反应来源于我们常说的排列组合。传统编程，我拿着 API、SDK 去编程，是根据我自己的需求、经验和对产品的理解，去实现一些比较固定的 workflow 组合或固定的业务流程，并且我们认为这个流程是绝大多数用户需要的。传统 SaaS 提供的服务就是这个样子：固定编排好的 workflow。它的上限其实比较低——你做成什么样，产品就是什么样，用户源源不断地提需求，你就得不断改变产品形态、不断迭代发版本。这就是传统 SaaS 的形态。今天有了 LLM 这种智能带来的高度自动化之后，排列组合就有了无限可能：我不需要根据用户需求或自己对产品的理解，把产品形态做成某个样子，而是完全让 agent、让 LLM、让 AI 去动态生成这个系统长什么样。可以理解成，我们整个 SaaS 系统变成了一个动态组合系统，驱动这种动态组合的完全是用户的临时需求：用户此刻怎么想，我就给他一个什么样的系统结果。所以它的上限看上去非常高，也是一种非常神奇的体验——我可能想要什么，它突然就给我生成了什么。

一啸：回到问题的本质，我觉得它其实等价于我们在做 AI 应用架构设计时，究竟用 workflow 还是用 agent 的那个争论，又回到了那个争论。今天再看这个问题会发现，workflow 就是固化好的东西，想象力上限很低，优点是我们常说的稳定，但对产品形态来说确实太死板。而通过 agent 这种架构方式，我们会发现产品的生命力旺盛很多，你可以从里面变出各种魔法，真的是 magic。

主持人乙：我之前做过几年低代码（low-code）平台。这种低代码或无代码平台，也是想解决自由度的问题，它是旧时代的魔法，今天 AI agent 是新时代的魔法。低代码、无代码平台提供的是封装好的原子能力，再通过平台提供的编排机制——不管是所见即所得的也好，还是可以写 workflow 的 DSL 也好——让用户自己实现需求。原子能力提供了确定性，编排机制提供了可能性。如果大家做过这种平台，会发现用户有时候能做出各种奇奇怪怪、超出你原本设想的东西，你会发现：我这个平台还能做成这样，我自己以前都没想到过。但这个过程的问题是，用户需要先自己动手做工具，然后才能用工具得到结果。而这个动手做工具的过程，哪怕有无代码平台辅助，其实也不简单，往复杂了做之后，还是需要不少专业知识。但今天 CLI 提供确定性的原子能力，大模型提供了无需编排的可能性，直接交付结果，把低代码、无代码平台最麻烦的那一步干掉了，对用户来说体验就非常爽：不需要中间那个过程，魔法直接帮你拿到结果。所以我感觉，如果今天还有在持续迭代维护的低代码、无代码产品，已经到了应该舍弃的时候了，不管投入了多久，都该壮士断腕了，它肯定已经没什么价值了。

主持人甲：认可。你讲的低代码平台，大概 5 年前左右确实挺火的。但这里面也正好隐含了一点：低代码平台本身对性能的要求不是特别高。这恰好跟我们刚才聊的 LLM 的组合能力对上了——它可能不是性能最高的那种，但可以帮你无限组合，恰好跟低代码平台特别合适。因为低代码平台首先是一个数据库集合，先是数据模型，其次才是上面的业务流程。它能做业务流程编排，就意味着它肯定不是性能最优的形式。今天我用 LLM 去替代它做流程编排，效果可能就特别好。这确实是一个蛮新的体验，也是对以前低代码产品的颠覆：数据模型加上 LLM，已经可以替代以前低代码平台的流程编排能力。

主持人甲：再回到 Skills，聊聊我自己用完 Podwise Skills 之后的感受：我发现不光我的 token 消耗量增长了，我自己消耗播客的数量也成倍增长了。举个例子，前两天我准备研究一下 Stripe 的前 CTO David Singleton——就是设计模式里那个“单例” singleton——他说了一些挺反常识的观点，我就想研究他之前在播客里还表达过什么。我就让 Podwise 帮我研究 David Singleton 过往的言论。它帮我找到了 9 期他参与的播客，其中 5 期处理过、4 期没处理过，结果它直接把那 4 期处理了，处理完统一汇总给我：他在 Stripe 时有什么样的表达，在新创业公司 Dreamer 做 CEO 之后又有什么样的表达。整个结论非常完美，因为都是从播客里提取的。也就是说，它不光消耗了很多 token，实际上也消耗了很多 Podwise 里的内容。这一点我觉得有点反直觉。当然这可能是我个人的案例，不知道你们有没有这种消耗量增长的体感？

主持人乙：可能是你读得更多了。我觉得这倒挺符合直觉的，因为 token 的流转本身就是内容的流转。大模型是通过 token 的流转来“阅读”和“理解”内容的——当然这个阅读和理解要加引号，毕竟从原理上讲，它只是在做模式匹配和概率推测的输出。但反正表象上，它消耗了输入的内容，把内容转化成 token，又把 token 转换出新内容，所以它其实也是在消费内容。从 coding 的角度，体感也一样。我们主要用的还是 coding，人写代码本身也要消费内容：要看已有的代码，要看文档、第三方库的文档。现在这些都是大模型在消费，效率有巨大提升。虽然从结果看是大模型直接写了代码，但在动手写代码之前，它其实以几百倍于人类的速度在阅读内容，然后梳理和产出方案。我自己最开始在 AI coding 能力还没那么强的时候，习惯先看代码、看文档，自己脑子里有个大概方案之后再描述给大模型，以提高产出的质量和确定性。但这个过程很耗时。就像我们以前常说的，程序员花时间最多的不是写代码，写代码很快，更多时间是花在想方案上。现在 AI coding 能力强了之后，这部分时间节约非常明显。所以我自己的体感是，以前一想到要去看个新东西、接个什么玩意儿、看看文档，就觉得很烦，现在觉得挺方便，因为让大模型代劳了，它帮我消费这些内容，效率非常高。

一啸：我的体感肯定也一样。今天这种内容型消费，我自己也基本不太会人肉去消费了。播客这件事就不说了，只要你通过我们的 Skills，通过 agent——OpenCode 也好、Claude Code（CC）也好——去消费，你会发现自己会关注很多不同的播客。我补充一些别的场景：比如我现在接触任何一个新产品，比如某个 SaaS 开发类产品，它的文档网站写得非常多，我几乎都是直接扔给 agent，让它先帮我读一遍、总结一遍。哪怕文档已经写得很清楚系统架构是怎样的，我也懒得看了，直接把文档扔给 agent，让它从架构原理到收费策略给我介绍一遍，把关键点列出来。它咔哧咔哧把所有文档读一遍，可能几分钟就看完了。换成我们自己慢慢看，可能只会挑 pricing 怎么收费、再了解一下架构设计，其他细节就不会再看了。所以你消费的内容肯定是成倍成倍增长的。但效率提升虽然明显，成本也摆在那儿。回到娱乐场景，比如播客或者其他娱乐场景，这种性价比我觉得还有很多需要考虑的。如果是工作、编程写代码，我觉得性价比非常高；但如果是纯娱乐，对你的工作效率没什么帮助，那 token 的消耗量投入还是挺高的。当然今天在 AI 时代，很多人也在鼓吹 token 消耗，觉得你要真正掌握 AI，就应该每天消耗多少 token、花多少钱的 token 才算合格，对吧？就像老黄（黄仁勋），这种人不断出来鼓吹 token 消耗量的标准和定义。和别人聊的时候我也会提醒对方：你想一想黄仁勋是做什么生意的？每个人都是从生意角度出发，观点都代表自己的视角。比如阿里、Google、腾讯是卖 token 的，黄仁勋是卖卡的，从他们的生意角度，当然希望每个人每天都来消耗 1 万美金，钱都进他们口袋，这也合情合理。

主持人乙：对，老黄宣传的是，一个年薪 50 万美金的程序员，一年至少得消耗 25 万美金的 token。

主持人甲：讲到消耗，我们也提一下 CLI 和 Skills 的商业模式问题。Podwise 的 CLI 和 Skills 现在是免费开源的，大家可以在 GitHub 上搜索 podwise-cli 找到。但对我们平台来说，转录本身还是挺昂贵的，不是免费的，成本挺高。那我们有没有为 CLI 和 Skills 设计一些收费策略或调用限制？比如现在很多 coding agent，像 Claude Code，有周限额、月限额，还有定时刷新，每几个小时刷新之类的。我们有类似的策略吗？

一啸：我们现在对价值比较高的能力做了滚动窗口限制。比如获取 AI 处理后的结果，我们做了每 5 小时一个滚动窗口，以及一周的滚动窗口，会重置限制。原则上让大家正常使用时够用，但如果你想一下子把我们的数据全扒完，那就要限制一下，防御这种情况，主要是这个。对于成本大头的转录和 AI 处理能力，现在 CLI 和我们 App 的 credits 是共享的，转录结果也是共享的，你用 CLI 转录的，在 App 上也能看到，毕竟本质上 CLI 就是对 App 能力的再包装。值得一提的是，目前推广期，我们给 free 用户也送了专属于 CLI 的 AI 处理配额，方便大家试用。这个是 CLI 专属的，Web 上用不了，所以大家可以不用付费，去体验一下前面提到的 CLI 加 agent 的神奇体验，欢迎大家试用。

主持人甲：我还想帮大家问一下，因为我们听众里有很多开发者：如果现在要重新做一个新产品，可能一开始考虑的就不光是给人用，也要给 agent 用，那在软件架构上，你们有什么建议吗？

一啸：总的来说，我觉得从工程技术上的架构来看，跨度还没有特别大。更多的是生态意识的转变：要不要转向 agent。这可能是所有开发者、做产品的人更需要思考的核心问题，纯工程技术的话都不是特别大的问题。当然，回到架构上分享几点我的思考。前后端分离是我们提了很多年的老东西，但你会发现，在过去所有前后端分离的架构里都有一个很神奇的点：前后端是分离了，但你找后端同学要一个清晰的 REST API，其实是没有的，几乎给不出一个特别好用、能作为 OpenAPI 对外开放、有完善的 token 认证和限流机制、和前端没有任何耦合的清晰 API，这种很少很少。所以我觉得现在做前后端分离，要的是绝对的 API 优先，在 API 先行的基础上，再考虑提供面向人的 GUI、面向 agent 的 CLI。这一点一开始可以多花些时间思考，免得后面又要重做。

一啸：面向 agent 的软件架构，当你决定做这件事时，会有更多选择，比如把更多逻辑放到 CLI 上实现，不需要全部放到服务端，服务端就可以更简单。举个例子，Podwise 的 CLI 可以导出内容，比如导出 SRT、VTT 这样的字幕格式，甚至生成 PDF、XMind 这样的格式。这些格式今天放在 CLI 端做就非常自然，利用本地桌面电脑的算力也很合适，完全不需要给服务端增加更多压力。服务端就可以专心提供那些稀缺的、高价值的核心能力。也就是说，你可以把服务端做成一个只提供一点核心能力的小服务，比如完成用户认证、计费，再提供最核心的业务流程和能力就够了。而 CLI 完全跑在本地桌面电脑或者其他服务器上，拥有对电脑算力、存储很强的控制能力，它是一个完整的程序，能做你在 Web 浏览器里做不到的所有事情。今天我们不要把 CLI 当成一个 wrapper 层，只是对 API 的包装，那样它干的事非常少。其实可以把 CLI 当成服务的标准配套，就像开发 iOS App 一样。今天的 iOS App 非常复杂，远不只是调用一个远程 API、展示结果就完了，它也利用了大量本地计算能力，做了很多本地逻辑。今天做 CLI 完全可以从这个角度出发，用 CLI 实现各种扩展功能，提供更多原子能力，供 agent 直接调用。

一啸：再举个例子，我们今天用 Claude Code 这样的 agent 时，它可以把一篇生成好的文章、一段文字内容，自己写代码先生成一个 HTML，再转成 PDF 保存到本地。这个过程几乎所有 AI agent 今天都能完成，但需要消耗非常多 token，也有更多不稳定因素，转出来的 PDF 是否足够漂亮，每一次也不一定。所以像把一段文字内容转成 PDF 这件事，完全可以沉淀到 CLI 里，变成一个固定的 tool、固定的原子能力，agent 就可以直接反复调用。从这个角度会发现，CLI 扮演的角色不是一个 wrapper，而是与服务端合理配套的客户端程序。回到 Podwise，我们为什么把它开源？因为我们大多数核心业务逻辑在服务端，特别是涉及计费、认证的都在服务端，所以客户端不重要，可以给到大家随便修改。但如果你把 CLI 做成了你核心服务的一部分，和 server 是配套的，就像我说的 iOS App 那种，那你可能就需要决策要不要开源，可能会选择不开源的方式提供给用户。这要根据自己的产品属性来，就像 App 一样，需要自己从这个角度去决策。

主持人甲：我们讲 iOS App 的时候，它不光有很多远程 API 调用，也有很多对 iOS 内部能力的调用，比如 iOS 本身的 SDK 提供了很多不需要和服务端交互的能力。就像刚才举的例子，我们本地其实可以转 PDF，软件里想装一个转 PDF 的组件也好，或者在 CLI 里调用别的能力，甚至转成视频，都可以，这就是本地能力。本地可以做很多很多这样的事，再跟服务端配合、整合，让 CLI 的能力变得更强，降低 token 消耗，给用户带来更好的体验。我觉得这是大家做产品设计时，从体验角度可以着重思考的，也可以降低用户成本。这一点非常好。
