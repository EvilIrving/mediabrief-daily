Chris：你亲身经历的就是这家吗？

Chris：也许我们先不诊断原因，继续看数据。还有什么？

Chris：你觉得这前十家里有多少是单页应用（SPA）？可能全都是吧？

Ben：我觉得数字没那么夸张，但我确实看到了这种情况。我没有大量使用所有网站，只是收集了它们的指标，但我确实看到了很多这种情况。这些是动态数据，比如你点一个日历——日历其实是我见过交互最差的东西之一。你可能会想：好，我选从这里出发、到这个目的地、大致的日期，你可以做那种七天搜索来查看航班，然后你打开日历组件，它就卡住了。显示一个日历应该是瞬间的，对吧？渲染它不应该是什么难事，客户端做也行，服务器端做也行，无所谓，它都应该立即渲染。但在很多情况下实际发生的是：他们在获取数据，然后才绘制。于是就是：点击，东西出现，获取数据，画面空着，然后也许日历上才冒出价格之类的东西。我看到的很多缓慢绘制和糟糕交互，你可以说“好吧，要获取数据，而数据有时就是不快”，我同意这一点，因为我理解这些技术怎么运作。但我不能同意的是：页面不应该位移，页面不应该在那一刻卡死。这其实就是 Web 开发本身，让页面不至于整个被挤走，其实没那么难，至少我这么认为。

Chris：很有意思。这让我作为前端 Web 开发者有点想笑：一个好的前端开发者能解决这个问题，这恰恰是他们的专长，而他们没去解决，真是令人沮丧。但也有意思的是，这大概不是框架本身的问题。我们行业里的诱惑当然是要么替 React 辩护，要么对 React 指指点点，但大概不是它的问题，大概是你用框架时做出的选择。

Ben：对，我是这么想的。我做 Calibre，它是一个让你查看性能数据的应用。所以我同样做的是一个有动态数据的应用，有图表、有列表，在数据到来之前我不知道它们会有多大，因为每个网站都不一样，对吧？而它恰好是个 React 应用。我不太喜欢写 React，但现实就是这样。但这不意味着我可以拿它当免死金牌，说“哦，因为是 React，所以网站很烂”，对我来说这不是有效的借口。以航空公司为例——不是要狠狠敲打他们——想象这样一个场景：你有一个页面，有一些动态数据，而现在很流行显示骨架屏加载器（skeleton loader）。你想让用户看到点什么，让他们知道有事在发生，然后它应该直接被内容替换。

Chris：我能想象。你经常看到这种情况吗？我有一个私下的——其实也不算私下的——看法：骨架屏加载器就是承认你输了，你被 Web 性能打败了。就把东西超快地放到页面上，没那么难，很多人都能做到。我有点开玩笑，但确实如此。我对它和加载转圈的设计对比很感兴趣，因为转圈并不暗示页面未来的结构。这几乎让我想把转圈请回来，至少我们知道它代表什么。我就讨厌那种“我们给你一个你压根不想要的东西”。它不只是个转圈，而是假内容，还指望让你开心。

Chris：是啊，没有什么比上线一个性能修复更让人舒坦的了。但讽刺的是，其中有些事也是大生意，我觉得你也想表达这一点，对吧？这些修复里大概是有钱可赚的。

Ben：几乎肯定有。我很难相信没有。我这里有一个来自 Shopify 的数据，我找找。好，Shopify 做了一项研究，他们看店铺页面加载的 LCP，发现如果你的页面在 2.5 秒加载，它的转化率会比快一秒加载时差 30%，这相当严重。一秒听起来不多，但再说一遍，这是聚合指标，有些人的体验要糟糕得多。如果还算不错的情况是两秒半，那它可能更糟。如果缓慢交互也会造成类似代价——看看像国泰航空这样的企业，去年收入是 720 亿港币，我想大概是 300 亿美元之类的，你可能得核对一下换算——我很难相信做这样的改动不值点钱。其实我曾经给澳航做过一个合同项目，几年前，我觉得说这个应该没问题。

Chris：说吧，没事，反正现在没人听这节目了。我听说现在全是 AI 垃圾内容之类的，所以我们就直接把他们筛掉。

Dave：嗯，AI 话题，我整天都在 AI。好吧，你说吧，你没问题。

Ben：好。我们有一个机制，每隔几周可以做一件自己想做的事，算是自由时间，一天的自由日，试着上线一些不一样的东西。于是我找了我的朋友，当时的首席设计师，我说：“Jazz，嘿，我们能不能让这个列表页看起来别像 1980 年代的？”因为它真的很老——这其实是酒店的页面——缩略图很小。而你订酒店时想看房间长什么样，这是第一件事，如果有好看的照片你就会点进去。于是我们整理了排版，把图片放大，简化了布局，都是些基础的东西，我们只是把布局现代化，让它在手机上不那么糟糕。他们什么都做 A/B 测试，你做的每一个改动在上线前都要经过 A/B 测试，看表现如何。所以非常注重指标，这很酷，是一种很好的工作方式。我们发现它的转化率高了大约 10%。而我在那里工作了几个月，因为各种原因延期，一直没能上线原本要做的项目，结果基本上两个下午的事情，变成了转化率高得多的东西。所以我确切知道这是真的。

Dave：我很好奇——你描述了你做过的工作——但这些航空公司网站，它们要做什么？要把 React 换掉吗？还是要削减点 CSS？你有没有深入到那个层面，比如“如果他们做了这些事，就很可能真正带来利润”？我记得 WPO Stats 就是那个收集了所有数据的老网站。我在一些非常大的产品旁边工作，那些数字是存在的，那些性能到转化、到用户的指标是存在的。所以这不是神话，就是在做科学。那么人们要做什么才能扭转他们的网站？好像是每 100 毫秒影响 10% 的转化率之类的，我不记得具体百分比了，但大概是那样。

Chris：我很喜欢我们原本还不确定能不能聊满一个小时，结果现在就到这儿了。希望我们没有陷得太深。

Ben：我想说得非常清楚的一点是：要理解性能并真正采取行动，第一件事显然是监控它。我知道我是做监控的人，我说“你应该买监控”，好像在说“你得买我的监控”。但你必须了解数字，才能对它做点什么。而你能做的最有效的事，简直就是“按最差排序”：对最受欢迎的页面或最受欢迎的元素，按最差排序。我在 Calibre 这个应用本身就是这样做的。我说过这个应用是 React 写的，我们确实有一些会到处位移的骨架屏加载器。所以我做了什么？我去找出位移最严重的页面，然后修好它们。因为是组件驱动的架构，这顺带修好了其他几处，我看着指标随时间变化。等那项工作落地、我确认完成之后，我再看一遍，选出下一个最差的东西。你完全可以对慢查询这样做，对糟糕的图片这样做，对 JSON 接口这样做，其实无所谓，只要你有时间和专注力，找到影响最多人的最差的那个东西，然后只修那一件事。即使你没有完全修好，只是改善了它，也是改善，当天就把它合进去。惯性是很有价值的，因为你可能永远没机会做那个三周的重构——那真的很难，让每个人都压力山大——但你可以做那一件小事，也许只是对 LCP 图片做一个非常简单的修复。
