两个 React The Two Reacts ｜ Overreacted, Dan Abramov ｜ 文章 ｜ https://overreacted.io/the-two-reacts/

Dan Abramov 的一篇短文，用来为 React 服务端组件铺垫思路。他从一个朴素的事实讲起：要在你的屏幕上显示东西，至少涉及两台设备，你的和我的。代码和数据起初在我的设备上，最终变成 HTML 和 JavaScript 到达你的设备。React 让我们把界面拆成组件、像乐高一样组合，但组件是代码，总得在某台电脑上运行，那该在谁的电脑上跑？他分别为两边辩护。

第一种立场：组件应该在你的电脑上跑。他放了一个计数按钮，点一下数字立刻加一，不用等服务器，因为点击次数这种客户端状态只存在于你电脑的内存里，我最多替你准备好初始的"点了 0 次"的 HTML，之后只能由你的电脑接手。有人会说可以每次点击都向服务器要新界面，以前的网站就是这样；这在点链接这类用户预期有点延迟的场景下没问题，但拖滑块、切标签、打字、点赞、滑卡片这类直接操作，如果没有即时反馈就会觉得坏了。他用日常直觉打比方：电梯按钮不必瞬间把你送到下一层，但至少要被按下去、亮起来；推门把手则必须跟着手动。所以界面必须能对部分交互做到零网络往返的低延迟响应。React 常被概括为 UI = f(state)，状态住在你的电脑上，计算界面的组件也就该在你的电脑上跑。

第二种立场：组件应该在我的电脑上跑。他展示了一张本博客另一篇文章的预览卡片，上面写着字数，网络面板里却没有任何额外请求：他没下载那篇文章，没嵌入全文，也没调 API。原因是这个组件在他的电脑上运行，读文件就用 fs.readFile，解析 Markdown 头部用 gray-matter，数字数就拆开文本数一数，因为代码就跑在数据所在的地方。列出全站文章和字数同样简单，组件运行的时间正是他上次部署博客的时刻，也就是在构建阶段跑完的。等你打开页面时，组件、文件内容、fs、gray-matter 全都不见了，你只收到渲染好的标题、链接和字数。按这种心智模型，UI = f(data)，数据只在我的设备上，组件就该在那里跑。

两种愿景各有所长，却似乎互不兼容：要计数器那样的即时交互，组件就得在客户端跑；可预览卡片原则上不能在客户端跑，因为它用的是只有服务器才有的 API，否则干脆放客户端就好了。全放服务器呢？服务器只能渲染计数器的初始状态，不知道当前状态，来回传状态又太慢，有时根本不可能，比如他的博客服务器代码只在部署时运行。于是看起来要在"客户端的 React"和"服务器的 React"之间二选一。但他指出真实的公式更接近 UI = f(data, state)，理想的编程范式应该同时处理两种情况，而不必换另一套抽象。真正要解决的问题是：如何把代表全部组件的 f 拆到两种截然不同的运行环境里，既保留 React 的长处，又能让两个环境的组件组合、嵌套。他把这个问题留给读者思考，说下次再对答案。
