Scott：欢迎收听 Syntax，这里是周一的 Hasty Treat（短节目）。今天我们要聊：为什么 node_modules 文件夹这么大？每个项目里都躺着的那个庞然大物一样的文件夹里，到底装了些什么？我是 Scott Tolinski，来自丹佛的开发者。和往常一样，和我一起的是 Wes，node_modules 大佬。

Wes：是的。在 Web 开发圈里，node_modules 文件夹体积巨大几乎成了一个梗。只要有人提到用 JavaScript 干活，它就像个出气筒："哦，那玩意儿可大了。"还有那张"地球上最重的东西"的梗图，node_modules 排在最重的位置。

Scott：就跟"CSS 里怎么居中"一样。

Wes：没错。我看了也会笑，但有时候我也会想：你最终的 JavaScript 其实并不会那么大。里面的绝大部分东西——我甚至可以说几乎全部——都不是真正会进入你的打包产物或者运行时的 JavaScript。所以我想不如做一期节目，聊聊里面到底装了什么、为什么这么大，因为大家很喜欢抱怨它大。当然确实有一些可以解决的问题，但里面有很多东西是为了让你的开发环境顺畅简单，并确保能在旧版本的 Node 等环境上运行。

那我们开始吧。先剧透一下：答案是文本。文本出乎意料地大，尤其是涉及描述信息和 polyfill 的时候。举个例子，我最近正在做 Syntax 的逐字稿，我们为每一个单词都标注了起止时间，有些文件有七兆。我当时就想，这没法在网站上加载啊，太大了。但它用 gzip 压缩效果非常好——gzip 是服务器可以发送、浏览器可以解压的压缩算法——压缩后小了十倍，具体小多少我也说不清。我还得再精简一下，但 gzip 之后大概只有 300K 左右。因为每个单词都带着同样的 "start" 和 "end" 这两个 JSON 键，哪怕出现了六千次，压缩后实际上也只需要传一次。

Scott：对。有一个常见的例子能说明文本到底能有多大，那就是日志文件。我们都遇到过：日志文件一直写、一直写，突然硬盘就满了，你还在纳闷空间都去哪了，最后发现全是往日志文件里写的文本。所以归根结底，只要是存在文件里的东西，越大就越占空间，最后可能占掉非常多。并不需要有很多多媒体文件才会出现超大的文件。

Wes：如果你用过 DaisyDisk 之类的软件，就会明白。

Scott：对，如果你是 Mac 用户，DaisyDisk 非常棒，我相信 Windows 上也有类似的东西。它是一个可视化工具，显示你所有文件夹有多大，然后你可以一层层点进去，看硬盘空间到底被什么占用了。用过这类工具的人马上就会看到，自己的缓存 node_modules，甚至各个项目的 node_modules 文件夹，在硬盘上到底有多大。它们确实占了很多空间，这也是我们通常不把它们提交到 GitHub 之类地方的原因之一——它们太大了。而且反正每次运行 npm install 都能自动重新生成。

Wes：其实我就是用 DaisyDisk 来为这期节目做研究的。我打开了几个窗口：一个是 Boss Monster，也就是我的课程平台，我把它后端的整个 node_modules 拖进去，又把前端（React 应用）的 node_modules 也放进去，还有其他几个项目，然后打开看：到底是什么大？是从哪来的？

第一类是源文件。有人往 npm 发布东西时，一般会先过一遍打包工具。你当然可以直接发布纯 JavaScript 到 npm，但很多人是用 TypeScript 写的，或者用 ESM 写的但想同时提供一个 CommonJS 版本，又或者不管出于什么原因有人用 CoffeeScript 写的，需要转译成 JavaScript。所以一般发布的是构建后的版本，但很多人并没有把源文件从发布包里去掉——可能是因为他们希望能被引用，你在 node_modules 里就能翻到真正的源码；也可能是因为大家不知道有个叫 .npmignore 的文件可以把它们排除掉。我自己也发布过几个这样的 node 模块：我在 GitHub 的 README 里放了几张截图，大概 400K，结果被打进了发布包里。这完全没必要，因为不可能有人需要在自己 node_modules 文件夹里的 README 中看那张截图。那可就是半兆了。乘以一千个 node 模块，每个人都不小心多塞个 200K，加起来就很可观了。我见过好几个 G 的 node_modules 文件夹。所以如果你硬盘空间不够了，这里是个找空间的好地方，看看里面都有些什么——尤其是你用户文件夹下（或者别的什么地方）存放缓存模块的那个文件夹，可能会变得相当大。

Scott：我个人有时候挺喜欢他们把源文件留在 node_modules 里的，就像你说的很多人这么做。哪怕它占用了我的硬盘空间，在使用第三方包时，我真的很感激能直接钻进它的源代码去深入理解，因为不是所有文档都写得很好。不仅如此，能读源代码确实让我成为更好的开发者。能读我正在用的东西的源码——尤其是组件，比如引入一个 Svelte 组件——能钻进去看看这个组件在底层（under the hood）到底长什么样，能让你更理解它的实现，以及该如何正确使用它。

Wes：说到"under the hood"，我们做过统计：我搜了最近 130 期 Syntax，我们在四分之一的节目里都说过这个词。

Scott：没错，相当可观，绝对可观。

Wes：下一类是类型定义。这一块其实挺大的。比如 AWS SDK——我的一个项目里装了 AWS SDK，光类型定义就有 14 兆。你希望你的 TypeScript 开箱即用。14 兆可能是个特例，但 AWS SDK 是一个单独的包，而 AWS 有无数个服务。我当时只是需要装转录服务的那个包，但你装的却是 AWS 上所有东西的 SDK——S3、云端，不管他们有什么。我当时就想：我的老天爷（Hokey Doodle），14 兆的类型。

Scott：我们应该统计一下"Hokey Doodle"在节目里被说过多少次。

Wes：好主意。

Scott：所以是的，你需要类型。我有点讨厌那种得自己去装类型的情况，所以很多包会默认自带类型，因为很多开发者在用 TypeScript。就算你不用 TypeScript，VS Code 也仍然会用这些类型给你提供非常好的自动补全。所以这些也占了相当大的一块。

Wes：没错。还有一部分是 source map（源码映射）。source map 其实就是从源代码到编译后代码的映射，这样调试的时候，调试器能知道问题出在实际源代码的哪里，而不是编译后的代码里。我们偶尔会看到——我前阵子还发过一条推文问：这里面这么多分号是怎么回事？整个文档里全是分号，占了很多空间。source map 真的挺离谱的，如果你打开看过一个，就知道是怎么回事。有人专门解释过 source map 里那些分号是干什么用的，我回头找一下那条推文的链接。总之 source map 文件是文本，如果你想要更好的调试体验，就必须把它们一起发布。

下一个是 polyfill。如果你希望你的 JavaScript 能在旧浏览器、旧版本的 Node 上运行，很多包会附带一个叫 core-js 的东西。core-js 是一个 polyfill 库，确保较新的 JavaScript 特性能在旧版本的 JavaScript、浏览器、Node 运行时等环境上工作。所以即使你运行的是最新的版本，它们也经常会把 core-js 作为依赖，你一 npm install，它就跟着进来了。不是每个包都这样，但 core-js 是 npm 上最流行的模块之一。我们去 npm 上看一下它……哦对了，我在 Raycast 里有个小东西，叫 npm i，是一个快速链接，我只要输入它，再输入包名，就直接带我到 npm 的页面。

Scott：我喜欢这个。这是个扩展，还是你自己写的？

Wes：不是，是现成的扩展，直接装就行。

Scott：你知道我想要什么吗？一个能链接到 Bundlephobia 的。

Wes：哦对，Bundlephobia。

Scott：Bundlephobia 能显示一个 npm 包有多大，跟这期节目挺相关的，我们可以放个链接。我自己调试要发布的东西时经常用 Bundlephobia，看看它实际有多大，或者我到底给用户发了些什么。说到 Raycast，顺便提一句：我不小心在 Raycast 里设置了一个文本片段，没想到 "sc" 会自动补全成我的邮箱。现在我只要打带 "sc" 的单词，它就会自动补全成我的邮箱，把我气得够呛。我马上就去删掉它。

Wes：我所有的文本扩展都用冒号做前缀。

Scott：哦，这样就永远不会……你怎么这么聪明？

Wes：我这么做大概有十年了，非常好用，因为极少会碰到意外触发展开的奇怪情况。就是冒号再加上缩写，我所有的扩展都带这个前缀。你也可以用别的，比如加号之类的，但我用冒号。我有一个触发词是 cc，用来输入 Braintree 和 Stripe 的测试信用卡号。

Scott：哦天哪，冒号 cc。让我说说我在 BetterTouchTool 里做的东西。BetterTouchTool 可以让你编排一连串动作。我设了一个：按 Hyper+S，它会粘贴 Stripe 的测试信用卡号 4242 4242……，按 Tab，粘贴月份和年份的有效期，按 Tab，粘贴 CVV，按两次 Tab，填入邮编，再按 Tab 然后回车提交。如果你在测试 Stripe，就会这么干。

Wes：是啊。只要你测试过信用卡号之类的东西就知道：填一次，不行；再填一次，还不行；再填一次……最后就变成那种得一遍又一遍重复的流程。

好，回到 node_modules。我们说到哪了？polyfill。哦，还有 Babel。几乎每个 node_modules 里都有 Babel 插件，而每一个 Babel 插件都包含大约 8K 的代码，却有将近 860K 的类型定义。我没完全搞明白原因，我猜是因为每个 Babel 插件都带上了其他所有 Babel 插件的类型。总之每个 Babel 插件里都有将近一兆的类型，这可不少，因为一个项目里可能有 20、30、40 个 Babel 插件，那轻轻松松就是 30 兆，每次安装都加到你的项目里。

Scott：这可真夸张。我之前完全没意识到。

Wes：我也没有。所以我才喜欢 DaisyDisk，直接拖进去就能看到："哇，我都不知道这东西在这里。"因为你几乎从来不会去看实际导出发布的内容。你在 GitHub 上看到的，并不是实际发布到 npm 上的东西。现在 npm 终于有了个功能，你可以点开一个标签页查看代码，看看里面有什么，它也会告诉你各个东西在哪，但做得不太好，我真希望它能更好一点。

Scott：是啊。而且我们现在生活在一个同时存在 ESM（ES 模块）和 CJS（CommonJS）的世界里，它们并不总是那么兼容。应对这个问题的一种策略就是两种都发布，这就又是在重复文件、重复同样的东西：同一份源代码编译出来，提供两种不同的导入方式。于是我们发布 ESM，也发布 CJS，大家都满意了，但文件数量翻了一倍。

Wes：对，这就是生态现状，你得让包在两种模式下都能用，所以每个包实际上发布了两个版本，有时甚至发布三个版本。

Scott：三个版本是出于什么原因？

Wes：我想可能是一个浏览器版本、一个 Node 的 ESM 版本、一个 Node 的 CommonJS 版本。有时候甚至还有一个可以直接用 script 标签引入的版本。挺疯狂的。

下一类是 Markdown。还是那句话，文本占了很多空间。我打开了 Boss Monster 播放器的那个 React 项目，搜索了所有 Markdown 文件，加起来一共 10 兆的 Markdown：README、许可证——开源代码必须附带许可证，这算是规矩吧，你不能直接把它们删掉，许可证规定了你可以再分发代码或者链接回代码，所以许可证必须一起带着——还有每一处改动都记录在案的变更日志、README，所有这些。

Scott：挺疯狂的，这也很可观。还有翻译：如果你用到国际化之类的东西，会有多少种语言？

Wes：是的，TypeScript 光是翻译字符串就有四兆。

Scott：哇，我发现我一直在想：哇，这些都很可观。所有这些在任何时候都不是我们实际在用的代码的东西，干脆全扔了得了。

Wes：是啊。比如你想知道"这个类型没有足够的重叠"是什么意思——就是你想转换某个东西的类型、做类型断言时，它告诉你不能这么做的那种错误——他们有土耳其语版、中文版，还有其他所有语言的版本。你装 TypeScript 的时候，不会想"哦我现在装 TypeScript，顺便去把它的中文翻译也装上吧"，它就是得开箱即用。所以每一个安装 TypeScript 的人，都会得到它被翻译过的每一种语言，那就是四兆。这些东西单个都不算大，TypeScript 的翻译差不多都能塞进一张软盘里，并不大。

Scott：是，但它们加起来就多了。说到这些，倒让人好奇：pnpm 或者其他安装工具能不能提供某种配置选项，把特定的东西删掉？当然，这听起来是个挺棘手的事。

Wes：嗯。

Scott：想象一下，如果有个包安装器能自动删除所有 changelog、README 或许可证文件；如果你是 ESM 项目，就自动删掉 CJS 版本；自动删掉我们今天聊到的那些你可能用不上的小东西。

Wes：我觉得那大概是个坏主意，谁知道呢。我觉得你会碰到问题，因为没有人真正知道该怎么删——甚至没人知道自己导入的是 CommonJS 还是 ESM，它们根本不知道该导入哪个版本。如果只是 changelog、README、许可证这些，自动删掉倒是可以，但大概省不了多少空间，没什么区别——当然也许会有点用。而且 pnpm 本来就已经帮你省了很多空间，因为它只是把包链接到你电脑上已经装好的版本，而不是一遍又一遍地复制同样的代码，这也是为什么 pnpm install 比普通的 npm install 快得多。

Scott：没错。

Wes：那么，面对这一切疯狂，解决办法是什么？现实是，这些代码几乎都不是真正运行你的应用所需要的。所以首先：放轻松，这并不是什么大不了的事。

Scott：对，确实。

Wes：其次，打包你的代码。如果你确实在意最终产物是什么样子，你可以把代码打包后再发布。举个例子——我们之后会有一期节目讲这个——Node 现在允许你把整个应用打包成一个单独的可执行文件，里面包括你的代码、Node.js 运行时，以及你所有的依赖。如果你担心"这个东西必须尽可能小，不能把 4 兆的 TypeScript 翻译塞进最终产物"，那你只需要用任意一个打包工具——Vite、esbuild 之类——处理一下你的代码，出来的东西可能连一兆都不到，也许就 50K、100K，取决于应用有多大。真正运行你应用的代码，和其他那些东西比起来根本不大。

Scott：是啊，说到底这些都不怎么重要。

Wes：我的电脑有 2TB 硬盘，几百兆算什么？

Scott：哦天哪，我以前用 1TB 的时候真是挣扎。不过那也是因为 Wes 和我是靠录视频为生的，对吧？

Wes：对，你想看什么占空间大，那就是视频。真的，我一小时的录屏可能就是 30G 的文件，太离谱了。然后我们却在这里抱怨区区四兆的翻译字符串。

Scott：我跟你说，我从 2004 年左右——甚至更早——就开始做视频了。那时候我的硬盘只有 40GB，做任何视频相关的事都很痛苦。我当时有一个 LaCie 的 200GB 外置硬盘，那简直是全世界最棒的东西，因为我突然可以同时做不止一个视频项目，而不用删掉旧的了。能有这么大的空间真是太好了。后来换成 SSD，苹果想卖给你一台 256G 的电脑，对于做这类事来说简直是个笑话。不过现在 SSD 价格多少降下来了，虽然苹果对 2TB 的收费还是贵得离谱，但能把过去一年做过的所有项目都放在电脑上真的很爽，其余的我就归档。这个我们改天另做一期节目聊。

Wes：总之，还有什么办法？使用 .npmignore；给别人提 pull request，说"嘿，我觉得你不需要……"——我自己就收到过几个 pull request，说你不需要把这个 README 或者这些图片发布到 npm。所以你可以加一个 .npmignore。使用 pnpm，这个我们聊过了。当你放弃支持旧版本的 Node 或旧浏览器时，记得清理相关的东西。这方面 Babel 的 preset-env 很擅长：你告诉它你要支持哪些浏览器，它会算出你需要哪些 polyfill，不会再多加。

Scott：对，你也可以直接用 pnpm。不过它不一定适合每个人，因为更换包管理器需要一定的投入。但说真的，我已经用了 pnpm 一段时间，迁移过程并不痛苦，可能这里那里有几个小问题。pnpm 的做法是把所有包存放在你用户目录下的一个根文件夹里并缓存起来，这样每个包你只需要下载一次，然后它对所有东西做——叫什么来着——符号链接（symlink）。如果你有 monorepo，它也是用符号链接，始终用符号链接把所有东西连在一起，这样就不会在你的机器上把同一个包装一百次，可以说每个版本只装一次。所以 pnpm 是个很好的方案，而且正因为如此它非常快，需要下载的东西更少；它也更高效，不需要占用那么多硬盘空间，另外还有很多很棒的功能。所以如果你是 Yarn 用户或者 npm 用户，真心推荐试试 pnpm，切换过来非常简单，我想你会喜欢的。对我来说这是个不错的转变，我已经用了绝对超过一年半，只有好话可说。

Wes：最后还有一个叫 npkill 的工具。你只要运行 npx npkill，它就会在你的硬盘上搜索 node_modules 文件夹，告诉你每个项目你上次是多久之前动过的，以及这些文件夹有多大。如果你想腾出一些硬盘空间——我记得我第一次用它的时候，之前从来没清理过，那是我有史以来第一次清理，一下子删掉了 30G 的 node_modules，相当可观，挺大的了。这很棒，因为你随时可以把它们找回来，随时 npm install 一下就全回来了。如果你需要更多空间，这是个加快、清理电脑的好办法。另外，用一条简单的命令行也很容易做到：find 查找 node_modules，直接找到并删除电脑上所有的 node_modules，非常——

Scott：是啊，实验文件夹这个，说实话还是让我有点害怕。我知道它没问题。但我喜欢 npkill，它的界面是最好的：用方向键选择，按空格删除，我不需要别的。

Wes：哦天哪，太棒了。
