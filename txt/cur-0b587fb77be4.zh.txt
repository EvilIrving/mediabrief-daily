软件之所以慢，是因为设计糟糕，而不是因为语言慢

很多人说，AI 会通过把软件改写成更快的语言来让软件变快，但这通常并不成立。大多数程序无法通过改写成 C 或 Rust 来获得有意义的提速。

这怎么可能呢？有些语言比其他语言快上几个数量级：例如，C 可能比 Python 快五十倍。那么，把我的 Python 程序改写成 C，不就能让它快五十倍吗？不，并不会。软件性能通常由 I/O 主导，而不是由语言的速度主导。在语言速度确实重要的地方，大多数慢语言都已经有了流行的库，让它们能够释放出接近 C 的速度。总的来说，性能是设计问题，而不是语言选择问题。

### 大多数真实程序都是 I/O-bound 的

设想一个带数据库的简单 CRUD 网站。对于任意一个请求，请求时间的 50%[1] 可能花在查询数据库上：获取当前用户、被请求的记录、任何相关的用户成员关系或设置，等等。用 C 重写那个网站只能加速另外那 50%，这就给你能取得的改进设下了一个硬上限[2]。最好的情况下，你能让请求快一倍（实践中大概更接近 1.5 倍）。这不算差，但远达不到一个数量级的提速。

换句话说，大多数真实程序都是“I/O-bound”（I/O 受限）的：它们把大部分时间花在等待数据从某处输入或输出，而不是像“CPU-bound”（CPU 受限）程序那样把大部分时间花在主动做事上。I/O-bound 程序并不一定只依赖数据库。程序常常要等待某个第三方 API，或者等待把数据写入磁盘或从磁盘读取。你可以把 curl 里的代码加速 100 倍，而你大概根本不会注意到，因为 curl 把所有时间都花在等待网络上了。

### 慢语言已经把工作委托给快语言

那那些明显不是 I/O-bound 的工作呢？例如，wiki 必须把存储的 markdown 转换成可渲染的 HTML[3]。用更快的语言重写这部分，难道不会带来巨大的提速吗？会的！这就是为什么做这件事的应用会使用像 cmark-gfm 这样的库，它们调用快速语言来完成 markdown 渲染。总的来说，大多数慢语言都能通过调用这类库来写出非常快的程序。Python 是出了名的慢语言，但对于机器学习和数学这类 CPU-bound 工作负载，它却是一个有竞争力的选择，因为它有一套健全的库，可以把这些工作负载卸载到快速的 C 代码上。如果一个 Python 程序把 80% 的时间花在 GPU 上做矩阵乘法，你极不可能通过把它改写成 C 来加速它，因为那些矩阵乘法已经是在高度优化的 C 或汇编代码里进行的了。

当然，有些程序确实用慢语言做了大量 CPU-bound 的工作。如果一个程序没有受到多少工程上的关注，那里可能有很多唾手可得的成果（low-hanging fruit）。但这些程序往往并不重要：如果它们重要，早就会有人在 AI 让这件事变得（相对）容易之前，进去把它们优化掉了。这并不意味着不可能找到一个有用的程序来重写。Actual Computer 最近用汇编重写了 tiktoken，带来了显著的[4]提速。然而，你并不会以此革新某个计算领域。即便是快速的 tokenization 也只是在边缘上有用，因为花在 tokenization 上的时间只是花在推理上的时间的一小部分。

### 加速软件通常涉及重新设计

尽管如此，我认为大多数软件都远比它本可以做到的慢得多。对于（无论有没有 AI）大幅加速常用软件的潜力，我是乐观的。但我认为这些提速中的大多数将来自重新设计程序，而不是用更快的语言重写它。

在 2018 年的一篇文章中，布莱恩·坎特里尔（Bryan Cantrill）描述了他尝试把一个 C 程序重写成 Rust 的经历。这很难，因为那个 C 程序精心优化的设计与 Rust 的 borrow checker（借用检查器）配合得不好。他放弃了，干脆用最朴素的方式用 Rust 写了这个程序，预计会慢 20% 甚至更多。结果它反而快了 30%。原因归结为 Rust 内部偏好使用 B-tree 而非二叉搜索树，而这恰好是一种对缓存更高效的数据结构。所以，即便是在一个很大程度上是 CPU-bound 的工作负载中，在一位非常擅长写快速 C 的人手里，性能也是由设计主导的，而不是由语言速度主导的。

这与我本人在更高层语言中的经验相符。当我回想我实现过的那些显著提速时，它们几乎无一例外都是对软件进行重新设计，让它做更少的工作：

- 缓存一个慢操作（通常是外部 API 调用）
- 异步执行慢操作，要么放在后台任务里，要么移出请求/响应生命周期
- 并行执行操作而不是顺序执行（有时为了做到这一点，会把大操作拆分开来）
- 用单条 SQL 查询替换一组 SQL 查询（修复 N+1 问题）
- 用快速的 SQL 查询替换慢速的 SQL 查询
- 跳过不必要的慢操作（例如在分页视图中，只从当前页上的实体获取辅助数据）

所有这些策略都与语言有多快完全无关。事实上，用慢的高层语言来写，反而可能让优化代码容易得多，因为你可以一眼看出程序在做什么。如果（出于某种原因）我先用汇编重写了那个 web 服务器，我要注意到那个 N+1 查询，或者注意到我们可以把某个 API 调用移进一个任务里等等，就会困难得多。

### 结论

现在，每个人都在让他们的 AI agent 用 Rust、C 或汇编重写程序。这很有趣，但这不是一次严肃的优化尝试。能通过这类重写获得有意义提速的程序集合非常窄。

如果你想用 AI 让一切都变快——你应该这么做！——那你反而应该让你的 agent 去对程序做性能分析（profile），找出热点（hotspots），并提出重新设计程序所做之事的方法。偶尔你可能会遇到一个真正是 CPU-bound、且无法重构为做更少工作的热点。在这些罕见的情况下，用更快的语言重写那一部分会有帮助。但一开始就简单地重写，其成功率会远低于大多数人的想象。

用另一种语言重写软件有很多好理由：可移植性、效率、可维护性等等。但就纯粹的原始速度而言，你最好把注意力放在程序的设计上。

edit：这篇文章在 lobste.rs 上得到了一些很精彩的评论，大多是批评性的。

许多评论者不同意 CRUD 软件是 I/O-bound 的，因为数据库查询只需约 5ms，而响应要花约 500ms。这是一个经验性问题，而我对此的立场来自我盯着成千上万个 Ruby flamegraphs（火焰图）的经历。单个请求发出几十甚至上百个查询，或者依赖比 5ms 慢得多的大查询或内部 API 调用，这种情况并不罕见。不过，虽然我在职业生涯中分析过大量 Rails 端点，但那只是在几家公司里。也许其他的单体应用（monoliths）不一样。

得票最高的评论者说，有很多非 I/O-bound 的程序，比如浏览器布局引擎、3D 渲染器、文字处理器和神经网络。我同意这些例子是 CPU-bound 的，但我认为大多数工程师并不是在做那样的任务。我的感觉是，全世界浏览器布局引擎、3D 渲染器和神经网络程序的数量加在一起，可能只占 CRUD 程序数量的百分之五左右（尽管它们占据了关于编程的公开讨论的 >50%，因为它们是更有趣的问题）。也许我错了！

其他评论者指出，语言自带生态系统，这会让性能变得更难或更容易。我同意这一点，但在我看来那属于设计范畴：在某些语言中，快速的设计比慢速的设计更自然。如果换语言让改变设计变得更容易，那么当然，换语言可能会加速你的程序。

无论如何，我确实认为我的观点在经验上是站得住脚的：如果你带着一个 LLM 到处去尝试“通过把软件改写成 C 来让软件变快”，你会遇到一些相比重写已经优化得惊人地好的软件，或者遇到无法轻易加速的 I/O-bound 工作负载，而你反而应该告诉你的 LLM“通过重新设计软件来让它变快”。

[1] 这个数字可能看起来高得离谱（如果你通常处理的是慢语言或 CPU-bound 工作负载），也可能低得离谱（如果你不是）。根据我的经验，对于解释型语言，它至少是八九不离十的。

[2] 这在形式上被称为 Amdahl's law（阿姆达尔定律）。

[3] 为什么不直接存储 HTML 呢？你可以这么做，但有时 HTML 的内容因用户而异（而且即使你存储 HTML，你也至少得转换一次）。

[4] 他们声称比 tiktoken 快 4-23 倍，而在我的笔记本电脑上它确实快了约 5 倍——不过可以说，这一提速来自避免依赖 regex 的重新设计，而不是来自 Rust 配合 Python 绑定的任何内在缓慢。
