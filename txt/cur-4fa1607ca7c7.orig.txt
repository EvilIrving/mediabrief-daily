我对几个大厂的 Cloud IDE 还算比较了解，跟这些同学都比较熟。我来字节的时候发现了一个让我有点惊讶的情况：Cloud IDE 这种东西，我看到很多国内大厂更多只是外包在用，正式员工其实没在用。但在字节这点不同，我们有非常多的正式员工在用，我有亲身感受。去年有一段时间资源不太够，自上到下很多人来 push 我们，比如说"你这个地方的性能和稳定性要给我做好"，而不是我们主动去跟人说"你要用我们的产品"。

主持人：你能帮我们分析一下为什么在字节里能推开吗？Cloud IDE 这件事，我们自己之前都是做开发的，毕竟它是网上的东西，总觉得不够丝滑、不够顺手，跟内部的文件等东西交互起来也不是特别顺畅。至少我们以前不管在阿里内部还是别的地方，感觉即使做了，大家用得也不多。你到字节看到内部有很多人在用，背后的原因能不能跟我们分享一下？

天猪：我只能代表自己的观点，这也是我观察来的。我觉得有各方面的原因。每个公司的开发者心智、业务和基建之间的关系其实都不一样，这块我感受挺强，因为我之前在阿里做 Node Infra，在字节也做 Node Infra，做事方式包括做出来的产品都是不一样的。至于 Cloud IDE，可能有点片面的原因：比如字节做算法的人比较多，很多情况下他们要做各种联调，就会有更多在线的要求，不然本地机器的规格跟不上；然后还有一些合规之类的考虑。当然这可能有点片面，只是我个人的猜测。但我看到的现象确实是有这么多用户一直在用，而且在 push 我们去优化。

主持人：你知道我的 Cloud IDE 使用场景是什么吗？我就希望能在 iPad 上写代码。

天猪：这个地方我想展开一点。每次看到别人把 Cloud IDE 和 Web IDE 画等号的时候，我都会跳出来反驳。我个人认为 Cloud IDE 不等于 Web IDE，我理解的 Cloud 是 anywhere，就是你随时随地都可以编程。我们去看一个 IDE，它其实有两个组成部分：一个是你能看到的 UI 层，这一层可以跑在本地的 Electron 里，也可以跑在 Web 浏览器里，还可以跑在 iPad 等移动端上；后面的容器，可以是本地硬盘，也可以像 StackBlitz 那样是浏览器里的 WebContainer 模拟，可以是本地的 Docker，当然也可以是像我们做的远端 K8s 容器。所以我觉得 Cloud IDE 的形态其实是在各种地方去用的。我们前面说的狭义的 Cloud IDE 也就是 Web IDE，它更多是一个切入点，但未来包括我们现在做的东西，其实是连通在一起的。这也是为什么 MarsCode 和 Trae 其实是由同一个团队负责，它们不是两个割裂的产品。

五花肉：我想补充一下上一个问题说的服务企业客户。这可能是我们推豆包 MarsCode 时和通义灵码等友商的优秀产品不一样的一个点：我们会更偏个人一些，而不是以 to B 的模式在做。所以你也可以看到，我们去年做的一些事情，更多在强调激发创意等案例和场景。这可能是和国内其他同类插件形式产品比较不一样的地方。

主持人：了解。那我接着问，我们今天聊的核心还是 AI。如果没有 AI 这件事，今天的 Cloud IDE 跟 5 年前、10 年前的 Cloud IDE 区别可能不是很大，只不过后端层面今天用上了 K8s、有自己的 container 等等。回到 AI，我觉得 AI 这件事起来，应该是从 GitHub Copilot 开始的吧？它先有了一定的补全能力。后来 GitHub Copilot 是收费的，10 刀一个月，如果你做开源可以免费用，后来又推出了免费版。之后还有 Tabnine、Supermaven 这类产品，它们一开始都是做 AI 补全的。但当时大家的补全都是顺序补全，比如单行补全，或者稍带一些多行补全。以前给我们的感觉是 GitHub Copilot 挺好用，但属于甜品级，不是杀手级——用上它能帮我补全一下，用起来还挺爽，但不至于离了它就不能编码了。大概从去年 10 月、11 月开始，Cursor 接了 Claude 3.5 之后，这个趋势就一发不可收拾了。不知道你们内部有没有分析过，为什么 Cursor 接了 Claude 3.5 之后突然就爆火了？你们觉得 Cursor 最核心、最革命性的东西是什么？

天猪：这块可以展开聊聊，这个领域我观察挺久了，挺有意思。在 AI Coding 领域，从我的观察来看，过去几年基本上每个月都在刷新我的认知。我记得半年前你们也有过一期关于 Cursor 的讨论，我也听了，当时还想有些点想补充一下，今天有机会也挺好。

先回答那个问题。我觉得 Cursor 去年比较火，主要原因是基础模型有了比较大的突破，就是 Claude 3.5 Sonnet，包括今天出来的 3.7，让 Cursor 过去做的很多事情被放大了。但只有模型能力是不够的。Cursor 和 Codeium 这些产品不是突然冒出来的，它们在这个行业里持续做了很多事情。它的成功在我看来更像一个厚积薄发的过程。

讲整个演变过程的话，我经常把它比作自动驾驶：L1 是人工编程，L2 我称为 AI 辅助编程，L3 是 AI 结对编程，L4 是 AI 驱动或者说主动编程。去年那个时间点刚好到了 L3 结对编程这个阶段。我继续展开讲，中间如果有问题，我们随时展开再聊。

前面大家感知比较多的点是代码补全。早期我们写代码，更多是代码提示，也就是一个下拉框，告诉你这个对象有哪些属性和方法。那个阶段做得比较好的是 Tabnine 这些插件。ChatGPT 出来之后，我们知道大模型的本质是预测下一个 token，相比自然语言，编程语言更简洁严谨，而且是可预测的。所以我们看到了 Copilot 的横空出世。它在代码补全上有一个极大的创新，就是很令人惊艳的 Ghost Text 交互方式：刚才说代码提示是下拉框，而 Copilot 是直接显示一段浅色的文字，你只需要按一下 Tab 就能快速采纳。这对程序员的多巴胺刺激是非常强烈的。不过 Copilot 刚出来的时候，只是针对新增代码的补全。

接下来我们看到，像 Codeium 和 Cursor，它们的下一个创新点是 Supercomplete，或者叫 Super Tab。创新在于：前面是预测你的下一个字符，现在变成了预测你的下一个编辑位置，从新增代码变成了可以修改存量代码。一个很直观的例子：比如我们写前端，有一个地区下拉列表，一开始你全写成英文，后来想改成中文，你改完第一行之后，它就能智能地提示下面所有的修改，你按 Tab 就全部改好，而不用一个个去改。这个我们叫超级补全。这是目前在代码补全方向上两个比较大的里程碑。所以从代码提示到代码补全，再到超级补全，这是补全能力的演进。

主持人：我想问一下，在补全层面，你刚才讲的 Super Tab，在 Codeium 和 Cursor 里它具体做了些什么？如果每按一次 Tab 都去调 ChatGPT，后面的用量费用会不会比较高？

天猪：这里其实会有很多专项训练。具体细节我可能说不太出来，因为模型训练我做得不多。我了解到，他们很多是拿 GitHub 上大量的 commit 去做训练，所以能学到修改的差异。这块原理我讲不太清楚，但门槛其实不低，你现在可以看到，能把这块做好的产品其实不多。

主持人：你刚才讲的有一点挺有意思，你不讲我还没意识到：大家是在用 commit 去训练。我们写 PR 的时候，其实写的就是 GitHub 的 commit message。我写 commit message 的时候，是在描述我想干什么。一般来讲，一个比较好的 GitHub repo，commit message 写得都比较好。如果能根据 commit message 反向训练它具体 diff 了什么代码，这样训练出来准确度应该会比较高。我突然觉得就应该这样训练，而不是只拿着 repo 去训练。因为我们知道 AI 训练时需要一个奖励机制或者判断机制，GitHub 上这些优秀仓库的 commit 或者 PR 其实就是最优质的数据源。

天猪：对，是的。

主持人：这种 public 仓库本身就会写好，因为它是 public 的嘛。像我的私人仓库，全都是 WIP，work in progress。

天猪：刚才聊的是代码补全，但在 AI Coding 里还有一个比较重要的概念，就是代码生成。举个例子，ChatGPT 刚出来的时候，我记得当时很震撼的一点是，在 ChatGPT 里跟它对话，它就能生成一个算法。但我们发现，在 ChatGPT 里你需要人肉跟它对话，再复制回 IDE，这边改完再复制给它，这个过程比较繁琐。所以很快 IDE 里就出现了一个东西叫 Side Chat，就是在左边或右边有个对话框。这个阶段更多是以插件的方式，比如 Copilot 有个 Chat，Codeium 也是以这个起家的。它的优势是什么呢？它直接在 IDE 里，可以拿到代码仓库的上下文，包括用户当前在 IDE 里的一些信息，比如你在哪一行，不需要人肉喂给 ChatGPT。

这看起来好像很高大上，但原理其实很直白。比如一个常见的例子，你在右边侧栏跟 AI 说"帮我把这个 HTTP 请求函数实现一下"，它背后就是拼一段大白话的 prompt：用户正在打开某某文件，光标在第几行，这一行的函数名是什么、注释是什么，最近他访问过哪几个文件，整个目录结构是什么样子，他要你干嘛。拼成这样一段大 prompt 丢给大模型，大模型根据需求生成回来，你再把代码合并进去。其实跟人肉没什么区别，但 IDE 能帮你把合适的上下文组装起来，这样比前面确实进了一步。

这里的技术含量在于，比如项目的理解能力：整个大仓库，你怎么更好地理解这个项目；还有上下文，我们刚才说要拼这么多东西，你得把合适的给它。因为现在 AI 的注意力还不是很好，你怎么把合适的上下文裁剪后给它？多轮对话之后，你怎么把上面的一些历史裁剪压缩，再放到一起？然后还包括模型能力，以及工程上的 prompt engineering 能力。Cursor 在这块最早做出了突破，因为它做了很多工程上的事情。大家刚才也提到，Claude 3.5 Sonnet 功不可没，它代表模型到了一个里程碑，从而在去年上半年掀起了第一波热潮。到了这一步，开发者可以在 IDE 里跟 AI 共享同样的上下文，不需要再转述。

接下来的一个创新点是什么？AI 生成了代码之后，你怎么把这段代码合并回各个文件里去。这里有几个点。第一个是你让 AI 生成什么样的代码：是整个文件全量生成，还是生成一个片段，还是生成 git diff 这种格式。这就涉及写回去的实现方式。我们可以看到 Cursor 和一些开源项目，一般有全文重写、搜索替换代码片段、git 合并等各种方式，业界一般是把这几种结合起来实践。Cursor 自己训练了一个 Fast Apply 的小模型，我们也有自己训练的这类模型，专门针对这种场景。这样前面让 AI 生成的时候，可以让它返回一个特定格式的代码，整个 prompt 包括 token 的消耗都会少很多，再通过这个小模型把它合并到合适的文件里。

演进到这个阶段，我把它称为 L2 阶段，也就是 AI 辅助编程。可以看到不管是代码补全还是右边的对话，它都在辅助你：辅助你生成代码，你再一键合并进去，这个阶段都是辅助。这是我观察到去年上半年时的状态。再往下一个阶段，就是 L3 的 AI 结对编程阶段。

主持人：OK，了解。你刚才讲的一点让我才发现，为什么我们在 ChatGPT 里或者 Sonnet 里写 prompt 生成的代码质量，不如你们在 IDE 里生成的代码质量。你刚才讲了你们内部是怎么拼 prompt 的，很多信息我们其实并没有带给 Sonnet，比如我打开过哪些文件，现在在哪一行，光标在哪个位置，我的函数是什么，全部告诉它，再告诉它要干嘛，前置信息足够长。但我们自己一般写的时候，就说"我想实现一个什么什么函数"，就结束了，效果可能就跟你们的有很大区别。我觉得你讲出了一个很细节的东西，真正做的时候才知道。我们老想着 prompt 随便写一写，好像大家生成出来效果都差不多，但仔细一想，跟你们的生成效果还是区别很大的。那要不然继续跟我们分享一下 L3 吧。

天猪：OK。L3 这里有个词叫 Agentic Flow。Agent 这个词最近大家都在说，2025 年是 Agent 元年。其实在去年年中到下半年，出现了几个产品，Cursor 最早出了 Composer，然后有 Windsurf，还有我们的 Trae Builder，在这个领域就有竞争了，我把它称为 Agent。怎么理解这个东西呢？前面的代码生成都是一问一答的单轮：你问一下它回给你，虽然有 Fast Apply，但你要手动操作，它可能回复说这几个文件要改，你就一个一个点 Apply，它帮你合过去，也就是要人工去确认。

那我们反过来想，我能不能跟它说一个大一点的事情，它帮我拆成 proposal，做一个需求分析，再根据需求拆解出一个 plan，也就是执行计划，然后根据这个计划一个一个去生成代码、去执行。生成代码之后，比如前端，我生成了 package 依赖之后，它能不能再进一步帮我执行一个指令，比如 npm install 去安装依赖；装完之后能不能帮我启动一个本地服务，npm run dev；启动完服务后，能不能帮我把浏览器打开到这个页面；打开之后我在这里操作，浏览器或者前面 npm install 运行时报错了，这个错误信息它能不能自动帮我分析，然后帮我修复？整个听起来是很智能、很让人兴奋的。这就是目前我认为的 L3 阶段，你会觉得就像一个实习生在你旁边跟你结对编程。你只要跟他说做这个事情，他去拆解，中间要做的事情他啪啪啪自己就做了，但中间有一些点会让你来确认，比如要不要执行这个指令，你看看效果怎么样。这就是我认为的结对编程。

这里很多人也会提到一个产品叫 Devin。我认为 Devin 瞄准的是 L4 阶段，也就是下一个阶段：AI 主动或者驱动编程。这两个阶段有什么区别？先说共性：L3 和 L4 比起前面的 L2，AI 多了几个能力。第一，它有了思考能力和调度能力，你给它一句话，它可以去拆解，像前阵子大家熟悉的 R1，可以去思考。同时在 IDE 里，它还多了两个能力：上下文环境的感知能力和工具调用能力。也就是说，它能感知到自己所处的环境，比如编程环境、代码的上下文环境，然后根据你给它的目标进行思考和拆解子任务，同时可以调用我给出的各种工具去帮它实现任务。这是两个阶段的共性。

不同点在于 AI 的自主性程度。像我们的 Trae Builder 或者 Composer，我经常这么形容：AI 目前是一个高潜的实习生，他很聪明，但还不够成熟，对公司里很多相关东西还不熟悉。所以这个阶段只能说我跟他一起结对编程，这样更具备可控性，也不会打破程序员以前的工作流，用这种方式可以把我们的效率提上来。Devin 更像是试图一步到位：这个 AI 已经是一个三年以上经验的社招 superstar，我给你安排任务后就别管了，你自己回去做，最后过一天或者多久给我提交回来。听起来很性感，但当下不管是工程还是 AI 的能力，都还不足以支撑它独立完成任务，所以只能说未来可期。

我记得当时调研 Devin，还调侃过一件很好玩的事。它是 500 刀一个月嘛，调研完后我就把它取消续费了。我跟别人说，我感觉这家伙做事又慢，效果也不太好，500 刀的月薪不太值，感觉就像解雇了一个未来可期但现在还不太合适的大厂员工，因为这个钱我可以去雇 25 个 Cursor 或 Windsurf 这样的小员工嘛。结果对方说：没关系啊，解雇的人你随时可以把他抓回来，等他能力强了再雇回来。我当时一身冷汗：老板看我们平时摸鱼是不是也这种感觉？

总结一下，以上 L1、L2、L3、L4，就是我目前对 AI Coding 各阶段的理解。现在整个业界包括我们，正在往 L3 这个 AI 结对编程方向走向深水区。这也是我觉得比较幸运的一点：在这个大争之世，能跟这么多聪明的同行者一起竞争，身处其中，其实挺兴奋的。
