Ryan：嗨，谢谢邀请。

Amal：我们很兴奋。你之所以是思想领袖和意见领袖，是因为你创造了 Solid，而且我们看到 Solid 里的很多 API 和功能正在整个生态里遍地开花，这非常棒。今天请你来，一方面聊聊 Solid，但我更想大范围地挖一挖 Solid 背后的一些原则，特别是为"响应式"（reactivity）正名。这个东西现在到处都是，Signals 也到处冒出来。我想聊聊真实的使用场景、优缺点……它不只是关乎性能，那还有哪些别的好处……今天要聊的很多。不过在进入这些话题之前，先请你做个自我介绍吧。你 2022 年上过我们节目，欢迎回来。给不熟悉你的听众讲讲你自己。

Ryan：好。你已经提到我创造了 Solid.js。我做 Web 开发已经很久了，从十几岁给我的乐队做网站就开始了。后来我在创业公司当产品工程师，然后某个时候我在业余时间决定写一个 JavaScript 框架，因为 JavaScript 框架的潮流已经偏离了我喜欢的方向。正如你提到的，响应式对我来说一直是——也不算一直，我其实是 2010 年才真正接触到它。但一旦"染上"了，我就一直坚持往前推。然后到了 2014、2015 年左右，一切都变了，人们不再那么热衷响应式库了，React 这类东西大行其道。我想继续做我喜欢的事，于是决定尝试把响应式的做法现代化，写出了 Solid.js。之后我意识到，因为生态变化太大，仅仅几年之后就几乎没人了解这些东西了，所以我花了大量时间做教育：写文章，后来做直播、教学……这成了我工作中很大的一部分。这就是我。我是"Signals 那个人"。

Amal：没错，更准确地说你是"Signals 的 CEO"。江湖上都这么叫你。

Nick：Ryan，我很好奇。照你这么说，React 的出现——不是要替你说话——好像让你挺扫兴的？在那之前你用的是什么？

Ryan：我用的是 Knockout.js。它确实挺混乱的，但有很多好东西。到了那个阶段，性能基准测试、各种范式之争纷纷出现，我感觉风向真的变了，流行的方案不再像 Knockout 那样工作，某些东西可能被过早地否定了。这事挺微妙的，因为在 React 出现前后，最流行的框架大概是 Angular，还有 Backbone 之类的……

Nick：我当时是 Backbone 阵营的。

Ryan：对。还有 Ember，它也有响应式。但人们对这些系统所做的某些假设——有些非常合理，有些我却不太认同。我一直看到那些性能基准测试，不仅场景在我看来很不现实，比如有人说"我的框架很快，因为我每秒能把整个数据库往页面上倒一百万次"——没人真想这么干。你想要的是通过网络少传数据，尽可能少更新，而不是暴力硬算。但当时就是那种心态。说实话，React 非常擅长把一件极其低效的事变得稍微高效一点。换句话说，React 很擅长给"性能能有多差"设一个下限。但要真正让东西变快——那是另一回事了。

Amal：对，我们深入聊聊这一点。我还是想把重点放在原则上，所以先简单给大家介绍一下 Solid 的基本情况：它是什么？和 React 这类工具有什么不同？对我来说 Solid 最酷的一点是它有多快。目前"市场"上比 Solid 更快的只有直接写原生 JS。开销极低，而原生 JS 也只比 Solid 快那么一丁点。当然，用 Solid 这样的框架或者库的好处是——等等，Ryan，它算框架还是库？

Ryan：我两种叫法都行。从理念上说我们偏向库那边，有点像 React：我们的初衷不是把一切都给你准备好，而是提供可以在上面搭建东西的基础构件。所以都行。

Amal：都行。我们需要一个合成词，互联网上的各位，拜托造一个吧，我没法一直说"框架或者库"，太拗口了。总之像 Solid 这样的工具会给你一大堆其他工具函数。好了，不废话了，请讲讲 Solid 是什么，和 React 有什么不同？

Ryan：我是带着一个实验性的想法来做 Solid 的：如果 Signals，也就是响应式本身，就是整个框架呢？如果它是框架的每一部分呢？如果不另外搞一套渲染器或者 diff 机制，就只用 Signals，看看能做到什么程度？因为从概念上说，我是从非常原生 JS 的思路出发的。我会想："如果我全部用原生 JS 写，它会怎么工作？"它会跑得非常快，但会有点啰嗦，有大量重复，你会想把东西抽象出来。我决定做的基本上就像 jQuery 那样：写一些响应式逻辑，只在需要的地方更新 DOM。也就是"当我更新这个值时，让 DOM 里的这个位置更新"。听起来够简单。但我想看看能不能把这种精简和简洁的东西，再扩展到能满足现代 Web 应用的需求。当时主要关注的是客户端，我在意的是仪表盘这类交互很多的东西。

结果证明这完全可行。我从 Knockout 借鉴了一些，又吸收了这些年从 MobX 等库那里学到的、如何让响应式更一致的经验。我意识到可以用编译器来处理语法。但我不想自己发明一套语法——很多人在这上面花了大量时间，这涉及语言设计的一整套故事。Svelte 就是个完美的例子，他们在"写起来是什么感觉"的美感上倾注了大量心思。

我就直接拿了 JSX，基本上是货架上的第一样东西：TypeScript 的工具链全都支持它，代码检查、语法高亮、Prettier，什么都有。我想："我能不能把 JSX 编译成 DOM 元素，并且能把响应式塞进去？"我基本上就是这么做的：拿标准的 JSX，让它输出我自己手写时会写出的代码，就像用 jQuery 那样。结果如你所料，非常快，因为写原生代码就是快，没别的。但问题在于，它能不能扩展到满足所有需要的场景？这需要证明。我相信这些年我们已经证明了。

我 2016 年开始做 Solid，2018 年开源。那时 DOM 部分已经做得相当不错，我们开始在基准测试里"夺冠"。但那只是个好的起点，不是终点。因为我做这个的初衷，是我喜欢在 Knockout 里开发的那种方式：我喜欢数据流，喜欢电子表格式的思维，喜欢"设好就不用管"——你制定好规则，更新数据，一切自动传播。

所以 Solid 的核心就是力求简单。它不是为了普及率，也不是为了谁能轻松上手。它有一定的学习曲线，因为你首先得了解 Signals。但同时它给了我完全的控制权，这是我喜欢的。我随时可以直接下到底层去更新 DOM，因为在 Solid 里，一个 JSX 的 div 元素就是一个 HTML 的 div 元素，就是真实的 DOM 节点，你随时都能访问它。而且因为它是这样构造的，我们的组件只运行一次——它们只是函数调用，创建一些以后会更新的东西。所以有这么一个非常简单的东西——早期组件几乎什么都不是。现在我们会通过 props 在响应式上多做一点处理，但总体而言，这些元素以一种连我自己一开始都没想明白的方式组合在一起，结果不仅能模拟你期望的大多数功能——从 context、并发渲染到 transitions，现代框架该有的功能都有——甚至还能超出 Web 的范围。做通用渲染并不需要虚拟 DOM。我们有移动端、桌面端，甚至电视端的方案……我说"大量"，但每个类别至少有三个库或框架可以配合 Solid 使用，纯响应式，能原生渲染到手机上，或者渲染 WebGL 3D 场景。所以这最终成了另一种模型，基本上能完成虚拟 DOM 或类 React 库能做的几乎所有事情，而它只建立在这一个基础构件之上。

Nick：很酷。这个基础构件就是你们不做"脏检查"……

Ryan：是 Signals。

Nick：对，Signals。你说得对，就是那种精确定点的更新，不用遍历所有节点去找哪里不同。你们的创建路径和更新路径是分开的。

Ryan：对。当你知道数据如何在应用中流动时，你能从中得到很多好处。这不是说你完全不需要 diff，这些东西总可以混搭使用。这里最强大的控制力，不只是你可以往下精简或往上扩展，而是变化的粒度完全由你决定，容器由你控制。就像在 React 里你可以调整组件的大小，而用 Signals，你可以把"更新单元"的大小调得更细或者更粗，你掌控着它。这就像多了一个维度。这听起来也许很多、很复杂，但最神奇的是——我有时会演示这个——你从像 jQuery 那样的写法开始，它就自然而然地演变成像 React 一样的东西。事实上，很多人第一次看到 Solid 时甚至会不屑一顾："哦，这不就是 React 嘛。"它看起来实在太像 React，以至于有人说："对，这是选 Solid 的理由之一，因为以后可以直接从 Solid 迁到 React。"我会说："没那么简单，底下其实有很多不同的东西。"但你会有这种印象，恰恰说明它的抽象很成功，说明它有我刚才说的那种能下能上的能力。

Nick：我觉得它的一大吸引力就在于它看起来这么像。说实话我对 React 本身没那么在意，但我喜欢 JSX，喜欢那样组织组件、用组件来思考……再加上"这个函数只会运行一次"——我没法告诉你这句话现在听起来有多美妙。就凭我最近不得不做的那些调试，我就想说"这也太糟了……！"

Ryan：对，这是我们听到的最棘手的痛点之一。再说一次，我不是想做一个"反 React"。我非常尊重 React 所做的一切。只是 Solid 出现的时候，正好是人们开始做大规模 React 应用、真切体会到重新渲染之痛、琢磨什么时候该给什么加 memo 的时候，而在 Solid 里这根本不是问题。我记得 React 团队做过一个视频，演示自动化编译器怎么工作——这个我们待会可能会聊到。我看了那个例子，他们整场演讲都在解释在 React 里你要怎么做、它会构造出什么，我觉得展示编译后的代码、再回到漂亮的源代码，说"看，这多好"，这个做法真的很高明。但对我来说那个演示最有意思的是：我用 Solid 写了同一个演示，就是他们在演讲前两分钟起步的那个原始版本，它直接就按应有的方式工作了。整场演讲、整个编译器、所有那些东西，在 Solid 里根本不需要发生。没有 createMemo，没有 memo，什么都不用，它本来就是那样工作的。想想这一点还挺有分量的：我们确实用编译器来处理 JSX，但那只是模板层面的事，Solid 的大部分其实是一个运行时库。这也是为什么我不认为 Solid 和 Svelte 很像。我们用编译器几乎是不情不愿的，原则是"如果编译能让开发体验好一点，我们就编译"。但我不想拿它当卖点。我喜欢保持透明，保持简单。某种意义上，编译器是又一层抽象，它让事情更容易，但是——

Amal：对，它是魔法。

Ryan：对，底下发生的事情会更复杂。我发现离底层越远、抽象越多，当你不得不掀开盖子看一眼时，冲击就越大。这其实是我个人的一个理论：为什么人们不喜欢 useEffect？不是因为别的那些东西，而是因为那是你意识到"React 并不是按你以为的方式工作"的时刻。

Amal：对我来说，这差不多就是我——我不想说"跳下 React 的车"——但就是 React 开始让我觉得很反直觉的时候。Hooks 从来没有按我预期的方式工作，还有一堆规则要记。所以看 Solid 的组件，感觉就是我期望中的 React，其实是我希望它成为的那个样子，这一点也很棒。不过我们能聊聊编译器吗？因为这算是这里的秘方。你说它更像运行时库，你们是不情不愿地用编译器……那编译器到底在做什么？我本来以为编译器会找出所有 Signals 在哪里，事先建好某种映射，然后才能做到精确更新……你来告诉我吧，它在做什么？

Ryan：好。其实比那简单得多，因为我们所有的依赖都是动态的，编译器根本不处理响应式。问题在于，JSX 有一个特点让标准转换对我们没什么用：它会立即求值所有"空位"、所有表达式，然后再传进去。而在响应式库里——我们用的是自动追踪——你希望在某个响应式作用域内去访问这些值。所以编译器要做的，就是在每个表达式外面包一层函数。我们还能更聪明一点：如果一个表达式里没有调用函数、也没有访问某个对象的属性，那它就不可能是响应式的。这是最大的区别之一：signal 必须以函数形式调用，不管是用 getter 还是别的方式，都得是一次函数调用。所以普通值我们可以直接原样传过去；但如果我们看到表达式里调用了函数，就要确保把它包在一个函数里。编译器主要就是干这个。

Nick：所以就是在 signal 更新时会发生一连串函数调用？就像一条函数链？这太聪明了，简单得要命，又聪明得要命。

Ryan：另一半是我们做了和 Lit 一样的事：把 JSX 当作模板，抽出 HTML 字符串，这样就可以克隆它来批量创建所有元素。

Amal：哦，对对对。这也是编译器做的，对吧？

Ryan：对。不过也可以在运行时做，Lit 就是在运行时做的，第一次运行时把模板抓下来，差别很小。但基本上，我们用编译器来做这件事。创建真实 DOM 节点时，就是克隆节点，然后走到对应的位置，把那些函数包在元素引用上。有点技术化，但本质上就是：克隆节点、收集节点，然后把它们传进负责更新 DOM 的 effect 里。编译器还有一些别的东西，但非原生元素的部分，也就是组件，基本上就是函数调用，和普通 JSX 一样，你可以随意移动它们。我们只需要确保把 props 包在函数里。

Amal：值得指出——顺便谢谢你这个精彩的解释——Lit 不用编译器，这是他们非常刻意做出的取舍，也挺神奇的。能有这么漂亮的 JavaScript，一种像 JSX 又不完全是 JSX 的东西，用的是模板字符串，完全不涉及编译器，非常棒。

Ryan：对。这其实也是我们这种函数式设计的一部分：我们也支持带标签的模板字面量，有一个像 Lit 那样工作的版本。

Amal：不错！

Ryan：所以其实我们并不一定需要编译器。但那样的话，就得由你自己把所有表达式包在函数里。

Amal：明白，明白，有道理。

Ryan：我个人觉得那样很麻烦。当然有办法绕过去，或者把 API 设计成迎合这种方式，比如用类属性之类的。我知道 Lit 一直在往他们的东西里加入 signal 响应式，最近好像用的是 Preact Signals。但这正是我们用编译器换来的一大人体工学收益——这也是为什么它看起来像 React：你可以直接把表达式放进模板里，它们就会被正确追踪、正常工作。没有某种转换来确保表达式不被提前执行，你是做不到这一点的。

Amal：在转向一般原则之前，再聊几点 Solid 的事。看你们的 API，它也很有 React 味儿，不只是组件的形状，API 本身也是：函数名字有 createContext、useContext，有 children、lazy，有 createEffect、createMemo，这些都很像 React。能讲讲你在这方面的考虑吗？

Ryan：当时就是觉得合理。有一点要记住：Solid 比 React Hooks 出现得早。所以我们当时并没有 use 这个命名约定，也没有返回两元素数组的元组约定——那个我其实是直接从 React 拿来的。当然，像 context 这类东西明显受了 React 的影响：我们有 provider，有某种使用 context 的方式。但基本上，我们的 API 做的是细粒度的事情，看起来已经很像 hooks 了，然后 React Hooks 发布了，我一看："这几乎一模一样。"那时我就想："干脆采用类似的约定吧。"

说实话，返回数组、也就是元组这件事，是我纠结了很久的问题。人们对响应式最常见的批评之一，就是它像双向绑定，更新很混乱。而我非常认同 React 关于单向数据流、单向绑定、没有双向、"数据向下、事件向上"的那套理念。我真的想要读写分离。但在那之前，几乎所有的 Signals API——因为你需要一个 getter 和一个 setter——通常都放在同一个对象上，或者是一个 proxy，或者干脆就是一个带 getter 和 setter 的对象。我试过很多种 API，想把它做得好看点，然后我看到了 hooks：它把两者分开，让人们自己命名——数组解构时这非常好——并且确保 get 和 set 不在同一个东西上。我当时就想："这就是我一直在找的东西。"

我在那之前好多年就一直在摆弄这些原语，这些看起来很像 hooks 的 Signals，却从没想到过这种模式。React 发布了 Hooks……我看 Dan（Abramov）最初那场演讲时，让我目瞪口呆的更多是他们解决了我的 API 难题，而不是 React 要有 hooks 了这件事本身。我当时就想："就是它！"

那时 Solid 还在 1.0 之前，所以几周之内我就把所有 API 改得更像 React。我选择不用 use，因为 use 在我看来暗示某种会被反复使用、可能运行多次的东西；我选了 create，表示它只运行一次，就像渲染函数那样。事情就是这样。

挺好笑的，因为在 React 有 hooks 之前，Solid 就已经有了看起来像 hooks 的东西和 JSX。所以我最初并没有在实现方式上模仿 React。我们用的是函数组件——那时 React 用的还是类组件。我不想要类，我想要函数组件，它已经有了我需要的所有部件。看到 React 之后，再做些收尾的 API 调整让它们看起来相似就很容易了——这显然把大家搞糊涂了。但我做这些决定，并不是因为想在 API 表面上直接照抄 React，因为我知道它们并不兼容，而是因为我认为 React 在这里做了正确的决定。强制读写分离等等，这些都是 React Hooks API 中非常好的设计细节，只会让 Signals API 更强大。

Amal：那可以说 hooks 多少受到了 Signals API 的影响吗？

Ryan：我不知道。他们发过一份东西，讲 React Hooks 的所有灵感来源，有一份文档在那里……里面没有出现任何一个我熟悉的 Signals 库。我当时有点怀疑，心想"怎么可能没注意到那么多类似的库？"那时 Solid 并不是唯一一个。我们是后来才慢慢火起来的，但之前有 Knockout，还有 CanJS、Ractive、Svelte 1 和 2……先例多得是。可不知怎么的，这些在 React Hooks 的灵感来源里就这么被略过了。所以我不知道，我们有很长的历史……

Ryan：有意思的是——不知道大家知不知道——我在 eBay 工作过几年。那是我和 Solid 的一个转折点，因为正是那时我终于决定认真投入。我在做 Marko，就是 eBay 的框架。他们读过我的文章，团队那边想的是："Ryan 来这儿，能真正改善 eBay 的首屏加载性能。"电商嘛，他们没那么在乎更新性能，只想确保页面尽可能快地加载，加载尽可能少的 JavaScript。后来我们意识到：如果知道数据依赖图，就能知道哪些会变、哪些是静态的。Marko 是那种编译很重的框架之一，和 Svelte 类似，有大量编译工作。我们想："如果能用 Signals，或者把它们内建进我们的语言，就能把静态部分 tree-shake 掉。"想想 Astro 那样的群岛架构（islands），但是自动的，你不用自己划分岛屿。Server Components 是另一种做法。我们就是把所有永远不需要再更新的部分摇掉，只发送那些需要更新的部分的最少代码。

在很多方面，Qwik 和可恢复性也借鉴了这一招。起初他们只是把一切都懒加载，并不能确定某样东西最终会不会被送到浏览器。但因为人们用 signal 的方式写代码，看清了数据依赖，把这些点连了起来，而且因为执行方式不需要重新渲染、不需要重新运行，那些不会重新运行的东西就可以在服务器上运行一次，永远不必送到浏览器。这可以通过静态分析和编译器判断出来。所以尽管它在更新上是性能提升，在创建和首屏加载上它也可能带来巨大的性能提升。可以说是三连胜。

Amal：太神奇了……我们已经多次提到懒加载和可恢复性，希望待会能给它下个定义。我们聊了很多 Signals，它是推动这一切响应式的核心原则。但它不只是关于性能，对吧？你把创建路径和更新路径分开，这带来了一堆非常酷的附带好处：比如渲染性能提升，因为你的创建路径优化得多，和你刚才解释的类似；复杂度的扩展方式也不同——应用不会因为组件越加越多、JavaScript 越发越多而变慢，不是线性增长的；还有你说的水合的那些东西，懒加载和可恢复性；当然，还没有那些疯狂的 hook 规则……所以还有一堆其他原则。也许我们先从可恢复性开始，以及响应式在水合方面的好处，以及由此获得的掌控力。

Ryan：好。这里最大的一点是：如果页面加载时你不用运行代码，那就是巨大的性能提升。哪怕你加载了 JavaScript，只要不运行它、不让它阻塞交互，影响就很大。这不只是页面多快显示出来的问题——尤其是对网速慢的用户——而是他们多快能和页面交互。因为通常如果用户在页面加载完之前就和它交互，会发生两种情况之一：要么点击被吞掉，用户很沮丧，"怎么不管用？"；要么有渐进增强，这通常是好事，因为它能工作。但我总是替这些人感到难过——我们在 eBay 讨论全球电商时经常想这个——因为这是个没有赢家的局面：即使你点了按钮或链接、它也工作了，你现在却要走一次完整的页面重新加载，从头再等一遍。而他们不知道，如果再多等半秒再点，也许 JavaScript 就加载好了，只需要在客户端快速处理一下。所以如果能把整个水合环节去掉，体验可以好得多，特别是在低端设备和慢速网络上。

而要做到不运行代码——抱歉，回到 Signals 上——你得知道有交互时该唤醒什么。你不想只是推迟水合，不想说"好，我现在什么都不做，等你点了，我就阻塞一切，把整个应用水合一遍"，那毫无用处。你希望能说："哦，我知道我其实只需要运行这一小段代码。"

所以 Signals 在这里变得很重要，一是因为它的粒度让你能在不先运行一遍的情况下唤醒东西；二是因为它是一张数据图，如果能把它序列化，从服务器送到客户端，你就能在原来的状态下直接醒来。而且因为这只是把数据放进图里，它是序列化框架内部状态的一种简便方式。

以 Qwik 为例，你可以和页面的一部分交互，然后如果点了"加入购物车"这样的按钮，借助响应式，它知道在那一刻"现在我需要真正运行代码来更新购物车数量"之类的。所以这些技术——这也是为什么 Google 的 Wiz 对它非常感兴趣——因为有些框架已经在做这样的事，而 Signals 就是一种内建的——将来可能内建于浏览器的——原语，能以可预测的方式配置这种通信。

Amal：太强大了。我觉得我们需要专门一整期来拆解这个……Nick，你觉得呢？挺震撼的，对吧？

Nick：对，内容太多了。

Ryan：说实话，我们聊的很多东西都是性能方面的。但性能有一种人们并不总能看到的影响，我希望大家明白：好的性能能减轻你实现理想用户体验的压力，对吧？基本上，如果你做的东西性能不好，你的开发体验迟早会受影响。也许一开始不会，因为你只是把它写出来了。但一旦你得回头真正去修问题，作为开发者，一切都会变得糟糕得多。

我想说的是，如果性能重要，而你把它当作一种思维方式，那就有一大堆事情你必须去做，而你在现有框架里可能并没有在做。比如在 React 里，组件边界会影响哪些东西重新运行、哪些更新，取决于你是否 memo 了它们，也取决于你在哪里拆分组件。如果你的框架不受组件布局方式的支配——而正如我说的，大多数框架，凡是做脏检查之类的，组件的大小、在哪里拆分、把状态放在哪里，这些都很重要——你突然就不用担心这些了。这是开发体验的巨大提升：尽管驱动它的是性能，但你突然完全不用操心了，可以按自己想要的方式组织代码。

所以所有这些——我想这就是为什么它对框架作者来说也许显而易见——我们花大量时间试图把人们引入"成功之坑"（pit of success）。我们希望人们只管写他们想写的东西，然后它就是高性能的，他们就满意了。如果我们能把性能作为基线白白得到，就有大得多的空间去改善开发体验。

Amal：除了大家都在慢慢采用 Signals 之外，还有一种整体的趋同……你看过那个蜘蛛侠互相指着对方的梗图吧？真的感觉所有东西都开始以同样的方式工作了。我在想，会不会有一天问题只剩下"你喜欢哪种语法？"，因为归根结底这些东西的工作方式都一样？那就好了。

Ryan：说实话，对于 Solid、Vue 和 Svelte 来说，六个月后可能就是这样了。

Amal：哇。

Ryan：当然，我们各有一些不同的特性，而且都在不断演进。Solid 在 Signals 上花了很多时间，Solid 现在的版本从 2019 年起基本就是这个样子了，而 Vue 和 Svelte 5 是今年才加入进来。但在基础层面，当你拿起 Vue Vapor、Svelte runes 或者 Solid，你的感觉会是"这些基本上是同一个东西"。所以区别就在于：你喜欢美元符号，喜欢 .value，还是喜欢把东西当函数调用之类的。我们显然会继续演进，但有意思的是，有时候这种方式的创新反而会让事物趋于整合。但即便如此——还是有个人偏好。这是我最敬佩 Rich Harris 的一点，他比我早得多就明白了这一点：这些偏好、这些争论细枝末节的讨论（bike-shedding）、审美上的感受，对不同的人来说永远会不一样，足以让人们继续根据这些方面来做选择，即便事物开始像这样趋同。

Ryan：对，真实使用场景。好，你说这个的时候——我们可以聊几类例子，你想的是什么？

Amal：哦对，抱歉。基本上就是说，它不只是性能，对吧？就像你说的，不只是我们能利用的性能提升，还会附带出很多别的东西。我们聊了一点可恢复性……还有其他各种好处，比如——我看到你之前提过——有一种 IDE 能链接到你更新某个状态的所有地方，在整个应用中拥有这种可追溯性，是使用 Signals 的另一个好处……

Ryan：好，我想我明白你的意思了。那个目前还不存在，但我能看出它是可能的。其实当时是有人在讲这个，他对 Signals 兴奋过一阵，因为有人把 Signals 移植到了 Rust，做了一个叫 Leptos 的框架，几乎和 Solid 一模一样，只是用 Rust 写的。所以那是在他的语言、他的地盘上，他就在讲用 IDE 里的东西去追踪它。我不认为有人已经做出来了。不过一个更常见、更实际的场景是：库的作者。我和 Tanner Linsley 合作很多，他创建了 TanStack——React Location，现在叫 TanStack Router，还有 TanStack Query 以及很多其他库。对他来说有意思的一件事是怎么管理状态。你可能会问："为什么需要管理状态？这些都是通用库啊。"但即使是处理数据获取之类的，他做的是仪表盘、大型表格、交互非常多的东西，他做工具给别人用。他为 React 开发东西的时候——他所有的库都支持 React——经常处在一个很尴尬的位置：没法用 React 的状态原语和 context，因为它们效率不够。这是常见情况。比如 Redux 一度改成纯用 React context 加 setState，后来发现太慢，又改回去了。

基本上，任何时候你为 React 写任何状态库，都得自己做一套外部状态管理，再把它接回 React 的更新周期。所以这是个挑战，后来 React 又有了并发模式，这意味着你得用 useSyncExternalStore，要跳过更多的坑才能让它在 React 这边好好配合。我见过这种情况——这大概也是为什么那些对 useEffect 之类东西批评最多的人，往往是给 React 写状态管理库的人，比如 XState、TanStack Query 的作者。你能看出一种趋势，因为他们基本上被推到了一种外部的二等公民的位置。

而一方面很酷的是，当框架本身管理状态时，意味着插件的每个框架版本确实都要用那个框架的状态，但因为有一套既定的做法，你直接接入就行。讽刺的是，如果不是 React 需要另一套方式——而且 React 版是最流行的 TanStack 库——Tanner 本可以直接给 Solid 用 Solid 的版本，给 Vue 用 Vue 的版本，给 Svelte 用 Svelte 的状态管理原语，根本不用在库里塞那么多额外代码。这一直是个大挑战。因为当状态原语理解并发、理解各个部分——因为它们内建于框架、完全可以导出——你就是把这些能力交给了库作者。

在 Solid 里我们有个叫 createResource 的东西，是一个基础的异步原语。但我说"基础"，指的是它处理数据获取，会自动为 SSR 做序列化，会在服务端和客户端自动触发 Suspense，所以自动支持乱序流式传输（out-of-order streaming）……因为框架知道这些。Tanner 他们要做的，只是让 TanStack Query 包装一下 createResource，突然之间所有这些功能就都能用了。你拿 Solid Query，也就是 TanStack Query 的 Solid 版本，上面这些全都能用：乱序流式传输、自动数据序列化、整套 Suspense、整套 transitions，全都直接可用。

光靠我嘴说很难讲清这有多大的影响。我们加入服务端函数时——原来叫 server$，现在我们用和 React 一样的 "use server" 语法，有时随大流更省事——它们也直接就融进来了，所有部件在第三方库里都能组合起来，因为它们在构建时就知道其他部件的存在。这就是我所说的原语设计。这是个真实案例：Solid Query 后来非常成功，以至于大家都会装的 TanStack Query 开发者工具——React、Svelte、Vue 版本的——现在其实都是用 Solid 写的。所以对我们来说这是个很好的用例。
