论合规与可读性：用 CSS 生成文字颜色

我们能否用已经广泛发布的 CSS 特性来模拟即将到来的 CSS `contrast-color()` 函数？如果可以，其中涉及哪些权衡，又该如何最好地平衡它们？

## 相对颜色

在我设计过的所有 CSS 特性中，相对颜色（Relative Colors），又称相对颜色语法（Relative Color Syntax，RCS），绝对是我最引以为豪的之一。简而言之，它允许 CSS 作者在任何受支持的颜色空间中，对颜色分量做任意数学运算，从已有的颜色值派生出新颜色：

```
--color-lighter: hsl(from var(--color) h s calc(l * 1.2));
--color-lighterer: oklch(from var(--color) calc(l + 0.2) c h);
--color-alpha-50: oklab(from var(--color) l a b / 50%);
```

当初的推介理由是：通过提供更底层的操作，它让作者能灵活地派生颜色变体，也给我们更多时间去弄清楚合适的高层原语应该是什么。

截至 2024 年 5 月，RCS 已在除 Firefox 外的所有浏览器中发布。但鉴于它是 Interop 2024 的重点领域、Firefox 已表达了积极的标准立场、Bugzilla 上的相关问题最近也有动静并已指派了负责人，我乐观地认为它很快会在 Firefox 中发布（更新：在写下这几行字 5 天后，它就在 Firefox 128 中发布了 🎉）。我猜它会在 2024 年底前成为 Baseline。

即便我的预测有偏差，它也已经覆盖了全球 83% 的用户。如果你把它的 caniuse 页面按使用量排序，会发现剩下 17% 中的绝大部分并非来自 Firefox，而是来自旧版的 Chrome 和 Safari。我认为以它目前的市场份额，今天就值得用于生产环境，只要我们用 `@supports` 确保在不支持的浏览器中也能正常工作，哪怕没那么好看。

大多数相对颜色教程都围绕它的主要驱动用例展开：通过调高或调低某个颜色分量来制作浅色、深色或其他颜色变体，和/或用固定值覆盖某个颜色分量，就像上面的例子。虽然这确实解决了一些非常常见的痛点，但这只是 RCS 能力的皮毛。本文探讨一个更高级的用例，希望能激发大家在实践中更有创意地使用 RCS。

## CSS `contrast-color()` 函数

CSS 一个长期存在的大痛点是：无法自动指定一种在任意背景上都保证可读的文字颜色，例如在较深的颜色上用白色、在较浅的颜色上用黑色。

为什么需要这样做？主要用例是颜色不在 CSS 作者掌控之中的情况，包括：

- 用户定义的颜色。一个你可能熟悉的例子：GitHub 标签。想想你创建标签时选择任意一种颜色，GitHub 会自动选择文字颜色——而且常常选得很差（稍后我们会看到原因）。
- 其他开发者定义的颜色。例如，你在编写一个支持用某些 CSS 变量来设置样式的 Web 组件。你"可以"要求文字和背景分别使用不同的变量，但这会让组件更麻烦，降低可用性。如果它能直接使用一个合理的默认值，你可以覆盖但很少需要覆盖，岂不是很好？
- 外部设计系统定义的颜色，比如 Open Props、Material Design，甚至（惊！）Tailwind。

即使在每一行 CSS 代码都由同一个作者掌控的代码库中，减少耦合也能提高模块化程度、促进代码复用。

好消息是，这个痛点不会持续太久了。CSS 函数 `contrast-color()` 正是为解决这个问题而设计的。它并不新，你以前可能听说过它的旧名 `color-contrast()`。我最近推动达成共识，把它的范围缩小为一个最小可行版本（MVP），只解决最突出的痛点，并且能够较快发布，因为它绕开了一些导致完整版特性停滞不前的非常困难的设计决策。随后我根据工作组决议把它加入了规范，不过一些细节仍有待敲定。

用法看起来是这样的：

```
background: var(--color);
color: contrast-color(var(--color));
```

很美妙，不是吗？当然，规范世界里的"较快"仍然意味着好几年。作为参考，从我过去的规范工作可以看出，运气好一点（加上浏览器有兴趣）的话，一个特性写进规范后，最快 2 年就能在所有主流浏览器中发布。当标准工作也有充足资金时，甚至有过一个特性从构想到 Baseline 只用了 2 年的情况，级联层（Cascade Layers）就是典型：Miriam 在 2019 年 10 月提出，到 2022 年 3 月已在所有主流浏览器中发布。但 2 年仍然很长（而且不保证不会更久）。在那之前我们能怎么办？

你可能已经从标题猜到了，答案是可以。也许不太优雅，但确实有办法用相对颜色来模拟 `contrast-color()`（或与之相近的效果）。

## 用 RCS 自动计算对比文字颜色

下面我们将使用 OKLCh 颜色空间，它是 CSS 支持的感知上最均匀的极坐标颜色空间。

假设存在一个亮度（Lightness）值，高于它时无论彩度和色相如何，黑色文字都保证可读；低于它时白色文字都保证可读。我们稍后会验证这个假设，现在先姑且认为它成立。在本文其余部分，我们把这个值称为"阈值"，记作 L<sub>threshold</sub>。

下一节我们会更严谨地计算这个值（并证明它确实存在！），现在先用 `0.7`（70%）。我们可以把它赋给一个变量，方便调整：

```
--l-threshold: 0.7;
```

让我们从想要的结果倒推。我们想构造一个由广泛支持的 CSS 数学函数组成的表达式，当 `L` ≤ L<sub>threshold</sub> 时返回 `1`，否则返回 `0`。如果能写出这样的表达式，就可以把这个值用作新颜色的亮度：

```
--l: /* ？？？ */;
color: oklch(var(--l) 0 0);
```

怎样简化这个任务？一种方法是放宽表达式需要返回的结果。我们其实并不需要精确的 `0` 或 `1`。如果能找到一个表达式，在 `L` > L<sub>threshold</sub> 时得到 `0`，在 `L` ≤ L<sub>threshold</sub> 时得到大于 `1` 的数，就可以直接用 `clamp(0, /* 表达式 */, 1)` 得到想要的结果。

一个思路是使用比值，因为比值有个好性质：分子大于分母时比值大于 `1`，否则小于或等于 `1`。

比值 L / L<sub>threshold</sub> 在 `L` ≤ L<sub>threshold</sub> 时小于等于 `1`，在 `L` > L<sub>threshold</sub> 时大于 `1`。这意味着 L / L<sub>threshold</sub> − 1 在 `L` < L<sub>threshold</sub> 时为负数，在 `L` > L<sub>threshold</sub> 时为正数。接下来只需把这个表达式乘以一个绝对值巨大的负数，这样当它为负时，结果就保证大于 `1`。

合在一起，是这样的：

```
--l-threshold: 0.7;
--l: clamp(0, (l / var(--l-threshold) - 1) * -infinity, 1);
color: oklch(from var(--color) var(--l) 0 h);
```

一个可能的担忧是：如果 L 足够接近阈值，我们可能会得到一个介于 `0` 和 `1` 之间的数。但在我的实验中这从未发生，大概是因为精度有限。

### 为不支持 RCS 的浏览器提供回退

拼图的最后一块是为不支持 RCS 的浏览器提供回退。我们可以用 `@supports`，以任意颜色属性和任意相对颜色值作为检测条件，例如：

```
.contrast-color {
	/* 回退 */
	background: hsl(0 0 0 / 50%);
	color: white;
	@supports (color: oklch(from red l c h)) {
		--l: clamp(0, (l / var(--l-threshold) - 1) * -infinity, 1);
		color: oklch(from var(--color) var(--l) 0 h);
		background: none;
	}
}
```

本着"确保在不支持的浏览器中也能工作，哪怕没那么好看"的精神，一些回退思路包括：

- 白色或半透明白色背景配黑色文字，或者反过来。
- 使用与文字颜色相反的颜色设置 `-webkit-text-stroke`。这对较粗的文字效果更好，因为描边有一半在字形内部。
- 使用多个与文字颜色相反的 `text-shadow` 值。这对较细的文字效果更好，因为阴影绘制在文字后面。

## 这个神秘的 L 阈值真的存在吗？

上一节我们做了一个相当大的假设：存在一个亮度值（L<sub>threshold</sub>），高于它时无论彩度和色相如何，黑色文字都保证可读；低于它时，无论彩度和色相如何，白色文字都保证可读。但这样的值存在吗？是时候检验这个说法了。

人们初次听说 Lab、LCH 或其改进版本 OkLab、OKLCH 这类感知均匀颜色空间时，会以为只要比较两种颜色的 L（亮度）值，就能推断出它们之间的对比度。遗憾的是并非如此，因为对比度取决于比感知亮度更多的因素。不过，亮度值与对比度之间确实存在显著的相关性。

这里我要指出，虽然大多数网页设计师都知道 WCAG 2.1 对比度算法——它是《Web 内容无障碍指南》的一部分，并被写入了许多国家的法律——但多年来人们早已知道它会产生极差的结果。差到什么程度？在某些测试中，对于任何不是很浅或很深的颜色，它的表现几乎和随机猜测一样糟。有一种更新的对比度算法 APCA，效果要好得多，但它尚未成为任何标准或法规的一部分，而且此前在向公众免费开放方面也遇到过一些波折（目前看来已基本解决）。

那网页作者该怎么办？事实证明处境相当尴尬。目前创建无障碍配色的最好方式似乎是两步走：

- 用 APCA 确保实际可读性；
- 合规保底：确保结果不会明确地不通过 WCAG 2.1。

我用 Color.js 做了一些快速实验：以越来越细的粒度遍历 OKLCh 参考范围（大致基于 P3 色域），计算白色是"最佳"文字颜色（即比黑色产生更高对比度）的颜色所对应的亮度范围，反之亦然。我还为 APCA 和 WCAG 分别计算了每个等级（不通过、AA、AAA、AAA+）的区间。

随后我把这次探索做成了一个交互式实验场，你可以自己运行同样的实验，也可以用更符合你用例的更窄范围或更高粒度。

下表是在 C ∈ [0, 0.4]（步长 0.025）、H ∈ [0, 360)（步长 1）条件下得到的：

| 文字颜色 | 等级 | APCA 最小 | APCA 最大 | WCAG 2.1 最小 | WCAG 2.1 最大 |
|---|---|---|---|---|---|
| 白色 | 最佳 | 0% | 75.2% | 0% | 61.8% |
|  | 不通过 | 71.6% | 100% | 62.4% | 100% |
|  | AA | 62.7% | 80.8% | 52.3% | 72.1% |
|  | AAA | 52.6% | 71.7% | 42% | 62.3% |
|  | AAA+ | 0% | 60.8% | 0% | 52.7% |
| 黑色 | 最佳 | 66.1% | 100% | 52% | 100% |
|  | 不通过 | 0% | 68.7% | 0% | 52.7% |
|  | AA | 60% | 78.7% | 42% | 61.5% |
|  | AAA | 69.4% | 87.7% | 51.4% | 72.1% |
|  | AAA+ | 78.2% | 100% | 62.4% | 100% |

注意，这些是每个等级的 L 最小值和最大值。例如，白色文字在 L ∈ [62.4%, 100%] 时"可能"不通过 WCAG，并不意味着"每一种" L > 62.4% 的颜色都不通过，只是说"有些"会不通过。所以，只有反转逻辑才能得出有意义的结论：既然所有白色文字的不通过情况都落在 L ∈ [62.4%, 100%] 内，那么逻辑上可以推出，如果 L < 62.4%，无论是什么颜色，白色文字都会通过 WCAG。

把这一逻辑应用到所有范围，我们就能为其中许多区间得出类似的保证：

|  |  | 0%–52.7% | 52.7%–62.4% | 62.4%–66.1% | 66.1%–68.7% | 68.7%–71.6% | 71.6%–75.2% | 75.2%–100% |
|---|---|---|---|---|---|---|---|---|
| 合规 WCAG 2.1 | 白色 | ✅ AA | ✅ AA |  |  |  |  |  |
|  | 黑色 |  | ✅ AA | ✅ AAA | ✅ AAA | ✅ AAA | ✅ AAA | ✅ AAA+ |
| 可读性 APCA | 白色 | 😍 最佳 | 😍 最佳 | 😍 最佳 | 🙂 尚可 | 🙂 尚可 |  |  |
|  | 黑色 |  |  |  |  | 🙂 尚可 | 🙂 尚可 | 😍 最佳 |

你可能已经注意到，总体而言 WCAG 在白色文字上有大量假阴性，而且倾向于把亮度阈值定得比 APCA 低得多。这是 WCAG 算法的已知问题。

因此，为了最好地平衡可读性与合规性，我们应该使用能够容许的最高阈值。这意味着：

- 如果必须通过 WCAG，能用的最高阈值是 62.3%。
- 如果只关心实际可读性，可以放心忽略 WCAG，在 68.7% 到 71.6% 之间选一个阈值，例如 70%。

下面是一个演示，你可以看看两者的实际效果。编辑下方的颜色，观察两个阈值在实践中的表现，并与颜色选择器旁边（或下方）表格中显示的实际对比度区间进行比较。

（页面提示：你的浏览器不支持相对颜色语法，因此下面的演示无法运行。以下是它在支持的浏览器中的样子。）

L<sub>threshold</sub> = 70%

L<sub>threshold</sub> = 62.3%

（演示中的"实际对比度"表格：分别列出白色和黑色文字的 APCA 与 WCAG 2.1 对比值，数值随所选颜色动态生成。）

避免使用标记为"P3+""PP"或"PP+"的颜色，因为它们几乎肯定超出了你屏幕的色域，而目前浏览器的色域映射做得不正确，视觉效果会有偏差。

注意，如果你实际使用的颜色范围更受限（例如只用部分色相或彩度，或特定色域），换一个阈值也许能更好地平衡这些权衡。用你实际的颜色范围自己跑一遍实验吧！

以下是我尝试过的一些更窄的范围，以及仍能通过 WCAG 2.1 的最高阈值：

| 描述 | 颜色范围 | 阈值 |
|---|---|---|
| 现代低端屏幕 | sRGB 色域内的颜色 | 65% |
| 现代高端屏幕 | P3 色域内的颜色 | 64.5% |
| 未来的高端屏幕 | Rec.2020 色域内的颜色 | 63.4% |
| 中性色 | C ∈ [0, 0.03] | 67% |
| 柔和色 | C ∈ [0, 0.1] | 65.6% |
| 暖色（红/橙/黄） | H ∈ [0, 100] | 66.8% |
| 粉色/紫色 | H ∈ [300, 370] | 67% |

特别有意思的是，仅仅忽略那些在现代屏幕上实际无法显示的颜色，阈值就能提高到 64.5%。所以，假如浏览器在色域映射时优先保留亮度（遗憾的是这个假设目前并不成立），我们"可以"使用 64.5%，同时仍保证符合 WCAG。

你甚至可以把它做成一个工具类，与不同的阈值组合使用：

```
.contrast-color {
	--l: clamp(0, (l / var(--l-threshold, 0.623) - 1) * -infinity, 1);
	color: oklch(from var(--color) var(--l) 0 h);
}
.pink {
	--l-threshold: 0.67;
}
```

## 结论与后续工作

把所有内容合在一起，包括回退方案，以及使用 `contrast-color()` 的"向前兼容"方案，这个工具类可以是这样的：

```
.contrast-color {
	/* 为不支持 RCS 的浏览器提供回退 */
	color: white;
	text-shadow: 0 0 .05em black, 0 0 .05em black, 0 0 .05em black, 0 0 .05em black;
	@supports (color: oklch(from red l c h)) {
		--l: clamp(0, (l / var(--l-threshold, 0.623) - 1) * -infinity, 1);
		color: oklch(from var(--color) var(--l) 0 h);
		text-shadow: none;
	}
	@supports (color: contrast-color(red)) {
		color: contrast-color(var(--color));
		text-shadow: none;
	}
}
```

这只是一个开始。我能想到很多改进方向，例如：

- 既然 RCS 允许我们在任何颜色空间中对任何颜色分量做数学运算，我想知道是否有一个更好的、仍然可以用 CSS 实现的公式，能更好地平衡可读性与合规性。例如，就在发布本文之前，我和 APCA 的创造者 Andrew Somers 聊过几次，他认为改为对亮度（luminance，即 XYZ 中的 Y 分量）做运算可能是一个有前景的方向。
- 我们目前只计算了白色和黑色文字的阈值。然而在实际设计中，我们很少需要纯黑文字，这也是为什么 `contrast-color()` 除非使用 `max` 关键字，否则只保证返回"非常浅或非常深的颜色"。这一方法如何扩展到背景色的较深色调？

## 附录

和往常一样，本文发布后，很多人联系我，分享了这一领域各种相关的工作。我想在这里分享其中一些最有意思的发现。

### 用亮度（luminance）代替明度（Lightness）

当颜色的明度值差异足够大时（白色或黑色文字就是这种情况），人类会忽略色彩对比（色相/鲜艳度带来的对比），基本上只用明度对比来判断可读性。这就是为什么 L 能如此好地预测白色还是黑色文字效果最好。

另一个度量是亮度（luminance），基本上就是颜色在 XYZ 颜色空间中的 Y 分量。切换为黑色文字的一个良好阈值是 Y > 0.36。这给了我们另一种计算文字颜色的方法：

```
--y-threshold: 0.36;
--y: clamp(0, (y / var(--y-threshold) - 1) * -infinity, 1);
color: color(from var(--color) xyz-d65 var(--y) var(--y) var(--y));
```

正如你在 Lloyd Kupchanko 的这个演示中看到的，使用 Y<sub>threshold</sub> > 36% 能非常接近地预测出 APCA 判定的最佳文字颜色。

在我的测试（CodePen）中，它看起来和 L<sub>threshold</sub> 方法效果一样好，也就是说很难找到两者判断不一致的颜色。不过，本文发布后，Lloyd 在他的演示中加入了多个 L<sub>threshold</sub> 边界，结果显示 L<sub>threshold</sub> 与 APCA 不一致的范围确实比 Y<sub>threshold</sub> 更宽。

鉴于此，我的建议是：如果你需要在黑白文字之间切换，就用 Y<sub>threshold</sub> 方法；如果需要进一步定制文字颜色（例如用很深的颜色代替黑色），就用 L<sub>threshold</sub> 方法。

### 浏览器 bug 与变通办法

本文发布大约一周后，我发现了一个与 `color-mix()` 和 RCS 有关的浏览器 bug：在 `from` 中使用通过 `color-mix()` 定义的颜色，会导致 RCS 无效。你可以用这个测试用例看看某个浏览器是否受影响。这个问题已在 Chrome 125 和 Safari Technology Preview 194 中修复，但它确实给这一方案添了乱，因为使用这项技术的全部意义就在于我们不必关心颜色是如何定义的。

有两种变通办法：

1. 调整 `@supports` 条件，改用 `color-mix()`，像这样：

```
@supports (color: oklch(from color-mix(in oklch, red, tan) l c h)) {
	/* ... */
}
```

缺点是目前这会把可用的浏览器范围限制到极小的一部分。

2. 注册包含该颜色的自定义属性：

```
@property --color {
	syntax: "<color>";
	inherits: true;
	initial-value: transparent;
}
```

这能彻底解决问题，因为如果属性已注册，那么当颜色到达 RCS 时，它就已经是一个解析好的颜色值了。`@property` 目前的浏览器支持范围比 RCS 广得多，所以这个变通办法完全不会损害兼容性。

### 有用的资源

许多人分享了这方面的有用资源，例如：
