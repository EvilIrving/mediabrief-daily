实用循环工程（Practical Loop Engineering） ｜ Addy Osmani ｜ 文章 ｜ https://addyosmani.com/blog/practical-loop-engineering/

Addy Osmani 平时同时开五到十个 agent。停止条件和约束清楚的任务，比如写文档、补测试覆盖，就完全放手；复杂的、涉及权限、认证、安全或财务的任务，就盯紧并审代码。所谓循环，是 agent 反复行动、检验、调整，直到达成目标。早期大家手写 bash 循环，比如 Geoff Huntley 的 Ralph 循环；如今 Claude Code 和 Codex 已经内置了 goal 和 loop 两个原语。但如果目标和约束没定义清楚就放任它跑，照样会出问题，新项目和银行那样的棕地代码库要区别对待。

他引用 Claude Code 团队的分级。每条提示本身就是一次人主导的循环。/goal 定义“完成”的样子：每当 agent 想停，评估模型就检查条件，没满足就打回去继续，所以测试通过数、分数阈值这类确定性标准最有效。/loop 按时间间隔重跑同一条提示，像 cron，只在本机运行，要搬到云端得用 /schedule。最高一级是主动循环，由事件触发、没有人实时参与，例行部分交给小模型，判断交给最强的模型。团队还给了一份前端验证 skill：真正启动服务、操作页面、截图、查控制台、跑 Core Web Vitals，任何一步失败就从头来。

他的用法：goal 用来把一件事做到可证明完成，比如页面五秒内加载完、处理完最近十个 issue，最好写明工具和硬指标，并设置“连续两轮没有改进就中止”这类条款。loop 用来轮询和监控。两条习惯：一是由另一个子 agent 来验证，因为干活的 agent 可能只测了桌面端，而你关心的是手机端；二是只委托任务，不委托品味和判断。他曾让 agent 调研竞品、在本地写出补齐差距的 PR，只读了调研没细看实现，差点推上去，后来才发现这些改动会给用户增加大量复杂度，收益却很小。另外，goal 背后的评估器并不判断内容好坏，只检查对话记录是否满足了硬性规则。

他每天在跑的流程：8 万星的 Agent Skills 仓库曾经一天来八九十个 PR，现在由 loop 定期汇总新 issue 的紧急程度、做初审。两个原语还可以组合：loop 每天查 bug 标签，有就用 goal 修到本地测试全过再推分支。这套系统最大的价值是交叉对照，比如重做某块系统时，能确保相关 issue 一并关闭。按贡献指南（例如“不接受翻译”）自动关掉不合规的 PR，也能大大减少审查量。

循环不适合标准模糊、要靠审美的任务，比如“把 UI 改到好看为止”：好看是对谁而言，又怎么评估？细则：同一命令第三次执行结果仍无变化，就该停了；周期性循环创建七天后过期（他以前误说是三天）；循环是会话级的，用 --resume 或 --continue 恢复会话可以带回仍在有效期内的任务，需要比会话活得更久就用 /schedule。他的建议是：每天早上手动做的那项检查，就是你的第一个循环。
