## 服务器端渲染速览

要把 React 服务器组件放在合适的语境中理解，先了解服务器端渲染（SSR）的工作方式会很有帮助。如果你已经熟悉 SSR，可以直接跳到下一节！

我 2015 年刚开始用 React 时，大多数 React 项目采用“客户端”渲染策略。用户收到的 HTML 文件是这样的：

```
<!DOCTYPE html>
<html>
  <body>
    <div id="root"></div>
    <script src="/static/js/bundle.js"></script>
  </body>
</html>
```
那个 `bundle.js` 脚本包含挂载和运行应用所需的一切，包括 React、其他第三方依赖，以及我们自己写的全部代码。

JS 下载并解析完成后，React 开始工作，凭空变出整个应用的所有 DOM 节点，并把它们放进那个空的 `<div id="root">` 里。

这种做法的问题在于，完成这些工作需要时间。**而在这一切发生期间，用户只能盯着一片空白的屏幕。** 这个问题往往会随时间恶化：我们每上线一个新功能，JavaScript 包就多出几 KB，用户等待的时间也随之延长。（有一些优化可以缓解，比如对特定模块做懒加载，或按路由拆分代码，但总的规律是，JS 包会越长越大。）

服务器端渲染就是为了改善这种体验而设计的。服务器不再发送一个空的 HTML 文件，而是渲染我们的应用，*生成*真正的 HTML。用户收到的是一个完整成型的 HTML 文档。

这个 HTML 文件仍然会包含 `<script>` 标签，因为我们仍然需要 React 在客户端运行来处理交互。但我们会让 React 在浏览器里以稍微不同的方式工作：它不再从零开始变出所有 DOM 节点，而是*接管*现有的 HTML。这个过程叫作*水合（hydration）*。

我很喜欢 React 核心团队成员 Dan Abramov 的解释：

> 水合就像用交互和事件处理器这些“水”，去浇灌“干燥”的 HTML。

JS 包下载完成后，React 会快速过一遍整个应用，构建出 UI 的虚拟草图，并把它“贴合”到真实 DOM 上，绑定事件处理器、触发各种副作用（effect）等等。

这就是 SSR 的要点。服务器生成初始 HTML，这样用户在 JS 包下载和解析期间不必盯着空白页面。随后客户端的 React 接过服务器端 React 的工作，接管 DOM，并撒上交互能力。

## 来回往返

我们来谈谈 React 中的数据获取。通常，我们有两个通过网络通信的独立应用：

- 一个客户端 React 应用
- 一个服务器端 REST API

借助 React Query、SWR 或 Apollo 之类的工具，客户端向后端发起网络请求，后端从数据库取出数据，再通过网络发回来。

我们可以用一张图来可视化这个流程：

（图示：客户端与服务器之间的事件序列，每个事件列为一项。）

1. 服务器响应。耗时：4 个时间单位。
2. 客户端“下载 JavaScript”。耗时：7 个时间单位。
3. 客户端“渲染外壳”。耗时：6 个时间单位。
4. 向服务器发请求。耗时：4 个时间单位。
5. 服务器端“数据库查询”。耗时：5 个时间单位。
6. 服务器响应。耗时：4 个时间单位。
7. 客户端“渲染内容”。耗时：5 个时间单位。

第一张图展示的是客户端渲染（CSR）策略的流程。它从客户端收到一个 HTML 文件开始。这个文件没有任何内容，但有一个或多个 `<script>` 标签。

JS 下载并解析后，React 应用启动，创建一堆 DOM 节点并填充 UI。不过一开始我们还没有任何真正的*数据*，所以只能渲染带加载状态的外壳（页头、页脚、整体布局）。

这种模式你大概见过很多。比如 UberEats 会先渲染一个外壳，同时去获取填充真实餐厅列表所需的数据：

在网络请求返回、React 重新渲染、用真实内容替换加载界面之前，用户看到的一直是这个加载状态。

**我们来看另一种架构方式。** 下一张图保持相同的数据获取模式，但用的是*服务器端*渲染而非客户端渲染：

（图示：客户端与服务器之间的事件序列，每个事件列为一项。）

1. 服务器端“渲染外壳”。耗时：3 个时间单位。
2. 服务器响应。耗时：4 个时间单位。
3. 客户端“下载 JavaScript”。耗时：7 个时间单位。
4. 客户端“水合”。耗时：3 个时间单位。
5. 向服务器发请求。耗时：4 个时间单位。
6. 服务器端“数据库查询”。耗时：5 个时间单位。
7. 服务器响应。耗时：4 个时间单位。
8. 客户端“渲染内容”。耗时：5 个时间单位。

在这个新流程里，第一次渲染在服务器上完成。这意味着用户收到的 HTML 文件不再是完全空的。

这是一个进步——有外壳总比空白页好——但说到底，它并没有带来实质性的改变。用户访问我们的应用不是为了看加载界面，而是为了看*内容*（餐厅、酒店列表、搜索结果、消息，随便什么）。

为了真正感受用户体验的差异，我们给图加上一些网页性能指标。**在这两个流程之间切换，留意那些旗标的变化：**

客户端渲染

（图示：客户端与服务器之间的事件序列，每个事件列为一项。）

1. 服务器响应。耗时：4 个时间单位。
2. 客户端“下载 JavaScript”。耗时：7 个时间单位。
3. 客户端“渲染外壳”。耗时：6 个时间单位。
4. 向服务器发请求。耗时：4 个时间单位。
5. 服务器端“数据库查询”。耗时：5 个时间单位。
6. 服务器响应。耗时：4 个时间单位。
7. 客户端“渲染内容”。耗时：5 个时间单位。

每面旗标代表一个常用的网页性能指标。具体如下：

1. **首次绘制（First Paint）**——用户不再盯着空白屏幕。整体布局已经渲染出来，但内容仍然缺失。有时也叫 FCP（首次内容绘制）。
2. **页面可交互（Page Interactive）**——React 已下载完毕，应用已完成渲染/水合。交互元素现在完全可以响应。有时也叫 TTI（可交互时间）。
3. **内容绘制（Content Paint）**——页面现在包含了用户关心的东西。我们已从数据库取出数据并渲染到 UI 中。有时也叫 LCP（最大内容绘制）。

通过在服务器上完成初次渲染，我们能更快地画出最初的“外壳”。这能让加载体验感觉快一点，因为它给人一种进展感，让人觉得事情在推进。

在某些情况下，这*确实*是有意义的改进。比如用户可能只是在等页头加载出来，好点击某个导航链接。

**但这个流程是不是有点傻？** 看着 SSR 那张图，我忍不住注意到请求是*从服务器开始*的。既然如此，与其再来一次网络往返，为什么不*在最初那次请求中*就把数据库的活干了？

换句话说，**为什么不这样做？**

（图示：客户端与服务器之间的事件序列，每个事件列为一项。）

1. 服务器端“数据库查询”。耗时：5 个时间单位。
2. 服务器端“渲染应用”。耗时：6 个时间单位。
3. 服务器响应。耗时：4 个时间单位。
4. 客户端“下载 JavaScript”。耗时：7 个时间单位。
5. 客户端“水合”。耗时：3 个时间单位。

我们不再在客户端和服务器之间来回往返，而是把数据库查询作为初始请求的一部分，直接把填充完整的 UI 发给用户。

可是，具体要怎么做到呢？

要让这行得通，我们得能交给 React 一段*只*在服务器上运行的代码，用来做数据库查询。但 React 一直没有这个选项……即便用了服务器端渲染，我们所有的组件也都会在服务器*和*客户端两边渲染。

**生态系统为这个问题想出了很多方案。** 像 Next.js 和 Gatsby 这样的元框架（“元框架”是构建在 React 之上的框架，增加了路由、数据管理等额外功能）都创造了各自让代码只在服务器上运行的方式。

例如，用 Next.js（旧版的“Pages”路由）时是这样写的：

```
import db from 'imaginary-db';
// 这段代码只在服务器上运行：
export async function getServerSideProps() {
  const link = db.connect('localhost', 'root', 'passw0rd');
  const data = await db.query(link, 'SELECT * FROM products');
  return {
    props: { data },
  };
}
// 这段代码在服务器和客户端上都会运行
export default function Homepage({ data }) {
  return (
    <>
      <h1>Trending Products</h1>
      {data.map((item) => (
        <article key={item.id}>
          <h2>{item.title}</h2>
          <p>{item.description}</p>
        </article>
      ))}
    </>
  );
}
```
**我们来拆解一下：** 服务器收到请求时，会调用 `getServerSideProps` 函数。它返回一个 `props` 对象。这些 props 随后被传入组件，组件先在服务器上渲染，再在客户端水合。

巧妙之处在于，`getServerSideProps` 不会在客户端重新运行。实际上，这个函数根本不会被打进我们的 JavaScript 包里！

这种做法在当时*超级*超前。说实话，它真的好得要命。但它*也*有一些缺点：

1. 这个策略只在路由层面有效，只适用于组件树最顶端的组件。我们不能在任意组件里这么做。
2. 每个元框架都有自己的一套做法。Next.js 一种，Gatsby 另一种，Remix 又是另一种。它没有被标准化。
3. 我们所有的 React 组件都*总是*会在客户端水合，即使它们根本没必要这么做。

多年来，React 团队一直在默默琢磨这个问题，试图拿出一个官方的解决方案。他们的方案就叫 **React 服务器组件**。

## React 服务器组件简介

从宏观上讲，*React 服务器组件*是一个全新范式的名字。在这个新世界里，我们可以创建*只在服务器上*运行的组件。这让我们能做到诸如直接在 React 组件里写数据库查询之类的事！

下面是一个“服务器组件”的简单例子：

```
import db from 'imaginary-db';
async function Homepage() {
  const link = db.connect('localhost', 'root', 'passw0rd');
  const data = await db.query(link, 'SELECT * FROM products');
  return (
    <>
      <h1>Trending Products</h1>
      {data.map((item) => (
        <article key={item.id}>
          <h2>{item.title}</h2>
          <p>{item.description}</p>
        </article>
      ))}
    </>
  );
}
export default Homepage;
```
作为一个用了 React 很多年的人，我第一次看到这段代码时觉得它*简直疯了*。😅

“等等！”我的直觉在尖叫，“函数组件不能是异步的！而且我们不允许像这样直接在渲染中产生副作用！”

**需要理解的关键是：** 服务器组件永远不会重新渲染。它们在服务器上只运行*一次*来生成 UI。渲染出的值被发送到客户端并固定下来。在 React 看来，这个输出是不可变的，永远不会改变。（至少在路由层面发生某些事情之前不会，比如导航到新页面。）

这意味着 React 的*一大块* API 与服务器组件不兼容。比如，我们不能使用 state，因为 state 会变，而服务器组件不能重新渲染。我们也不能使用 effect，因为 effect 只在渲染*之后*、在客户端运行，而服务器组件永远到不了客户端。

这也意味着我们在规则上多了些灵活性。比如在传统 React 中，我们需要把副作用放进 `useEffect` 回调、事件处理器之类的地方，以免它们在每次渲染时重复执行。但如果组件只运行*一次*，我们就不用担心这个了！

服务器组件*本身*出奇地简单，但“React 服务器组件”这个范式要复杂得多。这是因为我们*仍然有*普通的老式组件，而它们如何配合可能相当让人困惑。

在这个新范式中，我们熟悉的“传统”React 组件被称为*客户端组件（Client Components）*。说实话，我不太喜欢这个名字。😅

“客户端组件”这个名字暗示这些组件*只*在客户端渲染，但实际并非如此。**客户端组件会在客户端*和*服务器两边渲染。**

我知道这些术语相当混乱，所以我这样总结：

- *React 服务器组件*是这个新范式的名字。
- 在这个新范式中，我们熟悉并喜爱的“标准”React 组件被重新命名为*客户端组件*。这是旧东西的新名字。
- 这个新范式引入了一种新的组件类型：*服务器组件*。这些新组件只在服务器上渲染。它们的代码不会被打进 JS 包，因此永远不会水合或重新渲染。

### 兼容的环境

通常，当 React 推出新功能时，我们只要把 React 依赖升级到最新版本，就能在现有项目里开始使用。一句 `npm install react@latest` 就可以上路了。

可惜，React 服务器组件不是这样。

据我理解，React 服务器组件需要与 React 之外的一大堆东西紧密集成，比如打包器、服务器和路由器。

在我写这篇文章时，开始使用 React 服务器组件只有一种方式，那就是 Next.js 13.4+，使用它全新重构的“App Router”。

希望将来会有更多基于 React 的框架引入 React 服务器组件。一个 React 核心功能只能在某一个特定工具里使用，感觉挺别扭的。React 文档有一个“前沿框架（Bleeding-edge frameworks）”板块，列出了支持 React 服务器组件的框架；我打算时不时去看看，看看有没有新的选择出现。

### 指定客户端组件

在这个新的“React 服务器组件”范式中，**所有组件默认都被视为服务器组件。** 我们必须“选择加入”才能得到客户端组件。

方法是使用一个全新的*指令（directive）*：

```
'use client';
import React from 'react';
function Counter() {
  const [count, setCount] = React.useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      Current value: {count}
    </button>
  );
}
export default Counter;
```
顶部那个独立的字符串 `'use client'`，就是我们告诉 React 的信号：这个文件里的组件是客户端组件，应该被打进 JS 包，以便在客户端重新渲染。

用这种方式指定组件类型*看起来*可能非常奇怪，但这种做法有先例：JavaScript 中用来开启“严格模式”的 "use strict" 指令。

我们不会在服务器组件中写 `'use server'` 指令；在 React 服务器组件范式中，组件默认就被当作服务器组件。实际上，`'use server'` 是用于服务器操作（Server Actions）的，那是一个完全不同的功能，超出了本文范围。

## 边界

刚开始熟悉 React 服务器组件时，我最先想到的问题之一是：*props 变了会怎样？*

比如，假设我们有这样一个服务器组件：

```
function HitCounter({ hits }) {
  return (
    <div>
      Number of hits: {hits}
    </div>
  );
}
```
假设在最初的服务器端渲染中，`hits` 等于 `0`。那么这个组件会产出如下标记：

```
<div>
  Number of hits: 0
</div>
```
但如果 `hits` 的值变了呢？假设它是一个 state 变量，从 `0` 变成了 `1`。`HitCounter` 需要重新渲染，但它*不能*重新渲染，因为它是服务器组件！

**问题在于，服务器组件孤立来看并没有意义。** 我们必须把视角拉远，从整体上考虑应用的结构。

假设我们有如下组件树：

如果这些组件全都是服务器组件，那一切都说得通。任何 props 都不会改变，因为没有任何组件会重新渲染。

但假设 `Article` 组件拥有 `hits` 这个 state 变量。为了使用 state，我们需要把它转换成客户端组件：

你看出问题了吗？当 `Article` 重新渲染时，它所拥有的组件*也*会重新渲染，包括 `HitCounter` 和 `Discussion`。可如果它们是服务器组件，就*不能*重新渲染。

为了避免这种不可能的局面，React 团队加了一条规则：**客户端组件只能导入其他客户端组件。** 那个 `'use client'` 指令意味着这里的 `HitCounter` 和 `Discussion` 实例必须变成客户端组件。

我在学习 React 服务器组件时最大的“啊哈”时刻之一，就是意识到这个新范式的核心在于创建*客户端边界*。实践中实际发生的情况是这样的：

当我们给 `Article` 组件加上 `'use client'` 指令时，就创建了一个“客户端边界”。边界内的所有组件都会*隐式地*被转换为客户端组件。即使像 `HitCounter` 这样的组件没有 `'use client'` 指令，在这种特定情形下它们仍会在客户端水合/渲染。（`HitCounter` 组件本身在其他情形下仍可能作为服务器组件渲染，比如被其他地方的某个服务器组件导入时。）

这意味着我们不必给每一个需要在客户端运行的文件都加上 `'use client'`。实践中，只有在创建新的客户端边界时才需要加。

### 变通办法

当我第一次得知客户端组件不能渲染服务器组件时，觉得这限制挺大的。如果我需要在应用的高层使用 state 怎么办？难道意味着*所有东西*都得变成客户端组件？？

事实证明，很多情况下我们可以通过重构应用、改变组件的*拥有者（owner）*来绕过这个限制。

这不太好解释，我们用一个例子来说明：

```
'use client';
import { DARK_COLORS, LIGHT_COLORS } from '@/constants.js';
import Header from './Header';
import MainContent from './MainContent';
function Homepage() {
  const [colorTheme, setColorTheme] = React.useState('light');
  const colorVariables = colorTheme === 'light'
    ? LIGHT_COLORS
    : DARK_COLORS;
  return (
    <body style={colorVariables}>
      <Header />
      <MainContent />
    </body>
  );
}
```
在这个结构中，我们需要用 React state 让用户在深色模式和浅色模式之间切换。这必须发生在应用树的高层，这样我们才能把 CSS 变量令牌应用到 `<body>` 标签上。

为了使用 state，我们需要把 `Homepage` 变成客户端组件。而由于这是应用的顶层，这意味着其他所有组件——`Header` 和 `MainContent`——也会隐式地变成客户端组件。

为了解决这个问题，我们把颜色管理的部分抽出来，放进单独的组件，移到单独的文件里：

```
// /components/ColorProvider.js
'use client';
import { DARK_COLORS, LIGHT_COLORS } from '@/constants.js';
function ColorProvider({ children }) {
  const [colorTheme, setColorTheme] = React.useState('light');
  const colorVariables = colorTheme === 'light'
    ? LIGHT_COLORS
    : DARK_COLORS;
  return (
    <body style={colorVariables}>
      {children}
    </body>
  );
}
```
回到 `Homepage`，我们这样使用这个新组件：

```
// /components/Homepage.js
import Header from './Header';
import MainContent from './MainContent';
import ColorProvider from './ColorProvider';
function Homepage() {
  return (
    <ColorProvider>
      <Header />
      <MainContent />
    </ColorProvider>
  );
}
```
我们可以把 `'use client'` 指令从 `Homepage` 中移除，因为它不再使用 state 或任何其他客户端 React 功能。这意味着 `Header` 和 `MainContent` 不会再被隐式转换为客户端组件！

**但等一下。** `ColorProvider` 是客户端组件，它是 `Header` 和 `MainContent` 的*父组件*。不管怎样，它在树中的位置仍然更高，对吧？

但就客户端边界而言，父子关系并不重要。是 `Homepage` 在导入并渲染 `Header` 和 `MainContent`。这意味着由 `Homepage` 决定这些组件的 *props 是什么*。

记住，我们要解决的问题是服务器组件不能重新渲染，因此也不能接收新的 props 值。在这个新结构下，由 `Homepage` 决定 `Header` 和 `MainContent` 的 props，而 `Homepage` 是服务器组件，所以没有问题。

**这东西真的很烧脑。** 即便有多年 React 经验，我仍然觉得它非常绕 😅。我花了相当多的练习才培养出对它的直觉。

更准确地说，`'use client'` 指令作用于文件/模块层面。在客户端组件文件中*导入*的任何模块也必须是客户端组件。毕竟打包器打包代码时，会顺着这些导入走下去！

## 深入底层看看

我们从更底层的角度来看。使用服务器组件时，输出是什么样的？实际生成了什么？

我们从一个超级简单的 React 应用开始：

```
function Homepage() {
  return (
    <p>
      Hello world!
    </p>
  );
}
```
在 React 服务器组件范式中，所有组件默认都是服务器组件。由于我们没有明确把这个组件标记为客户端组件（也没有在客户端边界内渲染它），它只会在服务器上渲染。

在浏览器中访问这个应用时，我们会收到一个大致如下的 HTML 文档：

```
<!DOCTYPE html>
<html>
  <body>
    <p>Hello world!</p>
    <script src="/static/js/bundle.js"></script>
    <script>
      self.__next['$Homepage-1'] = {
        type: 'p',
        props: null,
        children: "Hello world!",
      };
    </script>
  </body>
</html>
```
我们看到 HTML 文档包含了 React 应用生成的 UI，也就是那个“Hello world!”段落。这要归功于服务器端渲染，并不能直接归功于 React 服务器组件。

再往下，有一个 `<script>` 标签加载我们的 JS 包。这个包包含 React 等依赖，以及应用中用到的所有客户端组件。而由于 `Homepage` 组件是服务器组件，它的代码*不*在这个包里。

最后，还有第二个 `<script>` 标签，里面是一些内联 JS：

```
self.__next['$Homepage-1'] = {
  type: 'p',
  props: null,
  children: "Hello world!",
};
```
这才是真正有意思的地方。本质上，我们在这里是告诉 React：“嘿，我知道你缺了 `Homepage` 组件的代码，但别担心：这是它渲染出来的结果。”

通常，React 在客户端水合时，会快速渲染所有组件，构建出应用的虚拟表示。对于服务器组件它做不到，因为代码不在 JS 包里。

所以我们把渲染出的值——服务器生成的虚拟表示——一并发过去。当 React 在客户端加载时，它会复用这份描述，而不是重新生成。

这正是上面 `ColorProvider` 例子能够成立的原因。`Header` 和 `MainContent` 的输出通过 `children` prop 传入 `ColorProvider` 组件。`ColorProvider` 想重新渲染多少次都行，但这些数据是静态的，被服务器锁定了。

这*确实*意味着 JS 包变小的同时，HTML 文件会变大。组件的*定义*不再放在 JS 文件里，取而代之的是组件的*返回值*被内联在 `<script>` 标签中。平均而言，我们通过网络发送的数据总量仍然更少，但值得记住的是，服务器组件并非*完全*免费。我还要指出，HTML 文件是分块流式传输的，所以浏览器仍然可以很快绘制 UI，无需等待 `<script>` 标签里那些冗余内容。

如果你想看服务器组件在网络上序列化和传输的*真实*形态，可以看看开发者 Alvar Lagerlöf 做的 RSC Devtools。

## 优势

React 服务器组件是 React 中第一种“官方”的只在服务器运行代码的方式。不过如前所述，在更广泛的 React 生态中这并不*真*是新事物；从 2016 年起我们就能在 Next.js 中运行仅限服务器的代码了！

最大的区别在于，我们以前从来没有办法*在组件内部*运行仅限服务器的代码。

最明显的好处是性能。服务器组件不会被打进 JS 包，这减少了需要下载的 JavaScript 量，也减少了需要水合的组件数量：

旧版 Next.js（RSC 之前）

（图示：客户端与服务器之间的事件序列，每个事件列为一项。）

1. 服务器端“数据库查询”。耗时：5 个时间单位。
2. 服务器端“渲染应用”。耗时：6 个时间单位。
3. 服务器响应。耗时：4 个时间单位。
4. 客户端“下载 JavaScript”。耗时：7 个时间单位。
5. 客户端“水合”。耗时：3 个时间单位。

不过对我来说，这或许是最不令人兴奋的一点。老实说，就“页面可交互”时间而言，大多数 Next.js 应用*已经*够快了。

如果你遵循语义化 HTML 原则，你的应用大部分功能在 React 水合之前就应该能用。链接可以点击，表单可以提交，手风琴可以展开和折叠（用 `<details>` 和 `<summary>`）。对大多数项目来说，React 花几秒钟水合是没问题的。

**但有一件事我觉得特别酷：** 我们不再需要在功能和包体积之间做同样的取舍了！

比如，大多数技术博客都需要某种语法高亮库。我这个博客用的是 Prism。代码片段看起来是这样的：

```
function exampleJavaScriptFunction(param) {
  return "Hello world!"
}
```
一个像样的语法高亮库，支持所有流行编程语言的话，会有好几 MB，大到根本没法塞进 JS 包。结果我们只能妥协，砍掉那些不是至关重要的语言和功能。

但假设我们*在服务器组件中*做语法高亮。那样的话，库的代码根本不会被打进 JS 包。于是我们无需任何妥协，可以用上所有花哨功能。

这正是 Bright 背后的核心思想，它是一个专为 React 服务器组件设计的现代语法高亮包。

这就是让我对 React 服务器组件感到兴奋的那类东西。那些放进 JS 包代价太高的东西，现在可以*免费*在服务器上运行，给包增加零 KB，还能带来更好的用户体验。

而且这不只是性能和用户体验的事。用了 RSC 一段时间后，我开始真心欣赏服务器组件有多轻松。我们再也不用操心依赖数组、过期闭包、记忆化（memoization），或者其他任何由*东西会变*引起的复杂问题。

说到底，现在还处于非常早期的阶段。React 服务器组件几个月前才刚走出 beta！我非常期待看到它在接下来几年如何演进，社区如何像 Bright 那样不断创新，利用这个新范式。现在是做 React 开发者的激动人心的时刻！
