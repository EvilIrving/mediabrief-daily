软件慢是因为设计差，不是语言慢 ｜ Sean Goedecke ｜ - ｜ https://seangoedecke.com/software-is-slow-because-of-bad-design-not-slow-languages/

很多人说 AI 会靠把软件改写成更快的语言让它变快，但通常并不成立。C 可以比 Python 快约五十倍，但软件性能通常由 I/O 主导；在语言速度确实重要的地方，慢语言往往已有流行库去释放接近 C 的速度。性能是设计问题，不是语言选择问题。

多数真实程序是 I/O-bound。以带数据库的 CRUD 网站为例，一次请求约 50% 时间可能花在查库上；用 C 重写只能加速另外那一半，最好约快一倍，实践中更接近 1.5 倍（阿姆达尔定律）。程序也常要等第三方 API 或磁盘读写；即便把 curl 的代码加速 100 倍，大概也几乎察觉不到，因为它几乎都在等网络。

对明显不是 I/O-bound 的工作，慢语言往往已把重活交给快语言：wiki 用 cmark-gfm 渲染 markdown；Python 在机器学习与数学上仍有竞争力，因为库把负载卸到快速 C。若程序 80% 时间在 GPU 上做矩阵乘法，改写成 C 也很难更快。确有程序在慢语言里做大量 CPU 工作，但它们往往不重要——若重要，早该有人优化。Actual Computer 最近用汇编重写 tiktoken，作者本机上约快 5 倍（宣称 4–23 倍），但分词只占推理时间的一小部分；脚注还指出，提速可能来自绕开 regex 依赖的重设计。

尽管如此，多数软件仍远慢于它本可达到的速度；显著提速多半来自重设计，而非换更快语言。Bryan Cantrill 在 2018 年试图把一段精心优化的 C 改成 Rust，因与 borrow checker 不合而放弃，改用朴素写法，原以为至少慢 20%，结果反而快 30%，原因是 Rust 内部偏好 B-tree 而非二叉搜索树，缓存更高效。作者自己做过的显著提速几乎都是让程序少做事：缓存慢操作、异步化、并行、用单条 SQL 修 N+1、换更快查询、分页时只取当前页实体的附属数据。这些都与语言快慢无关；用慢的高层语言反而更容易一眼看出在做什么。

因此，让 AI 代理用 Rust/C/汇编整段重写，通常不是严肃的优化。更该让代理做 profiling、找热点、提出重设计。只有少数真正 CPU-bound 且无法减少工作量的热点，才值得用更快语言重写局部。换语言可以有可移植性、效率、可维护性等理由，但就原始速度而言，应关注设计。

edit：lobste.rs 上批评居多。有人认为 CRUD 并非 I/O-bound，因单次查询约 5ms、响应约 500ms；作者称判断来自盯过大量 Ruby flamegraph 的经验，一次请求几十甚至上百次查询并不罕见，但也承认只在少数公司做过。最高赞评论举浏览器布局引擎、3D 渲染器、文字处理器、神经网络等；作者同意它们是 CPU-bound，但估计总数大约只占 CRUD 程序的 5%，却占公开讨论的一半以上。还有人谈语言生态对性能的影响；作者认为那仍属设计——有些语言里，快的设计更自然。
