棕地项目中的 agent 工程（Brownfield Agentic Engineering） ｜ Addy Osmani ｜ 文章 ｜ https://addyosmani.com/blog/brownfield-agentic-engineering/

Addy Osmani 认为，在老代码库里，仓库已不能完整描述系统的真实行为，许多约束藏在团队经验、临时补丁和其他团队的依赖里，放任 agent 去改，可能得到"能跑"却设计错误的结果。所以关键是让隐藏的约束显性化，让廉价的改动变得可信。

他的做法是先由人给代码分区：测试好、隔离好的绿区让 agent 放手迭代，黄区先写特征测试再改，认证、计费、权限这类红区要么全程结对，要么不碰，升级分区要靠补齐测试来挣。自主程度取决于爆炸半径、可观测性和可恢复性，而不是模型多自信。文档只写代码说不出的东西，如业务规则和取舍理由；黄区和红区的工作先做只读调研，产出带引用的理解备忘录，再规划、由人选方案；同一条评审意见出现第二次，就固化成 lint、测试或 skill。

落地从零风险的工作开始：先让 agent 解释系统，再用特征测试锁定现有行为，测试不能由同一个会话独自写。迁移要按完整单元做，旧依赖删干净才算完成，否则 agent 会看到相互矛盾的先例。他列举了 Bun、Stripe、Spotify、Asana 等案例，指出能借鉴的是围绕 agent 的那套结构，而不是数字本身。

agent 让同时尝试多种实现变得便宜，但选择所需的证据并没有变少；并行要放在最后，因为它会放大已有瓶颈。衡量效果别看生成多少行，要看交付周期、人工干预、逃逸缺陷和回滚次数。agent 给模糊性标上了看得见的价格，这正是为维护工作争取资源的论据。
