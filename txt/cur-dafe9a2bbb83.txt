这篇发表在 Martin Fowler 网站"探索生成式 AI"系列的文章，作者是 Thoughtworks 欧洲、中东和印度区 CTO Giles Edwards-Alexander。他用 Claude Code（少量 Cursor）完全由智能体写了一个约 15 万行的应用，主要是 Rust，自己几乎不看代码。直到看见终端里在编辑某文件第 4000 行，他才发现数据访问层已膨胀成一个 17,155 行的单一 Rust 文件：每个读写查询都重复同样的 HTTP 设置和 JSON 编解码，没有去重，也没有内部语言。

他借这个文件做了一个实验，验证"现在花 token 重构，能否让以后的改动更省 token"。正因为智能体从不学习，实验才做得成：先定一个严格遵循重构纪律的计划，再设计一个代表性改动（新增一个带三个方法的 ItemWatchStore trait）。每完成一步重构，就让一个全新的子智能体做完全相同的改动，记录 token、耗时和行数，然后丢弃改动。由于 Claude 不能可靠地实时报告 token，改用字符数除以四来估算。

结果很明确：输入 token 在最大文件开始缩小前基本持平，随后"断崖式下跌"，从 159,564 降到 27,360，减少 83%，而且以后每次涉及这一层的改动都能享受这个节省。按 Sonnet 5 每百万 token 3 美元算，单次只省 39.7 美分，但它能否在调试、复杂功能和整个代码库上叠加，重构本身又要花多少，都还是开放问题。关键在于：数据层总行数几乎没变（最终拆成 19 个文件），省下来是因为智能体能准确找到并只读最小的相关文件。所以随意切文件未必有用，前面那些局部去重的步骤正是在为最后的拆分铺路，这也是重构通常的推进方式。输出 token 基本不变，作者说需要更复杂的样例改动才能研究，因为代码生成的随机噪声掩盖了差异。

过程方面，他直言 Claude 不擅长重构：只会照提示词做，不能自己判断该用哪些手法，必须由人引导；开发流程里本来就有的重构环节也从没让它主动改这个文件。Claude.ai 制定的计划比 Claude Code 更好，看出可以提炼出整个客户端类。执行时它用 grep 和 sed 的 Python 脚本机械改代码，经常被缩进搞乱，还漏掉了价值最大的一步（拆分 store），只好事后补上。整个实验约 8 小时，基本无人值守，变慢的真正原因是 cargo 构建缓存膨胀拖慢了测试。重构本身花了多少 token 没有统计，上限约 500 万。作者承认这只是单人全新项目上的一次实验，但它第一次量化了重构在时间和金钱上的价值。附录给出了代表性改动的提示词，以及按 Fowler《重构》第二版条目编号的 13 步计划：提炼 FirestoreClient 类、提炼辅助函数和 FieldsBuilder、以函数调用替换内联 json 宏，再逐步把查询、trait、编解码、FakeStore、各 store 实现和测试搬到独立文件中。
