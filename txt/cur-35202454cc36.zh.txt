https://lethain.com/small-changes/

Imprint 的工程师平均合并的 PR 数量是两年前的 4 倍。好耶。藏在这个平均数背后的东西更有意思：我们有两个团队在这段时间里合并的 PR 数量涨到了 10 倍。有一位工程师每周合并的 PR 数量是两年前我们工程师平均水平的 25 倍，还有好几位正在逼近这个数字。这挺不错的，而且从曲线的斜率看，一年后我们的平均水平会更接近今天的 p90，而不是今天的 p50。更重要的是，我们不只是交付得更多，质量也提高了：事故数半年环比下降了 42%，严重事故半年环比下降了 78%。我想我们一直都知道“质量与速度此消彼长”这个说法没多大用处，但到今天这一点已经无可否认。

走在这条路上，我们——和所有走这条路的人一样——撞上了 pull request 评审的问题。两年前，p50 的 pull request 评审大约 33 分钟完成，现在大约要 77 分钟。这条曲线的斜率与合并的 pull request 数量紧密相关。紧密到解决它成了我这一周的优先事项之一。

我们解决了！开玩笑的，我们绝对没有解决它，但我觉得我们目前的做法挺有意思，我们称之为 `small-change`（小改动）。

*这里讨论的工作由 Imprint 的许多同事共同设计和完成，包括 Dan、Joy、Daniel、Lenny、Taylor、Ted 和 Annie 等等。*

## 为什么要评审 pull request？

我们评审 pull request 有四个原因：

1. **作者和评审者之间的知识分享**——软件工程一般是通过学徒制学会的，而评审是资深工程师教别人什么是好软件的主要途径。我们认为，按现在的数量，这种知识分享将不得不转向针对一批批 pull request 进行，而不是针对单个 pull request
2. **防止错误**——评审一直是捕捉错误代价很高的环节，我们认为，有效的 CICD 加上 harness 验证技术（比如 poteto 的 pstack），是比评审更有效的防错机制
3. **防止恶意行为**——我的经验是，即便是仔细的代码评审，通常也会漏掉*有能耐的*恶意行为，不过幸好大多数恶意行为都没什么能耐。我们认为，这两类行为最好用以下组合来识别：固定规则（修改这些特定对象/类/文件必须评审）、我们在基于 LLM 的会员支持体验中打磨过的反滥用机制、审计，以及审计日志检查
4. **我们书面控制措施中的合规义务**——这些可以改，但目前它们要求在我们的一部分代码库中，变更必须由一名独立的人来评审

在现代开发范式下，我们认为这些问题各自都有更好的解决办法。但我们也希望非常谨慎地做这些改变。

## 用 `small-change` 小步前进

我们相信，快速前进的方法是找到范围窄、可控的方式来验证新做法，从而迭代出有效的方案。为此我们提出了 `small-change` 这个概念。它是这样运作的：

1. 当一个 pull request 被标记为就绪时，CICD 会判断它是否有资格成为 `small-change`。这体现为一项通过的 Github 检查。为了便于查看，*另外*还有一个标签，但决定资格的是检查本身，它由构建系统管理、人工无法修改。（标签用于初步筛选，但检查仍会独立验证。）
2. 满足以下全部条件的才算 `small-change`：
  1. 代码少于 1,000 行
  2. 我们的 `ai-code-review` 自动评审机器人没有给出 p1 或 p2 级别的问题
  3. 作者在该服务或应用上有“经验”，定义为此前已有 10 个以上合并进该服务或应用目录的 pull request。对于跨多个服务或应用的变更，作者必须在所有这些服务或应用上都有经验才符合条件
  4. 影响的不同服务或应用少于 `N` 个。在我们的前端 monorepo 中 `N` 为 1，在后端 monorepo 中 `N` 为 3，因为那里的典型变更会同时修改一个 gRPC 服务和一个公共 HTTP 网关
  5. 共享库和工具类文件不符合 `small-change` 资格
  6. 每个代码库都有一个 `.small_change` 文件，允许按路径定制，以便我们继续调整这些行为。例如，可以把一个处理资金流转的服务排除在外
3. 我们的 Slack 自动化会给每一处提到 pull request 的地方加上表情回应（reacji），标示该 pull request 的状态，例如测试失败、已批准但测试仍在跑，或者可以合并。我们新增了一个 `small-change` 表情回应，标出其中哪些 pull request 符合 `small-change` 条件
4. 在我们内部的技能库里，我们创建了两个技能，并已分发到各个 harness：
  1. `review-small-change`：接收一个代码库列表，评审其中所有处于打开状态、非草稿的 small-change，若符合评审标准（包括 `small-change` 检查在内的所有检查都通过，且不涉及支付、安全等敏感话题）则给予批准。重要的是，这个技能只有两个选项：批准或忽略。它*从不*在 PR 上发评论，以免助长“肉身代理评审”（meat proxy review）——在一些团队里，这已经成了一种伪装成解决方案的瓶颈
  2. `review-pr-cluster`：成批评审 pull request，找出其中反复出现的共同主题，并提出值得讨论和可以增加验证的地方
5. 我们确立了一种共识：任何由 `small-change` 引起的错误都是我们系统的失败，必须在系统层面解决：改进 `ai-code-review`、验证机制、CICD、harness 等等。

实现和推出这套东西大约花了两天，期间只是断断续续地投入精力，不过我估计我们会在很长时间里不断调整这里的各个参数。也许永远都在调。

## 肉身代理评审

我在上面 `4.1` 里提到过，肉身代理评审已经成了许多团队一个有意思的瓶颈。这个瓶颈特别难对付，因为它一开始*看起来像*解决方案，实际却让情况更糟。大致模式是这样的：

1. 团队被评审淹没
2. 团队决定用自己本地的 harness 来评审 pull request
3. pull request 收到大量评论，有些有道理，有些没道理。不仔细研究就分不清哪些是哪些，你也不知道哪些评论代表评审者本人的看法。结果你不得不花大量功夫去反驳一些评审者自己可能都不认同的评论
4. 接着这些团队开始用 harness 去回复 harness 生成的评论，整个评审过程成了一种假象，既不促进学习，而且最重要的是，完全可以在没有其他团队成员参与的情况下完成

凡是在做肉身代理评审的情况，团队如果把投入放在集中式评审机制、harness 处理集中式评审反馈的循环上，然后直接盖章批准，都会得到更好的结果。

## `fleet`：集中编排的 harness

我简单提一下我们减少代码评审量的另一种做法，它以我们集中编排的 harness `fleet` 为核心。（它类似于 Stripe 的 Minions，不过并没有特别采用那种一次成型（one-shot）的做法。）我们依靠 `fleet` 在云端一个高度受控的 harness 里实现和验证软件，并用独立的评估机制为每个变更确定合适的独立评审者人数。对于被评估为安全的变更，这个人数可以低至一个（例如 `fleet` 写代码，一个人来评审）。

## 结果 / 下一步 / 反响

说实话，现在给出有用的结果还为时过早。从早期结果看，大约 10% 的变更符合 `small-change` 条件。这些变更现在有资格获得非常快速的批准，而且一般都能拿到，除非触发了某个标记，通常是因为涉及安全或与资金相关的话题。

虽然 10% 是个小比例，但这里的核心理念是行得通的，最终成败取决于我们能否在接下来几个月里扩大这个比例，同时让验证机制变得越来越全面。归根到底，它的成败取决于我们改进验证的能力；而在规模复杂度低、领域复杂度高的软件里做到这一点，比在规模复杂度高、领域复杂度低的产品里需要更难的技术——在后者中，增量发布之类的许多技术都格外有效。（别误会，这些技术依然管用，只是当大多数用户的配置和行为各不相同时，它们提供的覆盖面更小。）

大家对此并非一致兴奋，这和我们学会做好工程师的方式相比是一个重大转变，而重新审视一项长期坚持的最佳实践是否已沦为教条，也让人不舒服。当前这一轮周期最令人振奋的地方在于，我们每周都能重新审视这些伴随我们成长的做法；最痛苦的地方在于，一旦我们停止重新审视，很可能就会落后。
