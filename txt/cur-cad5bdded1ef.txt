读代码之前我先跑的几条 Git 命令（The Git Commands I Run Before Reading Any Code） ｜ Hacker News ｜ 文章 ｜ https://piechowski.io/post/git-commands-before-reading-code/

代码审计顾问 Ally Piechowski 的一篇短文：接手新代码库时，她不先打开代码，而是先跑几条 git log 命令，从提交历史里看出谁建的、问题集中在哪、团队是自信地交付还是在雷区里踮脚走路。

第一条统计过去一年改动最多的 20 个文件（在 src 下跑，避开锁文件和生成代码）。排第一的几乎总是大家警告她"没人敢碰"的那个。改得多不一定是坏事，但改得多又没人愿意负责，是她知道的最明确的危险信号，那里的每次修改都是补丁上打补丁。微软研究院 2005 年的研究发现，按组件大小归一化的相对改动量能很好地预测缺陷密度，绝对数量则不行，所以她会拿前五名去和 bug 热点交叉比对。第二条按提交数给贡献者排名，看"巴士因子"：一个人占六成以上就危险，如果他半年前已经离开，那就是危机；也要看尾部，三十个贡献者里只有三个还活跃，说明建系统的人和维护的人不是同一批。她提醒，压缩合并会让作者信息只反映合并者。第三条筛出提交信息里带 fix、bug、broken 的文件，和改动热点同时上榜的就是不断坏、不断补、从没真正修好的最高风险代码，前提是团队写提交信息有纪律。第四条按月统计整个历史的提交数，看曲线形状：稳定是健康，某月骤降一半往往是有人走了，半年到一年持续下滑说明团队在失去动力，周期性尖峰说明在攒版本发布。她曾给一位 CTO 看这张图，对方说"这正是我们失去第二位资深工程师的时候"。第五条找过去一年的 revert、hotfix、emergency、rollback：一年几次正常，每两周一次说明团队不信任自己的部署流程，背后是测试不可靠、缺预发环境或回滚太难；零次也是信号，要么很稳定，要么没人好好写提交信息。

她的结论是，这五条命令几分钟就能跑完，不能告诉你一切，但能让你知道先读哪些代码、读的时候注意什么，这就是第一天有条不紊和四处乱逛的区别。
