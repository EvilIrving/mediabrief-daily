laike9m：这期我们想聊一下 AI 编程工具的趋势，也就是大家每天用的 Cursor、Claude Code 这些。因为我最近写了一篇关于这个的文章，包括我自己现在在 Google 做 coding agent，也有一些想法，就趁这个机会来聊一下。先想问一下小 A，你在工作中还是手写代码吗？还是基本都拿 AI 写？

小 A：现在手写的情况非常非常少，大部分时间都是用 AI 来写。

laike9m：那你在公司一般用什么模型或者 agent 呢？

小 A：我们用的模型就是 Claude 的 API，目前一般用最新的 4.8。agent 的话，其实用的也是 Claude 的 API，我们会有一些内部的 context，或者很多 skill、MCP、plugin 接入，但整体来说，agent 框架用的就是普通的 Claude API 作为 coding agent。

laike9m：你是想说 Claude Code 是吧？

小 A：对。

laike9m：我们在 Google 内部大部分时候也是拿 AI 写了。虽然我们没办法很顺畅地用 Claude，但用 Google 最新的一些模型，大部分情况下也是 OK 的。我们使用的 harness 就是 Antigravity 里面它自己的 agent。

其实我在回顾 AI 编程工具发展历史的时候，发现它可以分为两个很明显的阶段。第一个阶段大概是 2023 年到 2025 年，我把它称作从手写代码到 AI 写代码的阶段。在这个阶段你会用一些东西，比如 VS Code 加上一个 AI 聊天侧边栏，Cursor 一开始的版本也可以算到这一类，还有 Claude Code，或者说 coding CLI，我们特指在命令行里和 AI agent 交互的这些工具。你可以发现，在这个阶段，大家其实并不太清楚 AI native 或者 agent native 的编程方式是怎样的，那最简单的方式当然就是在已有的 VS Code 编辑器基础上加一个 AI 侧边栏，来实现所有 AI 功能。包括 Claude Code 的创建者 Boris 不是说了吗，它一开始也就是一个试验性项目，他们也不知道能不能成功，所以就用了最简单的方式做一个 CLI 来跑通流程，验证到底可不可行。最后发现大家很喜欢，所以很多人就去学了这种 CLI 的方式。但包括我在内，很多人现在都觉得 CLI 并不是特别好的交互方式，因为它确实还是太受限了。所以我们可以看到第二阶段，现在编程工具已经进化到了 agent native 的工作流。

小 A：现在大家使用 Claude Code 的主要模式还是通过 CLI，那为什么你会把 CLI 放在 23 年到 25 年这个过渡阶段呢？

laike9m：因为这个过渡阶段指的其实是这种产品类型出现的时间，和用户还在不在用是无关的。确实现在很多人还在用 VS Code，包括在命令行里用 Claude Code，这些都非常主流，并不是说没人用了，只是说它们是在 2023 到 2025 年这个阶段出现的，而我认为它们是一个过渡阶段，下面我会讲为什么。

现在就要说到第二阶段，AI native、agent native 的工作流，大概是从 2025 年下半年到现在。我们发现有一些产品形态一开始就是以 agent 为中心的。比如现在有一类，我把它叫作 AI coworker 协作软件，本质上是一个 chat app，但你在这个聊天工具里可以 @ 你的 agent 去完成不同的事情。类似你用传统的 Slack，但里面很多成员不是员工，而是 agent，大家在里面协同工作。我认为这是非常 AI native 的工作流。

小 A：你指的就是"小龙虾"吧？

laike9m：对，OpenClaw 也可以算作这个类型，它们其实都是搭载在 IM，也就是聊天软件里面的。

另外一种是更新的、我发现可能 2026 年才出现的类型，我把它叫作 agent 指令中心。这个需要解释一下。如果你打开我那篇文章，可以看到我提到 Cursor 在 4 月份发布了 Cursor 3，它完全重写了原来基于 VS Code 的界面。原来的 VS Code，你打开就是一个代码编辑器，右边有一个 AI 聊天窗口。但现在不一样了：它的最左栏不再是文件列表，而是 agent 会话列表；中间的主体部分是你和 agent 的对话，也就是我们之前放在编辑器右栏的那些东西，这就是它的默认布局。最大区别就是它不再以代码编辑为中心，而是以和 agent 的对话作为最主要的 user journey。当你和 agent 完成一轮对话，需要检查它改的代码时，可以点击对话里提供的代码链接，右侧会显示它做的修改，你可以手动改，或者给它一些反馈。你会发现逻辑变化很明显：在你不需要的时候，这种 agent 指令中心甚至不会让你看到代码。换句话说，你完全可以一行代码都不读、一行代码都不写就把事情完成。我觉得这看起来是一个 UI 改变，但本质上是"从人出发"还是"从 agent 出发"的一个很重大的改变。

小 A：对，这个很有意思。

laike9m：其实你可以发现，Codex 和最近发布的 Antigravity 2.0，它们的界面和 Cursor 3 完全一样，都遵循这个模式。

小 A：我认为 Codex、Cursor、Antigravity 这一类以 agent 为先的新一代编辑器，其实弱化了很多看代码的功能，对看代码的支持没有以前 VS Code 那么强大。这也让我们在开发中，如果还处在非常需要回到代码、关注代码的情景下，Codex 就会显得有些不适配。但我认为 Codex 是想打破传统开发工程师中 coder 和 software builder 之间的界限：你不再需要先成为 coder 才能成为 software builder，你可以是任何人，你是 PM、是 designer，都可以成为 software builder，其实是降低了 builder 的门槛。我理解它就是这个意思。

laike9m：对，我觉得这个东西怎么说呢，其实我也还没有很深入地使用这种 agent 指令中心的产品，但它确实是一个很大的转变。如果你需要读每一行代码，传统编辑器肯定会更好一点。但现在我们的假设是，随着编程模型和 harness 越来越强，你可能不需要读每一行代码了，就像 OpenClaw 的作者不是说了嘛，他 ship 的那些代码他都没读过，所以这可能是一个趋势。我在文章里贴了三张图，Antigravity 2.0、Codex 和 Cursor 3，你可以看到它们的界面基本长得完全一样。这三家公司可以说是整个 AI coding 的领军公司了，既然它们做出这种决策，你必须相信这个决策是有道理的、是依据数据做出的，不然它们为什么要把一个已经有几百万人在用的 app 重新设计？这没有道理。所以可以暂且认为，在一段时间内，这种 agent 指令中心会是最流行的 agent coding 模式。

既然这样，如果这些工具长得都差不多，功能也差不多，一个很自然要问的问题是：有哪些方向能让这些工具持续进化、变得更好，或者说现在的产品还没做好的地方？我觉得有四点，我先非常快速地过一遍，然后再对每一点详细讨论。

第一点当然是更好的 agent harness，这个大家都可以理解，agent harness 在变得越来越好。第二点是主动式 AI，就是让 AI agent 不只是听从你的指令干活，而是可以主动提出建议，比如它觉得这里应该改进。第三点，我认为非常重要、而且现在几乎被所有编程工具忽视的，是 agent native 下的团队协作。我说的编程工具就是刚才提的 Codex、Antigravity、Cursor 这些。团队协作在 AI coworker 那种聊天工具里做得非常好，因为它以聊天为核心。但在 agent 指令中心里，你想象这样一个场景：你的团队在没有 AI coding 的时候，每人每天可能只写 5 个 commit，现在可能每天写 20 个，这非常有可能。在这种情况下，大家在同一个项目上工作，就很可能出现上下文割裂。比如你对数据库 schema 做了一个修改，别人也做了一个修改，但两个修改是冲突的；你们都在很快地拿 AI 写代码，并不知道别人也在改，就造成了割裂。包括你做了一些设计上的修改，别人也不知道，因为你们的 AI agent 之间的 memory 是不共享的。我觉得这是一个非常大的问题，并没有被很好地解决。最后一点是可验证性，这在学界和工业界讨论得已经比较多了：agent 做了代码修改，你怎么保证这些修改真正有效、真正完成了你想做的事？

OK，我们现在深入每一点聊一下。第一个是更好的 agent harness。这方面的研究非常多，首当其冲的就是关于上下文 context 的研究。只要你用过或者开发过 agent，就会知道这是最头疼的问题：上下文特别大，上下文窗口就爆掉了。最常见的处理手段是 compaction，就是对话轮数太多时，把之前的内容压缩、总结起来，不把原始信息发给大模型，但这样会造成一些信息丢失。为了解决这个问题，我们也会用 memory 机制，让 agent 不要忘记一些最重要的事情。现在有一些比较新的研究叫 dynamic context，动态上下文，思路是不再把所有需要的东西，比如所有需要的代码文件，一起发给大模型，而是每次只发一部分，或者让 agent 自己去取，这能在一定程度上解决上下文窗口爆炸的问题。这方面的研究还有特别多，很难在这里说完。

另一些方面的研究包括更安全的 sandbox，也就是沙箱，用来执行代码。我也发现有非常多公司发布了自己号称为 AI 设计的 sandbox，这是一个热门领域。然后是记忆和技能的管理。因为记忆有可能会失效，对吧？未来用户新的输入可能和原来的记忆不一样，你就要更新、删除旧的记忆，管理记忆的生命周期。其实 skill 和记忆在某种程度上非常像，都是需要定期更新维护的东西，我也看到了很多这方面的研究。

然后就是 sub agent，这可能在过去一年里是非常热门的领域。像 Anthropic 现在很喜欢 agent teams，他们会说你要创建一个由不同人格的 agent 组成的团队，比如有一个领导者，有 coder，有 designer，大家一起完成一个东西，本质上就是写在 prompt 里。

小 A：但我想问，比如同样是 PM 角色，也可以有严谨的 PM、有创造力的 PM。我们作为使用者设置 sub agent 的时候，一般是不会指定 sub agent 的性格的，这时它能提供这种动态的性质吗？

laike9m：说到这个，有一个很有意思的东西，就是 Anthropic 最近做的一个叫 dynamic workflow、中文叫动态工作流的东西。它会根据你的任务，创建它自己认为合适的 agent teams 组合，比如到底是一个领导者带一个人干活，还是一个 worker 加一个 verifier，先干活再验证、再干活再验证，它有不同的组合，会自动决定你到底要用什么样的 agent。

我觉得很有意思的一点是：你记得去年 Anthropic 的理念是"你不需要再写新的 agent 了，只要写 skill"，对吧？你应该记得。但最后发现，他们还是在写 agent，现在还让大家写多个 agent。我自己觉得这是一个循环。之前大模型训练时，智能体的对话数据是不足的，agent 没办法很好地完成长时间、多工具的调用。当这些数据逐渐积累起来，agent 就能更好地完成这些事。这时如果你只需要一个 single agent 的 ReAct loop，用一个很标准的 agent harness 就可以完成，无非是添加一些不同的 skill、tool。而当人们需要更复杂的模式，比如 multi-agent 智能体团队，现在大模型训练数据里又没有多 agent 调用的数据，你可能就需要在 harness 层把它做得更加动态或者定制化。也许未来把这些多智能体训练数据再塞给大模型时，它自己就能决定最合适的 agent flow 应该长什么样，这时你的 harness 层又可以做得更标准化、更薄。所以我觉得这可能就是一个循环，未来说不定又有新的模式，你又要加厚 harness 这一层，这也是比较有意思的事情。

小 A：对，我觉得有一个说法，就是之后很多 harness 的部分都会被放进 pre-training。可能很多不同的代码需求，在 Claude Code 被更广泛使用的今天被展现了出来，而 Anthropic 作为 coding agent 的制造商，需要先把这些需求做成功能放上架，放进 harness。用户通过 harness 使用这些带新功能的产品，再用用户的 data 做训练，通过用户数据和 harness 对 harness 层的设计进行反馈，最后达到放进模型做 pre-training 的效果。

laike9m：对，其实这就是一个 feedback loop，你有更多的用户数据，模型就可以训练得更好。当然我并不是做大模型 training 的专家，如果有听众觉得这里有问题，也希望能和我们交流指出来。

小 A：对，也欢迎来当嘉宾。

laike9m：第二个，关于 AI 编程工具，我觉得接下来的趋势是主动式 AI。不知道听众们有没有尝试过这类产品。在我的团队，Jules 这个 coding agent 会扫描你的代码库，看其中有没有 TODO，或者哪些地方有性能瓶颈，然后给你提供建议。它生成一个建议之后会给你发一封邮件，你进去确认这是你想要的修改，它就会创建一个 GitHub pull request。这其实非常实用，因为有很多小的 fix 你写在 TODO 里，后来就忘了，对吧？包括性能优化，它生成的建议都非常好，所以我已经合并了不少来自 Jules 的 PR。其他一些 coding agent 可能还没有这个功能，但我觉得未来它会是一个方向。除了 TODO 和性能瓶颈，你会发现有很多维护性质的任务 AI 完全可以自动完成，比如修复代码风格问题，也就是 lint 这类；创建测试，比如它发现某些代码的测试覆盖率有问题，当然这种测试不能太复杂，可能就是一些单元测试；还有升级依赖，当然 GitHub 本身就有这种 bot，很早之前就能做了；包括修复一些安全漏洞。有很多可以归到维护类的工作，都可以让 agent 主动完成。另外还有一个很多人已经在做的实践，就是把 GitHub issue 或者 Jira ticket 自动变成 prompt 发给 agent，让它自动完成用户要求的某个修改。

小 A：其实我有一个问题。我觉得当我们说 AI 很主动的时候，它并非真正主动地创造了一个新的 workflow。现在更多是人类在之前的 coding 中已经发现了一个可行的 workflow，然后把它抽象、标准化，集成成一个你只需一键启动、它就能自动帮你做的 workflow。本质上还是需要比如 Jules 团队的工程师主动把人类之前的 workflow 发现出来，再慢慢集成进去。

laike9m：对，所以这可能就是未来的一个发展方向：agent 能不能真正做一些有创造性的修改，比如添加一个新的 feature，它觉得加这个有道理就加上，没有任何其他外部输入。我目前还不知道有没有团队在这么做，但这是一件很有意思的事情。

小 A：我觉得应该有，只要你把 validator 加上，就可以拼命地做 A/B test。

laike9m：现在有一些是你设置一些比较高层的目标，比如"我就是想提高这个产品的转化率"，AI 可能会给你发一些 PR 做修改。但你总得有一些输入，我还没看到完全不依赖外部输入、AI 就能去改产品的，或许有，我不知道。

小 A：可能是没有高质量的。

laike9m：对，因为这样可能噪音很大，而且白白浪费 token，它做的修改不是你想要的。所以这还是一个有待探索的方向。

下一个 agent 进化的方向，我觉得是团队协作。我之前也简单描述过这个问题：当团队里所有工程师都在用 agent，你一天可能提交原来 10 倍的代码，就会有很多冲突，包括决策其实都是互相隔离的，每个人都只跟自己的 agent 对话，而没有和其他工程师沟通协作。一个很自然的想法是，如果我们做一个我称为 team memory、团队记忆的层，把每个人的记忆汇总到这里，让你的 agent 可以访问同事 agent 的记忆，是不是就能在一定程度上解决这个问题？我发现有一家创业公司就在践行这个理念，他们甚至做得更进一步：把团队开会录下来、转成文字，让 agent 提炼成 memory，以后你就可以说"我们昨天在一个会上讨论了什么什么，根据这个讨论，你去做什么什么事情"。这是他们的解决方案。但我觉得真正想解决这个问题，应该把 team memory 层做得更加无感，甚至集成进现在的 Codex、Cursor 或 Antigravity 里。我觉得团队规模越大、团队对 AI 的采用越多，这个问题可能就会越严重。因为我们在内部大量用 agent 开发一个产品的时候，已经感受到了：比如今天我的一个测试还是 work 的，明天突然就不 work 了，为什么呢？我一看，原来是同事做了一个修改，把我 break 了。但它不是直接的代码依赖，所以没办法在编译时检查出来。假设我的 agent 能通过 team memory 层提前知道"其他人已经做了这个修改"，我就可以做出对应的修改，或者发现之后去跟那位工程师协商：你这个修改可能有问题。所以我觉得团队协作是现在所有 agent 工具都解决得不太好的地方。

小 A：我看到有一些非常简单的解决方式，比如在 Codex 这类工具里直接建一个 team workspace，这样怎么样？

laike9m：team workspace 相当于它所有的 agent 都跑在云端，所以本来就是共享记忆的，是这个意思吗？

小 A：对。

laike9m：对，这种是可以的，相当于天然把所有人集中在一起，所有 agent 的对话对其他人都是可见的，这能解决这个问题。但我觉得还有一些没解决的问题，就是不是所有人都想把所有工作都放到 team workspace 上，这是一个问题。只要涉及记忆提取，就会有隐私问题，包括数据敏感性的问题。我看到之前做 Slack 的那批人，他们有一个很经典的论断，让我找一下。对，他们的一个工程师说："IM is the ultimate source of correct context and the most natural interface for growing context." 翻译一下就是：即时聊天软件其实非常适合收集上下文，并且是让上下文不断增长的最自然的界面。我确实非常同意。我之前说团队上下文没法很好管理，更多指的是 Codex、Antigravity、Cursor 这些；但如果你用的是 AI coworker 那种聊天软件，上下文天然就是共享的，因为大家就是在一个 workspace 的上下文里工作，这会好很多。但这些 app 又缺少编辑器本身的功能，所以如果能把两者结合起来，我觉得会非常好。

小 A：你指的是比如我跟我的 coworker 在 chat 里聊着聊着，代码就自动生成了？

laike9m：对，我们假设你在一个聊天群组里有很多 agent，你跟一个 agent 聊天，这些信息对其他 agent 也是可见的，它们天然就共享上下文。这是团队协作。

最后就是 verification，验证。不知道大家有没有看过自己和 agent 对话的轨迹，现在很多 agent 在最后一步都会自己做一些验证。比如你添加了一个 HTTP endpoint，它可能会起一个 local server，给这个 server 发一些请求，看返回值是否符合预期。基本上现在所有 coding agent 都会做这种简单的验证，如果验证失败，它会尝试修复问题，继续这个循环，直到测试通过。那这是否意味着验证问题已经解决了呢？我觉得不是。我觉得现在最大的瓶颈还是测试环境的搭建。发送 HTTP 请求当然是非常简单就能完成的任务，但比如更复杂一些的前端修改，你可能就需要浏览器自动化，也就是 browser use，甚至需要录制视频或者截图，再用一个大模型的 evaluator 去评估它是否完成了你的任务。这本身就是一个非常复杂的过程，甚至应该放进一个 sub agent 里。又或者你正在修复一个 Android 应用里的 bug，但本地根本没有 Android 工具链，怎么办？现在比较通用的解决方法是，所有 agent 本身就跑在一个远程沙箱里，沙箱已经装好了你所需要的依赖。但至少我看到的，更多还是针对某一个团队，比如这个团队有固定的项目，那沙箱里就装这些固定依赖，很难做成完全通用的 agent，因为需求千奇百怪，要做到通用我觉得很难。但也许也并不需要做到通用，因为给你的团队做一个沙箱也并不是非常困难的事情。

说回来，我觉得验证这一块非常重要。我的前老板跟我说过一句话：如果 agent 能够验证它的工作到底有没有完成任务，那它基本上就可以做任何事情。因为你只要让这个循环继续下去，让它一直找问题、解决问题、找问题、解决问题，直到验证它真正解决了，就可以完成非常非常复杂的任务。所以我觉得验证才是真正决定 agent 上限的能力。

小 A：我觉得主播说得非常对。这让我想到之前比较火的一个观点：当你使用 agent，特别是做一些比较后端的工作时，第一步并不是让它直接开始工作，而是先搭建你的验证系统，验证系统搭好后再让它开始工作。但我感觉这并不适合所有工作，可能有些工作一开始验证模型并不那么清晰。但对很多比较清晰的工作来说，应该先把验证这一步做好，然后再做其他的。
