Web 开发体验（DX）的本质矛盾在于：高层框架为了追求便利性引入的控制反转（Inversion of Control），往往以剥夺开发者已有平台原生知识的运用为代价，导致系统在遭遇未预期需求时陷入高成本的破坏性妥协。

Web 平台经历了从静态文档载体向全功能应用平台的演化，数十年的历史沉淀使其 API 呈现出鲜明的非均质性（Lumpiness）：底层存在 WebAssembly 这类极致开放但缺乏高层便利的低级虚拟机原语，上层存在 CSS 这类声明式表达力极强但边界严格锁死的特定语法，且不同时代的 API 风格（如基于事件监听的旧接口与基于 async/await 的现代接口）深度交织。《可扩展 Web 宣言》（Extensible Web Manifesto）确立了优先制定低级平台原语、将高层抽象留给生态探索的演进哲学。面对这种坑洼不平的平台现状，广大 Web 开发者历经长期实践，早已深刻掌握了 HTML、CSS、事件冒泡机制以及 History API 等底层特性的微观行为。

高层框架与抽象类库在提升开发体验时，最核心的挫败感往往并非源于底层平台的缺陷，而是当开发者手中明明拥有清晰的 Web 平台原生知识足以解决问题时，高层抽象却构筑了严密的屏障，强行阻止开发者运用这些既有知识。

借用 Martin Fowler 的架构定义，类库（Library）与框架（Framework）的根本分野在于“控制反转”（Inversion of Control）：
使用类库时，控制权牢牢掌握在应用代码手中，类库只是被调用的功能插件，其接触面极小，替换或弃用时的系统爆炸半径（Blast Radius）微乎其微；而框架则通过好莱坞原则（“不要调用我们，我们会调用你”）将自身置于系统运转的绝对中心，强制应用代码按照框架预设的插槽与生命周期运转。当开发需求严格落在框架设计者的预设轨道内时，这种反转能够提供顺滑的效率提升；然而一旦业务演进催生出框架未曾预见的边缘用例，开发者便会遭遇灾难性的架构阻碍。

针对这一困境，系统设计必须确立三项核心架构原则：
第一，构建具有平滑梯度的逃生舱（Escape Hatches）。由于任何抽象均不可能穷尽所有现实场景，逃生舱是防止工程卡死的生命线（例如 React 提供 ref 属性暴露真实底层 DOM 节点）。然而传统框架的逃生舱往往存在严重缺陷——开发者一旦突破抽象层，就必须断崖式地跌落至最原始的裸平台环境，被迫全盘重新手动实现框架所托管的状态同步与生命周期逻辑，造成极其高昂的补偿成本。
第二，最大化复用平台原生既有范式。优秀的抽象应当顺应平台现有的认知习惯，而非凭空臆造专属的私有概念。例如在处理深层嵌套组件向远端根节点传递状态变更时，利用平台原生支持的自定义事件冒泡（Custom Event Bubbling）即可优雅实现跨层级通知，无需强行引入复杂的外部全局状态总线；在引导开发者接入时，应坚持每次仅引入一个增量概念，避免给工程师施加认知过载。
第三，推行类似立体停车场的垂直分层架构（Multi-storey Car Park Architecture）。系统设计应彻底废除“非全即无”（All-or-Nothing）的单体抽象，将其重构为清晰递进的多层结构：底层采用纯粹的语义化原生 CSS；中间层封装为通用且符合 Web 标准的 Web Components 自定义元素；最顶层才提供轻薄的特定框架（如 React/Vue）语法糖封装。这种分层使得团队在遭遇框架限制或技术栈迁移时，能够从容地逐层向下退守，在保留绝大部分下层资产的同时灵活定制上层交互，杜绝推倒重写的破坏性重构。

衡量优秀开发体验的标准，绝非单纯提供极致封装的短期便利，而在于对平台原生知识的尊重与兼容——让每一层抽象均保持可替换性与可选性，并向开发者敞开通往下层原语的渐进通道。
