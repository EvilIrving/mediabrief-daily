# 扩展 Slack 与 GitHub：与 Maude Lemaire 对谈

当一个数百万人每天使用的产品，其底层架构开始撑不住时，你该如何扩展它？今天的嘉宾在 Slack 和 GitHub 都做过这件事。Maude Lemaire 是一名 principal engineer，也是《Refactoring at Scale》一书的作者。她在 Slack 待了八年，在 GitHub 做数据库扩展，在 Cursor 改善首个 token 的生成时间。今天我们要聊：

50 万 WebSocket 连接的负载测试；一个项目里，使用无头 Chrome 实例太耗资源、也太贵；为什么 GitHub 当时只有 16 个数据库分片来承载所有拉取请求和 issue；为什么散射查询在像 GitHub 这样的大型 Rails 单体应用里是个巨大的麻烦；为什么平台工程师和产品工程师应该在团队之间轮岗；以及更多内容。

如果你想了解我们可能每天都在使用的产品内部，规模扩大时是什么样子，这集就是为你准备的。本集由 turbopuffer 呈现，它是在对象存储之上构建的向量搜索和全文搜索。它快速、便宜，而且扩展性极强。本集由 Antithesis 赞助，这是一个让你能自信发布的平台。

在今天的节目里，我们会聊到在系统扩展时重写大规模生产系统，这是一种工程挑战，就像在半空中重建一架 747。但使用 AI 编码智能体时，为什么不能只靠代码审查？因为对于做到这一点，代码审查是一种越来越天真且低效的方法，所以 Antithesis 远远超出了这种做法，它会在一个敌意模拟环境中运行你的整个系统。

这个模拟既包括定向测试，也包括模糊测试。通过运行模拟，它会在用户之前发现每一个 bug；而且由于模拟是完全确定性的，它不仅能发现 bug，还能为每个问题提供完美的复现，这使得修复问题容易得多。

在创业公司的世界里，当你需要进入下一个阶段，拿下下一个客户，或者做出你认为会抓住什么的下一个功能——就像，你会做很多短期决策，你知道，可能在你灵魂深处，你总有一天会回头处理它们。而我们当时做的很多性能工作，就只是在重新审视——捷径。我是说，像经过精心计算的捷径。但也是我们知道最终迟早会让我们自食其果的捷径。所以当时我做了很多那样的工作。那是在企业版——Slack Enterprise 产品——发布之前。所以我是在 GA 前几个月入职的。IBM 当时已经在试用——这个产品——他们当时算是处在 beta 阶段。他们是一家大公司，很多人在那里工作——如果我没记错，有 10 万多人。是啊。所以当时的一个区别其实是，让……是没问题的——几万人同时待在一个频道里。而我们当时有点像是把他们分散到同一个 Slack 组织内的不同团队里。显然，他们可以互相发 DM，还有别的一些功能。那样勉强行得通——但 IBM 当时经常撑不住。而且——我想我没有参与这些对话，但事后看来，我的印象是，当我们同意 GA 时，他们也同意会开始扩容，给 Slack 增加更多用户。就像，一旦我们达到 GA，你知道，我们就不能那么紧地拽着缰绳、限制你们增加更多人了。所以我们到了 GA，然后——他们开始相当激进地增加更多用户。我们最终不得不专门组建一个团队，那就是企业性能团队。我最终能加入那个团队，是因为我恰好一直在处理一些零散、随机的性能问题。我绝对是团队里资历最浅的人。

那能不能来一点 2016—2017 年 Slack 架构的 101？现在，我们知道 Slack 已经变了很多；这完全不是它今天的样子。但当我们想到 Slack 工作区、频道、私密群组、私信时，

幕后是怎么搭起来的？从数据库角度，从你给某个人或某个频道发消息时发生了什么的角度，从扇出或写入的角度？那么，企业版之前以及企业版仍然沿用的模式是：一切都属于一个公司、一个工作区、一个团队单元。

而且所有数据也都是按团队分片的。所以如果你在一个非常大的团队里，那我们就会给你一个更大的数据库，直到最终你用尽能向亚马逊砸钱买到的最大数据库规格。但你是说，曾经有一段时间这种分片是可行的，那时——

一家大公司可能就拥有自己的数据库实例，而且有一段时间它能撑住——确实能撑住；它们没有把它填满。对。而共享的小公司——会有多个公司共用同一个多租户数据库实例。但作为客户，你的数据并没有分散在多个数据库分片里；它就在这一个分片上。

这也是我们分发消息的方式。所以就 WebSocket 连接而言，当你连接、登录 Slack、建立那个 WebSocket 连接时，你是在与一台与你公司关联的服务器建立那个 WebSocket 连接。

所以如果你公司的每个人都非常忙、在 Slack 上聊得非常起劲，你们所有人就都在同一台服务器上。再说一次，如果我们有非常非常忙的客户，最终我们也可以说：‘哦，好吧，这是你的……实例，具体就是——’

聊天服务器。而且在很长一段时间里，这基本没问题。企业版开始以一些特殊方式让这件事变复杂，因为我们——我的意思是，再说一次，创业公司嘛，你总会做出一些当下没问题、但后来就扩展不了的决定。

我们多少假设了，在真正的大公司内部，其实是一个个更小的公司。所以，比如说 IBM 的市场部就是一个独立的公司，于是你登录的是市场部工作区。

在 IBM，或者工程部门工作区。我的意思是，工程部门其实太大了，所以是 IBM 工程部门里的某个子集。听起来这有点像一厢情愿——你可以把一个大问题拆成更小的问题，对吧，然后就能让现有架构继续工作。但仍然需要有一个总揽全局的实体。

于是我们创建了一个企业实体，它其实只是团队表里的另一行，只是带有 is_enterprise = 1，然后所有与该企业关联的团队都有一个企业 ID。

而在 IBM 内部，你仍然会想说——比如你在某个工程团队，我在另一个工程团队，我们想协作，我想能给你发私信。我们在同一家该死的公司。我应该能给你发消息。我们假装公司内部的这些团队是它们自己的公司，但后来我们又不得不创建另一个实体。

那个实体统领一切，让你仍然可以跨团队。而这就很快变得非常复杂。但真正变得糟糕的部分是，IBM 所有人，不管是在市场团队、工程团队还是别的什么团队，全都在同时查询企业分片，以获取他们所有的私信、公司级大频道，以及所有这些东西。

然后在这些数据里，当你启动 Slack 时，左侧边栏会显示你的频道。你会以为事情很简单，就像：‘太好了，拿用户 ID，查出所有频道成员关系记录。’

事实并非如此。我觉得初衷是好的：私信看起来和普通公开频道是两回事，对吧？就像，你知道的，它们看起来不一样，所以那被做成了一张单独的表。

而公开频道就是公开频道，所以那也是一张单独的表。但后来私有频道看起来又不一样了，我觉得，从产品角度看，你完全能理解这一点；从产品安全角度看，你也完全能理解，在查询私有频道时你会希望有更多审查。

所以那也是一张单独的表。后来群组私信出现了，它看起来就有点像私有频道，于是就被直接粘进了私有频道表里。所以当你执行那条查询来填充侧边栏时，你实际上是在做一个又大又老的 join、union 查询。

那后来发生了什么？一旦你们——一旦团队意识到，或者说发现，这三张表并不合理，可这时你面对的是大量客户，包括 IBM 这样的公司，你知道，正把大量负载压在上面，他们在用这套东西。是啊。你怎么从这三张仍在被活跃使用的表迁移到一张表，而且还得一直保持运行？嗯，我觉得这事是从——计算提及数。所以计算提及数，比如为了显示那个徽标图标，也是一条非常复杂的查询，你得连接所有这些表——而且对延迟非常敏感。我们当时已经经历过一个过程，尽可能做了我们能做的一切，来——减轻负载。我有一位队友在做提及相关的工作时，他说：‘我们得——我们得把这些表合并起来。这不行——就像，我们能做的只有这么多，再往下就得真的开始挖坑了。’所以我就说：‘当然，行，我愿意去做这件没人想做的、非常吓人的事；这看起来完全没问题。’我现在回头看，也更能理解这件事了，因为如果你去看 GitHub 上的 Flamework——那是 Cal Henderson 在写完 Flickr 之后开源的 PHP 框架——它会解释很多事情。

而 Active Record 的问题在于，只有当查询完全相同时，它才会自动缓存输出。所以，比如说你在获取用户信息，像那种完整、笼统的 `SELECT * FROM users WHERE user_id = blank`，你拿到了完整的用户对象；但后来你又执行 `SELECT * FROM users WHERE user_id = blank AND something else`，它不会回头去取第一次查询缓存下来的结果，因为这些查询并不完全相同。每一个计数——至少在我离开的时候，GitHub 页面上你看到的几乎每一个计数——都是实时计算出来的。

但到目前为止，我们其实没怎么聊 AI——它就是没自然而然地出现。我想先问，你到目前为止怎么看 AI？你显然一直在用这些工具，而且用得越来越密集。哪些工作 AI 帮不上你，哪些部分它帮到了你，它有没有改变你的工作方式？

哦，天哪，是啊。它在性能优化上基本完全没帮到我——至少调查那部分没有。也许实现那部分会快一点，一旦你知道自己想做什么。但是啊，搞清楚我想做什么……比如说，我几个月前在 Cursor 想改进首 token 时间——首个可见 token 时间。

有很多因素会影响你多快开始收到那些 token。你输入提示词时，会花掉相当多的时间，

然后你按下提交，构建与即将发给 LLM 的请求相关的全部上下文，会花掉相当多的时间。接着，有一部分数据我们能缓存，有一部分不能缓存——既因为产品原因、隐私原因，也完全是因为——

负载，还有——再说一次——这些系统的成本。把你在 Cursor 查过的所有东西都在 Redis 里缓存 24 小时，可不便宜。那是很大一笔钱，所以我们不会那么做。

然后最终把那个请求发送到推理代理，推理代理再把请求发送给底层的 LLM 和各提供商。考虑到其间发生了这么多事，而且还有大量来回往返，这个过程的很多部分其实并不像这种体验让你以为的那样同步。

而在常规流程中，如果你运气够好能用上 HTTP/2——外面还有些可怜人被困在 HTTP/1 上——你会与后端服务器建立那条 gRPC 流式连接，并且能把这条连接拆成大概四条或更多条并发流，在这些流上收发不同的信息片段。

这非常复杂。另外，AI 还自以为很擅长给这些系统加埋点。事实证明它们并不擅长。它们以为——这就像写测试一样。它们以为自己很擅长写单元测试，但实际上它们真正擅长的，只是确认自己刚写下的东西。

所以我最终编写的一些技能，会先对代码跑一连串密集的变异测试，从而迫使 LLM 意识到：‘哦，我其实一个边界情况都没测到。让我重写这些测试，谢谢。’

所以我觉得，现在的 LLM 擅长做非常基础的埋点，但不擅长判断——尤其是在异步环境下——哪些东西值得埋点，以及该怎么埋点。

我喜欢 trace，我觉得它们非常棒。你能从中得到大量非常好的调试信息，尤其是从性能角度看。我们在 Cursor 就遇到过这个问题：我们的 trace 既太多又太少——我的意思是，我们有些 trace 包含……数百万乃至数千万个 span，而这些 span 完全没用。一个包含那么多 span 的 trace，你没法拿它做任何有意义的事。然后我们还犯了几乎人人都会犯的经典错误：我们因为成本原因开始采样，但不是在同一处采样——而这又……很容易让 LLM 这么干，因为它会说：‘哦，帮我找个能少发 trace 来省钱的地方。’然后它就想：‘行啊，我就在发给 Datadog 之类的东西之前采样一下。’不不不，别——别这么做。拜托别这么做。永远要在同一个地方做采样。重复采样的问题就是会严重得多，当你处理…………这种情况时。所以我最终不得不做的第一批事情之一，就是老老实实手动给很多这类流程加埋点，并亲自通读代码，弄清楚：‘好，这一段处理是同步的；这一段处理是异步的。’然后把所有这些整合起来。我开始这么做的方法之一，是让它生成一张很大的时序图，涵盖首 token 时间（time to first token）中的所有环节——也就是从你点击提交，到你收到第一个可见 token 为止。

那张图非常巨大。我去了 Staples，让他们把它打印在大张的蓝图纸上，因为我仍然是个很依赖纸笔的人。然后我对照着它去读代码，在那张大纸上做标注，比如：‘好，这是对的，或者这是错的；这一部分我们也许可以做点什么。’这一块——不，实际上它肯定得在另一块之前发生。我还发现它有一件事错得很离谱，就是它会去找那种经典的、可能——它当时在做什么？LLM 到底做错了什么？哦对，它做错的地方是……它在找——嗯，‘错’——‘错’这个字本身就不太对。主观看法嘛，我喜欢。天真地讲，天真地讲，它当时做的是：假设你有一堆事情；你发现有一堆彼此不依赖的任务，对吧？

但这些任务对延迟很敏感。经典解法是什么？把它们并行化。然而——再说一次，戴上产品经理的帽子，对吧？——如果基本上根本没人会做那四件事呢？那你为什么要把它们全都做了？

与此同时，你是在浪费资源、浪费延迟——你在等待，你在无缘无故地增加负载。所以我记得——我想是，恐怕我想是 Opus——它非常兴奋，像是发现了把这些任务并行化的机会，而我说，哦，乍一看，当然，那似乎……

像是件好事，但问题是，即使你把它们并行化，最长的那一个无论如何总会是瓶颈。而最长的那一个一直都比另外三个长得多，另外三个任务被运行的

比例如此之小——只有1%的用户会做另外三件事中的任何一件——所以这最终完全是浪费时间。就像，这并不是它向我推销的、作为灵丹妙药来

改善首个 token 的时间。而且很多实际上相当有帮助的事情，都是些非常傻的事情——我是说傻，比如在合理范围内提高我们存在 Redis 里的内容的 TTL。你是怎么用 LLM 的？因为到目前为止我的感觉是，从你的职业经历来看，你会看一个问题，理解它，想出怎么做；如果有时候失败了或犯了错，你会从中学习，也会向别人学习——包括现在，在过去几年里，AI 越来越无处不在。但当你让系统更可靠、性能更好时，听起来你仍然在做大量思考，大量——你现在，我感觉，是在旁边用 LLM来生成一些想法，来说不，这是错的；不，那是个好主意，好，让我用它。但和我交谈过的很多软件工程师不同，甚至在这个播客上，大多数人都在说，哦，我以前做的很多工作，LLM 都做了；我现在可以做更多事情，我可以专注于更高层的东西。我没有从你身上得到这种感觉。

是的，我的意思是，我整天都在以某种方式、某种形式和一个 LLM 聊天。我觉得我仍然做很多普通的工程工作，比如有时候我要值班，我就是得修一个愚蠢的 bug。

但我确实倾向于——我会做很多初步探索，但之后会手动验证。而且我经常这么说。就像，听起来即使你从 LLM 或别的什么那里得到东西，你也会验证，你会确保自己理解这是对的。

听起来你并不能判断它到底是对还是错，但你需要验证它，对吧？对，对，因为我觉得我处理的很多问题更像是产品平台类的问题，而重点是要整体性地解决一个问题。

并且要创建那个你可以在此基础上构建的基础，对吧？如果你只把地基建到覆盖房子的大约80%，那有什么意义呢？因为那另外20%没有建在地基上的部分将会

非常摇晃，并且影响你确实建在地基上的房子的其余部分。如果你已经在这边这么做了，那么，实际上没有什么能阻止你，比如说，再在地基之外加上10%，然后那又不断螺旋扩大，对吧？所以我觉得，尤其是，尤其是现在，就像……我觉得 AI 非常擅长到处复制东西，因为那看起来没问题，而它没有那种意识——它不擅长追问，你知道，'但为什么，但为什么'，而且是往上追问20层。它更倾向于'我就直接加上去。'我就直接在地基之外建一个额外的浴室，那没问题，对吧？就像，你让我建一个额外的浴室；我就在那里建，而不是质疑底层的基本假设，也就是：难道应该把浴室建在没有地基的地方吗？

而这些就是我一直在问自己的问题。我觉得部分原因是我来自产品平台的视角。我有一种感觉，产品平台的工作，也就是平台在可靠性和性能方面的工作，只会变得更加重要，因为再说一次，我们会有承载如此多负载、如此多压力的系统。

对于一个可能经验不多、也可能经验不少，但对性能和可靠性这个想法很兴奋、并且希望更靠近最终能在平台团队工作的软件工程师，你会有什么建议？你见过人们通过哪些路径进入你工作过的平台团队？他们是如何完成转变的？

我非常主张让更多产品这边的人——其实，是让产品这边的人和产品平台团队之间有更多交流。我很多次看到，产品平台团队是由那些非常在意……的产品工程师组建起来的。

最根本的东西，对吧？他们在意可靠性，他们本来就在意性能，他们一直试图改进这一点，并把它注入自己构建产品的方式里。然后我觉得，我合作过的最优秀的产品平台人，会到达这样一个阶段：他们已经——

在他们作为产品工程师构建东西的过程中，把一种模式看够多次，然后他们会想：'我想深入进去，把这个问题全面地解决掉。这个具体问题，因为我已经实现过两次、三次、四次，所以我理解得很深。我想去一劳永逸地解决它，然后完事，并且，做出一个别人也能用的东西，对吧？如果他们被这种重复劳动烦到了。'然后他们会去，也许是嵌入到一个产品平台团队里，或者和其他几个人一起拉起一个团队，然后他们就这么做；再然后，很多时候这些人最终会留在产品平台团队，继续真的很喜欢产品平台的工作，但随后他们越来越脱离产品开发实际是什么感觉。

而我觉得，这就是你会看到产品平台团队和产品团队之间最终被制造出来的那道鸿沟的地方——只是团队之间没有足够的交叉交流。所以我见过让那道鸿沟重新弥合的方式之一，就是让这些团队之间有轮岗周期，也就是产品平台团队里始终有个人，同时有一组核心的人负责维护主要系统和——他们搭建的平台，但始终有一个从产品团队轮岗到产品平台团队的人，带来这样的声音：'哦好吧，我不知道你们在这里都在干什么，但在产品这边，我们就是 YOLO 式地一直狂发这些 AI 垃圾。比如，什么——你还在读你的代码？什么？'呃，这是真的。这是真的。我们在产品这边，代码评审都快消亡了，完全不一样，对吧？但如果你不贴近那种情况，你也就不知道怎么把你的平台强化到它能达到的最好状态，好让他们能那样做。我看到我的角色——在当下这个，你知道，世界阶段，作为一个产品平台人，就是：护栏需要比以往任何时候都更好，因为产品这边的人需要——我是说，'需要'这个词有点重，但——理想情况下，他们应该能随口输出任何他们想输出的鬼东西，而平台应该拦住他们、警告他们，或者——对。所以，我理解你的建议是：看，如果你今天在一个产品团队，你在做产品，你在向客户、向用户交付——显然要理解业务在意什么，去构建——你知道，努力构建高质量的东西——但也要问自己，比如，你是否在意性能和可靠性？如果不在意，首先，为什么不在意？其次，当你开始在意这一点，并且如果你正在和一个平台团队合作，开始和他们合作，和他们待在一起，看看你能——你遇到的这些问题——我能不能帮忙构建一个解决方案？如果你有选择，转到这个团队；这挺有用的。而如果你就在这个团队，试着找到一种方式，稍微像——和这个团队一起实现一个功能，理解他们为什么发布得这么快、看起来这么不在乎。

因为这样，双向来看，都会让——看起来我们两边都需要，尤其是现在产品团队被推着要快得多地交付，而且顺便说一句，他们确实交付得更快了，还有了新工具——有些有用，有些没用——你知道，这就是我们将如何成为更好的工程师，以及我们将如何构建更好的系统，让我们能够去交付。

可靠且高质量的体验，这我完全支持。我讨厌看到软件质量下滑。哦不，不，我知道。我的意思是，我们可以阻止它，或者我们实际上可以构建更好的软件，希望如此。是啊，是啊，我想是这样。我觉得这非常类似于……
