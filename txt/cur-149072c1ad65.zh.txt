Jerod：很高兴请到你。你是 WebGLfundamentals.org 的作者，我相信你还做很多别的事。这期节目是听众 Daniel Buckmaster 点播的，他想聊 WebGL。我就想："我对 WebGL 了解不多，给 Gregg 发封邮件，看能不能聊聊 WebGL。"他回信说："我很乐意上节目。不过你们确定要聊 WebGL 吗？"因为 WebGPU 才是新热点，它会取代 WebGL 2，或者说已经在取代了，我也不太清楚……Gregg，把你跟我说的再讲一遍吧，为什么今天我们要聊 WebGPU。

Gregg：好。WebGPU 今年 5 月在 Chrome 里上线了，其他浏览器准备好之后也会跟进……而 WebGL 上线是——我想是 11 年前、12 年前了，所以……

Jerod：又老又过时，你是这个意思吗？又老又过时？

Gregg：不是又老又过时，但它肯定已经"完成"了。可能还会有些小改动，但差不多是该往前走的时候了。我想 WebGPU 就是大家希望它前进的方向。

Jerod：听起来也确实在往那个方向走。你说 Chrome 已经上线了，在 Firefox 和 Safari 上我记得是藏在开关（flag）后面。Edge 当然是基于 Chromium 的，在 caniuse.com 上是绿色支持……所以它正在成为现实，不会是昙花一现。

Gregg：应该不会是昙花一现，不会。很多人、很多不同的公司都在用。我记得 Unity 宣布了支持 WebGPU。我不知道除了 beta 之外他们是否真的发布了什么，但我很确定他们宣布过。如果没有，那我就麻烦了。[笑]

Jerod：突发新闻。

Gregg：不，我很确定他们宣布过。我也知道其他人在做别的东西。

Jerod：好，那给我们讲讲你自己吧。显然，你做了这个网站，一份关于 WebGL 的全面指南……你的背景是什么？你对什么感兴趣？你是怎么做出这个网站、又是怎么对这些技术产生兴趣的？

Gregg：我其实是个游戏开发者，至少我以前这么称呼自己……我还是想把自己当成游戏开发者，但我写的最后一个游戏是 2007 年的，这大概说明我该重新考虑一下这个头衔了。我是 2008 年来到 Google 的，来写一个游戏引擎，叫 O3D，你们可以查一下。它看起来可能不太像游戏引擎，但它发布了，然后又突然被砍掉了。Google 从来没有砍过已经发布的项目……

Jerod：没有，这是头一回。头一回。你是第一个。

Gregg：那完全是正确的决定……后来我转去做 WebGL，它是正确的替代品；它更灵活，因为人们可以写自己的引擎，而不用迁就我们的引擎。那是更好的决定。不知道为什么，我开始在 Stack Overflow 上回答问题。这类 GPU API 的问题之一是它们需要大量的准备工作……所以你没法像回答大多数 Web API 问题那样快速地回答。如果你想用 canvas 的 API 画一个圆：你有一个 canvas，创建一个 context，调用 arc，再调用 fill，就得到一个圆，大概四行代码。而这个不行，要 70、80、100 行才能做到……

Jerod：画一个圆？

Gregg：对，我不知道最少能压到多少行，但肯定没那么少。它非常底层。和一个库相比，它就像汇编语言。所以人们会在 WebGL 和 WebGPU 这样的技术之上写库。聪明的话你就用其中一个库；如果你喜欢自讨苦吃，那就自己另起炉灶，全部自己做。

Jerod：明白了。

Amal：对，这很酷。我确认一下……WebGL 这个规范／Web 标准，是 Google 基于你当时做的工作推动的吗？是这样吗？

Gregg：不是，我会说——我可能会记混。是 Mozilla 的某个人，或者 Opera 的某个人，或者两边一起，在某个时候推动了 WebGL。是某个人——不是我——决定"对，这是正确的方向，我们就往那边走"。

Amal：明白，明白。WebGL 出现多久了？

Gregg：我想它是 2011 年上线的……

Amal：好的。

Gregg：我们在那之前就开始做了，但我很确定它是 2011 年 9 月上线的……我得再查一下。

Amal：哇。

Gregg：太久了，我连昨天的事都记不住。

Amal：是啊，这很酷。所以现在它迎来了下一次演进，就像你说的，有望被 WebGPU 取代。

Gregg：我想可以这么看。目前还有一些取舍，但我们在努力消除它们。总之，我想把刚才那个故事讲完……事情是这样的：我在 Stack Overflow 上回答问题，而要有效使用它所需的知识量太大了，在 Stack Overflow 那种短小的形式里根本没法真正回答很多问题。于是我想："好吧，那我去写些文章。"一开始文章放在我的博客上；写了大约五篇之后，我想："好吧，我大概应该挪到别的地方去，这样也许其他人可以参与贡献、修 bug 之类的……"于是就变成了 WebGPU，哦不，WebGL Fundamentals。

Amal：这太酷了。我对这一点特别好奇，因为 WebGL 一直有一个巨大的入门门槛——我甚至不知道怎么说，感觉你得有一颗"计算机大脑"才能有效地用它……我总觉得自己很笨，心想："为什么我没法在脑子里想象出一个矩阵？"诸如此类。所以我很好奇，你能聊聊这种摩擦吗？因为在设计规范的时候，作为规范作者，你显然会有一定的偏见，因为你是这个东西的专家……那你怎么从人们那里得到反馈，知道"这个东西好不好用"？因为在我庞大的人脉网络里，真正在积极使用它的人，我一只手就数得过来，而且一只手里只伸出一根手指……

Gregg：嗯，这个问题有好几个答案。一是 WebGL 基于 OpenGL，也就是说它不是——它是一个现成的标准，WebGL 的目标只是"我们怎样把它带到 Web 上？"所以他们其实没有重新设计它的机会。他们的想法是："我们沿用一个现成的标准，这样所有使用这个标准的东西都会很容易用起来。"而如果他们写一个全新的东西，那些东西就都得从零开始。我想当时的考虑就是这样。

在 Web 之外，有 OpenGL，从 90 年代初就开始用了。很多原生应用都用 OpenGL。据我所知它在手机上依然流行……我想在桌面上也仍然有一些应用在用。所以 WebGL 某种程度上是被束住了手脚。如果他们的思路是"我们要把 OpenGL 带到 Web 上"，那就没法真正重新设计 API。他们能做的只是让它在 Web 上是安全的，并在需要的地方尽量让它更"Web 化"。

Amal：嗯，这说得通。谢谢你分享这个背景，这解释了很多。所以这是最糟糕意义上的"抽象泄漏"——就像是"这是用 JavaScript 来使用这个非常复杂的东西的方式，而它本来就很复杂"。

Gregg：看待这两个 API 的另一种方式是，它们有点像 WebAssembly。他们推出了叫 WebAssembly（WASM）的东西，但你一般不会直接写 WASM；你会用别的工具，比如 Emscripten——Emscripten 让你写 C++，再把它转换成 WASM。这样 C++ 程序员想写 Web 代码也可以。你看那些模拟器——如果你去过 Internet Archive，查过 Commodore 64 游戏或 Apple II 游戏，它们全都是通过 WASM 运行的：有人为原生平台写了模拟器，他们只是重新编译了一下。所以对，大多数人不直接写 WASM。同样，大多数人大概也不会直接写 WebGL 或 WebGPU。他们用库。最流行的大概是 Three.js，另一个流行的是 Babylon.js。

如果你在用 MapsGL，或者嵌入式的 Google 地图，它们都会替你用上这些技术。你什么都不用做，你只是在更高的层次上做事。所以这是把这些东西用起来最常见的方式。你不必亲自去做。

Jerod：怎么判断你是不是够底层？就是当你有一个叫 Three.js 的更高层抽象，而人们还会在它之上再写更高层的东西的时候。Three.js 我用过，学习曲线不算太陡……但还是有的。它有些啰嗦，有些东西需要理解……而它还是建立在这个之上的。所以你们是在最底下……为什么要这么底层？为什么是这些技术？你提到了游戏，然后是 Google 地图……除了这两个例子之外，或者说在此之上，还有哪些用例？为什么这么底层？难道不能为了库作者往上提一层吗？

Gregg：它之所以底层，是因为底层能给你带来所有这些速度。你可以针对你想做的事情优化你的方案。至于例子，如今的热门是机器学习，它就用这些 API。另外，你屏幕上的一切——你的浏览器、里面所有的文字、我们正在看的这些摄像头画面——都是通过 GPU 完成的。浏览器替你处理了，也有高层 API 可以做，但如果你想自己做，Google 地图就是一个例子；它目前全部是 WebGL。我相信 WebGPU 版本正在开发中……我没见过，但不用说，这是必然要发生的。所以基本上，如今要把任何东西显示到屏幕上，基础技术就是这些底层 API。

一个好例子——我不知道算不算好例子。我想想。Chrome 刚发布的时候，它用 CPU 渲染，有一个很快的渲染器，还有一些令人印象深刻的演示。我不记得了——他们展示过一些弹跳小球的物理演示，在当时挺厉害、挺快的。后来所有的操作系统和浏览器都加入了 GPU 渲染。GPU 本身会替你画三角形，在此基础上，你就得到了你看到的一切：贴了纹理的三角形，也就是里面有图像的三角形。如今大部分东西都是这样工作的。但最近，借助一种叫计算着色器（compute shader）的东西——它让你可以在 GPU 上做通用计算——有一些更新的算法走得更远。有一个叫 Vello 的库，你们可以查一下——我想是叫 Vello——它做结构化图形，就是 SVG 那类东西，你可以用它来渲染 UI 之类的。它用的完全是软件渲染；所谓软件，是说……我不知道该怎么讲；它们不让 GPU 用它那些老的光栅化功能，而是自己去计算像素。这算是一种演进。

另一个例子是——我想 Unreal 有一个叫 Nanite 的渲染器，他们也在用新技术，自己去渲染东西，而这些方式在仅仅 5 到 10 年前还很少见。所以如果我们给你一个更高层的 API，这些东西就不可能实现。

Amal：这说得通。

Gregg：如果我们只给你 SVG，你就做不了更底层的事情。

Amal：这真的很酷。我想退后几步，也许可以用大家都很熟悉的 Google 地图来走一遍：好，假设我是 Google 地图的工程师，我的队列里来了一个工单，说"好，这是一个技术预研（spike），去探索并估算一下，把我们目前基于 WebGL 的实现转换到 WebGPU 需要什么。去调查：工作量多大？收益是什么？迁移路径是什么？什么会坏？哪些浏览器上能用？我们怎样优雅地处理，以便渐进式地升级？"带我走一遍这个预研吧。因为这是一个非常真实的用例，很多工程师都要面对，即使在 React 这样的工具里也一样。我记得当年——我想我给团队做过 React 16 的升级，然后……你知道的，我们就得弄清楚这会对我们产生什么影响……所以你能带我们走一遍吗？

Gregg：那会很难……[笑]

Amal：对，大概会是个列要点的回答吧？我懂。

Jerod：这就是他的预研结论。他预研完了：会很难。

Amal：[笑] 太爱你了，Jerod。

Gregg：嗯，我不知道哪个更容易理解。对我来说更有意思的是，他们从旧版 Google 地图——提供的是切片图像——转到使用 WebGL 的新版 Google 地图。我不记得中间有没有过渡版本。但那是一个巨大的变化，因为它从这些预渲染的切片，变成了一个系统——他们发布时指出，他们可以改变哪些道路被标注、哪些道路被高亮，或者展示不同的东西，全都是因为切换到了动态渲染。我想当时用 2D canvas API 做不到，因为太慢了。但现在你打开 Google 地图，放大缩小、到处移动，运气好的话，一切都始终丝般顺滑。

Amal：说实话，确实令人印象深刻。这是我几乎每天都用的 Google 产品之一。我现在把手机换成了——我用的是苹果设备。我用了很多年安卓，我算是元老级安卓用户了。我从 Motorola Droid 一路用到 Pixel 3，然后就想"我受够了"，原因很多，也许可以另外做一期节目聊。但现在我是苹果用户——显然，谁想用苹果地图啊，对吧？因为我总能在任何设备上可靠地用网页版地图，而且它好用。真的非常非常好。

Jerod：听起来它是被砍掉的头号候选啊，Gregg。你不觉得他们要收手了吗——是不是该把那个项目关掉了？[笑]

Amal：不，我只是觉得大家应该知道地图用了 WebGL 这样的工具。而且更重要的是——我希望它不是闭源的，因为我很想看看它背后的工程实现。

Gregg：嗯，那个大概会一直闭源……

Amal：在我看来，它内部可能相当复杂。

Gregg：大概确实相当复杂……而且你知道，那里面大概有 PB 级的数据。他们最近做了一件事，你可以把数据拉出来，在 3D 库里使用。有在 Three.js、Babylon、Unity 和其他东西里使用它的示例。所以现在看看那些源码可能更有意义。我不知道，我没看过。

至于从 WebGL 到 WebGPU，如今——我想这是我的个人观点——主要有三四个图形 API：OpenGL、Vulkan、苹果设备上的 Metal，还有 Windows 设备上的 DirectX 12（11、12）……它们都不一样，但在某个层面上它们又都一样。所以从 WebGL 移植到 WebGPU，取决于你怎么看，不过是"好，这边我调用 fillRect()，那边我调用 rectFill()"的事。[笑] 没那么简单……但在某个层面上，确实如此。

Amal：那优势是什么？我想弄明白的是，作为工程师，我关心两件事：一是这东西的性能如何，它在硬件上跑得怎样，在浏览器里表现如何；二是 API 的易用性。那用它能得到什么改进？用 WebGPU 时，我作为开发者的生产力会提升吗？还是 API 依然一样复杂？

Gregg：它们都很复杂，并没有变得更简单。

Amal：好吧。

Gregg：区别在于加入了新特性，这些是旧 API 里没有的。这些新特性可以带来以前做不到的巨大新功能。

Amal：好的。

Jerod：那今天还有理由写 WebGL 吗？

Gregg：所以……有。很遗憾。这些新特性需要新硬件。所以如果你面向的市场群体用的是很老的硬件，你可能会发现 WebGL 能覆盖的用户比 WebGL 2 或 WebGPU 更多。

Jerod：明白了。

Gregg：用这些老设备的用户一直在减少。你也可以决定做回退。Google 地图没有 WebGL 也能运行，只是进入一种会丢掉部分功能的模式：你不能进入 3D，道路之类的东西可能没那么动态，帧率达不到每秒 60 帧，也没那么流畅，但它仍然能运行。有点像你仍然可以——嗯，我想他们正在弃用它，但你仍然可以使用纯 HTML 版的 Gmail……

Jerod：嗯……暂时还可以。

Gregg：……相对于完整的应用版本。暂时还可以，是的。

Jerod：不过我好奇有没有一个 old.gmail.com，让你可以永远使用 HTML 版本。

Gregg：就像 old Reddit？

Jerod：对，像 Reddit。

Amal：所以我想——问题在这儿……我觉得这看起来是渐进式体验的完美用例："这是旧 API，这是新 API。"我们的代码库会让两者并存，直到硬件更普遍地跟上之类的……但我觉得 WebGPU 肯定有一个营销问题……因为如果它不能在所有和 WebGL 相同的设备上运行，我有什么动力为它投入工程时间呢？因为我得维护两套代码库，或者两套实现。

Gregg：嗯，我想你得看你自己的市场，判断那些用老机器的人所占的比例，或者你想要的人群——比如说你在做一个游戏；不管你怎么做，这个游戏在他们的机器上都跑不够快。那就没有理由去兼顾那些老设备，举个例子。所以这真的取决于你在做什么。我不知道这里我还有没有别的要说，但……

Amal：嗯，这说得通。

Jerod：取决于你在做什么，以及你从哪里起步。比如，你是从零开始吗？你的目标是什么？因为我其实会从另一个角度出发。我会问"为什么不用 WebGPU？"这是我首先会问自己的。如果答案是"嗯，因为我需要持续支持这些设备"，那这就是你的答案。但否则，我是往前看的，我看到对 WebGPU 的支持正在到来，我会想"为什么还用 WebGL？"

Gregg：另一个例子是，也许你想做的事情根本没有别的办法做到。WebGPU 让网页可以访问一种叫计算着色器的东西，其他 API 里没有……而机器学习基本上就是基于计算着色器的。所以如果你想在浏览器里跑大语言模型，虽然也有办法硬塞进老 API 里……但基本上，你大概就应该用 WebGPU。

Amal：嗯，这说得通。我很好奇，既然由于 Web 的发展轨迹，这两者多多少少会无限期并存……会不会有一些特性——我想问的是，WebGL 会被弃用吗？因为——

Gregg：我不知道现在是否会用这个词……我只是觉得不会再有太多投入。浏览器团队里所有会做这两套 API 的人——嗯，两边都是同一批人在做，他们的时间有限，而且他们都想往前走。如果他们得把时间分给两边，那会是巨大的消耗，所以……

Amal：所以新特性大概会只加到——很可能只加到 WebGPU 里。

Gregg：这是我的猜测。

Amal：好，这说得通。

Jerod：那如果我们这些普通人大多是通过库来用它的，这些库也在移植吗？比如我用的是 Three.js，从没写过一行 WebGL，我能不能直接说"嘿，Three.js，切换到 WebGPU 模式"，然后就能用上了？

Gregg：差不多。是的。

Jerod：太棒了！

Gregg：挺酷的。

Jerod：没有更多问题了。[笑]

Amal：对，我们讲完了。播客结束。

Amal：让它们替我们自己策展自己……[笑] 真的吗，Jerod？

Jerod：我是说，我们干嘛这么拼？

Amal：我同意，你知道吗？我是说，以后会变成"好吧，伙计，我觉得好懒。我该洗澡了，但我不想洗头。"然后就会——我的第一反应会是"哦，能不能找个机器人来做？"这会变成我们对一切的默认反应吗？

Jerod：差不多吧……

Amal：这事能用 AI 做吗？

Jerod：我们最后会变成《机器人总动员》（WALL-E）里的那些人。你知道的，打开飞船，他们就那样——什么都不做，就在悬浮座椅上飘来飘去，越来越胖。

Amal：哦，天哪……

Gregg：说实话，我对这些东西真的很兴奋……你提到生成游戏，有时候我想做一个游戏。艺术家们可能会害怕这个，但在我需要素材的时候——我需要一个能四处走动的角色，需要一片森林、一堆东西、一座城堡——到某个时候我就可以直接说"嘿，做这个……"我不知道这是好是坏，我不想下判断。

而且我认为，在短时间内，你大概得不到你想要的风格、一种统一连贯的风格——就像你雇的真正的艺术家，或者如果你自己是艺术家，有自己的构想那样；这大概不会很快来自 AI……但我也不知道。

Amal：嗯。我同意，我对 AI 的辅助作用非常兴奋。那太重要了。我是说，我很想有一个工程师团队随时跟我一起工作，免费的——除了地球付出的代价。那太好了。而且是比我更聪明的工程师，懂更多编程语言，修的 bug 比制造的多……对，这一切听起来都很棒。

Jerod：嗯，这就引出了我给你的最后一个问题，Gregg。一个严肃的问题。你为什么从 2007 年以后就再没做过游戏？

Amal：哇……

Gregg：嗯，这是个好问题，我每天都在问自己。

Amal：[笑]

Gregg：我也跟朋友们说"嘿，我们应该做个游戏"，然后，对，我们就没做。原因之一是"金手铐"。你来到一家大科技公司，会想"哦，什么？我不用加班赶工（crunch），而且拿的钱多得多？"另一个原因是行业变了。我最后一次发布游戏是 2007 年前后……iPhone 是 2007 年出来的；手游兴起了，免费游戏兴起了。我来 Google 的时候，说过我是来写游戏引擎的；那是因为当时用 Unreal 实际上要花大约一百万美元。

我记得——Unity 当时可能是免费的，但它还没有"哦，这是你应该用的东西"那样的名声。所以我来 Google 做一个开源引擎。这一切都变了。现在有两个——它们不是免费的，但至少做原型是可以免费用的……甚至发布也可以。只有当你赚了很多钱，它们才想分一点钱。

还有 Godot 之类的，现在有一大堆其他引擎，是当年没有的。所以这从多个方面改变了局面。它让事情变得更容易了……所以理论上，如果 2008 年就有这些东西，我大概根本不会来 Google，而是会去尝试做点什么……另一方面，现在——我不记得具体数字了——每天都有好几千款新游戏。所以要脱颖而出难多了，面对这些，很难说"我有一个会卖得好的点子"。哦等等，我要投入三年，结果只卖出五份？我有朋友就是这样：他们把游戏做得很漂亮，发布了……我想他们卖了 80 份。

Amal：唉……

Gregg：而那是他们人生中的两年。游戏一直都是这样。你会想"我要成为摇滚明星。"

Jerod：那是登月级的冒险。

Gregg：对。要找到一种方式，让我有信心做出的东西会有市场……而且我想做独特的东西，而有一个独特的点子本身也……我不是在抱怨别人的游戏，但有太多游戏就是"这不就是[听不清]嘛。"对，我玩过《银河战士》（Metroid），不需要再玩一遍了。我想要新的东西。

Amal：对对对对。

Jerod：嗯，我对现代音乐、现代电影也是这种感觉……有很多——它们是翻版，但不是有灵感的翻版，只是有点像肤浅的克隆。

Gregg：对。我不是说我从中得不到乐趣，但是……我想做一些至少在我脑子里能脱颖而出的东西。我知道很多设计师大概觉得自己的游戏完全不同，但我分辨不出来……至少乍一看分辨不出来。也许深入玩进去我就能看出来了。

Amal：你看过 Apple 上那个剧吗，叫 Quest 什么的？

Gregg：我没看过。我想叫《神话任务》（Mythic Quest），差不多是这个名字？

Amal：《神话任务》，对。

Jerod：我也没看过。怎么了？好看吗？

Amal：嗯，我看了几集……看起来挺有意思的。比如 HBO 那部讲科技行业和创业公司的剧《硅谷》——我没法……它对我刺激太大了。我看的时候没法不想"天哪，这就像我认识的 50 个人……"我真的很难看下去。我第二季之后就没再看了，因为我觉得"天哪，太过了。"我对这部剧也是同样的感觉。它太像工作了，我就会"我不行……"我看电视是为了——

Jerod：因为他们在一家游戏开发公司工作；那部剧就是讲这个的。是一群做电子游戏的人。

Amal：对，对，对。就是跟我的工作方式太像了，所以……不过对，我只是好奇你是不是粉丝。

Gregg：我没看过。有一本书我刚读完，是一位也是游戏开发者的好友推荐的，叫《明天，明天，还有明天》（Tomorrow, and Tomorrow, and Tomorrow）。我有点震惊，它在亚马逊上有——我不记得是 7 万还是 12 万条评论。我想"哇，我从没听说过这本书，原来它这么火。"它讲的是两个孩子在初中相识，大学时一起创办了一家游戏公司。我读的时候真的是"这就是我的梦想！为什么我没能过上这样的人生？"[笑]

Amal：哎……你某种程度上已经过上了。

Gregg：嗯，我是过上了……

Amal：对。说实话，如果你问我……我是说，如果你是像你这样在底层为 Web 平台做贡献的人，在我看来，你留下的遗产比做游戏更酷。因为你让别人能够做游戏。所以你就像是基石，你懂我的意思吗？所以这样想吧。你现在是上游。

Gregg：好吧……

Jerod："好吧……"[笑] 我看他没被说服。他在那儿想"好，我就这么想吧"，但其实他并没有那样想。他在那儿想着他的游戏呢。

Gregg：这就像，你想当导演，结果你在造画布。[笑]

Jerod：他就像"我不想写剧本……没有剧本，导演和摄影师能干什么？"Gregg，你在写剧本，所以……

Amal：我想说的是，每个人都至少应该花 15 分钟看看这个网站。我觉得它很酷。WebGPUFundamentals.org。去看看吧，内容很扎实（solid）。没有双关的意思。[笑]
