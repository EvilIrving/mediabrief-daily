GitHub 的饱和故障：故事还在继续

说到公开的事故复盘，GitHub 一直是源源不断的宝藏。他们持续承受 AI 热潮带来的附带伤害：使用 AI 的开发者越多，他们系统上的负载就越大。而他们面向开发者的定位，也意味着他们会提供这些事故的一些技术细节。

今天我要写的是他们在 9 月 13 日发生的事故。这份报告的标题很含糊——“多项 GitHub 服务出现事故”（Incident with several GitHub Services），这是事故宣布时的标题。可惜他们事后不会给事故重新起标题。

这份报告很短，我就直接摘录讨论故障模式的那三段。

> 原因是一个内部数据清理任务，它在 UTC 时间 07:33 开始向一个共享数据库集群写入数据。该集群存储着几乎每个经过认证的请求都要读取的权限数据。为这个后台任务控制节奏的保护机制只监测一个健康信号——数据库副本的延迟有多大——而这个信号全程都保持在低位。它没有考虑主库本身正在积累的负载，所以任务一直在写，而主库则悄无声息地逼近了它的极限。
>
> 当主库的可用连接耗尽时，需要它的请求就无法完成。首先，这些数据库调用没有快速超时，所以请求处理程序一直在等待停滞的数据库，而不是快速失败，共享的请求处理能力因此退化成了全站错误。其次，令牌创建外围的一个重试循环不断重发那些已经在失败的写操作，使数据库保持饱和，而不是让它恢复。
>
> 监控在 UTC 时间 08:50 宣布了事故，但由于影响范围广，加上令牌创建造成的放大效应，找出负载来源花了一些时间。第一响应人通过卸掉内部负载和暂停该任务进行了缓解，所有服务在 UTC 时间 10:44 前恢复。

下面我尝试用一张示意图来描绘这段文字，并用我自己的话复述一遍。

GitHub 内部有一个数据库集群，采用典型的 SQL 数据库集群配置：一个主库加若干只读副本，主库负责处理所有写入。这个集群承载在线流量：也就是说，外部用户的活动会生成针对这个集群的查询。

GitHub 运行了一个离线任务（即不是由用户流量驱动的任务），它向数据库发起查询，以清理不再需要的数据。这个清理任务查询数据库的速率由一个保护机制控制，该机制监测数据库的健康状况：如果数据库看起来正在变得不健康，保护系统就会降低查询速率。保护机制用副本延迟来监测数据库健康（如果他们用的是 MySQL，大概跟踪的是 Seconds_Behind_Source）。副本延迟上升可能是副本负载过高的一个症状。

在这次事件中，副本本身是健康的，副本延迟一直低于保护机制监测的阈值。然而，面临饱和风险的是数据库集群的主节点。具体来说，主库达到了它的最大客户端连接数（在 MySQL 上，这由服务器系统变量 max_connections 控制）。这意味着任何试图通过新连接查询数据库的操作都会报错失败（在 MySQL 上是 ER_CON_COUNT_ERROR，错误信息为 Too many connections）。

当一些 Web 服务器试图调用这个数据库时，请求既没有立即成功，也没有立即失败，而是卡在那里等待。不幸的是，这些请求处理程序配置的超时时间很长。这意味着这些被阻塞的请求在受影响的 Web 服务器中不断堆积。每个进行中的请求都会消耗一定资源，堆积的阻塞请求多到让 Web 服务器本身也饱和了，于是造成了全站影响。

雪上加霜的是，有一个令牌创建流程不断尝试查询主库，失败，然后重试。这给主库施加了持续的负载，让系统更难恢复。

题外话：一些没有答案的技术问题

以下是我从原文中没能弄明白的几个问题。

连接耗尽是如何导致 Web 服务器超时的？是不是 Web 服务器用了连接池，池中并非所有连接都处于活跃状态，于是客户端一直卡着等待一个永远不会到来的新活跃连接？

那个后台任务是如何让主库超出最大连接数的？是这个任务消耗了多得出人意料的连接吗？任务开始之前，数据库离上限有多近？

——

你永远无法真正知道安全边界在哪里

当你让一个离线任务针对在线数据库运行时，总有风险会拖累数据库的性能，进而影响客户流量。离线任务的好处是，原则上它们完全可以由组织控制。而对于用户流量，你只能听凭用户摆布。

所以，GitHub 让一个自动化系统（保护机制）在清理任务运行期间监测数据库的健康，确保任务不会给数据库施加过多负载。如果负载变高，保护机制就会放慢清理任务查询数据库的速度。问题在于，保护机制所监测的指标并不能完整反映集群的健康状况。在保护机制看来，数据库仍然健康，尽管它的连接即将耗尽。这是“灰色故障”（gray failure）的一个绝佳例子：你内部的健康监测系统错误地认为系统是健康的。换句话说，指标很好看，但用户很不满。

用韧性工程的术语来说，系统误判了安全边界的位置。在越过边界之前，没有任何信号表明系统正在接近不安全状态。要注意，在真正越过安全边界之前，我们从来不知道它到底在哪里。而越过安全边界是非常、非常糟糕的事。所以我们总得估计安全边界在哪里，然后避免离它太近。但系统中的限制实在太多，可悲的是，我们没能监测到全部限制的可能性相当高。

离线任务与在线数据库：有时候你不得不跑

在理想世界里，我们希望在线数据库的所有查询流量都是，嗯，在线流量。这就是为什么，比如说，我们不在在线数据库上跑分析查询。然而，有些场景你别无选择：你必须针对在线数据库运行一个任务，因为你想对在线数据做某种改动。这次就是一个绝佳例子：这个任务必须在在线数据库上运行，因为它的目的就是修改那些数据。

清理是一把双刃剑

说到“清理”这个话题，无论是数据还是代码，一旦你见过足够多的事故，就会注意到一个规律：清理是一个常见的风险。有时事故发生是因为执行了清理任务，而被清理的东西其实还在使用中。有时事故发生则是因为某个早已不再使用的东西，以意想不到的方式与系统的另一部分发生了交互。换句话说：没有清理也是事故的成因之一。所以，不清理无用的东西是一种风险：它可能导致事故。但清理这个动作本身也是对系统的改动，同样带有风险。一切都是风险的权衡。

超时配置错误的不对称性

超时是构建可靠分布式系统的一个必不可少的工具。但“超时太短”和“超时太长”这两个问题之间存在不对称。如果超时太短，你在系统正常运行期间就会注意到，因为会看到大量超时发生。于是一旦出现这种情况，你就把超时调长。

然而，太长的超时更难发现。如果你运气好，可能会注意到用户界面有些迟钝，并诊断出问题与超时太长有关。但在很多情况下，在太长的超时酿成事故之前，你根本不会得到任何信号。正如我们在这里看到的，长超时会增加服务中进行中请求的数量，从而耗尽其资源，制造饱和风险。

你的系统里很可能就有配置得过长的超时，只是还没人注意到。

重试有帮助，直到它帮倒忙

重试是构建可靠分布式系统的另一个必不可少的工具。因为瞬时故障很常见，重试可以有效地对用户掩盖这些故障：他们永远不会知道你部署中有那么一个坏掉的 pod。但重试会增加负载，在饱和故障模式下，你可能遇到一种病态行为：重试让事故进一步恶化。这次就是这样，一个特定服务（令牌创建）一遍又一遍地重试，给数据库带来了无休止的负载。

你需要重试！但就像配置错误的超时一样，配置错误的重试在事故发生前可能很难被发现。正因如此，我们这个行业才为“重试让情况更糟”的故障模式起了一个专门的名字：重试风暴（retry storm）。

过载时，你需要减少负载

我们再看一遍引文的最后一段，它包含一些关于事故响应的细节（着重号是我加的）。

> 监控在 UTC 时间 08:50 宣布了事故，但由于影响范围广，加上令牌创建造成的放大效应，**找出负载来源花了一些时间**。第一响应人通过**卸掉内部负载**和暂停该任务进行了缓解，所有服务在 UTC 时间 10:44 前恢复。

做事故响应的人都知道，我们的第一要务永远是让系统恢复健康。如果你能迅速找出问题根源，那太好了！直接回滚那次有问题的部署就行。但我们往往看不出是什么导致了问题。在饱和故障模式下，我们通常能确定是哪个服务过载了（而且很多时候是数据库），但问题的根源究竟在哪里并不明显。在这类场景中，你希望响应人能够：

- 快速识别负载来源（是哪些查询，谁在发起它们？）
- 手动卸载负载（屏蔽特定的查询或来源）

要想在事故中随手就能用上这些运维工具，你必须提前把它们建好。到了事故当中就太晚了，你只能用手头已有的工具。

你的系统终究会过载，这一点我向你保证。你的在线数据库风险尤其大。现在就是做准备的时候。

解决方案一如既往：增加复杂度

以下是复盘报告的最后一段：

> 为防止再次发生，我们正在默认对针对共享、面向客户的数据库的后台任务进行限速，并增加基于主库负载（而不仅仅是复制延迟）的自动暂停和告警。我们还将把正在运行的后台工作直接展示在数据库健康信号旁边，让响应人无需离开这些仪表盘就能看到并暂停它们；为令牌签发路径的重试设定上限；并增加请求级超时，让一个不健康的数据库无法耗尽共享的 Web 服务器容量。此外，我们正在拆分这个数据库集群，以消除单点故障。在接下来两周内，我们会把包括授权数据在内的各种服务专属数据迁出这个共享集群。

提出的新干预措施包括：

- 增加限速
- 监测更多指标（主库负载）
- 增加请求级超时
- 对数据库集群进行分片

在我看来这些都是不错的干预措施。但请注意，它们全都增加了复杂度！它们都要往系统里加新东西，事故后的干预措施向来如此。我曾公开表示，为了提升可靠性而增加复杂度是不可避免的。但我们应该坦然看待这一点。通过增加复杂度，我们消除了已知的故障模式，代价是引入新的故障模式。而我们也确实会引入它们。
