Uber 的 AI 基础设施内幕 ｜ The Pragmatic Engineer ｜ 93分钟 ｜ https://newsletter.pragmaticengineer.com/p/ubers-ai-infra-from-the-inside

主持人 Gergely Orosz 曾在 Uber 工作到 2020 年。这期他请来 Uber 杰出工程师 Uday Kiran Medisetty，边聊边演示 Uber 内部近二十个开发工具。Uday 2015 年入职，大约是第 600 名工程师，前十年做业务平台，最近一年主导面向工程师和全公司的智能体 AI。全期反复回到一个观点：Uber 的 AI 工具看起来像是一年内建成的，其实是架在十年的开发者平台投资之上。

先讲 AI 之前。Uday 入职时 Uber 只有两个服务：Node.js 写的 Dispatch 负责乘客和司机流量，Python 写的 API 负责行程结束后的支付和收据。之后为他做过的实时 API（RT API，后来用 Go 重写，改名 Edge Gateway）开了头，进入超高速增长，服务数涨到数千个。2018 到 2019 年，公司统一用 Go 和 Java，开始平台化。如今业务大了十倍，服务数却和当年差不多，全球仍是一套技术栈。当年市面上没有能扛住这个规模的现成软件，只好自建：uOwn 查资产归属；M3DB 处理每秒约 5 亿条指标，后来开源，还催生了公司 Chronosphere；机器学习平台 Michelangelo；持久化工作流引擎 Cadence，Temporal 的思路正源于它；Morpheus 相当于 Uber 版 LaunchDarkly，做功能开关和实验，支持轮换实验（switchback），还把“城市”当一等公民。城市在 Uber 的基础设施里分量很重，关键服务按城市分片，单个城市可以跨区域故障转移。现在的原则是没有独特需求就买，自己做出通用价值的东西尽量开源。

对 AI 影响最大的旧投资是 DevPod。2017 到 2018 年，Uber 从每个服务一个仓库改成每种语言一个大仓库（monorepo），笔记本跑不动构建，于是做了自带构建缓存的云端开发机。到了 AI 时代，智能体同样需要这种工作空间。Uber 做了一个装下全部仓库的“超级 DevPod”，构建和测试本来就统一用 Bazel，所以顶层写一份 AGENTS.md 和 CLAUDE.md，大多数团队就能直接受益。Claude Code、Codex 和 OpenCode 都预装好，连非工程师也能直接上手。

AI 基础设施的总原则是不绑定任何模型和 harness（智能体外壳），因为两者都变得太快。最早的是 2023 年底的 Model Gateway，建在 Michelangelo 上，对外提供兼容 OpenAI 和 Anthropic 的接口。全公司每一次模型调用都走这里，团队拿项目 ID 就能调用任何开源或闭源模型。网关上的 AI Guard 由安全团队维护，用大约五个微调模型在严格延迟限制内检查每个请求和响应，防止敏感内容外泄。同一个入口还负责计费、缓存命中率、审计日志和按人按项目的消费档位。AIFX 把各家 harness 包了一层，设置、技能和插件在本地和各台 DevPod 之间同步，换 harness 不用重新配置。成本管理靠反馈而不是限制：每人有默认档位，快用完时经理点头就能升档，Cost Check 插件会根据你的用法给出省钱建议。

2025 年 4 月起做的 MCP Gateway 复用了已有的 Thrift/Protobuf 接口注册中心，能给任何服务自动生成 MCP 工具，并把动辄三四千 token 的描述改写得更适合模型读。团队改一处配置就能开放自己的服务，Slack、Google、Jira 等外部工具也都接进来了。最近又把所有 MCP 投射成 CLI。这件事由做 API 网关的原班团队来做，所以上手很快。技能也放进一个统一的 monorepo，带质量关卡，自动装给所有人，每天大约执行 3 万次。CLI 出来后，几个工程师借助 AI 就把全部技能改成了 CLI 调用，省掉常驻上下文的多个 MCP，token 效率明显提高。下一步是从使用轨迹里自动生成技能的改进补丁。Uday 最喜欢的是上下文图谱：有 100 多种节点、130 多种边，把人、PR、服务、设计文档、事故、值班、配置变更和 Jira 连成一张网。内部助手 Cortana 先在图谱上找到问题属于哪个领域，再深入查资料，答题质量更高，成本和延迟都下降了。比如问“全球多少单是现金支付”，它能顺着图谱找到相关的表、列和别人写过的官方认可查询。Cortana 在 Slack、网页和 CLI 里都能用，海外运营人员也能自助提问，权限沿用原有的用户权限。

然后是一个功能从头到尾的流程。设计文档、上线评审、生产就绪评审集中在一处，并接入图谱。Uday 强调规划仍然关键，因为 Uber 跨很多国家和城市，又在物理世界里运营，边界情况特别多。后台编程智能体 Minion 现在贡献了约 15% 的生产 PR。它跑在超级 DevPod 上，能跨仓库提交 PR，在 Slack 里 @minion 就能接手讨论串里的方案。值班时有人报 bug，常常当场定位当场修，不必排进下个迭代。PR 越来越多，评审成了瓶颈，CI 任务每年翻倍，公司甚至为 CI 宣布过“红色警报”。应对办法包括：`aifx validate` 把 lint、覆盖率、构建这些检查前移到本地；智能体可以起模拟器、网页或预发环境自己验证；自愈 CI 能自动修复、自动请求评审、自动合并；Code Inbox 把 AI 评审结果、测试截图和视频、风险评分和影响范围集中给评审人看。Uday 说事故代价太高，所以目前每个 PR 仍要人工评审。等风险评分能用多年数据回测、足够可信后，才考虑给低风险 PR 开“绿色通道”自动合入。

验证环节靠两个老系统。Slate 能把你的分支部署成独立实例，把测试账号的请求路由过去，其余服务照常走预发环境。它依赖多年前在所有服务里铺好的 Jaeger 链路追踪：路由信息作为随行数据（baggage）沿调用链传下去，服务网格据此转发。现在智能体也会部署 Slate，用浏览器对比 main 分支和自己的分支，生成前后对比报告。Capri 是捕获回放系统，用一个中间件录下真实生产请求和所有下游调用，按规则标出业务维度，生成 MatchGuard 全组合测试，在部署前检查“是不是只把巴西的现金单弄坏了”这类回归。它取代了 Gergely 当年用的 Deputy 和 Cerberus，智能体也能拿它循环修 bug，直到差异消失。其余几个系统：Shepherd 用 OpenRewrite 规则或 AI 技能，对全部模块做大规模迁移，比如从 JUnit 4 迁到 JUnit 5；Fox 让服务自愿登记死代码清理、性能分析、日志降噪等技能，每周日 CI 空闲时自动提 PR，目标是代码库自我改进；Wisdom 收集员工内测时上报的 bug，带上页面路径、日志和网络请求，智能体 Debug Assist 据此找根因，再交给 Minion 修，测试机还能回放当时的网络响应来复现。

最后谈工程师的工作怎么变。Uday 认为现在模型的能力有富余，缺的是编排能力和工具，所以工作就是不断找下一个瓶颈并消除它。衡量生产力时，他们不再只看 diff 数量，而是看功能交付速度：用 AI 给 PR 分类，看到功能类 PR 的占比在上升、维护类在下降；再把需求文档、设计文档和任务串起来，算出不同复杂度功能的 P50 交付时间，找出卡在哪个阶段。他自己提的 PR 比去年多得多，觉得工程师的核心能力变成了三件事：给智能体准备上下文和规格，同时推进多个会话，快速验证产出、及时发现代码坏味道。客服团队是个例子：把操作手册转成 AI 客服政策，原本要几周，教会智能体生成初版政策、自动配置、生成合成评测之后，只要几天。工程师从亲手做事，变成设计能自己完成并自己验证的系统。

Gergely 在结尾总结了三点。第一，Uber 现在约有 4500 到 5000 个服务，比十年前少，而且规模更合适。第二，代码评审在各处慢慢消亡，Uber 仍坚持人工把关，但在用大量 AI 信号帮人决定哪些 PR 值得细看。第三，从 AI 获益最多的公司，往往是早在 AI 之前就有开发者平台团队的公司。
