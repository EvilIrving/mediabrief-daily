棕地项目中的 agent 工程（Brownfield Agentic Engineering） ｜ Addy Osmani ｜ 文章 ｜ https://addyosmani.com/blog/brownfield-agentic-engineering/

Addy Osmani 认为，在老代码库里，仓库已经不能完整描述系统的真实行为，很多约束藏在团队经验、临时补丁、遗留服务和其他团队的依赖里。放任 agent 去改，可能得到“能跑”但设计错误、测试脆弱的结果。所以要做的是让隐藏的约束显性化，让廉价的改动可信。

他的做法如下。
分区：绿区测试好、隔离好，agent 可以紧凑循环地干；黄区先写特征测试再改；红区是认证、计费、权限、薪资，要么每一步都有人结对，要么干脆不做。地图由人来画，不然 agent 会直奔最吓人的文件。升级分区要靠挣，比如补齐了测试，负责人也审过 agent 最初的改动。
自主程度取决于爆炸半径、可观测性和可恢复性，而不是模型有多自信。只写下代码说不出来的东西：业务细节、架构取舍的理由、领域规则、反直觉实现背后的历史。
黄区和红区的工作先做一遍只读调研，产出一份带引用的理解备忘录，免得下一个 agent 再“考古”一遍。然后用干净的上下文做规划，由人选定方案，评审从验收标准倒推。
同一条评审意见出现第二次，就把它固化成 lint、钩子、类型、测试或 skill。

落地从零风险的工作开始：先让 agent 解释系统，再用特征测试锁定现有行为，包括那些丑陋但业务依赖的行为，而且测试不能由同一个会话独自写。Netflix 迁移 GraphQL 时用影子流量对比新旧路径的输出，也是同一思路。他讲了在 AOL 休假时被叫回去抢修首页的往事：几十个部门各管一块，只能靠人工验证。agent 没有消除这个问题，只是让尝试变便宜了。迁移要按完整单元做，旧依赖删干净才算完成，否则 agent 会看到相互矛盾的先例。SWE Refactor Bench 的 520 次运行中只有 28 次通过审计。他列举的案例包括：Bun 移植前先写了一份 Zig 到 Rust 的映射指南，每个单元配两名对抗式评审；VB6 转 C#，简单功能的行为等价率 92%，复杂功能只有 47%；Stripe 没用 agent，靠 codemod 把 370 万行代码迁到 TypeScript；Spotify 每月合并 650 多个 agent 提交的 PR；Asana 花约 1.2 万美元清掉了 Enzyme 积压，但这只是 token 账单，不算节省研究。能在公司之间借鉴的，是围绕 agent 的那套结构。

agent 让同时尝试多种实现变得便宜，Shopify 用 12 周把 Shop 应用重写为原生，但选择哪种实现需要的证据并没有变少。并行要放在最后，因为它会放大已有的瓶颈。自动评审应先呈现意图、改变了的不变量、测试结果和回滚路线，人的注意力先投向爆炸半径最大的地方。worktree 只隔离代码，不隔离凭据和网络。衡量效果别看生成了多少行，要看交付周期、人工干预、逃逸缺陷、回滚次数，以及迁移中新路径承载的流量。agent 给模糊性标上了看得见的价格，这正是为维护工作争取资源的论据。
