# 构建生成式 AI 平台

在研究了各家公司如何部署生成式 AI 应用之后，我注意到它们的平台有许多相似之处。本文概述生成式 AI 平台的常见组件：它们做什么、如何实现。我尽量让这个架构保持通用，但某些应用可能会有所不同。整体架构大致如下。

这是一个相当复杂的系统。本文将从最简单的架构出发，逐步添加更多组件。最简单的形式下，你的应用接收一个查询并把它发给模型；模型生成回应，再返回给用户。没有护栏，没有增强的上下文，也没有任何优化。图中的 **Model API（模型 API）** 方框既指第三方 API（例如 OpenAI、Google、Anthropic），也指自托管的 API。

在此基础上，你可以按需添加更多组件。本文讨论的顺序是常见的顺序，但你不必完全照搬。如果系统在没有某个组件时也运行良好，就可以跳过它。评估在开发过程的每一步都是必要的。

1. 让模型能够访问外部数据源和用于收集信息的工具，从而增强输入模型的上下文。
2. 加上护栏，保护你的系统和你的用户。
3. 添加模型路由器和网关，以支持复杂的流水线并增加安全性。
4. 用缓存优化延迟和成本。
5. 添加复杂逻辑和写操作，以最大化系统的能力。

可观测性（让你能看清系统内部，以便监控和调试）和编排（把所有组件串联起来）是平台中两个必不可少的组件。我们会在本文末尾讨论它们。

**» 本文不讨论什么 «**

*本文关注的是部署 AI 应用的整体架构，讨论需要哪些组件，以及构建这些组件时的考量。本文不讲如何构建 AI 应用，因此不讨论模型评估、应用评估、提示词工程、微调、数据标注规范或 RAG 的分块策略。所有这些主题都会在我即将出版的书《AI Engineering》中讲到。*

## 第 1 步：增强上下文

平台最初的扩展通常是加入一些机制，让系统能用必要的信息来增强每个查询。收集相关信息的过程称为上下文构建（context construction）。

许多查询需要上下文才能回答。上下文中的相关信息越多，模型就越不必依赖其内部知识——而由于训练数据和训练方法的原因，内部知识可能并不可靠。研究表明，在上下文中提供相关信息可以帮助模型生成更详尽的回应，同时减少幻觉（Lewis 等，2020）。

例如，对于查询"Acme 的 fancy-printer-A300 能达到每秒 100 页吗？"，如果给模型提供 fancy-printer-A300 的规格参数，它就能回答得更好。（感谢 Chetan Tekur 提供这个例子。）

基础模型的上下文构建，相当于经典机器学习模型的特征工程。两者目的相同：为模型提供处理输入所需的信息。

上下文学习（in-context learning），即从上下文中学习，是一种持续学习的形式。它让模型能不断吸收新信息来做决策，避免过时。例如，用上周数据训练的模型无法回答关于本周的问题，除非新信息被放进它的上下文。通过用最新信息（例如 fancy-printer-A300 的最新规格）更新模型的上下文，模型就能保持最新，并能回答超出其知识截止日期的查询。

### RAG

最广为人知的上下文构建模式是 RAG，即检索增强生成（Retrieval-Augmented Generation）。RAG 由两个组件构成：生成器（例如语言模型）和检索器——后者从外部来源检索相关信息。

检索并非 RAG 独有。它是搜索引擎、推荐系统、日志分析等的基础。许多为传统检索系统开发的检索算法都可以用于 RAG。

外部记忆源通常包含非结构化数据，例如备忘录、合同、新闻更新等，可以统称为*文档*。一份文档可能只有 10 个 token，也可能有 100 万个 token。简单粗暴地检索整份文档，会让上下文变得任意长。RAG 通常需要把文档切分成*可管理的块*，块的大小可以根据模型的最大上下文长度和应用的延迟要求来确定。想深入了解分块和最佳块大小，可以参考 Pinecone、Langchain、Llamaindex 以及 Greg Kamradt 的教程。

外部记忆源的数据加载并分块之后，检索主要有两种做法。

1. **基于词项的检索**
它可以简单到只是关键词搜索。例如，给定查询"transformer"，取回所有包含这个关键词的文档。更复杂的算法包括 BM25（利用 TF-IDF）和 Elasticsearch（利用倒排索引）。
基于词项的检索通常用于文本数据，但也适用于带有文本元数据（如标题、标签、字幕、评论等）的图像和视频。
2. **基于嵌入的检索**（也称向量搜索）
你用嵌入模型把数据块转换成嵌入向量，例如 BERT、sentence-transformers，以及 OpenAI 或 Google 提供的专有嵌入模型。给定一个查询，由向量搜索算法判定、向量与查询嵌入最接近的数据就会被取回。
向量搜索通常被表述为最近邻搜索，使用近似最近邻（ANN）算法，例如 FAISS（Facebook AI 相似性搜索）、Google 的 ScaNN、Spotify 的 ANNOY，以及 hnswlib（分层可导航小世界，Hierarchical Navigable Small World）。
ANN-benchmarks 网站在多个数据集上比较了不同的 ANN 算法，使用四个主要指标，并兼顾索引与查询之间的权衡。
  - **召回率（Recall）**：算法找到的最近邻所占的比例。
  - **每秒查询数（QPS）**：算法每秒能处理的查询数量。这对高流量应用至关重要。
  - **构建时间**：构建索引所需的时间。如果你需要频繁更新索引（例如因为数据会变化），这个指标尤其重要。
  - **索引大小**：算法所创建索引的大小，这对评估其可扩展性和存储需求至关重要。

这种方法不仅适用于文本文档，也适用于图像、视频、音频和代码。许多团队甚至尝试先对 SQL 表和 dataframe 生成摘要，再用这些摘要生成嵌入来做检索。

基于词项的检索比基于嵌入的检索快得多，也便宜得多。它开箱即用就能表现不错，因此是很有吸引力的起点。BM25 和 Elasticsearch 在业界都被广泛使用，是更复杂检索系统的强大基线。基于嵌入的检索虽然计算成本高，但可以随着时间显著改进，最终超越基于词项的检索。

生产环境中的检索系统通常会结合多种方法。把基于词项的检索与基于嵌入的检索结合起来，称为*混合搜索*。

一种常见模式是串行的。首先，由一个便宜但不太精确的检索器（例如基于词项的系统）取回候选项；然后，由一个更精确但更昂贵的机制（例如 k 近邻）从这些候选中找出最好的。第二步也称为重排序（reranking）。

例如，给定词项"transformer"，你可以先取回所有包含 transformer 一词的文档，不管它们讲的是电力设备（变压器）、神经网络架构还是电影（《变形金刚》）。然后用向量搜索在这些文档中找出真正与你的 transformer 查询相关的那些。

上下文重排序与传统搜索重排序的不同之处在于，条目的确切位置没那么关键。在搜索中，排名（例如第一还是第五）至关重要。在上下文重排序中，文档的顺序仍然重要，因为它会影响模型处理这些文档的效果——正如论文《Lost in the middle》（Liu 等，2023）所指出的，模型可能更容易理解位于上下文开头和结尾的文档。不过，只要文档被包含进来，其顺序的影响就远不如在搜索排名中那么大。

另一种模式是集成（ensemble）。记住，检索器的工作方式是按文档与查询的相关性得分对文档排序。你可以同时用多个检索器取回候选项，再把这些不同的排名合并，生成最终排名。

#### 基于表格数据的 RAG

外部数据源也可以是结构化的，例如 dataframe 或 SQL 表。从 SQL 表检索数据与从非结构化文档检索数据有很大不同。给定一个查询，系统的工作流程如下。

1. **文本转 SQL（Text-to-SQL）**：根据用户查询和表结构（schema），确定需要什么 SQL 查询。
2. **SQL 执行**：执行该 SQL 查询。
3. **生成**：根据 SQL 结果和原始用户查询生成回应。

在文本转 SQL 这一步，如果可用的表很多，它们的结构无法全部放进模型上下文，你可能需要一个中间步骤，预测每个查询该用哪些表。文本转 SQL 既可以由生成最终回应的同一个模型完成，也可以由众多专门的文本转 SQL 模型之一完成。

#### 智能体式 RAG（Agentic RAG）

一个重要的数据来源是互联网。像 Google 或 Bing API 这样的网页搜索工具，可以让模型访问丰富且最新的资源，为每个查询收集相关信息。例如，对于查询"今年谁获得了奥斯卡？"，系统会搜索最新一届奥斯卡的信息，并用这些信息为用户生成最终回应。

基于词项的检索、基于嵌入的检索、SQL 执行和网页搜索，都是模型为增强上下文可以采取的行动（action）。你可以把每个行动看作模型可以调用的一个函数。能够纳入外部行动的工作流也被称为*智能体式（agentic）*的。此时架构如下图所示。

**» 行动 vs. 工具 «**

一个工具可以提供一个或多个行动。例如，一个人员搜索工具可能提供两个行动：按姓名搜索和按邮箱搜索。不过两者的区别很小，所以许多人把*行动*和*工具*混用。

**» 只读行动 vs. 写行动 «**

从外部来源检索信息、但不改变其状态的行动是只读行动。赋予模型写行动（例如更新表中的值）能让模型完成更多任务，但也带来更多风险，后文会讨论。

### 查询改写

用户的查询往往需要改写，才能提高取回正确信息的可能性。考虑下面这段对话。

```
User: When was the last time John Doe bought something from us?
AI: John last bought a Fruity Fedora hat from us two weeks ago, on January 3, 2030.
User: How about Emily Doe?
```
最后一个问题"How about Emily Doe?（那 Emily Doe 呢？）"是含糊的。如果你原封不动地用这个查询去检索文档，很可能会得到无关的结果。你需要改写这个查询，以反映用户真正在问什么。新查询应该能独立成立。最后一个问题应改写为"Emily Doe 上一次从我们这里买东西是什么时候？"

查询改写通常借助其他 AI 模型完成，使用类似这样的提示词："根据下面的对话，改写用户最后一条输入，以反映用户真正想问的内容。"

查询改写可能会变得复杂，尤其是当你需要做身份解析或融合其他知识时。如果用户问"那他的妻子呢？"，你首先需要查询数据库，弄清他的妻子是谁。如果你没有这个信息，改写模型应当承认这个查询无法解决，而不是幻觉出一个名字，导致错误的答案。

## 第 2 步：加上护栏

护栏有助于降低 AI 风险，不仅保护你的用户，也保护你这个开发者。凡是可能出故障的地方，都应该设置护栏。本文讨论两类护栏：输入护栏和输出护栏。

### 输入护栏

输入护栏通常用于防范两类风险：把隐私信息泄露给外部 API，以及执行危害系统的恶意提示词（模型越狱）。

#### 向外部 API 泄露隐私信息

这种风险是使用外部模型 API、需要把数据发到组织之外时特有的。例如，某位员工可能把公司的机密或用户的隐私信息复制到提示词里，发送到模型托管的地方。

最著名的早期事件之一，是三星员工把三星的专有信息输入 ChatGPT，意外泄露了公司机密。目前尚不清楚三星是如何发现这次泄露的，也不清楚泄露的信息是否被用来对付三星。不过，这起事件严重到让三星在 2023 年 5 月禁用了 ChatGPT。

使用第三方 API 时，没有万无一失的办法能杜绝潜在的泄露。但你可以用护栏来缓解。你可以使用众多现成工具中的一种来自动检测敏感数据。要检测哪些敏感数据由你来指定。常见的敏感数据类别有：

- 个人信息（身份证号、电话号码、银行账户）。
- 人脸。
- 与公司知识产权或特许信息相关的特定关键词和短语。

许多敏感数据检测工具使用 AI 来识别潜在的敏感信息，例如判断某个字符串是否像一个有效的家庭住址。如果发现查询包含敏感信息，你有两个选择：拦截整个查询，或者把敏感信息从中移除。例如，你可以用占位符 \[PHONE NUMBER\] 遮蔽用户的电话号码。如果生成的回应中包含这个占位符，就用一个可逆的 PII 字典把占位符映射回原始信息，从而解除遮蔽，如下图所示。

#### 模型越狱

尝试越狱 AI 模型、让它们说坏话或做坏事，已经成了一项网络运动。有人可能觉得让 ChatGPT 发表争议言论很好玩，但如果印着你的名字和标志的客服聊天机器人也这么做，那就一点也不好玩了。对于能访问工具的 AI 系统来说，这尤其危险。想象一下，如果某个用户找到办法，让你的系统执行了一条破坏数据的 SQL 查询。

为了应对这一点，你首先应该在系统上设置护栏，使任何有害操作都不能被自动执行。例如，任何可能插入、删除或更新数据的 SQL 查询，未经人工批准都不得执行。这种额外安全措施的缺点是可能拖慢系统。

为了防止应用发表不该发表的离谱言论，你可以为应用定义超出范围的话题。例如，如果你的应用是客服聊天机器人，它就不应该回答政治或社会问题。一种简单的做法是过滤掉包含预定义短语的输入，这些短语通常与争议话题相关，例如"移民"或"反疫苗"。更复杂的算法则用 AI 来判断输入是否属于某个预定义的受限话题。

如果有害提示词在你的系统中很少见，你可以用异常检测算法来识别不寻常的提示词。

### 输出护栏

AI 模型是概率性的，这使其输出不可靠。你可以加上护栏，大幅提升应用的可靠性。输出护栏有两个主要功能：

1. 评估每次生成的质量。
2. 规定应对不同故障模式的策略。

#### 输出质量度量

要捕获不符合标准的输出，你需要了解故障是什么样子。下面是一些故障模式的例子以及如何捕获它们。

1. **空回应**。
2. **格式错误的回应**，即不符合预期输出格式的回应。例如，应用期望 JSON，而生成的回应缺了一个右括号。针对某些格式有现成的校验器，例如正则表达式、JSON 和 Python 代码校验器。也有用于约束采样的工具，例如 guidance、outlines 和 instructor。
3. **有毒的回应**，例如带有种族主义或性别歧视的内容。可以用众多毒性检测工具之一来捕获这类回应。
4. **事实不一致的回应**，即模型幻觉出来的内容。幻觉检测是一个活跃的研究领域，已有的方案包括 SelfCheckGPT（Manakul 等，2023）和 SAFE（搜索引擎事实性评估器，Search Engine Factuality Evaluator，Wei 等，2024）。你可以通过为模型提供充足的上下文，以及使用思维链（chain-of-thought）等提示技巧来减轻幻觉。幻觉的检测与缓解会在我即将出版的书《AI Engineering》中进一步讨论。
5. **包含敏感信息的回应**。这可能发生在两种场景中。
  1. 你的模型用敏感数据训练过，并把它们复述了出来。
  2. 你的系统从内部数据库中检索敏感信息来丰富上下文，然后把这些敏感信息传进了回应中。
这种故障模式可以通过从一开始就不用敏感数据训练模型、不允许模型检索敏感数据来预防。输出中的敏感数据可以用与输入护栏相同的工具来检测。
6. **带有品牌风险的回应**，例如错误描述你的公司或竞争对手的回应。一个例子是：X 训练的模型 Grok 生成了一条回应，暗示 Grok 是由 OpenAI 训练的，引得网友怀疑 X 窃取了 OpenAI 的数据。这种故障模式可以通过关键词监控来缓解。一旦识别出涉及你的品牌和竞争对手的输出，你可以拦截这些输出、交给人工审核员，或者用其他模型检测这些输出的情感倾向，确保只返回情感正确的内容。
7. **总体上很糟糕的回应**。例如，你让模型写一篇文章，结果写得很烂；或者你让模型给一份低卡蛋糕食谱，生成的食谱里却放了过量的糖。用 AI 评审（AI judge）来评估模型回应的质量已经成为流行做法。这些 AI 评审可以是通用模型（想想 ChatGPT、Claude），也可以是专门训练的打分器，针对给定查询为回应输出一个具体分数。

#### 故障处理

AI 模型是概率性的，这意味着同一个查询再试一次，可能会得到不同的回应。许多故障可以用基本的重试逻辑来缓解。例如，如果回应为空，就重试 X 次，或直到得到非空回应为止。同样，如果回应格式错误，就重试，直到模型生成格式正确的回应。

然而，这种重试策略会带来额外的延迟和成本。一次重试意味着 API 调用次数翻倍。如果在失败之后才重试，用户感受到的延迟会翻倍。为了降低延迟，可以并行调用。例如，对每个查询，与其等第一次调用失败后再重试，不如同时把这个查询发给模型两次，拿回两个回应，再挑更好的那个。这会增加冗余的 API 调用次数，但能把延迟控制在可接受范围内。

把棘手的查询转交给人工处理也很常见。例如，如果查询包含特定关键短语，你可以把它转给人工客服。有些团队使用专门的模型（可能是自研训练的）来决定何时把对话转给人工。例如，有个团队在其情感分析模型检测到用户开始生气时，就把对话转给人工客服。另一个团队则在对话达到一定轮数后转人工，以免用户陷入死循环。

### 护栏的权衡

**可靠性与延迟的权衡**：有些团队虽然承认护栏很重要，但告诉我延迟更重要。他们决定不实施护栏，因为护栏会显著增加应用的延迟。不过这些团队是少数。大多数团队认为，风险增加的代价比延迟增加更大。

输出护栏在流式补全模式下可能效果不佳。默认情况下，整个回应生成完毕后才展示给用户，这可能需要很长时间。在流式补全模式下，新 token 一生成就流式推送给用户，缩短了用户看到回应前的等待时间。缺点是很难评估不完整的回应，因此在系统护栏判定应当拦截之前，不安全的回应可能已经流式推送给了用户。

**自托管与第三方 API 的权衡**：自托管模型意味着你不必把数据发给第三方，从而减少了对输入护栏的需求。但这也意味着你必须自己实现所有必要的护栏，而不能依赖第三方服务提供的护栏。

现在我们的平台看起来是这样的。护栏可以是独立的工具，也可以是模型网关的一部分（后文会讨论）。如果用了打分器，它们归在模型 API 之下，因为打分器通常也是 AI 模型。用于打分的模型通常比用于生成的模型更小、更快。

## 第 3 步：添加模型路由器和网关

随着应用越来越复杂、涉及的模型越来越多，出现了两类帮助你使用多个模型的工具：路由器和网关。

### 路由器

一个应用可以用不同的模型来回应不同类型的查询。针对不同查询采用不同方案有几个好处。首先，这让你可以使用专门化的方案，例如一个模型专门处理技术故障排查，另一个专门处理订阅事务。专门化模型的表现可能优于通用模型。其次，这能帮你节省成本。与其把所有查询都路由到昂贵的模型，不如把较简单的查询路由到更便宜的模型。

路由器通常包含一个**意图分类器**，用于预测用户想做什么。根据预测的意图，查询被路由到相应的方案。例如，对于客服聊天机器人，如果意图是：

- 重置密码 –> 把用户引导到密码重置页面。
- 更正账单错误 –> 把用户转给人工客服。
- 排查技术问题 –> 把查询路由到为故障排查而微调的模型。

意图分类器还能帮助系统避免超出范围的对话。例如，你可以用一个意图分类器预测查询是否超出范围。如果查询被认定为不恰当（例如用户问你会在即将到来的选举中投票给谁），聊天机器人可以用一条预设回复礼貌地拒绝（"作为聊天机器人，我没有投票的能力。如果你对我们的产品有疑问，我很乐意帮忙。"），而不必浪费一次 API 调用。

如果你的系统可以执行多种行动，路由器还可以包含一个**下一步行动预测器**，帮助系统决定接下来采取什么行动。如果查询含糊，一个合理的行动是请求澄清。例如，针对查询"Freezing（冻结／好冷）"，系统可能会问："你是想冻结账户，还是在说天气？"或者干脆说："抱歉，能具体说说吗？"

意图分类器和下一步行动预测器可以是通用模型，也可以是专门的分类模型。专门的分类模型通常比通用模型小得多、快得多，因此系统可以同时使用多个，而不会产生显著的额外延迟和成本。

当把查询路由到上下文上限各不相同的模型时，可能需要相应地调整查询的上下文。设想一个 1,000 token 的查询，原定发给一个上下文上限为 4K 的模型。随后系统执行了一个行动，例如网页搜索，带回了 8,000 token 的上下文。你可以截断查询的上下文以适配原定的模型，也可以把查询路由到上下文上限更大的模型。

### 网关

模型网关是一个中间层，让你的组织能以统一且安全的方式与不同的模型交互。模型网关最基本的功能，是让开发者能以相同的方式访问不同的模型——无论是自托管模型，还是 OpenAI、Google 等商业 API 背后的模型。模型网关让代码更容易维护。如果某个模型 API 变了，你只需更新模型网关，而不必更新所有使用该模型 API 的应用。

最简单的形式下，模型网关就是一个统一的封装，类似下面的代码示例。这个示例只是让你了解模型网关大概如何实现，它并不能直接运行，因为其中没有任何错误检查或优化。

```
import google.generativeai as genai
import openai
def openai_model(input_data, model_name, max_tokens):
    openai.api_key = os.environ["OPENAI_API_KEY"]
    response = openai.Completion.create(
        engine=model_name,
        prompt=input_data,
        max_tokens=max_tokens
    )
    return {"response": response.choices[0].text.strip()}
def gemini_model(input_data, model_name, max_tokens):
    genai.configure(api_key=os.environ["GOOGLE_API_KEY"])
    model = genai.GenerativeModel(model_name=model_name)
    response = model.generate_content(input_data, max_tokens=max_tokens)
    return {"response": response["choices"][0]["message"]["content"]}
@app.route('/model', methods=['POST'])
def model_gateway():
    data = request.get_json()
    model_type = data.get("model_type")
    model_name = data.get("model_name")
    input_data = data.get("input_data")
    max_tokens = data.get("max_tokens")
    if model_type == "openai":
        result = openai_model(input_data, model_name, max_tokens)
    elif model_type == "gemini":
        result = gemini_model(input_data, model_name, max_tokens)
    return jsonify(result)
```
模型网关是**访问控制与成本管理**的关口。与其把组织的 token（很容易泄露）发给每个想访问 OpenAI API 的人，不如只让大家访问模型网关，从而形成一个集中、可控的访问点。网关还可以实现细粒度的访问控制，规定哪个用户或应用可以访问哪个模型。此外，网关可以监控并限制 API 调用量，防止滥用并有效管理成本。

模型网关还可以用来实现回退策略，以应对速率限制或 API 故障（遗憾的是后者很常见）。当主 API 不可用时，网关可以把请求路由到备用模型、稍等片刻后重试，或以其他优雅的方式处理故障。这能确保你的应用平稳运行、不被中断。

由于请求和回应本来就要经过网关，它也是实现负载均衡、日志记录和分析等其他功能的好地方。有些网关服务甚至提供缓存和护栏。

鉴于网关实现起来相对简单，市面上有许多现成的网关，例如 Portkey 的网关、MLflow AI Gateway、WealthSimple 的 llm-gateway、TrueFoundry、Kong 和 Cloudflare。

加上网关和路由器之后，我们的平台越来越有意思了。和打分一样，路由也放在模型网关里。和用于打分的模型一样，用于路由的模型通常也比用于生成的模型小。

## 第 4 步：用缓存降低延迟

我把这篇文章分享给朋友 Eugene Yan 时，他说缓存可能是 AI 平台中最被低估的组件。缓存能显著降低应用的延迟和成本。

缓存技术也可以用在训练阶段，但由于本文讲的是部署，我将聚焦于推理阶段的缓存。常见的推理缓存技术包括提示词缓存、精确缓存和语义缓存。提示词缓存通常由你所使用的推理 API 实现。评估一个推理库时，了解它支持哪些缓存机制会很有帮助。

*注意力机制的 KV 缓存不在本文讨论范围之内。*

### 提示词缓存

应用中的许多提示词都有重叠的文本片段。例如，所有查询都可能共用同一个系统提示词。提示词缓存把这些重叠片段存起来复用，这样你只需处理一次。不同提示词中常见的重叠片段就是系统提示词。没有提示词缓存，模型每处理一个查询都要处理一遍系统提示词；有了提示词缓存，只需在第一个查询时处理一次。

对于系统提示词很长的应用，提示词缓存能显著降低延迟和成本。如果你的系统提示词有 1000 个 token，而你的应用今天产生了 100 万次模型 API 调用，提示词缓存每天就能为你省去处理大约 10 亿个重复输入 token！不过这并非完全免费。和 KV 缓存一样，提示词缓存的体积可能相当大，需要大量工程投入。

提示词缓存对涉及长文档的查询也很有用。例如，如果许多用户查询都与同一份长文档（比如一本书或一个代码库）相关，就可以把这份长文档缓存起来，在多个查询间复用。

自 2023 年 11 月 Gim 等人提出以来，提示词缓存已经被纳入各家模型 API。Google 宣布 Gemini API 将于 2024 年 6 月以*上下文缓存（context cache）*之名提供这一功能。缓存的输入 token 相比普通输入 token 享有 75% 的折扣，但你需要为缓存存储额外付费（截至撰写本文时，每 100 万 token 每小时 1.00 美元）。鉴于提示词缓存的明显好处，如果它变得像 KV 缓存一样普及，我也不会感到意外。

llama.cpp 虽然也有提示词缓存，但它似乎只缓存完整的提示词，并且只对同一聊天会话中的查询有效。它的文档有限，但我读代码后的猜测是：在一段长对话中，它会缓存之前的消息，只处理最新的那条消息。

### 精确缓存

如果说提示词缓存和 KV 缓存是基础模型特有的，那么精确缓存则更通用、更直接。系统把处理过的条目存起来，等到同样的条目再次被请求时复用。例如，如果用户让模型总结某个产品，系统会先查缓存，看看这个产品的摘要是否已经缓存。如果有，就取出这份摘要；如果没有，就总结该产品并缓存摘要。

精确缓存也用于基于嵌入的检索，以避免重复的向量搜索。如果传入的查询已在向量搜索缓存中，就取出缓存的搜索结果；如果不在，就对该查询执行向量搜索并缓存结果。

对于需要多个步骤（例如思维链）和／或耗时行动（例如检索、SQL 执行或网页搜索）的查询，缓存尤其有吸引力。

精确缓存可以用内存存储来实现快速检索。但由于内存存储有限，缓存也可以用 PostgreSQL、Redis 等数据库或分层存储来实现，以平衡速度与存储容量。制定淘汰策略对于管理缓存大小和保持性能至关重要。常见的淘汰策略包括最近最少使用（LRU）、最不经常使用（LFU）和先进先出（FIFO）。

一个查询要缓存多久，取决于它再次被调用的可能性有多大。"我最近的订单状态如何"这类特定于用户的查询不太可能被其他用户复用，因此不应缓存。同样，缓存"天气怎么样？"这类时效性强的查询也没什么意义。有些团队会训练一个小型分类器来预测某个查询是否应该缓存。

### 语义缓存

与精确缓存不同，语义缓存不要求传入的查询与某个已缓存的查询完全相同。语义缓存允许复用相似的查询。设想一个用户问"越南的首都是哪里？"，模型给出答案"河内"。之后另一个用户问"越南的首都***城市***是哪里？"，问题相同，只是多了"城市"一词。语义缓存的思路是，系统可以复用答案"河内"，而不必从头计算这个新查询。

只有当你有可靠的方法判断两个查询在语义上是否相似时，语义缓存才能奏效。一种常见方法是基于嵌入的相似度，其工作方式如下：

1. 对每个查询，用嵌入模型生成其嵌入。
2. 用向量搜索找出与当前查询嵌入最接近的已缓存嵌入。假设这个相似度得分是 X。
3. 如果 X 高于你设定的相似度阈值，就认为已缓存的查询与当前查询相同，返回缓存的结果。否则，处理当前查询，并把它连同其嵌入和结果一起缓存。

这种方法需要一个向量数据库来存储已缓存查询的嵌入。

**与其他缓存技术相比，语义缓存的价值更值得怀疑，因为它的许多组件都容易出错。** 它的成功依赖于高质量的嵌入、可用的向量搜索以及可信的相似度指标。设定合适的相似度阈值也可能很棘手，需要大量试错。如果系统误把传入的查询当成与另一个查询相似，从缓存中取回的回应就会是错误的。

此外，语义缓存可能既耗时又耗算力，因为它涉及向量搜索。这次向量搜索的速度和成本，取决于你的已缓存嵌入数据库的规模。

如果缓存命中率很高，也就是说相当一部分查询都能借助缓存结果得到有效回答，语义缓存可能仍然值得。不过，在引入语义缓存的复杂性之前，务必评估与之相关的效率、成本和性能风险。

## 第 5 步：添加复杂逻辑和写操作

到目前为止我们讨论的应用流程都相当简单。基础模型生成的输出大多直接返回给用户（除非没通过护栏）。然而，应用流程可以更复杂，带有循环和条件分支。模型的输出还可以用来触发写操作，比如撰写邮件或下单。

### 复杂逻辑

模型的输出可以有条件地传给另一个模型，或者作为下一步输入的一部分回馈给同一个模型。这个过程一直持续，直到系统中的某个模型判定任务已完成、应当向用户返回最终回应。

当你赋予系统规划并决定下一步做什么的能力时，就会出现这种情况。举个例子，考虑查询"为巴黎规划一个周末行程"。模型可能首先生成一份潜在活动清单：参观埃菲尔铁塔、在咖啡馆吃午饭、游览卢浮宫等。然后，每项活动又可以回馈给模型，生成更详细的计划。例如，"参观埃菲尔铁塔"可能促使模型生成一些子任务，比如查询开放时间、购票、寻找附近的餐厅。这个迭代过程一直持续，直到生成一份全面而详细的行程。

我们的基础设施现在多了一个箭头，把生成的回应指回上下文构建，而上下文构建又反过来馈送给模型网关中的模型。

### 写操作

用于上下文构建的行动是*只读行动*。它们让模型从数据源读取信息以收集上下文。但系统也可以执行*写操作*，对数据源乃至现实世界做出改变。例如，如果模型输出"给 X 发一封邮件，内容是 Y"，系统就会调用行动 `send_email(recipient=X, message=Y)`。

写操作让系统的能力大大增强。它们能让你把整个客户拓展流程自动化：调研潜在客户、查找他们的联系方式、起草邮件、发送首封邮件、阅读回复、跟进、提取订单、用新订单更新数据库，等等。

然而，赋予 AI 自动改变我们生活的能力，这种前景令人害怕。正如你不该给实习生删除生产数据库的权限，你也不该允许一个不可靠的 AI 发起银行转账。对系统能力及其安全措施的信任至关重要。你需要确保系统能防范那些试图操纵它执行有害操作的恶意行为者。

AI 系统和其他软件系统一样容易受到网络攻击，但它们还有另一个弱点：*提示词注入*。提示词注入是指攻击者操纵输入模型的提示词，让模型表现出不良行为。你可以把提示词注入看作针对 AI 而非人类的社会工程攻击。

许多公司担心这样一种场景：他们让 AI 系统访问内部数据库，而攻击者诱骗系统泄露这些数据库中的隐私信息。如果系统对这些数据库有写权限，攻击者还能诱骗系统破坏数据。

任何想利用 AI 的组织都需要认真对待安全与防护。但这些风险并不意味着永远不该赋予 AI 系统在现实世界中行动的能力。AI 系统会出错，人也会出错。既然我们能让人们信任一台机器把我们送上太空，我希望有一天，安全保障也能足以让我们信任自主 AI 系统。

## 可观测性

虽然我把可观测性单独放在一节，但它应当从一开始就融入平台，而不是事后才想起来补上。可观测性对各种规模的项目都至关重要，而且系统越复杂，它就越重要。

与其他各节相比，这一节提供的信息最少。在一篇博客文章里不可能讲透可观测性的所有细节。因此，我只简要概述监控的三大支柱：日志、追踪和指标。我不会深入细节，也不涉及用户反馈、漂移检测和调试。

### 指标

谈到监控，大多数人会想到指标。要追踪哪些指标，取决于你想了解系统的哪些方面，这因应用而异。不过总体而言，你需要追踪两类指标：模型指标和系统指标。

系统指标告诉你整个系统的状态。常见的指标有吞吐量、内存使用、硬件利用率以及服务可用性／正常运行时间。系统指标是所有软件工程应用共有的。本文我将聚焦于模型指标。

模型指标评估模型的表现，例如准确率、毒性和幻觉率。应用流水线中的不同步骤也有各自的指标。例如，在 RAG 应用中，检索质量通常用上下文相关性和上下文精确度来评估。向量数据库则可以按索引数据所需的存储空间以及查询数据所需的时间来评估。

模型输出出错的方式多种多样。识别这些问题并制定指标来监控它们至关重要。例如，你可能想追踪模型超时、返回空回应或产生格式错误回应的频率。如果你担心模型泄露敏感信息，也要想办法追踪这一点。

与长度相关的指标，例如查询长度、上下文长度和回应长度，有助于理解模型的行为。某个模型是否比另一个更啰嗦？某些类型的查询是否更容易引出冗长的答案？这些指标对于发现应用中的变化尤其有用。如果平均查询长度突然下降，可能意味着存在需要调查的潜在问题。

与长度相关的指标对于追踪延迟和成本也很重要，因为更长的上下文和回应通常会增加延迟、产生更高的成本。

追踪延迟对于了解用户体验至关重要。常见的延迟指标包括：

- **首 token 时间**（Time to First Token，TTFT）：生成第一个 token 所需的时间。
- **token 间隔时间**（Time Between Tokens，TBT）：每两个 token 生成之间的间隔。
- **每秒 token 数**（Tokens Per Second，TPS）：生成 token 的速率。
- **每个输出 token 的时间**（Time Per Output Token，TPOT）：生成每个输出 token 所需的时间。
- **总延迟**：完成一次回应所需的总时间。

你还需要追踪成本。与成本相关的指标是查询数量以及输入和输出 token 的量。如果你使用有速率限制的 API，追踪每秒请求数很重要，以确保不超出分配的额度、避免潜在的服务中断。

计算指标时，你可以在抽查和全量检查之间选择。抽查是对一部分数据采样以快速发现问题，全量检查则评估每一个请求，以获得全面的性能视图。选择哪种取决于系统的需求和可用资源，两者结合能提供一种平衡的监控策略。

计算指标时，要确保它们可以按相关维度拆分，例如用户、版本发布、提示词／链的版本、提示词／链的类型以及时间。这种粒度有助于理解性能差异、定位具体问题。

### 日志

由于这篇文章越写越长，而且我在《Designing Machine Learning Systems》（《设计机器学习系统》）中已经详细写过日志，这里就简短带过。日志的理念很简单：什么都记。记录系统配置。记录查询、输出以及中间输出。记录组件何时启动、何时结束、何时崩溃，等等。记录每条日志时，务必给它加上标签和 ID，帮助你知道这条日志来自系统的哪个部分。

什么都记意味着日志量会增长得非常快。许多用于自动日志分析和日志异常检测的工具都由 AI 驱动。

虽然人工处理日志是不可能的，但每天人工检查生产数据、了解用户如何使用你的应用，是很有用的。Shankar 等人（2024）发现，随着开发者接触的数据越来越多，他们对何为好输出、何为坏输出的认识也会改变，这使他们既能改写提示词以提高得到好回应的概率，也能更新评估流水线以捕获坏回应。

### 追踪

追踪（trace）是指对一个请求在各个系统组件和服务中的执行路径的详细记录。在 AI 应用中，追踪展示从用户发送查询到返回最终回应的整个过程，包括系统采取的行动、检索到的文档以及发给模型的最终提示词。它还应显示每一步耗时多少，以及（如果可度量的话）相关成本。举个例子，下图是一次 Langsmith 追踪的可视化。

理想情况下，你应该能一步步追踪每个查询在系统中的变换过程。如果某个查询失败了，你应该能精确定位出错的步骤：是处理有误，是检索到的上下文无关，还是模型生成了错误的回应。

## AI 流水线编排

AI 应用可能变得相当复杂：由多个模型组成，从许多数据库检索数据，还能使用各种各样的工具。编排器帮助你规定如何把这些不同组件组合（串联）在一起，形成端到端的应用流程。

从高层次看，编排器分两步工作：组件定义和串联（也称流水线化）。

1. **组件定义**
你需要告诉编排器系统使用了哪些组件，例如模型（包括用于生成、路由和打分的模型）、系统可以检索数据的数据库，以及系统可以采取的行动。与模型网关直接集成可以简化模型的接入，有些编排工具也想成为网关。许多编排器还支持与评估和监控工具集成。
2. **串联（或流水线化）**
你告诉编排器，系统从收到用户查询到完成任务要经过哪些步骤。简而言之，串联就是函数组合。下面是一个流水线的示例。
  1. 处理原始查询。
  2. 根据处理后的查询检索相关数据。
  3. 把原始查询和检索到的数据组合起来，生成模型期望格式的提示词。
  4. 模型根据提示词生成回应。
  5. 评估回应。
  6. 如果回应被认为是好的，就返回给用户；否则，把查询转给人工客服。
编排器负责在各步骤之间传递数据，并可以提供工具，帮助确保当前步骤的输出符合下一步期望的格式。

为有严格延迟要求的应用设计流水线时，要尽量并行处理。例如，如果你有一个路由组件（决定把查询发往哪里）和一个 PII 移除组件，两者可以同时进行。

AI 编排工具有很多，包括 LangChain、LlamaIndex、Flowise、Langflow 和 Haystack。每个工具都有自己的 API，所以这里就不展示实际代码了。

**虽然在项目一开始就直接上编排工具很有诱惑力，但请先不用编排工具来构建你的应用。** 任何外部工具都会带来额外的复杂性。编排器可能把系统运作的关键细节抽象掉，让你难以理解和调试系统。

当你推进到应用开发的后期阶段时，可能会觉得编排器能让你轻松一些。评估编排器时，需要注意以下三个方面。

1. **集成与可扩展性**
评估编排器是否支持你已经在用或将来可能采用的组件。例如，如果你想用 Llama 模型，就要检查编排器是否支持。考虑到模型、数据库和框架如此之多，编排器不可能支持一切。因此，你还需要考虑编排器的可扩展性：如果它不支持某个特定组件，要改变这一点有多难？
2. **对复杂流水线的支持**
随着应用变得越来越复杂，你可能需要管理包含多个步骤和条件逻辑的复杂流水线。支持分支、并行处理和错误处理等高级特性的编排器，能帮你高效地管理这些复杂性。
3. **易用性、性能与可扩展性**
考虑编排器是否好用。寻找直观的 API、完善的文档和强大的社区支持，这些能显著降低你和团队的学习成本。避免使用会发起隐藏 API 调用或给应用引入延迟的编排器。此外，要确保随着应用数量、开发者数量和流量的增长，编排器能有效扩展。

## 结论

本文从一个基础架构出发，逐步添加组件，以应对不断增长的应用复杂性。每一项新增都有其自身的好处和挑战，需要仔细考虑和实施。

虽然组件的划分对于保持系统模块化、可维护很重要，但这种划分是流动的。组件之间有许多重叠。例如，模型网关可以与护栏共享部分功能。缓存可以在不同的组件中实现，例如在向量搜索和推理服务中。

这篇文章比我原本打算的长得多，但仍有许多细节没能进一步探讨，尤其是关于可观测性、上下文构建、复杂逻辑、缓存和护栏的部分。我会在即将出版的书《AI Engineering》中深入探讨所有这些组件。

本文也没有讨论如何部署（serve）模型，因为我假设大多数人会使用第三方 API 提供的模型。《AI Engineering》也会有一章专门讲推理与模型优化。
