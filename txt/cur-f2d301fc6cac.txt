postMessage 慢吗？（Is postMessage slow?） ｜ Surma ｜ 文章 ｜ https://surma.dev/things/is-postmessage-slow/

很多人因为担心 postMessage() 的性能而不敢用 Web Worker。Surma 的回答是“不太慢，视情况而定”，并用基准测试把“视情况”讲清楚。他的前提是：没测过就不算慢，测了也要结合上下文才有意义。

原理上，postMessage 依靠结构化克隆，可以理解成更聪明的 JSON.stringify/parse，能处理循环引用和 Map、Set、ArrayBuffer。序列化阻塞发送方，反序列化阻塞接收方。Chrome 和 Safari 会推迟到读取 .data 时才反序列化，Firefox 则在派发事件前就做完。两者都合规，他给 Mozilla 提了 bug，希望统一成前一种。因为无法单独测量序列化，他选择测端到端时间，作为开销的上限。

测试方法：从 worker 向主线程发送广度、深度各为 1–6 的随机对象，每种组合发 1000 个，取第 95 百分位。Spectre 之后浏览器降低了 performance.now() 的精度：桌面 Chrome 5µs，安卓 Chrome 100µs，Firefox 和 Safari 1ms（Firefox 的限制他关掉了），所以 Pixel 3 和 Safari 的数据看起来粗糙。结论是对象越复杂越慢。第二轮把叶子值换成 16 字节到 2KiB 的字符串，得出经验法则：传输时间大致与对象 JSON 字符串化后的大小成正比，但这只对超过约 100KiB 的大对象才有意义。

用 RAIL 预算来衡量：响应交互有 100ms，即使在最慢的设备上，100KiB 以内的对象也不会超预算。有 JS 驱动的动画时每帧只有 16ms，10KiB 以内没有风险。这也是优先用 CSS 动画和过渡的理由，它们跑在合成器线程上，不受主线程阻塞影响。

数据确实很大时的办法：
一是只发补丁。扫雷 PWA PROXX 的 40×40 棋盘状态约 134KiB，所以只发送变更，ImmerJS 可以生成和应用这类补丁，传输量只和改动大小有关。
二是分块。首次点击可能翻开 80% 的格子，补丁约 70KiB，对功能机仍然太多。worker 从点击处向外遍历，攒够阈值就先发一批。在每帧只能处理一条消息的 Nokia 8110 上，分批更新看起来像一段翻开动画；在强机器上，事件循环会自然多处理几条。
三是用 JSON 字符串包装，实测没有帮助。
四是二进制格式：ArrayBuffer 可以零拷贝转移，耗时与大小无关，但要自己编组数据，FlatBuffers 这类格式可以不解包整个缓冲区就读取字段。
五是 WebAssembly 取巧：用 Rust 定义不含指针的 State 结构体，直接把它的内存当作序列化结果复制出去，模块 gzip 后约 3KiB，传输时间近乎恒定，代价是访问状态更麻烦。只建议用 C、Rust、AssemblyScript 这类能掌控内存布局的语言。
六是 SharedArrayBuffer 加 Atomics 实现共享内存，或者用多线程 WebAssembly。当时只有桌面 Chrome 开放 SAB，而且同步本身也有开销。

结论：postMessage 有成本，但远不至于让主线程外架构不可行。负载更大时用补丁或二进制格式，最好从一开始就把状态布局、可转移性和可打补丁性当作架构决策来考虑。他认为今天就能在 Web 上做出高性能的主线程外架构，前提是走出“一切默认都在主线程”的舒适区。
