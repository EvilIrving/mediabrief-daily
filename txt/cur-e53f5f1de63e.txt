Ep 41. 和 Penguin 聊聊 CPython 优化和大厂编译器组的工作 ｜ 捕蛇者说 ｜ 73分钟 ｜ https://pythonhunter.org/episodes/ep41

这期《捕蛇者说》请来在腾讯数据平台部编译器组工作的 Penguin，聊他给 CPython 贡献的两个性能优化，以及大厂编译器工程师的日常；节目中途还有一位做 SRE、最近在接触龙芯项目的朋友临时加入旁听并参与讨论。Penguin 原本做安全，后来进了一家被蚂蚁收购的静态分析公司，再转去做编译器，组里主要为生产环境里的 Python 3.6、3.8 做定制优化，顺手把通用的补丁提交给社区。

第一个优化是 Python 3.12 新增的 RETURN_CONST 指令。他在用 3.11 的 opcode 统计功能分析自家解释器时发现，RETURN_VALUE 的前一条指令极大概率是 LOAD_CONST，对应 return None 这类返回常量的写法，而不写返回值的函数默认就会返回 None。既然常量已知，就没必要先压栈再出栈，于是把两条指令合成一条。他自测提升不到 1%，社区在 pyperformance 上跑出来超过 1%。他解释这个数字是 50 多个基准各自跑多遍取均值再平均的结果，个别 case 可能快 10%、也有慢几个百分点的，小 case 还受测量误差影响。对想尝试的人，他认为最难的是弄懂 CPython 大量自动生成代码的构建流程：从 opcode.py 生成 opcode.h 和跳转表，3.12 起执行逻辑也用 DSL 生成，GDB 会因为行号映射乱跳、断点打不上，所以建议先读 Makefile 弄清每一步的输入输出。他还讲解了 3.11 的指令特化原理，即缓存属性的偏移、类型一致时直接按偏移读取，并指出特化失败的原因统计至今仍很混乱，他提的几个 PR 正是在修复不同特化共用同一错误码导致信息错误的问题。他顺带给出实用建议：大量 LOAD_GLOBAL 时，可先把全局变量赋给局部变量。

第二个优化是让 list[int] 这类 GenericAlias 对象在被调用时直接走宿主类型的 vectorcall，而不是缓慢的、需要打包 tuple 和 dict 的 tp_call。内置类型的 vectorcall 兼容变长参数，只要存在就不会失败。这个发现来自他用 Python 改写一个高阶类型教学项目时的随手尝试，现实中的工厂模式也会把类型存进变量再调用。

谈到工作，Penguin 认为编译器工程师和 CRUD 程序员没有本质区别，业务程序员就是他们的甲方，只是没有产品经理，需求要靠线上监控和与人交流自己挖掘。他把问题定位比作漏斗，强调闭门造车不可能成功，旁听者也认同做基础组件反而更要懂业务。他对优化的价值有一套鲜明的看法：代码是“生长”出来的，必然腐化，优化是为这种腐化兜底、延长项目寿命，省下的 CPU 和钱应该用来重构，而不是继续写烂代码。他用一个招聘的例子说明这一点：花一百万请一位精通 C++ 和 Scala 的高手写出高性能的 Spark 代码，人会被海量需求累垮跳槽；花同样的钱请两位只会一点 Python 但懂算法的人，业务响应更快，却会不断积累脏代码。比如线上任务从一小时膨胀到五小时，优化者先把它压回三小时，业务方则必须趁这段时间重构回一小时。在 AI 方向，他具体描述了现状的痛点：不同框架的计算图、运行时和部署方式无法对齐，每接入一种异构硬件都要在优化层和框架层分别注册算子，模型有时还得在 PyTorch 与 TensorFlow 之间手工迁移，而 Java 程序员从来不必关心底层是哪家的 CPU。旁听者追问国产加速卡算子精度不一致、需要在模型代码里补偿的问题，Penguin 承认各家方案至今难以统一，TVM、太极等开源项目也只覆盖部分场景。他组里现在在做 AI 编译器与基础设施，希望屏蔽 PyTorch、TensorFlow 等框架之间以及异构硬件之间的差异，同时坦承这是蓝图，现实中能把适配从一个月降到两三天已是进步。被问到国产化，他只说做成了必然有利于国产化。最后他建议应届生考虑编译器方向：人才供给远少于需求，是相对不卷的赛道，旁听者也顺势为同样缺人的 SRE 招人。
