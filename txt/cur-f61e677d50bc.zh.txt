# 理解大模型的主要评估方法

在实践中，评估训练好的大模型有四种常见方式：多项选择、验证器、排行榜和大模型裁判，如下图 1 所示。研究论文、营销材料、技术报告和模型卡（model card，指大模型专用的技术报告）通常会包含其中两类或更多类别的结果。

[图 1：本文涵盖的 4 种不同评估方法概览。]

此外，这里介绍的四个类别又可分为两组：基于基准的评估和基于判断的评估，如上图所示。

（还有其他一些指标，比如训练损失、困惑度和奖励，但它们通常是在模型开发过程中内部使用的。）

下面各小节将简要概述并举例说明这四种方法。

# 方法 1：评估答案选项的准确率

我们从一种基于基准的方法开始：多项选择问答。

历史上，最广泛使用的评估方法之一是多项选择基准，比如 MMLU（Massive Multitask Language Understanding，大规模多任务语言理解的缩写，https://huggingface.co/datasets/cais/mmlu）。为了说明这种方法，图 2 展示了 MMLU 数据集中的一道典型题目。

[图 2：通过将大模型的多项选择预测与数据集中的正确答案进行比较，在 MMLU 上评估大模型。]

图 2 只展示了 MMLU 数据集中的一个例子。完整的 MMLU 数据集涵盖 57 个科目（从高中数学到生物学），共约 1.6 万道多项选择题，性能以准确率（答对题目的比例）来衡量，例如在 16,000 道题中答对 14,000 道，准确率就是 87.5%。

像 MMLU 这样的多项选择基准，以一种直接、可量化的方式测试大模型的知识回忆能力，类似于标准化考试、很多学校考试或驾照理论考试。

> 注意，图 2 展示的是多项选择评估的简化版本，即把模型预测的答案字母直接与正确答案比较。另外还有两种流行的方法，涉及对数概率打分（log-probability scoring）。我在 GitHub 上实现了它们（https://github.com/rasbt/reasoning-from-scratch/tree/main/chF/02_mmlu）。（由于它们建立在本文所讲的概念之上，我建议读完本文后再去看。）

下面各小节说明如何用代码实现图 2 所示的 MMLU 打分。

## 1.2 加载模型

我们不把大量 Qwen3 源代码复制粘贴过来，而是从我的 reasoning_from_scratch Python 库（https://github.com/rasbt/reasoning-from-scratch/blob/main/reasoning_from_scratch）中导入它，可以通过以下命令安装：

## 1.3 检查生成的答案字母

本节我们实现最简单、也许也是最直观的 MMLU 打分方法：检查生成的多项选择答案字母是否与正确答案一致。这与前面图 2 所示的类似，为方便起见再次展示如下。

[图 3：通过将大模型的多项选择预测与数据集中的正确答案进行比较，在 MMLU 上评估大模型。]

为此，我们将使用 MMLU 数据集中的一个例子：

```
example = {
    "question": (
        "How many ways are there to put 4 distinguishable"
        " balls into 2 indistinguishable boxes?"
    ),
    “choices”: ["7", "11", "16", "8"],
    “answer”: "D",
}
```

接下来，我们定义一个函数来格式化大模型的提示词。

#### 代码块 2：加载预训练模型（原文小标题如此，实为格式化提示词）

```
def format_prompt(example):
    return (
        f"{example['question']}\n"
        f"A. {example['choices'][0]}\n"
        f"B. {example['choices'][1]}\n"
        f"C. {example['choices'][2]}\n"
        f"D. {example['choices'][3]}\n"
        "Answer: "
    )
# Trailing space in "Answer: " encourages a single-letter next token
```

我们在这个 MMLU 例子上执行该函数，看看格式化后的大模型输入是什么样子：

```
prompt = format_prompt(example)
print(prompt)
```

输出为：

```
How many ways are there to put 4 distinguishable balls into 2
indistinguishable boxes?
A. 7
B. 11
C. 16
D. 8
Answer:
```

如上所示，这个模型提示词给出了不同答案选项的列表，并以 `"Answer: "` 文本结尾，鼓励模型生成正确答案。

虽然并非绝对必要，但有时额外提供一些附带正确答案的问题作为输入也会有帮助，这样模型就能看到它应该如何解决这个任务。（例如，提供 5 个例子的情况也被称为 5-shot MMLU。）不过，对于当前这一代大模型来说，即使是基座模型也已相当强，这并不是必需的。

接下来，我们对提示词进行分词，并把它包装成一个 PyTorch 张量对象，作为大模型的输入：

```
prompt_ids = tokenizer.encode(prompt)
prompt_fmt = torch.tensor(prompt_ids, device=device)
# Add batch dimension:
prompt_fmt = prompt_fmt.unsqueeze(0)
```

把这些准备工作都做完之后，我们在下面定义主要的打分函数。它会生成几个 token（这里默认是 8 个），并提取模型输出中第一次出现的字母 A/B/C/D。

#### 代码块 3：提取生成的字母

```
from reasoning_from_scratch.ch02_ex import (
    generate_text_basic_stream_cache
)

def predict_choice(
    model, tokenizer, prompt_fmt, max_new_tokens=8
):
    pred = None
    for t in generate_text_basic_stream_cache(
        model=model,
        token_ids=prompt_fmt,
        max_new_tokens=max_new_tokens,
        eos_token_id=tokenizer.eos_token_id,
    ):
        answer = tokenizer.decode(t.squeeze(0).tolist())
        for letter in answer:
            letter = letter.upper()
            # stop as soon as a letter appears
            if letter in "ABCD":
                pred = letter
                break
        if pred:
            break
    return pred
```

然后，我们可以用上面代码块中的函数检查生成的字母，如下：

```
pred1 = predict_choice(model, tokenizer, prompt_fmt)
print(
    f"Generated letter: {pred1}\n"
    f"Correct? {pred1 == example['answer']}"
)
```

结果是：

```
Generated letter: C
Correct? False
```

可以看到，在这个例子中生成的答案是错误的（`False`）。

假设各题的正确答案在各选项上分布均匀，一个随机猜测者（以均等概率选择 A、B、C 或 D）预期能达到 25% 的准确率。所以基座模型和推理模型的表现都不太好。

> #### **多项选择的答案格式**
>
> 注意，为了便于说明，本节实现的是多项选择评估的简化版本，即把模型预测的答案字母直接与正确答案比较。在实践中，还有一些使用更广泛的变体，比如对数概率打分：我们衡量模型认为每个候选答案有多大可能，而不仅仅检查最后选的字母。（我们会在第 4 章讨论基于概率的打分。）对于推理模型，评估还可以包括：在把正确答案作为输入提供时，评估模型生成该正确答案的可能性。
>
> [图 5：其他 MMLU 打分方法的介绍与代码见 GitHub（https://github.com/rasbt/reasoning-from-scratch/tree/main/chF/02_mmlu）]
>
> 不过，无论我们使用哪种 MMLU 打分变体，评估本质上仍是在检查模型是否从预先给定的答案选项中做出了正确选择。

**像 MMLU 这样的多项选择基准有一个局限：它们只衡量大模型从预定义选项中做选择的能力，因此除了检查模型相比基座模型是否遗忘了知识、遗忘了多少之外，对评估推理能力并没有太大用处。** 它也无法反映自由写作能力或现实中的实用性。

尽管如此，多项选择基准仍是简单而有用的诊断手段：例如，MMLU 分数高并不一定意味着模型在实际使用中很强，但分数低则可以揭示潜在的知识缺口。

# 方法 2：使用验证器检查答案

与上一节讨论的多项选择问答相关，基于验证的方法也通过准确率指标来量化大模型的能力。不过与多项选择基准不同，验证方法允许大模型给出自由形式的答案。然后我们提取出相关的答案部分，并用一个所谓的验证器（verifier）把这部分答案与数据集中提供的正确答案进行比较，如下图 6 所示。

[图 6：在自由形式问答中用基于验证的方法评估大模型。模型生成一个自由形式的回答（可能包含多个步骤）以及一个用方框标出的最终答案，提取该答案并与数据集中的正确答案比较。]

如上图所示，在把提取出的答案与给定答案比较时，我们可以借助外部工具，比如代码解释器或类似计算器的工具/软件。

缺点是，这种方法只能应用于那些容易（并且最好是可以确定性地）验证的领域，比如数学和代码。此外，这种方法可能引入额外的复杂性和依赖，而且可能把一部分评估负担从模型本身转移到外部工具上。

不过，由于它允许我们以编程方式生成无限多的数学题变体，并能受益于逐步推理，它已经成为推理模型评估和开发的基石。

# 方法 3：通过偏好和排行榜比较模型

到目前为止，我们介绍了两种能提供易于量化指标（如模型准确率）的方法。然而，上述方法都没有以更整体的方式评估大模型，包括评判回答的风格。本节如下图 8 所示，我们讨论一种基于判断的方法，即大模型排行榜。

[图 8：本书所涵盖主题的心智模型，重点是本附录介绍的基于判断和基于基准的评估方法。上一节已经介绍了基于基准的方法（多项选择、验证器），现在我们介绍衡量大模型性能的基于判断的方法，本小节聚焦于排行榜。]

这里介绍的排行榜方法是一种基于判断的方法，模型的排名不是依据准确率或其他固定的基准分数，而是依据用户（或其他大模型）对其输出的偏好。

一个流行的排行榜是 LM Arena（https://lmarena.ai/，原名 Chatbot Arena），用户在这里比较两个由用户选定或匿名的模型给出的回答，并投票选出自己更喜欢的那个，如图 9 所示。

[图 9：基于判断的排行榜界面示例（LM Arena）。两个大模型收到相同的提示词，它们的回答并排显示，用户投票选出更喜欢的答案。]

如上图所示收集到的这些偏好投票，随后会在所有用户之间汇总成一个排行榜，按用户偏好对不同模型进行排名。下面的图 10 是 LM Arena 排行榜的当前快照（访问于 2025 年 10 月 3 日）。

[图 10：LM Arena 排行榜截图，展示了基于用户在文本任务上的偏好、当前领先的大模型]

本节剩下的部分，我们将实现一个简单的排行榜示例。

举一个具体的例子：设想用户在类似图 9 的设置中向不同的大模型提问。下面的列表代表成对投票，其中第一个模型是胜者：

#### 代码块 4：构建排行榜

```
votes = [
    ("GPT-5", "Claude-3"),
    ("GPT-5", "Llama-4"),
    ("Claude-3", "Llama-3"),
    ("Llama-4", "Llama-3"),
    ("Claude-3", "Llama-3"),
    ("GPT-5", "Llama-3"),
]
```

在上面的列表中，votes 列表里的每个元组代表两个模型之间的一次成对偏好，写作 `(winner, loser)`（胜者，败者）。因此，`("GPT-5", "Claude-3")` 表示某个用户在 GPT-5 和 Claude-3 的回答中更喜欢 GPT-5 的。

本节剩下的部分，我们将把 `votes` 列表变成一个排行榜。为此，我们会使用流行的 Elo 等级分系统（https://en.wikipedia.org/wiki/Elo_rating_system），它最初是为国际象棋棋手排名而开发的。

在看具体代码实现之前，先简单说一下它的工作原理。每个模型从一个基准分数开始。然后，在每次比较和偏好投票之后，更新该模型的评分。（在 Elo 中，更新幅度取决于结果有多出人意料。）

具体来说，如果用户在当前模型和一个排名很高的模型之间更喜欢当前模型，当前模型就会获得相对较大的分数更新，在排行榜上排得更高。反之，如果它赢的是一个排名很低的对手，更新幅度就较小。（如果当前模型输了，也以类似方式更新，只是分数被扣除而非增加。）

把这些成对排名转换成排行榜的代码如下面的代码块所示。

```
def elo_ratings(vote_pairs, k_factor=32,
                initial_rating=1000):
    # Initialize all models with the same base rating
    ratings = {
        model: initial_rating
        for pair in vote_pairs
        for model in pair
    }

    # Update ratings after each match
    for winner, loser in vote_pairs:

        # Expected score for the current winner
        expected_winner = 1.0 / (
            1.0 + 10 ** (
                (ratings[loser] - ratings[winner])
                / 400.0
            )
        )

        # k_factor determines sensitivity of updates
        ratings[winner] = (
            ratings[winner]
            + k_factor * (1 - expected_winner)
        )
        ratings[loser] = (
            ratings[loser]
            + k_factor * (0 - (1 - expected_winner))
        )

    return ratings
```

上面定义的 `elo_ratings` 函数以投票作为输入，并把它转换成一个排行榜，如下：

```
ratings = elo_ratings(votes, k_factor=32, initial_rating=1000)
for model in sorted(ratings, key=ratings.get, reverse=True):
    print(f"{model:8s} : {ratings[model]:.1f}")
```

这会得到下面的排行榜排名，分数越高越好：

```
GPT-5 : 1043.7
Claude-3 : 1015.2
Llama-4 : 1000.7
Llama-3 : 940.4
```

那么，这是怎么运作的呢？对于每一对，我们用以下公式计算胜者的预期得分：

`expected_winner = 1 / (1 + 10 ** ((rating_loser - rating_winner) / 400))`

这个 `expected_winner` 值是在不允许平局的设定下，基于当前评分预测的该模型获胜概率。它决定了评分更新的幅度。

首先，每个模型都从 `initial_rating = 1000` 开始。如果两个评分（胜者和败者）相等，就有 `expected_winner = 0.5`，表示势均力敌。这种情况下，更新为：

```
rating_winner + k_factor * (1 - 0.5) = rating_winner + 16

rating_loser + k_factor * (0 - (1 - 0.5)) = rating_loser - 16
```

现在，如果一个大热门（评分很高的模型）获胜，就有 `expected_winner ≈ 1`。热门方只会获得很少的分数，败者也只会损失一点：

```
rating_winner + 32 * (1 - 0.99) = rating_winner + 0.32

rating_loser + 32 * (0 - (1 - 0.99)) = rating_loser - 0.32
```

然而，如果一个冷门（评分很低的模型）获胜，就有 `expected_winner ≈ 0`，胜者几乎获得完整的 `k_factor` 分数，而败者损失大致相同的幅度：

```
rating_winner + 32 * (1 - 0.01) = rating_winner + 31.68

rating_loser + 32 * (0 - (1 - 0.01)) = rating_loser - 31.68
```

> #### **顺序很重要**
>
> Elo 方法在每场比赛（模型比较）之后更新评分，所以后面的结果建立在已经更新过的评分之上。这意味着同一组结果，如果以不同顺序呈现，最终得分可能会略有不同。这种影响通常很轻微，但尤其在爆冷发生在早期还是晚期时，就可能出现差别。
>
> 为了减少这种顺序效应，我们可以把投票对打乱顺序，多次运行 `elo_ratings` 函数，然后对评分取平均。

像上面这样的排行榜方法，比静态的基准分数提供了对模型质量更动态的视角。然而，结果可能受到用户群体构成、提示词选择和投票偏差的影响。基准和排行榜也可能被刷分操纵，用户也可能依据风格而非正确性来选择回答。最后，与自动化的基准测试框架相比，排行榜无法对新开发的变体提供即时反馈，这使得它们在模型的活跃开发阶段更难使用。

> #### **其他排名方法**
>
> LM Arena 最初使用本节介绍的 Elo 方法，但最近转向了一种基于 Bradley–Terry 模型的统计方法。Bradley-Terry 模型的主要优点是它有统计学基础，因此可以构建置信区间来表达排名中的不确定性。此外，与 Elo 评分不同，Bradley-Terry 模型通过对整个数据集进行统计拟合来联合估计所有评分，因此不受顺序效应的影响。
>
> 为了让报告的分数保持在大家熟悉的范围内，Bradley-Terry 模型的拟合会产生与 Elo 可比的数值。尽管排行榜已不再正式使用 Elo 评分，"Elo"这个词仍被大模型研究者和从业者在比较模型时广泛使用。展示 Elo 评分的代码示例可以在 GitHub 上找到（https://github.com/rasbt/reasoning-from-scratch/tree/main/chF/03_leaderboards）。
>
> [图 11：Elo 与 Bradley-Terry 排名的比较；源代码见 GitHub（https://github.com/rasbt/reasoning-from-scratch/tree/main/chF/03_leaderboards）。]

# 方法 4：用其他大模型评判回答

在早期，大模型是用统计和启发式方法来评估的，包括一个叫 BLEU 的指标，它粗略地衡量生成文本与参考文本的匹配程度。这类指标的问题在于，它们要求词语完全匹配，没有考虑同义词、词形变化等等。

如果我们想把书面回答作为一个整体来评判，解决这个问题的一个办法就是使用上一节讨论的相对排名和基于排行榜的方法。然而，排行榜的一个缺点是基于偏好的比较具有主观性，因为它涉及人类反馈（以及收集这些反馈所带来的种种挑战）。

一个相关的方法是使用另一个大模型，配合预先定义的评分细则（rubric，即评估指南），把某个大模型的回答与参考回答进行比较，并依据预定义的细则评判回答质量，如图 12 所示。

[图 12：大模型裁判评估示例。待评估的模型生成一个答案，然后由另一个独立的裁判大模型依据评分细则和提供的参考答案为其打分。]

在实践中，当裁判大模型足够强时，图 12 所示的基于裁判的方法效果很好。常见的设置是通过 API 使用领先的专有大模型（例如 GPT-5 API），不过也有专门的裁判模型。（例如，众多例子之一是 Phudge（https://arxiv.org/abs/2405.08029）；说到底，这些专门模型大多只是经过微调、打分行为与专有 GPT 模型相似的较小模型。）

裁判之所以效果这么好，原因之一还在于评估一个答案往往比生成一个答案更容易。

要用 Python 以编程方式实现图 12 所示的基于裁判的模型评估，我们可以在 PyTorch 中加载一个更大的 Qwen3 模型，用评分细则和我们想要评估的模型答案去提示它。

或者，我们也可以通过 API 使用其他大模型，例如 ChatGPT 或 Ollama 的 API。

由于我们已经知道如何在 PyTorch 中加载 Qwen3 模型，为了更有意思一些，本节剩下的部分将用 Python 调用 Ollama API 来实现图 12 所示的基于裁判的评估。

具体来说，我们将使用 OpenAI 的 200 亿参数开放权重模型 gpt-oss，因为它在能力和效率之间取得了很好的平衡。关于 gpt-oss 的更多信息，请参阅我的文章《从 GPT-2 到 gpt-oss：分析架构上的进步》（From GPT-2 to gpt-oss: Analyzing the Architectural Advances）。

#### 代码块 6：查询本地 Ollama 模型

在本文剩下的部分，我们将用 Python 通过 Ollama REST API 与运行在本机上的 gpt-oss 模型交互。下面的 `query_model` 函数演示了如何使用这个 API：

```
import json
import urllib.request

def query_model(
    prompt,
    model="gpt-oss:20b",
    # If you used 
    # OLLAMA_HOST=127.0.0.1:11435 ollama serve
    # update the address below
    url="http://localhost:11434/api/chat"
):
    # Create the data payload as a dictionary:
    data = {
        "model": model,
        "messages": [
            {"role": "user", "content": prompt}
        ],
        # Settings required for deterministic responses:
        "options": {
            "seed": 123,
            "temperature": 0,
            "num_ctx": 2048
        }
    }

    # Convert the dictionary to JSON and encode it to bytes
    payload = json.dumps(data).encode("utf-8")

    # Create a POST request and add headers
    request = urllib.request.Request(  
        url,
        data=payload,
        method="POST"
    )
    request.add_header("Content-Type", "application/json")

    response_data = ""

    # Send the request and capture the streaming response
    with urllib.request.urlopen(request) as response:
        while True:
            line = response.readline().decode("utf-8")
            if not line:
                break
            # Parse each line into JSON
            response_json = json.loads(line)
            response_data += response_json["message"]["content"]

    return response_data
```

下面是如何使用我们刚刚实现的 `query_model` 函数的示例：

```
ollama_model = "gpt-oss:20b"
result = query_model("What is 1+2?", ollama_model)
print(result)
```

得到的回答是"3"。（由于默认设置不同，它与我们运行 Ollama run 或使用 Ollama 应用时得到的结果有所不同。）

借助 `query_model` 函数，我们可以用一个包含评分细则的提示词来评估我们的模型生成的回答：让 gpt-oss 模型以一个正确答案作为参考，在 1 到 5 分的范围内为目标模型的回答打分。

#### 代码块 7：设置包含评分细则的提示词模板

我们为此使用的提示词如下所示：

```
def rubric_prompt(instruction, reference_answer, model_answer):
    rubric = (
        "You are a fair judge assistant. You will be "
        "given an instruction, a reference answer, and "
        "a candidate answer to evaluate, according to "
        "the following rubric:\n\n"
        "1: The response fails to address the "
        "instruction, providing irrelevant, incorrect, "
        "or excessively verbose content.\n"
        "2: The response partially addresses the "
        "instruction but contains major errors, "
        "omissions, or irrelevant details.\n"
        "3: The response addresses the instruction to "
        "some degree but is incomplete, partially "
        "correct, or unclear in places.\n"
        "4: The response mostly adheres to the "
        "instruction, with only minor errors, "
        "omissions, or lack of clarity.\n"
        "5: The response fully adheres to the "
        "instruction, providing a clear, accurate, and "
        "relevant answer in a concise and efficient "
        "manner.\n\n"
        "Now here is the instruction, the reference "
        "answer, and the response.\n"
    )

    prompt = (
        f"{rubric}\n"
        f"Instruction:\n{instruction}\n\n"
        f"Reference Answer:\n{reference_answer}\n\n"
        f"Answer:\n{model_answer}\n\n"
        f"Evaluation: "
    )
    return prompt
```

`rubric_prompt` 中的 `model_answer` 在实践中代表我们自己的模型生成的回答。为了便于说明，这里我们硬编码了一个合理的模型答案，而不是动态生成它。（不过，你也完全可以用本文开头加载的 Qwen3 模型来生成一个真实的 `model_answer`。）

```

> #### **用过程奖励模型为中间推理步骤打分**
>
> 与符号验证器和大模型裁判相关，还有一类学习得到的模型，称为过程奖励模型（process reward models，PRM）。和裁判一样，PRM 可以评估推理过程，而不只是最终答案；但与通用裁判不同，它们专门关注推理的中间步骤。而与通过符号方式检查正确性、通常只在结果层面检查的验证器不同，PRM 在强化学习训练过程中提供逐步的奖励信号。我们可以把 PRM 归类为"步骤级裁判"，它们主要是为训练而开发的，而不是纯粹用于评估。（在实践中，PRM 很难大规模可靠地训练。例如，DeepSeek R1 就没有采用 PRM，而是在推理训练中结合使用了验证器。）

与基于偏好的排行榜相比，基于裁判的评估具有可扩展性和一致性等优势，因为它们不依赖大量的人类投票者。（从技术上讲，也可以把排行榜背后基于偏好的评分外包给大模型裁判。）然而，大模型裁判也和人类投票者有类似的弱点：结果可能受到模型偏好、提示词设计和回答风格的影响而产生偏差。此外，它们高度依赖裁判模型和评分细则的选择，也缺乏固定基准那样的可复现性。

# 结论

本文介绍了四种不同的评估方法：多项选择、验证器、排行榜和大模型裁判。

我知道这是一篇很长的文章，但希望它能帮你对大模型是如何被评估的有一个整体的了解。像这样从零开始的方式可能有些冗长，但它是理解这些方法底层如何运作的好办法，而这反过来又能帮助我们发现其中的弱点和改进空间。

话虽如此，你可能在想："评估大模型的最佳方法是什么？"遗憾的是，并没有单一的最佳方法，因为正如我们所看到的，每种方法都有不同的取舍。简而言之：

**多项选择**
(+) 大规模运行相对快速且便宜
(+) 标准化，在不同论文（或模型卡）之间可复现
(-) 衡量的是基本的知识回忆
(-) 不能反映大模型在现实世界中的使用方式

**验证器**
(+) 对有标准答案的领域提供标准化、客观的评分
(+) 允许自由形式的答案（对最终答案格式有一些限制）
(+) 如果使用过程验证器或过程奖励模型，也可以为中间步骤打分
(-) 需要可验证的领域（例如数学或代码），而且构建好的验证器可能很棘手
(-) 只看结果的验证器只评估最终答案，不评估推理质量

**竞技场式排行榜（人类成对偏好）**
(+) 在真实提示词上直接回答"人们更喜欢哪个模型？"
(+) 允许自由形式的答案，并隐式地考虑了风格、有用性和安全性
(-) 对人类来说昂贵且耗时
(-) 衡量的不是正确性，只是偏好
(-) 投票人群不断变化，可能影响稳定性

**大模型裁判（LLM-as-a-judge）**
(+) 可扩展到许多任务
(+) 允许自由形式的答案
(-) 依赖裁判的能力（用多个裁判组成集成可以让它更稳健）
(-) 依赖评分细则的选择

虽然我通常不太喜欢雷达图，但在这里用一张来可视化这些不同的评估维度会有帮助，如下所示。

[图 15：一张雷达图，从概念上说明在评估大模型时，理想情况下我们要关注不同的维度，以识别其优势和弱点。]

例如，多项选择评分高说明模型有扎实的通用知识。再加上验证器得分高，这个模型很可能也能正确回答技术问题。然而，如果模型在大模型裁判和排行榜评估中表现不佳，它可能难以有效地写出或表达回答，或许可以通过一些 RLHF 来改善。

所以，最好的评估是结合多个维度的。但理想情况下，它还应使用与你的目标或业务问题直接相关的数据。例如，假设你正在部署一个大模型来协助处理法律或与法律相关的任务。在 MMLU 这样的标准基准上运行一下模型作为快速的合理性检查是有意义的，但最终你会希望针对目标领域（比如法律）定制评估。你可以在网上找到一些可以作为良好起点的公开基准，但到头来，你还是会想用自己的专有数据来测试。只有这样，你才能比较有把握地确定模型在训练期间没有见过测试数据。

无论如何，模型评估都是一个非常大、非常重要的话题。我希望本文有助于解释这些主要方法是如何运作的，也希望下次你查看模型评估结果或自己动手评估时，能从中获得一些有用的启发。
