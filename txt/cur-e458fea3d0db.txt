Dan Abramov 2019 年在 Overreacted 上发表的这篇长文，不讲怎么用 React 构建界面，而是把 React 当作一种"编程运行时"，从第一性原理出发解释它的编程模型。他明确说这不是入门文章，面向的是有经验的程序员和其他 UI 库的作者；很多人不了解这些也能把 React 用好。

文章从"宿主树"讲起。React 程序输出的是一棵随时间变化的树，可以是 DOM、iOS 视图层级、PDF 图元乃至 JSON 对象，这些都属于 React 之外的宿主环境，各有自己的命令式 API，树上的节点叫宿主实例。React 押注两条原则：稳定性（大多数更新不会彻底改变结构）和规律性（UI 可拆成按钮、列表、头像这类一致的模式）。所以它适合写 Twitter 客户端，却不适合 3D 管道屏保。渲染器负责教 React 与具体宿主环境对话，React DOM、React Native、Ink 都是渲染器；它们大多工作在可变模式，也可以工作在克隆父树、替换顶层的持久模式（React Fabric 借此方便多线程）。

React 中最小的单元是 React 元素：一个描述宿主实例的普通 JS 对象，轻量、不可变、没有持久身份，像电影里的一帧。入口 ReactDOM.render 的意思是"让容器这棵宿主树与我的元素树一致"。再次调用时，React 不会推倒重建（那样慢，还会丢失焦点、选区、滚动位置），而是做"协调"：树中同一位置的元素类型前后对得上就复用宿主实例、只更新属性，对不上就销毁重建，并对子树递归应用同一规则。

条件渲染之所以通常不出问题，是因为组件里写成 {message} 时，未显示的消息会占一个 null 空位，输入框始终是第二个子节点，位置不变，状态也就不会丢。动态列表则不同：重新排序后类型全一样，React 只会逐项更新内容，导致输入框内容与商品错位，这就是 React 要求给数组元素加 key 的原因。key 让 React 在同一父元素内跨位置识别"同一个"条目；取值标准是"顺序变了你仍认为它是同一项"的东西，比如商品 ID。

组件是返回元素的函数，props 相当于具名参数。React 假设组件对 props 是纯的，不应修改 props，但渲染中新建对象的局部修改、无害的惰性初始化都可以；对 React 来说幂等比严格的纯粹性更重要，只是不能有用户直接可见的副作用。组件的惯用用法不是直接调用 Form()，而是写成 <Form />，即 type 为函数的元素，由 React 去调用并递归下钻，直到只剩宿主元素。作者称这是控制反转，好处有四：React 能给组件附加与树中身份绑定的局部状态；组件类型参与协调，从 <Feed> 切到 <Profile> 时内部状态整体丢弃；React 可以推迟协调、在组件调用之间让出主线程；开发者工具能识别组件。另一个好处是惰性求值：把 <Comments /> 作为 children 传给 Page，如果 Page 因用户未登录提前返回，Comments 根本不会被调用，既省了白做的工作，也让代码更不脆弱。

状态方面，React 把宿主实例那种"随位置保留、概念变化时销毁"的局部状态也提供给你的组件，这类能力叫 Hooks，例如 useState 返回当前值和更新函数。为保证一致性，React 把工作分成可中断、将来可异步的渲染阶段，和始终同步、一次性操作宿主树的提交阶段，避免用户看到更新到一半的界面。父组件 setState 时，默认会协调整棵子树，对中小规模的树不成问题；树太大时可以用 React.memo 在 props 浅比较相等时跳过，或用 useMemo 做表达式级缓存。React 不默认做记忆化，因为很多组件每次的 props 都不同。

作者特别解释了 React 为何不采用细粒度"响应式"订阅：建立监听要遍历模型，会拖慢可交互时间；多数交互要么很小要么是整页切换，细粒度订阅都浪费内存。React 直接处理从网络拿到的原始数据，渲染开销是 O(视图大小) 而非 O(模型大小)，还能用窗口化缩小视图。股票行情这种处处同时变化的场景可能不是 React 的强项；而渲染一棵全新的深层树、等待数据这类问题，响应式系统也解决不了，React 打算用并发渲染来解决。

批处理：同一事件中子组件和父组件都 setState 时，若立即渲染，子组件会白渲一次，所以 React 先跑完所有事件处理函数再统一重渲。副作用是连调三次 setCount(count + 1) 只会加 1，需要改用更新函数 setCount(c => c + 1)；逻辑更复杂时建议用 useReducer，给每种更新起名。

作者用"调用树"作比喻：普通运行时的栈帧函数返回即消失，而 UI 树必须保持存活，React 组件的帧（即源码里的 Fiber）在退出后仍保存局部状态和宿主实例引用，只在协调规则要求时才销毁。Context 则像组件的动态作用域，useContext 会找树中最近的 Provider，找不到就用 createContext 的默认值。Effect 用来做管理焦点、订阅数据源等必要的副作用，默认在浏览器绘制后执行，首次展示和每次更新后都会运行，可返回清理函数。依赖数组能跳过重复执行，但常是过早优化：写成 [] 时闭包里的 handleChange 永远停在首次渲染，count 恒为 0；依赖数组必须包含所有会变化的东西，包括函数，可配合 useCallback，或干脆接受重新订阅，addEventListener 本来就很快。Hooks 可组合成自定义 Hook，例如 useWindowWidth，共享的是逻辑而不是状态。

最后讲 Hooks 为什么必须在组件顶层无条件调用：如果把 useState 想象成一种"use"语法，放进条件、回调或组件外部都说不通，正如 import 只能在模块顶层；它并不是真的语法，但规则可用 lint 插件强制。内部实现上，Hooks 是挂在 Fiber 上的链表，每次调用移动指针，可以简化理解成按调用顺序索引的数组，这和协调靠位置"对上"元素是同一个思路。作者坦言多遍渲染、错误处理的 Hooks 版本、并发模式和 Suspense 尚无定论，并认为大多数人无需思考这些也能走得很远，正说明 React 默认行为和 key 警告之类的设计是成功的。
