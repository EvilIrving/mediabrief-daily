为什么 JavaScript 工具链这么烂

JavaScript 工具实在太难用了，而这不是你的错。

如果你点开这个标题是准备点头赞同的，那你就是问题的一部分。别担心，我也是。我自己就在做 JavaScript 工具，而且我认为我的工具还能好很多。所谓"你们中间谁是没有罪的"，就是这个意思。

如果你是带着怒气点进来、准备对我来一场"史诗级驳斥"的，也别担心，我也并不百分之百认同标题的前提。但你大概能在自己的经历里找到工具确实烂的例子。作为 JavaScript 开发者，我们花大量时间学习如何修补和掩盖工具的问题，却很少问为什么。（这是理性的行为，本文其余部分会提出一些原因。）

如果你是带着开放心态点进来的，你大概并不存在，不过还是欢迎。

以下是一些假设，而不是客观事实。我是在尝试解释，而不是辩护。我所有的博客文章都隐含"仅代表我当前观点"的声明，我也一直在寻求改变想法（哪天我会把这写进"使用条款"，因为有些人不理解个人博客及其认知状态背后的社会契约）。另外，JS 工具链也有巨大的好处，本文没有涉及。

## JavaScript 本来不是为此而生的

JavaScript 工具链烂，是因为 JavaScript 在设计时并没有考虑到关键业务级的工具和应用。

众所周知，JS 是在 10 天内创造出来的。那时几乎没人预见到软件会吞噬世界，接着浏览器软件会吞噬操作系统软件，然后 JavaScript 又会走出浏览器、进入操作系统。

JS 的文化在很大程度上源自它最初的设计决定。容易上手为许多程序员打开了大门，但随之而来的是所有缺陷，一直到访问未定义属性不会引发运行时错误，从而导致著名的"`undefined` is not a function"错误。我之所以认为这种"原罪"有文化上的分量，是因为社区对为 JavaScript 增加编译期检查存在巨大的、有时带着道德色彩的抵触。甚至还有人拒绝使用 Prettier。

WebAssembly 也许有一天能让不想用 JavaScript 的人摆脱 JavaScript，但在那之前，他们只能和我们一起困在这里。

这就引出了……

## 庞大的社区

JavaScript 工具链烂，是因为它不是只为你一个人做的。

作为地球上除电子表格之外最大的编程语言，从代码风格到软件交付再到测试方法，样样都注定会出现近乎宗教式的分裂。其中一个核心工具甚至就叫 Babel（巴别）！（考虑到它所指涉的那个故事，这在多个层面上都讽刺得妙。）

庞大的社区通常是好事，但人们也会忘记它的坏处。当"让所有人满意"真的意味着让"所有人"满意时，这与"把一件事做好"是截然不同、有时甚至相互冲突的命题。

让人满意最简单的办法就是加一个又一个配置项，我们也正是这么做的。然而这条路通向配置地狱，而且依然无助于工具之间的互操作。我欣赏 Jared Palmer 的做法：关注组合，关注 80% 的常见用例。更多人也应该试试 `patch-package` 这样的工具，以低成本维护分叉。

（视频）Dan Abramov 讲述了 JavaScript 这个"大熔炉"是如何形成的（也可以看演讲版），以及出路在于更少的配置、更多的工具包。

庞大的社区是好事，直到它导致……

## 移动的靶子，移动的球门

JavaScript 工具链烂，是因为它不是为单一目标运行时而做的。

我们对 JS 库是否应该同时在浏览器和 Node 中运行没有共识。

我们对 JS 工具是否应该转译它们自己的依赖没有共识。

我们对如何处理老旧浏览器没有共识。随着时间推移这会越来越不是问题，但我们现在仍深陷其中。Create React App 关于差异化分发（differential serving）的争论已经持续了两年。

我们对如何测试工具——如果它们有测试的话——没有共识。Kent C. Dodds 通过 Testing JavaScript 在这方面做了很多，但我们大量的工具完全没有测试，更别提在 Windows 等不同环境中测试了（抱歉！）。你可以试着争论一下：没有工具，和有一个没测试过（但能用！）的工具，哪个更好。

归根结底，我们对工具要解决什么问题都没有共识。一个极端是，初学者问 A 和 B（经常被当作替代品一起提起）有什么区别，维护者却回答 A 和 B 是"正交的"。另一个极端是，A 的专家（非常在意某一件事）冲 B 的专家（在努力做另一件事）大吼。

每当我们刚刚接近对某件事达成共识，球门就移动了，又冒出别的事来争论。比起支持彼此、提醒彼此我们都想要的大目标，我们更愿意在小分歧上互相拆台，结果导致倦怠。

这就引出了……

## 没有人掌舵

JavaScript 工具链烂，是因为它是自下而上的，而不是自上而下的。

JavaScript 不只是一门语言，但却没有"JavaScript SDK"或"标准库"。

TC39 管理语言本身（它有缺陷——我找不到出处，但我记得有人评论说，整体性的语言设计不应该按逐个特性、每年排期的方式来进行），但没有人掌管工具链。npm 曾经有机会，但现在没人希望它再掌管任何别的东西。Node 极其成功，但深陷原罪，以至于它的创造者现在在做一个替代品。在"大教堂与集市"的光谱上，JavaScript 把集市模式拥抱到了极致（它也并不孤单，Python 也类似，尽管 Anaconda 让它多了一点大教堂的味道）。

是的，我们每隔一段时间就会有一个新的前端框架（不是每天，也不是每月，别再装糊涂了，连看都不看就拿别人的劳动成果开玩笑，一点也不好笑）。是的，我们有三四个各干各事的打包工具。是的，我们有没人用的文件格式（暂时？）。是的，我们每月把三行代码的包下载 9300 万次。

这极其浪费、重复、不安全、令人疲惫，而且难学。

我们知道。但这也是确保我们在把想法永久固化进某个人人都必须使用的庞然大物之前，先充分试验和检验它们的最好方式。如果某个工具变坏了，总有另一个在候场。如果替代品明显更好，现有的那个起初会无视它，但最终会努力追赶，也可能追不上。

我并不是说 JavaScript 是一个真正的、信息完全的精英体制。"为工作选择合适的工具"是一句推脱——我们绝大多数人既没有时间、也没有承受风险的余地，去尝试别人都在用的之外的东西。

这实际上意味着我们根本懒得去检查自己用的是不是合适的工具，而且也没法检查，因为我们的工具又用了成千上万个工具……

## 我们"无法"对自己的工具负起责任

JavaScript 工具链烂，是因为它是层层叠叠的脆弱抽象。

我要打破本文到目前为止的写作风格，讲一件最近发生的事。我之所以能这么做，是因为没有编辑在旁边对我啧啧摇头。不过如果你看不下去了，请告诉我。

默认情况下，所有 `npm install` 都会以脱字符（`^`）来指定包版本，它会匹配包的次版本和补丁版本，前提是假定这些包遵守语义化版本（semver）。然而，semver 只是一种社会契约——简单来说，只要有用户依赖某个 bug，那么修复这个 bug 就是破坏性变更，所以 semver 依赖于"bug"的定义，而这个定义在技术上就是"软件没有按照我们以为自己想要的方式工作"。更重要的是，semver 在发布时没有任何实质性的强制，所以下载时也无法依赖它。然而我们默认使用脱字符时，恰恰就是在依赖它。

`event-stream` 事件发生了，一个包被下架了，尽管它还在注册表上登记着，于是所有 JS 工具以及基于这些工具构建的应用都开始失败。包管理的安全问题超出了我的能力范围，但它之所以造成如此大的影响，是因为一个字符：`^`。

那天我所有持续部署的 JavaScript 构建都挂了，因为 `flatmap-stream` 依赖于 `event-stream`，而它又在 `fsevents` 里，而每个人都依赖 `fsevents`，所以 Vue、React、Angular，可能还有所有其他人都挂了。一个号称竞争激烈、庞大而多样的生态系统，怎么会有单点故障？我有点慌，但知道怎么修。我能想象很多初学者那天被劝退了。我也能想象有些人（比如我）正要向别人演示自己的软件，第一次尝试就撞上这个问题，立刻给人留下了坏印象，好像是我的错。

这既有点是我的错，又有点不是。npm 可以通过把默认安装改为锁定版本来解决我上面的情况（据说 Go 生态就是这样做的），但这并没有解决问题真正的根源——我不知道自己在用什么。那天是我第一次听说 `flatmap-stream`。

接下来我要说点"异端"的话了。按理说我应该告诉你这是我的错。那就意味着，如果你也遇到过，那也是你的错。我最初给这一节取的标题是"我们'不'对自己的工具负责"。

我改主意了。

很多知名开发者喜欢说你应该像对待自己的代码那样对待 `node_modules`，但这听起来就是不对，而且好像在说这是你的错。要一路向下掌控自己的整个依赖链几乎是不可能的（Begin 的 Brian 是我能想到的一个例外）。托马斯·杨（Thomas Young）是"最后一个无所不知的人"，而他在 1829 年就去世了。

Rich Harris——那位以捅马蜂窝为乐的人——也指出过小模块方式的缺陷。他尤其抨击了可发现性和软件完整性："每个人都有办法让人更容易在干草堆里找到针，却没有人去问，这么多干草当初为什么会在这儿。"他基本上被无视了——你怎么让一个无比庞大的社区停下脚步呢？

即便你是模范开发者，你也不是一座孤岛。你会和不是模范开发者、不掌控自己工具的人一起工作。因此，从统计上说，你迟早会开始使用自己都不知道在用的工具。我把这称为"桥本引理"，出自 Mitchell Hashimoto 关于"为什么要多云"的一次回答。

基本上，如果我们整个工具链/生产力策略都依赖于掌控每一个依赖才能可靠，那我们大概应该探索别的思路了。（说清楚：我没有思路。只是在把想法说出来。）

## 我们把工具的制造者当成工具

JavaScript 工具链烂，是因为我们不制造工具，也不把制造工具的人当人看。

你不必什么都懂，但这并不意味着可以不关心你所用工具背后的制造者。而这是个真实的问题，而且是一种流行病。

也许感觉不到，但如果你花大量时间制作 JavaScript 工具，你很可能是个极端的异类。下载量不会说谎。TypeScript 有 412 名贡献者，webpack 有 547 名，Babel 有 757 名，React 有 1331 名。所有这些工具的用户数都比贡献者多至少三个数量级。而且你知道，即便在贡献者内部也存在幂律分布，其中大多数人只是修了错别字和文档（这一点也不坏！）。

如果你是一个普通的"JavaScript 简"或"TypeScript 汤姆"，你不做工具。你甚至不知道、也不在乎你用的工具的维护者是谁。你在一家财富 500 强公司工作，或者在一家挣扎的初创公司，或者在一家光鲜的数字代理公司，或者你正处在两份工作之间、试图转行，而你只想要大家都想要的东西：让东西显示在屏幕上！

这种不对称意味着，当工具的使用者与制造者互动时，存在巨大的"他者感"。而由于相对的知识差距，再加上普遍的支持善意，往往是工具的制造者不得不竭尽全力帮助用户诊断问题，甚至帮他们填写基本的 bug 报告。

这个问题比糟糕的 bug 报告还要普遍得多。JavaScript 教育者靠教人使用工具赚数百万，而工具制造者却在 Patreon 和 GitHub 上乞讨几美元。工程经理和 CTO 赚好几百万，却"超然于这一切之上"，沉迷于漂亮的图表。如果你也曾像他们一样，对工具采取"观望"态度，而不是亲自上手、检查并帮忙，那你就和我一样，是问题的一部分。工具，尤其是刚起步的工具，不会自己变好。它们需要你，才能变得更好。

更糟的是，这一切都有理性的解释。把一堆不是你做的东西组装起来、作为一个整体打包出售，确实有价值。在某些技术选择上更谨慎，也确实是明智的。但看在老天的份上，别停止尝试新东西、别停止回馈。也永远别因为把工具制造者当工具而沾沾自喜。

更初级的工程师做工具、而资深工程师往往退后一步思考更宏观的问题，这已经是普遍现象。但我希望我们能更好地传承知识。说"想当年我们才知道怎么正确地做软件！现在的孩子根本不会写代码！"太轻率了（这通常会引向对训练营和学位的门槛设置）。指望资深人士"不"超越工具层面去思考是不现实的，因为软件生产和管理远不止工具。但我希望我们能有更好的方式来传承和交流经验教训，而不是在社交媒体上冷嘲热讽。

（视频）Jonathan Blow 的《防止文明崩溃》，以及随后 Rich Harris 等人的讨论。

当然，没有人会因为我写了这篇文章就改变行为，于是工具制造者只好说……去你的，给钱。

## 资金

JavaScript 工具链烂，是因为我们仍在学习如何做出优秀的自由开源软件。

我把最大的问题留到了最后。JavaScript 有 97% 是开源的，所以开源的问题就是 JavaScript 的问题。

（旁注）顺便说一句，97% 到 99% 是任何与公地有关的事物中反复出现的有趣数字。它对应着内容消费者与创作者的比例。也对应着我们与黑猩猩共享的 DNA 比例。

开源维护的问题已有大量记载。为开源争取资金的失败尝试多得数不清。（说清楚：其中很多本来就是馊主意。）在最近的一次尝试之后，Feross 总结道："开源维护者就是一个没有任何上行收益的创业公司创始人。"这非常真实，尽管偶尔也有开源维护者最终围绕自己的工作创办了公司。

我不喜欢的方案：

- 广告商业模式（放在文档里和我的控制台里）
- 在 Patreon 上乞讨
- 在 GitHub 上乞讨
- 任何由开发者自掏腰包、而不是由其雇主（如适用）出钱的资助形式
- 像 Gitcoin 这样的悬赏系统

我喜欢的方案：

- 培训（比如 React Training）
- 托管服务（Laravel Forge、Meteor Galaxy）
- 我强烈推荐 Joseph Jacks 关于"开放核心"（Open Core）和开源商业模式的思考。不过要注意，所有这些都是以越来越少的开放协作和开放软件，来换取更多的钱。

撇开对开放商业模式经济学的冥想不谈，指望外在动机胜过内在动机是一个糟糕的赌注。但我们忍不住，我们对它上瘾了。丹尼尔·平克（Dan Pink）的《驱动力》（Drive）说得最好。

在基本需求得到满足这一重要前提下，我从根本上同意 DHH 的观点：内在动机是创造可持续开源的最佳方式。你选择的开源商业模式也许能让你在财务上成功，但如果你是被外部激励驱动的，那么到了某个时候，外部激励会让你做出与解决你最初想解决的问题无关的选择和妥协。

（视频）帮自己一个忙，去看或读一下 DHH 在 RailsConf 2019 上的主题演讲《超越市场的开源》，你就会明白。

## 并不是全都烂

JavaScript 工具链并不全都烂，而且比我们过去拥有的好得多！

我想留给你一些积极的东西，好表明我不是不分青红皂白地把一切都骂一遍。如今我们的工具收获了大量喜爱。仅在 2018 年的 State of JavaScript 调查中，你就能看到 Jest、Express、GraphQL 几乎受到一致喜爱；我找不到相关提及，但我很确定 Yarn 和 Prettier 也在其中。

在最近一次 State of JavaScript 调查中，所有的观点类问题都呈现更正面的趋势。你自己判断吧。

针对我前面提出的各个观点，逐一反驳：

- 设计：JavaScript 这门语言在 ES6 之后变得严肃和好用多了，所以它是在边走边设计的。TypeScript 的接受度也发展得不错，在 npm 用户中达到了 63%（并不是说它能解决一切问题，但比我们以前的强）。
- 社区：我们在建立行为准则方面越来越好，GitHub 推出了 issue 模板和表情回应，促使人们更好地协作。在这些模式有史以来最严酷的压力测试中，我们不断学习更好的组合与抽象模式。
- 移动的靶子：常青浏览器的日益普及有助于提供一个稳定的目标。尽管跨浏览器的不一致仍然需要抽象层，但它们之间的差异比以往任何时候都小，对工具选择的影响也更小。
- 没有人掌舵：这是特性，不是 bug。
- 责任归属：这方面我没有想法。
- 工具制造者：我们确实在传承"一些"知识。Anders Hejlsberg 拥有 35 年的语言和工具开发经验，如今在做 TypeScript，并在培养一代工具工程师。我们也在开发者大会上积极传承知识——看看 Christoph 和 Konstantin 讲的《构建高质量的 JavaScript 工具》，尤其是 Christoph 和团队为拯救 Jest 所做的事。
- 资金：尽管我已经说明了我的保留意见，但有很多帮助解决开源资金问题的举措，它们都是必要的。如果你对此感兴趣，我建议密切关注 GitHub 的 Devon Zuegel，也顺便推荐一下我的朋友 Travis Fischer。
