Nick：我总把它比作游戏循环，不知道这样是更清楚还是更混乱。对我来说更好理解：游戏要不停检查所有东西的状态，然后发出更新，浏览器做的也差不多。

Rick：没错。有要做的工作，有要进行的更新。有时候没有工作、也没有更新，浏览器线程空闲时事件循环只是空转，什么也不做。但迟早会有东西进来，比如一个定时器脚本突然冒出来，被加入任务队列，必须执行，于是在事件循环的下一圈就能发现这项工作并执行它。

Rick：这样理解事件循环很有帮助。比如你听说过"双重 RAF"，也就是连续两次 requestAnimationFrame——为什么要两次？一次不行吗？我是看了 Jake 的讲解才恍然大悟：requestAnimationFrame 实际是在布局和绘制工作之前执行的，让循环转两圈，就能确保更新发生在你预期的时机。所以这是理解浏览器和主线程的一个很有用的模型。

Annie：回到事件循环像游戏循环这个概念。游戏有帧率，而我们常常忘了网页其实也有帧率。东西在动的时候，网页就在产生帧。比如这段视频，每一帧网页都在产生一帧；有动画时产生帧；你和页面交互时也会产生帧——按钮高亮了、菜单弹出来了，那就是一帧。

Annie："帧"这个词有多重含义，比如 iframe，但这里说的是动画帧，就是持续播放的那种帧。而长动画帧就是耗时太久、超过用户期望的那一帧。

Amal：就是超过了被认为合理的阈值——是 60……？我一下忘了具体指标。

Annie：每秒 60 帧对应每帧 16.6 毫秒。不同场景下"长帧"的阈值可以不同。对单次用户交互的响应，我们所有的指导都说应该在 100 毫秒以内。所以如果用户在那一帧里点击了，那么超过 100 毫秒就算长帧。

Annie：如果你在玩游戏，那就只有 16.6 毫秒。但电影的帧率更低，所以期望值会有些弹性。如果是游戏、电影或动画，你需要稳定的帧率：稳定跑在每秒 20 帧，也比跑 60 帧但时不时大卡一下要好。

Amal：对，这非常有道理。

Annie：而长动画帧就是一种告诉你"嘿，动画帧太长的时候发生了什么"的方式。

Amal：明白了，谢谢。下一个是计算机科学和浏览器里另一个多义词：响应性（responsiveness）。

Rick：这个我来。

Amal：好。值得一提的是，响应性在不同语境下含义很多，我们或许应该聚焦在今天这个语境下它的意思。

Rick：没错。我们说的不是响应式网页设计，也就是调整浏览器窗口大小时内容会流畅地自适应。这里的响应性是指：用户在页面上做了某个操作，浏览器需要多久响应这个输入。你可以把交互——按键、点击、在触屏上轻触——看作用户想在页面上做点什么，他们期望几乎立刻有反应。Annie 提到过，100 毫秒通常是我们参考的阈值。

Rick：所以我们希望从用户操作到他得到任何视觉反馈——也就是下一帧绘制出来——之间的工作量尽可能少、发生得尽可能快。理想情况是 100 毫秒以内，不过后面会讲到，我们用来衡量这件事的指标实际上把 200 毫秒及以下作为响应性的达标线。

Amal：有道理。这其实是我设的一个小陷阱题，因为今天我们会频繁用到"响应性"这个词，我想确保大家知道我们具体指什么。谢谢 Rick。最后一个要先定义的是"交互"。什么是交互？

Annie：回到前面说的，动画帧的时限要求取决于用户在做什么。用户交互最基本的含义就是与页面的交互。在 INP 以及 Chrome 性能 API 的语境下，我们把它定义为"离散交互"：在触屏上轻触、用鼠标点击，或者按下键盘。

Annie：我的团队在给"交互"下正式定义时意识到，这里其实有两个用户动作：你按下按键，然后抬起手指。所以我们统计交互时非常小心，不会因为我抬手指抬得慢而惩罚网页。这里有些复杂性，但总体来说就是轻触、点击或按键。我们不包括滚动这类连续交互，因为它们测量起来复杂得多，网页也更难对其采取措施——我们有 GPU 加速滚动，很多滚动并不受网页控制，Chrome 在底层替你处理了。

Amal：哇，太酷了。我之前就好奇为什么滚动被排除在外，感觉那是卡顿（jank）非常多的地方，谢谢你解释。好，接下来从宏观层面聊 Core Web Vitals，细节稍后再展开。你们谁能为从没听说过它的人大致定义一下什么是 Core Web Vitals？以及为什么这个概念在 2020 年出现？

Rick：Annie，我来讲它是什么，你来讲背景？你可以把 Core Web Vitals 看作 Web 的健康指标。"vital"这个词会让人联想到量脉搏之类的画面。我们希望用户获得的网页和 Web 体验是良好、健康的。具体来说，我们关注的性能指标有三个：加载性能，用 LCP（Largest Contentful Paint，最大内容绘制）衡量；交互响应性，如果你是在 2024 年 3 月或之后看到这期节目，那就是 INP，而从 Core Web Vitals 推出以来一直用的是 FID（First Input Delay，首次输入延迟）；第三个是布局稳定性，用 CLS（Cumulative Layout Shift，累积布局偏移）衡量。Annie，你来讲讲我们是怎么走到 Core Web Vitals 这一步的？

Annie：好。我做 Web 性能已经很久了。在负责 Core Web Vitals 之前，我负责 Chrome 的性能测试和工具。我的团队和 Chrome 很多其他团队一直在努力寻找最接近用户体验真实情况的指标。历史上，页面的 onload 事件就被当作页面加载时间，它的正式定义大概是所有资源加载完成、DOM 解析完毕等等。结果发现它不一定和用户看到的东西相关。于是有了各种更接近的尝试：DOMContentLoaded 更接近一点，但仍然是一个不以用户为基础的形式化定义；Speed Index 非常好，但没法在真实用户环境（field）中测量；First Paint 其实相关性还不错；First Contentful Paint 相关性更好；Largest Contentful Paint 更好……但你听到这里大概会想："哇，东西也太多了吧。"对吧？我们把这些东西都抛出来，其他人也在提出他们的想法，这很好，但如果你想深入了解 Web 性能、搞清楚什么重要，你会发现我们真正想做的事——让页面加载更快——完全被"大约有七百万种测量方法"这个事实淹没了。所以我们做 Core Web Vitals，真正想做的是回到原点、把问题摆到最前面：我们要衡量的用户体验到底是什么？并且真正以用户为中心，最好是在真实用户环境中测量。

Annie：你在本地用自己的手机或电脑看，作为开发者我们的设备通常都不错，一切看起来都很好；或者没有包含生产环境的所有第三方内容，所以看起来也很好。因此我们希望聚焦真实用户体验中的关键时刻，这就是我们决定推出 Core Web Vitals 计划的原因。

Nick：我很好奇，一想到这个，我脑子里立刻冒出来的就是 DevTools 里的 Lighthouse，但我觉得不是它。作为开发者，到底怎么跟这些东西打交道？

Rick：你是说开发者用来测量 Core Web Vitals 的工具？

Nick：嗯。

Rick：对。Annie 提到了真实用户数据（field data），意思是收集访问你网站的真实用户的数据，看他们的体验是如何分布的。因为没有哪个单一数字能描述完整而多样的体验谱系，所以我们用百分位数，比如说 INP 的第 75 百分位是某个毫秒数，但这其实意味着有 25% 的用户比这更慢。开发者调试用户体验时会在本地测试，可能用 Lighthouse，或者用 Google 的服务比如 PageSpeed Insights，它底层也是跑 Lighthouse。我更倾向于把这些工具理解为"我知道我的网站慢，怎么让它更快？"Lighthouse 会给你可操作的建议，说"这些是我们发现的优化机会"。但让人困惑的是它还有一个 Lighthouse 分数，开发者特别爱把分数游戏化，想拿最高分，在 Lighthouse 里拿 100 分就像通关。而这个分数来自 Lighthouse 底层的各项性能指标，比如 Speed Index 分数、Total Blocking Time（总阻塞时间）分数等等，这些加权合成一个总的 Lighthouse 性能分。我觉得一部分困惑在于分数变绿之后，人们觉得活干完了，但其实你只是解决了 Lighthouse 在当前测试配置下能在页面上找到的所有问题。

Rick：也许你只是加载了页面，完全没跟它交互，那就发现不了 INP 问题；你没往下滚动，如果滚了，也许会看到首屏以下的内容加载进来时产生的各种布局偏移。所以真实用户数据才如此重要：看用户实际在做什么、他们如何受这些性能问题影响——这些问题几乎是潜伏着的，如果你自己没想到去测，工具可能也不会暴露出来。

Amal：Rick，这些观点非常好。性能测量既是艺术也是科学，真的是一门独立的学问。你基本上得把自己当成真实用户，确保测试了所有场景，认真考虑设备、延迟等等，还有那台硬件上同时在发生什么……因素太多了。Annie，也非常感谢你带我们回顾那段历史——"嘿，判断'这只火鸡熟了没'有那么多方法，可以在这儿测一下、那儿测一下，哪里才是正确的位置？"很高兴我们最终落在了这三项，现在是四项指标上。

Nick：这些年它是怎么演变的？LCP 似乎一直很稳定，CLS 也是，FID 看起来是要退场、让位给 INP 的那个。那从 2020 年以来都发生了哪些变化？

Annie：就测量哪些指标而言，主要的变化差不多就是这些。我们尽量保持一致。我们发现，告诉开发者的变化越少，他们就越能专注于真正重要的事，所以我们尽量不做大的改动。

Annie：我们非常努力地在不做大改的前提下，倾听开发者的反馈并帮助他们落实。所以大多数时候我们收到反馈后是在改进工具、提升可调试性。但有时候——比如 Core Web Vitals 刚发布后，我们收到很多做服务端渲染的框架的反馈：如果同一个 LCP 元素被完全相同地渲染了两次，我们计的是第二次而不是第一次。我们当时想："啊？为什么要这样做？"他们说："服务端渲染很重要啊"，还有水合（hydration）……这对性能非常重要，如果你们希望大家这么做，指标就必须体现出来——

Nick：计的是第二次？

Annie：第一次才是用户真正看到内容的时候。用户看到了内容，之后对用户来说什么都没变。所以那是非常好的反馈。我们做这类改动时，会在 Chrome 的真实流量上跑在线实验，看"到底有多少网站的分数会变化"。那次改动影响的网站远不到 1%，但对那些想做这项特定性能优化的人来说，让指标正确处理这种情况非常重要。所以我们做的很多改动、随时间推移的调整，都是这种很小、很细微、只影响一小部分流量，但对开发者真的很重要的事情。

Amal：有道理。那你们团队有没有遇到过这种情况：纸面上数字都很好看，各项指标都很棒，但应用实际表现还是很差？

Annie：我觉得不完全有。当然，一个应用可能本身就不好——整体性能和用户体验数字都很好，但内容有误导性、是垃圾内容，这类问题依然会出现。我们之所以用三个指标而不是一个，是因为它们能互相制衡。如果你想通过到处随机塞东西来刷 LCP，CLS 就会变差；如果你想通过冻结 UI 来刷，那 FID 或 INP 就会变差。Rick，你怎么看？

Annie：Core Web Vitals 的设计初衷是提供一条基线，主要面向 Web 内容。如果你在读新闻或者资讯文章，它们非常合适。难以泛泛地用某个指标衡量用户体验的，是那种长时间运行的应用。比如一个录播客的 Web 应用，我们大概会关心帧率，而那不在 Core Web Vitals 里，所以这类应用应该监控额外的指标。

Annie：但我能看到很多宏观数据，很多人说"我的应用是长时间使用的，加载时间不重要，因为用户会在里面待很久"，而当我实际去看人们在应用里花了多少时间，比你猜的要少得多。所以如果你有一个应用，并且认为 Core Web Vitals 跟你无关，那就认真监控一下：人们在里面花多少时间？发生多少次页面加载？好好做个全面梳理。另外，我们团队做的是 Core Web Vitals 和 Web 性能 API。用 JavaScript 测 Core Web Vitals 会有点难，因为我们提供的是更底层的 API：我们给你每一次交互的信息，而不只是最慢的那一次；我们给你大量不同绘制的信息。之所以这样做，是因为万一你的应用是个聊天应用，用户要打好几个小时的字呢？你大概会想要大量指标来了解体验如何，把按键和轻触、点击区分开……

Annie：所以如果 Core Web Vitals 不合适，理想情况下你的应用相当硬核，在做自己的性能指标，但你依然可以使用 Core Web Vitals 底层的这些 API。

Amal：那我们深入聊聊这些指标，先重点说 INP，因为它比较新。INP 是 Interaction to Next Paint 的缩写，未来几周就会正式成为新的 Core Web Vital。我们是在 2024 年 2 月 28 日录制的。那么，INP 是什么？

Rick：我来。INP 就是你说的 Interaction to Next Paint，它是三项指标里负责响应性的那个。最好的理解方式是：页面处理用户输入有多快。它考察页面整个生命周期内发生的所有交互，取大约最慢的那一次。所以如果用户有一次非常糟糕、很慢的交互体验，你大致可以把 INP 理解为那段时间。判断好坏的阈值是：200 毫秒及以下为良好，超过 500 毫秒就是很差的体验，介于两者之间的归为"需要改进"。

Rick：当然没人规定你不能在更尾部再划一档——比如超过一秒就是非常非常差，我有时觉得这样划分很有帮助。我之所以说"大约最慢"，是因为它对交互很多的应用内置了一些容差，比如那些不停打字的聊天应用：每 50 次交互里最慢的那一次实际上会被忽略，相当于一次"宽限交互"。也许那只是偶然，通常不会那样；也许在成百上千次交互里，用户早就忘了那次慢的。所以我们不会死盯着绝对最慢的那一次，有一定的内置容差。

Amal：那什么算好成绩？具体来说，像"我在 Dropbox 上传一个文件，可能要 10 分钟"这种交互，和用户点了按钮却毫无反应这种情况，权重怎么算？

Annie：好成绩是 200 毫秒。接着就会有人问："既然一次交互应该在 100 毫秒内完成，为什么 200 毫秒就算好？"原因有几个。一是低端手机、很差的网络这类情况下，设备可能根本无法在 100 毫秒内响应。二是有多次交互：如果用户交互很多，我们取的不是最差的，而是几乎最差的。如果几乎最差的那次是 200 毫秒，那么大多数交互都在 100 毫秒以下。这就是 200 算好成绩的原因。

Annie：那耗时非常长的交互呢？这就涉及 INP 到底在测什么，答案就在名字里：我点击、轻触或按键，然后下一次绘制、下一个动画帧出现，我得到某种即时响应。想象一下：你按下按钮，按钮显示为按下状态，这是按下时的响应；然后你松开，它显示激活状态。INP 很差的情况下，我们真的见过点一下按钮，四秒后才出现激活状态的。而用户体验研究说人们在 100 毫秒内想要的，并不是他们尝试的任何操作都在 100 毫秒内完成，而是得到某种反馈，表明电脑正在处理。他们期望这种反馈非常快。这就是 INP 测量的东西。

Annie：那如果确实有很耗时的操作呢？比如上传文件、向服务器发请求……你应该给用户显示反馈，并保持主线程空闲，让用户知道网站在处理期间并没有卡死。

Amal：嗯。

Nick：所以它其实和你实际在做什么无关。

Annie：对。

Nick：更像是：如果我点了按钮，立刻显示一个加载动画，就满足要求了。

Annie：对。

Nick：然后我实际要执行的操作——比如我可以做节流，等着看有没有别的输入进来，节流两秒都行，只要我向用户表示了"有事情发生了"，就仍然是安全的。

Annie：对。很多人还问我："那如果我把所有事都延迟、永远不响应用户交互呢？"问题在于，假设你真的有两秒钟连续的 JavaScript，而且没做节流，用户就会再点一次。然后第二次交互会被冻结，等着第一次完成，所以你在 INP 上依然会被扣分。别那么做。真正把任务拆开，这样你才能显示一个真正在转动的加载动画。

Amal：明白。那能不能给我们讲讲为什么它比 FID（首次输入延迟）更好？看起来它是要取代 FID，这个理解对吗？

Annie：对。为什么 INP 要取代 FID？我们刚启动 Core Web Vitals 计划时，首先更关注移动端，原本只打算做移动端，后来因为非常成功才扩展到桌面端。另外当时 Web 上的交互性要差得多，所以我们只想设一条基线。推出时只有大约 80% 的网站能达到那条基线。而 FID 只看第一次交互，只测量主线程空闲到浏览器开始处理你的交互所需的时间，要求这在合理时间内发生。

Annie：Core Web Vitals 推出后发生了几件很棒的事。我们扩展到了桌面端；同时，开发者大规模地解决了很多 FID 过慢的问题。我认为各个框架确实改变了水合方式，让它可以被用户输入打断，这解决了很大比例的 FID 问题。另外在 Chrome 这边——还记得你应该加 meta viewport 标签吗？那样会禁用双击缩放。我们发现有些情况下开发者没加这个标签，但我们依然可以不做双击缩放，于是修复了那个问题。这两个问题解决后，加载期间的大部分交互性问题、也就是输入之前的延迟，都解决了。我们其实没想到会这么快，也没想到需要解决的问题这么少。但我们觉得 Web 上的交互性依然存在大问题：如果你看 INP 的原始数值，无论移动端还是桌面端，每 100 个页面就有 1 个在你点击后要冻结超过整整一秒才看到下一帧。所以我们认为还有很多工作要做，这就是为什么我们决定推出这个新指标，让开发者了解这些问题。

Nick：我还有个问题，只是想给自己理清楚：假设我的网站有一个持续播放的超棒下雪动画，INP 会被它搞糊涂吗？因为它一直在持续更新。

Annie：这个问题很有意思，背后有挺深的 Chrome 技术背景。作为 Chrome 性能团队，尤其是我们的图形团队，一直在研究"Chrome 怎样能做得更好"。过去几年我们做的很多事情就是告诉大家："你应该用 CSS 动画，或者用合成器动画（composited animation）。"基本上，无论主线程上发生什么，合成器都能让那场雪照常下。错误的做法是用 JavaScript 代码一点点移动雪花、更新 DOM。如果用错误的方式，当有用户输入、并且处理需要 100 毫秒时，这额外的 100 毫秒会叠加到你的动画上，对吧？

Nick：对。

Annie：同样，如果你的动画需要 5 毫秒，它会把交互的响应延长到大约 105 毫秒。所以如果你用错误的方式做，我们会把它计入。但如果你用正确的方式——这也是这个指标开发了很久的原因——有用户交互时，我们在 Chrome 里会看什么发生了变化，我们称之为"DOM 是否有损伤（damage）"，也就是你的交互是否导致需要一次绘制？然后我们追踪是哪一次绘制，把交互和正确的那次绘制关联起来。所以你没法靠合成器动画来加快 INP，但如果你的动画做得好、用了合成器，就不会在 INP 上受到任何惩罚。

Nick：好，明白了。

Amal：Nick，我现在脑子里笑得不行……不过这个问题太棒了。我想 INP 的其他好处大概还有：它不局限于首次加载，而 FID 是局限于首次加载的，对吧？用 FID 在首次加载之后基本测不到什么。但用户的会话更长时，会随时间展开各种交互，我感觉 INP 能以更有意义的方式捕捉到其中一些。

Annie：对。虽然我之前说过你的会话没你想的那么长，但也确实相当长。平均而言——

Amal：Annie，别再伤人心了，别再说大实话了。每个人都有这种幻想："我的用户在我的应用上花好几个小时，一连好几个小时，那是他们每天做的第一件事。"

Annie：用户 90% 的时间是在页面加载完成之后度过的。也就是说，10% 的时间花在加载页面上，90% 的时间在加载之后。所以他们确实会花时间，捕捉他们使用页面期间发生的事情很重要。

Amal：对，有道理。那 Rick，INP 有哪些常见的坑？

Rick：其实就是任何拖慢交互的东西。要么是事件处理函数本身——用户点击时你有一个点击处理函数，它要跑多久？要么即使你的点击处理函数是瞬间完成的，它仍可能卡在"输入延迟"这个阶段，因为你的主线程正忙着做别的事。所以我把它看成两类问题："是你的交互本身慢？还是它恰好撞上了别的正在进行的事情？"

Rick：我最近把它比作一条路上有坑洼：路面质量会拖慢行程、让体验变差，但如果你的车本身就破破烂烂，也会让体验变慢变差。技术上说，会产生影响的因素之一是非常庞大的 DOM。如果你的 JavaScript 里有 querySelector，需要遍历 DOM，或者要改动 DOM 里大量的东西，那耗时就和其中元素的数量相关。所以如果你的网页非常大……我最常用来测试这个问题的就是 HTML 规范本身，因为它巨大无比，测这个页面你会碰上能想象到的所有性能瓶颈。

Rick：另一个就是 JavaScript 实在太多了。应用运行需要 JavaScript 没关系，但最好从这个角度想："什么需要立即发生？哪些工作可以推迟？"也就是渲染网页初始视图需要什么。比如设置分析统计，也许只需要一个非常轻量的东西，把需要回传日志的交互批量攒起来；任何不影响用户界面本身的事情大概都可以晚点做。这也引出了一些优化技巧，就是给你想在主线程上做的工作设置优先级。这样你就可以告诉浏览器："先做这个再做那个。这个非常关键，因为它影响用户界面，需要尽快完成"，而另一些则是"这只是可以在后台做的事，你什么时候有空做都行。"

Rick：我并不是想把 JavaScript 贬低成 Web 性能的万恶之源，它对于打造丰富的体验非常重要。关键只是负责任地使用它，别让页面塞满太多 JavaScript。因为光是下载、解析和执行就有它自己的性能成本和影响，甚至在你执行它之前，编译时间本身就可能让你栽跟头。

Rick：所以真正要做的就是用心，去追踪（trace）你的页面，看看主线程上实际发生了什么，从而理解它。不这么做，你就只是在猜、凭感觉。比如"我点了一下，快吗？不知道，我觉得挺快的……"每个人都有自己的理解。所以好的做法是使用客观的度量，用 Chrome DevTools 性能面板的追踪功能客观地看问题，从而真正弄清底层发生了什么。

Nick：这就是你说的优先级吗？并没有某个内置的东西让我能说"这个不重要，你不忙的时候再跑"，而更多是看清什么真正重要，然后用你自己的方式确保它先完成、相对不重要的东西被优先处理？

Rick：开发者确实可以做一些事来表达"从我的应用代码这个点开始，之后发生的一切大概都可以等一等，不必现在做，我更希望先往屏幕上绘制一帧给用户看。"于是你可以在代码里加一个让出点（yield point）。简单如零毫秒的 setTimeout，就是一种隐式地把控制权让回主线程的方式。但你也可以做更声明式的事情，比如用 Scheduler API 里的 postTask API 来说明"我接下来要做的工作是超高优先级的关键工作"。你传进去的参数可以设置不同的优先级，让浏览器清楚这项工作相对于其他事情应有的优先级。即使是你没有明确标为低优先级的东西，它也会和其他工作穿插进行，比如定时器触发后要做的工作。

Nick：我从来没看过 Scheduler API，太有意思了。

Amal：对，这是个挺酷的底层 API。Rick，你解释得太好了。有没有类似 Workbox 那样的东西，提供好用的高层抽象，让开发者能更声明式地把这些加到现有的 Web 应用、框架、库里？因为对我来说，这是我们缺失的一环，尤其是在我们开发应用的思维方式上。

Rick：有一些边缘情况：如果用户在图片加载时就和页面交互了，这对 Chrome 或其他 LCP 实现来说是一个信号，表明用户觉得页面已经足够可用，所以在那之后我们不会再看其他 LCP 候选。这就是为什么看真实用户数据或真实用户指标真的很重要：你能看到有一定比例的时间 h1 是你的 LCP 元素，另一部分时间是图片。你还能发现非常有意思的用户行为模式，比如如果有人通过深层链接到达你的页面，你可能就需要优先加载页面更下方的图片。我们常见的一种模式是图片懒加载，经验法则是"首屏以下的东西全部懒加载"。但在这些边缘情况下，有时首屏以下的图片恰恰是需要立即加载的。所以拥有分析数据、知道 LCP 的常见成因或者具体元素是什么，非常有帮助。

Annie：是 Cumulative Layout Shift，累积布局偏移。倒着讲，"布局偏移"是这里的基本单位，指的是页面布局过程中内容出现的意外移动。我们有一个 API，每次内容发生偏移都会单独上报，上报的值大致是相对于视口的一个比例。基本上，你半个屏幕都移动了，那就是很糟糕的偏移，0.5；而一点点像素级的偏移可能是 0.1。"累积"的意思是我们把这些偏移加起来，因为它们往往成堆出现，形成非常让人不适的模式。

Annie：最初，CLS 是在整个页面生命周期内求和。但正如我们之前说的，有些页面的生命周期非常长，我们都有过把会议页面开着一个多小时的经历，这对长时间存在的页面不公平。所以我们重新调整了算法。我们做了大量用户体验研究（UXR），看这些意外偏移什么时候对人们来说最糟糕，结论是出现一大波集中爆发的时候。它可能发生在较短或较长的时间段内，但通常不超过五秒。要么是我正往下滚动浏览一篇新闻，砰，突然冒出一个大广告；要么是我在加载页面；或者是单页应用的页面切换，做了一大堆奇怪的变化。

Rick：要好好回答这个问题，我得先讲宏观，再讲微观。在宏观层面，更快的 Web 对每个人都有好处，生态里的所有参与者都会从更健康的 Web 中受益。具体到某个网站，网站更快，转化就更多。这是说服那些关心、或者暂时还不关心 Web 性能的人投入其中的一个非常有效的方法，我们有大量案例研究可以引用。我们之前好像还没提过 WPO Stats 这个网站，它是个很好的去处，可以发给那些还在犹豫的人，说服他们 Web 性能确实能带来更多用户参与和转化。而这正是我们所有人在 Web 上做生意的原因，无论是什么生意——我这里的"生意"是广义的，即使是精心打造的个人博客之类的，我们也只是在相互分享内容。所以性能是用户体验的指标之一，我们希望人们能以尽可能顺畅的方式消费我们的内容。

Rick：这也可能涉及其他方面，比如页面的设计、可访问性如何。在某种意义上，性能就是一种可访问性，因为当东西慢到让人望而却步时，用户就无法访问它。所以在微观层面，我们是在努力为每一位访问网站的用户提供尽可能好的体验。我们会尽力而为。要让网站 100% 的时间都很快是非常难的，这就是为什么我们用第 75 百分位。我们会尽最大努力，如果能做到 P90、P100，甚至 P99 当然很好，但我认为我们只需要让每一种可能的用户体验都尽可能快。说实话，不测量我们就无从知道。所以我们需要测量这些用户体验，然后互相分享最佳实践。

Rick：如果你有一个成功的案例，讲你如何让网站变快，以及因此看到的所有业务指标变快——抱歉，不是变快，是变好——就把它分享给社区，因为那是非常有价值的信息，也能说服其他人。然后在这种病毒式的效应下，会有越来越多的人关心性能，不仅理解它为什么重要，还知道怎样改进。所以我能给的最好建议就是：分享你的知识，分享你的经验。
