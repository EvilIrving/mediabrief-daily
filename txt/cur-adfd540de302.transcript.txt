# 智能体（Agents）

在许多人看来，智能体是人工智能的终极目标。Stuart Russell 和 Peter Norvig 的经典著作《人工智能：一种现代方法》（Prentice Hall，1995）把人工智能研究领域定义为"*对理性智能体的研究与设计*"。

基础模型前所未有的能力，打开了过去无法想象的智能体应用的大门。这些新能力终于让我们有可能开发出自主的智能体，充当我们的助手、同事和教练。它们可以帮我们建网站、收集数据、规划行程、做市场调研、管理客户账户、自动录入数据、帮我们准备面试、面试我们的候选人、谈判交易等等。可能性似乎无穷无尽，这些智能体的潜在经济价值也极为巨大。

本节先概述智能体，然后讨论决定智能体能力的两个方面：工具和规划。智能体有新的运作方式，也就有新的失败方式。本节最后讨论如何评估智能体，以发现这些失败。

*本文改编自 **《AI Engineering》**（2025）中的 **Agents** 一节，略作修改，使其成为一篇独立的文章。*

1. AI 驱动的智能体是一个新兴领域，还没有公认的理论框架来定义、开发和评估它们。本节尽力从现有文献中搭建一个框架，但它会随着这个领域的发展而演变。与书中其他部分相比，本节更具实验性。我从早期审阅者那里得到了有益的反馈，也希望能得到这篇博文读者的反馈。

## 智能体概述

"智能体"（agent）一词已经在许多不同的工程语境中使用，包括但不限于软件代理、智能体、用户代理、对话代理和强化学习智能体。那么，智能体到底是什么？

智能体是任何能够感知其环境并对该环境采取行动的东西。《人工智能：一种现代方法》（1995）把智能体定义为：任何可以被视为通过传感器感知环境、并通过执行器作用于环境的事物。

这意味着，一个智能体由它所处的*环境*和它能执行的*动作集合*来刻画。

智能体能在什么环境中运作，由它的用例决定。如果开发一个智能体来玩游戏（例如 *Minecraft*、围棋、*Dota*），那个游戏就是它的环境。如果你想让智能体从互联网上抓取文档，环境就是互联网。自动驾驶汽车智能体的环境是道路系统及其周边区域。

AI 智能体能执行的*动作集合*，会因它能使用的*工具*而得到扩充。你每天接触的许多生成式 AI 应用都是能使用工具的智能体，尽管工具很简单。ChatGPT 就是一个智能体：它能搜索网页、执行 Python 代码、生成图像。RAG 系统也是智能体——文本检索器、图像检索器和 SQL 执行器就是它们的工具。

智能体的环境和它的工具集之间有很强的依赖关系。环境决定了智能体可能使用哪些工具。例如，如果环境是一盘国际象棋，智能体唯一可能的动作就是合法的棋步。然而，智能体的工具清单也限制了它能运作的环境。例如，如果一个机器人唯一的动作是游泳，它就只能待在水里。

图 6-8 展示了 SWE-agent（Yang 等，2024）的可视化，这是一个构建在 GPT-4 之上的智能体。它的环境是带有终端和文件系统的计算机，动作集合包括浏览代码仓库、搜索文件、查看文件和编辑代码行。

AI 智能体的使命是完成通常由用户给出的任务。在 AI 智能体中，AI 是大脑：它处理任务，规划实现任务的一系列动作，并判断任务是否已经完成。

让我们回到前面 Kitty Vogue 例子中那个处理表格数据的 RAG 系统。这是一个只有三个动作的简单智能体：

- 生成回复，
- 生成 SQL 查询，以及
- 执行 SQL 查询。

给定查询 `"Project the sales revenue for Fruity Fedora over the next three months"`（预测 Fruity Fedora 未来三个月的销售收入），智能体可能执行如下动作序列：

1. 推理如何完成这项任务。它可能判断，要预测未来销量，首先需要过去五年的销售数据。智能体的推理可以以中间回复的形式展示出来。
2. 调用 SQL 查询生成，生成获取过去五年销售数据的查询。
3. 调用 SQL 查询执行，执行这条查询。
4. 对工具输出（SQL 查询执行的结果）进行推理，看它们如何有助于销售预测。它可能判断这些数字不足以做出可靠的预测，也许是因为有缺失值。于是它决定还需要过去营销活动的信息。
5. 调用 SQL 查询生成，生成关于过去营销活动的查询。
6. 调用 SQL 查询执行。
7. 推理认为这些新信息足以帮助预测未来销量，然后生成预测。
8. 推理认为任务已成功完成。

与非智能体用例相比，智能体通常需要更强大的模型，原因有二：

- **错误累积**：智能体往往需要执行多个步骤才能完成任务，而整体准确率会随步骤数增加而下降。如果模型每一步的准确率是 95%，经过 10 步，准确率会降到 60%；经过 100 步，准确率只有 0.6%。
- **风险更高**：有了工具，智能体能执行影响更大的任务，但任何失败都可能带来更严重的后果。

需要很多步骤的任务，运行起来既耗时又费钱。一个常见的抱怨是，智能体只擅长烧掉你的 API 额度。然而，如果智能体能够自主运作，它们就能节省人的时间，让这些成本物有所值。

给定一个环境，智能体在其中能否成功，取决于**它能使用的工具**和**它的 AI 规划器有多强**。我们先来看看模型可以使用的各种工具，接下来再分析 AI 的规划能力。

## 工具

一个系统不需要使用外部工具也能算作智能体。但如果没有外部工具，智能体的能力就会很有限。模型本身通常只能执行一种动作——LLM 能生成文本，图像生成器能生成图像。外部工具让智能体的能力大大增强。

工具既帮助智能体感知环境，也帮助它作用于环境。让智能体感知环境的动作是*只读动作*，而让智能体作用于环境的动作是*写动作*。

智能体能使用的工具集合就是它的工具清单。由于工具清单决定了智能体能做什么，所以要仔细考虑给智能体哪些工具、给多少。工具越多，智能体能力越强。然而工具越多，理解和用好它们也就越难。要找到合适的工具集，必须做实验，后面"**工具选择**"一节会讨论这一点。

根据智能体所处的环境，可能的工具有很多。下面是你可能想考虑的三类工具：知识增强（即上下文构建）、能力扩展，以及让智能体作用于环境的工具。

### 知识增强

希望本书到目前为止已经让你相信，相关上下文对模型的回复质量有多重要。有一类重要的工具，就是帮助增强智能体知识的工具。其中一些前面已经讨论过：文本检索器、图像检索器和 SQL 执行器。其他可能的工具包括内部人员搜索、返回各产品状态的库存 API、Slack 检索、邮件阅读器等。

许多这类工具用你所在组织的私有流程和信息来增强模型。不过，工具也可以让模型获取公开信息，尤其是来自互联网的信息。

网页浏览是最早被整合进 ChatGPT、也最受期待的能力之一。网页浏览能防止模型"过时"。当模型训练所用的数据变得陈旧时，模型就过时了。如果模型的训练数据截止于上周，那么除非在上下文中提供本周的信息，否则它无法回答需要本周信息的问题。没有网页浏览，模型就无法告诉你天气、新闻、近期活动、股价、航班状态等。

我把"网页浏览"作为一个统称，涵盖所有访问互联网的工具，包括网页浏览器，以及搜索 API、新闻 API、GitHub API 或社交媒体 API 等各种 API。

虽然网页浏览让智能体能引用最新信息、生成更好的回复并减少幻觉，但它也可能让智能体暴露在互联网的污水池中。选择互联网 API 时要谨慎。

### 能力扩展

你也可以考虑那些弥补 AI 模型固有局限的工具。它们是提升模型表现的简便方法。例如，AI 模型出了名地不擅长数学。如果你问模型 199,999 除以 292 等于多少，模型很可能会算错。然而，如果模型能用计算器，这个计算就易如反掌。与其试图训练模型擅长算术，不如直接给模型一个工具，这样资源效率高得多。

其他能显著提升模型能力的简单工具包括日历、时区转换器、单位转换器（例如从磅换算成千克），以及能在模型不擅长的语言之间互译的翻译器。

更复杂但更强大的工具是代码解释器。与其训练模型理解代码，不如让它使用代码解释器来执行一段代码、返回结果或分析代码的错误。这种能力让智能体可以充当编程助手、数据分析师，甚至是能写代码跑实验并报告结果的研究助理。然而，自动执行代码伴随着代码注入攻击的风险，第 5 章"防御性提示工程"一节对此有讨论。适当的安全措施对于保护你和你的用户至关重要。

工具可以把纯文本或纯图像模型变成多模态模型。例如，一个只能生成文本的模型，可以把文生图模型当作工具，从而既能生成文本也能生成图像。收到一个文本请求后，智能体的 AI 规划器会决定调用文本生成、图像生成，还是两者都调用。ChatGPT 就是这样既生成文本又生成图像的——它使用 DALL-E 作为图像生成器。

智能体还可以用代码解释器生成图表，用 LaTeX 编译器渲染数学公式，或用浏览器把 HTML 代码渲染成网页。

同样，一个只能处理文本输入的模型，可以用图像描述工具处理图像，用转录工具处理音频，用 OCR（光学字符识别）工具读取 PDF。

*与单纯的提示甚至微调相比，使用工具能显著提升模型的表现*。Chameleon（Lu 等，2023）表明，一个由 GPT-4 驱动、配备 13 种工具的智能体，在多个基准上都能胜过单独的 GPT-4。这个智能体使用的工具包括知识检索、查询生成器、图像描述器、文本检测器和必应搜索。

在科学问答基准 ScienceQA 上，Chameleon 把已发表的最佳少样本结果提高了 11.37%。在涉及表格数学题的基准 TabMWP（Tabular Math Word Problems，Lu 等，2022）上，Chameleon 把准确率提高了 17%。

### 写动作

到目前为止，我们讨论的都是让模型从数据源读取信息的只读动作。但工具也可以执行写动作，对数据源做出更改。SQL 执行器可以检索一张数据表（读），也可以修改或删除这张表（写）。邮件 API 可以读取邮件，也可以回复邮件。银行 API 可以查询你当前的余额，也可以发起转账。

写动作让系统能做更多事。它们可以让你把整个客户拓展流程自动化：调研潜在客户、找到他们的联系方式、起草邮件、发送第一封邮件、阅读回复、跟进、提取订单、用新订单更新数据库等等。

然而，让 AI 拥有自动改变我们生活的能力，这个前景令人恐惧。正如你不应该给实习生删除生产数据库的权限，你也不应该允许一个不可靠的 AI 发起银行转账。对系统能力及其安全措施的信任至关重要。你需要确保系统受到保护，免受那些可能试图操纵它执行有害动作的恶意行为者的攻击。

**旁注：智能体与安全**

每当我向一群人谈起自主 AI 智能体，常常有人提到自动驾驶汽车。"*要是有人黑进汽车把你绑架了怎么办？*"自动驾驶汽车的例子因为其物理性而显得格外直观，但 AI 系统即使不在物理世界中存在，也能造成伤害。它可以操纵股市、窃取版权、侵犯隐私、强化偏见、传播虚假信息和宣传等等，第 5 章"防御性提示工程"一节对此有讨论。

这些担忧都是合理的，任何想要利用 AI 的组织都需要认真对待安全问题。然而，这并不意味着永远不应该赋予 AI 系统在现实世界中行动的能力。既然我们能信任机器把我们送上太空，我希望有一天，安全措施也能足够完善，让我们信任自主 AI 系统。况且，人也会出错。就我个人而言，比起一个普通的陌生人，我更愿意信任一辆自动驾驶汽车载我一程。

正如合适的工具能让人类的生产力大幅提高——你能想象没有 Excel 做生意、没有起重机盖摩天大楼吗？——工具也让模型能完成多得多的任务。许多模型提供商已经在其模型中支持工具使用，这一功能通常被称为函数调用（function calling）。展望未来，我预计大多数模型都会普遍支持调用大量工具的函数调用。

## 规划

基础模型智能体的核心，是负责解决用户所给任务的模型。一项任务由其目标和约束定义。例如，一项任务是规划一次从旧金山到印度的两周旅行，预算 5,000 美元。目标是两周的旅行，约束是预算。

复杂任务需要规划。规划过程的输出是一份计划，即一份列出完成任务所需步骤的路线图。有效的规划通常要求模型理解任务，考虑实现任务的不同方案，并选出最有希望的那个。

如果你参加过任何规划会议，就知道规划很难。作为一个重要的计算问题，规划已被深入研究，要全面讲述需要好几卷书。这里我只能浅尝辄止。

### 规划概述

给定一项任务，有许多可能的解决方式，但并非所有方式都能带来成功的结果。在正确的解法中，有些比另一些更高效。考虑这个查询：`"How many companies without revenue have raised at least $1 billion?"`（有多少家没有收入的公司融资至少 10 亿美元？），以及两种示例解法：

1. 找出所有没有收入的公司，再按融资额筛选。
2. 找出所有融资至少 10 亿美元的公司，再按收入筛选。

第二种方案更高效。没有收入的公司远远多于融资达 10 亿美元的公司。如果只有这两个选项，一个聪明的智能体应该选择方案 2。

你可以在同一个提示中把规划和执行结合起来。例如，你给模型一个提示，让它一步一步思考（比如用思维链提示），然后在同一个提示中执行这些步骤。但如果模型想出了一个 1,000 步的计划，而且根本实现不了目标呢？没有监督的话，智能体可能会把这些步骤跑上好几个小时，在 API 调用上浪费时间和金钱，直到你意识到它毫无进展。

为了避免徒劳的执行，应该把*规划*和*执行*解耦。你让智能体先生成一份计划，只有在计划经过*验证*之后才执行。计划可以用启发式规则来验证。例如，一条简单的启发式规则是剔除包含无效动作的计划。如果生成的计划需要谷歌搜索，而智能体无法使用谷歌搜索，这份计划就是无效的。另一条简单的启发式规则可能是剔除所有超过 X 步的计划。

计划也可以用 AI 评判者来验证。你可以让一个模型评估这份计划是否合理，或者如何改进。

如果生成的计划被评估为不好，你可以让规划器再生成一份。如果计划不错，就执行它。

如果计划中包含外部工具，就会调用函数调用。执行计划得到的输出随后又需要评估。注意，生成的计划不必是覆盖整个任务的端到端计划，也可以是针对某个子任务的小计划。整个过程如图 6-9 所示。

现在你的系统有三个组件：一个生成计划，一个验证计划，还有一个执行计划。如果把每个组件看作一个智能体，这就可以被视为一个多智能体系统。由于大多数智能体工作流都足够复杂，涉及多个组件，所以大多数智能体都是多智能体。

为了加快这个过程，你可以不按顺序生成计划，而是并行生成几份计划，让评估器挑出最有希望的那份。这是又一个延迟与成本的权衡，因为同时生成多份计划会产生额外成本。

规划需要理解任务背后的意图：用户用这个查询想做什么？意图分类器常被用来帮助智能体规划。正如第 5 章"把复杂任务拆分为更简单的子任务"一节所示，意图分类可以用另一个提示完成，也可以用专门为此训练的分类模型完成。意图分类机制可以被看作你的多智能体系统中的又一个智能体。

了解意图能帮助智能体挑选合适的工具。例如，在客户支持场景中，如果查询是关于账单的，智能体可能需要一个检索用户近期付款记录的工具。但如果查询是关于如何重置密码的，智能体可能需要访问文档检索。

**提示**：

有些查询可能超出了智能体的职责范围。意图分类器应该能把这类请求归为 `IRRELEVANT`，这样智能体就能礼貌地拒绝，而不是浪费算力（FLOPs）去想出不可能的解决方案。

到目前为止，我们假设智能体把三个阶段全部自动化：生成计划、验证计划和执行计划。实际上，人可以参与任何一个阶段，协助这个过程并降低风险。

- 人类专家可以提供计划、验证计划，或执行计划的一部分。例如，对于智能体难以生成完整计划的复杂任务，人类专家可以提供一份高层计划，由智能体在此基础上展开。
- 如果计划涉及有风险的操作，比如更新数据库或合并代码变更，系统可以在执行前请求人明确批准，或者交由人来执行这些操作。为此，你需要明确定义智能体在每个动作上可以拥有的自动化程度。

总结一下，解决一项任务通常包括以下过程。注意，反思对智能体来说并非必需，但它会显著提升智能体的表现。

1. *计划生成*：想出完成这项任务的计划。计划是一系列可管理的动作，所以这个过程也被称为任务分解。
2. *反思与纠错*：评估生成的计划。如果是个糟糕的计划，就生成一份新的。
3. *执行*：采取计划中列出的动作。这通常涉及调用特定的函数。
4. *反思与纠错*：收到动作结果后，评估这些结果，判断目标是否已经实现。找出并纠正错误。如果目标没有完成，就生成一份新计划。

你在本书中已经见过一些计划生成和反思的技巧。当你让模型"一步一步思考"时，你是在让它分解任务。当你让模型"验证你的答案是否正确"时，你是在让它反思。

### 基础模型作为规划器

一个悬而未决的问题是，基础模型到底有多擅长规划。许多研究者认为，基础模型——至少是那些构建在自回归语言模型之上的——不会规划。Meta 首席 AI 科学家 Yann LeCun 毫不含糊地声称，自回归 LLM 不会规划（2023）。

自回归 LLM 不会规划

（也不会真正推理）。

"虽然我们自己有限的实验没有显示微调能带来任何显著的［规划能力］提升，但有可能在更多微调数据和更多努力下，经验表现可能会…… https://t.co/rHA5QHi90C

—— Yann LeCun (@ylecun)，2023 年 9 月 13 日

虽然有大量零散证据表明 LLM 是糟糕的规划者，但尚不清楚这是因为我们不知道如何正确使用 LLM，还是因为 LLM 从根本上就不会规划。

**规划的本质是一个搜索问题**。你在通往目标的不同路径中搜索，预测每条路径的结果（奖励），然后选出结果最有希望的路径。很多时候，你可能会判断根本不存在能通往目标的路径。

搜索常常需要*回溯*。例如，设想你处在一个有两个可能动作 A 和 B 的步骤上。采取动作 A 之后，你进入了一个没有希望的状态，于是需要回溯到前一个状态去采取动作 B。

有人认为，自回归模型只能生成向前的动作，无法回溯去生成替代动作。因此他们得出结论：自回归模型不会规划。然而，这并不一定正确。在执行了一条采取动作 A 的路径之后，如果模型判断这条路径说不通，它可以改用动作 B 来修正路径，这实际上就是回溯。模型也总是可以从头开始，选择另一条路径。

LLM 之所以是糟糕的规划者，也可能是因为没有给它们规划所需的工具。要规划，不仅需要知道可用的动作，还需要知道*每个动作可能带来的结果*。举个简单的例子，假设你想爬上一座山。你可能的动作是右转、左转、掉头或直行。然而，如果右转会让你跌下悬崖，你可能就不会考虑这个动作。用技术术语来说，一个动作会把你从一个状态带到另一个状态，必须知道结果状态才能决定是否采取某个动作。

这意味着，像流行的思维链提示技术那样只提示模型生成一串动作序列是不够的。论文《Reasoning with Language Model is Planning with World Model》（Hao 等，2023）认为，LLM 包含了大量关于世界的信息，因此能够预测每个动作的结果。LLM 可以结合这种结果预测来生成连贯的计划。

即使 AI 不会规划，它仍然可以成为规划器的一部分。也许可以给 LLM 配上搜索工具和状态跟踪系统来帮助它规划。

**旁注：基础模型（FM）规划器与强化学习（RL）规划器**

*智能体*是强化学习中的核心概念。维基百科把强化学习定义为一个"*关注智能体应如何在动态环境中采取行动以最大化累积奖励*"的领域。

RL 智能体和 FM 智能体在很多方面相似。它们都由各自的环境和可能的动作来刻画。主要区别在于它们的规划器如何运作。

- 在 RL 智能体中，规划器由 RL 算法训练而成。训练这种 RL 规划器可能需要大量时间和资源。
- 在 FM 智能体中，模型本身就是规划器。可以通过提示或微调这个模型来提升其规划能力，通常所需的时间和资源更少。

然而，没有什么能阻止 FM 智能体引入 RL 算法来提升表现。我猜从长远来看，FM 智能体和 RL 智能体会融合。

### 计划生成

把模型变成计划生成器，最简单的办法是提示工程。设想你想创建一个智能体，帮助顾客了解 Kitty Vogue 的产品。你给这个智能体三个外部工具：按价格检索产品、检索热销产品，以及检索产品信息。下面是一个用于计划生成的提示示例。这个提示仅作演示之用，生产环境中的提示可能更复杂。

**系统提示**：

```
Propose a plan to solve the task. You have access to 5 actions:
* get_today_date()
* fetch_top_products(start_date, end_date, num_products)
* fetch_product_info(product_name)
* generate_query(task_history, tool_output)
* generate_response(query)
The plan must be a sequence of valid actions.
Examples
Task: "Tell me about Fruity Fedora"
Plan: [fetch_product_info, generate_query, generate_response]
Task: "What was the best selling product last week?"
Plan: [fetch_top_products, generate_query, generate_response]
Task: {USER INPUT}
Plan:
```
关于这个例子，有两点需要注意：

- 这里使用的计划格式——一个由函数组成的列表，参数由智能体推断——只是组织智能体控制流的众多方式之一。
- `generate_query` 函数接收任务当前的历史和最近的工具输出，生成一个查询，交给回复生成器。每一步的工具输出都会被加入任务历史。

给定用户输入"上周最畅销产品的价格是多少"，生成的计划可能是这样的：

1. `get_time()`
2. `fetch_top_products()`
3. `fetch_product_info()`
4. `generate_query()`
5. `generate_response()`

你可能会问："那每个函数需要的参数呢？"确切的参数很难提前预测，因为它们往往是从之前的工具输出中提取出来的。如果第一步 `get_time()` 输出"2030-09-13"，智能体就可以推断，下一步应该用如下参数调用：

```
fetch_top_products(
    start_date="2030-09-07",
    end_date="2030-09-13",
    num_products=1
)
```
很多时候，信息不足以确定函数的确切参数值。例如，如果用户问"畅销产品的平均价格是多少？"，以下问题的答案并不明确：

- 用户想看多少个畅销产品？
- 用户想要的是上周、上个月还是有史以来的畅销产品？

这意味着模型经常不得不猜测，而猜测可能出错。

由于动作序列和相应的参数都是由 AI 模型生成的，它们可能是幻觉。幻觉可能导致模型调用一个无效的函数，或者调用了有效的函数但参数错误。一般用于提升模型表现的技巧，都可以用来提升模型的规划能力。

让智能体更擅长规划的**建议**：

- 写一个更好的系统提示，附上更多示例。
- 更好地描述工具及其参数，让模型更好地理解它们。
- 改写函数本身，让它们更简单，比如把一个复杂的函数重构为两个更简单的函数。
- 使用更强的模型。一般来说，更强的模型更擅长规划。
- 针对计划生成微调一个模型。

#### 函数调用

许多模型提供商为其模型提供工具使用功能，实际上把模型变成了智能体。工具就是函数，因此调用工具通常被称为*函数调用*。不同模型的 API 运作方式不同，但大体上函数调用的流程如下：

1. *创建工具清单。* 声明所有你可能希望模型使用的工具。每个工具由其执行入口（例如函数名）、参数和文档（例如函数做什么、需要什么参数）来描述。
2. *指定智能体针对某个查询可以使用哪些工具。*
由于不同查询可能需要不同工具，许多 API 允许你为每个查询指定要使用的已声明工具列表。有些 API 还允许你通过以下设置进一步控制工具使用：
  - `required`：模型必须至少使用一个工具。
  - `none`：模型不应使用任何工具。
  - `auto`：由模型决定使用哪些工具。

图 6-10 演示了函数调用。它用伪代码写成，以便代表多种 API。要使用某个具体的 API，请参阅其文档。

给定一个查询，按图 6-10 定义的智能体会自动生成要使用的工具及其参数。有些函数调用 API 会确保只生成有效的函数，但无法保证参数值正确。

例如，给定用户查询"40 磅是多少千克？"，智能体可能判断它需要工具 `lbs_to_kg_tool`，参数值为 40。智能体的回复可能是这样的：

```
response = ModelResponse(
    finish_reason='tool_calls',
    message=chat.Message(
        content=None,
        role='assistant',
        tool_calls=[
            ToolCall(
                function=Function(
                    arguments='{"lbs":40}',
                    name='lbs_to_kg'),
                type='function')
        ])
)
```
根据这个回复，你可以调用函数 `lbs_to_kg(lbs=40)`，并用它的输出生成给用户的回复。

**建议**：使用智能体时，务必要求系统报告它在每次函数调用中使用了哪些参数值。检查这些值，确保它们正确。

#### 规划粒度

计划是一份列出完成任务所需步骤的路线图。路线图可以有不同的粒度。规划一年时，按季度的计划比按月的计划层级更高，而按月的计划又比按周的计划层级更高。

规划和执行之间存在权衡。详细的计划更难生成，但更容易执行；高层的计划更容易生成，但更难执行。绕开这种权衡的一种方法是分层规划。先用一个规划器生成高层计划，比如按季度的计划；然后针对每个季度，用同一个或另一个规划器生成按月的计划。

到目前为止，所有生成计划的例子都使用确切的函数名，这是非常细的粒度。这种做法的一个问题是，智能体的工具清单可能随时间变化。例如，获取当前日期的函数 `get_time()` 可能被改名为 `get_current_time()`。工具一变，你就需要更新提示和所有示例。使用确切的函数名，也让同一个规划器更难在使用不同工具 API 的不同用例之间复用。

如果你之前基于旧的工具清单微调过一个生成计划的模型，就需要在新的工具清单上再次微调。

为了避免这个问题，计划也可以用更接近自然语言的方式生成，这比领域特定的函数名层级更高。例如，给定查询"上周最畅销产品的价格是多少"，可以指示智能体输出这样的计划：

1. `get current date`（获取当前日期）
2. `retrieve the best-selling product last week`（检索上周最畅销的产品）
3. `retrieve product information`（检索产品信息）
4. `generate query`（生成查询）
5. `generate response`（生成回复）

使用更接近自然语言的方式，能让计划生成器对工具 API 的变化更稳健。如果你的模型主要是用自然语言训练的，它很可能更擅长理解和生成自然语言形式的计划，也更不容易产生幻觉。

这种做法的缺点是，你需要一个翻译器，把每个自然语言动作翻译成可执行的命令。Chameleon（Lu 等，2023）把这个翻译器称为程序生成器。不过，翻译比规划简单得多，可以由较弱的模型完成，产生幻觉的风险也更低。

#### 复杂计划

到目前为止的计划示例都是顺序的：计划中的下一个动作*总是*在上一个动作完成后执行。动作可以被执行的顺序称为*控制流*。顺序形式只是控制流的一种。其他类型的控制流包括并行、if 语句和 for 循环。下面列出了每种控制流的概述，也包括顺序控制流以作对比：

- **顺序**
在任务 A 完成后执行任务 B，可能是因为任务 B 依赖任务 A。例如，SQL 查询只有在从自然语言输入翻译过来之后才能执行。
- **并行**
同时执行任务 A 和 B。例如，给定查询"帮我找 100 美元以下的畅销产品"，智能体可能先检索前 100 个畅销产品，然后针对其中每个产品检索其价格。
- **if 语句**
根据上一步的输出执行任务 B 或任务 C。例如，智能体先查看英伟达的财报，然后根据财报决定卖出还是买入英伟达股票。Anthropic 的文章把这种模式称为"路由"（routing）。
- **for 循环**
重复执行任务 A，直到满足某个特定条件。例如，不断生成随机数，直到得到一个质数。

图 6-11 直观展示了这些不同的控制流。

在传统软件工程中，控制流的条件是精确的。而在 AI 驱动的智能体中，控制流由 AI 模型决定。采用非顺序控制流的计划，无论是生成还是翻译成可执行命令都更困难。

**建议**：

评估一个智能体框架时，要查看它支持哪些控制流。例如，如果系统需要浏览十个网站，它能同时进行吗？并行执行能显著降低用户感知到的延迟。

### 反思与纠错

即使是最好的计划，也需要不断评估和调整，才能最大化成功的机会。虽然反思对智能体的运作并非绝对必要，但对智能体的成功是必要的。

在任务过程中，有许多环节可以用上反思：

- 收到用户查询后，评估这个请求是否可行。
- 生成初始计划后，评估计划是否合理。
- 每个执行步骤之后，评估是否走在正确的轨道上。
- 整个计划执行完毕后，判断任务是否已经完成。

反思和纠错是两种不同但相辅相成的机制。反思产生洞见，帮助发现需要纠正的错误。

反思可以由同一个智能体借助自我批评提示来完成，也可以由一个单独的组件来完成，比如一个专门的评分器：一个为每个结果输出具体分数的模型。

交替进行推理和行动，最早由 ReAct（Yao 等，2022）提出，如今已成为智能体的常见模式。Yao 等人用"推理"一词同时涵盖规划和反思。在每一步，智能体都被要求解释自己的思考（规划）、采取行动，然后分析观察结果（反思），直到智能体认为任务已完成。通常会用示例提示智能体，让它按以下格式生成输出：

```
Thought 1: …
Act 1: …
Observation 1: …
… [continue until reflection determines that the task is finished] …
Thought N: … 
Act N: Finish [Response to query]
```
图 6-12 展示了一个遵循 ReAct 框架的智能体回答 HotpotQA（Yang 等，2018）中一个问题的例子。HotpotQA 是一个多跳问答基准。

你可以在多智能体设置中实现反思：一个智能体负责规划和行动，另一个智能体在每一步或若干步之后评估结果。

如果智能体的回复没能完成任务，你可以提示智能体反思失败的原因以及如何改进。基于这个建议，智能体生成新的计划。这让智能体能从错误中学习。

例如，对于一个代码生成任务，评估器可能评估出生成的代码有 ⅓ 的测试用例没通过。智能体随后反思：失败是因为没有考虑所有数字都是负数的数组。于是执行者生成新代码，把全负数组考虑在内。

这就是 Reflexion（Shinn 等，2023）采用的方法。在这个框架中，反思被分成两个模块：一个评估结果的评估器，以及一个分析哪里出错的自我反思模块。图 6-13 展示了 Reflexion 智能体运作的例子。作者用"轨迹"（trajectory）一词指代计划。在每一步，经过评估和自我反思之后，智能体提出一条新轨迹。

与计划生成相比，反思相对容易实现，而且能带来出人意料的性能提升。这种做法的缺点是延迟和成本。生成思考、观察，有时还有动作，可能要消耗大量 token，从而增加成本和用户感知到的延迟，尤其是对于中间步骤很多的任务。为了促使智能体遵循格式，ReAct 和 Reflexion 的作者都在提示中使用了大量示例。这增加了计算输入 token 的成本，也减少了可供其他信息使用的上下文空间。

### 工具选择

由于工具往往对任务的成败起着关键作用，工具选择需要仔细斟酌。给智能体哪些工具，取决于环境和任务，也取决于驱动智能体的 AI 模型。

关于如何选出最佳工具集，并没有万无一失的指南。智能体文献中的工具清单五花八门。例如：

- Toolformer（Schick 等，2023）微调 GPT-J，让它学会使用 5 种工具。
- Chameleon（Lu 等，2023）使用 13 种工具。
- Gorilla（Patil 等，2023）尝试提示智能体从 1,645 个 API 中选出正确的 API 调用。

工具越多，智能体的能力越强。然而工具越多，高效使用它们就越难。这就像人很难掌握一大堆工具一样。增加工具也意味着工具描述变多，可能塞不进模型的上下文。

和构建 AI 应用时的许多其他决策一样，工具选择需要实验和分析。下面这些做法可以帮助你做决定：

- 比较智能体在不同工具集下的表现。
- 做消融研究，看看从工具清单中移除某个工具后，智能体的表现下降多少。如果移除某个工具后表现没有下降，就把它移除。
- 找出智能体经常用错的工具。如果某个工具对智能体来说太难用——例如，大量提示甚至微调都无法让模型学会使用它——就换掉这个工具。
- 绘制工具调用的分布图，看看哪些工具用得最多，哪些用得最少。图 6-14 展示了 Chameleon（Lu 等，2023）中 GPT-4 和 ChatGPT 在工具使用模式上的差异。

Chameleon（Lu 等，2023）的实验还说明了两点：

1. 不同任务需要不同工具。科学问答任务 ScienceQA 对知识检索工具的依赖远远超过表格数学解题任务 TabMWP。
2. 不同模型有不同的工具偏好。例如，GPT-4 选用的工具似乎比 ChatGPT 更广泛。ChatGPT 似乎偏爱图像描述，而 GPT-4 似乎偏爱知识检索。

**建议**：

评估一个智能体框架时，要评估它支持哪些规划器和工具。不同框架可能侧重不同类别的工具。例如，AutoGPT 侧重社交媒体 API（Reddit、X 和维基百科），而 Composio 侧重企业 API（Google Apps、GitHub 和 Slack）。

由于你的需求很可能会随时间变化，要评估扩展智能体、接入新工具有多容易。

作为人类，我们提高生产力不仅靠使用现成的工具，还靠从简单的工具出发，逐步创造出更强大的工具。AI 能从它最初的工具出发创造出新工具吗？

Chameleon（Lu 等，2023）提出研究工具转移：在使用工具 X 之后，智能体有多大可能调用工具 Y？图 6-15 展示了一个工具转移的例子。如果两个工具经常一起使用，就可以把它们合并成一个更大的工具。如果智能体知道这一信息，它自己就可以组合初始工具，不断构建更复杂的工具。

Voyager（Wang 等，2023）提出用一个技能管理器来记录智能体获得的新技能（工具），以便日后复用。每项技能都是一段程序代码。当技能管理器判断一项新创建的技能有用时（例如，因为它成功帮助智能体完成了一项任务），就把这项技能加入技能库（概念上类似于工具清单）。这项技能日后可以被检索出来，用于其他任务。

本节前面提到，智能体在某个环境中能否成功，取决于它的工具清单和规划能力。任何一方面出问题都可能导致智能体失败。下一节将讨论智能体的各种失败模式以及如何评估它们。

## 智能体的失败模式与评估

评估就是发现失败。智能体执行的任务越复杂，可能的失败点就越多。除了第 3、4 章讨论过的所有 AI 应用共有的失败模式之外，智能体还有由规划、工具执行和效率导致的独特失败。有些失败比另一些更容易发现。

要评估一个智能体，就要识别它的失败模式，并衡量每种失败模式发生的频率。

### 规划失败

规划很难，可能以多种方式失败。最常见的规划失败模式是工具使用失败。智能体生成的计划可能包含以下一种或多种错误：

- **无效工具**
例如，它生成的计划中包含 `bing_search`，而这个工具不在工具清单里。
- **有效工具，无效参数**
例如，它用两个参数调用 `lbs_to_kg`，但这个函数只需要一个参数 `lbs`。
- **有效工具，参数值错误**
例如，它用一个参数 `lbs` 调用 `lbs_to_kg`，但 lbs 的值用的是 100，而本应是 120。

另一种规划失败模式是目标失败：智能体没能实现目标。这可能是因为计划没有解决任务，或者解决了任务但没有遵守约束。举个例子，设想你让模型规划一次从旧金山到印度的两周旅行，预算 5,000 美元。智能体可能规划了一次从旧金山到越南的旅行，或者给你规划了一次从旧金山到印度的两周旅行，但花费远远超出预算。

智能体评估中常被忽视的一个约束是时间。很多情况下，智能体花多长时间不那么重要，因为你可以把任务交给智能体，等它做完再去查看。然而，在很多情况下，智能体的用处会随时间流逝而降低。例如，如果你让智能体准备一份资助申请书，而它在申请截止日期之后才完成，那它就没什么帮助。

有一种有趣的规划失败模式是由反思中的错误引起的：智能体确信自己已经完成了任务，而实际上并没有。例如，你让智能体把 50 个人分配到 30 间酒店客房。智能体可能只分配了 40 个人，却坚称任务已经完成。

要评估智能体的规划失败，一种做法是创建一个规划数据集，其中每个样本是一个元组 `(task, tool inventory)`。针对每个任务，用智能体生成 K 份计划，并计算以下指标：

1. 在所有生成的计划中，有多少是有效的？
2. 对于给定任务，智能体需要生成多少份计划才能得到一份有效计划？
3. 在所有工具调用中，有多少是有效的？
4. 无效工具被调用的频率有多高？
5. 有效工具被以无效参数调用的频率有多高？
6. 有效工具被以错误参数值调用的频率有多高？

分析智能体的输出，寻找规律。智能体在哪些类型的任务上失败得更多？你有关于原因的假设吗？模型经常在哪些工具上出错？有些工具对智能体来说可能更难用。你可以通过更好的提示、更多示例或微调，来提升智能体使用困难工具的能力。如果都不行，可以考虑把这个工具换成更容易使用的工具。

### 工具失败

工具失败是指使用了正确的工具，但工具的输出是错的。一种失败模式是工具直接给出错误输出。例如，图像描述器返回了错误的描述，或者 SQL 查询生成器返回了错误的 SQL 查询。

如果智能体只生成高层计划，并由一个翻译模块把每个计划动作翻译成可执行命令，那么失败也可能源于翻译错误。

工具失败取决于具体工具。每个工具都需要独立测试。务必把每次工具调用及其输出打印出来，以便检查和评估。如果你有翻译器，就为它建立基准来评估。

要发现缺少工具导致的失败，需要了解应该使用哪些工具。如果你的智能体经常在某个特定领域失败，可能是因为它缺少这个领域的工具。与人类领域专家合作，观察他们会使用哪些工具。

### 效率

智能体可能用正确的工具生成了有效的计划来完成任务，但效率可能不高。下面是评估智能体效率时你可能想跟踪的几项指标：

- 智能体平均需要多少步才能完成一项任务？
- 智能体完成一项任务平均要花多少钱？
- 每个动作通常需要多长时间？有没有哪些动作特别耗时或特别昂贵？

你可以把这些指标与基线比较，基线可以是另一个智能体，也可以是人类操作员。把 AI 智能体与人类比较时要记住，人和 AI 的运作方式非常不同，所以对人来说高效的做法，对 AI 来说可能低效，反之亦然。例如，访问 100 个网页对一次只能访问一个网页的人来说可能很低效，但对能同时访问所有网页的 AI 智能体来说却轻而易举。

## 结语

从本质上说，智能体的概念相当简单。智能体由它运作的环境和它能使用的工具集来定义。在 AI 驱动的智能体中，AI 模型是大脑，它利用工具和环境的反馈，规划如何最好地完成任务。能使用工具会让模型的能力大大增强，所以智能体模式是必然的趋势。

虽然"智能体"这个概念听起来很新，但它们建立在许多从 LLM 早期就在使用的概念之上，包括自我批评、思维链和结构化输出。

本文从概念上讲述了智能体如何运作，以及智能体的不同组成部分。在以后的文章中，我将讨论如何评估智能体框架。

智能体模式经常要处理超出模型上下文限制的信息。一个能在处理信息时补充模型上下文的记忆系统，可以显著增强智能体的能力。由于本文已经很长，我将在以后的博文中探讨记忆系统如何运作。
