postMessage 慢吗？（Is postMessage slow?） ｜ Surma ｜ 文章 ｜ https://surma.dev/things/is-postmessage-slow/

Google 的 Surma 写的一篇性能实测文章。很多人不愿采用 Web Worker，理由是担心 postMessage 太慢，他的回答是"不太慢，视情况而定"，并用数据把这个"视情况"讲清楚。

他先解释原理：postMessage 用结构化克隆算法，在发送端序列化、在接收端反序列化，只有部分开销落在主线程。第一个基准测试测发一条消息本身要多久：桌面 Chrome 约 5 微秒，安卓 Chrome 约 100 微秒，Firefox 和 Safari 因为计时器精度限制约 1 毫秒，都很小。第二个测试研究什么让它变慢：他生成不同广度、深度和字符串长度的对象，各发送一千次取 95 分位，得出一条经验法则：传输时间大致与对象 JSON 字符串化后的大小成正比，但只有超过约 100KiB 的大对象才明显。

要判断"慢不慢"得有预算，他沿用 RAIL 模型：响应用户交互有 100 毫秒，所以即使在最慢的设备上，发送 100KiB 以内的对象也不会超预算；有 JS 驱动的动画时，每帧只有 16 毫秒，10KiB 以内没有风险，这也是优先用 CSS 动画的理由，因为它跑在合成线程，不受主线程阻塞影响。

接着他讲遇到大数据时的办法，以他们做的扫雷游戏 PROXX 为例。最大 40×40 的棋盘状态约 134KiB，不能每次全量发送，于是只发送变更补丁，ImmerJS 这类库可以方便地生成和应用补丁。首次点击可能翻开 80% 的格子，补丁达 70KiB，对功能机仍太多，他们就分块发送：worker 从点击处向外遍历，攒到阈值就先发一批，在 Nokia 8110 这样每帧只能处理一条消息的设备上，分批更新看起来就像翻开动画，而在强机器上事件循环会自然多处理几条。另一种思路是把状态放进 ArrayBuffer（他用一个约 3KiB 的 WebAssembly 模块管理），利用可转移对象实现几乎恒定的传输时间，代价是访问数据更麻烦。

他的结论是：postMessage 确实有成本，但远没有到让主线程外架构不可行的地步，对大多数应用都足够；作者呼吁 Web 不要固守一切都在主线程运行的默认模式，而要探索拥抱 Web 和 JavaScript 约束的新架构。
