【开场预告】

Varun Mohan：我们在公司内部下的很多注，都不是三四周之后就能见分晓的东西。我们应该每六到十二个月就"蚕食"一次自己产品的现状。每六到十二个月，新东西就应该让现有产品显得很傻，甚至让现有产品的形态看起来很蠢。

Lenny：你怎么判断该招人了？

Varun Mohan：我希望公司几乎像一个"脱水"的实体，每招一个人就像加了一点水，只有等我们重新回到脱水状态时，才会再去招人。

Lenny：随着 AI 的兴起，你觉得人们应该更多投资哪些技能？

Varun Mohan：随着我们越来越多地构建产品，工程师现在能产出更多的技术，构建技术的投资回报率其实是提高了，这实际上意味着你会招更多的人。最好的做法就是亲自上手把这些产品都用一遍，你可以成为组织的力量倍增器，而且是以他们根本没预料到的方式。

Lenny：今天的嘉宾是 Varun Mohan。Varun 是 Windsurf 的联合创始人兼 CEO，Windsurf 已经迅速成为大家最喜欢的 AI 编程工具之一，基本上也是 Cursor 的主要竞争对手，上线四个月用户就超过 100 万。在这次对话中，Varun 分享了 Windsurf 的独特之处；为什么他们在很早期就重金投入企业销售；为什么"能动性"（agency）将成为工程师和产品构建者最需要培养的技能；还有他们最初如何从一家 GPU 基础设施公司起步，意识到在技术栈更上层有大得多的机会，以及让他们走到今天的两次转型。他还做了现场演示，分享了用好 Windsurf 的建议，等等。关于工程师和产品构建者未来的走向，这次对话里有太多值得学习的东西，我非常高兴能带给大家。感谢 LinkedIn、Twitter 和我的 newsletter 社区里提出好问题的各位。下面有请 Varun Mohan。

【正式访谈】

Lenny：Varun，非常感谢你来，欢迎来到播客。

Varun Mohan：谢谢邀请，我是你的老听众了。

Lenny：非常感谢，很高兴你能来。我感觉你们好像成了一夜成名的公司——当然绝对不是一夜成名——但我越来越常听到 Windsurf 是大家最爱的 AI 工具。我觉得大家并不了解 Windsurf 背后的故事，也不了解你们打造的公司 Codeium，所以我想不妨从这里开始。你能简单讲讲 Codeium 的历史，以及 Windsurf 是怎么从 Codeium 里诞生的吗？

Varun Mohan：好的。公司其实是将近四年前创立的。你知道，四年前 AI 编程还不存在，ChatGPT 也还没出现。当时我们实际上做的是 GPU 虚拟化和编译器软件。在那之前我做自动驾驶，我的联合创始人——我们从初中就认识——在 Meta 做 AR/VR。我们相信深度学习会触及很多很多行业，不只是自动驾驶，还会触及金融服务、国防、医疗。我们认为这些深度学习应用很难构建，所以我们让你能在没有 GPU 的电脑上有效地运行这些复杂应用，把工作负载真正跑在 GPU 上的所有复杂性都替你处理掉。我们能把这些工作负载优化得非常好。到了 2022 年年中，我们有几百万美元收入，管理着上万块 GPU，当时只有八个人，自由现金流为正。

但我们感觉到，一旦这些生成式模型变得非常好，我们构建的很多东西就没那么有价值了。这对公司来说是非常非常艰难的时刻，我们当时只有八个人。我们想：人们以后还会去训练那种非常定制化的情感分类模型吗？还是直接问 GPT-N"这句话是正面还是负面情绪"？大概率是后者。而在一个人人都运行生成式 AI 模型的世界里，基础设施公司凭什么能形成差异化？因为大家最终跑的都是同一类基础设施。所以我们决定：我们相信生成式 AI 几乎会成为下一个互联网，那我们就应该去构建下一代伟大的应用，像 Google、像 Amazon 那样。

我们做了垂直整合，拿我们的推理基础设施去打造了当时的 Codeium。那时我们是 GitHub Copilot 的早期用户，我们认为编程领域在接下来几年会被极大地颠覆。于是我们用自己的基础设施，大规模运行自己的模型，最开始甚至训练了自己的模型。一开始非常非常简单，只是一个自动补全模型，也就是用户打字时，我们帮他补全接下来一两行、三四行代码。但我们是完全免费提供这个产品的，覆盖开发者写代码用的所有 IDE：VS Code、JetBrains、Eclipse、Visual Studio、Vim、Emacs。我们之所以能免费提供，是因为我们有基础设施背景，能把这些工作负载优化得非常好。

很快之后，一些大企业也想和我们合作，于是我们建立了一套企业业务，与 Dell、摩根大通这样的大公司合作。对他们来说，重点不只是"你能不能补全代码、能不能和代码库对话"，而是"你能不能给我们一个安全的方案，并且针对公司内部所有私有数据做个性化"。所以我们拿自己的基础设施，大力投入，确保能深入理解这些大公司的代码库。直到六个月前，我们一直在做这件事——不是说我们停止了，而是六个月前我们意识到，我们受限于已有的那些 IDE。VS Code 是非常流行的 IDE，但它对我们能向用户展示的 AI 能力有一个天花板。因此我们决定 fork VS Code，构建我们自己的 IDE，加入一些新的智能体（agentic）能力。而且过去几年，模型能力也在逐年指数级增长。这大概就是我们现在的状况，我跳过了很多细节，但大致如此。

Lenny：这里面有太多有意思的线索。一个是，大家一直在问 AI 里价值最终会沉淀在哪里。很有意思的是，你们几乎是从最底层的基础设施、GPU 起步，然后走到了人们所说的"GPT 套壳"——其实并不是。那么关于价值最终会落在 AI 工具栈的哪一层，你有什么经验或想法？

Varun Mohan：也许我先说一件我认为对创业公司非常真实的事：你最初认为应该去做的那件事，很不可能是对的。这是作为创始人很难消化的一点。你需要非理性地乐观，相信你要做的事会有差异化的重要性，否则你为什么要去做？如果它显而易见，大公司早就做了。但同时你也需要非常非常现实，因为大多数非常规的想法通常都是坏想法。所以这是一种奇怪的走钢丝：你在推动一个你相信会成真的未来，同时不断获得新信息，需要亲手扼杀自己原来的信念。

从基础设施说起，我们最初的假设是模型架构会非常非常异构。我们来自自动驾驶背景，那里有很多不同类型的模型架构：卷积神经网络、图神经网络、循环神经网络、LSTM，还有用于点云的网络（PointNet）等等，我们要处理的架构可能有几十种。当时我们觉得，复杂度这么高，如果有人能把这些复杂性接过去，显然会很有价值。快进到 2023 年年中，一切看起来都会变成 Transformer，那我们的假设就错了。这时候，至少我们认为，大部分价值不会单纯沉淀在基础设施层，而会沉淀在别处。哪一层才真正能做出差异化？我们认为应用层是一个非常非常深的、可以做差异化的层。我们能有多少种方式为开发者打造更好的用户体验、更好的工作流？我们认为这件事几乎没有天花板，我们能让开发者的生活好上无数倍。

Lenny：你触及的第二条我觉得非常有意思的线索是，你们是从行得通的想法上转型的——你们在赚钱，用户喜欢，你说有几百万美元的收入——然后你们就说"不，我们要彻底改变业务"。所以问题是：关于该追随什么，你学到了什么？我听到一个很有意思的点：一旦你构建想法所依赖的假设变了，就该重新思考这个想法，也许去尝试别的。

Varun Mohan：我们思考这件事的方式是，即便是现在，我们也接受自己会犯很多错，我们就是会犯很多错。当然那是一个非常重大的时刻，因为那是"押上整个公司"的时刻。我们基本上告诉投资人："我们在这个业务上赚钱，"——当时我们已经融了 2800 万美元——"但我们要彻底转型。"而且我们是一夜之间完成的，不是说"也许用一两个季度慢慢转"。因为我们知道对创业公司非常重要的一点是专注。如果你想做另一件你认为很大的事，却还专注于一件你不认为有价值的事，那你注定会在那件大事上失败。这是很显而易见的。

但我认为，一旦你带着"很多假设会是错的"这个前提进去，同时尽可能集中精力去验证这些假设，并且不爱上自己的想法——有好想法当然很棒，但你绝不该太爱自己的想法——再加上有一个非常追求真相的组织，那就好了。我觉得公司里很多人的想法都被一次次检验过。即使是做 Windsurf，这不是整个公司的转型，但也是公司做出的重大决定。你需要下一些注，有时错，有时对。但如果你的组织在你做错决定时士气不会低落，那是最好的，这意味着你永远拥有选择权。

Lenny，我常跟公司说的一点是：今年我们的工程产出总量，会比公司创立以来到现在的全部工程产出还要多。这几乎意味着每一年对我们都是一次新生，几乎是一次检验全新一套假设的机会。也许我们最初的假设就是错的——凭什么我们比别人更聪明、更常是对的呢？

Lenny：这太鼓舞人了。这让我想起上过这个播客的 Waze 创始人 Uri Levine，他把一句话印在 T 恤上，他的书也叫这个名字——"爱上问题，而不是解决方案"。我觉得这正是你说的。好，我们来聊聊 Windsurf。让大家理解 Windsurf 是什么，最简单的方式是什么？

Varun Mohan：Windsurf 是一个 IDE，是一个用来构建软件、构建应用的应用程序。疯狂的是，很多使用这个产品的人可能根本不知道 IDE 是什么，这很疯狂，我们待会儿再聊。但我们为什么要做 Windsurf？为什么不能在 Visual Studio Code 这样的传统 IDE 上做？简单说，我们看到 AI 越来越强大，我们认为人们构建技术的界面将发生巨大改变。它不会再是一个传统的纯文本编辑器，由用户写几行或大部分代码，IDE 只对用户做得对不对给出一点基础反馈，比如"你的软件里有个 bug""有个编译错误"。它能做得多得多，它可以直接修改大段代码。

我们认识到的一个关键点是：在这个新范式下，AI 可能会写远超 90% 的软件，那么开发者的角色和他们在 IDE 里做的事情，可能是审查代码，可能和过去有些不同。用 Windsurf 时你很快就会看到，用户相当大一部分时间其实是在审查 AI 的输出。所以我们需要在 IDE 里构建定制的审查流程，让这件事更容易做，因为开发者不再把所有时间花在写代码上。这就是我们打造这个产品的根本前提：如果只有非常非常基础的 UI，我们会受到极大限制。

举个简单例子。我们有个自动补全产品，能补全几行代码；现在我们推出了 Windsurf Tab，它还能给你展示重构，几乎是行内重构，我们能在 Windsurf 里为它构建定制 UI。但在 VS Code 里，受限于 API 的访问权限，我们得在用户光标旁边动态生成图片，因为我们没有能力正常展示编辑。我们发现，一迁移到 Windsurf，接受率立刻翻了三倍。同样的模型，接受率翻了三倍。这让我们确信：你可以说技术很重要——我也认为技术非常重要——但如果用户从你构建的技术中得到的价值很少，你就得认真想想，也许确实需要构建一个新的界面。这就是 Windsurf。

Lenny：说得再清楚一点，你们下的大注是：最初在大家都熟悉的现有 IDE 里工作，然后觉得"这没法让我们到达想去的地方"，于是要说服人们换到一个全新的东西上——我们自己的 IDE——因为它会好得多。我觉得大家可能没意识到这有多冒险，说服工程师用全新的东西是件大事。

Varun Mohan：当然。Lenny，我想分享的一个关键点是：我们很多开发者确实用 Visual Studio Code，但也有很多人用 Java、C++ 等语言写代码，他们可能用 JetBrains 系列 IDE，比如 IntelliJ。我们实际上仍然承诺在那些平台上继续开发。我们只是觉得，占主导地位的 IDE——Visual Studio Code——限制了我们能给客户提供的用户界面。

Lenny：Windsurf 目前的增长情况如何？你会听到你们这个领域竞争对手的各种疯狂数字，你能分享些什么？

Varun Mohan：好的，简单说几个。我们大约四个多月前推出这个产品，这段时间里有超过一百万开发者试用过，现在月活用户有好几十万。

Lenny：我太喜欢现在这种状态了，"一百万？没什么大不了的"。现在的数字太离谱了，我们都习惯了一亿美元年收入这种说法。四个月一百万用户，就像"那当然了，怎么可能没有"，但这其实很离谱，现在真是疯狂的时代。你提到了一个我本想后面再聊的话题，不如现在就聊：未来工程会如何变化。你抛出了"未来 90% 的代码会由 AI 编写"这个说法，Anthropic 的 Dario 最近也说了同样的话。你们对未来的样子有非常有意思的一瞥。那么你认为未来几年，编程具体会是什么样？和今天会有多大不同？

Varun Mohan：我们思考工程师实际在做什么时，大概可以分成三类：我该解决什么问题，我该怎么解决，然后去解决。我想这个领域里的每个人都越来越确信，"解决"这一步——也就是我已经知道怎么做，只是去做——绝大部分甚至全部都会由 AI 处理。事实上，借助我们在深入理解代码库方面做的一些工作，"该怎么解决"也越来越接近被解决了：如果你深入理解一个组织的内部环境，深入理解代码库，那么在最佳实践下该怎么解决，也会被解决。所以我认为，工程最终会回到你最初就希望工程师去做的事情上，也就是——
我们需要解决的最重要的业务问题是什么，我们的应用、我们的产品需要具备的最重要的能力是什么，然后去给这些排优先级，做出正确的技术决策并去实现它。我认为这大概就是工程的走向。

那这是不是意味着没人需要计算机学位了？我觉得这个说法可能有点被夸大了。我的论点是这样的：如今很多做全栈应用的开发者，至少在几年前，大概都上过大学，修过操作系统课，对吧？理论上，他们并不会经常去折腾操作系统，比如内核调度器。但这些原理能不能帮他们理解为什么应用很慢，能不能帮他们理解为什么某些设计决策比另一些更好？能，这让他们成为比别的工程师好得多的工程师。我认为这种理念、对底层发生了什么的理解，会让好工程师变得更好；但同时，它也赋能了一大批从来不懂这些东西的人，让他们知道怎么把东西做好。这是整个过程中涌现出来的另一件了不起的事。

Lenny：我不知道你有没有孩子，假设你有孩子，或者有侄子侄女要上大学，你会建议他们学计算机吗？还是会说，如果你现在选这个职业，日子不会好过？

Varun Mohan：我回想一下。我上的是 MIT，公司工程团队里很多人都是一起在 MIT 读的书。当我回想我们在工程或计算机科学中学到最多的东西，其实并不完全是怎么写代码——上完大学你会写代码，这几乎是理所当然的——更多的是你如何思考一个问题、如何拆解它、如何用有意思的方式解决它的原则。举个我很喜欢的课：分布式系统课。在那门课里你会读文献，理解某些设计决策是怎么做出来的。我觉得那更像一门解决问题的课。这个专业是关于在约束下如何解决问题的，约束就是今天的计算机如何运作：内存的速度是多少，一个周期或一秒内能做多少计算。基于这些你可以做权衡、解决问题。所以我不会说你不应该去拿计算机学位，我觉得在这个意义上计算机科学几乎就是"解决问题"的同义词，它相当有价值。

那计算机学位里学的东西都有用吗？我会说我学的很多东西都没用。举个例子，我修过一门用 Julia 讲的并行计算课，我觉得 Julia 现在已经不是很流行的编程语言了。我会因为上了这门课而难过吗？不会，并行计算的原理在今天依然非常有用。

Lenny：所以我听到的是，你仍然想培养的技能——无论是计算机科学还是某种形式的计算机科学——就是建立关于计算机和系统如何运作的心智模型：并行处理、内存、硬盘、互联网之类的。然后是解决问题的能力，能解决有意思的问题。随着 AI 构建越来越多的产品，你认为还有什么技能是人们应该更多投资的？

Varun Mohan：我觉得有一点可能有点被低估了，就是"能动性"这件事。我经常想这个问题。很多人上大学、上学，基本上都是在一张纸上被告知该做什么，被给予一些非常非常明确的路径去走。我觉得在社会和学校里，我们并没有把"如何确保培养出真正有能动性、想去构建东西的人"放在优先位置。他们的目标不只是大学毕业，然后进一家大型科技公司，被告知具体该做什么、在某个网站上把某个像素放在哪里。我觉得这可能是一项在最近十年左右被低估的技能，而它将会变得非常非常重要。对我们创业公司来说，这显然是我们要找的技能，我们找能动性非常高的人，因为我们清楚地知道：默认情况下，如果我们不创新、不做疯狂的事，我们就会死，公司就会死。所以我们找这样的人。但我会说，对于大多数软件工程岗位，情况大概并非如此。想想某家大公司 X 在招什么人，一般的软件工程面试大概不是这个样子的。

Lenny：我太喜欢你这个说法了——"如果我们不做疯狂的事、不创新，我们就会死"——这可以当这期播客的标题。我知道这百分之百是真的，现在发生着太多疯狂的事、太多创新，跟不上你就会死。我们来聊聊招聘。你们的招聘方法非常有意思，我这里有几个问题。一个是，你们如何保持非常精简——这是现在所有 AI 创业公司的共同主题——你们怎么判断该招人了？

Varun Mohan：我喜欢做一家精简公司的想法，但我并不把它神化，比如"做一家 10 个人或 20 个人、年收入 5000 万、1 亿或 2 亿美元的公司是梦想"。那不是我们公司内部推崇的。我们推崇的是：在满足我们雄心的前提下，做尽可能小的公司。这才是目标。Lenny，我可以这样说：如果我告诉你"我要造自动驾驶汽车"，然后说"我们团队有 10 个人"，你完全有理由说"Varun，你不是认真的"，而且你是对的，那时我确实不是认真的。所以答案是：要去做你那个疯狂的雄心项目，最少需要多少人？我们想做的项目是彻底改变软件构建的方式。我们在公司内部说过，我们的目标是把构建应用和技术所需的时间减少 99%。这是一个极其宏大的目标，长期来看，我们不可能只靠一个 10、20、30、40 人的工程团队去实现它，我们认为它的天花板非常非常高。所以这是第一个关键点：如果我们能做到成为一家相当大规模的公司，但依然像创业公司一样运作，那就是梦想。

就招聘理念而言，我们的思路是：只有当某个职能真的"淹没在水下"、忙不过来时，我们才会为那个岗位招人。比如说我们在做推理技术，除非那边已经忙不过来，否则我们不会去招人做那个。原因是，我其实认为这是一个陷阱：当你为一个岗位招人，而那里已经有足够的人时，最终会出现很多奇怪的办公室政治。这不是因为人坏。我觉得大多数人都是出于好意。但当有人加入公司，而你其实并不真的需要他们时，他们就会去制造一些别的、他们觉得应该做的事情，去找别的事做，而实际上那并不重要，但他们会去说服组织里的其他人说它很重要。我觉得作为一家创业公司，我们没有精力去处理这些。对我来说，我希望看到每个人几乎都在举手说"我快不行了，我们需要再加一个人"，那时我们才去招人。我喜欢用的一个比喻是：我希望公司几乎像一个"脱水"的实体，每招一个人就像加了一点水，只有等我们重新回到脱水状态时，才会再去招人。

Lenny：我太喜欢这个比喻了。听起来很痛苦——你需要被淹没、举手说"我快死了"、处于脱水状态。但我也知道这是一种非常令人兴奋的工作方式。听起来很难，但如果你身在其中……你能谈谈这一面吗？因为这听起来可能很可怕，"我不想这样工作"。

Varun Mohan：你知道吗，Lenny，我其实认为这非常好，原因有好几个。公司里的很多人，都是我们尊重和信任的人，这种压力会逼出无情的优先级排序。你有一个团队在做某件事，他们永远不会要求去做不重要的事。事实上，如果他们手上有两件事，他们会直接告诉我："我手上有两件事，我没法同时做两件，我只能做一件。"然后他们会挑最重要的那件。这其实又回到我认为对创业公司乃至所有公司都成立的一点：你不是靠把十件事做得还行来取胜的，你是靠把一件事做得非常好来取胜的，也许另外九件都失败了。我跟公司讲过，这和学校非常不同。在学校，你优化的是总 GPA；但对公司来说，我只需要在那一门真正重要的课上拿 A+，其他所有课都可以拿 F。其他课拿 F 不是说去做违法的事，基本上就是把不重要的事降级。这实际上会逼出一种组织层面的优先级排序，这非常非常好。

Douglas 和我——Douglas 是我的联合创始人——我们可以告诉公司"这两件事是最重要的"。但如果我们一边说"这两件事对公司最重要"，一边让公司比实际需要多 20% 的人，最终会发生什么？所以，人少一点、或者人在内部都忙不过来，几乎是一种强制无情排优先级的机制。

Lenny：每一个在大公司工作的听众都清楚你描述的情况：人太多时，他们都会找事做，都会去推销想法，都想展现影响力，想在绩效考核中表现好。这就是公司里人太多的本质。所以这一切都很有共鸣。再深入一点：当有人忙不过来、告诉你该招人时，具体是什么样？是有人来找你说"Varun，我们团队需要人，这根本不可能完成"吗？更具体地说是怎样的？

Varun Mohan：基本上就是这样：有压力要在短时间内完成某件事。顺便说一句，我们确实相信，对软件来说，如果你想做伟大的事，不可能只是说"我想一个月搞定"。你得从这个角度想：如果一个软件项目两三周就能做出来，那对于你所构建的东西的真实复杂度和差异化意味着什么？大概不会很高，除非你认为自己比所有人都聪明得多——但我觉得那是傲慢。我们确实有一支非常出色的工程团队，但同时，我不认为我们的工程团队出色到能在三周内做完世界上其他人六到九个月都做不了的事，那样想太蠢了。

所以基本上就是那个人站出来说"我没有足够时间去做 X"，然后我们谈一谈："好，那你能做什么？"如果答案是"我只能做少一些"，那也许我们就做个决定："哦，太好了，也许我们应该把它降级。"为什么呢？因为这对我和我的联合创始人这样的人来说也很难：我们也想做很多事，有一种冲动想做很多事。但如果我们被迫不断做出"我们不能做 X"的决定，这会让事情变得非常清晰。非常清晰，因为我们的工程面试流程通过率也极低，所以我们也很难很快地把人招进来、让他们很快入职。所以我觉得这对所有人都很清晰：对想要更多人手的人来说很清晰，我们可以直接告诉他"我们不认为你应该做另外那件事"；对我们来说也很清晰，因为我们能和他们达成共识。有时候我们也会同意："好，我们的团队很灵活，确实需要把某件事做完。"

我们一直努力确保在工程团队中成立的一点是：一个人对公司的价值与他团队的规模毫无关系。公司内部的项目都有直接负责人（DRI），如果我们觉得某个项目很重要，人们可以从一个项目转到另一个项目。公司里没有"某人拥有某些人"这种概念，那是一个非常糟糕、非常棘手的想法。事实上，公司里最有价值的人，是能用尽可能少的人去做最疯狂的项目的人，这才是你在内部应该奖励的。

Lenny：你们 Codeium 现在有多少人？

Varun Mohan：我们有接近 160 人，工程团队超过 50 人。

Lenny：太棒了。其他比较大的职能是什么？

Varun Mohan：我们有市场销售（go-to-market）团队。

Lenny：哦对，我想聊聊你们在销售上的经验。不过先把招聘的话题收个尾。我们聊了什么信号告诉你该招人了，那你在面试和招聘的人身上看重什么？

Varun Mohan：我们看重的一个关键点是——我们的技术门槛非常高，所以假设他们达到了技术门槛——我们找的是对我们要解决的使命真正非常有热情、并且愿意非常努力工作的人。我们不会去说服别人"我们是一家很佛系的公司，在这儿工作很爽"。不，这是一个非常激动人心、竞争非常激烈的领域，如果公司里的人不努力工作，你应该预期我们会输。我听到的最大的"暗号"之一是：当我问人"你愿意多努力地工作"时，有些人最后会说"我工作很聪明"。我基本上会反问他们一个问题："如果我们公司有很多既聪明又努力的人，那你的差异化在哪里？你会不会拖他们后腿？"

因为我认为公司的一个真相是，它就像一个巨大的小组作业。一个不尽自己本分的人，坏处不在于生产力。到了公司有好几百名工程师的时候，我不会去想那一个不尽力的工程师；问题在于和他共事的团队，他们几乎会问："这就是公司内部的标准吗？这就是期望吗？"Lenny，如果我告诉你，你在一个五人团队里，另外四个人根本不在乎，你会觉得自己应该多在乎？

Lenny：不会太在乎。

Varun Mohan：没错。所以对我们来说，这才是我们更在意的。我们的文化非常协作，虽然很大程度上是个人项目，但人们觉得可以依靠别人一起完成复杂任务。

Lenny：所以你问的问题基本上就是：你愿意多努力？你想多努力？我知道有一群人主张工作与生活平衡，"你怎么敢让我疯狂加班"。我很喜欢这种前置筛选：如果你在这里工作，你会非常努力，工作很长时间，这是一个疯狂的领域，我们会靠聪明且非常努力地工作来取胜。

Varun Mohan：是的。

Lenny：你之前某个时候说过，你们工程岗位的通过率大概是 0.6% 的候选人，差不多这样？

Varun Mohan：是的，这大概是带回家作业之后的数字。带回家作业本身大概还会在此之上再筛掉 10 到 15 倍。

Lenny：我越来越常听到一个问题：现在有 Windsurf 这样能帮你解决所有问题的工具，你们怎么面试？

Varun Mohan：我们可以接受人们使用这些工具。因为我认为最糟糕的事情之一就是有人来了却不喜欢用这些工具，我们相信它们能带来巨大的生产力提升。我们会请人来公司现场面试，这样我们能看到他们在白板上如何思考问题等等。我们确实想看他们如何临场思考，希望他们不是把我们说的话放进语音翻译器、贴进 ChatGPT 然后把答案拿出来。所以有办法做到。我的观点是，工具非常非常重要，但我们仍然要看一些解决问题的能力。如果你解决难题的唯一方式就是把它丢进 ChatGPT，我觉得这对我们来说是个隐患。

Lenny：好，我们来聊聊你们在市场销售上的经历。你们一开始显然像大多数人一样，没有销售团队就开始做产品，然后据我所知，你们意识到那是一个巨大的疏漏，也是一个巨大的机会。我想聊聊这个，因为我觉得你们拥有庞大的销售和市场团队，这非常独特。

Varun Mohan：是的，我们其实在公司历史上很早就做了这个决定。我们一年多以前就招了销售副总裁，现在公司的市场销售团队已经超过 80 人，是公司内部一个相当大的职能。讲一点背景：我们创办公司时，有几位天使投资人其实是市场销售方面的实操者，比如曾任 MongoDB 首席营收官（CRO）的 Carlos Delatorre。对我们来说，我们从不把企业销售和销售视为负面的东西。我觉得这一点很有意思：技术型创始人有时不太喜欢销售，认为销售是流程里很负面的部分，一切都应该是产品驱动增长（PLG）。我觉得事情没那么非黑即白，我认为企业销售非常有价值。

但当我们还是 GPU 虚拟化公司、基础设施公司的时候，我们之所以从没招过销售，是因为我不知道怎么规模化这个职能。当时是我自己在卖产品。所以说到底，如果连我自己一单一单卖产品都很难，我就不知道怎么把它变成一个可以规模化的流程。即便我能卖成一单，我也不知道怎么把业务收入从几百万做到几亿。
更别说几千万了。如果我自己都不知道怎么做，又怎么能招个人来让他把这件事规模化？反过来，在 Codeium 上，很多大企业很快就主动找上门来。光是这一点，到 2023 年年中，我和公司里另外几个人就开始卖产品，同时和大企业做几十个试点。我们很快就明白，这个领域需要建立一套大企业销售体系。所以到 2023 年年底，我们招了销售副总裁，此后很快扩建了销售团队。说到底，如果你想卖给财富 500 强，单靠刷信用卡是非常难做到的。

Lenny：我们聊聊 Cursor。我不想在竞争对手上花太多时间，但大家一想到你们，总会想到这个。你们算是这个领域的领先者，当然还有 Copilot，但那是另一回事。理解你们和 Cursor 区别的最简单方式是什么？你们又打算怎么在这个领域长期取胜？

Varun Mohan：我可以分享几点。在产品层面，我们投入了大量精力，确保对超大代码库的理解质量非常高，这是由我们的起点决定的。我们和世界上一些最大的公司合作，比如 Dell、摩根大通。像 Dell 这样的公司，单个代码库就超过一亿行代码。能非常非常快地理解它、进行大规模修改，是我们花了很多时间去做的事。这要求我们自己构建模型，在几千块 GPU 上并行处理他们代码库的大块内容，并对其排序，从而找出针对代码库的任何问题最重要的代码片段。所以我们基于自己的基础设施背景，构建了大型分布式系统来做这件事。这是其一。

Lenny：我顺着这条线追问一下，因为我觉得大家可能低估了这有多重要。我们请过 Bolt 和 Lovable 的创始人上播客，那些产品是从零开始构建东西，替你写代码。相比之下，把 Windsurf 加载到你的百万行代码库上——比如 Airbnb 或 Uber——去理解你到底有什么、它是怎么运作的、该去哪里改而不弄坏东西，这难得离谱。所以我听到的是，这是你们一个很大的差异化优势，你们其实是从这里起步的，而 Windsurf 现在正在把这个优势扩大。

Varun Mohan：没错。这是我们花了很多时间的一件大事：理解代码库在做什么。还有一点是，用户在代码库上的所有交互是什么，待会儿我也很乐意演示。第二个关键点大概是：我们不只绑定在 Windsurf 上。考虑到我们正在聊 Windsurf，这句话可能有点奇怪。我们其实非常专注于支持 JetBrains 这样的 IDE。JetBrains 或者说 IntelliJ——70% 到 80% 的 Java 开发者都在基于 JetBrains 的 IDE 里写代码。我们之所以不觉得有那么大的必要去做一个和 JetBrains 竞争的产品，是因为 JetBrains 实际上是一个可扩展性非常好的产品，而 VS Code 并不是，VS Code 的可扩展性不太好。

所以对我们来说，我们的目标不只是满足一部分能切换到我们 IDE 上的用户，我们想把这种智能体体验带给每一位开发者。如果这意味着有 Java 开发者在 JetBrains 里写代码，那也没问题。我们和很多大企业合作，他们有一万多名开发者，其中超过 50% 的开发者在用 JetBrains。那是一个非常大的产品。顺便说一句，那家公司本身是一家私营公司，每年营收好几亿美元，是一家非常非常大的公司。所以这是我们的另一个关键点：我们想在开发者所在的地方满足他们，如果他们用的是别的平台，我们也会去支持。

第三个关键点，对企业来说的另一个关键点是：我们能在很多非常安全的环境中工作。我们有 FedRAMP 合规，这意味着我们可以卖给非常大的政府机构。我们有一种混合模式来使用产品，这意味着所有被索引的代码实际上都存放在用户自己的租户上，代码是公司最重要的知识产权之一。所以如果你从大公司的视角看，多年来做企业产品，我们处理了很多大公司想看到的复杂问题。这一部分也是因为我们一路走来的历史。

【现场演示】

Lenny：好，Varun，别吊胃口了，我们来现场演示一下 Windsurf，让大家看看它是什么样。我会边看边问你一堆问题。你可以共享屏幕，打开 Windsurf。

Varun Mohan：好的。先介绍一下背景：这是一个非常基础的 React 项目，现在里面什么都没有，你打开任何文件，都是默认的 React 应用项目。我这里有一张简单的图片——你可以给 Windsurf 传图片，告诉它你希望项目长什么样——这是我希望"狗狗版 Airbnb"网站大概的样子。

Lenny：漂亮的线框图。顺便说一句，我太喜欢了，这就是你需要的全部。

Varun Mohan：这就是你需要的全部。基本上我们要做的是——Windsurf 很酷的一点是，它其实能在已有项目里工作——所以我可以直接说："把这个 React 应用改成基于这张图的狗狗版 Airbnb 网站，并且预览一下。"现在它就会开始执行，读取仓库。显然它不知道当前代码库长什么样，所以它会去分析代码库，找出需要做哪些修改。我们等着看它会做什么，同时我们继续聊。

Lenny：太棒了。所以首先，你打开 Windsurf，准备好了一个样板 React 项目，Windsurf 之前从没见过这段代码。你让它在你的代码库上做事，就是"按照这个设计把它改成狗狗版 Airbnb"。

Varun Mohan：没错，完全正确。

Lenny：好的，那我们让它跑着，我们聊。我问你一个我会问每一位做"帮工程师、产品经理和设计师构建产品"的产品的嘉宾的问题：如果你能坐在每一位刚打开 Windsurf 的新用户旁边，在他们耳边悄悄说几条建议，帮他们用好这个产品，你会说哪几条？

Varun Mohan：第一条就是稍微有点耐心，既要耐心，又要明确。当你让应用去做一些修改时，它可能会去做很多不相关的修改。我认为最能防止这种情况的，就是非常非常明确，尽可能明确。我会请大家一开始先做小一点的修改。如果有一个很大的目录，不要让它去重构整个目录，因为如果它错了，它基本上会毁掉 20 个文件。

在此基础上，我觉得用户使用这个产品时一个关键的收获是，他们会逐渐了解产品的"高山和低谷"——哪里强、哪里弱。我喜欢用自动补全来类比：你会觉得一个产品不停给建议，但只有 30% 的时候被接受，应该非常非常烦人。但之所以不太烦人，其实是因为你已经知道了"70% 的时候我不需要接受，而我接受的那些时候，我知道怎么从中获得价值"。你还会事先知道，如果你要写的东西非常复杂，你就预期自动补全不会起作用。所以我觉得这几乎就是要理解产品的高山和低谷。疯狂的是，每三个月这些就会改变、被重新评估，它几乎会变得比过去实质性地更好。所以，耐心和明确，也许是我会告诉用户的两个关键点。

Lenny：我觉得字里行间还有一点：对模型的能力培养出一种直觉，什么时候要具体，什么时候可以抽象。随着时间推移你会逐渐建立起这种直觉。

Varun Mohan：没错。说着说着，好像我们已经有预览了，你猜怎么着，我们有了一个不错的狗狗应用。很酷的一点是，我们做的不止是修改代码，还能指向不同的部分。我可以指着不同的元素说——这不是什么好设计——但我基本上可以选中这个元素，说"把这个背景改成红色"，就是选中某个元素去改它，把它改成红色，它应该就能做到。产品的预览功能——在应用构建过程中就能展示它——在这方面很有帮助。现在你其实可以完全待在"应用的世界"里，甚至可能根本不需要看代码。当然这看起来很丑，但某种程度上，如果我想，我就能这么做。

不过，Lenny，我还想展示另一个关键点。显然你可以继续下去，我可以挑不同的组件去改，我们有很多计划，不止是点选修改组件。但很酷的一点是，还有一套 AI 审查流程。就像我之前说的，AI 的角色现在变了很多，它现在会替你修改大段代码，开发者现在的工作是去审查 AI 生成的大量代码，然后采纳。在这期播客里我不会去审查所有生成的代码，但假设我想修改其中一些代码——如果你是真正的开发者，想去改，比如我不喜欢我的变量名叫 title，我想把它叫 titleString，像这样。如果我想做这个修改，改成 titleString，我就这么做，然后告诉 AI 继续。

这里很酷的一点是，Windsurf 不仅知道智能体做了什么，还知道用户做了什么。我们的目标是达到一种几乎像"心流"一样的状态，用户做的一切 AI 都知道，并且能预测意图。你可以看到它说："我注意到接口属性 title 被改成了 titleString。"然后它就去把应用里所有用到 title 的地方都改成了 titleString，现在就不再报错了。所以即使我在写软件，想做一些点状修改，AI 也能在用户的路径上快速完成这些修改。想象一下做一次重构或迁移，你只改了代码的一部分，就可以让 AI 把剩下的继续做完。因为它深入理解代码库，它应该能找到所有对应的地方去修改。显然，现在我重新加载应用，应用里没有 bug，依然能正常加载。

Varun Mohan：Lenny，有意思的是，你看到的这个基础应用也是 Windsurf 生成的。我们之所以没在演示里现场生成，是因为安装所有依赖要三四分钟，演示时我不想等。实际上，产品的大多数用户可能都是从零到一去构建这些应用的。我可以说一件有意思的事：我们推出 Windsurf 时，要求公司里每个人都用 Windsurf 去做一个应用，包括我们的市场团队和销售团队。有一个很疯狂的数据，我想大家会觉得惊讶：我们省下了超过 50 万美元本打算采购的 SaaS 产品，因为我们的市场团队现在自己做应用，而不是去买。比如我们的合作伙伴负责人，没有去买合作伙伴门户产品，而是自己做了一个合作伙伴门户。他以前从没做过软件。我们还在公司内部想出了办法，能轻松、安全地部署这些应用。我们现在正在为公司构建非常非常定制化的软件，让公司运作得更高效。这是我大概六个月前都不会想到的。

Lenny：这太有意思了。你不需要点名公司，但你最不看好哪个领域？你认为哪个领域会因为公司里的人自己做这类产品而面临最大的麻烦？

Varun Mohan：我的观点是，那些非常非常垂直化的细分产品，我认为会被大幅挤压，销售类产品就是一个例子。我不想说得太负面，但在我们这样的公司里，很难让最好的工程师去做一个一流的销售产品，没有足够的兴趣去做；也很难让他们去做一流的法律软件或财务软件，这对我们来说非常非常难。这其实是那些做出这些产品的公司的一条很大的护城河：他们能站出来，对如何做这件事有自己的观点和立场，招到足够好的工程师去构建软件，而我们公司不愿意做这些。所以以前我们会去买这些技术，因为别无选择。但现在疯狂的是，领域专家现在可以自己构建他们最终想要的工具了，这其实很疯狂。

想想看，这些软件公司、这些垂直软件公司为什么能够存在？原因是它们有很多功能，这种"大而全"的功能集适用于很多公司，但每家公司只想要其中 10% 的功能。问题是，每家公司都没有能力为那 10% 的功能维护一款软件或构建定制软件。但现在这完全变了，现在它们能做到了。

Lenny：一直以来都有这么一种说法："如果我能直接买，为什么要花时间自己做软件？"但现在只要五分钟，就五分钟，而且可能还更贴合你的系统。你有多少次买了一款软件，然后几乎会想："为什么没有和 X 的集成？我明明在用 X。"这有多烦人，这其实让软件对你没那么有用了。我觉得很酷的是，如果有人回到你开始演示的时候，那基本上就是一个产品经理在跟工程师说："给我做个狗狗版 Airbnb，这是我画的一个很蠢的线框图，就几个框。"这几乎像是一个很糟糕的产品经理在跟工程师说话，而它居然真的行得通，这才是疯狂之处。所以你分享的市场团队自己做东西的例子，他们不需要懂任何产品构建，只要用某种荒唐的方式描述一下，画几个框表示想要的样子，它就能做出东西来。

Lenny：我觉得对产品人来说更直接的一点是：销售跑来找你说"我想要这个东西，它能帮我的销售团队"，而你会说"我有一百万件事要做，我没时间"。现在这个问题消失了，我想这会让很多产品负责人非常开心。这背后用的模型是 Sonnet 吗？

Varun Mohan：是的。拆解一下它最终是怎么运作的：我们有一个负责规划的模型，我会说目前 Sonnet 是非常非常好的规划模型，我觉得 OpenAI 的 GPT-4o 也不错。我们尽量让基于 Anthropic 的模型、也就是 Sonnet 模型，尽可能多地做高层规划；然后在内部运行所有必要的模型，为智能体做高质量的检索。你可以看到，智能体需要理解代码库其余部分在做什么。我们确保运行模型去把整个代码库切块、理解代码库。显然，如果有一个一亿行的代码库，把整个代码库发给 Anthropic 不是好主意。首先你根本做不到，那是超过 15 亿个 token 的代码，比目前最大的上下文长度还要大三四个数量级；而且从成本和延迟的角度你也不会想这么做。这是其一。

第二点，你看到模型能非常快地对软件进行编辑。我们有自己构建的定制模型，是在流行的开源模型基础上做后训练（post-training）得到的，能非常非常快地对代码库做这些编辑。你之所以想这么做，一是因为更快，二是——
这个模型还能把更多代码库内容放进上下文，所以在应用修改方面甚至可以比 Anthropic 的模型做得更好。我们的思路是：我们唯一的目标就是怎样做出最好的产品，怎样把天花板拉到尽可能高。需要的地方我们会去构建模型、训练模型；但如果我们在某项任务上不会做得好，认为开源模型更好或 Anthropic 更好，我们就直接用开源或 Anthropic。

Lenny：那你们构建的这些模型，是建立在开源模型之上的吗？

Varun Mohan：有意思的是，负责检索的那个模型其实完全是我们自己内部预训练的。不过很多不同的部分是基于开源模型的。负责编辑和自动补全的那个也是内部的——就是你打字时，我们会做一些自动补全相关的事，我很乐意演示，但我想很多用户都熟悉这个能力了。所以我们的看法是：我们在什么方面能做到最好？那我们就去训练。但如果我们不会是最好的，就不应该为了面子去训练什么东西。

Lenny：这可能有点太技术了，但关于你们用什么数据训练，有什么有意思的地方吗？

Varun Mohan：有的。我们从用户那里得到的一个有意思的东西——这也是我们在思考"我们凭什么能做得更好"时的出发点——是我们每小时大概能从用户那里得到几千万条反馈。我们得到大量关于他们喜欢什么、不喜欢什么的反馈，对于自动补全这样的东西，我们得到大量偏好数据。这些偏好数据很特别，它不像你在互联网上找到的数据，而是用户正在打字时的数据。想象一下你正在代码库里敲代码，敲的过程中代码是不完整的，不会是完整成型的形态，不像 GitHub 上的代码那样。但我们有大量这样的数据，所以我们处于独特的有利位置，能构建一个好模型，即使代码处于不完整状态也能补全，而现有的前沿模型接触到的这类代码非常少。所以在这种情况下我们会觉得，我们有可能做得好得多，我们会用手上所有的偏好数据去训练模型。

检索也差不多。有办法知道我们检索的数据对不对：用户之后有没有接受代码修改？那次检索到底是不是好的检索？这是我们能拿到的信号。所以基本上我们的看法是：如果某件事纯粹是代码规划，我们没有很好的理由能在这方面做到最好，我想不出一个自洽的论证。但对于更像是"这里有一个处于中间状态、非常棘手的代码库，需要做这些修改"这样的事，我们知道代码是如何演化的，或者说我们在几百万用户身上见过代码的演化，我们觉得自己能做得很好。

Lenny：我觉得有意思的是，这对于在这个领域胜出的公司来说是另一个差异化因素或者说护城河：如果你领先，你就会比其他公司拥有越来越多这样的数据。

Varun Mohan：是的，没错。当然我们还有招聘、财务等一般管理职能，还有市场营销，公司内部还有其他一些职能。

Lenny：有意思。你总会听到像 Anthropic 的 Dario 这样的人说"90% 的代码将由 AI 编写"，但与此同时，你们都在疯狂招聘工程师。这矛盾吗？会不会出现一个拐点，"好了，我们现在不再需要他们了"？

Varun Mohan：我觉得这真的取决于：在内部增加更多工程师，你能不能获得增量价值。首先，先把事实澄清一下：AI 写了超过 90% 的代码，并不意味着工程师的生产力提高了 10 倍。工程师花的时间不只是写代码，他们还要审查代码、测试代码、调试代码、设计代码、部署代码、在代码中导航，工程师要做的事情大概有很多。并行计算里有一条著名的定律，叫阿姆达尔定律（Amdahl's law），不知道你有没有听过。它基本上是说：如果你有一个任务图，有一条关键路径，你挑出其中任何一个任务，把它高度并行化，让它几乎不花时间，整个流程能加快的程度仍然是有上限的。简单说，假设你有 100 个单位的时间，只有 30 个单位花在写软件上，我把 30 变成了 3，那我只是把 100 变成了 73，这只是 27% 的提升。

所以从大局看，我们确实看到了超过 30%、也许接近 40% 的生产力提升。但对于我们要实现的愿景，即便我说公司长期会有 200 名工程师，那时大概也还是太少了。所以问题在于每个人能多获得多少生产力。

我再补充一点，关于这些大公司。比如说摩根大通的 CIO，她每年的软件预算是 170 亿美元，公司内部有超过五万名工程师。如果你告诉她："这些工程师中的每一个现在都能产出更多的技术了"——这实际上就是你做到的事——那么摩根大通或任何这类公司会做出的正确计算是：构建技术的投资回报率其实提高了，所以不在技术上多投入的机会成本也提高了，这意味着你应该投入更多，也许短期内你还会有更多工程师。当然这不是普遍成立的，有些公司对自己构建的技术量很满意，他们想构建的技术量有一个上限。但对于技术天花板非常高的公司来说，这并不意味着你停下来，实际上意味着你会招更多的人。

Lenny：这对工程师来说是一个很好的看涨理由。我觉得工程师这个职业的"煤矿里的金丝雀"，就是像你们这样的公司放缓招聘工程师的时候。但这并没有发生，大家似乎都在招人。所以我觉得这很有希望。我觉得如果你还在上大学，现在进入工程领域仍然是合理的。好，作为最后一个问题：在构建 AI 产品、构建 Windsurf、身处这个领域的过程中，你学到的最反直觉的东西是什么？

Varun Mohan：我觉得一件奇怪的事是，在网上，大家都对我们取得的短期成果非常兴奋，比如我们每周发布的东西，我们每几周会发布一次"Wave"。但实际上，我们在公司内部下的很多注，都不是三四周之后的事，而是三个月、六个月、九个月之后的事，那才是我们在内部做的。因为——Lenny，这就像我之前跟你提到的——我跟公司每个人说的一个目标是：我们应该每六到十二个月蚕食一次自己产品的现状。每六到十二个月，新东西就应该让现有产品显得很傻，甚至让现有产品的形态看起来很蠢。

所以这里有一种奇怪的张力：你想在市场上有一个产品，想渐进式地迭代、倾听用户、让它越来越好。但我会说，我们是市场上第一个智能体 IDE 产品，这是我们推出时的定位。我认为它的价值会非常快地贬值，除非我们不断重新证明自己，而且我们需要以用户甚至都没要求的方式去重新证明自己。所以这里有一种张力：渐进式改进让人觉得很安全，再加一个按钮，用户说"我希望有这么个下拉菜单来做 X"，但这不是我们会赢的原因，那几乎只是基本门槛。这些需求我们会决定做一部分，很多可能不做。但正是公司内部那些几乎会颠覆现有产品的长期投入，才是我们最终会成功的原因。你脑子里必须同时容纳这种奇怪的张力，因为你也不能完全不听用户，他们是你存在的理由。

Lenny：这让我想起最近的一位嘉宾，Captions 的 Gaurav 上过播客，他告诉我们他们公司有两张路线图：一张是真实的路线图，就是基于功能需求、用户反馈和数据等制定的常规路线图；另一张是秘密路线图，完全不受用户或数据影响，纯粹是他们自己押注世界会往哪里走。

Varun Mohan：没错。

Lenny：我很喜欢他把它叫"秘密路线图"，听起来很神秘，非常聪明。好，我还有一个问题，抱歉。你希望在创办 Codeium 之前就知道的一件事是什么？

Varun Mohan：说实话，我希望自己——也许"谦逊"这个词不太对——能接受更快地犯错。我总在想，我和联合创始人做决定的时候，我们总会聊到："真希望我们早几个月就做了这个决定。"我们总在聊这个。奇怪的是，外面的人看来都会说："哇，其实这个决定做得正是时候。"但在我脑子里，我总是在懊恼："要是我们早几个月做了呢？"我想部分原因在于，我嘴上可以说得很漂亮，说"你需要非理性地乐观、毫不妥协地现实"，但在实践中这非常难做到。因为你自己也会"喝自己的迷魂汤"，而如果你不喝自己的迷魂汤，你早上都起不了床。答案早就有了，不是这些创业公司中的任何一家，答案是微软会成为每一个软件品类的赢家，不是吗？就因为分发、资源和资本，他们会把每个领域都商品化。所以在某种程度上，明白"要更频繁地重新评估你的假设、更频繁地让自己进入不舒服的状态"，是我直到今天都需要提醒自己的事，大概也是我刚开始创办公司时不知道的事。我们是在零利率（ZIRP）时代的顶峰创立公司的，那时候大概一切看起来都会一飞冲天，我会说当时有很多非理性的自信。

Lenny：Varun，我们聊了这么多内容，多么精彩的对话，我光是坐在这里听你讲、问你问题就学到了很多。在我放你走之前，你还有什么想分享的吗？想给听众留下最后一点智慧吗？

Varun Mohan：说实话，我可以对这个领域做一些预测，但大概大部分都会错。我觉得最好的做法就是亲自上手把这些产品都用一遍。我认为最明显会发生的一件事是：在接下来一年里，任何能最大限度利用这些工具的人都会获得巨大的超额收益（alpha）。想想你有多少同事甚至不知道这些工具的存在，不知道它们能做什么，他们的生产力会低多少。所以我只想说：尽可能快地、尽可能深入地亲自上手。

Lenny：你说亲自上手，基本上就是下载 Windsurf，开始写代码，让它帮你构建东西？

Varun Mohan：是的，做应用，做应用，开始用它，也许甚至用来做线框图、修改你现有的代码库。你大概可以用一些他们根本没预料到的方式，成为组织的力量倍增器。想象一下，如果你是一个能非常快地修改代码库、自己开始推送修改的产品经理，你大概会赢得工程同事极大的尊重，也能因此完成多得多的事。我觉得到那时就没有天花板了。

Lenny：我觉得你说的这一点被严重低估了。有能从零构建东西的应用，也有像这样能编辑你现有代码库的应用。如果你是——你们合作过的、可以公开的、人数最多的公司是哪家？

Varun Mohan：就说摩根大通吧，他们有超过五万名开发者。

Lenny：好，那你可以是摩根大通的一名产品经理，说："我有个问题要解决，我想推动这个指标，我要改注册流程里的一个步骤。"你直接打开 Windsurf，告诉它你想做的事，然后能直接推送到 GitHub 吗？

Varun Mohan：是的，其实你能做的更多。

Lenny：好，还能帮你提一个 PR。这太疯狂了，未来已经失控了。好，最后这一点太重要了，因为我觉得大家可能没意识到。他们看到这些别的应用，会觉得"哦，就是做做原型"。但这是真正能落地干活的东西。

Varun Mohan：是的。Lenny，想想你最尊重的那些人——至少我是这样——他们是那种不管头衔是什么，能动性和产出从最底层的细节一直到最高层的战略都近乎完美的人，他们知道什么时候该一路深入到底。我觉得有时你会看到有人谈论角色，非理性地觉得"因为我是这个角色，所以我不能碰这个"。而现在一切都是开阔的海洋了。我觉得这是一个机会，几乎可以一路深入到细节，也可以一路上到顶层，在每个层面都发挥作用。
