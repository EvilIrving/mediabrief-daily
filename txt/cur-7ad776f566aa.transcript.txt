Simon：好的。基本上有点像考场。你坐下来，五个小时，有一台电脑、一个编辑器、一个 C++ 编译器，差不多就这些。桌上通常有大约三道题，题目类型差别很大。比如我遇到过的一道题：告诉你机器上有五个目录，一个目录里是印象派画作的图片，另一个是立体派的，依此类推。然后你得自己写一个程序，用这个小小的训练集，对一张从没见过的图片进行分类，归入这五类之一：“这是印象派画作，这是立体派画作”，等等。这就是一种很抽象的题。

解法之一是看像素之间的平均颜色差异，因为你会发现这个指标在不同类型的画之间差别很大。像立体派那样有大块黄色、绿色区域的，平均颜色差异就比更印象派的作品小得多。

这是比较自由的题，一种开放式、临时性的问题。但题目也可能更偏算法。比如我记得一道：想象一个十字路口组成的网格，像曼哈顿那样几乎是完美的网格，每个路口都有一家咖啡店，每家咖啡店都有一个一定半径的 Wi-Fi 信号，也有一定的带宽。题目说：“假设你可以同时连接多个 Wi-Fi 并在所有 Wi-Fi 上下载，你站在哪个路口能获得最大带宽？”这就是更偏算法的题。

然后你写出解法，把 C++ 程序上传到所谓的评测机（judge）——那是你唯一能访问的东西，跑在内网上——然后拿到一个 1 到 100 分之间的分数。通常只有把题解得完美而且非常快，才能拿 100 分。很多时候你可以用一个很简单但很慢的算法解题，拿一些分，比如 30 分；而如果想出快得多的算法，可能就能拿到 100 分。所以你就坐在那里熬上五个小时，努力攻克这些题，同时权衡：“我该在这道题上多花时间吗？我做出来了吗？还没有？”那绝对是我人生中最艰难的几个小时之一，坐在那些考场里……但也非常有趣。

Adam：对。你想出了很多不同的工程方法、技巧和奇特的解决方案……分享一两个你的“绝招”吧——不是零日漏洞那种 exploit，而是你这些年在 Shopify 做的事。你在节目开始前提到在做一些 MySQL 相关的东西……当系统规模很大时，你得做一些其他工程师不必考虑的事，因为你会碰到某些技术的边界，你这些年肯定遇到过。

Simon：是的。回顾历史，我想到两个。一个大概是我最早做的、也是最大的项目——我们的“pod 化”项目。我们之前已经做了分片，也就是把数据库拆成多个。那是在我加入前后做的，不是我做的，是其他团队。但我们想更进一步，让一组组店铺共同存在、共同隔离，而且这些店铺应该能在多个数据中心运行。因为在那之前，我们只有一个数据中心，所有店铺都在那个数据中心里活跃。如果出了严重问题，我们就把所有店铺故障转移到另一个数据中心。但我们想把这些店铺隔离开，让它们可以同时在多个数据中心运行。为了确保没有任何东西依赖“所有东西都在同一个数据中心”这个前提，投入了大量工程工作。这是我几年前和一个非常棒的团队一起做的最大项目之一。

今年让我最兴奋的工作之一是：我很多精力都放在容量规划和韧性上，基本上就是要搞清楚，当一个系统变慢时，怎么确保它不会把整个系统堵死。数据库变慢比宕机糟糕得多，因为它会堵塞系统，在各个地方造成排队，引发更多连锁故障。

我们在这方面取得了很大成功的一项技术叫“负载削减”（load shedding）。它的思路是：当系统过载或接近过载时，你要开始对放行进系统的流量类型排优先级。所以如果有一家店铺遭遇大量恶意流量或某种复杂的 DDoS 攻击，我们要确保在丢弃其他商家的流量之前，先开始丢弃那部分流量，以保护整个平台。

我们在这方面做了很多工作，尤其是在边缘层，让负载均衡器能给流量排优先级，确保商家尽可能多地在线。但我们想更进一步，开始在数据库层面也提供这种能力。

如今数据库领域让我非常失望的一点是：很多公司都是 SaaS 公司，是多租户的，它们把所有这些租户跑在一个或少数几个数据库上。但其中某个租户可能对数据库造成不成比例的影响。他们可能有个 API 客户端，请求量比其他所有人都多；或者因为业务方式的某种特殊性，有一家商户有一百万个订单。所以商户、或者说你的客户，有各种基数差异和独特性。这不只是 Shopify 的问题，而是 SaaS 的问题。因为 SaaS 让你获得了在同一套基础设施上运行的成本效率，但我觉得基础设施还没真正跟上这一点。

在今天的数据库里，你不会为每个租户创建一个 schema。如果你有足够多的租户还这么做，MySQL 会冲你尖叫，因为它根本不是为此设计的。所以它并没有给你提供任何能做到这一点的原语。默认情况下，你设计数据库的方式根本就没有为多租户做好准备。所以回到单个租户压垮系统的例子，MySQL 也好，Postgres 也好，没有任何一个数据库有好的机制在这些商户之间给流量排优先级。

我们一直在研究的是：我们发现在 MySQL 协议里，你可以随查询返回一个任意字符串。所以我们想：“如果在返回查询结果的同时”——结果可能是一堆客户、一堆订单，什么都行——“我们还把这个查询消耗了多少资源也返回给应用呢？”CPU 上用了多少纳秒？多少 I/O 时间？往 MySQL 的页缓存里加载了多少内存？这个查询有多昂贵？就是你在慢查询日志里会看到的那类信息。

你可能会想：“看这些信息有什么用？”想象一下，API 限流不再是从帽子里随便抽出来的数字，比如“你每秒可以发 100 个请求”，而是真正基于数据库的状况，以及你的 API 调用引发的查询到底有多重。

在外部 API 上，比如 GraphQL，正确地做 API 限流极其困难，你几乎总是会低估或者高估查询的复杂度。但如果我们构建的系统和数据库在这个层次上内置了多租户能力，能把信息反馈给 API 限流，那会大有帮助。

你还可以把它反馈给负载削减机制，于是你能看到：“哦，这个租户在数据库那边表现很糟糕，尽管他们只发了很少的查询。”所以我认为这是更多数据库应该采纳的一件很重要的事，我们一直在开发一个 MySQL 补丁来暴露这些信息。

Adam：有意思。会不会有可观测性的问题，或者说海森堡原理——在观察慢查询本身的同时，如果“这是该查询的指标”随查询一起返回，你是不是在给本已很慢的查询增加负载？会不会让它失去意义？

Simon：其实不会。在我们看过的基准测试里，开销大概是 1% 或 2%，真的一点都不糟，而且是个很稳定的常数因子。你只是做一点簿记，看 MySQL 里那个线程在 CPU 上花了多少时间，并没有增加什么显著的负担，通常只是一次上下文切换。

Adam：不过这种东西得在上游实现……那你们是在跑一个 MySQL 的分支，还是仍处于实验阶段，情况如何？

Simon：对，我们在维护一个内部分支。这还没有在所有分片上投入生产。在推出你自己写的一堆 C 代码补丁之前，有很多尽职调查要做。但我们开始更大规模地推出它了。而且我们不只想把这些信息暴露给上游，以便在数据仓库里做数据分析、基于它做 API 限流，现在我们还可以在 MySQL 内部构建一个负载削减器来给流量排优先级。这样它会选择最有价值的查询，而不是那些最容易压垮系统的查询。

Jerod：Simon，我们聊到你进入 Shopify 时没有大学学位——当然有学习，但需要边做边学很多东西……而你在这方面非常有意识、非常自律。你想出了不同的学习方法，并把它们构建成一套系统。事实上，我们第一次注意到你，是在 Superorganizers 那个 newsletter 上，有一篇非常好的文章叫《如何把自己变成一台学习机器》（How to Make Yourself Into a Learning Machine），讲的全是你和你想出来的那套系统。

由此衍生出很多东西，但最值得一提、也是最近的，是你提出的“餐巾纸背面的数学”，也就是从第一性原理出发快速估算、理解系统，你一直在外面讲这个……这真的很有意思，它让人们能够非常快速、简单地——也许是简单，我们会聊到——弄清楚一个系统的某些事情，比如它应该有怎样的性能、应该花多少钱、应该有多大吞吐量，而不必说“我回头再告诉你”，或者花六个小时去算数字。

所以先跟我们讲讲你以这种刻意的方式学习的愿望，以及你在学的所有东西吧……你读书，基本上确保自己记住读过的东西，把它简化，但细节里有很多有意思的东西。然后再讲讲餐巾纸数学是怎么进入这个等式的。

Simon：好的。有意思的是，我们无意中以竞赛编程开场，而这些实践正是来自那里。做竞赛编程时，在比赛中实现一个解法，你知道根据复杂度大概要花 30 分钟到一小时。会有很多差一错误（off-by-one），编辑器、linter 之类的帮不上什么忙……所以你真的得事先知道程序会有怎样的表现，会有多快，能给你拿多少分。

幸运的是，这些比赛是非常受控的环境，所以你知道，如果只需要一个 O(N) 的算法，大概表现会不错。如果输入是 10,000，而你用的是 O(N²) 的算法，要在一秒内跑完就开始有麻烦了。所以在那里，餐巾纸数学非常简单，也非常受鼓励。任何关于竞赛编程的读物都会大谈这种关于算法能拿多少分的策略。

进入 Shopify 后，我有点把这个丢下了，那里并没有太多需要它的地方。对大多数程序员来说，日常编程里没有太多算法。但随着时间推移，我越来越多的时间花在评估系统会有怎样的表现、做技术评审、设计系统，而不是实现其中的部分，于是我基本上又重拾了这个习惯。你可能身处一场会议，和其他人讨论，有人说：“也许我们可以这样做。”另一个人说：“那大概太慢了。”又有人说：“那我们为什么不试试，一两周后再开会看看效果？”然后会议散了，那个人花一两周去做，你们回到会议室，那个人回来说：“哦，太慢了。”而最初提议的人说：“什么？你实现错了。我来帮你。给我一两周，我们再回头看。”

你能看出这个故事会怎么发展……你们来来回回花上一两个月。但我觉得只要稍加练习，你就能提前估算系统的性能，开始形成关于系统应该有怎样表现的预期。继续用 Ruby 或 Python 而不是 C++ 写这个合理吗？用这个数据库做这类操作合理吗？我们能在 MySQL 之上构建这个吗，还是从根本上需要一种不同的数据结构？

我非常坚定地相信，你应该自下而上地建立理解。比如我现在在做搜索。我对搜索一无所知，但我做的第一件事是去学倒排索引是怎么工作的：我会怎么实现它？Lucene 是怎么实现的？怎么做 top-k，也就是为一个查询找出最好的 k 篇文档，那是什么样子？它怎么高效地做到？在磁盘上是怎么布局的？用了什么启发式方法？然后从那里往上构建。因为这样一来，我的问题就不是“哦，Elasticsearch 有没有提供这个 API？”，而是思考：从根本上说，倒排索引能执行这个操作吗？会是什么样？要花多长时间？和在 MySQL 里做相比如何？哦，倒排索引不只擅长全文搜索，也擅长合并任意集合，这又让你发现其他应用场景。

所以我发现这非常有价值——你现在可以走进我刚才描述的那场会议，说：“等一下……我们把这些场景画出来，然后做一些信封背面的计算。”

我最喜欢的一件事是，我在办一份叫 The Napkin Math Newsletter（餐巾纸数学通讯）的 newsletter。你搜“napkin math newsletter simon”应该就能找到。基本上，这是我每月一次的餐巾纸数学练习。我给自己出题……比如我会给自己出这样一道题：“一个 MySQL 从根本上每秒能做多少个事务？1000 个？10000 个？”于是我坐下来，试着构建一个关于 MySQL 如何应用事务的简单模型，自下而上地思考。
