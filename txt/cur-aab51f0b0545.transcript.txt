主播：大家好，这里是 AsyncTalk，一档由前端开发工程师随便聊聊业界发展和前端开发技术的播客节目。距离上期播客发布其实已经有一段时间了，主要原因肯定是我比较懒，另外也是因为工作比较忙，平时还有一些其他的 side project 在做，所以更新频率确实有点问题。现在也没什么人督促我，所以频率就没有那么急。

好的，今天我想聊一个之前大概提过的话题：状态机。不确定大家有没有关注我的其他社交媒体，我之前有一段时间说过，我最近在做一个非常非常庞大的项目，前端代码量达到了 200 万行。前段时间我听到一位同事在做另外一个技术方案，我突然想到，状态机非常适合那位同事的业务。另外，前段时间我也在社交媒体上发过，我重构了 Clerk 的一段登录逻辑，也是拿状态机来重构的，它让整个流程变得非常清晰，维护成本也变得非常低。所以今天就以状态机作为引子，同时也分享一些我这些年开发的想法，我觉得还是蛮有用的。

第一点，我觉得我们现在都在用框架，React、Vue 这些。我相信听我们节目的大部分朋友都是这样。即使你是后端，也是用 Laravel，或者如果是 Go 的话大概是 Gin，还有 Java 的 Spring 这类框架。这些框架有很好的设计，我承认它们在很多方面的理解和见解都很好。但我觉得不能过度依赖它们：它们的设计很好，但只适用于某些场景。

拿大家比较熟悉的 React 来举例。实际上并不是所有业务都适合用 React Hooks 那种更新方式来做。Hooks 的更新其实非常简单。以前我们的组件是有生命周期的，对吧？有初始化、有 props 更新、有 state 更新，还有 componentDidMount、componentDidUpdate 这类生命周期。Hooks 出现之后，整个生命周期的概念就没有了，你只需要关心 state，state 变了就触发一个 useEffect，或者用 useCallback 去更新一些 callback function，或者用 useMemo 去更新一些值。这个设计我承认非常好，但你没法拿它做非常复杂的链式状态变更。大家设想这样一个场景：状态 A 变的时候，我需要改状态 B；状态 B 变的时候，要改状态 C；状态 C 变的时候，又要改到状态 D。这时 D 和 A 之间的关系就很难管理了，过两个月你都不知道 A 和 D 之间有什么关系。对于这种状态，其实不太应该拿 React 那套思维方式来解决。

还有一点是设计模式。我个人其实不是很推荐套用设计模式，我更推荐用各个 library 建议的方法，或者业界的一些 best practice——当然设计模式也算是一种 best practice。我觉得现在很多框架在设计上会尽量避免让你主动去用这些设计模式。但我还是觉得大家应该再学一遍设计模式，它有很多设计蛮好的，有很多非常精彩的部分能帮助我们做抽象、做更好的设计。

对应的观点就是，你不能无脑地只是写代码：来了一个需求，看了一下，OK，我写面条代码，花三天时间写完了。但如果你花六天时间，前三天好好想一想它的设计，说不定会更好。当然，这里我完全排除 PM 或者你的 manager 各种压你的情况，我想说的是，如果你要做好一件事情，还是应该多想想。

另外一点是状态机。我觉得现在大家用状态机用得不是很多，一方面是场景确实不够，大多数人接触的业务状态相对还是比较简单的，碰到需要状态机的情况比较少。而我们碰到复杂状态的时候，就像我刚刚说的，不动脑子——包括我自己也是——直接 useState 开干，最后可能花了三天写完，自己写了一坨东西也不知道是啥，反正能用，能用就交了。包括我自己反思一下，我们应该多想想怎么先把这样一个东西设计好。

再一点是同步。我相信绝大多数听我们 AsyncTalk 的朋友都至少很了解 JavaScript。就像我们的名字一样，我们是 AsyncTalk，对于 JavaScript 领域来说，所有东西都是 async 的。据我所知，JavaScript 的 API 里很少有那种同步的、要卡死主线程做强计算的东西，大家正常写的话其实很难写出那种同步状态，当然你要强行写 CPU 密集型计算也行。我想表达的是：同步其实并不是一件坏事，尤其是在可能出现竞态、出现状态冲突的时候，同步可以非常有效地帮你避免这些问题，很大程度上帮你规避很多需要处理的状态。代价是这段代码的性能可能会稍微差一点，这要看个人取舍。但同步不是一件完全的坏事，大家也不能走极端，说任何事情都必须异步、同步就是坏的，不是这么简单。

我还有一个观点：如果你做一个稍微大一点的项目，肯定逃不开同步这种状态，至少也要做一个"假同步"——中间所有步骤都是异步的，但你可以用各种 await 把它们串起来，形成一个假同步的状态，这一定是没办法避免的。当然我刚刚的例子不太好，因为拿 Promise 做假同步，情况复杂的时候是做不来的，因为还需要处理各种 switch 之类的状态。我的意思是，你不能完全拒绝同步，它不是一件完全的坏事。

还有一点，关于中大型项目，我觉得你一定要考虑状态机。就像我刚刚的例子，如果你直接拿 useState 硬写一个复杂的状态，当时或许能写好，但三个月之后，维护这段代码的人就很痛苦了。所以一个中大型项目，你一定要在前期设计时想一下：这个地方如果用状态机，整个流程大概是怎样的，会不会让东西变得更简单、让维护更简单一些。

说到这里，我要强调一点：我认为状态图非常非常非常重要。你从状态 A 到状态 B，中间发生了一些事件，调用了一些 side effect 方法，还有一些 guard，就是拦截之类的东西。如果你靠手写 useState 来做这种保护，想象一下代码会变得非常难看。这时如果考虑使用状态机，用它的状态图来描述流转和事件触发，会非常显著地降低维护成本。即使第二个人完全不懂你这块业务，只要拿到你的状态机，自己看一下整个流程，或者亲手跑一下，很快就能明白这个流程是怎么回事。所以状态图非常非常重要。

OK，前面讲得比较抽象，我一直在说事情该怎么做，那有没有一个例子呢？可以拿我很多年前写过的一个小需求来举例。那是一个和机器人聊天的业务，大概逻辑是：用户进到一个页面，页面调用后端 API，等它返回。返回之后会有三条数据，分别是三条语音，你需要等它播放。播放的时候，用户不能在输入框做任何操作，也不能暂停语音，但语音转出来的文字可以点击，查看解释之类的东西。等播放完成之后，底下的输入框会自动打开，它是一个语音实时输入，所以会自动开启录音，等待 WebSocket 连接触发事件。检测到语音输入完成后，你需要主动关掉录音状态；同时它也要能接收用户点击"我录音结束了"。中间其实还有很多细节，我大概就说这些。

我觉得大多数人——包括我一开始也是——就拿 React 的 state，把它完完全全堆在 View 层里做。后来，可能是跟同事聊过之后，我把它改成了用 redux-saga 来做。redux-saga 有个非常好的点，就是它和这个业务很契合。因为你听我刚刚讲完就知道，这个业务其实是一个比较标准的线性流程：用户进来，调 API，等 API 返回；之后三条语音一条一条播报，这中间可以切到另一个状态，就是用户点击屏幕查看解释。这条状态也非常简单，只是能打开、能关闭，对吧？所以它可以作为另一个非常小的事件来处理，用户其实仍然处在第二个状态里。接下来我们会调用系统录音，等待录音结束的事件。你可以看到这个流程也是非常线性的。所以当时拿 redux-saga，用一种非常线性的模式去等待各种事件、调 API、等 API 返回、dispatch action。这样在业务层，也就是 View 层，只需要监听那几个状态的变化来做展示。

我当时的实现就是这样，到现在我都觉得那个设计挺不错的。但听众朋友也许有更好的方式，也可以交流一下，写在评论区。这个东西其实也可以拿状态机来做，具体要看你们业务的设计。用状态机的话，你可以看到它其中有很多状态步骤，比如在播放状态中屏幕是锁着的，那就需要一个类似 playing 的状态，视图层根据这个 playing 状态决定界面怎么展示。视图层同样是订阅某些 state，但这个 state 变成了"状态"，而不是"结果"。不确定大家有没有听明白，或者我有没有讲明白，但我觉得这个场景还是蛮好的，大家也可以想想有没有更好的解决方案。

其实这期节目我并不是要硬推 XState 这样的状态机方案，而是说大家不能太定式思维。我们不能接到一个需求就直接写代码开干，这肯定不太合适。你需要一些设计、一些想法，需要更多时间好好思考整个上下游链路，思考怎样让代码不仅做得快、做得好，还要照顾它的可维护性、长期发展和 bug 率。

我还想说一点。我接触过一些朋友、同学，他们会觉得前端的天花板比较低。但就我刚刚聊的这些思路、设计来说，我觉得前端其实还有不少发展空间。大家可以多想想，也许通过这一点一滴，我们可以有更好的进步。
