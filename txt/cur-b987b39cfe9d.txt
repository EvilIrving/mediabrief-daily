Dan Abramov 这篇长文从一个反直觉的设想开场：API 返回的 JSON 本质上就是在给某个组件传 props，只是没写明传给谁；如果直接让 API“返回组件”，组件和 API 的关系就倒了过来，像好莱坞原则——不是组件调用 API，而是 API 返回组件。全文分三部分，从两条看似无关的历史脉络出发，最后汇合到 React 服务器组件（RSC）。

第一部分“作为组件的 JSON”从 REST 讲起。REST 资源按数据模型组织，而界面按屏幕演进：点赞按钮想显示“你、Alice 和另外 13 人赞过”，就得要么让客户端多次请求、拼接数据，形成瀑布，要么不断往通用接口里塞特定字段，接口变得臃肿又不敢删。作者认为根本矛盾在于 UI 需要的数据跟着 UI 变，REST 却试图独立于 UI。出路是在服务器上加一层专门为屏幕服务的“ViewModel API”，也就是 BFF（为前端服务的后端）：每个屏幕一个端点，在服务端一次往返组装好所需数据。这层还能继续拆分，LikeButtonViewModel、PostDetailsViewModel 等函数各自负责屏幕的一块，再像组件一样组合；通过内存缓存去重，重复调用 getPost 也无妨。参数需要从顶层一路传下来，类型也要和组件对齐。这样做解决了瀑布和接口臃肿，但留下一个缺口：ViewModel 和它供给 props 的组件之间没有直接连接。

第二部分“作为 JSON 的组件”换一条路：从九十年代的 HTML、SSI 和 CGI 说起，那时服务器本来就在一次往返里返回一个屏幕的全部“数据”（HTML 也是数据），并且可复用、可传参。PHP 的问题是把标记当字符串拼接，社区大多转向 Rails 式 MVC 和模板，Facebook 却发明了 XHP：标记是可组合的对象，标签渲染标签，于是重新发现了函数组合。异步 XHP 更进一步，让标签自己加载数据，组件自包含，而整屏仍只需一次往返；配合兄弟节点并行、BigPipe 分块输出、批量读取与共享缓存，这种模型极其高效。它的死穴是只能输出 HTML，无法在不丢状态的前提下就地刷新，于是 React 接管了交互界面，UI 和它需要的数据又被拆进了不同代码库，GraphQL/Relay 也只部分弥补。但标签既然是对象，就可以序列化成 JSON，发给原生应用去构建视图。这正是 Instagram、Airbnb、Uber、Reddit 等使用的“服务器驱动 UI”（SDUI）：端点返回由客户端原语组成的 UI 树，相当于从服务器向客户端传 props。

第三部分把两条线合并。作者列出“异步 UI 框架检查清单”：组件丰富可交互；组件能一键跳转到计算其 props 的服务器逻辑；UI 片段连同数据依赖真正自包含、可随意嵌套；任意屏幕一次往返到达，并从机制上杜绝瀑布；支持完整交互，服务器数据能在不丢客户端状态的情况下就地刷新。做法是让 ViewModel 不返回裸 JSON，而返回带客户端组件的 JSX 标签，例如 LikeButtonViewModel 返回 <LikeButton …/>，序列化后 JSON 里写明接收的组件，生产和消费 props 的代码之间只隔一次 Ctrl+点击，还白得类型检查。再约定 ViewModel 可以用 JSX 嵌入别的 ViewModel，发送前递归展开，就像 XHP 递归渲染；把 postLikes 改名为 children 后，服务器部分和客户端部分可以互相任意包裹，所有服务器取数仍在一次往返内完成，客户端拿到的 props 都已“预先算好”。路由也可以写成 ViewModel，外包一个客户端 <Router>，导航时重新请求 JSON，甚至按路径段细粒度地并行准备和刷新。

最后揭晓：这些 ViewModel 就是服务器组件，组件就是客户端组件。之所以都叫组件，是因为它们同样承接自异步 XHP，且常被两边共享。从 'use client' 模块导入得到的只是一个“如何加载”的引用，JSON 中带着加载指令，所以 RSC 需要打包器集成（作者推荐不绑框架的 Parcel 实现）。坚持输出 JSON 而非 HTML 很关键：可以就地重新获取而不丢状态，可以面向 Web 以外的平台，也仍能在服务端把客户端组件一并跑一遍生成首屏 HTML，而 HTML 无法反推回 JSON。作者承认 RSC 烧脑、需要由内而外地思考，工具也还在演进，但认为它让代码模块化、执行却合并为一次往返，是值得的方向。文末附一份去掉“ViewModel”叫法的完整示例代码。
