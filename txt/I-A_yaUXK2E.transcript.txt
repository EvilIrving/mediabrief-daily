第一部分：推理系统

（万晨）我们推理团队现在已经提供了对 DeepSeek V4 非常全面的支持，感兴趣的话可以直接扫一下这个二维码。我们提供了一个开箱即用的推理框架，可以针对不同的硬件、你想跑的模型以及各种不同的场景，基于这些设置去选择你想要的配置，这里也提供了启动指令。另一方面，我们团队也提供了训练框架的支持，待会儿悦明同学会做介绍。我们现在的适配已经能做到所有 Hopper 系列、Grace Blackwell 和 Blackwell 的硬件都能支持。

接下来讲一些技术细节。首先带大家简单回顾一下 DeepSeek 新的计算流程。对我们做框架的人来说，最有挑战的部分是它提出了一个非常新的注意力机制。在计算过程中，对于一个新进来的词元，它需要处理两类注意力。一类我们叫 SWA，sliding window attention，也就是它只会看最近的几个词元存下来的 KV Cache。另一方面，在不同的层中，它会在另外两种压缩过的 KV Cache 里选其中一种。第一种叫 Compressed Sparse Attention，也就是 C4，它会把每四个词元压缩成一个，计算时在上下文中做一次分层的选择，挑出最有影响力的词元，只对它们做注意力计算。另一种是 C128，对这一类我们做全注意力计算，也就是所有压缩过后的词元都会参与计算。

这对框架来说是非常新的挑战，因为这里面有很多种注意力机制、很多种 KV Cache。而且为了维护这两类压缩注意力需要的 KV Cache，我们还要再维护另外两份正在进行中的压缩状态：对 C4 来说，每算出 4 个词元才能做一次压缩；对 C128 来说，每算出 128 个才能压缩一次。所以总的来说我们有五类状态要维护：sliding window attention、C4、C128，以及 C4 和 C128 各自对应的进行中的压缩状态。

这一页 slide 描述的就是我们怎么维护这么复杂的状态，我们叫它 ShadowRadix。总的来说，我们会维护一个虚拟的列表，做其他各种操作时，比如 KV Cache 的搬运、Radix Cache 的查找，只需要检索这个虚拟地址。这个虚拟地址会结合你现在是第几层、需要哪种 KV Cache，去检索对应的状态。比如我们在算一个新词元时，会检索它 sliding window attention 里最近的部分；更前面的部分虽然还有对应的索引，但在物理上已经被删掉了，因为它们对计算不会产生任何影响。对后面两类压缩过的 KV，我们有另外一套映射机制。对于进行中的压缩状态，我们用一种环形 buffer 的技术，保证内存使用量是有限的。

除了这套注意力状态的维护框架，我们还做了很多内核层面的优化。比如 DeepSeek V4 的 KV 压缩过程有这么一套流程：先从显存里读很多数据，做加法、softmax 或者点乘之类的计算，每一步计算都要读写显存，最后再把结果存回去。我们发现这里总共有五次显存访问。我们做的优化是把中间三个和计算相关的操作合成一个算子，这样从前到后只需要两次显存访问。这对 GPU 计算来说是非常重要的优化，因为它能极大减少显存访问次数。

除了压缩过程的算子优化，我们还对 TopK 做了优化。刚才提到，有一类 attention 需要对前面所有词元做一次分层计算，然后只对其中最相关的部分做注意力计算，这里就涉及 TopK。对非常长的上下文，比如输入已经有 100 万个词元，TopK 计算非常慢。我们测下来，只算一个词元的 TopK 就需要大约 100 微秒。我们提出了一个叫 Lightning TopK 的算子，很巧妙地改变了计算流程来增加并行度。实验证明，用 Lightning TopK 替换原来基于纯 PyTorch 实现的 TopK，可以把计算时间从 100 微秒优化到 15 微秒。原来的 100 微秒是很难接受的，因为模型有 60 层，每层都可能需要这么一次操作，加起来就是 6 毫秒，这会极大限制推理速度。

另一方面，我们提供了非常灵活的混合并行支持。对长上下文推理，我们提供了上下文并行（CP）方案，把上下文分到多张卡上计算，均摊内存和计算开销。对这个新的注意力架构，我们也支持张量并行，但需要注意，它并不天然支持张量并行，因为底层内核对输入形状有要求：注意力头的数量如果不是 64 的倍数，就没法调用底层内核。所以我们采用 padding，也就是补齐机制，不是 64 的倍数就补到 64 的倍数，这样就能在张量并行下计算。对混合专家部分，我们也支持专家并行以及大规模部署。SGLang 支持这些并行方案的各种排列组合，欢迎大家去尝试，去 hack 我们的 engine。

另外，我们的推理已经支持 PD 分离。LLM 计算可以分为两部分：一部分叫 prefill，也就是对输入进行编码，可以理解为 AI 在做阅读理解、理解你在说什么；另一部分叫 decode，也就是生成自己的 token，可以理解为写作，生成要给你的答案。我们一般会把这两部分分到两类集群上。这对 DeepSeek V4 的实现来说也有一定挑战，我们的同学花了很大功夫去做适配。

（主持）直播间有位同学问：PP 和 CP 应该如何选？

（万晨）这是上下文并行和流水线并行的区别。我的理解是，如果你在单机内计算，我们会更喜欢上下文并行，因为机内通信很快。如果有多台机器、涉及跨机传输，可能会选流水线并行，这样能尽量节约跨机通信：第一台机器算前面一部分层，第二台机器算后面的层，它们之间只需要一次跨机传输。但流水线并行的问题是没法充分利用计算资源。比如我有 8 张卡，用流水线并行可能一次只有其中一部分在算；用上下文并行，一次可以用满 8 个计算单元。

（主持）还有一个问题挺好的：这些 KV Cache 的形状是不是统一的？如果不统一，SGLang 在显存管理中怎么规划对齐策略？

（万晨）非常好的问题。大叔能不能翻回我们讲 KV Cache 的那一页。因为这里涉及非常多种类的 KV Cache，不同计算流程需要的 KV Cache 大小是不一样的。举个例子，对于特别短的请求，压缩类的 buffer 需求不多，而 sliding window attention 部分需要的量一直是常量，几类大小可能接近均匀分布。但对非常长的上下文，压缩类 buffer 需要的资源会多得多，因为它和上下文长度成正比，而 sliding window 那部分仍然是常量。也就是说，不同的上下文长度下，各类缓存需要的内存比例不一样。所以在 SGLang 里，我们提供了一个参数，让用户根据实际请求情况来配置。一开始是静态预分配的内存池，在实时计算过程中我们也可以动态调整。

（主持）为什么 DeepSeek 的推理不建议开 TP，是 DP 有什么特殊优化吗？

（万晨）这就是我刚才提到的另一点：底层算子对张量并行不是很友好，它要求每张卡分到的头数是 64 的倍数，按头切分可能就满足不了这个约束，所以需要额外的补齐机制。但我需要强调的是，张量并行虽然会引入一些额外计算，在请求数量比较小、或者追求低延迟的场景下，它仍然是非常好的选择。

（主持）最后一个问题，也是我比较好奇的。DeepSeek V4 的 KV Cache 相比前一代做了相当大的压缩，100 万个词元只需要不到 10 GB 就能存下。这是不是让我们有更多机会把这些东西存到 CPU 内存甚至硬盘上？你们在优化中有没有感受到这可能是未来的趋势和机会？

（万晨）这个我们已经支持了，就是 HiSparse。经过验证，它可以带来最多 3 倍的上下文容量和性能提升。我们也觉得从长远来看这确实是一个优化方向。现在各种 agent、coding 类模型应用都非常流行，这些应用对上下文的要求越来越高。在这种情况下，有限的显存没法存下所有的 KV Cache，就需要一些 offload 的过程，把不那么需要的 KV Cache 放进 CPU 内存。

第二部分：强化学习训练（Miles）

（主持）非常感谢万晨老师。我们可以进入下一个环节了。SGLang 除了推理方面的优化，相比其他方案不一样的是，我们同时还提供了 RL 上的支持，相当于你直接就可以拿自己的数据在上面做微调、做优化，让模型适用于你的使用场景。下面邀请下一位同学来介绍 Miles 相关的开发。

（悦明）我觉得 Day-0 支持 RL 这件事本身可能是一个比较新的尝试。以前大家都只在推理上做 Day-0，在训练上做 Day-0 还是比较 challenging 的。先简单科普一下为什么训练做 Day-0 比较麻烦。一是推理时可能只需要实现一遍 forward kernel、一整个 forward pass，但训练里除了 forward，还要做 backward 的支持，比如想写一个 kernel，forward 和 backward 都要实现。还有很重要的一点：推理时大家可以通过测 benchmark 知道实现是否正确，如果掉点，大概率就是有错。但训练里没有一个标准的 baseline，整个训练 recipe 包括一整套实现是否正确，都需要想办法验证，需要比较长期的实验结果，比如训了几天，它涨点了，我们才能判断系统大致是正确的。这导致整个 debug 成本非常大。所以我们希望帮大家减少这部分成本，不用再花很多时间去 debug 自己的训练系统，在第一天就能用上一套完整的 RL 系统。

我们做的事情大概分成三部分。

第一部分是训练后端的实现，也就是在 Megatron 里的模型实现。就像刚才万晨讲的，DeepSeek V4 是一个非常复杂的模型，有好几个 compressor、indexer 等组件，包括 mHC，这些结构在 Megatron 里都没有原生支持。我不太清楚最新版本有没有支持 mHC，但像 compressed attention 肯定是没有的。所以我们需要把这些 operator 都在 Megatron 里实现一遍，本身就是比较大的工作量。并行方面，我们支持了 Megatron 里的六种并行：DP、TP、SP、EP、PP 和 CP，已经全面支持。DP 非常简单，直接就能开；EP 因为 MoE 部分没有很大改变，也可以直接开。TP 和 SP 是一套的，主要在 compressed attention 里实现，用的是 Megatron 的 primitives，但我们需要调通整个系统，让 TP 和 CP 能同时开，保证一整套正确、不出 bug，这花了一些时间。PP 方面，我们稍微改了一下 Megatron 的 PP 代码，因为用了 mHC，hidden states 从三维变成了四维，所以要改一下它的 P2P 传输。CP 可能是其中最复杂的，因为 compressor 里有一些非常复杂的变换，特别是 C4，也就是 paper 里叫 CSA 的那部分。它用了一个 overlap 的变换，相邻两个压缩 token 所用到的原始 token 会有重叠。因为这个机制，直接套用一般的 CP 实现就会出问题，所以我们做了特殊处理：先 all-gather，做完变换，再切回来，保证整个结果正确。在 sparse attention 里我们也支持了 CP。

kernel 方面，首先要感谢 slime，感谢子林哥为 GLM-5 实现的一些基础 kernel，对我们帮助很大。我们 adopt 了来自 GLM-5 的 DSA indexer kernel，做了一些修改，把它适配到 DeepSeek V4 的架构上。还扩展了 slime 的 TileLang kernel，主要是因为 DeepSeek V4 用了一个 per-head 的 attention sink，这导致 attention 计算和之前不太一样，所以我们改了它的 forward 和 backward kernel，并保证正确。其他组件比如 mHC，我们借用了 DeepSeek 自带的 kernel，接进系统，并确保端到端的精度是正确的。

第二部分是 RL 的一些 feature，也就是推理框架和训练框架两边的联动。精度上，我们支持 FP8 的 rollout，以及 FP8 和 BF16 的训练。要支持不同精度，我们在 Miles 里实现了不同的量化 processor，保证 weight update 是正确的，从训练后端传到推理引擎的权重符合 SGLang 期望的格式。我们还实现了 attention 的 QAT，比较简单，是基于 FP8 做的：rollout 这边的 attention 可以用 FP8 存，而训练里用的是 BF16。当然我们也实现了 Rollout Routing Replay，也就是 R3 这样的 feature。对已有的 feature 我们都基于 DeepSeek V4 架构做了扩展和适配。我们还实现了一个比较新的实验性 feature，叫 indexer replay。大家可能看过一些讨论：在 DSA，也就是 DeepSeek Sparse Attention 这种架构上，加入了一个类似 MoE router 的 attention 路由，这会给训练带来更大的不确定性。一个比较简单粗暴的方案是在推理里把它的路由结果记录下来，训练时再重放。这其实比较复杂，因为在 SGLang 里，这个路由结果存放在缓存里，格式不是那么直白，需要做特殊处理，在正确的位置提取出来，再传给训练侧去重放。这更多是一个实验性质的 feature，主要是为了让大家尝试、探索不同的可能性。

第三部分是我们花时间最多的：如何保证训练是正确的，并且能涨点。大家看 DeepSeek 的 paper 会发现，他们在确定性和训练稳定性上做了非常多努力。我们做的肯定没有 DeepSeek 那样完美，只是一些非常初步的尝试，抛砖引玉，希望大家一起来用 Miles、一起 develop，做到更好的训练稳定性。

首先，我们的每一套实现都会做 tensor level 的验证。我们会把端到端每一个 tensor，比如每一层的任何 activation，以及算出来的每一个梯度，不管是 activation 的梯度还是参数的梯度，都保存下来。当我们对任何地方做可能有破坏性的改动，比如接一个新的 kernel，或者换一种实现时，都会跟之前的实现做端到端、非常完整的逐 tensor 比较，确保两版的差距非常小，这样才能确定接进来的东西是正确的，不会对整个系统造成很大的精度影响。

举个例子。我们一开始写 CP 时发现，attention 里 KV 这个 tensor 的梯度，不管怎么实现，跑 CP=1 和 CP=2 的结果总是差得非常大，cosine similarity 大概差了 0.2，而其他 tensor 的差异都只在 1e-5 量级。我们花了挺多时间研究这个问题，最后发现是 compressed attention 的性质导致的：它是一个很稀疏的架构，一些 head 会 attend 很多 token，梯度的流动也比较复杂，这种情况下它对精度非常敏感。我们默认的实现用的是 BF16，对其他 tensor，比如 query 的 activation 和梯度、KV 本身的 activation，都没问题，但对 KV 的梯度这一个 tensor，精度完全不够。

（主持）是因为数值范围崩了吗，还是什么原因？

（悦明）我个人的理解是它的 reduction 比较复杂，涉及更多的累加，所以误差更大。我们把这一个 tensor 换成 FP32 之后，问题就解决了，然后就能彻底确定 CP=1 和 CP=2 前后几百个 tensor 都对得上。整个过程中我们用了很多这样的方法去验证正确性。

类似地，DeepSeek 的 technical report 里讲到了一些确定性（deterministic）方面的做法，我们也是昨天刚看到这个 report，但在这之前已经做了一些类似的事情。比如在 cuDNN 里用了 deterministic mode，在 MoE 的一些地方做了确定性改动，还禁用了 NCCL 的一些非确定性做法。这些对训练帮助不小，比如本来 KL loss 会有 spike，做完这些之后就消失了。还有其他一些比较小的优化和改动，这里就先不说了，可以翻下一页。

这是一个比较简单的结果：我们在 DAPO 上跑了 4096 max response length 的训练，用的是 32 张 GB300。因为时间非常有限，没法测更大的 scale、跑更长的训练或更长的序列，所以肯定是比较初步的结果，但大家可以看到 reward 确实在上涨，reward 和 evaluation score 都在涨，log prob 也相对稳定，第一步按我们的 metric 测下来，差异只有 0.02 左右，对这样一个复杂的架构来说是比较低的。

这里想额外说一下，我们其实很早就发现 DeepSeek Sparse Attention 这类架构本身对训练稳定性是非常大的挑战，因为架构很复杂，还多了 attention 的 indexer 这一重不确定性。我们从 DeepSeek V3.2 起就在做一些探索，那时就发现这类模型很难训稳定。正是靠一直延续到现在的这些探索，才能做出这次的 Day-0 support。

问答

（悦明）我们会先做 FP4 的 rollout，然后再做一整套 FP4 的、包括 QAT 的训练栈。

（主持）还有一个很有意思的问题：整个过程中最具挑战、花时间最长的是哪部分？

（悦明）花时间最长的就是对精度。

（主持）这部分能不能靠 agent？现在很多公司都在讲用 agent 帮我解决问题。你觉得这需要手工去做，还是可以通过 prompt 或者 skill 去实现？

（悦明）靠 skill 肯定可以做到不少，但有时候时间比较紧张，还是必须手工 push 一下。

（主持）还有同学问，背景板上的 RL 结果是 Flash 还是 Pro 模型？

（主持）OK，那来一个比较有趣的问题：能不能锐评一下 DeepSeek V4 这种混合注意力架构，下一代会不会更换？这更像一个预判的问题。

（万晨）我个人不做算法，是做系统的，所以只有一些不太成熟的看法。我个人觉得这种混合架构应该是大势所趋。因为注意力机制肯定还是需要看到非常远的内容，需要长程的注意力；但长程注意力需要的显存又非常多，从系统的角度出发，我们又会想到 sliding window attention 这样的机制。所以从长远看，因为系统的约束，这种混合架构应该会一直存在。

（主持）非常感谢万晨老师。还有个问题想问悦明老师：Miles 欢迎其他第三方硬件进行适配吗？

（悦明）指的是 AMD 或者国产加速器吧？我们现在在做 AMD 的适配，国产加速器暂时还没有，之后可能会有。

（主持）还有一个很有意思的问题。我记得 2023 年左右 SemiAnalysis 出了一篇报道，说 GPT-4 用了类似 MoE 的结构，当然后来 GPT-4 方面说没有用 MoE，但感觉上还是用了。MoE 出来到现在，大家是为了弥补大模型参数量带来的短板、提升计算效率。V4 也用了 MoE 架构。随着架构迭代，你们觉得 MoE 以后会消失，还是会变成一种新的形态？

（万晨）我觉得它其实是从稠密形态变到稀疏形态。MoE 的优势在于可以更充分地利用你的内存，但计算量仍然保持不变。现在显卡的显存越来越大，比如 GB300 已经能做到将近 300 GB，但如果要把这 300 GB 全部用来存参数，同时继续保持稠密计算，开销会非常大。所以从长远看，MoE 架构应该会仍然存在。在 LLM serving 中我们仍然非常在意速度，从速度和智能的 trade-off 来说，我们肯定还是希望 MoE 继续存在，这也会让我们系统方面一直有新的工作可以探索。

（主持）对，欢迎大家给我们提新的架构，这样我们做 AI Infra 的还有活可以干，欢迎大家疯狂给我们增加新的挑战。还有同学想问：训练和推理有没有可以分享的 recipe，比如方便大家上手的链接或者 blog？

（万晨）推理的话我们在 SGLang 的 Cookbook 上放了一些测过的、比较推荐的配置，就是我刚才放的二维码，待会儿可以再贴一下。

（主持）直播间好像不能放二维码，大家临时截个图……好，没了，大叔可以撤了。下一个问题：Miles 跟 slime 的区别是什么？

（悦明）我觉得 Miles 跟 slime 非常像，有很多 shared feature，我们最开始也是从 slime fork 出来的。要说区别的话，Miles 会做更多像 Blackwell 这种新硬件的适配，我们也会放一些自己的尝试上去，比如最近在做 agent training 的一套架构，之后会有更多 release。

（主持）还有一个问题，也是做优化这一层经常遇到的：比如做算子融合、在 kernel 上做优化，增加一些东西必然也会舍弃一些东西。你们在优化 DeepSeek V4 的过程中，有没有什么很厉害的东西，因为效率原因很可惜地最终放弃了？

（万晨）我可以分享一点：算子融合并不总是有效的。GPU 计算相当于矩阵乘法可以沿不同维度切分做并行计算，但两个算子融合在一起时，你得确保它们能沿同一个维度切，比如都沿头或者词元的维度。这时就有取舍：把两个算子合成一个可能减少一些显存访问，但对其中某个算子来说，这种切分方式未必最适合它，就会产生额外开销，或者没法充分利用显卡的计算资源。这是我们做算子实现时会考虑的细节。

（主持）非常感谢。刚才有同学问 DSA 是怎么加速的，可以之后看回放，我们花了挺长时间、有一页 PPT 专门讲了这个。下一个问题：如果 attention 可以越来越稀疏，它的下限究竟在哪？两位老师觉得 attention 优化有没有做到极限？如果没有，未来还有哪些空间？

（悦明）我个人觉得已经比较极限了。之前的 sparse attention，大家还是会用 full attention 和 sparse attention 混合的做法，还是会做一些折中。V4 里是比较纯的 sparse attention，去支持 1M 的 context window，我觉得这种做法是比较极限的。

（主持）我个人觉得极限不极限也取决于硬件，以后也可能会有针对硬件开发的模型和特殊架构，以更好地发挥硬件优势。这里汇总两个问题，关于 off-policy：在 RL 方向上，有没有新的想法或方案能更好地解决 off-policy 相关的挑战？

（悦明）我觉得这是个很 general 的问题。大家提到 agentic 这一类场景，这也是每家大厂和 frontier lab 都在探索的事情，还没有形成共识的 solution。我觉得最重要的是限制 staleness 的上限。具体到什么程度会崩、可以承受多大的偏离，在稳定性和推理效率之间平衡点在哪，需要靠实验去验证。

（主持）好，切换一下话题，问一个推理方向的问题。推理中经常遇到长尾问题，有的请求 latency 非常长。在 DeepSeek 优化过程中有没有遇到长尾问题？有什么好的解决方案？

（万晨）是问 DeepSeek V4 本身，还是特指 RL 训练中的长尾？

（主持）我感觉比较 general，两边都可以回答一下。

（万晨）从推理角度来说，长尾倒不是一个很重要的问题，它最多会增加 KV Cache 的消耗。这时我们可以用其他方式，比如暂时 abort、终止这类请求的计算，确保留下足够空间去处理其他请求，等其他请求处理完了，再回过头来处理这些 KV Cache 需求特别高的请求。所以我们确实不太喜欢这类 request，但也是可以处理的。我们最近的一些体会是：DeepSeek V4 的算法和之前的非常不一样，直接和我们现在的 main branch 结合，代码会有一些不太优雅的地方，所以最近在重构这些东西，挺伤脑筋的。

（主持）悦明老师有没有要补充的？

（悦明）我觉得像 DeepSeek V4 这种非常新的模型架构，做一件没有参考的、很新的事情，是比较 challenging 的点。

（主持）我的感觉是，我自己以前在亚马逊的时候也做过很多未发布模型的开发。模型的架构并不是从一开始就和现在一样，过程中也经历了很多变化。你们也是在变化中对新东西做适配，可能在一些方面要做重复性的工作，对精度、对 benchmark 也都不是一个简单的流程。

还有不少问题。有一个是：DeepSeek V4 Pro 在短上下文，比如 32K 以内，TTFT、TPOT 或者 OTPS 和 V3、V3.2 相比性能大概有什么区别？

（万晨）说实话我们没有和 V3.2 做过对比。不过就 V4 本身来说，我们在 GB200 上现在能达到每秒生成 200 个 token 的速度。

（主持）下一个问题比较有教育性：如果是一个零基础的 CS 本科生，应该如何加入 SGLang 社区做贡献，有没有比较好的思路？先插一句，上一期直播里志鹏老师也讲了他自己的心路历程，怎么从一个新手开始，慢慢发展成社区的核心开发者。我也希望各位老师分享一下，你们是不是也是从零开始接触社区、慢慢把能力做起来的。万晨老师先分享一下？

（万晨）我自己差不多也是这样。我先是自己发现了一些算子层面的问题，我的第一个 PR 就是解决一个算子实现的问题。我记得当时是在输入量特别大的情况下，会出现 illegal memory access，我就提了一个 PR 把它修了。那是一个 MoE 的算子，后来我就慢慢开始做 MoE 相关的工作，比如专家并行，再往后慢慢扩展，参与了 DP attention 相关的工作，之后又做了 DP attention、专家并行和投机解码等各种 feature 结合的工作。在这个过程中，我对项目的熟悉程度和开发范围越来越大：最开始只是修了一个 MoE 的 bug，慢慢做了并行策略的修改，后来又参与了投机解码以及 CUDA Graph 相关的工作。所以作为新上手 SGLang 的朋友，可以先看一些比较简单的 issue。SGLang 社区里也明确标出了一些非常适合新开发者贡献的 issue，有一类标签叫 good first issue。如果你对参与 SGLang 开发感兴趣，可以去检索这类 issue，开 PR 解决它们。

（主持）还有一个同学问：我是大厂的一个普通 SDE，怎么能在 SGLang 方面做贡献、往这个方向靠？这个问题我帮忙回答一下，因为我自己在一家中厂，也见到很多同学对 LLM 非常感兴趣。我觉得第一，最重要的还是能接触到算力。这还是有门槛的，能接触到算力的一般是做训练、做推理，或者做训练推理数据准备的同学。所以先尽可能往这个方向靠，接触到算力。当你手上有了算力，比如 H100，哪怕只是一张 A100，都可以开始做这方面的开发。另外，有一些比较硬核的课，虽然比较枯燥，但值得去学，比如教你怎么从底层写一个 PyTorch 之类的课程，对底层算子要有一定了解，对上层架构的设计也要去了解。然后像晨阳老师说的，可以先通过 mini-SGLang 入手，了解基本架构，把它跑起来，尝试做一点小优化，之后再从小 SGLang 优化到大 SGLang，在上面做开发。我觉得这是一条比较好的发展路径。

（月球大叔）我观察了一下身边做 MLSys 科研或者工程的人。如果你在做 MLSys 的过程中，每天只是看 profiling，只盯着代码行数，这个地方有个小窟窿，我把它补了，那个地方有个小窟窿，我又把它补了，一开始这样肯定是可以的，因为要先出活。但如果你站在一个 researcher 的角度，就应该想：我过去两三个月已经补了几十个窟窿，这些窟窿里有没有共性？我能不能用一套框架，比如开发一套 serving 框架，把 systems research 里常用的那些 scheduling 等各种手段融合起来，把过去几个月最头疼的问题，用一套框架里若干精巧的 API 或者精巧的设计端出来，同时性能提升了很多？我之前和很多人聊过，systems research 是需要一定的抽象和美感的。如果你一直在写那种你自己都受不了的工程代码，却没有去做这种艺术上的抽象，那就不是 systems research。但当你写了几个月之后，突然觉得要把它变得更美一点，当你决定去做一件更美的事情的时候，你就开始做 systems research 了。

（主持）我觉得大叔提到的还有一个很重要的点：现在不仅模型在提升，硬件也在不断进步。你想想，整个推理系统中有三个要素：存储、通信和计算。在每个系统中，我们都想让这三者达到一种优雅的平衡，适配自己的算力。但每一代新硬件进来，架构的改变都会打破这个平衡，打破之后我们就需要新的算法、新的架构、新的设计。然而你会发现，类似的问题在过去十年、二十年甚至三四十年的历史中都有人处理过。比如 LLM 世界里的 PagedAttention，它整个架构的设计思路，就是源于早年操作系统中对内存的分析所抽象出来的解决方案。这里面还有很多研究方向可以做，这是我的一个感受。

除此以外，我个人认为还有很多值得探索的方向。其中一方面是数据存储。很多人会觉得，现在有了 LLM，以前做数据库或者传统后端开发的就没有出路了。我的感觉非常不一样，反而现在大家对 LLM 本身的关注度没有那么高了。直播间也有同学问了一个很好的问题：在 agent 架构下，怎么更好地让 SGLang 去适配？其实很多问题已经逐步从对算力的压榨和优化，转变为数据管理和存储上的问题，包括 agent 的可持续记忆，还有 dreams 和 memory 这两个东西的区别，感兴趣的同学可以看一下 Anthropic 发的相关文章。有相当多与数据相关的东西也在不断发展。
