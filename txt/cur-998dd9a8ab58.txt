AI 原生软件开发生命周期（AI-native SDLC）将软件工程重构为由智能体主导的流水线工厂，但引发了对用户体验（UX）权责弱化的架构审视：Anthropic、Google 与 OpenAI 的方案普遍将写代码转变为意图驱动并以版本化 Markdown 产物链（intent.md → spec.md → plan.md → 代码）作为审计轨迹，却将 UX 降格为模型上下文约束，缺乏独立的阶段所有权与门禁验收机制。

传统的 SDLC 经历从 1960 年代瀑布流向敏捷迭代的演进，其核心决策机制始终围绕产品、工程与用户体验三方权衡展开：产品负责商业可行性，工程保障技术可行性，UX 则捍卫用户可用性与实际价值。然而在智能体驱动的代码工厂范式下，任何人均可借助 LLM 独立起草意图文档并由产品负责人直接核准，设计阶段退化为利用 AI 工具基于样式指南快速堆砌 UI 界面与交互原型，代码构建与自动化测试则完全交由智能体闭环推进。在此流程中，UX 既未在 intent 或 spec 审批环节设立独立的质量把关门禁，亦未在自动化部署流水线中获得阻断权。

这种权责缺位导致多维度的系统性风险。首先，孤立生成的 intent.md 极易演变为未经严谨用户研究验证的功能膨胀，团队缺乏对用户真实痛点的共同认知；其次，AI 工具在设计阶段生成的原型仅停留在视觉呈现与表面排版层面，无法替代对复杂信息架构、任务流心智模型以及多态交互异常的系统性推演；再次，在测试阶段，智能体通过像素级截图与视觉规范比对断言测试通过，仅能验证系统是否忠实复刻了设计图，却无法评估认知负荷、无障碍可访问性以及真实用户操作困境；最后，在系统维护阶段，传统 APM 监控只能捕获服务端崩溃与延迟报错，而当用户因信息层级混乱而放弃核心链路时，监控系统往往显示服务状态一切正常。

为重建智能体软件工程中的体验治理，组织必须落实六项工程实践：在 intent.md 模板中强制嵌入用户需求验证与反思追问机制；由产品负责人与 UX 专家联合制定用户价值验收准则；将导航拓扑重构、核心交互链路变更等明确界定为必须经由人工 UX 审查的高风险变更；将任务中断率、漏斗转化跳出率与工单激增作为与服务器 5xx 错误同等优先级的自动化预警指标；由专业设计团队主导编写并持续维护机器可读的组织级 UX Skills 与设计上下文；推进设计系统规范的形式化编码以约束生成式 UI 的边界。

这种治理重构要求工程团队在追求极致代码交付吞吐量的同时，必须建立跨阶段的体验连续性保护机制，避免持续不断的无序微小迭代对核心产品体验造成渐进式腐蚀与认知负荷累加。
