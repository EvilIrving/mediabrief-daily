Extreme Harness Engineering for Token Billionaires: 1M LOC, 1B toks/day, 0% human code, 0% human review — Ryan Lopopolo, OpenAI Frontier & Symphony ｜ Latent Space ｜ 文章 ｜ https://www.latent.space/p/harness-eng

这期 Latent Space 由 swyx 和 Vibhu 对谈 OpenAI Frontier 产品探索团队的 Ryan Lopopolo。他此前在 Snowflake、Brex、Stripe、Citadel 工作，最近一篇关于"Harness 工程"的长文在业内引发热议。节目开头的编者按把核心事实摆了出来：他的小团队用五个月做出一个内部 beta 产品，代码库超过 100 万行、PR 约 1500 个，人类手写代码为零，合并前也没有人工审查。Ryan 甚至说，每天用不到 10 亿 token（按市价约 2000 到 3000 美元）几乎算"失职"。

实验起点是他给自己定的硬约束：自己一行代码都不写。他的逻辑是，如果要做能部署进企业端到端干活的智能体，它就该能做他做的所有事；而模型和 harness 在能力上已经与他"同构"。起步用的是早期 Codex CLI 和 Codex Mini，头一个半月比他亲手写慢 10 倍。团队的原则是：智能体做不到时，不去改提示词或让它"再努力点"，而是追问缺的是什么能力、上下文或结构，把任务拆成更小的积木再组装。正因付出了这个代价，后来才跑得比任何单个工程师都快。模型一路从 GPT-5 升到 5.4，每代都有怪癖：5.3 引入后台 shell 后不愿阻塞等待，他们就把构建从 Makefile 换到 Bazel、Turbo，最后换成 Nx，硬压到一分钟以内。一分钟是内循环的上限，一旦超出就拆构建图，像棘轮一样维持纪律。token 便宜、并行度极高，所以这些不变量可以持续打理。

Ryan 认为真正的瓶颈是团队同步在线的人类注意力，模型本身可以无限并行。所以要用系统思维不断追问：智能体在哪里犯错、我把时间花在哪、怎样以后不再花。现在大部分人工审查都发生在合并之后，更像一个 500 人组织的技术负责人抽查样本，判断哪里需要帮助。为此他们先给智能体建可观测性：用 mise 拉下 Victoria 系列的 Go 二进制，加一点 Python 胶水，半个下午就搭好本地日志、指标和链路追踪。顺序也反过来了：先启动 Codex，再由它通过技能和脚本自己决定是否拉起这套栈。他认为这正是推理模型与 GPT-4、4o 的根本区别：旧模型得关进预定义状态机的盒子，现在 harness 本身就是盒子，给足选项和上下文让模型自己选择。

非功能性需求的编码是另一条主线。仓库里只有一个约 100 行的简短 AGENTS.md 作为目录，加上 core beliefs、技术债追踪表、质量评分等 markdown 文件，全团队共用约六个技能。告警暴露"缺超时"时，他直接在 Slack 里让 Codex 修复，同时更新可靠性文档，要求所有网络调用都必须设超时，把一次性修复变成持久的流程知识，再由它派生测试和审查规则。智能体的每个错误、每条 PR 评论、每次失败的构建，都说明某条需求还没写下来。审查也要调教：起初作者智能体被审查智能体"欺负"，来回改无法收敛。后来规定审查者偏向合并、只提 P2 以上的问题，作者也可以推迟或反驳。PR 全生命周期交给一个 $land 技能：推送、等审查和 CI、修不稳定的测试、解决冲突、进合并队列，直到合入 main。对 swyx 说 Cursor 因合并冲突放弃工作树一事，Ryan 的回应是模型很会解冲突，代码本来就是一次性的。他也承认这些都发生在全新仓库里，产品是不做持续部署的 Electron 应用，发布前仍有人工冒烟测试。

关于依赖，他同意 Bret Taylor 的"依赖正在消失"：几千行的库一个下午就能内化，还能删掉用不上的通用部分，Codex Security 审查也更方便。swyx 提出规模测试和"足够多的眼睛"这些反方理由，Ryan 承认内化等于从零重建信心。一位值班工程师花一个下午做了一个链路追踪可视化工具，Ryan 说这其实多余，直接把 tar 包丢给 Codex 五分钟就有答案，为人类可读性优化反而把人困在了回路里。

Ryan 还在推特上看到一个意外用法：有人直接把这篇文章的链接丢给 Pi 或 Codex，说"把我的仓库改成这样"，效果出奇地好。Vibhu 也拿自己的语音 TTS 副业仓库试过，觉得这是学习哪些地方该改的好办法。Ryan 强调，文档、测试、审查智能体做的其实是同一件事：把团队里每个工程师脑中"好的样子"、默认做法和会教给新人的东西，变成能注入智能体的文本。人类留下的工作，是又难又新的那个象限，比如前方一片空白的问题、接口形态还不清楚的深层重构，这也是他想花时间的地方。

Symphony 源于新的瓶颈。5.2 发布后，每人每天的 PR 从 3.5 个涨到 5 到 10 个，人被困在多个 tmux 窗格之间切换上下文。于是他们做了一个由 Linear 工单驱动的编排层：为每个任务起一个守护进程，推到完成后交给人做低成本审查，不合格就进"返工"状态，整个工作树和 PR 推倒重来，同时反思智能体为何做砸。它以规格说明的形式发布，也就是推特上说的"幽灵库"：让 Codex 参照私有仓库写规格，派一个断开连接的 Codex 去实现，再派一个对照上游审查并修订规格，像 Ralph 循环那样反复，直到规格能高保真复现系统。Elixir 实现是模型自选的，因为 BEAM 的进程监督和 GenServer 天然适合这种编排，而人会不会写 Elixir 已经不重要了。规格中的 Linear、GitHub 都可以替换，它更像一张蓝图。规格写得又长又严，因为智能体擅长遵循指令，成功标准越明确，部署成功率越高，也就越不用盯着它。Vibhu 拿深度研究举例：他问 LLM 的问题，模型理解成了法学硕士（LL.M.），花一小时交出一份跑偏的报告。Ryan 说正确的做法不是守着它，而是把教训写回提示词，就像把护栏写回代码库；能并行开四份就别当保姆。团队规模变大后的混乱靠每天 45 分钟的站会和约 500 个 NPM 包的"万人级"架构来化解，好让人不互相踩脚。

他理想的状态是"生活在海滩上，一天打开 Linear 两次，对结果说是或否"。正因为对写出来的代码没有依恋，扔掉重来毫无心理负担。Symphony 的规格还分出策略、配置、协调、执行、集成、可观测性六层。Ryan 说协调层最难做对；策略层最省事，只要给智能体 gh CLI 和一句"CI 必须通过"就行，不用写代码。智能体还能自己开工单记录后续工作。他也提到早期有人把 Playwright 包成一个只有几条命令的小 CLI 守护进程，他事先毫不知情，只觉得 Codex 突然变好用了，这说明不在回路里的代价就是常常搞不清代码的真实状态。

工具层面，Ryan 看空 MCP：它强行往上下文里注入 token，干扰自动压缩。他偏爱省 token 的 CLI，比如 gh，并把冗长输出包成只显示失败项的脚本。UI 可以光栅化成 ASCII 给模型看。PR 要附上智能体录制的演示视频，就像信任一个队友，不需要盯着他的屏幕。团队把全员的会话日志收进 blob 存储，每天跑智能体从中提炼技能，人人都能免费受益于别人的经验。他们甚至有教智能体做梗图、在 Slack 发水帖的技能，core-beliefs.md 里也写着团队成员、试点客户和 12 个月愿景，因为这些上下文同样影响软件该怎么写。他希望将来 ChatGPT 也能借 Frontier 学到团队的梗文化和工作方式。

至于模型的短板，Ryan 认为从零到一的产品原型和最棘手的重构仍需人来引导，但不要和模型对赌，它会持续往更高复杂度推进。他还没想好怎么用快速小模型 Spark，只觉得它适合原型、文档和把反馈转成 lint 规则。关于 harness 和训练的张力，他主张护栏应当是测试这类与代码原生契合的东西，而不是另造一套限制输出的脚手架，swyx 把这比作强化学习里的同策略。Frontier 方面，它是让企业部署可观测、可治理、可识别智能体的平台，对接 IAM、安全工具和自定义安全规范（如 gpt-oss-safeguard），仪表盘面向 IT、合规和安全团队，可以下钻到单个智能体轨迹，也可以撤销授权。他们还做了一个内部数据智能体，让模型理解数据仓库的本体和语义层，swyx 指出，连"收入""活跃用户"怎么定义人类自己都还没达成一致。节目最后，Ryan 介绍了 Codex 已突破 200 万周活、周增 25%，以及新开的 Bellevue 办公室和招聘情况。
