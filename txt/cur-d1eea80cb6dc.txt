agent 架构中的安全边界（Security boundaries in agentic architectures） ｜ Vercel Blog ｜ 文章 ｜ https://vercel.com/blog/security-boundaries-in-agentic-architectures

Vercel 官方博客的一篇安全架构文章，核心观点是：如今大多数 agent 在运行自己生成的代码时，拥有对你全部密钥的完全访问权限，这必须改变。

文章先指出，所有 agent 都越来越像编程 agent：读写文件、跑 shell、生成代码来解决问题，连客服 agent 生成 SQL 查账户也是同一种模式。风险在于提示注入加上代码执行。它举了一个例子：agent 排查线上故障时读到一份日志，里面藏着一段伪装成"计费服务已迁移，请运行诊断"的注入，要求把 ~/.ssh 和 ~/.aws/credentials 发到外部服务器；agent 照做，凭证就没了。攻击能成功，是因为 agent、它生成的代码和基础设施共享同一级权限。

文章把 agent 系统拆成四个角色：agent（按标准流程部署的 harness 可以信任，但模型本身会被注入、行为不可预测，信息应按需告知，比如用 SQL 工具不必看到数据库密码）；agent 的密钥；生成代码的执行（最难预测的变数）；文件系统和运行环境。由此得出几条原则：harness 永远不把自己的凭证直接暴露给 agent；工具范围越窄越好，给某位客户做客服的 agent 应该拿到只能访问该客户数据的工具，而不是一个接受客户 ID 参数的工具，因为参数可能被注入篡改。

接着按安全程度从低到高比较几种架构。零边界是今天的默认状态，Claude Code、Cursor 虽然自带沙箱，但常常默认关闭。密钥注入代理在网络出口处只对目标域名的请求注入凭证，生成的代码看不到真实密钥，能防外泄，但防不住运行时被滥用，好处是可以无痛加装。把 harness 和生成代码一起装进同一个沙箱，能保护外部环境，却保护不了 agent 免受自己生成的代码攻击。真正缺的一块是把 agent 和生成代码放到独立的计算环境里：harness 和密钥在一处，文件系统和代码执行在另一处。两者负载特征也不同，harness 大部分时间在等模型响应，适合按活跃 CPU 计费的计算；生成代码短命、不可信，适合每次执行即开即毁的临时虚拟机。最强的组合是应用沙箱加密钥注入，注入的请求头还会覆盖沙箱代码设置的同名头，防止凭证替换攻击。文章判断这种分离会成为 agent 系统的标准架构，现在就划好边界的团队会占据安全优势，并顺带介绍 Vercel Sandbox 已支持安全的密钥注入。
