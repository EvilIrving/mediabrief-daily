为什么我不太喜欢单页应用

有时看起来无障碍专家和其他 web 专业人士讨厌 JavaScript。对一些人或许如此，但多数人明白 JavaScript 可以改善 UX 甚至无障碍。JavaScript 方案常常比纯 HTML 或 CSS 对应物更无障碍。

我们知道 JavaScript 不是敌人，但不可否认，一些开发者对构建客户端渲染网站抱有某种保留。这些人常被斥为"守旧派"，因为他们对现代 web 开发似乎有非理性的厌恶。若你不明白这从何而来，就很难理解为什么有人会不想做单页应用（SPA），而选择有时被称为多页应用（MPA）的标准建站方式。

最近对 SPA、尤其是 React 的批评很多。个人层面我完全理解：我不喜欢 Meta 及其商业模式；不喜欢 React 意见领袖把库卖成它并不是的东西；不喜欢由此催生的那种兄弟文化。专业层面，我理解对有些人来说 React 不过是工具或一个 .js 文件——他们靠做网站谋生。尽管我不开心，我也理解 JS 库和框架常常是新 web 开发者进入这行的入口。不过也有正当且严肃的专业批评。这篇文章不是要说服谁换一种建站方式，只想分享一个做了二十多年网站的人的看法与经验，并概括为什么一些开发者（包括我）对做 SPA 保持警惕。举例之前先说重要的一句：我知道可以做出无障碍的单页应用，也知道有人（因为想或因为必须）使用 JS 框架，并因为在乎用户而把网站优化到极致。

很多怀疑来自：网站的一些关键特性在单页应用里工作方式根本不同。

路由

当你创建三个 HTML 文档（home、about、dashboard）并互相链接时，点击链接会发生：浏览器导航到新页面，页面加载，浏览器标签上的标题改变，焦点在 body 上；若你使用读屏软件，软件会朗读页面标题。当然还会发生更多事。这是简化且不完整的描述，但重要的是：无论你如何访问和激活链接（鼠标、读屏、触摸、开关设备等），你都知道发生了什么、有事发生了、以及你在哪里。加载过程与页面过渡告诉你已导航到新页面。焦点在 DOM 开头（你期望的位置），读屏自动朗读标题。

在单页应用里，你只创建一个 HTML 文档，用户点链接时替换页面主内容。为此你可能要用 React Router 之类的路由库。与前面原生路由相比，发生的是：DOM 内容变了，焦点仍在链接上，浏览器标签标题不变，读屏什么也不宣布。若幸运，你知道发生了什么、有事发生了、身在何处。若你是盲人读屏用户，多半完全得不到反馈。

虽非有意，单页应用至少在页面导航上，设计上就不无障碍。Reach Router 的作者曾尽力通过管理焦点让路由更无障碍，但由于路由切换时的数据加载与焦点管理耦合，很难做对。尽管他们努力，当 Reach Router 与 React Router 合并、并停止默认做"不够好的"焦点管理后，路由再次变得完全不无障碍。

手工做好的自定义路由与焦点管理实际上可以比无 JavaScript 的原生行为更好，但必须手动构建。很不幸，你在许多 SPA 里看不到这一点。我宁愿给用户提供不那么出色但一致的默认体验，也不愿完全没有体验。

不过，我们可以从 SPA 以及心里有无障碍、与之共事的人那里学到很多。Marcy Sutton 与 Fable Tech Labs 关于可访问客户端路由技术的用户测试研究非常出色。

文档标题

页面的 <title> 是 HTML 文档中最重要的元素之一。用户以多种方式受益于结构良好、具描述性的页面标题。

为缓解不无障碍的路由以及点击链接后缺失的反馈，读屏用户会用快捷键让软件朗读页面标题。页面标题告诉他们在哪一页。所以即便没有其他反馈，标题一变他们就知道到了新页面——如果标题变了的话！在 SPA 里，你通常必须手动实现标题管理。这又是原生路由里本来就好用的东西。

（原文表格：NVDA / JAWS 的 Ins+T；macOS VoiceOver 的 VO+Shift+I、VO+F2 等。）

你还想改页面标题的理由更多：它是书签/收藏的标签，搜索引擎在结果页使用它；社交媒体、聊天或邮件应用在未指定其他标题时用它做链接预览。

在你开始给我发链接之前：我知道这可以做到，我做过调研。我的重点是，这又是一件你必须手动重新实现的事。（列举 Hidde de Vries 的文章、React Document Title、React Helmet、Vue-meta。）

DOM 变更

DOM 变更并非 SPA 独有，而是使用 JavaScript 的一般问题。事实是，响应式 DOM 变更正是单页应用的核心。你做的每一处重要变更，都必须不仅在视觉上、也在语义上传达出去。Live region、ARIA 属性或焦点管理可以帮忙。你在官方 React 无障碍文档、Vue 无障碍文档或 Angular 文档里，找不到关于用 live region 或 focus() 来宣布 DOM 变更的信息。

我们往页面里加的 JavaScript 越多，界面就越脆弱，若想为所有人创造平等体验，就必须手动管理和传达得越多。

JSX

JSX 看起来有点像 HTML，但并不真是 HTML，因为它混了 HTML、组件标签和自造属性（说的就是你，className）。我知道 React 不强制使用 JSX，但许多新人先（且只）学 React 和 JSX，因为训练营和被灌输的社区告诉他们这是建网站的唯一正经方式，要找工作就得会 React。若你不理解实际标准（HTML）与抽象层的差别，这种抽象可能很糟。我们本来就已经不太会写原生 HTML，一门模糊标准语言的语言不会让事情更好。

在选择使用任何并非原生 HTML、但会编译成 HTML 的语言之前，我们应先学 HTML。这不仅适用于 JSX，也适用于 Markdown、Pug、Nunjucks 等。若我们知道输出该长什么样，输入会好得多。

页面语境

在 SPA 里你创建组件。组件可能嵌在另一组件里，再嵌，直到最终落进 index.html 的包装 <div>。看多数 SPA 的最终文档，页面不像一个连贯实体，更像一堆碰巧在视觉上组成页面的组件倾倒场。如前所述，HTML 是任何无障碍网站的基石，页面结构（健全的标题大纲、地标、DOM 顺序、语义化 HTML）很重要。

别误会，我也构建作为体系一部分的组件，但我也会花大量时间打磨运作良好的页面。HTML 文档几乎不必碰、你需要的一切都会经 JavaScript 注入，这一事实让文档和页面结构失去了焦点。

我不是说基于组件的方法是错的，哪怕写在 JavaScript 环境里也不错，恰恰相反；但因为用 JS 框架工作更方便高效，并不意味着我们必须把那些 JavaScript 都送给客户端。完全在客户端提供网站的传统方式已经过时，但我也不相信 hydration 之类概念好多少。

值得探索那些分离关注点、并尽量减少交付 JS 量的路线。一些值得注意的项目是 Lit、Astro、Svelte 或 WebC。

性能

多数 SPA 在我 3500 欧元的笔记本和 500 欧元的手机上大概表现不错，但 MacBook Pro 和华为 P30 未必是普通用户访问网页时的普通设备。我没有资格大谈客户端渲染、尤其是 React 的性能影响，但很早就有大量批评，因为 SPA 的表现并不像 Meta 或 Vercel 的意见领袖曾让你以为的那样好。（建议阅读《The Performance Inequality Gap, 2023》《The Market for Lemons》等文。）

复杂度

从零搭建 SPA 并不简单，涉及许多乏味步骤。即便用样板设置，你面对的也是一头复合依赖怪兽，随时会因为一个小细节不能开箱即用而毁掉你的一天。这些东西里复杂度如此之高，让有些人怀疑是否值得，以及会不会更聪明地把时间花在真正造福用户的事情上。

我想这里最大的批评是：相信单页应用及整个生态优越性的人，感觉更关注开发者体验（DX）而不是用户体验。这听起来像危险的一概而论，但这些年过去，我从未觉得"更好的 DX 带来更好的 UX"这一论点真正成立过。它不过是为巨大复杂度和可能显著更差的 UX 找的正当化说辞。即便核心论点不是 DX，可扩展性、可维护性、竞争力、更容易招人（"人人都用 React"）和成本效益等论点，在我的经验里也往往只是好听，很少兑现承诺。

结论

希望这听起来不像骂街，它不是。我只是想解释为什么对一些人来说 SPA 不是首选，甚至完全不是选项。我很高兴存在如此多样的工具图景，因为我们可以从创新中学习，并用这些知识创造更好的体验。我用过多种 JS 库和框架，因为那能糊口，但我从未在自己的项目里用过，也从未建议客户这样做，大概永远不会。简单理由是：我多数时候做的是网站，而不是复杂应用。JS 框架和客户端渲染有其时地，但对典型网站来说，它通常不是正确的选择。
