软件自动化测试的核心投资回报率（ROI），在于用最小的时间与维护成本换取最高级别的代码交付信心。测试奖杯（Testing Trophy）模型通过对传统测试金字塔（Testing Pyramid）的分层重构，确立了以集成测试为核心主体的现代前端与单体架构测试范式，纠正了盲目堆砌隔离单元测试所导致的虚假安全感与高昂维护负担。

测试奖杯模型自底向上由四个层级构成，各层级承载着清晰的权衡与职责边界：
1. 静态检查（Static）：由 ESLint 与 TypeScript 等工具构筑底座。在 JavaScript 动态弱类型生态中，静态分析能够以近乎零时延的成本在编码期捕获语法拼写错误、类型不匹配与基础逻辑死锁，拦截大量低级错误。
2. 单元测试（Unit）：针对完全隔离的独立函数、基础组件或无协作依赖的纯逻辑类进行断言。单元测试执行极快且定位精准，但其前提通常是对协作依赖进行大量伪造（Mock）。
3. 集成测试（Integration）：构成测试奖杯面积最大、投入倾斜最多的核心躯干。集成测试验证多个相互协作的单元在协同工作时的行为表现。在前端工程中，这意味着通过 MSW 等网络拦截工具模拟 HTTP 请求，并由 Testing Library 驱动真实 DOM 节点协同交互。
4. 端到端测试（End-to-End）：在真实或无头浏览器环境中挂载完整系统，尽量规避任何 Mock 介入，验证核心用户旅程闭环。E2E 测试虽然置信度极高，但运行耗时最长、基础设施成本高且容易产生偶发性测试飘移（Flakiness），因而适度控制总量。

测试奖杯对传统测试金字塔的核心修正，在于深刻揭示了“交付信心”与“实现细节解耦”的工程关系：
- 金字塔模型的局限性：传统金字塔诞生于编译型语言占主导的早期后端时代，预设单元测试成本低廉因此应占据绝对多数。但在现代 UI 与单体应用中，组件 A 渲染组件 B 并传递参数，单元测试分别证明 A 和 B 在孤立状态下能够运行，却完全无法保证 A 传递的属性是否会触发 B 的运行时异常。过度依赖单元测试会导致团队陷入测试孤岛。
- 遵循实际使用方式获得最高信心：Testing Library 的核心设计哲学——“测试越接近软件被实际使用的方式，越能提供坚实的信心”。集成测试能够以极高的执行效率直接覆盖组件装配、状态流转与真实 DOM 事件交互。
- 拒绝实现细节测试：单元测试为了达成高覆盖率，往往深入探测内部私有方法与局部状态，导致每次重构底层实现但未改变外部行为时测试大面积崩溃。集成测试只关注输入输出与可观测行为，从而赋予开发者自由重构内部逻辑的底层底气。
