渐进式图片渲染的现状与未来

渐进式图片格式允许解码器在只拿到部分图片资源时，就生成一个局部的渲染结果。有时是图片的一部分，有时是图片的低质量或低分辨率版本。我最近一直在深入研究这个问题，我认为存在一些常见的误解，而且我希望 AVIF 能拿出一个更务实的方案。

我们直接来看看目前浏览器原生支持哪几种渐进式渲染。

JPEG

可靠的老 JPEG 可以用渐进的方式编码，这也是 Squoosh 的默认设置。

这里有一个小网页应用，可以测试任意图片的渐进式渲染；这里是已经载入了狐狸图 JPEG 版本的应用。

你会得到一个从上到下的低分辨率渲染，大约在收到 1.2 kB 时开始，在约 33 kB（文件大小的 21%）时完成第一遍。有意思的是，Firefox 和基于 Chromium 的浏览器呈现的效果与 Safari 不同：

两种情况下你都能看出图片是什么，但 Safari 的渲染是一块块的马赛克，而 Firefox 和 Chromium 经过了平滑处理。我更喜欢 Firefox/Chromium 的渲染。

之后，分辨率会经过多遍逐步提高。

对 JPEG 来说，渐进式渲染在质量和体积上似乎是免费的，但在解码时间上并不免费。这是另一个小网页应用，用来在浏览器中对图片解码做基准测试。比较渐进式 JPEG 和非渐进式 JPEG，渐进式 JPEG 的解码时间大约长 40%，但在我的 M4 Pro 上只多了约 1.3 毫秒，这似乎是个合理的取舍。

PNG

PNG 通常从上到下渲染。它有一种隔行（interlaced）模式，但会显著增大文件体积，所以我不推荐。

为了完整起见，这里有一个演示。我不得不……呃……对图片做了些修改，才把文件大小降到可以接受的程度。

WebP

在 Firefox 和 Chrome 中，WebP 从上到下渲染。而且它要收到约 43 kB（28%）才会渲染出任何东西。我猜文件开头存放的是色彩数据，所以它只有在开始接收最后的亮度通道时才能渐进地渲染。

遗憾的是，Safari 对 WebP 不做任何渐进式渲染。它要等收到整个文件才会渲染出东西。

AVIF

更新：在我发表这篇文章之后，AVIF 的渐进式支持有了大幅改进。现在你可以提供最多三个渐进帧，按你想要的任何方式处理，并支持分数比例缩放。我打算以后再就此写文章。

普通的 AVIF 不支持任何形式的渐进式渲染。你先什么也看不到，然后看到整张图片（演示）。

不过，AVIF 确实有一个鲜为人知的渐进式渲染功能！我用它提供的 --progressive 选项没能得到好结果，但用更底层的 --layered 选项得到了一些有意思的东西。它是实验性的，我得自己编译 libavif 才能让它工作。这是我用的命令：

avifenc -s 0 -y 420 --layered \
  --scaling-mode:u 1/8 -q:u 0 fox.png \
  --scaling-mode:u 1 -q:u 16 fox.png \
  fox-progressive.avif

这会创建两层：一层是 1/8 分辨率、“最低”质量；另一层是全分辨率、较好的质量。这些层的工作方式类似视频的帧，第二层会利用第一层的数据来节省空间（用视频的术语说就是 P 帧）。

这是一个演示。它只在 Chromium 浏览器中渐进渲染。你会得到两次渲染：收到全部数据时的完整图片，以及更早在约 5.8 kB（4% 的数据）时的一次渲染：

它看起来……很糟，但你能认出是什么，而对 5.8 kB 来说已经相当不错了。

缺点是，使用 --layered 模式时，质量选项会出现一些奇怪的情况，它和普通 AVIF 编码中的数值并不对等。

另外，文件体积似乎也有一些额外开销，但很难测量。用 MS-SSIM 摸索下来，大概在 5–6 kB 左右，所以……差不多就是第一遍的大小。

我用的分层配置只是一个例子，但它看起来相当受限。只允许特定的缩放值，而且 1/8 是最小的。据称可以有更多层，让渐进渲染多几个步骤，但每次我尝试，编码器要么报错，要么把文件体积撑大到约 400 kB，即使用最低质量也是如此。我猜这就是它被标为“实验性”的原因。

在解码时间方面，这里比较了渐进式 AVIF 和普通 AVIF。在 Firefox 和 Safari 中，渐进式的解码时间大约长 1–2%。在 Chrome 中则长约 40%，在我的 M4 Pro 上是 3.5 毫秒。我猜 Chrome 缺少一条针对“不需要渲染第一层”情况的快速路径。

这是 Firefox 中跟踪 AVIF 渐进式渲染的问题单。

JPEG XL

如果你问 Web 开发者为什么想要 JPEG XL（我在 Bluesky 和 Mastodon 上问过），几乎每个人都会提到渐进式渲染。正因如此，我很惊讶地发现，Safari（唯一支持 JPEG XL 的浏览器）并不进行任何形式的渐进式渲染。这里有演示和 bug 报告。

我还惊讶地发现，在 Safari 中，JPEG XL 的解码时间比同等的 AVIF 长 150%（也就是 2.5 倍）。在我的 M4 Pro 上要多 17 毫秒。苹果的硬件往往是高端的，但这仍可能是个不小的问题。这与渐进式渲染无关，只是解码器本身很慢。有迹象表明苹果的实现只在单核上运行，所以也许还有改进空间。

Safari 中的 JPEG XL 支持其实来自底层操作系统，而不是浏览器本身。我猜苹果正考虑在 iPhone 上用 JPEG XL 而不是 HEIC 来存储照片，而把 JPEG XL 加进浏览器有点像是顺带的。不过这只是我的猜测。

Chromium 中曾经藏在实验开关后面的实现，确实在一定程度上支持渐进式渲染，但它要到约 60 kB（文件的 39%）才渲染出东西。渲染效果和上面 JPEG 的初次渲染相似，但需要多得多的图片数据才能达到。这是解码器的弱点，而不是格式本身的问题。稍后我会深入介绍 JPEG XL 能做到什么。

我还测试了 Chromium 那个旧的实验性 JPEG XL 解码器的性能，它的解码速度比 AVIF 慢 500% 以上（6 倍）。Firefox 那个旧的实验性 JPEG XL 解码器则和 Safari 的解码器差不多慢。拿实验性、未发布的东西来评判性能并不公平，但我本来有点希望其中某一个能说明 Safari 的实现只是个例外。

我原以为“解码快”是 JPEG XL 相对于 AVIF 的卖点之一，但现在我不那么确定了。

Firefox 中正在开发一个 JPEG XL 的 Rust 实现，但性能需要大幅提升，我们才能把它合并进来。

但我们真的能从渐进式渲染中受益吗？

多亏了现代图片格式（这里是 AVIF），上面这张图片只有 56.4 kB。对一张超过高清分辨率的图片来说，这相当惊人。狐狸图之所以大得多，是因为它细节锐利，但大多数图片并非如此。这意味着对很多图片来说，渐进式渲染的好处不大。

但即使是 155 kB 的狐狸图，Kornel 也提出了一个很好的观点：

“拥塞和缓冲膨胀（bufferbloat）让数据以滞后的突发方式到达，而不是缓慢地到达。信号极差时，往往也是时有时无。”

这意味着，即使接收这张图片要花 5 秒，这 155 kB 也不太可能在这段时间里均匀地陆续到达。我现在正用着飞机上的 WiFi，没错……大部分慢的时间都是什么都没收到。

这意味着要看到渐进式渲染，需要好运和坏运气恰好凑在一起：

- 坏运气：你的网络连接不太好，所以获取整张图片要花一段时间。
- 好运气：图片的一部分已经收到了。

当你碰上这个（不怎么）甜蜜的点时，渐进式渲染是一种很好的体验，但即使网速很慢，你也未必能看到它。它当然不能代替认真控制图片大小。

正因如此，我觉得以支持渐进式渲染的方式编码图片，在文件体积上的额外开销应该极小，而在不需要渐进渲染的情况下，解码开销也应该极小甚至为零。

我知道这个“故事”说服力不强。我动笔写这篇文章时，本打算为渐进式渲染做一番有力的论证。但深入研究之后，我的感觉没那么确定了。

用渐进式渲染代替响应式图片呢？

当我问大家为什么对 JPEG XL 感兴趣时，有些人认为它能让他们用一个最高分辨率的 JPEG XL 文件来取代响应式图片。设想是这样的：

- 浏览器收到一些图片数据。
- 浏览器对这些图片数据做部分解码。
- 浏览器意识到它不需要更高的像素密度了。
- 浏览器告诉服务器：“别再给我发这个资源了。”
- 服务器乖乖地停止发送这个资源。

很抱歉当这个报坏消息的人，但我相当肯定这行不通。

问题在于，这些步骤之间都有相当大的延迟，以至于在响应被成功取消之前，每张图片你都很可能已经收到了好几 MB 根本不需要的数据。

如果配合一个新的浏览器功能，让字节范围预先可知、浏览器可以发出所需的部分请求，也许还行得通：

<!-- 编造的例子 -->
<img
  srcset="
    img.jxl#range=0-10000   200w,
    img.jxl#range=0-30000   400w,
    img.jxl#range=0-70000   800w,
    img.jxl#range=0-150000 1600w
  "
  sizes="……和平常一样……"
/>

但即使我们有了这个 #range= 功能（而且围绕 CORS 有一些大问题，可能让它根本无法实现），它的复杂度也和今天的响应式图片差不多，而用响应式图片，你对可用的分辨率有更多的控制。

我想“范围”方案的一个优点是，如果浏览器后来发现需要更高的分辨率，比如从缩略图切换到全屏，它可以“续传”图片下载。但即便考虑到这一点，现有的响应式图片似乎还是更灵活。

JPEG XL 潜在的渐进式渲染

除了浏览器中的解码器之外，JPEG XL 的渐进式渲染还有一些很有前景的工作。不过，其中有多少能进入浏览器还不清楚，而且编码器的设置有点让人困惑。

当前版本的 cjxl（0.11.1）有一个 --progressive 选项，但它生成的文件要收到相当大一部分（狐狸图是文件的 39%）才能渲染。

要更早地渲染，你需要使用 --progressive_dc 1，而 cjxl --help 并没有提到这个选项。只有把详细输出选项用两次，也就是 cjxl --help -v -v，你才会发现它。代码库里似乎已经改成 --progressive 会隐含 progressive_dc 1，但这还没有进入正式发布的版本。

progressive_dc 似乎对文件体积没有影响，即使有，也很小。我也没看到解码时间上的差异（在 Safari 中测试），不过 JPEG XL 解码总体上就很慢，所以这算不上多大的胜利。

djxl 不支持 --progressive_dc 提供的更早渲染，但还有一个基于 Rust 的解码器 jxl-oxide，可以处理更早的渲染。

jxl-oxide 的速度还不足以用于浏览器，但它让我们有趣地预览了可能做到的效果。它还有一个很棒的 wasm 版本，可以让你看到局部渲染。如果你想自己试试，这里有狐狸图的渐进式版本。否则，这里有一份粗略的指南：

我认为在 6 kB 时，你就能对这张图有个不错的印象，而在 46 kB 左右就非常清楚了。它还可以做一些平滑处理，就像我们在 Firefox/Chrome 的 JPEG 渐进渲染中看到的那样。

过了 60 kB 之后，完整的细节以方块的形式出现。JPEG XL 的一个优点是这些方块可以以任意顺序出现，所以你可以在 68 kB 的渲染中看到，锐利的细节先出现在狐狸脸周围，然后才是其他地方。cjxl 允许你指定一个点作为“中心”，而更聪明的编码器可以检测人脸之类的东西，并优先处理它们。

这有主观成分，但我认为前面那个 5.8 kB 的 AVIF 渐进渲染，在细节上介于 17–27 kB 的 JPEG XL 渲染之间，不过你可以自己判断：

所以，如果浏览器下载了 6 kB 之后停滞了，AVIF 能给出更好的结果。但由于 AVIF 的渲染只有两遍，如果浏览器已经拿到了比如 50 kB，JPEG XL 的渲染就要好得多。

在它变得足够快、能进入浏览器之前，这一切都只是“理论上”的。

还有另一个 JPEG XL 的 Rust 解码器 jxl-rs，正在为 Firefox 开发。那个团队也在探索渐进式渲染可以如何实现。

给 AVIF 一个更好的“渐进”功能？

这篇文章比我预想的要长，不过还有最后一件事……

更新：在我发表这篇文章之后，AVIF 的渐进式支持有了大幅改进。现在你可以提供最多三个渐进帧，按你想要的任何方式处理，并支持分数比例缩放。我打算以后再就此写文章。

根据我的经验，在我认为的“Web 质量”下，AVIF 生成的文件比 JPEG XL 更小（尤其是针对高像素密度优化时）。而且从目前的实现来看，AVIF 的解码速度明显快于 JPEG XL。文件更小、解码更快是巨大的优势。尽管如此，我还是希望 AVIF 有一个更好的“渐进”功能。如果它支持一种早期渲染，让人能更好地控制第一遍的质量和缩放比例，最好还有一个可配置的后处理模糊效果来掩盖压缩伪影，那就太好了。

也许“分层”方案可以改进。也或许它是把问题复杂化了。例如：

上面这张图片只有 1.97 kB。它被缩小，用 AVIF 以最低质量压缩，并加上了后处理模糊。

加上模糊之后，我觉得它作为预览效果很好。那么，能不能……直接把它放在完整图片文件的开头？

这意味着在文件体积上，这个“预览”是百分之百的额外开销，但这也意味着我们 Web 开发者可以自由配置这个“预览”的质量，自己决定能接受多少额外开销。也许我只花 1.97 kB 太保守了，而不是比如 10 kB：

而且由于它是一张完全独立的图片，如果浏览器认为显示预览没有好处，解码开销就为零。也就是说，在浏览器已经拿到整个文件的情况下，它可以直接跳过预览。

后处理模糊需要成为格式本身的一部分，而不是留给 CSS 之类的东西来做。这样格式就能使用一种“廉价”的模糊滤镜，避免昂贵的渲染开销。

我最初在 2020 年就提出过这个想法，那时还没有人探索“分层”的思路。但也许是时候重新考虑它了。但愿如此！
