神经网络是我们在许多交易策略中大量使用的工具。但原始市场数据不能直接喂给神经网络。它是非结构化的输入，需要先做归一化和特征提取。

Flex Model 是一个特征工程框架，负责把市场事件转换成数值向量。它诞生于我们的香港办公室，后来推广到了全公司。在这篇文章里，我会介绍什么是特征工程、我们在开发 Flex Model 时做出的一些设计选择，以及我们不得不重建它的核心时发生了什么。

## 什么是特征工程？

原始市场数据是一串事件流：一笔订单被加入订单簿，一笔订单被撤销，一笔成交发生。特征是从这串事件流中派生出来的数值，特征工程就是设计和计算特征的工作。一个简单的例子是中间价（mid），即最优买价和最优卖价的中点。中间价只需要订单簿的当前状态。更复杂的特征往往需要更多信息。例如，要计算最近 10 笔成交的成交价与中间价之差的平均值，就既需要当前的订单簿，也需要一个存放最近成交的缓冲区。这个缓冲区就是该特征的状态。本文将始终以这个特征为例。

真实的模型可能会使用成百上千个这样的特征。其中许多特征需要在每个事件上更新。特征清单由研究员定义，而且经常变动。每个市场的结构都不一样，有用的特征也就不同，而我们不希望每加一个特征就去改一次框架。

## Flex Model 的起源

被 Flex Model 取代的那套系统大约在 2012 年投入生产。它是一个单体系统：包含数百个信号定义，既为研究生成数据，又计算实盘信号，还包含交易执行逻辑。当我们开始开发它的继任者时，主文件已经超过 1.1 万行代码，到它下线时更是增长到了 1.7 万行以上。光是这个文件里最大的两个函数，每个就接近 3000 行！

旧系统虽然运行良好、速度也相对较快，但添加新特征非常痛苦。比如有一次，我们加了一个只是两个数之比的简单特征。这个改动涉及十九个文件。这个特征要在大约六个地方声明，同一个参数还得在许多几乎一模一样的、按市场划分的调用点之间层层传递。此外，每次求值时，每个市场都要计算全部特征。一个市场需要的特征会拖慢所有市场，于是人们为不同市场加上了“仅在……时才计算”的开关。我们想要一个更易组合的东西，让研究员能轻松复用现有的组件。

2019 年，我们启动了一个替换旧系统的项目。这项工作始于香港办公室，很大程度上是因为那里对这些问题的感受最为深切。亚洲有许多市场，每个市场都有自己的监管机构，新规则和技术变更频繁生效。（交易所在一个周末之内换成一套全新交易系统的情况并不少见。）在这样的环境下手写特征根本行不通，所以我们需要具有通用性的软件。这样的软件也便于其他团队上手，Flex Model 就是这样推广到其他办公室的。

我们花了大约两年半才迎来第一次实际使用。我们曾试图一次性替换所有东西，结果发现难度太大。2021 年底，我们把范围缩小到一个市场中的一个简单策略，它在 2022 年初上线。又花了一年，才替换掉旧系统中最重要的那些实例。

Jane Street 的亚洲办公室恰好很适合孕育像 Flex Model 这样的项目。尤其是香港办公室，虽然已经不算小了，但依然有种人人都相互认识的感觉，大多数同事走几步就能找到。这里的工程师构建和运维的系统与纽约、伦敦是同一类，但人手更少，所以每个人最终都更像通才。这对开发 Flex Model 很有帮助。一个小团队就具备替换一套关键交易系统所需的全部能力，并且能在紧密的反馈循环中完成这项工作。

## Flex Model 的设计目标

核心思路是把特征计算和交易执行代码分开。我们希望特征是可以组合的小段代码，每个特征只在一个地方定义。系统还必须快，这主要意味着在热路径上避免内存分配（后文详述）。我们的理想是，研究员无需触碰核心，就能写出我们的示例特征，代码大致如下：

```
let mid = mid ~book () in
let trade_vs_mid = diff trade_price ~minus:mid in
average_over_last_n_trades ~n:10 trade_vs_mid
```
## 为什么不用 Incremental？

在上面的代码片段中，值之间的依赖关系构成了一张图。当一个事件到来时，我们只想更新受它影响的节点。我们已经有了 Incremental——我们自己的增量计算库，它做的正是这件事，那为什么不用它呢？简单的回答是：特征往往关心事件的历史，而 Incremental 是围绕当前值构建的。

一个非常适合 Incremental 的计算例子是计算 ETF 的价值。其核心是一个简单的乘积求和：把每只股票的价格乘以它在一篮子中的权重，再对所有股票求和。这个计算除了当前价格之外什么都不关心。（电子表格、构建系统和响应式 UI 也都以同样不涉及历史的方式工作。）

得益于这一性质，Incremental 可以使用两种优化：

- **合并更新：** 如果一个值在图需要重新计算之前变化了两次，我们可以放心地忽略除最后一个值以外的所有值。
- **截断（cutoff）：** 如果一个节点重新计算后值没有变化，就不需要重新计算依赖它的节点。节点被假定为其输入的纯函数，所以只要输入没变，输出也不会变。

我们来试一个示例特征的简化版：最近 10 笔成交的平均价格。如果我们用 Incremental 以一种朴素的方式实现它——以最新成交价为输入，再加一个存放最近 10 个价格的缓冲区——就会很糟糕：

```
let last_trade_price : int Incr.t = Incr.Var.watch ...
let recent_prices_average =
  let recent_prices = Queue.create () in
  Incr.map last_trade_price ~f:(fun price ->
    Queue.enqueue recent_prices price;
    if Queue.length recent_prices > 10 then Queue.dequeue_and_ignore_exn recent_prices;
    average recent_prices)
```
假设先后到来三笔成交，价格分别是 100、100 和 101。由于截断，第二笔成交永远进不了缓冲区，因为对它来说 `last_trade_price` 没有变化。更糟的是，如果图只在第三笔成交之后才重新计算，合并更新意味着我们只会把 101 加进缓冲区！

需要说明的是，Incremental 本来就不该这样用：`recent_prices_average` 内部的函数并不纯。通常的解决办法是把状态放在图的边缘。在这里，就是由行情数据处理程序维护缓冲区，而 Incremental 图只消费一个已经算好的平均值。这对这个简化版行得通，但我们真正的示例特征还需要每笔成交发生那一刻的中间价，而中间价位于图的内部。于是处理程序要么在每笔成交前重新计算整张图，放弃合并更新；要么把中间价再算一遍。每多一个这样的特征，图外就要多出一些手写代码。

## 把历史留在图中

理想情况下，历史应该和当前值一起留在图里。这是可以做到的，但要付出代价。Ron Minsky 在《Breaking down FRP》一文中写过这种取舍：“通过限制动态性，让历史变得可处理。”这正是 Flex Model 所做的选择。它放弃了在运行时修改图的能力（Incremental 允许这样做），以换取把历史保留在图中。

Flex Model 的做法是把每个特征拆分为一个事件处理函数（handler）和一个求值函数（eval）。事件到来时运行处理函数，更新节点的状态。当有人需要实际的值时运行求值函数，它根据输入和状态计算出值。例如，一笔 100 价位、5 股的成交是一个事件；当前的中间价（比如 101）是一个值。每个事件都很重要，但并非所有事件都会改变值。一个订单簿更新事件可能往簿里加了一笔新订单，却没有改变最优买价，因而也没有改变中间价。而两笔同价成交是两个不同的事件，却携带相同的值。所以，处理函数必须看到每个事件才能保持状态正确，而求值函数不必，因为它们只在需要值时才运行。

这样拆分之后，示例特征的代码大致如下：

```
module Recent_trade_vs_mid = struct
  type t =
    { recent_diffs : float array
    ; mutable next_idx : int
    ; mutable sum : float
    }
  (* 事件处理函数 *)
  let on_trade t ~trade_price ~mid =
    let trade_price_mid_diff = trade_price -. mid in
    (* 简化：未处理缓冲区尚未填满的情况 *)
    t.sum <- t.sum -. t.recent_diffs.(t.next_idx) +. trade_price_mid_diff;
    t.recent_diffs.(t.next_idx) <- trade_price_mid_diff;
    t.next_idx <- (t.next_idx + 1) mod Array.length t.recent_diffs
  (* 求值函数 *)
  let eval t = t.sum /. Float.of_int (Array.length t.recent_diffs)
end
```
注意，像中间价这样的无状态特征只需要求值函数。更复杂的特征，比如前面代码片段里的 `average_over_last_n_trades`，就是由和这个一样的节点构建的。节点可以组合，所以研究员大多是组合现有节点，只有在没有合适的现成节点时才自己写。

## 早期引擎及其问题

Flex Model 的早期版本已经做对了很多事。特征只实现一次，然后组合使用。同一份特征代码既用于实盘，也用于历史回放模式，这让训练结果和生产结果更容易对齐。

但早期引擎是围绕单一策略的逻辑构建的。由于那个策略只关心订单簿更新，引擎不处理其他类型的事件。所以每个特征只能响应订单簿更新并报告自己的值。

那个策略需要某些特征在不同时刻就绪：有些用来决定是否下单，有些总是要计算，还有些只在我们决定交易后才计算，比如用来设定价格。这些特征分组被硬编码在引擎里，它们的运行顺序也是。分组是随着需求出现一个个加上去的，这从我们最终得到的函数名就看得出来（略有改动）：

```
(* 每次订单簿更新时的操作顺序：
   1) 交易执行逻辑依赖的特征：
      [| Feature_1_on_book_event; Feature_1_evaluate
       ; Feature_2_on_book_event; Feature_2_evaluate |]
   2) 总是要求值的特征：
      [| Feature_3_on_book_event; Feature_3_evaluate
       ; Feature_4_on_book_event; Feature_4_evaluate |]
   3) 其他特征：
      [| Feature_5_on_book_event; Feature_6_on_book_event |]
   4) 交易执行逻辑本身
*)
run_feature_provider_on_book_event_and_evaluate_execution_dependencies_and_always_evaluate_feature_providers
  book_event;
```
与此同时，用户想要更多功能，但由于我们只能响应订单簿更新，这些功能无法实现。特别是，我们想支持定时器、来自其他进程的消息，以及行情以外的数据源。每一项都需要为每个特征再加一个事件处理函数，并在引擎里加入更多硬编码的顺序逻辑。Flex Model 依然很快，但决定每个事件该计算什么的那部分代码，已经悄然变成了人人都避之不及的地方。

## 重建引擎

重建保留了处理函数和求值函数，但改变了由谁来决定什么时候运行什么。在早期引擎中，每个特征只有一个事件处理函数，在每次订单簿更新时运行。现在，一个特征对它关心的每种事件各有一个处理函数。和以前一样，它也声明自己读取哪些值。

启动时，一个新组件“规划器”（planner）会把这些特征定义转换成一份具体的计划——针对每种事件，列出需要依次运行的求值函数和事件处理函数。事件类型决定哪些处理函数进入计划，而它们读取的值决定顺序，因为一个特征读取的任何东西都必须先算出来。旧的分组不再需要了，因为交易逻辑现在只是另一个声明自己读取什么的特征。下面是为我们的示例特征生成的计划：

```
订单簿更新时：
  book                  handle
成交时：
  mid                   eval
  recent_trade_vs_mid   handle   (压入 成交价 - 中间价)
模型请求特征时：
  recent_trade_vs_mid   eval     (缓冲区的平均值)
```
订单簿更新时，我们只更新自己那份订单簿副本。此时还不需要任何值，也没有其他处理函数关心这个事件。成交则更有意思。先计算中间价，因为 `on_trade` 处理函数需要它，然后才运行 `on_trade`。最后，当模型请求特征向量时，我们运行 `recent_trade_vs_mid` 的求值函数。因为计划只包含真正需要的东西，一个市场用到的特征不会拖慢其他所有市场——而在被 Flex Model 取代的旧系统里正是如此。

我们只是按顺序执行计划中的动作，不考虑任何截断。这是有意为之。截断可以在图的某些部分节省一些工作，但每个节点在运行时都要多判断一条 `if` 语句，而这些分支 CPU 很难预测准（因为它们取决于本质上看起来随机的市场数据）。不用截断也让引擎更容易理解。

规划器只负责把事件名称和处理函数对应起来，并不需要知道一个事件代表什么。所以团队可以在普通的库里添加定时器、新数据源或来自其他进程的消息，而无需触碰 Flex Model 的核心。只有关心这个新事件的特征才需要为它写处理函数。在早期引擎里，同样的改动会波及每个特征和引擎本身。

## 提升性能

为了避免热路径上的垃圾回收停顿，大部分工作在启动时完成：Flex Model 加载配置，规划器生成计划，所有数据结构和回调都被创建好。此后，事件处理路径只读写预先分配好的内存。代码使用由编译器检查的 `[@zero_alloc]` 注解，如果热路径发生内存分配，测试就会失败。

Flex Model 中的大多数值是浮点数。要在不分配内存的情况下支持任意值类型很难，所以早期版本只支持浮点数。在我们的示例特征中，用普通 OCaml 写的话，`t.sum <- ...` 每次成交都会分配一个新的装箱浮点数。过去，让浮点数保持非装箱（从而避免分配）依赖于精心设计、却很容易被破坏的内联注解。有了 OxCaml——我们开源的 OCaml 编译器分支——这件事变得简单多了。现在，`mutable sum : float#` 不会分配内存。编译器工程师曾在香港和 Flex Model 团队一起待了几周，做非装箱浮点数的原型。开始使用它们之后，在我们的一次测试回放中，尾延迟下降了约 25%。

下一个要优化的是计划的执行。目前计划以闭包数组的形式运行，所以每一步都是一次间接调用。我们正在试验用 OxCaml 的运行时元编程，把整个计划生成为一个直线型函数的代码，并在启动时编译。这将去掉最后一层解释器开销，而这之所以可行，正是因为图一旦开始运行就不再变化。

## Flex Model 的现状

Flex Model 已用于许多交易系统。过去一年里新增了数百个特征，一些团队还编写了自己的事件类型。它也被用来构建这些系统的其他部分，因为一个按顺序处理每个事件的引擎，事实证明不只对特征有用——不过特征工程仍然是它最重要的工作。

我们把 Flex Model 的通用部分移到了实习生可以访问的代码库中，把较敏感的特征单独保留。从那以后，实习生已经为这个框架的许多部分做出了贡献。

Flex Model 起初是为了应对亚洲种类繁多的市场，它是我们这里各办公室孕育出的工作的一个好例子。亚洲是 Jane Street 工程师大有可为的地方，如果你喜欢这类问题，欢迎来和我们一起构建。
