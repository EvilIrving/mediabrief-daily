Kanchan Shringi：大家好，欢迎收听本期 Software Engineering Radio。今天的嘉宾是 AWS 副总裁兼杰出工程师 Marc Brooker，我们的话题是规范驱动开发（spec-driven development）。如果你试过用 AI 写代码，大概已经发现 vibe coding 效率有多高，但也会发现东西很快就开始出问题。规范驱动开发就是为了纠正这一点。它不把提示词当作主要产物，而是把规范和意图当作事实来源，用它们来驱动代码、测试和评审。Marc，欢迎你来到节目，很高兴请到你。开始之前，关于今天的话题或者你的个人介绍，有什么想补充的吗？

Marc Brooker：好的，谢谢你，谢谢有这个机会聊这个话题。我以各种方式构建软件差不多有 30 年了，可能稍微超过 30 年。作为一名软件工程师，也作为一个真心热衷于构建软件、更广义地说是用软件构建系统来服务客户的人，工具箱里多了这一整套新工具，我非常兴奋。

Kanchan Shringi：你说你以各种形式开发软件已经很久了。能不能先帮我们总结一下当前 SDLC（软件开发生命周期）的最佳实践？

Marc Brooker：好。当然，这在不同组织、不同团队之间差别很大，但在我看来，一个高绩效的软件团队是一个迭代很快的团队。他们在收集需求时离客户很近，离业务也很近。他们努力尽快从业务方和客户那里得到关于所做东西的反馈。他们往往在运维上也离自己构建的东西很近，尤其是云服务或 SaaS。而且他们跨多个职能紧密协作：软件团队、设计师、产品人员、面向客户的人员等等。我们可以再深入聊软件开发本身那部分，但对我来说，关键在于把团队和组织搭建成能够快速迭代、贴近客户、贴近业务的样子，这才会给软件开发带来好的结果。

Kanchan Shringi：你提了很多迭代、反馈回路和团队结构。到目前为止，很多团队采用的是 Scrum 或类似的迭代开发流程。当我们开始把 AI 引入进来，你观察到了什么？

Marc Brooker：变化最大的可能是流程开销的乘数效应变大了，它的影响变得大得多。比如说，我过去 70% 的时间在构建软件——真正写代码、测代码、写设计等等——30% 的时间花在开销上。如果构建软件那部分的速度提高到 2 倍或 4 倍，就算 2 倍吧，那这个比例突然就从 70/30 变成接近 50/50 了。随着软件部分、也就是写代码这部分越来越快，我们也必须想办法加快软件开发流程的其余部分，否则就得不到多少收益。所以我在团队里看到的二阶效应是：他们拥抱了 AI，拥抱了随之而来的更快编码速度，同时也不得不花很多精力去思考如何构建更好的流程。

Marc Brooker：怎么让这些流程更轻量？怎么用 AI 加速其中很多流程？现在围绕这个话题有大量讨论，我对此很兴奋。另一方面，要利用好 AI 带来的构建速度，还有一个重要的推动因素，就是拥有出色的测试基础设施，能够确认代码是可用的。我看到从 AI 中获益最大的团队，正是那些在测试基础设施和测试上做了投入、清楚自己的软件应该做什么的团队，所以他们能跑得非常快，而且是有信心地跑得快。

Kanchan Shringi：你花了很多篇幅讲围绕写代码本身的各种事情，而过去一年的热潮基本都集中在写代码上，vibe coding 这个词几乎没人没听过。

Marc Brooker：是的。

Kanchan Shringi：你是怎么走过这段路的，或者说你观察到开发者是怎么从 vibe coding 走到如今认识到它只是整个体验中的一小部分、而非全部的？

Marc Brooker：我觉得这某种程度上是一段自然的旅程。我一开始 vibe coding，感觉很棒，对吧？感觉效率极高，做了好多事，生成了好多代码，然后我意识到，得把它上线到生产环境。如果我想对业务和客户产生影响，就必须把它上线。哦，现在我得能测试它，得能验证它，得能确认我做的这些功能是客户真正需要的功能。所以这是团队身上自然会发生的事：我们拿起这些 vibe coding 工具，感觉很好，觉得效率超高。然后就出现了"然后呢"的那一步——然后我得维护这个软件。

Marc Brooker：我得测试这个软件。我得倾听客户，听取他们的反馈，改进这个软件。这时候就非常明显了：vibe coding 感觉再好、作为工具再有用，也不是全部，它解决不了端到端的软件生命周期。它只解决或加速了其中一小部分。即使你把这一部分大幅加速了，也还没有加速构建一个成功软件系统所需的整个端到端流程。不过如果我是在做给自己用的业余小项目，那没问题，完全可以，单靠 vibe coding 就能完成整个生命周期的一大部分。但如果我在构建关键服务的一部分，或者要交到客户面前、需要达到安全标准、安保标准和质量标准的应用，那我就需要更多的东西，从长期看更是如此。如果我需要把这个软件维护几周、几个月、几年甚至几十年，那我需要的是一个比纯 vibe coding 方式更可持续的流程。

Kanchan Shringi：你几次提到维护，这很关键。但在那之前，读代码呢？那是怎么运作的？代码评审怎么做？

Marc Brooker：是的，我觉得这是业界现在在问的关键问题之一：代码阅读往哪里走？代码评审往哪里走？在我看来，代码评审历来是一个极其有用的工具，能推动软件质量、推动团队对齐、推动 API 质量。我对它防止 bug 的作用不是特别乐观，但我认为它确实提升质量、改进代码设计，带来这些好结果。可是随着我们加速，这种代码阅读的角色是什么？我猜对很多代码库——不是全部，但很多——最终的情况是，代码阅读会走上 50 年前阅读汇编代码那条路。当年人们开始用高级语言编程时，有人会说：你要用高级语言，就得去读编译器的输出，检查它对不对。

Marc Brooker：人们确实这么做过，很久以前确实这么做过。后来随着时间推移我们不再这么做了，因为那感觉不是对时间的好利用，我们觉得评审高级语言有用得多、高效得多，结果也更好。我认为 AI 驱动的软件构建大致也会走到这一步：我们会把很多生成的代码看成某种汇编代码，对吧？它是实现细节，而我们要评审和关注的是规范，是"软件应该做什么"的书面描述，以及我们如何检查它确实做到了。

Kanchan Shringi：这正是规范驱动开发的关键：我们如何检查软件该做什么，以及当初是怎么把这些提供出来的？这是核心目标吗？你能不能退一步，从你的角度解释一下什么是规范驱动开发？

Marc Brooker：好，确实值得退一步讲。我觉得，自从我们把构建软件当作一件组织性的事、一项团队运动以来，其中一部分工作就是弄清楚软件应该做什么并把它写下来。有时我们写成正式文档，有时写成一系列工单，有时写成一堆餐巾纸草图和白板上的东西，这些都是规范。在这个 AI 新时代，我们发现的是，把你的软件要做什么写下来——我们管它叫"规范"，这个词暗示了一定程度的正式性，但其实不一定需要——它是一份在必要程度上足够清晰的描述，说明软件能做什么、一个成功的软件是什么样子。

Marc Brooker：一旦有了这个产物，我们就可以用它做两件事。其一是构建软件，通常借助 AI 辅助的流程。如果你看看 Kiro 这类工具里的规范驱动开发流程，那是一个智能体（agentic）流程，它拿着规范开始用代码把它实现出来。另一件可以用规范做的事是构建测试。这正是基于属性的测试（property-based testing）这类技术大显身手的地方。我可以从规范中提取属性，构建测试来断言这些属性在我写出的代码上成立。但关键在于，规范不是静态产物。随着我写代码、测代码、和客户交流、和业务方交流、倾听各方利益相关者，我会不断改进这份规范。

Marc Brooker：我会把它澄清，也许在某些方面把它泛化，也许把其中某些部分写得具体得多。也许我会加进一些代码片段或 UI 草图（mock），来改进规范。然后这又反过来改进代码、改进测试。所以这是一种迭代式的软件开发方法，一种短周期迭代的软件开发方法，但它非常明确地把我们要构建的目标写下来，然后真正用 AI 工具来加速构建过程。

Kanchan Shringi：你提到了 Kiro，能跟听众介绍一下 Kiro 是什么吗？

Marc Brooker：好。Kiro 本质上是三样东西。它是一个 IDE，也是一个 CLI，即命令行界面。最重要的是，它是我们在 Amazon 构建的一套智能体，我们自己内部开发也在用——我们可以聊聊用它取得的一些成果——它也向客户开放，是一套用于智能体开发的工具。它支持 vibe coding 模式，支持基于 CLI 的逐步模式。但在我看来最重要的是，它支持这种规范驱动开发方式：你在 Kiro IDE 里和 Kiro 智能体一起编写软件规范，然后用这份规范开发软件，用这份规范构建测试，由 Kiro 智能体驱动，然后再形成反馈。你把软件推向外界、展示给大家，再把反馈拿回来改进和打磨规范。

Kanchan Shringi：现在市面上已经有很多工具了。我很好奇，是什么促使你们再做一个新的？

Marc Brooker：我觉得当时我们有两方面的愿景。其一是，当我们开始构建 Kiro 和 Kiro 智能体时，业界正在从把 AI 当作智能自动补全——那是个不错的过渡阶段——转向这种逐条提示词开发的 vibe coding 模式。我们在 Amazon 和 AWS 内部也用过这种方式。我们发现，这种逐条提示词开发早期感觉很好，但在更复杂的代码库上扩展得不太好。最重要的是，它在时间维度上扩展得不好。我们一条提示词一条提示词地构建软件，然后写一条提示词加一个功能，它就会把之前做的一堆东西给撤销掉。它有点忘了早先的需求。

Marc Brooker：这让我们好几个人从不同角度开始思考：如果我们能解决"需求随时间流失"这个问题会怎样？于是我们走到了规范驱动开发：把所有需求都写下来，把它们随时放在手边。这样在迭代软件时，就可以回头对照，问一句：这个软件还满足我们之前做的那些东西吗？这就像手里有一张地图，而不是只有逐个路口的导航指令。所以，构建 Kiro 让我们能够真正去试验、进而真正投入规范驱动开发。另一项我们一直在做的投入是代码推理和神经符号 AI（neuro-symbolic AI），也就是用符号工具、求解器等 AI 中更形式化的那一面来对代码做推理。我们也想以更容易上手的方式把这些工具的能力带给软件开发者。把这些工具内置进 Kiro，让它们支撑我们在基于属性测试上的部分工作，就能把代码推理工具和符号推理工具的能力带给程序员，而不要求他们成为形式化方法或自动推理等领域的专家。

Kanchan Shringi：能不能举个例子，带我们走一遍别人使用 Kiro 的步骤？我也很好奇你提了好几次的基于属性测试，能举个例子吗？

Marc Brooker：好，我们挑个例子。我们最近的一次发布——也许已经不算最近了——我们构建了 Aurora DSQL，一个出色的、可扩展的多区域多活 SQL 数据库。团队意识到客户需要一套驱动程序，好让这个数据库在 Java 里更容易使用。于是我们可以写一份规范，说明：这是我们要构建的驱动，这是它需要具备的属性，这是客户应该与它交互的方式，算是一个 API 草图，然后用这个流程生成驱动的实现。说到基于属性的测试，它会从规范中拿出某一条，比如"每次连接尝试都包含一个授权令牌"，然后构建一个测试，自动化地测试驱动 API 的大量、大量的使用组合，确保"每次连接尝试都包含授权令牌"这条属性无论 API 怎么组合都始终成立。

Marc Brooker：也就是说，要么我往 API 里传入东西，得到一个合法的请求；要么我传入东西，得到一个有帮助的失败或有帮助的错误信息。这算是偏小的场景，一个规模相对适中的项目，但非常有用。另一个更大的项目是，我们一直在构建推理基础设施中一个新的基础组件，同样用 Kiro、同样用规范驱动开发，这更偏云服务类型，而不是终端驱动。那里的规范讲的是：这是一个云服务，它做这些事，有这样的架构，有这样的 API，用 Rust 编写。比如我们要求全部使用安全（safe）代码，然后据此生成代码。接着我们又得到这些规范或属性，比如：如果客户调用这个 API，要么以这种形式转发请求，要么以这种形式路由请求，要么给客户返回一个有用的 400 或 500 错误信息。基于属性的测试要做的、也是它如此有意思的地方在于，它不会像人类开发者那样只测五六个用例。它会自动化地去测几百、几千、几百万种不同的 API 组合，确保这条属性在所有组合中都成立。

Kanchan Shringi：能不能带我们走一遍各个阶段？根据你说的一些内容，可能并非所有项目都适用。但我想到 SDLC，结合你给的一些提示：规范是第一步，那么问题是能否用 AI 来完善规范？然后是架构文档、设计文档，代码生成会跟在后面，再谈谈代码评审。你确实说过生成的代码可以开始看作汇编，不一定要去读，但你是否仍可能用另一个模型、通过某种形式的代码评审来验证代码？你讲了很多测试，不过能否带我们走一遍复杂项目的所有阶段，再说说简单项目哪些就不必做？

Marc Brooker：我觉得每个项目的第一步都是弄清楚你要解决什么问题、为谁解决，对吧？客户是谁，他们需要什么，业务的需求是什么？AI 在这里能帮忙。它能帮我汇集一堆需求，帮我写文档，帮我想清楚需要问不同利益相关者哪些问题，但它并不从根本上改变软件生命周期中的这一步。而这一步会因项目而异。如果我在为一个新的 AWS 服务写一段非常重要的代码，我会铺得很开，会和很多人交流，真正弄懂其中的经济账。如果我只是随手鼓捣一个软件项目，那这件事我在脑子里几分钟就做完了。然后就是写下规范的初始版本这一步。

Marc Brooker：这一步我可以手工做，也可以让 AI 帮我。可以是这样开始：基于这些提示、这些客户用例、这些客户反馈的具体事例来编写一份规范。然后我读这份规范，说：不对，这不太是我想要的，我们一起来迭代。所以这可以是从我一口气全写下来，到某种"vibe specifying"（凭感觉写规范），对吧？比如我一块一块来，一个事例一个事例地检查它们在规范里是否得到满足。但重要的是我在读这份规范，在思考它：这是对的东西吗？而且它只是初始规范，我们待会儿会闭合这个回路。接着，仍然和 AI 协作，我要把这份规范转化为一组设计决策。

Marc Brooker：比如这是一个 Web 服务吗？是微服务、是库、是 UI 应用、还是 Web 应用？这些都是重要的设计选择，同样由业务需求、由我要解决的问题的需求驱动。它们不是 AI 能替我做的决定，而是我基于对所解决问题的理解做出的决定。然后我们要做一系列实现层面的选择。我要选编程语言，也许选一些框架，也许选一些库。如果我在做 Web 应用，可能会用 TypeScript；如果在为 AWS 服务做新组件，可能会用 Rust；如果在做给别人在 Python 里用的库，可能会用 Python；如果在做 AI 科研和数据分析，也许还是用 Python。我想要什么框架？

Marc Brooker：用内部框架还是外部框架？用开源的东西吗？这样我就有了规范，有了软件设计的高层描述，也有了这些实现选择的低层描述。然后我就进入下一步：好，去生成代码，生成第一版代码和第一版测试。我会和智能体一步一步来，逐步推进规范，在每一步确保自己在前进，实现规范中越来越多的内容。然后就到了关键环节：代码生成好了，所有测试都通过了，现在我要看它是否满足客户或业务的需求？它是否做到了我构建这个软件系统所要做的事？

Marc Brooker：也许一开始它满足了，但随后人们会说：要是有个功能能做这件事就好了；要是这个按钮放在那边就好了；要是你重新设计一下让它在某些方面更清楚就好了。于是我就回到起点，回到规范，回到那些设计选择，迭代地修改它们。然后和智能体一起重建代码，和智能体一起重建测试，再把软件放到生产环境里运行。所以它始终是一个迭代过程，但这个迭代过程的核心目标是让规范保持最新，而在它下游的是让代码、测试等等保持最新。

Kanchan Shringi：我从你的话里还听出另一个好处：它让你能一路检查，而不是把规范扔给 AI 然后直接拿到最终生成的代码。你实际上有一个检查点，可以阅读生成的设计文档，确认它是对的，或者核对规范本身的细节，确认它是对的，等等。是这样吗？

Marc Brooker：对，完全正确。让 AI 跑多久，可能因应用、因目标而异，但它确实给了你这个检查点，让你确认：我的方向对吗？我在往对的地方开吗？就像你坐进一辆无人驾驶出租车，说"我要去这个地方"，然后看着窗外：我们是往那儿去吗？或者我改主意了，想去别的地方。所以它确实给了你这些中间步骤：好，在我去生成这么多代码、花这么多时间、花这么多 token 之前，我构建的东西真的能解决客户的问题吗？

Kanchan Shringi：关于你们用的模型有个问题。你有没有观察到，在其中某些阶段换用不同的模型有什么好处，比如在代码评审阶段？

Marc Brooker：嗯，这很有意思。其实我们是该谈谈代码评审的问题。我想暂且说是的。以目前的技术水平——而且事情变化太快，可能到这周末就不成立了——就我目前所见，让一个独立的智能体来做代码评审之类的事，而不是让写代码的那个自我监督，确实非常有用。你需要这样一个智能体，把代码当作一个产物来审视：它是否达成了我的目标？设计得好吗？内部 API 好吗？所有这些我们认为能累积成长期良好可维护性的东西。所以是一个不同的智能体，用不同的提示词，带着不同的目标，这对智能体来说才是重要的。那么换用不同的模型有帮助吗？我想暂且说是的。同样，我们看到了一些不错的迹象，用不同规模或不同能力的模型做代码评审是有用的，但我不会说这能比得上那种根本性的多智能体架构那么有用，也就是说：我希望代码评审由一个以追求卓越代码质量为目标的智能体来做，而不是由那个以实现规范、初步构建代码为目标的智能体来做。

Kanchan Shringi：前面我们聊了你们是怎么想出这套方法论的。你有没有一个故事，可以对比一下用 vibe coding 构建的项目和遵循规范驱动方法论构建的项目？

Marc Brooker：我不确定我们有没有做过 vibe coding 和规范驱动开发的那种并排对比，但我们发现的是——这么说吧，Amazon 是一种非常面向服务的架构，类似微服务架构，公司内部有成千上万个服务，各自提供某些功能。在我们采用 AI 的过程中，拥有这些服务的团队反馈说，他们一开始确实是用这种 vibe coding。他们发现，把代码库拉进 IDE，提示做一个修改，往往能看到修改成功实现了，但同时也会看到回归问题。AI 会把代码的某件事、某条属性给忘了，就好比说："我把这里优化了"，但这破坏了 API，让服务不能用了。

Marc Brooker：所以我们在 Amazon 内部看到的做法是：我有服务代码，我从中提取出一份规范，哪怕是一种逐个方法地把代码转成文字的过程，然后在规范驱动开发流程中使用这份规范。这会让构建下一个功能的那个智能体好得多，不会把过去的好东西撤销掉；也让另一个负责构建测试的智能体在考虑该构建哪些测试时好得多。所以我觉得我们没有做很多并排对比，但我们发现，随着团队拥抱规范驱动开发，规范这一层抽象是帮助他们跑得快得多的一步，因为它终止了在现有代码库上做 vibe coding 时可能出现的那种"进两步、退一步"的局面。

Kanchan Shringi：这点说得好，等我们多聊一些提供上下文的内容时再回到这里。但在那之前我很好奇：规范驱动是一种方法论，Amazon 构建了 Kiro，但我想规范驱动也可以应用到其他智能体 IDE 上。这么假设合理吗？

Marc Brooker：当然，完全可以。这是一种可以用于任何流行工具的方法论。它不像我们努力在 Kiro 里做到的那样顺手，但它是一种普遍有益的方法论。所以无论团队用什么工具构建软件，我们都推荐他们用。

Kanchan Shringi：谢谢 Marc。我们回到提供上下文的话题。我觉得你提了一个好观点：除非规范本身或你告诉 LLM 的内容包含了代码的上下文，否则总会出现回归。我们能把这点推广吗？是不是可以说，vibe coding 对新项目或者开源项目更有效？

Marc Brooker：开源我不确定，但我觉得我们至少从经验上看到，如果你从一开始就用 AI 构建一个代码库，AI 会觉得这些代码更容易理解。为什么会这样我其实不太清楚，但从经验上讲，我自己的体验是这样，我从同事那里听到的也类似。我还想说，对我来说，纯 vibe coding 那种轻松有趣的感觉在全新项目（greenfield）的场景下效果最好，但一旦我面对的是一个规模可观的现有代码库，就发现从这种交互中得不到那么多好处。所以是的，我会说 vibe coding 流程在从零走到一个很棒的初始原型这段路上，简直棒极了、效率极高。但在那之后它就没那么可扩展了，会逐渐后劲不足，对吧？

Marc Brooker：而规范流程会在前期多加载一点工作量，这一点没什么好隐瞒的。但你得到的是一个可持续得多的持续过程：更容易维护，更容易迭代，更容易在不引入回归的情况下添加功能，更容易获得很好的测试覆盖，更容易获得很好的 QA 覆盖。所以通过在开头多投入一点——不是多很多，只是多一点——你最终得到的是一个不会掉下去的流程，一个长期保持有效、保持高效的流程。

Kanchan Shringi：在上下文方面，你谈到了提取上下文并作为规范的一部分提供，但这够吗？我是说，代码库可能非常大，你当然不可能每次都这么做。还有哪些提供上下文的方式？

Marc Brooker：我非常喜欢这个问题，原因有两个。其一是，我觉得在很多方面，2026 年是思考 AI 智能体上下文管理的一年。它确实已经成为智能体构建领域最重要的问题之一。所以这是整个行业今年都会投入大量思考和大量资源的事情。其二，我们想想：在构建软件这个场景下该怎么看待它？对我来说非常有意思的是，我们为了让软件和代码库对人类可理解而发展出的那么多技术，在这里同样非常好用。从结构化编程的早期，一路回溯到 60 年前，我们一直在思考：怎么构建接口？

Marc Brooker：怎么实现模块化？怎么把功能抽取成库？怎么把功能抽取到 API 后面？无论是库 API、本地服务 API 还是远程微服务 API，我们让软件模块化，构建了 API，构建了契约，构建了协议。这些都是把一个极其复杂的软件、限制其交互方式、让我们人类能够推理它如何运作的手段。在很多方面，长期成功的软件和长期不成功的软件之间的差别，就在于它们能否以这样一种方式构建：能够演进，而不是每一次修改都可能改变它运作方式的一切。这正是贯穿整个软件历史、推动面向服务的微服务架构流行、推动库和模块化流行的原因。

Marc Brooker：所以我们可以这样想：在 AI 领域，要管理上下文、帮助 AI 理解代码库，我们需要的同样是模块化，是良好的设计，是良好的 API，是对 API 及其契约的良好文档——它们是什么意思、你可以假设什么、可以依赖什么。做到这些之后，你就可以在上面叠加语义搜索之类的东西。比如：我在找做这件事的库方法——好，在这儿。这样我就不必了解整个系统的一切。我可以说，这个库调用接收这些输入，对系统产生这样的效果。于是我能更局部地推理系统的行为。所以对我来说，软件智能体的上下文管理和人类开发者的上下文管理非常相似：把"在大规模下推理系统中每一行代码及其相互作用"这个不可能完成的问题，转化成更局部的推理，比如：我能不能只思考这一个库调用、这一处修改？我们越能把软件设计得让修改尽可能局部，成功修改所需的上下文就越少，就越能把修改测试好，效率也就越高。我认为这对 AI 智能体是成立的，正如在六十多年的软件工程实践中对人类一直成立一样。

Kanchan Shringi：你提到了一种方式，或者说两种。一种是把上下文提取到规范里，另一种是语义搜索，那可能需要为代码库里的一堆代码生成向量。你还试验过别的什么？对于现在刚进入这个领域的人，你有没有什么指导，他们应该怎么做？

Marc Brooker：嗯，我觉得在代码库索引、代码理解以及从代码库中提取理解方面，正在进行一些非常有意思的工作。但对于刚起步、开始进入这种编程方式的人，我会鼓励他们去思考软件设计，思考内部接口。思考类型，思考 API，思考如何以良好封装每个组件功能的方式来构建软件。这样当你告诉 AI 或修改规范时，就容易得多地找到要做事的那几行代码，对吧？比如就在 UI 点什么、TS 文件之类的地方，而不是"这东西散落在我整个代码库里"。我能找到那几行代码，能去修改那几行代码，而且它们尽可能局部。

Marc Brooker：所以刚开始做这件事时，一个可以去优化和留意的指标是：我要修改规范，比如添加一个小功能，AI 需要动我系统中的多少个模块才能做到？如果它得动系统里的每一个模块，那我就有一个设计问题，会随着时间推移让我的 AI 驱动开发越来越低效。如果它只需动系统中的一两个模块、一两个库、一两个服务——无论我怎么划分的——就能完成一个小功能改动，那我的设计很可能长期可行，能很好地扩展，不会撑爆上下文窗口，也不需要复杂的索引等技术。所以如果我看到这个数字在上升，也就是构建一个功能或添加某项能力需要修改的模块数量随时间上升，那也许就该退一步，和 AI 一起做些重构，把模块拆开，把 API 拆开。好消息是，AI 和这些智能体，尤其是在你已经在优秀测试上做了投入之后，做重构任务的能力极其强大。

Kanchan Shringi：我们聊聊你说的撑爆上下文窗口。什么时候会发生？还有一个相关问题：什么时候上下文太多，反而会损害结果？

Marc Brooker：这因模型而异，而且随着模型能力有所提升，它已经不那么成问题了，但仍然是个真实存在的问题。打个比方，我走进一家咖啡店，对方问：你想喝点什么？我说：我想要一杯拿铁，顺便说一下，外面 18 度，海鹰队（Seahawks）昨天赢了。这不仅会浪费一堆时间，还会把对方搞糊涂：这跟我有什么关系？你为什么告诉我这些？是想让我根据这些额外信息给你定制饮品吗？所以这会让人困惑。我觉得几乎可以类比——用类比来推理 AI 有一点风险，但几乎可以类比——往上下文窗口里塞一堆无关的东西，会让 AI 的结果变差。

Marc Brooker：所以这就是上下文管理变得如此重要的地方，它有两个方面。一是我刚才讲的那些设计和模块化的东西。二是 AI 工具，无论是 Kiro 还是其他众多 AI 驱动的开发工具，必须管理上下文窗口里放什么：确保有足够的上下文，让 AI 至少有能力发现自己该做什么，但又不能有太多上下文。如果里面包含一堆无关噪声，结果就会更差。那么想想智能体是做什么的？AI 智能体做的事情之一，就是通过一个发现的过程来构建自己的上下文窗口。

Marc Brooker：它们会去读那个文件，搜这个索引，用这个 MCP 工具对文档做语义搜索，努力构建自己的上下文窗口。同样，智能体开发之所以有挑战，原因之一就在于要确保它们尽可能可靠地构建上下文窗口，让相关信息与无关信息的比例尽可能高。所以这里有三件事：我该怎么构建和维护代码库，让它对人类和智能体都"上下文友好"？作为开发工具的构建者，我该怎么思考上下文管理？以及更广泛地，作为智能体开发者，我该怎么引导这些智能体有效地构建上下文窗口？还有我给智能体的工具返回的是什么？返回的是对的东西吗？它们是否让智能体能只请求所需的事实，等等。

Kanchan Shringi：那么如何有一个流程，确保你提供上下文的方式——如果来源不是代码本身——能保持更新？这是开发流程之外的事，还是内建在流程里的？

Marc Brooker：是的，这在软件领域同样不是新问题：我怎么让文档保持更新？前 AI 时代真正的挑战之一是，我怎么让需求和规范保持更新？规范驱动开发让一切都从规范向下流动，大大简化了这件事，在规范的时效性问题上帮了大忙。但文档时效性的问题依然存在：我怎么让文档保持更新？在之前的时代，我会从开发工作中抽时间，或者由技术文档撰写人员去查找代码的变化，再去更新文档。现在我可以用 AI 非常有效地加速这个过程：在协助我软件开发流程的那组智能体里，安排一个智能体去保持文档更新，保持 README 更新，保持 API 文档更新。

Marc Brooker：这又反馈到我下一轮想做修改时的流程中。我怎么知道那份 API 文档是最新的？因为我作为软件开发流程的一部分一直在持续更新它。所以即使在 vibe coding 的时候，即使不走规范驱动开发流程，我也总会确保我的提示词或引导文档（steering documents）在指示智能体保持 README 或某份文档更新：既供我作为人类参考，供客户在使用我的软件时参考，也供智能体自己在执行下一组步骤时参考。

Kanchan Shringi：谢谢 Marc。接下来我想花点时间谈谈：你们如何确保配置和模型本身是有效的？起初你把这套东西推广给团队，然后负责维护配置、上下文以及各种工作流程的核心小组，他们怎么让这些保持更新？比如说出了一个新模型，你怎么确保它没有以任何形式让流程退化？

Marc Brooker：嗯，我想正式的回答是：我们有一套评估流程。我们会拿一个智能体工作负载，大概先从离线开始，用新模型、新配置或新提示词跑一批样例，比较新旧两者的成功程度。可以由人来看，可以看测试是否通过，可以看采纳率，也可以用"LLM 当评委"（LLM as a judge）这种模式，本质上用另一个智能体给智能体的输出打分，说这些更好、这些更差。下一步，也是我认为实际上最有力的，是在线评估：好，我要开始在生产环境中试验这个新模型，类似 A/B 测试。

Marc Brooker：我给它分 5% 的流量，再分 10% 的流量，然后把所有成功信号反馈回来——无论是 LLM 评委、人类反馈、延迟信息，还是测试成功率——来看新版本是否做得更好。如果看起来更好，初步试验结果不错，我就逐步加量，最终提到 100%，然后准备好做下一个试验。之后在生产中持续不断地评估智能体的结果。同样，用什么指标取决于任务，随着时间推移我会知道：我的成功率好吗？如果成功率出于某种原因突然变化，或者呈下降趋势，那我就需要弄明白为什么。

Marc Brooker：也许我的任务变了，也许客户的需求变了，也许我有某段糟糕的上下文，也许那份 README 里有错误信息，把智能体引向了错误方向。但这里真正关键的是，从智能体构建者的角度——这里我说的不是 IDE 用户，他们其实不需要操心这些——而是我作为智能体构建者，需要思考如何拥有一套稳健的评估，这样才能围绕智能体、模型、提示词、上下文以及上下文的管理方式，运行一个真正数据驱动的改进流程。我做得越多，能给客户提供的产品质量就越好，也就越可靠。它还能帮我回答这样的问题：我今天在用一个非常大的模型做某件事，能不能换个小模型来降低延迟？孤立地回答这个问题，老天，几乎不可能；有了一套稳健的评估器，回答起来就容易得多。所以这是面向智能体构建者的流程，但它其实回到了整个问题的起点：我们想达成什么？我们想要的结果是什么？客户需要什么，业务需要什么？

Kanchan Shringi：结果是什么，然后成功率是多少。不过具体来说，团队应该衡量哪些东西？应该衡量 bug 率吗？人工代码评审中是否需要人工纠正？应该衡量代码与规范的偏离程度吗？能分享一下团队应该关注哪些指标吗？

Marc Brooker：同样，最重要的是端到端的指标：客户是否在生产中遇到 bug，客户是否在生产中遇到回归，客户对生产环境中的表现是否满意。这些是最重要的指标，但也是最难衡量的，风险也最高，因为我们希望在客户报告生产 bug 之前就把问题抓住。所以我们会在流程更早的阶段选择一些代理指标。比如，我是否看到回归测试失败？回归测试的失败率是多少？如果用人工代码评审，人工评审的通过率好吗？如果用独立的代码评审智能体，那个智能体的通过率好吗？

Marc Brooker：它给我的效果好吗？如果我在用渗透测试智能体，比如我们在 re:Invent 上发布的那个做"最后一公里"安全测试的智能体，它是否在上线前发现了安全漏洞？所以，如果我看到 bug 是在最后一个上线前的里程碑才被抓住，我就知道软件开发流程更早的环节出了问题。可能是软件生命周期早期的测试不充分，可能是糟糕的设计和接口的症状，也可能是某些糟糕的实现选择需要我去修正。或者是写进测试的需求和写进软件构建流程的需求之间没有对齐。比如其中一个说你需要在 10 毫秒内给客户返回结果，另一个说 10 秒，那显然会出现失败。

Marc Brooker：所以这些指标之间存在一种张力：最有价值的指标在软件开发生命周期的最末端，因为它们是我真正关心的，是客户看到的，但那里的代价也最高。所以我想把尽可能多的问题捕获和这些指标往流水线的左边推。这同样是软件工程的经典理念：尽早发现 bug。软件工程师已经这么说了四五十年，这一点没有变。

Kanchan Shringi：谢谢 Marc。现在我们多谈谈如何把这套东西推广到团队。有什么前提条件吗？需要发生某种思维转变吗？还是开个会、介绍一下工具，告诉大家"去用吧"就行？

Marc Brooker：嗯，我觉得这因情况而异。我认为最大的前提条件几乎是文化层面的。我们在新开发实践的推广中看到的是：你需要一个对客户和业务有深刻理解、标准很高的团队。你不能接受——我想现在大家用的词是"slop"（粗制滥造的 AI 产出）——我们不希望软件流程里出现这种东西。但同时我们也需要这样的人：转型最快的团队，是那些好奇心很强、真心乐于接触新东西、并且有很强行动倾向（bias for action）的团队，他们会说"我们去试试、去做实验"。所以我看到真正推动成功的，是团队内部的这种张力：我们要去尝试新东西，我们真心热衷于学习、尝试和采用新工具；但同时，我们绝不会为客户、为业务、为工程团队接受糟糕的结果。

Marc Brooker：当你把这两者结合在一起，我觉得奇迹就真的发生了。除了这种文化上的优点，我们也不应指望团队拿起一个新工具就立刻知道怎么用好。你需要这种沟通和分享：我们这样试过，这是我们学到的，这是我们想传给你们的。你要把这些融入团队之间的沟通。如果你在构建工具，就要把这些经验融入工具里。所以成功的另一部分在于，确保当一个团队学会更好地使用工具或改进工具时，整个组织都能学到。

Marc Brooker：理想情况下是整个世界都学到，我们一起推动一切向前。有时是大的经验，比如：我们要引入规范驱动开发，因为我们发现它比逐条提示词的 vibe coding 扩展得更好。有时是小事，比如：我们发现用这种方式索引代码、或用这种方式组织代码效果很好。举个具体例子，我们在 Amazon 内部发现，在 AI 驱动开发中使用 Rust 这样的语言——它有强类型系统和大量编译期检查——非常有用，能在流水线更早的阶段抓住 bug，从而加速开发。所以这是我们想传达给团队的信息：Rust 效果很好，TypeScript 效果也相当不错，Python 里的类型注解值得投入。

Marc Brooker：所以经验在组织中的传播极其重要。关于这点最后再说一句：毫不意外，整个 AI 领域发展得太快了。新技术、新工具几乎每天每周都在冒出来。要取得成功，你需要权衡的一点是：你希望团队关注这些新工具、对它们保持好奇，但你也承受不起天天去追每周的潮流。所以这里需要找到平衡。我们想采用新东西，想快速采用最好的东西，但不想把所有时间都耗在反复折腾、尝试当下最新最热或最时髦的工具上。所以是的，组织层面的成功需要把很多东西结合起来。

Kanchan Shringi：好奇心当然很关键，但从你的话来看，行动倾向似乎更重要。不过，具体到 AI 这件事，也存在一点恐惧。你怎么应对这一点？

Marc Brooker：哪种恐惧？能多说说是哪些担心吗？

Kanchan Shringi：我是说，随着 AI 做得越来越多，在这段旅程中，对开发者的期望会变得不同，或者变少吗？

Marc Brooker：我认为软件开发这份工作，更广义地说软件工程这份工作，正在改变。我们的工作在 2 年、5 年、10 年后会和今天大不相同。任何重大变化都会带来不确定性。人们会思考：这个变化对我意味着什么？对我当初进入这一行的理由、对我热爱这份工作的那些地方意味着什么？对此我非常乐观。我认为 AI 驱动开发正在解放我们，让我们花更多时间在重要的事情上——无论这些重要的事是更贴近客户、更贴近业务、真正理解我们所构建系统的全局，还是深入设计的各个部分、深入协议、深入效率——而少花时间在构建中那些同质化的琐碎杂务上。

Marc Brooker：所以是的，这是行业变化非常快的时期，我认为这总会伴随一定程度的焦虑。我非常乐观地相信，它将解放我们去做更有成就感、更有价值的工作。几十年来我们看到软件是多么强大的经济力量。而在软件存在的整个历史中，它一直受供给约束：软件的经济影响一直受限于我们能构建多少优秀的软件。我坚信，如果我们能用 AI 工具把软件开发成本降低到十分之一，软件的经济影响至少会扩大 10 倍，甚至 100 倍。

Marc Brooker：所以我认为软件和软件工程在未来会比今天更加重要，但它会是一份不同的工作。它会包含不同的东西，我们需要以不同的方式去优化。我觉得人们对此感到有挑战是非常合理的，停下来反思"这对我意味着什么"也是非常合理的。我只能说，就我个人而言，作为一个一直对技术充满热情和兴奋的人，我觉得未来实在太令人激动了。

Kanchan Shringi：谢谢 Marc。我们开始收尾了，还有几个问题。软件开发之后的那些步骤呢？部署、事故管理等等？这和你们在 Kiro 或 AWS 其他方面的设想有关联吗？

Marc Brooker：去年 12 月的 re:Invent 上，我们发布了 DevOps 智能体（AWS DevOps Agent），它是为在云上做这些 DevOps 工作而设计的智能体，协助处理事故、处理工单、协助基础设施的维护等等。所以这是软件团队工作的另一部分。我们还发布了安全智能体（AWS Security Agent），用于协助渗透测试以及安全测试生命周期的其他环节。我们还有 AWS Transform，这是一组把系统从一种实现迁移到另一种实现的智能体。既可以是小的打补丁任务，比如"我想升级到最新版本的 Java"，也可以是大型软件的重新架构，比如"我想脱离大型机、迁到云上"。

Marc Brooker：所以它远远超出了构建软件本身。我们会用智能体加速软件部署，简化软件运维，简化软件维护。维护是很大的一块。我认识的软件工程师里，没几个会对"确保能从 Java 11 迁到 Java 17，或者 21，或者现在最新的哪个版本"感到兴奋。但这是关键工作，对安全、对效率、对其他所有方面都至关重要。所以这会是很大的一块。能够更轻松、更低风险地更换后端实现，对工程团队意义重大。比如：我有这么多遗留系统，是我以前构建的，也许全是用 Fortran 写的。它是我们组织的镇店之宝，因为它是我们业务逻辑的唯一表达。

Marc Brooker：我怎么把它带进现代实现？怎么把它带进现代架构？这是 AI 真正会帮我们推动的事。测试验证、UI 测试，围绕软件的流程有太多东西，甚至包括更新工单，所有这些。我认为这些是我们在 AWS 大力投入的领域，因为我们一直在密切关注软件开发者——无论是内部的还是客户那边的——把时间花在了哪里。软件团队和组织在这些事情上花了大量时间，但它们不像构建软件那样光鲜酷炫。所以所有的热度都集中在"这东西能帮我更快写更多代码"上。我觉得这也没问题，但真正的大局是：这东西能让我作为一个软件组织、作为软件组织的领导者，更快、更可靠地为客户交付价值。而这需要的远不止写更多代码。

Kanchan Shringi：不过，你们在构建这些智能体时仍然在写代码，你们在写代码来构建这些智能体。为智能体本身生成代码有什么特别需要考虑的地方吗？

Marc Brooker：是的，我认为这是一个正在兴起的领域。看看最初几代的智能体构建，大量的 Python，大量临时性的技巧，这些都很有价值。但随着时间推移，正在浮现的方向是：我们能不能混入符号推理之类的工具？能不能加入更多结构？举个例子，我们在我们的智能体框架 Strands 里构建了一组很酷的功能，叫 Strands steering，它使用一种神经符号技术，把模型和符号推理结合起来，把智能体的运行轨迹往正确的方向推一推。我们看到越来越多的工具在闭合这个优化与评估的回路，比如改进工具描述等等。我们还看到像我们在 AgentCore 里构建的 Policy 这样的工具：你可以用纯文本描述一条安全约束或运维约束，把它转换成用 Cedar 这类可证明的语言写成的、清晰明确的授权代码，并应用到所有智能体上。

Marc Brooker：所以我认为我们将要学习、也正在积极学习的是：如何构建围绕智能体的软件开发实践和工具，让我们能利用智能体的灵活性和能力——这正是我们需要的，我们希望智能体灵活，希望它们在解决问题时几乎具有创造力——但同时又要以安全、满足业务需求、不做危险事情的方式来做到这一点。Policy 帮助实现这种平衡，Strands steering 也帮助实现这种平衡。我们还需要降低成本，这就是模型定制之类的东西发挥作用的地方。所以智能体构建正处在一个非常激动人心的时刻：既已经产生了巨大影响，又有海量的创新。我认为在接下来几年里，构建可靠的智能体会变得越来越容易，构建高性价比、投资回报出色的智能体也会更容易。这一直是我们在 AWS 的重点，当然也是整个行业的重点：如何让智能体构建从一种相当随意、几乎像念一堆咒语的做法，变成一门真正的工程学科。

Kanchan Shringi：谢谢 Marc。我们没时间了，所以就不问你几次提到的神经符号推理了，但我很希望能拿到一些参考资料，加到节目说明里给听众。

Marc Brooker：好的，很乐意分享。

Kanchan Shringi：今天还有什么我们遗漏的、你想花几分钟讲讲的吗？

Marc Brooker：我想对软件构建者说的总体信息是：想想代码，它以非常非常清晰的方式向计算机编码了它做什么。但作为软件构建者，我们历来没有可靠地养成写下"为什么"的习惯：代码为什么是这样的？我认为规范驱动开发的力量，就来自于把"代码为什么是这样"同时向人类和模型明确表达出来。所以我认为我们将在软件领域看到这样一个巨大转变："怎么做"的细节也许会变得没那么有价值，而解释"为什么"的那些产物——软件为什么这样设计？它要达成什么？为谁达成？——会变得越来越、越来越有价值。如果你在做规范驱动开发，这一点成立；我认为在做 vibe coding 时也成立；而且我认为无论下一波由智能体驱动、由 AI 驱动、甚至由人类主导的开发实践是什么样子，这一点都会成立。

Marc Brooker：可以看看我的博客，brooker.co.za。我也在 LinkedIn、X 以及其他各种社交平台上。我很乐意在这些平台上分享我和团队在 AWS 做的工作，也一直很乐意听到大家深思熟虑的问题，和大家深入讨论软件工程的未来。
