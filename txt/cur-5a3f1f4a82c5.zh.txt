我们几乎在所有东西上都需要默认的硬性预算上限
2026 年 10 月 3 日

在接下来的几个月乃至几年里，世界将会越来越需要这样一个产品功能：默认的硬性预算上限。我说的是按用量付费的服务和 API 里的这样一个功能，它允许你设定"每月超过 X 美元后，切断这个服务并返回错误"。这必须是硬性限制。软上限，也就是"每月超过 X 美元后给我发一封警告邮件"，是不够的。

编程 agent 和个人 agent（套上了一层不那么吓人界面的编程 agent）大大降低了搭建能做有用事情的代码的门槛。有时这些事情是要花钱的——调用付费 API、托管的 Web 应用，或者会对额外存储和算力计费的系统。

没有人想在早上醒来时看到一封半夜发出的预算超限警告邮件，然后发现在自己睡觉时，失控的服务又多消耗了几百（甚至几千）美元的用量。

反对的理由之一是，企业不希望自己托管的应用因为超出某个预算而开始报错。我预计大多数企业和个人都宁愿看到报错，也不愿收到一张一万多美元的意外账单。

我认为硬性预算上限必须是默认设置。如果有人想冒险，应该允许他这么做，但必须是主动选择开启。在某个显眼的地方放一个清晰的复选框：

移除预算上限。即使超出所设定的预算限额，我的应用也不会被关停，后续产生的费用由我承担。

我最希望看到提供这一功能的服务是 AWS。我听过很多人说，他们出于（合理的）担心而拒绝用 AWS 做个人项目，害怕某个失控的服务会让他们破产。我也听过一些人没有预料到这种情况，结果被严重坑了的故事。

……结果发现，AWS 几周前终于推出了花费上限！摘自他们 9 月 16 日的公告《新的 AWS 体验帮助开发者更快上手、更快交付》：

当你准备升级到付费方案时，可以根据你的使用模式为项目设置月度花费上限，从而保持在预算之内。如果某个项目的用量达到花费上限，该项目将在当月暂停。

另见 AWS 设置中的"创建花费上限"页面，不过该页面提示"我们目前正在向有限数量的客户推出新体验"。希望它很快能对现有账户全面开放。

Google Cloud 在 7 月推出了一个类似的功能，叫作 Spend Caps，可以让你"为项目中的特定服务设定月度财务上限"。看起来这正在成为一种趋势！

在理想的世界里，我们的 agent 也能在这方面提供帮助。如果 agent 开始倾向于推荐提供硬性预算上限的服务商，并提醒新手和缺乏经验的开发者不要把应用部署在可能给他们带来麻烦的无上限服务上，那就太好了。
