Gergely：Uber 的软件工程师都在用哪些内部工具来开发软件？今天，我们请到了 Uber 资历最老的工程师之一 Uday Kiran Medisetty，独家带大家从内部、而且是大量配图演示地看一看。如今 Uday 主导着 Uber 的大部分智能体 AI 工作。这次对谈会聊到 Uber 在 AI 之前自建并使用的内部开发系统，比如 uOwn、M3DB、Michelangelo、Cadence、Morpheus 等；公司搭建的 AI 基础系统，比如 MCP Gateway、AI Guard 和 AIFX；还有几乎所有工程师都在用的新系统，比如 Minion、Code Inbox、Slate、Shepherd、Wisdom 等。如果你想了解在 Uber 这样拥有数千名工程师的现代科技公司里，AI 原生开发是什么样子，以及为什么在久经考验的开发者基础设施之上加装 AI 要容易得多，这期节目就是为你准备的。

今天这期讲的是 Uber 为了帮工程师借助 AI 智能体交付软件而搭建的近二十个内部系统。其中一个结论是：可上生产的代码远比单纯用一个 AI 编程 harness 复杂得多。harness 是容易的部分，难的是围绕它的一切。

Gergely：Uday，欢迎来到节目。

Uday：非常感谢邀请。我一直在关注你的工作，看到你产生的影响、你为所有工程师发布的那么多好内容，真的很了不起。所以今天能来这里聊聊我们在做的事，我非常荣幸。

Gergely：其实早在 The Pragmatic Engineer 诞生之前，我们就在 Uber 共事过。不算真正一起干活，但我也知道你的工作。你具体是什么时候加入 Uber 的？

Uday：我是 2015 年 5 月加入 Uber 的。事实上，当年推荐我的两位工程师现在都还在公司。我加入的是实时 API 团队，当时我们正在把单体应用拆成微服务。我负责的是所有移动 App 的 API 网关，还参与改造了我们的移动端协议。之后我做过很多不同的业务平台，从履约平台，到司机（earner）入驻、交易市场、定价。而最近这一年全是智能体 AI，既面向我们的用户、客服，也面向终端用户等等。所以这一年做这些事，就像坐过山车一样。

Gergely：对于没在那儿和我们共事过的人，能不能简单回顾一下实时 API，我们内部叫 RT API，它是什么，为什么那么重要，为什么承受那么大的负载？

Uday：我加入的时候，Uber 只有两个服务。一个叫 Dispatch，用 Node.js 写的；另一个叫 API，用 Python 写的。当时 Dispatch 处理所有乘客和司机的流量，协议也很简单，是一个每四秒一次的 ping 协议：你调用一次，它就把整个世界的状态都返回给你。行程结束后，交给 API 处理所有行程后的事情：支付、收据等等。RT API 就是在那时诞生的，用来把所有内部服务与移动端隔离开，同时把协议从简单的四秒轮询改成既有 REST API、又有服务器到客户端通信的形式，我们当时叫它推送协议。因为我们的 App 非常动态，每隔几秒一切都在变化。所以我们需要一种方式，在收到新更新、在物理世界发生变化时，高效地更新乘客端和司机端 App 的状态。所以它当时是 QPS 最高的服务之一。因为当时我们的技术栈只有 Node.js 和 Python，所以那是很自然的选择。后来几年我们把它改成了 Go，它到现在仍是我们 QPS 最高的服务之一。

Gergely：我想听众听到 2015 年前后 Uber 只有两个服务会很惊讶，因为 Uber 恰恰以微服务热潮出名。Thuan 上过这档节目，也聊过一点，但你能不能回忆一下，这些微服务是怎么出现的？在你看来，突然有了那么多服务意味着什么？

Uday：嗯，关于这个已经有很多博客、很多人讲过。正如我说的，我加入时只有两个服务。回想当时我们所处的超高速增长阶段：我们不停地进入新国家，不停地扩展出行业务的产品线，后来又加了 Uber Eats，也在不断扩张。我们需要一种机制，让各团队能非常快地构建各种功能，跟上业务增长的规模。所以我们在各种服务基础设施上投入了很多，让团队能方便地构建服务：指标、链路追踪、监控、可观测性、部署，以及围绕这些的一大堆东西。而按我们当时的规模和变化速度，市面上几乎没有现成的软件可用，所以那时很多东西都得我们自己在内部做。这就造成了一个爆发周期：我们从两个服务增长到了数千个服务的量级。然后在 2018、2019 年前后，我们统一了编程语言，选定 Go 和 Java 作为主要语言。我们把技术栈现代化了很多，花了大量时间思考架构分层、如何平台化。这些年里，事实上我做其中一个履约平台时，我们还把一些服务合并成了少数几个。即便到现在，我们的服务数量也大致在同一个量级，尽管业务规模大了十倍，产品也多了很多很多。经过这么多平台化和多年的投入，我们在运营的所有国家仍然跑着同一套全球技术栈。有很多很多平台用共享的构建模块服务于所有出行业务线和所有配送业务线，这让我们能开拓更多出行和配送业务线，因为这些年我们做了大量平台化。

Gergely：能不能说说你加入时工程团队有多大，后来是怎么增长的？我觉得外面的人很难体会那次增长有多大。

Uday：我加入时大约是第 600 名工程师。事实上，当时整个交易市场团队也就五六十名工程师。之后几年，随着业务和流量的扩张，我们增长到了几千名工程师；在 2019、2020 年前后，我们还开始扩展到不同的研发中心。现在我们在全球有 12 个技术中心，几乎遍布我们运营所在的每个大洲。这帮助我们为那些超本地化的市场打造产品，其中一些产品之后会推广到所有适合这类功能的市场。所以这让我们既能在全球范围内吸纳人才，又能打造细致入微的本地化产品，同时仍然保持一套全球技术栈。

Gergely：说到打造产品和技术栈，你以前在、现在也还在平台团队，对吧？

Uday：对。至少头十年我都在不同的业务平台团队。最近这一年，我更多时间花在开发者平台上：面向工程师的智能体 AI、面向公司其他部门的智能体 AI。这个过程中，我也参与了一些面向用户的 AI 项目。

Gergely：能不能带我们回到 2015 年，讲讲 Uber 的内部工具是怎么变化的？因为我当时在那儿，我真的很惊讶我们有那么多自研工具。我们聊了 RT API，但还有 Edge Gateway 等等。你能不能讲讲，在 2015、2016 年，一个工程师加入 Uber，会用到哪些工具，这些工具又是怎么演变的？我说的是大多数工程师，无论后端还是移动端，在 Uber 都会接触的那些主要工具。

Uday：当然。那时候按我们的扩张方式，几乎没有现成产品可用。我们聊过 RT API 和 Edge Gateway。我们还得自己做的东西里，有一个叫 uOwn 的系统，让公司里任何人都能查到某个资产归谁负责，比如服务。

Gergely：对，值班的时候就能查：出了故障，你能找出是哪个团队负责、谁在值班这类信息，对吧？

Uday：没错。随着工程组织的壮大，我们也开始为工程设计文档和产品设计文档建立端到端的工具，把它们都集中到一个地方。我们还把所有事故管理集中到一个地方。我们对如何处理事故、从中吸取教训非常执着，所以围绕这个做了很多很好的工具。其中比较复杂的是指标系统。早在 2015、2016 年，我们每秒大概就要产生约 5 亿条指标，而且基数很高，没有任何现成的指标系统能用。这就催生了 M3DB，它后来开源了，还有一家公司 Chronosphere 围绕它成立。这让我们能处理我们那样的指标量。我们还得自建端到端的机器学习平台，因为我们有几百个机器学习模型，要覆盖整个生命周期：构建特征、训练模型、监控、上线服务。

Gergely：这就是 Michelangelo，对吧？

Uday：Michelangelo。就在几个月前，我们把 Michelangelo 基础设施里深度学习的部分开源了。所以那里有很多扎实的基础构建模块。另一个有意思的是 Cadence。想想有些工作流要跨越好几天，不管是司机入驻，还是某个 CRM 营销活动。你会看到很多工程师各自做自己的容错、自己的状态管理，于是就有了 Cadence，一个持久化工作流引擎，后来也开源了。

Gergely：我觉得知道 Cadence 的人不多，但很多人知道 Temporal，对吧？据我了解，它要么是受 Cadence 启发，要么很多想法来自 Cadence。我甚至不确定它是不是 Cadence 的开源版，但它大致相当于 Cadence 在 Uber 所扮演角色的外部版本。

Uday：对，那些人看到了对这类东西的真实需求，并且能够把它推广到 Uber 之外，规模做得更大。但我想说的模式是：那时为了我们的规模，有一大堆东西必须自己发明。这些年随着行业也成熟了，现在凡是我们认为没有独特需求的，我们就买；如果我们做的东西对业界其他人也有意思，我们就尽可能开源。

Gergely：我觉得还有两个工具值得一提，因为我正好记得。一个是 Morpheus。它基本上就是 Uber 版的 LaunchDarkly，但集成得深入得多，到处都是。你可以进去跑实验，立刻看到结果。它是功能开关加实验平台，还和移动端功能开关集成，我记得在 Uber 内部它被集成进了一大堆工具，几乎所有工具，对吧？

Uday：对。因为我们扩展到了那么多国家，你需要一个非常好的配置平台，无论是配置后端服务、做功能开关系统，还是做实验。Uber 是一家非常数据驱动的公司：一切都要经过功能开关，一切都要经过实验。而且因为我们是双边、三边市场，有些实验非常复杂。不只是简单的 A/B 测试，我们还有 switchback（轮换实验），我们得构建非常深入的实验能力，并把它嵌入所有工具里，能自动生成分析：p 值是多少、用哪些指标。这也促使我们在指标基础和数据基础上做了大量工作，确保我们从这些指标得出的分析是可信的，能据此做业务决策。

Gergely：对。我记得我一直纳闷为什么我们要有自己的功能开关系统，后来我想：给我找一个支持“城市”的厂商功能开关方案看看。事实上，城市是一等公民，因为在 Uber 内部城市太重要了，很多工具都把城市当作一个维度，比如在基数方面，每个城市都有自己的指标。然后你会意识到，很少有东西会这样对待城市。Uber 有一大堆有意思的约束，是这个规模下别人都没有的。

Uday：对，完全是。城市这个很有意思，它深深嵌入了我们的基础设施。比如，对一些关键平台服务，我们还按城市做分片，这样也能在不同等级的城市之间做观测。即便现在，在我们承载流量的所有区域里，我们把一个城市分配到某个特定区域，并且随时可以把这个城市跨区域故障转移。我们还有逻辑部署组，一组城市被路由到一组容器。我们不是对所有服务都这样做，只对那些需要这种分片程度和可靠性级别的服务这样做。

Gergely：我还想问一个系统，我记得用过，我想是 2017 年在开发的，那就是 DevPods。在当时它感觉真的领先业界。它是怎么来的，后来变成了什么？

Uday：好，DevPod 的背景是这样的：我们聊过微服务的增长。起初我们是微仓库，每个服务一个独立代码仓库，当时也没有标准的构建系统。每个服务都有自己的 Makefile，我们至少有两三套构建系统、两三套测试系统。即便是中心团队，想跨所有服务做库升级也非常困难。所以在 2017、2018 年前后，我们改变策略，转向单一仓库（monorepo）：尽管还是微服务，但所有服务都从 monorepo 部署。我们每种语言一个 monorepo：Go 一个，Java 一个，iOS 一个，Android 一个，等等。然后当这些仓库变得足够大，跑构建就非常困难，而在本地笔记本上把这些系统都搭起来，又要经历各种环境配置问题。所以我们做了 DevPod，也就是云端开发机，你想要几台都可以。每个 monorepo 对应一种 DevPod 规格，所以如果我主要在 Java monorepo 里工作，我就创建 Java 规格的 DevPod。它有全部构建缓存，构建更快，跑在比笔记本还强的云端机器上，所以我们能对构建时间和测试时间给出很好的 SLA，也不用担心环境配置问题，因为我们能确保装好了合适的工具。有意思的是，进入 AI 时代后，就连智能体也需要类似的工作空间和云端机器，我们正好能借上这个。我们还做了一个包含所有仓库的“超级 DevPod”，因为这样我就能让智能体跨仓库创建 PR。它有在任何仓库工作、查看任何仓库上下文所需的全部工具。这也帮助我们在顶层目录创建了 AGENTS.md 和 CLAUDE.md：因为我们构建和测试都是标准化的，一旦写好顶层文件，大多数团队开箱就能得到很大价值，不必深入去做每个模块的配置。而且 DevPod 上默认装好了所有 AI 工具。你拿到一台新 DevPod，连 Claude Code、Codex、OpenCode 都不用装，全都在。这让公司里即使是非工程师也能很轻松地创建 DevPod，开箱即可上手玩 Claude Code 和 Codex。

Gergely：嗯，所以我猜很早就有云端开发环境帮了大忙。

Uday：对，这些年的平台化也在我们推进智能体之旅时帮了大忙，因为我们为让工程师省事而建的一切，同样让智能体省事。

Gergely：在聊今天在用的东西之前，我想先谈谈这些，因为我觉得很多东西是相互关联的。当时为平台、为工具建了那么多东西，很多是 Uber 定制的。不过这部分聊得差不多了：今天是什么样子？今天的开发是什么样子，你们用什么工具？也许你可以先给我们入个门，讲讲你们专门为 AI 打下的基础：建了什么，为什么建。

Uday：首先，尤其是在 AI 世界里，我们很早就意识到一件事：因为整个格局变化很快，harness 变化很快，模型也变化很快，所以我们想投资于一套与 harness 和模型都无关的基础构建模块，这样不管这些东西怎么变，我们都能轻松在不同模型、不同 harness 之间迁移。我们投资了几样东西。从 ChatGPT 刚推出、也就是 2023 年底 2024 年初，我们就开始做模型网关。所以那时我们就有了模型网关，它对外提供兼容 OpenAI 的 API，或者兼容 Anthropic 的……

Gergely：抱歉，这是 2023、2024 年，对吧？

Uday：对，2023 到 2024 年初，GPT 模型刚推出的时候。我们很快注意到，我们想让公司里任何想利用这些模型、用它们构建智能体的团队都能轻松上手。所以我们有一个模型网关，把所有复杂性都藏在后面：所有安全和策略防护都到位，所有可观测性都到位，这样你可以在不同模型或不同厂商之间切换，你只要有组织或项目的 ID，就能使用网关开放的任何模型。

Gergely：所以你把它放进一个模型选择器，接到模型网关，再路由到合适的模型，可能是当时的 ChatGPT，或者 Opus，这类模型。

Uday：对。而且它是建在 Michelangelo 之上的。我们做了 Michelangelo GenAI。

Gergely：哦，Michelangelo，那是机器学习平台，对吧？

Uday：对。现在 Michelangelo 平台上有一套生成式 AI 基础组件。你在 Michelangelo 上创建一个生成式 AI 项目或智能体 AI 项目，配置好项目，选择你想要的模型，然后你会得到一个唯一的项目 ID，供你的智能体使用。所以我们能用同一套 Michelangelo 基础设施，在同样的基础上开始构建 AI 专属功能。回头看，那是一项很早的投资，后来回报很大。

Gergely：Model Gateway 是什么？

Uday：我可以快速演示一下我们建了什么。那是 2023 年底，第一批大语言模型发布时，我们很快发现有一大堆内部团队想把它们用于不同场景，我们想让他们用起来非常方便。它建在 Michelangelo 平台之上，作为其中的又一个组件。

Gergely：顺便回顾一下，Michelangelo 是从 2015、2016 年开始建的机器学习平台，所以它比大语言模型早得多。

Uday：没错。现在 Michelangelo 里也有一套生成式 AI 或智能体 AI 组件，我们现在还在建更多。这些还没进开源版本，但我们正在为智能体 AI 世界积极构建很多东西。不过 Model Gateway 是第一个。最初版本没有这些中间件组件，有些是过去一两年才建的。但对公司里任何团队来说，体验就是：创建一个客户端，填上在 Michelangelo 里初始化好的项目 ID，再加上调用令牌，就这么多。我们对外提供一个兼容 OpenAI 的 API 或兼容 Anthropic 的 API，所有厂商的所有模型，无论开放权重还是闭源，都在这个网关后面。我们在那里加的第一样东西，叫 AI Guard。

Gergely：AI Guard 是什么？

Uday：本质上，我们想确保不会把任何敏感内容发给模型或返回给用户。所以这是一个入口，我们可以在这里加中间件，统一在所有项目上强制执行，安全团队也能在 AI Guard 专用的模型上不断迭代：内容方面的、安全策略方面的、一大堆合规与沟通政策方面的。他们在那里做了大约五个不同的微调模型，每个请求和每个响应都要过一遍，并有严格的延迟限制。这大大帮助我们确保所有项目都有同样的标准基线。而且因为每个项目都在这里被追踪，我们可以按用户、按调用方做归属。今年晚些时候，我们加了项目的消费档位和用户的消费档位。因为所有请求都经过一个地方，我们还能加审计日志、会话追踪以及围绕这些的一大堆基础设施。Uber 的每一个模型请求都经过这里，没有一个模型请求不经过。所以这给了我们覆盖所有模型的单一入口。

Gergely：我猜你也能追踪计费，成本之类的所有东西。

Uday：没错：追踪计费、缓存命中率等各种东西。现在业界在大量讨论模型路由之类的话题，这里会是一个很好的切入点，因为我们所有模型都经过这里。沿着让工程师方便地切换模型这条路，下一件事就是：怎么让工程师方便地切换 harness？如果我在用 Claude Code，然后换成 Codex，我得把所有设置、所有技能、所有工具、所有插件都带过去。所以我们在内部用一个叫 AIFX（AI foundations，AI 基础）的封装层把所有 harness 包起来。它预装在 DevPod 上，你也可以装在本地机器上。我们有“角色”（persona）的概念，一个角色自带一大堆默认插件和技能，所以任何工程师都能开箱获得一大堆默认技能，什么都不用装。因为一切都被包装起来，所有设置都是托管的。无论你在本地还是在任何一台 DevPod 上使用哪个 harness，设置都是同步的。所以我们可以在中心统一管理一套设置，推送给所有用户，而每个用户的个人设置也会在他所有环境之间同步。同样，这让事情变得非常简单，因为现在切换 harness、切换工具都只有一个入口。我们还加了一个状态栏，可以给出提示，并追踪你跨 harness、在当前 harness、在当前会话里的花费。所以所有这些额外的东西我们都能加上，工程师不需要做任何显式配置。

Gergely：不错。说到追踪花费，你们现在怎么处理这件事？作为 Uber 的工程师，如果我刚以高级工程师身份入职，我需要关注花费、成本吗？背后的思路是什么？

Uday：是这样，我们希望工程师能用上任何可用的工具，我们有“消费档位”这个概念。默认你会得到某个档位，档位有很多级。快用满当前档位时，你可以申请升到下一档，只需要经理简单批准一下。这时你可以和经理讨论这个项目的投入产出比、你是怎么花的。这是一场关于负责任使用的对话。我们不想限制工程师：如果是用在对的项目、对的用途上，他们需要花多少就应该能花多少，因为归根结底我们想最大化收益。但你也要确保使用是负责任的，所以我们尽量把跨档位所需的手续减到最少。而且他们在我们任何工具里都能看到自己在当前 harness 内以及所有 harness 上花了多少。我们对不同的托管智能体也有不同档位：所有交互式 harness 共用一个消费档位，一些后台编程智能体则有单独、独立的档位。这样确保他们能轻松地统筹管理。

Gergely：嗯，有道理。就算我做业余项目，我也会留意自己的花费和自己的额度。我的理解对吗：思路就是别把 token 花在毫无意义的蠢事上，或者你可能在无意中烧钱却不知道，所以就给出反馈，让人知道这些东西不是免费的？

Uday：正是。就是要有这种反馈。我们还有一个叫 Cost Check 的插件，会扫描你所有会话，根据你的使用情况给出个性化提示，比如：你在这个项目、这个会话上花了这么多，这些是你可以用来进一步优化成本的技巧。这一切在经理和工程师之间营造了良性对话，工程师自己也能得到关于花费效率的良好反馈。这在上下文健康度、模型选型等方面的实时指导上帮了我们很多，让工程师也意识到在这个新时代该怎么工作。我们也不希望有低效的花费。

Gergely：你们还建了哪些基础设施？你展示过 MCP 网关。

Uday：哦对。背景大概是 2025 年初。随着 Cursor 流行起来，我们启用了 Cursor，而 MCP 也是那时候提出的规范。我们很快意识到，通过以简单的方式开放所有内部工具，可以大大增强 AI 的能力。这样我们就有可能把它用到编码之外，用于各种软件工程任务。所以大约在 2025 年 4 月，我们开始做 MCP Gateway。和模型网关类似，这是所有工具的统一网关。我们的做法是：因为我们所有服务早已有一个很好的 IDL 注册中心，无论它们用 Thrift 还是 Proto，既然有 IDL 规范，我们就能为任何服务自动生成 MCP 规范。

Gergely：解释一下：Uber 的服务要么用 Thrift、要么用 Protocol Buffers 作为强类型契约，对吧？

Uday：对。起初我们只有 Thrift，后来也加了 Proto 支持。最近几年的新服务全是 Proto；几年前建的那些是 Thrift，它们在重写时团队通常会换成 Proto。但无论 Thrift 还是 Proto，因为所有 IDL 都在同一个注册中心里，我们就能用这个注册中心为它们生成默认的 MCP 规范。公司里任何人都可以去 MCP Gateway 这个工具，看到我们自动生成的所有 MCP 服务器。点进任何一个，你都能看到从现有 API 生成的全部工具；这些是那些服务的 API，被投射成 MCP 工具。我们自动生成请求规范、响应规范和描述。后来，我们还基于 API 描述，为 API 和字段生成针对大语言模型优化的描述。我们见过有些工具描述长达三四千 token，所以可以针对模型的使用来优化。而且只需改一处配置和安全策略，团队就能启用，不需要改任何代码。如果他们想要定制的 MCP，随时都可以：我们有一个用于创建定制 MCP 的框架，他们的定制 MCP 也通过 MCP Gateway 代理。我们做的另一件有意思的事是，连所有厂商工具，不管是 Google 还是 Slack，也全都通过 MCP Gateway 开放。这大大减轻了配置管理的负担。我们已经讲过 AIFX，所以我能以同样的方式安装任何工具，无论是内部还是外部的 MCP 工具。最近几个月，我们还把所有这些 MCP 投射成了 CLI，所以任何 MCP 都可以当作 CLI 来执行。如果某个智能体 harness 想当 CLI 用，就当 CLI 用；想用传统 MCP，就用 MCP。

Gergely：我的理解是不是这样：这一切之所以可能，是因为 API 一开始就已经是生成的或者以结构化方式写成的，很多是生成的，Uber 有一个 API 平台，所以加上 MCP 在某种程度上，我是说，很简单。当然还是要花功夫，但你懂我的意思。现在生成 CLI 也相对简单，因为你们在 AI 之前就有了基础，对吧？这就是我开始在 Uber 身上看到的：你们在 2022 年之前建了一大堆东西，然后可以很轻松地在上面加上 AI 基础设施。

Uday：而且做 API 网关的同一个团队也做了 MCP Gateway。他们本来就是做 API 网关的，懂得怎么做各种协议转换，所以我们能很快建好。尤其是把 Google Workspace 和所有 Slack 工具也接进来之后，就催生了各种了不起的智能体工作流。那时候人们可以自动化任何事情：从 Slack 到 Google、Jira、Linear，任何厂商工具或任何内部服务，都只是一个 CLI 调用的距离。我们开始思考这个领域时的另一组基础……所有这些都属于与厂商无关、与 harness 无关的构建模块，不管发生什么你都得建，因为智能体需要某种方式来访问你的工具。另一件事是技能（skills）。我们今年早些时候就跟进了。既然我们已经有 monorepo 的理念，我们在某种意义上建了一个技能 monorepo，里面有中心平台团队构建的所有核心技能，以及各团队可以自己构建的团队专属技能。

Gergely：这些技能就是那种技能文件夹，就像 Claude Code 等用的插件？

Uday：正是。是能在所有 harness 上通用的插件和技能。然后我们有一套统一的质量关卡，在所有技能上运行，并且让它们能在所有 harness 之间移植。你用我提到的同一套 AIFX 工具来安装：如果你对某个技能执行 plugin add，它会更新所有 harness 的配置，不管你当时有没有在用那个 harness，所以即使切换 harness，这些插件也已自动装好，你不用操心重新安装和重新配置。而且因为所有技能都使用 MCP Gateway 上的工具，所有技能访问任何工具都有一套标准机制。现在我们正在做一些工具，工程师选择自己的技能，它就会给出各种改进建议。下一步正在进行的是：怎么从 harness 收集追踪数据，为技能生成改进补丁，让我们能根据经验持续改进技能？业界有很多关于技能质量和技能演进、以及怎么持续改进的讨论。刚建好的技能可能并不完美，你需要某种机制来持续改进它。MCP 和技能都给我们带来了很多好处。最近几周，每天大约有 3 万次技能执行。

Gergely：这对我来说很有意思，因为如果你跟人说“我们在建一个技能仓库”，大多数人，在创业公司里，我不是说 Uber，会觉得：不就建个 git 仓库，放一堆技能文件夹，就这样嘛。但很明显它更复杂。它更复杂是因为你要支持的工程师太多？还是因为你们在不断修改这些技能所以要跑评测，或者要追踪它们有没有被使用之类的？

Uday：对，完全是。用现在任何一个最新模型，做出一个技能的 v0 版本都很容易；但要让它在各种场景下都真正好用就很难了。这就是为什么你需要一个地方来统一更新所有技能。事实上，当我们为所有 MCP 开放了 CLI 投射之后，只用了几个工程师借助 AI，就把这个仓库里所有技能都改成了 CLI 模式，因为它更省 token。因为如果每个技能都说“我要 MCP ABC 和 MCP DEF”，那我装了这两个插件，就会有六个 MCP 一直占着我的上下文，上下文负担太重了。我们把所有技能都换成了 CLI 模式，这对我们的 token 效率也有很大影响。另外，因为我们给每个人自动安装这个技能市场，又省掉了一步配置。所以可发现性好，安装、配置和管理都简单，我们也能围绕它建一大堆评测流水线和可发现性流水线。仍有一些团队有自己的仓库，但大多数技能都走这里。

Uday：我最喜欢的是上下文图谱。

Gergely：上下文图谱是什么？

Uday：背景是，去年 12 月，一位工程师做了一个 AI 助手，我们叫它 Cortana。你可以在网页或 Slack 上找它，问任何代码库的任何问题；它会在我们所有仓库里做智能体式搜索并回答问题。然后我们看到人们问各种各样的问题：可能是调研，这条查询怎么跑，这个数据的来源是什么，这个归谁负责，能不能帮我做个根因分析，一大堆软件工程任务。我们看这些追踪记录时，很明显能优化模型获得“落地”（grounding）所需的轮次，因为我们系统太多了。历史上这些都是孤立的系统：工程师得去任务管理平台，去值班看板，去我们聊过的归属看板。于是我们想：怎么把这一切接进一张给智能体用的“心智地图”？最近几个月我们做了一个很酷的可视化，叫 Uber 上下文图谱。我们有 100 多种节点类型、130 多种边类型，这是截至大概三天前的实时数据。点任何一个人的节点，你就能看到他管理哪些资产、写了哪些设计文档、在做哪些功能、处理过哪些值班事件、做了哪些配置变更、处理过哪些事故、有哪些 Jira 事件。任何节点都和其他所有节点有关系。这让我们能做到：我提到的那个助手现在把上下文图谱作为默认的落地依据。你问任何问题，它先用图谱导航：这个人在问什么？一旦落地了，哦，这是关于这个领域、这一组服务的，它就能深入下去，读其他文档和其他资料。所以它减少了智能体的执行轨迹和给出好答案所需的轮次。我们已经看到，在一大堆类别的问题上，质量上升，成本下降，延迟下降。我们在发挥它的全部潜力上还处于早期，对今后在它上面能构建的一切都非常兴奋。

Gergely：那节点是人还是工具？

Uday：这是模式（schema）的可视化。公司里每个人都有一个节点：有我的节点，每个员工都有节点，它和所有实例都有关系。我生成的每个 PR 都有一个节点，还有一条连线表示是我创建了这个 PR、我管理这个资产、我做这个产品功能、我参与了这份设计文档。所以节点既是人，也是资产。

Uday：对，正是。举个简单例子：假设你问“全世界有多少出行订单是用现金支付的？”你首先要弄清楚有哪些表、有哪些列，有没有别人写过这类查询，他们是数据科学团队的还是出行数据科学团队的。现在所有这些数据都是互相关联的：你可以查看最近 30 天有没有人做过相关查询、有哪些表，再去探查那些列。因为一切都互相关联，你能很快找到我们“官方认可”的查询，即使是复杂问题也能很快回答。否则你就得翻很多很多文档，调用很多很多次工具。这样就非常高效。让我们自己手写这些 Cypher 查询要难得多，但智能体非常擅长在图上导航，就像它们非常擅长用 bash 在文件系统里导航一样。

Gergely：这在我看来非常超前，但真的很酷。我猜要存的数据量巨大，毕竟 Uber 轻轻松松就有一万多名员工。

Uday：对。好在，就像我们的 API Edge Gateway 团队参与了 MCP Gateway 一样，管理我们拥有数十亿节点的生产图谱的图平台团队，也帮忙搭建了这个图谱。和生产图谱相比，这个小多了，所以对他们来说不算规模上的挑战。我刚才只简单提了 AI 助手 Cortana，它接入了所有上下文图谱的工具和技能，在 Slack、网页和 CLI 上无处不在。所以公司里任何人，哪怕是某个国家的运营人员，都可以问任何问题：这个是怎么做的，它在哪里，谁在做，背后的历史是什么？它能调用所有这些数据和我们所有的 Google 文档，给出非常好的回答。它打破了各个组织之间的信息孤岛：大家可以自助，问任何问题，执行任何人做好的任何技能。

Gergely：我猜它至少对合适的人来说必须能访问数据源，这样它才能去看日志、监控之类的东西？

Uday：对，它能看日志和监控。你可以问“这个服务的健康状况如何？”它会去查看它所有的依赖、用了哪些存储系统，跑完所有查询，给你一份关于这个资产的 360 度健康报告。而且我们沿用了所有现有的用户权限，所以我只能访问我本来就有权限访问的东西，否则数据是不可访问的。

Gergely：对，因为在 Uber 内部，我记得以前叫“破窗”（break glass）：当你需要一个没有权限的系统的访问权时，要走审批流程，经理或总监之类的审批。在我那时 Uber 就已经非常重视这一点了。

Uday：对，完全是。这些就是部分基础设施。我们还有更多在做，在考虑更多智能体化的用例。但这些构建模块在我们的智能体之旅中帮了大忙，让我们从纯粹用于编码，扩展到了各种工程任务。

Gergely：我们回到 Uber，看看今天从开发者使用的工具角度，构建一个功能是什么样子。PRD 和 ERD：不了解的人可能不知道，PRD 是产品需求文档，ERD 是工程需求文档，对吧？对不熟悉 Uber 内部运作的人来说，就是产品方案和工程方案。

Uday：对。我们聊了一些 AI 基础设施；现在如果你考虑一个功能的生命周期，我们怎么在生命周期的每个环节应用合适的 AI 基础设施，同时为 AI 时代重新设计这些工具？有些方面我们已经走得比较远，有些还在早期讨论阶段。哪怕是让智能体和工程师一起迭代打磨的“联合方案”这个概念，也有很多很酷的想法。我们还有各种用来处理设计文档的智能体技能。正如我之前说的，不管是产品设计文档、工程设计文档、上线评审、架构评审、生产就绪评审，全都在一个地方。我这里筛选了一些很老的项目方便大家看，但你能确切知道谁在做、跟踪它们的状态。所有这些数据也会进入图谱，所以我们知道完整的历史：权威信息源是什么，设计文档，审批状态，谁在做。每一个还附有 Jira 链接或 Linear 链接，所以我们能从这个项目追溯它是如何转化为执行的。这为人和智能体都提供了一个权威信息系统，可以了解每个项目的规格说明。

Gergely：我想规划仍然非常重要，尤其是对那种不是一句提示词、一次就能做完的简单项目来说。

Uday：对，正是。考虑到我们的产品多样性和国家多样性，我们需要真正考虑各种边界情况，而不只是正常路径，以及它们应该如何表现。而且因为我们在物理世界运营，边界情况就更多了。我们得认真想：这里出问题会怎样，那里出问题会怎样，这种情况的客服工单怎么处理？

Gergely：这个不用多说，但我还是补充一下，因为可能没那么显而易见：Uber 在那么多国家和城市运营，即便两个城市之间，现实情况也可能不同，期望可能不同，人们的习惯也不同，等等。

Uday：对，完全是。所以提前想好正确的方案就变得非常重要，这也让工程师或智能体更容易拿着方案去拆解、执行。有了方案之后，下一步就是怎么拆解并执行。现在就说到我们内部叫 Minion 的东西了。这是我们的后台编程智能体。目前大约 15% 的生产 PR 都是通过 Minion 完成的。有些 PR 工程师想交互式地做，但我们也想让另一种情况变得非常简单：对于规格说明写得很好、或者我只想少量引导的任务，我可以交给一个 minion。我们经历了好几次迭代，最新版叫 Minion v2。你可以在网页上用，也可以在 Slack 里用；可以用计划模式，然后让它在后台执行；如果是简单的提示，也可以只给一次提示，让它在后台执行。它用的是超级 DevPod，所以能访问我们所有的仓库和代码库。它可以跨仓库工作，根据你的方案和规格生成一个或多个 PR。刚开始时，交给 Minion 的大多是维护类任务。随着我们往前推进，往 Minion 环境里加入越来越多工具，让 Minion 能在网页、移动端或后端 API 上自我验证工作，我们的目标是随着时间推移，增加人们能用 Minion 完成的任务种类和任务占比。

Gergely：看一下怎么调用：在 Slack 里直接提及它就行？@minion，还是怎么说？

Uday：你可以 @minion，它会显示状态。你不必去网页，直接在 Slack 里就能引导它。也许你和工程经理或产品经理有一个 Slack 讨论串，在里面迭代设计。如果事情简单，你们在那里迭代、达成一致，然后说：“嘿 @minion，按这个讨论串来，能不能创建一个 PR？”它会拿这个 Slack 讨论串的上下文为你创建 PR。即便在我们的支持频道里也非常有用。我看到有人报了个 bug，值班的人问 Minion：“嘿，能看看是什么问题吗？”Minion 回复：根因是这个。哦，看起来挺简单的，那就当场修了吧。不用再走“加进待办、下个迭代再做”那一套循环，当场就修好了。随着 Minion 越来越强，我们看到这样的情况越来越多。

Uday：所以我们过了一遍构建这一步。之前我们也聊过 DevPod。

Gergely：从那以后改进了不少吧？

Uday：对。这里显示的是我所有的 DevPod，因为我在做上下文图谱。如果你想新建一台 DevPod，会看到要选哪种规格。给 Minion 用的有一种包含所有仓库、专门为 Minion 优化的 DevPod 规格。但对于交互式使用，它会创建一台 DevPod，几秒钟之内就能跑起来。

Gergely：几秒钟，很厉害。我相信你们做了些巧妙的事，比如让机器保持预热或者预构建好，直接复制。

Uday：对。因为这是开发者用的环境，我们为此用了单独的多个云，一个 Kubernetes 集群，一切都是预热好的。你申请的时候，我们直接从预构建镜像克隆，里面已经有构建缓存，所有仓库也都已克隆好，随时可以开始构建，因为我们所有仓库都用 Bazel 作为构建系统。所以我刚才进入一个仓库，对它跑了 Bazel，整个过程在几秒量级。任何工程师，如果我想在这里改代码，几秒钟就有一台 DevPod，构建任何模块都只有一种方式，人人都知道那条命令。现在智能体也知道同样的方式：在 CLAUDE.md 和 AGENTS.md 里，它们知道怎么构建和测试任何仓库里的任何模块，用的是完全相同的命令。

Uday：这就差不多讲完了写代码这一步要做的事：你可以用交互式 harness，也可以通过 Minion。下一件事是：有了 PR 之后怎么办？也许先走自愈 CI。我们意识到一件事：因为我们的 PR 数量逐年上升……

Gergely：肯定是爆炸式增长了。

Uday：对。我们的 P50 和 P90 周期时间，既包括内循环，也就是你有了改动、想让它变绿并创建远程 PR；也包括 PR 创建之后，拿到人工评审、让所有 CI 检查都通过。评审已经成了一个大瓶颈，和其他所有公司一样，我们逐年都能看到。我们非常专注于拆解其中的每个环节，深入下去为 AI 时代做优化。我们做的第一件事是，把一大堆以前在创建 PR 后才跑的简单 CI 任务挪到内循环里，并把它们全放在一条命令后面：aifx validate。这样智能体创建 PR 时，就能跑 lint、覆盖率规则、构建规则、模板规则等所有这些，让 PR 处于良好状态的概率提高。然后我们接入了可视化验证的能力：我可以起一个模拟器测试，可以起网页测试，可以起一个预发环境，把这个改动部署上去，跑被测 API。现在 Minion，甚至我的交互式 harness，这些智能体都有相应技能，能走完这个验证循环。假设你创建了 PR，还是有东西失败了，那我们有自愈 CI，你可以对所有 PR 启用，也可以按单个 PR 启用。这是我们给所有 GitHub PR 加的一行 Uber 专属内容：你可以链接到正在处理的工单，能看到哪些检查失败，还能设置一大堆自动化：自动请求评审、自动合并、自动修复。本质上就是我们能做的一切，用来缩短 P50 和 P90 周期时间。做完这些之后，我们还有一个叫 Code Inbox 的东西。这里展示的是一个模拟版本。任何工程师都可以进去，看到所有在等他评审的 PR，以及他自己创建、在等别人评审的所有 PR。如果有工程师把这个发来让我评审，我进这个页面，就能看到到目前为止做过的所有事。它让我非常容易看到：AI 代码评审通过了，它检查了这些东西，这是冒烟测试的截图。所以我可以快速看一眼，还有视频，我能看到构建检查之类的所有东西。我们还在加 PR 的风险评分和影响范围等等。所有这些都会给工程师很好的信号，帮他们判断是否可以合入，以及该重点看 PR 的哪些部分。我们正在全力推进这方面，有一大堆想法，但我们想确保自己准备好迎接 PR 的涌入。事实上，我们不得不为 CI 系统宣布了内部的“红色警报”（code red），因为 CI 任务数量逐年翻倍甚至不止翻倍。所以我们得在这个领域加固一大堆基础设施，好为新 PR 的涌入做好准备。

Gergely：我猜你们也看到了，工程师不可能再像过去那样严格地评审所有 PR，所以你们在做工具，提示哪些需要多加注意、哪些可能低风险，从影响、从影响范围等多个角度。你怎么看代码评审未来会变成什么样？你认为会一直有人工代码评审，还是某些情况下它会消失？

Uday：对。对我们来说，我们总是想偏向安全的一边，因为对 Uber 来说一次事故的代价真的很高。所以即便有了所有这些工具，现在我们仍要求每个合入的 PR 都必须有一位工程师评审。随着我们对风险评分越来越有信心，而且我们可以用多年的数据做回测，这些数据我们都有，再加上对 AI 代码评审越来越有信心，那么对于某一类低风险 PR，我们也许可以启用我们所说的“绿色通道”，也就是自动合入。但在走到那一步之前，我们要对所有关心的维度都非常非常确定。现在的首要任务是让工程师非常方便地拿到更快评审所需的全部信号。如果这方面做得好，我相信随着时间推移，自动合入的 PR 比例可以提高。但最优先的是先把所有信号放到对的地方。

Gergely：不错。Code Inbox 很好，我喜欢。还有一件事我们该聊聊，就是怎么做冒烟测试。冒烟测试（sanity testing），给不了解内部黑话的人解释一下，就是手动测试，对吧？

Uday：对，手动测试。假设我在做一个新功能，涉及两三个服务。我怎么知道这个功能端到端是否正常？在智能体出现之前，工程师的典型流程是用我们叫 Slate 的东西。本质上你可以创建自己的实例，部署你正在开发的分支，然后把你的测试账号 UUID 路由到你创建的实例。登录时，你执行的就恰好是那个分支，其余上下游都走其他预发环境。这样你就能做端到端测试，不用担心基础设施的其他部分。这在整张服务图里都会传递下去：你在移动 App 上指定要用的测试账号，请求经过其他服务，碰到被测服务时就会转到你的 Slate 实例。如果你测试两三个服务，请求会转到这两三个被测服务上。所以我们甚至能用它做多服务测试。有了这个之后，我们只需要教会智能体如何部署 Slate，再把所有测试 API 给它们。

Gergely：基本上，这原本是我作为工程师想做冒烟测试、也就是手动测试改动时用的东西。我有一种很酷的方式来做，而现在你们直接把它交给智能体，它们就能以安全的方式端到端地测试自己的改动。

Uday：对。这里展示的是它的网页版。你可以看到这就是我们讲过的 CLI 模式：它在用 Slate MCP，“创建新的 Slate 环境”，并给出环境名称。环境建好后，它说“把服务部署到这个环境”，并给出服务名，这是一个测试服务。现在它有了自己的环境。这是 Slate 的界面，你看这里，可以把测试账号 UUID 绑定到这个实例，还能看到这个环境里的所有服务，能看到 Git SHA。现在智能体在内部就能使用所有这些技能和工具。看看它做了什么：它对那个网页功能做了 A/B 对比测试。它在 Slate 环境里用智能体浏览器分别跑了 main 分支和我的分支，然后生成了一份报告让我审阅全部改动。之后我们可以打开它生成的报告：它展示了前后对比，告诉我没有回归。工程师很容易验证，我们还可以把一些截图和视频附到 PR 上。iOS、Android、网页都有同样的功能。如果你想测后端 API，也可以测后端 API。

Gergely：我想补充一点，同样，如果你在 Uber 之外可能体会不到。Slate 之所以如此重要，是因为 Uber 直到今天仍有数千个微服务，或者说不那么“微”的服务。想端到端测试时，只在一个服务上运行改动，这本身就很难，对吧？这就是为什么 Slate 当初花了好几年才建成。

Uday：对。你还得考虑绑定账号的路由：“这是我希望你路由到我刚部署在预发环境里那个分支的测试账号”。这一点也不简单。事实上，它的工作原理要追溯到我们大概在 2017、2018 年建的一样东西：Jaeger，一个分布式链路追踪基础设施，现在已经开源。我们所有服务都有 Jaeger span。本质上，调用从哪里发起，那里就有一个父 span，每一跳都有一个子 span，你可以在链路上附加任意 baggage（随行数据），它会沿调用栈传播。所以当你在 Slate 网页界面上做绑定时，我们本质上是在加 baggage，说明哪些是被测服务、要路由的是哪个账号。请求经过我们的服务网格时，网格识别这个 baggage，就可以说：这个请求不要发到这个环境，而是发到这个 Slate 环境。因为我们建好了链路追踪，并且它在整个技术栈中传播，我们才能可靠地把这些测试请求路由到正确的环境，测试就变得非常容易。这花了好几年，要确保所有现有服务都改造支持了它，所有新服务在设计时都考虑到了它。

Gergely：我开始察觉到一个趋势：Uber 在 AI 之前花了多年建东西，建的是对人来说容易测试、容易自动化的基础设施；而现在有了 AI，看起来好像，哦，这些是你们去年才建的。但实际上你们是建在花了多年打下的坚实基础上的，对吧？

Uday：当然。如果我们没有 Slate 这样的系统，智能体要自我验证会非常困难，这件事就没法自动化。正如你说的，这类东西真的很有帮助。

Uday：我再讲一个很有意思的东西，它非常 Uber 特有，而且非常非常难做好。过去我们做过很多个版本，但我想这大概是最好的版本，而且我们真的能把它推广到所有团队。就算只看我们的核心乘客 App，我们也有几百个页面……

Gergely：乘客 App 就是大多数人以为的“Uber App”，对吧？

Uday：Uber App，没错。我们有不同的业务、不同的产品线、不同的城市，一大堆维度。如果我要测试任何新东西，我怎么知道这些维度的每种组合都没有回归？如果你要把所有排列组合都建出来，就得在整个技术栈上维护成千上万个测试，光这一点本身就是个非常难的问题。所以对我们一些最复杂的平台，我们有一个叫 Capri 的东西，即捕获-回放。本质上，你只需一个中间件就能捕获真实的生产流量；因为现在所有服务的语言框架都已标准化，接入非常容易。它不仅捕获那个服务层的入站和出站，还捕获该服务调用的下游 API：那些请求和响应也会被捕获。所以在某种意义上，你捕获了完整的请求和响应，以及所有出站请求和响应。所有这些被捕获的请求都会经过一条流水线，你可以写简单的规则，比如：如果在请求里看到这类字段，这就是那个维度的取值。这样你就能捕获那个平台团队关心的所有维度。一旦有了所有请求和所有维度，你在某种意义上就能生成那个平台当前支持的全部实时维度和实时组合，我们叫它 MatchGuard。我可以在 CI/CD 里部署前运行它：对这次部署包含的所有 PR，针对这个平台支持的全部组合进行验证，并展示前后差异。这样你就能获得很高的信心：我是不是用这个配置把比如“只在巴西的现金订单”搞坏了？这种事工程师或智能体手动测试都非常难。

Gergely：所以第一步是捕获你想捕获的东西，然后有一个系统重新运行它，检查有没有回归。

Uday：对。我现在进入一个启用了这个功能的业务域。你能看到它捕获的所有会话。我可以点进任何会话，看到全部元数据和标签。它显示这个请求被标记为交易市场类型 X、业务线 Y，处于某种终止状态。它捕获了所有请求。你还能看到它用到的所有出站调用；点进去，会显示出站调用的请求和响应。顶部还有 Slate 工作流界面，或者按环境名搜索。所以假设我在修一个 bug，出于某种原因它只影响旧金山的 Uber X 订单。我修好这个 bug，为我的代码改动创建一个 Slate 环境，然后来这里说：只在我的 Slate 环境上回放这个请求，给我看差异。

Gergely：所以你能看到差异，你期待的是修复或者某种变化。

Uday：对，我期待的是修复，因为我知道修复前和修复后的请求。我可以针对某个特定维度做。我们还会生成我提到的 MatchGuard，也就是全部可能的维度组合，所以你在某种意义上可以为那个团队建一套自动化测试套件，同时也能更方便地手动测试你关注的那一种组合。

Gergely：我在的时候还没有这个，但我们有叫 Deputy 和 Cerberus 的东西。我猜那些算是很早期的版本。

Uday：对。Deputy 能把生产环境的任意请求路由到你的测试实例，Cerberus 则能把请求从你本地的测试实例路由回预发服务器。但现在有了 Slate，我们就不一定要用 Deputy 和 Cerberus 了：你可以部署一个 Slate 环境，两者都不需要。

Gergely：我只想强调一下，因为从外面很难看出来：这真的很难建，因为同样，你有几千个服务，它们全都得支持这些东西，从路由，到捕获生产流量，再到回放。我猜这是巨大的工作量。

Uday：对。而且就像我们把 Slate 开放给智能体一样，我们也能把 Capri 的全部功能开放给智能体，这样智能体就能检查：我在修这个问题，让我拿到所有这类会话，看看请求长什么样，能不能在我的 Slate 实例上构造一个这类请求，看看修没修好？如果没修好，我就循环下去直到修好。

Gergely：对。现在智能体即使“看不见”，也能看到差异，能判断比如什么都没变。所以它有了反馈循环。

Uday：正是，正是。这帮助很大。智能体也可以在 Slate 上配合这些做捕获回放。我们刚才只简单提了 Edge Gateway。

Gergely：Edge Gateway，就是 Uber 的内部 API 层，对吧？它以前叫 RT API，实时 API，现在叫 Edge。它是 Go 优先的吗？我记得我们那时候就是用 Go 写的。

Uday：对，是 Go 写的。现在它支持一大堆端点类型：有 REST API、gRPC、webhook、GraphQL。所有 API 都经过同一个入口，我们可以围绕它在监控和告警上建一大堆工具。所有可靠性功能也都在那里；Edge 还有自己的捕获回放，和 Capri 类似，背后用的就是 Capri。如果你想看任何东西的可靠性，我们可以查看那个服务的整张服务图，告诉你哪个节点可能不健康、需要看一看。借助 Jaeger 链路追踪，我们确切知道服务之间的依赖，还自动标注了哪些是必需依赖、哪些是可选依赖，这些元数据都在。所以即便只是查看告警、诊断告警时，所有这些丰富的上下文都能真正帮助工程师更快排查问题，也帮助智能体更快排查。

Uday：实验我们已经聊过了。最后要讲的是我们叫 Shepherd 和 Fox 的东西。我们转向 monorepo 之后……我们转向 monorepo 是因为升级库非常难。

Gergely：对，要跨所有不同的仓库。

Uday：对，正是。你转向了 monorepo，但现在得有人去把那个仓库里所有模块对某个库的用法都升级一遍。怎么自动化？我们一开始用 OpenRewrite 策略。如果是简单改动，只是函数签名变了，你可以把它写成一条 OpenRewrite 策略，Shepherd 知道哪些模块分别归哪些团队，会自动为每个模块创建一个 PR。AI 出现后，我们加了基于 AI 的 Shepherd：如果我想修复所有服务的上下文传播，让链路追踪工作得更好，我可以写一组提示词和技能，然后让智能体在每个模块上运行，更快地修复每个服务里的问题。所以这是我们的大规模变更平台，不管你想要确定性的改动，还是跨模块的智能体改动。这些年我们通过它完成了很多迁移。我们把每一次叫作一个“战役”（campaign）。比如从 JUnit 4 迁移到 JUnit 5，会有一个写着策略的 YAML 文件，你会看到为每个模块创建的一大堆 PR，战役负责人可以跟踪状态、逐个处理。这让管理这些迁移变得非常容易。几个月前，我们在同一个平台上又加了一个功能。我们想持续改进代码库，而不只是做一次性的迁移。

Gergely：代码维护。

Uday：对，代码维护。我们叫它 Fox。本质上我们想打造自我改进的代码库。因为我们已经有一大堆智能体技能，Uber 的任何服务都可以来这里登记加入不同的技能。他们可以说：我要死代码清理，或者性能分析，或者嘈杂日志治理；有一大堆技能可以接入。Fox 做的是：每个周末，基本上是每周日 CI 负载不高的时候，用比如死代码清理技能为这个服务生成一个新 PR：我能不能清理掉一些代码？能不能改进它的性能？能不能修掉嘈杂的日志？所以这是自动化的代码库改进。

Gergely：我喜欢这个，因为我听说有人会设置一个 AI 循环，比如在 Claude Code 或 Codex 里，说“找找改进我代码库的办法”，然后每晚或每周执行一次。但这听起来优化得多，而且我喜欢你们可以“登记”代码库这一点，因为在 Uber 每个代码库都归某个工程师或团队负责，对吧？

Uday：对，正是。因为我们在快速扩展，现在还处于主动加入（opt-in）阶段。等我们改进了一些技能，会把其中一些改成默认加入、可主动退出（opt-out）。但只要你为某个服务加入了某个技能，每周你都会得到一个新 PR。就像一个托管的智能体循环，所以你在持续改进。我们减少的琐碎工作越多，工程师就能把越多时间花在功能开发上。所以我们一直在思考怎么为工程师消除更多琐碎工作，把这些事情自动化。我们不断审视所有维护类 PR：是不是需要新建一个技能，或者改进某个技能，好让这一类 PR 也能接入这个自动化托管循环？

Gergely：这很好，我喜欢。最后我还听说了 Wisdom。Wisdom 是什么？

Uday：哦对。我们用 Wisdom，是因为我们所有员工都在“吃自己的狗粮”，用自家产品。如果你在用乘客 App 或司机 App 时看到 bug，可以直接在 App 里上报。现在我们有各种 AI 功能，会自动把它路由到正确的团队。而且你上报 bug 时，因为来自员工、来自员工内测版 App，我们能采集到围绕它的一大堆日志和遥测数据。这让负责那个功能的团队修起来非常容易。这里这个例子是一个内部功能：如果你想在不同国家测试某个功能，可以在设备上模拟位置。所以如果有人上报了问题，第一件事是：怎么复现？以前复现是个大难题。现在我们知道用户经过了哪些页面，因为日志里都有，所以我们能给工程师复现步骤、预期行为和实际行为，让我们能很快定位到问题。而且从 App 采集的所有遥测数据，所有日志都能在一个地方看到，无论是分析事件、网络请求，还是各种功能开关。这提供了大量上下文。有了这些上下文，我们做了一个叫 Debug Assist 的托管智能体，它查看所有这些信息，查看代码库，尝试定位根因，以及影响、证据和时间线。一旦我认为这是对的根因，就可以交给我们聊过的 Minion：“嘿，根因看起来没问题，你为它建个 PR 吧？”Minion 拿上所有这些上下文创建 PR，并把 PR 关联到 Jira 任务上。Jira 任务里也有根因分析，所以任何在处理这件事的人都知道根因分析。如果有人在评论里更新了根因，或者创建了新的 PR，同样，这些都是数据，我们可以用来弄清楚怎么改进 Debug Assist、怎么改进 Minion：是我们没拿到对的根因分析，还是根因分析没生成对的 PR？两者我们都能持续改进。

Gergely：我理解得对吗：你们能更容易地捕获和复现 bug 了？

Uday：对。而且我们还加了一个能力：因为员工上报的 bug 我们都有完整日志，我可以拿我的测试设备，让它模拟那位员工所经历的情况。只要我给出 bug 的 UUID，我们本质上就会返回当时给上报者的相同网络响应，所以我能在测试设备的 App 上体验到同样的问题。修好之后，我也能看到它确实修好了。这让复现变得非常容易。

Gergely：我喜欢录制这部分，因为它太重要了。就算在网页上做都已经够难了，要做到网站上你得给自己搭定制工具，而你们在移动端做到了。

Uday：对，这对可复现性和找到正确的根因帮助很大。

Gergely：你们建了所有这些系统，尤其是去年，似乎有那么多全新系统在做诸如维护代码质量、让智能体自我验证之类的事。你认为 Uber 内部软件工程师的工作正在发生什么变化？你从这些新工具中学到了什么？看起来你自己也在学习。

Uday：某种意义上，在智能体 AI 的世界里，你总是在不停地寻找下一个瓶颈并消除它，想办法同时借助 AI 和系统工程来缓解这个瓶颈。因为归根结底，我们的目标是在所有产品上最大化能交付的功能数量，这要求我们审视整个生命周期，思考怎么为新世界重新布线，需要建哪些工具。这会是一段持续的旅程。业界有很多关于“能力过剩”（capability overhang）的讨论：我觉得即便现在，就有很多事情我们本可以借助最新模型去做，但我们还没有足够的编排能力，或者围绕模型的 harness 和工具，来在对的地方以对的方式利用这些模型。我觉得在这上面投入越多，我们能解锁的就越多，能交付的功能越多，能释放的生产力也越多。我们在尝试度量其中很多东西，并不断思考需要建的下一组基础设施是什么，让工程师工作起来更容易，也让智能体工作起来更容易。

Gergely：你提到了生产力。你怎么看工程生产力？我在 Uber 的时候，也就是到 2020 年为止，经理们确实会看一些指标。那不是主要的，但我们确实会看比如每个工程师的 diff 数，只是为了看出如果有人两周都没贡献，那你在干嘛？或者如果有人做了大量代码评审，我们其实是想注意到的。但听起来，很多这类东西，代码产出、代码产物，可能没那么相关了。在你心目中，现在在 Uber 或你的团队里，什么样的工程师才算高产？

Uday：在 AI 之前，我们衡量的是标准的东西，比如代码吞吐量，那些是容易的。每隔几个月我们还会做开发者体验调查，看 NPS，看各个维度上的满意度。我们还看代码质量维度：每天事故数是多少，代码覆盖率是多少，所有这些指标。现在有了 AI，我觉得我们可以利用新的能力，让这个讨论更细致。现在我们内部谈的不只是 diff 速度，而是功能速度：这些新增的吞吐量里有多少在用于解锁新功能？我们甚至怎么改变组织流程，来缩短 P50 的功能交付时间？因为你可以产出 100 个 diff，但如果它们不都是功能相关的 diff，可能就不一定在提升我们给用户提供的价值。比如，我们做的一件事是把所有 PR 分类打标签：复杂度级别，以及它是功能 PR、bug 修复、维护、测试还是文档。我们能看到这个构成比例逐年怎么变化。幸运的是，至少目前，我们功能类 PR 的比例在上升，维护类 PR 的比例在下降。这给了我们一个很好的信号，说明我们方向是对的：代码量在上升，功能类 PR 的比例也在上升。然后我们在这方面投入了很多，因为以前即使有 uPlan 工具，有时也没法从产品设计文档到工程设计文档再到具体任务之间建立正确的可追溯关系，所以很难可靠地衡量所有功能的端到端周期时间。现在我们用 AI 自动把这些东西聚类、补上缺失的标签，这样就能可靠地得出过去两三年里每个半年度、不同复杂度功能的 P50 功能速度。然后我们就能深入看瓶颈在哪：是在 PRD 阶段、上线阶段，还是放量阶段？那里发生了什么，我们需要投资什么，来加快每半年能交付的功能数量？

Gergely：和 AI 之前、这些工具出现之前相比，你对软件工程的心智模型发生了什么变化？还是同一份工作吗？

Uday：确实变了。至少在我整个工程生涯里，我的工作方式从没发生过这么大的变化。比如，我们说 Uber 所有工程师都亲自动手；即便是 Uber 的杰出工程师（Distinguished Engineer）也亲自动手，他们也创建 PR。我以前以为自己算是亲自动手的工程师，但我对“亲自动手”的定义已经彻底变了。就我个人而言，我现在提的 PR 比去年多得多；做这些事情容易多了，我能探索的想法也比过去可能做到的多得多。但工程的工作在某种意义上是：你怎么为智能体构建正确的上下文，让它们产出可靠的结果？你需要变得非常擅长上下文工程。以前我是带着一些上下文去做一些任务；现在我总是在想：如果我想把部分工作交给一个智能体，它需要什么上下文？我怎么搭好带有正确上下文的环境，让它能产出这份工作？除了构建正确的上下文，你还得非常擅长给智能体提供正确的规格和正确的约束。然后，多任务处理变成了一件实实在在的事。以前创建一个 PR 要花很多时间，你会全神贯注于它，但现在你不停地在很多事情之间切换。所以你需要非常擅长在所有会话之间多任务处理：你怎么界定工作范围，怎么跟踪工作，怎么非常快地验证工作？因为如果你没法验证工作、发现智能体留下的代码坏味道，那你就会把回归问题发到生产环境。所以上下文工程、多任务处理能力、评审和验证产出的能力，这些现在都变得重要得多，因为你能比以前并行得多得多。

Gergely：我感觉到的一点是，也许出现了一种新的基本单元。我们以前构建软件时想的是：我怎么构建这个软件，怎么验证它？而现在，就像你说的，问题往往变成：我怎么搭建一个智能体，让它能构建这个东西，并且能验证它？所以几乎是上升到了元层面，这类事情更多了，对吧？

Uday：对。我给你举一个有意思的例子。我在和客服团队的一些工程师一起工作。我们正在推进让 AI 智能体处理部分客服政策。这个流程原本是：你有一份人工客服遵循的操作手册，然后从这份手册出发，经过一大堆步骤，制定一份 AI 智能体可以遵循的政策。然后你得考虑：这里有些动态要素，我需要调用哪些 API 来拿数据，需要用哪些属性？然后我得配置系统，改一堆配置，然后上线前要做人工评测，上线后还要做持续评测。最近几个月，我们把所有这些步骤拿出来，问：我怎么把用于政策转换的全部上下文和全部原则拿出来，教会智能体去做这件事，从而得到一份由智能体生成的非常好的 v0 政策？然后把所有配置搭建、人工测试、寻找正确的 API 和正确的属性都自动化，好把正确的动态要素接进来。这以前要花几周，现在任何一份政策都只要几天。然后，与其做人工评测，你怎么利用过去的所有上下文生成合成评测，从而加速、部署并快速验证？本质上就是你说的那件事：不是自己去做那份工作，而是怎么构建正确的工具和 harness，让工作流自动化。当然中间需要合适的护栏和人工验证步骤，但你是在设计一个能完成这些事情的系统，而不是在所有这些步骤上依赖大量人工。

Gergely：听起来你学到了很多，因为这些都是你现在正在用的新概念，你边做边了解它们的局限，我也明白你说的学得更多、PR 也更多是什么意思。最后：有什么工具是你特别喜欢用的？可以是数字工具，也可以是非数字工具，你觉得有帮助的就行。

Uday：你知道吗，最近几天我迷上了市面上的一些个人智能体，把它们都拿来玩了一遍。它们在帮我自动化个人生活中的一大堆手工杂事。某种意义上，它遵循的是同样的流程：给它完成任务所需的全部上下文，给它所需的全部输入，然后由我担任验证环节里的那个人。它在帮我把所有手工的个人事务自动化方面帮助很大。

Gergely：太好了。Uday，非常感谢你带我们走了一遍 Uber 在用的所有内部系统。我觉得非常有意思，尤其是我已经很久没见过这些了。

Uday：嗯，非常感谢给我们这个机会。我觉得我们在这件事上还很早期；还有那么多要做、那么多要建。我们非常兴奋能踏上这段旅程，去建对的东西，看看软件工程会怎么变，以及最终如何通过做对的事情，为公司、为我们的业务释放价值。

Gergely：希望你和我一样喜欢这次对 Uber 工具的探访。我离开 Uber 已经六年了，所以 Uday 给我展示的很多工具对我来说也是新的。十年前，Uber 以大约 2000 名工程师拥有大约 5000 个服务而闻名，但从那以后公司开始把服务合并成规模合适的服务，今天的微服务比十年前还少。现在大约在 4500 到 5000 个之间，尽管这些服务已经没那么“微”了，而是规模更加合适。

我特别喜欢的一个软件是 Capri，那个事件捕获与回放软件。我在 Uber 的时候，也就是 2016 到 2020 年间，我们有两个叫 Deputy 和 Cerberus 的工具，能做一定程度的生产数据回放，但用起来没那么容易，而且一开始要捕获流量就非常困难。有了 Capri，捕获会话再回放就简单多了，这在复现 bug、以及测试某个 bug 的修复是否有效方面效果非常好。当你像 Uber 那样运行着将近 4500 到 5000 个服务时，构建 Capri 这样的系统尤其复杂。

另一件有意思的事是看到代码评审的走向。它正在各处慢慢消亡。看 Uber 用 Code Inbox 为代码评审打造的工具，每个 PR 仍然要在一位人类工程师判断可以合入之后才会被合入，但 Uber 在构建大量自动化检查，其中很多借助 AI，为改动的风险程度和 AI 智能体产出的质量提供更多信号。所以最终，工程师更容易判断哪些 PR 值得花时间深入看，哪些可以放心地用一句简单的 LGTM 批准，你甚至可能决定不去读那些代码。

最后，我的感觉是，Uber 在开发者生产力上投资了十年，这在 AI 集成上真的、真的得到了回报。比如，他们早在 2017 年就建了叫 DevPods 的云端开发环境，而 Uber 在构建叫 Minion 的云端智能体时，几乎复用了全部这些基础设施。用于验证软件、安全发布软件的现有系统也是如此：现在智能体可以把这些工具当作反馈循环来用。所以感觉上，从 AI 中获益最多的公司，正是那些在 AI 之前就已经有开发者平台团队的公司，至少 Uber 是这样。欢迎去节目说明里查看更多关于 Uber 工程文化的 Pragmatic Engineer 深度文章；Uber 大概是我到目前为止报道得最详细的公司之一。如果你喜欢这期播客，请给个评分，并告诉你的同事和朋友。谢谢，我们下期见。
