本期 Software Engineering Radio 第 710 期，主持人 Kanchan Shringi 与 AWS 副总裁兼杰出工程师 Marc Brooker 讨论规范驱动开发（spec-driven development）：不再把一条条提示词当作核心产物，而是把写清"软件该做什么"的规范当作事实来源，由它驱动代码、测试和评审。

Brooker 先指出 AI 带来的二阶效应：写代码提速两到四倍后，原本 70/30 的"构建/流程开销"比例会逼近 50/50，因此需求、设计、测试、验证这些环节必须一起提速，否则收益有限；从 AI 获益最多的，是早已在测试基础设施上投入、清楚软件应做什么的团队。vibe coding 从零做出原型时极其高效，业余项目完全够用，但一旦要上线、维护几年、满足安全与质量标准，它就后劲不足。他预测，对很多代码库而言，读生成代码会像五十年前读编译器输出的汇编一样逐渐淡出，人们转而评审规范以及"如何验证软件做到了它"。

规范不必很正式，工单、白板草图都算，关键是足够清晰且持续更新。有了规范可以做两件事：交给 Kiro（AWS 的 IDE、CLI 加一组智能体）这类工具生成实现，以及从中提取属性做基于属性的测试。例子是 Aurora DSQL 的 Java 驱动："每次连接尝试都带授权令牌"这条属性会在成千上万种 API 组合下被自动验证；另一个例子是用 Rust 编写的新推理基础设施组件。Brooker 说，做 Kiro 的动因是逐条提示词开发会"忘掉"早先需求、新功能撤销旧成果，规范就像地图而非逐路口导航；同时把神经符号推理能力带给不懂形式化方法的程序员。

完整流程是：先弄清为谁解决什么问题，再写初版规范（可与 AI 来回迭代），然后由人做出架构与实现选择（服务还是库、TypeScript 还是 Rust），再和智能体逐步生成代码与测试，上线听取反馈后回到规范修改，形成闭环。主持人指出这样做的另一个好处是一路都有检查点：可以先读生成的设计文档、核对规范细节，而不是把规范丢给 AI 直接拿最终代码。Brooker 把它比作坐无人驾驶出租车时看着窗外确认方向，在花掉大量时间和 token 之前，先确认做的东西真能解决客户问题。代码评审最好交给目标不同的独立智能体，换模型也有些帮助，但不如多智能体分工重要。Amazon 内部团队的做法是先从现有服务代码中提取规范，以此终止"进两步退一步"的回归。

他认为 2026 年是智能体上下文管理之年。最好的手段仍是老办法：模块化、清晰的 API 与契约、强类型和好文档，再叠加语义搜索；一个实用指标是加一个小功能需要改动几个模块，数字上升就该让 AI 帮忙重构。无关上下文会让结果变差，就像点拿铁时顺带讲气温和海鹰队昨天赢球，只会把店员搞糊涂；智能体通过读文件、搜索索引、调用 MCP 工具自行构建上下文，工具返回的内容应尽量只含所需事实。文档可以由专门的智能体持续更新。评估新模型或新提示词，应先离线跑样例（测试通过率、LLM 当评委），再在线小流量 A/B 逐步放量；指标上，客户在生产中遇到的 bug 最重要也最昂贵，因此要用回归测试失败率、评审通过率、渗透测试智能体的发现等代理指标把问题尽量左移。

推广方面，关键是高标准、拒绝"slop"与好奇心、行动倾向并存的文化，以及在组织内传播经验，例如 Rust 的强类型和编译期检查很适合 AI 开发，Python 类型注解值得投入，同时不必追逐每周的新潮流。对职业焦虑，他保持乐观：软件一直受供给约束，开发成本降到十分之一，经济影响可能扩大 10 到 100 倍。AWS 还把智能体扩展到 DevOps Agent、Security Agent、AWS Transform（Java 升级、大型机迁移）等环节；他说软件工程师很少对从 Java 11 迁到 17 或 21 这类工作感到兴奋，但它对安全和效率至关重要，用 Fortran 写成的遗留系统往往是组织业务逻辑的唯一载体，让 AI 帮忙迁移意义重大。构建智能体本身则借助 Strands steering、AgentCore Policy（把文字约束转成 Cedar 授权代码）等工具，从"念咒语"走向工程学科。结尾他强调，代码只说明"怎么做"，规范驱动开发的价值在于把"为什么"明确写给人和模型看。
