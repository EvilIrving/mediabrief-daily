主播：大家好，这里是 AsyncTalk，我是主播。今天想跟大家聊一个前端开发领域非常老生常谈的话题：UI 组件。这个话题其实已经很久了，那它还有什么好聊的吗？我想聊聊几种非常不同的设计思路。

首先，UI 组件至少可以分为两个时代。第一个时代大概从我刚入行的 2015 年左右，一直到前几年。这个阶段 UI 组件的方向是尽可能提升效率，让我们更快地完成功能。比如大家能看到很多 Form 组件，用 Form 可以非常简单地搭建各种表单，因为后台在很大程度上就是表单的组合，再加上一些信息展示，比如 Table 组件、Tooltip 组件。一句话来说，这个时代的组件是开箱即用的，各个组件库之间竞争的是谁的功能多、谁的 API 更简单。

在这之后，兴起了另一种 UI 组件模式，就是 Headless 组件：我给你逻辑，但 UI 你要自己拼。它和之前的设计思路完完全全不一样。在我看来，它的一个很大的转折点，一方面是 Tailwind 给前端开发带来了 design system 的概念，于是我们的界面设计可以变得更加模块化、更加现代；另一方面是 React Server Component 的概念。

这两派看起来是在竞争，但其实它们回答的是不同的问题。以前以 AntD 为主的 UI 组件库，回答的问题是：我怎么样更快地做完一件事情，更快地交付，更快地完成业务需求。而新的这套模式相对没有那么重视快，它的核心设计理念是：我怎么样去做对的事情、正确的事情。

好，我们还是一点点、更细节地解释这两个流派。首先是以 AntD 为首的传统 UI 组件库，它的优点非常明显：你完全可以 30 秒上手，文档很齐全，示例很丰富，生态也很成熟。如果大家都在 React 管理后台这个领域，八成其实都是拿 AntD 拼拼凑凑，稍微改一些样式之类的东西，大概就是这个样子。

那它的缺点是什么呢？首先，对我来说最不能接受的一点是语义化。AntD 从最开始设计一直到今天的版本——当然我也有些年头没用了——都非常不在乎语义化。举个例子，我相信大家都用过 Tooltip，就是鼠标 hover 在一个东西上面时，会有一段内容展示出来，多数情况下是一个解释。在 AntD 的 API 里，它就是一个 Tooltip 加一个 content，content 里写一段内容，Tooltip 的 children 包住的内容就是它的 trigger。它简单吗？确实很简单，直接写就可以了，也蛮直观。但它正确吗？我不觉得。因为 trigger 和 content 是完完全全两个东西，而这里的 trigger 并没有很明确地表示它是一个 trigger。一句话里其实可能有好几个地方能触发不同的 trigger。还有 Tooltip 的层级结构，如果好几个 Tooltip 堆在一起，对语义化的影响是非常大的，会让人产生疑惑：我这个 children 里面，到底什么是 trigger，什么不是？

第二点，在 React 蓬勃发展的这个时代，AntD 其实非常不适合。你可以看到它几乎所有组件都是 Client Component，同时还大量使用了非常繁重的 JavaScript 计算，重灾区基本是 Table 以及相关的 Form，甚至一些文本展示、Alert 信息展示也都是 Client Component。你知道在 Server Component 的时代，这会有一些影响，比如影响 SEO，所以它并不太适合新的 Server Component 时代。同时，这类传统组件库的更新频率也没有那么高。

第三点，AntD 有一些做法我不是特别同意，举几个例子。一个是 CSS：你可以看到它是在最顶层引入一个 CSS。这一方面导致没办法做 tree shaking，另一方面导致 global 样式满天飞。你的应用可能在最外层有一个 global，最内层又有一个 global，各种打架。代码如果一万行也许还好，但代码量一上去，global style 就很容易出问题：可能在 user profile 页面看起来正常，到了 post detail 页面又错了。这是很容易发生的事，我相信有一定工作经验的人都很能理解。

还有一些神奇的挂载点。还是用前面的 Tooltip 来举例：Tooltip 有一个 trigger，有一个 content，content 就是用户 hover 到内容上之后展示的东西。听起来很简单，但它有好几个层级，也许外层有一个 container 包着，这时你 hover 上去展示的内容可能会被隐藏掉。这时你就需要用 Tooltip 里一个叫 getPopupContainer 的方法，强行把它挂载到更顶层的节点，一般就是 document.body。可挂载到那里又会损失一些东西，比如鼠标滚动的时候它没办法跟着滚，因为它的挂载点已经从 DOM 本身向上变成了 document.body。另外还有 z-index，z-index 永远在冲突，下面的盖到上面，上面的盖到下面。我相信大家都碰到过。

还有一个我觉得很重要的问题是自定义。大家都有一些后台系统，后台系统用了 AntD——我不是单纯在说 AntD 这一个东西，而是以 AntD 为首的这一类 UI 框架——是很难对样式做自定义的，因为它里面的 DOM 结构是黑盒。比如你想改 Alert 的颜色，就需要从上层一层一层用 CSS 选到这个内容。而且它在不同状态下 DOM 结构也许不一样，前一个版本和后一个版本的 DOM 结构也可能不一样，所以这样一层一层地改是比较危险的操作。所以用这种框架，自定义程度非常受限，看起来你是在改一个样式，实际上你是在和框架作者打架。你需要用各种 !important、各种神奇的 CSS selector 去选到某个内容。当然，这些框架也尝试解决这个问题，比如通过 ConfigProvider，但你也能看到收效很有限。

所以，过去这种比较传统的 UI 组件，本质上只是一个实用主义的产物，并不是以长期可维护为目标来做的产品。如果你业务压力重，就会在业务压力和其他因素的取舍中，一次又一次地选择面向业务——我要把业务做得更快、做得更好——然后抛弃掉其他东西。这是这样一种选择。

另一方面，shadcn 这一派是怎么做的呢？它的核心理念是：我们不再把 UI 库作为一个 dependency，而是作为我们自己的代码。它是 copy paste 的，你 own 这些代码，可以任意修改，想怎么调整都随你。它跟着项目走，你的自由度非常高。相对前面的传统 UI 框架，它解决了很多问题。

第一，它的语义化程度非常高。你可以看到它有非常多 accessibility 相关的属性挂载在元素上，让屏幕阅读器能够正确理解这个模块到底是干什么的。第二，它的自定义程度当然更高，因为你拥有这些代码，它只是把代码从它的库里复制粘贴到你自己的代码里，然后你拥有所有内容。第三，它对 React Server Component 也很友好。因为代码在你手里，它的大多数组件也没有强行写 "use client" 或 "use server"，一些只读的展示组件可以直接用，仍然符合 Server Component 的概念。同样，它也没有版本升级的烦恼，因为代码已经进了你的仓库，没什么需要升级调整的，你只需要升级它底下的一些依赖库，比如 Radix 或其他一些逻辑层面的库。

当然它也不完美，同样对应前面的传统 UI 框架来说。首先是上手成本高，你需要先理解 Tailwind，代码量也会比较长。为了语义化，它把组件拆成好几个部分：Tooltip 在传统组件库里只是一个 Tooltip 组件，但在 shadcn 这样的框架里分了好几层，分别有 Root、Content、Trigger，还有各种各样的 primitive 概念。总的来说，它的 API 设计比原先的传统框架要复杂一些。而且因为它是复制一份代码过来，心智负担其实也是存在的。

OK，前面我们提到传统 UI 库上手门槛较低，但可维护性和正确性相对不太好；另一方面又聊了 shadcn，它和前者刚好相反，有更好的性能、更正确的语义，但上手难度略高一些。那有没有更好的方式呢？

接下来是我自己的想法。我个人写的一些项目，UI 框架都是自己生成的。在我看来，AI 时代写代码的成本已经变得非常低了，你不再需要用一套非常完整的所谓企业级框架来限制自己，而完全可以靠 AI 生成你需要的组件，然后把那些不需要的组件全部扔掉。另一方面，基础的 Headless 组件库已经非常成熟了。比如你要做 Tooltip，市面上有叫 Floating UI 的库，已经做得非常完善，在各个框架下的逻辑都处理得非常好，有正确的 offset，有可以高度自定义的样式和逻辑，甚至可以把 Tooltip 展示在完全虚拟的结构上，也完全没问题。所以我们自己写 UI 组件库的成本已经变得非常低了。

自己维护、靠 AI 生成 UI 组件库，有几个非常好的点。首先是品牌一致性：这个库完全是你自己设计的，所以你既不受限于 AntD 那种传统样式，也不受限于 shadcn 内部 Tailwind 那种结构，你有更大的自由度。因为你完全 own 这些代码，只要告诉 AI"这个地方给我改改"就可以了。其次是性能：像 Radix 性能不错，但仍然有一些兼容性的问题；如果代码完全是你的，性能可以更好，因为你可以抛弃很多不需要的功能。再次是演进是自由的：你的产品如果要变，只要告诉 AI 去改这些组件就可以了。

那它有没有成本呢？有，它唯一的成本就是你个人的开发成本。但我觉得如果你用 AI 工具写代码，这个成本已经压得非常低了，只比用 AntD 的开发成本略高一丁点而已。也许只要半个小时，你就可以写出一个非常可用的 UI 组件。同时你的自定义程度也是最高的。

最后说一说怎么选。如果你做的是一次性的后台，而且是内部工具，对自定义程度要求也不高，只是一个凑合能用的东西，那用 AntD 或者 Material UI 这样的组件库完全没有任何问题，它可以很快帮你解决问题、完成你想要的功能。如果你的项目稍微大一点，对正确性以及 AI friendly 的要求比较高，那我会更推荐你基于 shadcn 拼接自己的 UI 库，甚至完全抛弃 UI 库，通过 AI 自己生成，这也完完全全没有问题。对我个人来讲，我更推荐你自己靠 AI 做 UI 库，它会更适合你的项目。

OK，UI 框架在过去十年也许是一个最优解，能快速帮你完成很多东西。但在下一个十年，或者说下一个三五年，我认为靠 AI 协作完成的自有 UI 库，也许是更正确的选择。观众朋友们，你们怎么看？欢迎在评论区留言告诉我你的看法，也欢迎转发给你的朋友，听听他们的看法。好的，今天的节目就到这里，再见。
