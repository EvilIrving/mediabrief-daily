https://surma.dev/things/when-workers/

你应该总是使用 Web Workers。而在我们当前的框架格局下，这几乎不可能做到。

这句话引起你的注意了吗？很好。当然，和任何话题一样，这里面有细微之处，我会把它们全部摆出来。但我有观点，而且这些观点很重要。系好安全带。

## 性能鸿沟正在加宽

**注：**我讨厌"新兴市场"这个说法，但为了让这篇博文对尽可能多的人来说都直观易懂，我在这里还是会用它。

手机越来越快了。我想没有人会反对这一点。更强的 GPU，更快、更多的 CPU，更多的内存。手机正在经历桌面电脑在 2000 年代初经历过的那种快速发展。

然而，那只是分布的一端。***慢*手机停留在了 2014 年。**制造半个十年前那些芯片的工艺已经变得非常便宜，以至于手机现在能卖到 20 美元左右，而更便宜的手机会触达更广泛的人群。世界上约 50% 的人在线，也就是说另外约 50% 的人不在线。然而，这些离线的人正在*上线*，而且他们主要分布在新兴市场，那里的人根本买不起"富裕西方网络"（Wealthy Western Web）里的任何旗舰手机。

在 Google I/O 2019 上，Elizabeth Sweeny 和 Barb Palser 在一次合作伙伴会议上分发了 Nokia 2 手机，并鼓励他们用上一周，去*真正*体会世界上许多人每天使用的是什么档次的设备。Nokia 2 很有意思，因为它看起来、摸起来都像一部高端手机，但内里更像一部半个十年前的智能手机，搭配着今天的浏览器和操作系统——你能感受到这种错位。

让事情更极端的是，功能机正在卷土重来。还记得那些没有触摸屏、而是带着数字键和方向键的手机吗？没错，它们正在回归，而且现在还能运行浏览器。这些手机的硬件更弱，但也许有点出人意料的是，性能反而更好。部分原因是它们要控制的像素少得多。换句话说：相对于 Nokia 2，它们每个像素拥有的 CPU 算力更多。

虽然每一代我们都能拿到更快的旗舰手机，但绝大多数人买不起它们。更实惠的手机停留在过去，性能指标波动极大。在未来几年里，这些低端手机很可能会被大量新上网的人使用。**最快和最慢手机之间的差距正在加大，而中位数正在*下降*。**

## JavaScript 是阻塞的

也许值得明说：长时间运行的 JavaScript 糟糕之处在于它是阻塞的。JavaScript 运行时，其他任何事情都无法发生。**主线程除了运行 Web 应用的 JavaScript 之外，还有其他职责。**它还要做页面布局、绘制、及时把所有这些像素送到屏幕上，并留意点击或滚动之类的用户交互。在 JavaScript 运行时，这些都无法进行。

浏览器为此推出了一些缓解措施，例如在某些条件下把滚动逻辑移到另一个线程。但总的来说，如果你阻塞了主线程，你的用户就会很难受。是*真的*难受。他们会愤怒地狂点你的按钮，会被卡顿的动画和可能迟滞的滚动折磨。

## 人类感知

阻塞多少算太多？RAIL 是回答这个问题的一种尝试，它基于人类感知，为不同任务提供基于时间的预算。例如，要让动画在人眼看来流畅，你只有约 16ms 的时间，下一帧就必须渲染出来。**这些数字是固定的**，因为人类心理不会因为你手里拿的是什么设备而改变。

看看"不断加宽的性能鸿沟™️"，这就意味着麻烦。你可以构建你的应用，尽职尽责地做性能审计，修复所有瓶颈，达到所有指标。**但除非你是在现有最慢的低端手机上开发，否则几乎不可能预测一段代码在今天最慢的手机上要跑多久，更别说明天最慢的手机了。**

这就是拥有无与伦比覆盖面的 Web 所背负的担子。你无法预测你的应用会运行在什么档次的设备上。如果你说"Surma，这些性能不足的设备和我/我的业务无关！"，在我听来，这和"依赖读屏软件的人和我/我的业务无关！"极其相似。**这是包容性的问题。我鼓励你*认真*想一想：不支持低端手机，你是否在把一些人排除在外。**我们应该努力让每个人都能获取世界上的信息，而你的应用就是其中的一部分，不管你喜不喜欢。

话虽如此，像这样的一篇博文永远无法给出适用于所有人的指导，因为总有细微之处和具体背景。上面那段话也是如此。我不会假装无障碍或为低端手机开发很容易，但我确实相信，作为工具和框架作者的社区，我们能做很多事情来帮人们走上正路，让他们的作品默认就更易访问、性能更好，这也会让它们默认就更具包容性。

## 解决它

我们就是这样，试图在流沙上建城堡。试图构建能守住 RAIL 时间预算的应用，却要面对种类繁多的设备，在这些设备上一段代码的运行时长几乎不可预测。

### 合作式调度

减少阻塞的一种技术是"把 JavaScript 切块"或"让出给浏览器"。意思是在代码中定期加入*断点*，让浏览器有机会停下你的 JavaScript，送出新的一帧或处理一个输入事件。浏览器处理完后，会回来继续运行你的代码。在 Web 平台上让出给浏览器的方法是调度一个任务（task），这可以通过多种方式实现。

**必读：**如果你不熟悉任务（task），和/或不清楚任务和微任务（microtask）的区别，我推荐 Jake Archibald 关于事件循环的演讲。

在 PROXX 中，我们用一个 `MessageChannel`，并用 `postMessage()` 来调度任务。为了在加入断点时保持代码可读，我强烈推荐使用 `async`/`await`。下面是我们在 PROXX 中实际上线的代码：在用户与游戏主界面交互的同时，我们在后台生成精灵图。

```
const { port1, port2 } = new MessageChannel();
port2.start();
export function task() {
  return new Promise(resolve => {
    const uid = Math.random();
    port2.addEventListener("message", function f(ev) {
      if (ev.data !== uid) {
        return;
      }
      port2.removeEventListener("message", f);
      resolve();
    });
    port1.postMessage(uid);
  });
}
export async function generateTextures() {
  // ...
  for (let frame = 0; frame < numSprites; frame++) {
    drawTexture(frame, ctx);
    await task(); // 断点！
  }
  // ...
}
```
但**切块仍然受到"不断加宽的性能鸿沟™️"的影响**：一段代码到达下一个断点所需的时间本质上取决于设备。在一部低端手机上不到 16ms 的工作，在另一部低端手机上可能要花长得多的时间。

## 离开主线程

我之前说过，主线程除了运行 Web 应用的 JavaScript 之外还有其他职责，这就是为什么我们需要不惜一切代价避免在主线程上运行长时间阻塞的 JavaScript。但如果我们把大部分 JavaScript 移到一个*专门*运行我们的 JavaScript、不做其他任何事的线程上呢？一个没有其他职责的线程。在这种设置下，我们就不必担心代码受到"不断加宽的性能鸿沟™️"的影响，因为主线程不受影响，仍然能够响应用户输入，并保持帧率稳定。

### Web Workers 又是什么来着？

**Web Workers，也叫"专用 Worker"（Dedicated Workers），是 JavaScript 版的线程。**JavaScript 引擎在构建时假设只有一个线程，因此不存在对 JavaScript 对象内存的并发访问，也就无需任何同步机制。如果把带有共享内存模型的常规线程加进 JavaScript，说得轻点也会是一场灾难。取而代之，我们得到了 Web Workers，它基本上是一个运行在独立线程上的完整 JavaScript 作用域，没有任何共享内存或共享值。为了让这些完全分离、相互隔离的 JavaScript 作用域协同工作，你有 `postMessage()`，它能在*另一个* JavaScript 作用域中触发一个 `message` 事件，并附上你提供的值的一份拷贝（使用结构化克隆算法复制）。

到目前为止，除了少数"稳操胜券"的用例（通常是长时间运行的数值计算任务）之外，Worker 几乎没有被采用。我认为这应该改变。**我们应该开始使用 Worker。大量使用。**

### 酷孩子们都在这么做

这根本不是什么新想法。恰恰相反。**大多数原生平台把主线程称为 UI 线程，因为它*只*应该用于 UI 工作，**而且它们给了你实现这一点的工具。Android 从最早的版本起就有 `AsyncTask`，之后又加入了更方便的 API（最近的是协程 Coroutines，它可以很容易地调度到不同线程上）。如果你选择开启"严格模式"（Strict mode），某些 API——比如文件操作——在 UI 线程上使用时会让你的应用崩溃，帮你发现自己在 UI 线程上做了非 UI 工作。

iOS 从一开始就有 Grand Central Dispatch（"GCD"），用来把工作调度到不同的、由系统提供的线程池上，包括 UI 线程。这样一来，它们同时强制推行了两种模式：你总是必须把工作切成任务以便放入队列，让 UI 线程在必要时可以处理它的其他职责；同时你只需把任务放入另一个队列，就能在另一个线程上运行非 UI 工作。锦上添花的是，任务可以被赋予优先级，这有助于确保时间敏感的工作尽快完成，同时不牺牲整个系统的响应性。

关键在于，这些原生平台从诞生起就支持利用非 UI 线程。我想可以公平地说，随着时间推移，它们已经证明了这是个好主意™️。把 UI 线程上的工作降到最少，有助于你的应用保持响应。为什么这种模式没有在 Web 上被采用呢？

## 开发者体验是一道障碍

Web 上我们唯一的线程原语就是 Web Workers。当你开始用它们提供的 API 使用 Worker 时，`message` 事件处理器就成了你宇宙的中心。这感觉并不好。此外，Worker *像*线程，但并不等同于线程。你无法让多个线程访问同一个变量（比如一个状态对象），因为一切都必须通过消息传递，而这些消息能携带许多但并非所有的 JavaScript 值。例如：你无法发送一个 `Event`，也无法在不丢失数据的情况下发送任何类实例。我认为，这一直是劝退开发者的一个主要因素。

### Comlink

正是出于这个原因，我写了 Comlink。它不仅把 `postMessage()` 对你隐藏起来，甚至把你在使用 Worker 这一事实本身也隐藏了。它让你*感觉*像是能共享访问其他线程中的变量：

```
// main.js
import * as Comlink from "https://unpkg.com/comlink?module";
const worker = new Worker("worker.js");
// 这个 `state` 变量实际上位于 worker 中！
const state = await Comlink.wrap(worker);
await state.inc();
console.log(await state.currentCount);
```
```
// worker.js
import * as Comlink from "https://unpkg.com/comlink?module";
const state = {
  currentCount: 0,
  inc() {
    this.currentCount++;
  }
}
Comlink.expose(state);
```
**注：**为了让示例简短，我这里使用了顶层 await 和 Worker 中的模块。真实示例和更多细节请参见 Comlink 的代码仓库。

Comlink 并不是这个问题领域的唯一方案，只是我最熟悉的一个（考虑到是我写的，这不奇怪 🙄）。如果你想看看不同的思路，可以看看 Andrea Giammarchi 的 workway 或 Jason Miller 的 workerize。

我不在乎你用哪个库，只要你最终转向离开主线程的架构就行。我们在 PROXX 和 Squoosh 中都非常成功地使用了 Comlink，因为它很小（gzip 后 1.2KiB），并且让我们能使用许多来自拥有"真正"线程的语言中的常见模式，而没有明显的开发开销。

### Actor

最近我和 Paul Lewis 一起评估了另一种方法。我们没有隐藏使用 Worker 和 `postMessage` 的事实，而是从 70 年代汲取灵感，使用了 Actor 模型——一种把消息传递*拥抱*为基本构建块的架构。从这个思想实验出发，我们构建了一个 actor 支持库和一个入门套件，并在 Chrome Dev Summit 2018 上做了一场演讲，解释这种架构及其影响。

## "基准测试"

你们有些人大概在想：**采用离开主线程的架构值得花这些功夫吗？**我们来做个成本/收益分析：有了 Comlink 这样的库，转向离开主线程架构的成本应该比以前低得多，接近于零。那收益呢？

Dion Almaer 让我写一个所有东西都在主线程上运行的 PROXX 版本，大概就是为了弄清这个问题。于是我写了。在 Pixel 3 或 MacBook 上，差别只是偶尔才能察觉。然而在 Nokia 2 上玩，差别就是天壤之别。**所有东西都在主线程上时，在最坏情况下应用会冻结长达 6.6 秒。**而且市面上还有比 Nokia 2 性能更弱的设备！运行采用离开主线程架构的 PROXX 线上版本时，运行 `tap` 事件处理器的任务只需 48ms，因为它做的全部事情就是调用 `postMessage()` 给 worker 发一条消息。这说明，尤其是考虑到"不断加宽的性能鸿沟™️"，**离开主线程的架构增强了对意外地大或长的任务的韧性**。

需要注意的是，工作并没有凭空消失。在离开主线程的架构下，代码仍然需要约 6 秒来运行（就 PROXX 而言实际上明显更长）。但由于这些工作现在发生在另一个线程中，UI 线程保持响应。我们的 worker 还会把中间结果发回主线程。**通过让事件处理器保持精简，我们确保了 UI 线程保持空闲，能够更新画面。**

## 框架的困境

现在是我的劲爆观点：**我们当前这一代框架让离开主线程的架构变得困难，并削弱了它的回报。**UI 框架本应做 UI 工作，因此有权在 UI 线程上运行。然而在现实中，它们所做的工作是 UI 工作和其他相关、但归根结底并非 UI 工作的混合体。

以 VDOM diff 为例：虚拟 DOM 的目的是把对真实 DOM 的高代价更新与开发者的操作解耦。虚拟 DOM 只是一个镜像真实 DOM 的数据结构，对它的修改没有任何高代价的副作用。只有当框架认为合适时，对虚拟 DOM 的修改才会被重放到真实 DOM 上。这通常称为"刷新"（flushing）。在刷新之前的一切都完全不需要在 UI 线程上运行。可它偏偏就在那上面跑，浪费你宝贵的 UI 线程预算。在 PROXX 中，我们实际上放弃了 VDOM diff，自己实现了 DOM 操作，因为处在性能谱系低端的手机应付不了那么多的 diff 工作。

VDOM diff 只是框架选择开发者体验或实现的简单性、而不是节约终端用户资源的众多例子之一。除非一个面向全球发布的框架把自己标榜为专门面向"富裕西方网络"的用户，**否则它就有责任帮助开发者覆盖"不断加宽的性能鸿沟™️"谱系上的每一部手机。**

## 结论

Web Workers 帮助你的应用在更广泛的设备上运行。像 Comlink 这样的库帮助你在不损失便利性和开发速度的情况下使用 Worker。我认为**我们应该质疑：为什么*除了 Web 之外*的每个平台都在为让 UI 线程尽可能空闲而努力**。我们需要转变默认做法，并帮助塑造下一代框架。
