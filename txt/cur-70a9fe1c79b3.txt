SE Radio 688: Daniel Stenberg on Removing Rust from Curl ｜ Software Engineering Radio ｜ 57分钟 ｜ https://se-radio.net/2025/10/se-radio-688-daniel-stenberg-on-removing-rust-from-curl/

本期由 Gavin Henry 主持，嘉宾是 curl 创始人兼首席开发者 Daniel Stenberg，复盘 curl 引入、最终又移除 Rust 写的 HTTP 库 Hyper 的全过程。Stenberg 先介绍 curl：它是命令行工具加 libcurl 库，支持 28 种 URL 协议，嵌在 iOS、Android、游戏机等数十亿台设备里，一部手机上常有五到十份 libcurl，因为系统不对应用开放 API。但他是团队里唯一的全职，大公司几乎都免费使用而不付支持费。他把这归结为经典的经济学规律：只要不是非付不可，企业就宁愿不付，而且每家都以为别人在付。主持人也感慨，这类关键的互联网基础软件背后往往只有一两个人，圈外人很难想象。

引入 Hyper 的动机是内存安全。curl 用 C 写成，历来有不少内存类安全问题；它本就有可插拔后端的架构（TLS、SSH、域名解析等都可以换第三方库），所以由 Let's Encrypt 背后的 ISRG 通过 Prossimo 项目资助，新建一个由 Hyper 驱动的可选 HTTP 后端，逐个组件替换而不是整体重写——两人都认为用 Rust 重写 curl 是疯狂的。之所以选 Hyper，Stenberg 承认并没有经过严密比较：他不熟悉 Rust 生态，基本采纳了 ISRG 的建议，和 Hyper 首席维护者 Sean McArthur 谈过后，认为它在技术栈里的抽象层级合适，自己从零写 Rust 版协议既工作量巨大，他也不是合适人选。为此他还专门在 curl 里创造了“HTTP 后端”这个原本不存在的概念。Stenberg 坦言 HTTP 解析并不是 curl 内存问题最集中的地方，这些年他们更多靠内部辅助函数和编码规则写出更好的 C 来减少错误。

实现上，curl 并不直接调用 Rust，而是由 Hyper 维护者 Sean McArthur 专门写出 C 接口的胶水库，curl 在 configure 里检测并链接它，对 curl 来说"只是另一个 C 库"。难点有三：一是 FFI 当时还很早期，许多接口要两边一个个补；二是 Rust 库的文档都写给 Rust 用户，从 C 调用时类型、返回码都对不上，只能读代码猜，需要同时精通两种语言的人；三是 Hyper 的异步模型、头部顺序不保留等行为与 curl 不同，而 curl 的测试套件逐字节比对请求和响应，只能请 Hyper 改动、并微调测试。主持人补充，用 FFI 把 Rust 函数压成返回 0/1 或指针的 C 接口，等于双倍设计工作，还丢掉了 Rust 丰富的错误类型；再加上跨边界传递内存时谁分配、谁释放的约定，复杂度很快上升。Stenberg 也理解 Rust 维护者优先照顾 Rust 用户，C 调用者是小众，这无可厚非，但确实让集成更难。

为什么最终放弃？关键不是选错了部位，而是没有用户。curl 让各后端"适者生存"，而 Hyper 后端一直标为实验性，几乎没人试用，严重 bug 长期无人报告，贡献者也极少。约 2000 个测试里 HTTP 相关的有八九百个，最后只剩约 15 个失败，它们牵涉 NTLM、Digest 等 curl 自己实现、Hyper 不具备的认证逻辑，要同时懂 Hyper、C 胶水层、curl 和协议的人才能修，却找不到这样有时间精力的人。项目停在 97% 左右的测试通过率很久，加上 curl 用户满意原生实现、Hyper 用户本就不用 curl，需求落在真空地带，于是 2024 年底整体移除，连可二选一的后端框架也一并拆掉，因为他觉得那套接入方式做得别扭，不如留待以后重新设计。被问到是否考虑过自己从零重写，他说自己 Rust 水平不够，也就不会要求别人去做，所以选项只有 Hyper 或者不做。ISRG 没有给时间表，一直很灵活，自己也努力找人接手未果，最后认同这个决定；大门并未关死，旧代码仍在版本历史里，将来有契机还可以重启。

Stenberg 不认为这是失败：它证明了方案可行，curl 的 HTTP 处理因此变得更严谨，HTTP 特有逻辑也从通用代码里清理了出去，这些都保留了下来，下次再做 HTTP 后端会更好。Hyper 一方同样借此完善了 C 接口。主持人认为能走到只剩 15 个测试已是相当大的胜利，Stenberg 也同意它证明了想法站得住、实现虽不完美但能用，只是最后没有走完全程，而折腾到底也换不来用户需求这座“奖杯”。至于为什么没人站出来帮忙，两人归结为所需知识横跨 Rust、C 接口、curl 内部和具体协议四个领域，同时也没人觉得 curl 的原生实现不安全。由于 C 带来的可移植性，原生实现无论如何都会保留。rustls、quiche 等 Rust 后端仍在使用，因为 TLS 是更清晰的抽象层。他的结论是：在大型 C 项目中逐组件引入 Rust 是合理的路线，Apache 用 rustls 替换 OpenSSL 的 mod_tls 就是同一思路。他也指出其中的讽刺：rustls 底层有时仍会用到 C 的加密代码。主持人则总结，如果没有数据证明投入多少能换来多少安全收益，这类改造的价值很难量化。最后他特别强调，Hyper 团队投入很大，这次放弃不是他们的错。
