什么时候该用 Web Workers？

你应该总是用 Web Workers。而在我们当前的框架格局里，这几乎不可能。

这句话吸引到你的注意了吗？很好。当然任何话题都有细微之处，我会一一铺开。但我有观点，而且它们很重要。系好安全带。

性能鸿沟在加宽

（注：我讨厌"新兴市场"这个术语，但为让尽可能多人直观读懂，文中仍使用它。）

手机在变快。更强的 GPU、更多更快的 CPU、更多 RAM。手机正经历台式机在 2000 年代初经历过的那种快速发展。

然而那只是分布的一端。慢手机卡在 2014 年。半个十年前的芯片制程已经便宜到手机可以卖到约 20 美元，更便宜的手机会触达更广受众。约 50% 的世界已联网，意味着另外约 50% 还没有；这些离线者正在上网，且主要位于新兴市场，人们根本买不起富裕西方 Web 的旗舰机。

2019 年 Google I/O，Elizabeth Sweeny 与 Barb Palser 在合作伙伴会上发放 Nokia 2，鼓励他们用一周，真正感受世界上许多人日常使用的设备档次。Nokia 2 有趣之处在于：手感和外观像高端机，内核却更像半个十年前的智能手机配上今天的浏览器与系统——你能感觉到这种错位。

更极端的是功能机正在回归：没有触摸屏、有数字键和方向键的那种，现在也能跑浏览器。硬件更弱，但或许有些意外地，性能更好——部分因为要控制的像素少得多，相对 Nokia 2，每像素 CPU 更多。

我们每个周期都得到更快的旗舰，但绝大多数人买不起。更便宜的手机卡在过去，性能指标高度波动。未来几年大规模上网的人，多半会用这些低端机。最快与最慢手机之间的鸿沟在变宽，中位数在往下走。

JavaScript 会阻塞

值得说清楚：长跑 JavaScript 的坏处是它会阻塞。JS 在跑时别的事都做不了。主线程除了跑 web 应用的 JavaScript，还要做页面布局、绘制、及时把像素送到屏幕，并留意点击或滚动等用户交互。JS 在跑时这些都不能发生。

浏览器已有一些缓解，例如在特定条件下把滚动逻辑挪到另一线程。但总体而言，阻塞主线程会让用户很惨：狂点按钮、动画卡顿、滚动迟滞。

人类感知

多少阻塞算太多？RAIL 试图用基于人类感知的时间预算回答，例如约 16ms 就要渲出下一帧才觉得动画顺滑。这些数字是固定的，因为人类心理不随你手持的设备而变。

对照不断加宽的性能鸿沟，这就麻烦了。你可以做尽职调查、性能审计、修瓶颈、打中所有指标——但除非你在能买到的最慢低端机上开发，否则几乎不可能预测一段代码在今天最慢的手机上要跑多久，更别说明天最慢的那台。

这是 web 无与伦比触达面带来的负担。你无法预测应用会跑在哪一档设备上。若你说"这些欠功耗设备与我/我的生意无关！"，在我听来可怕地像"依赖读屏的人与我/我的生意无关！"。这是包容性问题。我鼓励你认真想想：不支持低端机是否在排斥人。我们应努力让每个人都能获取世界信息，你的应用是其中一部分，无论你喜不喜欢。

当然，这样一篇博文永远无法给出适用于所有人的指导，因为总有细微与语境。我不会假装无障碍或为低端机写作很容易，但我相信作为工具与框架作者社区，我们有很多事可做，从默认就把人设置到更无障碍、更高效能的路上，从而也更包容。

修复它

我们试图在流沙上造城堡：让应用留在 RAIL 时间预算内，却面对代码耗时几乎不可预测的海量设备。

一种减弱阻塞的技术是"切分 JavaScript"或"让出给浏览器"：在代码里定期加断点，让浏览器有机会停下你的 JS、送出新帧或处理输入。web 上让出的方式是调度一个任务。若你不熟任务与微任务的差别，推荐 Jake Archibald 的事件循环演讲。在 PROXX 里我们用 MessageChannel 的 postMessage 调度任务，并强烈建议用 async/await 保持可读。（原文给出 task() 与 generateTextures 循环中 await task() 的示例。）

但切分仍受性能鸿沟影响：跑到下一断点的时间本质上依赖设备。某台低端机上不到 16ms 的事，在另一台上可能久得多。

离开主线程

若我们把大部分 JavaScript 挪到一条只跑我们的 JS、没有别的职责的线程呢？那样就不必担心代码受性能鸿沟拖累，主线程仍能响应输入并稳住帧率。

Web Workers（也称 Dedicated Workers）是 JavaScript 对线程的取法。引擎一直假定单线程，因而没有对 JS 对象内存的并发访问，也就不需要同步机制。若把带共享内存的常规线程加进 JS 会是灾难。我们得到的是 Workers：在另一线程上跑的整个 JS 作用域，没有共享内存或共享值；用 postMessage 在另一作用域触发 message 事件并带上你提供的值的拷贝（结构化克隆）。

迄今 Workers 几乎没有普及，除了少数"灌篮"用例（通常是长跑数值计算）。我认为这应改变。我们应开始大量使用 workers。

所有酷小孩都在这么做

这绝不是新想法。多数原生平台把主线程叫 UI 线程，认为它只应做 UI 工作，并给你工具达成这一点。Android 很早有 AsyncTask，后来有更方便的 API（最近是协程）；打开"严格模式"时，文件操作等 API 在 UI 线程使用会直接让应用崩溃。iOS 从一开始就有 Grand Central Dispatch，把工作调度到包括 UI 线程在内的系统线程池，并强制两种模式：工作必须切成任务入队，非 UI 工作只要放进不同队列即可，还可设优先级。要点是：这些原生平台从诞生起就支持利用非 UI 线程。把 UI 线程上的工作压到最少，有助于应用保持响应。为什么 web 没采纳这一模式？

开发者体验是障碍

web 上线程的唯一原语是 Web Workers。用它们自带的 API 时，message 事件处理函数成为宇宙中心，感觉不好。此外 Workers 像线程又不是线程：不能多线程访问同一变量，一切须经消息，且消息不能无损携带所有 JS 值（例如 Event、任意类实例）。我认为这是主要劝退因素。

正因如此我写了 Comlink：不仅藏起 postMessage，也藏起你在用 Workers 的事实，感觉像跨线程共享变量。（原文给出 main.js / worker.js 用 Comlink.wrap / expose 的短例。）我用了顶层 await 与 worker 中的模块以保持简短。Comlink 不是该问题空间唯一解，只是我最熟的（毕竟是我写的）。也可看 Andrea Giammarchi 的 workway 或 Jason Miller 的 workerize。我不在乎你用哪家库，只要你最终转向离开主线程的架构。我们在 PROXX 和 Squoosh 里用 Comlink 很成功：体积小（gzip 约 1.2KiB），又能几乎无开发开销地使用"真线程"语言里的常见模式。

我最近还和 Paul Lewis 一起评估另一路线：不藏 Workers 与 postMessage，而从七十年代的 Actor 模型取灵感，拥抱消息传递。我们做了 actor 支持库、起步套件，并在 2018 Chrome Dev Summit 讲了架构与含义。

"基准测试"

采用离开主线程架构值得吗？用 Comlink 一类库后，切换成本应显著低于从前、接近零。收益呢？Dion Almaer 让我写一版一切跑在主线程上的 PROXX。在 Pixel 3 或 MacBook 上差异很少察觉；在 Nokia 2 上却是昼夜之别。一切在主线程时，最坏情况应用可冻结长达约 6.6 秒。线上 Worker 版里，处理 tap 的任务只需约 48ms，因为它只做 postMessage。工作并未消失（PROXX 里实际可能显著更久），但发生在另一线程，UI 线程保持响应；worker 还回传中间结果。通过保持事件处理精瘦，我们确保 UI 线程空闲并更新画面。尤其面对性能鸿沟，离开主线程的架构增强了对意外庞大或漫长任务的韧性。

框架困境

我的辛辣看法：我们当前这一代框架让离开主线程的架构变难，并削弱其回报。UI 框架本该做 UI 工作，因而有权跑在 UI 线程；现实中它们做的却是 UI 与相关但终非 UI 工作的混合物。以 VDOM diff 为例：虚拟 DOM 的目的是把对真 DOM 的昂贵更新与开发者操作解耦；直到框架"flush"之前，这些工作完全没有必须跑在 UI 线程的要求，却仍在浪费宝贵的 UI 线程预算。在 PROXX 我们甚至退出了 VDOM diff、自己做 DOM 操作，因为光谱低端的手机扛不住那么多 diff。除非自称只面向富裕西方 Web 用户，全球发布的框架有责任帮助开发者覆盖性能鸿沟全谱。

结论

Web Workers 帮助你的应用跑在更广的设备上。Comlink 一类库帮助你在不丢掉便利与速度的情况下利用 workers。我认为我们应质疑：为什么除了 web 之外每个平台都在争取让 UI 线程尽可能空闲。我们需要改变默认做法，并帮助塑造下一代框架。
