软件工厂：亮灯与熄灯

2026 年 7 月 20 日

软件工厂就是大规模地驾驭循环。你可以让人留在循环里运行（亮灯工厂）：用判断力和专注力去换取速度、承担出错。也可以把人撇开（熄灯工厂），让智能体自己确定范围、构建并交付代码，而没有人真正去读细节。但如果人们不再阅读，他们就会不再理解你的软件。你现在最难的工作，是知道该构建哪些检查，以及该下放多少自主权。

"软件工厂"这个说法可以追溯到 Bob Bemer 1968 年发表的论文《程序生产的经济学》（The Economics of Program Production）。半个世纪以来，许多人梦想着一个世界：软件是一个可重复、可度量的生产过程（就像在工厂里冲压汽车零件），而不是个人孤立的手艺。从历史上看，这个梦想通常（虽然并非全部）落空了，部分原因在于想法很难被"冲压"出来。

但在过去两年里，情况发生了足够剧烈的变化，现在值得重新审视这个老梦想。而且，由于一些微妙之处很容易被一笔带过，有必要比较精确地说清楚，到底什么是真正新的、不同的，什么又可能是披着新机遇外衣的老陷阱。

HumanLayer 联合创始人 Dex Horthy 最近在 AI Engineer World's Fair 上做了一场很棒的演讲，题为《光有驾驭工程还不够：软件工厂为何失败》（Harness Engineering is not Enough: Why Software Factories Fail），关于这个话题值得一看。

## 循环是原子，工厂是规模化的循环

结构决定一切，而一切都从小单元开始。整个体系其实是三个概念层层叠加：循环（loop）、驾驭框架（harness）和工厂（factory）。

循环是一个智能体反复做同一件工作：收集上下文、采取行动、检查结果，然后再来一遍，直到满足某个条件。它是智能体工作的最小单位，之上的一切都只是循环叠着循环。

循环工程的要点在于：你不再一轮一轮地给智能体写提示，而是设计一个替你给它写提示的小系统。

驾驭框架是循环四周的围墙：它运行所在的沙箱、它能触及的工具、在多次运行之间留存的记忆，以及决定什么叫"完成"的关卡。循环是行为；驾驭框架是行为在其中运行的环境。

给一个裸模型而不配驾驭框架，它会乐此不疲地永远空转下去。驾驭框架就是它周围让它有用、且能安全运行的一切。

软件工厂是许多套着驾驭框架的循环同时运行，由一个工作队列供料，经过一道评审关卡排放到生产环境，而人类从上方掌管整个系统。它不是一个更大的智能体；它是一张由循环组成的组织架构图。

最终的范式转变，是从写代码转向构建和运营写代码的工厂。工作的单位上移了一层，变成了循环、驾驭框架以及它们之间的流转，而不再是单个代码 diff。

总的来说，这张图里的每个方框几乎都是零成本的：生成、测试、扫描。它们都能以可忽略的成本大规模运行。只有一个昂贵的方框顽固地抗拒规模化，那就是评审关卡。那个醒目的琥珀色方框就是"判断力"，而关于我们能否让开发更快、更频繁的争论，症结就在这里。

## 为什么叫"熄灯"

熄灯工厂在物理意义上关着灯运行，因为车间里只有机器，而机器不需要光就能看见。熄灯软件工厂是同样的做法：交付的代码没有任何人读过，只由其他机器验证。

这个意象借自制造业。它的起源是物理的而非数字的，扎根于那些关着灯、由机器人完成工作的设施。日本的发那科（FANUC）自 2001 年起就在运营这类无人化工厂；小米在 2024 年也开设了自己的高度自动化黑灯工厂。它们的共同点是：产品在组装和出厂过程中，没有任何一个人"读"过它。当"阅读"这一行为被从流程中移除时，"熄灯"就出现了。

我借用这个概念，并不是为了营造氛围，也不是为了贬损。尽管它听起来有点瘆人，但这里的"熄灯"只是一个简单的物理陈述：原来的工厂车间，只是没有了灯光。在软件里，车间就是 diff。写 diff 的人、评审它的人、交付它的人，这些人都不在了，剩下的只是一个仅由构建它的机器来验证的 diff。

这件事出人意料地容易做到，至少一开始是这样。之所以容易，是因为缺失的那个评审步骤原本处处碍事。它的缺席让你对团队纵向吞吐量的感知突然、大幅地提高。感觉就像突破了音障。可尽管看上去很容易，要在这些熄灯工作流及其所有隐藏成本中存活下来，比看上去难得多。

## 光有驾驭工程还不够

在模型与外部世界以及彼此交互的过程中，编排、沙箱原型和工具调用所构成的驾驭框架会变得越来越强大、有效。然而，在长期以及持续的增量变更中，试图维持代码库质量存在一种模型内在的失败，我认为有充分理由相信，单靠模型最终会输掉这场与理解债务的战斗。

理解债务是现存代码量与任何人仍然理解的代码量之间不断扩大的鸿沟。熄灯工厂不会偿还它；它会以最快的速度举债，而且一路上测试都是绿的。

这是一个重要的区分，因为模型在某些任务上做得很好。但对于任何不是对代码库一小部分做即时修改的事情，尤其是在复杂的存量（brownfield）系统中，纯模型的自动化编码会遇到无法逾越的障碍。周末玩具和业余项目的共同点是，几个月的开发周期通常就足以让东西正常运转，或者至少差不多。但一个已经开发了十年甚至更久的企业系统是另一回事；它必须在专业环境中、以专业的节奏得到维护。项目进行三到六个月时，你就已经淹没在没人读过的代码里了。那种环境，尤其是生产代码强加的约束，即使是强大的智能体也会表现不佳，这与做周末玩具的开发者所享受的氛围编程（vibe coding）形成鲜明对比。

Dex 根据亲身经验报告说，这是一次重大失败，严重到需要煞费苦心地手动调试才能找到问题所在。这来自他运行一个全自动代码工厂约四个月的经历，期间没有任何人看过写出来的代码。这段经历背后，是两个相互冲突的指标之间的权衡。一个是最大化 token 利用率，也就是我们目前当作进展的那个数字。另一个则被它悄悄地最小化了：在任何时刻，任何人类参与者仍然理解的系统部分有多少。

熄灯工厂真正的"长处"在于，它能在测试保持绿色的同时，把原本干净的代码消耗殆尽。最终的清算到来时，不会是戏剧性的"一切都乱套了"的时刻。它会来得悄无声息，而且很晚。

## 瓶颈从来不是生成

软件工厂的根本约束不在于我们能产出多少代码，而在于我们能多快地验证它。

背压（back pressure）是这样一条规则：你交给一个循环的自主权，只能与你能廉价且可靠地验证的程度相当，一寸也不能多。验证，而不是生成，才是工厂真正的约束。

由于无限的生成能力与有限、不可扩展的人类注意力资源之间存在永恒的张力，核心问题就是廉价生成与有限评审之间的差距。看看这个漏斗：只要代表验证的瓶颈口不变宽，它就会堵塞。正如 Dex 指出的，问题不只是数量：我们真正受困的是糟糕的 PR 过剩。当你有大量产出却没有可信的关卡时，制造出缺陷就是不可避免的。这又是背压：自主权不能超出能被廉价且可靠地验证的范围。

二阶问题在于，为什么改进模型并不会自动弥合它能生成的与能被验证的之间的差距。在架构良好的系统上进行训练，可以说比通过简单测试难得多：要记住，衡量架构优劣的代价函数不是以秒甚至分钟来度量的，而是以月和年。整洁的梯度在实际上无法计算，所以一个期待对复杂设计决策进行清晰、即时评估的系统，是不会在好的样例上得到训练的。

## 把灯重新打开

亮灯工厂是同一条流水线，只是在判断力所在之处把灯开着。智能体仍然承担大部分构建工作，但在交付之前有人会阅读产出的东西，而且在任何一个错误决定代价高昂的地方，灯都开着。

亮灯版本不是在末尾加上评审，而是把人类判断的位置前移，在智能体启动循环之前，放到产品、设计和架构上。

前期这一小时的一大好处是，它会减少实现所需的时间。它把一场漫长而令人沮丧的代码评审，变成快速读一份两百行的计划。你得以在决策被实现之前评审它，这样之后就不用在两千行生成的代码里追查当初到底做了什么决定。有些决策代价足够高、影响足够长远，你会希望在成本复利累积之前就有人尽早参与。当然，即便你在前期花了时间，仍然有需要看 diff 的时候。

你可能会觉得这一切听起来毫不光鲜。你说得对。这张安全网由一些再普通不过的架构实践构成，我们一直知道，却大多忽视了：良好的类型和方法签名，让错误被编译器而不是在生产环境中捕获；测试接缝（test seams），让我们能固定行为并使变更可观察；合理组织代码，让下一位读者——无论是人还是模型——知道去哪里找他们关心的东西；保持调用栈简短易读；保持组件边界定义清晰，使一次变更不会有巨大的波及范围；以及依赖注入，让我们能把一个部件换成另一个。这些都不新。我们一直说自己在乎良好的架构。但现在我们在用自动编码智能体，架构终于开始承担第二份工作：成为一张廉价而难以造假的安全网，兜住智能体会犯的错误。

这张安全网必须存在于模型之外，因为模型不会提供它。那些感觉最强大的编码智能体，包括 Claude Code 和 Codex，都是针对它们自己的驾驭框架和工具进行强化训练的：精通这一行的所有工具和惯用法，却不精通长期可维护性这类东西。我们一直挂在嘴边的刻意架构，正是捕获这种债务的工具，而我们在它上面的投入，就是在赎回我们的自主权。再加上安全的基础设施，就有一些紧凑、低风险的循环可以无人值守地运行。Horthy 在最近一篇文章中描述过一个：一个每晚运行的 GitHub Actions 定时任务，每次只修复一个反模式——一处 lint 违规或一个不必要的可选属性——然后提交并开一个小 PR，全部自动完成，于是团队醒来时看到的是一个稍微更好的代码库，以及一个短到可以读完的 diff。但对于风险足够高的循环，你可不想冒险醒来时发现认证系统、计费引擎或公共 API 契约坏了。在那些地方要把灯开着，相信一个有判断力、对系统有真实了解的人会发现错误。

## 什么样的循环配得上熄灯

无论你称之为背压、验证还是电灯开关，这条规则都适用。

一个循环只有在检查廉价、高频运行、并且依赖于难以被轻易糊弄的东西时，才能赢得完全自动化的地位。红绿判定的预言机（oracle）、类型关卡、属性测试，以及配有真正评分标准的评审智能体，都符合条件。你还需要预言机能立即给出答案，并且不会随时间漂移。当"完成"不仅能由你、还能由机器来证明时，你就实现了自动化。

短循环比长循环更容易验证。Dex 的经验法则是：一个智能体能坚持三到十步，超过二十步就开始失去头绪。原因是上下文累积，智能体拖着的东西越多，就越可能跑偏。循环短时，验证它就很廉价。冗长的循环把错误藏在角落里，换句话说，它们从来就没有赢得熄灯的资格。

保持亮灯则是相反的情况。如果错误答案代价高昂、且只有人能发现，那么这个循环就需要评审。测试抓不到的微妙生产 bug、巨大的波及范围、将影响一年或更长时间工作的决策，都属于这一类。在这些情况下，人类判断不会离开软件；你的注意力是那个昂贵而不可或缺的部分。

危险在于忘了逐个拨动开关，而是把它们全都设成同一种模式。全部熄灯，你四个月后就只能推倒重来。全部亮灯，没人能及时完成评审，你就会困在一个巨大的瓶颈里。真正困难、需要技巧的工作，是决定每个开关放在哪里。

## 循环、图还是状态机？

当你把一个任务交给智能体时，你很可能会围绕它构建一张图，无论你把这张图称为有限状态机，还是一组按条件串联的服务调用。在这种框架下，软件不只是遵循某些抽象规则，而是一个结构化的工作流：每个节点是一个明确的步骤，节点之间的每条边是一个明确的条件。这听起来结构很多，但其中大部分在任何软件里本来就有，因为任何代码都可以表示为控制流图。所以唯一真正的新意在于，一个坚持自主的智能体其实只是在某张特定的图上走动，它的自由被限制在节点内部。而人们忘记的部分，Dex 一年前就写下来了：软件本来就会有这种结构。我们过去把程序画成流程图是有原因的。真正新的做法，是试图把图扔掉，依赖一个由模型逐次工具调用自己选择路径、直到宣布完成的循环。那感觉像是一种解放，直到它遇上一个十年历史的代码库；而现在大家都在重新发现的那门纪律——掌控你的控制流——其实只是把循环重新绕回到图上。所以，"我们是否应该从循环转回图"这个问题，几乎等于承认我们一直都需要流程图。

下面是实践中的样子。拿一个要修的 bug 来说。作为纯循环，你坐下来思考：弄清楚哪里出了问题，改一些代码，跑测试，看看结果，如果这一轮没有让运行失败，就绕回去重新开始。整个旅程都是边走边定的：追哪个问题、改哪些代码、跑哪些测试以及按什么顺序、到底跑不跑测试、是再试一次还是宣布胜利。作为图，你做的第一件事是规划应该发生什么。复现 bug 或去要更多信息，找到原因，尝试修复，跑测试，失败的运行路由回修复步骤，通过的则进入评审，只有获得批准才能到达"完成"。智能体在每个方框内部仍然很聪明；它只是不能偏离你批准的路径。Santi 用一张图把这一点画了出来，差别一目了然。

当然，这张图真正的吸引力在于，它是画成图的背压。你放弃了智能体的一部分自由，换来强制性的检查和清晰可辨的失败点，于是当一次运行失败时，你可以指出是哪个节点导致的。这与 Dex 那句直白的话背后是同一种直觉：大多数所谓的智能体其实根本没那么"智能体"，"大部分是确定性代码，只在恰当的位置撒上一些 LLM 步骤"。而且这不仅仅是人们当下恰好这样构建东西的产物：你可以在 LangGraph 和 LlamaIndex Workflows 中看到这种模式，在 Jerry Liu 那种在智能体之上叠加工作流图、并由外层循环在运行中扩展图的局部的混合方案中看到，也可以在 David Khourshid 的提醒中看到：这其实只是状态机和 Actor 模型换了身新衣服。

有一点需要澄清，因为这个术语被严重滥用了：我一直称之为图，并不是指知识图谱。我指的是一张预先定义好的、描述工作应当如何流转的有向图，包括条件边在内，它给循环一个你真正可以信任的形状。

## 人究竟去了哪里

注意，人从来没有离开工厂。他们只是换了位置。

我认为工程师需要越来越多地掌控外层循环。智能体可以调查 bug、写出诊断、实现修复、跑测试、写报告。那是内层循环的执行，它们能做得和任何人一样高效。但那从来就不是这份工作的本质。你掌控的部分，是我所说的外层循环：判断这是不是解决问题的正确方式，核实诊断和实现是否可靠，批准变更，并承担出错的后果。两个循环之间的边界是证据：diff、测试、日志，以及把它们联系起来的简短说明。类型、接缝和评分标准，使你无需为每次变更做大量工作就能监督这一切。

我觉得这样说很有用：你不再待在生产线上写变更了；你在生产线的尽头，设计它、守住关卡。要让模型更好、让驾驭框架更强，你能做的事有很多，但我观察到，识别那些长期代价高昂的问题，通常不是你能自动化掉的东西。仍然属于这份工作核心的，是比任何文书流程和计算能力都更好地运用人的判断力。

机器人在黑暗中运转没问题，但人需要看见自己在做什么。如果工厂车间里一片漆黑，你什么也看不见，甚至连电灯开关都找不到，那才是危险所在。
