【开场介绍】TypeScript 是一门构建在 JavaScript 之上的编程语言，它为 JavaScript 加上了一套类型系统。借助这些类型，开发者可以描述数据的结构，在代码运行之前就发现错误；同时，类型也支撑着如今许多开发者每天都离不开的自动补全和编辑器工具。

TypeScript 于 2012 年首次发布，此后成为 Web 开发中使用最广泛的工具之一。最近，随着 7.0 版本的发布，TypeScript 经历了其历史上最重大的变革之一。Daniel Rosenwasser 是微软 TypeScript 的首席产品经理，他在 TypeScript 1.0 发布后仅几周就以工程师身份加入了团队。本期节目中，Daniel 和 Josh Goldberg 一起聊 TypeScript 7 的新特性，讨论 TypeScript 团队做工具的思路、TypeScript 与 JavaScript 背后的 TC39 标准化流程之间的关系、新的 API 与 IPC 边界、大语言模型可能如何重塑类型检查和代码检查（lint），等等。

本期主持人 Josh Goldberg 是一位独立的全职开源开发者，主要参与 TypeScript 生态中的项目，最知名的是 typescript-eslint——一套强大的 JavaScript 和 TypeScript 静态分析工具。他也是 O'Reilly 出版的《Learning TypeScript》一书的作者、微软开发者技术方向的 MVP，以及 Squiggle Conf（一个专注于优秀 Web 开发者工具的大会）的联合创始人。可以在 Bluesky、Mastodon 以及 joshuakgoldberg.com 上找到他，用户名都是 Joshua K Goldberg。

Josh：今天和我一起的是微软 TypeScript 首席产品经理 Daniel Rosenwasser。Daniel，欢迎来到 Software Engineering Daily。

Daniel：非常感谢邀请我，Josh，很高兴今天和你聊。

Josh：是啊，我们都很期待你来，我自己也盼了很久。TypeScript 现在有很多很酷的事情，既有最近的几个版本，也有接下来的工作。不过在我们一头扎进这个奇妙世界之前，Daniel，你是怎么进入技术行业的？

Daniel：怎么进入技术行业……我觉得这对很多人来说都是一个很常见的故事吧：玩电子游戏之类的，然后对各种东西、它们是怎么运作的越来越好奇，心想也许我也能做这个、做那个。但对我来说有意思的地方在于——具体说编程的话——我很大程度上是通过互联网那种有点诡异的氛围入门的：在论坛上认识一些素不相识的人。那时候我可能年纪太小了，不太适合混电子游戏论坛，大概十岁、十一岁吧。我在上面认识了世界各地的陌生人，后来发现他们也就十五、六、七岁，而且自己在运营论坛。我当时就想：等一下，你们是一群青少年，在运营一个网站？这居然是可能的？怎么做到的？

于是我自然是好奇心占了上风，就问他们：我要从哪里开始学这些东西？他们说：嗯，有个东西叫 HTML，你可以用 GeoCities 之类的网站来做各种试验。所以我早期做的很多东西就是在家里的电脑上瞎折腾，用各种方式把它搞坏——我相信很多人都干过这种事。但同时也在创造一些东西，并且意识到：哇，哪怕是最基础的 HTML 也有这么大的威力。你还能给朋友搞点小恶作剧，比如往一个页面里塞一千个 alert 弹窗。那还是 IE6 的年代，你没法直接选“不再显示弹窗”，只能一个一个忍着点完。

后来我慢慢对其他编程语言也产生了兴趣。我身后的书架上其实还有那本书——《编程入门 For Dummies》，因为，嗯，那就是我。我通过它学了 QBasic，非常好玩。当时那已经是有点过时的环境了：那是 2000 年代初，而 QBasic 大概是 80 年代末、90 年代初的东西，但它就附在 Windows 98 的光盘里。从那以后我还探索了其他东西，比如我想学怎么搭网站，于是学了 PHP，在 Apache 服务器上搭站，走了一整套 WAMP 栈，然后又是 LAMP 栈，学 Linux。我还学了 C++，当时我并不知道它会比我想象的更难懂。之后就是比较典型的路线了：高中上计算机科学的 AP 课程，然后是常规的从大学到工业界的路径。

Josh：那你是怎么从折腾 LAMP 栈走到微软的？看起来跨度有点大。

Daniel：我觉得我一直对自己所用的电脑的每一个部分是怎么运作的有天然的好奇心，我对它的每个部分都非常着迷：操作系统是怎么工作的，这一切是怎么工作的。我不知道你的问题里是不是有这层意思，比如“这个家伙开始钻研非常底层的操作系统的东西了”。但我一直对外面各种各样的技术都很兴奋，我会去尝试 C# 和 Visual Studio 之类的东西，我就是特别喜欢折腾。我尤其对底层的东西感兴趣，因为总有一个“好吧，那它又是怎么工作的？”的问题——你可以一层一层剥掉抽象，去了解内部原理。比如说，你的电脑能计时，但它是怎么做到的？这个可能是我比较近期才琢磨的。还有各种抽象，CPU 到底是怎么运作的，系统调用又是怎么工作的，等等等等。同时编程语言对我来说也非常迷人。

所以我陆续尝试了各种语言。大学里有那么一群人，我们有一阵子都在搞函数式编程，而那一整群人后来也都多修了一些课，比如编译器构造课、程序语言理论课。我的兴趣在这里交汇了，我非常确定自己想做开发者工具。而在我看来，做开发者工具的公司可能就那么一小撮，微软是其中让我印象特别深的一家。于是我通过实习项目申请进去，结果被分到了 Azure 的某个部门。这在当时让我有点害怕，因为在大学学过的所有内容里，网络大概是我最弱的一门——我的教授在他自己的课上都快睡着了，那是一段有点奇怪的经历。所以我完全没有自信自己懂那方面的东西。但我记得我实习时的招聘经理跟我说：这个暑假你不做开发者工具，并不意味着将来没有可能。说到底，想去微软的其他部门，最好的办法就是先进微软。所以后来我不停地烦我的实习协调人，一直说“我真的很想做开发者工具”。老实说，我觉得当时争着去做开发者工具的人并不多。这一点总让我很震惊：确实有一类特定性格的人特别迷这些东西，而每次发现有人不迷的时候我都很惊讶——那是因为我属于前一类人。

Josh：这挺有意思的。开发者每天都在用这些工具，你越会用这些工具、越理解它们，你用它们做出来的东西就越高效。那么跟我们讲讲，你和 TypeScript 团队、以及你身边所有做开发者工具的人，共有的那种心态是什么？

Daniel：我差点想回答“这是为了精进手艺”之类的。确实有一点这个成分，但还有大量的共情在驱动决策。你知道作为一个开发者你在追求什么，你自己踩过所有那些坑，你理解别人想完成什么，这会真正驱动你去为自己、也为别人把东西做得更好，因为你知道你能给别人的日常体验带来多大的改善。

在 TypeScript 团队早期，有一个功能是关于语法着色的。我们有好几层着色机制，这样就能尽快把代码着上色，然后再事后补上更完整的颜色，而且这个过程很难被察觉。当时有一个较老版本的 Visual Studio 只支持其中一种着色模式、一个层级之类的。我非常非常努力地想为它也实现一版着色，就是因为我知道，如果开发者还在用早一个版本的 Visual Studio，能有更好的语法高亮会让他们开心得多。我知道没有的话对大家来说有多扫兴，会让很多开发者多么沮丧。所以我觉得说实话，很大一部分就是共情。

我真心觉得在很多方面我都很幸运，进了这个团队。刚开始在 TypeScript 团队一起共事的人在这些事情上的心态都非常好：他们真的对开发者有共情，有一种追求卓越的劲头。这么说可能在时间线上跳得有点多，但我其实一开始是以开发者身份加入团队的，那是我大学毕业后第一份真正的全职工作，TypeScript 大概在三四周前刚发布了 1.0。我进去的时候，大问题是：我们接下来要做什么？我真的不知道目标是什么。我在大学时听说过 TypeScript，有很多怀疑。我觉得这是个好主意，但作为一个不在微软工作的局外人，看到微软试图推出一门面向 JavaScript 的、开源的编程语言，我当时非常怀疑。这完全不是公司当时所处的状态。

Josh：你是说微软当时对开源的立场和政策？

Daniel：是的，有好几个方面。我觉得当时公司在开源上想往哪个方向走，存在很多不确定性。有几个很酷的项目是以“某种程度上算开源”的许可证发布的，但总有一种“嗯，我不太熟悉那个许可证，我不知道自己能不能真的用”的感觉。而且这些项目往往来自研究部门——这是我的感受。但我加入的时候，Roslyn 刚刚开源，TypeScript 刚到 1.0，VS Code 大概还要再过一年到一年半才作为产品正式公开发布。所以那是很早期的阶段，我觉得当时的开发者生态和现在大不一样。在我加入后的那些年里，开源成了公司开发的众多开发者工具和产品的默认选项。我不知道大家对这段历史有多熟悉，但早期有很多时候，人们甚至对我们团队抱有不信任，我们必须通过坚定地加倍坚持我们的立场、坚持我们的原则、全力推动我们认为正确的事，来证明很多人是错的。

Josh：我们之前在 Software Engineering Daily 有一期节目请了你一位很受爱戴的同事 Jake Bailey，非常棒的人。Jake 给我们讲了 TypeScript 的很多技术细节，也就是你们当时在做的东西：编译器、什么是 AST、它是怎么工作的。如果有人对这些细节好奇，我强烈推荐去听那一期。不过对你，我想换个方向，继续聊共情这个话题。你刚才讲到了在生态中的定位上的共情：当时微软确实需要证明，是的，他们能做出一个真正对 JavaScript 开发者有好处的开源项目，这是在处境层面上。但在技术层面上，TypeScript 当时还有一个问题没有解决，那就是 TypeScript 和 JavaScript 之间的关系。对于那些可能不在这个生态里工作、或者不太了解 TC39（这个我们后面可以展开）的人来说，TypeScript 和 JavaScript 是什么关系？为什么在 1.0 前后这件事那么难搞清楚？

Daniel：我说的话你们得打点折扣听，因为正如我说的，我是在 TypeScript 1.0 发布几周后才加入的。也许只是我一个人，也许是大家共同的经历：作为一个初级开发者，当时我在大量吸收信息，同时又并没有完全意识到正在发生的事情的所有细节，比如并不一定意识到我收到的某些邮件有多重要，我会想“这跟我有关系吗？我不知道，我大概还是专心去实现模板字符串什么的吧”。我觉得这在别人身上一定也很常见，如果不是的话，嘿，你们尽管笑话我好了。

不管怎样，回答你的问题：TypeScript 是一门构建在 JavaScript 之上的语言，它以所谓“类型”的形式给语言带来了各种扩展。类型是一种表达方式，用来说明“我的程序里流转的对象大概是这样的形状”：这些对象有这些特定的属性，其中一个是数字，一个是字符串，它们的拼写都是确定的。你可以在项目里加上这些类型，确保另一个程序能检查一遍，在你用错的时候告诉你。我们还能提供非常强大的编辑器集成，在你写代码的时候，我们可以预判你接下来要写某个特定名字的属性之类的。所以我们不仅能做校验，还能支撑编写体验，帮助你探索代码。所以某种意义上，TypeScript 就是带类型语法、带强大工具的 JavaScript。

在一门语言之上构建另一门语言，有一个挑战：内层的那门语言有它自己的一条发展轨道。它有自己的语言开发团队或者委员会，想往语言里加它们自己的特性。JavaScript 想加入特定的语法结构，而 TypeScript 基本上必须确保自己不会造成分歧问题。在早期，并不清楚 TypeScript 可以在多大程度上开发新特性：哪些特性必须忍住不做，哪些可以放开去做。TypeScript 早期的很多开发是基于和 TC39 的互动，基于对 class 会长什么样的早期设想。

Josh：确认一下，TC39 就是 JavaScript 的技术委员会，你现在也在里面，对吧？

Daniel：对，TC39，抱歉。TC39 是 JavaScript 的标准委员会。如果你去查，它会说自己是 ECMAScript 的标准委员会，因为有一大堆商标上的问题，而管理这份规范的机构 Ecma 的名字也就进了这门编程语言规范本身的名称里。TC39 大概一年开六次会吧，来自不同公司和组织的代表聚在一起，提出对语言的新增或修订，以改进语言，或者为实现者消除歧义——实现者通常就是浏览器里的引擎，或者是 Node.js、Deno、Bun 里运行的引擎。目标基本上就是让语言的改进在这些不同的引擎之间保持一致，这样你的代码就能以一致的方式在任何地方运行。TypeScript 在 TC39 也有代表，这让我们能很好地把握语言的走向，就我们能否提供良好的类型检查和编辑体验给出反馈——类型检查就是扫一遍你带类型的 JavaScript、告诉你哪里有错的那个过程。我们也可以就提案如何改进给出反馈，以避免某些容易踩的坑和陷阱。

在 TypeScript 早期，TypeScript 是在 class 语法真正标准化之前开发的，也是在模块标准化之前开发的。很多不同的东西是在被真正确定下来之前就在 TypeScript 里加上并实现了，所以 TypeScript 不得不好几次修改自己的实现，人们也因此不得不把代码重写好几次，才能在 TypeScript 后续版本里正常工作、编译成 JavaScript。

Josh：你后悔做装饰器吗？

Daniel：我不知道我会不会这么说。我觉得当我们回头看装饰器的时候……不。

Josh：那你能解释一下，为什么我刚才问的是个很烦人的问题吗？为什么我们在碰一个敏感话题？

Daniel：我还以为不会有刁钻问题呢——开玩笑的。装饰器是 ECMAScript，也就是 JavaScript 里的一个提案特性，它让你能做的关键事情，是对类以及类的各个部分进行某种程度的所谓元编程。比如你可以说：当你调用这个方法时，我其实想让你去调用另一个方法；这样你就能拦截方法的进入和退出，可以用别的功能替换某些成员，还可以把成员注册到某种框架里，让某些东西能被追踪，或者被依赖注入。用装饰器能做的事情有一大堆。你大概都见过，它们以 @ 符号开头，通常和类关联在一起。

在 TypeScript 早期，大约同一时间发生了几件事，那大概是 2014 年底。我们正在为 TypeScript 1.1 做一次重写，那其实是我作为团队工程师最早参与的事情之一。当时一个叫 Flow 的类型检查器开始登场，这是 Facebook 做的类型检查器，同样也是针对 JavaScript 的，不是随便哪个类型检查器。而 Angular 团队宣布了一个叫 AtScript 的项目。我们当时的口号、或者说我们当时描述 TypeScript 的一种说法，是“TypeScript 是 JavaScript 的超集”。AtScript 则是一个设想中的语言，它是 TypeScript 的超集：它有类型，但还加了一个叫“注解”（annotations）的东西。他们的想法是在下一个版本的 Angular 里使用注解，这样就能有一些工具以特定方式利用它们，进行优化。

当时有好几个人参与了这件事：我们团队的 Ron Buckton、Sophia Turner，以及团队里的其他人都深度参与了很多相关工作；还有 Yehuda Katz，他是从 Ember.js——另一个 JavaScript 框架——的角度来考虑这件事的。于是就有了一个问题：能不能有一个运行时版本，而不只是某个特殊编译器才能理解的东西？于是就有了装饰器提案。Angular 团队的计划其实是：好，有个装饰器，但我们只把它当作静态注解，会对它做些特殊处理，也许也会有个运行时实现，但作为最终用户你不用太操心，那不是我们希望你需要关心的东西。但它当年毕竟是一个 JavaScript 语言提案，于是 TypeScript 在某个时候实现了它。

我有点跳着讲了，抱歉，我没想到今天会聊装饰器。AtScript 宣布的时候，我们团队的 Sophia 其实主动联系了 Angular 团队，看有没有办法真正合作，弄清楚缺口在哪里。我觉得这又回到了我刚才说的那个时代背景：在开发者工具生态、在 JavaScript 生态里，人们并不怎么信任微软。所以当时这个来自谷歌、运营着一个开源 JavaScript 框架的团队，突然被我们说“嘿，我们能不能一起想想办法”，怎么说呢，也许他们就是不信任我们。等我们真的和他们见了面之后，我觉得他们看到了我们只是一群出于好意、想提供真正优秀的开发者工具的人，很多想象中的隔阂就消失了，大家都非常兴奋地想要合作。那之后，Yehuda 等做装饰器的人就更多地参与到流程中，我们把它带到了 TC39，不是作为我们的提案，但围绕装饰器有大量的来回讨论，比如：这个符号真的应该是 @ 吗？我们是不是该把它用在别的地方？我们能不能改一下它的运行时语义？这就是 TypeScript 早期的问题之一：不太清楚在 JavaScript 新特性到达某个阶段之前，自己可以提前多少去实现它们。

所以回过头看，你问装饰器有没有遗憾，我觉得你得看有多少人因为有了这个东西而变得更高效了。我们在某种程度上让 TypeScript 和 Angular 社区都壮大了很多，其他框架也能用上这个东西。我觉得我们现在处在一个有挑战的阶段：装饰器的方向存在一些不确定性，它们在过程中被重新设计过，有了新的语义、新的 API，所以理解委员会对此的想法有点难。但我们仍然参与其中，微软也有其他人在努力从内部框架和库收集反馈来理解这件事。

它确实改变了我们对 TypeScript 的定位。说到 TypeScript 实现哪些特性，我们的新政策——其实已经不新了，我们已经这么做很多年了——是：一旦某个特性在 ECMAScript 标准化流程中到达所谓的 Stage 3，我们就实现它。在这个流程中，一个特性到达 Stage 4 就正式成为下一版规范的一部分；Stage 3 则被称为给实现者的“可以开始实现”的信号，这对我们来说通常就足够了，所以我们在那个时候实现。除此之外，当我们想为类型、为真正有助于静态分析和工具层面的东西加新特性时，我们会去做，但仅限于所谓的“可擦除语法”（erasable syntax）：基本上就是可以脱离其他文件、单独编译的东西，所有的输出、所有 JavaScript 的生成都完全不由类型来驱动。理论上应该做到：你把所有特殊的类型语法剥掉，剩下的就是等价的、可读的 JavaScript。这就是我们今天的状态。这大大简化了我们和 JavaScript 标准化委员会的协作方式，也给了我们一条清晰的界线，哪些在我们的范围内、哪些不在。当某个东西不在我们的范围内而我们又非常认同它时，我们可以在 TC39 里担任这个特性的倡导者（champion）。

一个例子就是可选链（optional chaining）和空值合并（nullish coalescing），有时也被叫做“猫王运算符”（Elvis operator），因为其中一个写作问号加点，那个问号看起来像猫王的发型，加上两个点。这些特性让处理 undefined 和 null 变得更容易，其他语言里也有。这些特性最初不是我提出的，但我后来在 TC39 里积极地倡导它们。当时有很多声音说：要在委员会里把这个推动下来看起来非常难，某些地方有很多反对意见。但我觉得那是一个我们真正深入探索了问题空间的案例：我们真的和委员会里的每个人都聊过，努力收集反馈，努力理解大家的动机，非常尽心地去推动它。并不全是我一个人，倡导小组里还有其他人，帮忙做测试，帮忙对规范提反馈，都是非常棒的人。能看到我们来自不同公司的人一起创造出一个东西，让 JavaScript——不是 TypeScript，是 JavaScript 这门语言本身——因此变得更好，这真的很酷，而这也让 TypeScript 变得更好。

Josh：我想很多听众会惊喜地发现，我们不光在聊 TypeScript，有很多事情要归功于你和你的团队，比如 TypeScript 的性能——这个我们接下来聊——还有猫王运算符、空值合并和可选链，这些都是好东西，谢谢你们。

好，你已经描绘了 TypeScript 如何从微软内部诞生、变得非常开源，以及它与 JavaScript 社区和 JavaScript/ECMAScript 语言之间的关联。我们往后快进一点。我们之前也有一期节目讲过 Go 移植，但你能不能简单回顾一下，2026、2027 这段时间 TypeScript 过得怎么样？你们在忙什么？Go 移植进展如何？

Daniel：我们刚刚发布了 TypeScript 7，几周前发布的。对于不熟悉的人来说，这个版本非常特别，因为它完全不同了——好吧，要加个限定：它是一个不同的代码库。它用原生的 Go 代码重写了，这在很多代码库上通常带来了 10 倍的提速。我们实现这一点的方式是几方面的结合：一方面是移植本身，从用 TypeScript 写的编译器换成用 Go 写的编译器，通过 Go 代码获得原生速度的提升；另一方面是能够利用共享内存、并行和并发，真正充分利用所有核心和你拥有的所有线程能力，最大化吞吐量，尽可能快地完成工作。很多人可能都注意到了，至少过去二十年里，处理器大体上是核心数在增长，而不是主频在增长。随着硬件规模上去了，我们的程序常常没有利用上所有这些核心。所以现在我们有了一个新的编译器，可以解析你所有的文件、尽可能地把核心跑满，对很多人来说构建几乎是瞬间完成的。

这是一项非常大的工程，到目前为止我们大概做了至少一年半以上。这个过程让人非常兴奋，是我们做过的最有趣的事情之一。我前面提过，我刚当工程师的时候也参与过一次重写，而这次我们更多地称之为“移植”，因为我们基本上是屏幕左边一边、右边一边：一边是 TypeScript，另一边是我们要转换成的 Go，我们尽量让所有东西保持一一对应。这非常有意思，找各种办法让它超过 10 倍、变得更快，找其他能做的优化，也很有意思。这个版本反响非常好。我们很多人都非常希望确保这一点，因为当初开始做这件事的时候，这个决定对我们来说并不容易，所以团队里每个人都在努力坚持到底，确保它顺利完成，确保这对大家来说是一个好版本。

我们知道 TypeScript 7 的故事还没讲完，我们知道还有一些事情，比如提供 API 之类的。我们知道 TypeScript 和 JavaScript 生态中很大一部分人还在等 TypeScript 7 的下一步，这样他们才能在 Vue 文件、Angular 文件之类的地方获得 TypeScript 支持。但这个版本已经让很多人很开心了。就像我说的，提速是 10 倍——当然这取决于你的电脑、你的处理器等等——但微软内部有些团队的代码库极其庞大，他们在旧版 TypeScript 上经历了很多挫折，因为 TypeScript 6.0 及之前的版本是一个 JavaScript 代码库。我不知道你想让我讲多少我们决定做 TypeScript 7 的历史，但基本上，我们有一个用 TypeScript 写的编译器，就一个跑在 JavaScript 引擎上的带类型应用而言，它已经非常快了，但它终究被限制在单线程上。在非常大的代码库上，人们经常会遇到内存不足的问题，对于非常大的项目，往往要等好几分钟，项目才能在编辑器里加载完，然后才能做任何事。

Josh：我推荐听众去听 Jake Bailey 那一期，我们在那期里讲过这些，是很好的概览。

Daniel：谢谢。

Josh：不过我也想稍微深入一下你刚才说的那个领域。正如你在博客文章和其他视频里说过的，7.1 是会为集成方提供大量 API 集成的版本。API 有什么问题导致它需要推到 7.1？是什么让这成为一个难题？你们又在怎么和社区合作解决它？

Daniel：在 TypeScript 原来的版本里，我们开发 API 的方式之一就是有机生长，这是你写一个 TypeScript 或 JavaScript 库时很典型的做法：你有一堆函数和方法，理想情况下它们在结构上有坚实的基础，有一定的一致性，然后你会说：这个我觉得已经可以开放给别人了，因为别人想做的事情和我的应用内部想做的事情是一样的，或者他们需要同样的数据或者某些内部数据来做事。于是你得想出一些抽象，但要有纪律地做到这一点非常难。所以基本上就是有这么一套非常有机地生长出来的 API。

所以当我们转向 Go 的时候，在技术层面有几个大挑战。主要是：你现在是用 Go 写的了，到底要怎么让所有这些 JavaScript 库继续使用这些信息？再有，如果你想让其他应用也能使用你的数据呢？我的意思是，Node 生态的默认做法是“嘿，我提供一个 JS API”，但与我们同时，很多人还经历了一场原生工具的复兴，人们可能想用 Rust 写东西，也消费同样的数据。而我们选择了 Go 这门语言，在某些方面让这件事特别难，因为它有一个运行时，对于内存归谁所有、怎么拥有、为什么、在哪里，都有一套特定的预期。所以我们必须想出一个相对有纪律、我们能放心地以某种方式开放给 JavaScript 和其他消费者的东西。

所以基本上，我们最终做的是提供一个 IPC 边界，也就是进程间通信边界，放在我们的 API 之间。不是说你在我们的进程里看到和我们一样的所有数据，你实际上需要把东西传过来，并且在通过网络请求某些信息时要更有纪律一些，这样你就不会把地址空间里的内存用光，再把它们全部镜像一遍。我们选 Go 是因为它让移植容易得多，同时也能带来大量的速度提升。但无论我们选了哪门别的语言，我们都不希望语言选择成为一个暴露在“你如何从 TypeScript 编译器获取数据”这件事上的实现细节。所以我们想出了一个不管选什么语言都会是好方案的东西。

于是我们一直在开发的这套方案，对 JavaScript 消费者里的类型有一等公民级别的支持，但最终可以在任何语言中使用。我们也看到了其他一些消费者在用它。同时我们也看到有些人在过渡期不用这个 API，自己去做 linter 之类的东西。这是开源的，你也没法真的阻止别人，但我们也不一定会劝阻，因为我觉得看看这些东西会走向哪里是好事。看到很多工具借助这些东西可能走到的地方，真的非常有前景。我们非常致力于确保这里有一个好的方案，因为——我不知道能不能有把握地说是四分之一还是三分之一的用户——但肯定有一大批人在用嵌入式语言，也就是那种把 TypeScript 和 JavaScript 嵌入其中的模板语言。他们非常期待有好的 TypeScript 支持，无论是语言服务（LS）还是其他工具。显然你对这个领域非常熟悉，我相信你也在密切关注。但我们确实需要在那里提供扎实的体验。

Josh：作为参考，目前 lint 或者说 JavaScript 工具生态里最好笑的一点是，有第三门语言在参与：Rust。那个新兴的、非常快、高度集成的 linter Oxlint 是用 Rust 写的，但它的 TypeScript 集成是一个叫 tsgolint 的东西。我见过它的作者们用一些不雅的词来形容它是怎么伸手进 TypeScript 内部的，也用过“漂亮”“巧妙”这样的词。另外还有用 TypeScript 写的自定义规则。那么你觉得这个生态在接下来会不会趋于正常化、标准化，变得没那么离谱？
Daniel：这非常有意思。我不知道，我觉得对某些工具来说，采用那种做法也不是不可能。我们做这个 API 的一个期望，是尽量减少重复。所以我们有一个概念：多个客户端可以共享一个所谓的项目“会话”。基本上就是说，有好几个东西在用这个 API，它们都看到同一个视图，甚至可以接入你编辑器里正在用的那个视图，这样它们就不用在各自的进程里把同样的东西重新加载一遍。这是理想状态。对某些项目来说，自己留一份副本之类的也许也不是最坏的事：如果他们发现对某些人来说存在速度和内存之间的权衡，那也完全合理。但我们在设计时确实是把很多“当初希望能做到的事”放在心上的，也就是 TypeScript 6.0 时代那些“要是能支持多个客户端就太酷了”“要是能做这做那就太酷了”的想法。可在没有线程的情况下那是做不到的，不在内部大规模重做一堆东西、语言服务器又不是专门为此设计的情况下，那也是做不到的。我们在旧代码库的基础上做了大量架构改进，让事情简单了很多，甚至还提升了 TypeScript 7 的可靠性。这很酷，因为我们可以说：它不仅更好了，还更少崩溃。

Josh：在如今这个软件时代，听到这种话可真是难得。

Daniel：我们非常认真地确保从外部合作伙伴和公司那里获得了大量反馈，不只是我们和微软内部团队合作，而是我们一贯地加倍努力向外伸手，去了解外面的情况。

Josh：你谈到了会带来新 API 的 TypeScript 7.1，可以想见 7.2 也会在此基础上有所补充。在最后五到十分钟的技术讨论里，我想聊聊 7.3，甚至是更远的 8.0。假设你们已经搞定了 linter 的方案，搞定了 Astro 这类嵌入式语言的方案，所有这些都已经标准化、正常化了，那个生态在你看来是什么样的？等这一切都解决之后，作为一个只想好好写点 TypeScript 的人，会是什么感受？

Daniel：哇，这是个大问题。我觉得要准确知道我们会落到哪里，实在太难了。8.0 一般离 7.0 大概两年半，要确切知道到时候我们在哪……我们通常没有那种两年半的计划。我可以告诉你我们在这方面的几个大问号。当然很大一部分是开发实践的变化。显而易见、房间里的大象是：除了现在编辑器里各种优秀而强大的工具之外，我们还有了大语言模型这样的模型，在很多情况下它们能生成第一次就高度正确的代码。

所以我经常做的一个思想实验是：这对表达力和冗长程度之间的权衡意味着什么？或者对你能强制执行的那些规则意味着什么？在编程语言里，存在所谓“可靠性”（soundness）和“完备性”（completeness）之间的权衡。我稍微极客一下：基本上，你常常会通过更“可靠”来捕获某一类 bug，但代价是，为了表达某个操作其实没问题，你往往要牺牲完备性——或者说你需要提供表达力来传达这一点，往往就是“我得想办法告诉检查器或编译器这个东西是没问题的”。所以一个想法是：我们是否要找更多办法，让类型检查更彻底？我们有没有某些缺口可以补上？另一面是，这在某种程度上是好事，但常常有些地方你其实想检查的是更临时性的东西：更特定于你的公司或团队的东西，或者你的代码库特有的某类 bug。我相信你脑子里已经亮灯了：嘿，那些不就是 lint 规则吗？

Josh：没错。

Daniel：所以确实有一个问题：语言模型是不是非常适合即时创建新的 lint 规则？比如你团队里有人说“要是能写条 lint 规则做这个做那个就太酷了”，确实很酷，但你还有别的事要做，除非你那位队友被这个想法深深吸引——被“书呆子狙击”了——否则它就是不会发生。而这些事情现在变得触手可及多了。所以很有可能随着时间推移，API 会变得更加重要，让我们能支撑起那个生态，也许我们的工具里会有更多集成来解锁这些能力。

但我们的视野里也总有很多其他事情：总有新的 JavaScript 特性，总有 Node.js 和其他运行时新增的功能需要我们去实现。还有很多“有了会很好”的东西。比如人们在 TypeScript 里用各种奇怪的办法做元编程，说：嘿，我想能在 TypeScript 里拆分字符串字面量类型的名字或内容——字面量类型就是描述一个字符串具体内容的类型，我们的类型系统就是这么强大。要是有一种不那么取巧的拆分字符串的方式，不是很酷吗？有很多改善生活质量的东西我们一直搁置着，因为过去一年半我们一直在努力把东西做得尽可能快。那是一个有风险的权衡，但我觉得它越来越明显地显出前景了。

Josh：我很好奇，有没有什么类型或者类型特性，比如依赖类型、否定类型等等——你可以先给听众定义一下——因为 TypeScript 7 的性能提升，现在可能变得可行、也可能仍然不可行？

Daniel：一个明显的、我们出于性能原因拒绝过的特性，是对方法里 this 的更严格的类型。当你在类上定义一个方法时，我们曾有过一个严格模式选项，说：不不不，你永远不能在不以某种方式重新绑定的情况下“孤立”这个方法，除非你显式……

Josh：你得给大家定义一下“孤立一个方法”是什么意思。

Daniel：对。基本上你可以从一个对象上拿到某个方法的引用。JavaScript 里的每个方法，或者说大多数函数——这里坑太多了——在被调用时都隐式地带有一个叫 this 的值。当你把函数作为对象上的方法来调用，比如 object.myMethod()，this 基本上就被绑定为点号左边的那个东西，也就是通常所说的接收者对象。如果你只是拿到这个方法的引用然后直接调用它，点号左边没有对象，压根就没有点号，你就会得到 undefined；然后如果方法里访问了 this，你就会得到一个报错，说 undefined 不是一个有效的对象之类的。我们出于性能原因没有做这个，而且从用户体验来说它也有点痛苦，所以我们有可能重新考虑。

否定类型的话，其实最近一两周团队里又提起来了，有人在做实验。我觉得那里也有一些性能方面的特点，但我们一开始拒绝的很多东西，主要是因为用户体验上的故事有点太复杂。比如你说“我有一个非数字”，这就是否定类型：你说我接受任何不是数字的东西。这很奇怪，因为如果你真要较真，去看看所谓的构造主义逻辑，就会有一整套讨论：这个东西不描述一个数字，那什么东西不描述数字呢？字符串当然是，它们是不相交的集合，真正不相交。但还有很多东西从技术上讲也“不是数字”。比如你有一个 unknown 类型的东西，它涵盖了类型系统里所有可能的对象。那你能把一个 unknown 赋给“非数字”吗？不能，因为从技术上讲数字也是 unknown，所以你必须拒绝。好吧，也许对这些特定类型来说还行，你直接说这些不合法就好了，但一旦开始讨论对象类型，事情就变得非常棘手。我很喜欢类型系统里的很多东西，喜欢它的代数性质，如果我有块白板之类的，我们可以讨论一下，可以真正展示出它是怎么变得非常纠缠的：既从数学角度不太说得通，从类型系统角度也很难推理。但如果我们再多下点功夫，也许能找到一个对人们仍然有用、只是在某些例子上有点复杂的东西。所以我不知道，这其实没有完全回答你关于性能的问题，但这些是我们一直在讨论的一些东西。

Josh：我觉得你回答得很对，你回答的是那个正确的问题。很多时候，要不要把这些东西加进类型系统，并不是性能问题。听起来即使性能没问题，它的复杂度也高得离谱，也许让用户能表达这些东西根本不值得。也许更好的投入是更深入的大语言模型集成、整体性能，就是让它对人和工具都更好用。

Daniel：是的。我确实觉得，如果你回头看，很多年前有一篇文章或者说博客，以前托管在微软的博客上，大意是每个特性都从负 100 分起步。今天依然如此。你真的得为某个东西进入语言给出充分理由，因为现在每个人都得开始考虑这个特性。你很少能说“我们有这个语言特性，但它是按需付费的，别担心，它不会出现在你面前”。它会出现在人们面前，他们得去想它，他们得知道自己是不是需要了解它，这可能会让人沮丧。也许有了大语言模型会好一些，我觉得还得再看看。在我和其他编程语言设计者的每一次讨论中，感觉我们今天对语言的所有顾虑，同样适用于这些模型：复杂度、熟悉度，要在这些不同的考量之间取得平衡。

Daniel：我觉得如果你已经在用 TypeScript 6.0，并且没有使用任何编辑器集成、语言插件之类的东西，比如你现在没在用 Vue、Angular 这类框架，那么你很可能今天就可以直接开始跑 TypeScript 7。你可以先安装 TypeScript 7 的扩展，比如在 VS Code 里，或者查查你喜欢的编辑器的支持情况，你马上就会拥有一个加载项目快得多的东西。所以今天就该试试。即使你在用 API 之类的，比如你用的 VS Code 里的 TypeScript 仍然和 TypeScript 6 集成，你也可以把两者并排使用，我们的博客文章里有明确的文档说明怎么做，去看看吧。

在此期间，我觉得可以关注一下我们在 GitHub 上为 API 集成方开设的一些讨论帖。我们正在和各个库和框架团队合作，努力确保 TypeScript 7.1 会有一个扎实的方案。他们往往已经有了一些原型，比如构建和编辑器集成，已经能跑了，那里有一大堆很酷的东西。我记得最近参与 ts-loader 工作的 Johnny Reilly 让 TypeScript 7 跑在了 webpack 上，这非常酷——所以即使你在用 webpack，也可以通过我们现在开放的一些早期 API 开始用 TypeScript 7。当然，这些需要 TypeScript 的 nightly 版本，但我觉得非常有前景。所以我想我的推荐就是：去试试新编译器吧，它快得多，而且比你以为的更成熟。我们已经从非常多的团队那里听说，这个东西对他们的日常生产力来说简直是救命稻草。我们和 Slack 的人、Vanta 的人以及很多很多公司合作过，有整家公司已经在用 TypeScript 7 了。所以，试试看。
