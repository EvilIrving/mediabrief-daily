Scott：欢迎收听 Syntax，这里是周一的 Hasty Treat（短节目）。今天我们要聊 node_modules——为什么每个项目里都躺着这么一个庞然大物一样的 node_modules 文件夹？我是来自丹佛的开发者 Scott Tolinski，和往常一样，和我一起的是 Wes Bos，node_modules 大佬。

Wes：是的。在 Web 开发圈里，node_modules 体积巨大几乎成了一个梗。只要有人提到用 JavaScript 干活，就会有人说"哦，那玩意儿可大了"，还有那张"地球上最重的东西"的梗图，node_modules 排在最重的位置。这就跟"CSS 里怎么居中"一样是个老梗。我看了也会笑，但另一方面我想说：你最终的 JavaScript 其实并不会那么大。node_modules 里的绝大部分东西——我甚至可以说几乎全部——都不是真正会进入你的打包产物或者运行时的 JavaScript。

所以我想不如做一期节目，聊聊里面到底装了什么、为什么这么大。大家很喜欢吐槽它大，确实也有一些可以改进的问题，但里面有很多东西是为了让你的开发环境顺畅简单，并确保能在旧版本的 Node 上运行。

那我们开始吧。先剧透一下：答案是文本。文本出乎意料地大，尤其是涉及描述信息和 polyfill 的时候。我最近正在做 Syntax 的逐字稿，我们为每一个单词都标注了起止时间，有些文件大到好几兆。我当时就想，这没法在网站上加载啊，太大了。但它用 gzip 压缩效果非常好——gzip 是服务器可以发送、浏览器可以解压的压缩算法——压缩后大概小了一百倍。我还得再精简一下，不过 gzip 之后大概只有 300K 左右。因为每个单词都带着同样的 "start" 和 "end" 这两个 JSON 键，哪怕出现了六千次，压缩后实际上也只需要传一次。

Scott：对。有一个常见的例子能说明文本到底能有多大，那就是日志文件。我们都遇到过：日志文件一直写、一直写，结果硬盘满了，你还在纳闷空间都去哪了，最后发现全是往日志文件里写的文本。所以归根结底，只要是存在文件里的东西，越大就越占空间，最后可能占掉非常多。并不需要有什么多媒体文件才会出现超大的文件。

Wes：如果你用过 DaisyDisk 之类的工具，就会明白。

Scott：我超爱 DaisyDisk。如果你是 Mac 用户，DaisyDisk 非常棒，我相信 Windows 上也有类似的东西。它是一个可视化工具，显示你所有文件夹有多大，然后你可以一层层点进去，看硬盘空间到底被什么占用了。用过这类工具的人马上就会看到，自己的缓存 node_modules 和各个项目的 node_modules 文件夹在硬盘上到底有多大。它们确实占了很多空间，这也是我们通常不把它们提交到 GitHub 之类地方的原因之一。反正每次运行 npm install 都能自动重新生成。

Wes：为了准备这期节目，我专门做了点研究。我打开了几个项目：一个是 Boss Monster，也就是我的课程平台，我把它后端的整个 node_modules 拖进去看了，又把前端（React 应用）的 node_modules 也放进去，还有其他几个项目，然后逐一看：到底是什么大？是从哪来的？

第一类是源文件。有人往 npm 发布东西时，一般会先过一遍打包工具。你当然可以直接发布纯 JavaScript 到 npm，但很多人是用 TypeScript 写的，或者用 ESM 写的但想同时提供一个 CommonJS 版本，又或者有人用 CoffeeScript 写的，需要转译成 JavaScript。所以一般发布的是构建后的版本，但很多人并没有把源文件从发布包里去掉——可能是因为他们希望能被引用，你可以在 node_modules 里翻到真正的源码；也可能是因为大家不知道有个叫 .npmignore 的文件可以把它们排除掉。我自己也发布过几个这样的模块：我在 GitHub 的 README 里放了几张截图，大概 400K，结果它们被打进了发布包里。这完全没必要，因为不可能有人需要在自己的 node_modules 文件夹里看 README 里的截图。那可就是半兆了。乘以一千个 node 模块，每个人都不小心多塞个 200K，加起来就很可观了。我们见过好几个 G 的 node_modules 文件夹。所以如果你硬盘空间不够了，这里是个找空间的好地方，看看里面都有些什么——尤其是你用户目录下某处存放缓存模块的那个文件夹，可能会变得相当大。

Scott：我个人在使用第三方包时，非常喜欢能直接看到它的源代码，以便更深入地理解它，因为不是所有文档都写得很好。不仅如此，能读源代码确实让我成为更好的开发者。能读我正在用的东西的源码——尤其是组件，比如引入一个 Svelte 组件——能钻进去看看这个组件在底层到底长什么样，能让你更理解它的实现，以及该如何正确使用它。

Wes：（玩笑）我们做过统计，我搜了一下，我们在四分之一的节目里都说过"under the hood（在底层）"这个词。

Scott：确实相当可观。

Wes：下一类是类型定义。这一块其实很大。比如 AWS SDK——我的一个项目里装了 AWS 的 SDK，光类型定义就有 14 兆。你希望你的 TypeScript 开箱即用。这可能是个特例，因为 AWS SDK 是一个单独的包，而 AWS 有无数个服务。我当时只需要转录服务的那个包，但你装的却是整个 SDK。这些类型文件仍然会被 VS Code 用来给你提供很好的智能提示。

然后是 source map（源码映射）。source map 里面就像是一整份全是分号的文档，占了很多空间。source map 真的挺离谱的，如果你打开看过一个，就知道是怎么回事。有人专门解释过 source map 里那些分号是干什么用的，我回头找一下那条推文的链接。总之 source map 文件是文本，如果你想要更好的调试体验，就必须把它们一起发布。

接下来是 polyfill。即使你运行的是最新版本的 Node，很多包仍然会把 core-js 作为依赖，你 npm install 的时候它就跟着进来了。不是每个包都这样，但 core-js 是 npm 上最流行的模块之一。我们去 npm 上看一下它……（用 Raycast）我输入包名，它就直接带我到 npm 页面了。

Scott：我喜欢这个。这是扩展还是你自己写的？

Wes：不是，是现成的扩展，直接装就行。

Scott：哦对。

Wes：还有 Bundlephobia，它能显示一个 npm 包有多大，跟这期节目挺相关的，我们可以放个链接。

Scott：我自己调试要发布的东西时经常用 Bundlephobia，看看它实际有多大，或者我到底给用户发了些什么。说到 Raycast，顺便提一句：我不小心在 Raycast 里设置了一个文本片段，没想到 "sc" 会自动补全成我的邮箱。现在我只要打带 "sc" 的单词，它就会自动补全成我的邮箱，把我气得够呛。我马上就去删掉它。

Wes：我所有的文本扩展都用冒号做前缀。

Scott：哦，这招——你怎么这么聪明？

Wes：我这么做大概有十年了，非常好用，因为极少会碰到意外触发展开的奇怪情况。就是冒号加上缩写，我所有的扩展都带这个前缀。你也可以用别的，比如加号之类的，但我用冒号。

Scott：冒号确实很好。

Wes：我还有一个是 cc，用来输入 Braintree 和 Stripe 的测试信用卡号。

Scott：哦天哪，冒号 cc。让我说说我在 BetterTouchTool 里做的东西。BetterTouchTool 可以让你编排一连串动作。我设了一个：按 Hyper+S，它会粘贴 Stripe 的测试信用卡号 4242 4242……，按 Tab，粘贴月份和年份的有效期，按 Tab，粘贴 CVV，按两次 Tab，填入邮编，再按 Tab 然后回车提交。如果你在测试 Stripe，那种流程简直是噩梦，你得一遍又一遍地填。

Wes：回到 polyfill：还有 Babel。几乎每个 node_modules 里都有的 Babel 插件，每一个都包含大约 8K 的代码，却有将近 860K 的类型定义。我没完全搞明白原因，我猜是因为每个 Babel 插件都带上了其他所有 Babel 插件的类型。总之每个 Babel 插件里都有将近一兆的类型。而一个项目里可能有 20、30、40 个 Babel 插件，那轻轻松松就是 30 兆，每次安装都加到你的项目里。

Scott：这可真不少，我之前完全没意识到。

Wes：我也没有。所以我才喜欢 DaisyDisk，直接拖进去就能看到："哇，我都不知道这东西在这里。"因为你几乎从来不会去看实际发布出去的内容。你在 GitHub 上看到的，并不是实际发布到 npm 上的东西。现在 npm 终于有了个功能，你可以点开一个标签页查看代码，看看里面有什么，它也会告诉你各个东西在哪，但做得不太好，我真希望它能更好一点。

Scott：是啊。而且我们现在生活在一个同时存在 ESM（ECMAScript 模块）和 CJS（CommonJS）的世界里，它们并不总是那么兼容。

Wes：对，这就是生态现状，你得让包在两种模式下都能用，所以每个包实际上发布了两个版本，有时甚至是三个版本。

Scott：三个版本是出于什么原因？

Wes：我想可能是一个浏览器版本、一个 Node 的 ESM 版本、一个 Node 的 CommonJS 版本。有时候甚至还有一个可以直接用 script 标签引入的版本。挺疯狂的。

下一类是 Markdown，同样占了不少空间。我打开了 Boss Monster 播放器的那个 React 项目，搜索了所有 Markdown 文件，加起来一共 10 兆的 Markdown。里面有许可证——开源代码必须附带许可证，这算是规矩吧，你不能把它们删掉，许可证规定了你可以分发代码或者链接回代码，所以许可证必须一起带着。还有每一处改动都记录在案的变更日志、README，这些全都有。

Scott：这也很可观。

Wes：是的。还有字符串，光是字符串本身就很多。比如 TypeScript 自带了它被翻译成的所有语言。

Scott：哇，我发现我一直在想：哇，这些都很可观。所有这些在任何时候都不是我们实际在用的代码的东西，干脆全扔了得了。

Wes：是啊。你装 TypeScript 的时候，不会想"哦我现在装 TypeScript，顺便把它的中文翻译也装上吧"。它就是得开箱即用，所以每一个安装 TypeScript 的人都会得到它被翻译过的每一种语言。这些东西单个都不算大，翻译文件几乎可以忽略不计，但加起来就多了。

Scott：说到这些，倒让人好奇：pnpm 或者其他安装工具能不能提供某种配置选项，把特定的东西删掉？当然，这听起来是个挺棘手的事。但想象一下，如果有个包安装器能自动删除所有 changelog、README 或许可证文件；如果你是 ESM 项目，就自动删掉 CJS 版本；自动删掉我们今天聊到的那些你可能用不上的小东西。我觉得那样你运行一下就能自动清掉这些文件。

Wes：首先，放轻松，这并不是什么大不了的事。

Scott：对，确实。

Wes：其次，如果你确实在意最终产物的体积，可以把代码打包后再发布。举个例子——我们之后会有一期节目讲这个——Node 现在允许你把整个应用打包成一个单独的可执行文件，里面包括你的代码、运行时以及所有依赖。如果你担心这个东西必须尽可能小，不能把 4 兆的 TypeScript 翻译文件塞进最终产物，那你只需要用任意一个打包工具（Vite、esbuild 之类）处理一下你的代码，出来的东西可能连一兆都不到，也许就 50K、100K，取决于应用有多大。真正运行你应用的代码，和其他那些东西比起来根本不大。

Scott：是啊，说到底这些都不怎么重要。

Wes：我的电脑有 2TB 硬盘，几百兆算什么？

Scott：哦天哪，我以前用 1TB 的时候真是挣扎。毕竟 Wes 和我是靠录视频为生的，对吧？

Wes：对，你想看什么是大文件，那就是视频。真的，我一小时的录屏可能就是 30G 的文件。

Scott：我跟你说，我从 2004 年左右——甚至更早——就开始做视频了。那时候我的硬盘只有 40GB，做任何视频相关的事都很痛苦。我当时有一个 LaCie 的 200GB 外置硬盘，现在看简直是个笑话。不过现在 SSD 价格多少降下来了，虽然苹果还是会狠狠宰你一笔。

Wes：总结一下怎么减小体积：如果你是包作者，可以使用 .npmignore 来避免把不必要的文件发布到 npm。当你放弃支持旧版本的 Node 或旧浏览器时，记得清理相关的东西。在这方面 Babel 的 preset-env 很好用：你告诉它你要支持哪些浏览器，它会算出你需要哪些 polyfill，不再需要的就不会加进来。

Scott：你也可以直接用 pnpm。不过它不一定适合每个人，因为更换包管理器需要一定的投入。但说真的，我已经用了 pnpm 一段时间，迁移过程并不痛苦，可能这里那里有几个小问题。pnpm 的做法是把所有包存放在你用户目录下的一个根文件夹里并缓存起来，这样每个包你只需要下载一次，然后它用——叫什么来着——符号链接（symlink）把一切连起来。如果你有 monorepo，它也是用符号链接把所有东西连在一起，这样就不会在你的机器上把同一个包装一百次，基本上每个版本只存一次。所以 pnpm 是个很好的方案，而且正因为如此它非常快，需要下载的东西更少；它也更高效，不需要占用那么多硬盘空间，这对我来说也是很棒的特性。如果你是 Yarn 或 npm 用户，真心推荐试试 pnpm，切换过来非常简单，我想你会喜欢的。对我来说这是个不错的转变，我已经用了一年半多，只有好话可说。

Wes：最后还有一个叫 npkill 的工具。你只要运行 npx npkill，它就会在你的硬盘上搜索 node_modules 文件夹，告诉你每个项目你上次是什么时候动过的，以及这些文件夹有多大。如果你想腾出一些硬盘空间——我记得我第一次用它的时候，之前从来没清理过，一下子删掉了 30G 的 node_modules，非常可观。

Scott：可我手上同时在做六七个项目，我还不想删掉那些 node_modules。

Wes：不，你是在当前所在的目录下运行它的。比如我在某个目录里，只想清理这个目录下的东西，有时候想直接干掉 node_modules，而不是手动 rm -rf。

Scott：你也可以对所有站点实验项目这么干。我不知道你的 sites 文件夹是怎么组织的，我有一个 exp 文件夹，也就是实验文件夹，任何时候想快速折腾点什么，我都丢到那里面，有时候就忘了。所以定期把实验文件夹里所有的 node_modules 清掉，这没问题。

Wes：实验文件夹这个，说实话还是让我有点害怕。我知道它没问题，但我喜欢 npkill 的界面，是最好的：用方向键选择，按空格删除。

Scott：哦天哪，太棒了。不过等你哪天不小心删错了目录，可别来找我。

Wes：嘿，你可是在跟一个在自己 home 目录下运行过 git clean 的人说话。

Scott：哦，是啊。好了，今天就到这里。感谢大家收听，我们周三见。
