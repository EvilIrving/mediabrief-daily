NAVER D2 这篇是「自研 vLLM 插件」系列第二篇。第一篇讲了把搜索与推荐模型做成 vLLM 自定义插件；本篇聚焦其后更麻烦的事：每个模型都要重复的转换流程，以及如何跟上大约每两周发一版的 vLLM。作者团队的做法不是追求一键魔法，而是把转换到部署做成可打磨的 AI-native 自动化——具体落在 Claude Code Skill 上。

转换难，是因为要保留 Hugging Face 权重、却按 vLLM 重写实现，同时横跨模型结构与服务基础设施两个领域：模型开发者不懂池化接口和 IO Processor，MLOps 工程师又不熟权重量映射和两套实现的细微差别。框架还在从 v0.1 冲到 v0.20。于是他们做了 `convert-vllm` 技能，用户给出模型路径后，五个子技能依次跑完：搭环境、写 vLLM 配置/模型/加载/注册代码、按需做 IO Processor、做含等价性（parity）验证的测试与基准，最后上传 MLflow 并开 PR。全程不是黑盒全自动：执行前必须写出 `plan.md` 给人审批；测试与验证由独立上下文的子代理做，避免「自己改自己验」漏错。用这套流程已转换分类、NER、嵌入、ABSA、图像打分等 7 类模型，踩坑规则从 5 条滚到 45 条。

两次大试错决定了技能长什么样。第一次：在 200K 上下文时代做了 4 个检查点和 9 个状态字段，好从中断处续跑；Claude Code 升到 1M 上下文后，五步可在单会话做完，检查点反而成了占 `SKILL.md` 三分之一的死重量，删掉后文档从 492 行降到 332 行。作者借此强调：技术债不只在源代码里，AI 工具一变，技能也要跟着改——Opus 4.6 升 4.7 时就有技能局部失效。第二次：起初用钩子在每次工具调用前灌入整份知识库，单次约多 6900 token，重复调用后同一内容占掉约 15 万 token，还造成注意力稀释，代理去引用无关模型类型的规则。他们转向 Claude Code 技能的分层加载——先只看 `description`，选中后再读正文和 `references/`——并参照 Supabase 的 `agent-skills`（Problem / Wrong / Correct / References，按前缀分类），把流程技能 `convert-model` 与领域知识技能 `vllm-best-practices` 拆开，用 `category-index.md` 按模型类型按需拉取。额外加上 `vllm_version` 和源码 `Source` 行号，方便版本升级后复查规则。结果是传递知识的单次调用 token 从 6900 降到 170（降 97%），选择知识的主体也从「系统强塞」变成「模型自选」。

最后把同一原则扩到仓库之外：在 GitOps 仓库用「KServe vLLM 新建部署」Issue 模板触发 `kserve-vllm-deploy`；用户填模型、环境、GPU 等，代理留言建议命名、类型、GPU 与运行时，人批准后自动开 PR（文中 `clip-score` 一例为 3 文件 69 行），再经 ArgoCD 同步集群。vLLM 执行参数与 GPU 建议仍留在插件仓库，经技能市场（Git URL）以 `pai-vllm-serve-guide` 插件按需提供，避免知识落在非所有者仓库。结语归纳四点：工具升级要重审技能；给 AI 的信息要设计时机与剂量；AI-native 模式要按自己的问题重组而非照搬；好的协作结构靠一行 Git URL 就能跨仓库复用。
