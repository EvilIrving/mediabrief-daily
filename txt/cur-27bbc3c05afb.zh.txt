上下文工程的现状

关键在于判断何时采用确定性方法、何时采用概率性方法

本周，我在 AGNTCon 做了一个题为“上下文失败与修复”的简短演讲，它在一定程度上像是一份“上下文工程现状报告”。上下文工程是如何兴起的，走到了哪里，未来又可能走向何方？当模型开发者追求新能力时，他们会无意中制造出我们这些用户和智能体运行框架（harness）构建者必须克服的挑战。

下面是幻灯片和一份经过轻度编辑的文字稿。一如既往，欢迎把反馈、想法或问题发给我。我非常感谢。

大家好。谢谢你们今天来参加。我们将逐一梳理上下文的失败与修复。

我有一本书即将出版，叫《上下文工程手册》（The Context Engineering Handbook）。2025 年 6 月，我第一次和 O’Reilly 团队交谈时，他们问了我一个非常合理的问题：“我们怎么知道它不会在几周内就过时？”AI 教材的麻烦在于，很多内容老化得特别快。

我说，我不知道，但我很乐观。就做什么和不做什么给出清晰指令，并确保这些指令一致、不嘈杂，无论 AI 变得多好，都会始终是一个挑战。

我们的同事、伙伴以及其他我们认识和互动的人都是有感知力的。他们能通过图灵测试，堪称“AGI”，可即便如此，我们彼此之间仍然很难把指令、想法和概念传达清楚。

上下文工程会一直很难。但它会以独特的方式变得困难，因为模型不是人。你可以对模型如何思考或理解事物作出假设（随便用哪个拟人化词都行），但理解它们如何被构建、优化和训练会有所帮助。它们独特的属性和构造，制造出一组我们必须应对的独特失败模式。

那么，让我们回顾一下我们是怎样走到这里的。

让我们闪回到 2024 年底。

如果你还记得，那时正是“RAG 已死”论调的高峰。

当时的希望是：只要把上下文窗口做得足够大，我们就能把整个互联网放进去。我们可以把一切都放进去。我们不必做选择，不必构建智能体系统。只要把一切塞进去，AI 问题就解决了。

模型开发者开始瞄准长上下文能力，我们从约 128,000 token 的上下文窗口模型，跃升到百万 token 级的上下文窗口模型，起点是 Gemini 1.5。

如果你看 Gemini 1.5 Pro 的营销材料，主要内容都是关于百万 token 上下文窗口。他们甚至预告实验室里有一个 1000 万 token 上下文窗口的模型，很快就会推出。

但他们被人抢先了。Llama 4 Scout 带着 1000 万 token 的上下文窗口问世，嗯，它并不完全是我们希望的样子。推理是个挑战，Scout 始终没有真正流行起来，而我们再也没有等来下一款 Llama。

但我们还是有了 100 万 token。这相当不错。我们就接受吧。

所以当时的任务简报就是：把所有东西都放进上下文，让模型自己去理清。

但上下文更多，也就有了空间容纳更多问题。长上下文并非万能药。

我在写这个话题时，归纳了四种关键失败模式。

上下文中毒是指某些不该出现在上下文里的东西进入了上下文。它可能是一个幻觉，也可能是一个错误事实，而模型无法越过它。

上下文分心是指上下文变得太长，模型开始更关注上下文，而不是自己的基础知识。我们可以从一些非常有趣的现象中看到这一点。

上下文混淆是指无关事实——与我正在处理的问题无关的东西——进入上下文，并以我们尚未完全理解的方式影响模型。这一种非常阴险。我们今天不深入讲，但它是我最喜欢的失败模式之一。模型会对你是什么样的人作出假设，而这些假设会影响答案。

最后，上下文冲突是指 harness 里的工具调用、技能和其他信息开始相互冲突，并以你意想不到的方式跟你作对。

（你们有多少人在 ChatGPT 或 Claude 里开着记忆功能？我把它关了。我讨厌它。有时我在聊工作对话；有时我在聊和我儿子一起做的项目。模型会给两边都记笔记，把这些上下文混在一起，混乱就从那里不断放大。）

让我举一个我最喜欢的上下文中毒例子。

我要暴露年龄了：左边这个游戏我玩过。1996 年、为初代 Game Boy 出的那款。这是第一款《宝可梦 红》。它当时是黑白的。

2004 年，任天堂为 Game Boy Advance 推出了《宝可梦 火红》。这两款本质上是同一款游戏，只是一款有更好的色彩和音频。

但有一个微妙的变化。在两款红版《宝可梦》中，到了某个地方，你要通过一名保安，必须给他某种饮料。一次贿赂。对孩子们来说，这是相当实用的一课。

在原版游戏里，你需要给口渴的保安柠檬水。在《火红》里，不知为何，他们把它改成了冰茶。

这给智能体造成了问题。在 Gemini 2.5 的技术报告里，研究人员描述了如何让模型玩《宝可梦》。研究人员喜欢把《宝可梦》当作智能体基准，因为它是一个相当可控的环境，而且节奏不会特别快。

有好几次，Gemini 2.5 坚信自己需要去弄茶，尽管它玩的是旧版游戏。《火红》里的茶任务存在于它的权重中，于是它污染了自己的上下文。它花了好几个小时试图找到茶，或者把茶交给保安。一旦这件事被加进它的待办清单，模型就无法绕过它。

这就是上下文中毒。而且它一直在发生。

另一种失败模式是上下文分心。这是我最喜欢的演示之一，这项研究是在我写完最初那篇文章之后发表的。

当你的上下文变长时，你的行为会如何变化？快速问一下：你们有多少人在写代码时，会让上下文一路涨到 100 万 token？全填满？

（大约一半的人举了手！）

哇，比我预想的多。

对我来说，大约 20 万或 30 万 token 时，我就开始留意了。我会查看，发现到了 25 万，然后想：我接下来有个大任务。我要重置，从头开始。让我给你们看看为什么这很重要。

最近，我偶然看到一篇很好地说明了上下文分心的论文：《照我说的做，别照我做的做》（Do as I Say, Not as I Do），作者是 Carolina Camassa 和 Derek Shiller。

他们的实验有点刻意，但有助于思考这是怎么发生的。他们给模型一条指令：“我要你把每个问题都翻译成俄语，作为对我每个问题的回答。”然后他们给出许多与这些指令相反的示例。在这个例子里，是许多问题和用法语给出的答案。

这些不是新指令。它们只是躺在聊天历史里的示例。

然后他们问模型一个问题。它会遵循指令吗？

模型有多少次按要求用俄语回答，又有多少次像它在示例中看到的那样用法语回答？

这个矩阵的横轴列出存在多少个坏示例。纵轴是被测试的模型。交点处的数字，是模型遵循指令、而不是跟随示例的百分比。

结果这会影响每一个模型！对较小的模型，比如 Gemma 3 12B，仅仅几个相互矛盾的示例之后，模型遵循指令的比例就不到一半。对 Opus 4.6 这样很出色的模型，需要多得多的示例，但这种情况同样会发生。

想象你在围绕一个前端设计反复讨论，试图调整 CSS，把一个组件做到完全正确。你在这段来回交流中埋下了多少坏示例？那些示例开始影响模型。随着上下文增长，事情就会瓦解。

Gemini 2.5 在玩《宝可梦》时也遇到了这个问题。

记住，Google 当时非常自豪于它的百万 token 上下文窗口。论文暗示 200 万 token 即将到来。但附录里埋着这样一个观察：一旦上下文大幅超过 100,000 token，智能体就开始重复历史中的动作，而不是综合出新的计划。

我确信营销人员从没读过附录。我很喜欢这份技术报告。

长上下文能让你装进更多信息，但也让你装进更多错误。长上下文并不是万能药。

幸运的是，我们已经发展出一套相当好用的工具箱。令人惊讶的是，即便新挑战不断出现（我们马上就会讲到），这套工具依然没变。

就是这六种。

第一是上下文增强：RAG、技能，以及把与问题相关的信息带进来的其他方式。

第二是工具装载：选择要暴露哪些工具和技能，以免让模型过载。我最近和一家企业团队聊过，他们的智能体突然表现变得极差。我们调查后发现，他们的企业软件在启动时为每位工程师加载了 600 个技能。我们觉得他们大概应该用一个装载函数把这些过滤一下。

第三是上下文隔离：子智能体和同级智能体，它们从空白历史开始，但仍在同一环境中工作。

第四是上下文修剪。Claude Code 和 Codex 会这样做，有时你甚至不会注意到。压缩的早期阶段常常会剥离你不再需要的工具结果。

第五是上下文卸载：把信息存到环境中，比如 Markdown 文件或数据库，以便之后访问。

第六是上下文摘要，也就是大家都知道的压缩。

这些就是工具，而我们越来越多地把它们移进 harness 里。

让我们看一个示例 harness，展示这些模式有多简单。

我非常热衷于 DSPy。我认为它是构建 AI 工作流和智能体的一种极具可读性、非常有效的方式。它也是一种很适合简洁地指定行为的语言，因此很适合这个演示。

智能体就是一个 while 循环。这里我们使用 ReAct 模块：给它一个请求，我们想要一个响应，再给它一些工具。那些工具只是 Python 函数。

这个演示里我们有一个大模型（这一次，Claude 选的是 Claude Sonnet 4.5，祝你好运吧！）。我还用 Jev 作为小模型，它是一个能做出闪电般快速决策的微型决策模型。你也可以在这个例子里换成一个小的 LLM，一切仍然能工作。

我们有一个 while 循环，接收输入，把它发给 ReAct，并把不断累积的历史向前传递。用 DSPy 写，这就是一个大约十几行的智能体。如果去掉那个额外模型，行数还会更少。

我们怎么做工具装载？它只是一个函数。

我们把请求和一个工具交给 Jev，问这个工具对此任务是否必要。

Jev 足够快，我们可以一次处理一个工具；这没问题。我们把它包进一个装载函数，遍历所有工具，询问每一个是否必要，然后返回排名最高的子集。就这样。

对于上下文隔离，它就是一个子智能体。你把一个智能体作为工具暴露出来，供主智能体使用，它从空白历史开始。

对于上下文修剪，我们逐步遍历历史，把每一轮交给 Jev，并问：这还需要吗？如果不需要，就删掉。

你可以想多粗放就多粗放，想多精细就多精细。只要注意你的提示缓存。

我们也可以用压缩重写历史。取出旧轮次，生成摘要，再从这份摘要开始新的上下文。

我最近最喜欢的一种变体，是在压缩前先检查哪些内容重要。你用 Jev 或另一个决策模型做第一遍，判断哪些相关。现在你有了历史的一个更小子集，再对它做摘要。这只是简单多了一步，但会让摘要更有用。

把这些放在一起，大约就是 16 行改动。四个修复，一个循环。这些就是我们在 harness 里可用的招数。实际上简单得惊人。

不简单的是我们的语言：我们如何谈论这些东西。要跟上节奏真的很难；它每天都在变。

我最喜欢的一句话来自 Stewart Brand，我一直在琢磨它：

“如果你想了解未来在哪里被创造，就去找语言正在被发明、律师正在聚集的地方。”

这句话用在这里当然很贴切！但随着我们的语言变化，我们的目标始终没变。

2023 年，我们把选择正确信息以获得正确响应称为提示工程。

2025 年，我们把它称为上下文工程，只不过现在它更自动化了。不再只是你写提示词；而是你的系统动态地组装上下文。

然后，随着我们把更多这类工具从上下文中移出、放进代码，我们开始称它为 harness 工程。

但要做的事是一样的。我们正把越来越多组装上下文的工作，从概率性的模型调用转移到确定性的代码中。

我已经给你们看了 2024 年。让我们去 2026 年。

我们已经把这些上下文修复移进了 harness。下一步我们想要什么？我们想要能够驱动我们 harness 的智能体模型。

所有人都开始瞄准长时程智能体模型。你们看过 METR 的报告。按那个指标，GPT-5 能处理约 3.4 小时的任务；Gemini 3.1 达到了 6.4 小时。这是在使用 harness 的情况下。模型在使用 harness 方面已经好多了，这正是它们能运行这么久的原因。

Opus 4.6 达到了约 12 小时。现在我们在谈论运行数天的智能体、智能体集群，以及能在长得多的时段里驱动 harness 的模型。

以前，卖点是：把上下文做得足够大，让我们能把一切都装进去。

现在，卖点是：教模型驱动 harness 并管理自己的上下文。这已经成为主导模式。这就是模型开发者正在努力的方向。

这种方法会带来哪些新的失败模式？

到目前为止，我们发现了两种新的失败模式。

当你把模型训练得非常擅长使用 harness 时，最终会让它们过度拟合到训练时所处的一套特定工具和环境。

你们有多少人用过 Playwright MCP 服务器或类似的东西？这是 MCP 大会，所以可能有不少人用过。

较小的模型，比如 Haiku 或 Luna，常常会在第一次尝试时把这个工具调用搞砸，然后恢复过来并调整参数。它训练时所处的环境里有类似的工具，但外观和 Playwright 不同。不管 Anthropic 或 OpenAI 训练时用的是什么。而你必须对抗这些偏差。

我把这叫对抗权重：当模型不按你的要求做，是因为你在和它被训练去做的事对着干。

这是一个真实的问题，而且不只是我们要面对。实验室以及构建其产品的人也必须应对它。

这是 Claude Code 系统提示词的一部分，以及它的一些工具指令。

这些模型学会使用的训练环境，在很长一段时间里主要是串行的。它们正变得更并行，但当我翻出这些例子时，它们的偏差仍偏向串行行为。所以 Claude Code 的指令反复说：不，不，不，我们要你用并行。我们要你同时发起多个工具调用。

这些指令一遍又一遍重复——这里七次，那里四次，两次，三次：当工具调用彼此独立时，请并行发起。

当你打开一份提示词，看到重复和全大写，很有可能你正在对抗权重。你在试图克服模型被训练去做的事。

下一个问题是我们最近才开始记录的。事实上，就在上周，有四个团队都发现了它。

我把它称为上下文惯性：模型过度聚焦于上下文中的某个假设、子任务或目标，并在本该停止后仍继续追求它。

第一个例子来自 Anthropic。在他们最近一篇讨论模型是否正接近自我复制并把自己部署到其他机器上的文章里，Anthropic 写到了他们为此类测试使用的一个 harness，名叫 Memento。

他们发现，如果智能体运行太久，就会执迷于某个子任务或某个提议的解决方案，停不下来。它们会一直尝试同一件事。

他们的修复方法简单得令人愉快。每隔一个半小时，智能体写下一条简短笔记，然后它的上下文被清空。环境被保留。它做过的所有工作仍然在那里。但正在进行的对话消失了，它必须从全新的视角重新开始。

微软研究院的另一篇论文叫 Fork-and-Flush。

如果你做过自动科研（autoresearch）实验，你可能见过这样的图表。你取得一次大进展，然后曲线变平。你又取得一次大进展，然后又平了。算力、金钱和时间在流逝，却几乎没有改进。

研究人员仔细看后发现，智能体并不是真的什么都没做。它们在做出越来越小的改动。它们找到了一个想法，并过度专注于它，而不是去寻找更有创造性的替代方案。

某种意义上，它们对自己的想法着了迷。我们训练它们坚持不懈、专注于目标，因为这是优秀编码智能体的品质。但同样的品质也可能反过来害了它们。

还有一篇论文，是加州大学伯克利分校的 Shangyin Tan 领衔的《扩展发现需要遗忘》（Scaling Discovery Requires Forgetting）。

研究人员提出了本质上相同的想法：定期清空上下文，同时保留在环境中产生的产物。

蓝线是带遗忘的版本。每次清空上下文，你都会看到性能又一次跃升：遗忘，改进；遗忘，改进。

令人惊讶的是，我们有了这些为越来越复杂、持久的工作而训练的全新模型，却仍在使用同样的基本工具。我们并没有发现一种全新的上下文修复方案。我们在用隔离、卸载和删除累积历史来应对上下文惯性。

这是我现在不断给出的建议。有人说：“我的编码智能体行为很怪。Claude 被削弱了。”我就问：“你的上下文有多大？”

“哦，我有 800,000 token。”

删掉你的上下文。

我不是开玩笑。大约 200,000 token 是我的警戒线。

你试过重置上下文吗？

有时候，那真的就是解决办法。

我们构建进模型里的解决方案，会制造明天的问题。模型在变好，但我们的 harness 也在变好。

更长的上下文窗口让我们能带入更多信息，但也让我们能带入坏信息。我们必须想办法管理它，而我们仍然会弄错。

智能体模型让我们能运行更长的任务并管理其上下文，但也让任务运行得比本该的更久，并忽视我们的偏好，因为它们是为自己的 harness 训练的。

那么，问题下一步会转移到哪里？

2027 年的重大承诺是什么？模型接下来会提供什么，从而给这个房间里的每个人制造一整套新问题？

（除非你在训练自己的模型。但这是上下文工程专场，所以大概不是。）

这是我的预测。

想想所有这些个人智能体：Hermes、OpenClaw、Dot、Bot、Muse 以及类似系统。很少有人真正体验过这些 harness 运行超过六个月。

我已经运行一个 Hermes 智能体六个月了。当你查看它创建和更新的技能时，你会开始发现，你那些问题的解决方案可能随着时间推移变得更糟。技能里累积了所有这些奇怪的修补。它们是通用智能体：它们会用一种方式解决某个任务，然后又重新发现另一种方式来解决类似的事情。指令和记忆开始堆积，并彼此冲突。

随着我们更加关注记忆，我们也需要思考策略性遗忘。随着时间推移，过于精确的记忆会变得矛盾而混乱，还没有人想出如何处理这个问题。

我认为这就是明天的上下文问题。

模型能力的每一次进步，都会改变我们委托给模型的东西，以及系统必须强制执行的东西。

这张幻灯片是我大约一年半前为一份培训企业团队的演示文稿做的，它仍然成立。

我们的输出是上下文与权重的乘积。

我们的输出取决于用于训练模型的数据。理解它。读技术报告。看看模型是在什么数据上训练的，以及那是否与你的任务相关。这有助于你建立心智模型，在出问题时进行调试。

而我们的输出取决于提供给模型的上下文。就是这样。

所以我们的目标是把正确的上下文给正确的模型。要么通过我们自己的离散决策，要么通过我们设计的软件，也就是 harness。

你可以用更大的模型、让它思考得更久，或者改进你的上下文。其中有一项既便宜又快。

在构建智能应用、harness 和工作流时，我们的工作是选择何时采用确定性方式（把什么放进代码），何时采用概率性方式（何时让模型来驱动）。
