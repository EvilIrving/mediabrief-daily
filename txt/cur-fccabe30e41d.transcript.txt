# 棕地项目中的 agent 工程

## 2026 年 9 月 14 日

**在老代码库中做 agent 工程，关键在于让隐藏的约束变得可见，让廉价的改动变得可信。我们来谈谈在棕地（brownfield）代码库中该怎么做。**

在我的职业生涯中，我待过一些代码库已经存在很久的团队。那些就是棕地系统：代码仓库已不再能完整描述这个东西实际上如何运行。机构内的经验知识、临时修补的胶带、遗留服务，以及其他团队所依赖的预期，都存在于代码树之外。你必须在写新代码之前了解这些约束，也必须证明一次改动没有破坏它们。我很喜欢和 agent 一起写代码，但如果把它们扔进一个较老的棕地代码库、不加监督，你最终可能得到一个“能用”的东西，但系统设计是错的，测试也很脆弱。

即使在 AI 出现之前就想推动现代化改造的团队里，你往往也得非常非常零碎地推进，要有强有力的测试，有一层坚实的信心，确保自己没有把东西弄坏。你大致知道，除了真实的用户旅程测试之外，你做的任何迁移都必须通过一大堆可重复的测试，来保证一切按预期运行。如今有些人可能会说，一旦 agent 写下了不是你逐个决策亲手写出的代码，你就已经身处一个棕地项目中了。无论如何，你都要优化的是：让廉价的改动被安全地完成。

而如今，尤其是最近——我想说大概五到十年——更加重视测试、更加重视验证、更加重视如何以不会弄坏东西的方式做改动，这种理念我觉得得到了更多关注。但这并不改变一个事实：如果你投入大量精力引入 agent 工程，再引入软件工厂以及其他各种在大型代码库中自主推进工作的模式，你就必须额外投入相当多的审慎，否则你就可能给自己签下一个满是技术债的世界。

**在深入之前，我们先假定代码应当是唯一的事实来源（source of truth）。我们在其之上为棕地项目额外添加的任何东西，都应是无法轻易推断出来的内容。我想从分区、爆炸半径（blast radius）以及其他几个我认为有帮助的模式来谈这个问题。**

## 分区

**如果我要进入一个已经存在一段时间的老代码库，我大概会想先弄清楚哪些代码我不应该碰。** 你可以把它们看作分区。例如：绿区 = 安全 / 测试良好 / 隔离良好，黄区 = 质量参差，红区 = 敏感 / 认证 / 计费 / 权限。

代码库中哪些部分非常非常敏感，或者并不是每个人都很理解？也许你会把它们划成不同的区。也许你有一块绿区，测试覆盖非常好，使用的是现行的现代约定，隔离也做得好。对系统的这些部分，agent 可以自己去干，在一个紧凑的循环里工作。

有些网站，尤其是我合作过的一些电商网站，很容易就有五六个部门，各自拥有自己的微站点，而对终端用户来说，整个体验感觉就是一个整体。表面之下其实有大量固有的复杂性。一个团队可能给自己的东西写了非常好的测试覆盖，也许它是最近几年才建的；其他团队可能没有。于是你就有了这片绿区。

也许你还有黄区，质量参差不齐，可能是各种东西的混合，agent 可以在写好特征测试（characterization tests）之后修改那里的代码。

然后你可能还有红区，那里是敏感的东西，比如认证、计费、权限、薪资，任何你通常不会去碰、不会草率修改的东西。例如，只有很少几个人明白它的整体运作方式。在那种系统里，你不希望出现无人监督的重写。

有三条规则让分区成为一套操作规程，而不只是一个比喻。第一，由人来画地图，而不是 agent；让它自己选的话，agent 会从最吓人的文件开始，因为最吓人的文件里有最有意思的名字。第二，分区只有在挣得资格时才能变动：只有当特征测试已经存在、并且模块负责人审查过 agent 的头几次改动之后，黄区才变成绿区。第三，分区决定了可以做的动作：绿区是紧凑循环，黄区是先写测试，红区则是每一步都有人结对，否则就不做。

## 把代码说不出的东西写下来

**自主程度应当取决于爆炸半径、可观测性和可恢复性。模型自身的信心是一个糟糕的指引。**

所以我认为，至少要有这样一种意识：你如何看待这张世界地图，以及 agent 能从代码库中自己推断出什么？**agent 实际上能从代码本身推断出相当多的东西。** 曾经有一段时间，人们会试图为所有东西都配上 markdown 文件，然后把它们塞进上下文窗口。agent 其实相当擅长理解系统的地图。**你想给它们的，是那些从代码本身看不出来的东西。** 有没有约定？有没有模式？有没有不在代码里的微妙之处？我认为这很重要。

具体来说，这意味着：业务或团队特有的细微差别；解释系统*为什么*以某种方式组织的权衡；没有被静态分析或工具明确强制执行的准则；特定领域的规则；外部约束；以及反直觉实现背后的历史背景等等。

**把代码说不出的东西写下来，其他的一概不写。**

## 让调研结果在会话结束后留存下来

**如果你的 agent 的探索没有产出任何持久的产物，下一个 agent 就得为同样的考古工作再付一次钱。**

我会给那张地图再加上一样东西：一份持久的调研产物。对于黄区和红区的工作，我喜欢单独做一遍只读的梳理，产出一份简短的理解备忘录：入口点、负责人、调用方、现有抽象、测试、生产环境信号、相关历史以及待解决的问题。每一条论断都应引用某个文件、issue、负责人记录或仪表盘。

否则，默认的循环会浪费掉它的调研成果。agent 弄清楚了认证流程如何运作，完成了任务，会话一结束，这个认知模型也就丢了。聊天记录并不是一个好的记录系统，尤其是在上下文被压缩之后。

调研之后，我会用一个干净的上下文开始做规划。问清楚：各种可行的方案会碰到哪些文件，它们保持了哪些不变量，以及你会如何撤销它们。由人来选择路径。如果实现过程中发现地图是错的，就应该停下来。评审要从头开始，从验收标准倒推。一个干净的评审者更有可能注意到：某个测试证明了实现，却漏掉了需求。

## 当指令变成驾驭环境

**每一次重复的纠正，都是驾驭环境（harness）中缺失的一块。**

把各个部件的位置说清楚是有用的。指令（instructions）记录关于仓库的不寻常事实。技能（skills）封装可复用的流程，比如检查爆炸半径或验证一次 schema 变更。插件（plugins）可以提供受管控的访问途径，连接负责人目录、事故档案或仪表盘。

驾驭环境是围绕 agent 的工作环境：上下文、工具、权限、测试、日志和恢复手段。工厂则调度许多可靠的循环，保存持久状态，并把新出现的情况交还给人。

实际的检验标准是 agent 出错时会发生什么。如果你悄悄修好了 diff，下一个会话可能会重犯。当同样的评审意见再次出现时，就把它变成一条 lint 规则、钩子、类型、测试或技能。只有那些无法机械强制执行的约束，才保留为文字说明。

一条拒绝规则、一个限定范围的凭据或一项 CI 检查，不需要靠记忆。随着时间推移，驾驭环境会成为一份失败记录，记录着团队决定不再付第二次代价的那些错误。

## 从零风险的工作开始

**在让任何东西改进当前行为之前，先把它锁定。**

如果你要把 agent 引入一个现有代码库，这和其他类型的现代化改造非常相似。也许你会从零风险的工作开始。不应该是“嘿，我们用 Rust 把这个单体重写一遍”之类的。也许第一步是：先解释清楚这些东西是怎么运作的。

**生成能够锁定当前行为的特征测试。**

> 特征测试是一种自动化测试，用于记录系统实际的当前行为，以便你能安全地重构或修改遗留代码。

我说的特征测试，是指把模块今天的行为钉住的测试，包括丑陋的部分，因为在老系统中，有些丑陋的行为恰恰是业务赖以运行的东西，而 agent 会很乐意在一套全绿的测试背后把它“修好”。这套机制之所以古老，是因为这个问题本身就很古老。Netflix 在 GraphQL 切换中以生产规模使用了同样的思路——把回放流量和影子流量同时打到新旧两条路径上，比较返回的数据，只有一致时才推进切换。当一个首页级别的界面没有一套靠得住的单元测试时，这就是推进的路径：不要猜，两边都跑，然后比较。

当由 agent 负责让测试通过时，不要让同一个会话成为测试的唯一作者。先钉住行为，在单独的一轮中完成，或者由人完成；然后再让 agent 干活。否则你得到的就是一套全绿的测试，它编码的恰恰是你刚刚发明出来的实现。

然后你再开始走机械式转换的路子。你可以做死代码和未使用导出的清点。你不会想从系统中最棘手、最复杂的部分开始。最终，你希望在所有这些迁移中都有这种信心。

我记得自己在大型代码库上参与过许多不同类型的迁移，人们都非常小心，即使是在修复本来就坏掉的东西时。

我参与过的较老的代码库之一是在 AOL。有一天我本该休息，正在逛办公室附近的一家漫画书店，恰巧老板给我发短信，问我能不能过去一趟。AOL.com 首页彻底坏了，而当时身边没有足够的 JavaScript 专家去查明原因。于是我说，好吧，我过来看看。如今你可能会想，哦，一个首页而已，能有多复杂？但当有几十上百个部门的人，各自拥有许多不同的组件、许多不同的标准、许多不同的脚本、A/B 测试，所有这些东西，你就要避免把所有人的世界都弄坏，因为你未必能像自己希望的那样，在每个地方都有测试覆盖。那一次我把问题修好了，但我们基本上至少得对那些没有自己单元测试的东西做用户测试。东西运行得怎么样，有没有给所有人弄坏？所以这一点挺重要的。

这仍然是这份工作的本质。agent 并没有消除“几十个部门”的问题；它们只是让针对这个问题尝试一次改动变得更便宜。一个只有生产流量才真正“理解”的界面，按定义就是红区；在你构建出能替代那些流量的东西之前，我在休息日做的那种用户测试，依然是那道关卡。

## 以完整单元进行迁移

**只有当新路径可以工作、且旧依赖被证明已经消失时，一次迁移才算完成。**

迁移做到一半，对 agent 来说尤其令人困惑。搜索结果显示旧方案出现在四十个文件里，替代方案出现在十二个文件里，还有一个兼容垫片（shim）把两者都呈现为现行做法。agent 看到的是相互矛盾的先例。

我宁愿把一条路由从头到尾做完，包括删除旧路径，也不愿转换三十个文件却让两种模式并存。如果删除工作被留作将来的清理工单，那这个迁移单元就没有完成。

当替代实现仍在调用遗留实现时，测试照样可以保持全绿。SWE Refactor Bench 把这种情况称为迁移“盲视”（Blindness）。在 520 次 agent 运行中，只有 28 次通过了它的迁移审计、行为测试和独立验证。

如果一个 codemod 就能完成常规改动，那就用 agent 帮忙编写和检查这个 codemod，把例外队列交给 agent。Stripe 的迁移在这里之所以有参考价值，恰恰是因为它完全没有用到 agent：真正持久的产物是那台迁移机器。

## 更大规模迁移的经验

Bun 从 Zig 移植到 Rust，针对一个 535,000 行的代码库，在 11 天里运行了大约 50 个工作流，每个生成的单元都有两名对抗式评审者，并以全部原有测试套件作为合并关卡；值得效仿的部分是，在任何 agent 开始运行之前，他们花了好几个小时编写一份把 Zig 惯用法映射到 Rust 的移植指南。Anthropic 自己的迁移流程会先在一次一次性的小型迁移上对规则手册进行压力测试，并在正式大规模运行开始之前把试运行的产出全部丢掉。

一项受控的 VB6 到 C# 研究测得，简单功能的行为等价率为 92%，复杂功能则为 47%：单元大小才是杠杆。这种做法的形态完全早于 agent：Stripe 通过数月的 codemod 工作，用一个 PR 把 370 万行代码迁移到了 TypeScript，全程没有 agent 参与；Google 关于大规模变更（large-scale changes）的那一章解释了为什么随着代码库增长，原子性变更会越来越小。Spotify 如今报告，每月有 650 多个 agent 提交的 PR 被合并，靠的是 Backstage 多年前就搭好的轨道。

Asana 用两个自然周、约 12,000 美元的模型和基础设施成本，清掉了积压多年的 Enzyme 迁移。这 12,000 美元只是一张 token 账单，并不能取代他们账面上那份五年人力的估算；应把它看作供应商报告的生成成本，而不是一项受控的节省研究。可迁移的部分与 Bun 相同：一次范围狭窄的机械式迁移、一套原有的测试套件、人仍然审查每一处改动。

**在公司之间可以迁移借鉴的，是围绕 agent 的那套结构。**

## 真正改变了的是什么

**agent 改变了尝试多种可行实现的价格。它们没有改变选择其中一种所需的证据。**

我想你可能已经看到了，今年我们开始读到越来越多老牌公司用 agent 做大规模重写的案例。我和一些 CTO 聊过，他们允许团队让 agent 尝试用不同语言或框架进行多次重写，因为现在可以更便宜地做到这一点，并评估其中的权衡。

Shopify 用一个小团队，在十二周内把 Shop 消费者应用从 React Native 重建为原生 Swift 和 Kotlin，采用由 agent 把关、以单个屏幕为粒度的检查点。规模大得多的商家应用仍然是那个棕地问题：数百个屏幕、深度的平台集成，同样的关卡，更长的时间。

你也看到了其他重写为 Rust 的例子，看到了人们做框架级别的迁移。已经有各种各样的迁移完成了。很多情况下，这些迁移原本要花长得多的时间。如今，如果你有足够的 token，你真的可以让 agent 去尝试跨一系列不同的技术栈或语言完成一次迁移。

你可以尝试让 agent 把某样东西用几种相互竞争的方案分别实现。与其让一个团队选定一种方案然后全力押注，不如让它们把所有方案都实现出来。它们都可以用你的单元测试来检验。你可以对所有方案做性能剖析，然后再做决定，这在某些情况下比以往要便宜得多。我认为对今天的团队来说，这完全是另一回事了。

## 最后才并行化

**更多生成的代码应当带来更有选择性的人工评审，而不是更少的人类所有权。在你开始考虑 loop / goal / 并行化之前，认真想清楚什么能让你的棕地项目走向成功。**

软件工厂可以同时运行许多改动。我只会在某一个单元已经拥有可靠的评判者、恢复路径，以及人们能够消化的评审格式之后，才照搬这一部分。

并行会放大你已有的瓶颈。自动化验证可以处理五个经过检查的改动。而一位逐行阅读的资深工程师，得到的是一个队列、碎片化的注意力，最终是走过场式的批准。

我更希望自动化评审先给出意图、改变了的不变量、测试结果、对等性不一致之处以及回滚路线。完整的 diff 仍然可以查看。人的注意力首先投向爆炸半径最大、判定依据（oracle）最薄弱的地方。

worktree 隔离的是改动，而不是行为。它们可能共享 Git 元数据、凭据、本地服务和网络访问。受信任的工作也许可以接受这种取舍。而无人值守、要处理不受信任内容的 agent，则需要更强的沙箱和限定范围的凭据。

## agent 给模糊性标上了价格

生成了多少行代码，并不能告诉你代码库是否变好了。我会跟踪交付周期、评审分钟数、人工干预次数、逃逸缺陷、回滚次数、判定依据不一致的次数，以及遗留下来的告警抑制。

对于一次迁移，要跟踪剩余的旧导入数量、新路径承载的流量、对等性不一致之处，以及已移除的遗留依赖。如果测试全绿，而所有流量仍走旧路径，那就是在瞎忙。

**agent 给模糊性标上了看得见的价格。部落式的约定会变成反复出现的评审意见。**

这份成本一直都在，只是在新人上手、代码评审和事故恢复中被支付掉了。agent 让其中更多的部分可以被计量。这为团队早已知道有价值的维护工作，提供了更有力的论据。

下一次 agent 处理相当于那个首页的东西时，我希望它留下的不只是修复：还要有一条合成的用户旅程、一份负责人记录，以及一个回归测试。

下一位工程师和下一个 agent 继承到什么，同样重要。
