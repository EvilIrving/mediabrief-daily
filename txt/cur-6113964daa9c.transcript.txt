什么是 Codemode

Armin Ronacher 的思考与写作
写于 2026 年 10 月 6 日

一年多前我在这里写过几篇帖子，建议人们不要把自定义工具装进上下文（或 MCP 服务器），而要更多地使用脚本。最重要的是我写过《Code Is All You Need》，也写过 MCP 需要代码。随着 Pi 1.0，我们现在通过 Codemode 加入了 MCP 支持——这在某种意义上酝酿已久，但对有些人来说也许有点意外。所以我想在这篇博客里分享一些更新后的想法，说明这一切意味着什么。

当像 Pi 这样的 harness 为 LLM 提供可调用的工具时，它会给出一些工具定义，这些定义在服务端会变成某种 token 结构。模型是否被鼓励去调用某个工具，是强化学习过程的结果。我以前写过这个，想了解更多可以去看。

我们强烈倾向 CLI 和 bash 的原因之一，是它便于组合调用，也因为模型在训练时就学过文件系统如何工作。所以当它调用像 echo foo > /tmp/test.txt 这样的工具时，模型也学到：这次工具调用之后，/tmp 里现在有一个叫 test.txt 的文件。

然而 bash 有一个根本限制：它只能组合能跑起来的程序。而有些东西不是程序，却必须是 LLM 的原生工具。

最明显的例子是 read 或 view_image。如果多模态模型需要读一张图，它不能用 cat，因为 harness 需要把真实的图像载荷注入 LLM 的协议。

另一个很鲜明的例子是子 agent。要生成并编排子 agent，很难避开 harness 提供的工具。理论上 agent 可以提供一个通过环境变量和 Unix 套接字与外层 harness 通信的 CLI 工具，但那相当粗糙。它还有另一个问题：代码跑在哪里。

要更好理解这一点，需要多想想各个部件分别跑在哪里。通常真的有两套不同的系统。第一是大脑，也就是 harness：它跑在一台机器上，是受信任的。第二常常是同一台机器，但其实是工具执行的地方：手。在 Pi 里我们现在称之为执行环境，你可以把它想成所有操作的目标。

对我们至关重要的是：harness 大脑和跑 bash、执行工具的目标环境之间有一条分界线。

把这劈成两半会带来一些非常重要的后果。首先意味着它们跑在不同的文件系统上，信任级别也不同。比如你用 Gondolin 这类沙箱方案，bash 的东西会被沙箱化，但 harness 本身不会。

这就引出 Codemode 真正做的事：它是一种方式，让 LLM 在 harness 侧——而不是执行环境侧——表达和编排复杂操作。Codemode 跑在 harness 里、它自己的沙箱中。在 Pi 里，它跑在 WASM 运行时中的 QuickJS 上，带有刻意的限制：无网络、无文件系统、无定时器、内存有限。唯一的出路是再调用更多工具。你也可以想象 Codemode 跑 Scheme 或其他语言。

如果你还不熟悉 Codemode：它基本上就是一种在某种语言（我们这里是 JavaScript）内部发起工具调用的方式。这样你可以组合这些调用，而不必一定经过 LLM 的上下文。命名归功于 Cloudflare 的朋友们，是他们造了这个词。

比如，若你把一次 bash 调用当成常规工具调用发给 LLM，我们只会把末尾 2000 行丢进上下文；若 agent 想要更多，得自己去看溢出文件。若 agent 通过 Codemode 发起同一次调用，Codemode 侧会以结构化方式收到更大的输出。

最重要的是，因为 Codemode 是 JavaScript，agent 可以表达并发操作和基本工作流。你现在常看到 agent 这样用：先从某次工具响应里探针 5–10 条看看长什么样，再写一段 Codemode 脚本处理接下来的 n 条。

Codemode 还允许你把状态扔进会话记录！也就是说，一次 Codemode 调用可以藏起数据，同会话里下一次调用可以再加载。记住：这是在 harness 主机上，不在沙箱里。

在 Pi 里，Codemode 还允许你发起在 Pi 传统界面里本来说不通的调用。比如要用图像模型生图，或用一次性分类器模型给文本分类，这些 Pi API 通过 Codemode 暴露，而不是作为常规工具（那样只会浪费上下文）。

既然已经谈了不少，大概值得更明确一点。下面过几段我最近 Pi 会话里的 Codemode 调用。注意：这些代码没有一行是人写的，都来自 Pi 的真实会话，只是为阅读方便重新缩进。agent 会自动开始用 Codemode，要么因为任务让模型自然拿起这个工具，要么因为用户要求它用。

默认情况下，Codemode 只在启用 MCP 时在 Pi 里开启，但你可以在设置里用 "defaultTools": ["+codemode"] 打开。直接让 Pi 帮你启用就行。

先从简单的生图开始。生图是 Pi 在 AI SDK 核心里支持的功能，但不是 agent 能用的工具。过去要用图像模型，只能写专门的扩展，或让 agent 自己跑 node 并调用内部图像 API。因为我们在 Codemode 里暴露了不少内部模型 API，agent 现在可以直接用。（原文示例：getAvailableOfType("image")、generateImages，再用 image()/text() 回传。）

注意对 image() 的调用会把图像作为图像内容送回 LLM。在 harness 侧，它会直接喂给 agent，并作为临时产物落盘，以便 agent 再把该图交给 bash。

分类器模型如 Jev 也类似。它们也不太适合通过典型工具塞进 agent 工作流。与其做专门工具，Codemode 让 agent 伸进 AI SDK 直接调用。原文示例用 Jev 批量处理 GitHub issue 做快速情绪分析：bash 拉 issue 列表，Promise.all 并发 classify，store("sentiment_results", results)，再按挫败感排序返回前几条。

上面的例子里还调用了 store()，把那次执行的结果倒进会话记录。未来的 Codemode 调用若需要可以读回。这里的 Promise.all 没问题，因为 Pi 本身把并发工具执行总数限制为四，其余进队列。

更冒险的例子是用 Jev 驱动游戏引擎做调试：它知道 tankctl 命令，快速搭了一个最小循环，每一步既问游戏引擎要文本状态，又问 Jev 下一步做什么（约 30 步）。

Codemode 显然也很适合调用 MCP 服务器。因为我们并不把任何 MCP 工具直接暴露给 LLM，agent 会先在 Codemode 里用提供的 API 做工具搜索，发现已连接服务器能做什么。这种渐进式发现让今天许多 MCP 用例足够好用。例如有时 agent 会直接伸向 Sentry MCP（即便没先发现工具），大概是在 RL 过程中已经学过 Sentry MCP 长什么样；但它是从我们注入系统提示的内容知道 Sentry 服务器可用的，并非完全瞎猜。

我其实不太想在这里多谈 MCP，但 MCP 确实是一种从 Codemode 获益极大的协议。问题部分在于：实践中 MCP 常常针对的是（尚？）不用 Codemode 的 harness。不过潮流在变。在此期间，一个临时拐杖是像 Cloudflare 那样，在 MCP 服务器内部做 Codemode。但现在就变成了 Codemode 套 Codemode，相当糟糕：双重 JSON 转义，小模型容易搞混，内层代码也调不了外层工具。所以若在 Pi 里用 Cloudflare 的 MCP 服务器，agent 需要写 JavaScript，再通过更多 JavaScript 漏斗过去。这真的不理想，但发生这一切也可以理解。

那么收尾：Codemode 今天和 MCP 配合得怎样？嗯……不算惊人地好。因为 MCP 服务器还没有真正针对使用 Codemode 的 harness（尽管此刻我认为多数 harness 已经支持它）。

要让它好好工作，有几条建议：

- 结构化内容：Codemode 希望调用返回格式良好的 JSON。这需要从服务器回来，而许多服务器还没做到。MCP 的 outputSchema 体系对此很有帮助。
- 结果一致：一个有趣的失败情形是 MCP 服务器返回不一致的数据，比如为了省 token，结果集条目数不同时形状就变。这会导致先用 5 条探针成功，拉最大批量时却失败。
- 大型二进制数据：今天 MCP 还不支持大型二进制，许多真正有趣的用例完全不好做，只能搞各种奇怪的变通，比如预签名 URL，让上传走非 MCP 通道。
- 可组合的工具搜索：MCP 服务器可能比客户端更清楚哪个工具适合某任务，但今天没有好机制让 harness 把工具搜索扇出到多个 MCP 服务器。全靠涌现行为，扩展到多个活跃服务器时扩展性不好。

这把我们留在哪里？这是对一年前我鼓励 CLI 的立场的反转吗？我不这么认为。事实上，在我看来 MCP 生态恰好接住了我们一年前指出的有效做法：代码。但 Codemode 超越了 MCP，因为它可以在 harness 内部充当一种有能力的机制，给 agent 表达更多自由。

不过仍有些事需要想清楚。其一，Codemode 的持久化更棘手。我们也许得借用持久工作流引擎的思路来快照调用。又或者，像 Starlark 这样因其确定性而更适合的组合语言，会比 JavaScript 更好。

图像、二进制数据，以及这种模式难以与更小模型配合，也需要继续充实。所以它肯定还不是完美方案，但是一个相当有用的模式，我预计我们会更多地利用它。
