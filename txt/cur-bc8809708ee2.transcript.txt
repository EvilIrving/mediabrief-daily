主持人（Sven Johann）：这里是 Software Engineering Radio，我是 Sven Johann。今天的嘉宾是 Mike Barker，他是 LMAX（伦敦多资产交易所，London Multi-Asset Exchange）的研发程序员、前软件负责人。Mike 活跃于 Java 社区，零星为 GNU Classpath、JBoss、Mono 等开源项目做过贡献，现在住在新西兰，远程为 LMAX 工作。今天我们聊 LMAX 的架构。Mike，欢迎来到节目。我有没有漏掉关于你的什么重要信息？

Mike Barker：谢谢，谢谢 Sven。我想开源方面唯一要补充的是，我目前在开源领域主要做的事情是维护 LMAX Disruptor。我们后面应该会聊到它。

主持人：好，先交代一下背景。LMAX 是什么？

Mike Barker：好的。值得从 Betfair 讲起，因为它是我们历史中很重要的一部分。Betfair 是一个点对点的体育博彩平台，可以押注赛马、足球之类的比赛。很多年前，在我加入 LMAX 之前，他们搞过一个项目，想试着做一个性能高得多的交易所，大概比当时的系统快 100 倍。因为从技术角度看，体育博彩交易所和金融交易所其实很相似：都有价格和数量的概念，博彩系统按赔率撮合，金融系统按价格撮合。于是他们启动了一个研究项目，持续了一段时间，在交易所应该怎么运作这个问题上有了一些有意思的发现。随后他们决定拿其中一些想法，成立一家叫 Tradefair 的公司，算是从博彩向金融领域的一次试水。他们沿用了研究项目里的很多思想，但没有用任何实际代码，最终做出了后来的 LMAX 交易所。过了一段时间，公司改了名，不再用 Tradefair 这个名字。几年前 Betfair 已经出售了对 LMAX 的控股权，CEO 主导了一次管理层收购，所以 LMAX 现在更独立了。我相信 Betfair 仍持有一部分股份，但现在主要由 CEO 和员工持有。

主持人：能举一个 LMAX 的典型业务场景吗？比如，什么是一个订单？

Mike Barker：好。我可能该先解释我们做什么，最开始漏讲了。我们的目标是做一个差价合约（CFD，contract for difference）类型的金融交易所，基本上可以交易任何资产：期权、期货、保证金交易的股票等等。这些是保证金产品，你不用付全款，本质上是一种衍生品。后来我们越来越聚焦于外汇领域，所以 LMAX 本身运营的是一个外汇交易所。我们为几个不同的市场板块提供服务：有所谓的专业交易所，主要面向经纪商和个人；有机构交易所，面向更高端的交易；还有银行间交易所，专门服务银行。

讲一点交易所怎么运作的背景。业内有几个比较通用的术语，我们常说的几个概念是：指令（instruction）、订单（order）、成交（trade）和执行（execution）。首先，有人会给我们发一条消息，说"我想下一个单"或者"我想撤一个单"，我们把这些叫作指令。我们从各类客户和供应商那里收到的消息都是指令。指令到达交易所后会被执行，产生我们所说的"执行"。执行就是交易所内部发生的某件事。执行的结果可能是创建一个订单，也可能是撤销、移除一个订单。订单是存在于交易所内部的实体，通常有价格和数量，价格可以没有。这些订单有的会在交易所里存在一段时间，有的会立即成交。随着订单的创建和销毁，我们会向用户发回执行报告（execution report）。

有意思的是订单本身。如果你发一条指令，下一个指定价格和数量的单，它就会进入订单簿，待在那里，带着一个价格。交易所负责根据订单到达的时间和报出的价格给这些订单排序：买单按出价从高到低排，卖单按要价从低到高排。这样你看到的永远是市场上的最优价格。一旦我们收到一个能和对手方价格匹配的订单，也就是买单和卖单价格相同或者交叉了，就真正发生交换：在我们这里是交换外币，也可以是用钱换某种商品。这时就产生了一笔成交，也就是双方交换了某样东西。这大概就是金融交易所里最主要的五个概念。

主持人：你们面对的主要非功能需求是什么？我能想到可扩展性，因为这是一个开放的交易平台。

Mike Barker：最重要的服务等级协议（SLA）是关于响应时间的。在金融交易所里，合作伙伴和客户最大的顾虑之一是风险。交易所给他们的交易带来的最大风险因素，就是我们响应一个订单所需的时间。如果他们发来指令说要下这么多的单，而我们能在很短的时间内回复"你的订单已下，现在以这个价格挂在市场上"，并且这个时间又短又可预测，就能减少他们承担的风险，尤其是外部大市场突然发生某个事件的时候。他们可以接着向市场下新单、调整价格或者撤掉现有报价，并且对这一来一回的耗时有把握。所以我们的核心 SLA 是延迟，尽量压低。刚起步时，我们的目标是典型响应时间大约一毫秒。有意思的是，那是六七年前的事，随着时间推移整个市场都在变，我们一直在追逐越来越低的延迟，好像停不下来。现在我们的典型延迟已经接近 100 微秒，目标整整提高了十倍。

主持人：我平时做的应用，延迟大概是一百毫秒、五十毫秒。

Mike Barker：是的，这是完全不同的玩法，非常有意思。这也是我非常喜欢在金融交易所工作的原因之一：它会让你接触到一整套以前可能从没考虑过的问题，逼着你去深入理解很多东西，操作系统、硬件、你用的软件平台、虚拟机、标准库、编译器等等。你最终要学的东西比在别处多得多。

主持人：是啊，我看过 Disruptor 的代码，感觉"哇，这完全是另一个世界"。不过我们稍后再说它。在写 Disruptor 之前，你们试过别的技术吗？我一听说金融交易所，第一反应是他们大概用 Erlang 或者 Akka 之类的。你们评估过其他方案吗？如果评估过，基准测试是怎么做的？

Mike Barker：那部分我没怎么参与，那是 Betfair 做的研究项目，用来试验各种形式的交易所。他们在这方面做了大量实验，从猛压数据库的方案，到我相信有的 Erlang 原型，还有现成产品的原型，我记得 IBM 也一度参与过。他们跑了很多不同的原型和不同类型的系统。至于基准测试怎么做的，我没法评论，因为我当时不在。但从中得出的有意思的结论是：第一，如果你想要快，数据就得放在内存里。想想当年做这些实验时，也就是大约十年前，典型的 Web 应用是怎么做的：人们做 Java 应用，通常有一个数据库，MySQL、Oracle 之类，然后有一个带业务逻辑的 Web 层，可能再用一个 ORM 映射工具。于是你的业务逻辑里有一份领域对象的表示，数据库里又有一份表示，两边来回搬数据。我老板对此有个很妙的比喻：这就像隔着信箱口用一双筷子吃晚饭。数据远在一处，逻辑远在另一处。而且几乎普遍成立的是，你越想让某个东西快，就越要让执行代码和数据本身挨在一起。Betfair 在他们自己的系统上其实已经有过这种经验，他们的系统非常依赖 Oracle 数据库，最后把大量逻辑搬进了存储过程，让逻辑靠近数据，省掉在执行处和数据存放处之间来回的开销。他们为 LMAX 交易所总结出的想法是：反过来把数据搬到逻辑旁边，让系统运行时的"记录系统"（system of record）就在内存里。

主持人：这个我们后面深入聊。在那之前，我想了解 LMAX 系统的上下文：主要用户是谁？它和哪些系统通信？

Mike Barker：我们最大的交易所是专业交易所，里面有两类市场参与者。第一类是做市商。在金融市场里，作为交易所，我们有责任维持一个有序的市场。我们必须确保即使行情往糟糕的方向走，也始终有流动性可供交易，始终有价格和数量。如果有人买了东西而价格在跌，我们要确保他确实能卖出去，止损离场，而不是赔光一切。做到这一点的办法之一，就是有一批做市商提供所谓的双边报价，也就是同时向市场报出买价和卖价。这些做市商是一些你可能听过的大银行，比如高盛、摩根大通、花旗、西太平洋银行这类大型银行。另一边则是基本上在和这些报价交易、彼此之间也互相交易的人。两者的区别在于：对做市商我们不做太多风控；而主要的专业用户会通过我们的经纪商进来，他们会把钱存在我们这里，我们和外部清算系统，比如主经纪商（prime broker）或清算所有合作关系。他们交易时，我们会监控他们花了多少钱、在市场上有哪些订单、是在赚钱还是亏钱。如果亏得太多，我们会启动各种风控措施给他们平仓，免得他们输光所有。这大概就是我们打交道的两类主要人群。

至于系统和什么通信：我们为这些客户提供了开放的 API，有好几种。一种是基于 Web 的类 REST API，上面还有用户界面；另外还有 FIX API。如果你没在金融行业干过，大概从没听说过 FIX，但它在整个金融行业里被广泛使用。它是一种面向 socket 连接的协议，不像 HTTP 那样无连接。你打开一个连接、登录，然后以全双工的方式双向流式传输：指令发上去，执行报告传回来。两类市场参与者的接入方式略有不同，但都可以通过 FIX 连到系统。

系统通信的另一个主要方面，是负责为我们的成交做清算的机构。在交易平台上，人们来买、来卖，但这些东西其实只是以 0 和 1 的形式存在。所有已发生的交易信息都会发给一组第三方，在外汇行业我们叫主经纪商，在其他金融板块则叫清算所之类。我们会把所有成交发给主经纪商或清算所，他们在一天结束时算出谁欠谁多少钱。想象有人花一百万美元买了点东西，又以一百万美元卖掉，再买别的，最终这些都会相互轧差抵销，各方之间真正需要转移的钱可能只有很少一点。这就是我们系统的三个主要接触点：清算，以及各类市场参与者。此外还有大量小的接入点：处理支付的系统、做信用检查和授权、确认客户身份的系统，还有 CRM 的接入，因为我们是通过 Salesforce 而不是在自己的平台上开通用户。任何大规模的业务都免不了要处理很多这样的小集成点。

主持人：LMAX 本身的主要组件有哪些？能先简单讲讲吗？后面我们再深入。

Mike Barker：好。我们说的两个主要部分是经纪商（broker）和交易所（exchange）。交易所我前面讲了一点，主要负责接收指令、管理订单、撮合订单产生成交。系统第二个重要部分是经纪商，负责管理风险。我们在经纪商里运行一个实时保证金系统，监控我们所说的"头寸"（position）。比如你出去花一千美元买胡萝卜，你现在就持有胡萝卜的头寸，胡萝卜价格涨跌，你就有盈亏。经纪商的工作是跟踪所有这些信息，算出你赚了多少、亏了多少，然后据此采取相应的动作。它还负责收取佣金，这是我们作为一门生意赚钱的方式。

这是两个主要组件。在它们背后还挂着一大堆辅助系统。交易所后面有一个叫交易报告（trade reporting）的系统，负责把所有成交发往各个清算目的地。还有历史行情数据和市场监察系统：市场运行、人们在交易时，你得能看着正在发生什么。我们有专门的市场运营人员做这件事，他们的工作一是确保市场有序，二是确保没人在搞内幕交易、抢先交易（front-running）或者洗钱。所以有很多工具用来实时分析市场，也能回溯过去，在客户提出疑问或者出现监管问题时调查发生过的事情。

主持人：抱歉，你继续。

Mike Barker：然后系统里还有很多其他部分，用来管理大量 CRUD 类的数据：管理交易品种、管理客户、管理用户账户。我们算是一种微服务架构，虽然有些人看了可能不会真把它叫作微服务。我们大约有 40 个不同的服务在运行，经纪商是一个，交易所是一个，还有更多支撑服务来做各种各样的操作。

主持人：那输入 Disruptor、输出 Disruptor、业务逻辑处理器，这些是怎么嵌进去的？

Mike Barker：我们的服务分好几种，主要有三类。一类我们叫网关（gateway），位于系统边缘，对外说某种协议，比如 FIX，或者面向 Web 之类的，我们也有处理邮件等等的网关。第二类叫通用服务，它们会和数据库打交道，主要管理 CRUD 类的操作：你给它发一条消息，它替你往数据库里存点东西或查点东西。第三类是我们的核心服务，本质上就是经纪商和交易所，它们正是用那种有两个 Disruptor 的架构构建的。它们接收消息，用日志（journaling）的方式持久化全部状态，运行单一的业务逻辑线程，把消息喂进去；业务逻辑执行时，再发出响应消息。

主持人：和大多数知名的架构风格相比，这种做法在追求低且可预测的延迟、高吞吐等特性上相当新颖。它主要是由"机械同理心"（mechanical sympathy）驱动的。我们 Software Engineering Radio 做过一期节目讲这个，但你能简单解释一下机械同理心是什么意思吗？

Mike Barker：好。这个词是 Martin Thompson 大量用到软件上的，但它最早来自一级方程式赛车，是 Jackie Stewart 提出来的。按照它在赛车里的原意，并不是说开发者或 F1 车手需要知道如何制造、组装一辆车，或者如何造一台电脑、写一个操作系统、造硬件，而是说开发者或 F1 车手需要对它如何运作有一定程度的同理心、一定程度的理解，尤其是理解它在什么情况下工作得最好：CPU 擅长什么样的操作，不擅长什么样的操作。

举个简单的例子：理解缓存架构如何运作。CPU 架构优化内存访问主要有三种途径。一是优化时间上相近的内存操作，即时间局部性：如果你在访问某个东西后不久又访问它，很可能会非常快，因为它在缓存里的概率更高。二是空间局部性：在内存中位置相邻的东西，你访问它们时更可能获得更好的吞吐，因为挨在一起的东西更可能都在缓存里。三是步长（striding）：如果你的访问模式是一致的，比如线性地访问数组，CPU 更有可能识别出这种步长规律，提前把一部分数据预取到缓存里。如果你在一大片内存空间里做非常分散的随机访问，就会发现这类操作比在较小内存区域上做顺序访问慢得多。你不必真正弄懂这些为什么会这样，但对"事情就是这样运作的"有一定的同理心，并能通过实验判断哪种可行、哪种不行，就能让你设计出在自己电脑上、在你部署的系统上跑得更好而不是更差的软件。

主持人：说到处理器缓存，如果我所有数据都在 L1 缓存里，和随机访问相比，大概能快几个数量级？

Mike Barker：我手头没有确切数字，但访问 L1 缓存里的东西大概只要一到三个 CPU 周期；如果要一路访问到主内存，可能要两百个周期左右，所以主内存和 L1 之间差了约两百倍。L3 大概在 40 到 60 个周期，所以即便 L1 和 L3 之间也差了很大的倍数，大约四十倍。在抽象层面研究这类问题的工作也很有意思。我才刚开始钻研的一个是"缓存无关算法"（cache-oblivious algorithms）。它的思路是：我们有这些缓存层级，而且每台机器都不一样；缓存无关算法提出了一个缓存层级的理论模型，以及一套数学方法，不再按操作次数来分析算法，而是假设有两层存储，一层快、一层慢，用必须访问慢速存储的次数来衡量算法的代价。这方面有一些有意思的数学，也有一些有意思的算法研究，表明从抽象层面理解缓存层级，可以让你设计出在真实硬件上跑得更快的算法。

主持人：你们在哪里、怎样实现了缓存无关算法？

Mike Barker：对我来说，这更多是一个研究方向，学术界在这方面有相当多的成果。不过，即便是顺序访问一个数组这样的事，也体现了缓存无关算法的思想：你假设缓存层级会对步长访问提供某种支持，在按步长访问时优化预取。这是应用缓存无关算法的一个非常简单的例子：如果你有一个数据数组，想对它做点什么，线性地遍历这个数组，而不是随机访问，会得到更好的结果。

主持人：说到数组，我们来聊聊 Disruptor。Disruptor 是什么？

Mike Barker：Disruptor 是我们写的一个小型库，用于在线程之间非常快速地传递消息。这里值得稍微回顾一下 LMAX 最初的架构。当我们研究怎样最好地构建交易所时，主要的收获是：我们想要一个几乎完全在内存中运行、以内存作为记录系统的系统。要让它高效运作，你仍然得有办法真正存储数据，因为不能只把一切放在内存里，机器关掉怎么办？数据总得以某种方式存下来。所以方法相当简单：把流入系统的所有消息按顺序存进一个持久化日志；如果发生崩溃或者需要重启机器，我们有一个快照形式的已知初始状态，先加载它，然后按原来应用的顺序把消息重放进系统，回到同样的状态。

当然，要让这件事正确运作有几个约束：你需要确定性的执行，必须避免调用 System.currentTimeMillis()，或者使用种子不固定的随机数生成器之类的东西，确保把消息重放进系统时能回到一致的状态。采用这种架构，我们得到的是一个非常异步的系统：消息进、消息出。系统有几个部分：业务处理、日志。我们还想要高可用，也就是有备机（secondary），接收同样的事件流，能在内存中以相同状态持有同样的数据集，用来做故障切换。所以我们要把消息发给备机，把消息写入日志，还要做业务逻辑处理，而且希望这三件事并发进行。它们之间需要一种顺序依赖：我们希望写日志和向备机复制完全并行，谁也不用等谁；但在处理某条消息之前，这两件事都必须完成。这样，在确认消息已经在另一个系统中得到保障、并且在本地写入日志之前，我们不会更新状态，也不会开始往外发消息。这就是我们想提供的保证。

我们最初的架构只用了标准的 Java 队列，就是标准 JDK 里那些。思路是：把消息发给日志系统，日志系统再发给复制系统，消息复制完成后再发给业务逻辑，由它来做实际工作。我想这常被称为 SEDA 架构，大概有二十来年历史了。但这种架构的缺点是一切都是串行的，而我们非常想让日志和复制并行运行。我们发现这两个阶段是系统中最昂贵的，而业务逻辑本身最终非常快：当你完全在内存中运行、使用优化得不错的数据结构、对业务模型想得比较清楚、代码也写得像样时，实际的业务逻辑会相当快，所有的开销都花在了日志和复制上。

所以我们发现，我们想要的不是像队列那样点对点的东西，即一个生产者、一个消费者，消息进来，在另一端被消费掉。我们真正想要的更像 JMS 里的 topic：当你发送一条消息时，那个数据结构可以有多个订阅者，以一种多播的方式拿到这条消息。这大概就是 Disruptor 这种在线程间传递消息的东西，和同样在线程间传递消息的队列之间的关键区别：你发出消息，然后把它多播给多个接收者。这让日志器和复制器可以并行运行，因为它们只需连接到环形缓冲区（ring buffer）：一条消息进入环形缓冲区，两个线程同时看到这条消息，处理的是同一份数据。

Disruptor 内置的另一个有意思的特性是依赖图（graph of dependencies）的概念。这是我们想要的第二个特性：我们希望能够声明"在确认复制和写日志都已完成之前，不要做业务逻辑"。我们通过序列号做到这一点。流经 Disruptor 的每一条消息都按严格递增的顺序获得唯一的序号。环形缓冲区上的每个消费者也有自己的序列号，表示它处理到了哪条消息。Disruptor 允许你这样设置消费者：这个消费者，在我们的例子里是业务逻辑，要被另外两个消费者"门控"（gated）。这意味着它会和其他消费者一样看到环形缓冲区上流出的消息，但会停下来等其他消费者先处理完消息，也就是等它们的序列号往上走；一旦被门控的处理器看到那些序列号前进了，它就可以继续处理这些消息。这样一来，复制的次数减少了，而在队列式的实现里，你要在所有这些线程之间把数据复制进复制出。它让我们能把那些昂贵的操作并行跑，同时拥有依赖图，根据之前已处理的内容约束事情发生的时机，从而提供可靠性保证。

主持人：环形缓冲区只是一个在启动时预先填充好的普通对象数组，对吗？

Mike Barker：对，没错。关于 Disruptor 以及我在 3.0 版本里做的工作，有意思的一点是，我们设法把环形缓冲区，也就是数据存储，和所有处理并发的代码完全分离开了。有意思的是，你其实可以把 Disruptor 几乎当成一个通用的序列器（sequencer）来用。默认实现提供的是环形缓冲区：你给 Disruptor 传一个工厂对象作为参数，Disruptor 会初始化一个对象环形缓冲区，并用那个工厂构造器把它们全部初始化好，相当于预先建好一大批对象。然后往 Disruptor 里放消息时，你可以复用数组里的这些对象。

主持人：这么做和机械同理心有关吗？

Mike Barker：是的。最初的原因是：我们做了大量优化之后，也就是我们建好了 Disruptor，去掉了所有的锁，无锁的部分我们待会儿可以聊，日志跑得很快，复制也运作良好，那时响应时间上最大的开销显然就是垃圾回收。我想几乎任何在托管环境里工作过的人都明白垃圾回收的代价。所以我们希望，如果我们决定这么做，这个东西就可以不产生任何垃圾。这就是关键所在，我们想让它以零垃圾的方式工作。这是预分配的原因之一。但你并不一定要预分配，它是"可选地零垃圾"的。环形缓冲区另一个有意思的地方是，你也可以把自己的数据结构放进去。

主持人：它之所以零垃圾，是因为我预先初始化了它？

Mike Barker：对，所有对象都是预先创建好的。我们的做法是在里面放一个表示消息的小对象，对象上有一些头部信息，末尾是一个字节数组。当我们从网络上收到数据时，只是取出当前位于 Disruptor 中的那个对象，把从网络收到的字节复制进 Disruptor 里早已预分配好的字节数组。在网络这一侧，我们有一个复用的缓冲区，直接传给网络调用，拿回一些数据，然后把数据复制进 Disruptor 中预分配的数组，再交给业务逻辑线程。所有这些缓冲区都是预先创建、反复复用的，所以在整个操作过程中根本没有分配，也就不产生垃圾。

主持人：好。那序列计数器呢？能解释一下它做什么，以及它和内存屏障、内存栅栏的关系吗？

Mike Barker：这就开始进入无锁、非阻塞算法的领域了。我们研究队列的时候有一些发现。我们对 JDK 里的各种队列做了相当多的研究，也写了自己定制的队列，花了不少时间优化，尽量不要频繁撞上锁。我们想避免的是锁竞争，因为我们发现，这其实是在线程间传递消息时最显著的开销之一。如果你用标准队列，底层会有一个锁对象，用条件变量通知等待中的线程有消息可用。消费者线程进入锁，如果没有消息，就拿到条件对象，等待信号；当有消息被发进队列时，生产者同样获取锁，拿到条件对象，通知所有在上面等待的线程有消息可用了。

我们刚开始时用的是稍旧一些的硬件，测出来这个过程大约要三十多微秒，这本身不算太糟。问题在于延迟的长尾：有时消息到达另一个线程、让这个通知操作生效，要花多达两毫秒甚至四毫秒，因为它必须一路进入内核，内核得去找到那个进程，唤醒它，让它重新运行起来，而它的缓存是冷的，还要做一堆上下文切换之类的事情才能把线程唤醒、重新跑起来。所以我们发现，要让系统达到我们想要的性能、我们所需的响应时间，还必须让 Disruptor 无锁，或者说可选地无锁。也就是可以声明：我愿意牺牲 CPU 周期和能效，来换取延迟或响应时间上的好处。

我们的做法是，让所有关乎内存安全、避免内存损坏、确保正确性的并发操作都用无锁算法完成，而序列就是这一切的核心。在 Java 内存模型以及其实大多数其他内存模型里，都有 happens-before（先行发生）、happens-after 的概念。大多数语言里都有特定的指令，让你可以说："这里是对某块内存的一批操作，现在我要做这个特定的并发操作，它保证前面所有这些操作都发生在这个操作之前。"之所以需要这样，是因为现代 CPU 和现代编译器被允许对你代码的顺序做一些自由处理。它们会看你用 Java、C 或者别的什么语言写的那一批指令，编译器或 CPU 可能会决定重排这些指令以获得更好的吞吐；通过各种优化，它可能会完全消除某些指令。CPU 有指令级并行之类的东西，可能有好几个执行单元，它会说："我看到这些指令了，我有空闲的执行单元，就把它们并行跑。"结果它们可能在不同的时间点完成。所以内存模型的作用，就是让你对此有某种推理依据或某种控制。

在我们这里，具体说的是把数据写进 Disruptor 里的这些对象：我们从网络复制字节，设置一些带有这条消息元信息的头部字段，所有这些操作都可能在一定程度上被重排。我们要确保的是，在接收端、在消费者那里，不会看到写了一半的信息、损坏的信息，或者还没真正到达的信息。所以，当我们把想要的数据填满消息之后，再递增序列号。而这条指令恰好是所谓的栅栏指令，也就是内存屏障。我们用的是所谓的 store-store 栅栏。它的意思是：如果你有一大堆对内存的写入，也就是我们往 Disruptor 中各个对象里写数据，那么在这个点上，所有对那片内存的写入都会在这一次写入之前完成。于是在消费端，我们做的第一件事就是读取序列号。如果消费者看到序列号变了，它就知道在序列号递增之前发生的所有写操作对它都是可见的、正确的、没有损坏的。在读取端，相应地有所谓的 load-load 栅栏：我知道读了这个之后，我后续从 Disruptor 读取数据的所有操作，都不会被重排到我第一次读序列号之前。所以序列号的写入是一个 store-store 屏障，阻止任何在它之后的写入跑到前面；它的读取是一个 load-load 屏障，意味着我对那些数据的任何读取都不会发生在这次读取之前。这使得数据能在两个线程之间被正确地传递。

主持人：那环形缓冲区只有一个写入者，还是有多个？如果有多个写入者，就又有竞争了，对吗？

Mike Barker：没错。我们其实两种都支持。很多时候你没法回避这个事实：系统里可能有多个线程想往同一个环形缓冲区放数据。我们在不少场景里都遇到过。比如我们其实在很多不同的服务里都用 Disruptor，不仅仅是核心服务，在 Web 层也用。就像你说的，任何 Web 应用都总有成百上千个线程在处理各种 Web 请求，它们都要写进同一个环形缓冲区。我们的确提供了单写入者场景的选项：设置 Disruptor 时，如果你知道在你的场景里只有一个线程在写，这在一些高吞吐网络应用里很常见，我自己就经常只用一个非阻塞 IO 的网络线程，那你可以声明只支持单线程生产者，这样你往往能从 Disruptor 得到好上一个数量级的性能和吞吐。如果你做不到这个保证，默认就用多生产者模式，它多了几条指令，必须用比较并交换（compare-and-set，CAS）指令，确保各个生产者在 Disruptor 中各自拿到一个独立的槽位。所以这样做会有额外开销。但在这种场景下用 Disruptor 而不是一般的竞争方式，一个好处是它做的是绝对最少的工作，至少是我们能压榨出来的最少，把竞争的代价降到实际上只有一条 CAS 指令。如果你不用 Disruptor 这样的东西，而是试图在多个线程中同时做一大堆操作，最后就得用锁，或者其他稍微棘手的并发控制形式，竞争区间也可能长得多。所以把一切都塞进 Disruptor，再用单个消费者线程非常快地处理这些事件，好处就是能把竞争量降到非常小。

主持人：好。有一点我觉得特别有意思：环形缓冲区的大小总是 2 的幂，这和处理器支持的操作有关。能解释一下吗？

Mike Barker：好，这个挺有意思的。根本原因在于，环形缓冲区是一个相当直接、简单的环形缓冲区：它有一个大小，序列号单调递增。序列号是一个 64 位有符号整数，会一直增大，能涨多大就涨多大。当我想往环形缓冲区放一条消息时，典型的操作是：拿序列号做取模运算，算出余数，然后把值放进余数所指向的槽位，这是相当典型的操作。难点在于，如果大小不是 2 的幂，就必须用取模运算，而它实际上就是一次除法，开销和除法基本一样，而除法特别慢。我一下子记不清确切数字，但在现代 Intel CPU 上要几十个周期。我们用 2 的幂，是因为如果除数是 2 的幂，就可以做一个优化，用位运算算出余数：把除数减一，然后对输入值做一次非常快的掩码运算，就得到了余数。这只在除数是 2 的幂时适用。那条指令只要一个周期，而且和其他指令的流水线衔接得非常好，所以性能代价差别很大。差别大到连标准 JDK 里的 Java HashMap 都转向了以 2 的幂为大小的数组。在哈希表理论里，人们常说数组大小要用质数，因为元素分布更好；但实际上除法运算的开销意味着，用 2 的幂大小的数组，再去下功夫设计统计上更好的哈希算法、让元素在哈希表中分布得更均匀，反而更高效。这是机械同理心另一个有意思的例子：理论告诉你一回事，硬件的实际机制告诉你另一回事。

主持人：是啊，有很多我觉得非常有意思的东西。我记得 Martin Thompson 也写过博客文章，详细解释了这些，对吧？

Mike Barker：是的。

主持人：我也会把它们放进节目说明里。我想结束 Disruptor 的话题，转到业务逻辑处理器。你说过好的领域模型对性能非常重要，为什么？什么才算好的领域模型？

Mike Barker：这是个有意思的问题，怎么定义"好"。来到 LMAX 学到的一件有意思的事，也是在那里工作时被反复灌输的，就是对领域建模有多重要。这一点我到了那里才真正领会：一旦你开始按业务用户的方式思考问题，代码里有了那些重要的概念，这大概就是 DDD 里"提炼"（distillation）的那一部分。一旦真正重要的概念在代码里得到了体现，你就更可能构建出一个只做它该做的事情的系统。这个概念比较微妙，很难给出非常具体的示例或论证。但我经常在一些系统里工作过，我自己当然也构建过这样的系统：系统中对领域模型并没有真实的表示，结果软件不得不做一些和业务逻辑其实无关的工作，而这是有代价的。所以，好的领域模型能提升性能，总体的理论是：如果你的代码建模得好、能很好地表达问题，你就只做解决业务问题真正需要做的事。这种微妙之处很难给出特别有力的例子，但在这个领域工作了很长时间后，我慢慢开始有了体会。对我们来说，这意味着我前面讲的那些术语，订单、成交、指令、执行、执行报告，在我们的系统里都有对应的领域对象。所以如果你想"我需要知道这个下单指令在哪儿、长什么样、做什么"，你真的可以在代码里搜索这些概念并找到它们：你能找到订单对象，而它们之间的关系确实就是按业务领域所要求的方式建模的。

主持人：好。如果所有数据都挨着操作，那也意味着你可以把它们加载进处理器缓存。

Mike Barker：是的，这很大程度上就是关于把记录系统放在内存里的事。这样做真正好的地方在于，我们能真正采用一种非常领域驱动的方式，因为没有额外的开销。比如说，如果我们的持久化存储是数据库，就会有一份内存表示和一份数据库表示，还有一大堆映射之类的东西。而我们只需要思考领域模型，直接写出表示它的对象。因为内存中的表示就是系统的真实记录，我们就可以用这些术语来思考。如果想表示对象之间的关系，表示起来非常简单：我只要建一个字段，如果是通过键关联到另一组对象，那就是一个 map；或者是一个 list；或者就是对另一个对象的直接引用。所以，在设计对象模型时你可能会在图上画出的那些关系，在系统里都可以非常容易地表示出来，不必把它们建模成数据库约束之类的东西。这让事情保持得相当简单，把领域表示真正构建出来是相当直接的。

主持人：领域类长什么样？比如说一个普通的类，你用一个 int，让 JVM 去分配内存，还是你们也会做一些优化，比如通过 sun.misc.Unsafe 之类的直接分配内存？

Mike Barker：业务逻辑方面，我们就是直接用普通的领域对象。这里大致有两条路可走。很多人，尤其是在金融领域和高性能领域，正在转向基本上自己写一套对象模型系统，建立在 direct ByteBuffer 或者内存映射的 ByteBuffer 之上，用 Unsafe 和各种操作。我们确实研究过，将来也许会这么做。我们没这么做的原因之一是，这么做的理由归根结底只有垃圾回收，也就是能按自己想要的方式管理内存。在步长访问、把对象放在一起、控制内存布局等方面也有一些别的好处，但关键似乎还是垃圾回收。几年前我们面临过怎么解决垃圾回收问题的选择，因为那确实是个问题。几年前我们做了相当多的优化，把交易所系统的 GC 停顿降到了大约五毫秒，其他一些系统稍多一点。最后我们决定迁移到 Azul Systems 的 Zing 平台，这让我们可以继续直接用标准的 Java 对象，而且它基本消除了绝大部分 GC 停顿。我们偶尔会有非常罕见的一毫秒停顿，但大多数时候 GC 周期都在一到两百微秒的范围内。所以它消除了响应时间上这项非常显著的开销，让我们能继续用一些更简单的对象建模方式。我想如果我们坚持用 Oracle 的 JVM，大概就得走那条路：用堆外内存、摆弄 direct ByteBuffer，为交易所里领域模型的一些核心部分自己写内存管理。

主持人：好。我想就此结束 Disruptor 和业务逻辑处理器的话题，聊点完全不同的。Dave Farley 是《持续交付》（Continuous Delivery）一书的作者之一，他也在 LMAX 工作过。我想那本书的大部分章节都基于他在 LMAX 的工作，对吗？

Mike Barker：是的。我想书里很多章节基于他多年的经验，既有在 ThoughtWorks 的，也有在 LMAX 的。而且我想持续交付的很多应用实践，都是在 LMAX 尝试、实验、摸索出来的。这是我非常感激的一点，也意识到自己非常幸运，一开始就在 LMAX 和 Dave Farley 这样的人共事，从中学到了难以置信多的东西。让我们的工作轻松很多的一点，大概是我们起步就站在一个好位置上：从一开始就做测试驱动开发、验收测试驱动开发，非常注重自动化的端到端测试，非常注重确保持续集成运作良好，很早就搭起持续交付流水线的各个环节：加入二进制制品库，构建部署工具，确保部署到测试环境的方式和部署到生产系统尽可能接近，甚至完全一样。这些都是持续交付，也就是他写的那本书中，非常关键的一些技术实践。

主持人：那你们大概也有自动化性能测试吧？

Mike Barker：是的，有。我数过，我们大概有八种不同类型的自动化测试：自动化单元测试、集成测试、验收测试、性能测试、静态分析、数据库测试，可能还有几种我一下子想不起来。是的，我们有两个层次的自动化性能测试。一种是大型端到端性能测试，跑一次大约 40 到 45 分钟：我们在一套和生产系统相当的硬件上启动整个系统的完整实例，每秒跑上万笔交易，在一小时的时间里监控响应时间，寻找个别离群值，试图找出响应时间耗在了哪里。还有一种是较小的、微基准测试风格的测试：我们拿出单个组件，比如日志、基础设施的各个部分、各个业务逻辑组件，把它们当作较小的类来测，几乎就像针对性能的单元测试，确保这些单个组件也足够快。

主持人：那你们还得以某种方式测试所有机械同理心相关的东西，比如垃圾回收有没有启动之类的？

Mike Barker：是的。有意思的是，我们在端到端性能测试中做的很多事情，和我们在生产环境中做的非常相似。因为我们理想中希望的是，在性能环境中跑一轮，收集海量指标。显然我们会测量端到端的交易时间，我们捕获流经系统的每一条消息的交易时间，然后尽量拉出各种各样的指标：显然有消息流经的每个服务的垃圾回收停顿时间；我们想找出写磁盘时的延迟、写网络时的延迟、业务逻辑内部的延迟；如果触发了某个集合扩容，或者某条路径在算法上很糟糕，我们希望能找出来。而我们也希望在生产环境中能做同样的事，所以希望性能环境和生产环境有同样的监控信息，我们在这上面投入了很多精力。我们测量交易时间的方式，是用一个工具通过 pcap 观察网络上流过的消息，重建这些数据流，然后找出输入消息和对应的输出消息，测量两者的时间差。生产环境里也运行着同一套基础设施，这让我们在测量时能尽可能确保两个环境测的是完全相同的东西。

主持人：好，很棒。有没有什么重要的问题我忘了问，你想提一下？

Mike Barker：有。简单回到持续交付和自动化验收测试的话题。显然，作为一个团队，我们在性能之类的方面投入了大量考虑，但我们在 LMAX 作为一个团队所做的事情中，最重要的方面大概是自动化测试，以及我们所实施的自动化测试的程度。我有一个不太科学的猜想或者说观察：我们是一个非常敏捷的团队，从一开始就践行敏捷，而我注意到，随着时间推移，我们真的抛弃了很多实践。比如我们没有 Scrum Master，不怎么做估算，我们仍然有看板，但用得相当轻量。我所见过的敏捷里很多规划和项目管理方面的东西，是为了照顾那些可能没有非常强的自动化测试的团队。而我们这种能力，只要做一个改动，放进持续集成环境，就能非常有信心地确认我们做的东西是正确的、足够快的，上线到生产时也是安全的，这使得很多其他类型的项目管理手段，或者关于什么时候发布什么的讨论之类的细节，似乎都不需要了。你其实可以用自动化测试来弥补项目管理某些方面的缺失。所以对我来说，就 LMAX 而言，关键是我们的自动化测试做得有多好，以及它给我们团队带来了多大的好处。

主持人：我记得听 Dave Farley 讲过这个，对你们搭建的那一整套基础设施印象非常深。搭建这样的基础设施花了多久？还是说，它就是随着时间慢慢长出来的，现在你们有了一个非常先进的、用测试覆盖一切的系统？

Mike Barker：我想这个问题的答案大概是：等我们做完了再告诉你。我们已经建设了很长时间。Dave 做过一些非常出色的演讲，讲我们构建的一些东西，但即便在那之后，我们还在继续构建越来越多的工具，帮助我们理解自动化测试。构建大量自动化测试时最大的挑战之一，是那些间歇性失败：一切看起来都对，但某个测试有时失败、有时通过，弄清楚为什么会这样可能是真正的难题。现在我们的系统已经有了非常可观的自动化测试覆盖，这大概是我们最大的挑战：把间歇性问题挤压出去，努力做到构建持续保持绿色，这是我们花最多精力的地方。我偶尔会做一些关于自动化测试的演讲，总是让我无比震撼的，是我们团队为改进它所付出的努力。我看着一张图，上面是我们所说的"每月绿色构建数"，也就是一个月里整套端到端验收测试套件全部通过的次数。三四年前我们刚开始统计时，这个数字是个位数，零、一或者二；而最近三四个月，这个数字是九百到一千。这是惊人的转变，是多年努力的结果。我们确实投入了大量精力让它运作起来，但收益远远超过了这些投入。

主持人：可以想象。如果你完全确信随时可以把任何东西推上生产，就不会再有压力了，我觉得这真的很棒。

Mike Barker：是的。它还有一个很好的地方：我们也有一个测试团队。用 Dave Farley 的话说，人不擅长写 for 循环。人聪明、有创造力、有智慧，但非常不擅长一遍又一遍地做同样的事并且每次都做得完全正确。如果你的测试人员的工作是照着测试脚本一遍遍重复，那是对人的极大浪费。我们更希望测试人员发挥创造力，想出新的、有意思的办法来搞垮我们的系统，我想业内很多人把这叫作探索性测试。这是拥有大量自动化测试的另一个好处：测试人员可以专注于有意思的部分，想出新颖、有创意的办法让系统出错，于是我们能修复这些问题，围绕这些想法补上测试，进而提升系统的质量。

Mike Barker：不客气，非常感谢邀请我。
