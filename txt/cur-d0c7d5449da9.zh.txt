编程 Agent 的组成部分
副标题：编程 Agent 如何借助工具、记忆和代码仓库上下文，让大模型在实践中更好用

在这篇文章里，我想讲讲编程 agent 和 agent harness（智能体外壳/运行框架）的整体设计：它们是什么、如何运作、各个部件在实践中如何组合在一起。我的《从零构建大语言模型》（Build a Large Language Model (From Scratch)）和《从零构建推理模型》（Build a Large Reasoning Model (From Scratch)）两本书的读者经常问起 agent，所以我觉得写一篇可供随时引用的参考文章会很有用。

更宽泛地说，agent 之所以成为重要话题，是因为实用大模型系统近来的许多进展并不只是来自更好的模型，而在于我们如何使用模型。在很多真实应用里，外围系统——比如工具调用、上下文管理和记忆——发挥的作用和模型本身一样大。这也有助于解释，为什么 Claude Code 或 Codex 这样的系统，会比在普通聊天界面里使用同一个模型显得强大得多。

本文中，我将列出编程 agent 的六个主要构建模块。

## Claude Code、Codex CLI 以及其他编程 Agent

你大概已经熟悉 Claude Code 或 Codex CLI，不过为了铺垫一下：它们本质上是一种 agent 式编程工具，把大模型包裹在一个应用层里——也就是所谓的 agent harness——从而在编程任务上更方便、表现更好。

编程 agent 是为软件工作而设计的，其中值得关注的不仅是选用哪个模型，还有外围系统，包括代码仓库上下文、工具设计、提示词缓存的稳定性、记忆以及长会话的连续性。

这个区分很重要，因为当我们谈论大模型的编程能力时，人们往往把模型、推理行为和 agent 产品混为一谈。不过在进入编程 agent 的细节之前，我先简要介绍一下几个更宽泛的概念——大模型、推理模型和 agent——之间的区别。

## 关于大模型、推理模型与 Agent 之间的关系

大模型（LLM）是核心的"预测下一个 token"的模型。推理模型仍然是大模型，只不过通常经过训练和/或提示，会在推理阶段花更多计算在中间推理、验证或在候选答案中搜索上。

agent 是建立在其上的一层，可以理解为围绕模型的一个控制循环。通常，给定一个目标后，agent 层（或者说 harness）会决定接下来检查什么、调用哪些工具、如何更新自身状态、何时停止，等等。

粗略地说，可以这样理解它们的关系：大模型是引擎，推理模型是加强版的引擎（更强，但用起来更贵），而 agent harness 帮助我们[驾驭]这个模型。这个类比并不完美，因为传统大模型和推理大模型也可以作为独立模型使用（在聊天界面或 Python 会话中），但我希望它传达了要点。

[图 2：传统大模型、推理大模型（推理模型）以及被 agent harness 包裹的大模型之间的关系。]

换句话说，agent 就是在某个环境中反复调用模型的那个系统。

简而言之，可以这样概括：

* 大模型：原始模型
* 推理模型：经过优化、会输出中间推理过程并更多地自我验证的大模型
* Agent：一个使用模型加上工具、记忆和环境反馈的循环
* Agent harness：围绕 agent 的软件脚手架，负责管理上下文、工具使用、提示词、状态和控制流
* 编程 harness（coding harness）：agent harness 的一个特例，即专为软件工程打造的任务专用 harness，负责管理代码上下文、工具、执行和迭代反馈

如上所列，在 agent 和编程工具的语境下，还有两个流行术语：agent harness 和（agent 式）coding harness。coding harness 是围绕模型、帮助它高效编写和修改代码的软件脚手架；agent harness 则更宽泛一些，并不专门针对编程（比如可以想想 OpenClaw）。Codex 和 Claude Code 可以算作 coding harness。

总之，更好的大模型为推理模型（需要额外训练）提供了更好的基础，而 harness 则能从推理模型身上榨出更多能力。

当然，大模型和推理模型本身（没有 harness）也能解决编程任务，但编程工作只有一部分是生成下一个 token。很大一部分工作在于浏览代码仓库、搜索、查找函数、应用 diff、执行测试、检查报错，以及把所有相关信息保持在上下文里。（写代码的人大概知道这是很费脑的工作，这也是为什么我们不喜欢在写代码时被打断 :)）。

[图 3：一个 coding harness 由三层组成：模型家族、agent 循环和运行时支撑。模型提供"引擎"，agent 循环驱动迭代式的问题求解，运行时支撑提供底层管道。在循环中，"观察"（observe）从环境收集信息，"检查"（inspect）分析这些信息，"选择"（choose）决定下一步，"行动"（act）执行它。]

这里的要点是：一个好的 coding harness 能让推理模型和非推理模型都显得比在普通聊天框里强得多，因为它在上下文管理等方面提供了帮助。

## 编程 Harness

如上一节所说，当我们说 harness 时，通常指的是围绕模型的软件层：它负责组装提示词、暴露工具、跟踪文件状态、应用修改、运行命令、管理权限、缓存稳定的前缀、存储记忆，等等。

如今使用大模型时，相比直接向模型发提示或使用网页聊天界面（更接近"和上传的文件聊天"），正是这一层塑造了大部分用户体验。

在我看来，如今各家大模型的原版能力已非常接近（例如 GPT-5.4、Opus 4.6 和 GLM-5 等的原版），因此 harness 往往会成为让一个模型比另一个更好用的决定性因素。

这只是推测，但我怀疑，如果把最新、能力最强的开放权重大模型之一（比如 GLM-5）放进一个类似的 harness 中，它很可能可以和 Codex 里的 GPT-5.4 或 Claude Code 里的 Claude Opus 4.6 表现相当。话虽如此，针对 harness 做一些专门的后训练通常还是有益的。例如，OpenAI 过去就分别维护了 GPT-5.3 和 GPT-5.3-Codex 两个版本。

## 1. 实时的代码仓库上下文

这可能是最显而易见的组件，但也是最重要的组件之一。

当用户说"把测试修好"或"实现 xyz"时，模型应该知道自己是否身处一个 Git 仓库、在哪个分支上、哪些项目文档里可能有说明，等等。

这是因为这些细节常常会改变或影响什么才是正确的操作。例如，"把测试修好"并不是一条自足的指令。如果 agent 看到了 AGENTS.md 或项目 README，它可能就会知道该运行哪个测试命令，等等。如果它知道仓库根目录和目录布局，就能去正确的地方查找，而不是瞎猜。

此外，git 分支、状态和提交记录也有助于提供更多上下文，说明当前有哪些改动在进行中、应该把注意力放在哪里。

[图 6：agent harness 首先构建一份简短的工作区摘要，再与用户请求合并，以提供额外的项目上下文。]

要点是：编程 agent 在开始任何工作之前，会先收集信息（作为工作区摘要的"稳定事实"），这样它就不会在每次收到提示时都从零开始、毫无上下文。

## 2. 提示词结构与缓存复用

一旦 agent 掌握了仓库的概况，下一个问题就是如何把这些信息喂给模型。上图展示了一个简化的视图（"合并后的提示词：前缀 + 请求"），但在实践中，每次用户提问都重新拼接并重新处理工作区摘要是相当浪费的。

也就是说，编程会话是高度重复的，agent 的规则通常保持不变，工具描述通常也不变，甚至工作区摘要通常也（基本）不变。主要的变化通常是最新的用户请求、最近的对话记录，或许还有短期记忆。

"聪明"的运行时不会在每一轮都把所有内容重建成一个巨大的、不加区分的提示词，如下图所示。

[图 7：agent harness 构建一个稳定的提示词前缀，加上不断变化的会话状态，然后把合并后的提示词喂给模型。]

与第 1 节的主要区别在于：第 1 节讲的是收集仓库事实；这里我们关心的是如何为反复的模型调用高效地打包和缓存这些事实。

"稳定提示词前缀"中的"稳定"指的是其中包含的信息变化不大。它通常包括通用指令、工具描述和工作区摘要。如果没有重要变化，我们不想在每次交互时都浪费算力从头重建它。

其他部分则更新得更频繁（通常每一轮都更新），包括短期记忆、最近的对话记录和最新的用户请求。

简而言之，"稳定提示词前缀"的缓存，就是聪明的运行时会尽量复用这一部分。

## 3. 工具的访问与使用

从工具访问和工具使用开始，事情就不那么像聊天、而更像 agent 了。

普通模型可以用文字建议你运行哪些命令，但 coding harness 中的大模型应该做一件范围更窄、也更有用的事：真正能够执行命令并取回结果（而不是由我们手动运行命令再把结果粘贴回聊天里）。

不过，harness 通常不会让模型随意即兴发挥任意语法，而是提供一份预先定义好的、带名字的允许工具清单，每个工具都有清晰的输入和明确的边界。（当然，像 Python 的 `subprocess.call` 这样的东西也可以包含在内，这样 agent 也能执行范围很广的任意 shell 命令。）

工具使用的流程如下图所示。

[图 8：模型输出一个结构化的动作，harness 对其进行校验，必要时请求批准，然后执行，并把有长度限制的结果反馈回循环中。]

为了说明这一点，下面是使用我的 Mini Coding Agent 时用户通常看到的界面示例。（它没有 Claude Code 或 Codex 那么漂亮，因为它非常精简，只用纯 Python、没有任何外部依赖。）

[图 9：Mini Coding Agent 中工具调用审批请求的示意。]

在这里，模型必须选择一个 harness 能识别的动作，比如列出文件、读取文件、搜索、运行 shell 命令、写文件等等。它还必须以 harness 能够检查的格式提供参数。

所以当模型请求做某件事时，运行时可以先停下来，执行一些程序化的检查，比如：

* "这是已知的工具吗？"
* "参数合法吗？"
* "这需要用户批准吗？"
* "请求的路径到底在不在工作区内？"

只有通过这些检查之后，才会真正执行任何操作。

运行编程 agent 当然有一定风险，但 harness 的检查也提高了可靠性，因为模型不会执行完全任意的命令。

此外，除了拒绝格式错误的动作和设置审批关卡之外，还可以通过检查文件路径，把文件访问限制在仓库之内。

从某种意义上说，harness 给模型的自由更少了，但同时也提高了可用性。

## 4. 尽量减少上下文膨胀

上下文膨胀并不是编程 agent 独有的问题，而是大模型普遍面临的问题。当然，如今大模型支持的上下文越来越长（我最近也写过让长上下文在计算上更可行的各种注意力变体：https://magazine.sebastianraschka.com/p/visual-attention-variants），但长上下文仍然昂贵，而且还会引入额外的噪声（如果有大量无关信息的话）。

在多轮对话中，编程 agent 比普通大模型更容易出现上下文膨胀，因为会反复读取文件、产生冗长的工具输出、日志等等。

如果运行时把这些内容全部原样保留，可用的上下文 token 很快就会耗尽。因此，一个好的 coding harness 在处理上下文膨胀方面通常相当讲究，远不止像普通聊天界面那样简单地截断或总结信息。

从概念上讲，编程 agent 中的上下文压缩可能如下图所示那样运作。具体来说，我们是把上一节图 8 中的 clip（第 6 步）部分再放大一些来看。

[图 10：大段输出会被截短，较早的读取会被去重，对话记录在送回提示词之前会被压缩。]

一个最小化的 harness 至少会使用两种压缩策略来处理这个问题。

第一种是截短（clipping），用来缩短长文档片段、大段工具输出、记忆笔记和对话记录条目。换句话说，它防止任何一段文字仅仅因为碰巧很啰嗦就占满提示词预算。

第二种策略是对话记录的精简或总结，把完整的会话历史（下一节会详细讲）变成一份更小、可以放进提示词的摘要。

这里的一个关键技巧是：让最近的事件保留更丰富的细节，因为它们更可能与当前步骤相关；而对较早的事件压缩得更狠，因为它们很可能没那么相关。

此外，我们还会对较早的文件读取进行去重，这样模型就不会仅仅因为某个文件在会话早期被读过多次，就一遍又一遍地看到相同的文件内容。

总的来说，我认为这是优秀编程 agent 设计中被低估的、枯燥的部分之一。很多表面上的"模型质量"，其实是上下文质量。

## 5. 结构化的会话记忆

在实践中，这里讲的 6 个核心概念彼此高度交织，不同的小节和图示只是以不同的侧重点或缩放程度来讲它们。上一节我们讲的是在构建提示词时如何使用历史，以及如何构建紧凑的对话记录。那里的问题是：下一轮应该把多少过去的内容送回模型？所以重点在于压缩、截短、去重和时间上的远近。

而这一节——结构化的会话记忆——讲的是历史在存储时的结构。这里的问题是：agent 会长期保留什么作为永久记录？所以重点在于：运行时会把一份更完整的对话记录作为持久状态保存下来，同时还有一个更轻量的记忆层，它更小，会被修改和压缩，而不只是不断追加内容。

总结一下，编程 agent 会把状态分成（至少）两层：

* 工作记忆：agent 显式维护的、小而精炼的状态
* 完整对话记录：涵盖所有用户请求、工具输出和大模型的回复

[图 11：新事件会被追加到完整对话记录中，并被总结进工作记忆。磁盘上的会话文件通常以 JSON 文件存储。]

上图展示了两个主要的会话文件——完整对话记录和工作记忆——它们通常以 JSON 文件的形式存储在磁盘上。如前所述，完整对话记录保存全部历史，即使关闭 agent 也可以恢复。工作记忆更像是一个精炼版本，保存当前最重要的信息，这和紧凑对话记录有一定关系。

但紧凑对话记录和工作记忆的职责略有不同。紧凑对话记录用于重建提示词，它的任务是给模型一份压缩过的近期历史视图，让模型不用每一轮都看完整记录也能把对话继续下去。工作记忆则更多是为了任务的连续性，它的任务是保存一份小的、显式维护的摘要，记录跨轮次都重要的东西，比如当前任务、重要文件和最近的笔记。

在上图第 4 步之后，最新的用户请求连同大模型的回复和工具输出，会在下一轮作为一个"新事件"同时记录进完整对话记录和工作记忆——为了让图不那么杂乱，这一步没有画出来。

## 6. 使用（有边界的）子 Agent 进行委派

一旦 agent 拥有了工具和状态，下一个有用的能力就是委派。

原因在于，它让我们可以通过子 agent 把某些工作拆成子任务并行处理，从而加快主任务的进度。例如，主 agent 可能正在处理一项任务，同时还需要一个旁支问题的答案，比如某个符号是在哪个文件里定义的、某个配置写了什么、某个测试为什么失败。把这些拆出去作为有边界的子任务很有用，而不是强迫一个循环同时扛起所有的工作线索。

（在我的 mini coding agent 中，实现更简单，子 agent 仍然是同步运行的，但背后的思想是一样的。）

子 agent 只有继承了足够的上下文才能做实际的工作，才有用处。但如果不加以限制，就会出现多个 agent 重复劳动、修改同一批文件，或者继续派生更多子 agent 等问题。

所以棘手的设计问题不只是如何派生一个子 agent，还在于如何约束它 :)。

[图 12：子 agent 继承足够的上下文以发挥作用，但它运行在比主 agent 更严格的边界之内。]

这里的诀窍是：子 agent 继承足够有用的上下文，但同时也受到约束（例如只读、限制递归深度）。

Claude Code 很早就支持子 agent 了，Codex 则是最近才加入。Codex 一般不会强制子 agent 进入只读模式，它们通常会继承主 agent 的大部分沙箱和审批设置。因此，边界更多体现在任务范围、上下文和深度上。

## 它与 OpenClaw 相比如何？

OpenClaw 可能是一个有趣的比较对象，但它并不完全是同一类系统。

OpenClaw 更像是一个本地的、通用的 agent 平台，也能写代码，而不是一个专门的（终端）编程助手。

它与 coding harness 仍有若干重叠之处：

* 它在工作区中使用提示词和指令文件，比如 AGENTS.md、SOUL.md 和 TOOLS.md
* 它保存 JSONL 格式的会话文件，并包含对话记录压缩和会话管理功能
* 它可以派生辅助会话和子 agent
* 等等

不过如上所述，二者的侧重点不同。编程 agent 是为这样的场景优化的：一个人在代码仓库里工作，让编程助手高效地检查文件、修改代码和运行本地工具。OpenClaw 则更侧重于在多个聊天、频道和工作区中运行许多长期存在的本地 agent，编程只是其中一项重要工作负载。
