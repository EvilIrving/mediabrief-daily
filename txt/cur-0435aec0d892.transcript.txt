Philip Winston：欢迎收听 Software Engineering Radio，我是 Philip Winston。今天和我在一起的是 Maxim Fateev。Maxim 是 Temporal 的联合创始人兼 CEO。他曾在亚马逊、微软、谷歌和 Uber 担任领导职务。他在亚马逊领导开发了 AWS Simple Workflow Service（简单工作流服务），在 Uber 领导开发了开源的 Cadence 工作流。Maxim 拥有计算机科学和物理学学位。今天我们要聊的是用分布式系统来自动化业务流程，不过先从一个可能不是每个人都熟悉的术语说起：持久执行（durable execution）。Maxim，什么是持久执行？它为什么是一种有用的抽象？

Maxim Fateev：持久执行是一种新的抽象，算是我们引入的，现在还不太广为人知，但我认为每个工程师都绝对应该把它放进自己的工具箱里。这个想法相当直接。想象一个运行时，它始终把你代码执行的完整状态持久化保存。这意味着如果某个进程崩溃，或者发生了任何其他基础设施故障，比如网络事件、停电等等，问题解决之后你的代码会继续运行。或者如果进程崩溃，它会被迁移到另一个进程上。而如果整个区域都宕机了，只要它恢复，你的代码就会继续执行。我说的不是进程，而是完整的状态。举个例子，如果你有一个函数阻塞了——比如说它要执行三个 API 调用 A、B、C，阻塞在 B 上，然后这个进程崩溃了——这次执行会迁移到另一台机器上，它仍然阻塞在 B 上，B 的结果可能两天后才返回，然后它会继续执行。所以所有局部变量、整个状态，包括阻塞中的调用，始终都被完整保留。

Philip Winston：很好。我们肯定会深入讨论它是如何实现的。不过在那之前，我们先聊一点历史，看看是怎么走到今天的。但先描述一下现在的 Temporal 是什么样的吧。

Maxim Fateev：Temporal 是一个开源项目，采用 MIT 许可证，所以你完全可以自己运行它，包括 SDK 库和保存状态的后端服务器。这个项目是我们在 Uber 启动的，最初叫 Cadence。四年前我们创办了一家公司，fork 了这个项目，取名 Temporal。它已经在高规模的生产环境中运行了七年，被全世界数千家公司用于关键任务应用。

Philip Winston：我们再往前追溯一点。在 Cadence 之前，你在亚马逊做 Simple Workflow Service。能讲讲那个项目是怎么开始的、目标是什么吗？

Maxim Fateev：我可能要从更早说起。我 2002 年第一次加入亚马逊，那时亚马逊正在积极地从单体架构迁移到微服务架构。当时还不叫微服务，就叫服务，后来叫 SOA。但基本理念是一样的：那个单体已经难以为继了，光是重新链接那个二进制文件，在高端台式机上就要 45 分钟，根本没法做开发。所以亚马逊不得不这么做。我们发现，实际上当时我们就已经采用了一种标准做法：用队列把多个服务连接起来，基本上靠它来执行所有这些后端业务流程。我当时是发布-订阅（pub/sub）组的技术负责人，我领导的这个组负责亚马逊所有后端的发布-订阅系统。我参与开发了队列的分布式复制存储，我想它现在仍然被用作 Simple Queue Service（SQS）的后端。

Maxim Fateev：所以我参与了很多关于设计选择的讨论。当你用队列和事件驱动架构构建这些大规模系统时，很快就会发现这不是正确的抽象。事件和队列不是构建这类系统的正确抽象。这里有很重要的一点：它们是非常好的运行时抽象，对吧？事件驱动系统和队列能给你极好的运行时特性，因为比如说你的服务可能很慢，但其他服务不会因此被拖慢，因为东西可以缓冲在队列里；或者你的服务甚至可能宕机，其他服务根本察觉不到，它们只是看到消息可能没来，或者被缓冲了。所以这些系统的运行时特性非常棒，但作为一种设计选择，它们实际上会造就非常脆弱的系统，因为所有东西都和所有东西相连，没有清晰的 API，很难在每个服务里构建状态机并支撑所有业务逻辑。

Maxim Fateev：我们团队认识到了这一点，开始考虑编排器（orchestrator）。亚马逊内部有一个基于 Petri 网思想的编排器，构建在 Oracle 之上，实际用于编排订单。我们开始考虑更具扩展性的方案。我们在内部做了三轮迭代、三个版本的服务，只有第三个版本公开了，作为 Simple Workflow Service，也就是 AWS Simple Workflow Service 发布。我们尝试了很多次才把它做对，不过即使是 Simple Workflow，我也不认为我们真的做对了，因为它到现在仍不是一个很受欢迎的服务，但我们确实从中学到了很多。后来我们各自去了其他公司。Temporal 的联合创始人 Samar Abbas 当时和我一起做 Simple Workflow，他去了微软，在微软写了 Durable Task Framework，后来被 Azure Functions 采用，现在微软有了 Azure Durable Functions。然后我们在 Uber 重逢，把所有这些想法拿过来，打造了下一代技术，也就是我们现在在做的东西。你可以把 Temporal 看作十多年来所有这些先前尝试的延续。

Philip Winston：能讲讲你们选择 fork Cadence 来创建 Temporal，而不是比如说从头再来的过程吗？你们是怎么做这个决定的？

Maxim Fateev：如果你认为现有方案不够好，你才会从头再来，对吧？Cadence 很扎实，因为我们在生产环境中运行了三年多，其中两年是大规模运行，有一百多个用例把它用于关键任务应用。但我们也知道有很多东西想修，因为三年里我们学到了很多。可我们承诺过完全的向后兼容和在线升级，所以什么都不能破坏。要在不破坏任何东西的前提下从 A 点走到 B 点，会极其、极其困难。可以做到，但会很难。而 fork 项目时，我们实际上获得了一次性的机会来修复大量这类小问题。最基本的一个例子是从 Thrift 迁移到 protobuf，从 Uber 专用的定制协议迁移到 gRPC，这些主要改动在安全等方面给我们带来了很多好处。还有很多其他小东西需要修。从 fork 项目到发布并宣布可用于生产，我们花了一年时间。光是在 fork 上工作就花了一年才发布，因为我们做了非常多的改动。

Philip Winston：你提到了 MIT 许可证。Temporal 的哪些部分采用这个许可证？我猜有客户端 SDK，有服务器或 Web 界面，Temporal 由哪些不同的部分组成？

Maxim Fateev：Temporal 有一个后端集群，包含多个角色。当然你可以把所有这些角色放在一个二进制文件里运行，我们有单二进制版本，比如用于本地开发，里面也包含 UI。但你也可以把这五个角色作为单独的进程池分别运行。后端服务还需要一个数据库。在开源版本里，我们支持 MySQL、Postgres 和 Cassandra，SQLite 也是官方支持的数据库。这个集群连接数据库，通过其前端角色暴露 gRPC 接口，整个集群都是 MIT 许可的，你可以自己运行。然后当你编写应用时，应用位于集群外部，包含所有代码和所有业务逻辑，这个应用只是通过 gRPC 连接到后端集群。这些应用不需要开放任何端口，只发起到集群的出站连接。所以，是的，所有这些组件都是 MIT 许可。我想 Java SDK 因为历史原因是 Apache 2 许可，因为我们最初 fork 的是我在 Simple Workflow 时期构建的亚马逊框架的实现。

Philip Winston：我们接下来要聊 Temporal 的核心概念，包括工作流、活动、定时器等等。不过首先我想提一下几期与工作流系统或任务系统相关的往期节目：第 502 期，Omer Katz 谈用 Celery 实现分布式任务队列；第 351 期，Bernd Rücker 谈用工作流管理编排微服务；第 198 期，Wil van der Aalst 谈工作流管理系统。最后那期已经是十年前的了，但我很惊讶，其中很多概念至今仍在被讨论，仍然有意义。那么进入核心概念：你们不一定把 Temporal 称为工作流系统，但工作流是核心概念之一。在 Temporal 的语境下，你能讲讲工作流吗？

Maxim Fateev：我认为非常重要的一点是要理解，当我在 Temporal 的语境下说“工作流”时，我指的始终是持久执行，正是我前面描述的那个概念。你用顶层的编程语言写代码，可以用 Java、Go、TypeScript、PHP、.NET 写代码，而这段代码是持久的。我们始终保留完整的状态，包括我说过的阻塞中的调用和所有变量状态。这非常适用于各种场景，对吧？每当你需要持久性，每当你需要完成保证，每当你需要 saga 或执行补偿，Temporal 都非常合适。问题在于，当你说“工作流引擎”时，人们通常想象的恰恰是你提到的那些方案，全都基于 YAML、XML、JSON，或者靠画图。这些方案从未真正流行起来是有原因的，因为工程师在大多数用例中甚至不会考虑它们，因为这些系统从来就不是为开发者友好而设计的，对吧？不是开发者优先的。总有这样一种承诺：非技术人员能写工作流，因为他们会画图。现实是这从来行不通，对吧？工程师还是得去写这些 XML、JSON 文件或者画图，而这不是工程师想要的。他们想要代码。所以当我说工作流时，我指的始终是持久执行，我认为这一点应该非常、非常清楚，对吧？这和其他任何人推销工作流时完全不同，他们指的总是某个 JSON 文件、XML 文件之类的东西。

Philip Winston：我用过 AWS Step Functions 和 Google Cloud Workflows，在那里你确实要用 JSON 或 YAML 来定义工作流。我的体会是，JSON 或 YAML 也许非常适合做配置，但在那些系统里，你实际上是在用一种受限的语言写命令式代码。对我来说，这就是事情开始变得很不舒服的地方。那么讲讲实现 Temporal 的一些技术挑战吧，它确实支持任意编程语言，或者至少相当多的编程语言。我知道每种语言都有不同的 SDK 来支持，但一定有某种共同的技术让这成为可能。

Maxim Fateev：是的，你想想看，要始终保存代码的状态，真正说来只有两种方法。一种方法是每次代码推进后都对代码的内存做快照，把它存到某个地方，然后如果需要在另一台机器上激活这次执行，就加载那段内存，继续执行。问题在于，某些运行时也许可以这么做，比如 WebAssembly 可以，但你没法直接拿 Java 来序列化 Java 执行的完整状态，尤其是在它阻塞在某些调用上的时候。如果是同步代码，运行时……Go 代码也一样，对吧？你没法直接把阻塞在某段代码上的 Go 拿走。技术上可以，但你需要相当深入地 hack 运行时。

Maxim Fateev：TypeScript 等等也一样。所以另一种方法实际上就是使用我们所说的重放（replay）。你从头开始运行代码，每当代码执行某个外部操作时，你就拦截它，如果这个操作已经完成了，就直接把结果交给代码。比如像我说的，你的代码阻塞在函数 B 上，然后这个进程崩溃了。你会有一份历史，我们称之为工作流的事件历史（event history），它记录着：操作 A 被请求过并且已完成，操作 B 被请求过但尚未完成。然后你会重启它，实际上就是进程恢复：你运行这个函数，调用 A，验证对 A 的调用在历史中，然后把 A 的结果交给代码，代码会从 A 那一行走到 B 那一行，然后你验证对 B 的调用确实做过、在历史里，于是我们就知道这段代码现在阻塞在 B 上，接下来需要等待 B 的结果被交付给 B。

Maxim Fateev：这里面有很多细节。比如，你如何确保 B 的结果被路由到当前正在等待它的那个进程，因为之前的进程已经崩溃了。所以这里有一整个路由层，还有很多其他东西。一个很大的前提假设是函数的代码是确定性的。这是什么意思呢？意思是如果你再次执行这段代码，它会到达同一个点。比如说，如果你的代码写的是：如果随机数大于 50，走分支 A，比如发起 API 调用 A；如果小于 50，发起 API 调用 B。这段代码就不是确定性的，因为每次从头运行它都可能走不同的分支。所以如果你需要用随机数，实际上你得用确定性的随机数：第一次调用时是随机的，之后重放时会返回相同的值。Temporal 为所有这些情况提供了专门的 API，用于随机数、时间、创建线程，因为线程显然也不是确定性的，除非你用我们自己的运行时。

Philip Winston：来个简单的例子怎么样？我有一个邮件或即时通讯应用，有个功能可以按我指定的任意时长延迟发送消息。这个工作流在某个端点之后启动，用户已经指定了延迟多久。当我看工作流代码时，它看起来是线性的：开始，有一个 sleep，或者说定时器，然后真正发送消息。第一次执行到那个定时器时会发生什么？它会退出吗？到底发生了什么，让它之后能够继续？

Maxim Fateev：会发生的是，工作流代码运行在应用的空间里，对吧？它不在 Temporal 集群内部运行。通常你会创建——我们称之为工作者进程（worker process），即工作流工作者进程，它托管工作流代码。你可以把这个工作者进程看作一个队列消费者，就和比如说你从 Kafka 消费消息一样，你会有一个始终运行的进程作为队列消费者。Temporal 工作者也一样，它始终在运行，始终在监听 Temporal 内部一个特定的队列，叫任务队列（task queue）。它会说：我在监听任务队列 foo，对吧？比如我的工作流 foo 注册到这个任务队列上。当你启动工作流时，它会在 Temporal 自身内部创建一个任务和数据状态，然后把任务放进那个队列，而且这一切都是事务性的，所以那里不存在竞态条件。

Maxim Fateev：然后这个工作者会取走这个任务，任务里包含工作流的参数之类的信息，然后开始执行。接着它会碰到 sleep，没法再往前推进，这个 sleep 会被转换成“创建定时器”命令，这个命令会被发回 Temporal 服务器，Temporal 会在它的基础设施里创建一个持久定时器，并把这个定时器存进数据库。然后如果你 sleep 的是比如两周，两周后这个定时器会触发，创建一个新任务，一个新的工作者，某个不同的进程会取走这个任务，恢复工作流状态，解除定时器的阻塞，然后继续。

Philip Winston：所以工作者并不退出，但在 sleep 开始时，那个任务可能就已经结束了。

Maxim Fateev：正是这样。还有一个优化是，我们会在工作者内部把那个工作流状态缓存一段时间，因为如果 sleep 很短，或者只是在等一个活动完成，那么这个工作流很可能很快又会被需要。所以我们不想每次都恢复它。我们实际上会在工作者上把那个工作流缓存一段时间。所以快速运行的工作流总是被缓存着，我们只需要把新事件交付给它们，不需要做恢复。但这纯粹是优化。

Philip Winston：说到时长，在你看来，或者在 Temporal 看来，什么算短时长的工作流，什么算长的？根据我的经验，我经常和别人讨论工作流时，我想的范围或时长和对方完全不同。所以我只是好奇，从 Temporal 的角度，或者从你对 Temporal 用户的经验来看，时长的范围是多少？

Maxim Fateev：首先，Temporal、持久执行并不在乎时长。它既可以用于非常非常短的场景，也可以用于非常非常长的场景。关键在于持久性：你是否需要完成保证？尤其是补偿。比如说，有人把它用于即时支付的用例。你执行这个操作的时间窗口非常小，对吧？但为什么需要 Temporal 这样的东西呢？因为如果某些 API 调用失败，你需要执行补偿，对吧？比如你从一个账户取了钱，想把它存进另一个账户，而另一个账户因为某种原因失败了。你会非常快地向用户返回错误，但你需要确保把钱退回原账户，而且你需要保证这一点。

Maxim Fateev：由于如今跨服务之间没有事务，Temporal 实际上是在分布式架构中替代事务的最佳方式。这是一个非常常见的用例，即使时长非常短、有人在等着，它也能工作。同时，我们也有工作流一直运行的用例。比如我们称之为实体工作流（entity workflow）的东西。比如说你有一个代表某个用户的工作流，这个工作流会处理与该用户的所有通信。我可以给你一个实际的例子。想象你是一家航空公司，想做一个忠诚度计划，有积分。你完全可以为每位客户运行一个一直在运行的工作流，监听各种事件，比如航班完成事件，每完成一次航班，它就获取航班的里程，并据此增加积分。

Maxim Fateev：积分可以直接存成工作流变量，因为它们始终是持久的。然后如果你达到了一定积分，就可以执行一些操作，比如通过活动通知其他服务你现在是金卡会员了。如果你想在工作流里放一个定时器，每月发一封邮件说：好，这是你最新的积分，顺便问一下，你想要这个促销吗？你也可以把这一切实现为一个单独的工作流。但关键是这个工作流一直在运行，没有终点，除非客户想退出你的系统，而在这类场景中这实际上几乎从不发生。

Philip Winston：我确实碰到过“工作流即实体”这个想法，我也想稍微深入聊聊，不过我们先回到核心概念。我们谈了工作流，接下来谈谈活动（activity）吧。我之前说在延迟邮件的例子里会用 sleep 或定时器，但活动是一个更普遍的概念。能讲讲在 Temporal 里什么构成一个活动吗？它应该或者必须具备哪些属性？

Maxim Fateev：正如我描述的，Temporal 恢复工作流状态的方式是通过重放。所以实际上主要要求是代码是确定性的。任何外部 IO 按定义都不是确定性的，因为它可能这次成功、下次失败，也可能返回不同的结果。这就是为什么 Temporal 要拦截那些外部调用，实际上定下了一条规则：所有外部通信都要通过活动进行，而活动在每种语言里就只是一个函数。所以它就像一个任务，对吧？就像比如你有一个队列消费者，可以有处理那个队列的任务；同样，在 Temporal 里你写一个活动，通常就是一个函数，每次你从工作流里调用这个活动时，就会调用这个函数的代码。我们对这个函数里能写什么不做任何限制。

Maxim Fateev：Temporal 活动相比队列任务的好处在于，首先 Temporal 活动想运行多久都可以。如果有必要，你可以运行它一年。当然，对于长时间运行的活动，你需要心跳（heartbeat），你不会想要一个超时设为一年的活动，然后等一年直到超时。但它可以每分钟发一次心跳，一旦你的进程崩溃，比如一分钟后它就会被重试。你还可以往心跳里添加信息，所以可以在心跳里存储一些关于进度的信息。比如说如果你的活动在扫描一个巨大的数据集，它可以每处理一条记录就通过心跳上报进度，然后如果活动失败，它会被重启，你可以获取最后一次心跳的数据，拿到你的进度，从那里继续。所以你可以有这样的活动。而且活动是可以取消的。

Maxim Fateev：只要活动发心跳，它就可以被取消，所以它可以优雅地处理取消。我们还可以把活动路由到特定的主机。比如说，如果你需要在你机群中的主机 B 上运行某个活动，因为活动 A 已经把某个文件下载到那里了，你可以专门把活动路由到那台主机。我们有很多功能。另外，如果活动失败，它们会以指数退避方式重试。我们有指数重试，重试可以持续你想要的任意时长。所以如果你想重试一周、重试一个月，都完全支持。这和队列很不一样，因为在队列里，任务的时长和重试次数通常非常有限。

Philip Winston：所以活动当然可以位于远程系统上，某种远程过程调用或 Web 接口。但有没有这样的情况：即使它在同一个进程里，你也想把它当作一个活动？

Maxim Fateev：实际上这是 Temporal 的一种限制——我不会说是限制，只是一种设计选择：每个外部 IO 都应该放在活动里。我们有一个本地活动（local activity）的概念，它和工作流运行在同一个进程里，作为某些场景下的优化，它可以支持那些可能需要非常非常低延迟的场景。但还是那句话，如果这个活动要发邮件，它就应该是一个活动，然后工作流去调用“发送邮件”活动。

Philip Winston：我们谈过确定性的必要。分布式系统中另一个总会出现的概念是幂等性（idempotency）。我猜你们所有的活动都需要是幂等的？还是它们永远只会被调用一次？

Maxim Fateev：这是个非常好的问题。Temporal 不会盲目地重试活动。如果活动失败或超时，会有一个关联的重试策略。如果你在策略里把最大尝试次数设为 1，它就不会被重试。但这种情况下会发生什么呢？工作流会收到一个错误，它需要处理这个错误，对吧？而这只是常规的语言抽象。比如如果是 Java，你会写 try-catch，捕获“活动失败”这个异常，然后你可以按任何方式处理它，比如执行补偿、执行不同的活动。所以这比“哦，我们会盲目重试”要复杂一点。但在现实中，处理这类场景最常见的做法是让活动幂等，然后直接盲目重试，默认情况下我们会重试它们。但我认为重要的一点是，Temporal 是一个完全一致的系统，所以它只在你要求时才做盲目重试。但如果你把最大尝试次数设为 1，就存在你的活动永远不会运行的可能，对吧？因为也许任务已经交付了，定时器已经启动了，然后进程崩溃了。

Maxim Fateev：在这种情况下，Temporal 保证超时之后会抛出异常，并把它交付给工作流。所以它不会丢失那个活动，但可能出现活动从未被执行的情况。如果你的最大尝试次数是 1，你就需要自己处理错误。所以是的，但如果你把它做成幂等的，你就不用考虑这个，对吧？你只要说：好，我们一直重试直到完成。

Philip Winston：你之前提到了 saga 模式。这是 Temporal 帮你实现的东西吗？我想先问，什么是 saga 模式？我想它和这样一个想法有关：我有多个活动，也许其中一些已经成功执行了，但有一个失败了，我想撤销其他那些。能讲讲它是怎么运作的吗？

Maxim Fateev：我不确定它的确切表述是什么，但我来讲讲我是怎么看的。想法正是如此。如果你执行多个 API 调用，这些 API 调用很可能会执行一些存储变更、做一些修改。而由于这些调用之间没有事务——比如最明显的例子：从一个账户取钱，存入另一个账户。你从第一个账户取了钱，然后没法把钱存进第二个账户，因为也许账户 ID 错了。那这种情况下你怎么办？既然没有事务，技术上你唯一能做的就是执行一个补偿操作，而补偿操作就是把钱存回账户 A，对吧？这种场景一直在出现。所以你实际上需要执行补偿，而 saga 只是一种模式，它说的是：是的，如果你执行多个活动——

Maxim Fateev：比如你执行了 10 个，其中 8 个成功了，第 9 个失败了，怎么去为前面那 8 个执行补偿？我认为 Temporal 相比其他任何框架——尤其是所有这些基于 JSON 和 YAML 的现有框架——的一个重要之处在于，因为代码非常动态，它让实现 saga 变得非常简单。想想看，saga 是什么？是补偿的保证。Temporal 保证即使进程崩溃或发生其他故障，你的函数也会继续运行。所以 Temporal 可以很容易地保证，如果发生了什么事，这个流程会继续运行。如果你的流程里有 try/catch 块，并且你在 catch 块里捕获了异常，你就执行补偿，这对 Temporal 来说是很容易做到的保证。然后你可以写专门的类。比如 Temporal 的 Java SDK 里有一个 Saga 类，它不过就是一组回调的集合，对吧？

Maxim Fateev：然后当你说“补偿”时，我们就去执行这些回调，而这些回调里可以包含一些补偿逻辑。重要的一点在于它是动态的。想象你有大约 50 个可能的活动，还有复杂的分支逻辑，每次你执行某个事务时会执行其中 5 个活动，但每次执行的是哪 5 个都不一样。用 Temporal，你只要把这个 saga 对象一路传下去，在每个分支里把执行过的活动累加到列表里，然后补偿时，你就补偿那 5 个活动。试试用任何静态的 DAG，或者通过 YAML、XML 生成的图来做这件事——因为你没有动态补偿，你实际上需要把每条路径和每条补偿路径分别建模。只要有几个可能的分支，这实际上就变得无法管理了。我们发现，关于 saga 应该如何实现，存在一种非常普遍的误解；在 Temporal 里很简单的事情，在其他任何基于配置的语言里几乎都不可能做到。

Philip Winston：这么说来，各语言的 SDK 提供了一块相当精巧的小技术来帮你实现 saga。而在基于配置语言的工作流系统里，除非系统本身提供，否则就没有这一环。

Maxim Fateev：有意思的是，saga 并不精巧，因为 SDK 精巧的地方在于保证你的代码会持续运行，对吧？并且完整状态被保留。saga 本身就像我说的，是一个你 20 分钟就能写出来的类，因为它不过是一个补偿操作的列表，然后你说“补偿”，就遍历这个列表执行这些回调。我写这个 Saga 类大概花了不到一个小时。所以任何人都能写自己的版本，写自己的代码。你可以写自己的库、自己的框架，而 Temporal 提供运行时保证：保证代码执行完成，保证持久性。有一种说法叫“对故障无感”（fault oblivious），对吧？你的代码甚至不需要知道发生过故障，因为它已经无缝恢复了。

Philip Winston：这让我想到“关注点分离”这个说法。在我看来，工作流代码专注于一切正常的“快乐路径”，我不一定需要操心重试。这大概就是目标。

Maxim Fateev：我认为有两类故障。一类是基础设施故障：进程崩溃、网络中断，对吧？比如停电，这些和你的业务逻辑无关的事情，Temporal 会无缝地处理掉。你甚至不需要考虑它们。它们不是你代码的一部分，你也不需要为了挺过故障并恢复而去持久化状态，因为状态始终是持久化的，你代码里的每个局部变量都是持久的。但另一类是业务层面的故障，比如像我说的，你要存款到某个账户，而账户 ID 是错的，在基础设施层面就没什么能做的了，对吧？这是你的业务逻辑，这时你实际上可以抛出一个异常，然后处理这个异常。在活动里，你可以区分哪些异常是可重试的，哪些是不可重试的。

Maxim Fateev：你实际上可以说：好，“账户 ID 错误”是不可重试的异常。然后它会被传播到工作流，工作流会执行 saga 补偿把钱退回去。但如果是活动因为超时、数据库或者别的随机原因，或者空指针而失败，它就会被重试。大致就是这个思路。另一件有意思的事是，间歇性问题可以变成你两小时内修好的问题。比如说你遇到了空指针，你看代码：哦对，我这里有个 bug，比如这是另一条代码路径。活动会一直重试。你只要去部署修好 bug 的新代码，两小时后在下一次重试时它就通过了，你什么都不用做，你的工作流继续运行，就像什么都没发生过，因为任何部署都不会打断它们。这是一种非常强大的范式：你可以在生产环境中边运行边修复，而不会丢失任何东西。

Maxim Fateev：人们刚接触 Temporal 时，第一反应往往是：哦，遇到间歇性错误就让工作流失败吧。我们会说：不，你不需要这么做，你想重试多久都可以，对吧？所以你甚至不需要考虑引入人工流程——现在人们就是靠人工流程来处理的，他们有死信队列（dead letter queue），需要手动处理。所有这类流程、脚本，这些都不需要了。这需要一些时间去内化，人们并不习惯“甚至不需要考虑这类问题”。但我认为在你上线 Temporal 之后，这一点超级强大。

Philip Winston：你说的是一个开发者，可能在和运维一起工作，或者自己在处理运维，他们发现了一个问题，这很可能要用到 Temporal 的 Web 界面。能讲讲它提供哪些信息、有什么用处吗？

Maxim Fateev：Temporal 的好处在于，就像我说的，我们记录了工作流中的每一个事件。我们实际上是用事件溯源（event sourcing）来恢复工作流状态的。这意味着我们记录了一切。每次活动调用你都能看到参数，每次活动完成你都能看到结果。如果活动失败、你的工作流卡住了，你能看到活动为什么失败、重试了多少次、下一次重试在什么时候。所以你能看到所有信息，能看到到目前为止执行过的所有步骤，以及所有参数之类的东西，还有所有时间信息，比如每个定时器等等。所以你能轻松理解发生了什么，你有深度的可见性。在最坏的情况下，比如说你遇到了空指针，又因为代码路径非常复杂而不明白为什么，你可以按一个按钮，以 JSON 格式下载工作流历史，实际上就是接入你代码中的调试器，在调试器里把那个工作流重放任意多次，

Maxim Fateev：在你的本地机器上复现那个问题。所以这是一种超级强大的排障技术。UI 还让你能看到单个工作流的情况，包括历史和不同的视图。我们还支持列表查询，因为你的系统里可能有数亿、数十亿个工作流在运行。所以我们有索引和你的自定义属性，你可以列出工作流、根据不同条件过滤工作流，还能根据这些条件计数。所以你可以查：好，给我列出这位客户昨天失败的所有工作流，然后把它们列出来，深入调查这些工作流的问题。另外，Temporal 集成了常见的指标、上下文传播、日志。所以你能获得你公司现有的所有常规集成，比如指标，这样出问题时你会收到告警，因为我们会自动为每个活动、每个工作流、每次重试发出指标。所有重要的东西都会被发出。所以你实际上不需要添加任何自定义指标就能开始理解你的应用。

Philip Winston：我想我们已经涵盖了所有核心概念：工作流、活动、定时器、它如何运行事件历史、重放、出错时重试，以及用于调试的 Web 界面。我们回到你之前提到的一个东西：“工作流即实体”的想法。我想在那种情况下，这些工作流永远不会结束或终止，除非实体消失。我想你在那里暗示了两样东西：信号（signal）和查询（query）。能谈谈信号和查询吗？因为它们在我看来并不像是我熟悉的那种工作流概念。

Maxim Fateev：我们现在有信号、查询和更新（update）。更新是最近才加的。信号是对工作流的单向调用，实际上就是把一个事件交付给某个工作流、某个特定的工作流实例。你说“向工作流发信号”，给出工作流 ID——顺便说一句，工作流 ID 由应用开发者提供，我们保证工作流按 ID 唯一。所以有硬性保证：系统中不会同时运行两个相同 ID 的工作流。因此你实际上获得了工作流的“恰好一次”执行保证。信号就只是一个事件，如何处理它取决于语言。比如在 Java 里它就是一个回调。你说：对这种信号类型，这是我的参数，每次这个事件被发送给工作流时，这个回调就会被调用，工作流可以对它做出反应，而这可以是一段完全异步的代码。

Maxim Fateev：查询是同步地从工作流中获取信息的方式。当你发起查询时，你调用的是工作流内部的一个回调，这个回调不能修改工作流状态，只能返回数据，但它可以从你的工作流里返回任何数据，这是你的代码。所以你可以返回一张图片，也可以只返回状态，可以拼接任何东西，而调用方会同步阻塞。所以如果你想在 UI 里展示这个工作流的某些信息，你就发起查询，它会阻塞，一旦数据返回，就在 UI 里展示出来。而更新算是两者的结合。更新是你向工作流发送一个请求，这是对工作流内部的一个回调。工作流可以让这个回调阻塞任意长的时间，然后在某个时刻返回结果，你的调用方就会解除阻塞。调用更新有两种方式：对于短时的请求可以是同步的，比如即时支付之类的。

Maxim Fateev：但也会有异步更新，它实际上可能需要长得多的时间，你会在后台对结果做某种优化过的长轮询。但从概念上讲，你有信号，即单向事件；有查询，即只是从工作流中获取信息；还有更新，实际上就是比如说，想象你有这个实体工作流，你想说：我要领取某个促销并做点什么。于是你更新工作流，它会更新自己的状态，也许执行一些活动，然后解除你的更新调用的阻塞，告诉你这个促销是成功了还是被拒绝了。

Philip Winston：其实再给我举一个关于更新的例子吧。我还不是完全清楚，再带我过一遍。

Maxim Fateev：好，我举一个不同的例子。想象你要实现一个页面流，比如向导（wizard），对吧？显示第一页。比如说，你在实现一个结账流程，对吧？我在亚马逊的订单服务工作过，所以在这方面有些想法。你有一个结账流程。你先显示某个页面，比如你的购物车，对吧？然后你选择几个按钮，点“下一步”，根据你选的内容，下一页会不一样。然后你填写支付信息之类的，点“下一步”，下一页又不一样。用更新的话，你可以有一个比如说“结账流程”工作流，它会阻塞着等待那个页面返回数据。然后你说：好，这是我的数据。这会解除工作流的阻塞，它可以执行任意逻辑，包括运行活动。然后它可以说：好，现在显示另一个页面，对吧？它实际上会返回新页面的信息，然后你又会在那里阻塞。所以你可以把整个向导建模成这样一个实际上会阻塞的工作流。想象一下，对吧？显示第一页，等等等等，业务逻辑，显示第二页，等等等等，业务逻辑。它想多复杂都可以，因为它是代码，而对它来说，有状态的会话实际上就是一个工作流。这是实现它的一种非常好的方式。

Philip Winston：拦截器（interceptor）呢？那可能是严格在客户端的东西？我不太确定。

Maxim Fateev：目前我们只有客户端拦截器。我们在考虑服务器端的，因为有些场景需要它们。拦截器的思路是，有时你想为特定的业务用例创建某种功能。比如可以很简单：我想在每次某个活动完成时保存它，发出某个事件，对吧？发一个事件到 Kafka，进入我的数据仓库。你可以写一个拦截器，因为我们在工作流前面拦截了对工作流的所有 API 调用，你可以写一个拦截器，比如在每次活动完成后运行一个发布到 Kafka 的活动。然后你只要把这个拦截器注册到工作者上，每个工作流都会自动获得这个功能。拦截器显然有很多用例。它们让你不必去包装 API，因为在拦截器出现之前，人们会说：哦，现在我得包装 Temporal 的 API 才能得到这个功能。但现在你可以写一个拦截器，你那些使用标准 API 的普通工作流就会开箱即用地获得这些好处。

Philip Winston：所以你有某个横切关注点，想把它注入到你写的每个工作流里。

Maxim Fateev：正是，或者每个活动。

Philip Winston：我想这可以让我们过渡到客户端 SDK，也就是各语言的 SDK。我想我们已经讲了核心概念，也讲了一些额外的概念。你们有 Go、Java、PHP、Python、TypeScript 的 SDK，.NET 的也即将推出。不过我读到，至少有一部分客户端库是构建在一个 Rust 内核之上的。能谈谈这是怎么来的吗？可是又没有 Rust SDK。能讲讲客户端 SDK 的结构是怎样的吗？

Maxim Fateev：我们的客户端是相当“胖”的客户端，因为它们实现了一个相当复杂的状态机，因为它们需要确保这次代码执行是正确的，而服务器的 API 只给你一份历史。所以你实际上得到的是一堆事件，你需要通过大量的状态机把它们转换成实际的代码执行。我们还希望每个 SDK 对该语言的用户来说尽可能原生，对吧？所以如果你用 TypeScript，你希望感觉很自然，在 TypeScript 里不做任何不自然的事，对吧？如果你用 .NET，你希望用 .NET 里常规的 async，对吧？比如你用 Python，我们就用 Python 的 asyncio；如果你用 Java，我们实际上用阻塞调用，你只做同步调用，因为 Java 还没有真正类似 async 的东西，对吧？

Maxim Fateev：而如果你用 Go，你会想用 channel、select 等等。这意味着每个 SDK 首先都包含如何让它尽可能贴近语言原生的逻辑。但在底层是非常复杂的状态机，我们发现这个公共的状态机大概占了 80% 的代码和复杂度。于是我们决定写一个单独的库，把所有这些复杂度封装起来。我们考虑过用什么语言写，发现 Rust 实际上非常合适，首先因为 Rust 和很多语言都能很好地集成，比如和 Python 有非常好的原生集成，和很多语言都是，而且如果需要，它也允许你提供 C API。

Maxim Fateev：另外，我们的开发团队就是喜欢 Rust，原因显而易见。这么说吧，我们写完这个项目花了一年，这是一个非常复杂的项目，我想我们从来没遇到过任何崩溃，对吧？或者任何超出逻辑 bug 范畴的问题。我们当然有过逻辑 bug，但从来没有过与实现本身相关的 bug，对于如此复杂的一项技术来说，这很了不起。所以 Rust 内核就是一个库，然后 Python、.NET、TypeScript 都构建在这个库之上，实现就简单得多得多。我们的 Java 和 Go SDK 是在内核之前写的，仍然独立实现这些状态机。这也有一些好处，主要是比如说，我知道 Go 和 Java 开发者不喜欢原生库。比如 Python 开发者可以接受把共享库链接进他们的代码，但 Java 开发者不喜欢这样。所以我们不确定是否会把内核放进去。我们在考虑不同的做法，但从概念上讲，如果能把每个 SDK 都放到内核上是最理想的，我们走着瞧。总有一天，我们一定会在这个内核 SDK 之上做一个 Rust SDK，只是我们还没有足够的时间和资源来优先做这件事。

Philip Winston：我想所有这些语言都必须具备的一个工作流功能是并行执行。比如我有五个任务想同时运行，我不一定知道哪个会耗时最长。能用你喜欢的任何一种语言举例，描述一下我们如何做并行执行吗？

Maxim Fateev：好，这在很大程度上取决于语言。比如说 Java，你只要异步地调用它们，拿回一个 Promise。Promise 和 Future 很像，但出于确定性方面的实际原因，它是我们专门的版本。然后你只要遍历这些 Promise，调用 promise.get() 并阻塞在那里，或者你也可以说：等待这个列表中第一个就绪的 Promise，如果你想要更复杂的逻辑的话。如果你用的是 .NET 之类的，你就直接用 async 函数，对吧？然后 await 那些调用返回的任务。所以你只要用常规的语言构造来做并行执行，没有什么神奇的。在 Go 里你可以用 goroutine，直接运行五个并行的 goroutine。另一个选择是，在 Go 里你可以调用活动，它会返回一个 Future，所以你可以用 Future.Get 写异步风格的程序。所以你有多种选择，而且你拥有 Go 语言的全部能力，包括用 goroutine 来实现并行处理。

Philip Winston：回到 Temporal 如何工作、事件重放如何工作，但把它和这个并行执行的情况联系起来。假设我并行启动了五个任务，并且假设它们都是长时间运行的。我好奇其中一个完成时会发生什么。现在假设我的代码要等它们全部完成。是每完成一个，我的工作流就被重新运行一遍，还是系统知道要等它们全部完成？

Maxim Fateev：目前我们没有服务器端的“等待全部完成”。每完成一个，工作流都会收到通知，然后继续阻塞。如果它们运行时间不是很长，工作流会被缓存，所以开销不会很大，但仍然有一些开销。如果它们运行时间非常长，是的，工作流会被恢复多次，但同样，如果它们运行得那么久，这大概也不是问题。我们考虑过增加某种功能，比如：好，只在它们全部就绪时才唤醒工作流。但目前这只是一个优化，我觉得到目前为止这对大家来说并不是真正的痛点。

Philip Winston：那我们就以客户端 SDK 收尾，然后我要转到 Temporal 集群和 Temporal Cloud。先从集群说起。能谈谈作为开发者，搭建它需要做些什么吗？我知道有一个单二进制文件，它是怎么工作的？然后你如何过渡到生产环境的部署？

Maxim Fateev：好，对于本地开发，如果你用 Mac，只要执行 brew install temporal，你就会得到 Temporal 二进制文件：Temporal CLI 加上功能齐全的服务器，都在一个二进制文件里。然后你只要执行 temporal server start-dev，默认情况下它会用内存中的 SQLite 数据库启动服务器。这对开发来说相当好，因为每次重启它都会清空所有状态，这挺好的。你还会得到 UI，就在 localhost 上有一个 Web UI。所以只要有了这个单二进制文件，你就拥有了做开发的完整环境。我想有一件事我忘了提，我们还有不需要服务器的单元测试框架。这意味着比如在 Java 里你想对你的工作流做单元测试，你只要用我们的支持类，即使你的工作流会阻塞很长时间，它们也能工作。

Maxim Fateev：比如，如果工作流说 sleep 两周，单元测试框架会发现这一点，在工作流阻塞的那一刻把时间向前跳两周。所以你可以在几毫秒内测试那些要运行好几周的工作流，这就是单元测试。但如果你想做真正的开发，就用单二进制文件，然后你可以部署到你的基础设施上，这取决于具体情况。在本地也可以，有些人用 Docker Compose。如果你想要多机安装，你完全可以用 Docker Compose，它把 Temporal 的各个角色作为单独的 Docker 容器运行。另外，比如你想看看指标是什么样的，就会用 Docker Compose，因为单二进制文件里不包含比如 Prometheus。至于人们如何部署 Temporal 本身，它就是一个编译好的二进制文件，后端服务器是用 Go 写的。所以你可以用任何你想要的方式部署它。

Maxim Fateev：所以如果你想在裸金属上运行，你完全可以部署这些二进制文件，用 SCP 把这些二进制文件拷到 50 台机器上，正确地配置好它们。确保这些机器之间能互相通信，因为 Temporal 需要直接通信，然后它就能工作了。然后你大概还要确保在前端节点前面放一个负载均衡器。但显然如今大多数人不这么做，他们用 Kubernetes 或者其他类似的技术，然后你只要通过 Helm Chart 部署 Temporal，或者自己写一个 Helm Chart 来部署，或者用 ECS 之类的。所以 Temporal 对你如何运行这些二进制文件绝对没有任何偏好，对吧？在前端负载均衡器和节点间通信方面有一些要求，然后你需要数据库，你需要准备好数据库，准备好 schema，然后只要把数据库连接信息交给 Temporal 集群就行了。

Philip Winston：说到数据库，你提到单二进制文件用的是内存中的——我记得是 MySQL？

Maxim Fateev：SQLite。

Philip Winston：哦抱歉，SQLite。你还说重启它在某种程度上是好事，因为会重置状态。那数据库里到底有什么？是严格地只有当前正在执行的工作流，也许还有一些用于调试的历史，还是里面还包含别的什么？

Maxim Fateev：里面包含工作流状态、工作流历史，以及工作流的索引——如果你需要跨工作流列出、列出多个工作流的话。还有一些技术性的东西，比如持久定时器，因为光有工作流状态本身是不够的，对吧？比如它要 sleep 30 天，你就需要一个持久定时器，还有很多其他的活动部件。但从你的角度看，概念上是的：工作流、状态、历史、任务和索引。在生产部署中，尤其是规模很大时，我们推荐——我们为此集成了 Elasticsearch，这样索引就会放在 Elasticsearch 里。

Philip Winston：回到“工作流即实体”，如果在那种情况下我的一些工作流可能会永远运行下去，那么在允许多少状态放在工作流里，和仍然保留一个我自己的独立数据库之间，是否需要做个决定？这是需要做的决定吗？你觉得人们通常怎么做？

Maxim Fateev：这是个非常好的问题。比如我描述的航空积分用例，我知道一些规模非常大的生产用例根本不用数据库，就把状态存在那里。同时，状态其实也没多少，对吧？就是积分，也许还有用于事件去重的 ID，比如最近的一些用于去重的事件。不过有一些基本的限制。我们并不直接存储工作流的状态，我们只存储活动结果的状态，因为我们记录的是事件。所以工作流的输入、参数和活动结果就构成了状态。我们把历史的大小限制在 50 MB，每个活动结果不能大于 2 MB。所以从技术上讲，甚至 25 个各返回 2 MB 的活动就会超过这个限制。所以我们不推荐这样做。如果你需要传递大的二进制对象，Temporal 不是用来传递大块数据的技术。

Maxim Fateev：我们推荐把大块数据存在别的系统里，然后传递指针。我们不是大数据系统。对于一直运行的工作流、实体工作流，有一个需要注意的地方：想象它们永远运行下去，比如说它们有一个处理事件的事件循环，这份历史的大小会变得无界，对吧？因为它会一直增长。所以我们有一个专门的机制，叫 continue-as-new，你实际上可以做类似尾递归消除的事情：你从头再次调用这个工作流，显式地传入状态，然后历史被重置为零。所以实际上这类工作流需要定期调用这个操作来重置历史大小。这样它们就可以永远运行下去，实际时长和长度都不受限制。这就是我们提供的机制。另外，它也让代码升级成为可能，因为在工作流已经启动之后升级代码是不简单的。所以如果你定期调用 continue-as-new，代码升级方面就有了保证，这也让事情更容易。

Philip Winston：我想你说的是工作流版本管理，这是我本来就打算谈的，现在正是时候。这看起来确实是个挑战，尤其是如果你有这些长时间运行的工作流，代码可能会变。你怎么知道某次工作流执行和新代码兼容，或者反过来？

Maxim Fateev：是的，这总体上是个难题。想象一下在有东西正在进行中时更新代码，对吧？在所有工作流类、长时间运行的系统里，版本管理有两种方法。一种是在启动工作流的那一刻就把版本固定下来，实际上就是说：这个工作流用版本 1 启动；然后你部署了版本 2，就说这个（新的）工作流固定在版本 2 上。这样你就没法真正修复版本 1 里的 bug，对吧？因为只有所有新工作流才能从改动中受益。这对于相对较短的工作流非常有效。如果你的工作流最长一小时、一天，这实际上是非常常见的做法，我们也推荐这样做，因为它让你的生活更轻松。但如果你有一个要运行一个月的工作流，它又不调用 continue-as-new，因为它就是一串要花一个月的步骤，那么要能为每个版本部署并运行一个工作者池，就成了一项艰巨的任务，

Maxim Fateev：而且可能根本不现实。所以 Temporal 提供了一种方式，我们称之为打补丁（patching），能够给已经在运行的工作流打补丁。我们的做法实际上就是保留两个版本的代码。在你的代码里，同时有旧版本的代码和新版本的代码。你可以把它放在任何地方，可以是一个库，也可以只是一个函数，可以在多个地方这么做，你只要说：如果是旧版本，执行旧代码；新版本，执行新代码。然后通过 API 调用，你可以确认所有旧版本的工作流都已完成，然后就可以删掉旧的分支。但它实际上让你能够修复已经在运行的工作流里的 bug，并保证它们是兼容的，因为我们在版本管理中有专门的检查条件。我们还提供了测试的方法：我们有单元测试支持和重放支持，确保你没有误破坏兼容性。

Philip Winston：版本管理听起来确实可能变得很复杂，但我想，如果你根本没有工作流的显式表示——如果你压根没用这样的工作流系统——版本管理仍然会是个巨大的问题。

Maxim Fateev：会糟糕得多，根本不可能。因为你可以做向后兼容的改动，但一旦你需要做不兼容的改动，由于你的逻辑分散在多个服务里——你的顺序逻辑到处都是，不在一个地方——这实际上就不可能了。我可以告诉你，我们有客户说他们被卡住了，没法做改动。他们很害怕，因为不知道什么会坏掉。因为事件驱动系统，尤其是基于编舞（choreography）的系统，你可以把它们看作一大堆全局变量。当人们说“哦，你可以发布一条消息，某个服务会消费它，而我永远不需要知道，这很好”，其实这不是个好主意。这就像全局变量：你更新了它，完全不知道代码的哪些其他部分会坏掉。所以这些系统极难维护，也极难保证它们不会因改动而崩坏。

Philip Winston：接下来关于 Temporal 集群的话题，我想会把我们引向 Temporal Cloud，因为我们要谈的是当你需要扩容时会发生什么、如何管理。有一个多集群复制的概念。那是为了性能、为了可靠性，还是两者兼有？

Maxim Fateev：纯粹是为了可靠性。我先谈谈性能和可扩展性，然后我们再谈多集群。Temporal 的设计目标是能够几乎无限地扩展。实际上它可以把任何数据库压满。到目前为止，我们还没找到压不满的数据库。这意味着，如果你在 Temporal 上有一个应用，配置正确，你的集群也配置正确，那么瓶颈永远是数据库，而且是 CP 数据库。实际情况是，MySQL 和 Postgres 没有内置分片，所以你只能纵向扩展。我知道有些公司用 Vitess，所以它们也是可以横向扩展的。我们不直接支持这种方式，但在大多数情况下，你可以用最大的实例，纵向扩展到一定程度，然后就撞墙了。如果你用 Cassandra，Cassandra 能让你横向扩展到更多主机，所以 Cassandra 能达到大得多的规模。

Maxim Fateev：我们见过有人跑一百个节点的 Cassandra 集群来运行某些工作负载，而 Temporal 能跟得上，集群本身总能跟得上数据库。所以你就是这么做的。如果你的用例速率较低，选 MySQL 或 Postgres 就好。但如果你需要很高的速率，而你运行的是自托管版本的 Temporal，那你大概就需要 Cassandra。回到多集群。Temporal 有一种非常独特的方式来保证跨区域、跨可用区的可靠性。每个集群都可以部署到多个可用区，对吧？你完全可以把 Cassandra 部署在三个可用区，也可以把 Temporal 集群分布式部署，这样它能毫无问题地挺过单个可用区的故障。但如果整个区域都宕机了，或者数据库损坏了呢？Temporal 允许你在不同区域运行更多集群，而这些集群是完全独立的。

Maxim Fateev：它们有各自的存储，甚至可以是不同类型的存储。比如一个集群可以跑 MySQL，另一个集群可以跑 Cassandra。它们通过顶层的、高层的应用协议通信，这是 Temporal 专用的协议。我们实际上传输的是事件，对吧？我们传输的就是放进事件历史里的那些事件。这意味着，在 Temporal 中，这些集群彼此独立到没有“爆炸半径”问题，你不可能下发一条命令就把比如两个集群同时搞坏。所以这种架构比你在外面看到的任何东西都要高可用得多，尤其是那些多区域数据库，因为对这些数据库，你总可能下发一次 schema 更新或一条错误的命令，就把整个系统搞垮。我们知道，大多数故障都是操作员失误、升级失误、版本失误，而 Temporal 甚至允许你在不同版本上运行这些集群。

Maxim Fateev：所以从设计上讲，这种多区域部署和故障转移是非常非常高可用的。而且因为是异步复制——出于性能考虑，我们不想等待到远程区域的往返——我们实际上有冲突解决代码。因为数据库只看最后的时间戳，然后丢弃超出它的数据。而 Temporal 实际上会检测冲突，并有冲突解决代码，即使在发生冲突的情况下——比如在故障转移前并非每个事件都已传播过去之类的情况——也不会丢失数据和事件。所以我们的多区域支持确实非常强大，当初在 Uber 编写它时，对很多团队来说这是运行重要工作负载的主要要求：如果不能挺过整个数据中心故障或多个完整区域的故障，就不能运行一级（tier one）工作负载。但这并不意味着它能提升性能，对吧？这纯粹是为了可用性，因为每个集群是独立的，有自己的规模上限，前提假设是远程集群能承受同样的规模。所以它们通常大小相同，但每个单独的命名空间都可以单独做故障转移。Temporal 有命名空间（namespace）的概念，它是多租户系统，所以你甚至不需要对整个集群做故障转移，必要时可以对单个命名空间做故障转移。但它不会让集群更快，只会让它更可靠。

Philip Winston：我想这为介绍 Temporal Cloud 做了很好的铺垫，因为你提到了命名空间，而我想你们把云服务定位为“命名空间即服务”，而不只是托管集群。能讲讲这两个概念的区别，以及命名空间即服务有什么优势吗？

Maxim Fateev：开源版有命名空间的概念。如果你部署一个集群，可以在里面创建多个命名空间，但你仍然有一个集群。在 Temporal Cloud 里，我们只给你命名空间，集群这个概念甚至都不暴露。显然在幕后我们仍然有集群，但那是我们的问题，不是云用户的问题。这和你去 S3 说“创建新存储桶”一样，你对 S3 的后端完全不知情，对吧？也许他们有集群，也许没有，对吧？也许只有一个——我怀疑不会只有一个，对吧？但它被完全隐藏了。Temporal Cloud 也一样。你得到一个命名空间，实际上就是通过 API 创建一个新命名空间，得到命名空间端点，马上就能开始使用。保证这个命名空间的可扩展性和可靠性很重要，而我们在单个命名空间上实际上可以无限扩展。

Maxim Fateev：我们做过测试，跑到了每秒 30 万次操作，而且还能更高，只是我们不想为此付更高的 AWS 账单。所以我们可以支持吞吐量非常高的用例。我们能做到这一点，是因为我们实际上写了自己的存储。就像我说的，存储是可插拔的，所以我们可以用不同的数据库，而我们写了自己的数据库。我们之所以能做到，是因为我们写的数据库实际上只服务于一个 API 调用方。我们当然没有资源去写一个通用数据库并维护那套系统。但我们意识到，Temporal 有非常特定的访问模式，它是为非常特定的更新和读取模式构建的，所以我们为此写了数据库，实际上用例非常窄。这让它仅针对这个用例就能做到超级高效、超级快、可扩展。它当然不是通用数据库，但它让我们的云服务的扩展能力远超比如用 Cassandra 能达到的任何水平，并且提供比现有任何数据库都更高的可用性。

Philip Winston：你提到了 S3，我想你们的情况也类似，需要适应客户规模的巨大动态范围。你们可能有很多刚起步的客户，正在熟悉 Temporal，实际上只用到你们那边集群的一小部分。但也有已经步入正轨的客户，也许多个团队都在采用 Temporal，他们可能会扩容，实际上在幕后用掉好几个集群的算力。

Maxim Fateev：我们是多租户的，就像我说的，我们其实并不提供集群。每个集群都可以运行多个客户、多个客户的命名空间，我们当然会执行一些逻辑来把命名空间分配到集群上，确保它们分布均匀。另外，我们显然会留出足够的余量，我们也有扩缩容功能来承受流量尖峰，所以我们可以同时服务吞吐量非常高和很低的客户。另外，就像你说的，如果你有多个团队在用 Temporal，每个团队大概都会有自己的命名空间，所以它们甚至不需要在同一个集群里。但同时，如果你有一个命名空间和用例需要极高的速率，我们也完全能支持。举个例子，每一次 Snapchat 快拍（Story）更新都是一个经过我们云服务的 Temporal 工作流。所以我们能支持非常高的速率，想象一下除夕夜或超级碗期间 Snapchat 快拍的数量。Snap 使用我们服务的原因之一，就是他们不需要为这些活动考虑扩容，因为那由 Temporal 服务本身负责。

Philip Winston：Temporal Cloud 的数据保留或分析呢？我想你们不会希望实时工作流用的数据库，和我可能想用来分析过去一年任务的数据库是同一个。有没有什么组合方案？

Maxim Fateev：有的，目前在 Temporal Cloud 里，你可以把工作流在命名空间内保存最多三个月。将来我们可能会延长，但在那之后，或者在那之前任何时候，你都可以选择配置导出功能。导出实际上就是把你的工作流历史以合适的格式放进你自己的 S3 存储桶。所以实际上，工作流完成后我们就把它交给你，然后你想怎么处理都可以。你想为了合规永久保存它们，或者想在上面跑 MapReduce 作业，你都完全可以做。这是导出的一个非常常见的场景。

Philip Winston：这在某种程度上和可观测性整体相关。既然它运行在云上，如果我想自己做——我不知道——调试或者计费核算，我有哪些钩子可用？

Maxim Fateev：首先，你显然有 UI。有一件事我忘了提：UI 做的所有事情都是通过定义明确的 gRPC 接口完成的，所以你完全可以用它来构建你自己版本的 UI。其次，我们有 CLI，你在 UI 里能做的一切，甚至更多，都能通过 CLI 做，它和同一个接口通信。所以你完全可以通过 CLI 查看工作流、列出工作流、发送信号、发送命令、发起查询等等。所以在云上 CLI 相当强大。你也能访问同样的 UI，甚至更强大，然后你还有 CLI。至于指标，我们可以暴露一个专门的端点提供 Prometheus 指标，你可以用你自己的证书配置自己的端点，这样就能访问你自己的指标。另外还有 SDK，大多数指标其实是由 SDK 发出的。只有一些仅在服务器端、SDK 看不到的指标，才通过那个端点发出，大多与性能相关，是优化你的工作负载所需要的，由云服务暴露出来，但你可以访问它们。

Philip Winston：如果我需要加密我的输入和输出，因而无法在 UI 上直接查看它们，有一个编解码服务器（codec server），能让我看到实际数据。

Maxim Fateev：是的。好，我先从大局讲一下。我想，当我们说“哦，比如你想用 Temporal Cloud 而不是开源版本”时，一个非常常见的第一反应是：我们绝不可能用你们的 SaaS 产品，对吧？Temporal Cloud 是你们的 SaaS 产品，这是常见的反应。实际情况是，在我们去解释了 Temporal Cloud 如何运作之后，大多数人会说：哦，是的，这完全可行，我们能通过安全审查。我们通过了全球最大银行的安全审查，而这些审查非常严格。为什么呢？有几点。首先就是你提到的加密。Temporal 不是数据库，它不需要查看后端集群里的数据，对吧？首先，代码运行在你的场所内，对吧？

Maxim Fateev：因为 Temporal 只负责保管后端集群，就像 Confluent 为你运行 Kafka 集群，而你在自己的场所运行向那个集群发布和读取消息的应用一样。Temporal 也是一样。你链接 SDK，用任何你想要的方式把应用部署到你的系统里。Temporal 不知道你如何部署你的应用，它只需要一个到 Temporal 集群的连接。你只需要从你的 VPC 或数据中心到 Temporal 的出站连接，因为 Temporal 从不反向连接。总是你的代码连到 Temporal，通过 gRPC。所以你只需要开放一个端口，然后运行你的代码。只有出站连接，而且你可以在发送之前把所有东西都加密，因为 Temporal 从不查看载荷。所以如果你有一个活动输入或工作流输入，它会用你的编解码服务器、你的加密算法、你的密钥加密，Temporal 永远看不到任何明文。

Maxim Fateev：然后我们有一个专门的 UI 插件，实际上在 UI 里你可以说：好，我在浏览器里运行 JavaScript，我想用位于我 VPC 内的编解码器，浏览器会直接连接那个编解码服务器，如果我有权限，就解密数据。所以 Temporal Cloud 永远看不到这些，因为 UI 运行在你的浏览器里。所以所有未加密的数据都不会离开你的内部数据中心或 VPC。我认为重要的是理解这三点：Temporal 不运行你的代码；它永远看不到任何明文；除了到 Temporal 端点的连接外没有任何其他连接。这三点实际上足以通过最严格组织的安全审查。

Philip Winston：我想这又回到了节目开头谈的关注点分离：Temporal 不需要知道我代码的这些内部细节，因为那根本不是它的领域，不是它负责的东西。

Maxim Fateev：没错。是的，因为 Temporal 并不理解你的工作流逻辑，它看不到你的任何代码。它看到的实际上只是事件，对吧？运行这个活动、完成这个活动、创建这个定时器、触发这个定时器。所以都是非常底层的细节，而你的业务逻辑存在于你的代码里，Temporal 永远看不到。

Philip Winston：好，这很有道理。定价呢？Temporal Cloud 是怎么计费的？

Maxim Fateev：我们百分之百按用量计费。这意味着你只为你用的东西付费。用量单位是我们所说的“操作”（action）。每次活动执行是一个操作，每个信号是一个操作。

Philip Winston：好，我想 Temporal Cloud 就聊到这里。我们现在得开始收尾了。你提到单二进制文件是上手 Temporal 的好方法。对于刚起步的人，你还有其他建议吗？他们该去哪里看？网站上的视频吗？你推荐什么？

Philip Winston：我会附上课程和其他资源的链接。那么 Temporal 和 Temporal Cloud 接下来有什么计划？我想我们说的是 2024 年第一季度，或者进入 2024 年。

Maxim Fateev：有几件大事正在进行。一是我们正在把我提到的多区域支持产品化。我们在云上还没有让它运行起来，它将在明年初推出。我们称之为全局命名空间（global namespace），就是分布在多个区域的命名空间。它能让你的工作负载获得非常高的可用性。另一件事是，我们目前还不能让人通过注册流程、只填信用卡信息就注册我们的云服务，你仍然需要填一个表单，然后我们会给你发邮件，这比必要的要复杂一些。所以明年初我们会打造一个完全自助的账户注册流程。这是另一件大事。还有一个重要项目，我们称之为 Nexus，它是一种新的思考方式，因为想想 Temporal，它不只是工作流。

Maxim Fateev：Temporal 是面向长时间运行操作的服务网格（service mesh）。因为当你调用活动时，技术上你是在以阻塞的方式调用一个函数，对吧？取决于你的语言，也许是异步阻塞，在 Java 里也许是真正的阻塞。而这个函数运行在这台远程机器上。所以技术上你是在调用 RPC，而这个 RPC 可以耗时五天。这是一种非常强大的范式，它让你作为开发者的生活比试图把它建模成一堆异步事件要简单得多。在 Temporal 里，我们希望让它成为一等公民，这样实际上你就能定义 API，而每个 API 都可以想运行多久就运行多久。所以我们有了这种“任意时长操作”的概念，即可以耗时任意长的操作，这将让你实际上能把 Temporal 当作服务网格，把企业里的所有服务连接在一起，而不依赖队列或事件，实际上就是做这种长时间运行的 RPC。我们称之为 Project Nexus。我想它的第一个版本应该会在明年初推出。
