Lauren Tan：从盯着 agent 到让它自动合并 PR（直播分享） ｜ 视频来源：Codez（X） ｜ 55:03 ｜ https://x.com/huxlab/status/2095867276042154469

SpaceX AI 工程师 Lauren Tan（前 Meta 工程师，参与 Cursor 的 agent 窗口和新产品 GrokBot）在一场线上分享里讲她怎样爬上对编程 agent 的"信任曲线"：从紧盯一两个 agent 的每条输出，到早上醒来发现 agent 已自动合并了约 20 个 PR。上个月她合入了约 1000 个 PR。她承认这会让人质疑质量，自嘲"保证我不是 slop 工匠"，但坚持认为只要设置得当就能做到。

她的出发点是管理类比：不信任下属的经理只能微观管理，人就成了瓶颈，也就谈不上并行。第一步是验证，让 agent 像用户一样真正运行应用、抓性能 trace、看模拟器，这样至少能保证写出来的代码是正确的。她入职第一周就被派去抢救 agent 窗口的性能，截图问 agent，agent 只会自信地乱猜，于是她做了一个控制应用的技能，并配上"功能地图"，告诉 agent 每个功能在界面上怎么找到。这样即使反馈只有一张截图加"？？？"，agent 也能定位并复现。这些技能后来汇成了她的插件 PStack，名字是对 Garry Tan 的 GStack 的玩笑（两人同姓但无亲戚关系）。

第二步是把失败模式沉淀成技能。她观察 agent 的工具调用，比如发现它根本没读相关代码就下结论，就把"别猜，去查代码，多用子 agent"之类写进 Markdown 技能里。她还用评测（eval）给技能做"单元测试"：协调 agent 先定评分标准，再派生子 agent，目录名刻意不让它们察觉自己在被测；用不同模型当裁判交叉核验，用 /loop 一直"爬山"到满分。她说这要求人在早期当个尽职的"后座司机"。她的比喻是：工程师现在像餐厅主厨，不必亲手做每道菜，但自己得会做。

第三步是架构。她认为有完善护栏的老项目反而适合 agent，大公司那套"为最弱的工程师设计"的规范同样能管住 agent，而且 Meta 那种体量本来就有"人类 slop"。最危险的是靠氛围编程起家的新项目，GrokBot 就是如此，代码会逐渐失控。她花了约 600 个 PR，把 GrokBot 重构到一个叫 Dune 的严格架构上：禁用 useEffect，禁止代码注释（agent 爱把"Lauren 说过别这样"写进去），用 CI 检查依赖图，防止渲染线程被误拖慢。核心原则是"最短路径就是最好路径"，因为 agent 爱抄近路，那就让近路即正路。约束要尽量硬（CI、lint、编译器，所以 Rust 很香）。规则、技能、Bugbot 这类软约束会被遗忘，只能叠加，不能单靠。每次想在 PR 里留评论纠正，都应该当成信号，把它变成一条硬规则。

在问答里，她建议先在本地观察 agent，建立信任后再上云端。例如 agent "Benny" 会自动接 bug 报告、在云端电脑上复现，还能确认问题已在主干修复。她提醒别在信任没建立之前就开上百个 agent 烧 token。关于成本，她承认自己有无限 token，但认为这笔投入的 ROI 是正的：一个人可以做完过去要几年的重构，还能让 PM、设计师直接交代码。她也顺带提到当天发布的 Grok 4.6，同价更聪明。她把 GrokBot 形容为非技术人群的"Cursor 时刻"：界面像 iMessage，每个 agent 像一个同事。
