便利的代价

构建抽象，让开发者少做事、多产出，是很诱人的。然而，如果做得不对，很容易让开发者感到挫败。

每当我试用一个库或框架、照着它的“入门”指南走一遍，或者浏览它的示例代码时，我都会留意自己的反应。每当有什么让我觉得“这感觉不对”，我就会记下来，并试着提炼出我会怎样做得不同。在这篇博文里，我试图弄清楚我认为什么才是好的开发者体验。

Web 平台

Web 平台是一团美丽的乱麻。过去几十年里，它由成百上千的人不断扩展和演化，从一个文档平台演变成一个能力极强的应用平台。它的进步速度也在稳步加快。这无疑留下了“妊娠纹”。Web 平台上有些 API 已有几十年历史，另一些才刚问世几个月。每个 API 都只能利用它诞生时 Web 所能提供的东西，这就导致了出了名的不一致的 API 面貌。例如，许多老 API 本可以受益于 JavaScript 的 async/await，但这个特性直到 2010 年代末才进入 JavaScript。正如 Paul Kinlan 不久前在博客里写的，Web 是“坑坑洼洼的”。

另一个促成因素是，Web 平台的很多部分是按照《可扩展 Web 宣言》（Extensible Web Manifesto）的理念设计的。它优先提供底层原语，把构建高层抽象的负担推给生态系统。高层 API 只有在经过尝试、检验并被认为成功之后，才会被纳入平台。结果就是 Web API 的抽象层级差异极大。光谱的一端是 WebAssembly 这样的东西，一个不提供任何便利、但几乎什么都能做的底层虚拟机；另一端是 CSS，一种声明式的样式语言，让复杂的布局和动画在任何设备上都很容易实现，但你只能做它有声明式语法支持的事。

别忘了，Web 平台属于所有人，又不属于任何特定的人，这意味着取得进展和共识比在 Android 或 iOS 上难得多。它有多个相互独立、经常略有分歧的实现。这有显而易见的缺点，也有优点，不过坦白说，这些优点更微妙，也不总是立竿见影。

总之，Web 至少在三个维度上是不平整的：抽象层级、API 设计，以及在各浏览器中的可用性和行为。一切都坑坑洼洼。

总体而言，尽管 Web 平台有缺陷，Web 开发者还是接纳了它。他们学习 HTML、JavaScript、CSS；他们学会了 pushState 的种种怪癖，爱上了 CSS Grid 或 async/await 这类更现代的新特性。更别提他们还得学习工具生态（npm、Rollup、Webpack、Vite……）。

当然，平台仍有空白和不足，这些往往由库或框架来弥补，我把它们统称为“抽象”。

学习与修补

无论你从谁的角度读这篇文章，有一个普遍的事实：开发者想要构建东西，而且通常想把它做完。生态系统也越来越关注这一点，设计各种抽象来让许多流程变得更简单、更快捷。我认为这是好事，问题不在于“做什么”，而在于“怎么做”：

每当我拥有解决某个问题的知识（特别是 Web 平台的知识），而抽象却阻止我运用这些知识时，我就会感到挫败。

完全是巧合，Evan You 也表达过类似的感受。

这让我意识到一件反直觉的事：虽然 Web 平台的不平整看起来像是摩擦的主要来源，但开发者很可能早已学会并掌握了它。如果开发者被迫使用某个抽象，而不能用自己已有的技能，他们可能并不会觉得这是净收益。

让我再详细解释一下我的想法。

作为抽象的库和框架

“库”和“框架”之间的区别一直存在争议。我不会假装自己能平息这场争论，但在这篇博文的语境里，我将采用 Martin Fowler 的思维模型。

库和框架可以通过“控制反转”来区分。使用库时，我把库放进自己的代码里，并在合适的地方调用它。而框架则把自己当作宇宙的中心，提供插槽让我把代码插进去。这就是好莱坞原则：不是你调用框架，而是框架调用你。

这种控制反转本身并不坏。毕竟，框架就是被设计来处于这个位置的，它很可能提供了一些相当精巧的机制，让代码更容易编写、运行得更高效，或者更好地利用其他外围资源。

尤其是那些让代码更容易编写的抽象，已经变得非常流行，这只会强化把“良好的开发者体验（DX）”作为项目核心部分的趋势。抽象的作者想替开发者分担工作，为他们挖一个“成功之坑”。然而，我认为我们还没弄清楚何时以及如何让开发者接触一个抽象，也没弄清楚如何评估一个抽象何时值得使用。抽象通常是为一组特定的用例设计的。而问题恰恰始于开发者想做一件抽象没有预料到的事。

逃生舱

当抽象被证明不够用或过于专横时，往往就需要刺穿抽象，到底层去做事。有时这意味着干脆不用这个抽象。然而，由于框架常常把自己置于整个架构的核心，想要退出可能很难。毕竟开发者的代码是为框架写的，离开框架就无法运行。为了解决这个问题，框架有时会在抽象中故意留一些洞，也就是小小的“逃生舱”，让开发者能接触到底层的平台原语。例如，React 有 ref 属性，可以拿到组件对应的 DOM 元素，从而暴露底层的平台原语。

退出匝道：对我来说，这是库相对于框架的优势之一。尤其在规模较大时，你一开始用了某个框架，但到了某个时候，你发现自己已经超出了这个框架的能力（或者框架停滞太久了），想要换掉它。这可能非常困难，因为框架塑造了你的代码，而每个框架又各不相同，所以没有简单的迁移路径。相比之下，与库的接触面通常很小，从一个库换到另一个库的工作量要小得多，波及范围也小。

在我看来，逃生舱对任何库或框架都是绝对必要的。几乎不可能预料到所有的用例，而提供逃生舱能让开发者绕过限制、继续前进，而不是卡住。

逃生舱的缺点，尤其是在框架中，是开发者往往会一路掉到平台底层。这对开发者来说可能是个挑战，因为他们现在得重做框架之前替他们做的工作：从一个可能很底层的平台原语，一步步往上搭到框架的抽象层级。框架和平台之间的差距越大，开发者要做的工作就越多。

归根结底，提供逃生舱是必要的，这样才不会限制开发者；但它也不理想，因为开发者使用它们的代价可能相当高。

模式复用

抽象经常做错的另一点，是没有复用 Web 平台已经确立的模式和惯用法。这不是要复兴 #useThePlatform 运动，而是出于我对“被迫学习”的观察：如果开发者已经掌握了一项技能，却被迫花时间学习另一种方式来做同样的事，挫败感就会产生。如果除了也许更“地道”或更“纯粹”之外，用“新方式”做并没有实际好处，那就更是加倍的挫败。

这里的一个例子，是 React 中数据如何从子组件传给一个（很远的）祖先组件。自从有了 Web Components 和可扩展的 Event，我就知道如何派发一个自定义事件，并让祖先元素监听它。而 React 由于组件树和 DOM 之间的阻抗失配，让这个模式变得很难用。当然，它有自己的解决方案：通过 props 显式地把回调一层层传下去，或者把回调放进 context。前者非常不方便，后者则是我得为它另学一套东西，却没有明显的好处，唯一的理由是它很“地道”，因为它又是一个 React 组件。

在我看来，在教程或“入门”指南中复用模式尤其重要。这些资料是给新手用的，没有什么比迎面撞上一堵由新概念和新惯用法砌成的墙更令人沮丧的了，而他们必须理解并内化这些东西才能迈出第一步。如果你在意开发者体验和抽象的推广，那么让开发者尽可能多地使用已有技能，并一次只引入一个新概念，会有益得多。附带的好处是，让开发者在智识上从平台慢慢上升到抽象，他们就更有可能理解这个抽象是如何工作的，以及卡住时如何自救。

选择加入还是选择退出

我会把这一切总结如下：当开发者无法使用自己已有的技能，或者因为按自己的方式而不是你的方式做事而感到受到了不成比例的惩罚时，挫败感就产生了。

换句话说：替开发者分担工作的抽象是有价值的！当然有价值。问题只出现在开发者想用不同方式做某件事、却觉得被抽象拴住了的时候。重要的是不要把模式强加给他们。

通过给开发者提供解决问题的多种选择，开发者就能自救，而我有时觉得抽象的作者对这一点考虑得还不够。如果抽象倾向于采用平台的模式，甚至直接暴露底层的平台原语，开发者就可以借助 StackOverflow 之类的资源来摆脱困境。如果抽象密不透风，或者引入了新模式，那就需要 Web 上出现一大批新的博客文章和其他可被索引的资料，开发者才能获得帮助。

最终，一个抽象是采用选择加入（opt-in）还是选择退出（opt-out）的机制更好，取决于目标和用例。但从现在起，我会把“选择”这一部分视为必须的！

分层架构

许多抽象的目标是覆盖在底层平台的所有原语之上。有时这么做是为了能在不改代码的情况下把底层平台换成另一个（见 React Native），有时是为了让抽象能控制何时以及如何使用底层平台。这里的取舍在于，即使有逃生舱，开发者也只剩下一个二元选择：要么在抽象之上工作，要么扔掉抽象提供的所有功能，回到平台。

有一种办法可以支持那些不得不求助于逃生舱的开发者，同时还能改善抽象的整体架构：构建多个层层叠加的抽象。就像一架梯子，或者更像一座立体停车场。每一层都增加一些功能和便利。而由于取舍的本性，它也不可避免地增加了一些主张和约束。根据开发者在特定情况下的知识和需求，他们可以选择哪一层提供合适的便利程度和抽象层级，并且可以视具体情况下降一层（或两层、三层……）。

较低的层不应以抽象掉平台为目标，而应拥抱平台提供的原语，遵循平台已经确立的模式和惯用法，因为开发者已经学会了它们。

这种方法的另一个好处是，它迫使作者真正地“吃自己的狗粮”。如果你严格执行，任何一层都只应使用它下面那一层（以及平台原语）来实现自己的功能。如果做到了，你就可以确信它会是开发者的一个有用的逃生层。一旦这个原则被打破，就说明下面那一层要么抽象得太多，要么提供的功能不够。

让我用一个例子来说明这一切。

例子：设计系统

目前的设计系统似乎有两种形态：一种是纯 CSS 库，开发者可以复制粘贴一些使用了该 CSS 库中类名的标记；另一种是一组 React 组件。

当然，如果他们是 React 用户，那就皆大欢喜。他们选用 React 版本，就能得到现成的外观和基础的组件功能。然而，如果某个 React 组件的行为（或外观）不符合需要，开发者有三条路可以探索：

- 使用 React 的 ref 逃生舱打猴子补丁（前提是组件使用了 forwardRef）。
- 分叉这个组件（也就是复制粘贴它的实现），按自己的喜好修改（当实现依赖多个未导出的工具函数时，这往往行不通）。
- 一路退回到只用 HTML + CSS，自己重新实现全部的行为逻辑（这不仅工作量大，还很容易让整套 CSS 被加载两遍）。

如果他们用的是 React 以外的框架，就只能选第三条路。那要重做大量的工作。

如果采用分层的方法，情况会有什么不同？一个极有价值的附加层，是用 Web Components 实现这些组件。Web Components 是一种被充分理解和检验过的平台原语。它们会基于 CSS 库来实现，这也会倒逼 CSS 库做到模块化、可摇树优化（tree-shaking）。Web Components 可以实现与现有平台元素相似的行为和接口，让 Web 开发者感到熟悉。当然，鉴于 React 如此流行和普及，提供一个 React 版本仍然非常有益。不过，设计系统的 React 版本现在应该基于这些 Web Components 来实现，变成一层薄薄的封装。长话短说，我们最终得到三层：纯 CSS、Web Components、React。

这样做的好处是，React 开发者可以继续用 React。但当某个组件不太符合需要（或者有 bug）时，他们可以下降一层，视具体情况直接编排 Web Components，而不必放弃所有久经考验的实现工作。偏爱 SolidJS 或 Svelte 等其他框架的人，可以使用 Web Components 这一层，只需为这些自定义元素提供一层符合各自框架惯用法的封装，而不用从零开始。

当然，这只是一个例子。分层的方法不仅适用于设计系统，也可以应用于 CLI 这样的开发者工具、GraphQL API 或 UI 设计。它甚至适用于其他生态系统，只是 Web 的坑坑洼洼和 JavaScript 碎片化的生态让它的好处格外明显。

结论

这一思维模型的核心，是思考任何一个抽象的目标开发者是谁，以及这些开发者很可能带着什么技能而来。抽象应该依托这些技能，通过复用概念来尽量减少认知摩擦，并在入门流程（也就是教程、“入门”文档等）中错开引入新概念的时机。每个抽象最好都是可选的（选择加入或选择退出），并且配有逃生舱。如果可能，它还应该暴露顶层之下的各层抽象，让开发者能够掌控局面、自己帮助自己。
