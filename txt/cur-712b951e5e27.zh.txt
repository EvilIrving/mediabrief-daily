Python 的 GC 遇上多进程会发生什么——Python 与 Airflow 及相关问题解决记（第 2 篇）

在《Python 的多进程与 Airflow 的 task 运行方式——Python 与 Airflow 及相关问题解决记（第 1 篇）》中，我们考察了 Airflow 执行 task 时所需的并行性和隔离性，并确认 Airflow 为满足这些要求，无论是每个 task 用完即弃的短期进程，还是创建后复用的长期进程，都以 fork 方式创建。fork 在创建速度和内存效率上都远胜 spawn，但我们也提到它伴随两个局限：一是会原样继承父进程的资源，二是在 Python 中写时复制（Copy-on-Write，COW）并不像预期那样起作用。

本文先从这两个局限在我们的 PoC（概念验证）环境中具体表现为什么问题讲起。两个问题分别是 worker 进程内存持续增长，以及在 MySQL 环境下 dag-processor 间歇性重启。表面上看是两个毫不相干的症状，但深挖下去，共同点都是 Python 的 GC 遇上 fork 引发的问题。本文将详细介绍我们追查原因、解决问题并向 Airflow 贡献代码的过程。

## 问题 1：worker 内存持续增长

在用 CeleryExecutor 对 Airflow 3.1 系列做 PoC 时，最先引起注意的是 worker 容器的内存占用随时间不断增长。

CeleryExecutor 在 worker 容器内放置多个用 fork 创建的 worker 进程来处理 workload。正如第 1 篇“Airflow 的 task 执行模型”中所见，Airflow 3 的 LocalExecutor 也是同样的结构：在 scheduler 进程内用 fork 创建 worker 进程并复用。由于正值 Airflow 大版本升级初期，内存增长的报告也很多，所以我们先从 LocalExecutor 查起。

排查 Python 进程内存增长时常用的工具是 Memray。它按调用栈追踪堆（heap）分配并通过 UI 展示，可以轻松看出哪段代码占着内存。用 Memray 追踪一个 worker 进程后，我们发现了两个问题。

第一，secrets masker 为了做类型检查，import 了整个 kubernetes.client。这是 worker 执行 task 时根本用不到的模块，却每个 worker 占用约 32MB，32 个 worker 就接近 1GB。

第二，Task SDK client 存在反复创建 SSL context 的泄漏。去掉第一个问题后，单个 worker 仍在 30 分钟内从 8MB 涨到 23MB，而且之后也没有停止。

这两个问题是典型的堆浪费和泄漏，我们整理成 issue 提交给 Airflow 后，在 3.1.2 中得到了解决。

由于 Memray 在这个过程中非常有用，我们还为 Airflow 添加了无需修改代码即可让主要组件在 Memray 追踪下运行的功能，以及《Memory Profiling with Memray》文档。

修好这两个问题后，worker 的内存占用依然在上涨。问题在于这部分增长 Memray 抓不到。也就是说，worker 自己新分配的内存并不多，内存占用却在增加。

于是我们回到第 1 篇整理过的指标。用 smem 查看各进程的 PSS 和 USS，发现了一个特别之处：刚创建时 20～30MB 左右的 PSS 会慢慢上升，到某个时刻跳到 100MB 以上，然后就不再回落。大约 1～2 小时，大部分 worker 都会达到这个状态。

```
  PID  Command                          USS(before)  USS(after)  PSS(before)  PSS(after)  RSS(before)  RSS(after)
    7  /usr/python/bin/python3.12            106716      287896       116419      297592       196144      375492
   38  airflow worker -- LocalExec            23280       98988        35810      102606       162572      169284
   39  airflow worker -- LocalExec            23640       98724        36138      102342       162640      169024
   50  airflow worker -- LocalExec            23844       99820        36625      103441       163992      170120
   53  airflow worker -- LocalExec            23756       99840        36545      103460       163928      170136
```

如果 worker 的 RSS 几乎不变，只有 PSS 和 USS 上涨，就意味着进程触及的页面总量不变，但其中原本与父进程共享的页面正在变成它自己的副本。用 pmap 命令按地址区域比较 PSS，可以确认 PSS 的增长发生在与父进程地址相同的映射上。由此可以推测，子进程中发生了某种写入，从而触发了 COW。

## 问题 2：dag-processor 间歇性重启

第二个症状出现在完全不同的组件上，表现也完全不同：在用 MySQL 作为元数据库的环境中，dag-processor Pod 会不规律地重启。日志中留下了如下异常：

```
sqlalchemy.exc.OperationalError: (MySQLdb.OperationalError)
(2013, 'Lost connection to server during query')
[SQL: SELECT dag_priority_parsing_request.id, ...]
```

也就是 dag-processor 的主循环在查询优先解析请求时，MySQL 连接断开了。这个位置没有被重试或异常处理包住，所以进程直接退出。同一时刻其他查询也报出了类似的异常，只不过那些查询走了重试逻辑，容器没有重启而已，原因看起来是一样的。

查看 MySQL 侧的 general log，发现出问题的时刻，有一条 Quit 命令通过那个连接发了过来。并不是服务器因超时断开，而是客户端走了正常的关闭流程。然而 dag-processor 主进程还在继续从连接池里使用这个连接。有人擅自关掉了连接，而它在不知道已经断开的情况下继续使用。

在 Airflow 中，所有数据库连接都通过 SQLAlchemy Engine 对象管理。为了查明原因，我们在 connect 事件上挂了钩子，并给新建的连接对象附上 weakref.finalize，这样连接对象被销毁时就会留下日志。

```
@event.listens_for(engine, "connect")
def on_connect(dbapi_connection, connection_record):
    weakref.finalize(
        connection_record,
        lambda: print(f"{datetime.now().isoformat()} connection_record finalized in pid {os.getpid()}"),
    )
    weakref.finalize(
        dbapi_connection,
        lambda: print(f"{datetime.now().isoformat()} dbapi_connection finalized in pid {os.getpid()}"),
    )
```

结果如下：

```
2025-09-22T13:41:30.352393 connection_record finalized in pid 417
2025-09-22T13:41:30.352403 dbapi_connection finalized in pid 417
```

PID 417 是为解析而 fork 出的子进程，销毁时刻与 MySQL 日志中的 Quit 时刻完全一致。父进程创建的连接对象的副本在子进程中被销毁，而这次销毁把父进程的 socket 关掉了。

mysqlclient 驱动在释放连接对象时，会显式地向服务器发送 COM_QUIT。服务器收到子进程发来的 Quit 后结束会话，父进程在下一次查询时就会收到 2013 错误。

剩下的疑问是连接对象被销毁的原因：必须找出这个对象在子进程中经由什么路径被销毁。复现条件也是个谜。重启发生得相当频繁、影响也很致命，却没有任何已报告的 issue。因此我们推测，这是只在特定条件下才会出现的问题。

## 共同原因：CPython 的内存管理

两个问题有一个共同点：fork 出的子进程在触碰从父进程继承来、自己却并不使用的对象。在第一个症状中，结果表现为页面复制（COW）；在第二个症状中，则表现为对象销毁（连接关闭）。原因在于 CPython 的内存管理方式。

CPython 分两个阶段回收内存。第一阶段是引用计数。每个对象都在对象头里记录着指向自己的引用数量，一旦这个数变为 0，对象立即被释放。大部分回收到这里就结束了，但两个对象互相指向的循环引用，即使外部没有任何人使用，计数也不会变成 0。

补充这一点的第二个机制是循环 GC。循环 GC 只给能容纳其他对象的容器对象附加一个名为 PyGC_Head 的额外头部来追踪。收集时，先把每个对象的引用计数复制到这个头部，再减去被追踪对象之间互相持有的引用，从而找出没有外部引用的环，并释放这些对象。

为了降低开销，被追踪对象分为第 0、1、2 代（generation）。新对象进入第 0 代，每在一次收集中存活下来就升入下一代。每次收集都在各代计数器超过阈值（默认 700、10、10）的瞬间自动开始。GC 什么时候运行，不由程序决定。

循环 GC 的核心步骤是弄清“每个对象被外部引用了多少”。为此，GC 会遍历被收集代中的所有追踪对象，把一个名为 gc_refs 的临时值写入 PyGC_Head，然后再遍历一遍递减这个值。

现在从子进程的角度来看。fork 之后，子进程原样继承了父进程创建的几十万个追踪对象。子进程分配新对象、计数达到阈值时，就会执行循环 GC。每次收集，GC 都可能对所有追踪对象（包括从父进程继承来的对象）的 PyGC_Head 执行写入，与子进程是否使用这些对象无关。

结果是，放着从父进程继承来的对象的几乎所有页面都会逐渐被复制。被复制的页面计入子进程的内存占用，PSS 随之上升。这就是问题 1 中内存占用增长的原因。

为了更细致地理解这个症状，下面再多讲一点写时复制的工作原理。

每个进程都有各自独立的页表。页表是把进程使用的虚拟页映射到实际物理页框号 PFN（Page Frame Number）的表，其中每一行称为 PTE（Page Table Entry）。PTE 包含映射信息以及该页是否可写。

用 fork 创建进程时，子进程原样复制父进程的页表。也就是说，物理页框不被复制，实际内存占用也不会增加。取而代之的是，内核增加物理页框的引用数，并把父子双方的 PTE 都改为不可写状态。并不是父进程持有原件、子进程持有副本，而只是双方都以禁止写入的状态指向同一个页框。

第 1 篇中确认的 fork 创建进程开销极低的原因就在于此：不复制物理数据，只复制页表。

此后无论哪一方尝试写入，都会触发 page fault，内核检查有几个进程引用该物理页框。若有两个以上，就复制到新的物理页框（即发生 COW），并只更新尝试写入的那个进程的 PTE；若只有一个，就不复制，直接写入该页框。与是父进程还是子进程无关：父进程先写，父进程就拿到副本，直到最后都没写的一方保有原件。

那么循环 GC 是否真的会引发 COW？我们通过实验来确认。

查看 /proc/<pid>/pagemap，可以得到每个进程每个虚拟页所映射的 PFN。对同一个虚拟地址，父子进程的 PFN 相同就是在共享，不同就是已被复制。

父进程创建 30 万个 GC 追踪对象，记录位于不同页面上的 20 个对象的地址，然后执行 fork。子进程在 fork 后立即读取 PFN，调用一次 gc.collect() 强制执行循环 GC，然后再读一次。子进程中没有任何访问这些对象的代码。

```
    virt page | parent PFN | child before collect | child after collect | parent after collect
--------------|------------|----------------------|---------------------|---------------------
  0x7f83934c3 |   0x106bcd |             0x106bcd |            0x107d09 |             0x106bcd
  0x7f83934c4 |   0x106bce |             0x106bce |            0x107d0a |             0x106bce
  0x7f83934c5 |   0x106bcf |             0x106bcf |            0x107d0b |             0x106bcf
```

虚拟页 0x7f83934c3 在 fork 刚结束时，父子进程都指向页框 0x106bcd。子进程调用 gc.collect() 之后，只有子进程变成了 0x107d09，父进程仍是 0x106bcd。子进程从未碰过这些对象，被回收的对象也是 0 个，但仅仅因为执行了循环 GC，20 个页面就全部被复制了。也就是说，可以确认一旦发生循环 GC，对象所在的页面就会因此发生 COW。

回到第二个症状。现在可以解释“子进程为什么销毁了父进程的连接对象”了。

为了防止 fork 出的子进程直接使用父进程的数据库连接，Airflow 在子进程启动时会重新创建 SQLAlchemy Engine 的连接池（原始代码）。

```
    if register_at_fork := getattr(os, "register_at_fork", None):
        # https://docs.sqlalchemy.org/en/20/core/pooling.html#using-connection-pools-with-multiprocessing-or-os-fork
        def clean_in_fork():
            _globals = globals()
            if engine := _globals.get("engine"):
                engine.dispose(close=False)
            if async_engine := _globals.get("async_engine"):
                async_engine.sync_engine.dispose(close=False)
        # 在 Windows 上无效
        # fork 之后立即在子进程中执行 clean_in_fork 函数。
        register_at_fork(after_in_child=clean_in_fork)
```

这本身是正确的做法，也是 SQLAlchemy 推荐的与 fork 一起使用时的方法（参见 SQLAlchemy 2.0 文档中的“Using Connection Pools with Multiprocessing or os.fork()”）。执行 engine.dispose(close=False) 后，会在不碰父进程正在使用的连接的前提下创建并使用新的连接池，从而防止子进程关闭继承来的连接、导致父进程正在用的连接被意外关闭。

引用已经断开，看起来应该马上被销毁，但 SQLAlchemy 的连接池和连接记录（connection record）是互相引用的结构，仅靠引用计数无法释放，必须等循环 GC 运行才会被回收。因此，连接关闭的时刻不是重建连接池的时刻，而是子进程中 GC 达到阈值的时刻。

像使用 dynamic DAG generation 这样执行时间较长的情况，GC 运行的概率就高；而在小规模环境中，子进程在达到阈值之前就完成解析并退出了。这就是复现条件随规模而不同的原因。

一旦发生回收，mysqlclient 的连接对象被释放，释放过程中 COM_QUIT 会通过与父进程共享的 socket 发出。结果，子进程中发生的 GC 让父进程的连接断开了。

## 解决方案

### 尝试一：减少子进程继承的对象

找到原因后，我们首先想到的方案是减少子进程继承的对象总量。继承的对象少了，即使所有对象都发生 COW，内存也不会大幅增加。

最初的做法是在 scheduler 的循环开始之前创建 worker 进程。另外，文件顶部的 import 语句会连锁加载该模块又 import 的模块。所以我们通过 Memray 分析，找出加载大量模块的 import 语句，把它们移到 worker 进程创建之后。下面是简化表示这一结构的伪代码（原始代码）。

```
def _run_scheduler_job(args):
    # 进入调度循环之前创建 worker
    spawn_workers()
    # 延迟加载重型模块
    from airflow.jobs.job import Job, run_job
    from airflow.jobs.scheduler_job_runner import SchedulerJobRunner
    # 启动循环
    enable_health_check = conf.getboolean("scheduler", "ENABLE_HEALTH_CHECK")
    with _serve_logs(args.skip_serve_logs), _serve_health_check(enable_health_check):
        run_job(job=job_runner.job, execute_callable=SchedulerJobRunner()._execute)
```

实际上这并不奏效，有两个大问题。

首先，能减少的量有限。Airflow 的各个组件都像 airflow scheduler 这样通过 CLI 启动。在这个过程中，airflow 包的 __init__.py 和 __main__.py 会被执行，SQLAlchemy、FastAPI 这类重型库也会被加载，光这些就占了 100MB。

其次，worker 的 task 处理性能下降，吞吐量减少。正如第 1 篇所述，由于把重型模块的 import 推迟到了 fork 之后，每个 task 都必须重新 import 这些模块，task 处理性能也就相应降低。原来每分钟能处理 100 多个 task 的逻辑，变成只能处理 60～70 个。

最终，我们必须找到从根本上防止 COW 的办法。在子进程中关掉 GC（gc.disable()）最简单，但那样子进程自己产生的循环引用对象就不会被回收，可能造成另一类泄漏。

### 尝试二：gc.freeze()

CPython 从 3.7 版本起正是为此提供了 gc.freeze()。Python 官方文档明确建议使用 fork 的程序使用这个函数：

If a process will fork() without exec(), avoiding unnecessary copy-on-write in child processes will maximize memory sharing and reduce overall memory usage.
（如果进程只 fork() 而不 exec()，避免子进程中不必要的写时复制可以最大化内存共享，降低总体内存占用。）

它会把调用时 GC 追踪的所有对象移到“永久代（permanent generation）”，此后的收集都会忽略这一代。也就是说，把调用时存在的所有对象排除在 GC 对象之外。

gc.freeze() 是 Instagram 的工程师在自家基于 fork 的 Web 服务器上遇到完全相同的 COW 问题后，直接贡献给 CPython 的功能。其背景整理在 Instagram Engineering 博客的文章中。

因此，在 fork 之前执行 gc.freeze，就能同时解决前面两个问题：

- 这些对象不再是循环 GC 的对象，PyGC_Head 不会被修改，因此不会发生 COW。
- 父进程的对象不会被回收，因此不会产生副作用（连接关闭）。

也许有人会问：“被排除在 GC 之外，这些对象的内存岂不是永远不会被释放？”它们只是不再是循环 GC 的对象，基于引用计数的释放仍然有效，因此视情况仍可回收。

调用开销也几乎可以忽略。同一代的对象由双向链表连接，这些信息由 PyGC_Head 管理。freeze 只是把三条链表接到永久代链表的后面。发生头部写入的只有各链表的首尾节点和链表头，是 O(1) 操作。

### 应用于 LocalExecutor

在 LocalExecutor 中实际应用时还多了一个条件：worker 进程要在 freeze 状态下运行，但作为父进程的 scheduler 不能被 freeze。scheduler 在调度循环中不断创建和丢弃对象，如果这些对象被绑在永久代里，scheduler 侧就可能出现新的泄漏。因此我们这样应用：

```
def _spawn_workers(self, n: int):
    gc.freeze()
    try:
        for _ in range(n):
            self._spawn_worker()
    finally:
        gc.unfreeze()
```

在创建 worker 进程之前调用 gc.freeze()。子进程原样继承父进程的内存，所以子进程继承的所有对象都在永久代中，第 0～2 代是空的。此后子进程执行 task 时创建的对象，只有它们进入第 0 代，成为循环 GC 的对象。

按需创建完 worker 进程后，用 gc.unfreeze() 把原有对象放回参与 GC 的代。被移到永久代的原有对象重新回到 GC 范围。此后照常执行分代 GC，调度循环中创建的对象也会被正常回收。

由于这个 unfreeze，父子进程之间出现了差异：子进程的对象处于 freeze 状态，PyGC_Head 不会改变；而父进程的对象会被循环 GC 修改，所以只在父进程一侧发生 COW。不过，原来在每个子进程中各发生一次的复制，经过这一改动后变成只在父进程中发生 1 次。

实测下来，GC freeze/unfreeze 一个来回的开销分别约为 19μs 和 10μs，如上所述，影响可以忽略。

这一改动以 PR #58365 合入 Airflow，并回移到 3.1.4。

### 应用于 dag-processor

在 dag-processor 中，为解析而 fork 出的子进程大多寿命很短，在发生 COW 之前就退出了。但使用 dynamic DAG generation 时，子进程可能持续 1～2 分钟以上；如果多个这样的 DAG 同时执行，还可能遇到短暂的内存尖峰。我们预计也能顺带解决问题 2 中的 MySQL 连接问题，于是讨论决定应用 gc.freeze。

起初我们像 LocalExecutor 那样套用 freeze/unfreeze 循环，结果父进程的内存反而持续增长。原因在于 gc.freeze() 会把第 0、1、2 代各自的收集计数器全部重置为 0。循环 GC 要在这些计数器超过阈值时才启动，而 dag-processor 每个文件都要 fork 一次，所以在两次 fork 之间，计数器还没达到阈值就又归零了。在此期间，父进程处理解析结果时产生的循环引用垃圾，会被 gc.unfreeze() 全部移到第 2 代。第 2 代只有 full collection 才会扫描，而 full collection 的触发条件不断被重置、永远不会到来，于是垃圾无法回收，单调增长。

LocalExecutor 只在 worker 不足时偶尔 fork，因此不受计数器重置的影响；而 dag-processor 的 fork 远比 GC 达到阈值频繁，GC 实际上等同于被关掉了。

如果在 freeze 之前强制 gc.collect()，垃圾会在升入第 2 代之前被回收，问题就能解决，但每次 fork 都要做一次 full collection 的开销太大，所以没有采用。

取而代之，我们只在进入解析循环之前 freeze 一次，并且不 unfreeze。需要防止的 COW 来自 import airflow 和初始化过程中创建的对象，而这些对象在循环开始前就已存在。此后父进程创建的对象会被正常回收。

这一改动以 PR #60505 合入 Airflow。

### 应用于 CeleryExecutor

CeleryExecutor 启动的 Celery worker 主进程，会用 fork 预先创建 worker_concurrency（默认 16）个 ForkPoolWorker 并分配 task。这些进程不会每个 task 结束就丢弃，而是常驻；和 LocalExecutor 一样，可以观察到它们的内存随时间因 COW 而增长。

我们借助 Celery 提供的信号来应用。在第 1 篇介绍过的 celery_import_modules 信号中，重型模块 preload 完成后立即调用 gc.freeze()。ForkPoolWorker 在此之后才被 fork，因此继承的是 preload 对象已进入永久代的状态，结果就不会发生 COW。

和 LocalExecutor 一样，我们也应用了 unfreeze：使用 Celery 信号中的 @worker_ready.connect，在 worker 完成初始化时执行 unfreeze。

这一改动以 PR #62212 合入 Airflow。

## 效果

我们比较了三个组件应用前后的 PSS 和容器整体内存占用。由于 workload 不同，各组件的测量环境也不同。

LocalExecutor 在每分钟执行 500 个 task、持续 12 小时的环境下测量。应用前所有 worker 都收敛到 100MB 以上，应用后稳定在 40MB 左右。以启动 32 个 worker 的 scheduler 容器整体来看，PSS 合计从约 3.6GB 降到约 1.5GB，减少约 2.1GB（58%）。

dag-processor 在与我们运营的平台类似的环境下测量：解析在运营中的 DAG 文件里挑出的 5 个 dynamic DAG 文件，每个文件平均生成 40 个 DAG。

可以看到，打了补丁的版本（蓝色）比打补丁前的版本（橙色）内存占用低得多。我们还确认了问题 2 也已解决。

CeleryExecutor 和 LocalExecutor 一样，各进程的 PSS 和整个容器的内存占用都下降了。单个 worker 容器的内存占用从 2.25GB 降到 1.07GB。

应用结果总结如下：

- LocalExecutor：每进程 PSS 从 100MB 降到 40MB。容器整体 PSS 合计从约 3.6GB 降到约 1.5GB，减少约 2.1GB（58%）。
- dag-processor：DAG 解析时的内存尖峰减小。Pod 重启问题得到解决。
- CeleryExecutor：单个 worker 容器的内存占用从 2.25GB 降到 1.07GB。

这三项改动分别包含在 Airflow 3.1.4、3.1.7 和 Celery provider 3.17.2 中。如果你在运营 Airflow 3 时看到类似的内存模式，只要升级到这些版本或更高版本，应该就能见效。

## 结语

这个问题并非 Airflow 独有。凡是像 gunicorn 的 preload 那样先加载重型模块、再用 fork 创建子进程的 Python 服务，都可能出现同样的模式。这种情况下可以考虑 gc.freeze。但要特别注意：在 fork 比 GC 达到阈值更频繁的进程里，不应反复执行 freeze/unfreeze。

此外，虽然本文没有详细展开，我们还为 3.x 版本的内存稳定做了其他工作：

- Fix memory growth from pathlib sys.intern in long-running processes (#65706)（修复长期运行进程中 pathlib sys.intern 导致的内存增长）
- Fix memory leak in LocalExecutor caused by unreleased file descriptor locks (#65121)（修复 LocalExecutor 中未释放的文件描述符锁导致的内存泄漏）
- Fix memory leak in Client via SSL context creation (#57334)（修复 Client 因创建 SSL context 导致的内存泄漏）
- fix serialize_template_field handling callable value in dict (#63871)（修复 serialize_template_field 对字典中可调用值的处理）
- add static checker for preventing to increase dag version (#59430)（新增防止 DAG 版本无谓递增的静态检查）

结果，在包含所有这些改动的 3.3.0 中，以我们的环境为准，已经没有发现 worker 内部的内存泄漏，我们团队也在更积极地考虑引入 3.x 版本。
