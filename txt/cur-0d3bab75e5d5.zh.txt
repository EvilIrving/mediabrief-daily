智能体循环中的 TDD——是走过场还是真有价值？
Birgitta Böckeler ｜ martinfowler.com ｜ 2026-08-11

本文是“探索生成式 AI”系列的一部分。

TDD（测试驱动开发）工作流可以通过多种方式与 AI 增强编程结合使用：

1. 人写测试：由人以某种形式定义测试场景，可以是自然语言、BDD 风格，或直接写成代码。然后由 AI 编写实现，让这些测试通过（也许第一步是把人写的场景转换成代码）。
2. 为人设置审查检查点：AI 写一个失败的测试，人查看它，审查这个测试是否在测试想要的行为，然后 AI 编写实现。
3. 完全在智能体循环内部：提示智能体先逐个编写失败的测试，然后编写实现，并检查之前失败的测试变绿。

目前，最后一种用法是迄今最常见的。但要求智能体完全在自己的循环内部遵循 TDD 工作流，真的有区别吗？它真的提供了价值，还是说这是少有的例子之一——对人有益的东西，对编程智能体可能无关紧要甚至有害？

我搭建了一个探索性的评估环境，想对这个问题浅尝一下，看看会发现什么。它远不是一个全面、结构化的评估结果，但如果你正在努力让你的智能体使用 TDD，它确实提出了一些值得思考的假设。

**太长不看：**根据 Opus 对结果质量的判断，TDD 工作流与非 TDD 工作流之间没有明显可辨的差异。相反，Opus 不止一次在设计和测试质量上把非 TDD 工作流的方案排得略高。各方案之间的变异测试得分也没有实质差异。

## 实验设置

- *任务：*我在 Claude 的帮助下创建了一个小型、一个中型和一个较大的任务，都是一小段业务逻辑的全新实现。我让它提了一堆建议，要求使用特异、具体的逻辑，以提高方案之间出现差异的概率，而不只是重复训练数据中已经占主导的东西。
- *指令：*在所有运行中，我都加入了至少达到 80% 代码覆盖率的指令。
- *模型：*我用 Sonnet 4.6 生成方案。
- *TDD 遵守情况的判断：*对 TDD 遵守情况的评估同样由 Sonnet 4.6 完成。
- *方案的判断：*由 Opus 4.8 比较两种方案及其测试的质量，它并不知道这些方案是如何产生的。我没有就我认为的好质量给出非常具体的输入，因为这是一次非常开放的探索。而且根据我的经验，我给得越具体，模型就越可能不必要地过度关注我列出的质量标准。在判断代码质量方面，Opus 已被证明是一个相当有能力的模型。为了给方案排名，它即时制定了一份评分标准，传给所有评估各个方案的子智能体。

当你根据我的结果得出自己的结论时，需要考虑的主要注意事项是：

- 这显然是一个非常小的样本量，所以请持保留态度
- 对“质量”含义的判断几乎完全交给了 Opus（只就测试质量给了几点提示）
- 没有一次运行完美地遵循了 TDD，但遵循得相当好
- 给智能体的编码任务都是全新开发，规模相对较小，纯粹关于业务逻辑

## 智能体到底有多擅长 TDD？

在开始之前，我需要确保 TDD 指令真的被遵循了。过去在这方面我的经历并不顺利：智能体常常先写实现、后生成测试，跳过确认红灯这一步，或者超出当前测试过度实现，导致下一个测试从未变红就直接通过了。

我最终使用的提示词在 Sonnet 上效果足够好，可以用来做比较，尽管所有会话都在一定程度上出现了这些问题。对于每次 TDD 运行，我都让一个独立的智能体根据会话记录判断工作流的遵循程度，以免我不小心把一次并没有实质执行 TDD 的运行算进去。

## 结果

我创建了 5 批方案，每批包含两个非 TDD 方案和两个 TDD 方案。在其中一批中，我还加入了两次运行，指示它们先写测试，但不遵循完整的 TDD 纪律（没有增量的红/绿循环）。

在小型（1 批）和中型（3 批）任务中出现了一点规律：Opus 把两个非 TDD 方案排在第 1 和第 2 名，把两个 TDD 方案排在第 3 和第 4 名。只有一次——在我用更明确的“重构与设计审查”步骤强化了 TDD 提示词之后——一个 TDD 方案排到了第 1 名。不过在同一批中，用完全相同提示词运行的另一个 TDD 方案却排在了最后……在较大的任务中，TDD 排在中间，而两个非 TDD 运行分别占据了最好和最差的位置。

## 假设

总结一下，在各批次中，TDD 和非 TDD 都既有得分最好的方案，也有最差的方案，TDD 总体表现略差。

当我让 Opus 在知道每个方案用了哪种工作流的情况下查看会话记录、对结果提出假设时，它发现非 TDD 和测试先行的运行总是在写任何代码或测试之前就创建了完整的设计（架构、数据类型、边界情况、契约），而不是一次处理一个需求/测试。这似乎正是让结果略微倾向于相对更好的数据模型、更多横切性的边界情况和更完整的功能的因素。

TDD 指令会主动阻碍这种前置设计步骤。在那些运行中，设计是由许多局部最小化的决策累加而成的，而且很少被重新审视，所以它往往定型为第一个测试碰巧锁定的那种形状。智能体没想到要写测试的行为，干脆就根本没有实现。

当我和 Ivett Ördög 聊到这个话题时，她提出了这样一个理论：“AI 智能体的训练方式是，它们看到的是完成的函数以及这些函数的描述。它们见过的真正一步步做 TDD 的例子，只占训练数据中极小的一部分。这意味着大语言模型内部对代码的表征，是从需求到代码的直接转换，而不是如何得到这种表征的过程。”

## TDD 的目标——在智能体循环中还能实现吗？

以下是我关于在智能体循环中使用 TDD 的总体思考，不仅仅基于这次实验。我会逐一检视我个人使用 TDD 时的最终目标，略过一些关于“拥有测试”本身、尤其是单元测试的目标（比如重构安全网、活文档、测试覆盖率），聚焦于那些 TDD 工作流特有的目标。

### 测试先行 >> 避免同义反复

测试先行让我更容易断言我想要的输出，而不是复述实现。复述实现的测试在实现错误时永远不会失败，因为它源自它本应检查的同一套逻辑。当断言与具体实现路径解耦时，测试才能真正发现行为不符合我的意图。

**在智能体循环中还能实现吗？**

在我的实验中，尽管先写了测试，一些 TDD 会话还是出现了这个问题。在一个特别明显的例子中，测试拿实现的输出和它自己做比较，重新运行同一段代码来产生“期望”答案（见这份观察清单的第 4 条）。先写测试并不能可靠地防止这种情况——它可能会降低发生的概率，而对于大语言模型，这本来也是我们所能期待的全部了，但从这个小数据集中，我无法就这个概率得出任何结论。

### 测试先行 >> 可测试性

测试先行确保代码从一开始就被设计成可测试的，而不是事后补上比必要的更复杂、更脆弱的测试。

**在智能体循环中还能实现吗？**

结果在这一点上没有给我任何明确的信号。不管怎样，我选择的任务的规模和性质并不需要太多可能暴露这一点的设计复杂度。不过在某种程度上，可测试性是驱动设计的一个推论（见下文）。

### 红-绿 >> 测试有效性

先观察到测试失败、然后成功（*红-绿*），可以证明它确实能捕获回归。

**在智能体循环中还能实现吗？**

当把人移出这个过程时，这真的还有多少意义？只有当有人检查测试*为什么*变红时，看着测试变红才能证明些什么。当智能体既写测试又确认它失败了时，一个红色测试告诉你的只是智能体运行了它并看到了失败，而不是失败的原因是正确的。我实验中对 TDD 遵守情况的评估也表明了这一点：智能体仍然有时会跳过或伪造红灯步骤，或者超前于测试实现，使测试立即通过。回归有效性可以通过变异测试来监控和改进（我在这里写过）。各方案的变异测试得分没有显示任何信号表明 TDD 运行比非 TDD 运行产生了明显更好的变异得分。我并不在乎回归质量是*如何*达到的，只要我有一种机制能看出它有多好。

### 测试先行、红-绿-重构 >> 驱动更好的设计

先写测试迫使我们在实现之前先规定用法，推动我们走向更好的接口和更模块化的代码。TDD 循环中的重构步骤进一步推动我们一步步改进设计。

**在智能体循环中还能实现吗？**

这次实验至少完全没有证明 TDD 运行有更优的设计。根据 Opus 的评分，我现在甚至怀疑 TDD 是否让设计变得更糟，因为非 TDD 方案多数时候排名更高，而且它列出的设计缺陷在我看来是有道理的。但数据集当然太小，无法得出任何确定的结论。（如果有人有时间和 token 来做更大规模的实验，那会非常有意思！）

当人先写测试时，这迫使我们在实现之前思考用法，我们必须忍受在知道如何构建之前就规定行为和期望的那种摩擦。智能体不会经历这种摩擦，它可以在规划实现的同一瞬间写出测试。如果两者之间没有一个人工检查点，先写测试真的还剩下什么意义吗？

### 小步前进 >> YAGNI（你不会需要它）

只写足以通过下一个测试的代码，讲的是克制。它本应阻止我们去构建抽象，或处理还没有人要求的情况。

**在智能体循环中还能实现吗？**

这是一个非常以人为中心的好处，当智能体自己做 TDD 时就丢失了。我们不再身处那种摩擦之中——在那种摩擦中，我们真的必须思考所构建之物的所有细节。理论上，这种思考正在转移到我们编写交给智能体的规格说明的时候，但在那里我们没有一种类似 TDD 的机制，让我们小步地把规格想清楚。

但智能体难道不能以那样的小步工作，并在发现可能不必要的东西时向我们提问吗？根据我的总体经验，它们不太擅长这个。在实验中也是如此，要求最小实现的指令并不能可靠地阻止它们构建更多东西。它们经常超额实现，做了超出当前测试要求的内容，因为它们手握完整的需求。我们通常不会把规格一条一条地喂给它们，那样效率太低了。

### 小步前进 >> 快速、局部化的反馈

一次只迈一小步意味着，当测试失败时，我几乎能确切知道是什么导致的，因为自上一次绿灯状态以来唯一的变化，就是你刚写的那一处。

**在智能体循环中还能实现吗？**

这个实验设置没有显示智能体在使用与不使用 TDD 时，陷入调试困境的频率是否有差异。但根据我的总体经验，即使没有经过小而审慎的步骤，智能体通常也相当擅长弄清楚一个测试为什么变红。对于它们确实卡住的那些时候，我仍然怀疑能否通过小步 TDD 有意义地缓解，以及整体的成本收益比较是否站得住脚。

### 小步前进 >> 信心与学习

在 Kent Beck 为《测试驱动开发》（Test-Driven Development: By Example）所写的前言中，他提出 TDD 最大的理由是“管理恐惧”。他说，对难题的合理恐惧会让开发者畏首畏尾、更少沟通、回避反馈。有了 TDD，每个通过的测试都向我们展示了进展，所以我们可以放松下来，*知道进展已经被锁定*。测试是一种帮助我们坚持下去的心理机制。

**在智能体循环中还能实现吗？**

这在很大程度上是关于管理*人*的恐惧、允许*人*放松。当智能体在循环内部做 TDD 时，这一点无法转移，因为它不能给我像我自己一步步做时那样的掌控感和信任。

## 成本

### 至少 3 倍的 token

*详细数字见附录。*

自然地，由于 TDD 工作流需要更多的轮次和工具调用，会消耗更多的 token。不过其中很多会是缓存命中，所以请注意，3 倍或更高的 token 倍数并不直接代表成本高出多少。（遗憾的是，我在实验中没有记录缓存命中情况。）

### 提示词的维护与测试

TDD 似乎是模型并不“天然习惯”的流程。这就像是在和训练数据进行一场艰难的拉锯战，需要对提示词进行大量迭代，才能让模型在大部分时间里遵循这个流程。例如，在前几批之后，我意识到智能体在红-绿-重构循环中没做多少重构，于是修改了提示词，更加强调这一步，因为它当然是 TDD 的关键。后来我让 Opus 查看那些会话，看它是否发现重构工作有所改进。它确实报告了重构步骤的增加——但它也列出了一些案例：智能体着手重构，却认定设计已经足够好，而在 Opus 看来设计显然并不够好（例如，所有东西都实现在一个大模块里，但显然可以拆分成多个职责）。

TDD 是一套相对复杂、变量众多的指令，因此智能体对它的理解也有很多变化。所以我猜想，这类提示词在不同模型之间会比简单指令更加不稳定，这意味着需要投入精力，才能让提示词在不同模型和模型版本之间持续有效。

## 我的结论

我认为目前总体上有越来越多的证据表明，对我们希望模型*如何*做某件事规定得过于具体，并不是一种可持续的方法。相反，我们应该尽可能多地找到监控结果和给予反馈的方法。这种反馈应尽可能自动化，而我们需要仔细思考，在哪里把自己作为好坏对错的裁决者插入进去。

尽管我知道我这个小评估远远不能代表对 TDD 有效性的广泛看法，但它确实没有给我任何新的迹象表明所有这些努力是值得的。尤其是在我们能找到其他方式实现 TDD 大部分好处的情况下。

我个人已经不再让我的编程智能体先写测试了，更不用说做 TDD（说实话我从来没这么做过），直到我看到能说服我的评估或其他有力论据为止。我正试着转而关注在智能体循环之外使用 TDD 时的好处，并探索实现这些好处的替代方法。

### 如何获得好的回归测试？

*……以便现有功能出问题时，智能体和我都能得到信号*

我仍然在乎扎实的回归测试，因为尽管智能体当然可能以错误的方式修复红色测试，但至少红色测试给了它一个反馈信号，让它复查可能被破坏的既有需求。我借助变异测试来监控和改进回归质量，而不是给出详尽的 TDD 指令然后听天由命。

### 如何把定期重构纳入流程？

*……以便代码库保持易于修改*

重构仍然至关重要，但传统 TDD 的小步方式似乎不是在智能体循环中进行重构的高效或有效方式。触发重构的几个例子：让智能体使用静态代码分析；定期审查结构和模块化；建立团队仪式，以保持对代码库的良好理解并及早发现偏移；留意每次变更所涉及文件数的趋势，以及每次变更所用 token 数的趋势。

### 如何获得信心？

*……以便我不怕推送到生产环境*

最难的问题依然存在：我们如何获得 TDD 曾经给我们的那种信心，如何管理恐惧，如何锁定进展？我对此没有明确的答案，但我想提一个看起来不错的基础构件：我最近尝试了 Ivett Ördög 倡导的“已批准场景”（Approved Scenarios）方法。用我自己的话说（别拿这个来要求她），它是一种半手动测试，由为每个应用专门定制的测试运行器提供支持。这个运行器以一种便于思考的方式向我展示功能测试场景，并允许我在彻底确认之后，在运行器中“冻结”这些期望（场景/测试夹具）。今后每当这些被冻结的期望被违反时，我都必须重新批准它们。我的同事 Matteo Vaccari 在这里对他使用这种方法的经验做了很好的概述。

无论将来最终是什么给了我们对软件的信任和信心——我认为我们所熟知的 TDD 的角色，已经比生成式 AI 出现之前小得多了。
