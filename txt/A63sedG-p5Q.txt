Cursor 团队工程师 Lauren Tan 与产品负责人 Roshan Sadanani 在访谈中，系统解析了自主 Agent 产品 GrokBot 的架构设计、Grok 4.6 的基准评测表现，以及多 Agent 范式对软件工程流程与开发者角色的深层重构。核心研判指出，Agent 的普及不仅不会导致软件工程被取代，反而促使工程师角色转变为数字团队管理者与高标准代码架构师，带来更大的工程协同需求。

两人先讲 GrokBot 的来历。它最早是一个小团队给自己做的原型，后来在公司内部"找到了产品市场契合"：从销售、运营到工程、产品，几乎每个岗位的人都找到了用法。原因一是它能无缝接入大家已经在用的工具，二是每个 bot 都有自己的电脑，你不在电脑前它也照样干活。Cursor 惯例先在内部工程团队深度验证，再推向外部。Roshan 说设计的出发点就是"保持简单"：很多 AI 应用功能强大，代价却是复杂；Cursor 本身面向专业开发者，到处是旋钮，而 GrokBot 想回答"如果 agent 更像同事会怎样"：你不会盯着同事问他在调用什么工具，而是像跟人一样聊天，需要时看一眼他的屏幕。所以界面借鉴了即时通讯模式。它的想法也来自 Lauren 那个出名的 Slack bot "Benny"：一个以小狗为头像、在她睡觉时自动修 bug 的持久 bot。由此衍生出让每位成员自主定义 Agent 身份、计算环境与例行工作流的设计理念。

现场演示里，Roshan 让他的"幕僚长" bot 去询问负责网购的 bot "Shoppie" 最近买了什么，又让刚配好的营销 bot 登录他的 LinkedIn，几十秒内就发出了一条宣传帖，还 @ 对了 MTS Live 的账号；接着让幕僚长从内部频道"GrokBot wins"收集好评、做成 Figma 幻灯片。Lauren 则让幕僚长把当天发现的 bug 分派给她的 GrokBot 团队，这些 bot 再去启动 Cursor 云端 agent，各自在自己的电脑上干活，最后交回 PR、视频和截图给她审查。她说现在每次有人提 GrokBot 反馈，她的 bot 都会自动去修，她只审代码，自己"几乎成了数字同事们的经理"；Roshan 补充说 GrokBot 很大一部分就是用 GrokBot 做出来的。

谈及工程范式演进，核心在于极速压缩从构想到工程实现的交付管道，利用协同 Agent 群按架构标准输出成果。Lauren 说工程师的新职责，一是当 agent 的经理，二是让代码库保持在 PM 和设计师也能提交高质量代码的状态，例如投入重构乃至重写，把规则和风格指南变成会让 CI 失败的 lint 硬约束，让"不那么聪明的 agent"也能做好。她自己几乎一个人完成的几次大规模迁移，过去需要一个团队几个月乃至几年。她再次用"米其林厨房"作比：她不再亲手做每道菜，而是用技能和重构"训练"出一支 agent 团队，自己像主厨一样摆盘、把控质量。主持人观察到，外界以为 agent 会让工程师失业，现实里需求却比以往更大；两人都认同，原型成本大降，但品味依然需要人。

关于接下来的计划，Roshan 说会根据大量测试反馈继续打磨 GrokBot，并继续在前沿模型上投入；Lauren 最关心性能和可靠性，还透露自己早期曾"偷偷黑进"过 iMessage 支持，可以直接给 bot 发短信。这是常见需求，团队在考虑之中，因为同事不该只能在 Slack 里找到。最后谈 Grok 4.6 的成绩：在 CursorBench 3.2 上，Grok 4.6 extra high 得分 70.8%，平均每个任务 2.81 美元；Fable 5 Max 得分 70.5%，却要 17.32 美元。在模型选型上，开发团队既看重 Grok 的高性价比与响应速度，也会结合任务复杂度混合调度 Fable 等前沿模型。Roshan 说同样 20 美元预算，单任务成本降下来就能做更多事、开更多 bot，所以他们会在效率上大量投入，同时不放松智能。这种算力经济学直接拉平了初创团队与大厂在复杂原型验证上的资源鸿沟。
