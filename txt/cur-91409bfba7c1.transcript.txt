UI 工程的要素

2018 年 12 月 30 日

在上一篇文章里，我谈到了承认自己的知识盲区。你可能会以为我是在建议大家安于平庸。并不是！这是一个很宽广的领域。

我坚信你可以“从任何地方开始”，不需要按照某种特定的顺序学习技术。但我也非常看重积累专长。就我个人而言，我最感兴趣的一直是构建用户界面。

我一直在琢磨，自己到底真正懂什么、又认为什么有价值。当然，我熟悉几门技术（比如 JavaScript 和 React）。但从经验中得来的更重要的教训很难捉摸，我从来没尝试把它们写成文字。这是我第一次尝试把其中一些整理出来并加以描述。

关于技术和库的“学习路线图”有很多。2019 年哪个库会流行？2020 年呢？该学 Vue 还是 React？Angular 呢？Redux 还是 Rx 呢？需要学 Apollo 吗？REST 还是 GraphQL？很容易迷失。万一作者说错了呢？

我在学习上最大的突破都不是关于某项特定技术的。相反，我学得最多的时候，是在苦苦解决某个具体 UI 问题的时候。有时候，我后来才发现有能帮上忙的库或模式；另一些时候，我会想出自己的解决办法（有好的，也有坏的）。

正是理解问题、试验解决方案、运用不同策略这三者的结合，带来了我人生中最有收获的学习经历。这篇文章只关注问题本身。

如果你做过用户界面，很可能至少遇到过下面的部分挑战，无论是直接处理，还是借助某个库。不管哪种情况，我都鼓励你写一个不用任何库的小应用，试着复现并解决这些问题。这些问题都没有唯一正确的解法。学习来自探索问题空间、尝试各种可能的取舍。

- 一致性。你点击一个“赞”按钮，文字更新为：“你和另外 3 位朋友赞了这条帖子。”再点一次，文字又变回去。听起来很简单。但也许屏幕上有好几个地方都有这样的标签；也许还有别的视觉提示（比如按钮背景）需要改变；之前从服务器取回、悬停时显示的“点赞者”名单现在也应该包含你的名字；如果你跳转到另一个界面再回来，这条帖子不应该“忘记”它被赞过。光是本地的一致性就带来了一系列挑战。而其他用户也可能修改我们正在显示的数据（比如给我们正在看的帖子点赞）。我们如何让屏幕上不同地方的同一份数据保持同步？又该如何、在何时让本地数据和服务器保持一致，反过来呢？

- 响应性。人们只能在有限的时间内容忍自己的操作得不到视觉反馈。对于手势和滚动这类连续操作，这个时限很低（哪怕只跳过一个 16 毫秒的帧，都会让人觉得“卡顿”）。对于点击这类离散操作，有研究表明，用户会觉得任何小于 100 毫秒的延迟都一样快。如果某个操作耗时更长，我们就需要显示一个视觉指示器。但这里有一些反直觉的挑战：会让页面布局“跳动”的指示器，或者要经历好几个加载“阶段”的指示器，会让操作感觉比实际更久。同样，以掉一帧动画为代价在 20 毫秒内处理完交互，可能比在 30 毫秒内处理完且不掉帧感觉更慢。大脑不是基准测试。我们如何让应用对不同类型的输入都保持响应？

- 延迟。计算和网络访问都需要时间。有时如果计算成本不影响目标设备上的响应性，我们可以忽略它（一定要在低端设备上测试你的应用）。但处理网络延迟是不可避免的，它可能要好几秒！我们的应用不能干等着数据或代码加载而卡住。这意味着任何依赖新数据、新代码或新资源的操作都可能是异步的，需要处理“加载中”的情况。而几乎每个界面都可能出现这种情况。我们如何优雅地处理延迟，而不显示“一连串”的加载转圈或空白的“洞”？如何避免布局“跳动”？又如何在改变异步依赖时，不必每次都给代码“重新接线”？

- 导航。我们期望界面在交互时保持“稳定”，东西不应该在我们眼皮底下消失。导航无论是由应用内部发起（比如点击链接），还是由外部事件引起（比如点击“返回”按钮），也都应该遵守这个原则。例如，在个人资料页的 /profile/likes 和 /profile/follows 两个标签之间切换，不应该清空标签视图之外的搜索框。即使是跳转到另一个界面，也像是走进一个房间：人们期望稍后回来时，东西还是自己离开时的样子（也许多了些新东西）。如果你正浏览到信息流的中间，点进某人的个人页再返回，丢失在信息流中的位置，或者要等它重新加载，都是很让人沮丧的。我们如何设计应用架构，使它能处理任意的导航而不丢失重要的上下文？

- 陈旧。我们可以通过引入本地缓存，让“返回”导航瞬间完成。在缓存里，我们可以“记住”一些数据以便快速访问，即使理论上可以重新获取。但缓存也带来自己的问题：缓存会过时。如果我改了头像，缓存里的头像也应该更新；如果我发了新帖子，它需要立刻出现在缓存里，否则缓存就需要失效。这可能变得很困难、很容易出错。如果发帖失败了怎么办？缓存在内存里保留多久？重新获取信息流时，我们是把新获取的信息流和缓存的“拼接”起来，还是扔掉缓存？分页或排序在缓存中如何表示？

- 熵。热力学第二定律大致是说“随着时间推移，事物会变成一团乱”（好吧，并不完全是这样）。这一点同样适用于用户界面。我们无法预测用户确切的交互及其顺序。在任何时刻，我们的应用都可能处于数量多得令人难以置信的状态之一。我们尽最大努力让结果可预测，并受我们的设计约束。我们不希望看着一张 bug 截图纳闷“这是怎么发生的”。对于 N 种可能的状态，它们之间有 N×(N−1) 种可能的转换。例如，如果一个按钮可能处于五种不同状态之一（正常、激活、悬停、危险、禁用），那么更新按钮的代码就必须对 5×4=20 种可能的转换都正确，或者禁止其中一些。我们如何驯服可能状态的组合爆炸，让视觉输出可预测？

- 优先级。有些事情比别的更重要。一个对话框可能需要在物理上出现在弹出它的按钮“之上”，并“突破”其容器的裁剪边界。一个新安排的任务（比如响应点击）可能比一个已经开始的长时间任务（比如渲染屏幕下方的后续帖子）更重要。随着应用不断变大，由不同的人和团队编写的各部分代码，会争夺处理器、网络、屏幕空间和包体积预算等有限资源。有时你可以把竞争者放在一个共同的“重要性”尺度上排序，比如 CSS 的 z-index 属性，但结局很少是好的。每个开发者都倾向于认为自己的代码很重要。而如果一切都重要，那就什么都不重要！我们如何让彼此独立的组件相互合作，而不是争夺资源？

- 无障碍。无法无障碍访问的网站并不是一个小众问题。例如，在英国，每五个人中就有一人受到残障影响（这里有一张不错的信息图）。我自己也有切身体会。虽然我才 26 岁，但我已经很难阅读字体纤细、对比度低的网站了。我尽量少用触控板，也害怕有一天不得不用键盘去浏览那些实现得很糟糕的网站。我们需要让我们的应用对有困难的人来说不那么糟糕，好消息是有很多唾手可得的改进。这要从教育和工具开始，但我们也需要让产品开发者能轻松地做正确的事。我们能做些什么，让无障碍成为默认，而不是事后补救？

- 国际化。我们的应用需要在全世界运行。人们不仅说不同的语言，我们还需要以最少的产品工程师工作量支持从右到左的布局。我们如何在不牺牲延迟和响应性的前提下支持不同的语言？

- 交付。我们需要把应用代码送到用户的电脑上。用什么传输方式和格式？这听起来可能很直接，但这里有很多取舍。例如，原生应用往往会预先加载全部代码，代价是巨大的应用体积；Web 应用的初始载荷往往更小，代价是使用过程中更多的延迟。我们如何选择在哪个环节引入延迟？如何根据使用模式优化交付？要得到最优方案，我们需要什么样的数据？

- 容错。如果你是昆虫学家，你可能喜欢虫子（bug），但你大概不喜欢在自己的程序里看到它们。然而，你的一些 bug 不可避免地会进入生产环境。那时会发生什么？有些 bug 会导致错误但定义明确的行为，比如你的代码在某些条件下显示了错误的视觉输出。但如果渲染代码崩溃了呢？那我们就无法有意义地继续下去，因为视觉输出会不一致。渲染一条帖子时发生的崩溃，不应该“拖垮”整个信息流，或者让它进入一种半坏的状态，进而引发更多崩溃。我们如何编写代码，把渲染和数据获取的失败隔离开，让应用的其余部分继续运行？对用户界面来说，容错意味着什么？

- 抽象。在一个很小的应用里，我们可以硬编码很多特殊情况来应对上述问题。但应用往往会不断变大。我们希望能够复用、分叉和合并代码的各个部分，并集体协作开发。我们希望在不同的人所熟悉的部分之间划出清晰的边界，并避免让经常变化的逻辑过于僵化。我们如何创建能隐藏某个 UI 部分实现细节的抽象？又如何避免在应用增长的过程中，重新引入我们刚刚解决的那些问题？

当然，还有很多问题我没有提到。这份清单绝非详尽无遗！例如，我没有谈到设计师与工程师的协作，也没有谈到调试和测试。也许下次再说。

读这些问题时，人们很容易在心里想着某个视图库或数据获取库作为解决方案。但我鼓励你假装这些库都不存在，再从这个角度重读一遍。你会如何着手解决这些问题？在一个小应用里试试吧！（我很想在 GitHub 上看到你的实验，欢迎发推回复我。）

这些问题有意思的地方在于，它们中的大多数在任何规模上都会出现。无论是在输入提示（typeahead）或工具提示（tooltip）这样的小组件里，还是在 Twitter 和 Facebook 这样的巨型应用里，你都能看到它们。

想一个你喜欢用的应用里不简单的 UI 元素，对照这份问题清单过一遍。你能描述出它的开发者做了哪些取舍吗？试着从零开始重现类似的行为！

我通过在不用库的小应用里试验这些问题，学到了很多关于 UI 工程的东西。我向任何想更深刻地体会 UI 工程中各种取舍的人推荐同样的做法。
