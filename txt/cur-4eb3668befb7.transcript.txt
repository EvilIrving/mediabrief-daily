主持人（开场）：AI 辅助编程早已远远超出了自动补全。大语言模型如今已经能够编辑整个代码库、协调长时间运行的任务，并在多个系统之间协作。随着这些能力日趋成熟，软件开发的核心挑战正在从编写代码，转向编排工作、管理上下文，以及在成群的智能体之间维持共同的理解。

Steve Yegge 是一位软件工程师、作家和业内老兵，他的文章影响了许多开发者对自身工作的看法。过去一年里，Steve 一直在探索软件开发的前沿，打造了 Beads 和 Gas Town 等工具，用来试验多智能体协同、共享记忆以及 AI 驱动的软件工作流。

在本期节目中，Steve 与 Kevin Ball 一起讨论了 AI 编程的演进：从基于聊天的辅助到完整的智能体编排；管理智能体集群在技术和认知上的挑战；任务图、基于 Git 的账本等概念如何改变工作的本质；以及这些变化对软件团队、工具和行业未来意味着什么。

Kevin Ball，也就是 KBall，是 Mento 的工程副总裁，也是面向工程师和工程管理者的独立教练。他曾联合创办两家公司并担任 CTO，创立了圣迭戈 JavaScript 聚会，并通过 Latent Space 组织 AI in Action 讨论小组。欢迎查看节目说明，在 Twitter 或 LinkedIn 上关注 KBall，或访问他的网站 kball.llc。

所以我见过很多东西，经历过很多次变革之类的。我是在亚马逊开始写博客的，因为当时我想弄明白怎样才能说服一个有 800 名工程师的组织，让他们接受某些事情——我觉得他们在那些事情上的想法是错的。于是我开始吐槽，结果越来越受欢迎，然后，我也说不清，这就成了我的标志了，对吧，博客吐槽，那种"醉酒博客吐槽"。其实我九年多以前就戒酒了，正在向十年不喝酒迈进。

Kevin Ball：但你把吐槽保留下来了。

Kevin Ball：好的。我今天很兴奋能和你聊的原因之一是，我觉得在你的吐槽里，你是把我们行业当下正在发生的变革最前沿讲出来的人之一。我们不妨先梳理一下这段演进，我很想听你讲讲你当时一步步的想法。我想回到——我记得你有一篇博客文章，指出了我们当时开始看到的一种模式，你称之为 CHOP，也就是"面向聊天的编程"（chat-oriented programming），那是 2024 年的事吧，我记得。那是你开始接触大语言模型的起点吗，还是更早还有别的？

Steve Yegge：还要更早。我是说，你看，ChatGPT 3.5 刚出来的时候，我就震惊于它能写出相当不错的 Emacs Lisp 函数，对吧。我是说，只是单个函数，那差不多就是它能力的极限了，但我还是觉得：哇，Emacs Lisp，那可是相当冷门的边缘场景了，对吧。所以，我也说不清。

我觉得聊天那个阶段大概是我第一次开始觉得自己像吃错了药一样，没人听我的。因为今天大家都在用聊天，光是 Claude Code 那批人，现在占开发者的多少，10%、15%？20% 还是更少？它在增长，对吧，但我是说，大多数人仍然在用聊天。而整个 2024 年我都在努力让人们去用聊天，对吧？他们却说：不，补全接受率。你还记得那个指标吧？

Kevin Ball：记得。据我所知 VS Code 现在还在盯着它。

Steve Yegge：哇。嗯，我是说，可能确实还有开发者在用补全。所以，是啊，我开始有点觉得自己能看见未来了，对吧。因为，我也说不清，你看，当你干了 40 年这行，追求了 40 年的生产力，一直在努力让自己更快，你就会对自己什么时候变快了有一种感觉，对吧。所以，是的，路上有很多减速带，AI 会做错很多事情，诸如此类，但那种感觉就像是，我也说不清，就像在《塞尔达》游戏里找到了早期的悬浮摩托，你还没有电池，但它还是比走路快。每个人都抱怨悬浮摩托老是坠毁，但我想说，伙计，它比走路快，你现在就得用它。而从那以后它一直在变得更好，对吧。

所以，Claude Code 把聊天放进了循环里，对吧——聊天是把提问放进了循环，然后 Claude Code 把聊天放进了循环，Gas Town 又把 Claude Code 放进了循环，Geoffrey Huntley 的 Ralph Wiggum 也是这样。所以我们看到的基本上就是：AI 乘以更多的 AI，再乘以更多的 AI，这就是一切问题的解决方案。而这真的让人们很恼火，对吧。

Kevin Ball：是的，Hacker News 上的帖子之类的。

Steve Yegge：对吧。

Kevin Ball：嗯，我想我们会聊到这个。不过我很好奇，沿着这条路，你说 GPT-3.5 是第一次让你开眼，突然间滑板车比走路快了。这一路上对你来说还有其他转折点吗？

Steve Yegge：下一个转折点非常明确是 GPT-4o，对吧。因为在那之前，我们在构建只内置了聊天的编程智能体时——我们会做复制粘贴之类的操作，对吧——一直苦恼的是，一旦一个文件长到大约 800 行，它们在修改时就没法很好地忠实复现原文件了，对吧。有点像现在 Nano Banana 编辑它自己生成的东西时，会开始变得模糊。所以转折点在于，4o 能够完美忠实地复现一个一千行的文件，同时只做一行或者一个字符的修改。这非常重大，因为世界上大多数源文件都在一千行代码以内，或者说本该如此。所以这时候我们谈论的就是：GPT 能够编辑世界上所有的文件并做简单修改了。就在那时，我立刻——我甚至没意识到那还是在去年之前，对吧，那是 2024 年中，2024 年中后期我想——就已经是：哦，你可以刷这个了。你知道，我是个游戏玩家，我是说，拜托，立刻把一切游戏化。

然后下一个，Sonnet 3.7 又来了一次，那时候就是：哦，哇，对吧。那就是 Claude Code。那是我史上最火的一条推文，大概 30 万次浏览之类的，我就说了句"哦，Claude Code 挺不错的"。然后是 Opus 4.5。下一个大的是什么呢，对吧？这一个就是让 Gas Town 得以发布的那个。没有 Opus 4.5 它就发布不了，对吧，是 Opus 4.5 让它起飞的。

如果你一直在数的话，Anthropic 模型的"半衰期"在 2025 年初大约是每四个月一个新模型，而现在已经缩短到大约每两个月一个，所以我们很可能很快就会看到 Opus 5 发布了，对吧。所以那些唱反调的人——我是说，我们会聊到的——但就你问的这些转折点来说，很多现在看着这个问题并且不以为然的人，他们的视野大约只有以今天为中心前后三个月的窗口。他们只回看大约三个月，看上一代模型是什么样子，而他们并不太了解艾萨克·牛顿是怎么发明微积分的。如果你把镜头拉近，对吧，他们正处在一段非常陡峭的坡上，而他们看不见。他们只看到导数。所以正在发生的事情是，我从 ChatGPT 3.5 起就有这样的看法——其实是在 40 年的加速中一直如此——而现在我看到它开始极快地加速，Opus 4.5 就是那一下水花，是砸进池塘的那块大石头，人们开始意识到，它现在根本不需要再变得更聪明了。

Kevin Ball：完全正确。我在某种程度上也有类似的历程。我会说，大约从 Sonnet 3.5 开始，我们就到了这样一个阶段：至少我开始说，你知道吗，就算他们再也不发布新模型，我们只是不断学习如何使用它们、围绕它们打造工具，软件工程的世界也已经永远改变了。它可能没法进入某些领域，3.5 和 3.7 有它们的局限，它们能啃下的山头有一定大小，你得把事情拆成那个大小才能用它们，但这是可行的。而现在有了 4.5，那座山的尺寸变得大多了，而且显然还会继续变大。

Steve Yegge：所以我是说，你看，我们面对的是一个新世界。我是说，发明 Redis 的那个人，antirez 还是叫什么来着，你看到他的帖子了吗？就在几周前他有了这样的领悟，他用 Opus 4.5 和 Claude Code 干活之后说：嗯，我们再手写代码已经没有任何意义了。而这真的、真的是——这就是整个行业现在必须吞下的那颗大药丸，对吧？

Kevin Ball：是的，我想消化其中的含义会是一段有意思的时光。不过我们不妨看看当下这个时刻处于什么状态。我会说，在这段演进中，正如你强调的，当前的门槛是我们如何在成群的智能体之间进行协调，不管它们是并行工作，还是串行地去做一系列不同的事情。你在这方面做了一些项目，所以我们不妨从 Beads 开始。如果我没记错的话，那才是三个月前的事。

Steve Yegge：没错，三个月前。

Kevin Ball：它确实非常受欢迎，也有一堆相关的概念。不过我们先聊聊 Beads 吧。它们是什么？作为我们所处的这个智能体集群世界里的一种基础原语，它是什么？

Steve Yegge：好的，我不知道你有没有看到，昨天 Anthropic 发布了一个更新，他们废除了 To-dos，对吧，推出了 Tasks，并称其受到了 Beads 的启发，我觉得他们这样做非常友好。我也理解他们为什么不直接用 Beads，对吧，这个我们可以聊。不过基本上，Beads 是一个任务追踪器，就像给你的智能体用的更好的待办清单，但它有三个特性，让它变得非常非常有意思。

其一，它是一个图。它是一个任务图，非常像你的工作图、你的实施计划、你的甘特图，以及你通常管理知识工作的方式。所以它有点意外地具备了这样一种能力：把所有工作都拆成微小的单元，拆成会随着认知能力的提升而真正可扩展的小块。所以 Beads 很有意思的一点是，它们只不过是把工作划分成一个图，这件事我们一直都在做，只不过——

是的，还有两个要素。你加上 SQL。我是说，图和数据库一直结合得不太好，但人们已经为此努力了 40 年，现在已经相当不错了，它就是一堆节点和边。所以，对，你加上 SQL，数据库喜欢 SQL——

Kevin Ball：数据库喜欢 SQL，大语言模型也喜欢。你只要跟它说"用 SQLite 来追踪你的思考，开始吧"，就能接近到令人吃惊的程度。

Steve Yegge：你可以，对吧。但 Beads 引入了一些我们人类大概永远不会加进去、也想不到的图的边。Claude 参与设计了 Beads，正因如此，它包含了一些 AI 觉得非常重要、而且一直在用的东西，比如"discovered-from"（发现自），它会告诉你这个 bead 被打开的时候是谁在做什么。它们很喜欢这个，用来做取证，用来理解工作是如何展开的。因为 Beads 是工作在执行过程中的那个"曲面"：所有已关闭的 bead，也就是曲面下方的积分，是你已经完成的工作；所有未关闭的 bead 是剩余的工作；而 Beads 本身大体上追踪的就是那个曲面。

所以，是的，让它变得完全神奇的第三个组成部分是 Git。它是你所有工作的一本 Git 账本。所以你已经把工作拆成了一口大小、可寻址、可以相互引用的小块，它有图结构，可以用数据库查询，而且全都在一本 Git 账本上。这一点有用得惊人，因为你永远不会丢失它们，历史永远都在，出了问题你总能重建，对吧。而且还不止于此，因为你实际上可以开始查看这些账本，判断智能体随着时间推移表现得如何，你甚至可以在账本上看到你自己的工作，它就像一份便携的简历，真是太疯狂了。所以 Beads 是一个非常有意思的发现。

Kevin Ball：是的，我觉得其中几个部分值得深挖。不过我们不妨先从概念上说起。对于一个习惯了写代码、管理工作的开发者来说，如果我们先停留在 Beads，还不谈 Gas Town——

Steve Yegge：好的。

Kevin Ball：如果你开始和你的智能体一起使用 Beads，作为开发者你要做出什么样的认知转变？

Steve Yegge：嗯，如果你已经在用智能体了，那它大概已经在用待办清单和 Markdown 文件了。不然你还会用什么呢？也许你有个 Wiki 或者数据库。好吧，所有这些方案的问题在于它们没有 Git。或者你用的是 Markdown，也用了 Git，那问题在于它没有一个能在数据库里查询的图结构，大语言模型每次查看时都得读取和解析那些 Markdown 文件才能得到那个图结构，而且这些文件会过时，等等。所以，如果你在用智能体，而且真的在深度依赖它，那么你一试 Beads——你真的只要试一下就行——人们从世界各地联系我，KBall，伙计，他们每天都来联系我。就在两天前，一个同事跟我见面，他说：我开始用 Beads 了，嗯，它带来了巨大的解锁，但我不明白为什么，对吧。原因是，它对大语言模型来说就像猫薄荷，就像糖果，它就是它们的记忆。一旦它们明白了它能提供什么，它们就只想用它，你要是想把它拿走，它们还会有点生气，对吧。

因为你再也不会丢失任何工作了。你知道大语言模型是什么样的，它们专注于你交给它们的那件事，它们会注意到"哦，顺便说一下，你另一个房间着火了，但那不太是我的问题，所以我就专注于这件事吧"，对吧。它们会撇清工作，会说"是一个跟我完全无关的人把构建搞坏的"，其实就是它们自己在上一个会话里干的，对吧。有了 Beads 这种事就不必再发生了，因为它们会说：哦，我看到这是个问题，我给它记一个 bead，对吧？

你可以看到这和智能体编排是怎么联系起来的。因为当你不断堆积 bead 时，你就在堆积一份工作待办列表，而你可以——我是说，取决于这个 bead 的规格写得有多好，因为如果你愿意，可以在 bead 里写规格说明，有各种字段、评论、设计之类的，对吧——所以如果这是一项规格写得很清楚的工作，你就可以把它交给自动化，交给一个智能体，让它直接去做，再让另一个智能体做代码审查，然后签入，就完事了，对吧。我是说，只要它通过了所有测试就行。

所以你可以看到，人们正在把 Beads 当作智能体编排的底层基础。它是一种记忆，一种共享记忆，通过 Git 实现联邦化，这意味着它对你的智能体来说就像一个分布式数据库，不管你跑在 AWS、GCP 还是哪个超大规模云上，对吧，Azure 也行。它们都能通过 Beads 相互通信，你不需要一个中心化的托管服务，一切都通过你的 Git 仓库进行，太疯狂了。

Kevin Ball：不，这绝对很疯狂。说到通过 Git，我还没看过 Beads 的实现。你本质上是把 bead 存在比如 SQLite 里，所以它就在文件系统里，还是你有某种专有接口？你实际上是怎么把它管理进 Git 的？

Steve Yegge：所以，一个任务图，它在 SQL 里，但它也在 Git 里。

Kevin Ball：那它就只是 SQLite 文件吗？

Steve Yegge：对。我做了最蠢的那种事，就是我完全没做任何调研，我没意识到这东西会这么有用。我想要 Git，Claude 想要 SQL，所以我们决定用最糟糕的方式把它们硬塞到一起，对吧。有一个 JSONL 文件，每个 issue 一行，它一天到晚都有合并冲突，然后被吸进数据库里，还有一个守护进程，而且数据会变得陈旧，作为一个两层架构它糟透了。在下一个版本里这一切都会消失，新版本大概这个周末就会发布，对吧。要是我当初做了调研，我就会意识到，我需要的是一个 Git 数据库。我需要一个数据库，我也需要 Git，我需要有版本的数据集，对吧。结果发现有人已经解决了这个问题，就是 Dolt 团队。

Kevin Ball：（笑）

Steve Yegge：你笑了。我知道这个——嗯，我之前不知道，不过结果创办 Dolt 的 Tim Sehn 也是我在亚马逊时的一个小伙伴，对吧，我也有朋友在那儿工作，而我之前根本不知道他们有这个东西。不过，是的，Beads 会切换到它上面，它会把一切都修好。

Kevin Ball：那确实——我是说，我见过很多人用 SQLite，但它和 Git 一起用的挑战也是合并冲突，对吧，到处都是合并冲突。

Steve Yegge：所以，是的，有一个 Git 原生的数据库，我是说，三方合并就没了，bd sync 没了，守护进程没了，这一整套都没了。你仍然有 Git 导出，你仍然有联邦化，Dolt 的联邦化方式和 Beads 的完全一样。很奇怪，就好像我在追随他们的脚步，对吧，但他们做得是对的，而且他们投入了十年，它还可以嵌入 Go 程序，所以恰好可以嵌入到 Beads 里，对吧。所以这只会是一次很小的变动，你甚至都不会注意到，它只会变得更好。而且它还能实现一大堆东西，比如字段级别而不是 issue 级别的合并冲突解决，还有各种新的历史记录，以及一些我们之前没法得到的、新的维度上的视角。还有键值存储之类的，人们开始用 Beads——Beads 是一个数据平面，伙计，它是一个数据平面，太疯狂了。人们就像——有一位贡献者加了一个键值存储，我看着它，努力想弄明白它，然后我觉得：对，如果你有智能体把它当作记忆来用，这完全说得通，对吧，它们想要能够共享东西，并且有一种可靠的方式去查找，诸如此类。

Kevin Ball：是的，是的。
