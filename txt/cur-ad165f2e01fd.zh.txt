我喜欢和设计师合作，部分原因是（与管理者和产品经理不同）他们在文化上与工程师不同。然而，一个团队里有不止一名设计师就是自找麻烦，而我对设计系统有着复杂而负面的看法。

设计是个奇怪的岗位

设计师能立刻展示自己的价值。做某个功能时，我通常会先拼出一个自己还算满意的占位 UI。然后我拿给设计师看，对方摸着下巴说：“嗯，我在这里有些想法。”接着他们走开，做出一个界面设计稿，不仅明显更好，而且好在我根本想象不到的地方。科技公司里没有其他任何岗位能让你一眼就看出价值。

设计师在其他方面也是个不寻常的岗位。工程经理、产品经理和工程师大体上都出自同一类人：技术型、注重细节的计划者。我们是电子表格一族。事实上，许多管理者和产品经理都曾是工程师：这是很自然的转变。设计师则不然。我确信这样的人存在，但我从没遇到过任何工程师出身的设计师。

因此，设计师在文化上与工程师距离很远。以我的经验，这是很大的优点。我以前抱怨过，曾经是工程师的产品经理往往更糟，而不是更好。一旦你开始试图私下做自己的技术评估，而不是设法信任你的工程团队，你就注定要失败：你不可能做得足够好，而你试图这样做的本身，就会让你无法建立所需的信任。设计师完全没有这个问题¹。

一次一个设计师

到目前为止，我把设计师说得像中土世界的精灵：神秘的生灵在科技公司里飘来飘去，施展魔法。事实上，他们更像是斯拉夫的家宅精灵，也就是多莫沃伊（Domovoy）。一户人家如果有一个多莫沃伊，它会保护你的家免遭不幸。一旦你有了不止一个，它们就会激烈争斗：“弄出各种声响、弄伤牲畜、把主人从床上赶下来、趁人睡着时掐住人的脖子，等等。”同样，一名设计师能把你的粗糙产品变得真的很美——但你最好只有一名设计师，否则就是自找麻烦。

我与设计师合作过的最糟经历，是在一个我们有三名设计师的产品上：最初只有一名，后来轮岗离开项目，由两位非常资深的设计师接替。就我判断，最初的设计相当不错。不幸的是，新来的设计师并不这么认为。他们做的第一件事就是把产品彻底重新设计，这意味着我不得不重写大部分前端样式。然后他们开始彼此意见不合。我觉得产品的每个页面我们都返工了三四次：一个设计师让我改 X，另一个又把它改回去，如此反复。与此同时，我正拼命想让产品能跑起来。

理论上我知道自己该做什么：把所有人叫到一个房间里互相谈，敲定一个决定。也许在需求更稳定的另一个产品上，这本来会奏效，但在这里行不通。品味上的差异虽然在我看来难以察觉，却实在太深了。似乎设计师 A 做出的每样东西，在设计师 B 眼里都稍有不对，反过来也一样。最后我们只是硬撑着实现²每一个新迭代，直到截止日期前大约一周，我才请来上下两级管理层撑腰³，把设计冻结在当时的状态。

这些人真的是非常优秀的设计师！他们在设计上比我强得多得多，而且是非常好的人，我很乐意再次与他们合作。我只是认为，一次与不止一名设计师合作本质上就是糟糕的。我在不同的团队和公司一次又一次遇到这种情况。对于原因我只能猜测⁴，但有两个理论：

工程分歧可以围绕延迟、缺陷、代码行数等具体的质量指标来定夺，而设计师只能依靠品味。

任何地方的设计改动都会影响整个产品，因为用户把产品当作一个整体设计来体验；而许多工程选择对用户不可见（因此可以放心地不一致）。

灵活性与设计系统

公司试图扩大设计工作规模的一种方式，是制作一套“设计系统”：一个前端组件库，其中所有组件都符合设计规范，理论上可以像乐高积木一样拼装成页面，看起来与公司其他部分保持一致。我讨厌设计系统。然而，就像民主一样，在我见过的所有用于强制实现一致设计的方法中，它们是最好的。

设计系统的第一个问题是激励问题。拥有设计系统⁵的工程团队有动力做出永远看起来漂亮的优雅组件。使用设计系统的工程团队则有动力做出能满足不优雅甚至难看客户需求的系统。于是就有了一场持久的拉锯战：产品团队要求某个功能——比如能够把任意图片嵌入下拉组件——而设计团队则因为担心它会显得难看而抵制。

我上面描述的那种动态（设计师往往彼此意见不合）会让情况糟糕得多。工程团队里的驻场设计师常常会争取某种与设计系统略有不同的设计，这（a）让设计系统的所有者非常不满，（b）也让工程师不满，因为必须把组件折磨成一种只有细微差别的外观。

这个问题的结果是，工程团队永远在想方设法绕过设计系统：重新实现自己版本的组件、用 CSS 深入修改现有组件的样式（这些修改又会在每次组件更新时被破坏），等等。

这引出了第二个问题：兼容性。设计系统通常用最新最潮的前端框架编写，但公司实际的前端代码总是各种技术和版本的大杂烩，更新起来成本太高、风险太大。例如，你经常会遇到一套 React 设计系统被用来规划对纯 HTML 和 CSS⁶前端的改动。我人生中有好几年都在与这个确切的问题搏斗：要么你花很长时间重新实现 React 组件的某一部分，要么你尝试使用过时的纯 CSS 设计系统（如果存在的话），要么你放弃，直接把 React 组件嵌入 HTML。所有这些都因不同的原因而非常令人不快。

一种常见情况是，你能用的设计系统版本（即纯 CSS 版本，或 React 16 版本）与你设计师能用的设计系统看起来有细微差别，所以当你把乐高积木拼在一起时，并不能完全得到他们所设想的效果。这会导致一场非常乏味的对话，你必须解释：不，把整个应用升级到最新版 React 其实并不轻松⁷。当你真正实现应用时，还得在脑子里不断进行某种翻译：“好吧，设计师想要下拉功能 A，但我这个版本的设计系统里的下拉菜单只提供功能 B 和 C，那我猜 C 已经够接近了……”

我仍然认为设计系统比替代方案更好。当你版本跟得上、又没有设计师想要什么奇怪的东西时，它们非常好用。确保一个巨型应用中的一千名工程师都产出统一的 UI 是个非常难的问题，我不知道别的办法。我只是希望与我合作过的设计师能更体谅这个事实：设计系统常常让眼前的工程工作更难做。

你真的需要设计师吗？

产品开发的经典三脚凳由工程、产品管理和设计组成。设计肯定是较短的那条腿。我工作过的几乎每个团队都有某种形式的驻团队产品管理，但我工作过的团队⁸中只有大约一半能接触到某种设计支持（团队里有驻场设计师的就更少了）。为什么会这样？

部分原因是，有些产品不需要设计，或者至少不需要设计师所提供的那种视觉意义上的设计。我工作过的一些团队负责的系统没有真正的视觉组件：API、计费与对账、Markdown 或 PDF 渲染⁹。我见过公司还是把设计师安排进这些团队，出于某种认为“设计思维”能改善 API 结构的想法。这是胡说。好的 API 设计非常重要，但那是技术工作，不是审美工作。这些团队里的设计师通常只是无所事事，或者把注意力狭窄地盯在团队确实拥有的某个不重要 UI 部分上（例如某个客户永远不会看到的内部管理组件）。

另一个原因是，设计糟糕的产品仍然能用。我认为 Netlify Analytics 设计得不好：用起来别扭，而且不给我看它明明拥有的信息。但我仍然为它付费，因为我想要为我的博客提供服务器端分析。我认为没有多少人称赞过 Microsoft Azure 管理门户的美学，但 Azure 今年收入突破了 1000 亿美元。设计真正关乎业务成败的软件产品非常少。

作为一名工程师，我自私地希望能一直和设计师合作。我想做出漂亮的产品，而我无法靠自己把它们变漂亮。
