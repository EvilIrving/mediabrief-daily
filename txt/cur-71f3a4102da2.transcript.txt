messense：OK。PyO3 简单来说就是对 CPython API 的一层封装。Rust 里有一种东西叫过程宏（procedural macro），PyO3 通过过程宏把整个 CPython 的接口做了一层抽象，让你能在 Rust 中比较方便地、用比较安全（safe）的代码写一个 Python 扩展。因为在 Rust 里其实可以直接调用 CPython 的 C API，但这样会导致整个项目里全都是 unsafe 代码。所以从这一点来说，它主要是提供了一个更好的抽象。

laike9m：听你的意思，这个抽象是给 Rust 用的，是吗？就是给 Rust 调用 Python API 的抽象。

messense：对。这里有段历史可以简单说一下：PyO3 这个项目是从一个叫 rust-cpython 的项目 fork 出来的。rust-cpython 做的事情其实一样，但思路不太一样。它为了让写扩展更简单，用的不是过程宏，而是声明宏（declarative macro），很像 C 里的那种宏，就是字符替换的感觉，所以写出来会很奇怪。怎么说呢，很像在 Rust 里写 Python 代码，比如你要定义一个 class，它可能是用一种类似模式匹配的写法，写个 class 什么什么，一点也不像 Rust 代码，也不像 Python 代码，有点奇怪。

PyO3 的创建者应该是 Nikolay Kim。他最开始也用 rust-cpython，当时想通过 rust-cpython 把 Tokio 的运行时暴露给 Python 用，相当于做一个 Rust 版本的 uvloop。他在这个过程中遇到了非常多 rust-cpython 的问题，也尝试去解决，给它提了不少 PR。但因为那个项目的维护者当时不是很活跃，过了一段时间他就不想再提 PR 了，干脆自己 fork 出来，用他觉得对用户更友好的过程宏方式做了 PyO3。

laike9m：因为我们几位主播和听众可能对 Rust 不是特别熟，能不能简单介绍一下过程宏这个概念？

messense：OK。过程宏，就是在构建过程中由编译器帮你生成代码。它通过一个注解（annotation）来用，可以打个比方，很像 Python 的装饰器（decorator）。你在装饰器里也可以做很多事情，而过程宏则是由 Rust 编译器来帮你做这件事：编译器会把你加了注解的代码展开（expand），加入很多你想做的事情。比方说给一个函数增加一些简单的参数校验，或者给一个 struct 加上某些 trait 的实现，大概可以这样理解。

laike9m：细节实现我们可以之后再聊。回过头来说，PyO3 一开始相当于让 Rust 能够调用 Python API，而现阶段很多人用它来提供 Python 扩展。你觉得这是它最初的设计目的，还是后来有一些转变，大家发现原来还可以这样用？

messense：我认为这就是它最初的目标之一。其实 PyO3 现在支持两种用法：一种是我们最常见的写 Python 扩展；还有一种稍微小众一点的应用，就是可以直接嵌入（embed）一个 Python 解释器来用，你可以跑一个二进制程序，它去调 Python API，不一定非得是一个扩展模块。

laike9m：这个二进制是 Rust 写的？

messense：maturin 简单来说就是一个 PEP 517 的构建后端（build backend）。它实现了 PEP 517 的接口，能让 pip 从源码包编译出 Python wheel。除此之外，它也可以不作为构建后端，而是直接作为一个辅助程序来用。这样开发的时候不需要通过 pip 来调用它编译，还能享受 Rust 编译时增量编译（incremental compilation）这些优势。我觉得它最主要的特点是，大大简化了用 PyO3 或其他方式写的扩展的构建和分发过程。它现在几乎支持所有 manylinux 平台，Mac 也好、Windows 也好，全都支持，而且它本身也为所有这些平台发布了 wheel。

赖信涛：OK。我不太了解 PEP 517，要是用户安装一个 Rust 写的 Python 扩展，pip 会干啥呀？它会先把整个包下载下来，然后在这个过程中是不是必须先 pip install maturin，再去构建？

前面介绍了 PyO3 主要是用来用 Rust 写 Python 能调用的库。我们当然也非常好奇它的底层到底是怎么工作的。比如我之前问了一下 ChatGPT，PyO3 是不是生成了一个 C 扩展，结果发现其实不是。那请 messense 介绍一下 PyO3 到底是怎么工作的，它怎么让 Python 去调用 Rust 写的、生成的代码？

messense：OK，其实前面已经提到了一些。它首先是通过过程宏让写代码的过程变得更简单，也更安全。我举个例子：一个 Python 扩展——现在说"C 扩展"已经不太合适了——它得有一个 module，这个 module 肯定是通过 CPython 的某个 API 来创建的。在 PyO3 里，它会通过一个叫 #[pymodule] 的宏，把你写的那段关于模块怎么初始化的代码，变成供 C API 调用的过程。从本质上来说，这和你在 C API、也就是 C 扩展里的写法没什么区别，都是调用 Python 扩展的 C API 来初始化。然后你在初始化代码中可以加入更多东西，比方说添加一个 class 或者一个 function，我们通过另外几个宏，比如 #[pyclass]、#[pyfunction]，把它们注册进去，你在初始化的时候把它们加进去就好了。所以从底层原理来说，我觉得 ChatGPT 说的也不完全对。

laike9m：对，我只是把它贴在这。

messense：你不能说它是 C 扩展，但它跟 C 扩展本质上没有区别。

laike9m：OK，换句话说，它首先打包成的肯定是一个动态链接库，对吧？

messense：对的，基本上是这样。

messense：我觉得区别也不明显。因为你创建一个纯 Python 的对象，它也是通过 CPython 内部那些 API 来创建的，对吧？性能上应该区别也不大。我觉得现在 PyO3 这边性能上比较能明显感知到的地方，是从 Rust 对象转换成 Python 对象，或者 Python 对象再转换成 Rust 对象，这个开销是比较大的。至于你用 Rust 写了一个 Python 扩展之后带来的性能提升，更多是因为你的 Rust 代码比较高效，而不是因为 PyO3 做了什么让它高效。

messense：是的。所以你会遇到这种情况：你写了一个非常小的函数，传的对象可能比较复杂，你去跑 benchmark 会发现它的性能不一定好过你用纯 Python 写的，因为它主要的工作都花在对象转换的过程中了。

messense：这个都是被封装掉的。引用计数（reference count）这些，一方面 Rust 本身有所有权（ownership）这些机制，可以做一些优化；另一方面，凡是涉及 Python 对象，在整个传递过程中你肯定会对它做 incref、decref 这类操作。但整个过程都被 PyO3 封装掉了，所以绝大多数情况下你不需要关心。

赖信涛：哦，那就是在 Python 里这个对象引用计数降到零的时候，它也会被释放掉。

laike9m：OK。我之前还让 ChatGPT 写了一个 Rust 如何调用 Python C API 的例子，看上去还挺直接的，但不知道它写得对不对。
