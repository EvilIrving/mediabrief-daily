行为 harness 值得付出代价吗？

本文是系列「Exploring Gen AI」的一部分。

我对比了编码 agent 在有无行为 harness 的情况下构建同一套 API 服务。前沿模型 GPT-6 Sol 无论有无 harness，外部评测全部通过。但成本优化型模型 GPT-6 Luna，无 harness 时 10 次里只成功 3 次，有 harness 则 10 次全过。虽然给 Luna 加上 harness 会增加 token 用量和运行时间，但带 harness 的 Luna 跑次达到了与 GPT-6 Sol 相同的 10/10 可靠性，且单次成本低约 33%（0.273 美元对 0.406 美元）。这个实验表明，行为 harness 或许是一条实用路径，能让更小、更省钱的模型交出可靠结果。

2026 年 10 月 13 日

我做这个实验时，原本以为行为 harness 能帮编码 agent 更稳地满足需求、省 token、少做无用功。给 agent 清晰的架构契约，并在它写代码时提供确定性的测试反馈，看起来显然有助于它第一轮就做对实现。

对 GPT-6 Sol 来说，harness 大约多用了 10.5 倍 token，耗时接近 3 倍，费用约高 7 倍，但两种条件都在全部 10 次跑次里成功了。

结果彻底打脸了这个预期，也让我吃惊。用 Codex 搭配低推理力度的 GPT-6 Sol，agent 在 10 次跑次里每次都交出了通过全部 178 个自动化验收测试的应用，无论有没有 harness。按这个指标，harness 没有带来可观察的最终应用改进。

GPT-6 Sol（token、时间、费用的 10 次平均值）：

| Harness | Tokens | Time | Estimated cost | Accepted runs |
|---|---|---|---|---|
| Yes | 11,331,970 | 19 mins 53 secs | ~$2.679 | 10 of 10 |
| No | 1,076,371 | 6 mins 51 secs | ~$0.406 | 10 of 10 |

harness 提高了平均耗时和费用，却没有改变观察到的验收结果。在探索性跑次里，Claude Sonnet 4.6、Claude Opus 4.6 和 Gemini 3.8 Flash（均为低推理力度）也都能在无辅助时第一次就完成任务。

这些前沿模型在有无 harness 时都能稳定完成这个任务。那可执行反馈能否帮成本优化型模型达到同样稳定的结果？

先看成本型模型的结果之前，说明一下实验怎么搭的：

实验设置

借用 Birgitta Böckeler 的框架，行为 harness 由引导（guides）和传感器（sensors）组成。引导预判 agent 可能走偏的地方，在它行动前纠正方向，提高第一次做对的概率。传感器在它行动后观察结果，提供帮助它自我纠正的反馈。

对每个模型，我对比了有无行为 harness 的 agent。两种条件都从应用简报和基线仓库说明开始，各自在独立私有工作区里工作。带 harness 的 agent 还额外获得了下文「内环」一节描述的 API 规格、示例和工具。

图 1：两种开发条件及其独立评测

实验把开发与评测分成两个不同的环。内环在带 harness 的 agent 构建时提供反馈。agent 完成后，外环对其生成的服务跑 178 个自动化验收测试。两种条件面对同一套评测，内环 harness 从未接触评测套件的答案。最后我汇总验收结果、token 用量、时间和估算费用。

本实验里，只有成功启动并通过全部 178 个外部验收测试的应用才算可接受。可靠性指模型在重复跑次中产出可接受应用的一致性。token 用量、耗时和估算费用则是单独的运行效率指标。

应用简报

每次尝试都以一份详细的应用简报开场。我描述服务该做什么，但把代码级实现细节留给 agent。

任务是做一个产品发现用的 BFF（backend-for-frontend）。它要暴露面向消费者的 HTTP API，校验入站请求与下游响应，并调用 Order API。可用性搜索成功后，还只能把返回的第一个产品发布到 Kafka。如果发布每一个产品，agent 就可以原样透传数据，而不必实现选择行为。

图 2：简报描述的应用架构

简报还规定了不那么显眼的行为。超时的产品创建必须变成延迟请求：返回 202，并在响应头里放一个消费者可以轮询的链接。瞬时搜索失败必须返回带可用恢复间隔的 429；依赖不可用或事件发布失败必须变成 503；即便下游成功响应，仍须遵守请求的产品过滤条件，否则返回 502。

图 3：一次成功的可用性搜索及其 Kafka 发布

简言之，这个服务不只是一组 CRUD 端点：agent 必须同时协调 HTTP 语义、异步事件、模式边界和容错策略。

对无辅助 agent 来说，这也是一个相对友好的起点：简报把功能需求、架构与技术约束、外部接口细节、响应形态和失败行为写得异常详细。我还不清楚，简报没那么完整时结果会如何变化。

内环：行为 harness

本实验中，引导包括以机器可读形式表达接口约定的 OpenAPI 与 AsyncAPI 规格，为可执行检查提供基础。它们补充简报，而不是另立一套需求。引导里还有这些接口的请求–响应示例，覆盖下游超时、畸形载荷、过滤违规、重试序列和 Kafka 事件确认。一份 API 开发 skill 提供了实现实践，以及依赖模拟、行为验证、如何诊断并应对失败的指导。

传感器检查契约符合性，用 API 测试验证 HTTP 响应值，并断言可观察副作用，包括对下游 mock 的调用和 Kafka 发布。测试结果、CTRF 报告和 API 覆盖率报告在开发过程中把这些观察回传给 agent。

Birgitta 还区分了由确定性工具执行的计算型控制，与依赖模型解释或判断的推断型控制。这个 harness 两者都用。行为检查产生计算型反馈，不靠 LLM 判定对错。在 skill 指令引导下，agent 仍须解读这些结果，决定如何修复失败。

图 4：行为 harness 及其反馈路径

一个 agent 插件提供了 skill 和 MCP 工具，并附带契约与示例。OpenAPI 规格覆盖 BFF 与下游 Order API；AsyncAPI 规格覆盖 Kafka。

实现服务前，agent 会连同简报一起阅读规格和示例。skill 引导它梳理应用组件，并把每项所需行为关联到下游交互与验证检查。辅助脚本搭好这些文档、验证证据记录，以及构建、启动和测试服务的命令；agent 再补全行为相关细节。

配置工具把契约接到应用和依赖 mock 上。契约驱动的依赖 mock 让下游交互可执行，使 agent 能对照定义好的下游响应、失败和恢复序列演练实现。另有助手验证时序约束。这些工具合在一起，既提供实现指导，也提供 agent 可用来检查决策的可执行环境。

agent 通过项目的测试命令调用 harness。该命令校验配置与示例，跑必要的构建和单元检查，启动下游 mock，并对照它们启动应用，然后跑上述检查。

报告摘要会标出具体的契约、响应值和交互不匹配。agent 按 skill 指令诊断，改实现或执行设置，并用助手重跑受影响场景。这些场景通过后，再把完整套件当作最终门禁跑一遍。反馈环依赖 agent 在开发中主动调用这些工具；它不会在每次代码编辑后自动运行。

图 5：内环测试与反馈序列

让引导与传感器保持同步

设计这类行为 harness 的一大挑战，是确保引导和传感器不互相矛盾、不把 agent 搞糊涂。我用下面的办法应对：

跑任何测试前，「examples validate」命令会检查示例载荷是否符合各自的 API 规格。测试再用这些规格和示例检查实现，使传感器与其源头引导对齐。

这些检查的来源很重要。如果 agent 自己解读需求来同时写实现和测试，同一种误读或遗漏就可能两边都出现。允许它在测试失败时改期望结果，也会掩盖缺陷。这里，契约和示例以可执行形式代表经人类约定的期望。契约检查由所供规格确定性生成，所供示例配合行为夹具定义取值与副作用断言。agent 被要求保留这些输入和 skill 的验证助手，调查失败，并纠正实现或执行设置，而不是削弱期望。

这样，验证期望就有了独立于实现 agent 解读的来源。作为确定性计算型控制，它们让正确性可检查，而不依赖 agent 自报或 LLM 判断，从而让人把评审精力放在契约未覆盖的地方。

同一套传感器因此在不同时机承担两种角色：

- 开发期间：传感器结果作为可执行注意力反馈给 agent，引导构建并帮助它从疏漏中恢复。
- 完成时：传感器结果成为验收依据：对照人类期望独立检查 agent 的解读，这对每个模型都重要。

skill 还要求留下可审查的依赖交互证据和最终验证结果，使完成有据可查，而不只是 agent 的口头声称。

本实验里，我用 Specmatic 实现行为 harness，不过等价的契约测试与服务虚拟化工具也能提供同样能力。

外环：评测 harness

为保持比较公平，每次尝试都在隔离的 Docker 容器里跑，自有工作区和全新的、针对本次尝试的 Codex home。除共享鉴权与语言依赖缓存外，每个 agent 起步时都没有此前跑次留下的会话、记忆、插件、skill 或其他状态。

两种条件的差别在于 agent 开发时能用什么；在每组对比内部，完成的应用面对同一套外部评测。

开发结束后，外环评测 harness 用同一套 178 个组合功能检查测每个应用，包括非法输入、下游失败、恢复序列，以及成功请求产生的消息。这些检查演练简报规定的行为，包括面向客户端的 API、下游交互和 Kafka 发布。评测 harness 控制自己的下游夹具与消息捕获，而不依赖应用的开发测试。

测试成本优化型模型

OpenAI 把 GPT-6 Sol 定位为复杂专业工作的旗舰模型，而 GPT-6 Luna 针对成本敏感、高吞吐工作负载做了优化，大致对应更早 GPT-5 家族里的 nano 档。

方法就位后，核心问题是：能力画像更小的模型表现是否不同。

我对低推理力度的 GPT-6 Luna 跑了完全相同的实验。无 harness 时 10 次里成功 3 次；有 harness 则 10 次全过。

GPT-6 Luna（token、时间、费用的 10 次平均值）：

| Harness | Tokens | Time | Estimated cost | Accepted runs |
|---|---|---|---|---|
| Yes | 22,933,648 | 35 mins | ~$0.273 | 10 of 10 |
| No | 5,860,736 | 15 mins 56 secs | ~$0.086 | 3 of 10 |

在这个样本里，harness 并没有解锁 Luna 原本没有的能力；它把 3/10 的基线变成了 10/10 的可靠性。

提供这些反馈平均多花了 17,072,912 token、19 分 4 秒自主运行时间，以及约 0.187 美元的 API 等价估算费用。带 harness 的尝试整体 token 大约是无 harness Luna 的 3.9 倍。但看比较经济学：即便有 harness 开销，带 harness 的 Luna 单次仍比无 harness 的 Sol 便宜约 33%（0.273 美元对 0.406 美元），且两种条件在本样本里都达到了 10/10 验收率。

好于预期的地方

抛开标题通过率，深入看代码库，有几处实现令人印象深刻：

- GPT-6 Sol 无辅助一枪过关。
一次 /goal 提示就够了。全部 10 个无 harness 的 GPT-6 Sol 应用第一次就通过了所有功能检查，无需人工调试或纠正性跟进。

- GPT-6 Luna 独自也相当接近。
无 harness 的 GPT-6 Luna 跑次通过了 94.8% 的功能检查。它卡在细微边界情况上，而不是完全没理解任务。

- 异步 202 工作流端到端串得起来。
返回 202 Accepted 本身不难。让我吃惊的是看到 agent 接好监视端点、跟踪挂起请求、用原始幂等键重试下游创建，并在轮询 URL 上暴露最终载荷。

- Kafka 发布与搜索事务绑在一起。
可接受应用不是异步甩出一条消息再立刻返回 200，而是等 Kafka 确认后再响应，并把发布失败或超时正确翻译成 503 Service Unavailable。

- 边界校验一贯偏防守。
两个模型都会对照模式校验入站载荷，并在使用前校验下游响应结构和业务约束，而不是盲目信任下游服务。

无 harness 跑次哪里滑倒

失败的无 harness Java 应用并没有无效语法，也没有从根本上误解简报。每一个仍至少通过了 178 个组合功能检查中的 144 个。失败集中在延迟创建工作流，以及一小撮协议细节：

观察到的缺口出现在协议边界、弹性路径和集成接缝上——看起来像样的实现仍可能作为系统失败。

- 延迟创建在超时边界上断开。
下游产品创建超过配置超时时，BFF 本应返回带监视链接的 202 Accepted，在后台重试，并最终暴露下游 201 响应。结果 4 个无 harness 应用返回 503，2 个返回 400，1 个返回 429。上面已计入的另一个应用在某些场景创建了监视器，但重试从未到达终态 201。若干实现靠匹配狭窄的异常类型或 cause-chain 形状来识别超时。产物能证明响应不对，却往往不记录实际客户端异常，所以该机制只是可能解释，而非已证实的共同原因。

- 缺少监视链接导致次生失败。
在 7 次跑次中，对超时创建的错误响应也意味着没有返回监视 URL。后续评测检查在试图使用这个缺失 URL 时失败。我把这些错误当作破碎的 202 流程的后果，而不是独立的应用缺陷。

- Kafka 投递成功，契约符合性却失败。
在 3 次跑次中，每条期望消息都到了 Kafka，但评测仍拒绝发布。两个应用用了 Spring 的 JSON 序列化器，多加了意外的 __TypeId__ 头。另一个发出了 “categories”: null，尽管可选字段在出现时必须是数组。集成在机械层面工作，却仍违反线路契约。

- 错误响应未精确符合 HTTP 契约。
其他观察到的失误更窄。虽然 415 Unsupported Media Type 是不支持媒体类型的常规响应，但应用简报明确要求这类非法请求返回 400，所以评测把 415 算作契约违规。另一些情况下，非法请求落到了通用 500 处理器，缺失的监视器返回了错误表示。代码差异很小，却足以让应用在外部评测下不可接受。

- 配置名在集成接缝处分叉。
普通产品创建返回 503 而不是 201。生成的客户端读 ORDER_API_API_KEY，而记录的启动环境提供的是 ORDER_API_KEY。这个不匹配是下游失败的合理解释。在带 harness 的跑次里，契约驱动的依赖 mock 和配置检查能在部署前验证这些环境变量。

harness 作为可执行注意力

行为 harness 把书面需求变成环境反馈，在传感器变红时把漏掉的细节重新拉回焦点。

我开始用「可执行注意力」来想这种动态。

这些失败背后的行为，在所供需求里都写明了。应用简报清楚规定了延迟创建工作流、Kafka 消息契约和精确错误响应。一条需求可以在简报里很明确，却仍在实现过程中失去影响力。我把这看作注意力疏漏：结果代码省略或不完整实现了 agent 已经拿到的需求。

在不断膨胀的上下文里同时折腾库选择、样板搭建、依赖注入和异步接线，可能促成这类疏漏，不过本实验没有确定原因。可执行注意力让这些缺口可观察，给 agent 又一次按需求行动的机会。

- 超时创建不算延迟，除非响应包含监视链接，且轮询最终到达下游结果。
- Kafka 发布不能只因为消息到了就有效；载荷和头都必须符合线路契约。
- 可选字段不能序列化为 null，若契约只允许数组或省略。
- 错误响应不对，除非其状态码、内容类型和正文都匹配面向客户端的契约。

GPT-6 Sol 在所有观察到的跑次里都从书面简报保住了这些细节。GPT-6 Luna 无 harness 时也正确实现了大部分行为，但可接受结果不稳定。Luna 的失误与需求在实现中失去影响力相一致。我的解读是：harness 充当了外部记忆和注意力辅助，每当传感器变红就把漏掉的需求拉回焦点。

稳定结果的经济学

把两个模型样本并排放在一起，这种反馈的成本就看得见了。这些是基于记录的 token 用量和模型价格的 API 等价估算，不是实际账单。

图 6：两个模型的平均估算费用与时间

在 GPT-6 跑次内部，带 harness 的 Luna 平均每次约 0.273 美元，而无 harness 的 Sol 为 0.406 美元；两者都在 10 次尝试中有 10 个被接受的应用。因此在本样本里，带 harness 的 Luna 平均约便宜 33%。

全部 10 个带 harness 的 GPT-6 Luna 应用通过了外部评测，成功率 100%。这个小样本无法告诉我们长期失败率，或达成可接受应用的总成本。

这些数字只衡量自主生成成本和机器时间。它们不包括编写、评审和维护契约、示例、断言与 harness 的前期投入，也不包括发现、诊断和修复不可接受结果的精力。跨实现复用接口契约和检查可以分摊搭建成本，但我没有度量这种复用或由此产生的总成本。

Sol 的 10/10 结果仍依赖独立评测。这提示另一种比较：只在最终验证门禁时把传感器交给 agent，而不是贯穿整个开发。最终门禁工作流能提供独立验收检查，并在第一次实现就通过时把开销降到最低。不过失败仍可能需要诊断和修复循环。我没有度量那种工作流的成本。

本实验的边界

本实验覆盖每个模型 10 对配对跑次、1 个从零开始的 Java 服务，两个模型都是低推理力度。该样本描述观察到的结果；它不能确立长期可靠性。

更苛刻的架构或更刁钻的弹性场景，可能会暴露 Sol 需要 harness 的缺口。反过来，更简单的任务可能让 Luna 不靠这种行为 harness 也能稳定跑。

简报把功能行为、架构、技术和接口规定得异常详细。我还没有测试：改遗留代码、换语言或推理设置、或从含糊/不完整需求出发时，这一模式是否成立。简报更不完整，可能同时影响无辅助实现，以及供给 harness 的契约与示例质量。把这些精确数字外推到不同简报、架构、代码库或团队工作流，我会谨慎。

因为 harness 同时加入了引导和传感器，本实验也无法拆开它们各自的贡献。

实践含义

我会把这些结果当作针对特定任务选择模型和反馈节奏的起点。随模型能力变化的是传感器何时、多常运行，而不是是否需要独立检查。

模型能力改变的是传感器何时、多常运行，不是是否需要独立验证门禁。

- 对成本优化型模型：当成本型模型结果不稳定时，在整个开发过程中跑行为 harness。它充当可执行注意力，边发生边抓住漂移，把不稳定尝试变成可靠交付。
- 对前沿模型：即便模型第一次就稳定通过，仍保留独立验收检查。不必在开发中连续检查，而是在验收前把自动化测试当作确定性最终验证门禁跑一次，以最小开销提供独立检查。
- 投资清晰的规格与示例：检查只能强制人类编码进去的期望。把这些期望与实现一并评审维护，并用人工评审补覆盖缺口。

结论

我原先的假设太粗。行为 harness 并不是对每个模型、每项任务都自动划算。对 Sol 而言，贯穿开发跑 harness 增加了开销，却没有检测到验收收益；对 Luna 而言，带 harness 的尝试验收更稳，且在本样本里平均比无 harness 的 Sol 更便宜。

于是我得到一个修订后的、有条件的假设：

随模型能力变化的，不是是否需要独立传感器，而是它们何时运行。对无辅助尝试结果不稳定的模型，在开发中连续跑传感器，能提供可执行注意力，扩大团队可以成功使用的模型集合。对能一枪解决简报的前沿模型，把同一套传感器当作独立最终验收门禁跑一次，就能提供每个系统都需要的验证，而不背开发期开销。

实践中，工程团队很少只凭原始基准智力选模型。单位经济、延迟预算、数据隐私，以及能否在本地运行，往往主导决策。如果行为 harness 能把已经符合这些运营约束的更便宜、更轻的模型，拉到可靠交付，那就是很有吸引力的选项。

目前我只在单一从零服务、异常详细简报上测过。下一步是测前沿模型的「仅最终门禁」条件，度量其开销以及门禁多常抓住偏差。再往后，我打算变化简报质量和漏掉需求的后果，然后测试在改现有代码库、换编程语言或本地跑开权模型时，这一假设还站不站得住。
