棕地项目中的 agent 工程（Brownfield Agentic Engineering） ｜ Addy Osmani ｜ 文章 ｜ https://addyosmani.com/blog/brownfield-agentic-engineering/

Addy Osmani 谈怎样把编程 agent 带进历史悠久的老代码库。他的核心看法是：在棕地项目里，代码仓库已经不能完整描述系统的真实行为，大量约束藏在团队经验、临时补丁、遗留服务和别的团队的依赖里；放任 agent 上手，可能得到一个"能跑"但系统设计错误、测试脆弱的结果。所以这里的工作是把隐藏的约束显性化，让廉价的改动变得可信。

他提出几个做法。第一是分区：绿区测试充分、隔离良好，agent 可以紧密循环地干；黄区质量参差，要先写特征测试再改；红区是认证、计费、权限、薪资这类只有少数人懂的敏感部分，要么人逐步结对，要么不做。地图必须由人来画，因为让 agent 自己挑，它会直奔最吓人的文件；区域升级要靠挣来，比如补齐特征测试、模块负责人审过 agent 最初的改动。第二，自主权应该跟着影响范围、可观测性和可恢复性走，而不是看模型有多自信。agent 从代码里能推断出很多东西，没必要什么都写成 markdown 塞进上下文，只需写下代码说不出来的：业务细节、架构取舍的理由、工具没有强制的规范、领域规则、反直觉实现背后的历史。第三，让调研成果活过这次会话：对黄区和红区的工作，先做一次只读调研，产出一份引用了文件、issue 和仪表盘的简短备忘录，否则下一个 agent 还得重新"考古"；之后用干净的上下文做规划，由人选方案，发现地图有误就停，审查也要从头按验收标准倒推。第四，每一次重复的纠正都说明 harness 缺了一块：同样的审查意见再出现，就把它变成 lint 规则、钩子、类型、测试或 skill，只把无法机械执行的约束留在文字里，久而久之 harness 就成了团队决定不再重复付费的失败清单。

落地时要从零风险的工作开始：先让 agent 解释系统，再写特征测试锁定现有行为，包括那些丑陋但业务依赖的行为，而且这些测试不能由同一个 agent 会话独自完成，否则测试只会固化它刚发明的实现。Netflix 迁移 GraphQL 时用影子流量对比新旧两条路径的输出，就是同一思路。他讲了在 AOL 休假时被叫回去抢修首页的往事：几十个部门各管一块，没有完整测试，只能人工逐个验证，他认为 agent 并没有消除这种问题，只是让尝试变得更便宜。迁移要以完整单元为单位，新路径能用、旧依赖确实删掉才算完成，半拉子迁移会让 agent 看到相互矛盾的先例；有基准显示 520 次 agent 迁移只有 28 次通过全面审计。他列举了 Bun 从 Zig 移植到 Rust、Stripe 用 codemod 把 370 万行代码迁到 TypeScript、Spotify、Asana 等案例，结论是能在公司之间复用的，是围绕 agent 搭建的结构，而不是 agent 本身。
