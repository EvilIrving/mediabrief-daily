734: Web Performance with Ben Schwarz ｜ ShopTalk Show ｜ 57分钟 ｜ https://shoptalkshow.com/734/

这一期 ShopTalk Show 由 Dave Rupert 和 Chris Coyier 主持，嘉宾是 Calibre 创始人兼 CEO Ben Schwarz，他上一次上节目还是 2013 年的第 68 期。开场三人怀旧了一番，盘点当年的嘉宾如今的去向：Mike Taylor 在 Google 低调做 Web 兼容性，Hampton Catlin 转向创业，Val Head 还在 Adobe。随后话题转入 Ben 最近那篇关于航空公司网站为何如此之慢的研究。

Ben 先介绍了 Calibre。这套面向团队的 Web 性能工具已经做了近十年，提供三种视角：合成测试（持续跑 Lighthouse，可以深挖每个请求和第三方资源）、来自 Chrome 真实用户的 CrUX 数据，以及装脚本采集的真实用户监控（RUM）。所有结果都按受影响的会话数排序，打开就能看到对最多人影响最大的页面或元素。

选航空公司，是因为在 Calibre 的行业基准里，这一类差得最远，加上他最近订去日本的机票时亲身受罪：点一下想看座位，页面卡几秒，然后大面积重绘、内容位移。花两三千美元、本来就紧张的订票过程，被技术弄得更让人晕头转向。Chris 坦言，他原本以为又是在首页跑跑分的老套研究，可订票时谁在乎首屏快不快，问题出在使用过程中每次点击后的卡顿和位移。Ben 解释说，他用的正是预订引擎域名（比如 booking.qantas.com.au）的 CrUX 数据，只看核心订票流程，每个站点背后都是每月数千以上真实用户的会话。

由此展开了合成测试和 RUM 的科普。Dave 指出，在 5000 美元的 MacBook 上跑 Lighthouse 只是虚荣指标，现实中的用户用着 3G、4G、低端安卓机（他引用了 Alex Russell 的数据）。Ben 认为 Lighthouse 被误解了：分数每次不一样，恰恰反映了真实存在的差异，关键是看指标本身，不必执着于那个 100 分。Lighthouse 的价值在于大约 50 项审计清单，比如别给 LCP 图片加懒加载。RUM 成本较高，多见于大公司，但能覆盖隧道里、火车上、Wi-Fi 被 Netflix 占满等各种真实场景，还能借浏览器 API 定位导致慢 LCP、慢交互或布局位移的具体元素，按 P75 聚合，甚至发现“印度用户普遍体验很差”这类问题。Calibre 还会为每个临时会话打一个“UX 评分”。Dave 插了一段亲身经历：在信号极差的奥斯汀机场，达美的机器打印不了登机牌，网页又不让值机，被逼着下载 200 MB 的应用，差点误机，所以“一定要在机场的破网络里试用你自己的应用”。

研究数据方面：111 家航空公司里，95% 在移动端没通过核心 Web 指标，桌面端也只有 13% 通过，而 Google 的阈值其实只要求“还过得去”。更讽刺的是，Skytrax 评分越高的航司表现反而越差：排名第三的国泰航空在所有指标上垫底，LCP 10 秒、INP 1.4 秒，而它一年有 2800 万乘客。三类指标里最差的是交互。订一次票要经过 5 到 20 次交互，所谓“单页应用加载完就快”是个谬论，日历组件尤其糟糕：一打开就卡住，取完数据才绘制，价格随后才冒出来。数据慢可以理解，页面卡死和位移却是纯粹的前端问题。Chris 认为这不该怪 React，而在于使用框架时的选择。Ben 补充说 Calibre 本身也是 React 应用，同样要处理动态数据，所以框架不能当借口。三人还吐槽了骨架屏：尺寸和真实内容对不上、会闪烁，而且常常是设计稿里没有、事后才补上的。Chris 甚至认为骨架屏等于“承认输给了性能”。

谈到商业价值，Ben 引用 Shopify 的研究：LCP 2.5 秒的店铺比快一秒的转化率低 30%。他还讲了当年在澳航做合同工时的经历：和设计师用两个下午把酒店列表页现代化（放大图片、整理排版），A/B 测试显示转化率提高了约 10%。Chris 对“改个蓝色就涨 5%”这类 A/B 结论一向存疑，但认为真正的性能体验确实关乎真金白银，钱越多的网站反而越烂，是一种讽刺。

最后是行动建议。Ben 认为首先要监控，然后“按最差排序”：找到影响最多人的最差页面、元素、慢查询或接口，一次只修一件，修一点也当天合并，再看下一个。他在 Calibre 里就是这样一个个消除骨架屏位移的。很多修复其实很简单：布局位移只是 CSS 层面的问题；details、dialog、popover、锚点定位和可自定义 select 等原生能力，可以替代那些动辄十几层 div 的重型 UI 库，代码更少，还自带键盘支持和无障碍。Chris 吐槽有的站点要加载 850 个资源、89 MB 的 JavaScript。Dave 赞同“温水煮青蛙”式的渐进改进：喊着“拿掉 React”会招来组织阻力，而“修好骨架屏闪烁”配一段前后对比的 GIF，谁都会支持。Ben 收尾说，别陷入技术圣战，要看结果、以用户为重；团队没有性能文化，就从小改动做起，把前后数据贴进拉取请求、分享给同事，以此带动大家。
