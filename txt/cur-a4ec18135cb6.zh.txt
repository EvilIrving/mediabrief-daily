揭秘：GitHub Agentic Workflows 的安全架构

GitHub Agentic Workflows 以隔离、受约束的输出和全面的日志记录为基础构建。了解我们的威胁模型和安全架构如何帮助团队在 GitHub Actions 中安全地运行 agent。

无论你是开源维护者还是企业团队的一员，早上醒来看到文档修复、新的单元测试和重构建议，都可能是一个真正的“啊哈”时刻。但自动化也引出了一个重要的担忧：你如何给能够访问你的仓库和互联网的 agent 设置护栏？你会不会怀疑你的 agent 依赖了某个可疑网站上的文档，或者推送了一个包含 API 令牌的提交？如果它某天决定给每个未关闭的 issue 都加上一条噪音评论呢？自动化必须是可预测的，才能提供持久的价值。

但是，把 agent 加入 CI/CD 这样的现有自动化中，最安全的方式是什么？agent 是非确定性的：它们必须消费不可信的输入，对仓库状态进行推理，并在运行时做出决策。让 agent 在没有实时监督的情况下在 CI/CD 中运行，可以让你扩展软件工程的规模，但也需要新颖的护栏，以免你制造出安全问题。

GitHub Agentic Workflows 运行在 GitHub Actions 之上。默认情况下，一个 action 中的所有东西都运行在同一个信任域里。失控的 agent 可以干扰 MCP 服务器、访问认证密钥，并向任意主机发起网络请求。一个有 bug 或遭到提示注入、又能不受限制地访问这些资源的 agent，可能会以出乎意料且不安全的方式行事。

这就是为什么安全被融入了 GitHub Agentic Workflows 的架构之中。我们把 agent 的执行视为 CI/CD 模型的延伸，而不是一个独立的运行时。我们把开放式的编写与受管控的执行分开，然后把工作流编译成一个带有明确约束的 GitHub Action，这些约束包括权限、输出、可审计性和网络访问。

这篇文章解释我们如何从第一天起就以安全为念构建 Agentic Workflows，先从威胁模型及其所需的安全架构讲起。

威胁模型

Agentic workflows 有两个特性改变了自动化的威胁模型。

第一，agent 能够对仓库状态进行推理并自主行动，这使它们很有价值，但也意味着默认不能信任它们，尤其是在存在不可信输入的情况下。

第二，GitHub Actions 提供了一个高度宽松的执行环境。对于确定性的自动化来说，共享信任域是一个特性，它带来了广泛的访问能力、可组合性和良好的性能。但当与不可信的 agent 结合时，单一信任域可能会在出问题时造成很大的爆炸半径。

在这个模型下，我们假定 agent 会试图读写它不应该读写的状态，通过非预期的渠道通信，并滥用合法渠道执行不希望发生的操作。默认情况下，GitHub Agentic Workflows 以考虑了这一威胁模型的严格安全模式运行，其设计遵循四条安全原则：纵深防御、不把密钥托付给 agent、暂存并审查所有写操作，以及记录一切。

纵深防御

GitHub Agentic Workflows 提供了一个分层的安全架构，由底座层、配置层和规划层组成。每一层都通过强制执行与其假设一致的不同安全属性，来限制其上层故障造成的影响。

底座层建立在一台 GitHub Actions 运行器虚拟机（VM）和几个可信容器之上，这些容器限制了 agent 能访问的资源。总体而言，底座层提供组件之间的隔离、对特权操作和系统调用的中介，以及由内核强制执行的通信边界。即使某个不可信的用户级组件被攻破，并在其容器隔离边界内执行任意代码，这些保护依然有效。

底座层之上是配置层，它包括声明式的配置产物，以及解释这些产物、以实例化安全的系统结构和连接关系的工具链。配置层决定加载哪些组件、组件如何连接、允许哪些通信渠道，以及分配哪些权限。外部签发的令牌，比如 agent 的 API key 和 GitHub 访问令牌，是界定组件对外影响的关键输入，配置控制着哪些令牌被加载进哪些容器。

最后一层防线是规划层。配置层决定存在哪些组件以及它们如何通信，但它不决定随着时间推移哪些组件处于活动状态。规划层的主要职责是创建一个分阶段的工作流，各阶段之间有明确的数据交换。下文将更详细介绍的“安全输出”（safe outputs）子系统，是安全规划的主要实例。

不把密钥托付给 agent

从一开始，我们就希望工作流中的 agent 对密钥零访问。Agentic workflows 作为 GitHub Actions 执行，其中的组件在运行器虚拟机之上共享单一的信任域。在这种模型下，agent 认证令牌和 MCP 服务器 API key 这类敏感材料存放在环境变量和配置文件中，对虚拟机里的所有进程可见。

这很危险，因为 agent 容易受到提示注入的影响：攻击者可以精心构造恶意输入，比如网页或仓库 issue，诱骗 agent 泄露敏感信息。例如，一个遭到提示注入、又能使用 shell 命令工具的 agent，可以读取配置文件、SSH 密钥、Linux 的 /proc 状态和工作流日志，从中找到凭据和其他密钥。然后它可以把这些密钥上传到网上，或者把它们编码进仓库 issue、拉取请求和评论这类面向公众的 GitHub 对象里。

我们的第一项缓解措施，是把 agent 隔离在一个专用容器中，并严格控制出口流量：互联网访问要经过防火墙，MCP 访问要经过可信的 MCP 网关，LLM API 调用要经过一个 API 代理。为了限制互联网访问，agentic workflows 在 agent 和防火墙之间创建了一个私有网络。MCP 网关运行在一个独立的可信容器中，负责启动 MCP 服务器，并独占 MCP 的认证材料。

虽然 Claude、Codex 和 Copilot 这样的 agent 必须通过经过认证的渠道与 LLM 通信，但我们避免把这些令牌直接暴露给 agent 的容器。相反，我们把 LLM 认证令牌放在一个隔离的 API 代理中，并配置 agent 通过这个代理来路由模型流量。

零密钥的 agent 需要在安全性和实用性之间做出根本性的取舍。编码类工作需要广泛访问编译器、解释器、脚本和仓库状态，但扩展容器内的环境配置会重复现有 actions 的配置逻辑，并增加必须被防火墙放行的网络目标。

因此，我们使用容器卷挂载小心地暴露宿主机的文件和可执行程序，并在 chroot 监牢中运行 agent。我们首先把整个虚拟机宿主文件系统以只读方式挂载到 /host。然后用空的 tmpfs 层覆盖选定的路径，并在以 /host 为根的 chroot 监牢中启动 agent。这种方法保持了宿主端配置的完整，同时把 agent 可写、可发现的范围限制在它完成工作所需的部分。

暂存并审查所有写操作

即使无法访问密钥，遭到提示注入的 agent 仍然可能造成危害。例如，一个失控的 agent 可能用毫无意义的 issue 和拉取请求轰炸仓库，压垮仓库维护者，或者在仓库对象中加入令人反感的 URL 和其他内容。

为了防止这类行为，agentic workflows 的编译器把工作流分解为明确的阶段，并为每个阶段定义：

- 活动的组件和权限（读还是写）
- 该阶段产出的数据产物
- 这些产物可接受的下游消费者

agent 运行时，可以通过 GitHub MCP 服务器读取 GitHub 状态，而只能通过 safe outputs MCP 服务器暂存它的更新。agent 退出后，由 safe outputs MCP 服务器缓冲的写操作会经过一套 safe outputs 分析的处理。

首先，safe outputs 允许工作流作者指定 agent 可以执行哪些写操作。作者可以选择允许哪一部分 GitHub 更新，比如创建 issue、评论或拉取请求。其次，safe outputs 会限制允许的更新数量，比如限制 agent 在一次运行中最多创建三个拉取请求。第三，safe outputs 会分析更新的内容，去除不想要的模式，比如通过输出清理移除 URL。只有通过整条 safe outputs 流水线的产物才能被传递下去，从而确保每个阶段的副作用都是明确且经过审查的。

记录一切

即使做到了零密钥和写操作审查，agent 仍然可能以非预期的方式转换仓库数据、调用工具，或者试图突破我们施加给它的约束。agent 会不择手段地完成任务，而且为此拥有一个深得出人意料的花招工具箱。如果 agent 表现出意外的行为，事后分析就需要能看清完整的执行路径。

Agentic workflows 通过在每个信任边界进行大量日志记录，把可观测性作为架构的一等属性。网络和目标层面的活动在防火墙层被记录；模型请求/响应的元数据和经过认证的请求由 API 代理捕获；工具调用由 MCP 网关和 MCP 服务器记录。我们还在 agent 容器中加入了内部埋点，审计诸如访问环境变量这类潜在的敏感操作。这些日志合在一起，支持端到端的取证重建、策略验证，以及对 agent 异常行为的快速检测。

无处不在的日志记录也为未来的信息流控制奠定了基础。每一个可以观察到通信的位置，也都是可以对通信进行中介的位置。Agentic workflows 已经支持 GitHub MCP 服务器的锁定模式，在接下来的几个月里，我们将推出更多的安全控制，根据可见性（公开还是私有）和仓库对象作者的角色，在各个 MCP 服务器之间执行策略。
